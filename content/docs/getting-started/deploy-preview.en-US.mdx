description: "Provision the Cloudflare resources, then build, verify and deploy the preview Worker."

The `preview` environment deploys a Worker named `martebizuteria-preview`, which Cloudflare serves at `https://preview.martebizuteria.pl` and at `https://martebizuteria-preview.pjborowiecki.workers.dev`, the URL the preview workflow posts on each pull request. Production deploys `martebizuteria`, which until the shop goes live is served only at `https://martebizuteria.pjborowiecki.workers.dev`; `https://martebizuteria.pl` is attached at go-live.

`preview` in `wrangler.jsonc` attaches its custom domain through `routes` with `custom_domain: true`, `production` keeps its `routes` empty until the shop goes live on `martebizuteria.pl`, and both set `workers_dev: true`, because Wrangler would otherwise turn the `workers.dev` hostname off for a Worker with routes, and the deploy's live-site check asks that hostname. Preview's custom domain is the host besides `workers.dev` that `HOSTS_BY_MODE` in `src/modules/_core/constants/api.ts` accepts for auth, email links and the Stripe return URL. `HOSTS_BY_MODE` already accepts `martebizuteria.pl` for production, but nothing serves it yet. `src/modules/_core/constants/__test__/api.test.ts` fails when preview's `routes` and hosts disagree, or when production's `routes` is not empty. No `www` hostname is attached: `APP_URL`, and with it every canonical link, is the bare `https://martebizuteria.pl`.

## Provision the resources

`bun run deploy:preview` starts with `scripts/verify-bindings.ts`, which reads the same JSONC that Wrangler reads and throws unless six bindings resolve — `DB`, `CACHE`, `IMAGES`, `AUDIT_LOG_QUEUE`, `NEWSLETTER_QUEUE` and `REALTIME_INVALIDATION_HUB`; it does not check `ASSETS` — and the consumer of each producer queue names a dead-letter queue that the Worker consumes too. So provision first:

```sh
bunx wrangler login
bunx wrangler d1 create martebizuteria-preview
bunx wrangler kv namespace create martebizuteria-cache-preview
bunx wrangler r2 bucket create martebizuteria-preview
bunx wrangler r2 bucket dev-url enable martebizuteria-preview
bunx wrangler queues create martebizuteria-audit-log-preview
bunx wrangler queues create martebizuteria-audit-log-preview-dlq
bunx wrangler queues create martebizuteria-newsletter-preview
bunx wrangler queues create martebizuteria-newsletter-preview-dlq
```

Then put the ids into `wrangler.jsonc`, under both `development` and `preview` if you want them to share resources as the committed configuration does:

| Field                                  | Where                                                                                                                  |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `d1_databases[].database_id`           | `env.development` and `env.preview`                                                                                    |
| `d1_databases[].database_name`         | The same two                                                                                                           |
| `kv_namespaces[].id`                   | The same two                                                                                                           |
| `r2_buckets[].bucket_name`             | The same two                                                                                                           |
| `queues.producers[].queue`             | Must match `queues.consumers[].queue`                                                                                  |
| `queues.consumers[].dead_letter_queue` | Each producer queue's consumer names its `-dlq` queue, which has a consumer of its own: four consumers per environment |

The preview bucket starts empty, while the preview database points at the seed and marketing images. Copy them into it before the first deploy and set `VITE_R2_URL` to the address `dev-url enable` prints, as [Image delivery](/docs/guides/image-delivery) describes.

Keep the binding names exactly as they are — `DB`, `CACHE`, `IMAGES`, `AUDIT_LOG_QUEUE`, `NEWSLETTER_QUEUE`, `REALTIME_INVALIDATION_HUB`, `ASSETS` — and keep `migrations_dir` pointing at `./src/integrations/drizzle-orm/migrations`. The binding names are what `src/types/worker-configuration.d.ts` is generated from and what the whole server layer is typed against.

The Durable Object needs no provisioning. It is created by the migration already in the file:

```jsonc
"migrations": [
  {
    "tag": "v1",
    "new_sqlite_classes": ["RealtimeInvalidationHub"],
  },
],
```

Here is exactly what `verify-bindings.ts` insists on, so you know when you are done. `audit` and `newsletter` are the `AUDIT_LOG_QUEUE` and `NEWSLETTER_QUEUE` producers, and `hasDeadLetterConsumer` holds when the queue has a consumer that names a `dead_letter_queue` the Worker consumes too:

```ts
const consumerOf = (queue: string | undefined) => config.queues.consumers.find((consumer) => consumer.queue === queue)
const hasDeadLetterConsumer = (queue: string | undefined): boolean => consumerOf(consumerOf(queue)?.dead_letter_queue) !== undefined

if (
  !database?.database_id ||
  /^[0-]+$/u.test(database.database_id) ||
  !cache?.id ||
  /^[0-]+$/u.test(cache.id) ||
  !images?.bucket_name ||
  !audit?.queue ||
  !hasDeadLetterConsumer(audit.queue) ||
  !newsletter?.queue ||
  !hasDeadLetterConsumer(newsletter.queue) ||
  realtime?.class_name !== "RealtimeInvalidationHub"
) {
  throw new Error(`Missing database, cache, images, audit, newsletter, or realtime binding for ${environment}`)
}
```

A production deploy also throws `Production and preview share the images bucket <name>` when its `IMAGES` bucket is the one preview binds.

Note the placeholder check: an id of all zeroes and dashes is rejected, which is what stops a copied template being deployed.

### The custom domains

Wrangler attaches a custom domain only in a zone of the same Cloudflare account, so `martebizuteria.pl` has to be an active zone there before the first deploy. Cloudflare then creates the DNS record and the certificate for each hostname itself. An A, AAAA or CNAME record already on `martebizuteria.pl` or `preview.martebizuteria.pl` conflicts with the custom domain: a deploy from a terminal asks before replacing it, and a deploy from CI replaces it without asking. The zone's MX and TXT records, which the shop's mailbox and the Resend sender rely on, are not touched.

A deploy makes the Worker's custom domains match `routes`, so a hostname attached to the Worker by hand in the dashboard is detached by the next deploy; add it to `routes` instead. Besides deploying Workers, the API token needs the Workers Routes edit and Zone read permissions on the `martebizuteria.pl` zone to attach the domains.

### If you change the hostname

Three changes go with it:

- `APP_DOMAIN` in `src/presentation/branding/app.ts`, which `APP_URL`, and through it the canonical links, the OG tags and the structured data, derive from.
- `HOSTS_BY_MODE` in `src/modules/_core/constants/api.ts`. Better Auth is configured with `baseURL: { allowedHosts: appHostsForMode(import.meta.env.MODE) }`, so a host absent from that list has its auth requests rejected and sign-in fails on the new domain with no obvious error. `resolveRequestOrigin` checks the same list before it builds an email link or a Stripe return URL, so on a missing host the newsletter sign-up, the checkout and the admin's shipping and customer-deletion actions answer `FORBIDDEN` as well.
- The `routes` entry of each environment in `wrangler.jsonc`, which attaches the new hostname to the Worker as a custom domain.

## Deploy

```sh
bun run deploy:preview
```

The deploy applies the pending migrations to the preview database itself, after the build and right before `wrangler deploy`, so the new Worker never starts on a schema it does not know; a build alone applies nothing. In a terminal Wrangler asks before applying them, and answering no skips the migrations but not the deploy, so stop with Ctrl+C instead.

The domain of `RESEND_EMAIL_FROM` must also be verified in Resend before the first deploy; [Resend](/docs/integrations/resend#sender-domain) lists the DNS records. `bun run email:verify preview` runs the same check the deploy runs, on its own.

Preview takes Stripe test keys: `VITE_STRIPE_PUBLISHABLE_KEY` starting with `pk_test_` and `STRIPE_SECRET_KEY` starting with `sk_test_` or `rk_test_`. Live keys would charge a real card for every test order, so the deploy refuses them.

`deploy:preview` is eight steps chained with `&&`:

```sh
bun scripts/verify-bindings.ts preview \
  && bun scripts/verify-stripe-keys.ts preview \
  && bun scripts/verify-email-sender.ts preview \
  && bun run build:preview \
  && bun scripts/prepare-deploy-secrets.ts preview \
  && bun run db:migrate:preview \
  && env -u CLOUDFLARE_ENV vp exec wrangler deploy \
       --config dist/server/wrangler.json \
       --secrets-file .wrangler/secrets.preview.json \
  && bun scripts/verify-deployment.ts preview
```

1. **`verify-bindings.ts preview`** — the binding check above. Fails the deploy rather than warning.
2. **`verify-stripe-keys.ts preview`** — takes `VITE_STRIPE_PUBLISHABLE_KEY` and `STRIPE_SECRET_KEY` from the process environment or `.env.preview` and reads each key's mode from its prefix. A missing key, live keys, or a publishable key whose mode differs from the secret key's fails the deploy here; the message names the variables and their mode, never a key.
3. **`verify-email-sender.ts preview`** — takes `RESEND_API_KEY` and `RESEND_EMAIL_FROM` from the process environment or `.env.preview` and asks Resend whether it would send as that address. A domain that is missing from the Resend account or not verified fails the deploy here, before the build, with the DNS records still to publish.
4. **`build:preview`** — `rm -rf dist`, regenerate `.source/`, `CLOUDFLARE_ENV=preview vp build --mode preview`, then `verify-build.ts preview`.
5. **`prepare-deploy-secrets.ts preview`** — reads `secrets.required` from `wrangler.jsonc`, takes each value from the process environment or `.env.preview`, and writes `.wrangler/secrets.preview.json` with mode `0600`. A missing value throws `Missing <NAME> in .env.preview or the process environment`, and so does a blank one, except for `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID`, which may stay blank until the shop has InPost credentials. Only declared secrets are written, which is how `CLOUDFLARE_ACCESS_TOKEN` and the other management credentials stay off the Worker.
6. **`db:migrate:preview`** — `wrangler d1 migrations apply DB --env preview --remote` applies every migration file the preview database has not recorded yet. A failing migration is rolled back on its own, the ones before it stay applied, and the deploy stops before the Worker is uploaded.
7. **`wrangler deploy`** — deploys the generated `dist/server/wrangler.json` and uploads the secrets file in the same call. The generated config is flat: it already carries `"name": "martebizuteria-preview"` and `"vars": { "APP_ENV": "preview" }` at the top level with no `env` section, which is why the command unsets `CLOUDFLARE_ENV` first — with it set, Wrangler would look for an environment section that the generated file does not have.
8. **`verify-deployment.ts preview`** — asks `https://martebizuteria-preview.pjborowiecki.workers.dev` for `/`, `/products`, `/robots.txt`, `/api/webhooks/stripe` and `/api/health`, and fails the deploy unless `/` and `/products` answer `200` with HTML, `robots.txt` answers `200` as plain text, the webhook route refuses the `GET` with `405` and `/api/health` answers `200` because D1, KV and R2 answered. A page that answers wrongly is asked up to three times in all, five seconds apart.

### What the build verification catches

`scripts/verify-build.ts` reads `.wrangler/deploy/config.json`, resolves the config it points at, and then refuses to pass unless:

- the resolved path is exactly `dist/server/wrangler.json`;
- `vars.APP_ENV` equals the environment you asked for;
- the Worker name matches — `martebizuteria` for production, `martebizuteria-preview` otherwise;
- the entrypoint and `dist/client/fonts` both exist;
- `assets.directory` resolves to `dist/client`;
- `dist/client/assets` contains at least one `.js` and one `.css` file;
- no client `.js` asset imports `cloudflare:workers` or any `node:` builtin.

That last one is the interesting check. It scans each client bundle with `Bun.Transpiler` and fails on a server-only import that leaked into the browser graph — the class of mistake that otherwise shows up as a blank page in production.

## Automatic deployments

| Workflow                | Trigger                                       | Environment  |
| ----------------------- | --------------------------------------------- | ------------ |
| `ci.yml`                | Pull requests, and pushes to `main`           | none         |
| `deploy-preview.yml`    | Pull requests to `main`                       | `preview`    |
| `deploy-production.yml` | `ci.yml` passing for a push to `main`; manual | `production` |
| `e2e-full.yml`          | Pushes to `main`, Mondays 03:15 UTC, manual   | none         |
| `e2e-reusable.yml`      | Called by `ci.yml` and `e2e-full.yml`         | none         |

Both deploy workflows use `.github/actions/setup`, then `touch .env.<env>` and run the deploy script with every value supplied through the job environment. The preview workflow runs `bun run check` first; the production workflow starts only once `ci.yml` has passed for a push of the same commit to `main` and deploys it only while it is still the tip of `main`, or by hand for such a commit, see [CI/CD](/docs/tooling/ci-cd). `verify-stripe-keys.ts`, `verify-email-sender.ts` and `prepare-deploy-secrets.ts` prefer `process.env` over the file, so the empty file is intentional — it exists only so the `readFile` call in `prepare-deploy-secrets.ts` succeeds.

The preview workflow finishes by posting or updating a comment on the pull request with the preview URL. Concurrency is keyed per pull request for preview and globally for production, with `cancel-in-progress: false` on production so two pushes to `main` cannot race.

### Required GitHub configuration

Repository **secrets**:

`CLOUDFLARE_ACCESS_TOKEN` (passed to Wrangler as `CLOUDFLARE_API_TOKEN`), `CLOUDFLARE_ACCOUNT_ID`, `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `INPOST_API_TOKEN`, `INPOST_ORGANIZATION_ID`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and optionally `RESEND_MANAGEMENT_API_KEY`, which `verify-email-sender.ts` uses to read the sender domain's DNS records and which is never uploaded. The two InPost secrets may be empty; the order page then explains how to ship by hand.

The **E2E (full)** workflow also reads `E2E_STRIPE_SECRET_KEY` and `E2E_STRIPE_PUBLISHABLE_KEY`, the test keys of a separate Stripe sandbox. Both are set, so its Stripe test-mode job pays by card, BLIK and Przelewy24 in every run; see [Testing](/docs/tooling/testing#stripe-test-mode).

Repository **variables**:

`VITE_R2_URL` and `VITE_STRIPE_PUBLISHABLE_KEY`. Both are inlined into the client bundle at build time, so they must be variables rather than secrets. `VITE_R2_URL` differs between preview and production, so set it as an environment variable of the GitHub `preview` and `production` environments, which overrides a repository variable of the same name.

## After deploying

The deploy's last step has already asked the new Worker for the home page, the product listing, `robots.txt`, the Stripe webhook route and the health check. When it fails, the new version is live but not answering like the shop; [Roll back a deploy](/docs/guides/roll-back-a-deploy) covers what to do.

Register the provider callbacks for the new host, as listed in [Environment variables](/docs/getting-started/environment-variables): `/api/auth/callback/google` and the Stripe endpoint at `/api/webhooks/stripe`, which is `https://preview.martebizuteria.pl/api/webhooks/stripe` on preview and, until the shop goes live, `https://martebizuteria.pjborowiecki.workers.dev/api/webhooks/stripe` in production. Create each endpoint on API version `2026-09-30.endive`, the `STRIPE_API_VERSION` in `src/integrations/stripe/stripe.constants.ts`, and enable the ten events the handlers cover: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `payment_intent.payment_failed`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, `refund.failed` and `refund.updated`. The current endpoints are `we_1URCKtKoub4YqqV84bxHLS0D` for preview and `we_1URCUkJhNVr9Gkhk2gFlLYQD` for production; older endpoints, including those on the previous `dahlia` API version, are disabled. Stripe issues a different signing secret per endpoint, so the preview and production `STRIPE_WEBHOOK_SECRET` values differ. The endpoint's host does not decide where the order confirmation links: it links to the address the checkout was made on, taken from the session's `return_url`.
