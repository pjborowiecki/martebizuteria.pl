The `preview` environment deploys a Worker named `martebizuteria-preview`, which Cloudflare serves at `https://preview.martebizuteria.pl` and at `https://martebizuteria-preview.pjborowiecki.workers.dev`, the URL the preview workflow posts on each pull request. Production deploys `martebizuteria`, served at `https://martebizuteria.pl` and at `https://martebizuteria.pjborowiecki.workers.dev`.

Each of the two environments in `wrangler.jsonc` attaches its custom domain through `routes` with `custom_domain: true` and sets `workers_dev: true`, because Wrangler would otherwise turn the `workers.dev` hostname off for a Worker with routes, and the deploy's live-site check asks that hostname. The custom domains are the hosts besides `workers.dev` that `HOSTS_BY_MODE` in `src/modules/_core/constants/api.ts` accepts for auth, email links and the Stripe return URL, and `src/modules/_core/constants/__test__/api.test.ts` fails when the two disagree. No `www` hostname is attached: `APP_URL`, and with it every canonical link, is the bare `https://martebizuteria.pl`.

## Provision the resources

`bun run deploy:preview` starts with `scripts/verify-bindings.ts`, which reads the same JSONC that Wrangler reads and throws unless all five bindings resolve. So provision first:

```sh
bunx wrangler login
bunx wrangler d1 create martebizuteria-preview
bunx wrangler kv namespace create martebizuteria-cache-preview
bunx wrangler r2 bucket create martebizuteria
bunx wrangler queues create martebizuteria-audit-log-preview
```

Then put the ids into `wrangler.jsonc`, under both `development` and `preview` if you want them to share resources as the committed configuration does:

| Field                          | Where                                 |
| ------------------------------ | ------------------------------------- |
| `d1_databases[].database_id`   | `env.development` and `env.preview`   |
| `d1_databases[].database_name` | The same two                          |
| `kv_namespaces[].id`           | The same two                          |
| `r2_buckets[].bucket_name`     | The same two                          |
| `queues.producers[].queue`     | Must match `queues.consumers[].queue` |

Keep the binding names exactly as they are — `DB`, `CACHE`, `IMAGES`, `AUDIT_LOG_QUEUE`, `REALTIME_INVALIDATION_HUB` — and keep `migrations_dir` pointing at `./src/integrations/drizzle-orm/migrations`. The binding names are what `src/types/worker-configuration.d.ts` is generated from and what the whole server layer is typed against.

The Durable Object needs no provisioning. It is created by the migration already in the file:

```jsonc
"migrations": [
  {
    "tag": "v1",
    "new_sqlite_classes": ["RealtimeInvalidationHub"],
  },
],
```

Here is exactly what `verify-bindings.ts` insists on, so you know when you are done:

```ts
if (
  !database?.database_id ||
  /^[0-]+$/u.test(database.database_id) ||
  !cache?.id ||
  /^[0-]+$/u.test(cache.id) ||
  !images?.bucket_name ||
  !audit?.queue ||
  !config.queues.consumers.some(({ queue }) => queue === audit.queue) ||
  realtime?.class_name !== "RealtimeInvalidationHub"
) {
  throw new Error(`Missing database, cache, images, audit, or realtime binding for ${environment}`)
}
```

Note the placeholder check: an id of all zeroes and dashes is rejected, which is what stops a copied template being deployed.

### The custom domains

Wrangler attaches a custom domain only in a zone of the same Cloudflare account, so `martebizuteria.pl` has to be an active zone there before the first deploy. Cloudflare then creates the DNS record and the certificate for each hostname itself. An A, AAAA or CNAME record already on `martebizuteria.pl` or `preview.martebizuteria.pl` conflicts with the custom domain: a deploy from a terminal asks before replacing it, and a deploy from CI replaces it without asking. The zone's MX and TXT records, which the shop's mailbox and the Resend sender rely on, are not touched.

A deploy makes the Worker's custom domains match `routes`, so a hostname attached to the Worker by hand in the dashboard is detached by the next deploy; add it to `routes` instead. Besides deploying Workers, the API token needs the Workers Routes edit and Zone read permissions on the `martebizuteria.pl` zone to attach the domains.

### If you change the hostname

Three changes go with it:

- `APP_DOMAIN` in `src/presentation/branding/app.ts`, which `APP_URL`, and through it the canonical links, the OG tags and the structured data, derive from.
- `HOSTS_BY_MODE` in `src/modules/_core/constants/api.ts`. Better Auth is configured with `baseURL: { allowedHosts: appHostsForMode(import.meta.env.MODE) }`, so a host absent from that list has its auth requests rejected and sign-in fails on the new domain with no obvious error. `resolveRequestOrigin` checks the same list before it builds an email link or a Stripe return URL, so on a missing host the newsletter sign-up, the checkout and the admin's shipping and customer-deletion actions answer `FORBIDDEN` as well.
- The `routes` entry of each environment in `wrangler.jsonc`, which attaches the new hostname to the Worker as a custom domain.

## Deploy

```sh
bun run deploy:preview
```

The deploy applies the pending migrations to the preview database itself, after the build and right before `wrangler deploy`, so the new Worker never starts on a schema it does not know; a build alone applies nothing. In a terminal Wrangler asks before applying them, and answering no skips the migrations but not the deploy, so stop with Ctrl+C instead.

The domain of `RESEND_EMAIL_FROM` must also be verified in Resend before the first deploy; [Resend](/docs/integrations/resend#sender-domain) lists the DNS records. `bun run email:verify preview` runs the same check the deploy runs, on its own.

Preview takes Stripe test keys: `VITE_STRIPE_PUBLISHABLE_KEY` starting with `pk_test_` and `STRIPE_SECRET_KEY` starting with `sk_test_` or `rk_test_`. Live keys would charge a real card for every test order, so the deploy refuses them.

Preview takes Cloudflare's always-passing Turnstile testing keys: `VITE_TURNSTILE_SITE_KEY` `1x00000000000000000000AA` and `TURNSTILE_SECRET_KEY` `1x0000000000000000000000000000000AA`, the values in `.env.example`. They pass every visitor, so preview's checkout has no real bot check; a widget's own keys also work, as long as the site key and the secret key are of the same kind.

`deploy:preview` is nine steps chained with `&&`:

```sh
bun scripts/verify-bindings.ts preview \
  && bun scripts/verify-stripe-keys.ts preview \
  && bun scripts/verify-turnstile-keys.ts preview \
  && bun scripts/verify-email-sender.ts preview \
  && bun run build:preview \
  && bun scripts/prepare-deploy-secrets.ts preview \
  && bun run db:migrate:preview \
  && env -u CLOUDFLARE_ENV vp exec wrangler deploy \
       --config dist/server/wrangler.json \
       --secrets-file .wrangler/secrets.preview.json \
  && bun scripts/verify-deployment.ts preview
```

1. **`verify-bindings.ts preview`** — the binding check above. Fails the deploy rather than warning.
2. **`verify-stripe-keys.ts preview`** — takes `VITE_STRIPE_PUBLISHABLE_KEY` and `STRIPE_SECRET_KEY` from the process environment or `.env.preview` and reads each key's mode from its prefix. A missing key, live keys, or a publishable key whose mode differs from the secret key's fails the deploy here; the message names the variables and their mode, never a key.
3. **`verify-turnstile-keys.ts preview`** — takes `VITE_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` from the process environment or `.env.preview` and fails the deploy when one is missing or when a testing key is paired with a widget's key; production additionally refuses the testing keys.
4. **`verify-email-sender.ts preview`** — takes `RESEND_API_KEY` and `RESEND_EMAIL_FROM` from the process environment or `.env.preview` and asks Resend whether it would send as that address. A domain that is missing from the Resend account or not verified fails the deploy here, before the build, with the DNS records still to publish.
5. **`build:preview`** — `rm -rf dist`, regenerate `.source/`, `CLOUDFLARE_ENV=preview vp build --mode preview`, then `verify-build.ts preview`.
6. **`prepare-deploy-secrets.ts preview`** — reads `secrets.required` from `wrangler.jsonc`, takes each value from the process environment or `.env.preview`, and writes `.wrangler/secrets.preview.json` with mode `0600`. A missing or blank value throws `Missing <NAME> in .env.preview or the process environment`. Only declared secrets are written, which is how `CLOUDFLARE_ACCESS_TOKEN` and the other management credentials stay off the Worker.
7. **`db:migrate:preview`** — `wrangler d1 migrations apply DB --env preview --remote` applies every migration file the preview database has not recorded yet. A failing migration is rolled back on its own, the ones before it stay applied, and the deploy stops before the Worker is uploaded.
8. **`wrangler deploy`** — deploys the generated `dist/server/wrangler.json` and uploads the secrets file in the same call. The generated config is flat: it already carries `"name": "martebizuteria-preview"` and `"vars": { "APP_ENV": "preview" }` at the top level with no `env` section, which is why the command unsets `CLOUDFLARE_ENV` first — with it set, Wrangler would look for an environment section that the generated file does not have.
9. **`verify-deployment.ts preview`** — asks `https://martebizuteria-preview.pjborowiecki.workers.dev` for `/`, `/products`, `/robots.txt` and `/api/webhooks/stripe`, and fails the deploy unless `/` and `/products` answer `200` with HTML, `robots.txt` answers `200` as plain text and the webhook route refuses the `GET` with `405`. A page that answers wrongly is asked up to three times in all, five seconds apart.

### What the build verification catches

`scripts/verify-build.ts` reads `.wrangler/deploy/config.json`, resolves the config it points at, and then refuses to pass unless:

- the resolved path is exactly `dist/server/wrangler.json`;
- `vars.APP_ENV` equals the environment you asked for;
- the Worker name matches — `martebizuteria` for production, `martebizuteria-preview` otherwise;
- the entrypoint and `dist/client/fonts` both exist;
- `assets.directory` resolves to `dist/client`;
- `dist/client/assets` contains at least one `.js` and one `.css` file;
- no client `.js` asset imports `cloudflare:workers` or any `node:` builtin.

That last one is the interesting check. It scans each client bundle with `Bun.Transpiler` and fails on a server-only import that leaked into the browser graph — the class of mistake that otherwise shows up as a blank page in production.

## Automatic deployments

| Workflow                | Trigger                                       | Environment  |
| ----------------------- | --------------------------------------------- | ------------ |
| `ci.yml`                | Pull requests, and pushes to `main`           | none         |
| `deploy-preview.yml`    | Pull requests to `main`                       | `preview`    |
| `deploy-production.yml` | `ci.yml` passing for a push to `main`; manual | `production` |

Both deploy workflows use `.github/actions/setup`, then `touch .env.<env>` and run the deploy script with every value supplied through the job environment. The preview workflow runs `bun run check` first; the production workflow starts only once `ci.yml` has passed for a push of the same commit to `main` and deploys it only while it is still the tip of `main`, or by hand for such a commit, see [CI/CD](/docs/tooling/ci-cd). `verify-stripe-keys.ts`, `verify-turnstile-keys.ts`, `verify-email-sender.ts` and `prepare-deploy-secrets.ts` prefer `process.env` over the file, so the empty file is intentional — it exists only so the `readFile` call in `prepare-deploy-secrets.ts` succeeds.

The preview workflow finishes by posting or updating a comment on the pull request with the preview URL. Concurrency is keyed per pull request for preview and globally for production, with `cancel-in-progress: false` on production so two pushes to `main` cannot race.

### Required GitHub configuration

Repository **secrets**:

`CLOUDFLARE_ACCESS_TOKEN` (passed to Wrangler as `CLOUDFLARE_API_TOKEN`), `CLOUDFLARE_ACCOUNT_ID`, `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `AUTH_GITHUB_CLIENT_ID`, `AUTH_GITHUB_CLIENT_SECRET`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `TURNSTILE_SECRET_KEY`.

Repository **variables**:

`VITE_R2_URL`, `VITE_STRIPE_PUBLISHABLE_KEY`, `VITE_TURNSTILE_SITE_KEY` and `VITE_APP_URL`. The first three are inlined into the client bundle at build time, so they must be variables rather than secrets. `VITE_APP_URL` is passed by both workflows but is not read anywhere in `src/` and is not a declared Worker secret — see [Environment variables](/docs/getting-started/environment-variables).

## After deploying

The deploy's last step has already asked the new Worker for the home page, the product listing, `robots.txt` and the Stripe webhook route. When it fails, the new version is live but not answering like the shop; [Roll back a deploy](/docs/guides/roll-back-a-deploy) covers what to do.

Register the provider callbacks for the new host, as listed in [Environment variables](/docs/getting-started/environment-variables): `/api/auth/callback/google`, `/api/auth/callback/github` and the Stripe endpoint at `/api/webhooks/stripe`, which is `https://preview.martebizuteria.pl/api/webhooks/stripe` on preview and `https://martebizuteria.pl/api/webhooks/stripe` in production. Stripe issues a different signing secret per endpoint, so the preview and production `STRIPE_WEBHOOK_SECRET` values differ. The endpoint's host does not decide where the order confirmation links: it links to the address the checkout was made on, taken from the session's `return_url`.
