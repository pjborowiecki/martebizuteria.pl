## Tools

| Tool             | Version            | Why                                                                                                         |
| ---------------- | ------------------ | ----------------------------------------------------------------------------------------------------------- |
| Vite+ (`vp` CLI) | any recent release | Every script goes through `vp`. `vp check`, `vp test`, `vp dev`, `vp build`, `vp fmt`, `vp lint`, `vp exec` |
| Bun              | 1.4.0              | Package manager and script runner; pinned by `packageManager` in `package.json` and by CI                   |
| Node.js          | 24.x               | `vite-plus` declares `^22.18.0 \|\| ^24.11.0 \|\| >=26.0.0`; CI pins Node 24 in `.github/actions/setup`     |
| Git              | any recent version | The install step registers the hook dispatcher for `.vite-hooks/`                                           |

Install the global `vp` CLI first, because the `prepare` lifecycle script calls it during `bun install`:

```sh
curl -fsSL https://vite.plus | bash
```

On Windows use `irm https://vite.plus/ps1 | iex`. Then open a new shell and check the installation with `vp help`. The global CLI also manages the Node.js runtime and the package manager, so you do not have to install Node or Bun separately.

Vite+ ships two CLIs: the global `vp` and the project-local `vite-plus` package (pinned here to `1.1.0` in `devDependencies`). `vp` in this repository resolves to the local package, which is why `bun run check` and `vp check` behave identically.

`wrangler`, `drizzle-kit`, `shadcn`, `jsdom` and the Vitest coverage provider are all `devDependencies`. Run them through the package scripts, or directly with `vp exec wrangler …` / `bunx wrangler …` — never a globally installed copy, because the version would differ from the one CI uses.

### Optional

## Accounts

### Cloudflare — required

The application cannot start without its bindings. `wrangler.jsonc` declares the same seven in every environment: the six below, plus `ASSETS`, which serves the static files in `./public`.

| Binding                     | Resource                                                                                                                                        | Used for                                                                                                                  |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `DB`                        | D1 database                                                                                                                                     | All application data — 41 tables plus the `storefront_search` FTS5 index                                                  |
| `IMAGES`                    | R2 bucket: `martebizuteria` in production, `martebizuteria-preview` in development and preview, a local `martebizuteria-test` in the test build | Product image uploads                                                                                                     |
| `CACHE`                     | KV namespace                                                                                                                                    | The email sender availability flag, the keys that limit incident alerts to one per incident, and the health check's probe |
| `AUDIT_LOG_QUEUE`           | Cloudflare Queue                                                                                                                                | Audit events, written by the queue consumer                                                                               |
| `NEWSLETTER_QUEUE`          | Cloudflare Queue                                                                                                                                | Newsletter batches, sent by the queue consumer                                                                            |
| `REALTIME_INVALIDATION_HUB` | Durable Object                                                                                                                                  | WebSocket fan-out for realtime cache invalidation                                                                         |

Two caveats worth knowing before you provision anything:

- Cloudflare Queues is not available on every Workers plan. If your account cannot create a queue, a deploy will fail at `scripts/verify-bindings.ts`, which requires both a producer and a matching consumer for `AUDIT_LOG_QUEUE` and for `NEWSLETTER_QUEUE`, and a consumed dead-letter queue for each consumer. Each environment therefore needs four queues: `…-audit-log`, `…-audit-log-dlq`, `…-newsletter` and `…-newsletter-dlq`.
- `placement: { mode: "smart" }` in `wrangler.jsonc` is also a paid-plan feature. It is a hint, not a requirement, so it is safe to remove locally if your account rejects it.

The Durable Object needs no provisioning step. It is created by the `v1` migration in `wrangler.jsonc`, which declares `RealtimeInvalidationHub` under `new_sqlite_classes`.

### Google OAuth — required for social sign-in

`src/integrations/better-auth/auth.server.ts` configures Google, the only social provider, unconditionally:

```ts
socialProviders: {
  google: { clientId: env.AUTH_GOOGLE_CLIENT_ID, clientSecret: env.AUTH_GOOGLE_CLIENT_SECRET },
},
```

The client id and secret are listed under `secrets.required` in every `wrangler.jsonc` environment, so `scripts/prepare-deploy-secrets.ts` refuses to deploy without them. The redirect URI is `https://<host>/api/auth/callback/google`, matching the Better Auth handler mounted at `src/routes/api/auth.$.ts`.

### Resend — required to create any account

Email and password sign-in is enabled with verification enforced:

```ts
emailAndPassword: {
  enabled: true,
  maxPasswordLength: PASSWORD_MAX_LENGTH,
  minPasswordLength: PASSWORD_MIN_LENGTH,
  onPasswordReset: handlePasswordReset,
  requireEmailVerification: true,
  revokeSessionsOnPasswordReset: true,
  sendResetPassword: sendResetPasswordEmail,
},
emailVerification: {
  afterEmailVerification: handleEmailVerified,
  autoSignInAfterVerification: true,
  sendOnSignUp: true,
  sendVerificationEmail: sendVerifyEmail,
},
```

Without a working `RESEND_API_KEY` and a verified `RESEND_EMAIL_FROM` sender, the verification email never arrives and the account can never sign in. Outside the local `test` environment of the end-to-end suite there is no seeded admin account and no way to skip verification from the UI, so this is a hard prerequisite for reaching `/admin` — see [First run](/docs/getting-started/first-run). Locally, `onboarding@resend.dev` works without a domain of your own as long as you sign up with the Resend account owner's address; preview and production need a domain verified with the DNS records listed in [Resend](/docs/integrations/resend#sender-domain). `bun run email:verify development` checks the key and sender in `.env.development`.

### Stripe — required for checkout

You need a test-mode secret key, the matching publishable key, and a webhook signing secret. Payment succeeds in the browser but the order is only created by the webhook handler at `/api/webhooks/stripe`, which verifies the signature with `STRIPE_WEBHOOK_SECRET` and rejects anything it cannot verify.

The opt-in `stripe-test-mode` browser tests, which pay by card, BLIK and Przelewy24 in Stripe's real Payment Element, need the keys of a separate Stripe sandbox with no webhook endpoint and with Cards, BLIK and Przelewy24 turned on. CI reads them from the `E2E_STRIPE_SECRET_KEY` and `E2E_STRIPE_PUBLISHABLE_KEY` repository secrets; see [Testing](/docs/tooling/testing#stripe-test-mode).

### InPost — an account only for shipments

The parcel-locker picker calls the public points API directly from `src/integrations/inpost/inpost.api.ts`, with no account:

```ts
const INPOST_API_BASE = `${INPOST_POINTS_API_ORIGIN}/v1/points`
```

`INPOST_POINTS_API_ORIGIN` is `https://api-pl-points.easypack24.net`, in `src/integrations/inpost/inpost.constants.ts`.

Booking shipments, printing labels and reading their status from the admin order page goes through InPost's ShipX API and needs an InPost Manager account: its API section (My Account, API) gives the token for `INPOST_API_TOKEN` and the organisation id for `INPOST_ORGANIZATION_ID`. Development and preview call InPost's sandbox, which has its own account at `https://sandbox-manager.paczkomaty.pl`. Both values may stay blank, and the order page then explains that automatic InPost shipping is not connected and how to ship by hand: create the parcel in InPost Manager, then mark the order shipped with its tracking number. The customer's email, the account's order page and the admin's order page link that number to InPost's tracking page through `resolveOrderTrackingUrl`. See [InPost](/docs/integrations/inpost#credentials). The points API, which the checkout searches for lockers and asks to confirm the chosen one, needs no account.
