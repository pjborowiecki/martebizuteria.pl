Wszystko jest skryptem z `package.json` napędzanym przez Vite+. Dwie zasady oszczędzają zamieszania:

- `vp <nazwa>` uruchamia polecenie **wbudowane** w Vite+; `vp run <nazwa>` uruchamia **skrypt lub zadanie**. Skrypty nie mogą przesłonić wbudowanych poleceń, więc `vp dev` i `vp run dev` to nie to samo — `vp dev` to serwer deweloperski Vite, a `vp run dev` to skrypt `dev` tego projektu, który najpierw generuje jeszcze kolekcje Fumadocs.
- Używaj `bun run <nazwa>` (albo `vp run <nazwa>`) zamiast wywoływać narzędzia bezpośrednio — dzięki temu dostajesz wersje przypięte w `devDependencies`, a nie to, co akurat jest w `PATH`.

## Codzienna praca

| Zadanie                                        | Polecenie              | Uruchamia                                                                         |
| ---------------------------------------------- | ---------------------- | --------------------------------------------------------------------------------- |
| Start serwera deweloperskiego                  | `bun run dev`          | `bun run content`, a potem `CLOUDFLARE_ENV=development vp dev --mode development` |
| Formatowanie, lint i kontrola typów            | `bun run check`        | `vp check` — brama, którą przechodzi CI                                           |
| To samo, z automatyczną naprawą                | `bun run check:fix`    | `vp check --fix`                                                                  |
| Tylko formatowanie                             | `bun run format`       | `vp fmt`                                                                          |
| Sprawdzenie formatowania bez zapisu            | `bun run format:check` | `vp fmt --check`                                                                  |
| Tylko lint                                     | `bun run lint`         | `vp lint`                                                                         |
| Ponowne wygenerowanie kolekcji MDX             | `bun run content`      | `fumadocs-mdx … .source`                                                          |
| Ponowne wygenerowanie typów Workera i kolekcji | `bun run typegen`      | `bun run cf-typegen && bun run content`                                           |

`bun run check` to jedno polecenie wykonujące trzy zadania, wszystkie skonfigurowane w `vite.config.ts`: Oxfmt z 17 własnymi grupami importów, Oxlint z sześcioma kategoriami ustawionymi na `error` (włącznie z `nursery`) oraz kontrolę typów. `denyWarnings: true` i `reportUnusedDisableDirectives: "error"` oznaczają, że ostrzeżenie albo nieaktualne wyłączenie reguły również przerywa przebieg, nie tylko błąd.

## Testy

| Zadanie                   | Polecenie                  | Projekt Vitest                              |
| ------------------------- | -------------------------- | ------------------------------------------- |
| Wszystko raz              | `bun run test`             | wszystkie trzy                              |
| Testy jednostkowe         | `bun run test:unit`        | `node`                                      |
| Testy bazodanowe          | `bun run test:integration` | `integration` — `*.integration.test.ts`     |
| Testy komponentów         | `bun run test:component`   | `component` — `*.component.test.tsx`, jsdom |
| Tylko to, co się zmieniło | `bun run test:changed`     | wszystkie trzy, `--changed`                 |
| Tryb obserwowania         | `bun run test:watch`       | wszystkie trzy                              |
| Pokrycie wraz z progami   | `bun run test:coverage`    | wszystkie trzy plus progi                   |

Trzy projekty są zadeklarowane w `vite.config.ts`. Projekt `node` wyklucza `*.component.test.*` i `*.integration.test.*`, więc `test:unit` faktycznie jest szybkim podzbiorem. Tylko projekt `component` wczytuje `src/platform/testing/setup.ts` i działa w jsdom.

Każdy próg pokrycia wynosi 100:

```ts
thresholds: {
  autoUpdate: false,
  branches: 100,
  functions: 100,
  lines: 100,
  statements: 100,
},
```

Instrukcja, gałąź, funkcja albo linia bez pokrycia przerywa `bun run test:coverage` i CI, więc nowy kod przychodzi razem ze swoimi testami. `autoUpdate: false` nie pozwala Vitestowi przepisywać tego bloku. Z pomiaru wykluczone są testy, katalogi `__test__`, pliki `*.d.ts`, `src/routeTree.gen.ts`, `src/integrations/**/migrations/**`, `src/presentation/components/shadcn/**` oraz `src/platform/testing/**`.

Używaj `bun run test`, nigdy `bun test` — to drugie to własny runner Buna, który nie wie nic o projektach Vitest, o pliku setup ani o wartościach środowiska `test` wczytywanych przez `loadEnv("test", …)`.

## Testy end-to-end

Playwright steruje zbudowanym Workerem w prawdziwych przeglądarkach. Konfiguracja to `playwright.config.ts`; specyfikacje leżą w `e2e/specs/`, a obiekty stron, fikstury i dane obok nich w `e2e/`.

| Zadanie                             | Polecenie                                        | Uruchamia                                         |
| ----------------------------------- | ------------------------------------------------ | ------------------------------------------------- |
| Jednorazowa instalacja przeglądarek | `bun run test:e2e:install`                       | `playwright install --with-deps chromium webkit`  |
| Wszystkie projekty                  | `bun run test:e2e`                               | `playwright test`                                 |
| Projekty Chromium uruchamiane w CI  | `bun run test:e2e:pr`                            | `--project=chromium --project=chromium-shop-wide` |
| Płatności w piaskownicy Stripe      | `bun run test:e2e:stripe`                        | `--project=stripe-test-mode`                      |
| Tylko specyfikacja smoke            | `bun run test:e2e:smoke`                         | `e2e/specs/smoke.spec.ts` w Chromium              |
| Vitest, a potem specyfikacja smoke  | `bun run test:all`                               | `bun run test && bun run test:e2e:smoke`          |
| Podgląd przeglądarki albo interfejs | `bun run test:e2e:headed`, `bun run test:e2e:ui` | `--headed`, `--ui`                                |

Testy działają na czwartym środowisku Wranglera, `test`, nigdy na zasobach zdalnych:

| Zadanie                         | Polecenie                 | Uruchamia                                                                        |
| ------------------------------- | ------------------------- | -------------------------------------------------------------------------------- |
| Build testowego Workera         | `bun run build:test`      | `rm -rf dist` → `content` → `CLOUDFLARE_ENV=test vp build --mode test`           |
| Serwowanie go                   | `bun run start:test`      | `CLOUDFLARE_ENV=test vp preview --mode test --host 127.0.0.1 --port 3000`        |
| Migracje lokalnej bazy testowej | `bun run db:migrate:test` | `wrangler d1 migrations apply DB --env test --local --persist-to .wrangler/test` |
| Wypełnienie jej danymi          | `bun run db:seed:test`    | `bun scripts/seed-test.ts`                                                       |
| Odtworzenie jej od zera         | `bun run db:reset:test`   | `rm -rf .wrangler/test`, potem `db:migrate:test` i `db:seed:test`                |

Poza CI `webServer` Playwrighta sam uruchamia `bun run db:reset:test && bun run build:test`, a potem `start:test`, chyba że na porcie 3000 już odpowiada serwer — wtedy używa go ponownie, więc najpierw trzeba zatrzymać `bun run dev`. `scripts/seed-test.ts` wczytuje jedenaście plików danych startowych katalogu i konta testowe z `e2e/data/accounts.ts`, w tym administratora z już włączonym uwierzytelnianiem dwuskładnikowym, bo build `test` wymaga go tak jak produkcja. Punkt wejścia Workera, `src/platform/testing/worker.ts`, odpowiada za Stripe, Resend i InPost ShipX z emulatorów w pamięci. Wyjątkiem, który łączy się ze Stripe, jest `test:e2e:stripe`: jego specyfikacje płacą kartą, BLIK-iem i Przelewy24 w prawdziwym Payment Element, gdy `STRIPE_SECRET_KEY` i `VITE_STRIPE_PUBLISHABLE_KEY` zawierają testowe klucze piaskownicy, a w przeciwnym razie są pomijane. Zobacz [Testy](/docs/tooling/testing#testy-end-to-end).

## Baza danych

Wszystko to znajduje się w `src/integrations/drizzle-orm/`. Pliki migracji trafiają do `migrations/`, zbiorczy plik schematu to `drizzle.schemas.ts`, a konfiguracja CLI to `drizzle.config.ts`.

| Zadanie                                             | Polecenie                                                  | Uwagi                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Wygenerowanie migracji ze schematu                  | `bun run db:generate`                                      | `drizzle-kit generate`, prefiks czasowy, zapis do `migrations/`                  |
| Nałożenie migracji zdalnie                          | `bun run db:migrate:{development,preview,production}`      | `wrangler d1 migrations apply DB --env <env> --remote`                           |
| Nałożenie migracji na lokalną bazę                  | `bun run db:migrate:local`                                 | `--env development --local`, dla `bun run start`                                 |
| Lista nałożonych migracji                           | `bun run db:migrations:{development,preview,production}`   | Tylko odczyt                                                                     |
| Otwarcie Drizzle Studio                             | `bun run db:studio:{development,preview,production}`       | Używa wartości `CLOUDFLARE_*` z odpowiedniego pliku `.env`                       |
| Wypchnięcie schematu bez migracji                   | `bun run db:push:{development,preview,production}`         | Bezpośrednia synchronizacja; unikaj dla trwałych zmian                           |
| Introspekcja istniejącej bazy                       | `bun run db:introspect:{development,preview,production}`   | Zapisuje `migrations/schema.ts` i `relations.ts`                                 |
| Wypełnienie danymi słownikowymi                     | `bun run db:seed:{preview,production}`                     | **Zapisuje do zdalnej bazy.** Zobacz ostrzeżenie poniżej                         |
| Migracje, dane i odtworzenie bazy testów end-to-end | `bun run db:migrate:test`, `db:seed:test`, `db:reset:test` | Tylko lokalnie, w `.wrangler/test`; zobacz [Testy end-to-end](#testy-end-to-end) |

Skrócone aliasy: `db:migrate` → preview, `db:studio` → development, `db:push` → development, `db:pull` → `db:introspect:development`, `db:seed` → preview.

Skrypty wypełniające wykonują po kolei jedenaście wywołań `wrangler d1 execute … --remote` na żywej bazie — najpierw kurierzy i metody dostawy, potem kategorie, kolekcje, atrybuty, produkty, warianty, stany magazynowe, zdjęcia i trzy tabele łączące. Nie są zsynchronizowane z żywym katalogiem, a dziesięć z nich najpierw usuwa wiersze kolidujące z danymi startowymi, a potem nadpisuje każdą zmianę w wierszu startowym (zobacz [Pierwsze uruchomienie](/docs/getting-started/first-run#tryb-deweloperski-zapisuje-do-bazy-preview)). Nie uruchamiaj ich na bazie z prawdziwymi danymi.

Migracje nakłada `wrangler d1 migrations apply` w kolejności nazw plików. Obecnie w `migrations/` jest 108 plików `.sql`, natomiast własny `meta/_journal.json` Drizzle wymienia 52 pozycje — dziennik nie jest źródłem prawdy, a faktyczną kolejność wyznaczają nazwy plików.

## Build, podglądy i wdrożenia

| Zadanie                         | Polecenie                   | Uruchamia                                                                                                |
| ------------------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| Build Workera preview           | `bun run build:preview`     | `rm -rf dist` → `content` → `CLOUDFLARE_ENV=preview vp build --mode preview` → `verify-build.ts preview` |
| Build Workera produkcyjnego     | `bun run build:production`  | To samo z `production`                                                                                   |
| Build (alias)                   | `bun run build`             | `build:preview`                                                                                          |
| Serwowanie ostatniego buildu    | `bun run start`             | `CLOUDFLARE_ENV=preview vp preview --mode preview --host 127.0.0.1 --port 3000`                          |
| Serwowanie buildu (alias)       | `bun run preview`           | `start`                                                                                                  |
| Build Workera testów end-to-end | `bun run build:test`        | `rm -rf dist` → `content` → `CLOUDFLARE_ENV=test vp build --mode test`, bez `verify-build.ts`            |
| Serwowanie go                   | `bun run start:test`        | `CLOUDFLARE_ENV=test vp preview --mode test --host 127.0.0.1 --port 3000`                                |
| Wdrożenie preview               | `bun run deploy:preview`    | Zobacz [Wdrożenie podglądu](/docs/getting-started/deploy-preview)                                        |
| Wdrożenie produkcyjne           | `bun run deploy:production` | To samo dla środowiska `production`                                                                      |

Oba buildy kończą się skryptem weryfikującym, a nie ostrzeżeniem. `scripts/verify-build.ts` przerywa pracę, jeśli zbudowany Worker celuje w niewłaściwe środowisko, jeśli brakuje `dist/client/fonts`, jeśli nie ma klienckiego JavaScriptu lub CSS, albo jeśli którykolwiek zasób kliencki nadal importuje `cloudflare:workers` lub wbudowany moduł `node:` albo zawiera Drizzle ORM.

## Co uruchamiają hooki

`.vite-hooks/pre-commit` to jedna linia:

```sh
bun run check:pre-commit
```

Czyli `vp staged`, a `vite.config.ts` definiuje, co to znaczy:

```ts
staged: { "*": ["vp check --fix"] },
```

Każdy commit formatuje więc, lintuje i sprawdza typy plików w przechowalni, naprawiając to, co da się naprawić.

`.vite-hooks/prepare-commit-msg` uruchamia `scripts/commit-msg.ts`, który wymusza konwencjonalny temat commita i dokleja do niego emoji. Dozwolone typy to `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style` i `test`; cokolwiek innego kończy się kodem błędu i wypisaniem listy. Tematy commitów merge, revert, fixup i squash przechodzą bez zmian.

## Kolejność, w jakiej działa CI

`.github/workflows/ci.yml`, po `.github/actions/setup`:

```sh
bun run check
bun run test:coverage
bun run build:preview
```

To zadanie `verify`. Drugie zadanie, `e2e`, wywołuje `.github/workflows/e2e-reusable.yml` dla Chromium: `bun run db:reset:test`, `bun run build:test`, a potem projekty `chromium` i `chromium-shop-wide`, które lokalnie odtwarza `bun run test:e2e:pr`. Uruchom wszystkie cztery przed otwarciem pull requesta i nie powinno być niespodzianek. Workflow **E2E (full)** dokłada WebKit przy każdym pushu do `main` (a także Chromium w harmonogramie w poniedziałki o 03:15 UTC i przy ręcznym uruchomieniu) i uruchamia projekt `stripe-test-mode` z kluczami piaskownicy z sekretów repozytorium `E2E_STRIPE_SECRET_KEY` i `E2E_STRIPE_PUBLISHABLE_KEY`. Wdrożenie podglądu ponownie uruchamia `bun run check` przed buildem, a produkcja wdraża tylko commit, którego CI przeszło, więc potknięcie w formatowaniu blokuje zarówno merge, jak i wdrożenie.
