## Development with remote bindings

```sh
bunx wrangler login
bun run db:migrate:development
bun run dev
```

1. **Sign in to Cloudflare.** `bun run dev` uses remote bindings, so Wrangler needs an authenticated session (or `CLOUDFLARE_API_TOKEN` in the environment).
2. **Apply migrations.** `db:migrate:development` runs `wrangler d1 migrations apply DB --env development --remote` against the database named `martebizuteria-preview`. If you are working on the existing project rather than your own Cloudflare account, the migrations are already applied and the command is a no-op; `bun run db:migrations:development` lists what is on the database.
3. **Start the server.** `bun run dev` runs `bun run content` first, then `CLOUDFLARE_ENV=development vp dev --mode development`. The port is fixed in `vite.config.ts` with `strictPort: true`, so a busy port 3000 is an error rather than a silent move to 3001.

The shop is then at:

| URL                                  | What                                        |
| ------------------------------------ | ------------------------------------------- |
| `http://localhost:3000`              | Storefront in Polish (`pl-PL`, the default) |
| `http://localhost:3000/en-US`        | Storefront in English                       |
| `http://localhost:3000/auth/sign-up` | Registration                                |
| `http://localhost:3000/admin`        | Admin console — requires the `admin` role   |
| `http://localhost:3000/docs`         | These pages                                 |
| `http://localhost:3000/dev/emails`   | Email template previews, development only   |

Route files carry no locale segment. The router de-localizes the URL before matching and re-applies the prefix when generating links, so `/en-US/products/x` and `/products/x` are served by the same `_storefront.products.$handle.tsx`. A redundant `/pl-PL/...` URL is redirected to the bare path by `resolveLocale` in `src/server.ts`, before the router ever runs.

### Development writes to the preview database

Worth repeating, because it surprises people: the `development` and `preview` environments in `wrangler.jsonc` declare the same `database_id` (`1660d0df-…`), the same R2 bucket (`martebizuteria-preview`) and the same KV namespace. The bucket has to exist before `bun run dev` can reach it; [Image delivery](/docs/guides/image-delivery) creates it and copies the images into it. Anything you create while developing is visible in the preview deployment, and vice versa. There is no separate development database.

Two related warnings:

- **Do not run `bun run db:seed:preview` or `db:seed:production` against a database that holds real data.** Both scripts execute `wrangler d1 execute … --remote` against the live database. Only `delivery-methods.sql` in `src/integrations/drizzle-orm/seeds/` uses `INSERT OR IGNORE`. The other ten first `DELETE` the rows that collide with the fixtures — a category, collection, attribute or product reusing a seed handle under another id, a variant reusing a seed SKU, and the images, stock rows, attribute values and category and collection links of the two seed products — and then upsert the fixtures with `ON CONFLICT(id) DO UPDATE` or `INSERT OR REPLACE`, which overwrites every admin edit to a seeded row. They are not maintained in step with the live catalogue. `bun run db:seed:test` loads the same files into the local end-to-end database, where that is harmless.
- `bun run db:push:*` applies schema changes directly without a migration file. Use `bun run db:generate` and the migrate scripts instead for anything you intend to keep.

## Creating an account

The remote databases have no seeded user; only the local `test` database of the end-to-end suite has seeded accounts (see [below](#a-seeded-local-run)). Sign up at `/auth/sign-up` with an email address you can read, because verification is mandatory:

```ts
emailAndPassword: {
  enabled: true,
  maxPasswordLength: PASSWORD_MAX_LENGTH,
  minPasswordLength: PASSWORD_MIN_LENGTH,
  onPasswordReset: handlePasswordReset,
  requireEmailVerification: true,
  revokeSessionsOnPasswordReset: true,
  sendResetPassword: sendResetPasswordEmail,
},
emailVerification: {
  afterEmailVerification: handleEmailVerified,
  autoSignInAfterVerification: true,
  sendOnSignUp: true,
  sendVerificationEmail: sendVerifyEmail,
},
```

With `sendOnSignUp: true` the verification email is sent immediately, and `autoSignInAfterVerification: true` means clicking the link both verifies the address and signs you in. If `RESEND_API_KEY` is wrong or the sending domain is not verified in Resend, nothing arrives; `bun run email:verify development` tells you which, and [Resend](/docs/integrations/resend#sender-domain) lists the DNS records a domain needs. The row still exists in `user` with `email_verified` at `0`, and the refusal is in `/admin/audit` as `email.failed`. Once a newsletter, order or account-deleted email meets the same refusal, sign-up, password reset, resend-verification and change-email answer for the next five minutes that emails cannot be sent. Once the sender works, sign in with the new account: the sign-in page refuses the unconfirmed address and offers **Send the confirmation link again**.

Google sign-in bypasses the verification email, so a working OAuth app is the faster route if your Resend sender is not ready. Such an account has no password. It can keep signing in with Google after you promote it to admin, and it adds a password with **Set** next to the password in its security section (`setAccountPassword`), which accepts only a session signed in within the last 24 hours; turning on two-factor authentication asks for that password.

### Promoting yourself to admin

New accounts get the default role. From `src/integrations/better-auth/auth.access.ts`:

```ts
export const ROLES = {
  ADMIN: "admin",
  CUSTOMER: "customer",
} as const

export const DEFAULT_ROLE = ROLES.CUSTOMER
```

The `user` table's `role` column is a text enum defaulting to that value. To gain admin access, change it to `admin`:

```sh
bun run db:studio:development
```

Open the `user` table, find your row, set `role` to `admin`, then sign out and back in with your password. After sign-in the `/auth` guard sends an admin to `/admin`. The `/admin` layout uses `requireAdmin` from `src/integrations/better-auth/auth.routes.ts` as its `beforeLoad`, and the guard calls `hasAdminAccess(user.role)`; a customer hitting `/admin` is redirected to `/account/overview` rather than shown an error.

In production and in the end-to-end test build the admin panel also requires two-factor authentication: `isAdminTwoFactorRequired` in `auth.access.ts` holds only when the build's mode is `production` or `test`. In development and preview it is optional, and the panel opens without it.

Where it is required, the guard sends you to `/admin/security` the first time instead. Choose **Enable**, confirm your password, scan the QR code with an authenticator app (or type the setup key), enter the six-digit code and keep the recovery codes; then **Go to the admin panel**. From then on you sign in with your password and a code, or with Google: the `twoFactor` plugin does not ask for the shop's code on that path, so the Google account's own 2-Step Verification takes its place; keep it on for that Google account. If you signed up with Google, the account has no password yet: choose **Set** on the same page to give it one before **Enable**, because enabling two-factor authentication asks for it. Afterwards you manage the password, two-factor authentication, signed-in devices, the panel language and your time zone under **Settings** in the sidebar (see [Admin settings](/docs/features/admin-settings)). See [Better Auth](/docs/integrations/better-auth#two-factor-authentication-for-admins).

Only the first admin is made in D1. Every further admin signs up and confirms their address like any customer, and an admin then gives that account access under **Settings › Team**, which also takes it away again (see [Admin settings: Team](/docs/features/admin-settings#team)). Setting `role` by hand skips the team's rules, so keep it for the first admin, or for the shop's last admin should that account be lost.

Drizzle Studio connects over the D1 HTTP API using `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` and `CLOUDFLARE_ACCESS_TOKEN` from `.env.development`. If those are missing, Studio opens but every query fails.

## Stripe webhooks in development

Card payment completes in the browser, but the order is created by the webhook. Forward events to your local server in a second terminal:

```sh
bun run stripe:listen
```

That runs `stripe listen --latest --forward-to localhost:3000/api/webhooks/stripe`. The Stripe CLI prints a `whsec_…` value for the session — put it in `.env.development` as `STRIPE_WEBHOOK_SECRET` and restart the dev server, otherwise `constructEventAsync` fails signature verification and the handler answers `400 Webhook Error: Invalid Signature` for every event.

Without the listener the checkout flow appears to hang at the payment step: Stripe accepted the payment, but nothing ever calls back to create the order.

## Previewing transactional emails

`/dev/emails` renders eighteen of the twenty React Email templates without sending anything, the withdrawal one in both its customer and its shop version; `newsletter-confirmation` and `newsletter-campaign` have no preview entry. The index lists each template with HTML and plain-text links for both locales:

```
/dev/emails?template=order-confirmation&locale=pl-PL
/dev/emails?template=order-confirmation&locale=pl-PL&format=text
```

The available slugs are `account-deleted`, `change-email`, `email-changed`, `incident-alert`, `new-order`, `newsletter-already-subscribed`, `order-cancelled`, `order-confirmation`, `order-delivered`, `order-in-progress`, `order-refunded`, `order-shipped`, `order-tracking`, `order-withdrawal`, `order-withdrawal-notice`, `password-changed`, `payment-failed`, `reset-password` and `verify-email`. `order-in-progress`, `order-shipped`, `order-tracking` and `order-delivered` are the status e-mails the admin's fulfilment steps send: work started, parcel sent, a tracking number added or changed after the shipped e-mail, and delivery. The `GET` handler answers 404 unless `import.meta.env.DEV` is true, so a built Worker shows no previews.

## Running a production-shaped build locally

```sh
bun run build:preview
bun run start
```

`start` serves the build with `CLOUDFLARE_ENV=preview` on `http://127.0.0.1:3000`. Because `remoteBindings` in `vite.config.ts` is enabled only for `CLOUDFLARE_ENV=development`, this run uses Wrangler's local simulated D1, R2 and KV under `.wrangler/state/` instead of the remote resources. That gives you an isolated environment, but it starts empty; `bun run db:migrate:local` applies the migrations to the local D1 store.

`bun run build:preview` ends with `scripts/verify-build.ts`, the same check CI runs on the built artifact.

## A seeded local run

```sh
bun run db:reset:test
bun run build:test
bun run start:test
```

This is the run the end-to-end suite uses, and the only one with data and no remote resource. `db:reset:test` deletes `.wrangler/test`, applies the migrations to the local `martebizuteria-test` database and runs `scripts/seed-test.ts`, which loads the catalogue seeds and three accounts from `e2e/data/accounts.ts`: an admin with two-factor authentication already on, an admin without it and a customer, all with the same known password and verified e-mail addresses. `build:test` builds with `--mode test` and `.env.test`, so admin two-factor authentication is enforced as in production. `start:test` serves the build at `http://127.0.0.1:3000` through `src/platform/testing/worker.ts`, which answers Stripe, Resend and InPost ShipX from in-memory emulators. See [Testing](/docs/tooling/testing#end-to-end-tests).
