Środowisko `preview` wdraża Workera o nazwie `martebizuteria-preview`, którego Cloudflare udostępnia pod adresem `https://preview.martebizuteria.pl` oraz `https://martebizuteria-preview.pjborowiecki.workers.dev` — ten drugi adres workflow podglądu publikuje w komentarzu przy każdym pull requeście. Produkcja wdraża Workera `martebizuteria`, który do startu sprzedaży jest dostępny wyłącznie pod `https://martebizuteria.pjborowiecki.workers.dev`; `https://martebizuteria.pl` zostanie podłączony przy starcie.

`preview` w `wrangler.jsonc` podłącza swoją domenę własną przez `routes` z `custom_domain: true`, `production` ma puste `routes` do startu sprzedaży na `martebizuteria.pl`, a oba ustawiają `workers_dev: true`, bo bez tego Wrangler wyłączyłby nazwę `workers.dev` Workerowi, który ma trasy, a kontrola działania po wdrożeniu pyta właśnie tę nazwę. Domena własna preview to host inny niż `workers.dev`, który `HOSTS_BY_MODE` w `src/modules/_core/constants/api.ts` akceptuje dla uwierzytelniania, linków w e-mailach i adresu powrotu ze Stripe. `HOSTS_BY_MODE` akceptuje już `martebizuteria.pl` dla produkcji, ale na razie nic go nie obsługuje. `src/modules/_core/constants/__test__/api.test.ts` nie przechodzi, gdy `routes` preview rozjedzie się z jego hostami albo gdy `routes` produkcji nie jest puste. Nazwa `www` nie jest podłączona: `APP_URL`, a z nim każdy link kanoniczny, to sam `https://martebizuteria.pl`.

## Przygotowanie zasobów

`bun run deploy:preview` zaczyna od `scripts/verify-bindings.ts`, który czyta ten sam plik JSONC co Wrangler i przerywa pracę, jeśli nie rozwiąże się któryś z sześciu bindingów — `DB`, `CACHE`, `IMAGES`, `AUDIT_LOG_QUEUE`, `NEWSLETTER_QUEUE` i `REALTIME_INVALIDATION_HUB`; `ASSETS` nie jest sprawdzany — albo konsument którejś kolejki producenta nie wskazuje kolejki martwych listów, którą Worker również konsumuje. Zasoby trzeba więc utworzyć najpierw:

```sh
bunx wrangler login
bunx wrangler d1 create martebizuteria-preview
bunx wrangler kv namespace create martebizuteria-cache-preview
bunx wrangler r2 bucket create martebizuteria-preview
bunx wrangler r2 bucket dev-url enable martebizuteria-preview
bunx wrangler queues create martebizuteria-audit-log-preview
bunx wrangler queues create martebizuteria-audit-log-preview-dlq
bunx wrangler queues create martebizuteria-newsletter-preview
bunx wrangler queues create martebizuteria-newsletter-preview-dlq
```

Następnie wpisz identyfikatory do `wrangler.jsonc` — pod `development` i `preview`, jeśli mają współdzielić zasoby tak, jak robi to konfiguracja w repozytorium:

| Pole                                   | Gdzie                                                                                                                                        |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `d1_databases[].database_id`           | `env.development` i `env.preview`                                                                                                            |
| `d1_databases[].database_name`         | Te same dwa                                                                                                                                  |
| `kv_namespaces[].id`                   | Te same dwa                                                                                                                                  |
| `r2_buckets[].bucket_name`             | Te same dwa                                                                                                                                  |
| `queues.producers[].queue`             | Musi zgadzać się z `queues.consumers[].queue`                                                                                                |
| `queues.consumers[].dead_letter_queue` | Konsument każdej kolejki producenta wskazuje jej kolejkę `-dlq`, która ma własnego konsumenta: w każdym środowisku jest czterech konsumentów |

Bucket preview startuje pusty, a baza preview wskazuje na zdjęcia z plików seed i grafiki marketingowe. Skopiuj je do niego przed pierwszym wdrożeniem i ustaw `VITE_R2_URL` na adres wypisany przez `dev-url enable`, tak jak opisuje [Dostarczanie zdjęć](/docs/guides/image-delivery).

Zostaw nazwy bindingów dokładnie takie, jakie są — `DB`, `CACHE`, `IMAGES`, `AUDIT_LOG_QUEUE`, `NEWSLETTER_QUEUE`, `REALTIME_INVALIDATION_HUB`, `ASSETS` — i nie ruszaj `migrations_dir`, który wskazuje na `./src/integrations/drizzle-orm/migrations`. Z nazw bindingów generowany jest `src/types/worker-configuration.d.ts` i względem nich typowana jest cała warstwa serwerowa.

Durable Object nie wymaga przygotowania. Tworzy go migracja już obecna w pliku:

```jsonc
"migrations": [
  {
    "tag": "v1",
    "new_sqlite_classes": ["RealtimeInvalidationHub"],
  },
],
```

Oto dokładnie to, czego wymaga `verify-bindings.ts`, żeby było wiadomo, kiedy przygotowania są zakończone. `audit` i `newsletter` to producenci `AUDIT_LOG_QUEUE` i `NEWSLETTER_QUEUE`, a `hasDeadLetterConsumer` jest spełnione, gdy kolejka ma konsumenta, który wskazuje `dead_letter_queue` konsumowaną także przez Workera:

```ts
const consumerOf = (queue: string | undefined) => config.queues.consumers.find((consumer) => consumer.queue === queue)
const hasDeadLetterConsumer = (queue: string | undefined): boolean => consumerOf(consumerOf(queue)?.dead_letter_queue) !== undefined

if (
  !database?.database_id ||
  /^[0-]+$/u.test(database.database_id) ||
  !cache?.id ||
  /^[0-]+$/u.test(cache.id) ||
  !images?.bucket_name ||
  !audit?.queue ||
  !hasDeadLetterConsumer(audit.queue) ||
  !newsletter?.queue ||
  !hasDeadLetterConsumer(newsletter.queue) ||
  realtime?.class_name !== "RealtimeInvalidationHub"
) {
  throw new Error(`Missing database, cache, images, audit, newsletter, or realtime binding for ${environment}`)
}
```

Wdrożenie produkcyjne rzuca też `Production and preview share the images bucket <nazwa>`, gdy jego bucket `IMAGES` jest tym, który wiąże preview.

Zwróć uwagę na kontrolę wartości zastępczych: identyfikator złożony wyłącznie z zer i myślników jest odrzucany — to właśnie ta reguła nie pozwala wdrożyć skopiowanego szablonu.

### Domeny własne

Wrangler podłącza domenę własną tylko w strefie tego samego konta Cloudflare, więc `martebizuteria.pl` musi być tam aktywną strefą przed pierwszym wdrożeniem. Rekord DNS i certyfikat dla każdej nazwy Cloudflare tworzy wtedy sam. Rekord A, AAAA albo CNAME istniejący już na `martebizuteria.pl` lub `preview.martebizuteria.pl` koliduje z domeną własną: wdrożenie z terminala pyta, zanim go zastąpi, a wdrożenie z CI zastępuje go bez pytania. Rekordy MX i TXT strefy, na których opiera się skrzynka sklepu i nadawca Resend, zostają nietknięte.

Gdy `routes` wymienia domeny własne, wdrożenie ustawia domeny własne Workera dokładnie według tej listy, więc nazwę podłączoną ręcznie w panelu następne wdrożenie odłączy; dopisz ją zamiast tego do `routes`. Gdy `routes` jest puste, jak w produkcji do startu, wdrożenie zostawia domeny własne Workera bez zmian. Poza wdrażaniem Workerów token API potrzebuje uprawnień Workers Routes (edycja) i Zone (odczyt) do strefy `martebizuteria.pl`, żeby podłączyć domeny.

W dniu startu podłącz `martebizuteria.pl` i `www.martebizuteria.pl` przez `routes` produkcji, jak opisuje [Lista kontrolna przed startem sprzedaży](/docs/guides/go-live-checklist); Worker sam odsyła `www` na domenę bez `www`.

### Jeśli zmieniasz nazwę hosta

Idą z tym trzy zmiany:

- `APP_DOMAIN` w `src/presentation/branding/app.ts`, z którego wyprowadzany jest `APP_URL`, a przez niego linki kanoniczne, znaczniki OG i dane strukturalne.
- `HOSTS_BY_MODE` w `src/modules/_core/constants/api.ts`. Better Auth jest skonfigurowany z `baseURL: { allowedHosts: appHostsForMode(import.meta.env.MODE) }`, więc host nieobecny na tej liście ma odrzucane żądania uwierzytelniania, a logowanie na nowej domenie po prostu nie działa, bez wyraźnego błędu. `resolveRequestOrigin` sprawdza tę samą listę, zanim zbuduje link do e-maila albo adres powrotu ze Stripe, więc na brakującym hoście zapis do newslettera, checkout oraz wysyłka zamówienia i usuwanie klienta w panelu administratora też odpowiadają `FORBIDDEN`.
- Wpis `routes` każdego środowiska w `wrangler.jsonc`, który podłącza nową nazwę do Workera jako domenę własną.

## Wdrożenie

```sh
bun run deploy:preview
```

Wdrożenie samo nakłada oczekujące migracje na bazę preview, po kompilacji i tuż przed `wrangler deploy`, więc nowy Worker nigdy nie startuje na schemacie, którego nie zna; sam build niczego nie nakłada. W terminalu Wrangler pyta przed nałożeniem, a odpowiedź „nie” pomija migracje, ale nie wdrożenie, więc zamiast tego przerwij Ctrl+C.

Przed pierwszym wdrożeniem domena z `RESEND_EMAIL_FROM` musi też być zweryfikowana w Resend; rekordy DNS wymienia [Resend](/docs/integrations/resend#domena-nadawcy). `bun run email:verify preview` uruchamia osobno tę samą kontrolę, którą wykonuje wdrożenie.

Preview przyjmuje testowe klucze Stripe: `VITE_STRIPE_PUBLISHABLE_KEY` zaczynający się od `pk_test_` i `STRIPE_SECRET_KEY` zaczynający się od `sk_test_` albo `rk_test_`. Klucze live obciążałyby prawdziwą kartę przy każdym testowym zamówieniu, więc wdrożenie je odrzuca.

`deploy:preview` to osiem kroków połączonych operatorem `&&`:

```sh
bun scripts/verify-bindings.ts preview \
  && bun scripts/verify-stripe-keys.ts preview \
  && bun scripts/verify-email-sender.ts preview \
  && bun run build:preview \
  && bun scripts/prepare-deploy-secrets.ts preview \
  && bun run db:migrate:preview \
  && env -u CLOUDFLARE_ENV vp exec wrangler deploy \
       --config dist/server/wrangler.json \
       --secrets-file .wrangler/secrets.preview.json \
  && bun scripts/verify-deployment.ts preview
```

1. **`verify-bindings.ts preview`** — opisana wyżej kontrola bindingów. Przerywa wdrożenie, a nie tylko ostrzega.
2. **`verify-stripe-keys.ts preview`** — bierze `VITE_STRIPE_PUBLISHABLE_KEY` i `STRIPE_SECRET_KEY` ze środowiska procesu lub z `.env.preview` i rozpoznaje tryb każdego klucza po przedrostku. Brakujący klucz, klucze live albo klucz publiczny w innym trybie niż klucz tajny przerywają wdrożenie już tutaj; komunikat podaje nazwy zmiennych i ich tryb, nigdy sam klucz.
3. **`verify-email-sender.ts preview`** — bierze `RESEND_API_KEY` i `RESEND_EMAIL_FROM` ze środowiska procesu lub z `.env.preview` i pyta Resend, czy wyśle pocztę z tego adresu. Domena, której nie ma na koncie Resend albo która nie jest zweryfikowana, przerywa wdrożenie już tutaj, przed kompilacją, a komunikat podaje rekordy DNS do opublikowania. Tak samo adres w domenie `martebizuteria.pl`: preview wysyła z `hello@pjborowiecki.com`, żeby jego testowe e-maile nigdy nie wychodziły pod adresem sklepu.
4. **`build:preview`** — `rm -rf dist`, ponowne wygenerowanie `.source/`, `CLOUDFLARE_ENV=preview vp build --mode preview`, a potem `verify-build.ts preview`.
5. **`prepare-deploy-secrets.ts preview`** — czyta `secrets.required` z `wrangler.jsonc`, bierze każdą wartość ze środowiska procesu lub z `.env.preview` i zapisuje `.wrangler/secrets.preview.json` z uprawnieniami `0600`. Brakująca wartość powoduje wyjątek `Missing <NAZWA> in .env.preview or the process environment`, podobnie pusta, z wyjątkiem `INPOST_API_TOKEN` i `INPOST_ORGANIZATION_ID`, które mogą zostać puste, dopóki sklep nie ma danych InPost. Zapisywane są wyłącznie zadeklarowane sekrety — tak `CLOUDFLARE_ACCESS_TOKEN` i pozostałe dane zarządcze nie trafiają do Workera.
6. **`db:migrate:preview`** — `wrangler d1 migrations apply DB --env preview --remote` nakłada każdy plik migracji, którego baza preview jeszcze nie odnotowała. Migracja, która zawiedzie, zostaje wycofana, wcześniejsze pozostają nałożone, a wdrożenie zatrzymuje się przed wysłaniem Workera.
7. **`wrangler deploy`** — wdraża wygenerowany `dist/server/wrangler.json` i w tym samym wywołaniu wysyła plik sekretów. Wygenerowana konfiguracja jest płaska: ma już `"name": "martebizuteria-preview"` i `"vars": { "APP_ENV": "preview" }` na najwyższym poziomie, bez sekcji `env` — i właśnie dlatego polecenie najpierw usuwa zmienną `CLOUDFLARE_ENV`. Z nią ustawioną Wrangler szukałby sekcji środowiska, której w wygenerowanym pliku nie ma.
8. **`verify-deployment.ts preview`** — pyta `https://martebizuteria-preview.pjborowiecki.workers.dev` o `/`, `/products`, `/robots.txt`, `/api/webhooks/stripe` i `/api/health` i przerywa wdrożenie, chyba że `/` i `/products` odpowiedzą `200` z HTML-em, `robots.txt` odpowie `200` zwykłym tekstem, trasa webhooka odrzuci `GET` kodem `405`, a `/api/health` odpowie `200`, bo odpowiedziały D1, KV i R2. O stronę, która odpowie źle, kontrola pyta łącznie najwyżej trzy razy, co pięć sekund.

### Co wychwytuje weryfikacja buildu

`scripts/verify-build.ts` czyta `.wrangler/deploy/config.json`, rozwiązuje ścieżkę do konfiguracji, na którą ten plik wskazuje, i nie przepuszcza buildu, jeśli:

- rozwiązana ścieżka to nie dokładnie `dist/server/wrangler.json`;
- `vars.APP_ENV` nie jest równe żądanemu środowisku;
- nazwa Workera się nie zgadza — `martebizuteria` dla produkcji, `martebizuteria-preview` w pozostałych przypadkach;
- brakuje pliku wejściowego albo katalogu `dist/client/fonts`;
- `assets.directory` nie wskazuje na `dist/client`;
- `dist/client/assets` nie zawiera przynajmniej jednego pliku `.js` i jednego `.css`;
- którykolwiek kliencki plik `.js` importuje `cloudflare:workers` albo wbudowany moduł `node:`;
- którykolwiek kliencki plik `.js` zawiera Drizzle ORM, rozpoznawany po wywołaniu `Symbol.for`, które rejestruje jego symbol `drizzle:entityKind`.

Dwie ostatnie kontrole są najciekawsze. Pierwsza skanuje każdy bundle kliencki przy użyciu `Bun.Transpiler` i przerywa build przy imporcie tylko serwerowym, który przeciekł do grafu przeglądarki — czyli przy klasie błędów objawiającej się na produkcji pustą stroną. Druga przerywa build, gdy moduł wczytywany przez przeglądarkę wciąga Drizzle, na przykład schemat Zod zbudowany z tabeli, który dołożyłby ORM do każdej strony, która z niego korzysta.

## Wdrożenia automatyczne

| Workflow                | Wyzwalacz                                        | Środowisko   |
| ----------------------- | ------------------------------------------------ | ------------ |
| `ci.yml`                | Pull requesty oraz pushe do `main`               | brak         |
| `deploy-preview.yml`    | Pull requesty do `main`                          | `preview`    |
| `deploy-production.yml` | Udany `ci.yml` dla pusha do `main`; ręcznie      | `production` |
| `e2e-full.yml`          | Pushe do `main`, poniedziałki 03:15 UTC, ręcznie | brak         |
| `e2e-reusable.yml`      | Wywoływany przez `ci.yml` i `e2e-full.yml`       | brak         |

Oba workflow wdrożeniowe korzystają z `.github/actions/setup`, a potem wykonują `touch .env.<env>` i uruchamiają skrypt wdrożeniowy z wszystkimi wartościami podanymi przez środowisko zadania. Workflow podglądu najpierw uruchamia `bun run check`; workflow produkcyjny startuje dopiero wtedy, gdy `ci.yml` przeszedł dla pusha tego samego commita do `main`, i wdraża go tylko wtedy, gdy wciąż jest najnowszym commitem na `main`, albo ręcznie dla takiego commita, zobacz [CI/CD](/docs/tooling/ci-cd). `verify-stripe-keys.ts`, `verify-email-sender.ts` i `prepare-deploy-secrets.ts` wolą `process.env` od pliku, więc pusty plik jest celowy — istnieje tylko po to, żeby wywołanie `readFile` w `prepare-deploy-secrets.ts` się udało.

Workflow podglądu kończy się dodaniem lub zaktualizowaniem komentarza w pull requeście z adresem podglądu. Współbieżność jest kluczowana per pull request dla preview i globalnie dla produkcji, z `cancel-in-progress: false` na produkcji, żeby dwa pushe do `main` nie wyścigowały się ze sobą.

### Wymagana konfiguracja w GitHubie

**Sekrety** repozytorium:

`CLOUDFLARE_ACCESS_TOKEN` (przekazywany Wranglerowi jako `CLOUDFLARE_API_TOKEN`), `CLOUDFLARE_ACCOUNT_ID`, `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `INPOST_API_TOKEN`, `INPOST_ORGANIZATION_ID`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` oraz opcjonalnie `RESEND_MANAGEMENT_API_KEY`, którym `verify-email-sender.ts` odczytuje rekordy DNS domeny nadawcy i który nigdy nie trafia do Workera. Oba sekrety InPost mogą być puste; strona zamówienia wyjaśnia wtedy, jak nadać paczkę ręcznie.

Workflow **E2E (full)** czyta też `E2E_STRIPE_SECRET_KEY` i `E2E_STRIPE_PUBLISHABLE_KEY`, testowe klucze osobnej piaskownicy Stripe. Oba są ustawione, więc jego zadanie trybu testowego Stripe płaci kartą, BLIK-iem i Przelewy24 przy każdym uruchomieniu; zobacz [Testy](/docs/tooling/testing#tryb-testowy-stripe).

**Zmienne** repozytorium:

`VITE_R2_URL` i `VITE_STRIPE_PUBLISHABLE_KEY`. Obie są wstawiane do bundle'a klienckiego na etapie budowania, więc muszą być zmiennymi, nie sekretami. `VITE_R2_URL` różni się między preview a produkcją, więc ustaw go jako zmienną środowisk GitHub `preview` i `production`, która ma pierwszeństwo przed zmienną repozytorium o tej samej nazwie.

## Po wdrożeniu

Ostatni krok wdrożenia zapytał już nowego Workera o stronę główną, listę produktów, `robots.txt`, trasę webhooka Stripe i kontrolę stanu. Gdy zawiedzie, nowa wersja działa na żywo, ale nie odpowiada jak sklep; co wtedy zrobić, opisuje [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

Zarejestruj adresy zwrotne dostawców dla nowego hosta, zgodnie z listą w [Zmiennych środowiskowych](/docs/getting-started/environment-variables): `/api/auth/callback/google` oraz punkt końcowy Stripe pod `/api/webhooks/stripe`, czyli `https://preview.martebizuteria.pl/api/webhooks/stripe` na preview i, do startu sprzedaży, `https://martebizuteria.pjborowiecki.workers.dev/api/webhooks/stripe` na produkcji. Każdy punkt końcowy trzeba utworzyć w wersji API `2026-09-30.endive`, czyli `STRIPE_API_VERSION` z `src/integrations/stripe/stripe.constants.ts`, z włączonymi dziesięcioma zdarzeniami, które obsługują handlery: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `payment_intent.payment_failed`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, `refund.failed` i `refund.updated`. Obecne punkty końcowe to `we_1URCKtKoub4YqqV84bxHLS0D` dla preview i `we_1URCUkJhNVr9Gkhk2gFlLYQD` dla produkcji; starsze punkty końcowe, w tym te w poprzedniej wersji API `dahlia`, są wyłączone. Stripe wydaje osobny sekret podpisu dla każdego punktu końcowego, więc wartości `STRIPE_WEBHOOK_SECRET` dla preview i produkcji się różnią. Host punktu końcowego nie decyduje, dokąd linkuje potwierdzenie zamówienia: linkuje ono pod adres, na którym złożono zamówienie, wzięty z `return_url` sesji.
