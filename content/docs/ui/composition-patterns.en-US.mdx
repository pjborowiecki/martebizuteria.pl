## Routes compose, components decide

A route file owns four things and nothing else: the component that places the screen, the `loader` that warms the cache, the `head` that produces meta, and `staticData.namespaces` that lists the message namespaces the screen needs. The markup itself lives in `src/presentation/components/custom/pages/<area>/`.

`src/routes/_storefront.index.tsx` is the clearest example — the component is a list of sections and nothing more:

```tsx
const HomePage = (): JSX.Element => {
  const rootRef = useRef<HTMLDivElement>(null)
  useLandingAnimations({ rootRef })

  return (
    <main ref={rootRef} className="bg-background text-foreground" data-landing-page>
      <HeroSection />
      <VideoExperienceSection />
      <ValuesSection />
      …
      <NewsletterSection />
    </main>
  )
}
```

A layout route does the same for chrome. `src/routes/_storefront.tsx` mounts `Navigation`, `Footer`, the paused-sales notice, the cart banner and the activity tracker, subscribes to realtime invalidation, attaches its route stylesheet, and loads the collections the navigation's full-screen menu shows together with the sales status the notice reads and the seller's details the footer shows:

```tsx
export const Route = createFileRoute("/_storefront")({
  component: StorefrontLayout,
  head: () => ({ links: [{ href: storefrontCss, rel: "stylesheet" }] }),
  loader: async ({ context }) => {
    await Promise.all([
      context.queryClient.query({ ...getCollectionsQuery(), staleTime: "static" }).catch(noop),
      context.queryClient.query(getSalesStatusQuery()).catch(noop),
      context.queryClient.query(getSellerDetailsQuery()),
    ])
  },
  staticData: { namespaces: ["pages.cart"] },
})
```

Route stylesheets are imported with `?url` and linked from `head`. They hold plain CSS and, where they need theme values, borrow them with `@reference "./globals.css"` rather than emitting Tailwind's utilities again. `globals.css` is the only Tailwind entry point, linked from the root route.

## Components read their own data

A component fetches what it needs rather than receiving it. In practice that means:

- **Text** with `useTranslations("<namespace>")` from `use-intl/react`. `useLocale()` returns the interface language, which picks messages and localised content.
- **Formatting** of dates, numbers and prices with the display-preference hooks in `src/hooks/use-display-format.ts`: `useFormatter()` returns a use-intl formatter bound to the viewer's formatting locale and time zone, and `useFormatLocale()` and `useDisplayTimeZone()` return those two values for a module's own formatter, such as `formatAdminOrderDate(createdAt, { formatLocale, timeZone })`.
- **Query data** with `useQuery` / `useSuspenseQuery` against the same query options the route loader already primed — for example `getAdminOrdersPageQuery(pageInput)` from `src/modules/order/use-cases/get-admin-orders-page.ts`.
- **Route data** with `Route.useLoaderData()` inside the route file, or `getRouteApi("…")` elsewhere.

```tsx
export const NewArrivalsSection = (): JSX.Element => {
  const t = useTranslations("pages.landing.newArrivalsSection")

  return (
    <section id="nowosci" className="storefront-container space-y-10 pt-20 pb-20 lg:pt-28 lg:pb-28">
      …
      <Suspense fallback={NEW_ARRIVALS_GRID_SUSPENSE_FALLBACK}>
        <NewArrivalsProductGrid />
      </Suspense>
    </section>
  )
}
```

Props carry only what the parent alone knows: an entity (`order` on `OrdersRowActions`), controlled dialog state (`open` with `onOpenChange`), or a callback (`onRowClick`). There are no label props, no prop drilling, and no wrapper components that merely rename props or forward children.

## Folder shape

Small areas are flat files. Larger ones subdivide, and the subdivision is consistent:

| Subfolder     | Contents                                                                 |
| ------------- | ------------------------------------------------------------------------ |
| `components/` | The rendered pieces — one widget, cell, badge, filter or dialog per file |
| `hooks/`      | Screen state and data wiring, one hook per file                          |
| `lib/`        | Pure helpers and column definitions for that screen                      |
| `utils/`      | Screen-level singletons, such as the `createDataGrid` object             |
| `detail/`     | A detail page's parts, where a list and a detail share the area          |
| `sections/`   | Page sections: landing page, product page, account profile               |
| `_styles/`    | Reused class strings in `*.styles.ts` files                              |
| `__test__/`   | One test per sibling file, plus shared harnesses                         |

`pages/admin/orders/` has `components/`, `hooks/`, `lib/`, `utils/`, `detail/` and `__test__/`, plus `summary/` for the printable order summary at `/admin/orders/$orderId/summary`; `pages/cart-page/` is just `cart-item-card.tsx`, `cart-summary.tsx` and `__test__/`. Start flat and split only when the area grows.

Components shared across areas, or mounted by a layout or the root route, sit directly in `custom/`: `image.tsx`, `product-card.tsx`, `product-price.tsx`, `localized-link.tsx`, `icons.tsx`, `mdx.tsx`, `docs-content.tsx`, `docs-mdx.tsx`, `floating-field.tsx`, `validation-field-error.tsx`, `smooth-scroll.tsx`, `cart-availability-banner.tsx`, `sales-paused-banner.tsx`, `customer-activity-tracker.tsx`, `seller-contact-details.tsx`, `storefront-critical-fonts-head.tsx`.

## No comments

The convention is to write no comments: intent is expressed through names and types. No lint rule forbids comments, so the convention is upheld in review. Two consequences for composition:

- Name the thing rather than annotate it. `closeMenuAndRequestDeleteConfirm`, `suppressDataGridRowClickAfterDialogDismiss` and `ADMIN_CATALOG_DATAGRID_PAGE_CLASS` all read as sentences.
- When behaviour genuinely needs explaining, it goes in these docs or in a test name, not above the code.

## Module-level constants, not render-time objects

Anything that is a stable object or element is defined once at module scope, below the component that uses it. This is a convention rather than a lint rule, and it keeps object and element identity stable between renders:

```tsx
const NEW_ARRIVALS_GRID_SUSPENSE_FALLBACK = <NewArrivalsProductGridSkeleton />
```

```tsx
const THEME_INIT_SCRIPT_HTML = { __html: THEME_INIT_SCRIPT }
```

```tsx
const ITEM_CLASS = "…"
const WHITE_CHECKBOX = "border-input bg-background data-[state=checked]:border-foreground …"
```

Elements passed to a Base UI `render` prop are memoised instead, because they usually close over handlers:

```tsx
const button = useMemo(
  () => (
    <Button variant="outline" size="icon-lg" aria-label={t("view.label")}>
      <Settings2 className="size-4" strokeWidth={1.5} />
    </Button>
  ),
  [t],
)
```

A constant used by one file stays in that file. Only genuinely shared values move — and then into the owning module's `*.constants.ts` or the presentation-level style files such as `admin-layout.styles.ts` and `sheet-control.styles.ts`. There are no barrel files and no objects that only collect unrelated helpers; always import from the file that defines the thing.

## Class names

`cn` comes from the `cn` package, never from a local wrapper:

```tsx
className={cn("relative", className)}
```

```tsx
className={cn("peer", showValid && VALID_INPUT_CLASS)}
```

Long class strings that are reused live in a `*.styles.ts` file in a `_styles/` folder next to their screen, never among the `.tsx` files. `vite.config.ts` configures the formatter to sort Tailwind classes inside `className`, `classList` and the `cn`, `cva` and `tw` functions against `globals.css`, so class order is not a matter of taste — run `bun run format` and it settles.

Component variants belong in `cva`, in the primitive, not in a conditional at the call site. If three screens need the same button shape, add a variant to `button.tsx`.

## Links and routes

Never write a route path as a literal. `src/routes.ts` exports `ROUTES`, a flat table of every path in the application, and `LocalizedLink` wraps TanStack Router's `Link` so that route params default to `true` and the locale prefix is applied by the router's rewrite:

```tsx
<LocalizedLink to={ROUTES.PRODUCTS} className="…">
  {t("cta")}
</LocalizedLink>
```

`LocalizedTo` is derived from `FileRouteTypes["to"]` in the generated route tree, so a wrong path is a type error. In MDX and in the Markdown of the content pages, internal links are written without a locale prefix and the link component in `custom/mdx.tsx`, which `ContentPageArticle` reuses, localises them at render time with `localizePathname`.

## Images

Use `custom/image.tsx`, not a bare `<img>`. It wraps `@unpic/react` and takes `alt`, `width`, `height`, `src`, plus:

| Prop          | Effect                                                                        |
| ------------- | ----------------------------------------------------------------------------- |
| `priority`    | `loading="eager"`, `decoding="sync"`, `fetchPriority="high"`, higher quality  |
| `optimize`    | Defaults to `true`; `false` resolves the raw asset URL with `resolveAssetURL` |
| `quality`     | Overrides the default and priority quality from `IMAGE_CONSTANTS`             |
| `blurDataURL` | Passed to unpic as `background`                                               |
| `sizes`       | The responsive `sizes` attribute                                              |

`width` and `height` are required, which keeps the layout stable. With `optimize` on, an image on the `VITE_R2_URL` host is resized on that host through Cloudflare Image Transformations and unpic writes the `srcset`; an image on an `r2.dev` host is served at its original size, because `r2.dev` cannot transform images.

## Providers

Only two application providers exist, and both are mounted once in `src/routes/__root.tsx`, around the document body:

```tsx
<body>
  <TranslationsProvider locale={locale}>
    <ThemesProvider>{children}</ThemesProvider>
  </TranslationsProvider>
  <Scripts />
</body>
```

`TranslationsProvider` renders use-intl's `IntlProvider` with the route locale, the loaded messages and the viewer's display time zone, and inside it `DisplayPreferencesContext` with the `{ formatLocale, timeZone }` resolved from `displayPreferencesQuery`. `useFormatter`, `useFormatLocale` and `useDisplayTimeZone` read that context. The `QueryClientProvider` is not mounted by hand: `setupRouterSsrQueryIntegration` in `src/router.tsx` wraps the router with it.

`Tooltip.Provider` from Base UI wraps the outlet in `RootComponent`, and `SmoothScroll` wraps it only outside `/admin`:

```tsx
{
  isAdmin ? (
    <Outlet />
  ) : (
    <SmoothScroll>
      <Outlet />
    </SmoothScroll>
  )
}
```

Everything else is state, not context: the cart is a Zustand store (`src/modules/cart/cart.store.ts`), the data grid's context is created privately by `createDataGrid`, and the checkout form uses its own `CheckoutFormProvider`. Do not add a global provider for something one screen needs.

## Loading, error and empty states

The router registers three defaults in `src/router.tsx`: `DefaultPendingComponent`, `DefaultErrorComponent` and `DefaultNotFoundComponent`, all in `custom/defaults/`. They are locale-aware without hooks — `default-messages.ts` imports both message catalogues statically and picks one by locale, because these components can render before `TranslationsProvider` is useful. `DefaultPendingComponent` renders an empty `min-h-0` div inside `/admin` and a full-height shell elsewhere, so the console does not flash.

Within a screen, prefer a `Suspense` boundary with a purpose-built skeleton (`NewArrivalsProductGridSkeleton`, `CheckoutFormSkeleton`, `DataGridSkeleton`) over a spinner.

## Import order

`vite.config.ts` defines the groups and the formatter enforces them, with a blank line between groups. The order is:

```
server-only  cloudflare  react  builtin+external  platform  providers  integrations
modules  routes  hooks  constants  types  lib  branding
components-shadcn  components-custom  components-other  styles  relative  unknown
```

`constants` covers `~/src/data/**` and `~/src/presentation/theme/**`. You do not maintain any of this by hand — `bun run format` does. The order also follows the main dependency direction: presentation imports from modules and integrations. The reverse is limited to a few kinds of import: use cases that send e-mail import their templates from `src/presentation/emails/`, modules and integrations read the brand constants from `src/presentation/branding/`, six module `*.constants.ts` files share the catalog data-grid constants from `pages/admin/catalog/lib/catalog-admin-datagrid.constants.ts`, and `fumadocs.docs.ts` loads `custom/docs-content.tsx` with a dynamic import.

## Checks

```bash
bun run check    # oxfmt + oxlint (six categories, including nursery, as errors) + type check
bun run test:component
```

The lint budget applies to components too: 800 lines per file, 150 lines per function, 20 statements per function. A component that hits those limits is a component that should have been split — usually into a hook plus a presentational piece, which is exactly how the data-grid screens are organised.
