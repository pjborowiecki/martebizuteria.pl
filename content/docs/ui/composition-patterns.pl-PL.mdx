## Trasy składają, komponenty decydują

Plik trasy odpowiada za cztery rzeczy i nic więcej: komponent rozkładający ekran, `loader` rozgrzewający cache, `head` produkujący metadane oraz `staticData.namespaces` z listą przestrzeni nazw komunikatów, których ekran potrzebuje. Same znaczniki mieszkają w `src/presentation/components/custom/pages/<obszar>/`.

`src/routes/_storefront.index.tsx` jest najczystszym przykładem — komponent to lista sekcji i nic ponad to:

```tsx
const HomePage = (): JSX.Element => {
  const rootRef = useRef<HTMLDivElement>(null)
  useLandingAnimations({ rootRef })

  return (
    <main ref={rootRef} className="bg-background text-foreground" data-landing-page>
      <HeroSection />
      <VideoExperienceSection />
      <ValuesSection />
      …
      <NewsletterSection />
    </main>
  )
}
```

Trasa layoutu robi to samo dla chromu. `src/routes/_storefront.tsx` montuje `Navigation`, `Footer`, komunikat o wstrzymanej sprzedaży, banner koszyka i tracker aktywności, subskrybuje unieważnianie w czasie rzeczywistym i ładuje kolekcje pokazywane w pełnoekranowym menu nawigacji razem ze stanem sprzedaży, który czyta komunikat, i danymi sprzedawcy, które pokazuje stopka:

```tsx
export const Route = createFileRoute("/_storefront")({
  component: StorefrontLayout,
  loader: async ({ context }) => {
    await Promise.all([
      context.queryClient.query({ ...getCollectionsQuery(), staleTime: "static" }).catch(noop),
      context.queryClient.query(getSalesStatusQuery()).catch(noop),
      context.queryClient.query(getSellerDetailsQuery()),
    ])
  },
  staticData: { namespaces: ["pages.cart"] },
})
```

Arkusze tras importuje się przez `?url` i dołącza z `head`. Zawierają zwykły CSS, a jeśli potrzebują wartości motywu, pożyczają je przez `@reference "./globals.css"`, a nie emitują ponownie narzędzi Tailwinda. `globals.css` jest jedynym punktem wejścia Tailwinda, dołączanym z trasy głównej.

## Komponenty same pobierają dane

Komponent pobiera to, czego potrzebuje, zamiast to otrzymywać. W praktyce oznacza to:

- **Teksty** przez `useTranslations("<przestrzeń>")` z `use-intl/react`. `useLocale()` zwraca język interfejsu, który wybiera komunikaty i zlokalizowane treści.
- **Formatowanie** dat, liczb i cen przez hooki preferencji wyświetlania z `src/hooks/use-display-format.ts`: `useFormatter()` zwraca formater use-intl związany z językiem formatowania i strefą czasową oglądającego, a `useFormatLocale()` i `useDisplayTimeZone()` zwracają te dwie wartości dla własnego formatera modułu, jak `formatAdminOrderDate(createdAt, { formatLocale, timeZone })`.
- **Dane zapytań** przez `useQuery` / `useSuspenseQuery` na tych samych opcjach zapytania, które loader trasy już przygotował — na przykład `getAdminOrdersPageQuery(pageInput)` z `src/modules/order/use-cases/get-admin-orders-page.ts`.
- **Dane trasy** przez `Route.useLoaderData()` w pliku trasy albo `getRouteApi("…")` poza nim.

```tsx
export const NewArrivalsSection = (): JSX.Element => {
  const t = useTranslations("pages.landing.newArrivalsSection")

  return (
    <section id="nowosci" className="storefront-container space-y-10 pt-20 pb-20 lg:pt-28 lg:pb-28">
      …
      <Suspense fallback={NEW_ARRIVALS_GRID_SUSPENSE_FALLBACK}>
        <NewArrivalsProductGrid />
      </Suspense>
    </section>
  )
}
```

Propsy przenoszą tylko to, co wie wyłącznie rodzic: encję (`order` w `OrdersRowActions`), sterowany stan dialogu (`open` z `onOpenChange`) albo wywołanie zwrotne (`onRowClick`). Nie ma propsów z etykietami, nie ma przekazywania propsów w dół przez kilka poziomów i nie ma komponentów-nakładek, które tylko zmieniają nazwy propsów albo przekazują dzieci.

## Kształt katalogów

Małe obszary to płaskie pliki. Większe dzielą się dalej, i podział jest konsekwentny:

| Podkatalog    | Zawartość                                                                                |
| ------------- | ---------------------------------------------------------------------------------------- |
| `components/` | Renderowane części — po jednym widżecie, komórce, plakietce, filtrze lub dialogu na plik |
| `hooks/`      | Stan ekranu i podłączenie danych, po jednym hooku na plik                                |
| `lib/`        | Czyste funkcje pomocnicze i definicje kolumn tego ekranu                                 |
| `utils/`      | Singletony ekranu, takie jak obiekt z `createDataGrid`                                   |
| `detail/`     | Części strony szczegółów, gdy lista i szczegóły dzielą obszar                            |
| `sections/`   | Sekcje stron: strony głównej, strony produktu, profilu konta                             |
| `_styles/`    | Wielokrotnie używane łańcuchy klas w plikach `*.styles.ts`                               |
| `__test__/`   | Po jednym teście na plik siostrzany oraz współdzielone obudowy testowe                   |

`pages/admin/orders/` ma `components/`, `hooks/`, `lib/`, `utils/`, `detail/` i `__test__/`, a do tego `summary/` dla podsumowania zamówienia do druku pod `/admin/orders/$orderId/summary`; `pages/cart-page/` to po prostu `cart-item-card.tsx`, `cart-summary.tsx` i `__test__/`. Zaczynaj płasko i dziel tylko wtedy, gdy obszar naprawdę rośnie.

Komponenty współdzielone przez obszary albo montowane przez layout lub trasę główną leżą bezpośrednio w `custom/`: `image.tsx`, `product-card.tsx`, `product-price.tsx`, `localized-link.tsx`, `icons.tsx`, `mdx.tsx`, `docs-content.tsx`, `docs-mdx.tsx`, `floating-field.tsx`, `validation-field-error.tsx`, `smooth-scroll.tsx`, `cart-availability-banner.tsx`, `sales-paused-banner.tsx`, `customer-activity-tracker.tsx`, `seller-contact-details.tsx`, `storefront-critical-fonts-head.tsx`.

## Bez komentarzy

Konwencja jest taka, że nie pisze się komentarzy: intencję wyrażają nazwy i typy. Żadna reguła lintera nie zabrania komentarzy, więc konwencji pilnuje przegląd kodu. Dla kompozycji ma to dwie konsekwencje:

- Nazywaj rzecz, nie opisuj jej. `closeMenuAndRequestDeleteConfirm`, `suppressDataGridRowClickAfterDialogDismiss` i `ADMIN_CATALOG_DATAGRID_PAGE_CLASS` czytają się jak zdania.
- Gdy zachowanie naprawdę wymaga wyjaśnienia, trafia ono do tej dokumentacji albo do nazwy testu, nie nad kod.

## Stałe na poziomie modułu, nie obiekty tworzone w renderze

Wszystko, co jest stabilnym obiektem albo elementem, definiuje się raz na poziomie modułu, poniżej komponentu, który tego używa. To konwencja, a nie reguła lintera, i zachowuje tożsamość obiektów oraz elementów między renderami:

```tsx
const NEW_ARRIVALS_GRID_SUSPENSE_FALLBACK = <NewArrivalsProductGridSkeleton />
```

```tsx
const THEME_INIT_SCRIPT_HTML = { __html: THEME_INIT_SCRIPT }
```

```tsx
const ITEM_CLASS = "…"
const WHITE_CHECKBOX = "border-input bg-background data-[state=checked]:border-foreground …"
```

Elementy przekazywane do propa `render` w Base UI są zamiast tego memoizowane, bo zwykle domykają się nad handlerami:

```tsx
const button = useMemo(
  () => (
    <Button variant="outline" size="icon-lg" aria-label={t("view.label")}>
      <Settings2 className="size-4" strokeWidth={1.5} />
    </Button>
  ),
  [t],
)
```

Stała używana przez jeden plik zostaje w tym pliku. Przenosi się tylko to, co faktycznie współdzielone — wtedy do pliku `*.constants.ts` modułu właściciela albo do plików stylów warstwy prezentacji, takich jak `admin-layout.styles.ts` i `sheet-control.styles.ts`. Nie ma plików zbiorczych (barrel) ani obiektów, które tylko gromadzą niepowiązane funkcje; importuj zawsze z pliku, który daną rzecz definiuje.

## Nazwy klas

`cn` pochodzi z pakietu `cn`, nigdy z lokalnej nakładki:

```tsx
className={cn("relative", className)}
```

```tsx
className={cn("peer", showValid && VALID_INPUT_CLASS)}
```

Długie, powtarzalne łańcuchy klas trzymamy w pliku `*.styles.ts` w folderze `_styles/` obok ekranu, nigdy między plikami `.tsx`. `vite.config.ts` konfiguruje formater tak, aby sortował klasy Tailwinda w `className`, `classList` oraz w funkcjach `cn`, `cva` i `tw`, względem `globals.css` — kolejność klas nie jest więc kwestią gustu: uruchom `bun run format` i się ułoży.

Warianty komponentu należą do `cva`, w prymitywie, a nie do warunku w miejscu użycia. Jeśli trzy ekrany potrzebują tego samego kształtu przycisku, dodaj wariant w `button.tsx`.

## Linki i trasy

Nigdy nie zapisuj ścieżki trasy jako literału. `src/routes.ts` eksportuje `ROUTES`, płaską tablicę wszystkich ścieżek aplikacji, a `LocalizedLink` opakowuje `Link` z TanStack Router tak, że parametry trasy domyślnie przyjmują `true`, a prefiks języka nakłada przepisywanie adresów w routerze:

```tsx
<LocalizedLink to={ROUTES.PRODUCTS} className="…">
  {t("cta")}
</LocalizedLink>
```

`LocalizedTo` wywodzi się z `FileRouteTypes["to"]` w wygenerowanym drzewie tras, więc błędna ścieżka jest błędem typów. W MDX i w Markdownie stron treści linki wewnętrzne zapisuje się bez prefiksu języka, a komponent linku z `custom/mdx.tsx`, którego używa też `ContentPageArticle`, lokalizuje je przy renderowaniu przez `localizePathname`.

## Obrazy

Używaj `custom/image.tsx`, nie surowego `<img>`. Komponent opakowuje `@unpic/react` i przyjmuje `alt`, `width`, `height`, `src`, a dodatkowo:

| Prop          | Efekt                                                                            |
| ------------- | -------------------------------------------------------------------------------- |
| `priority`    | `loading="eager"` i `fetchPriority="high"`; dekodowanie zostaje `async`          |
| `optimize`    | Domyślnie `true`; `false` rozwiązuje surowy adres zasobu przez `resolveAssetURL` |
| `quality`     | Nadpisuje jakość domyślną i priorytetową z `IMAGE_CONSTANTS`                     |
| `blurDataURL` | Przekazywany do unpic jako `background`                                          |
| `sizes`       | Atrybut `sizes` dla obrazów responsywnych                                        |

Bez `priority` obraz ma `loading="lazy"` i `decoding="async"` przy domyślnym priorytecie przeglądarki. `priority` dostaje jeden obraz na stronę, ten, na którym wypada Largest Contentful Paint: zdjęcie w hero strony głównej i główne zdjęcie na stronie produktu. Renderer serwerowy Reacta zamienia każdy obraz, który nie jest leniwy, w `<link rel="preload" as="image">` na początku dokumentu, więc każdy dodatkowy obraz priorytetowy konkuruje z właściwym o pierwsze wymiany z serwerem. Gdy układ renderuje to samo zdjęcie dwa razy dla dwóch punktów przerwania, jak galeria produktu w karuzeli na telefonie i w kolumnie na komputerze, obie kopie dostają ten sam `src`, `width`, `height` i `sizes`: przeglądarka sprowadza je wtedy przy każdej szerokości ekranu do jednego adresu, React wysyła jeden preload, a ukryta kopia nie kosztuje drugiego pobrania.

`width` i `height` są wymagane, co utrzymuje stabilny układ. Przy włączonym `optimize` obraz na hoście z `VITE_R2_URL` jest zmniejszany na tym hoście przez Cloudflare Image Transformations, a unpic buduje `srcset`; obraz na hoście `r2.dev` serwowany jest w oryginalnym rozmiarze, bo `r2.dev` nie przekształca obrazów.

## Dostawcy kontekstu

Istnieją tylko dwaj dostawcy aplikacji i obaj montowani są raz, w `src/routes/__root.tsx`, wokół ciała dokumentu:

```tsx
<body>
  <TranslationsProvider locale={locale}>
    <ThemesProvider>{children}</ThemesProvider>
  </TranslationsProvider>
  <Scripts />
</body>
```

`TranslationsProvider` renderuje `IntlProvider` z use-intl z językiem trasy, wczytanymi komunikatami i strefą czasową oglądającego, a w nim `DisplayPreferencesContext` z `{ formatLocale, timeZone }` rozstrzygniętymi z `displayPreferencesQuery`. Z tego kontekstu czytają `useFormatter`, `useFormatLocale` i `useDisplayTimeZone`. `QueryClientProvider` nie jest montowany ręcznie: opakowuje nim router `setupRouterSsrQueryIntegration` w `src/router.tsx`.

`Tooltip.Provider` z Base UI opakowuje outlet w `RootComponent`, a `SmoothScroll` tylko poza `/admin`:

```tsx
{
  isAdmin ? (
    <Outlet />
  ) : (
    <SmoothScroll>
      <Outlet />
    </SmoothScroll>
  )
}
```

Wszystko pozostałe jest stanem, nie kontekstem globalnym: koszyk to store Zustanda (`src/hooks/use-cart-store.ts`), kontekst tabeli danych tworzy prywatnie `createDataGrid`, a formularz kasy używa własnego `CheckoutFormProvider`. Nie dodawaj globalnego dostawcy dla czegoś, czego potrzebuje jeden ekran.

## Stany ładowania, błędu i pustki

Router rejestruje trzy komponenty domyślne w `src/router.tsx`: `DefaultPendingComponent`, `DefaultErrorComponent` i `DefaultNotFoundComponent`, wszystkie w `custom/defaults/`. Są świadome języka bez użycia hooków — `default-messages.ts` importuje oba katalogi komunikatów statycznie i wybiera jeden po języku, bo te komponenty mogą renderować się, zanim `TranslationsProvider` będzie użyteczny. `DefaultPendingComponent` renderuje puste `div` z `min-h-0` wewnątrz `/admin`, a poza nim powłokę na pełną wysokość, żeby konsola nie mrugała.

Wewnątrz ekranu wybieraj granicę `Suspense` z przygotowanym szkieletem (`NewArrivalsProductGridSkeleton`, `CheckoutFormSkeleton`, `DataGridSkeleton`) zamiast kręcącego się spinnera.

## Kolejność importów

`vite.config.ts` definiuje grupy, a formater je wymusza, z pustym wierszem między grupami. Kolejność jest taka:

```
server-only  cloudflare  react  builtin+external  platform  providers  integrations
modules  routes  hooks  constants  types  lib  branding
components-shadcn  components-custom  components-other  styles  relative  unknown
```

Grupa `constants` obejmuje `~/src/data/**` i `~/src/presentation/theme/**`. Nic z tego nie utrzymujesz ręcznie — robi to `bun run format`. Kolejność odpowiada też głównemu kierunkowi zależności: prezentacja importuje z modułów i integracji. Odwrotny kierunek ogranicza się do kilku rodzajów importów: przypadki użycia wysyłające e-maile importują szablony z `src/presentation/emails/`, moduły i integracje czytają stałe marki z `src/presentation/branding/`, sześć plików `*.constants.ts` modułów współdzieli stałe tabel katalogu z `pages/admin/catalog/lib/catalog-admin-datagrid.constants.ts`, a `fumadocs.docs.ts` ładuje `custom/docs-content.tsx` dynamicznym importem.

## Kontrole

```bash
bun run check    # oxfmt + oxlint (sześć kategorii, w tym nursery, jako błędy) + kontrola typów
bun run test:component
```

Budżet lintera obowiązuje także komponenty: 800 wierszy na plik, 150 wierszy na funkcję, 20 instrukcji na funkcję. Komponent, który dobija do tych limitów, to komponent, który należało podzielić — zwykle na hook plus część prezentacyjną, dokładnie tak, jak zorganizowane są ekrany z tabelami danych.
