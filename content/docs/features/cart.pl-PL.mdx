---
title: "Koszyk"
description: "Koszyk to utrwalany store zustand w przeglądarce; serwer odpowiada, co jest na stanie i ile teraz kosztuje."
---

M'Arte nie ma koszyka po stronie serwera. Koszyk żyje w `localStorage` pod kluczem `marte-cart`, a tabele `cart` i `cart_item` w bazie są nieużywane. Przed kasą jedyne odwołanie do serwera to sprawdzenie stanu magazynowego i aktualnych cen. Gdy krok płatności otworzy sesję Stripe Checkout, serwer wycenia koszyk według bazy i przechowuje tak wyceniony koszyk w wierszu płatności sesji, w `payment.lines` (zobacz [Kasa: koszyk w wierszu płatności](/docs/features/checkout#koszyk-w-wierszu-płatności)).

## Store

`src/hooks/use-cart-store.ts` tworzy `useCartStore` z middleware `persist` z zustand:

```ts
{
  migrate: (persisted) => { /* zachowuje tylko wiersze przechodzące isPersistedCartItem */ },
  name: "marte-cart",
  version: CART_PERSIST_VERSION,
}
```

`CART_PERSIST_VERSION` wynosi `3`. Funkcja `migrate` nie przekształca starych kształtów — waliduje ponownie każdy wiersz predykatem typu `isPersistedCartItem` i odrzuca wszystko, co nie pasuje, więc koszyk zapisany przez starszą wersję degraduje się do pustego lub częściowego, a nie wywala strony. Sprowadza też `qty` każdej zachowanej linii do przedziału od jednej sztuki do `CART_LINE_QUANTITY_MAX`; wersja `3` sprawia, że uruchamia się raz dla koszyków zapisanych przed wprowadzeniem tego limitu, więc żaden z nich nie wyśle ilości, którą kasa by odrzuciła.

Linia koszyka to:

```ts
export interface CartItem {
  readonly id: string
  readonly variantId: string
  readonly slug: string
  readonly title: string
  readonly variantTitle: string
  readonly image: string
  readonly price: string
  readonly rawPrice: number
  readonly priceChanged?: boolean
  qty: number
}
```

`id` jest zawsze ustawiane przez `addItem` na `variantId`, więc **tożsamością linii jest wariant**: dodanie tego samego wariantu dwa razy zwiększa `qty`, a nie tworzy drugiej linii. `price` to gotowy napis do wyświetlenia, a `rawPrice` to jednostki podrzędne. `priceChanged` oznacza linię, której cenę sklep zmienił, gdy leżała w koszyku.

Akcje: `addItem`, `applyCurrentPrices(prices)`, `removeItem(id)`, `updateQuantity(id, qty)`, `clearCart`, `itemCount()` i `cartTotal()`. `addItem` i `updateQuantity` trzymają `qty` linii między jedną sztuką a `CART_LINE_QUANTITY_MAX` (10, w `src/modules/cart/cart.constants.ts`), czyli najwyższą liczbą sztuk jednego produktu, jaką kasa przyjmuje w zamówieniu (zobacz [Kasa: limity trzymania towaru](/docs/features/checkout#limity-trzymania-towaru)), więc dodanie produktu, którego koszyk ma już dziesięć sztuk, zostawia dziesięć.

Obok store'a eksportowane jest `useCartHydrated()`. Subskrybuje `useCartStore.persist.onFinishHydration` i zwraca `false`, dopóki rehydratacja się nie zakończy — korzysta z niego każdy odbiorca, który nie może działać na pustym koszyku przed hydratacją, a przede wszystkim strażnik kasy.

## Ceny

`src/modules/cart/cart.utils.ts` zawiera dwie funkcje wspólne dla store'a i interfejsu:

```ts
export const getCartLineUnitPriceCents = (item: { readonly price: string; readonly rawPrice: number }): number => {
  if (Number.isFinite(item.rawPrice) && item.rawPrice >= MIN_PRICE_CENTS) {
    return item.rawPrice
  }

  return parseMoneyInputToMinorUnits(item.price, STORE_CURRENCY_CODE) ?? 0
}

export const getCartLineTotalCents = (item: { readonly price: string; readonly qty: number; readonly rawPrice: number }): number =>
  getCartLineUnitPriceCents(item) * item.qty
```

`rawPrice` ma priorytet; parsowanie napisu to fallback dla koszyków zapisanych, zanim `rawPrice` istniało. `MIN_PRICE_CENTS` i `parseMoneyInputToMinorUnits` pochodzą z `src/modules/_core/utils/currency.ts`.

**Ceny w koszyku podążają za katalogiem.** `rawPrice` zaczyna od ceny ze strony, z której dodano produkt. Każde sprawdzenie dostępności zwraca też cenę, za jaką wariant sprzedaje się teraz, a każda sesja checkoutu otwarta przez serwer zwraca ceny, po których ją wyceniono. Obie trafiają do `applyCurrentPrices(prices)`, które ustawia `rawPrice` w każdej linii, której wyświetlana cena się różni, i oznacza ją `priceChanged`. Oznaczona linia pokazuje `pages.cart.priceChanged` w koszyku i `checkoutSummary.priceChanged` w podsumowaniu kasy, dopóki nie zostanie usunięta albo zamówienie nie zostanie złożone; stara cena nie jest pokazywana. Linia, dla której serwer nie podał ceny, zachowuje swoją, a kasa odrzuca ją z `INVALID_PRICE`, `VARIANT_NOT_FOUND` albo `PRODUCT_NOT_FOUND`. Ceny z koszyka służą wyłącznie do wyświetlania: serwer nigdy ich nie dostaje, bo `cartItemSchema` nie ma `price` ani `rawPrice`, a sesję Stripe wycenia z `variant.price` w `validateAndCalculateItems` — zobacz [Kasa](/docs/features/checkout). Tak samo z `title`, `variantTitle` i `image` linii: `cartItemSchema` zachowuje tylko `slug`, `variantId` i `qty`, a nazwa i zdjęcie w płatności, zamówieniu i e-mailach o nim pochodzą z katalogu.

## Sprawdzenie dostępności

`src/modules/cart/use-cases/check-cart-availability.ts` to jedyna funkcja serwerowa w tym module. Jest publiczna (`withRequest`), przyjmuje `{ heldSessionId?, lines: [{ variantId, qty }] }` i odpowiada dla każdej linii, razem z aktualną ceną każdego wariantu:

```ts
const variantIds = lines.map((line) => line.variantId)
const [availabilityByVariantId, priceByVariantId, heldLines] = await Promise.all([
  getAvailabilityByVariantIds(variantIds),
  getSellPricesByVariantIds(variantIds),
  heldSessionId === undefined ? [] : getHeldLinesByTransactionId(heldSessionId),
])

const issues = lines.flatMap((line) => {
  const stockOnSale = availabilityByVariantId.get(line.variantId)
  const available = stockOnSale === undefined ? 0 : stockOnSale + sumHeldQuantity(heldLines, line.variantId)
  if (available >= line.qty) {
    return []
  }

  return [{ available, qty: line.qty, variantId: line.variantId }]
})

return {
  hasUnavailableItems: issues.length > 0,
  issues,
  prices: [...priceByVariantId].map(([variantId, unitPrice]) => ({ unitPrice, variantId })),
}
```

`getAvailabilityByVariantIds` w `inventory.accessors.ts` łączy każdy wiersz `inventory` z jego wariantem i produktem i zwraca stan tylko produktów `published`. Wariant bez wiersza w `inventory` albo taki, którego produkt sklep zarchiwizował lub przywrócił do szkicu, nie trafia do tej mapy i liczy się jako `0` dostępnych sztuk, niezależnie od tego, co trzyma własny checkout kupującego: koszyk oznacza linię komunikatem `pages.cart.availability.itemUnavailable` („Nie jest już dostępny”, „No longer available”), pojawia się baner, a kasa odsyła kupującego do koszyka. Listy produktów, wyszukiwarka i strona produktu ukrywają taki produkt na podstawie tego samego statusu (zobacz [Katalog i wyszukiwanie](/docs/features/catalog-and-search)), a kasa go odrzuca (zobacz [Kasa](/docs/features/checkout)). `prices` pochodzi z `getSellPricesByVariantIds` w `src/modules/product-variant/product-variant.accessors.ts`, jednego zapytania do `product_variant`, które pomija wariant, którego cena nie przechodzi `isSellPriceCentsValid`. `heldSessionId` to otwarta sesja Checkout przeglądarki, którą kasa trzyma w `localStorage` (zobacz [Kasa](/docs/features/checkout)). `getHeldLinesByTransactionId` w `payment.accessors.ts` zwraca `reserved_lines` płatności tej sesji, dopóki płatność i jej checkout są oba `pending`, czyli pod tym samym warunkiem, pod którym zwolnienie nadal by je oddało, a w przeciwnym razie nic. Te sztuki są doliczane tylko tej przeglądarce, więc kupujący, którego własny checkout trzyma ostatnią sztukę, nadal widzi ją jako dostępną w koszyku i w kasie po odświeżeniu, a każdy inny kupujący widzi ją jako zarezerwowaną. Endpoint jest publiczny, więc jego wejście jest ograniczone: najwyżej `CART_LINES_MAX` linii, całkowite ilości od jednej sztuki, identyfikatory wariantów nie dłuższe niż zapisany identyfikator i identyfikator sesji o długości najwyżej 255 znaków. Identyfikator sesji dolicza tylko to, co ta sesja już trzyma, więc odgadnięcie go nic nie daje.

`checkCartAvailabilityQuery(lines, heldSessionId)` jest `enabled` tylko wtedy, gdy jest co najmniej jedna linia, i używa `staleTime: 0`, więc sprawdzenie jest świeże przy każdym montowaniu. Ustawia `refetchOnWindowFocus: false` i `refetchOnReconnect: false`, więc powrót do karty ani odzyskanie połączenia nie uruchamiają go ponownie. Kupujący, który płaci BLIK-iem na telefonie, opuszcza krok płatności, żeby zatwierdzić płatność w aplikacji banku, i wraca, gdy płatność się kończy. Gdy już się zakończy, sesja nie trzyma już sztuki, więc sprawdzenie uruchomione przy powrocie uznałoby ostatnią sztukę za sprzedaną, a strażnik kasy odesłałby jej nabywcę do koszyka, zanim strona zdążyłaby pokazać potwierdzenie. Gdy telefon w tym czasie odrzuci kartę i strona się przeładuje, kasa pyta `getCheckoutSessionStatus` o zapisaną sesję, zanim strażnik uruchomi jakiekolwiek sprawdzenie, i pokazuje potwierdzenie sesji opłaconej albo czeka na bank przy płatności, którą ten wciąż potwierdza (zobacz [Kasa](/docs/features/checkout)). Klucz to `[...CART_QUERY_KEYS.AVAILABILITY, lines, heldSessionId]` — linie i trzymana sesja są częścią klucza, więc zmiana ilości albo otwarcie sesji wywołuje ponowne zapytanie. `placeholderData: keepPreviousData` zachowuje ostatnią odpowiedź, dopóki nowy klucz jest sprawdzany, więc strażnik kasy nie wraca do pierwszego sprawdzenia i nie odmontowuje formularza, gdy krok płatności zapisuje swoją sesję. `CART_QUERY_KEYS.AVAILABILITY` to `["cart", "availability"]` i występuje w `STOREFRONT_REALTIME_QUERY_PREFIXES`, więc zmiana stanu albo ceny wypchnięta z panelu ponawia sprawdzenie w otwartych kartach, a nowa cena trafia do koszyka i kasy bez przeładowania.

`src/hooks/use-cart-availability.ts` odczytuje trzymaną sesję przez `useSyncExternalStore(subscribeToCheckoutSessionId, loadCheckoutSessionId, …)`, bez sesji na serwerze, owija zapytanie i zwraca `{ hasUnavailableItems, isChecking, isFirstCheck, issues, issuesByVariantId }`. Efekt przekazuje `prices` z każdej odpowiedzi do `applyCurrentPrices`, więc każda strona, która uruchamia sprawdzenie, a dzięki `CartAvailabilityBanner` jest to każda strona sklepu przy niepustym koszyku, utrzymuje ceny w koszyku aktualne. `isChecking` jest prawdziwe, gdy `isPending || isFetching` i jest co najmniej jedna linia. `isFirstCheck` jest prawdziwe tylko przy `isPending` i co najmniej jednej linii, czyli dopóki zapytanie nie ma żadnej odpowiedzi do pokazania, własnej albo, dzięki `keepPreviousData`, poprzedniego klucza; strażnik kasy czeka tylko na nie, więc późniejsze sprawdzenie nie odmontowuje formularza.

Informacja o stanie linii pochodzi ze sprawdzenia dostępności: `pages.cart.availability.itemUnavailable` („Nie jest już dostępny”), gdy nie zostało nic, a w przeciwnym razie `pages.cart.availability.itemLimited` („Pozostało tylko 2 szt.” przy dwóch pozostałych sztukach), gdy koszyk chce więcej, niż zostało.

Ceny są formatowane według formatu dat i liczb kupującego, a nie języka strony (zobacz [Internacjonalizacja](/docs/features/internationalization)). Strona buduje sumę przez

```ts
const formatLocale = useFormatLocale()
const subtotal = formatPrice(cartTotal(), STORE_CURRENCY_CODE, formatLocale)
```

a `CartItemCard` pokazuje cenę jednostkową każdej linii, nie wartość całej linii, przez `useFormatter()`. Oba hooki pochodzą z `src/hooks/use-display-format.ts`.

Poniżej breakpointu `lg` podsumowanie znajduje się pod liniami; od `lg` zajmuje obok nich kolumnę o szerokości 380 pikseli i pozostaje widoczne, gdy linie się przewijają (`lg:sticky lg:top-28`). Odnośnik „Kontynuuj zakupy” stoi obok tytułu od breakpointu `sm`, a na węższych ekranach pod ostatnią linią. Na ekranie dotykowym (`pointer-coarse`) przyciski usuwania i zmiany ilości rosną do 40 pikseli.

## Podsumowanie to tylko suma częściowa

`cart-summary.tsx` renderuje trzy wiersze — sumę częściową, dostawę i sumę — ale dostawa to komunikat `pages.cart.summary.shippingValue`, a wiersz sumy wypisuje tę samą wartość `subtotal`:

```tsx
<div className="flex justify-between gap-4">
  <span className="font-medium">{t("summary.total")}</span>
  <span className="font-medium">{subtotal}</span>
</div>
```

Koszt dostawy nie jest znany, dopóki nie wybrano metody dostawy, a to dzieje się w kasie. Prawdziwą sumę z dostawą wylicza Stripe z pozycji sesji.

Gdy `checkoutDisabled` albo `salesPaused` jest prawdziwe, odnośnik do kasy zastępuje nieinteraktywny `<span aria-disabled="true">`, więc nie ma przycisku, który daje się kliknąć, ale nic nie robi. Przy `salesPaused` podsumowanie nad nim mówi też dlaczego, w akapicie z `role="status"` i `pages.cart.salesPaused.checkoutClosed`: „Przyjmowanie zamówień jest wstrzymane, więc kasa jest teraz zamknięta. Twój koszyk poczeka tu do wznowienia sprzedaży.”

## Blokowanie niepoprawnego koszyka

Wynik sprawdzenia dostępności wykorzystują trzy strażniki:

- `/cart` blokuje odnośnik do kasy, dopóki `hasUnavailableItems || isChecking`, a także dopóki `getSalesStatusQuery()` zgłasza wstrzymaną sprzedaż, co przekazuje podsumowaniu jako `salesPaused`. Sam koszyk działa dalej, więc kupujący może trzymać w nim produkty do wznowienia sprzedaży.
- `CartAvailabilityBanner` renderuje pasek z `role="alert"` i komunikatem `pages.cart.availability.banner`, gdy linie są niedostępne. Nad nim `SalesPausedBanner` renderuje na każdej stronie sklepu pasek z `role="status"` i komunikatem `pages.cart.salesPaused.banner`, dopóki sprzedaż jest wstrzymana; layouty konta i dokumentacji też renderują go pod swoją nawigacją. Zobacz [Kasa: wstrzymanie sprzedaży](/docs/features/checkout#wstrzymanie-sprzedaży).
- `/checkout` przekierowuje z powrotem na `/cart`, gdy zhydratowany koszyk jest pusty albo ma problemy ze stanem. Zobacz [Kasa](/docs/features/checkout).

## Śledzenie porzucenia koszyka

`src/presentation/components/custom/customer-activity-tracker.tsx` obserwuje store. Dla zalogowanego odwiedzającego, gdy `document.visibilityState` zmienia się na `hidden`, a koszyk nie jest pusty, wywołuje `trackCartAbandoned({ itemCount, lineCount })` raz na sesję (zabezpieczone kluczem `sessionStorage` `customer-activity:cart-abandoned-sent`). Opróżnienie koszyka czyści tę flagę przez `resetCartAbandonedTracking()`.

## Nieużywane tabele

`cart` i `cart_item` istnieją w `src/modules/cart/cart.schema.ts` oraz `src/modules/cart-item/cart-item.schema.ts`, z kolumnami `discount_id`, `expires_at`, `session_id` i `user_id` oraz standardowymi indeksami, i są eksportowane z `src/integrations/drizzle-orm/drizzle.schemas.ts`. Nic ich nie czyta ani nie zapisuje. To schemat koszyka serwerowego, którego nie zbudowano; `checkout.cart_id` odwołuje się do `cart.id`, ale nigdy nie jest wypełniane. Wyceniony koszyk, za który płaci checkout, leży zamiast tego w jego wierszu płatności, w `payment.lines`, zapisywanym, gdy krok płatności otwiera albo zastępuje sesję (zobacz [Kasa: koszyk w wierszu płatności](/docs/features/checkout#koszyk-w-wierszu-płatności)).
