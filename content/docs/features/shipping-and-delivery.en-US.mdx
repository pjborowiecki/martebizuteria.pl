## Two tables

`courier` (`src/modules/courier/courier.schema.ts`) is the carrier:

| Column          | Notes                            |
| --------------- | -------------------------------- |
| `internal_code` | Unique, not null (e.g. `inpost`) |
| `name`          | Not null                         |
| `logo`          | Nullable, up to 2048 characters  |
| `is_active`     | Boolean, default `true`          |

`delivery_method` (`src/modules/delivery-method/delivery-method.schema.ts`) is what the customer picks:

| Column             | Notes                                                                |
| ------------------ | -------------------------------------------------------------------- |
| `courier_id`       | `references(() => courier.id, { onDelete: "cascade" })`, not null    |
| `name`             | Not null; shown verbatim in checkout, so it is **not** translated    |
| `description`      | Nullable                                                             |
| `price`            | Integer minor units, not null; `0` means free                        |
| `type`             | `locker \| courier \| in_store`, not null                            |
| `api_service_code` | Not null; a carrier service identifier, currently informational only |
| `is_active`        | Boolean, default `true`                                              |

`api_service_code` is stored but never read. An InPost shipment booked from the admin takes its ShipX service from the method's `type` instead: `inpost_locker_standard` for `locker` and `inpost_courier_standard` for `courier` (see [InPost](/docs/integrations/inpost#shipments-through-shipx)).

## The three types

`delivery-method.constants.ts`:

```ts
export const DELIVERY_METHOD = { COURIER: "courier", IN_STORE: "in_store", LOCKER: "locker" } as const
export const DELIVERY_METHODS = [DELIVERY_METHOD.COURIER, DELIVERY_METHOD.LOCKER, DELIVERY_METHOD.IN_STORE] as const
export const DELIVERY_METHOD_QUERY_KEYS = { ALL: ["deliveryMethods"] as const } as const
```

`DELIVERY_METHODS` fixes the display order in the checkout step: courier, then locker, then in-store.

## Listing methods

`listDeliveryMethods` (`use-cases/list-delivery-methods.ts`) is public (`withRequest`) and returns only rows whose method **and** courier are both active. The rule is `offeredDeliveryMethod` in `delivery-method.accessors.ts`, which the checkout's server-side lookup shares:

```ts
export const offeredDeliveryMethod = and(eq(deliveryMethod.isActive, true), eq(courier.isActive, true))

const rows = await db
  .select({ courier, deliveryMethod })
  .from(deliveryMethod)
  .innerJoin(courier, eq(deliveryMethod.courierId, courier.id))
  .where(offeredDeliveryMethod)

return rows.map((row) => Object.assign(row.deliveryMethod, { courier: row.courier }))
```

Deactivating a courier therefore hides all of its methods at once.

`listDeliveryMethodsQuery()` has no `staleTime`, so it follows the client's default. It is read by the delivery step, the courier sub-step and the payment step (which needs the price to compute the Stripe amount). The `/checkout/` page loader loads it with `staleTime: "static"` while the layout reads the checkout messages, so those steps read the methods from the cache instead of requesting them after the form appears. The loader skips the read on the confirmation after payment, and a failed read leaves the steps to request the methods themselves.

`getOfferedDeliveryMethodByIdQuery(id)` in `delivery-method.accessors.ts` is the server-side lookup `resolveDelivery` in `stripe.actions.server.ts` uses when a payment session is opened or replaced. It joins the courier and applies `offeredDeliveryMethod`, and returns only the method's `price` and `type`. A method that is unknown, switched off, or whose courier is switched off, including one deactivated mid-checkout, is refused with `DELIVERY_METHOD_UNAVAILABLE`; the payment step then toasts `errors.deliveryMethodUnavailable` and sends the shopper back to the delivery step with the method list fetched again. See [Checkout](/docs/features/checkout#server-side).

Delivery goes only to the countries in `DELIVERY_COUNTRY_CODES` (`delivery-method.constants.ts`), currently `PL`. `checkoutSchema` refuses any other shipping `countryCode`; nothing in `delivery_method` or `courier` records a country.

## Seed data

`src/integrations/drizzle-orm/seeds/delivery-methods.sql` inserts two couriers (`inpost` and `marte-atelier`) and three methods:

| Method           | Type       | Price (minor units) | `api_service_code`        |
| ---------------- | ---------- | ------------------- | ------------------------- |
| Paczkomat InPost | `locker`   | 1499                | `inpost_locker_standard`  |
| Kurier InPost    | `courier`  | 1999                | `inpost_courier_standard` |
| Odbiór w atelier | `in_store` | 0                   | `marte_atelier_pickup`    |

The seed uses `INSERT OR IGNORE` with fixed UUIDv7 ids. Do not run `bun run db:seed:preview` against the live database — the seed files lag behind production data.

Each seeded method also has a Polish `description`, which no page shows. The descriptions follow § 7 of the terms of service: up to 4 business days from dispatch for the locker and the courier, and collection from the workshop in Bochnia, ready by the end of the fulfilment time. `20261010220000_delivery_method_descriptions.sql` gives rows seeded before that the same descriptions, replacing the 1–2 day transit and the Warsaw atelier ready in 24 hours. It changes a row only while its description is still the old seeded text, so a description the owner has rewritten stays as it is.

## Delivery step

`_steps/delivery-step.tsx` renders one `OptionCard` per **type** that has at least one active method, using `DELIVERY_ICONS` (`Truck`, `Package`, `Store` from lucide). The card description shows the cheapest price in the group:

```ts
const lowestPrice = Math.min(...methods.map((m) => m.price))
if (lowestPrice === 0) {
  return t("deliverySubsteps.free")
}

const price = format.number(lowestPrice / CENTS_IN_ZLOTY, { currency: "PLN", style: "currency" })

return methods.length > 1 ? `${t("deliverySubsteps.from")} ${price}` : price
```

Picking a type writes `deliveryMethodType` and either auto-selects the single method or clears `deliveryMethod` so the sub-step must choose.

### Courier

`delivery/courier/delivery-courier.tsx` renders a radio group of the `courier` methods with their formatted prices, then `deliverySubsteps.parcelDeliveryTime`, plus the free-text `deliveryNotes` field. That paragraph gives the delivery time of § 7 of the terms of service: the fulfilment time stated on the product page, counted from the acceptance of the order and the longest one for several products, then up to 4 business days from dispatch with InPost, with the tracking number sent by e-mail. That field is persisted as `checkout.customer_note` and copied onto `order.customer_note`. The component returns `undefined` when there are no courier methods.

### In-store

`delivery/store/delivery-in-store.tsx` is copy only: two paragraphs from `deliverySubsteps.inStoreTitle` and `deliverySubsteps.inStoreText`. The second gives the address and opening hours and, as § 7 does, says the order is ready by the end of the fulfilment time stated on the product page and that the shopper is told when it is. There is no store picker; the `storeLocation` field exists in `checkoutSchema` but nothing writes it.

### Locker

`delivery/locker/delivery-locker.tsx` shows `deliverySubsteps.lockerText`, which the map dialog also uses as its description, the same `deliverySubsteps.parcelDeliveryTime` as the courier step, and the currently selected locker id, and hosts `InpostSelector`. The `lockerId` field is required by the `superRefine` in `checkoutSchema` whenever `deliveryMethodType === "locker"`, which shows `validation.lockerIdRequired` on the step. The server does not trust that type: `resolveDelivery` requires a `lockerId` matching `INPOST_POINT_NAME_PATTERN` whenever the method's `type` in the database is `locker`, and refuses the session with `LOCKER_REQUIRED` otherwise. It then asks InPost whether the point exists with `fetchPointByName`, waiting at most three seconds: a point InPost does not list is refused with `LOCKER_NOT_FOUND`, which sends the shopper back to this step, and when InPost cannot answer the locker is accepted with `checkout.locker_unconfirmed` set, so the admin order asks the shop to check it before shipping. For any other type it drops `lockerId`, so `checkout.locker_id` and `order.locker_id` stay empty for courier and in-store orders.

## InPost point picker

The integration is four small files in `src/integrations/inpost`:

```ts
const INPOST_API_BASE = "https://api-pl-points.easypack24.net/v1/points"
const MIN_CITY_LENGTH = 3

export const fetchPointsByCity = async (city: string): Promise<InpostPointParsed[]> => {
  const trimmed = city.trim()
  if (trimmed.length < MIN_CITY_LENGTH) {
    return []
  }

  const url = `${INPOST_API_BASE}?city=${encodeURIComponent(capitalizeCity(trimmed))}&per_page=1000`
  ...
}
```

Points of note:

- The city search goes **straight from the browser** to InPost's public points API. There is no server function, no proxy and no API key. The server only calls the same API through `fetchPointByName` (`/v1/points/<name>`, three-second timeout) to confirm the chosen point when the payment session is opened or replaced.
- `capitalizeCity` upper-cases the first letter of each word, which the API expects.
- A non-OK response throws; a response that fails `inpostApiResponseSchema.safeParse` returns `[]` rather than throwing, so a schema drift at InPost degrades to "no points found".
- `inpostPointsByCityQueryOptions(city)` caches aggressively: `staleTime` one day, `gcTime` two days, keyed by the lower-cased trimmed city, and `enabled` only from three characters.

`inpost.zod.ts` parses each point into `{ address_details, location, location_description, location_type, name, opening_hours, payment_available, status }`. `location_description` is transformed from `null` to `""`.

The UI lives in `.../delivery/locker/inpost/`:

| File                                            | Role                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------ |
| `inpost-provider.tsx`                           | `InpostProvider` / `useInpost`; debounces the city input by 400 ms |
| `inpost-selector.tsx`                           | The dialog with the MapLibre map and the sidebar                   |
| `inpost-map-updater.tsx`                        | Recentres the map when the point set changes                       |
| `inpost-marker.tsx`                             | One marker per point                                               |
| `inpost-popup.tsx`                              | `HoveredPointPopup` for the hovered marker                         |
| `inpost-sidebar.tsx`, `inpost-sidebar-item.tsx` | The scrollable point list                                          |
| `inpost-point-details.tsx`                      | The selected point's address and opening hours                     |

The map is `react-map-gl/maplibre` with the Carto Voyager basemap (`https://basemaps.cartocdn.com/gl/voyager-gl-style/style.json`) and `maxBounds` clamped to Poland. Clicking the map background clears `lockerId`. The chosen point's `name` is what goes into the form, so `checkout.locker_id` and `order.locker_id` hold an InPost point name such as `KRA01A`.

## How delivery reaches the order

1. `deliveryMethod` (the method id) is submitted with the checkout form.
2. `resolveDelivery` refuses a method the shop does not offer, a locker method without a locker and a locker InPost does not list, keeps `lockerId` only for a locker method, notes whether InPost could be asked about it, and reads the method's `price`.
3. `prepareCreateCheckoutBatch` writes the method to `checkout.delivery_method_id`, `lockerId` to `checkout.locker_id` and the unanswered lookup to `checkout.locker_unconfirmed`; `createStripeSession` adds a delivery line item for the price when it is above zero, named for the method's type in the shopper's language (`deliveryLineItem` in `pages.checkout`).
4. `prepareFulfillCheckoutBatch` copies `deliveryMethodId`, `lockerId`, `lockerUnconfirmed` and `customerNote` from the checkout snapshot onto the new `order` row, and computes `shippingTotal = Math.max(session.amount_total - itemsSubtotal, 0)`.
5. For a locker or courier order, an admin can book the parcel with InPost from the order page. The shipment's id and status land on `order.inpost_shipment_id` and `order.inpost_shipment_status`, its tracking number and link on `order.tracking_number` and `order.tracking_url`, and its PDF label is downloaded from the same card. See [InPost](/docs/integrations/inpost#shipments-through-shipx).

## Delivery in the emails

`src/modules/order/order.email.utils.ts` renders the delivery block. `resolveDeliveryMethodLabel` appends the locker id for a locker method:

```ts
if (method.type === "locker" && lockerId !== undefined && lockerId !== "") {
  return `${method.name} · ${lockerId}`
}
```

The estimated delivery is copy, looked up by delivery type. The fulfilment time is read from the catalogue when the email is built:

```ts
const deliveryType = context?.deliveryMethod?.type ?? "courier"

return {
  estimatedDelivery: messages.estimatedDelivery[deliveryType],
  fulfillmentTime: describeOrderFulfillmentTime(fulfillmentTimes, messages),
}
```

`getFulfillmentTimeAttributesByVariantId` in `attribute-on-product.server.ts` reads the `czas-realizacji` attribute (`FULFILLMENT_TIME_ATTRIBUTE_HANDLE`) the way the product page shows it: the variant's own value when the variant has attributes of its own, otherwise the product's, and none when the value is blank. `resolveOrderLineFulfillmentTimes` in `src/modules/order/order.fulfillment-time.utils.ts` labels each value in the order's locale, and a product without one takes `fulfillmentTime.fallback`, 10 business days. `describeOrderFulfillmentTime` reads the number and unit of each label (hours, days, business days, weeks or months, in Polish or English) and states the longest, followed by `fulfillmentTime.note`, which says it runs from the acceptance of the order and that the order ships in one parcel. When a label has no number and unit it can compare, such as "na zamówienie", it lists every product with its own time instead. The email therefore states the period itself, as Article 21 of the Consumer Rights Act requires, rather than pointing at product pages that can change after the order.

`messages/{locale}/emails.order-confirmation.json` has the `fulfillmentTime` object with `fallback` and `note`, and an `estimatedDelivery` object keyed by `courier`, `locker` and `in_store`. Both repeat § 7 of the terms of service: the fulfilment time stated on each product page, or up to 10 business days when a page gives none, with the longest applying to the whole order, then up to 4 business days in transit with InPost, or collection at the atelier once the fulfilment time ends. Changing the fallback or the transit time is a message-catalogue edit and an edit to § 7 in `/admin/content`, and changing a product's time is an edit to its `czas-realizacji` attribute. The shipped email keeps its own `deliveryTiming` in `emails.order-shipped.json`, which gives the same up to 4 business days after dispatch for the courier and the locker, and collection once the shopper is told for in-store orders; the checkout's courier and locker steps state the same transit time.

## What is not there

- No carrier but InPost: shipments, labels and tracking go through InPost's ShipX API only, and an order picked up at the atelier has none.
- No automatic order updates from the carrier: InPost's status is shown on the order and refreshed on demand or by InPost's webhook, but marking the order shipped and delivered stays with the admin. Without an InPost shipment, `order.tracking_number` and `order.tracking_url` are what the admin types into the ship dialog.
- No shipping rules: the price is a flat per-method amount with no weight, size, basket-value or destination logic. The only destination rule is the `DELIVERY_COUNTRY_CODES` check.
- No store locations table for `in_store`.
- No admin screen for couriers or delivery methods — rows are managed directly in D1.
