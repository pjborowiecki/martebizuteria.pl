## Route

Two files:

- `src/routes/checkout.tsx` — the layout. It validates the search params, reads the `pages.checkout` messages in its loader and renders `CheckoutHeader` plus an `Outlet`. It is **not** inside `_storefront`, so it has no shop navigation or footer.
- `src/routes/checkout.index.tsx` — the page. It first learns the state of the Checkout Session the browser holds or the address names, as described under [Coming back to the checkout](#coming-back-to-the-checkout), and then shows either the success panel or the guarded form. Its loader reads `listDeliveryMethodsQuery()` and `getSalesStatusQuery()` while the layout reads the messages, so the client-only form finds the delivery methods in the cache when it mounts and the guard already knows whether sales are paused. `loaderDeps` passes only `success`, so moving between steps does not run it again, and on `?success=true` it reads nothing. Each read ends with `.catch(noop)`: if one fails, the page still renders and the form or the guard asks again itself.

The search schema tolerates junk:

```ts
const checkoutSearchSchema = z.object({
  session_id: z.string().trim().max(CHECKOUT_SESSION_ID_MAX_LENGTH).optional(),
  step: z.preprocess(coerceStep, z.number().int().min(MIN_STEP).max(MAX_STEP).default(DEFAULT_STEP)),
  success: z.preprocess(coerceSuccess, z.boolean().optional()),
})
```

`coerceStep` returns `DEFAULT_STEP` (1) for anything that is not an integer between 1 and 4; `coerceSuccess` accepts `true` and the string `"true"`. So `/checkout?step=banana` lands on step 1 instead of erroring. `session_id` is the Checkout Session id, capped at `CHECKOUT_SESSION_ID_MAX_LENGTH` (255) characters, the limit `src/integrations/stripe/stripe.constants.ts` defines once for every input that carries a Checkout Session id. Stripe puts it into the session's `return_url`, and the payment step adds it itself when a payment is confirmed on the page.

There is no sign-in requirement. Guest checkout is the default path; a signed-in session is picked up server-side by `getRequestSession()` when the Stripe session is created.

## The guard

`CheckoutGuard` in `checkout.index.tsx` renders only once the session check below has answered. It waits for the basket to rehydrate, then bounces bad baskets back:

```ts
const isEmpty = hydrated && itemCount === 0
const hasStockIssues = hydrated && !isChecking && hasUnavailableItems
useEffect(() => {
  if (isEmpty || hasStockIssues) {
    void navigate({ params: (prev) => prev, replace: true, to: "/cart" })
  }
}, [hasStockIssues, isEmpty, navigate])
```

Until the basket is hydrated, checked once and valid it renders `CheckoutFormSkeleton`. The check runs again when the payment step mounts, when the basket or the held session changes, and when the payment step is refused with `INSUFFICIENT_INVENTORY`, but not when the shopper comes back to the tab or the connection comes back. The checkout has no realtime socket, so a stock change elsewhere does not re-run it either. Those later re-checks keep the form mounted (`isFirstCheck` is false then); only the pay button waits for them through `isChecking`. Every check counts the stock the browser's own open checkout holds as available to it, so the reservation the payment step makes, or a reload with that reservation in place, does not send the shopper back to the basket, and a trip to the banking app to approve a BLIK payment runs no check at all; see [Cart](/docs/features/cart). A basket whose stock went to another shopper, for example after the hold ran out, is still sent back. The form itself is wrapped in `ClientOnly` and `Suspense`, because `CheckoutForm` lives in `checkout-form.client.tsx` and imports `@tanstack/react-start/client-only`.

The guard also reads `getSalesStatusQuery()`. While sales are paused it renders `CheckoutSalesPaused` (`src/presentation/components/custom/checkout/components/checkout-sales-paused.tsx`) in place of the skeleton and the form: "Orders are paused", a sentence saying the cart will wait until the shop reopens, and a link back to the cart, from `salesPaused` and `checkoutForm.backToCart` in `pages.checkout`. An empty basket is still sent to the cart. The confirmation of a paid session is decided before the guard renders, so a pause never hides it. The guard reads the switch with `refetchOnWindowFocus` and `refetchOnReconnect` off, like the availability check: it asks when the page loads and when the server refuses a session with `SALES_PAUSED`, but not when the shopper comes back from the banking app, so a payment approved there on a session opened before the pause keeps its form and reaches the confirmation. See [Pausing sales](#pausing-sales).

## Coming back to the checkout

A stored session is not assumed to be payable. `useCheckoutSessionEntry` in `src/presentation/components/custom/checkout/hooks/use-checkout-session-entry.ts` runs in `CheckoutPage` before the guard. On `/checkout` it reads the id stored under `marte-checkout-session` once, when the page mounts; on `?success=true` it takes `session_id` from the address. While it holds an id without an answer the page renders `CheckoutFormSkeleton`, so neither the availability check nor the payment step, and with it the update path, runs before the session's state is known. The answer comes from `getCheckoutSessionStatus` through `checkoutSessionStatusQuery`, which asks once per visit (`staleTime: "static"`, `gcTime: 0`, two retries):

| Answer       | On `/checkout`                                                                                                                                                                                                                                         | On `?success=true`                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `complete`   | When the basket still holds what the session was opened for, replaces the address with `?success=true&session_id=<id>`, so `CheckoutSuccess` clears the basket and the stored id and shows the order; otherwise the same as `closed`, basket untouched | `CheckoutSuccess`, which clears the basket only while it still holds what the session was opened for |
| `open`       | The guard and the form; the payment step continues the session through the update path as before                                                                                                                                                       | An `errors.paymentNotCompleted` toast and `?step=4`, where the payment step continues the session    |
| `processing` | Kept like `open`: the guard and the form, where the payment step waits for the bank instead of replacing the session (see the payment step below)                                                                                                      | `?step=4` without the toast, where the payment step waits for the bank                               |
| `closed`     | `forgetCheckoutSessionId(id)` drops the id, if it is still the stored one, before the guard renders, so the payment step opens a fresh checkout                                                                                                        | The same, then the toast and `?step=4`                                                               |

So a phone that discarded the tab while the shopper approved a BLIK payment in the banking app, a late return from Przelewy24 and `/checkout` opened in another tab after paying all show the confirmation of the paid session. The guard no longer counts the sold piece against its buyer, and no second payment form appears. Stripe sends a redirected payment back to the `return_url` whether or not it went through, so a shopper who leaves the bank's page without paying is no longer told the payment succeeded: the basket stays, and the same checkout continues on the payment step. A reload while the banking app still asks the shopper to approve a BLIK payment, or while the bank is still processing one, keeps that session, and the payment step waits for the bank, so the shopper is not asked to approve a second payment. If the state cannot be learned, the page does what it did before the check existed: the checkout on `/checkout`, the confirmation on `?success=true`. The id is read once per visit, so the payment step storing a replacement session does not send the page back to the skeleton.

A shopper who pays by redirect or BLIK and never comes back leaves the paid session stored. The stored session records the basket it was opened for, and `wasCheckoutSessionOpenedForAnotherCart` compares it with the basket once the basket has loaded from storage. When the shopper returns days later with other pieces in the basket, the paid session is forgotten and a fresh checkout opens for the basket as it is, so neither the old confirmation nor its clearing of the basket takes over the new purchase. When the basket is still exactly what was paid for, the page shows that order's confirmation and clears it, as it would have had the shopper come back at once. The comparison is by variant and quantity, not price, so a price the shop changed since does not hide a paid basket and offer it for payment a second time.

The confirmation makes the same comparison before it clears anything. A `?success=true&session_id=<id>` address can be opened again long after the payment, from a restored tab, the history or a bookmark, when the basket already holds other pieces. `CheckoutSuccess` clears the basket, the draft, the stored id and the abandonment flag only while `isCheckoutSessionHeldForCart` finds that the browser still holds the session the address names, opened for exactly the basket as it is now. Otherwise it shows the order and leaves all of them alone: the stored id of a newer checkout stays where it is, and a paid session stored for another basket is forgotten on the next visit to `/checkout`, as above. An address without a `session_id` names no session, so it clears nothing either. The comparison runs again whenever the basket changes, so a basket that loads from storage after the page mounts is still compared.

On `/checkout` the check acts on its first answer only. The payment step navigates to the confirmation itself, with `?success=true&session_id=<id>` added to the address, both after a payment it confirmed on the page and when the update path reports the session it continued as paid (see the payment step below). Before it navigates it writes `complete` into `checkoutSessionStatusQuery` for that session, so the confirmation follows without another request. When that is the session the check found, the cache write reaches the check too, but it has already acted, so the payment step's navigation is the only one and the page keeps the form until the address names the session.

`getCheckoutSessionStatus` in `src/modules/checkout/use-cases/get-checkout-session-status.ts` is a public `POST` server function behind `withRateLimit("checkout-status", RATE_LIMITS.CHECKOUT)`, since it can call Stripe. It returns only `"complete"`, `"open"`, `"processing"` or `"closed"`; the confirmation is addressed by the session id the browser already holds. Like the confirmation route it treats holding the session id as proof that the browser started the checkout, so a paid session is `"complete"` whoever asks, including a signed-in shopper whose bank returns them to a browser where they are not signed in; the confirmation route shows that order to the same holder of the id anyway. All it keeps from a request that is not signed in as the account owning a checkout is whether that account's unpaid session is still open or waiting for the bank: such a request gets `"closed"`, the answer an id no payment carries gets, and the update path would refuse it the session in any case. A `failed` payment is `"closed"` and a `succeeded` or `refunded` one `"complete"`, both without a Stripe call. For a `pending` payment it retrieves the session with its payment intent expanded: `complete`, which includes an asynchronous payment still processing, is passed on to anyone, `open` to a guest checkout's holder and to the owning account, and an `expired` session first goes through `releaseExpiredCheckoutSession`, the guarded release the update path runs, so the fresh checkout finds the stock free before the expiry webhook arrives. An `open` session whose payment is under way is `"processing"`, under the same ownership rule as `open`. `isCheckoutSessionProcessing` in `src/integrations/stripe/stripe.utils.ts` decides that from the payment intent: `processing`, or `requires_action` with the next action `blik_authorize`, a BLIK payment waiting for approval in the banking app. An action that only the page which started it can finish, such as a card's 3-D Secure challenge or the Przelewy24 redirect, does not count, so a session the shopper left in the middle of one is replaced as before instead of keeping them waiting until it expires. A payment the bank declined puts the intent back to `requires_payment_method`, and the session is `open` again.

## The four steps

`src/presentation/components/custom/checkout/lib/checkout-steps.ts` is the single definition of the steps and their fields:

| Index | `id`       | `titleKey`       | Validated fields                                                                                                                                                |
| ----- | ---------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0     | `contact`  | `steps.contact`  | `email`, `phone`                                                                                                                                                |
| 1     | `billing`  | `steps.billing`  | `firstName`, `lastName`, `address1`, `address2`, `postalCode`, `city`, `countryCode`, `province`, `sameAsShipping`, `companyInvoice`, and the `billing*` fields |
| 2     | `delivery` | `steps.delivery` | `deliveryMethod`, `lockerId`                                                                                                                                    |
| 3     | `payment`  | `steps.payment`  | none                                                                                                                                                            |

`getFurthestReachableStepIndex(values)` parses the whole form with `checkoutSchema` and returns the index of the first step that owns an invalid field, or the last index when everything validates. The provider clamps the requested `?step=` to that index, so a visitor cannot deep-link past an incomplete step.

Each step is code-split. `checkout-step-loaders.client.ts` maps each `id` to a `lazy()` import of its component, so the payment step and its Stripe bundle only load when the visitor reaches step 4.

## Form state

`checkout-form-provider.tsx` builds the `react-hook-form` instance:

```ts
const form = useForm<CheckoutFormSchema>({
  defaultValues: { ...EMPTY_CHECKOUT_VALUES, ...draftValues },
  mode: "onTouched",
  resolver: zodResolver(checkoutSchema),
})
```

`useCheckoutForm()` exposes `activeStepIndex`, `control`, `getValues`, `setValue`, `trigger`, `isFormValid`, `isPending`, `onNext`, `onEdit`, `checkoutSession` and `setCheckoutSession`. `onNext(stepId)` triggers validation for just that step's fields and, on success, navigates to `?step=<next>` inside a `startTransition`. `onEdit(stepId)` jumps back without validating.

## The draft

`checkout-draft.ts` persists the form to **`sessionStorage`** under `marte-checkout-draft`, in a versioned envelope:

```ts
interface CheckoutDraftEnvelope {
  readonly v: number
  readonly values: Partial<CheckoutFormSchema>
}
```

`SCHEMA_VERSION` is `1` and `isDraftEnvelope` rejects anything with a different `v`, so an old draft is ignored rather than merged. Every accessor is wrapped in `try`/`catch` and returns `undefined` when storage is unavailable, so the form still works in a private window. The provider reads the draft once into the form's default values (`EMPTY_CHECKOUT_VALUES` presets both country codes to `"PL"`), so every step sees the shopper's details and only the step they can reach from its first render; `useCheckoutDraftPersistence` saves on every `watch` change; `CheckoutSuccess` calls `clearCheckoutDraft()` when it clears the basket the session paid for.

Because it is `sessionStorage`, the draft survives a reload but not a new tab — unlike the basket, which is `localStorage`.

The same file keeps the id of the browser's open Checkout Session in **`localStorage`** under `marte-checkout-session`, as JSON together with the basket the session was opened for: `{ cart, sessionId }`, where `cart` is the session's lines as sorted `variantId:qty` pairs. The provider's `setCheckoutSession` saves it with `saveCheckoutSession(session)` whenever the payment step receives a session, and `loadCheckoutSessionId` reads it back; a value without both fields, such as a bare id an older build stored, counts as no session. Unlike the draft it is shared by every tab and outlives the tab that wrote it, because the session it names holds stock for the whole browser: a reload, a second tab or a return from the basket continue that session instead of opening another. Saving dispatches a `checkout-session-change` event, and `subscribeToCheckoutSessionId` listens for it and for the `storage` event other tabs fire, so `useCartAvailability` follows the id. `clearCheckoutDraft()` forgets the id together with the draft. `forgetCheckoutSessionId(id)` forgets only the id, and only while it is still the stored one, keeping the shopper's details for the fresh checkout, when the session check finds the stored session closed or paid for another basket.

## Validation

`src/modules/checkout/checkout.zod.ts` builds `checkoutSchema` from a Drizzle-derived address schema plus the checkout-only fields. Its messages are **message keys**, not sentences: `"validation.addressRequired"`, `"validation.phoneInvalid"` and so on, resolved against `pages.checkout` by `validation-field-error.tsx`.

Five rules go beyond field presence, all in the `superRefine`:

1. **Destination country.** `countryCode` must be one of `DELIVERY_COUNTRY_CODES` in `src/modules/delivery-method/delivery-method.constants.ts`, currently only `PL`, or the field reports `validation.countryNotDelivered`. No table records the countries the shop serves; the set holds what the address form offers, the delivery methods reach and § 7 of the terms states. The server functions parse with the same schema, so a request for another country is refused before the handler runs. The billing country is not restricted.
2. **Polish postal code.** `POSTAL_CODE_PATTERNS` currently contains only `PL: /^\d{2}-\d{3}$/u`. A billing country with no pattern passes.
3. **Billing address.** When `sameAsShipping` is `false`, each `billing*` field becomes required and the billing postal code is pattern-checked too.
4. **Company invoice.** When `companyInvoice` is `true`, `billingCompanyName` is required (`validation.companyNameRequired`, at most `COMPANY_NAME_MAX_LENGTH`, 256, characters) and so is `billingNip` (`validation.nipRequired`), which must also be a valid Polish NIP or the field reports `validation.nipInvalid`. The schema's `overwrite(normalizeNip)` strips spaces, hyphens and a leading `PL` first, so `526-000-12-46` and `PL5260001246` both reach the rule, and the server, as `5260001246`. `isValidNip` then wants ten digits whose first nine, weighted 6, 5, 7, 2, 3, 4, 5, 6, 7, sum to a number whose remainder modulo 11 is the tenth digit; a remainder of 10 matches no digit. While the box is unticked neither field is checked.
5. **Locker.** When `deliveryMethodType === "locker"`, `lockerId` must be a non-empty string. This only guides the form: the server decides from the method's type in the database, see [Server side](#server-side).

The country field of the address step is read-only, so the step offers as a shipping address only the saved addresses in one of `DELIVERY_COUNTRY_CODES`; picking one abroad would leave a country the shopper cannot change. Every saved address is still offered for billing.

Below the billing address the step offers `checkoutForm.companyInvoice`, "I want an invoice for a company". Ticking it shows the company name field (`autocomplete="billing organization"`, `maxLength` 256) and the NIP field (`inputMode="numeric"`) with a note that the invoice goes to the company at the billing address, so a buyer whose company is elsewhere unticks "Same as shipping address" and enters it. The labels, the note and the three validation messages are in `pages.checkout` in both languages. The app records what to invoice; it does not issue the invoice, which the owner does from the accounting system.

Phone numbers are validated with `libphonenumber-js/mobile`'s `isValidPhoneNumber(value, "PL")`, so a mobile number must be valid for Poland.

## Delivery step

`_steps/delivery-step.tsx` reads `listDeliveryMethodsQuery()` and groups the rows by `type` in the fixed order of `DELIVERY_METHODS` (`courier`, `locker`, `in_store`). Choosing a type sets `deliveryMethodType` and, when that type has exactly one method, auto-selects `deliveryMethod`; otherwise it clears it. The card subtitle shows the lowest price of the group, `deliverySubsteps.free` when that price is zero, or `from <price>` when the group has more than one method.

The sub-step depends on the type: `DeliveryCourier`, `DeliveryLocker` (with the InPost map) or `DeliveryInStore` (copy only). Each states the delivery time of § 7 of the terms of service before the shopper pays: the courier and locker steps give the fulfilment time stated on the product page, then up to 4 business days from dispatch with InPost, and the in-store step says the order is ready by the end of that fulfilment time. See [Shipping and delivery](/docs/features/shipping-and-delivery).

## The summary

`CheckoutSummary` (`checkout-summary.tsx`) sits beside the steps and lists the basket lines, each with `checkoutSummary.priceChanged` when the shop changed its price after it was added (see [Cart](/docs/features/cart)). Until there is a payment session it estimates the totals from the basket: the item subtotal from `cartTotal()`, whose prices the availability check keeps current, the price of the chosen delivery method (`checkoutSummary.deliveryCalculated` until one is chosen), and the total and VAT from `computeOrderTotals`. Once the payment step holds a session that `isCheckoutSessionFor` matches with the basket and the form, the summary shows that session's `totals` instead: the subtotal, discount, delivery, total and VAT the server computed from database prices when it built the Stripe session, which are the amounts Stripe charges. While a changed basket or form waits for its replacement session the summary goes back to the estimate, and the payment form stays hidden until the replacement arrives.

The discount comes from the form, not from component state. The summary reads `discountCode` and asks the server what the code takes off the current basket through `validateDiscountCodeQuery`, keyed by the code, the item subtotal, the delivery cost and the e-mail. The e-mail joins the check only once the contact step is complete, so typing it never sends a request. A code restored from the draft is therefore checked and shown again after a reload, and choosing another delivery method checks it again. A code that no longer applies stays on screen with its reason and is not taken off.

Without a matching session, the total is shown only when the check for the current basket has answered. While it is in flight, or after it failed, the total reads `checkoutSummary.totalAwaitingCode` and the VAT line is hidden, because the summary cannot know whether the server will apply the code; a failed check also offers a retry. See [Discounts](/docs/features/discounts).

## Payment step

`_steps/payment-step.client.tsx` drives the Stripe Elements checkout. `useCheckoutSessionLoader` is the interesting part:

- `isCheckoutSessionFor(session, { items, values })` from `src/integrations/stripe/stripe.checkout.ts` compares two fingerprints: `buildCheckoutLinesFingerprint` (sorted `variantId:qty:unitPrice` triples, for the session from the lines the server quoted and for the basket from its current prices) and `buildCheckoutValuesFingerprint(values)` (the form values as sorted JSON).
- `sessionMatches` is true when both fingerprints equal the stored session's. When they do not, `ensureCheckoutSession` updates the session the browser holds, read with `loadCheckoutSessionId()` at that moment, or the one on screen when storage is unavailable, and creates a session only when there is neither. After a reload, in a second tab or back from the basket the page has no session in memory, so once the session check has found the stored session open it continues it through the update path, which replaces it and releases its stock once, instead of reserving the basket a second time. When the server refuses the update with `SESSION_CLOSED`, because the session expired, was already replaced or belongs to another account since the check, or because the checkout is too old to edit (see [Limits on holding stock](#limits-on-holding-stock)), it creates a fresh checkout instead, which asks for a new Turnstile token. When it answers `SESSION_COMPLETE`, because the session was paid in the moment between the check and the update, no fresh checkout is opened: `ensureCheckoutSession` and `resetCheckoutSession` throw `PaidCheckoutSessionError` naming that session, and the step records it as `complete` and navigates to its confirmation. Only a stored session opened for another basket is forgotten instead, with a fresh checkout for this one, as on arrival. When it answers `SESSION_PROCESSING`, because the bank is still confirming the session's payment, nothing is replaced, expired or opened either, however old the checkout is, because the server checks for a payment under way before it applies the edit window: they throw `ProcessingCheckoutSessionError` (`stripe.checkout.processing.ts`) naming that session, and `useCheckoutSessionOutcome` records it as `processing` in `checkoutSessionStatusQuery` and replaces the payment form with `PaymentAwaitingBank`, which shows the `paymentAwaitingBank` copy. It asks `checkoutSessionStatusQuery` again on mounting, every eight seconds while the tab is in front and when the shopper comes back to the tab (`staleTime: 0`, `refetchInterval`), slowly enough to stay under the ten calls a minute the `checkout-status` rate limit allows. `complete` opens the confirmation as for `SESSION_COMPLETE`. `open`, a payment the bank declined, and `closed`, a session that expired meanwhile, toast `errors.paymentNotCompleted` and load the payment step again, which continues or replaces the session as usual.
- Every session carries `expiresAt`, set on arrival to `CHECKOUT_SESSION_LIFETIME_SECONDS` later, the same hold the server asks Stripe for. `useCheckoutSessionExpired` arms a timer for it, and when it fires the step replaces the payment form with `PaymentError` showing the `paymentExpired` copy and a `restartPayment` button that calls `resetCheckoutSession`. Nothing renews the hold by itself, so a tab left open does not keep the stock from other shoppers.
- Every session that comes back goes through `applyCurrentPrices(session.lines)` before it is stored, so the basket takes the prices the session was quoted at and the two match. A price the shop changes while the step is open reaches the basket through the availability check, the lines fingerprint no longer matches, and the session is replaced at the new price; the summary and the submit button follow it. No session is opened for an empty basket. A delivery price edited after the session opened is not picked up until something else changes, and the summary shows the delivery the session charges.
- The code entered in `CheckoutSummary` is the form value `discountCode`, so applying or removing it changes the values fingerprint and the session is updated. See [Discounts](/docs/features/discounts).
- If `isCheckoutComplete(getValues())` is false it calls `onEdit(CHECKOUT_STEP_ID.CONTACT)` and sends the visitor back to step 1.
- `inFlightRef` prevents concurrent session calls.
- Opening a checkout needs a Turnstile token. `useTurnstileToken` keeps an empty `div` above the step's content, hidden by `empty:hidden` while Turnstile shows nothing in it, and gives `ensureCheckoutSession` and `resetCheckoutSession` a `requestTurnstileToken` that renders a fresh `checkout` widget there with `issueTurnstileToken` (see [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile)). They call it only when they create a session, so continuing the session the browser holds, or waiting for the bank to confirm its payment, runs no check; once its checkout is `CHECKOUT_SESSION_LIFETIME_SECONDS` old the server refuses the update with `SESSION_CLOSED`, and the fresh checkout they open instead asks for a token. Most shoppers never see the widget; one Turnstile wants to challenge sees it above the payment skeleton until they pass. A request made after the step has left the page is refused with `BOT_CHECK_FAILED`.
- On error it shows `PaymentError` and toasts `t(getCheckoutErrorKey(error))`, which maps `BOT_CHECK_FAILED`, `DELIVERY_METHOD_UNAVAILABLE`, `INSUFFICIENT_INVENTORY`, `INVALID_PRICE`, `LOCKER_REQUIRED`, `PRODUCT_NOT_FOUND`, `SALES_PAUSED`, `SESSION_CLOSED`, `SESSION_COMPLETE`, `SESSION_PROCESSING`, `TOO_MANY_OPEN_CHECKOUTS`, `VARIANT_NOT_FOUND` and `UNKNOWN_ERROR` to keys under `errors.` (`src/integrations/stripe/stripe.errors.ts`). Neither a `PaidCheckoutSessionError` nor a `ProcessingCheckoutSessionError` gets this far, because the step opens the confirmation or waits for the bank instead. `useCheckoutSessionFailure` does both, and for `INSUFFICIENT_INVENTORY` and `PRODUCT_NOT_FOUND` it also invalidates `CART_QUERY_KEYS.AVAILABILITY`, so the availability check runs again and the guard sends the shopper to the basket, where each short line shows what is left and a line whose product is gone or no longer published shows that it is no longer available. That is how a shopper whose hold ran out while another shopper bought the piece reaches the basket, since returning to the tab no longer re-runs the check, and how one whose piece the shop archived mid-checkout learns which line to remove. For `DELIVERY_METHOD_UNAVAILABLE` and `LOCKER_REQUIRED` it invalidates `DELIVERY_METHOD_QUERY_KEYS.ALL` and calls `onEdit(CHECKOUT_STEP_ID.DELIVERY)`, so a shopper whose method the shop switched off after the page loaded, or whose draft still names it, is back on the delivery step with the methods offered now and the toast saying why. For `SALES_PAUSED` it invalidates `STORE_SETTING_QUERY_KEYS.SALES`, so the guard reads the switch again and replaces the form with the paused notice.

The `PaymentElement` is configured in `PAYMENT_ELEMENT_OPTIONS`: accordion layout, `billingDetails: "never"` (M'Arte collects the address itself), wallets and Link disabled, and `paymentMethodOrder` from `CHECKOUT_PAYMENT_METHOD_ORDER` — `["card", "blik", "p24"]`. The submit button reads `checkoutForm.placeOrderFor` with `checkout.total.total.amount`, the total the Stripe Checkout SDK reports for the session, formatted by Stripe, and `checkoutForm.placeOrder` until the SDK has loaded.

Confirming calls `confirmCheckoutSession`, which runs `checkout.confirm({ billingAddress: buildCheckoutContact(values), redirect: "if_required" })`. Any error other than code `paymentFailed` is treated as recoverable: the session the browser holds is reset and the visitor is asked to retry. A reset of a session that has expired meanwhile is refused with `SESSION_CLOSED`, and the visitor gets a fresh checkout; a reset that finds the session paid opens its confirmation instead, and one that finds its payment still under way waits for the bank, both without the retry toast. On success the page records the `checkoutSession` it paid as `complete` in `checkoutSessionStatusQuery` and navigates to `?success=true&session_id=<id>` with its id, so a payment confirmed on the page, such as a card that needs no 3-D Secure step, carries `session_id` too. A payment that leaves the page for a redirect comes back through the session's `return_url`, which carries the same two parameters on the checkout path of the shopper's locale, built with `buildLocalizedUrl` on the origin the checkout request came in on (see [Payments](/docs/features/payments)). Stripe sends the shopper there whether or not the payment went through, and the session check decides between the confirmation and the payment step.

`CheckoutSuccess` mounts once the session check has answered `complete`, or could not answer, or the address names no session. It clears the basket, the draft and the abandonment flag only when the basket still holds what the session it names was opened for (see [Coming back to the checkout](#coming-back-to-the-checkout)), and refreshes the account's orders and overview in a separate effect either way. With a `session_id` it loads the order through `getOrderConfirmationQuery`, which asks again every 1.5 seconds, five times, while the webhook has not written the order yet, showing `pendingTitle` meanwhile and `unavailableTitle` if the order never appears. Its query function turns the server's empty answer into a `NOT_FOUND` error, because TanStack Query treats `undefined` data as a final failure and would not retry it. Without a `session_id` it shows the generic confirmation. The confirmation shows the shipping address recorded on the order, so a later edit to the customer's address book does not change it; orders placed before addresses were recorded on orders fall back to the checkout's address. The description does not say the confirmation email is on its way: the Stripe webhook sends it only after the order row exists, and the page cannot see whether Resend accepted it. It asks the shopper to get in touch and quote the order number if the email has not arrived within a few minutes.

## Server side

`createCheckoutSessionFn` and `updateCheckoutSessionFn` (`src/integrations/stripe/stripe.actions.ts`) are thin: they validate with the schemas in `stripe.actions.schemas.ts`, which take at most `CART_LINE_QUANTITY_MAX` of each line and, for a new checkout, a `turnstileToken`, apply `withRateLimit("checkout-create" | "checkout-update", RATE_LIMITS.CHECKOUT)` — ten calls per minute per client address — and dynamically import the handler so the Stripe server SDK stays out of the client bundle.

`handleCreateCheckoutSession` in `stripe.actions.server.ts` first calls `admitNewCheckout`. That calls `assertSalesOpen()`, which refuses the request with `ERROR_CODES.CONFLICT` and `SALES_PAUSED` while sales are paused (see [Pausing sales](#pausing-sales)), then checks the Turnstile token and counts the open checkouts of the shopper's address and email (see [Limits on holding stock](#limits-on-holding-stock)). A refusal from any of them means none of the steps below runs. Otherwise it runs this order:

1. `resolveDelivery(data.checkoutValues)` — reads the chosen method through `getOfferedDeliveryMethodByIdQuery` (`delivery-method.accessors.ts`), which applies `offeredDeliveryMethod`, the rule `listDeliveryMethods` lists by: the method and its courier are both active. An unknown method, a switched-off one or one whose courier is switched off is refused with `ERROR_CODES.VALIDATION` and `DELIVERY_METHOD_UNAVAILABLE` before the Stripe customer, the catalogue or the stock is touched. The method's `type` in the database, not the `deliveryMethodType` the browser sends, decides whether a locker is needed: a `locker` method needs a `lockerId` that, trimmed, matches `INPOST_POINT_NAME_PATTERN` (`src/integrations/inpost/inpost.constants.ts`: 3 to 32 letters, digits, `_` or `-`, starting with a letter or digit), or the request is refused with `LOCKER_REQUIRED`. The pattern checks the shape of an InPost point name; the server does not ask InPost whether the point exists. Any other type drops `lockerId`, so a locker picked before switching to the courier never reaches the order. The trimmed locker id goes on with the checkout values, and the method's `price` is the shipping cost.
2. `validateAndCalculateItems(data.items, [])` — loads the `published` products by handle with inventory through `getPublishedProductsWithInventoryByHandles`, then for each line resolves the variant and throws an `AppError` with a `CHECKOUT_ERROR_CODES` code when the product or variant is missing, the price fails `isSellPriceCentsValid`, or `inventory.quantityAvailable` plus the stock already held by the session being replaced (none for a new checkout) is below `qty`. **The price used from here on is `variant.price` from the database. The request carries no basket price at all: `cartItemSchema` has no `price` or `rawPrice`.**
3. `resolveCheckoutDiscount(...)` checks `checkoutValues.discountCode` against the subtotal of the database prices and the shipping cost, and returns nothing when the code does not apply. See [Discounts](/docs/features/discounts).
4. `reserveInventoryForItems(validatedItems)` — a reservation guarded on the stock available when it runs, see [Inventory](/docs/features/inventory).
5. `createCheckout(...)` — inserts the `address` rows and the `checkout` row, with the request's client address in `client_address`, in one D1 batch. With a code from step 3 the same batch claims one of its uses in `discount_claim` and sets `discount_id` only when the claim was written, so a code whose remaining uses other open checkouts hold is dropped like any code that no longer applies, and the session is built at the full price. See [Discounts: Holding a use while the shopper pays](/docs/features/discounts#holding-a-use-while-the-shopper-pays).
6. `createStripeSession(...)` — `ui_mode: "elements"`, `mode: "payment"`, `expires_at` set `CHECKOUT_SESSION_LIFETIME_SECONDS` (32 minutes, Stripe's 30-minute minimum plus a margin) from now, so an abandoned checkout returns its stock after 32 minutes instead of after Stripe's 24-hour default, line items plus a delivery line when the cost is above zero, named for the method's type in the shopper's language from `deliveryLineItem` in `pages.checkout`, metadata carrying `checkoutId`, `discountCode`, `discountTotal`, `locale`, `userId` and the chunked item list, and, when a discount applies, a one-time Stripe coupon in `discounts`, tagged with the checkout id and deleted again if Stripe refuses the session.
7. `createPendingPayment(...)` — a `payment` row with `status: "pending"`, `transaction_id` set to the Stripe session id and `reserved_lines` set to the `{ qty, variantId }` lines step 4 reserved.
8. `scheduleProductCatalogInvalidation()`.

If anything after step 4 throws, `releaseInventoryForItems` gives the reservation back before the error propagates, and when steps 6 or 7 throw for a checkout holding a code, `releaseDiscountClaims` gives that use back too.

It returns `clientSecret`, `sessionId` and `amount` (Stripe's `amount_total`, also stored on the payment) with `lines`, each `{ variantId, qty, unitPrice }` at the database price, and `totals` from `computeOrderTotals` over those lines, the shipping cost and the discount. Those are the figures the session's line items and coupon were built from and the ones fulfilment records on the order, and the client shows them in the summary. `handleUpdateCheckoutSession` returns the same for the replacement session.

`handleUpdateCheckoutSession` additionally verifies ownership (`context.userId` must match the current session when the checkout belongs to a user) and refuses to change a checkout that can no longer be paid. A mismatch is `FORBIDDEN` with `SESSION_CLOSED`, so a browser that signed out, or another account on the same browser, starts its own checkout while the old session waits out its hold. A guest's checkout has no owner to match, and when the request continuing it is signed in, as after a guest reaches the payment step and then signs in, the update hands the checkout to that account: the replacement session gets the account's `userId` and its Stripe customer from `ensureStripeCustomer`, and the checkout's `user_id` is set in the supersede batch below. The order then belongs to the account, and the shopper keeps the stock the guest session held. A payment that has `succeeded` or been `refunded`, checked before ownership because the confirmation page shows that order to whoever holds the session id anyway, and an old session Stripe already reports `complete` before its webhook has arrived, are refused with `ERROR_CODES.CONFLICT` and `SESSION_COMPLETE`, and the client shows the confirmation instead of a second payment form. Otherwise, unless the `checkout` row and its `payment` are both `pending` and Stripe still reports the old session as `open`, it throws `ERROR_CODES.CONFLICT` with `SESSION_CLOSED` before touching Stripe or stock; an unknown session id gets `NOT_FOUND` with the same reason. The client then starts a fresh checkout. When Stripe already reports the old session `expired` but its webhook has not arrived yet, the refusal first runs `releaseCheckout` for that session, the guarded batch the webhook runs, so the fresh checkout finds the stock free and the webhook later finds nothing left to release. An `open` old session whose payment `isCheckoutSessionProcessing` reports under way is refused with `ERROR_CODES.CONFLICT` and `SESSION_PROCESSING` before anything changes, so the session, its stock and its claim stay as they are and the bank can still complete the payment the shopper started; the client waits for it (see the payment step above).

Only once the old session is known to be open and payable does it call `assertSalesOpen()`. While sales are paused it refuses with `SALES_PAUSED` before it validates the edited cart, claims a code or creates a replacement, so the old session keeps its stock and its claim until it is paid or expires. Because a paid or closed session is answered first, a shopper who paid before the pause still reaches the confirmation, and the request that is refused is the fresh checkout the browser opens for a closed session.

Next, `assertCheckoutStillEditable` refuses a checkout created `CHECKOUT_SESSION_LIFETIME_SECONDS` or more ago with `SESSION_CLOSED`, although its session is still `open`, because every update gives the replacement a fresh hold. The refusal first expires that session with `stripe.checkout.sessions.expire`, so it can no longer be paid, and passes the expired session to `releaseExpiredCheckoutSession`, so the fresh checkout, which needs a new Turnstile token, finds the stock free. When Stripe will not expire it, for example because it was paid in that moment, the update fails and the stock stays with the session. Coming after the pause check, it leaves a paused shop's open sessions payable.

Otherwise it reads the old session's reserved lines out of its metadata, validates the edited cart against the available stock plus what the old session holds, resolves the delivery and the discount again, claims the code for the checkout with `claimCheckoutDiscount` (a checkout already holding it keeps its claim; a code whose uses are held elsewhere is dropped), and creates the replacement Stripe session. A delivery `resolveDelivery` refuses leaves the old session, its stock and the checkout row as they were. It then expires the old session, so it can no longer be paid, and calls `supersedeCheckoutSession`, which moves the `payment` row onto the new session id, records the edited cart's lines in its `reserved_lines` and releases the old lines in one D1 batch, only while that payment and its checkout are still `pending`. The same batch releases the checkout's claims of every code but the one the replacement applies. For a signed-in request it also sets the checkout's `user_id` to that account, only while the checkout has no owner, so an owned checkout never changes hands. If creating the replacement or retiring the old session fails, `releaseUnappliedDiscountClaims` gives back any claim except that of the code in `checkout.discount_id`, which the old session still uses. If the expiry webhook released the checkout first, the update is refused and the replacement expired; if its release lands after the move, it finds no pending payment on the old session and changes nothing. Either way the old lines are released once. Last, it reserves the edited cart and updates the checkout row including `discount_id`; if either fails, `releaseCheckout` fails the checkout on the replacement session and returns what was reserved.

## Pausing sales

The owner can stop taking orders during an incident or a holiday with the Sales switch on the admin dashboard (see [Admin dashboard](/docs/features/admin-dashboard#sales-switch)). The switch is the `sales_paused` column of the single `store_setting` row, declared in `src/modules/store-setting/store-setting.schema.ts` and created and seeded by `20261005420000_store_settings.sql`. `isSalesPaused()` in `store-setting.accessors.ts` reads it from D1 on every checkout request, with no cache in between, so a pause applies to the next request on every Worker instance. A missing row counts as open.

While the switch is on:

- `handleCreateCheckoutSession` refuses every new checkout, and `handleUpdateCheckoutSession` every edit of an open one, with `ERROR_CODES.CONFLICT` and `SALES_PAUSED`, before any stock is reserved or any discount use is claimed. The toast reads `errors.salesPaused`: "We have paused orders for a while, so this payment cannot go ahead. Your cart will wait until we reopen."
- A Checkout Session opened before the pause is left as it is. It can still be paid until it expires, at most `CHECKOUT_SESSION_LIFETIME_SECONDS` after it opened, and its webhook fulfils it as usual, because fulfilment never reads the switch. An unpaid one returns its stock when it expires.
- Every storefront page shows `SalesPausedBanner` (`src/presentation/components/custom/sales-paused-banner.tsx`) under the navigation with `pages.cart.salesPaused.banner`, the cart summary says that checkout is closed and offers no checkout link (see [Cart](/docs/features/cart)), and the checkout shows `CheckoutSalesPaused` instead of the form.

The storefront reads the switch through the public `getSalesStatus` server function in `src/modules/store-setting/use-cases/get-sales-status.ts`, with `getSalesStatusQuery()` keyed `STORE_SETTING_QUERY_KEYS.SALES`. The `_storefront` and checkout loaders read it, so the notice is in the server-rendered page. Changing the switch calls `scheduleSalesStatusInvalidation()`, which publishes that key to the storefront hub and `STORE_SETTING_QUERY_KEYS.ADMIN.SALES` to the admin hub, so every open storefront tab shows or hides the notice and blocks or reopens the cart within moments (see [Realtime invalidation](/docs/architecture/realtime-invalidation)). The checkout has no realtime socket and learns of a pause when it next loads or when the server refuses its session.

## Limits on holding stock

Guest checkout is open to anyone, and every new checkout holds its stock for up to `CHECKOUT_SESSION_LIFETIME_SECONDS`. Four limits keep one visitor or script from holding the catalogue:

- **At most `CART_LINE_QUANTITY_MAX` (10) of one piece per order.** `cartItemSchema` refuses a larger `qty` in both server functions, before a handler runs. The basket never sends one: the cart store keeps every line between one and the limit, a basket stored before the limit existed is brought down to it when it loads, the basket's plus button stops there with `pages.cart.quantityLimit` ("You can order up to 10 of one piece. For a larger order, please contact us."), and the product page's quantity picker stops at the lower of the stock and the limit. See [Cart](/docs/features/cart).
- **A Turnstile bot check before every new checkout.** `admitNewCheckout` passes the request's `turnstileToken` to `verifyTurnstileToken` with the action `checkout`, the hostname of the origin the request came in on and the shopper's `cf-connecting-ip`. A token siteverify does not confirm for that action on that host is refused with `ERROR_CODES.FORBIDDEN` and `BOT_CHECK_FAILED` before anything is counted, reserved or created, and the toast reads `errors.botCheckFailed`: "We could not finish the check that keeps bots out of checkout. Please try again." Siteverify accepts a token once, so a script cannot replay one.
- **Edits only within `CHECKOUT_SESSION_LIFETIME_SECONDS` of opening.** An update of an open checkout needs no token and is not counted, and each one opens a replacement session with a fresh hold, so `handleUpdateCheckoutSession` edits a checkout only while it is younger than one session's lifetime. An older checkout is refused with `SESSION_CLOSED` even while its session is open: the refusal first expires that session and returns its stock, and the browser opens a new checkout, which needs a new token and is counted. One passed check therefore holds stock for at most twice the session lifetime, about an hour.
- **At most `OPEN_CHECKOUTS_PER_CLIENT_ADDRESS_MAX` (5) open checkouts per client address and `OPEN_CHECKOUTS_PER_EMAIL_MAX` (3) per email.** `countOpenCheckouts` in `src/modules/checkout/use-cases/count-open-checkouts.server.ts` reads, in one query over the pending checkouts, those whose `client_address` is the request's and those whose email, in lower case, is the form's. A checkout counts while it and its payment are `pending` and the payment row was written or moved to a new session less than `CHECKOUT_SESSION_LIFETIME_SECONDS` ago, the longest any of its sessions stays open, so a checkout whose expiry webhook is late stops counting when its session expires. When either count has reached its limit the request is refused with `ERROR_CODES.TOO_MANY_REQUESTS` and `TOO_MANY_OPEN_CHECKOUTS`, before any stock is reserved, and the toast reads `errors.tooManyOpenCheckouts`. The address is `clientAddress(headers)` from `src/lib/rate-limit.ts`, the key the rate limits use: `cf-connecting-ip`, with an IPv6 address reduced to its /64.

A shopper's browser keeps one open checkout and continues it (see [Coming back to the checkout](#coming-back-to-the-checkout)), so a real shopper meets the open-checkout limits only when paying from several browsers or devices at once, or when several shoppers share one address. The count and the reservation are separate statements, so requests that arrive together can each pass the count; the rate limit of ten new checkouts a minute per address and the single-use token bound how far that goes.

`createCheckout` stores the address in `checkout.client_address`. Fulfilment sets it back to `NULL` when the checkout completes, and the release when it fails, so the address is kept only while the checkout is open.

## Metadata chunking

Stripe caps a metadata value at 500 characters, so `checkout-metadata.zod.ts` splits the item JSON across `items0`, `items1`, … and reassembles it:

```ts
export const readCheckoutSessionItemsJson = (metadata: Record<string, string | undefined> | null | undefined): string => {
  ...
  const legacy = metadata[ITEMS_CHUNK_KEY_PREFIX]
  if (legacy !== undefined && legacy !== "") {
    return legacy
  }
  ...
}
```

A single `items` key is still read for sessions created before the chunking, and a missing metadata object yields `"[]"`.

## The checkout row

`checkout` (`src/modules/checkout/checkout.schema.ts`) holds `email`, `client_address` (only while the checkout is `pending`, see [Limits on holding stock](#limits-on-holding-stock)), `customer_note`, `locker_id`, `delivery_method_id`, `shipping_address_id`, `billing_address_id`, `billing_company_name`, `billing_nip`, `cart_id`, `discount_id`, `user_id` and a `status` of `pending | processing | completed | failed | abandoned`. In practice the code uses `pending`, `completed` (fulfilled) and `failed` (released); `processing` and `abandoned` are never written.

When `sameAsShipping` is true, `prepareCreateCheckoutBatch` points both address columns at the **same** `address` row rather than duplicating it.

`billing_company_name` and `billing_nip` hold the company a business buyer asked to be invoiced. `resolveCompanyInvoice` hands both batches the two values only while `companyInvoice` is `true`, so a company typed and then unticked is never stored, and `prepareUpdateCheckoutDeliveryBatch` sets them back to `NULL` when an edit unticks the box. They travel with the rest of the form through `createCheckoutSessionFn` and `updateCheckoutSessionFn`, and because the form's fingerprint changes, editing them replaces the open Stripe session like any other edit. Fulfilment copies them onto the order through `getCheckoutForFulfillment`, and the confirmation email reads them through `getCheckoutEmailContext`.

`discount_id` holds the code that `resolveCheckoutDiscount` accepted on the server and the checkout claimed. `prepareCreateCheckoutBatch` writes it once the claim in its own batch exists, and `prepareUpdateCheckoutDeliveryBatch` rewrites it on every session update, setting it to `NULL` when no code applies. Fulfilment reads it back through `getCheckoutForFulfillment`.

`prepareUpdateCheckoutDeliveryBatch` uses an `INSERT … SELECT … ON CONFLICT DO UPDATE` whose source row is the pending checkout, so an address upsert simply does nothing if the checkout is no longer pending. `updateCheckoutDelivery` then inspects the last statement's `returning()` and throws `ERROR_CODES.CONFLICT` when no row was updated.

An address joins the customer's address book only while its `saveShippingAddress` or `saveBillingAddress` box is ticked: both batches leave `user_id` null otherwise, and a delivery update that unticks the box sets it back to null. When an update saves an address, the same batch clears `is_default` on the customer's other addresses, guarded by the pending checkout like the upserts, so the customer keeps one default.

Thirty days after a checkout ends, as `failed`, as `abandoned` or as `pending` with no `payment` row, the daily retention clean-up erases its e-mail, note, company, NIP, parcel locker and account, deletes the addresses no account owns and any discount hold it still kept, and leaves the row and its payment; see [Data retention](/docs/guides/data-retention#ended-checkouts).
