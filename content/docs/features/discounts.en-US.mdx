Discount codes work end to end. An admin creates them on `/admin/coupons`, a shopper enters one in the checkout summary, the server checks it again while it builds the Stripe session, and fulfilment records the redemption. The code lives in `src/modules/discount/`.

## The tables

`discount` and `discount_redemption` (`src/modules/discount/discount.schema.ts`):

```ts
export const discount = sqliteTable(
  "discount",
  {
    code: text("code").notNull().unique(),
    description: text("description", { length: 512 }),
    endsAt: timestamp("ends_at"),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    isActive: integer("is_active", { mode: "boolean" }).default(true).notNull(),
    maxDiscountAmount: integer("max_discount_amount"),
    minOrderTotal: integer("min_order_total"),
    perCustomerLimit: integer("per_customer_limit"),
    startsAt: timestamp("starts_at"),
    type: text("type", { enum: DISCOUNT_TYPES }).notNull(),
    usageCount: integer("usage_count").default(0).notNull(),
    usageLimit: integer("usage_limit"),
    value: integer("value").notNull(),
    ...timestamps(),
  },
  (table) => [index("discount_code_idx").on(table.code), index("discount_isActive_idx").on(table.isActive)],
)

export const discountRedemption = sqliteTable(
  "discount_redemption",
  {
    amount: integer("amount").notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    orderId: text("order_id").references(() => order.id, { onDelete: "cascade" }),
    userId: text("user_id").references(() => user.id, { onDelete: "set null" }),
    ...timestamps(),
  },
  (table) => [
    index("discount_redemption_discountId_idx").on(table.discountId),
    index("discount_redemption_discountId_email_idx").on(table.discountId, table.email),
    uniqueIndex("discount_redemption_orderId_unique").on(table.orderId),
  ],
)
```

The three types are `percentage`, `fixed_amount` and `free_shipping` (`DISCOUNT_TYPES` in `discount.constants.ts`). `value` is a single integer: a whole percentage for `percentage`, an amount in minor units for `fixed_amount`, and ignored for `free_shipping`. The limit columns are nullable, and null means no limit: `usage_limit` caps redemptions overall, `per_customer_limit` caps them per e-mail address, `min_order_total` is the minimum item subtotal in minor units, and `max_discount_amount` caps what a percentage may take off.

`discountRelations` declares `many(cart)`, `many(checkout)`, `many(order)` and `many(discountRedemption)`. `cart`, `checkout` and `order` each carry a `discount_id` column, and `order` additionally has `discount_total`. The `description` column, the three rule columns, the `is_active` index and the `discount_redemption` table come from `20260930200000_discount_rules_and_redemptions.sql`.

## Rules

`discount.utils.ts` holds the two pure functions that both the storefront check and the server use:

- `resolveDiscountRejection` checks, in order, `is_active`, `starts_at`, `ends_at`, `usage_count` against `usage_limit`, the customer's earlier redemptions against `per_customer_limit`, and the item subtotal against `min_order_total`. It returns the first failure as a `DISCOUNT_REJECTION` code (`inactive`, `notStarted`, `expired`, `exhausted`, `alreadyUsed` or `minOrderNotMet`), or `undefined`.
- `calculateDiscountAmount` returns the shipping total for `free_shipping`, `min(value, itemsSubtotal)` for `fixed_amount`, and for `percentage` the rounded share of the item subtotal, capped by `max_discount_amount` and by the subtotal itself.

The seventh rejection code, `notFound`, comes from the validator when no row matches. Codes are compared after `normalizeDiscountCode`, which trims and upper-cases them. A rejection is a code rather than a sentence, and the checkout renders it from `pages.checkout.discount.rejection.<code>`.

## At checkout

`CheckoutDiscountField` (`src/presentation/components/custom/checkout/components/checkout-discount-field.tsx`) sits in `CheckoutSummary`, below the totals. Submitting it calls `validateDiscountCode` (`use-cases/validate-discount-code.ts`) with the code, the e-mail, the item subtotal and the shipping cost. The function has no `authorized` middleware, so a guest can try a code, and `use-case-authorization.test.ts` lists it among the public use cases. It answers with `applied` (code, `discountId`, type and amount) or with a `rejection`, and nothing more. The per-customer check uses the e-mail from the form, or the signed-in user's when the form has none.

When a code applies, `CheckoutSummary` keeps the result in state, shows a discount line in totals computed by `computeOrderTotals`, and writes the code into the form's `discountCode` field; removing the code clears the field. `checkoutSchema` declares `discountCode: zod.string().trim().max(DISCOUNT_CODE_MAX_LENGTH).optional()`, and no step validates it.

The validation response is only a preview. `handleCreateCheckoutSession` and `handleUpdateCheckoutSession` call `resolveCheckoutDiscount` (`discount.checkout.server.ts`) with `checkoutValues.discountCode`, the item subtotal computed from database prices, and the shipping cost. It applies the same rules again. A code that no longer applies is logged and dropped, and one that would take nothing off is dropped, instead of failing the checkout. The resulting `discountId` is written to `checkout.discount_id`.

## In the Stripe session

Stripe has no negative line item, so `toSessionDiscounts` in `src/integrations/stripe/stripe.actions.server.ts` creates a one-time coupon for the computed amount, and `createStripeSession` sets it as `params.discounts`:

```ts
const coupon = await stripe.coupons.create({
  amount_off: discount.amountMinorUnits,
  currency: STRIPE_CURRENCY,
  duration: "once",
  name: discount.code,
})

return [{ coupon: coupon.id }]
```

A `free_shipping` code therefore becomes an `amount_off` equal to the shipping cost, and the `"Shipping"` line item stays on the session. Every session created or replaced with a code gets a new coupon, and none is deleted. The session metadata also carries `discountCode` and `discountTotal`, which the webhook does not read. Stripe's own promotion codes are not enabled.

## On fulfilment

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) loads the checkout with its `discount` row, recalculates the amount with `calculateDiscountAmount` from the metadata lines and the delivery method's price, and passes it to `computeOrderTotals`, which caps the discount at items plus shipping. `prepareFulfillCheckoutBatch` copies `discount_id` onto the order and writes `discount_total`. The rules are not checked again at this point, because the customer has already paid.

After the batch, `fulfillCheckout` hands `recordDiscountRedemption` (`discount.redeem.server.ts`) to `scheduleBackgroundWork`. It inserts a `discount_redemption` row with `onConflictDoNothing` on `order_id`, and increments `discount.usage_count` only when that insert wrote a row. When it reports success, `fulfillCheckout` records a `discount.redeemed` audit entry. A failure is logged and swallowed: recording the redemption is kept apart from the order batch so that it can never cost an order.

| Column or table        | Written by                                                         | Read by                                                                                   |
| ---------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `cart.discount_id`     | nothing                                                            | nothing                                                                                   |
| `checkout.discount_id` | `prepareCreateCheckoutBatch`, `prepareUpdateCheckoutDeliveryBatch` | `getCheckoutForFulfillment`                                                               |
| `order.discount_id`    | `prepareFulfillCheckoutBatch`                                      | nothing                                                                                   |
| `order.discount_total` | `prepareFulfillCheckoutBatch`                                      | the checkout confirmation, the account order page, the admin order page, the order e-mail |
| `discount.usage_count` | `recordDiscountRedemption`                                         | `resolveDiscountRejection`, `resolveDiscountStatus`, `getAdminDiscountStats`              |
| `discount_redemption`  | `recordDiscountRedemption`                                         | `countCustomerRedemptions`, `getAdminDiscountStats`                                       |

## The admin coupons page

`/admin/coupons` is `src/routes/admin.coupons.tsx`. Its loader primes `getAdminDiscountsPageQuery({})` and `getDiscountStatsQuery()`, and it renders `CouponStats` and `CouponListTable` from `src/presentation/components/custom/pages/admin/coupons/`.

- `CouponStats` shows four cards from `getAdminDiscountStats`: codes usable right now, all codes, redemptions, and the total amount given away.
- `CouponListTable` lists codes newest first, with a search over `code` and `description`. Each row shows type, value, minimum order, usage against the limit, expiry and a status from `resolveDiscountStatus`: `active`, `scheduled`, `expired`, `exhausted` or `disabled`. The row menu edits or deletes the code.
- `CouponFormDialog` validates with `discountZodSchemas.adminDiscountFormValues`, the schema the server functions parse, and shows only the fields that apply to the chosen type. Amounts are entered in minor units.

| Use case                      | Guard                               | Effect                                                                                                |
| ----------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `get-admin-discounts-page.ts` | `authorized({ order: ["read"] })`   | A searchable page of codes, `ADMIN_DISCOUNTS_PAGE_SIZE` (25) by default                               |
| `get-admin-discount-stats.ts` | `authorized({ order: ["read"] })`   | The four card values                                                                                  |
| `create-discount.ts`          | `authorized({ order: ["update"] })` | Inserts the row; a taken code throws `CONFLICT` with `DISCOUNT_CODE_TAKEN`; audits `discount.created` |
| `update-discount.ts`          | `authorized({ order: ["update"] })` | Updates the row and sets emptied fields to `null`; audits `discount.updated`                          |
| `delete-discounts.ts`         | `authorized({ order: ["update"] })` | Deletes by id; audits `discount.deleted`                                                              |

After a mutation, `useCouponActions` refreshes `DISCOUNT_QUERY_KEYS.ADMIN.ALL` through `syncQueryInvalidation`, which also tells other tabs of the same browser.

## What is still open

These are the seams the current code leaves, not recommendations about product design:

1. **The cart column.** `cart.discount_id` is neither written nor read; the applied code lives only in the checkout form.
2. **Permissions.** There is no `discount` resource in `src/integrations/better-auth/auth.access.ts`, so the coupons functions reuse the `order` read and update permissions.
3. **Realtime invalidation.** `ADMIN_REALTIME_QUERY_PREFIXES` has no `DISCOUNT_QUERY_KEYS` entry and there is no `scheduleDiscountInvalidation()` in `realtime-invalidation.catalog.server.ts`, so a change made from another browser does not reach a coupons page that is already open.
4. **Paging.** `CouponListTable` requests the first page only and has no pager, so it shows at most 25 codes.
5. **Deletion.** Deleting a code also deletes its `discount_redemption` rows (`onDelete: "cascade"`). `checkout.discount_id` and `order.discount_id` have no foreign key and keep the old id, and a pending checkout whose code was deleted is fulfilled without a discount in its totals, which `reconcileTotals` logs as a mismatch with the amount Stripe charged.
