description: "Discount codes from the admin coupons page to the checkout field, the use an open checkout holds, the Stripe coupon and the redemption recorded with the order."
---

Discount codes work end to end. An admin creates them on `/admin/coupons`, a shopper enters one in the checkout summary, the server checks it again and claims one of its uses while it builds the Stripe session, and fulfilment turns that claim into a redemption in the batch that creates the order. The code lives in `src/modules/discount/`.

## The tables

`discount`, `discount_redemption` and `discount_claim` (`src/modules/discount/discount.schema.ts`):

```ts
export const discount = sqliteTable(
  "discount",
  {
    code: text("code").notNull().unique(),
    description: text("description", { length: 512 }),
    endsAt: timestamp("ends_at"),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    isActive: integer("is_active", { mode: "boolean" }).default(true).notNull(),
    maxDiscountAmount: integer("max_discount_amount"),
    minOrderTotal: integer("min_order_total"),
    perCustomerLimit: integer("per_customer_limit"),
    startsAt: timestamp("starts_at"),
    type: text("type", { enum: DISCOUNT_TYPES }).notNull(),
    usageCount: integer("usage_count").default(0).notNull(),
    usageLimit: integer("usage_limit"),
    value: integer("value").notNull(),
    ...timestamps(),
  },
  (table) => [index("discount_code_idx").on(table.code), index("discount_isActive_idx").on(table.isActive)],
)

export const discountRedemption = sqliteTable(
  "discount_redemption",
  {
    amount: integer("amount").notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    orderId: text("order_id").references(() => order.id, { onDelete: "cascade" }),
    userId: text("user_id").references(() => user.id, { onDelete: "set null" }),
    ...timestamps(),
  },
  (table) => [
    index("discount_redemption_discountId_idx").on(table.discountId),
    index("discount_redemption_discountId_email_idx").on(table.discountId, table.email),
    uniqueIndex("discount_redemption_orderId_unique").on(table.orderId),
  ],
)

export const discountClaim = sqliteTable(
  "discount_claim",
  {
    checkoutId: text("checkout_id")
      .references(() => checkout.id, { onDelete: "cascade" })
      .notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    ...timestamps(),
  },
  (table) => [
    uniqueIndex("discount_claim_checkoutId_discountId_unique").on(table.checkoutId, table.discountId),
    index("discount_claim_discountId_email_idx").on(table.discountId, table.email),
  ],
)
```

The three types are `percentage`, `fixed_amount` and `free_shipping` (`DISCOUNT_TYPES` in `discount.constants.ts`). `value` is a single integer: a whole percentage for `percentage`, an amount in minor units for `fixed_amount`, and ignored for `free_shipping`. The limit columns are nullable, and null means no limit: `usage_limit` caps redemptions overall, `per_customer_limit` caps them per e-mail address, `min_order_total` is the minimum item subtotal in minor units, and `max_discount_amount` caps what a percentage may take off.

`discountRelations` declares `many(cart)`, `many(checkout)`, `many(discountClaim)`, `many(order)` and `many(discountRedemption)`. `cart`, `checkout` and `order` each carry a `discount_id` column, and `order` additionally has `discount_total`. The `description` column, the three rule columns, the `is_active` index and the `discount_redemption` table come from `20260930200000_discount_rules_and_redemptions.sql`.

A `discount_claim` row is a use of a code that an open checkout holds: the checkout, the code and the e-mail it was claimed for, kept from the moment the checkout's Stripe session is built with the code until the session is paid, expires, fails or is replaced (see [Holding a use while the shopper pays](#holding-a-use-while-the-shopper-pays)). `discount_claim_checkoutId_discountId_unique` lets a checkout hold each code once, and `discount_claim_discountId_email_idx` counts a code's holds, all of them or one address's. Both foreign keys cascade, so deleting a checkout or a code deletes its claims. The table comes from `20261005400000_discount_claims.sql`.

## Rules

`discount.utils.ts` holds the pure functions that decide what a code is worth. The storefront check and the server both use the first two:

- `resolveDiscountRejection` checks, in order, `is_active`, `starts_at`, `ends_at`, `usage_count` against `usage_limit`, the customer's earlier redemptions (`redeemedByCustomer` on the row) against `per_customer_limit`, and the item subtotal against `min_order_total`. It returns the first failure as a `DISCOUNT_REJECTION` code (`inactive`, `notStarted`, `expired`, `exhausted`, `alreadyUsed` or `minOrderNotMet`), or `undefined`.
- `resolveDiscountPreviewRejection` is the checkout preview's verdict. It returns what `resolveDiscountRejection` returns and, when that passes, `held` while `usage_count` plus the uses other checkouts hold (`heldByOtherCheckouts`) reaches `usage_limit`, or while the customer's redemptions plus the uses their other checkouts hold (`heldForCustomer`) reach `per_customer_limit`. These are the sums the claim compares (see [Holding a use while the shopper pays](#holding-a-use-while-the-shopper-pays)), so the preview refuses what the claim would refuse at that moment.
- `calculateDiscountAmount` returns the shipping total for `free_shipping`, `min(value, itemsSubtotal)` for `fixed_amount`, and for `percentage` the rounded share of the item subtotal, capped by `max_discount_amount` and by the subtotal itself.
- `resolveAppliedCheckoutDiscount` is the checkout's verdict. It takes the row (or none), the item subtotal, the shipping cost and the current time. It returns nothing when there is no row, when a rule rejects the code (which it logs) or when the amount is zero or less; otherwise it returns the applied discount.

The rules read one row. `getDiscountByCodeForCustomerQuery(code, email)` (`discount.accessors.ts`) selects the discount with exactly that code and, in the same statement, `redeemedByCustomer`: a correlated count of its `discount_redemption` rows whose lower-cased e-mail equals the trimmed, lower-cased e-mail it was given. Without an e-mail the count is 0 and no redemption is read. The builder returns a relational `findFirst`, so callers await it on its own: inside a `db.batch` an unknown code would throw instead of resolving to `undefined` (see [Drizzle ORM and D1: Batches](/docs/integrations/drizzle-orm-d1#batches)). SQLite finds the code through `discount_code_unique` and counts from the covering `discount_redemption_discountId_email_idx`, which `query-plans.integration.test.ts` checks.

The checkout's preview reads its row with `getDiscountByCodeForPreviewQuery({ code, email, heldSessionId })`, the same statement with two more correlated counts of `discount_claim`: `heldByOtherCheckouts`, the code's claims, and `heldForCustomer`, those of them claimed for the same lower-cased e-mail (0 without an e-mail). Given the Stripe session id the browser holds, it leaves out the claims of that session's checkout, found through `payment.transaction_id`, so a shopper's own open checkout never counts against them; an id that matches no payment leaves every claim in. SQLite counts the claims from `discount_claim_discountId_email_idx` and finds the payment through `payment_transactionId_unique`, which `query-plans.integration.test.ts` also checks.

The validator adds two rejection codes: `notFound`, when no row matches, and `held`, from `resolveDiscountPreviewRejection`. Codes are compared after `normalizeDiscountCode`, which trims and upper-cases them. A rejection is a code rather than a sentence, and the checkout renders it from `pages.checkout.discount.rejection.<code>`.

## At checkout

`validateDiscountCode` (`use-cases/validate-discount-code.ts`) checks a code against a basket: it takes the code, an optional e-mail, the basket's lines (`variantId` and `qty`, at most `CART_LINES_MAX`), and optionally the id of the chosen delivery method and the Stripe session id of the checkout the browser holds. The browser sends no prices or totals. The function prices the lines with `getSellPricesByVariantIds`, the current sell prices the cart's availability check also uses, and leaves out a line whose variant has no valid price. Only a `free_shipping` code reads the delivery method, through `getOfferedDeliveryMethodByIdQuery`, and takes off its price; before a method is chosen, or for one the shop no longer offers, it takes off nothing. The verdict comes from `resolveDiscountPreviewRejection`, so a code whose remaining uses other checkouts hold is refused as `held` instead of shown as applying. The function has no `authorized` middleware, so a guest can try a code, and `use-case-authorization.test.ts` lists it among the public use cases. It sits behind `withRateLimit("discount-validate", RATE_LIMITS.CHECKOUT)`, ten checks per minute per client address in a bucket of its own, so the field cannot be used to try codes, or which addresses already used one, at speed; past the limit it answers `TOO_MANY_REQUESTS` and the field shows `pages.checkout.discount.rejection.error`. It answers with `applied` (code, `discountId`, type and amount) or with a `rejection`, and nothing more. The per-customer check uses the e-mail it is sent, or the signed-in user's when none is sent; an empty e-mail counts as none, and a malformed one fails validation. The limiter's counter is one D1 round trip before the handler runs. After it, with an e-mail the session is not read at all, and the code with its counts and the variants' prices are two statements sent side by side. Without one, it reads the session first: for a signed-in shopper that is one round trip before the same two, with the account's e-mail; a guest has no session cookie, so Better Auth answers without reading D1. A `free_shipping` code that passes the rules adds one round trip for its delivery method.

The same file exports the two ways the checkout calls it:

- `validateDiscountCodeMutation` backs the Apply button. Its `mutationFn` always calls the server, never a cached answer, and then stores the answer with `setQueryData` under the key of `validateDiscountCodeQuery` for the same input.
- `validateDiscountCodeQuery({ code, deliveryMethodId, email, heldSessionId, lines })` is the summary's query; `DiscountCheckBasket` is that input without the code. Its key is `DISCOUNT_QUERY_KEYS.VALIDATION` (`["discount", "validate"]`) followed by that input, and `staleTime` is `DISCOUNT_QUERY_STALE_MS` (one minute), so the summary shows the answer Apply just stored without asking again. With no code the query is skipped (`skipToken`).

`CheckoutDiscountField` (`src/presentation/components/custom/checkout/components/checkout-discount-field.tsx`) sits in `CheckoutSummary`, below the totals, while the form has no code. It is a `react-hook-form` form validated by `discountZodSchemas.checkoutCodeFormValues`. It sends the code with the summary's `DiscountCheckBasket`, so Apply stores its answer under the key the summary reads. A rejected code stays in the field with its reason, a failed request shows `pages.checkout.discount.rejection.error`, and typing clears either message. An accepted code is written into the checkout form's `discountCode` field, which the draft keeps in `sessionStorage`.

`CheckoutSummary` keeps no copy of the result. It reads `discountCode` from the form and runs `validateDiscountCodeQuery` with the basket's lines, the id of the chosen delivery method and the session id `loadCheckoutSessionId()` reads, which it follows with `useSyncExternalStore` and `subscribeToCheckoutSessionId` like `useCartAvailability`. A code restored after a reload is therefore checked and shown again, changing a quantity or the delivery method checks it again, and so does the payment step storing the session it opened, which then no longer counts that checkout's own claim. The e-mail goes into the check only once the contact step is complete (`activeStepIndex` is past it). While the shopper is on the contact step the check goes without it, so the server falls back to the signed-in account's address and typing an address never sends a request; moving on checks the code again with the confirmed address.

While the form has a code, `CheckoutDiscountCode` (`checkout-discount-code.tsx`) shows it in place of the field, with what the check said:

| Check              | Code row                                                                      | Discount line | Total                                                             |
| ------------------ | ----------------------------------------------------------------------------- | ------------- | ----------------------------------------------------------------- |
| In flight          | The code and a spinner                                                        | None          | `checkoutSummary.totalAwaitingCode`, no VAT line                  |
| `applied`          | The code and the amount it takes off                                          | The amount    | Items plus delivery, less the discount, from `computeOrderTotals` |
| `rejection`        | The code struck through, with `discount.rejection.<code>` below it            | None          | Items plus delivery                                               |
| The request failed | The code, `discount.checkFailed` and a `discount.retry` button that refetches | None          | `checkoutSummary.totalAwaitingCode`, no VAT line                  |

A code that no longer applies stays in the form and the draft with its reason on screen, and the server drops it when it builds the session (below). From then on the summary shows the discount and total the server quoted for that session, so the total shown is the one charged. When the check fails the summary cannot know which total the server will charge, so it shows none until a retry answers. Removing the code clears `discountCode`. `checkoutSchema` declares `discountCode: zod.string().trim().max(DISCOUNT_CODE_MAX_LENGTH).optional()`, and no step validates it.

The validation response is only a preview. `handleCreateCheckoutSession` and `handleUpdateCheckoutSession` call `resolveCheckoutDiscount` (`discount.checkout.server.ts`) with `checkoutValues.discountCode`, the checkout e-mail, the item subtotal computed from database prices, and the shipping cost. It skips the read for an empty code, reads the row with `getDiscountByCodeForCustomerQuery` in one statement, and passes it to `resolveAppliedCheckoutDiscount`, which applies the same rules again. A code that no longer applies is logged and dropped, and one that would take nothing off is dropped, instead of failing the checkout. A code that passes is then claimed for the checkout, below, and only a claimed code reaches the session and `checkout.discount_id`.

## Holding a use while the shopper pays

The rules compare `usage_count` with `usage_limit`, and redemptions with `per_customer_limit`, but both grow only once a session is paid. Checked alone, every checkout opened while a code had one use left would get the code, and so would every concurrent checkout of a customer limited to one use. So the checkout claims the use before Stripe sees the coupon, the way it reserves stock, and holds it in `discount_claim` while its session can be paid.

`prepareDiscountClaim` in `discount.claim.server.ts` builds the claim as one statement, an `INSERT … SELECT … FROM discount WHERE id = ? … ON CONFLICT (checkout_id, discount_id) DO UPDATE`. The `SELECT` yields the code's row only while `usage_count` plus the claims of other checkouts is below `usage_limit`, and while the customer's redemptions plus their claims in other checkouts, both matched on the lower-cased e-mail, are below `per_customer_limit`; a null limit always passes. It returns the claim it wrote, or nothing. D1 runs one statement at a time, so of two checkouts racing for a code's last use only one gets a row back. A checkout claiming a code it already holds updates the e-mail on its claim, and its own claims never count against it.

| Moment                                   | Where                                                                                     | The claim                                                                                                                       |
| ---------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| A checkout is opened with a code         | `prepareCreateCheckoutBatch`, in the batch that writes the checkout                       | Claimed. The same batch sets `checkout.discount_id` only where the claim exists, and `createCheckout` reports `discountClaimed` |
| An open session is edited                | `claimCheckoutDiscount` in `handleUpdateCheckoutSession`, before the replacement is built | Claimed, or kept if the checkout already holds the code. The old session's claim stays until the swap                           |
| The replacement takes over               | `supersedeCheckoutSession`, in the batch that moves the payment                           | The checkout's claims of every other code are released, only once the payment has moved                                         |
| Building or swapping the session fails   | `releaseDiscountClaims` for a new checkout, `releaseUnappliedDiscountClaims` for an edit  | Released. An edit keeps the claim of the code in `checkout.discount_id`, which the still open old session uses                  |
| The session expires or its payment fails | `prepareReleaseCheckoutBatch`, guarded by the pending payment and checkout like the stock | Released once; a redelivered event finds the checkout already failed                                                            |
| The session is paid                      | `prepareDiscountRedemption`, in the order's batch                                         | Replaced by the redemption (see [On fulfilment](#on-fulfilment))                                                                |

When the claim fails, the code is dropped like any code that no longer applies: `keepClaimedDiscount` logs `Discount <code> not applied to checkout: other checkouts hold the uses its limits allow.`, and the session is created, or replaced, without the coupon and at the full price, which the summary then shows from the server's quote. The checkout's code check counts the same holds, leaving out those of the shopper's own checkout, so a code whose remaining uses are all held is refused with `pages.checkout.discount.rejection.held` before the shopper pays. It is still a preview: a use claimed between the check and the session is caught by the claim, which drops the code as above.

## In the Stripe session

Stripe has no negative line item, so `toSessionDiscounts` in `src/integrations/stripe/stripe.coupons.server.ts` creates a one-time coupon for the computed amount, and `createStripeSession` sets it as `params.discounts`:

```ts
const coupon = await stripe.coupons.create({
  amount_off: discount.amountMinorUnits,
  currency: STRIPE_CURRENCY,
  duration: "once",
  metadata: { checkoutId, source: STRIPE_COUPON_SOURCE },
  name: discount.code,
})

return [{ coupon: coupon.id }]
```

A `free_shipping` code therefore becomes an `amount_off` equal to the shipping cost, and the delivery line item stays on the session. The session metadata also carries `discountCode` and `discountTotal`, which the webhook does not read. Stripe's own promotion codes are not enabled.

Every session created or replaced with a code gets its own coupon, tagged in the coupon's metadata with the checkout id and `source: STRIPE_COUPON_SOURCE` (`"marte_checkout"`). `deleteCheckoutCoupons`, in the same file, deletes it once no session can use it any more:

| Moment                                                               | Caller                                            | The session's coupon                                                                   |
| -------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Stripe refuses to create the session                                 | `createStripeSession`                             | Deleted at once, since no event will ever name it                                      |
| `checkout.session.completed`                                         | The webhook, after `handleFulfillCheckoutSession` | Deleted, also while the payment is still settling                                      |
| `checkout.session.expired`                                           | The webhook, after `handleReleaseCheckoutSession` | Deleted; replacing a session expires the old one, so this covers replaced sessions too |
| `checkout.session.async_payment_succeeded` or `async_payment_failed` | The webhook                                       | Left alone, because the completed event already deleted it                             |

`deleteCheckoutCoupons` reads `session.discounts` and treats a missing or `null` list as no coupons. A coupon given as an id is retrieved first, and only a coupon whose metadata carries `source: "marte_checkout"` and the session's own `checkoutId` is deleted, so a coupon made by hand in the Stripe dashboard is never touched. A failed retrieve or delete is logged and never fails the webhook. When fulfilment throws, the coupon is kept, so Stripe's retry of the event can still delete it. Deleting a coupon does not change an amount Stripe has already applied, so a completed session is charged and refunded as before.

## On fulfilment

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) loads the checkout with its `discount` row, recalculates the amount with `calculateDiscountAmount` from the metadata lines and the delivery method's price, and passes it to `computeOrderTotals`, which caps the discount at items plus shipping. `prepareFulfillCheckoutBatch` copies `discount_id` onto the order and writes `discount_total`. The rules are not checked again at this point, because the customer has already paid.

`fulfillCheckout` appends the statements of `prepareDiscountRedemption` (`discount.redeem.server.ts`) to that batch, so the order and its redemption are one D1 transaction. They delete the checkout's claims, insert a `discount_redemption` row with the amount, the checkout e-mail, the order and the account, and increment `discount.usage_count`. The redemption is an `INSERT … SELECT … FROM discount WHERE id = ?`, so a code deleted while the customer paid writes nothing rather than breaking the foreign key, and none of the three checks a limit: a customer who has paid is never refused, even if the code ran out meanwhile. Because `order.checkout_id` is unique, the batch of a second delivery of the same payment fails as a whole, `fulfillCheckout` finds the order the first one placed and returns without an audit entry, and the use is counted once (see [Payments](/docs/features/payments#fulfilment)). A checkout without a code only has its claims deleted. After the batch, `fulfillCheckout` records a `discount.redeemed` audit entry with the amount, also when D1 committed the batch but answered with an error and the order found afterwards is the one this delivery inserted.

| Column or table        | Written by                                                                                                   | Read by                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `cart.discount_id`     | nothing                                                                                                      | nothing                                                                                                                  |
| `checkout.discount_id` | `prepareCreateCheckoutBatch`, `prepareUpdateCheckoutDeliveryBatch`                                           | `getCheckoutForFulfillment`, `releaseUnappliedDiscountClaims`                                                            |
| `order.discount_id`    | `prepareFulfillCheckoutBatch`                                                                                | nothing                                                                                                                  |
| `order.discount_total` | `prepareFulfillCheckoutBatch`                                                                                | the checkout confirmation, the account order page, the admin order page, the order e-mail                                |
| `discount.usage_count` | `prepareDiscountRedemption`                                                                                  | `resolveDiscountRejection`, `resolveDiscountStatus`, `getAdminDiscountStats`, `prepareDiscountClaim`                     |
| `discount_redemption`  | `prepareDiscountRedemption`                                                                                  | `getDiscountByCodeForCustomerQuery`, `getDiscountByCodeForPreviewQuery`, `getAdminDiscountStats`, `prepareDiscountClaim` |
| `discount_claim`       | `prepareDiscountClaim`; deleted by the release, supersede and redemption batches and the two release helpers | `prepareDiscountClaim`, `getDiscountByCodeForPreviewQuery`                                                               |

## The admin coupons page

`/admin/coupons` is `src/routes/admin.coupons.tsx`. Its loader primes `getAdminDiscountsPageQuery({})` and `getDiscountStatsQuery()`, and it renders `CouponStats` and `CouponListTable` from `src/presentation/components/custom/pages/admin/coupons/`.

- `CouponStats` shows four cards from `getAdminDiscountStats`: codes usable right now, all codes, redemptions, and the total amount given away.
- `CouponListTable` lists codes newest first, with a search over `code` and `description`. Each row shows type, value, minimum order, usage against the limit, expiry and a status from `resolveDiscountStatus`: `active`, `scheduled`, `expired`, `exhausted` or `disabled`. The row menu edits or deletes the code.
- `CouponFormDialog` validates with `discountZodSchemas.adminDiscountFormValues`, the schema the server functions parse, and shows only the fields that apply to the chosen type. Amounts are entered in minor units.

| Use case                      | Guard                               | Effect                                                                                                |
| ----------------------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `get-admin-discounts-page.ts` | `authorized({ order: ["read"] })`   | A searchable page of codes, `ADMIN_DISCOUNTS_PAGE_SIZE` (25) by default                               |
| `get-admin-discount-stats.ts` | `authorized({ order: ["read"] })`   | The four card values                                                                                  |
| `create-discount.ts`          | `authorized({ order: ["update"] })` | Inserts the row; a taken code throws `CONFLICT` with `DISCOUNT_CODE_TAKEN`; audits `discount.created` |
| `update-discount.ts`          | `authorized({ order: ["update"] })` | Updates the row and sets emptied fields to `null`; audits `discount.updated`                          |
| `delete-discounts.ts`         | `authorized({ order: ["update"] })` | Deletes by id; audits `discount.deleted`                                                              |

After a mutation, `useCouponActions` refreshes `DISCOUNT_QUERY_KEYS.ADMIN.ALL` through `syncQueryInvalidation`, which also tells other tabs of the same browser.

## What is still open

These are the seams the current code leaves, not recommendations about product design:

1. **The cart column.** `cart.discount_id` is neither written nor read; the applied code lives only in the checkout form.
2. **Permissions.** There is no `discount` resource in `src/integrations/better-auth/auth.access.ts`, so the coupons functions reuse the `order` read and update permissions.
3. **Realtime invalidation.** `ADMIN_REALTIME_QUERY_PREFIXES` has no `DISCOUNT_QUERY_KEYS` entry and there is no `scheduleDiscountInvalidation()` in `realtime-invalidation.catalog.server.ts`, so a change made from another browser does not reach a coupons page that is already open.
4. **Paging.** `CouponListTable` requests the first page only and has no pager, so it shows at most 25 codes.
5. **Deletion.** Deleting a code also deletes its `discount_redemption` and `discount_claim` rows (`onDelete: "cascade"`). `checkout.discount_id` and `order.discount_id` have no foreign key and keep the old id, and a pending checkout whose code was deleted is fulfilled without a discount in its totals, which `reconcileTotals` logs as a mismatch with the amount Stripe charged.
6. **Holds in the admin.** The coupons table counts redemptions only: `/admin/coupons` shows `usage_count`, so a code whose remaining uses are all held by open checkouts still reads as having uses left.
