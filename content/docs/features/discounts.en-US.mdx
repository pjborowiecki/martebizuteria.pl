Discount codes work end to end. An admin creates them on `/admin/coupons`, a shopper enters one in the checkout summary, the server checks it again and claims one of its uses while it builds the Stripe session, and fulfilment turns that claim into a redemption in the batch that creates the order. The code lives in `src/modules/discount/`.

## The tables

`discount`, `discount_redemption` and `discount_claim` (`src/modules/discount/discount.schema.ts`):

```ts
export const discount = sqliteTable(
  "discount",
  {
    code: text("code").notNull().unique(),
    description: text("description", { length: 512 }),
    endsAt: timestamp("ends_at"),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    isActive: integer("is_active", { mode: "boolean" }).default(true).notNull(),
    maxDiscountAmount: integer("max_discount_amount"),
    minOrderTotal: integer("min_order_total"),
    perCustomerLimit: integer("per_customer_limit"),
    startsAt: timestamp("starts_at"),
    type: text("type", { enum: DISCOUNT_TYPES }).notNull(),
    usageCount: integer("usage_count").default(0).notNull(),
    usageLimit: integer("usage_limit"),
    value: integer("value").notNull(),
    ...timestamps(),
  },
  (table) => [index("discount_code_idx").on(table.code), index("discount_isActive_idx").on(table.isActive)],
)

export const discountRedemption = sqliteTable(
  "discount_redemption",
  {
    amount: integer("amount").notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    orderId: text("order_id").references(() => order.id, { onDelete: "cascade" }),
    userId: text("user_id").references(() => user.id, { onDelete: "set null" }),
    ...timestamps(),
  },
  (table) => [
    index("discount_redemption_discountId_email_idx").on(table.discountId, table.email),
    index("discount_redemption_userId_idx").on(table.userId),
    uniqueIndex("discount_redemption_orderId_unique").on(table.orderId),
  ],
)

export const discountClaim = sqliteTable(
  "discount_claim",
  {
    checkoutId: text("checkout_id")
      .references(() => checkout.id, { onDelete: "cascade" })
      .notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    ...timestamps(),
  },
  (table) => [
    uniqueIndex("discount_claim_checkoutId_discountId_unique").on(table.checkoutId, table.discountId),
    index("discount_claim_discountId_email_idx").on(table.discountId, table.email),
  ],
)
```

The three types are `percentage`, `fixed_amount` and `free_shipping` (`DISCOUNT_TYPES` in `discount.constants.ts`). `value` is a single integer: a whole percentage for `percentage`, an amount in minor units for `fixed_amount`, and ignored for `free_shipping`. The limit columns are nullable, and null means no limit: `usage_limit` caps redemptions overall, `per_customer_limit` caps them per e-mail address, `min_order_total` is the minimum item subtotal in minor units, and `max_discount_amount` caps what a percentage may take off. `toDiscountInsertValues` and `toDiscountUpdateValues` (`discount.persist.utils.ts`) store `max_discount_amount` only for a `percentage` code and leave it `null` for the other two types, whatever the form sends.

`discountRelations` declares `many(cart)`, `many(checkout)`, `many(discountClaim)`, `many(order)` and `many(discountRedemption)`. `cart`, `checkout` and `order` each carry a `discount_id` column, and `order` additionally has `discount_total`. The `description` column, the three rule columns, the `is_active` index and the `discount_redemption` table come from `20260930200000_discount_rules_and_redemptions.sql`. `20261003130000_query_indexes.sql` later dropped the `discount_redemption_discountId_idx` that migration created, because `discount_redemption_discountId_email_idx` starts with the same column, and added `discount_redemption_userId_idx` for the `user_id` foreign key. `query-plans.integration.test.ts` fails when a foreign key has no index, so deleting an account or a code never scans the redemptions.

A `discount_claim` row is a use of a code that an open checkout holds: the checkout, the code and the e-mail it was claimed for, kept from the moment the checkout's Stripe session is built with the code until the session is paid, expires, fails or is replaced (see [Holding a use while the shopper pays](#holding-a-use-while-the-shopper-pays)). `discount_claim_checkoutId_discountId_unique` lets a checkout hold each code once, and `discount_claim_discountId_email_idx` counts a code's holds, all of them or one address's. Both foreign keys cascade, so deleting a checkout or a code deletes its claims. The table comes from `20261005400000_discount_claims.sql`.

## Rules

`discount.utils.ts` holds the pure functions that decide what a code is worth. The storefront check and the checkout both apply `resolveDiscountRejection` and price the code with `calculateDiscountAmount`, and each wraps them in its own verdict: `resolveDiscountPreviewRejection` for the check, `resolveAppliedCheckoutDiscount` for the checkout.

- `resolveDiscountRejection` checks, in order, `is_active`, `starts_at`, `ends_at`, `usage_count` against `usage_limit`, the customer's earlier redemptions (`redeemedByCustomer` on the row) against `per_customer_limit`, and the item subtotal against `min_order_total`. It returns the first failure as a `DISCOUNT_REJECTION` code (`inactive`, `notStarted`, `expired`, `exhausted`, `alreadyUsed` or `minOrderNotMet`), or `undefined`.
- `resolveDiscountPreviewRejection` is the checkout preview's verdict. It returns what `resolveDiscountRejection` returns and, when that passes, `held` while `usage_count` plus the uses other checkouts hold (`heldByOtherCheckouts`) reaches `usage_limit`, or while the customer's redemptions plus the uses their other checkouts hold (`heldForCustomer`) reach `per_customer_limit`. These are the sums the claim compares (see [Holding a use while the shopper pays](#holding-a-use-while-the-shopper-pays)), so the preview refuses what the claim would refuse at that moment.
- `calculateDiscountAmount` returns the shipping total for `free_shipping`, `min(value, itemsSubtotal)` for `fixed_amount`, and for `percentage` the rounded share of the item subtotal, capped by `max_discount_amount` and by the subtotal itself.
- `resolveAppliedCheckoutDiscount` is the checkout's verdict. It takes the row (or none), the item subtotal, the shipping cost and the current time. It returns nothing when there is no row, when a rule rejects the code (which it logs) or when the amount is zero or less; otherwise it returns the applied discount.
- `resolveDiscountStatus` labels a code for the admin list: `disabled` while `is_active` is off, then `expired` once `ends_at` has passed, `exhausted` once `usage_count` reaches `usage_limit`, `scheduled` before `starts_at`, and `active` otherwise. The per-customer limit, the minimum order and the uses open checkouts hold play no part in it.

The rules read one row. `getDiscountByCodeForCustomerQuery(code, email)` (`discount.accessors.ts`) selects the discount with exactly that code and, in the same statement, `redeemedByCustomer`: a correlated count of its `discount_redemption` rows whose lower-cased e-mail equals the trimmed, lower-cased e-mail it was given. Without an e-mail the count is 0 and no redemption is read. The builder returns a relational `findFirst`, so callers await it on its own: inside a `db.batch` an unknown code would throw instead of resolving to `undefined` (see [Drizzle ORM and D1: Batches](/docs/integrations/drizzle-orm-d1#batches)). SQLite finds the code through `discount_code_unique` and counts from the covering `discount_redemption_discountId_email_idx`, which `query-plans.integration.test.ts` checks.

The checkout's preview reads its row with `getDiscountByCodeForPreviewQuery({ code, email, heldSessionId })`, the same statement with two more correlated counts of `discount_claim`: `heldByOtherCheckouts`, the code's claims, and `heldForCustomer`, those of them claimed for the same lower-cased e-mail (0 without an e-mail). Given the Stripe session id the browser holds, it leaves out the claims of that session's checkout, found through `payment.transaction_id`, so a shopper's own open checkout never counts against them; an id that matches no payment leaves every claim in. SQLite counts the claims from `discount_claim_discountId_email_idx` and finds the payment through `payment_transactionId_unique`, which `query-plans.integration.test.ts` also checks.

The validator adds two rejection codes: `notFound`, when no row matches, and `held`, from `resolveDiscountPreviewRejection`. Codes are compared after `normalizeDiscountCode`, which trims and upper-cases them. A rejection is a code rather than a sentence, and the checkout renders it from `pages.checkout.discount.rejection.<code>`.

## At checkout

`validateDiscountCode` (`use-cases/validate-discount-code.ts`) checks a code against a basket: it takes the code, an optional e-mail, the basket's lines (`variantId` and `qty`, at most `CART_LINES_MAX`), and optionally the id of the chosen delivery method and the Stripe session id of the checkout the browser holds. The browser sends no prices or totals. The function prices the lines with `getSellPricesByVariantIds`, the current sell prices the cart's availability check also uses, and leaves out a line whose variant has no valid price. Only a `free_shipping` code reads the delivery method, through `getOfferedDeliveryMethodByIdQuery`, and takes off what its delivery costs, which is nothing once the basket's products reach the free delivery threshold (see [Free delivery and discount codes](#free-delivery-and-discount-codes)); before a method is chosen, or for one the shop no longer offers, it takes off nothing. The verdict comes from `resolveDiscountPreviewRejection`, so a code whose remaining uses other checkouts hold is refused as `held` instead of shown as applying. The function has no `authorized` middleware, so a guest can try a code, and `use-case-authorization.test.ts` lists it among the public use cases. It sits behind `withRateLimit("discount-validate", RATE_LIMITS.CHECKOUT)`, ten checks per minute per client address in a bucket of its own, so the field cannot be used to try codes, or which addresses already used one, at speed; past the limit it answers `TOO_MANY_REQUESTS` and the field shows `pages.checkout.discount.rejection.error`. It answers with `applied` (code, `discountId`, type and amount) or with a `rejection`, and nothing more. The per-customer check uses the e-mail it is sent, or the signed-in user's when none is sent; an empty e-mail counts as none, and a malformed one fails validation. The limiter's counter is one D1 round trip before the handler runs. After it, with an e-mail the session is not read at all, and the code with its counts and the variants' prices are two statements sent side by side. Without one, it reads the session first: for a signed-in shopper that is one round trip before the same two, with the account's e-mail; a guest has no session cookie, so Better Auth answers without reading D1. A `free_shipping` code that passes the rules adds one round trip for its delivery method.

The same file exports the two ways the checkout calls it:

- `validateDiscountCodeMutation` backs the Apply button. Its `mutationFn` always calls the server, never a cached answer, and then stores the answer with `setQueryData` under the key of `validateDiscountCodeQuery` for the same input.
- `validateDiscountCodeQuery({ code, deliveryMethodId, email, heldSessionId, lines })` is the summary's query; `DiscountCheckBasket` is that input without the code. Its key is `DISCOUNT_QUERY_KEYS.VALIDATION` (`["discount", "validate"]`) followed by that input, and `staleTime` is `DISCOUNT_QUERY_STALE_MS` (one minute), so the summary shows the answer Apply just stored without asking again. With no code the query is skipped (`skipToken`).

`CheckoutDiscountField` (`src/presentation/components/custom/checkout/components/checkout-discount-field.tsx`) sits in `CheckoutSummary`, below the totals, while the form has no code. It is a `react-hook-form` form validated by `discountZodSchemas.checkoutCodeFormValues`. It sends the code with the summary's `DiscountCheckBasket`, so Apply stores its answer under the key the summary reads. A rejected code stays in the field with its reason, a failed request shows `pages.checkout.discount.rejection.error`, and typing clears either message. An accepted code is written into the checkout form's `discountCode` field, which the draft keeps in `sessionStorage`.

`CheckoutSummary` keeps no copy of the result. It reads `discountCode` from the form and runs `validateDiscountCodeQuery` with the basket's lines, the id of the chosen delivery method and the session id `loadCheckoutSessionId()` reads, which it follows with `useSyncExternalStore` and `subscribeToCheckoutSessionId` like `useCartAvailability`. A code restored after a reload is therefore checked and shown again, changing a quantity or the delivery method checks it again, and so does the payment step storing the session it opened, which then no longer counts that checkout's own claim. The e-mail goes into the check only once the contact step is complete (`activeStepIndex` is past it). While the shopper is on the contact step the check goes without it, so the server falls back to the signed-in account's address and typing an address never sends a request; moving on checks the code again with the confirmed address.

While the form has a code, `CheckoutDiscountCode` (`checkout-discount-code.tsx`) shows it in place of the field, with what the check said:

| Check              | Code row                                                                      | Discount line | Total                                                             |
| ------------------ | ----------------------------------------------------------------------------- | ------------- | ----------------------------------------------------------------- |
| In flight          | The code and a spinner                                                        | None          | `checkoutSummary.totalAwaitingCode`, no VAT line                  |
| `applied`          | The code and the amount it takes off                                          | The amount    | Items plus delivery, less the discount, from `computeOrderTotals` |
| `rejection`        | The code struck through, with `discount.rejection.<code>` below it            | None          | Items plus delivery                                               |
| The request failed | The code, `discount.checkFailed` and a `discount.retry` button that refetches | None          | `checkoutSummary.totalAwaitingCode`, no VAT line                  |

A code that no longer applies stays in the form and the draft with its reason on screen, and the server drops it when it builds the session (below). From then on the summary shows the discount and total the server quoted for that session, so the total shown is the one charged. When the check fails the summary cannot know which total the server will charge, so it shows none until a retry answers. Removing the code clears `discountCode`. `checkoutSchema` declares `discountCode: zod.string().trim().max(DISCOUNT_CODE_MAX_LENGTH).optional()`, and no step validates it.

The validation response is only a preview. `handleCreateCheckoutSession` and `handleUpdateCheckoutSession` call `resolveCheckoutDiscount` (`discount.checkout.server.ts`) with `checkoutValues.discountCode`, the e-mail the form carries (`checkoutValues.email`), the item subtotal computed from database prices, and the shipping cost before any code. It skips the read for an empty code, reads the row with `getDiscountByCodeForCustomerQuery` in one statement, and passes it to `resolveAppliedCheckoutDiscount`, which applies the same rules again. A code that no longer applies is logged and dropped, and one that would take nothing off is dropped, instead of failing the checkout. A code that passes is then claimed for the checkout, below, and only a claimed code reaches the session and `checkout.discount_id`.

## Holding a use while the shopper pays

The rules compare `usage_count` with `usage_limit`, and redemptions with `per_customer_limit`, but both grow only once a session is paid. Checked alone, every checkout opened while a code had one use left would get the code, and so would every concurrent checkout of a customer limited to one use. So the checkout claims the use before Stripe sees the coupon, the way it reserves stock, and holds it in `discount_claim` while its session can be paid.

`prepareDiscountClaim` in `discount.claim.server.ts` builds the claim as one statement, an `INSERT … SELECT … FROM discount WHERE id = ? … ON CONFLICT (checkout_id, discount_id) DO UPDATE`. The `SELECT` yields the code's row only while `usage_count` plus the claims of other checkouts is below `usage_limit`, and while the customer's redemptions plus their claims in other checkouts, both matched on the lower-cased e-mail, are below `per_customer_limit`; a null limit always passes. It returns the claim it wrote, or nothing. D1 runs one statement at a time, so of two checkouts racing for a code's last use only one gets a row back. A checkout claiming a code it already holds updates the e-mail on its claim, and its own claims never count against it. SQLite finds the code by its primary key and counts the holds and the customer's redemptions from `discount_claim_discountId_email_idx` and `discount_redemption_discountId_email_idx`, which `query-plans.integration.test.ts` checks too.

| Moment                                          | Where                                                                                                                                                                                     | The claim                                                                                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| A checkout is opened with a code                | `prepareCreateCheckoutBatch`, in the batch that writes the checkout                                                                                                                       | Claimed. The same batch sets `checkout.discount_id` only where the claim exists, and `createCheckout` reports `discountClaimed`        |
| An open session is edited                       | `claimCheckoutDiscount` in `handleUpdateCheckoutSession`, before the replacement is built                                                                                                 | Claimed, or kept if the checkout already holds the code. The old session's claim stays until the swap                                  |
| The replacement takes over                      | `supersedeCheckoutSession`, in the batch that moves the payment                                                                                                                           | The checkout's claims of every other code are released, only once the payment has moved                                                |
| Building or swapping the session fails          | `releaseDiscountClaims` for a new checkout, `releaseUnappliedDiscountClaims` for an edit                                                                                                  | Released. An edit keeps the claim of the code in `checkout.discount_id`, which the still open old session uses                         |
| Saving the edited delivery fails after the swap | `abandonReplacementCheckout` in `saveReplacementDelivery`, through `releaseCheckout` for the replacement session                                                                          | Released with the stock by `prepareReleaseCheckoutBatch`; the checkout and its payment fail, and the replacement session is expired    |
| The session expires or its payment fails        | `prepareReleaseCheckoutBatch` through `releaseCheckout`, from the webhook or from `releaseExpiredCheckoutSession` ahead of it, guarded by the pending payment and checkout like the stock | Released once; a redelivered event finds the checkout already failed                                                                   |
| The session is paid                             | `prepareDiscountRedemption`, in the order's batch                                                                                                                                         | Replaced by the redemption (see [On fulfilment](#on-fulfilment))                                                                       |
| A failed release left a claim behind            | `anonymizeEndedCheckouts`, in the daily retention clean-up                                                                                                                                | Deleted 30 days after the checkout ended, with its contact details (see [Data retention](/docs/guides/data-retention#ended-checkouts)) |

When the claim fails, the code is dropped like any code that no longer applies: `keepClaimedDiscount` logs `Discount <code> not applied to checkout: other checkouts hold the uses its limits allow.`, and the session is created, or replaced, without the coupon and at the full price, which the summary then shows from the server's quote. The checkout's code check counts the same holds, leaving out those of the shopper's own checkout, so a code whose remaining uses are all held is refused with `pages.checkout.discount.rejection.held` before the shopper pays. It is still a preview: a use claimed between the check and the session is caught by the claim, which drops the code as above.

## Free delivery and discount codes

When the owner sets a free delivery threshold (see [Shipping and delivery: Free delivery](/docs/features/shipping-and-delivery#free-delivery)), the products' value it is compared with is counted after a `percentage` or `fixed_amount` code and before delivery. Such a code can take a basket back below the threshold, and delivery is then charged again; the checkout says how much is missing. A `free_shipping` code does not count towards the threshold. Below it, the code takes off the delivery price as before. Once the products reach the threshold, delivery is already free and the code is worth nothing: `validateDiscountCode` prices the delivery it covers with `resolveDeliveryPrice` and answers with an amount of zero, and `resolveAppliedCheckoutDiscount` drops the code when the session is built, like any code that would take nothing off, so it is neither claimed nor sent to Stripe.

## In the Stripe session

Stripe has no negative line item, so `toSessionDiscounts` in `src/integrations/stripe/stripe.coupons.server.ts` creates a one-time coupon for the computed amount, and `createStripeSession` sets it as `params.discounts`:

```ts
const coupon = await stripe.coupons.create({
  amount_off: discount.amountMinorUnits,
  currency: STRIPE_CURRENCY,
  duration: "once",
  metadata: { checkoutId, source: STRIPE_COUPON_SOURCE },
  name: discount.code,
})

return [{ coupon: coupon.id }]
```

A `free_shipping` code therefore becomes an `amount_off` equal to the shipping cost, and the delivery line item stays on the session. The session metadata also carries `discountCode`, which nothing reads, and `discountTotal` and `shippingTotal`, the discount and the delivery charge the session was priced with, which fulfilment reads. Stripe's own promotion codes are not enabled.

Every session created or replaced with a code gets its own coupon, tagged in the coupon's metadata with the checkout id and `source: STRIPE_COUPON_SOURCE` (`"marte_checkout"`). `deleteCheckoutCoupons`, in the same file, deletes it once no session can use it any more:

| Moment                                                               | Caller                                            | The session's coupon                                                                   |
| -------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Stripe refuses to create the session                                 | `createStripeSession`                             | Deleted at once, since no event will ever name it                                      |
| `checkout.session.completed`                                         | The webhook, after `handleFulfillCheckoutSession` | Deleted, also while the payment is still settling                                      |
| `checkout.session.expired`                                           | The webhook, after `handleReleaseCheckoutSession` | Deleted; replacing a session expires the old one, so this covers replaced sessions too |
| `checkout.session.async_payment_succeeded` or `async_payment_failed` | The webhook                                       | Left alone, because the completed event already deleted it                             |

`deleteCheckoutCoupons` reads `session.discounts` and treats a missing or `null` list as no coupons. A coupon given as an id is retrieved first, and only a coupon whose metadata carries `source: "marte_checkout"` and the session's own `checkoutId` is deleted, so a coupon made by hand in the Stripe dashboard is never touched. A failed retrieve or delete is logged and never fails the webhook. When fulfilment throws, the coupon is kept, so Stripe's retry of the event can still delete it. Deleting a coupon does not change an amount Stripe has already applied, so a completed session is charged and refunded as before.

## On fulfilment

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) takes the discount the session was priced with from its `discountTotal` metadata, read by `resolveCheckoutSessionDiscountTotal` (`checkout-metadata.zod.ts`), the way it takes the delivery charge from `shippingTotal`, and passes it to `computeOrderTotals`, which caps the discount at items plus shipping. Only a session opened before that field existed has the amount recalculated: `calculateDiscountAmount` works it out from the code's current row in the checkout's `discount`, the session's lines, which `readCheckoutSessionLines` reads from `payment.lines` (see [Checkout](/docs/features/checkout#the-cart-on-the-payment-row)), and the delivery charge. `prepareFulfillCheckoutBatch` copies `discount_id` onto the order and writes `discount_total`. The rules are not checked again at this point, because the customer has already paid. A code changed or deleted while the shopper pays therefore changes nothing for that order: it records what Stripe took off.

`fulfillCheckout` appends the statements of `prepareDiscountRedemption` (`discount.redeem.server.ts`) to that batch, so the order and its redemption are one D1 transaction. They delete the checkout's claims, insert a `discount_redemption` row with the order's `discount_total`, the checkout e-mail, the order and the order's `user_id`, and increment `discount.usage_count`. The redemption is an `INSERT … SELECT … FROM discount WHERE id = ?`, so a code deleted while the customer paid writes nothing rather than breaking the foreign key, and none of the three checks a limit: a customer who has paid is never refused, even if the code ran out meanwhile. Because `order.checkout_id` is unique, the batch of a second delivery of the same payment fails as a whole, `fulfillCheckout` finds the order the first one placed and returns without an audit entry, and the use is counted once (see [Payments](/docs/features/payments#fulfilment)). A checkout without a code, or whose session took nothing off, only has its claims deleted. After the batch, `fulfillCheckout` records a `discount.redeemed` audit entry with the amount, also when D1 committed the batch but answered with an error and the order found afterwards is the one this delivery inserted.

The redemption's `user_id` is read from the order the same batch inserts, so it is the account the order is filed under: the signed-in customer's, or, for a guest checkout, the verified account with the checkout's e-mail, and none otherwise. When `claimGuestOrdersForUser` links guest orders to an account afterwards, the same batch sets `user_id` on the redemptions of every order the account holds that are not yet filed under it (see [Orders](/docs/features/orders#customer-order-history)); SQLite finds them through the account's orders and `discount_redemption_orderId_unique`, which `query-plans.integration.test.ts` checks. `20261017130000_discount_redemption_order_account.sql` did the same once for the orders `20261016140000_claim_past_guest_orders.sql` and earlier fulfilments filed under an account. Nothing reads `discount_redemption.user_id`: the per-customer limit counts redemptions by e-mail, so a claimed order's redemption counts against its address as before. Deleting an account sets the column to `null`.

## The admin coupons page

`/admin/coupons` is `src/routes/admin.coupons.tsx`. Its loader primes `getAdminDiscountsPageQuery({ page: 1, pageSize: ADMIN_DISCOUNTS_PAGE_SIZE })` and `getDiscountStatsQuery()`, both with `staleTime: "static"`, and the route sets `shouldReload: false` and a `staleTime` of `DISCOUNT_QUERY_STALE_MS` (one minute). The page renders `AdminHeader` and `CouponsTableContent` inside `CouponsSheetProvider`, whose value comes from `useCouponsSheetState`: whether the sheet is closed, creating or editing, and the code being edited. The components live in `src/presentation/components/custom/pages/admin/coupons/`.

`CouponsTableContent` (`components/coupons-table.tsx`) lays the page out like the other admin lists (see [Data table](/docs/ui/data-table)): `CouponsStats` above a `DataGridShell` that holds the toolbar, the body and the pager. `CouponSheet` is mounted only while the sheet is open.

### Stats

`CouponsStats` reads `getDiscountStatsQuery()` with `useSuspenseQuery` and shows the four cards of `COUPON_STAT_CARDS` (`coupons-stats.config.ts`) in this order: all codes (`total`), codes usable right now (`active`), redemptions, and the amount given away (`redeemedTotalMinorUnits`). `getAdminDiscountStats` counts as usable the codes that are active, have started, have not ended and are below their usage limit, and counts and sums every `discount_redemption` row for the last two. The counts are written with `toLocaleString` and the amount with `formatPrice`, both in the admin's format locale. The first two cards are filter buttons: "Active coupons" toggles the grid's status filter to `active`, and "Total coupons" clears it; each shows as pressed while the filter matches it. While a stale stats query refetches, the values show skeletons and the buttons are disabled. The cards sit two to a row below the `xl` breakpoint and four from it.

### The grid

`useCouponsDataGrid` (`hooks/use-coupons-data-grid.ts`) builds the grid from `couponsDataGrid`, whose `persistenceKey` is `COUPONS_DATA_GRID_KEY` (`admin.coupons`), so column order, widths and visibility persist like on the other lists. It runs in server mode with manual pagination: each page is one `getAdminDiscountsPageQuery({ page, pageSize, search, status, type })` request, with `placeholderData: keepPreviousData`, and the body shows skeleton rows while a page is fetching. Rows come newest first, and no column sorts.

- **Search.** The toolbar's search box sets the table's global filter, which `useAdminDebouncedTableSearch` debounces by 300 ms before it becomes the query's `search`. The server matches it, ignoring case, inside `code` and `description`. A new term returns to the first page.
- **Filters.** `CouponsStatusFilter` and `CouponsTypeFilter` (`components/coupons-filters.tsx`) are selects over `DISCOUNT_STATUSES` and `DISCOUNT_TYPES`, each with an "All" entry. `applyCouponsFilter` merges a change into the active filters, returns to the first page and clears the row selection. The server turns a status into SQL (`discountStatusCondition` in `discount.accessors.ts`) with the same precedence as `resolveDiscountStatus`, and `discount.accessors.integration.test.ts` checks that each status filter returns exactly the codes the list labels with it.

`buildCouponColumns` (`lib/coupons-column-defs.tsx`) defines the columns; their ids, widths, default visibility and pinning are `ADMIN_DISCOUNT_TABLE_COLUMN_ID`, `ADMIN_DISCOUNT_TABLE_COLUMN_SIZE`, `ADMIN_DISCOUNT_TABLE_DEFAULT_COLUMN_VISIBILITY` and `ADMIN_DISCOUNT_TABLE_COLUMN_PINNING` in `discount.constants.ts`.

| Column      | Header            | Shows                                                                             |
| ----------- | ----------------- | --------------------------------------------------------------------------------- |
| `select`    | none              | The row's checkbox; pinned to the start                                           |
| `code`      | Code              | The code, with its description below it; pinned to the start                      |
| `recordId`  | ID                | The id; hidden by default                                                         |
| `status`    | Status            | `CouponStatusBadge` with the status from `resolveDiscountStatus`                  |
| `type`      | Type              | The type's label                                                                  |
| `value`     | Discount          | The percentage, or the amount of a `fixed_amount` code; empty for `free_shipping` |
| `minOrder`  | Min. basket value | `min_order_total` as a price, or empty                                            |
| `usage`     | Usage             | `usage_count` against `usage_limit`, or only the count when there is no limit     |
| `startsAt`  | Starts            | The start date; hidden by default                                                 |
| `endsAt`    | Expires           | The end date                                                                      |
| `createdAt` | Created           | The creation date                                                                 |
| `actions`   | none              | The row menu; pinned to the end                                                   |

Prices go through `formatPrice` with `STORE_CURRENCY_CODE` in the admin's format locale, and dates through `useFormatter` with `dateStyle: "medium"` in the admin's time zone. Below the `64rem` breakpoint the grid stops pinning its columns once they would leave less than 240 px to scroll in.

Clicking a row opens the sheet on that code (`onRowClick` is `openEdit`); the actions column sets `preventRowClick`. `CouponsRowActions` offers Edit coupon, Copy code and Copy ID, which copy to the clipboard and confirm with a toast, and Delete coupon, which asks first in `CatalogDeleteConfirmDialog`. Selecting rows shows `CouponsBulkActions` in the toolbar: the count and a "Delete (n)" button whose `AlertDialog` deletes the selected codes in one `deleteDiscounts` call, reports how many were deleted and clears the selection. The toolbar also holds "Create coupon" (`CatalogToolbarAddButton`), which opens an empty sheet, and `CouponsRefreshAction`, which calls `invalidateQueryPrefix` on `DISCOUNT_QUERY_KEYS.ADMIN.ALL` for this tab only and spins while any admin discount query is fetching.

### The coupon sheet

`CouponSheet` (`edit-coupon/coupon-sheet.tsx`) wraps `CouponFormProvider` in `CatalogFormSheetContent`, the resizable side sheet of the catalog forms, and shares their saved width (persistence key `admin.catalog.form-sheet`). The provider holds a `react-hook-form` form resolved with `discountZodSchemas.adminDiscountFormValues`, the schema the server functions parse. Its defaults come from `toCouponFormValues`: the row being edited, or an active percentage code with no value. A submit the schema rejects marks the fields and shows a toast. The form has four sections in `edit-coupon/_sections/`:

- **Code** (`DetailsSection`): the id, read-only, when editing; the code, shown upper-case with a character counter and upper-cased by `normalizeDiscountCode` when saved; the internal description.
- **Discount** (`DiscountSection`): the type, then the value: a whole percentage with a `%` suffix, an amount for `fixed_amount`, or a note that free shipping needs none. Changing the type resets the value to 0 and empties the maximum discount, so a cap typed for a percentage is not saved, hidden, with another type. The maximum discount appears only for a percentage, the minimum basket value for every type.
- **Limits** (`LimitsSection`): total uses and uses per customer, blank for unlimited.
- **Availability** (`AvailabilitySection`): active or disabled, and the start and end.

Money fields (`CouponMoneyField`) take złoty, not grosze. `parseMoneyInputToMinorUnits(next, STORE_CURRENCY_CODE, formatLocale)` reads what the admin types in their format locale, and `formatMinorUnitsToMoneyInput` writes the stored minor units back the same way (see [Internationalization](/docs/features/internationalization)). The start and end are `datetime-local` inputs in the admin's display time zone (`useDisplayTimeZone`), the one the grid shows dates in, whatever zone the browser is in. `toLocalInputValue` shows the stored instant as that zone's wall clock through `toCalendarDateTime`, and `toIsoOrUndefined` turns the wall clock typed back into an instant through `wallClockStartMs`, like the admin date filters, so each side of a daylight saving change gets that zone's offset and a time the clocks skip moves on by the skipped hour. Below the `sm` breakpoint the sheet takes the full width without its resize handle, and the paired fields stack.

### Server functions

| Use case                      | Guard                               | Effect                                                                                                                                                                                                                                                                                                    |
| ----------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `get-admin-discounts-page.ts` | `authorized({ order: ["read"] })`   | One page of codes, newest first, narrowed by `search`, `status` and `type`; `page` defaults to 1 and `pageSize` to `ADMIN_DISCOUNTS_PAGE_SIZE` (25), at most `LIST_PAGE_SIZE_MAX` (250)                                                                                                                   |
| `get-admin-discount-stats.ts` | `authorized({ order: ["read"] })`   | The four card values                                                                                                                                                                                                                                                                                      |
| `create-discount.ts`          | `authorized({ order: ["update"] })` | Inserts the row with the normalised code; a taken code throws `CONFLICT` with `DISCOUNT_CODE_TAKEN`, also when another admin saves the same code between the check and the insert, whose unique-constraint failure `refuseTakenDiscountCode` turns into the same error; audits `discount.created`         |
| `update-discount.ts`          | `authorized({ order: ["update"] })` | An unknown id throws `NOT_FOUND` with `DISCOUNT_NOT_FOUND`, and a changed code another row already has throws `CONFLICT` with `DISCOUNT_CODE_TAKEN`, also when that row is saved between the check and the update; otherwise updates the row, sets emptied fields to `null` and audits `discount.updated` |
| `delete-discounts.ts`         | `authorized({ order: ["update"] })` | Deletes by id and returns how many were deleted; audits `discount.deleted` with the ids                                                                                                                                                                                                                   |

The page query's key is `DISCOUNT_QUERY_KEYS.ADMIN.PAGE` followed by its input, and the stats query's is `DISCOUNT_QUERY_KEYS.ADMIN.STATS`. Both set `refetchOnMount` and `refetchOnWindowFocus` to `false`.

### Saving and deleting

`useSaveCoupon`, in `edit-coupon/coupon-form-provider.tsx`, runs `createDiscountMutation` for a new code and `updateDiscountMutation` for an edited one. On success it shows a toast, calls `syncQueryInvalidation(queryClient, DISCOUNT_QUERY_KEYS.ADMIN.ALL)` and closes the sheet. A `CONFLICT` puts "That code is already in use." on the code field and in a toast; any other error shows a generic toast and keeps the sheet open. `useDeleteCoupons` (`hooks/use-delete-coupons.ts`), which the row menu and the bulk action share, runs `deleteDiscountsMutation` and calls the same `syncQueryInvalidation` on success. `DISCOUNT_QUERY_KEYS.ADMIN.ALL` is `["admin", "discounts"]`, the prefix of the page and stats keys, so a save or a deletion refetches both in this tab and, through the `BroadcastChannel`, in the browser's other tabs (see [TanStack Query](/docs/integrations/tanstack-query#cross-tab-invalidation)).

## What is still open

These are the seams the current code leaves, not recommendations about product design:

1. **The cart column.** `cart.discount_id` is neither written nor read; the applied code lives only in the checkout form.
2. **Permissions.** There is no `discount` resource in `src/integrations/better-auth/auth.access.ts`, so the coupons functions reuse the `order` read and update permissions.
3. **Realtime invalidation.** `ADMIN_REALTIME_QUERY_PREFIXES` has no `DISCOUNT_QUERY_KEYS` entry and there is no `scheduleDiscountInvalidation()` in `realtime-invalidation.catalog.server.ts`, so neither a change made from another browser nor a redemption recorded by a paid checkout reaches a coupons page that is already open; its refresh button reloads it.
4. **Deletion.** Deleting a code also deletes its `discount_redemption` and `discount_claim` rows (`onDelete: "cascade"`), so its redemptions also leave the redemptions and given-away cards. Both delete dialogs say so: the code stops working at once, and orders that used it keep their discount, but its uses no longer count in those statistics. `checkout.discount_id` and `order.discount_id` have no foreign key and keep the old id, and `order.discount_total` and the order's totals do not change, which `discount.delete.integration.test.ts` checks. A checkout paid with a code deleted meanwhile records the discount Stripe took off, but no redemption. Once the redemptions are gone, which code an order used is no longer recorded in the shop's database, only in its Stripe session's `discountCode` metadata. Keeping that history would mean archiving a code instead of deleting it.
5. **Holds in the admin.** The coupons page counts redemptions only: the usage column, the status and the active card read `usage_count`, so a code whose remaining uses are all held by open checkouts still reads as having uses left.
