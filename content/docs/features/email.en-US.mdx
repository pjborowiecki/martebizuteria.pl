## Sending

One function sends every email — `src/integrations/resend/resend.send.ts`:

```ts
const RESEND_TEST_SENDER = /@resend\.dev>?$/iu

const refusesEverySend = ({ name, statusCode }: ErrorResponse, sender: string): boolean =>
  SENDER_REFUSAL_NAMES.has(name) || (SENDER_REFUSAL_STATUSES.has(statusCode) && !RESEND_TEST_SENDER.test(sender))

const deliver = async ({ from, revealsAccountExistence, ...message }: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const sender = from ?? `${APP_NAME} <${env.RESEND_EMAIL_FROM}>`
  try {
    const { error } = await resend.emails.send({ ...message, from: sender, replyTo: BUSINESS.EMAIL })

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error, sender)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

The message, which is `react`, `subject`, `to` and any `attachments`, goes to Resend as it was passed. Only the order confirmation carries an attachment. `sendEmail` adds `replyTo: BUSINESS.EMAIL` to every message, so a customer's reply reaches the shop's contact address `kontakt@martebizuteria.pl` rather than `RESEND_EMAIL_FROM`; see [Resend](/docs/integrations/resend#sender-domain).

Note the contract: **it never throws.** It returns `undefined` on success and the failure message as a string otherwise. The Resend SDK has no timeout of its own, so `sendEmail` gives up after `SEND_EMAIL_TIMEOUT_MS` (10 seconds) and returns `Resend did not answer within 10000 ms`; a stalled Resend cannot hold a signup or a webhook open indefinitely. Every caller is therefore written as `const failure = await sendEmail(...)` followed by a decision about what to do with `failure` — a mail outage cannot roll back an order or a deletion.

Some refusals mean that no email from this sender can go out at all: a 401 or 403 from Resend (an invalid or restricted API key, or a sending domain that is not verified), an invalid `from` address, or an exhausted daily or monthly quota. For those, `sendEmail` also runs `markEmailSenderUnavailable` from `src/integrations/resend/resend.availability.server.ts` in the background, unless the caller passed `revealsAccountExistence: true`. Better Auth's verification, reset and change-email confirmation pass it, because they are sent only when an account does or does not exist, and a flag set by their refusal would reveal that. `markEmailSenderUnavailable` writes only when the flag is not set yet. It writes `email-sender-unavailable:<APP_ENV>` to the `CACHE` KV namespace with a five-minute expiry (`EMAIL_SENDER_UNAVAILABLE_SECONDS`). The key includes `APP_ENV` because development and preview share one namespace. A refusal that concerns one message, such as an invalid recipient, `rate_limit_exceeded`, a 5xx answer, a network error, the timeout, or the 403 that Resend's `resend.dev` test sender gets for any recipient but the Resend account owner, leaves the flag alone, so one bad address or one burst cannot stop every other email. Only the Better Auth gate acts on the flag, and it lets requests through when KV cannot be read; see [Better Auth](/docs/integrations/better-auth#email-delivery-gate). Nothing clears it early: once the sender is fixed, the first attempt after the flag expires goes out normally.

The client is `src/integrations/resend/resend.config.ts`, a one-line `new Resend(env.RESEND_API_KEY)`. The default `from` is `APP_NAME <RESEND_EMAIL_FROM>`. Both `RESEND_API_KEY` and `RESEND_EMAIL_FROM` are in the `secrets.required` list of every environment in `wrangler.jsonc`. The sender's domain must be verified in Resend, and a deploy stops before the build when it is not; see [Resend](/docs/integrations/resend#sender-domain).

Each template **exports its own namespace constant** next to the component, for example `export const ORDER_CONFIRMATION_NAMESPACE = "emails.order-confirmation"`. That is the convention: the template owns the name of its message catalogue, so there is no separate mapping to keep in step.

Shared pieces: `email-layout.tsx` (the wordmark, the gold rule, the tagline and the footer), `email-highlight-box.tsx` (`EmailBodyText`, `EmailBorderedSection`, `EmailDetailRow` for a label above its value, and the CTA and label class names) and `email-styles.ts` (the inline `CSSProperties` objects).

## Localisation

An email is never rendered with a React hook. Messages are loaded explicitly and passed in as a prop, and the subject is produced by a standalone translator:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await requireAuthEmailDelivery("verification", {
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verificationUrl }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

`loadNamespace` is from `src/integrations/use-intl/i18n.messages.ts` and `createTranslator` from `use-intl` — the non-React entry point, which is what makes this work inside a webhook handler with no request context.

Where the locale comes from differs by trigger:

| Trigger                   | Locale source                                                                   |
| ------------------------- | ------------------------------------------------------------------------------- |
| Better Auth emails        | `getCurrentLocale()` — the request the user is making                           |
| `sendAccountDeletedEmail` | The `locale` captured before the deletion, falling back to `getCurrentLocale()` |
| Newsletter emails         | The `locale` sent with the subscription, falling back to `getCurrentLocale()`   |
| Order confirmation        | `resolveLocale(session)` from the Stripe session metadata                       |
| Payment failed            | `resolveLocale(session)` from the Stripe session metadata                       |
| Order shipped             | `resolveOrderLocale(orderRow.metadata)` from the order's stored JSON            |
| Order cancelled, refunded | `resolveOrderLocale(orderRow.metadata)` from the order's stored JSON            |
| Shop's new-order notice   | `I18N.DEFAULT_LOCALE`, the shop's own language, whatever the customer used      |

The order emails matter: a webhook has no browser, and an admin's language is not the customer's, so the locale must have been persisted at checkout time. `createStripeSession` puts `locale: getCurrentLocale()` in the session metadata and `prepareFulfillCheckoutBatch` copies it into `order.metadata`, which is why a Polish customer's shipping notice arrives in Polish days later.

## Link origin

Links the shop writes into its own emails point at the address the customer or admin was using, the way Better Auth's links follow the host it was called on. A server function resolves the origin before it writes anything, with `resolveRequestOrigin(request)` (`src/lib/request.ts`): it takes the origin from `request.url`, accepts only the hosts `appHostsForMode(import.meta.env.MODE)` lists, and throws `AppError(FORBIDDEN)` for anything else. The origin is then passed down as a string: `sendNewsletterConfirmation({ email, locale, origin, token })`, `sendNewsletterAlreadySubscribed({ email, locale, origin })`, `sendAccountDeletedEmail({ email, locale, name, origin })`, `notifyOrderShipped(orderId, origin)` and `notifyOrderCancelled({ orderId, refundedAmount }, origin)`. After a self-service deletion, Better Auth's `afterDelete` hook resolves it from the request Better Auth hands it, and after a password reset `sendPasswordChangedEmail` does the same with the request Better Auth hands `onPasswordReset`.

The order confirmation is sent from the Stripe webhook, whose request only says which endpoint Stripe called. It takes its origin from the session's `return_url` instead: the checkout request built that URL on its own validated origin, and it comes back inside the signature-checked event. `resolveDeploymentOrigin(session.return_url)` accepts a host that any deployment serves, local, preview or production, and requires `https:` everywhere but `localhost:3000` and `127.0.0.1:3000`. A local checkout therefore links back to the address it was made on, even though `stripe:listen` forwards the webhook to `localhost:3000`, and even when the preview deployment, which shares the Stripe test account and the database with development, fulfils it. The failed-payment email does the same with the session in its event, the shop's new-order email with the session that created the order, and the refund email with the Checkout Session `resolveCheckoutSession` finds for the refunded charge.

Used on `http://127.0.0.1:3000`, the shop links to `http://127.0.0.1:3000`. On preview it links to the preview host in use, and in production to `https://martebizuteria.pl` or `https://martebizuteria.pjborowiecki.workers.dev`, whichever the customer or admin used. `APP_URL` is used for SEO only. [Resend](/docs/integrations/resend) lists where each flow gets its origin.

## Order confirmation in detail

This is the most involved template. `stripe.webhooks.tsx` builds it in `buildOrderConfirmationEmailPayload`:

1. The recipient is `session.customer_email ?? session.customer_details?.email`. If there is none, nothing is built and the failure `The Stripe session has no email address` is recorded against the order. Before that, `sendOrderConfirmationEmail` takes the link origin from `session.return_url` with `resolveDeploymentOrigin`. A session without one records `The Stripe session has no return URL to link the email to`, and one on a host no deployment serves records `FORBIDDEN`.
2. `getCheckoutEmailContext(checkoutId)` loads the addresses, the delivery method, the locker id, the customer note and the company a business buyer asked to be invoiced. When the checkout has a company name or NIP, `describeCompanyInvoice` puts the name above `NIP <digits>`, and the details block shows them under "Invoice for a company" after the billing address; otherwise the row is left out.
3. `resolveStripePaymentMethodLabel(session, messages)` turns the Stripe payment method into a translated label.
4. `getFulfillmentTimeAttributesByVariantId(variantIds)` reads the `czas-realizacji` attribute each ordered variant's product page shows, and `resolveOrderLineFulfillmentTimes(order.lines, attributes, locale)` labels it in the order's locale. `buildOrderConfirmationDetails({ context, fulfillmentTimes, messages, paymentMethod })` then assembles the details block.
5. `buildOrderConfirmationItems(order.lines, locale, origin)` formats the line items, linking each one to its product page on `origin`, the address the checkout was made on.
6. `buildOrderAccountCta({ isGuest, locale, messages, orderId, origin })` chooses the button: a signed-in customer gets a link to `/account/orders/<id>`, a guest gets `/auth/sign-up`. `isGuest` is derived from an empty `userId` in the session metadata.
7. Totals: `itemsSubtotal` from the metadata lines and `shippingTotal = Math.max(session.amount_total - itemsSubtotal, 0)`.
8. `buildOrderLegalLinks(origin, locale)` links the terms of service, the exchanges-and-returns page and the privacy policy on `origin`, in the order's locale.
9. `loadWithdrawalFormAttachment(origin)` in `src/integrations/resend/withdrawal-form.attachment.server.ts` reads `/forms/formularz_zwrotu.pdf` through the Worker's `ASSETS` binding and returns it base64-encoded as a Resend attachment. The binding serves `public/` through Vite in development and the deployed static assets in preview and production, so the PDF is attached everywhere, including a local checkout whose `localhost` address Resend could not fetch. If the form cannot be read, the payload is not built and the order records the failure, such as `The withdrawal form /forms/formularz_zwrotu.pdf could not be read from the static assets: HTTP 404`, instead of sending a confirmation without it.

The helpers are in `src/integrations/resend/order-confirmation.utils.ts`, and `resolveDeliveryMethodLabel` there appends the locker id for a locker delivery.

The email is the confirmation of the contract on a durable medium that Article 21 of the Consumer Rights Act requires, so below the sign-off it repeats what the customer agreed to: the seller's legal name, postal address, NIP, e-mail and phone from `BUSINESS` in `src/presentation/branding/business.ts`, the 14-day right of withdrawal with how to use it, who pays to send the goods back and how the refund is made, the complaint procedure with the out-of-court routes of § 10 of the terms, and the three legal links. The total with VAT and delivery, the payment and delivery method and the delivery time are in the order summary above it. See [Legal pages](/docs/features/legal-pages#the-order-confirmation).

The transit estimate is copy chosen by delivery type, and the fulfilment time is the longest one the ordered products' pages give, stated as a period rather than a reference to those pages, which can change after the order. See [Shipping and delivery](/docs/features/shipping-and-delivery#delivery-in-the-emails):

```ts
const deliveryType = context?.deliveryMethod?.type ?? "courier"

return {
  estimatedDelivery: messages.estimatedDelivery[deliveryType],
  fulfillmentTime: describeOrderFulfillmentTime(fulfillmentTimes, messages),
}
```

## Cancellation, refund and failed payment

**Cancelled.** `cancelOrder` sends `order-cancelled.tsx` after its batch has cancelled the order, so a cancellation the batch refuses sends nothing. `requestFullOrderRefund` returns the `amount` of the refund Stripe created, and the email states it with how the money comes back; a free order is told there was nothing to refund. `notifyOrderCancelled` in `order-cancelled.notification.server.ts` reads the address, number, currency, total, locale and account of the order with `getOrderForRefundEmail` and links the account button on the admin's origin, as the shipped email does.

**Refunded.** Every refund reaches the shop as `charge.refunded`: the Refund button, the refund a cancellation issues and one made in the Stripe dashboard. `prepareRefundBatch` starts with a select of the payment's `refunded_amount` and the order's status, so `refundOrder` learns what the payment had recorded before this event in the same D1 transaction that records it. It returns the refund as `Order["unannouncedRefund"]` only when the charge's cumulative `amount_refunded` is above that and the order was not cancelled, and the email states the difference. Each partial refund is therefore announced once with its own amount, and the one that completes the refund says the order was refunded in full; when a newer event overtakes an older one, its email covers both refunds. The payment keeps the larger of the recorded amount and the event's, so a redelivered event, an older event delivered after a newer one and the `charge.refunded` that follows a cancellation's own refund return nothing, and D1 runs concurrent deliveries one batch at a time, so only one of them sees the lower amount. `handleChargeRefunded` then sends through `notifyOrderRefunded(refund, session.return_url)`. When the refund's event lands before the cancellation's batch, the order is already refunded, the cancellation is refused, and the customer gets the refund email alone.

**Payment failed.** `checkout.session.async_payment_failed` arrives when a delayed payment fails after the customer left the checkout. `releaseCheckout` returns whether its batch moved the session's payment from `pending` to `failed`, and `handleAsyncPaymentFailed` sends `payment-failed.tsx` only then, so a redelivered event finds nothing pending and sends nothing, and an expired session sends nothing at all. The email goes to the session's address in the session's locale, lists the pieces with links to their product pages, states the amount and links back to `/products`. No order exists, so `recordOrderEmailAttempt` records the outcome against the session id, the target of the `order.released` entry of the same release; it shows in `/admin/audit` rather than on an order.

## The shop's new-order email

Every order the Stripe webhook creates is also emailed to the shop, so the owner learns of it without watching the admin. `handleFulfillCheckoutSession` starts `notifyShopOfNewOrder(orderId, session.return_url)` from `src/integrations/resend/new-order.notification.server.ts` next to the customer's confirmation, hands both to `scheduleBackgroundWork` as one `Promise.all` and awaits it. A redelivered event creates no order and sends neither email.

The recipient is `RESEND_EMAIL_FROM`, the address the shop sends from, which every environment requires, so every environment sends the notice. In the `test` environment the end-to-end suite builds, `.env.test` sets it to `noreply@example.test`, a dummy inbox the mocked Resend captures.

The email is in the shop's language, `I18N.DEFAULT_LOCALE`, whatever language the customer used. It reads the order with `getAdminOrderDetailRow` and `getAdminOrderItemRows`, the reads behind the admin order page, and states the order number in the subject and heading, every piece with its variant, SKU, quantity, unit price and line total (`mapAdminOrderDetailItem`), the total with delivery, the customer's name, e-mail and phone, the delivery method with the locker id, the shipping address from the order's snapshot (`resolveAdminOrderDetailAddresses`), the company to invoice and the customer's note. The company row appears only when the order has a company name or NIP: `describeCompanyInvoice` gives the name and `NIP <digits>`, followed by the billing address from the order's snapshot, so the owner has what the invoice needs. Its button opens `/admin/orders/<id>` (`ROUTES.ADMIN_ORDER`) on the origin of the session's `return_url`, the origin of the confirmation's links.

The attempt goes through `recordOrderEmailAttempt` like every order email, labelled `New order notification → <address>`, so a refusal shows on the order's Activity card and in `/admin/audit`. It never touches the order or the customer's confirmation: `notifyShopOfNewOrder` does not throw, and the webhook still answers 200.

## Auditing

Order emails record their outcome in the audit log:

```ts
export const recordOrderEmailOutcome = ({
  failure,
  label,
  orderId,
}: Readonly<{ failure: string | undefined; label: string; orderId: string }>): void => {
  if (failure === undefined) {
    recordEmailSentAudit(orderId, { detail: label, resourceId: orderId })

    return
  }
  console.error(`${label} failed for order ${orderId}: ${failure}`)
  recordEmailFailedAudit(orderId, { detail: `${label} — ${failure}`, resourceId: orderId })
}
```

The `label` is a human string such as `Order confirmation → jane@example.com`. Every order email is split the same way. `sendOrderConfirmationEmail` and `sendPaymentFailedEmail` in `stripe.webhooks.tsx`, and `sendOrderShippedEmail`, `sendOrderCancelledEmail`, `sendOrderRefundedEmail` and `sendNewOrderEmail` in their `*.notification.server.ts` files, return `{ failure, label }`, and the caller hands that attempt to `recordOrderEmailAttempt` in `src/integrations/resend/order-email.outcome.server.ts`:

```ts
export const recordOrderEmailAttempt = async (
  attempt: Promise<OrderEmailOutcome>,
  { label, orderId }: Readonly<{ label: string; orderId: string }>,
): Promise<boolean> => {
  const outcome = await attempt.catch((error: unknown) => {
    console.error(`${label} for order ${orderId} could not be prepared:`, error)

    return { failure: error instanceof Error ? error.message : String(error), label }
  })
  recordOrderEmailOutcome({ failure: outcome.failure, label: outcome.label, orderId })

  return outcome.failure === undefined
}
```

An error thrown while the email is prepared is logged with its stack and becomes the outcome too, labelled without a recipient and described the way `sendEmail` describes an error it catches. Every attempt therefore ends in an entry:

| What went wrong                   | Detail of the `email.failed` entry                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| Resend refused the send           | `Order confirmation → jane@example.com — The example.com domain is not verified…`    |
| The Stripe session has no address | `Order confirmation — The Stripe session has no email address`                       |
| The order has a blank address     | `Order shipped — The order has no email address`                                     |
| The order row is gone             | `Order shipped — The order could not be found`                                       |
| The session has no return URL     | `Order refunded — The Stripe session has no return URL to link the email to`         |
| Preparing the email threw         | `Order shipped — D1_ERROR: …`, or the thrown value as text when it is not an `Error` |

The order id is the target and `resourceId` of every entry. The failure therefore shows in the order's **Activity** card in the admin, as "Email failed" with a "Failed" badge and the detail underneath, and in `/admin/audit` under the `email` category with severity `error`. Audit entries reach D1 through the queue a few seconds after the send, so `processAuditLogQueueBatch` publishes `ORDER_QUERY_KEYS.ADMIN.ORDERS` whenever a batch carries an action from an order timeline: every open admin tab refetches the order list, stats or order page it has on screen and drops the order queries it only has cached, so an open order page shows the entry without a reload. Newsletter and Better Auth failures use the same `email.failed` action, so they trigger that refetch as well. An entry can still be lost on its way to D1, when the queue send fails or a batch fails three times, because no dead-letter queue is configured; only the Worker log has the failure then. The admin has no button to resend an order email yet: once the cause is fixed, the shop contacts the customer at the address shown on the order.

A newsletter email that Resend refuses is audited as well. `subscribeToNewsletter` calls `recordEmailFailedAudit(email, { detail })`: the address is the audit target, and the detail names the email and the Resend error, such as `Newsletter confirmation — The example.com domain is not verified` or `Newsletter already-subscribed notice — …`. An unverified sender domain therefore shows up in `/admin/audit` on the first signup instead of only in the Worker log. An email that went out is not recorded.

Better Auth's five emails are audited the same way, through `recordAuthEmailFailure` in `auth.server.ts`:

```ts
const recordAuthEmailFailure = (kind: string, recipient: string, failure: string): void => {
  console.error(`[Auth] Failed to send ${kind} email to ${recipient}: ${failure}`)
  recordEmailFailedAudit(recipient, { detail: `Auth ${kind} email — ${failure}` })
}

const deliverAuthEmail = async (kind: string, email: Parameters<typeof sendEmail>[0]): Promise<boolean> => {
  const failure = await sendEmail(email)
  if (failure === undefined) {
    return true
  }

  recordAuthEmailFailure(kind, email.to, failure)

  return false
}
```

The target is the recipient's address and the detail names the email, for example `Auth reset-password email — The example.com domain is not verified`. The verification or reset link never goes into the audit log, because it is a credential. Whether the person is told depends on the endpoint; [Better Auth](/docs/integrations/better-auth) lists what each one answers.

`AUDIT_LOG_ACTION.EMAIL_DEFERRED` exists but nothing emits it.

## Waiting for the send

The shop's own senders wait for Resend's answer, so the result reaches whoever is looking. Better Auth's sign-up, password reset and change-email hooks are the exception: Better Auth runs them through `advanced.backgroundTasks`, which is `scheduleBackgroundWork` (`src/lib/background.ts`, the Worker's `waitUntil`), as [Better Auth](/docs/integrations/better-auth) describes. The password-changed email is the other exception: `onPasswordReset` hands `sendPasswordChangedEmail` to `scheduleBackgroundWork` itself and does not wait for it, because Better Auth signs every device out only after the hook returns.

`shipOrder`, `cancelOrder`, `deleteCustomer` and the Stripe webhook also hand the send they wait for to `scheduleBackgroundWork` before awaiting it:

```ts
const shippedEmailDelivery = notifyOrderShipped(orderId, origin)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery
```

When the admin closes the tab or Stripe stops waiting, the Workers runtime may cancel what the request was still awaiting, but not a promise passed to `waitUntil`. The email therefore still goes out and its outcome is still recorded. Better Auth's `afterDelete` awaits `sendAccountDeletedEmail` without this, so a customer who closes the tab during self-deletion can still cut the goodbye email short.

`shipOrder` awaits `notifyOrderShipped` after the order row is updated and returns `shippedEmailSent`. The admin always sees "Order marked as shipped.", and when the email failed also a warning toast, "Shipping email not sent", that points to the order's Activity card for the error. The order stays shipped either way, because `notifyOrderShipped` records the failure and returns `false` instead of throwing. Shipping from the orders list shows the same toasts.

`cancelOrder` awaits `notifyOrderCancelled` after the cancel batch in the same way and returns `cancelledEmailSent`. The admin sees the cancellation toast and, when the email failed, a warning toast, "Cancellation email not sent", that points to the order's Activity card. The order stays cancelled and its refund stays issued.

`deleteCustomer` awaits `sendAccountDeletedEmail` after `removeUser` and returns `goodbyeEmailSent`. The admin sees "The account was deleted and a confirmation email was sent.", or, when the email failed, a warning toast titled "Account deleted — email not sent" that points to the audit log. A refusal never undoes the deletion: `sendAccountDeletedEmail` returns `false` instead of throwing, both when Resend refuses the email and when it cannot even be prepared.

`subscribeToNewsletter` awaits its email, because the person who just signed up is told whether it went out. A new, pending or unsubscribed address gets `sendNewsletterConfirmation`; an address that is already confirmed, submitted by anyone but its signed-in owner, gets `sendNewsletterAlreadySubscribed`. Both return the Resend error message, or `undefined` when the send was accepted. On a failure the use case logs it, audits it and answers `confirmationFailed`. A subscriber row that was waiting for confirmation stays `pending`, so submitting the address again issues a fresh token and sends a new email. The request takes one Resend round trip longer, at most `SEND_EMAIL_TIMEOUT_MS`, which the form covers with its "Signing you up..." state.

The Stripe webhook awaits `notifyOrderConfirmed` and `notifyShopOfNewOrder` too, but nobody sees its answer, so the order's activity is where a failure shows. Neither throws: a refusal and a thrown error both end as an `email.failed` entry, and the webhook still answers 200. Throwing would not resend the email anyway. The handler would answer 500 and Stripe would redeliver the event, but on redelivery `fulfillCheckout` finds no pending checkout and the handler stops before the email step, so the only effects would be failed deliveries in Stripe and a coupon cleanup pushed to the retry.

The checkout success page therefore does not say the confirmation is on its way. It asks the shopper to contact the shop and quote the order number if the email has not arrived within a few minutes.

## Previewing

```bash
bun run dev
open http://localhost:3000/dev/emails
```

`src/routes/dev.emails.tsx` is a `GET` handler, not a React page. It is guarded by the build mode:

```ts
if (!import.meta.env.DEV) {
  return notFound()
}
```

so the route does not exist in a preview or production build. With no `?template=` it renders an index of cards; with `?template=<slug>&locale=<locale>` it renders that template, and adding `&format=text` returns the plain-text rendering instead of HTML.

`src/integrations/resend/email-previews.tsx` is the registry. `EMAIL_PREVIEWS` maps each slug to `{ element: async (locale) => …, label }`, and `renderEmailPreview(slug, locale, plainText)` calls react-email's `render`. The fixtures are realistic Polish data — `PREVIEW_ORDER_ITEMS` uses "Bransoletka Aurora" at 24 900 minor units and "Kolczyki Luna" ×2 at 18 900, `PREVIEW_ADDRESS` is a Warsaw address, and there are two CTA fixtures, `PREVIEW_GUEST_CTA` and `PREVIEW_CUSTOMER_CTA`, so both branches of `buildOrderAccountCta` can be seen.

Every template except `newsletter-confirmation` is listed in both `pl-PL` and `en-US`, in HTML and plain text — eight links per template — which makes the index the fastest way to check a translation change.

Adding a template means: the component plus its namespace constant under `src/presentation/emails/`, the two message files under `messages/{locale}/`, an `EMAIL_PREVIEWS` entry, and a caller that loads the namespace and calls `sendEmail`.

## What is not there

- No abandoned-cart email. The event is recorded in the audit log but nothing sends anything.
- No delivered notification.
- No email when a payment fails while the customer is still paying (`payment_intent.payment_failed`): the payment form shows the error instead.
- No retry or dead-letter queue for email; a failure is logged and audited. The person retries instead: a newsletter signup from the landing form or with "Resend email" in the account preferences, an unconfirmed account with "Send the confirmation link again" on the sign-in page, and a password reset with "Send a new link".
