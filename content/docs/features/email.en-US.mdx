## Sending

One function sends every transactional email — `src/integrations/resend/resend.send.ts`. Newsletters go out in batches through a path of their own, described under [The newsletter](#the-newsletter).

```ts
const RESEND_TEST_SENDER = /@resend\.dev>?$/iu

const refusesEverySend = ({ name, statusCode }: ErrorResponse, sender: string): boolean =>
  SENDER_REFUSAL_NAMES.has(name) || (SENDER_REFUSAL_STATUSES.has(statusCode) && !RESEND_TEST_SENDER.test(sender))

const deliver = async ({
  from,
  idempotencyKey,
  revealsAccountExistence,
  ...message
}: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const sender = from ?? shopSender()
  try {
    const { error } = await resend.emails.send(
      { ...message, from: sender, replyTo: BUSINESS.EMAIL },
      idempotencyKey === undefined ? {} : { idempotencyKey },
    )

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error, sender)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

The message, which is `react`, `subject`, `to` and any `attachments`, goes to Resend as it was passed. Only the order confirmation carries an attachment. An `idempotencyKey`, which every order email passes, goes to Resend as the `Idempotency-Key` header, so a retry under the same key never sends the email twice; see [Delivery and retries](#delivery-and-retries). `sendEmail` adds `replyTo: BUSINESS.EMAIL` to every message, so a customer's reply reaches the shop's contact address `kontakt@martebizuteria.pl` rather than `RESEND_EMAIL_FROM`; see [Resend](/docs/integrations/resend#sender-domain).

Note the contract: **it never throws.** It returns `undefined` on success and the failure message as a string otherwise. The Resend SDK has no timeout of its own, so `sendEmail` gives up after `SEND_EMAIL_TIMEOUT_MS` (10 seconds) and returns `Resend did not answer within 10000 ms`; a stalled Resend cannot hold a signup or a webhook open indefinitely. Every caller is therefore written as `const failure = await sendEmail(...)` followed by a decision about what to do with `failure` — a mail outage cannot roll back an order or a deletion.

Some refusals mean that no email from this sender can go out at all: a 401 or 403 from Resend (an invalid or restricted API key, or a sending domain that is not verified), an invalid `from` address, or an exhausted daily or monthly quota. For those, `sendEmail` also runs `markEmailSenderUnavailable` from `src/integrations/resend/resend.availability.server.ts` in the background, unless the caller passed `revealsAccountExistence: true`. Better Auth's verification, reset and change-email confirmation pass it, because they are sent only when an account does or does not exist, and a flag set by their refusal would reveal that. `markEmailSenderUnavailable` writes only when the flag is not set yet. It writes `email-sender-unavailable:<APP_ENV>` to the `CACHE` KV namespace with a five-minute expiry (`EMAIL_SENDER_UNAVAILABLE_SECONDS`). The key includes `APP_ENV` because development and preview share one namespace. A refusal that concerns one message, such as an invalid recipient, `rate_limit_exceeded`, a 5xx answer, a network error, the timeout, or the 403 that Resend's `resend.dev` test sender gets for any recipient but the Resend account owner, leaves the flag alone, so one bad address or one burst cannot stop every other email. Only the Better Auth gate acts on the flag, and it lets requests through when KV cannot be read; see [Better Auth](/docs/integrations/better-auth#email-delivery-gate). Nothing clears it early: once the sender is fixed, the first attempt after the flag expires goes out normally.

Four of the emails go to any address a visitor types in: the verification email, the password-reset link and the two newsletter emails. Their senders first ask `admitPublicEmail` in `src/integrations/resend/resend.public-email-limits.server.ts`, which allows three of one kind to one address an hour and 50 of all four kinds a day for the whole shop. An email past either limit is skipped, and the visitor gets the same answer as if it had been sent, because a different one would reveal whether the address has an account or a subscription; the daily limit also records `email.failed`. Every other email goes straight to `sendEmail`, so a busy day never holds back an order email. See [Resend: Emails visitors can request](/docs/integrations/resend#emails-visitors-can-request).

The client is `src/integrations/resend/resend.config.ts`, a one-line `new Resend(env.RESEND_API_KEY)`. The default `from` is `APP_NAME <RESEND_EMAIL_FROM>`. Both `RESEND_API_KEY` and `RESEND_EMAIL_FROM` are in the `secrets.required` list of every environment in `wrangler.jsonc`. The sender's domain must be verified in Resend, and a deploy stops before the build when it is not; see [Resend](/docs/integrations/resend#sender-domain).

## Localisation

An email is never rendered with a React hook. Messages are loaded explicitly and passed in as a prop, and the subject is produced by a standalone translator:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await requireAuthEmailDelivery("verification", {
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verificationUrl }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

`loadNamespace` is from `src/integrations/use-intl/i18n.messages.ts` and `createTranslator` from `use-intl` — the non-React entry point, which is what makes this work inside a webhook handler with no request context.

Where the locale comes from differs by trigger:

| Trigger                   | Locale source                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------ |
| Better Auth emails        | `getCurrentLocale()` — the request the user is making                                |
| `sendAccountDeletedEmail` | The `locale` captured before the deletion, falling back to `getCurrentLocale()`      |
| Newsletter emails         | The `locale` sent with the subscription, falling back to `getCurrentLocale()`        |
| Newsletter campaign       | Each subscriber's `newsletter_subscriber.locale`; a test send renders both languages |
| Order confirmation        | `resolveCheckoutSessionLocale(session)` from the Stripe session metadata             |
| Payment failed            | `resolveCheckoutSessionLocale(session)` from the Stripe session metadata             |
| Order shipped             | `resolveOrderLocale(orderRow.metadata)` from the order's stored JSON                 |
| Order cancelled, refunded | `resolveOrderLocale(orderRow.metadata)` from the order's stored JSON                 |
| Shop's new-order notice   | `I18N.DEFAULT_LOCALE`, the shop's own language, whatever the customer used           |
| Shop's incident alert     | `I18N.DEFAULT_LOCALE`, the shop's own language                                       |

The order emails matter: a webhook has no browser, and an admin's language is not the customer's, so the locale must have been persisted at checkout time. `createStripeSession` puts `locale: getCurrentLocale()` in the session metadata and `prepareFulfillCheckoutBatch` copies it into `order.metadata`, which is why a Polish customer's shipping notice arrives in Polish days later.

## Link origin

Links the shop writes into its own emails point at the address the customer or admin was using, the way Better Auth's links follow the host it was called on. A server function resolves the origin before it writes anything, with `resolveRequestOrigin(request)` (`src/lib/request.ts`): it takes the origin from `request.url`, accepts only the hosts `appHostsForMode(import.meta.env.MODE)` lists, and throws `AppError(FORBIDDEN)` for anything else. The origin is then passed down as a string: `sendNewsletterConfirmationEmail({ email, locale, origin, token })`, `sendNewsletterAlreadySubscribedEmail({ email, locale, origin })`, `sendAccountDeletedEmail({ email, locale, name, origin })`, `sendOrderShippedEmail(orderId, origin)` and `sendOrderCancelledEmail({ orderId, refundedAmount }, origin)`. After a self-service deletion, Better Auth's `afterDelete` hook resolves it from the request Better Auth hands it, and after a password reset `sendPasswordChangedEmail` does the same with the request Better Auth hands `onPasswordReset`.

The order confirmation is sent from the Stripe webhook, whose request only says which endpoint Stripe called. It takes its origin from the session's `return_url` instead: the checkout request built that URL on its own validated origin, and it comes back inside the signature-checked event. `resolveDeploymentOrigin(session.return_url)` accepts a host that any deployment serves, local, preview or production, and requires `https:` everywhere but `localhost:3000` and `127.0.0.1:3000`. A local checkout therefore links back to the address it was made on, even though `stripe:listen` forwards the webhook to `localhost:3000`, and even when the preview deployment, which shares the Stripe test account and the database with development, fulfils it. The failed-payment email does the same with the session in its event, the shop's new-order email with the session that created the order, and the refund email with the Checkout Session `resolveCheckoutSession` finds for the refunded charge.

Used on `http://127.0.0.1:3000`, the shop links to `http://127.0.0.1:3000`. On preview it links to the preview host in use, and in production to `https://martebizuteria.pl` or `https://martebizuteria.pjborowiecki.workers.dev`, whichever the customer or admin used. `APP_URL` is used for SEO only. [Resend](/docs/integrations/resend) lists where each flow gets its origin.

## Order confirmation in detail

This is the most involved template. `sendOrderConfirmationEmail` in `src/modules/order/use-cases/send-order-confirmation-email.server.ts` builds it in `buildOrderConfirmationEmailPayload`:

1. The recipient is `session.customer_email ?? session.customer_details?.email`. If there is none, nothing is built and the failure `The Stripe session has no email address` is recorded against the order. Before that, `attemptOrderConfirmationEmail` takes the link origin from `session.return_url` with `resolveDeploymentOrigin`. A session without one records `The Stripe session has no return URL to link the email to`, and one on a host no deployment serves records `FORBIDDEN`.
2. `getCheckoutEmailContext(checkoutId)` loads the addresses, the delivery method, the locker id and the locker's address, the customer note and the company a business buyer asked to be invoiced. When the checkout has a company name or NIP, `describeCompanyInvoice` puts the name above `NIP <digits>`, and the details block shows them under "Invoice for a company" after the billing address; otherwise the row is left out.
3. `resolveStripePaymentMethodLabel(session, messages)` turns the Stripe payment method into a translated label.
4. `getFulfillmentTimeAttributesByVariantId(variantIds)` reads the `czas-realizacji` attribute each ordered variant's product page shows, and `resolveOrderLineFulfillmentTimes(order.lines, attributes, locale)` labels it in the order's locale. `buildOrderConfirmationDetails({ context, fulfillmentTimes, messages, paymentMethod })` then assembles the details block.
5. `buildOrderConfirmationItems(order.lines, locale, origin)` formats the line items, linking each one to its product page on `origin`, the address the checkout was made on.
6. `buildOrderAccountCta({ isGuest, locale, messages, orderId, origin })` chooses the button: a signed-in customer gets a link to `/account/orders/<id>`, a guest gets `/auth/sign-up`. `isGuest` is derived from an empty `userId` in the session metadata.
7. Totals: `itemsSubtotal` from the metadata lines and `shippingTotal = Math.max(session.amount_total - itemsSubtotal, 0)`.
8. `buildOrderLegalLinks(origin, locale, orderNumber)` links the terms of service, the exchanges-and-returns page, the privacy policy and the online withdrawal form at `/withdraw-from-contract?order=<number>` on `origin`, in the order's locale.
9. `loadWithdrawalFormAttachment(origin)` in `src/modules/order-withdrawal/order-withdrawal.form.server.ts` reads `/forms/formularz_zwrotu.pdf` through the Worker's `ASSETS` binding and returns it base64-encoded as a Resend attachment. The binding serves `public/` through Vite in development and the deployed static assets in preview and production, so the PDF is attached everywhere, including a local checkout whose `localhost` address Resend could not fetch. If the form cannot be read, the payload is not built and the order records the failure, such as `The withdrawal form /forms/formularz_zwrotu.pdf could not be read from the static assets: HTTP 404`, instead of sending a confirmation without it.

The helpers are in `src/modules/order/order.email.utils.ts`. `describeEmailDestination` there shows a locker order's parcel locker, with its code, directions and address, as where the order goes, and the shopper's name and phone as the recipient InPost texts the pickup code to; see [Shipping and delivery](/docs/features/shipping-and-delivery#delivery-in-the-emails).

The email is the confirmation of the contract on a durable medium that Article 21 of the Consumer Rights Act requires, so below the sign-off it repeats what the customer agreed to: the seller's legal name, postal address, NIP, e-mail and phone from `BUSINESS` in `src/presentation/branding/business.ts`, the 14-day right of withdrawal with how to use it, who pays to send the goods back and how the refund is made, the complaint procedure with the out-of-court routes of § 10 of the terms, and the three legal links. The total with VAT and delivery, the payment and delivery method and the delivery time are in the order summary above it. See [Legal pages](/docs/features/legal-pages#the-order-confirmation).

The transit estimate is copy chosen by delivery type, and the fulfilment time is the longest one the ordered products' pages give, stated as a period rather than a reference to those pages, which can change after the order. See [Shipping and delivery](/docs/features/shipping-and-delivery#delivery-in-the-emails):

```ts
const deliveryType = context?.deliveryMethod?.type ?? "courier"

return {
  estimatedDelivery: messages.estimatedDelivery[deliveryType],
  fulfillmentTime: describeOrderFulfillmentTime(fulfillmentTimes, messages),
}
```

## Cancellation, refund and failed payment

**Cancelled.** `cancelOrder` sends `order-cancelled.tsx` after its batch has cancelled the order, so a cancellation the batch refuses sends nothing. `requestFullOrderRefund` returns the `amount` of the refund Stripe created, and the email states it with how the money comes back; a free order is told there was nothing to refund. `sendOrderCancelledEmail` in `send-order-cancelled-email.server.ts` reads the address, number, currency, total, locale and account of the order with `getOrderForRefundEmail` and links the account button on the admin's origin, as the shipped email does.

**Refunded.** Every refund reaches the shop as `charge.refunded`: the Refund button, the refund a cancellation issues and one made in the Stripe dashboard. `prepareRefundBatch` starts with a select of the payment's `refunded_amount` and the order's status, so `refundOrder` learns what the payment had recorded before this event in the same D1 transaction that records it. It returns the refund as `Order["unannouncedRefund"]` only when the charge's refunds that still stand, read from Stripe when the event is handled and leaving out any that are `failed` or `canceled`, add up to more than that and the order was not cancelled, and the email states the difference. Each partial refund is therefore announced once with its own amount, and the one that completes the refund says the order was refunded in full; when a newer event overtakes an older one, its email covers both refunds. The payment keeps the larger of the recorded amount and the event's, so a redelivered event, an older event delivered after a newer one and the `charge.refunded` that follows a cancellation's own refund return nothing, and D1 runs concurrent deliveries one batch at a time, so only one of them sees the lower amount. `handleChargeRefunded` then sends through `sendOrderRefundedEmail({ ...refund, refundId }, session.return_url)`, with `refundId` the newest refund that stands. When the refund's event lands before the cancellation's batch, the order is already refunded, the cancellation is refused, and the customer gets the refund email alone. A refund that fails or is cancelled after it was announced sends the customer nothing: `refund.failed` and `refund.updated` take it off the order and alert the shop instead, because the owner decides how to pay the money back (see [Payments: Refunds and disputes](/docs/features/payments#refunds-and-disputes)).

**Payment failed.** `checkout.session.async_payment_failed` arrives when a delayed payment fails after the customer left the checkout. `releaseCheckout` returns whether its batch moved the session's payment from `pending` to `failed`, and `handleAsyncPaymentFailed` sends `payment-failed.tsx` through `sendPaymentFailedEmail` in `src/modules/checkout/use-cases/send-payment-failed-email.server.ts` only then, so a redelivered event finds nothing pending and sends nothing, and an expired session sends nothing at all. The email goes to the session's address in the session's locale, lists the pieces with links to their product pages, states the amount and links back to `/products`. No order exists, so `deliverOrderEmail` records the outcome against the session id, the target of the `order.released` entry of the same release; it shows in `/admin/audit` rather than on an order. A refused payment failure email is retried like every order email, under the key `payment-failed/<session id>`, but with no order page to show it on it cannot be resent by hand.

## The shop's new-order email

Every order is also emailed to the shop, so the owner learns of it without watching the admin. `announcePlacedOrder` in `src/integrations/stripe/stripe.fulfillment.server.ts` starts `sendNewOrderEmail(orderId, session.return_url)` from `src/modules/order/use-cases/send-new-order-email.server.ts` next to the customer's confirmation and returns both as one `Promise.all`. It runs once per order, for whichever of the Stripe webhook and the shopper's return page placed it: `handleFulfillCheckoutSession` hands the promise to `scheduleBackgroundWork` and awaits it, and the return page only hands it to `scheduleBackgroundWork`, so the confirmation page does not wait for Resend (see [Payments: Fulfilment from the return page](/docs/features/payments#fulfilment-from-the-return-page)). A redelivered event, and the late webhook of an order the return page placed, create no order and send neither email.

The recipient is `RESEND_EMAIL_FROM`, the address the shop sends from, which every environment requires, so every environment sends the notice. In the `test` environment the end-to-end suite builds, `.env.test` sets it to `noreply@example.test`, a dummy inbox the mocked Resend captures.

The email is in the shop's language, `I18N.DEFAULT_LOCALE`, whatever language the customer used. It reads the order with `getAdminOrderDetailRow` and `getAdminOrderItemRows`, the reads behind the admin order page, and states the order number in the subject and heading, every piece with its variant, SKU, quantity, unit price and line total (`mapAdminOrderDetailItem`), the total with delivery, the customer's name, e-mail and phone, the delivery method, the destination, which is the parcel locker with its code and address for a locker order and otherwise the shipping address from the order's snapshot (`resolveAdminOrderDetailAddresses`), the company to invoice and the customer's note. The company row appears only when the order has a company name or NIP: `describeCompanyInvoice` gives the name and `NIP <digits>`, followed by the billing address from the order's snapshot, so the owner has what the invoice needs. Its button opens `/admin/orders/<id>` (`ROUTES.ADMIN_ORDER`) on the origin of the session's `return_url`, the origin of the confirmation's links.

The attempt goes through `deliverOrderEmail` like every order email, under the key `new-order/<order id>` and labelled `New order notification → <address>`, so a refusal is retried and, when the retries fail too, shows on the order's Activity card with **Resend email** and in `/admin/audit`. It never touches the order or the customer's confirmation: `sendNewOrderEmail` does not throw, and the webhook still answers 200.

## Delivery and retries

Every order email goes out through `deliverOrderEmail` in `src/modules/order/order.email-delivery.server.ts`. The caller hands it a function that prepares and sends the email under a given idempotency key, and describes the delivery:

```ts
export const sendOrderShippedEmail = (orderId: string, origin: string): Promise<boolean> =>
  deliverOrderEmail((idempotencyKey) => attemptOrderShippedEmail(orderId, origin, idempotencyKey), {
    idempotencyKey: `${ORDER_EMAIL_KIND.SHIPPED}/${orderId}`,
    label: ORDER_SHIPPED_LABEL,
    orderEmail: { kind: ORDER_EMAIL_KIND.SHIPPED },
    orderId,
  })
```

`attemptOrderConfirmationEmail`, `attemptPaymentFailedEmail`, `attemptOrderInProgressEmail`, `attemptOrderShippedEmail`, `attemptOrderDeliveredEmail`, `attemptOrderTrackingEmail`, `attemptOrderCancelledEmail`, `attemptOrderRefundedEmail` and `attemptNewOrderEmail`, each in the `send-*-email.server.ts` use case that hands it to `deliverOrderEmail`, read what their email needs, render it and pass the key to `sendEmail`. They return `{ failure, label }`, where `label` is a human string such as `Order confirmation → jane@example.com`.

Each key names the email and what it is about:

| Email                         | Idempotency key                                             |
| ----------------------------- | ----------------------------------------------------------- |
| Order confirmation            | `order-confirmation/<order id>`                             |
| New-order notice to the shop  | `new-order/<order id>`                                      |
| Fulfilment started            | `order-in-progress/<order id>`                              |
| Shipped                       | `order-shipped/<order id>`                                  |
| Delivered, the thank-you      | `order-delivered/<order id>`                                |
| Tracking number               | `order-tracking/<order id>/<tracking number>`               |
| Cancelled                     | `order-cancelled/<order id>`                                |
| Refunded                      | `order-refunded/<order id>/<Stripe refund id>`              |
| Payment failed                | `payment-failed/<Checkout Session id>`                      |
| Withdrawal acknowledgement    | `order-withdrawal/<order id>/<statement time in ms>`        |
| Withdrawal notice to the shop | `order-withdrawal-notice/<order id>/<statement time in ms>` |

Resend keeps a key for 24 hours and answers a request whose key it has already sent with the original response instead of sending again. A retry therefore never delivers an email twice, even when the first attempt only looked failed because Resend answered after `SEND_EMAIL_TIMEOUT_MS`. A refund's key carries the id of the Stripe refund it announces, so two partial refunds of the same amount are two emails, and so is a refund issued again for the same amount after the first one failed. A refund email recorded before the key named the refund has no `refundId` in its audit metadata; Resend email sends it again under its old key, `order-refunded/<order id>/<total refunded>`, so the resend settles that record.

`deliverOrderEmail` awaits the first attempt and returns whether Resend took it. When it did not, the attempt is recorded as `email.deferred` and the retries go to `scheduleBackgroundWork`, the request's `waitUntil`, so the response does not wait for them and no queue is involved. The email is tried again after `ORDER_EMAIL_RETRY_DELAY_MS` (one second) and again `ORDER_EMAIL_RETRY_BACKOFF` times that later (four seconds), `ORDER_EMAIL_RETRIES` retries in all, each preparing the email afresh and sending it under the same key. The first retry Resend takes is recorded as `email.sent`; an email still refused after the last one is recorded as `email.failed`, and `sendIncidentAlert` emails `RESEND_EMAIL_FROM` an `orderEmailFailed` alert keyed by the idempotency key, so each email that finally fails alerts once, like the shop's other incidents (see [The shop's incident alerts](#the-shops-incident-alerts)). With `SEND_EMAIL_TIMEOUT_MS` at ten seconds the retries end about 25 seconds after the response at the latest, inside the 30 seconds the Workers runtime gives `waitUntil` work. Every failure is retried, including one that comes from preparing the email, because a failed D1 read or asset fetch recovers as often as a rate-limited send does; one that cannot recover, such as an order without an address, ends as `email.failed` five seconds later.

An error thrown while the email is prepared is logged with its stack as `<label> for order <id> could not be prepared:` and becomes the outcome, labelled without a recipient and described the way `sendEmail` describes an error it catches.

## Order progress emails, once each

Resend keeps a key for only 24 hours, and the audit log is written through a queue and expires, so neither can tell whether the customer was already told about a step. The order row does.

`fulfillOrder` claims the fulfilment started email (`order-in-progress.tsx`, sent by `sendOrderInProgressEmail`) by setting `in_progress_email_at` while the order is `fulfilled` and the column is empty, and sends it only when the claim matched, through `announceClaimedOrderEmail` in `order.email-delivery.server.ts`; otherwise the notice is `alreadySent`. The email says the handmade piece is being prepared in the atelier and, by delivery type, that a shipping email with the tracking number follows, or for a pickup that the shop writes when it can be collected. `20261015200000_order_fulfillment_started.sql` added `in_progress_email_at` together with `fulfillment_started_at`, the time fulfilment started, and set both for every order already past confirmation, from its first `order.fulfillment_started` audit entry or else its shipping, delivery or last update time.

`markOrderDelivered` claims the thank-you email (`order-delivered.tsx`, sent by `sendOrderDeliveredEmail`) the same way, by setting `delivered_email_at` while the order is `delivered` and the column is empty; `20261015300000_order_delivered_email.sql` set it for every order already delivered. The email thanks the customer, hopes they enjoy the handcrafted piece, gives four care tips condensed from the FAQ's jewellery care answers with a link to `/faq`, repeats that a consumer may withdraw within 14 days of taking possession of the products, except for pieces made to their own specifications, in the order confirmation's words, with links to the withdrawal form for this order and to Exchanges and returns, and gives `BUSINESS.EMAIL` and `BUSINESS.PHONE`. It names no deadline date, because the admin may mark the order delivered later than the customer received it.

`shipped_email_at` and `tracking_email_number`, added by `20261015150000_order_shipped_email.sql`, record that the customer was told the order shipped and the tracking number they were last sent. `announceOrderShipment` in `src/modules/order/use-cases/announce-order-shipment.server.ts` claims an email with one conditional `UPDATE … RETURNING` before it sends it:

- The shipped email is claimed by setting `shipped_email_at` while the order is `shipped` and the column is empty. The same statement copies the order's tracking number into `tracking_email_number`, so the number the shipped email carries is not sent again.
- Otherwise the tracking number email (`order-tracking.tsx`, sent by `sendOrderTrackingEmail`) is claimed by copying the tracking number into `tracking_email_number` while the order is `shipped`, its shipped email is claimed and its number is set and differs from the one last sent.
- When neither claim matches, nothing is sent and the notice is `alreadySent`.

Only the request whose claim matched sends, and nothing clears a claim, so repeated clicks, a second tab, and an order stepped back and shipped again never send the same email twice. `shipOrder` announces right after it ships the order. `refreshInpostShipment` and the InPost webhook announce in the background after they read the shipment back, so a number InPost assigns after the parcel was marked shipped reaches the customer once, while a number known before the order ships goes out in the shipped email itself. A different number typed when an order is shipped again goes out the same way. The migration counts every order that was already shipped or delivered as told, with the number it had, so none of them gets a late email. A claimed email whose delivery finally fails is not sent again by moving the order forward; **Resend email** in the Activity card sends it again under its own key.

## Withdrawal from the contract

`order-withdrawal.tsx` exports two e-mails over one message catalogue, `emails.order-withdrawal`, because both repeat the same statement. `OrderWithdrawalReceived` (`received`) is the acknowledgement on a durable medium that Article 11a of the Consumer Rights Directive requires: it goes to the order's e-mail address in the language of the request, states that the statement arrived and repeats its content, then says where to send the products back and how the refund works. `OrderWithdrawalNotice` (`notice`) goes to `RESEND_EMAIL_FROM` in the shop's language with a link to the order in the admin. They are built by `sendWithdrawalConfirmationEmail` and `sendNewWithdrawalEmail` in `src/modules/order-withdrawal/use-cases/` and recorded as `Withdrawal acknowledgement → <address>` and `Withdrawal notice → <address>`. They go out through `deliverOrderEmail` like the order emails, under the keys `order-withdrawal/<order id>/<statement time>` and `order-withdrawal-notice/<order id>/<statement time>`, so a refused one is tried twice more and then alerts `RESEND_EMAIL_FROM`; neither carries what **Resend email** needs, so the Activity card never offers them. The date and time are written out in Polish time with `Intl.DateTimeFormat`, because the Worker runs in UTC. A withdrawal sent by order number from `/withdraw-from-contract` sends both only when `admitPublicEmail` admits a `withdrawal` e-mail to the order's address, like the other e-mails a visitor can ask for; one from the account always sends them. See [Legal pages: The withdrawal function](/docs/features/legal-pages#the-withdrawal-function).

## The shop's incident alerts

`sendIncidentAlert` in `src/lib/incident-alert.server.ts` emails `RESEND_EMAIL_FROM` when something the owner must act on fails: a paid Checkout Session that cannot become an order, a Stripe event the webhook answers with an error, an audit-log batch the queue consumer cannot process, a newsletter campaign that stops part way, an order email still refused after its retries, and a refund Stripe reports as failed or cancelled after the shop recorded it. The template is `incident-alert.tsx` with its `emails.incident-alert` catalogue, in the shop's language, with a heading and an explanation for each kind of incident, the reference, the cause and the environment.

Every environment sends the alerts, like the shop's new-order notice. Each incident is keyed by its environment, kind and reference — the Checkout Session, the Stripe event id, the Stripe refund id, the queue, the campaign or the order email's idempotency key — in the `CACHE` KV namespace for an hour (`INCIDENT_ALERT_SECONDS`), or for a failed Stripe event the three days Stripe retries it (`STRIPE_EVENT_RETRY_SECONDS`), so a retry storm sends one email. An alert never throws: a failure to read KV, render or send is logged with `[Alert]`, and the webhook's answer and the queue's retry stay as they were. Unlike order emails, alerts are not recorded in the audit log, because the database may be what failed. [Monitoring and alerts](/docs/guides/monitoring-and-alerts) explains when each one fires and what to do.

## Auditing

`deliverOrderEmail` records every outcome through `recordOrderEmailOutcome` in `src/modules/audit-log/audit-log.events.server.ts`, with the key and the email in the entry's metadata:

```ts
export const recordOrderEmailOutcome = ({ failure, label, metadata, orderId, willRetry }: Readonly<OrderEmailOutcomeRecord>): void => {
  if (failure === undefined) {
    recordEmailSentAudit(orderId, { detail: label, metadata, resourceId: orderId })

    return
  }
  console.error(`${label} failed for order ${orderId}: ${failure}`)
  const options = { detail: `${label} — ${failure}`, metadata, resourceId: orderId }
  if (willRetry) {
    recordEmailDeferredAudit(orderId, options)

    return
  }
  recordEmailFailedAudit(orderId, options)
}
```

An attempt Resend does not take therefore always ends in an entry, `email.deferred` first and `email.failed` when the retries fail too:

| What went wrong                   | Detail of the entry                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| Resend refused the send           | `Order confirmation → jane@example.com — The example.com domain is not verified…`    |
| The Stripe session has no address | `Order confirmation — The Stripe session has no email address`                       |
| The order has a blank address     | `Order shipped — The order has no email address`                                     |
| The order row is gone             | `Order shipped — The order could not be found`                                       |
| The session has no return URL     | `Order refunded — The Stripe session has no return URL to link the email to`         |
| Preparing the email threw         | `Order shipped — D1_ERROR: …`, or the thrown value as text when it is not an `Error` |

The order id is the target and `resourceId` of every entry, and its metadata is `{ idempotencyKey, orderEmail }`, where `orderEmail` is what a resend needs to build the email again: its kind and, for a cancellation, the refunded amount, for a refund, the refund's amount, whether it completed the refund and the refunded total. The outcome therefore shows in the order's **Activity** card in the admin, as "Email deferred" with a "Deferred" badge or "Email failed" with a "Failed" badge and the detail underneath, and in `/admin/audit` under the `email` category with severity `warning` or `error`. Audit entries reach D1 through the queue a few seconds after the send, so `processAuditLogQueueBatch` publishes `ORDER_QUERY_KEYS.ADMIN.ORDERS` and the overview's `ADMIN_DASHBOARD_QUERY_KEYS.ALL` whenever a batch carries an action from an order timeline: every open admin tab refetches the order list, stats, order page or overview it has on screen and drops the order and overview queries it only has cached, so an open order page shows the entry without a reload. Newsletter and Better Auth failures use the same `email.failed` action, so they trigger that refetch as well. An entry can still be lost on its way to D1, when the queue send fails, or when it still cannot be written after the dead-letter queue has retried it on its own three times; only the Worker log has the failure then, and the failures also email `RESEND_EMAIL_FROM`, at most once an hour for each queue.

## Resending from the order

The Activity card offers **Resend email** under the newest `email.deferred` or `email.failed` entry of each order email that has not gone out since. `resolveResendableOrderEmails` in `src/modules/order/order.detail.utils.ts` reads the order's timeline newest first, takes the first delivery entry of each idempotency key whose metadata names an email, and offers it unless it is `email.sent`. Entries written before deliveries carried this metadata, and the failed payment email, which belongs to a session rather than an order, are never offered.

The button calls `resendOrderEmail` in `src/modules/order/use-cases/resend-order-email.ts` with the order and the entry's id. It requires `order: ["update"]`, reads the timeline again and refuses with `CONFLICT` unless the entry is still the one to resend, so a second tab or an email that went out in the meantime sends nothing. It records `email.resend_requested` against the order through `scheduleAuditLogFromRequest`, with the admin as the actor, their IP address and the failed entry's detail, and then builds the email again from the sources its first attempt used. The shipped, tracking number and cancellation emails link on the admin's origin, as `shipOrder` and `cancelOrder` do, and a tracking number email is sent again with the number its failed delivery carried. The confirmation, the shop's notice and a refund email retrieve the order's Checkout Session from Stripe by the payment's `transaction_id`, and an order without one is refused with `CONFLICT`. The resend goes through the same notifier and `deliverOrderEmail` under the same key, with the same retries and entries, so within 24 hours of the first send an email that did reach Resend, although its outcome said otherwise, is not sent a second time.

The hook `useResendOrderEmail` toasts "Email sent" when Resend took the email, and "Email not sent yet", saying that it is tried twice more, when it did not. While the email has still not gone out, the button appears again under its newest entry.

A newsletter email that Resend refuses is audited as well. `subscribeToNewsletter` calls `recordEmailFailedAudit(email, { detail })`: the address is the audit target, and the detail names the email and the Resend error, such as `Newsletter confirmation — The example.com domain is not verified` or `Newsletter already-subscribed notice — …`. An unverified sender domain therefore shows up in `/admin/audit` on the first signup instead of only in the Worker log. An email that went out is not recorded.

Better Auth's five emails are audited the same way, through `recordAuthEmailFailure` in `auth.email-delivery.server.ts`:

```ts
export const recordAuthEmailFailure = (kind: string, recipient: string, failure: string): void => {
  console.error(`[Auth] Failed to send ${kind} email to ${recipient}: ${failure}`)
  recordEmailFailedAudit(recipient, { detail: `Auth ${kind} email — ${failure}` })
}

export const deliverAuthEmail = async (kind: string, email: Parameters<typeof sendEmail>[0]): Promise<boolean> => {
  const failure = await sendEmail(email)
  if (failure === undefined) {
    return true
  }

  recordAuthEmailFailure(kind, email.to, failure)

  return false
}
```

The target is the recipient's address and the detail names the email, for example `Auth reset-password email — The example.com domain is not verified`. The verification or reset link never goes into the audit log, because it is a credential. Whether the person is told depends on the endpoint; [Better Auth](/docs/integrations/better-auth) lists what each one answers.

Only `deliverOrderEmail` writes `email.deferred`. The other emails record a refusal as `email.failed`: Better Auth's emails and the newsletter sign-up emails at once, a newsletter campaign when its third batch attempt fails.

## Waiting for the send

The shop's own senders wait for Resend's answer, so the result reaches whoever is looking. Better Auth's sign-up, password reset and change-email hooks are the exception: Better Auth runs them through `advanced.backgroundTasks`, which is `scheduleBackgroundWork` (`src/lib/background.ts`, the Worker's `waitUntil`), as [Better Auth](/docs/integrations/better-auth) describes. The password-changed email is the other exception: `onPasswordReset` hands `sendPasswordChangedEmail` to `scheduleBackgroundWork` itself and does not wait for it, because Better Auth signs every device out only after the hook returns.

`shipOrder`, `cancelOrder`, `deleteCustomer` and the Stripe webhook also hand the send they wait for to `scheduleBackgroundWork` before awaiting it. For the order progress emails `awaitOrderEmailNotice` in `order.email-delivery.server.ts` does it:

```ts
export const awaitOrderEmailNotice = async (
  kind: Order["emailNotice"]["kind"],
  delivery: Promise<boolean>,
): Promise<Order["emailNotice"]> => {
  scheduleBackgroundWork(delivery)

  return { kind, status: (await delivery) ? ORDER_EMAIL_NOTICE_STATUS.SENT : ORDER_EMAIL_NOTICE_STATUS.FAILED }
}
```

When the admin closes the tab or Stripe stops waiting, the Workers runtime may cancel what the request was still awaiting, but not a promise passed to `waitUntil`. The email therefore still goes out and its outcome is still recorded. The request waits only for the first attempt: `deliverOrderEmail` schedules the retries of a refused order email the same way, so they run after the response. Better Auth's `afterDelete` awaits `sendAccountDeletedEmail` without this, so a customer who closes the tab during self-deletion can still cut the goodbye email short.

`fulfillOrder` and `markOrderDelivered` return the same `email` notice for the fulfilment started and thank-you emails, and `useFulfillOrder` and `useMarkOrderDelivered` show the same warnings. `shipOrder` returns `email`, the notice `announceOrderShipment` gives back: the email it claimed, `order-shipped` or `order-tracking`, with `sent` or `failed`, whether Resend took it at the first attempt, or `alreadySent` when that email was already claimed for the order (see [Order progress emails, once each](#order-progress-emails-once-each)). The admin always sees "Order marked as shipped.". A failed email adds the warning "Customer email not sent yet", which names the email, says it is tried twice more within a few seconds and that, if it still fails, it can be resent from the order's Activity card, which also shows the error; `alreadySent` adds "No repeat email", and a tracking number email "Tracking number sent". The order stays shipped either way, because the senders record a failure and return `false` instead of throwing. Shipping from the orders list shows the same toasts, and `setOrderTrackingNumber` returns the same `email`, so Add tracking number shows "Tracking number saved." with the same warnings.

`cancelOrder` awaits `sendOrderCancelledEmail` after the cancel batch in the same way and returns `cancelledEmailSent`. The admin sees the cancellation toast and, when Resend did not take the email at once, a warning toast, "Cancellation email not sent yet", with the same retry and resend advice. The order stays cancelled and its refund stays issued.

`deleteCustomer` awaits `sendAccountDeletedEmail` after `removeUser` and returns `goodbyeEmailSent`. The admin sees "The account was deleted and a confirmation email was sent.", or, when the email failed, a warning toast titled "Account deleted — email not sent" that points to the audit log. A refusal never undoes the deletion: `sendAccountDeletedEmail` returns `false` instead of throwing, both when Resend refuses the email and when it cannot even be prepared. The email says what was deleted, including the Stripe customer with the saved cards, and that the orders and payments are kept for 5 years from the end of the year of each order for the accounting records, no longer linked to an account, and that a new account confirmed with the same address shows them again.

`subscribeToNewsletter` awaits its email, because the person who just signed up is told whether it went out. A new, pending or unsubscribed address gets `sendNewsletterConfirmationEmail`; an address that is already confirmed, submitted by anyone but its signed-in owner, gets `sendNewsletterAlreadySubscribedEmail`. Both return the Resend error message, or `undefined` when the send was accepted. On a failure the use case logs it, audits it and answers `confirmationFailed`. A subscriber row that was waiting for confirmation stays `pending`, so submitting the address again issues a fresh token and sends a new email. The request takes one Resend round trip longer, at most `SEND_EMAIL_TIMEOUT_MS`, which the form covers with its "Signing you up..." state.

The Stripe webhook awaits `sendOrderConfirmationEmail` and `sendNewOrderEmail` too, but nobody sees its answer, so the order's activity is where a failure shows. Neither throws: a refusal and a thrown error both end in an `email.deferred` entry and the retries, and the webhook still answers 200 without waiting for them. Throwing would not resend the email anyway. The handler would answer 500 and Stripe would redeliver the event, but on redelivery `fulfillCheckout` finds no pending checkout and the handler stops before the email step, so the only effects would be failed deliveries in Stripe and a coupon cleanup pushed to the retry.

The checkout success page therefore does not say the confirmation is on its way. It asks the shopper to contact the shop and quote the order number if the email has not arrived within a few minutes.

## The newsletter

The owner writes newsletters on the admin's **Marketing** page, `/admin/marketing`. **New newsletter** opens `/admin/marketing/new`, built from the content editor's pieces: a Polish and an English tab, each with a subject of up to 150 characters and a letter of up to 20 000 characters written in the same Markdown editor as the information pages. Links must be full `https://`, `mailto:` or `tel:` addresses, because a relative link means nothing in an inbox, and images are refused as they are on content pages; `newsletterCampaignZodSchemas.composeValues` checks both with `hasOnlyMarkdownLinksMatching(NEWSLETTER_LINK_PATTERN)`. Leaving the page with an unsent letter asks first.

**Send test to me** calls `sendNewsletterTest`, which sends both language versions to the signed-in admin's own address, without recording a campaign and without unsubscribe headers. **Send to subscribers** asks for confirmation, naming how many confirmed subscribers the letter reaches, and calls `sendNewsletterCampaign`. Both require `content: ["update"]`.

`sendNewsletterCampaign` counts the confirmed subscribers and refuses with `NEWSLETTER_NO_RECIPIENTS` when there are none. It records the campaign in `newsletter_campaign` under the id the composer generated when it opened, with both subjects and letters, the origin of the admin's request, which the links point to, the recipient count and the status `sending`. The insert does nothing when the id is already there and the function answers `NEWSLETTER_ALREADY_SENT`, so a double click or a retried request never starts a second send. The campaign then goes onto the `NEWSLETTER_QUEUE` Cloudflare Queue, the send is audited as `newsletter.sent` against the admin, and open admin pages refresh the list. When the queue refuses the message, `deleteUnsentNewsletterCampaign` removes the campaign again, unless a batch has already gone out, so the list shows nothing that never started and the admin is told nothing was sent. The composer keeps the letter and its id, so sending again records and queues the campaign afresh, and a retry whose first attempt did reach the queue still answers `NEWSLETTER_ALREADY_SENT`.

`processNewsletterQueueBatch` in `src/modules/newsletter-campaign/newsletter-campaign.queue.server.ts`, which `src/server.ts` calls for a batch from a queue whose name starts with `martebizuteria-newsletter`, sends one batch of the campaign per message. It reads the next 100 (`NEWSLETTER_BATCH_SIZE`) confirmed subscribers in id order after `last_recipient_id`, the last one the campaign reached, and `sendNewsletterBatch` in `src/modules/newsletter-campaign/use-cases/send-newsletter-batch.server.ts` sends them in one call to Resend's batch endpoint, which takes at most 100 emails. Each subscriber gets the subject and the letter in the language they subscribed in, rendered by `newsletter-campaign.tsx` inside the shop's layout and followed by why they receive it and an **Unsubscribe** link to `/newsletter/unsubscribe?token=<their token>` in their language, which works without signing in. The letter ends by naming who sends it, as Article 9 of the Polish Act on the Provision of Services by Electronic Means requires of commercial information: the trader's legal name and address from `BUSINESS_POSTAL_ADDRESS_LINES`, the country, and the shop's e-mail, `BUSINESS.EMAIL`. Each email also carries `List-Unsubscribe: <origin/api/newsletter/unsubscribe?token=…>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, so mail providers can offer their own unsubscribe button, which posts to that route (RFC 8058).

A campaign is never sent twice. Each batch goes to Resend with the idempotency key `newsletter-<campaign id>`, or `newsletter-<campaign id>-after-<last subscriber id>` after the first batch, so Resend does not send a batch again when its message is delivered twice within 24 hours. The cursor moves only through an update conditional on the cursor the batch started from, and only the delivery that moved it queues the next batch, one second later. The consumer takes one message at a time (`max_batch_size: 1`, `max_concurrency: 1`), which keeps the shop well under Resend's default of two requests a second. A batch smaller than 100, or finding nobody left, marks the campaign `sent`.

A batch Resend refuses, or one that fails for any other reason, is retried after 60 seconds. On the third attempt (`NEWSLETTER_SEND_ATTEMPTS`) the campaign is marked `failed` with the reason, `email.failed` is audited against the campaign, `sendIncidentAlert` emails `RESEND_EMAIL_FROM` a `newsletterFailed` alert keyed by the campaign id (see [Monitoring and alerts](/docs/guides/monitoring-and-alerts#e-mail-alerts-from-the-shop)), and the rest of the list is not sent. A message the consumer keeps throwing on, for example while D1 is unavailable, goes after `max_retries` (3) to the queue's `-dlq` dead-letter queue. The same Worker consumes it with the same function, one message at a time and five minutes apart, so the campaign carries on from the last subscriber it reached, or stops and alerts as above. A subscriber who confirms while a campaign is going out receives it when their id sorts after the batches already sent; anyone who unsubscribes before their batch is skipped.

The Marketing page has two tabs under its header, `MarketingTabs`. **Newsletters**, `/admin/marketing`, shows how many subscribers are confirmed, awaiting confirmation and unsubscribed, each card linking to the **Subscribers** tab narrowed to its status, and lists the 50 most recent newsletters with their subject in the admin's language, their status (Sending, Sent or Stopped), how many of the confirmed subscribers they reached, when they started and finished and why a stopped one stopped. The list updates by itself as batches go out.

### The subscriber list

**Subscribers**, `/admin/marketing/subscribers`, is `src/routes/admin.marketing.subscribers.tsx` rendering `NewsletterSubscribersTableContent` from `src/presentation/components/custom/pages/admin/marketing/subscribers/`, built on the shared data grid like the coupons list. It lists every row of `newsletter_subscriber`, newest first and 50 to a page: the address, its status (Confirmed, Awaiting confirmation or Unsubscribed), the language it signed up in, where it signed up (the home page, checkout or the customer account), a link to the customer account it belongs to, and when it signed up and confirmed. The ID and the unsubscribe date are hidden columns the column options can show, and **Copy email** in the row menu copies the address. Four cards above the table count all addresses and each status; a card narrows the list to its status and pressing it again, or the all-addresses card, widens it again, as does the status filter in the toolbar. The search finds addresses by any part, and **Download table as CSV** writes `newsletter-subscribers.csv` with every address the search and status select. A link such as `/admin/marketing/subscribers?status=pending`, which the cards on the Newsletters tab use, opens the list on that status; the route's `validateSearch` accepts only the three statuses.

`getAdminNewsletterPage` filters by `status` and `exportAdminNewsletterSubscribers` returns every matching row unpaged. Both require `user: ["list"]`, like `getNewsletterStats`, and neither returns the confirmation token. A page of one status reads `newsletter_subscriber_status_createdAt_idx` on (`status`, `created_at`), which replaced the single-column status index, so it comes newest first straight from the index, without a sort.

The list holds an address only as long as the retention rules do: a pending address is deleted 30 days after it last asked for a confirmation and an unsubscribed one 30 days after it unsubscribed (see [Data retention](/docs/guides/data-retention)). The Unsubscribed count is therefore the addresses that left in the last 30 days, not everyone who ever left. An address that signs up again after unsubscribing goes back to pending with its confirmation and unsubscribe dates cleared, so the list and the CSV never show a confirmation date beside an address that is still awaiting one.

The row menu also has **Unsubscribe**, for an address that has not unsubscribed yet, and **Erase data**, each behind a confirmation. **Unsubscribe** calls `unsubscribeNewsletterSubscriber`, which requires `user: ["update"]` and applies `unsubscribeSubscriber` from `newsletter.unsubscribe.server.ts`, the same change the unsubscribe link, the one-click route and the account preferences make: the status becomes `unsubscribed` and `unsubscribed_at` is set, no email is sent, and the token stays, so the confirmation link of a pending address then answers that it is invalid. Nothing in the admin confirms an address; only the subscriber's own confirmation link does. **Erase data** calls `eraseNewsletterSubscriber`, which requires `user: ["delete"]` and deletes the row, for example when someone asks for their data to be erased; a customer account with the same address stays as it is, and deleting that account erases its subscription anyway.

Both answer `NEWSLETTER_SUBSCRIBER_NOT_FOUND` when the row is already gone, and the table then refreshes. Both are recorded in the audit log under `email`, as `newsletter.subscriber_unsubscribed` and `newsletter.subscriber_erased`, with the address as both the target and the resource, so deleting a customer account with that address deletes them along with the account's other entries. Like the other admin mutations they are not rate-limited.

**Erase data** deletes the row and, in the same D1 batch, the audit entries about that address's newsletter: `newsletter.subscriber_unsubscribed` and the `email.failed` entries whose `emailKind` is `newsletter-confirmation`, `newsletter-already-subscribed` or `newsletter-subscription`, the confirmation emails, already-subscribed notices and daily-limit refusals that did not go out. The address's other entries, such as a customer account's sign-ins and auth emails, stay. The erasure entry is written afterwards and keeps the address in the audit log for its 24 months as the record that the request was carried out, the way `customer.deleted` keeps the address of a deleted account. An entry recorded in the few seconds before the erasure can still be in the audit queue and land after it. Both the subscriber list and the audit log refresh in every open admin tab.

Every change to a subscriber row calls `scheduleAdminNewsletterSubscribersInvalidation()`: a sign-up, including a repeated one, a confirmation, an unsubscribe through `unsubscribeSubscriber`, which the unsubscribe link, the one-click route, the account preferences and the admin share, an erasure, and `eraseAccountData`. A tab showing the list or its counts refetches them, and a tab that only has them cached drops them, so opening the list again loads the current statuses.

### Newsletters and the transactional mail

Newsletters never go through `sendEmail` or `admitPublicEmail`. The daily cap of 50 emails that visitors can make the shop send, which `admitPublicEmail` keeps for the verification, password-reset, newsletter sign-up and withdrawal emails, therefore neither counts a campaign or a test send nor holds them back, and a campaign never uses up that day's allowance for visitors; a refused newsletter batch never sets the sender-unavailable flag either. Newsletters do share the Resend account with the transactional mail: every newsletter email counts against the account's daily and monthly quota and its request rate. On Resend's free plan, 100 emails a day, a newsletter to more than a few dozen subscribers would use up the day's quota and order emails would fail until the next day, so the shop needs a paid Resend plan before the list grows.

## Previewing

```bash
bun run dev
open http://localhost:3000/dev/emails
```

`src/routes/dev.emails.tsx` is a `GET` handler, not a React page. It is guarded by the build mode:

```ts
if (!import.meta.env.DEV) {
  return notFound()
}
```

so the route does not exist in a preview or production build. With no `?template=` it renders an index of cards; with `?template=<slug>&locale=<locale>` it renders that template, and adding `&format=text` returns the plain-text rendering instead of HTML.

`src/presentation/emails/email-previews.tsx` is the registry. `EMAIL_PREVIEWS` maps each slug to `{ element: async (locale) => …, label }`, and `renderEmailPreview(slug, locale, plainText)` calls react-email's `render`. The fixtures are realistic Polish data — `PREVIEW_ORDER_ITEMS` uses "Bransoletka Aurora" at 24 900 minor units and "Kolczyki Luna" ×2 at 18 900, `PREVIEW_ADDRESS` is a Warsaw address, and there are two CTA fixtures, `PREVIEW_GUEST_CTA` and `PREVIEW_CUSTOMER_CTA`, so both branches of `buildOrderAccountCta` can be seen.

Every template except `newsletter-confirmation` and `newsletter-campaign`, which the owner checks with **Send test to me**, is listed in both `pl-PL` and `en-US`, in HTML and plain text — eight links per template — which makes the index the fastest way to check a translation change.

Adding a template means: the component plus its namespace constant under `src/presentation/emails/`, the two message files under `messages/{locale}/`, an `EMAIL_PREVIEWS` entry, and a `send-<name>-email.server.ts` use case in the module the email belongs to that loads the namespace and calls `sendEmail`.

## What is not there

- No abandoned-cart email. The event is recorded in the audit log but nothing sends anything.
- No delivered notification.
- No email when a payment fails while the customer is still paying (`payment_intent.payment_failed`): the payment form shows the error instead.
- No queue, outbox or dead-letter queue for transactional email. An order email is retried twice within the request's `waitUntil` and then waits for the admin's **Resend email**; the failed payment email, which has no order, cannot be resent. Better Auth's emails and the newsletter sign-up emails are tried once, and a failure is logged and audited. The person retries those instead: a newsletter signup from the landing form or with "Resend email" in the account preferences, an unconfirmed account with "Send the confirmation link again" on the sign-in page, and a password reset with "Send a new link".
