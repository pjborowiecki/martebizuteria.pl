The `user` table is shared with Better Auth, so "customers" is a view over authentication data joined to order aggregates. The module is `src/modules/user`.

## The user table

`src/modules/user/user.schema.ts` extends Better Auth's base user with M'Arte's own columns:

| Column                                | Notes                                                                                                     |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `email`                               | 320 characters, unique, not null                                                                          |
| `name`                                | 256 characters, not null                                                                                  |
| `email_verified`                      | Boolean, default `false`, not null                                                                        |
| `role`                                | `admin \| customer`, default `DEFAULT_ROLE` (`customer`)                                                  |
| `banned`, `ban_reason`, `ban_expires` | Better Auth admin plugin fields                                                                           |
| `is_anonymous`                        | Boolean, default `false`; nothing writes it (see below)                                                   |
| `two_factor_enabled`                  | Boolean, default `false`                                                                                  |
| `phone`                               | 32 characters; written by `updateCustomerPhone` and `updateCustomer`                                      |
| `timezone`                            | 64 characters; the customer's saved time zone, written by `updateDisplayPreference`, `NULL` for Automatic |
| `format_locale`                       | 35 characters; the saved date and number format, written the same way                                     |
| `image`                               | 2048 characters                                                                                           |
| `stripe_customer_id`                  | Written by `ensureStripeCustomerWithEmail` at checkout and `ensureStripeCustomer` on the account page     |
| `metadata`                            | A JSON string holding admin notes and tags                                                                |

One index: `user_createdAt_idx`.

`is_anonymous` belongs to Better Auth's `anonymous()` plugin, which the shop does not load (see [Better Auth](/docs/integrations/better-auth#no-anonymous-sign-in)): nothing sets it, and a new user takes the default. It marks the users that plugin created, which the grid lists as customers with a placeholder address and the name "Anonymous". It stays in the table and in the Drizzle schema until a migration of its own drops it, applied only after code that no longer declares it is deployed, because a Worker still running older code selects it with every user row it loads.

## Routes

| Route                  | File                        | Permission of its server functions                               |
| ---------------------- | --------------------------- | ---------------------------------------------------------------- |
| `/admin/customers`     | `admin.customers.index.tsx` | `user: ["list"]`                                                 |
| `/admin/customers/$id` | `admin.customers.$id.tsx`   | `user: ["get"]` for the detail, `order: ["read"]` for its orders |

The routes themselves only need the `/admin` layout's `requireAdmin`; each server function checks its own permission. The index loader prefetches `getAdminCustomersPageQuery({ page: 1, pageSize: ADMIN_CUSTOMER_PAGE_SIZE })` and `getAdminCustomerStatsQuery()`, and the detail loader prefetches `getAdminCustomerQuery(id, locale)` and the first page of the customer's orders, `getAdminOrdersPageQuery({ page: 1, pageSize: CUSTOMER_ORDERS_VIEW.pageSize, userId: id })`, all with `staleTime: "static"`. `ADMIN_CUSTOMER_PAGE_SIZE` is 25 and `ADMIN_CUSTOMER_QUERY_STALE_MS` is 60 000. Both routes declare `staticData.namespaces: ["pages.admin.customers"]`.

## The grid

`getAdminCustomersPage` (`use-cases/get-admin-customers-page.ts`) is `authorized({ user: ["list"] })`. It supports a search term, a `statFilter` and seven column filters:

```ts
filters: {
  averageOrderValue: input.averageOrderValue,
  banned: input.banned,
  createdAt: input.createdAt,
  emailVerified: input.emailVerified,
  lastOrderAt: input.lastOrderAt,
  role: input.role,
  totalSpent: input.totalSpent,
}
```

`createdAt` and `lastOrderAt` are filtered by the day in the admin's time zone through `buildAdminDateTimeFilterSql`, as on the orders page and in the audit log.

The search term matches the name, email, phone, id and Stripe customer id, and also every account that has ever used an address containing it (`accountsWithAddressContaining` over `user_email_history`, see [Account: The addresses an account has used](/docs/features/account#the-addresses-an-account-has-used)), so a customer is found by an address they no longer sign in with. The export applies the same search.

The accessor returns five things — `rows`, `orderStats`, `defaultAddresses`, `latestShippingAddresses` and `total` — and the use case stitches them together client-side of the database:

```ts
const statsByUserId = mapCustomerOrderStats(orderStats)
const locationByUserId = mapCustomerLocations(defaultAddresses, latestShippingAddresses)
const items = rows.map((row) => toAdminCustomerListItem(row, statsByUserId.get(row.id), locationByUserId.get(row.id)))
```

So the location column shows the city, province and country of the customer's **saved default address**. That can be a billing address: a customer who ticks "Save this billing address for future use" at checkout gets the billing address saved as a default too. When checkout leaves both the shipping and the billing address marked as default, `getDefaultCustomerAddressesQuery` returns them in the order they were saved and `mapCustomerLocations` keeps the first, which is normally the shipping address because checkout saves it first. A customer without a saved default address gets the shipping address (`order_address` of type `shipping`) of their newest order that has one, whatever the order's status. A cancelled or refunded order therefore gives the location even though it does not count toward the "Last Order" column, and a newer order without a shipping row is skipped. When two orders share the same moment, the later order number wins. For a parcel-locker order the shipping address is the address the customer typed, not the locker's, and an order without stored address snapshots (no `order_address` rows) gives no location. `getLatestOrderShippingAddressesQuery` picks one address per customer in a single `row_number()` query for the whole page or the whole export, which shows the same location as the grid. It reads the customers' orders through `order_userId_status_idx` and each order's shipping row through `order_address_orderId_idx`. The unary `+` on `order_address.type` stops SQLite from starting at `order_address_type_idx`, which would walk every shipping address in the shop.

A customer's order count, total spent, average order value and lifetime value use the dashboard's sale rule (see [Admin dashboard](/docs/features/admin-dashboard#the-snapshot)): `orderCountsAsSale` picks their processing and completed orders, and `netSalesSum` adds up each one's total less what was refunded on its payment, so pending, cancelled and refunded orders do not count and a partial refund comes off. The average order value divides that sum by the same orders, and the "total spent" on an order's customer card (`getAdminOrderCustomerStats`) is the same figure. The spending chart, the category breakdown and the preferred category and collection read the same orders; the last three add up order lines, which record no refunds. The orders grid on the detail screen is the exception: it lists every order of the customer, whatever its status.

The column ids, widths, default visibility and pinning are all in `user.constants.ts` under `ADMIN_CUSTOMER_TABLE_COLUMN_ID`, `ADMIN_CUSTOMER_TABLE_COLUMN_SIZE`, `ADMIN_CUSTOMER_TABLE_DEFAULT_COLUMN_VISIBILITY` and the pinning object. The columns are `select`, `customer` (the name, with the email address under it), `recordId`, `stripeCustomerId`, `role`, `phone`, `emailVerified`, `banned`, `location`, `orderCount`, `totalSpent`, `averageOrderValue`, `lastOrderAt`, `createdAt` and `actions`; `recordId` and `stripeCustomerId` start hidden. Amounts and dates are written in the admin's format locale and time zone.

The grid is `customersDataGrid` (`utils/customers-data-grid.ts`), whose column order, widths and visibility persist under `admin.customers`, and `useCustomersDataGrid` (`hooks/use-customers-data-grid.ts`) drives it with server-side pagination and a debounced search over the name, email, phone, id and Stripe customer id, and the addresses each account has used before. Clicking a row opens `/admin/customers/$id`. The row menu offers the details, copying the id, the email or the Stripe customer id, and **Delete account**, greyed out on every admin's row (see [The two mutations](#the-two-mutations)).

Components are in `.../admin/customers/components/`: `customers-table.tsx`, `customers-columns.tsx` (with the column definitions in `lib/customers-column-defs.tsx`), the filters (`customers-role-filter`, `customers-banned-filter`, `customers-email-verified-filter`, `customers-date-column-filter` with `customers-date-filter-form`, `customers-numeric-column-filter`), the badges (`customer-role-badge`, `customer-banned-badge`, `customer-email-verified-badge`), `customer-name-cell`, `customer-table-cells`, `customers-row-actions`, `customers-stats` with `customer-stat-card`, and the refresh action; the export is the shared `Export` of `customersDataGrid`. The cards are configured in `.../admin/customers/customers-stats.config.ts`, and `hooks/use-delete-customer.ts` runs the deletion.

## Stats

`getAdminCustomerStats` runs three queries in parallel and derives the cards in a pure function:

```ts
const [[totalRow], [rollupRow], [averageProductsPerOrderRow]] = await Promise.all([
  getAdminCustomerTotalCountQuery(),
  getAdminCustomerOrderRollupStatsQuery(),
  getAverageProductsPerOrderQuery(),
])

return computeAdminCustomerStatsFromAggregates({
  averageLtv: rollupRow?.averageLtv ?? 0,
  averageProductsPerOrder: averageProductsPerOrderRow?.value ?? 0,
  customersWithOrders: rollupRow?.customersWithOrders ?? 0,
  repeatCustomers: rollupRow?.repeatCustomers ?? 0,
  total: totalRow?.count ?? 0,
})
```

`computeAdminCustomerStatsFromAggregates` and `resolveAdminCustomerReturningRate` are in `user.utils.ts`, which keeps the arithmetic unit-testable. The four cards are the number of customers, the returning rate, the average lifetime value and the average number of products per order, written in the admin's format locale. The stat filters are declared in `ADMIN_CUSTOMER_STAT_FILTER` (`total` and `returning`), and the first two cards act as filters on the grid: `total` shows every customer, and `returning` keeps those with at least `ADMIN_CUSTOMER_MIN_REPEAT_ORDERS` (2) sale orders.

## Detail screen

`/admin/customers/$id` reads `getAdminCustomerQuery(id, locale)` with `useSuspenseQuery` and throws `notFound()` through `ensureAdminCustomerDetail` when the row is missing.

`getAdminCustomer` (`authorized({ user: ["get"] })`) is the widest read in the codebase — twelve reads, `getUserById` first and the other eleven in parallel: nine more accessors from `user.accessors.ts`, `getUserEmailHistory` from `user-email-history.accessors.ts` and `getOrdersPlacedWhileSignedIn` from `order.accessors.ts`:

| Accessor                              | Feeds                                                                                                    |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `getUserById`                         | Identity, role, verification, ban state, metadata                                                        |
| `getCustomerOrderStatsQuery`          | Order count, total spent, last order                                                                     |
| `getAdminCustomerOrderRowsQuery`      | The timeline's "Placed order" entries: the newest sale orders, `ADMIN_CUSTOMER_DETAIL_ORDERS_LIMIT = 10` |
| `getCustomerMonthlySpendingQuery`     | The spending chart, `ADMIN_CUSTOMER_DETAIL_MONTHS = 12`                                                  |
| `getCustomerCategoryBreakdownQuery`   | The category breakdown: the five primary categories the customer spent most on                           |
| `getCustomerPreferredCategoryQuery`   | The preferred-category line                                                                              |
| `getCustomerPreferredCollectionQuery` | The preferred-collection line                                                                            |
| `getDefaultCustomerAddressFullQuery`  | `formatAdminCustomerFullAddress` and the editor's address fields                                         |
| `getLatestSessionActivityQuery`       | `formatAdminCustomerLastActive`                                                                          |
| `getCustomerAuditTimelineQuery`       | `buildAdminCustomerTimeline`                                                                             |
| `getUserEmailHistory`                 | `buildAdminCustomerEmailHistory`: every address the account has used, newest first                       |
| `getOrdersPlacedWhileSignedIn`        | `signedInOrderCount`, which enables **Change email** (see [below](#changing-a-customers-email-address))  |

"Last active" is the newest session's `updatedAt`, or the last order when no session is left, or the row's `updatedAt`, written by `formatRelativeFromNow`: a relative time in the page's language for a week, then the date.

The spending chart counts months as the dashboard does (see [Admin dashboard](/docs/features/admin-dashboard#charts)). `resolveAdminDashboardMonths(now, ADMIN_CUSTOMER_DETAIL_MONTHS, timeZone)` gives the last twelve months up to the one it is in the admin's time zone now, each starting at midnight there on its first day, and `getCustomerMonthlySpendingQuery(userId, window)` sums the customer's sales from the window's `start` until its `end`, grouped with `calendarPeriodKey`. For an admin in Poland, an order placed at 00:30 on 1 April therefore counts in April, although it is still 31 March in UTC. `buildAdminCustomerMonthlySpendingSeries` gives each month of the window one point, zero where nothing was bought, named in the admin's format locale. The join date and the timeline's dates and totals use the same preferences; the category names keep the page's language. The category breakdown is a list rather than a chart: each category with its amount and a bar scaled to the largest one.

The customer's orders are the orders data grid itself. `CustomerOrders` calls `useOrdersDataGrid({ onRowClick: openOrder, userId, view: CUSTOMER_ORDERS_VIEW })`, so `getAdminOrdersPage` reads the page with `userId` added to its conditions, and the columns, badges, search and row actions are those of `/admin/orders` (see [Orders: Admin list](/docs/features/orders#admin-list)); the toolbar has the search only, without the filters, refresh and export of the orders page. `CUSTOMER_ORDERS_VIEW` (`customer-detail/utils/customer-orders-data-grid.ts`) hides the customer, email and selection columns, pins the order id and the actions, starts at 10 rows a page and keeps its own column preferences under `admin.customer-orders`. Clicking a row opens `/admin/orders/$orderId`, and **View All** leads to `/admin/orders`. Orders are named by their `orderNumber` (`MRT-2026-00001`) here and in the timeline's "Placed order" entries, and a row still opens the order by its id.

Tags are derived, not stored:

```ts
export const resolveAdminCustomerTags = (row: User["select"], orderCount: number): AdminCustomerDetailTag[] => {
  const tags: AdminCustomerDetailTag[] = []
  if (row.role === ROLES.ADMIN) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.ADMIN)
  } else {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.CUSTOMER)
  }
  if (orderCount >= ADMIN_CUSTOMER_MIN_REPEAT_ORDERS) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.RETURNING)
  }
  if (row.emailVerified) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.VERIFIED)
  }
  if (row.banned === true) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.BANNED)
  }

  return tags
}
```

`ADMIN_CUSTOMER_MIN_REPEAT_ORDERS` is 2. Custom tags added by an admin come from the metadata column and are merged in separately.

`buildAdminCustomerTimeline` merges three sources, newest first: the account's creation, the "Placed order" entries of up to ten sale orders with their numbers and totals, and up to `CUSTOMER_AUDIT_TIMELINE_LIMIT` (50, `user.constants.ts`) `audit_log` rows whose resource is the user, limited to `auth.email_changed`, `auth.login`, `auth.logout`, `customer.cart_item_added`, `customer.cart_abandoned` and `customer.page_viewed`. A change of address reads "Changed the sign-in email from X to Y", with both addresses taken from the entry's change metadata or, for an entry without it, from its `old → new` detail, or "Changed the sign-in email" for an entry that names neither. See [Audit log](/docs/features/audit-log).

The sidebar's Email addresses section (`customer-email-history.tsx`) lists the rows of `getUserEmailHistory`, newest first: the current address with "Current, since" and the day the account took it, and each earlier one with "Used" and the days it was taken and given up, in the admin's format locale and time zone.

The UI is `.../admin/customers/customer-detail/`: `customer-detail-page.tsx` lays out `customer-kpis.tsx`, `customer-charts.tsx` and `customer-orders.tsx` in the main column and `customer-sidebar.tsx`, which holds `customer-email-history.tsx` below the customer's details and ends with `customer-timeline-card.tsx`, beside it; `edit-customer/customer-sheet.tsx` is the editor. Below the `xl` breakpoint the sidebar follows the main column; from `xl` it is a 340 px column. On a `2xl` screen at least 57rem high the page fits the window and each column scrolls on its own.

## Notes and tags in `metadata`

There is no notes or tags table. Both live in `user.metadata` as JSON, with a tolerant parser:

```ts
export const parseAdminUserMetadata = (raw: string | null | undefined): User["adminUserMetadata"] => {
  const trimmed = raw?.trim()
  if (trimmed === undefined || trimmed === "") {
    return {}
  }

  const record = tryParseJsonRecord(trimmed)
  const structured =
    record === undefined || !("notes" in record || "tags" in record) ? undefined : userZodSchemas.adminUserMetadata.safeParse(record).data
  if (structured === undefined) {
    return { notes: trimmed }
  }

  const notes = structured.notes?.trim()

  return { notes: notes === "" ? undefined : notes, tags: normalizeTags(structured.tags) }
}
```

A column that holds plain text rather than JSON is treated as notes, so a legacy value is never lost. `serializeAdminUserMetadata` returns `undefined` when both fields are empty, and `updateCustomer` then writes a SQL `null` rather than the string `"{}"`.

## The two mutations

`updateCustomer` (`use-cases/update-customer.ts`), `authorized({ user: ["update"] })`:

- 404s with `USER_ERROR_CODES.NOT_FOUND` when the user is missing
- writes `phone` (clearing to `NULL` on an empty string) and the serialized `metadata`
- upserts the default address through `upsertDefaultAddressForUser`, but only when `hasAddressInput` passes — `address1` and `city` must both be non-blank
- when the submitted `countryCode` is blank it reuses the existing default address's country rather than writing an empty string, and skips the address write entirely if there is still no country

It does **not** change email, name, role or ban state. The email address changes only through a link the new address confirms, sent when its owner changes it from the account page (see [Account: Changing the email address](/docs/features/account#changing-the-email-address)) or when customer care starts the change from this page (see [below](#changing-a-customers-email-address)); the others are Better Auth operations. Once the writes are done it records `customer.updated` against the admin, with the customer's email address as the target and their id as the resource. It writes the row directly rather than through Better Auth, so no `databaseHooks.user` hook runs: `CustomerFormProvider` invalidates the detail, the grid and the stats in the editing admin's own browser.

`deleteCustomer` (`use-cases/delete-customer.ts`), `authorized({ user: ["delete"] })`, has four guards:

| Condition                                                            | Error                                                  |
| -------------------------------------------------------------------- | ------------------------------------------------------ |
| Request on a host this build does not serve (`resolveRequestOrigin`) | `ERROR_CODES.FORBIDDEN`                                |
| User not found                                                       | `ERROR_CODES.NOT_FOUND` / `USER_ERROR_CODES.NOT_FOUND` |
| `targetUser.id === context.auth.user.id`                             | `ERROR_CODES.CONFLICT` / `CANNOT_DELETE_SELF`          |
| `targetUser.role === ROLES.ADMIN`                                    | `ERROR_CODES.FORBIDDEN` / `CANNOT_DELETE_ADMIN`        |

An admin account cannot be deleted from here. The row menu shows **Delete account** greyed out on every admin's row, the signed-in admin's own included, with "Remove the admin access in Settings › Team first."; should the server still refuse, the toast says "Admin accounts cannot be deleted. Remove the admin access in Settings › Team first." Once the access is removed under [Settings › Team](/docs/features/admin-settings#team) the account is a customer account and can be deleted. Better Auth's own `/admin/remove-user` refuses an admin account too (see [Better Auth: Admin roles](/docs/integrations/better-auth#admin-roles)).

It captures the email, name, current locale and request origin **before** deleting, erases the account's data with `eraseAccountData`, hands the deletion to `auth.api.removeUser`, and then waits for the goodbye email:

```ts
if (!(await eraseAccountData(targetUser))) {
  throw new AppError(ERROR_CODES.INTERNAL_ERROR, USER_ERROR_CODES.STRIPE_CUSTOMER_NOT_DELETED)
}

await auth.api.removeUser({ body: { userId }, headers: getRequestHeaders() })

const goodbyeEmailDelivery = sendAccountDeletedEmail(goodbyeEmail)
scheduleBackgroundWork(goodbyeEmailDelivery)
const goodbyeEmailSent = await goodbyeEmailDelivery

return { goodbyeEmailSent, ok: true as const, userId }
```

`sendAccountDeletedEmail` never throws; a refusal from Resend, or an error while preparing the email, is logged, recorded as `email.failed` in the audit log and returned as `false`, and the deletion stands. Handing the same promise to `scheduleBackgroundWork` puts it on the Worker's `waitUntil`, so the email and its audit entry finish even if the admin closes the tab first. `useDeleteCustomer` picks the toast from `goodbyeEmailSent`: a success toast, "The account was deleted and a confirmation email was sent.", or a warning toast, "Account deleted — email not sent", with "The confirmation email to the customer could not be sent. The error is recorded in the audit log."

`eraseAccountData` is the step a customer's own deletion runs in Better Auth's `beforeDelete`: it deletes the account's Stripe customer with its saved cards, then the account's audit log entries and newsletter subscription (see [Account: Closing the account](/docs/features/account#closing-the-account)). When Stripe cannot delete the customer, nothing is deleted, `customer.deletion_failed` is recorded, and `useDeleteCustomer` shows "Stripe could not delete the customer's profile and saved cards, so the account was not deleted. Try again in a few minutes. The error is recorded in the audit log." The confirmation dialog, `rowActions.deleteDescription`, lists what is deleted and that the orders and payments stay in the accounting records for 5 years.

Because deletion goes through Better Auth, its `databaseHooks.user.delete.after` records `customer.deleted` against the admin whose session made the `removeUser` call, with the deleted customer's email address as the target, and the cascades on `session`, `account`, `address`, `wishlist_item`, `two_factor` and `user_email_history` apply, while `order.user_id`, `checkout.user_id` and `discount_redemption.user_id` are `onDelete: "set null"` — so the orders survive as guest orders. If an account later verifies the deleted account's last address, `claimGuestOrdersForUser` files the orders placed with that address under it like any other guest order; the orders placed with an earlier address carry `keptFromClaims` and stay unclaimed (see [Account: Guest orders in the account](/docs/features/account#guest-orders-in-the-account)).

## Changing a customer's email address

When a customer can no longer reach the mailbox their account signs in with, or the address has a typo, customer care can move the account to a new address from its page. **Change email** in the header, beside **Edit customer**, opens `customer-email-change-sheet.tsx`, a sheet built like those of Settings › Team (`SettingsSheet`, `SettingsFormSection`, the same fields, buttons and toasts). It is not shown on an account with admin access, which changes its own address under [Settings › My account](/docs/features/admin-settings#my-account), and on an account without an order placed while signed in it stays greyed out with "Needs an order placed while signed in to this account, to check who is asking." as its tooltip, the way the order page explains a blocked action. `signedInOrderCount` in the detail tells the page which case applies.

The sheet asks for the number of one of the customer's orders and the postal code of that order's delivery address, both as the customer gives them, and for the new address beside the current one, and lists the rules the change follows. Only an order placed while signed in to the account counts: one whose `checkout` row carries the account's `user_id` as well as the order. A guest order paid with an account's address joins that account by itself (see [Account: Guest orders in the account](/docs/features/account#guest-orders-in-the-account)), so anyone who knows the address could otherwise place an order, with their own delivery address, and pass the check.

`requestCustomerEmailChange` (`use-cases/request-customer-email-change.ts`), `authorized({ user: ["update"] })`, validates its input with `userZodSchemas.customerEmailChangeInput` and then:

1. refuses an account that does not exist (`ERROR_CODES.NOT_FOUND`), an account with admin access (`FORBIDDEN`), the address the account already has, whatever its letter case (`CONFLICT`), and an address another account holds now according to `getCurrentAddressHolder` (`CONFLICT`), each with its reason from `CUSTOMER_EMAIL_CHANGE_ERROR`;
2. counts the attempt with `withinRateLimit` under `customer-email-change:<account id>`, `CUSTOMER_EMAIL_CHANGE_ATTEMPTS.MAX` (5) an hour per account, whoever asks, and refuses any further attempt that hour with `TOO_MANY_REQUESTS`, even one with the right details, so the check cannot be used to guess them;
3. looks among `getOrdersPlacedWhileSignedIn` for an order whose number and delivery postal code both match, compared without letter case, spaces or punctuation, and refuses with `FORBIDDEN` when there is none, without saying which of the two did not match;
4. signs a link with Better Auth's own `createEmailVerificationToken`, with the payload Better Auth's `changeEmail` gives the second step of a customer's own change — the current address as `email`, the new one as `updateTo` and `requestType: "change-email-verification"` — and Better Auth's lifetime of an hour, to `/api/auth/verify-email` on the request's host, with the customer's profile page as `callbackURL`;
5. sends it to the new address with `sendSupportEmailChangeEmail`, which renders the `ChangeEmail` template with the copy of `emails.support-email-change` ("Confirm your new email address — M'Arte"), which says customer care started the change, in the language of the order the customer named, and refuses with `INTERNAL_ERROR` when Resend does not take it.

The address does not change yet. Opening the link runs Better Auth's `/verify-email` exactly like the second link of a customer's own change: `guardAuthRequest` refuses it once the account has taken another address since or another account has taken the new one, Better Auth moves the account and signs the customer in, and `finishEmailChange` records `auth.email_changed`, moves the newsletter subscription and the Stripe customer, signs out every other device signed in to the account, keeping only the browser the link was opened in, and tells the old address (see [Account: Changing the email address](/docs/features/account#changing-the-email-address)).

Every attempt that gets past step 1 is recorded against the customer's account and credited to the admin, with the request's address, through `recordCustomerEmailChangeAudit` (`record-customer-audit.server.ts`), as a warning under `customers`: `customer.email_change_requested` once the link is sent, and `customer.email_change_verification_failed` with `refusal` set to `mismatch` or `tooManyAttempts` when it is not. Both carry the new address and the order number as typed; the postal code is never recorded or logged. The toast names the address the link went to and closes the sheet, and a refusal keeps the sheet open with its reason.

## Export

**Export** in the toolbar downloads the list as CSV, JSON, XML or plain text through the export every admin grid shares (see [Data grid](/docs/ui/data-table#export)). A file holds every customer the role, verification, ban, spending, date, card and search filters select, not only the page on screen, and the columns the table shows, in their order and under their headers. Each cell is written as the table shows it: the customer column holds the name and the Email column, shown by default, holds the address; the role and the yes-or-no columns by name; the amounts in złoty and the dates in the admin's format locale. The ID and the Stripe customer ID are hidden columns the column menu can add.

`exportAdminCustomers` (`use-cases/export-admin-customers.ts`) requires `user: ["list"]`, returns every matching customer as a list item and records `customer.list_exported`. `useCustomersExportSource` (`hooks/use-customers-export-source.ts`) gives the grid the list name `customers`, the page title, the active filters in words and the call to `exportAdminCustomers`.

## Realtime

`USER_QUERY_KEYS.ADMIN.CUSTOMERS` is in `ADMIN_REALTIME_QUERY_PREFIXES`, and `scheduleAdminCustomersInvalidation()` pushes `CUSTOMERS`, `CUSTOMERS_PAGE` and `TEAM`, the Settings › Team list, since an account's role, two-factor state or deletion can change it. Better Auth's `databaseHooks.user` call it after a user is created, updated or deleted (`auth.hooks.server.ts`), and `grantAdminAccess` and `revokeAdminAccess` after a change of admin access, so a sign-up, a change made through Better Auth such as a verified or changed email address, or a deletion refreshes an open grid, its stats and an open detail screen, whose keys all start with `CUSTOMERS`. Every batch the audit queue writes pushes the audit-log keys, so the matching `customer.registered` or `customer.deleted` entry appears in an open audit log too.
