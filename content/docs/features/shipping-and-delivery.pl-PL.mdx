## Dwie tabele

`courier` (`src/modules/courier/courier.schema.ts`) to przewoźnik:

| Kolumna         | Uwagi                             |
| --------------- | --------------------------------- |
| `internal_code` | unikalna, not null (np. `inpost`) |
| `name`          | not null                          |
| `logo`          | nullowalna, do 2048 znaków        |
| `is_active`     | boolean, domyślnie `true`         |

`delivery_method` (`src/modules/delivery-method/delivery-method.schema.ts`) to to, co wybiera klient:

| Kolumna            | Uwagi                                                                      |
| ------------------ | -------------------------------------------------------------------------- |
| `courier_id`       | `references(() => courier.id, { onDelete: "cascade" })`, not null          |
| `name`             | not null; pokazywana dosłownie w kasie, więc **nie** jest tłumaczona       |
| `description`      | nullowalna                                                                 |
| `price`            | całkowite jednostki podrzędne, not null; `0` oznacza darmową dostawę       |
| `type`             | `locker \| courier \| in_store`, not null                                  |
| `api_service_code` | not null; identyfikator usługi przewoźnika, obecnie wyłącznie informacyjny |
| `is_active`        | boolean, domyślnie `true`                                                  |

`api_service_code` jest zapisywany, ale nigdy nie czytany. Przesyłka InPost nadana z panelu bierze usługę ShipX z `type` metody: `inpost_locker_standard` dla `locker` i `inpost_courier_standard` dla `courier` (zobacz [InPost](/docs/integrations/inpost#przesyłki-przez-shipx)).

## Trzy typy

`delivery-method.constants.ts`:

```ts
export const DELIVERY_METHOD = { COURIER: "courier", IN_STORE: "in_store", LOCKER: "locker" } as const
export const DELIVERY_METHODS = [DELIVERY_METHOD.COURIER, DELIVERY_METHOD.LOCKER, DELIVERY_METHOD.IN_STORE] as const
export const DELIVERY_METHOD_QUERY_KEYS = { ALL: ["deliveryMethods"] as const } as const
```

`DELIVERY_METHODS` ustala kolejność wyświetlania w kroku kasy: kurier, potem paczkomat, potem odbiór osobisty.

## Listowanie metod

`listDeliveryMethods` (`use-cases/list-delivery-methods.ts`) jest publiczne (`withRequest`) i zwraca tylko te wiersze, w których aktywna jest **i** metoda, **i** przewoźnik. Reguła to `offeredDeliveryMethod` w `delivery-method.accessors.ts`, którą dzieli z nim serwerowy odczyt kasy:

```ts
export const offeredDeliveryMethod = and(eq(deliveryMethod.isActive, true), eq(courier.isActive, true))

const rows = await db
  .select({ courier, deliveryMethod })
  .from(deliveryMethod)
  .innerJoin(courier, eq(deliveryMethod.courierId, courier.id))
  .where(offeredDeliveryMethod)

return rows.map((row) => Object.assign(row.deliveryMethod, { courier: row.courier }))
```

Dezaktywacja przewoźnika ukrywa więc od razu wszystkie jego metody.

`listDeliveryMethodsQuery()` nie ma `staleTime`, więc podlega domyślnym ustawieniom klienta. Czytają je krok dostawy, podkrok kuriera i krok płatności (który potrzebuje ceny do wyliczenia kwoty dla Stripe). Loader strony `/checkout/` ładuje je z `staleTime: "static"`, podczas gdy layout czyta teksty zamówienia, więc te kroki czytają metody z cache, zamiast pytać o nie po pojawieniu się formularza. Na potwierdzeniu po płatności loader pomija ten odczyt, a gdy odczyt się nie uda, kroki same pytają o metody.

`getOfferedDeliveryMethodByIdQuery(id)` w `delivery-method.accessors.ts` to odczyt po stronie serwera, którego używa `resolveDelivery` w `stripe.actions.server.ts`, gdy sesja płatności jest otwierana albo zastępowana. Dołącza przewoźnika, stosuje `offeredDeliveryMethod` i zwraca tylko `price` i `type` metody. Metoda nieznana, wyłączona albo taka, której przewoźnik jest wyłączony, również zdezaktywowana w trakcie checkoutu, dostaje odmowę `DELIVERY_METHOD_UNAVAILABLE`; krok płatności pokazuje wtedy toast `errors.deliveryMethodUnavailable` i odsyła kupującego do kroku dostawy z ponownie pobraną listą metod. Zobacz [Kasa](/docs/features/checkout#strona-serwera).

Dostawa trafia tylko do krajów z `DELIVERY_COUNTRY_CODES` (`delivery-method.constants.ts`), obecnie `PL`. `checkoutSchema` odrzuca każdy inny `countryCode` dostawy; ani `delivery_method`, ani `courier` nie zapisują kraju.

## Dane startowe

`src/integrations/drizzle-orm/seeds/delivery-methods.sql` wstawia dwóch przewoźników (`inpost` i `marte-atelier`) oraz trzy metody:

| Metoda           | Typ        | Cena (jednostki podrzędne) | `api_service_code`        |
| ---------------- | ---------- | -------------------------- | ------------------------- |
| Paczkomat InPost | `locker`   | 1499                       | `inpost_locker_standard`  |
| Kurier InPost    | `courier`  | 1999                       | `inpost_courier_standard` |
| Odbiór w atelier | `in_store` | 0                          | `marte_atelier_pickup`    |

Seed używa `INSERT OR IGNORE` ze stałymi identyfikatorami UUIDv7. Nie uruchamiaj `bun run db:seed:preview` na żywej bazie — pliki seedów są starsze niż dane produkcyjne.

Każda metoda z seeda ma też polski `description`, którego nie pokazuje żadna strona. Opisy idą za § 7 regulaminu: do 4 dni roboczych od nadania dla paczkomatu i kuriera oraz odbiór w pracowni w Bochni, gotowy najpóźniej z upływem czasu realizacji. `20261010220000_delivery_method_descriptions.sql` nadaje te same opisy wierszom wstawionym wcześniej, zastępując doręczenie w 1–2 dni i atelier w Warszawie gotowe w 24 godziny. Zmienia wiersz tylko wtedy, gdy jego opis wciąż jest dawnym tekstem z seeda, więc opis przepisany przez właściciela zostaje bez zmian.

## Krok dostawy

`_steps/delivery-step.tsx` renderuje jedną kartę `OptionCard` na każdy **typ**, który ma co najmniej jedną aktywną metodę, używając `DELIVERY_ICONS` (`Truck`, `Package`, `Store` z lucide). Opis karty pokazuje najtańszą cenę w grupie:

```ts
const lowestPrice = Math.min(...methods.map((m) => m.price))
if (lowestPrice === 0) {
  return t("deliverySubsteps.free")
}

const price = format.number(lowestPrice / CENTS_IN_ZLOTY, { currency: "PLN", style: "currency" })

return methods.length > 1 ? `${t("deliverySubsteps.from")} ${price}` : price
```

Wybór typu zapisuje `deliveryMethodType` i albo automatycznie wybiera jedyną metodę, albo czyści `deliveryMethod`, żeby wybór nastąpił w podkroku.

### Kurier

`delivery/courier/delivery-courier.tsx` renderuje grupę radiową metod typu `courier` ze sformatowanymi cenami, pod nią `deliverySubsteps.parcelDeliveryTime` oraz pole tekstowe `deliveryNotes`. Ten akapit podaje termin dostawy z § 7 regulaminu: czas realizacji podany na stronie produktu, liczony od przyjęcia zamówienia, a przy kilku produktach najdłuższy z nich, potem do 4 dni roboczych od nadania przez InPost, z numerem przesyłki wysyłanym e-mailem. To pole jest utrwalane jako `checkout.customer_note` i kopiowane na `order.customer_note`. Komponent zwraca `undefined`, gdy nie ma metod kurierskich.

### Odbiór osobisty

`delivery/store/delivery-in-store.tsx` to sama treść: dwa akapity z `deliverySubsteps.inStoreTitle` i `deliverySubsteps.inStoreText`. Drugi podaje adres i godziny otwarcia oraz, tak jak § 7, mówi, że zamówienie jest gotowe najpóźniej z upływem czasu realizacji podanego na stronie produktu i że klient dostanie o tym powiadomienie. Nie ma wyboru salonu; pole `storeLocation` istnieje w `checkoutSchema`, ale nic go nie zapisuje.

### Paczkomat

`delivery/locker/delivery-locker.tsx` pokazuje `deliverySubsteps.lockerText`, którego okno z mapą używa też jako opisu, to samo `deliverySubsteps.parcelDeliveryTime` co krok kuriera i aktualnie wybrany identyfikator paczkomatu oraz osadza `InpostSelector`. Pole `lockerId` jest wymagane przez `superRefine` w `checkoutSchema`, ilekroć `deliveryMethodType === "locker"`, co pokazuje na kroku `validation.lockerIdRequired`. Serwer nie ufa temu typowi: `resolveDelivery` wymaga `lockerId` pasującego do `INPOST_POINT_NAME_PATTERN` zawsze, gdy `type` metody w bazie to `locker`, a w przeciwnym razie odmawia sesji z `LOCKER_REQUIRED`. Następnie pyta InPost przez `fetchPointByName`, czy punkt istnieje, czekając najwyżej trzy sekundy: punkt, którego InPost nie ma na liście, dostaje odmowę `LOCKER_NOT_FOUND`, która odsyła kupującego do tego kroku, a gdy InPost nie może odpowiedzieć, paczkomat zostaje przyjęty z ustawionym `checkout.locker_unconfirmed`, więc zamówienie w panelu prosi sklep o sprawdzenie go przed wysyłką. Dla każdego innego typu porzuca `lockerId`, więc `checkout.locker_id` i `order.locker_id` zostają puste przy zamówieniach z kurierem i z odbiorem osobistym.

## Wybór punktu InPost

Integracja to cztery małe pliki w `src/integrations/inpost`:

```ts
const INPOST_API_BASE = "https://api-pl-points.easypack24.net/v1/points"
const MIN_CITY_LENGTH = 3

export const fetchPointsByCity = async (city: string): Promise<InpostPointParsed[]> => {
  const trimmed = city.trim()
  if (trimmed.length < MIN_CITY_LENGTH) {
    return []
  }

  const url = `${INPOST_API_BASE}?city=${encodeURIComponent(capitalizeCity(trimmed))}&per_page=1000`
  ...
}
```

Rzeczy warte uwagi:

- Wyszukiwanie po mieście idzie **wprost z przeglądarki** do publicznego API punktów InPost. Nie ma funkcji serwerowej, nie ma proxy i nie ma klucza API. Serwer woła to samo API tylko przez `fetchPointByName` (`/v1/points/<name>`, limit trzech sekund), żeby potwierdzić wybrany punkt, gdy sesja płatności jest otwierana albo zastępowana.
- `capitalizeCity` zamienia pierwszą literę każdego słowa na wielką, czego API oczekuje.
- Odpowiedź inna niż OK rzuca wyjątek; odpowiedź, która nie przejdzie `inpostApiResponseSchema.safeParse`, zwraca `[]` zamiast rzucać — zmiana schematu po stronie InPostu degraduje się więc do „nie znaleziono punktów”.
- `inpostPointsByCityQueryOptions(city)` cache'uje agresywnie: `staleTime` jeden dzień, `gcTime` dwa dni, klucz po przyciętej nazwie miasta w małych literach i `enabled` dopiero od trzech znaków.

`inpost.zod.ts` parsuje każdy punkt do `{ address_details, location, location_description, location_type, name, opening_hours, payment_available, status }`. `location_description` jest przekształcane z `null` na `""`.

Interfejs leży w `.../delivery/locker/inpost/`:

| Plik                                            | Rola                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------ |
| `inpost-provider.tsx`                           | `InpostProvider` / `useInpost`; opóźnia wpisywanie miasta o 400 ms |
| `inpost-selector.tsx`                           | okno dialogowe z mapą MapLibre i panelem bocznym                   |
| `inpost-map-updater.tsx`                        | ponownie centruje mapę przy zmianie zbioru punktów                 |
| `inpost-marker.tsx`                             | jeden znacznik na punkt                                            |
| `inpost-popup.tsx`                              | `HoveredPointPopup` dla znacznika pod kursorem                     |
| `inpost-sidebar.tsx`, `inpost-sidebar-item.tsx` | przewijana lista punktów                                           |
| `inpost-point-details.tsx`                      | adres i godziny otwarcia wybranego punktu                          |

Mapa to `react-map-gl/maplibre` z podkładem Carto Voyager (`https://basemaps.cartocdn.com/gl/voyager-gl-style/style.json`) i `maxBounds` ograniczonym do Polski. Kliknięcie tła mapy czyści `lockerId`. Do formularza trafia `name` wybranego punktu, więc `checkout.locker_id` i `order.locker_id` trzymają nazwę punktu InPost, na przykład `KRA01A`.

## Jak dostawa trafia do zamówienia

1. `deliveryMethod` (identyfikator metody) jest wysyłany razem z formularzem kasy.
2. `resolveDelivery` odrzuca metodę, której sklep nie oferuje, metodę paczkomatową bez paczkomatu i paczkomat, którego InPost nie ma na liście, zachowuje `lockerId` tylko dla metody paczkomatowej, zapamiętuje, czy udało się o niego zapytać InPost, i odczytuje `price` metody.
3. `prepareCreateCheckoutBatch` zapisuje metodę do `checkout.delivery_method_id`, `lockerId` do `checkout.locker_id`, a nieodpowiedziane zapytanie do `checkout.locker_unconfirmed`; `createStripeSession` dodaje dla ceny pozycję dostawy, gdy jest większa od zera, nazwaną według typu metody w języku kupującego (`deliveryLineItem` w `pages.checkout`).
4. `prepareFulfillCheckoutBatch` kopiuje `deliveryMethodId`, `lockerId`, `lockerUnconfirmed` i `customerNote` z migawki checkoutu na nowy wiersz `order` i wylicza `shippingTotal = Math.max(session.amount_total - itemsSubtotal, 0)`.
5. Przy zamówieniu do paczkomatu albo kurierem administrator może nadać paczkę w InPost ze strony zamówienia. Identyfikator i status przesyłki trafiają do `order.inpost_shipment_id` i `order.inpost_shipment_status`, numer do śledzenia i link do `order.tracking_number` i `order.tracking_url`, a etykietę PDF pobiera się z tej samej karty. Zobacz [InPost](/docs/integrations/inpost#przesyłki-przez-shipx).

## Dostawa w e-mailach

`src/modules/order/order.email.utils.ts` renderuje blok dostawy. `resolveDeliveryMethodLabel` dokleja identyfikator paczkomatu dla metody typu `locker`:

```ts
if (method.type === "locker" && lockerId !== undefined && lockerId !== "") {
  return `${method.name} · ${lockerId}`
}
```

Przewidywany czas dostawy to treść wyszukiwana po typie dostawy. Czas realizacji jest odczytywany z katalogu w chwili budowania e-maila:

```ts
const deliveryType = context?.deliveryMethod?.type ?? "courier"

return {
  estimatedDelivery: messages.estimatedDelivery[deliveryType],
  fulfillmentTime: describeOrderFulfillmentTime(fulfillmentTimes, messages),
}
```

`getFulfillmentTimeAttributesByVariantId` w `attribute-on-product.server.ts` czyta atrybut `czas-realizacji` (`FULFILLMENT_TIME_ATTRIBUTE_HANDLE`) tak, jak pokazuje go strona produktu: wartość wariantu, gdy wariant ma własne atrybuty, w przeciwnym razie wartość produktu, a przy pustej wartości nic. `resolveOrderLineFulfillmentTimes` w `src/modules/order/order.fulfillment-time.utils.ts` zamienia każdą wartość na etykietę w języku zamówienia, a produkt bez niej dostaje `fulfillmentTime.fallback`, czyli 10 dni roboczych. `describeOrderFulfillmentTime` odczytuje z każdej etykiety liczbę i jednostkę (godziny, dni, dni robocze, tygodnie albo miesiące, po polsku lub po angielsku) i podaje najdłuższy czas, a po nim `fulfillmentTime.note`, które mówi, że czas biegnie od przyjęcia zamówienia i że zamówienie jest wysyłane w jednej przesyłce. Gdy etykieta nie ma liczby i jednostki, które da się porównać, na przykład „na zamówienie”, e-mail wymienia zamiast tego każdy produkt z jego własnym czasem. E-mail podaje więc sam termin, czego wymaga art. 21 ustawy o prawach konsumenta, a nie odsyła do stron produktów, które mogą się zmienić po zamówieniu.

Plik `messages/{locale}/emails.order-confirmation.json` ma obiekt `fulfillmentTime` z kluczami `fallback` i `note` oraz obiekt `estimatedDelivery` z kluczami `courier`, `locker` i `in_store`. Oba powtarzają § 7 regulaminu: czas realizacji podany na stronie każdego produktu, a gdy strona go nie podaje, do 10 dni roboczych, przy czym dla całego zamówienia obowiązuje najdłuższy, a potem do 4 dni roboczych doręczenia przez InPost albo odbiór w pracowni po upływie czasu realizacji. Zmiana czasu zastępczego albo czasu doręczenia to edycja katalogu komunikatów i § 7 w `/admin/content`, a zmiana czasu produktu to edycja jego atrybutu `czas-realizacji`. E-mail o wysyłce ma własne `deliveryTiming` w `emails.order-shipped.json`, które podaje te same do 4 dni roboczych od wysyłki dla kuriera i paczkomatu oraz odbiór po powiadomieniu dla zamówień z odbiorem osobistym; kroki kuriera i paczkomatu w kasie podają ten sam czas doręczenia.

## Czego nie ma

- Nie ma przewoźnika poza InPost: przesyłki, etykiety i śledzenie idą wyłącznie przez API ShipX, a zamówienie odbierane w pracowni nie ma żadnej z nich.
- Nie ma automatycznych zmian zamówienia od przewoźnika: status InPost jest widoczny na zamówieniu i odświeżany na żądanie albo przez webhook InPost, ale oznaczenie zamówienia jako wysłanego i dostarczonego zostaje w rękach administratora, a nadanie przesyłki nie oznacza zamówienia jako wysłanego, bo nadana paczka jeszcze nie opuściła pracowni. Bez przesyłki InPost `order.tracking_number` i `order.tracking_url` to to, co administrator wpisze w oknie wysyłki. Numer, który InPost nada po oznaczeniu zamówienia jako wysłanego, trafia do klienta e-mailem raz.
- Nie ma reguł wysyłki: cena to płaska kwota na metodę, bez logiki wagi, rozmiaru, wartości koszyka ani miejsca dostawy. Jedyną regułą miejsca dostawy jest sprawdzenie `DELIVERY_COUNTRY_CODES`.
- Nie ma tabeli lokalizacji sklepów dla `in_store`.
- Nie ma ekranu panelu dla przewoźników ani metod dostawy — wiersze zarządza się bezpośrednio w D1.
