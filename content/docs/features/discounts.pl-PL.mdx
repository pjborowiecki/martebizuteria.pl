title: "Rabaty"
description: "Kody rabatowe od strony kuponów w panelu, przez pole w kasie, wykorzystanie trzymane przez otwarty checkout i kupon Stripe, po wykorzystanie zapisywane razem z zamówieniem."

Kody rabatowe działają od początku do końca. Administrator tworzy je na `/admin/coupons`, kupujący wpisuje kod w podsumowaniu kasy, serwer sprawdza go ponownie i rezerwuje jedno jego wykorzystanie podczas budowania sesji Stripe, a realizacja zamienia tę rezerwację w wykorzystanie we wsadzie, który tworzy zamówienie. Implementacja znajduje się w `src/modules/discount/`.

## Tabele

`discount`, `discount_redemption` i `discount_claim` (`src/modules/discount/discount.schema.ts`):

```ts
export const discount = sqliteTable(
  "discount",
  {
    code: text("code").notNull().unique(),
    description: text("description", { length: 512 }),
    endsAt: timestamp("ends_at"),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    isActive: integer("is_active", { mode: "boolean" }).default(true).notNull(),
    maxDiscountAmount: integer("max_discount_amount"),
    minOrderTotal: integer("min_order_total"),
    perCustomerLimit: integer("per_customer_limit"),
    startsAt: timestamp("starts_at"),
    type: text("type", { enum: DISCOUNT_TYPES }).notNull(),
    usageCount: integer("usage_count").default(0).notNull(),
    usageLimit: integer("usage_limit"),
    value: integer("value").notNull(),
    ...timestamps(),
  },
  (table) => [index("discount_code_idx").on(table.code), index("discount_isActive_idx").on(table.isActive)],
)

export const discountRedemption = sqliteTable(
  "discount_redemption",
  {
    amount: integer("amount").notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    orderId: text("order_id").references(() => order.id, { onDelete: "cascade" }),
    userId: text("user_id").references(() => user.id, { onDelete: "set null" }),
    ...timestamps(),
  },
  (table) => [
    index("discount_redemption_discountId_idx").on(table.discountId),
    index("discount_redemption_discountId_email_idx").on(table.discountId, table.email),
    uniqueIndex("discount_redemption_orderId_unique").on(table.orderId),
  ],
)

export const discountClaim = sqliteTable(
  "discount_claim",
  {
    checkoutId: text("checkout_id")
      .references(() => checkout.id, { onDelete: "cascade" })
      .notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    ...timestamps(),
  },
  (table) => [
    uniqueIndex("discount_claim_checkoutId_discountId_unique").on(table.checkoutId, table.discountId),
    index("discount_claim_discountId_email_idx").on(table.discountId, table.email),
  ],
)
```

Trzy typy to `percentage`, `fixed_amount` i `free_shipping` (`DISCOUNT_TYPES` w `discount.constants.ts`). `value` to jedna liczba całkowita: cały procent dla `percentage`, kwota w jednostkach podrzędnych dla `fixed_amount`, a dla `free_shipping` jest ignorowana. Kolumny limitów są nullowalne, a `null` oznacza brak limitu: `usage_limit` ogranicza łączną liczbę wykorzystań, `per_customer_limit` ogranicza ją dla jednego adresu e-mail, `min_order_total` to minimalna suma pozycji w jednostkach podrzędnych, a `max_discount_amount` ogranicza, ile może odjąć rabat procentowy.

`discountRelations` deklaruje `many(cart)`, `many(checkout)`, `many(discountClaim)`, `many(order)` i `many(discountRedemption)`. Każda z tabel `cart`, `checkout` i `order` ma kolumnę `discount_id`, a `order` ma dodatkowo `discount_total`. Kolumna `description`, trzy kolumny reguł, indeks `is_active` i tabela `discount_redemption` pochodzą z `20260930200000_discount_rules_and_redemptions.sql`.

Wiersz `discount_claim` to wykorzystanie kodu, które trzyma otwarty checkout: checkout, kod i adres e-mail, dla którego je zarezerwowano. Trwa od chwili, gdy sesja Stripe checkoutu zostaje zbudowana z kodem, aż do jej opłacenia, wygaśnięcia, nieudanej płatności albo zastąpienia (zobacz [Utrzymanie wykorzystania na czas płatności](#utrzymanie-wykorzystania-na-czas-płatności)). `discount_claim_checkoutId_discountId_unique` pozwala checkoutowi trzymać każdy kod raz, a `discount_claim_discountId_email_idx` liczy rezerwacje kodu, wszystkie albo jednego adresu. Oba klucze obce są kaskadowe, więc usunięcie checkoutu albo kodu usuwa jego rezerwacje. Tabela pochodzi z `20261005400000_discount_claims.sql`.

## Reguły

`discount.utils.ts` zawiera czyste funkcje, które ustalają, ile kod jest wart. Z dwóch pierwszych korzysta zarówno sprawdzenie w sklepie, jak i serwer:

- `resolveDiscountRejection` sprawdza po kolei `is_active`, `starts_at`, `ends_at`, `usage_count` względem `usage_limit`, wcześniejsze wykorzystania klienta (`redeemedByCustomer` w wierszu) względem `per_customer_limit` oraz sumę pozycji względem `min_order_total`. Zwraca pierwszą porażkę jako kod `DISCOUNT_REJECTION` (`inactive`, `notStarted`, `expired`, `exhausted`, `alreadyUsed` albo `minOrderNotMet`) albo `undefined`.
- `calculateDiscountAmount` zwraca koszt dostawy dla `free_shipping`, `min(value, itemsSubtotal)` dla `fixed_amount`, a dla `percentage` zaokrągloną część sumy pozycji, ograniczoną przez `max_discount_amount` i przez samą sumę.
- `resolveAppliedCheckoutDiscount` rozstrzyga, czy rabat trafi do zamówienia. Przyjmuje wiersz (albo jego brak), sumę pozycji, koszt dostawy i bieżący czas. Nic nie zwraca, gdy wiersza nie ma, gdy któraś reguła odrzuca kod (wtedy zapisuje to w logu) albo gdy kwota wynosi zero lub mniej; w pozostałych przypadkach zwraca zastosowany rabat.

Reguły potrzebują jednego wiersza. `getDiscountByCodeForCustomerQuery(code, email)` (`discount.accessors.ts`) wybiera rabat o dokładnie tym kodzie, a w tej samej instrukcji także `redeemedByCustomer`: skorelowaną liczbę jego wierszy `discount_redemption`, których adres e-mail po zamianie na małe litery jest równy przekazanemu adresowi po przycięciu i zamianie na małe litery. Bez adresu e-mail liczba wynosi 0, a `discount_redemption` nie jest w ogóle odczytywana. Funkcja zwraca relacyjne zapytanie `findFirst`, więc wywołujący wykonują je samodzielnie (`await`): dodane do `db.batch` rzuciłoby przy nieznanym kodzie wyjątek, zamiast zwrócić `undefined` (zobacz [Drizzle ORM i D1: wsady](/docs/integrations/drizzle-orm-d1#wsady)). SQLite znajduje kod w indeksie `discount_code_unique` i liczy wykorzystania z indeksu pokrywającego `discount_redemption_discountId_email_idx`, co sprawdza `query-plans.integration.test.ts`.

Siódmy kod odrzucenia, `notFound`, pochodzi z walidatora, gdy żaden wiersz nie pasuje. Kody są porównywane po `normalizeDiscountCode`, które przycina je i zamienia na wielkie litery. Odrzucenie to kod, a nie zdanie, a kasa renderuje je z `pages.checkout.discount.rejection.<code>`.

## W kasie

`validateDiscountCode` (`use-cases/validate-discount-code.ts`) sprawdza kod względem koszyka: przyjmuje kod, opcjonalny adres e-mail, sumę pozycji i koszt dostawy. Ta funkcja nie ma middleware `authorized`, więc gość może wypróbować kod, a `use-case-authorization.test.ts` wymienia ją wśród publicznych use case'ów. Stoi za `withRateLimit("discount-validate", RATE_LIMITS.CHECKOUT)`, czyli dziesięcioma sprawdzeniami na minutę z jednego adresu klienta we własnym koszyku limitu, więc pola nie da się użyć do szybkiego zgadywania kodów ani tego, które adresy już z kodu skorzystały; po przekroczeniu limitu odpowiada `TOO_MANY_REQUESTS`, a pole pokazuje `pages.checkout.discount.rejection.error`. Odpowiada albo `applied` (kod, `discountId`, typ i kwota), albo `rejection`, i niczym więcej. Sprawdzenie limitu na klienta używa przesłanego adresu e-mail, a gdy żadnego nie przesłano, adresu zalogowanego użytkownika; pusty adres liczy się jako brak adresu, a błędny nie przechodzi walidacji. Licznik limitu to jedno żądanie do D1 przed uruchomieniem handlera. Po nim, gdy adres został przesłany, sesja w ogóle nie jest odczytywana, a sprawdzenie zajmuje jeszcze jedno żądanie. Bez adresu funkcja najpierw odczytuje sesję. U zalogowanego klienta to jedno żądanie o sesję i drugie o kod z adresem konta, czyli dwa po liczniku. Gość nie ma ciasteczka sesji, więc Better Auth odpowiada bez sięgania do D1, a sprawdzenie nadal zajmuje jedno żądanie po liczniku.

Ten sam plik eksportuje dwa sposoby, w jakie kasa ją wywołuje:

- `validateDiscountCodeMutation` obsługuje przycisk „Zastosuj”. Jego `mutationFn` zawsze pyta serwer, nigdy nie bierze odpowiedzi z pamięci podręcznej, a potem zapisuje odpowiedź przez `setQueryData` pod kluczem `validateDiscountCodeQuery` dla tych samych danych.
- `validateDiscountCodeQuery({ code, email, itemsSubtotal, shippingTotal })` to zapytanie podsumowania. Jego klucz to `DISCOUNT_QUERY_KEYS.VALIDATION` (`["discount", "validate"]`) z tymi danymi, a `staleTime` to `DISCOUNT_QUERY_STALE_MS` (minuta), więc podsumowanie pokazuje odpowiedź zapisaną przez „Zastosuj” bez ponownego pytania. Bez kodu zapytanie jest pomijane (`skipToken`).

`CheckoutDiscountField` (`src/presentation/components/custom/checkout/components/checkout-discount-field.tsx`) leży w `CheckoutSummary`, pod sumami, dopóki formularz nie ma kodu. To formularz `react-hook-form` walidowany przez `discountZodSchemas.checkoutCodeFormValues`. Odrzucony kod zostaje w polu razem z powodem, nieudane zapytanie pokazuje `pages.checkout.discount.rejection.error`, a pisanie czyści oba komunikaty. Przyjęty kod trafia do pola `discountCode` formularza kasy, które szkic przechowuje w `sessionStorage`.

`CheckoutSummary` nie trzyma kopii wyniku. Czyta `discountCode` z formularza i uruchamia `validateDiscountCodeQuery` z bieżącą sumą pozycji i kosztem dostawy, więc kod przywrócony po przeładowaniu jest sprawdzany i pokazywany ponownie, a wybór innej metody dostawy sprawdza go jeszcze raz. Adres e-mail trafia do sprawdzenia dopiero po ukończeniu kroku kontaktu (`activeStepIndex` jest za nim). Dopóki klient jest na kroku kontaktu, sprawdzenie idzie bez adresu, więc serwer używa adresu zalogowanego konta, a wpisywanie adresu nigdy nie wysyła zapytania; przejście dalej sprawdza kod ponownie z potwierdzonym adresem.

Gdy formularz ma kod, `CheckoutDiscountCode` (`checkout-discount-code.tsx`) pokazuje go zamiast pola, razem z wynikiem sprawdzenia:

| Sprawdzenie             | Wiersz kodu                                                                      | Linia rabatu | Suma                                                     |
| ----------------------- | -------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------- |
| W toku                  | Kod i wskaźnik ładowania                                                         | Brak         | `checkoutSummary.totalAwaitingCode`, bez linii VAT       |
| `applied`               | Kod i kwota, którą odejmuje                                                      | Kwota        | Pozycje plus dostawa minus rabat, z `computeOrderTotals` |
| `rejection`             | Przekreślony kod z `discount.rejection.<code>` pod spodem                        | Brak         | Pozycje plus dostawa                                     |
| Zapytanie się nie udało | Kod, `discount.checkFailed` i przycisk `discount.retry`, który ponawia zapytanie | Brak         | `checkoutSummary.totalAwaitingCode`, bez linii VAT       |

Kod, który już nie obowiązuje, zostaje w formularzu i szkicu z powodem na ekranie, a serwer pomija go przy budowaniu sesji (niżej). Od tej chwili podsumowanie pokazuje rabat i sumę, które serwer wycenił dla tej sesji, więc pokazana suma to ta pobrana. Gdy sprawdzenie się nie uda, podsumowanie nie wie, jaką sumę naliczy serwer, więc nie pokazuje żadnej, dopóki ponowna próba nie da odpowiedzi. Usunięcie kodu czyści `discountCode`. `checkoutSchema` deklaruje `discountCode: zod.string().trim().max(DISCOUNT_CODE_MAX_LENGTH).optional()`, a żaden krok go nie waliduje.

Odpowiedź walidacji to tylko podgląd. `handleCreateCheckoutSession` i `handleUpdateCheckoutSession` wywołują `resolveCheckoutDiscount` (`discount.checkout.server.ts`) z `checkoutValues.discountCode`, adresem e-mail zamówienia, sumą pozycji wyliczoną z cen z bazy i kosztem dostawy. Przy pustym kodzie funkcja niczego nie odczytuje. W przeciwnym razie odczytuje wiersz jedną instrukcją przez `getDiscountByCodeForCustomerQuery` i przekazuje go do `resolveAppliedCheckoutDiscount`, które ponownie stosuje te same reguły. Kod, który już nie obowiązuje, jest logowany i pomijany, a kod, który nic by nie odjął, jest pomijany, zamiast przerywać zakup. Kod, który przejdzie reguły, zostaje następnie zarezerwowany dla checkoutu (niżej) i tylko zarezerwowany kod trafia do sesji i do `checkout.discount_id`.

## Utrzymanie wykorzystania na czas płatności

Reguły porównują `usage_count` z `usage_limit`, a wykorzystania klienta z `per_customer_limit`, ale oba rosną dopiero po opłaceniu sesji. Samo sprawdzenie dałoby kod każdemu checkoutowi otwartemu, gdy zostało jedno wykorzystanie, i każdemu równoległemu checkoutowi klienta z limitem jednego wykorzystania. Dlatego checkout rezerwuje wykorzystanie, zanim Stripe zobaczy kupon, tak jak rezerwuje towar, i trzyma je w `discount_claim`, dopóki jego sesję można opłacić.

`prepareDiscountClaim` z `discount.claim.server.ts` buduje rezerwację jako jedną instrukcję: `INSERT … SELECT … FROM discount WHERE id = ? … ON CONFLICT (checkout_id, discount_id) DO UPDATE`. `SELECT` zwraca wiersz kodu tylko wtedy, gdy `usage_count` plus rezerwacje innych checkoutów jest mniejsze od `usage_limit`, a wykorzystania klienta plus jego rezerwacje w innych checkoutach, dopasowane po adresie e-mail zamienionym na małe litery, są mniejsze od `per_customer_limit`; limit `null` zawsze przechodzi. Zwraca zapisaną rezerwację albo nic. D1 wykonuje jedną instrukcję naraz, więc z dwóch checkoutów walczących o ostatnie wykorzystanie kodu tylko jeden dostaje wiersz. Checkout, który rezerwuje kod już przez siebie trzymany, aktualizuje adres e-mail swojej rezerwacji, a jego własne rezerwacje nigdy nie liczą się przeciwko niemu.

| Moment                                      | Gdzie                                                                                           | Rezerwacja                                                                                                                                   |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Checkout zostaje otwarty z kodem            | `prepareCreateCheckoutBatch`, we wsadzie, który zapisuje checkout                               | Zarezerwowana. Ten sam wsad ustawia `checkout.discount_id` tylko tam, gdzie rezerwacja istnieje, a `createCheckout` zwraca `discountClaimed` |
| Otwarta sesja zostaje zmieniona             | `claimCheckoutDiscount` w `handleUpdateCheckoutSession`, przed zbudowaniem sesji zastępczej     | Zarezerwowana albo zachowana, jeśli checkout już trzyma ten kod. Rezerwacja starej sesji trwa do zamiany                                     |
| Sesja zastępcza przejmuje płatność          | `supersedeCheckoutSession`, we wsadzie, który przenosi płatność                                 | Rezerwacje checkoutu dla wszystkich innych kodów zostają zwolnione, dopiero gdy płatność została przeniesiona                                |
| Zbudowanie albo zamiana sesji się nie udaje | `releaseDiscountClaims` dla nowego checkoutu, `releaseUnappliedDiscountClaims` dla zmiany       | Zwolniona. Zmiana zachowuje rezerwację kodu z `checkout.discount_id`, z której korzysta wciąż otwarta stara sesja                            |
| Sesja wygasa albo płatność się nie udaje    | `prepareReleaseCheckoutBatch`, z tym samym warunkiem oczekującej płatności i checkoutu co towar | Zwolniona raz; ponowione zdarzenie zastaje checkout już nieudany                                                                             |
| Sesja zostaje opłacona                      | `prepareDiscountRedemption`, we wsadzie zamówienia                                              | Zastąpiona wykorzystaniem (zobacz [Przy realizacji](#przy-realizacji))                                                                       |

Gdy rezerwacja się nie uda, kod jest pomijany jak każdy kod, który już nie obowiązuje: `keepClaimedDiscount` loguje `Discount <code> not applied to checkout: other checkouts hold the uses its limits allow.`, a sesja zostaje utworzona albo zastąpiona bez kuponu i w pełnej cenie, którą podsumowanie pokazuje potem z wyceny serwera. Endpoint walidacji pozostaje podglądem: liczy wykorzystania, a nie rezerwacje, więc kod, którego wszystkie pozostałe wykorzystania są zarezerwowane, wygląda na obowiązujący, dopóki sesja nie zostanie zbudowana.

## W sesji Stripe

Stripe nie ma ujemnych pozycji, więc `toSessionDiscounts` w `src/integrations/stripe/stripe.coupons.server.ts` tworzy jednorazowy kupon na wyliczoną kwotę, a `createStripeSession` ustawia go jako `params.discounts`:

```ts
const coupon = await stripe.coupons.create({
  amount_off: discount.amountMinorUnits,
  currency: STRIPE_CURRENCY,
  duration: "once",
  metadata: { checkoutId, source: STRIPE_COUPON_SOURCE },
  name: discount.code,
})

return [{ coupon: coupon.id }]
```

Kod `free_shipping` staje się więc `amount_off` równym kosztowi dostawy, a pozycja dostawy zostaje w sesji. Metadane sesji niosą też `discountCode` i `discountTotal`, których webhook nie czyta. Kody promocyjne samego Stripe nie są włączone.

Każda sesja utworzona lub zastąpiona z kodem dostaje własny kupon, oznaczony w metadanych kuponu identyfikatorem checkoutu i `source: STRIPE_COUPON_SOURCE` (`"marte_checkout"`). `deleteCheckoutCoupons` z tego samego pliku usuwa go, gdy żadna sesja nie może już z niego skorzystać:

| Moment                                                                | Wywołujący                                 | Kupon sesji                                                                     |
| --------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------- |
| Stripe odmawia utworzenia sesji                                       | `createStripeSession`                      | Usuwany od razu, bo żadne zdarzenie go nie wskaże                               |
| `checkout.session.completed`                                          | Webhook, po `handleFulfillCheckoutSession` | Usuwany, także gdy płatność jeszcze się rozlicza                                |
| `checkout.session.expired`                                            | Webhook, po `handleReleaseCheckoutSession` | Usuwany; zastąpienie sesji wygasza starą, więc obejmuje to też sesje zastąpione |
| `checkout.session.async_payment_succeeded` lub `async_payment_failed` | Webhook                                    | Nietknięty, bo zdarzenie completed już go usunęło                               |

`deleteCheckoutCoupons` czyta `session.discounts` i traktuje brakującą lub `null` listę jak brak kuponów. Kupon podany jako identyfikator jest najpierw pobierany, a usuwany jest tylko kupon, którego metadane niosą `source: "marte_checkout"` i `checkoutId` tej samej sesji, więc kupon utworzony ręcznie w panelu Stripe nigdy nie jest ruszany. Nieudane pobranie lub usunięcie jest logowane i nigdy nie przerywa webhooka. Gdy realizacja rzuci wyjątek, kupon zostaje, więc ponowienie zdarzenia przez Stripe nadal może go usunąć. Usunięcie kuponu nie zmienia kwoty, którą Stripe już zastosował, więc ukończona sesja jest obciążana i zwracana jak wcześniej.

## Przy realizacji

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) wczytuje checkout razem z wierszem `discount`, ponownie wylicza kwotę przez `calculateDiscountAmount` z linii z metadanych i ceny metody dostawy, a następnie przekazuje ją do `computeOrderTotals`, które ogranicza rabat do sumy pozycji i dostawy. `prepareFulfillCheckoutBatch` kopiuje `discount_id` na zamówienie i zapisuje `discount_total`. Reguły nie są w tym miejscu sprawdzane ponownie, bo klient już zapłacił.

`fulfillCheckout` dokłada do tego wsadu instrukcje z `prepareDiscountRedemption` (`discount.redeem.server.ts`), więc zamówienie i jego wykorzystanie to jedna transakcja D1. Usuwają one rezerwacje checkoutu, wstawiają wiersz `discount_redemption` z kwotą, adresem e-mail checkoutu, zamówieniem i kontem oraz zwiększają `discount.usage_count`. Wykorzystanie to `INSERT … SELECT … FROM discount WHERE id = ?`, więc kod usunięty w trakcie płatności nie zapisuje niczego, zamiast łamać klucz obcy, a żadna z trzech instrukcji nie sprawdza limitu: klient, który zapłacił, nigdy nie zostaje odrzucony, nawet jeśli kod się w międzyczasie wyczerpał. Ponieważ `order.checkout_id` jest unikalne, drugie dostarczenie tej samej płatności przepada w całości, a wykorzystanie liczy się raz. Checkout bez kodu ma tylko usuwane rezerwacje. Po wsadzie `fulfillCheckout` zapisuje wpis audytu `discount.redeemed` z kwotą.

| Kolumna lub tabela     | Zapisywana przez                                                                                                  | Czytana przez                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |

## Strona kuponów w panelu

`/admin/coupons` to `src/routes/admin.coupons.tsx`. Jej loader wstępnie wczytuje `getAdminDiscountsPageQuery({})` i `getDiscountStatsQuery()`, a strona renderuje `CouponStats` i `CouponListTable` z `src/presentation/components/custom/pages/admin/coupons/`.

- `CouponStats` pokazuje cztery karty z `getAdminDiscountStats`: kody, których można użyć teraz, wszystkie kody, wykorzystania i łączną kwotę udzielonych rabatów.
- `CouponListTable` wyświetla kody od najnowszych, z wyszukiwaniem po `code` i `description`. Każdy wiersz pokazuje typ, wartość, minimalne zamówienie, wykorzystanie względem limitu, datę wygaśnięcia i status z `resolveDiscountStatus`: `active`, `scheduled`, `expired`, `exhausted` albo `disabled`. Menu wiersza pozwala edytować albo usunąć kod.
- `CouponFormDialog` waliduje przez `discountZodSchemas.adminDiscountFormValues`, czyli schemat, który parsują funkcje serwerowe, i pokazuje tylko pola pasujące do wybranego typu. Kwoty wpisuje się w jednostkach podrzędnych.

| Use case                      | Zabezpieczenie                      | Skutek                                                                                        |
| ----------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------- |
| `get-admin-discounts-page.ts` | `authorized({ order: ["read"] })`   | Strona kodów z wyszukiwaniem, domyślnie `ADMIN_DISCOUNTS_PAGE_SIZE` (25)                      |
| `get-admin-discount-stats.ts` | `authorized({ order: ["read"] })`   | Wartości czterech kart                                                                        |
| `create-discount.ts`          | `authorized({ order: ["update"] })` | Wstawia wiersz; zajęty kod rzuca `CONFLICT` z `DISCOUNT_CODE_TAKEN`; audyt `discount.created` |
| `update-discount.ts`          | `authorized({ order: ["update"] })` | Aktualizuje wiersz i ustawia opróżnione pola na `null`; audyt `discount.updated`              |
| `delete-discounts.ts`         | `authorized({ order: ["update"] })` | Usuwa po identyfikatorze; audyt `discount.deleted`                                            |

Po mutacji `useCouponActions` odświeża `DISCOUNT_QUERY_KEYS.ADMIN.ALL` przez `syncQueryInvalidation`, które powiadamia też inne karty tej samej przeglądarki.

## Co wciąż jest otwarte

To szwy, które zostawia obecny kod, a nie rekomendacje produktowe:

1. **Kolumna koszyka.** `cart.discount_id` nie jest ani zapisywana, ani czytana; zastosowany kod żyje tylko w formularzu kasy.
2. **Uprawnienia.** W `src/integrations/better-auth/auth.access.ts` nie ma zasobu `discount`, więc funkcje kuponów korzystają z uprawnień `order` do odczytu i aktualizacji.
3. **Unieważnianie w czasie rzeczywistym.** `ADMIN_REALTIME_QUERY_PREFIXES` nie ma wpisu `DISCOUNT_QUERY_KEYS`, a w `realtime-invalidation.catalog.server.ts` nie ma `scheduleDiscountInvalidation()`, więc zmiana wprowadzona w innej przeglądarce nie dociera do już otwartej strony kuponów.
4. **Stronicowanie.** `CouponListTable` pobiera tylko pierwszą stronę i nie ma przełącznika stron, więc pokazuje najwyżej 25 kodów.
5. **Usuwanie.** Usunięcie kodu usuwa też jego wiersze `discount_redemption` i `discount_claim` (`onDelete: "cascade"`). `checkout.discount_id` i `order.discount_id` nie mają klucza obcego i zachowują stary identyfikator, a oczekujący checkout, którego kod usunięto, zostaje zrealizowany bez rabatu w sumach, co `reconcileTotals` loguje jako niezgodność z kwotą pobraną przez Stripe.
6. **Rezerwacje na ekranie.** Ani podgląd w kasie, ani kolumna wykorzystania w panelu nie liczą zarezerwowanych wykorzystań: kod, którego wszystkie pozostałe wykorzystania są zarezerwowane, wygląda na obowiązujący, dopóki serwer nie pominie go w sesji, a `/admin/coupons` pokazuje tylko `usage_count`.
