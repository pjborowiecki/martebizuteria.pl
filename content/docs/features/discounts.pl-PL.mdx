title: "Rabaty"
description: "Kody rabatowe od strony kuponów w panelu, przez pole w kasie, wykorzystanie trzymane przez otwarty checkout i kupon Stripe, po wykorzystanie zapisywane razem z zamówieniem."
---

Kody rabatowe działają od początku do końca. Administrator tworzy je na `/admin/coupons`, kupujący wpisuje kod w podsumowaniu kasy, serwer sprawdza go ponownie i rezerwuje jedno jego wykorzystanie podczas budowania sesji Stripe, a realizacja zamienia tę rezerwację w wykorzystanie we wsadzie, który tworzy zamówienie. Implementacja znajduje się w `src/modules/discount/`.

## Tabele

`discount`, `discount_redemption` i `discount_claim` (`src/modules/discount/discount.schema.ts`):

```ts
export const discount = sqliteTable(
  "discount",
  {
    code: text("code").notNull().unique(),
    description: text("description", { length: 512 }),
    endsAt: timestamp("ends_at"),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    isActive: integer("is_active", { mode: "boolean" }).default(true).notNull(),
    maxDiscountAmount: integer("max_discount_amount"),
    minOrderTotal: integer("min_order_total"),
    perCustomerLimit: integer("per_customer_limit"),
    startsAt: timestamp("starts_at"),
    type: text("type", { enum: DISCOUNT_TYPES }).notNull(),
    usageCount: integer("usage_count").default(0).notNull(),
    usageLimit: integer("usage_limit"),
    value: integer("value").notNull(),
    ...timestamps(),
  },
  (table) => [index("discount_code_idx").on(table.code), index("discount_isActive_idx").on(table.isActive)],
)

export const discountRedemption = sqliteTable(
  "discount_redemption",
  {
    amount: integer("amount").notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    orderId: text("order_id").references(() => order.id, { onDelete: "cascade" }),
    userId: text("user_id").references(() => user.id, { onDelete: "set null" }),
    ...timestamps(),
  },
  (table) => [
    index("discount_redemption_discountId_email_idx").on(table.discountId, table.email),
    index("discount_redemption_userId_idx").on(table.userId),
    uniqueIndex("discount_redemption_orderId_unique").on(table.orderId),
  ],
)

export const discountClaim = sqliteTable(
  "discount_claim",
  {
    checkoutId: text("checkout_id")
      .references(() => checkout.id, { onDelete: "cascade" })
      .notNull(),
    discountId: text("discount_id")
      .references(() => discount.id, { onDelete: "cascade" })
      .notNull(),
    email: text("email", { length: 320 }).notNull(),
    id: text("id")
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    ...timestamps(),
  },
  (table) => [
    uniqueIndex("discount_claim_checkoutId_discountId_unique").on(table.checkoutId, table.discountId),
    index("discount_claim_discountId_email_idx").on(table.discountId, table.email),
  ],
)
```

Trzy typy to `percentage`, `fixed_amount` i `free_shipping` (`DISCOUNT_TYPES` w `discount.constants.ts`). `value` to jedna liczba całkowita: cały procent dla `percentage`, kwota w jednostkach podrzędnych dla `fixed_amount`, a dla `free_shipping` jest ignorowana. Kolumny limitów są nullowalne, a `null` oznacza brak limitu: `usage_limit` ogranicza łączną liczbę wykorzystań, `per_customer_limit` ogranicza ją dla jednego adresu e-mail, `min_order_total` to minimalna suma pozycji w jednostkach podrzędnych, a `max_discount_amount` ogranicza, ile może odjąć rabat procentowy.

`discountRelations` deklaruje `many(cart)`, `many(checkout)`, `many(discountClaim)`, `many(order)` i `many(discountRedemption)`. Każda z tabel `cart`, `checkout` i `order` ma kolumnę `discount_id`, a `order` ma dodatkowo `discount_total`. Kolumna `description`, trzy kolumny reguł, indeks `is_active` i tabela `discount_redemption` pochodzą z `20260930200000_discount_rules_and_redemptions.sql`. `20261003130000_query_indexes.sql` usunął potem utworzony przez nią indeks `discount_redemption_discountId_idx`, bo `discount_redemption_discountId_email_idx` zaczyna się od tej samej kolumny, i dodał `discount_redemption_userId_idx` dla klucza obcego `user_id`. `query-plans.integration.test.ts` nie przechodzi, gdy któryś klucz obcy nie ma indeksu, więc usunięcie konta albo kodu nigdy nie skanuje wykorzystań.

Wiersz `discount_claim` to wykorzystanie kodu, które trzyma otwarty checkout: checkout, kod i adres e-mail, dla którego je zarezerwowano. Trwa od chwili, gdy sesja Stripe checkoutu zostaje zbudowana z kodem, aż do jej opłacenia, wygaśnięcia, nieudanej płatności albo zastąpienia (zobacz [Utrzymanie wykorzystania na czas płatności](#utrzymanie-wykorzystania-na-czas-płatności)). `discount_claim_checkoutId_discountId_unique` pozwala checkoutowi trzymać każdy kod raz, a `discount_claim_discountId_email_idx` liczy rezerwacje kodu, wszystkie albo jednego adresu. Oba klucze obce są kaskadowe, więc usunięcie checkoutu albo kodu usuwa jego rezerwacje. Tabela pochodzi z `20261005400000_discount_claims.sql`.

## Reguły

`discount.utils.ts` zawiera czyste funkcje, które ustalają, ile kod jest wart. Zarówno sprawdzenie w sklepie, jak i checkout stosują `resolveDiscountRejection` i wyceniają kod przez `calculateDiscountAmount`, a każde z nich opakowuje je we własny werdykt: sprawdzenie w `resolveDiscountPreviewRejection`, checkout w `resolveAppliedCheckoutDiscount`.

- `resolveDiscountRejection` sprawdza po kolei `is_active`, `starts_at`, `ends_at`, `usage_count` względem `usage_limit`, wcześniejsze wykorzystania klienta (`redeemedByCustomer` w wierszu) względem `per_customer_limit` oraz sumę pozycji względem `min_order_total`. Zwraca pierwszą porażkę jako kod `DISCOUNT_REJECTION` (`inactive`, `notStarted`, `expired`, `exhausted`, `alreadyUsed` albo `minOrderNotMet`) albo `undefined`.
- `resolveDiscountPreviewRejection` rozstrzyga podgląd w kasie. Zwraca to, co `resolveDiscountRejection`, a gdy reguły przechodzą, zwraca `held`, jeśli `usage_count` plus wykorzystania zarezerwowane przez inne checkouty (`heldByOtherCheckouts`) osiąga `usage_limit` albo jeśli wykorzystania klienta plus wykorzystania zarezerwowane przez jego inne checkouty (`heldForCustomer`) osiągają `per_customer_limit`. To te same sumy, które porównuje rezerwacja (zobacz [Utrzymanie wykorzystania na czas płatności](#utrzymanie-wykorzystania-na-czas-płatności)), więc podgląd odmawia tego, czego w tej chwili odmówiłaby rezerwacja.
- `calculateDiscountAmount` zwraca koszt dostawy dla `free_shipping`, `min(value, itemsSubtotal)` dla `fixed_amount`, a dla `percentage` zaokrągloną część sumy pozycji, ograniczoną przez `max_discount_amount` i przez samą sumę.
- `resolveAppliedCheckoutDiscount` to werdykt checkoutu. Przyjmuje wiersz (albo jego brak), sumę pozycji, koszt dostawy i bieżący czas. Nic nie zwraca, gdy wiersza nie ma, gdy któraś reguła odrzuca kod (wtedy zapisuje to w logu) albo gdy kwota wynosi zero lub mniej; w pozostałych przypadkach zwraca zastosowany rabat.
- `resolveDiscountStatus` nadaje kodowi status na liście w panelu: `disabled`, gdy `is_active` jest wyłączone, potem `expired`, gdy minęło `ends_at`, `exhausted`, gdy `usage_count` osiągnęło `usage_limit`, `scheduled` przed `starts_at`, a w pozostałych przypadkach `active`. Limit na klienta, minimalne zamówienie i wykorzystania trzymane przez otwarte checkouty nie mają na niego wpływu.

Reguły potrzebują jednego wiersza. `getDiscountByCodeForCustomerQuery(code, email)` (`discount.accessors.ts`) wybiera rabat o dokładnie tym kodzie, a w tej samej instrukcji także `redeemedByCustomer`: skorelowaną liczbę jego wierszy `discount_redemption`, których adres e-mail po zamianie na małe litery jest równy przekazanemu adresowi po przycięciu i zamianie na małe litery. Bez adresu e-mail liczba wynosi 0, a `discount_redemption` nie jest w ogóle odczytywana. Funkcja zwraca relacyjne zapytanie `findFirst`, więc wywołujący wykonują je samodzielnie (`await`): dodane do `db.batch` rzuciłoby przy nieznanym kodzie wyjątek, zamiast zwrócić `undefined` (zobacz [Drizzle ORM i D1: wsady](/docs/integrations/drizzle-orm-d1#wsady)). SQLite znajduje kod w indeksie `discount_code_unique` i liczy wykorzystania z indeksu pokrywającego `discount_redemption_discountId_email_idx`, co sprawdza `query-plans.integration.test.ts`.

Podgląd w kasie odczytuje swój wiersz przez `getDiscountByCodeForPreviewQuery({ code, email, heldSessionId })`: tę samą instrukcję z dwiema dodatkowymi skorelowanymi liczbami z `discount_claim`. `heldByOtherCheckouts` to rezerwacje kodu, a `heldForCustomer` to te z nich, które złożono dla tego samego adresu e-mail po zamianie na małe litery (0 bez adresu). Gdy dostanie identyfikator sesji Stripe, który trzyma przeglądarka, pomija rezerwacje checkoutu tej sesji, znalezionego przez `payment.transaction_id`, więc własny otwarty checkout klienta nigdy nie liczy się przeciwko niemu; identyfikator, który nie pasuje do żadnej płatności, zostawia wszystkie rezerwacje. SQLite liczy rezerwacje z indeksu `discount_claim_discountId_email_idx` i znajduje płatność przez `payment_transactionId_unique`, co również sprawdza `query-plans.integration.test.ts`.

Walidator dodaje dwa kody odrzucenia: `notFound`, gdy żaden wiersz nie pasuje, oraz `held` z `resolveDiscountPreviewRejection`. Kody są porównywane po `normalizeDiscountCode`, które przycina je i zamienia na wielkie litery. Odrzucenie to kod, a nie zdanie, a kasa renderuje je z `pages.checkout.discount.rejection.<code>`.

## W kasie

`validateDiscountCode` (`use-cases/validate-discount-code.ts`) sprawdza kod względem koszyka: przyjmuje kod, opcjonalny adres e-mail, pozycje koszyka (`variantId` i `qty`, najwyżej `CART_LINES_MAX`) oraz opcjonalnie identyfikator wybranej metody dostawy i identyfikator sesji Stripe checkoutu, który trzyma przeglądarka. Przeglądarka nie przesyła żadnych cen ani sum. Funkcja wycenia pozycje przez `getSellPricesByVariantIds`, czyli bieżące ceny sprzedaży, z których korzysta też sprawdzenie dostępności koszyka, i pomija pozycję, której wariant nie ma prawidłowej ceny. Metodę dostawy odczytuje tylko kod `free_shipping`, przez `getOfferedDeliveryMethodByIdQuery`, i odejmuje to, ile kosztuje jej dostawa, czyli nic, gdy produkty w koszyku osiągną próg darmowej dostawy (zobacz [Darmowa dostawa a kody rabatowe](#darmowa-dostawa-a-kody-rabatowe)); zanim metoda zostanie wybrana albo gdy sklep już jej nie oferuje, nic nie odejmuje. Werdykt pochodzi z `resolveDiscountPreviewRejection`, więc kod, którego pozostałe wykorzystania rezerwują inne checkouty, zostaje odrzucony jako `held`, zamiast wyglądać na obowiązujący. Ta funkcja nie ma middleware `authorized`, więc gość może wypróbować kod, a `use-case-authorization.test.ts` wymienia ją wśród publicznych use case'ów. Stoi za `withRateLimit("discount-validate", RATE_LIMITS.CHECKOUT)`, czyli dziesięcioma sprawdzeniami na minutę z jednego adresu klienta we własnym koszyku limitu, więc pola nie da się użyć do szybkiego zgadywania kodów ani tego, które adresy już z kodu skorzystały; po przekroczeniu limitu odpowiada `TOO_MANY_REQUESTS`, a pole pokazuje `pages.checkout.discount.rejection.error`. Odpowiada albo `applied` (kod, `discountId`, typ i kwota), albo `rejection`, i niczym więcej. Sprawdzenie limitu na klienta używa przesłanego adresu e-mail, a gdy żadnego nie przesłano, adresu zalogowanego użytkownika; pusty adres liczy się jako brak adresu, a błędny nie przechodzi walidacji. Licznik limitu to jedno żądanie do D1 przed uruchomieniem handlera. Po nim, gdy adres został przesłany, sesja w ogóle nie jest odczytywana, a kod z jego liczbami i ceny wariantów to dwie instrukcje wysyłane równolegle. Bez adresu funkcja najpierw odczytuje sesję: u zalogowanego klienta to jedno żądanie przed tymi samymi dwiema, z adresem konta; gość nie ma ciasteczka sesji, więc Better Auth odpowiada bez sięgania do D1. Kod `free_shipping`, który przejdzie reguły, dodaje jedno żądanie o swoją metodę dostawy.

Ten sam plik eksportuje dwa sposoby, w jakie kasa ją wywołuje:

- `validateDiscountCodeMutation` obsługuje przycisk „Zastosuj”. Jego `mutationFn` zawsze pyta serwer, nigdy nie bierze odpowiedzi z pamięci podręcznej, a potem zapisuje odpowiedź przez `setQueryData` pod kluczem `validateDiscountCodeQuery` dla tych samych danych.
- `validateDiscountCodeQuery({ code, deliveryMethodId, email, heldSessionId, lines })` to zapytanie podsumowania; `DiscountCheckBasket` to te dane bez kodu. Jego klucz to `DISCOUNT_QUERY_KEYS.VALIDATION` (`["discount", "validate"]`) z tymi danymi, a `staleTime` to `DISCOUNT_QUERY_STALE_MS` (minuta), więc podsumowanie pokazuje odpowiedź zapisaną przez „Zastosuj” bez ponownego pytania. Bez kodu zapytanie jest pomijane (`skipToken`).

`CheckoutDiscountField` (`src/presentation/components/custom/checkout/components/checkout-discount-field.tsx`) leży w `CheckoutSummary`, pod sumami, dopóki formularz nie ma kodu. To formularz `react-hook-form` walidowany przez `discountZodSchemas.checkoutCodeFormValues`. Wysyła kod razem z `DiscountCheckBasket` podsumowania, więc „Zastosuj” zapisuje odpowiedź pod kluczem, który czyta podsumowanie. Odrzucony kod zostaje w polu razem z powodem, nieudane zapytanie pokazuje `pages.checkout.discount.rejection.error`, a pisanie czyści oba komunikaty. Przyjęty kod trafia do pola `discountCode` formularza kasy, które szkic przechowuje w `sessionStorage`.

`CheckoutSummary` nie trzyma kopii wyniku. Czyta `discountCode` z formularza i uruchamia `validateDiscountCodeQuery` z pozycjami koszyka, identyfikatorem wybranej metody dostawy i identyfikatorem sesji odczytanym przez `loadCheckoutSessionId()`, który śledzi przez `useSyncExternalStore` i `subscribeToCheckoutSessionId`, tak jak `useCartAvailability`. Kod przywrócony po przeładowaniu jest więc sprawdzany i pokazywany ponownie, zmiana ilości albo metody dostawy sprawdza go jeszcze raz, podobnie jak zapisanie przez krok płatności otwartej sesji, po którym własna rezerwacja tego checkoutu przestaje się liczyć. Adres e-mail trafia do sprawdzenia dopiero po ukończeniu kroku kontaktu (`activeStepIndex` jest za nim). Dopóki klient jest na kroku kontaktu, sprawdzenie idzie bez adresu, więc serwer używa adresu zalogowanego konta, a wpisywanie adresu nigdy nie wysyła zapytania; przejście dalej sprawdza kod ponownie z potwierdzonym adresem.

Gdy formularz ma kod, `CheckoutDiscountCode` (`checkout-discount-code.tsx`) pokazuje go zamiast pola, razem z wynikiem sprawdzenia:

| Sprawdzenie             | Wiersz kodu                                                                      | Linia rabatu | Suma                                                     |
| ----------------------- | -------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------- |
| W toku                  | Kod i wskaźnik ładowania                                                         | Brak         | `checkoutSummary.totalAwaitingCode`, bez linii VAT       |
| `applied`               | Kod i kwota, którą odejmuje                                                      | Kwota        | Pozycje plus dostawa minus rabat, z `computeOrderTotals` |
| `rejection`             | Przekreślony kod z `discount.rejection.<code>` pod spodem                        | Brak         | Pozycje plus dostawa                                     |
| Zapytanie się nie udało | Kod, `discount.checkFailed` i przycisk `discount.retry`, który ponawia zapytanie | Brak         | `checkoutSummary.totalAwaitingCode`, bez linii VAT       |

Kod, który już nie obowiązuje, zostaje w formularzu i szkicu z powodem na ekranie, a serwer pomija go przy budowaniu sesji (niżej). Od tej chwili podsumowanie pokazuje rabat i sumę, które serwer wycenił dla tej sesji, więc pokazana suma to ta pobrana. Gdy sprawdzenie się nie uda, podsumowanie nie wie, jaką sumę naliczy serwer, więc nie pokazuje żadnej, dopóki ponowna próba nie da odpowiedzi. Usunięcie kodu czyści `discountCode`. `checkoutSchema` deklaruje `discountCode: zod.string().trim().max(DISCOUNT_CODE_MAX_LENGTH).optional()`, a żaden krok go nie waliduje.

Odpowiedź walidacji to tylko podgląd. `handleCreateCheckoutSession` i `handleUpdateCheckoutSession` wywołują `resolveCheckoutDiscount` (`discount.checkout.server.ts`) z `checkoutValues.discountCode`, adresem e-mail z formularza (`checkoutValues.email`), sumą pozycji wyliczoną z cen z bazy i kosztem dostawy przed jakimkolwiek kodem. Przy pustym kodzie funkcja niczego nie odczytuje. W przeciwnym razie odczytuje wiersz jedną instrukcją przez `getDiscountByCodeForCustomerQuery` i przekazuje go do `resolveAppliedCheckoutDiscount`, które ponownie stosuje te same reguły. Kod, który już nie obowiązuje, jest logowany i pomijany, a kod, który nic by nie odjął, jest pomijany, zamiast przerywać zakup. Kod, który przejdzie reguły, zostaje następnie zarezerwowany dla checkoutu (niżej) i tylko zarezerwowany kod trafia do sesji i do `checkout.discount_id`.

## Utrzymanie wykorzystania na czas płatności

Reguły porównują `usage_count` z `usage_limit`, a wykorzystania klienta z `per_customer_limit`, ale oba rosną dopiero po opłaceniu sesji. Samo sprawdzenie dałoby kod każdemu checkoutowi otwartemu, gdy zostało jedno wykorzystanie, i każdemu równoległemu checkoutowi klienta z limitem jednego wykorzystania. Dlatego checkout rezerwuje wykorzystanie, zanim Stripe zobaczy kupon, tak jak rezerwuje towar, i trzyma je w `discount_claim`, dopóki jego sesję można opłacić.

`prepareDiscountClaim` z `discount.claim.server.ts` buduje rezerwację jako jedną instrukcję: `INSERT … SELECT … FROM discount WHERE id = ? … ON CONFLICT (checkout_id, discount_id) DO UPDATE`. `SELECT` zwraca wiersz kodu tylko wtedy, gdy `usage_count` plus rezerwacje innych checkoutów jest mniejsze od `usage_limit`, a wykorzystania klienta plus jego rezerwacje w innych checkoutach, dopasowane po adresie e-mail zamienionym na małe litery, są mniejsze od `per_customer_limit`; limit `null` zawsze przechodzi. Zwraca zapisaną rezerwację albo nic. D1 wykonuje jedną instrukcję naraz, więc z dwóch checkoutów walczących o ostatnie wykorzystanie kodu tylko jeden dostaje wiersz. Checkout, który rezerwuje kod już przez siebie trzymany, aktualizuje adres e-mail swojej rezerwacji, a jego własne rezerwacje nigdy nie liczą się przeciwko niemu. SQLite znajduje kod po kluczu głównym, a rezerwacje i wykorzystania klienta liczy z indeksów `discount_claim_discountId_email_idx` i `discount_redemption_discountId_email_idx`, co również sprawdza `query-plans.integration.test.ts`.

| Moment                                             | Gdzie                                                                                                                                                                                | Rezerwacja                                                                                                                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Checkout zostaje otwarty z kodem                   | `prepareCreateCheckoutBatch`, we wsadzie, który zapisuje checkout                                                                                                                    | Zarezerwowana. Ten sam wsad ustawia `checkout.discount_id` tylko tam, gdzie rezerwacja istnieje, a `createCheckout` zwraca `discountClaimed`                         |
| Otwarta sesja zostaje zmieniona                    | `claimCheckoutDiscount` w `handleUpdateCheckoutSession`, przed zbudowaniem sesji zastępczej                                                                                          | Zarezerwowana albo zachowana, jeśli checkout już trzyma ten kod. Rezerwacja starej sesji trwa do zamiany                                                             |
| Sesja zastępcza przejmuje płatność                 | `supersedeCheckoutSession`, we wsadzie, który przenosi płatność                                                                                                                      | Rezerwacje checkoutu dla wszystkich innych kodów zostają zwolnione, dopiero gdy płatność została przeniesiona                                                        |
| Zbudowanie albo zamiana sesji się nie udaje        | `releaseDiscountClaims` dla nowego checkoutu, `releaseUnappliedDiscountClaims` dla zmiany                                                                                            | Zwolniona. Zmiana zachowuje rezerwację kodu z `checkout.discount_id`, z której korzysta wciąż otwarta stara sesja                                                    |
| Zapis zmienionej dostawy nie udaje się po zamianie | `abandonReplacementCheckout` w `saveReplacementDelivery`, przez `releaseCheckout` dla sesji zastępczej                                                                               | Zwolniona razem z towarem przez `prepareReleaseCheckoutBatch`; checkout i jego płatność kończą się niepowodzeniem, a sesja zastępcza zostaje wygaszona               |
| Sesja wygasa albo płatność się nie udaje           | `prepareReleaseCheckoutBatch` przez `releaseCheckout`, z webhooka albo wcześniej z `releaseExpiredCheckoutSession`, z tym samym warunkiem oczekującej płatności i checkoutu co towar | Zwolniona raz; ponowione zdarzenie zastaje checkout już nieudany                                                                                                     |
| Sesja zostaje opłacona                             | `prepareDiscountRedemption`, we wsadzie zamówienia                                                                                                                                   | Zastąpiona wykorzystaniem (zobacz [Przy realizacji](#przy-realizacji))                                                                                               |
| Nieudane zwolnienie zostawiło rezerwację           | `anonymizeEndedCheckouts` w codziennym czyszczeniu danych                                                                                                                            | Usunięta 30 dni po zakończeniu checkoutu, razem z jego danymi kontaktowymi (zobacz [Okresy przechowywania danych](/docs/guides/data-retention#zakończone-checkouty)) |

Gdy rezerwacja się nie uda, kod jest pomijany jak każdy kod, który już nie obowiązuje: `keepClaimedDiscount` loguje `Discount <code> not applied to checkout: other checkouts hold the uses its limits allow.`, a sesja zostaje utworzona albo zastąpiona bez kuponu i w pełnej cenie, którą podsumowanie pokazuje potem z wyceny serwera. Sprawdzenie kodu w kasie liczy te same rezerwacje, pomijając rezerwacje własnego checkoutu klienta, więc kod, którego wszystkie pozostałe wykorzystania są zarezerwowane, zostaje odrzucony z `pages.checkout.discount.rejection.held`, zanim klient zapłaci. Nadal jest to podgląd: wykorzystanie zarezerwowane między sprawdzeniem a sesją wychwytuje rezerwacja, która pomija kod jak wyżej.

## Darmowa dostawa a kody rabatowe

Gdy właściciel ustawi próg darmowej dostawy (zobacz [Wysyłka i dostawa: Darmowa dostawa](/docs/features/shipping-and-delivery#darmowa-dostawa)), wartość produktów porównywana z progiem jest liczona po kodzie `percentage` albo `fixed_amount` i bez dostawy. Taki kod może więc sprowadzić koszyk z powrotem poniżej progu i wtedy dostawa znów jest płatna; kasa podaje, ile brakuje. Kod `free_shipping` nie wlicza się do progu. Poniżej progu odejmuje cenę dostawy jak dotąd. Gdy produkty osiągną próg, dostawa jest już darmowa, a kod nic nie jest wart: `validateDiscountCode` wycenia pokrywaną dostawę przez `resolveDeliveryPrice` i odpowiada kwotą zero, a `resolveAppliedCheckoutDiscount` porzuca kod przy budowaniu sesji, jak każdy kod, który nic by nie odjął, więc nie zostaje ani zarezerwowany, ani wysłany do Stripe.

## W sesji Stripe

Stripe nie ma ujemnych pozycji, więc `toSessionDiscounts` w `src/integrations/stripe/stripe.coupons.server.ts` tworzy jednorazowy kupon na wyliczoną kwotę, a `createStripeSession` ustawia go jako `params.discounts`:

```ts
const coupon = await stripe.coupons.create({
  amount_off: discount.amountMinorUnits,
  currency: STRIPE_CURRENCY,
  duration: "once",
  metadata: { checkoutId, source: STRIPE_COUPON_SOURCE },
  name: discount.code,
})

return [{ coupon: coupon.id }]
```

Kod `free_shipping` staje się więc `amount_off` równym kosztowi dostawy, a pozycja dostawy zostaje w sesji. Metadane sesji niosą też `discountCode`, którego nic nie czyta, oraz `discountTotal` i `shippingTotal`, czyli rabat i opłatę za dostawę, z którymi sesja została wyceniona; realizacja czyta oba. Kody promocyjne samego Stripe nie są włączone.

Każda sesja utworzona lub zastąpiona z kodem dostaje własny kupon, oznaczony w metadanych kuponu identyfikatorem checkoutu i `source: STRIPE_COUPON_SOURCE` (`"marte_checkout"`). `deleteCheckoutCoupons` z tego samego pliku usuwa go, gdy żadna sesja nie może już z niego skorzystać:

| Moment                                                                | Wywołujący                                 | Kupon sesji                                                                     |
| --------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------- |
| Stripe odmawia utworzenia sesji                                       | `createStripeSession`                      | Usuwany od razu, bo żadne zdarzenie go nie wskaże                               |
| `checkout.session.completed`                                          | Webhook, po `handleFulfillCheckoutSession` | Usuwany, także gdy płatność jeszcze się rozlicza                                |
| `checkout.session.expired`                                            | Webhook, po `handleReleaseCheckoutSession` | Usuwany; zastąpienie sesji wygasza starą, więc obejmuje to też sesje zastąpione |
| `checkout.session.async_payment_succeeded` lub `async_payment_failed` | Webhook                                    | Nietknięty, bo zdarzenie completed już go usunęło                               |

`deleteCheckoutCoupons` czyta `session.discounts` i traktuje brakującą lub `null` listę jak brak kuponów. Kupon podany jako identyfikator jest najpierw pobierany, a usuwany jest tylko kupon, którego metadane niosą `source: "marte_checkout"` i `checkoutId` tej samej sesji, więc kupon utworzony ręcznie w panelu Stripe nigdy nie jest ruszany. Nieudane pobranie lub usunięcie jest logowane i nigdy nie przerywa webhooka. Gdy realizacja rzuci wyjątek, kupon zostaje, więc ponowienie zdarzenia przez Stripe nadal może go usunąć. Usunięcie kuponu nie zmienia kwoty, którą Stripe już zastosował, więc ukończona sesja jest obciążana i zwracana jak wcześniej.

## Przy realizacji

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) bierze rabat, z którym sesja została wyceniona, z jej metadanych `discountTotal`, odczytanych przez `resolveCheckoutSessionDiscountTotal` (`checkout-metadata.zod.ts`), tak jak opłatę za dostawę bierze z `shippingTotal`, i przekazuje go do `computeOrderTotals`, które ogranicza rabat do sumy pozycji i dostawy. Kwota jest wyliczana ponownie tylko dla sesji otwartej, zanim to pole istniało: `calculateDiscountAmount` wylicza ją z obecnego wiersza kodu w `discount` checkoutu, z pozycji sesji, które `readCheckoutSessionLines` odczytuje z `payment.lines` (zobacz [Kasa](/docs/features/checkout#koszyk-w-wierszu-płatności)), i z opłaty za dostawę. `prepareFulfillCheckoutBatch` kopiuje `discount_id` na zamówienie i zapisuje `discount_total`. Reguły nie są w tym miejscu sprawdzane ponownie, bo płatność już przeszła. Zmiana albo usunięcie kodu w trakcie płatności nic więc nie zmienia w tym zamówieniu: zapisuje ono to, co odjął Stripe.

`fulfillCheckout` dokłada do tego wsadu instrukcje z `prepareDiscountRedemption` (`discount.redeem.server.ts`), więc zamówienie i jego wykorzystanie to jedna transakcja D1. Usuwają one rezerwacje checkoutu, wstawiają wiersz `discount_redemption` z `discount_total` zamówienia, adresem e-mail checkoutu, zamówieniem i `user_id` zamówienia oraz zwiększają `discount.usage_count`. Wykorzystanie to `INSERT … SELECT … FROM discount WHERE id = ?`, więc kod usunięty w trakcie płatności nie zapisuje niczego, zamiast łamać klucz obcy, a żadna z trzech instrukcji nie sprawdza limitu: klient po zapłacie nigdy nie zostaje odrzucony, nawet jeśli kod się w międzyczasie wyczerpał. Ponieważ `order.checkout_id` jest unikalne, wsad drugiego dostarczenia tej samej płatności przepada w całości, `fulfillCheckout` znajduje zamówienie utworzone przez pierwsze i wraca bez wpisu audytu, a wykorzystanie liczy się raz (zobacz [Płatności](/docs/features/payments#realizacja)). Checkout bez kodu albo taki, którego sesja nic nie odjęła, ma tylko usuwane rezerwacje. Po wsadzie `fulfillCheckout` zapisuje wpis audytu `discount.redeemed` z kwotą, także wtedy, gdy D1 zatwierdziło wsad, ale odpowiedziało błędem, a znalezione potem zamówienie jest tym, które wstawiło to dostarczenie.

`user_id` wykorzystania jest odczytywane z zamówienia wstawianego w tym samym wsadzie, więc to konto, do którego trafia zamówienie: konto zalogowanego klienta albo, dla checkoutu gościa, zweryfikowane konto z adresem e-mail checkoutu, a w pozostałych przypadkach żadne. Gdy `claimGuestOrdersForUser` przypisuje później zamówienia gościa do konta, ten sam wsad ustawia `user_id` na wykorzystaniach wszystkich zamówień konta, które jeszcze do niego nie należą (zobacz [Zamówienia](/docs/features/orders#historia-zamówień-klienta)); SQLite znajduje je przez zamówienia konta i `discount_redemption_orderId_unique`, co sprawdza `query-plans.integration.test.ts`. `20261017130000_discount_redemption_order_account.sql` zrobiła to samo jednorazowo dla zamówień, które `20261016140000_claim_past_guest_orders.sql` i wcześniejsze realizacje przypisały do konta. Nic nie czyta `discount_redemption.user_id`: limit na klienta liczy wykorzystania po adresie e-mail, więc wykorzystanie z przejętego zamówienia liczy się dla jego adresu tak jak wcześniej. Usunięcie konta ustawia tę kolumnę na `null`.

| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Strona kuponów w panelu

`/admin/coupons` to `src/routes/admin.coupons.tsx`. Jej loader wstępnie wczytuje `getAdminDiscountsPageQuery({ page: 1, pageSize: ADMIN_DISCOUNTS_PAGE_SIZE })` i `getDiscountStatsQuery()`, oba z `staleTime: "static"`, a trasa ustawia `shouldReload: false` i `staleTime` równy `DISCOUNT_QUERY_STALE_MS` (minuta). Strona renderuje `AdminHeader` i `CouponsTableContent` wewnątrz `CouponsSheetProvider`, którego wartość pochodzi z `useCouponsSheetState`: czy panel boczny jest zamknięty, czy służy do tworzenia, czy do edycji, oraz który kod jest edytowany. Komponenty leżą w `src/presentation/components/custom/pages/admin/coupons/`.

`CouponsTableContent` (`components/coupons-table.tsx`) układa stronę tak jak pozostałe listy w panelu (zobacz [Tabela danych](/docs/ui/data-table)): `CouponsStats` nad `DataGridShell`, który zawiera pasek narzędzi, treść tabeli i stronicowanie. `CouponSheet` jest montowany tylko wtedy, gdy panel jest otwarty.

### Statystyki

`CouponsStats` czyta `getDiscountStatsQuery()` przez `useSuspenseQuery` i pokazuje cztery karty z `COUPON_STAT_CARDS` (`coupons-stats.config.ts`) w tej kolejności: wszystkie kody (`total`), kody, których można użyć teraz (`active`), wykorzystania i kwotę udzielonych rabatów (`redeemedTotalMinorUnits`). `getAdminDiscountStats` liczy jako dostępne kody aktywne, już rozpoczęte, jeszcze niezakończone i poniżej limitu użyć, a dla dwóch ostatnich kart liczy i sumuje wszystkie wiersze `discount_redemption`. Liczby są zapisywane przez `toLocaleString`, a kwota przez `formatPrice`, obie w formacie administratora. Dwie pierwsze karty są przyciskami filtra: „Aktywne kody” przełącza filtr statusu tabeli na `active`, a „Wszystkie kody” go czyści; każda jest wciśnięta, gdy filtr do niej pasuje. Gdy nieaktualne zapytanie o statystyki pobiera dane ponownie, wartości pokazują szkielety, a przyciski są wyłączone. Poniżej progu `xl` karty stoją po dwie w rzędzie, od niego po cztery.

### Tabela

`useCouponsDataGrid` (`hooks/use-coupons-data-grid.ts`) buduje tabelę z `couponsDataGrid`, którego `persistenceKey` to `COUPONS_DATA_GRID_KEY` (`admin.coupons`), więc kolejność, szerokości i widoczność kolumn są zapamiętywane jak na pozostałych listach. Działa w trybie serwerowym z ręcznym stronicowaniem: każda strona to jedno zapytanie `getAdminDiscountsPageQuery({ page, pageSize, search, status, type })` z `placeholderData: keepPreviousData`, a podczas pobierania strony treść tabeli pokazuje szkieletowe wiersze. Wiersze są ułożone od najnowszych i żadna kolumna nie sortuje.

- **Wyszukiwanie.** Pole wyszukiwania na pasku narzędzi ustawia globalny filtr tabeli, który `useAdminDebouncedTableSearch` opóźnia o 300 ms, zanim trafi do zapytania jako `search`. Serwer szuka go, bez względu na wielkość liter, w `code` i `description`. Nowa fraza wraca do pierwszej strony.
- **Filtry.** `CouponsStatusFilter` i `CouponsTypeFilter` (`components/coupons-filters.tsx`) to listy wyboru z `DISCOUNT_STATUSES` i `DISCOUNT_TYPES`, każda z pozycją „Wszystkie”. `applyCouponsFilter` dołącza zmianę do aktywnych filtrów, wraca do pierwszej strony i czyści zaznaczenie wierszy. Serwer zamienia status na SQL (`discountStatusCondition` w `discount.accessors.ts`) z tą samą kolejnością warunków co `resolveDiscountStatus`, a `discount.accessors.integration.test.ts` sprawdza, że każdy filtr statusu zwraca dokładnie te kody, które lista oznacza tym statusem.

Kolumny definiuje `buildCouponColumns` (`lib/coupons-column-defs.tsx`); ich identyfikatory, szerokości, domyślna widoczność i przypięcie to `ADMIN_DISCOUNT_TABLE_COLUMN_ID`, `ADMIN_DISCOUNT_TABLE_COLUMN_SIZE`, `ADMIN_DISCOUNT_TABLE_DEFAULT_COLUMN_VISIBILITY` i `ADMIN_DISCOUNT_TABLE_COLUMN_PINNING` w `discount.constants.ts`.

### Panel kodu

`CouponSheet` (`edit-coupon/coupon-sheet.tsx`) obejmuje `CouponFormProvider` panelem `CatalogFormSheetContent`, czyli bocznym panelem formularzy katalogu ze zmienną szerokością, i dzieli z nimi zapisaną szerokość (klucz `admin.catalog.form-sheet`). Provider trzyma formularz `react-hook-form` walidowany przez `discountZodSchemas.adminDiscountFormValues`, czyli schemat, który parsują funkcje serwerowe. Wartości początkowe daje `toCouponFormValues`: edytowany wiersz albo aktywny kod procentowy bez wartości. Wysłanie formularza, które schemat odrzuca, oznacza błędne pola i pokazuje komunikat. Formularz ma cztery sekcje w `edit-coupon/_sections/`:

- **Kod** (`DetailsSection`): przy edycji identyfikator tylko do odczytu; kod, wyświetlany wielkimi literami z licznikiem znaków i zamieniany na wielkie litery przez `normalizeDiscountCode` przy zapisie; opis wewnętrzny.
- **Rabat** (`DiscountSection`): typ, a po nim wartość: cały procent z dopiskiem `%`, kwota dla `fixed_amount` albo informacja, że darmowa dostawa jej nie wymaga. Zmiana typu zeruje wartość. Maksymalny rabat pojawia się tylko przy procencie, minimalna wartość koszyka przy każdym typie.
- **Limity** (`LimitsSection`): łączna liczba użyć i liczba użyć na klienta, puste oznacza brak limitu.
- **Dostępność** (`AvailabilitySection`): aktywny albo wyłączony oraz początek i koniec.

Pola kwot (`CouponMoneyField`) przyjmują złote, nie grosze. `parseMoneyInputToMinorUnits(next, STORE_CURRENCY_CODE, formatLocale)` odczytuje to, co administrator wpisuje w swoim formacie, a `formatMinorUnitsToMoneyInput` w ten sam sposób wypisuje zapisane jednostki podrzędne (zobacz [Internacjonalizacja](/docs/features/internationalization)). Początek i koniec to pola `datetime-local`, które `toLocalInputValue` i `toIsoOrUndefined` odczytują i zapisują w strefie czasowej samej przeglądarki, a nie w strefie wyświetlania, w której tabela pokazuje daty. Poniżej progu `sm` panel zajmuje całą szerokość, bez uchwytu do zmiany szerokości, a pola ustawione parami układają się jedno pod drugim.

### Zapisywanie i usuwanie

`useSaveCoupon` z `edit-coupon/coupon-form-provider.tsx` uruchamia `createDiscountMutation` dla nowego kodu i `updateDiscountMutation` dla edytowanego. Po sukcesie pokazuje komunikat, wywołuje `syncQueryInvalidation(queryClient, DISCOUNT_QUERY_KEYS.ADMIN.ALL)` i zamyka panel. `CONFLICT` umieszcza „Ten kod jest już używany.” przy polu kodu i w komunikacie; każdy inny błąd pokazuje ogólny komunikat, a panel zostaje otwarty. `useDeleteCoupons` (`hooks/use-delete-coupons.ts`), z którego korzystają menu wiersza i akcja zbiorcza, uruchamia `deleteDiscountsMutation` i po sukcesie wywołuje to samo `syncQueryInvalidation`. `DISCOUNT_QUERY_KEYS.ADMIN.ALL` to `["admin", "discounts"]`, prefiks kluczy strony i statystyk, więc zapis albo usunięcie pobiera oba ponownie w tej karcie, a przez `BroadcastChannel` także w pozostałych kartach przeglądarki (zobacz [TanStack Query](/docs/integrations/tanstack-query#unieważnianie-między-kartami)).

## Co wciąż jest otwarte

To szwy, które zostawia obecny kod, a nie rekomendacje produktowe:

1. **Kolumna koszyka.** `cart.discount_id` nie jest ani zapisywana, ani czytana; zastosowany kod żyje tylko w formularzu kasy.
2. **Uprawnienia.** W `src/integrations/better-auth/auth.access.ts` nie ma zasobu `discount`, więc funkcje kuponów korzystają z uprawnień `order` do odczytu i aktualizacji.
3. **Unieważnianie w czasie rzeczywistym.** `ADMIN_REALTIME_QUERY_PREFIXES` nie ma wpisu `DISCOUNT_QUERY_KEYS`, a w `realtime-invalidation.catalog.server.ts` nie ma `scheduleDiscountInvalidation()`, więc ani zmiana wprowadzona w innej przeglądarce, ani wykorzystanie zapisane przez opłacony checkout nie docierają do już otwartej strony kuponów; odświeża ją przycisk odświeżania.
4. **Usuwanie.** Usunięcie kodu usuwa też jego wiersze `discount_redemption` i `discount_claim` (`onDelete: "cascade"`), więc jego wykorzystania znikają też z kart wykorzystań i udzielonych rabatów. `checkout.discount_id` i `order.discount_id` nie mają klucza obcego i zachowują stary identyfikator. Checkout opłacony kodem usuniętym w międzyczasie zapisuje rabat odjęty przez Stripe, ale bez wykorzystania.
5. **Rezerwacje w panelu.** Strona kuponów liczy tylko wykorzystania: kolumna wykorzystania, status i karta aktywnych kodów czytają `usage_count`, więc kod, którego wszystkie pozostałe wykorzystania rezerwują otwarte checkouty, nadal wygląda, jakby miał wolne wykorzystania.
