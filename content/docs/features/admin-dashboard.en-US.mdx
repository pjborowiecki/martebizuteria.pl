## Layout

`src/routes/admin.tsx` is the console shell.

```ts
beforeLoad: requireAdmin,
```

`requireAdmin` (`src/integrations/better-auth/auth.routes.ts`) requires a session whose role passes `hasAdminAccess`, which checks membership of `ADMIN_PANEL_ROLES = [ROLES.ADMIN]` (`src/integrations/better-auth/auth.access.ts`). A signed-in customer is redirected to `/account/overview`, an admin without two-factor authentication to `/admin/security`, and an anonymous visitor to `/auth/sign-in?redirect=<path>`. The guard re-checks the session on every real navigation into `/admin`, leaves it in the TanStack Query cache, and resolves to `{ user }`, which becomes route context. See [Integrations: Better Auth](/docs/integrations/better-auth).

Three things the layout does that nothing else does:

1. **Its own stylesheet.** `head` links `src/presentation/styles/admin.css?url`, so the admin CSS is not loaded on the storefront.
2. **Forces light mode.** `useAdminLightTheme()` (`src/presentation/theme/use-admin-light-theme.ts`) removes the `dark` class on mount and restores the storefront preference from `localStorage` on unmount.
3. **Subscribes to realtime invalidation.**

```ts
useRealtimeQuerySync({
  hub: REALTIME_INVALIDATION_HUB.ADMIN,
  subscriptions: ADMIN_REALTIME_QUERY_PREFIXES,
})
```

`ADMIN_REALTIME_QUERY_PREFIXES` (`src/integrations/realtime-invalidation/realtime-invalidation.subscriptions.ts`) lists fifteen key prefixes — audit log page and stats, admin orders, admin customers, the admin all/stats keys for categories, collections, products and product attributes, the admin all/by-handle keys for content pages, and the admin sales status. A mutation anywhere in the console refreshes every other open console tab.

The sidebar's open state is read server-side by `getAdminSidebarDefaultOpen()` from the `sidebar_state` cookie (`src/presentation/theme/sidebar-preference.ts`), and an inline `SIDEBAR_INIT_SCRIPT` copies the `localStorage` value into that cookie before hydration so the sidebar does not flash.

`/admin` redirects to `/admin/overview`, and the layout declares `staticData.namespaces: ["pages.admin", "components.datagrid"]`.

## Navigation

`admin-sidebar.tsx` defines four groups:

| Group  | Items                                                                                           |
| ------ | ----------------------------------------------------------------------------------------------- |
| (top)  | Dashboard (`/admin/overview`)                                                                   |
| Main   | Orders, Customers, and a collapsible Catalog with Products, Categories, Collections, Attributes |
| Tools  | Marketing, Coupons, and Content                                                                 |
| System | Audit, Settings — Settings has `disabled: true`                                                 |

A disabled item renders as a non-interactive `SidebarMenuButton disabled` with `cursor-not-allowed opacity-50`, so the two disabled screens are not reachable from the UI at all — only by typing the URL.

The sidebar footer's sign-out button calls `signOut` and then does a full page load of `/auth/sign-in`, which discards the query cache.


## Sales switch

The first card on the overview, `DashboardSalesSwitch` (`dashboard/components/dashboard-sales-switch.tsx`), stops and restarts sales. It shows the state as an "Open" or "Paused" badge with a sentence saying what customers get, and a switch labelled "Pause sales" ("Wstrzymaj sprzedaż"); the copy is under `pages.admin.dashboard.sales` in both languages. While sales are paused the card turns amber.

It reads `getAdminSalesStatusQuery()`, which calls the public `getSalesStatus` under the admin key `STORE_SETTING_QUERY_KEYS.ADMIN.SALES`, and the route loader prefetches it. Flipping the switch runs `setSalesPausedMutation`, which calls `setSalesPaused` in `src/modules/store-setting/use-cases/set-sales-paused.ts`. That server function is guarded by `authorized({ settings: ["manage"] })`, the dashboard's own permission, so a customer, or a request without a session, is refused by the server whatever the page shows. It writes the `sales_paused` column of the single `store_setting` row with one upsert that changes the row only when the value differs, and when it did change it schedules `scheduleSalesStatusInvalidation()` and records `sales.paused` or `sales.resumed` in the audit log against the admin making the request (see [Audit log](/docs/features/audit-log)). A second admin asking for the state the shop is already in changes nothing and records nothing. The switch is disabled while the request is in flight; on success the card writes the answer into both the admin and the storefront cache entries and toasts "Sales paused" or "Sales resumed", and on failure it keeps the state it showed and toasts an error.

What a pause does to the storefront and the checkout is described in [Checkout: Pausing sales](/docs/features/checkout#pausing-sales).

## The snapshot

`getDashboardSnapshot` (`src/modules/admin-dashboard/use-cases/get-dashboard-snapshot.ts`) is guarded by `authorized({ settings: ["manage"] })` — the same permission as the audit log, not an `order` or `product` permission. It takes a `locale` so the chart labels can be formatted server-side, and runs **eleven queries in one `db.batch`**.

The comparison window comes from `resolveAdminDashboardComparisonPeriod(now)` with `ADMIN_DASHBOARD_COMPARISON_PERIOD_DAYS = 30`, so every KPI is "the last 30 days versus the 30 before that".

| KPI                 | Accessor            | Source                                                           |
| ------------------- | ------------------- | ---------------------------------------------------------------- |
| `revenue`           | `salesTotalsQuery`  | `netSalesSum` over the sales                                     |
| `orders`            | `salesTotalsQuery`  | `count()` of the sales                                           |
| `customers`         | `newCustomersQuery` | `count()` of `user` rows by `created_at`                         |
| `pageViews`         | `pageViewsQuery`    | `count()` of `audit_log` rows with action `customer.page_viewed` |
| `averageOrderValue` | `salesTotalsQuery`  | `netSalesAverage`, the revenue divided by the orders, rounded    |

**What counts as a sale.** An order counts when its status is in `ORDER_SALE_STATUSES` (`processing` and `completed`, in `src/modules/order/order.constants.ts`), whether or not it has been sent, because checkout writes an order as `processing` only once its payment has succeeded and the order stays `processing` until the admin marks it delivered. Pending orders, which nobody has paid for, and cancelled and refunded orders are left out. `orderCountsAsSale`, `netSalesSum` and `netSalesAverage` in `src/modules/order/order.accessors.ts` are that condition and the sum and rounded average of what each sale brings in, `max(order.total - payment.refunded_amount, 0)`, so a partial refund given from the Stripe Dashboard comes off the order it was paid back on. The two sums read `payment`, so their query left-joins it on `order.payment_id`. Revenue, orders and the average come from the same `salesTotalsQuery`, so the average is always the revenue divided by the orders.

**Page views come from the audit log**, written by `trackPageViewed` in `src/modules/customer-activity`. Because that tracker only fires for signed-in users and de-duplicates per session via `sessionStorage`, the figure is "unique pages viewed by logged-in customers", not total traffic.

`buildAdminDashboardKpiStat(current, previous)` computes the `trendPercent` with `ADMIN_DASHBOARD_TREND_PERCENT_SCALE = 100`.

## Charts

Days, months and years on the dashboard are the shop's, in Polish time (`DEFAULT_TIMEZONE_CODE`, `Europe/Warsaw`, from `src/modules/_core/constants/timezone.ts`), not UTC, which is the only time D1 and the Worker know. An order placed at 00:30 on 1 January in Poland, still 31 December in UTC, counts towards the new day, month and year, and a day is 23 or 25 hours long when the clocks change.

`resolveAdminDashboardDays(now, count)` and `resolveAdminDashboardMonths(now, count)` (`admin-dashboard.utils.ts`) build a chart window: the last `count` days or months up to the one it is in Poland now, each as `{ key, start }` with an ISO key (`2026-06-15` or `2026-06`) and the moment it starts at midnight in Warsaw, plus the window's `start` and its exclusive `end`. The starts come from `startOfCalendarDate` in `src/modules/_core/utils/datetime.ts`. `orderAggregatesQuery(window)` counts the sales and sums their revenue net of refunds from `start` until `end`, grouped with `calendarPeriodKey` from `drizzle.utils.ts`, which gives each order the key of the last period that started at or before it. `buildAdminDashboardChartPoints` turns the window's periods into one point each, zero where no order fell, labelled from the period's start in Warsaw with `ADMIN_DASHBOARD_DAY_LABEL_FORMAT` or `ADMIN_DASHBOARD_MONTH_LABEL_FORMAT` in the requested locale.

Three series are precomputed in the same snapshot:

- `chartPoints30d` — `orderAggregatesQuery` over `resolveAdminDashboardDays(now, ADMIN_DASHBOARD_CHART_DAYS_30)`, with `ADMIN_DASHBOARD_CHART_DAYS_30 = 30`
- `chartPoints7d` — `chartPoints30d.slice(-7)`, so no extra query
- `chartPoints1y` — `orderAggregatesQuery` over `resolveAdminDashboardMonths(now, ADMIN_DASHBOARD_CHART_MONTHS_1Y)`, with `ADMIN_DASHBOARD_CHART_MONTHS_1Y = 12`

`yearToDateRevenueMinorUnits` is the revenue of a separate `salesTotalsQuery(resolveAdminDashboardYearStart(now))`, from midnight on 1 January in Poland. The KPI comparison above stays a rolling window of 30 times 24 hours back from now.

A custom range is a second server function. `getDashboardChartRange` takes `{ startDate, endDate, locale }` as ISO dates, returns `[]` when `isAdminDashboardCustomChartRangeValid` rejects the pair, and otherwise builds the window of every day from `startDate` to `endDate` with `resolveAdminDashboardDateRange`, from midnight in Poland on the first day until midnight after the last, and runs `orderAggregatesQuery` over it. Its query is `enabled` only for a valid range. The controls are `dashboard/components/dashboard-chart-range-controls.tsx` driven by `dashboard/hooks/use-dashboard-chart-range.ts`, using `react-day-picker`.

## Stat cards

`dashboard-stats.tsx` renders four cards from a local `STAT_CARDS` constant keyed `revenue`, `orders`, `customers` and `views`, each with a lucide icon and a Tailwind gradient. Labels come from `pages.admin.dashboard.stats.<key>.label` and the comparison caption from `dashboard.stats.vsPrevious`. `dashboard/dashboard-trend-badge.tsx` renders the up/down badge.

## Recent orders

`recentOrdersQuery` selects the latest `ADMIN_DASHBOARD_RECENT_ORDERS_LIMIT = 5` orders, left-joining `user` for the customer name and `payment` for the status, and the snapshot maps each row through `toAdminOrderListItem` — the same mapper the orders grid uses, so the badges match. Note it passes `itemCount: 0`, so the recent-orders list never shows an item count. It also selects the order's `metadata`, from which the mapper sets `hasOpenDispute`; the dashboard shows no dispute.

## Top products

`topProductsQuery` groups `order_item` by `product_id`:

```ts
.from(orderItem)
.innerJoin(order, eq(orderItem.orderId, order.id))
.leftJoin(product, eq(product.id, orderItem.productId))
.leftJoin(categoryOnProduct, and(eq(categoryOnProduct.productId, orderItem.productId), eq(categoryOnProduct.isPrimary, true)))
.leftJoin(productCategory, eq(productCategory.id, categoryOnProduct.categoryId))
.where(orderCountsAsSale)
.groupBy(orderItem.productId)
```

and the snapshot drops rows with a null id, which only lines whose variant was gone before their product was recorded have: lines written before the backfill below whose variant had since been deleted, and lines whose variant was deleted while the customer paid:

```ts
const validTopProductRows = topProductRows.filter((row): row is typeof row & { productId: string } => row.productId !== null)
```

`prepareFulfillCheckoutBatch` (`src/modules/checkout/checkout.utils.ts`) records each line's product and variant by looking them up through the line's variant in the same insert, and the migration `20261003120000_order_item_product_backfill.sql` filled in the lines written before that whose variant still existed. The thumbnail is read with `max(...)` from the grouped lines.

`ADMIN_DASHBOARD_TOP_PRODUCTS_LIMIT` is 4. `resolveTopProductName` and `resolveTopProductCategoryLabel` pick the locale out of the JSON title maps, falling back to the stored `order_item.title`.

## Weekly orders

`buildAdminDashboardWeeklyOrderPoints` reuses the same `dailyAggregateRows` with the last seven days of the 30-day window to produce `{ dateKey, dayLabel, orders }` points, the weekday named as it is in Poland, again with no extra query.

| Route                  | File                        | Components                                                                                | Data                                                                                                             |
| ---------------------- | --------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `/admin/marketing`     | `admin.marketing.index.tsx` | `NewsletterStats`, `NewsletterCampaignsTable`                                             | `getNewsletterStatsQuery`, `getAdminNewsletterCampaignsQuery`; see [E-mail](/docs/features/email#the-newsletter) |
| `/admin/marketing/new` | `admin.marketing.new.tsx`   | `NewsletterComposer` with `NewsletterComposerFields` and `NewsletterSendDialog`           | `getNewsletterStatsQuery`, `sendNewsletterTest`, `sendNewsletterCampaign`                                        |
| `/admin/coupons`       | `admin.coupons.tsx`         | `CouponStats`, `CouponListTable` with `CouponFormDialog`                                  | `getAdminDiscountsPageQuery`, `getDiscountStatsQuery`; see [Discounts](/docs/features/discounts)                 |
| `/admin/settings`      | `admin.settings.tsx`        | `SettingsPage` with `settings-tabs.tsx`, `settings-general/*`, `settings-placeholder.tsx` | `src/data/settings.ts` (`SETTINGS_TAB_DEFINITIONS`, `STORE_INFO_DEFAULTS`, `TOGGLE_SETTING_KEYS`)                |

Marketing is the newsletter. Its page shows how many subscribers are confirmed, awaiting confirmation and unsubscribed, and lists the 50 most recent newsletters with their progress, refreshed by the admin realtime hub as batches go out. **New newsletter** opens the composer, where the owner writes the letter in Polish and English in the content editor, sends a test to their own address and sends it to every confirmed subscriber; [E-mail](/docs/features/email#the-newsletter) describes the sending.

Settings has no loader, query or mutation. The settings screen's General tab renders `STORE_INFO_DEFAULTS` into inputs and `TOGGLE_SETTING_KEYS` into switches that hold local state only, so its maintenance switch does nothing; sales are paused from the [Sales switch](#sales-switch) on the overview. The other tabs render `settings-placeholder.tsx`.

Coupons is a working screen: its loader prefetches `getAdminDiscountsPageQuery({})` and `getDiscountStatsQuery()`, and `use-coupon-actions.ts` calls `createDiscount`, `updateDiscount` and `deleteDiscounts`.

`/admin/orders/$orderId` is a working screen that loads one order through `getAdminOrder`. See [Orders](/docs/features/orders).

Content is a working screen that edits the legal pages and the FAQ. See [Legal pages](/docs/features/legal-pages).
