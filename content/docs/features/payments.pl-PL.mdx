Stripe jest jedynym dostawcą płatności. Nie ma innego adaptera, a `payment.provider` jest typowany jako literał `"stripe"`.

## Klienci

| Plik                                           | Czym jest                                                                                                                                               |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/integrations/stripe/stripe.server.ts`     | serwerowe SDK: `new StripeServer(env.STRIPE_SECRET_KEY, { apiVersion, appInfo: { name: APP_NAME }, httpClient: StripeServer.createFetchHttpClient() })` |
| `src/integrations/stripe/stripe.client.ts`     | `getStripe(locale)` — zapamiętane `loadStripe(import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY)`                                                             |
| `src/integrations/stripe/stripe.appearance.ts` | `getStripeAppearance("light" \| "dark")` dla motywu Elements                                                                                            |

`createFetchHttpClient()` ma znaczenie: klient HTTP z Node'a nie działa wewnątrz Cloudflare Workera.

Przypięta wersja API leży w `stripe.constants.ts`:

```ts
export const STRIPE_API_VERSION = "2026-08-26.dahlia" as const
```

`getStripe` mapuje język aplikacji na język Stripe Elements (`pl-PL → pl`, `en-US → en`, pozostałe `auto`) i przy braku klucza publicznego ostrzega w konsoli, zamiast rzucać wyjątek — źle skonfigurowane środowisko deweloperskie wciąż się renderuje.

## Waluta i metody

```ts
const STRIPE_CURRENCY_BY_CODE = { PLN: "pln" } as const satisfies Record<SupportedCurrencyCode, string>
export const STRIPE_CURRENCY = STRIPE_CURRENCY_BY_CODE[STORE_CURRENCY_CODE]
export const CHECKOUT_PAYMENT_METHOD_ORDER = ["card", "blik", "p24"] as const
```

`STORE_CURRENCY_CODE` to `"PLN"` (`src/modules/_core/constants/currency.ts`), a `SUPPORTED_CURRENCY_CODES` zawiera tylko `PLN`, więc ograniczenie `satisfies` wymusza dodanie nowej waluty w obu miejscach naraz. BLIK i Przelewy24 to dwie polskie metody oferowane obok kart; portfele i Link są wyłączone w `PAYMENT_ELEMENT_OPTIONS`.

## Sesja

Sesje są tworzone z `ui_mode: "elements"`, co oznacza, że formularz płatności jest wbudowany w `/checkout`, a nie przekierowuje na stronę hostowaną przez Stripe:

```ts
const params: StripeType.Checkout.SessionCreateParams = {
  expires_at: Math.floor(Date.now() / MILLISECONDS_PER_SECOND) + CHECKOUT_SESSION_LIFETIME_SECONDS,
  line_items: toLineItems(lines, { cost: shippingCost, name: messages.deliveryLineItem[deliveryType] }),
  metadata,
  mode: "payment",
  payment_intent_data: { metadata, receipt_email: email },
  return_url: returnUrl,
  ui_mode: "elements",
  ...(customerId === undefined
    ? { customer_email: email }
    : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
}
const discounts = await toSessionDiscounts({ checkoutId, discount })
if (discounts.length > NO_COST) {
  params.discounts = discounts
}

const session = await stripe.checkout.sessions.create(params).catch(async (error: unknown) => {
  await deleteCheckoutCoupons({ checkoutId, discounts })
  throw error
})
```

`expires_at` to `CHECKOUT_SESSION_LIFETIME_SECONDS` (1920 sekund, w `stripe.constants.ts`) od teraz. Stripe przyjmuje od 30 minut do 24 godzin i domyślnie ustawia 24 godziny, a sesja trzyma towar, dopóki nie wygaśnie, więc wartość domyślna pozwalała jednemu porzuconemu albo skryptowemu checkoutowi zabrać sztukę wszystkim innym kupującym na dobę. 32 minuty to minimum Stripe plus zapas na czas trwania żądania i z nawiązką wystarcza na kartę, BLIK albo przelew Przelewy24. Towar zwalnia potem webhook wygaśnięcia (zobacz [Stany magazynowe](/docs/features/inventory)).

`customerId` jest ustawiane tylko dla zalogowanego kupującego. `handleCreateCheckoutSession` (`src/integrations/stripe/stripe.actions.server.ts`) bierze je z `ensureStripeCustomer`, które przy pierwszym użyciu tworzy klienta Stripe i zapisuje jego identyfikator w `user.stripe_customer_id`; `handleUpdateCheckoutSession` odczytuje zapisany identyfikator przez `getStripeCustomerId`, gdy checkout już należy do konta, a wywołuje `ensureStripeCustomer`, gdy przekazuje checkout gościa kontu, na które od tego czasu się zalogowano, co ustawia też `user_id` checkoutu, więc zamówienie trafia na to konto (zobacz [Checkout](/docs/features/checkout)). Taka sesja należy do tego klienta Stripe i pozwala kupującemu zapisać kartę, która potem pojawia się na `/account/payment`. Sesja gościa dostaje zamiast tego `customer_email`. Zalogowany klient może też dodać kartę bezpośrednio na `/account/payment`, bez płacenia, przez SetupIntent na kartę dla tego samego klienta Stripe. Zobacz [Konto](/docs/features/account).

`returnUrl` to `${origin}/checkout?success=true&session_id={CHECKOUT_SESSION_ID}`, z prefiksem `/en-US` dla checkoutu po angielsku, gdzie Stripe wstawia identyfikator sesji, a `origin` pochodzi z `resolveRequestOrigin(getRequest())` w `src/lib/request.ts`. To adres, na który przyszło żądanie checkoutu, sprawdzony z listą hostów obsługiwanych przez ten build, więc checkout lokalny wraca na `localhost` albo `127.0.0.1`, checkout na preview na host preview, a produkcyjny na `martebizuteria.pl`. Stripe używa go dla płatności, która opuszcza stronę, na przykład Przelewy24, niezależnie od tego, czy kupujący zapłacił, dlatego strona najpierw pyta `getCheckoutSessionStatus` o zwróconą sesję i pokazuje potwierdzenie tylko dla sesji `complete`; porzucona płatność wraca na krok płatności z zachowanym koszykiem, a płatność, którą bank wciąż potwierdza, czeka tam na bank (zobacz [Kasa](/docs/features/checkout)). Nagłówki `Origin`, `Referer`, `Host` i `X-Forwarded-*` nie są odczytywane, a żądanie na każdy inny host jest odrzucane z `FORBIDDEN`, zanim zostanie dotknięty klient Stripe, rezerwacja stanu magazynowego czy wiersz checkoutu.

Ten sam obiekt `metadata` jest dołączany do sesji i do payment intentu, więc webhook, który ma tylko intent, wciąż znajdzie checkout. Metadane zawierają `checkoutId`, `discountCode` i `discountTotal` (pusty napis i `"0"`, gdy nie ma rabatu), `locale` (z `getCurrentLocale()`), `userId` (pusty napis dla gościa) i pociętą listę `items0…N`.

Pozycje sesji są budowane z cen zwalidowanych na serwerze, plus pozycja dostawy, gdy metoda dostawy kosztuje więcej niż zero. Ta pozycja ma nazwę w języku kupującego: `createStripeSession` wczytuje teksty `pages.checkout` dla języka checkoutu i bierze `deliveryLineItem.<typ>` dla typu metody, więc na polskim potwierdzeniu płatności pozycja brzmi „Dostawa kurierem” albo „Dostawa do Paczkomatu InPost”, a na angielskim „Courier delivery” albo „InPost Parcel Locker delivery”. Własne pole `name` metody nie jest używane, bo jest zapisane tylko po polsku. Nazwy pozycji pochodzą z `lineTitle`, czyli `"<tytuł produktu> — <tytuł wariantu>"`, chyba że tytuł wariantu jest pusty. Rabat nie jest pozycją: `toSessionDiscounts` (`src/integrations/stripe/stripe.coupons.server.ts`) tworzy jednorazowy kupon Stripe na kwotę wyliczoną przez `resolveCheckoutDiscount`, oznaczony identyfikatorem checkoutu i `source: "marte_checkout"`, a sesja dostaje go w `discounts`. `createStripeSession` usuwa ten kupon od razu, gdy Stripe odmówi utworzenia sesji, a webhook usuwa go, gdy sesja zostanie ukończona lub wygaśnie. Zobacz [Rabaty](/docs/features/discounts).

## Wiersz płatności

`payment` (`src/modules/payment/payment.schema.ts`):

| Kolumna           | Uwagi                                                                        |
| ----------------- | ---------------------------------------------------------------------------- |
| `checkout_id`     | `references(() => checkout.id, { onDelete: "cascade" })`, not null           |
| `amount`          | jednostki podrzędne, not null                                                |
| `currency`        | 3 znaki, domyślnie `"PLN"`                                                   |
| `provider`        | not null; jedyna zapisywana wartość to `"stripe"`                            |
| `transaction_id`  | identyfikator **sesji Checkout** Stripe, z unikalnym indeksem                |
| `status`          | `pending \| succeeded \| failed \| refunded`, domyślnie `pending`            |
| `refunded_amount` | jednostki podrzędne, domyślnie `0`                                           |
| `refunded_at`     | nullowalny znacznik czasu                                                    |
| `reserved_lines`  | JSON `{ qty, variantId }[]` trzymanych przez sesję, not null, domyślnie `[]` |

To, że `transaction_id` trzyma identyfikator sesji, a nie payment intentu, jest powodem, dla którego kilka handlerów webhooka wywołuje `resolveCheckoutSession(paymentIntent)` — funkcja listuje sesje filtrowane po `payment_intent` i bierze pierwszą. Zwrot z panelu potrzebuje odwrotnego odczytu: pobiera sesję, aby znaleźć PaymentIntent, który Stripe może zwrócić (zobacz [Zwroty z panelu](#zwroty-z-panelu)).

Akcesory w `payment.accessors.ts`: `createPendingPayment` (zapisuje zarezerwowane linie), `getPaymentByTransactionId`, `getPaymentContextByTransactionId` (dołącza `email`, `userId`, `status` i `created_at` z checkoutu oraz zwraca własny `status` płatności) oraz `getHeldLinesByTransactionId`, które zwraca `reserved_lines` tylko wtedy, gdy płatność i jej checkout są oba `pending`, i przez które sprawdzenie dostępności koszyka liczy własną rezerwację kupującego. Aktualizacja checkoutu przenosi wiersz na zastępczą sesję przez `supersedeCheckoutSession` w `src/modules/checkout/use-cases/supersede-checkout-session.server.ts`, który przenosi tylko płatność `pending` checkoutu `pending` i aktualizuje kwotę oraz zarezerwowane linie. Metadane Stripe pozostają zapisem, z którego webhooki zwalniają i realizują zamówienie; `reserved_lines` służy tylko do odpowiedzi na pytanie o dostępność bez wywoływania Stripe.

## Punkt końcowy webhooka

`src/routes/api/webhooks.stripe.ts` — handler trasy `POST`, a nie funkcja serwerowa:

```ts
const signature = request.headers.get("stripe-signature")

if (signature === null || !env.STRIPE_WEBHOOK_SECRET) {
  return new Response("Missing signature or webhook secret", { status: HTTP_STATUS.BAD_REQUEST })
}

const event = await verifiedStripeEvent(request, signature, env.STRIPE_WEBHOOK_SECRET)
```

`verifiedStripeEvent` używa `stripe.webhooks.constructEventAsync` — wariant asynchroniczny jest wymagany na Workers, gdzie API kryptograficzne opiera się na obietnicach. Nieudana weryfikacja loguje błąd i zwraca 400.

Zweryfikowane zdarzenie musi też pochodzić z trybu Stripe, w którym działa środowisko. `requiredStripeMode(env.APP_ENV)` ze `stripe.keys.ts`, ta sama reguła, którą kontrola wdrożenia stosuje do kluczy, w `production` przyjmuje tylko zdarzenia live (`livemode: true`), a w każdym innym środowisku, także w `test`, tylko zdarzenia testowe. Zdarzenie z drugiego trybu dotyczy płatności, których to środowisko nigdy nie przyjęło, więc zanim uruchomi się jakikolwiek handler, trasa loguje `[Stripe] Ignoring <tryb> event <id> (<typ>): <APP_ENV> accepts only <tryb> events` i odpowiada `200` z `{ received: true }`, przez co Stripe przestaje je ponawiać. Taki wpis oznacza, że endpoint, który wysłał zdarzenie i którego sekret podpisujący to środowisko trzyma jako `STRIPE_WEBHOOK_SECRET`, działa w drugim trybie.

Typ zdarzenia bez handlera loguje `[Stripe] Safely ignoring unhandled event` i zwraca `200`, więc Stripe nie ponawia zdarzeń, które sklepu nie interesują. Handler, który rzuci wyjątek, zwraca `500`, więc Stripe **ponawia** takie zdarzenie, a trasa w tle przekazuje `notifyShopOfIncident` incydent `stripeWebhookFailed` dla typu zdarzenia, który wysyła e-mail na `RESEND_EMAIL_FROM` najwyżej raz na godzinę na typ; zobacz [Monitorowanie i alerty](/docs/guides/monitoring-and-alerts).

## Osiem obsługiwanych zdarzeń

`webhookHandlers` w `src/integrations/stripe/stripe.webhooks.tsx` (plik `.tsx`, bo buduje elementy e-maili potwierdzenia i nieudanej płatności):

| Zdarzenie                                  | Handler                        | Skutek                                                                        |
| ------------------------------------------ | ------------------------------ | ----------------------------------------------------------------------------- |
| `checkout.session.completed`               | `handleFulfillCheckoutSession` | tworzy zamówienie, potem `deleteCheckoutCoupons` usuwa oznaczony kupon sesji  |
| `checkout.session.async_payment_succeeded` | `handleFulfillCheckoutSession` | to samo, dla BLIK/P24 rozliczanych później                                    |
| `checkout.session.async_payment_failed`    | `handleAsyncPaymentFailed`     | zwalnia rezerwację, ustawia płatność i checkout na `failed`, pisze do klienta |
| `checkout.session.expired`                 | `handleReleaseCheckoutSession` | to samo zwolnienie, potem `deleteCheckoutCoupons` usuwa oznaczony kupon sesji |
| `payment_intent.payment_failed`            | `handlePaymentIntentFailed`    | tylko wpis do audytu i ostrzeżenie w logach — bez zmiany stanu                |
| `charge.refunded`                          | `handleChargeRefunded`         | `refundOrder`, który nie przywraca stanu, potem e-mail o nowym zwrocie        |
| `charge.dispute.created`                   | `handleChargeDisputeCreated`   | `flagOrderDispute`, wpis do audytu, unieważnienie listy zamówień w panelu     |
| `charge.dispute.closed`                    | `handleChargeDisputeClosed`    | przegrany → `refundOrder`; inaczej `clearOrderDispute`                        |

Klucze pochodzą ze `STRIPE_WEBHOOK_EVENTS` w `stripe.constants.ts`, więc ta stała jest listą zdarzeń do zarejestrowania w panelu Stripe.

## Realizacja

`handleFulfillCheckoutSession` najpierw filtruje po statusie płatności:

```ts
const FULFILLABLE_PAYMENT_STATUSES = new Set<StripeType.Checkout.Session["payment_status"]>(["no_payment_required", "paid"])
```

Zdarzenie `checkout.session.completed` z `payment_status: "unpaid"` — normalne dla BLIK i P24 — loguje informację i wraca, a zamówienie powstaje później z `async_payment_succeeded`. Kupon sesji i tak jest usuwany przy `completed`, bo jego usunięcie nie zmienia kwoty, którą Stripe już zastosował do sesji.

Następnie parsuje linie pozycji z metadanych, wywołuje `fulfillCheckout`, a jeśli wróci identyfikator zamówienia:

1. `recordOrderPlacedAudit(orderId, …)` i `recordOrderPaymentCapturedAudit(orderId, …)` ze sformatowaną kwotą.
2. `scheduleAdminOrdersInvalidation()` i `scheduleProductCatalogInvalidation()`.
3. `notifyOrderConfirmed(session, orderId)` i `notifyShopOfNewOrder(orderId, session.return_url)`, uruchomione obok siebie w jednym `Promise.all`. Każde zapisuje swój wynik przy zamówieniu i nigdy nie rzuca wyjątku, więc odrzucony e-mail nie zmienia odpowiedzi webhooka z 200, a po odpowiedzi webhooka jest wysyłany jeszcze dwa razy. Ich linki używają originu `session.return_url`, czyli adresu, na którym złożono zamówienie, a `resolveDeploymentOrigin` akceptuje go tylko na hoście obsługiwanym przez któreś wdrożenie. Obietnica trafia do `scheduleBackgroundWork`, zanim handler na nią poczeka, więc oba e-maile kończą się nawet wtedy, gdy Stripe przestanie czekać. Powiadomienie sklepu trafia na `RESEND_EMAIL_FROM`; zobacz [E-maile transakcyjne](/docs/features/email#e-mail-sklepu-o-nowym-zamówieniu).

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) rozwiązuje oczekujący checkout po identyfikatorze transakcji, wczytuje metodę dostawy i rabat checkoutu, wylicza kwoty i uruchamia jeden wsad D1 zbudowany przez `prepareFulfillCheckoutBatch`:

```ts
statements: [
  db.update(payment).set({ status: "succeeded" }).where(eq(payment.transactionId, transactionId)),
  db
    .update(checkout)
    .set({ status: "completed" })
    .where(and(eq(checkout.id, context.checkoutId), eq(checkout.status, "pending"))),
  orderNumberAllocation.statement, // podbija licznik bieżącego roku w order_number_sequence
  db.insert(order).values({ /* …, */ orderNumber: orderNumberAllocation.orderNumber }),
  ...(addressSnapshots.length > 0 ? [db.insert(orderAddress).values(addressSnapshots)] : []),
  ...tail, // insert do orderItem + jedna aktualizacja inventory na linię
]
```

Aktualizacja `checkout` jest warunkowana przez `status = "pending"`, co czyni cały webhook **idempotentnym**: ponownie dostarczone zdarzenie znajduje checkout już w stanie `completed`, `resolvePendingCheckout` zwraca `undefined`, a `fulfillCheckout` wraca bez żadnego zapisu.

Numer zamówienia pochodzi z `prepareOrderNumberAllocation` (`src/modules/order/order.number.server.ts`): jedna instrukcja podbija licznik bieżącego roku w Polsce w `order_number_sequence`, a insert zamówienia odczytuje numer podzapytaniem w formacie `MRT-<rok>-<pięć cyfr>`. Obie są we wsadzie, więc dostawa, której wsad się nie powiedzie, cofa licznik razem ze wszystkim innym, a ponowienie dostaje ten sam numer zamiast zostawiać lukę.

Każda pozycja zamówienia zachowuje to, za co klient zapłacił: tytuł, cena, ilość i zdjęcie pochodzą z metadanych sesji. Jej `variant_id` i `product_id` są wyszukiwane w tym samym insercie (`select id from product_variant where id = …`), więc wariant albo produkt usunięty w czasie, gdy klient płacił, zostawia oba pola puste (`null`) zamiast naruszać klucz obcy `order_item.variant_id`, a zamówienie i tak powstaje. Administrator zwykle w ogóle nie może usunąć takiego wariantu (zobacz [Panel katalogu](/docs/features/admin-catalog)); wyszukiwanie obsługuje checkout otwarty w chwili między tym sprawdzeniem a usunięciem. Realizacja nie czyta też `product.status`, więc sesja opłacona, zanim produkt zarchiwizowano albo przywrócono do szkicu, albo taka, której Stripe nie wygasił, gdy ten zapis próbował ją zamknąć, nadal staje się pozycją zamówienia powiązaną z produktem. Każdą inną otwartą sesję trzymającą produkt ten zapis wygasza (zobacz [Panel katalogu](/docs/features/admin-catalog#zapis)), a nieopublikowany produkt odrzucają nowe i edytowane checkouty (zobacz [Kasa](/docs/features/checkout)).

**Gdy opłacona sesja nie tworzy zamówienia**, `handleFulfillCheckoutSession` loguje błąd i zapisuje `order.fulfillment_failed` przez `recordOrderFulfillmentFailedAudit` z poziomem `error`, więc wpis widać w dzienniku audytu w panelu i w liczniku błędów. Celem wpisu jest identyfikator sesji, a szczegóły mają postać `<kwota> — <e-mail klienta> — <przyczyna>`. Błąd z kodu albo z bazy, w tym metadane, których nie da się sparsować, jest następnie rzucany dalej, trasa odpowiada `500`, a Stripe ponawia zdarzenie. `resolvePendingCheckout` rzuca `ERROR_CODES.NOT_FOUND`, gdy żaden wiersz płatności nie ma tej sesji, gdy jej checkout już nie istnieje albo gdy checkout jest w innym stanie niż `pending` lub `completed` (na przykład `failed` po zwolnieniu). Ponowienie tego nie zmieni, więc po zapisaniu wpisu handler uruchamia w tle alert `paidCheckoutWithoutOrder` dla tej sesji na `RESEND_EMAIL_FROM`, odpowiada `200`, a administrator zwraca klientowi pieniądze w Stripe.

Kwoty zamówienia są wyliczane, a nie brane od klienta: `itemsSubtotal` to suma `price * qty` po liniach z metadanych, `shippingTotal` to cena metody dostawy checkoutu, a rabat jest ponownie wyliczany przez `calculateDiscountAmount` z wiersza `discount` checkoutu. `computeOrderTotals` (`src/modules/order/order.totals.ts`) ogranicza rabat do sumy pozycji i dostawy oraz wylicza `total` i `taxTotal`. `reconcileTotals` porównuje tę sumę z `session.amount_total`, przekazanym jako `paidAmount`, i gdy się różnią, jedynie loguje błąd.

Ten sam wsad przekształca rezerwację kodu rabatowego checkoutu: `prepareDiscountRedemption` usuwa wiersze `discount_claim` checkoutu, a gdy zamówienie ma rabat, zapisuje wiersz `discount_redemption` i zwiększa `discount.usage_count`, nie sprawdzając żadnego limitu, bo klient już zapłacił. Zamówienie i jego wykorzystanie zatwierdzają się więc razem, a drugie dostarczenie, które przepada na `order.checkout_id`, niczego nie liczy. Zobacz [Rabaty](/docs/features/discounts#przy-realizacji).

Rezerwacja jest przekształcana, a nie zwalniana: każda linia wykonuje `quantityReserved = quantityReserved - qty`, zostawiając `quantityAvailable` w stanie po rezerwacji. Zobacz [Stany magazynowe](/docs/features/inventory).

## Zwolnienie

`releaseCheckout` uruchamia `prepareReleaseCheckoutBatch` bez wcześniejszego odczytu. Wsad zwraca stan magazynowy, usuwa wiersze `discount_claim` checkoutu, żeby trzymane przez niego wykorzystanie kodu znów było wolne, potem ustawia checkout na `failed`, a na końcu płatność:

```ts
db.update(inventory)
  .set({
    quantityAvailable: sql`${inventory.quantityAvailable} + min(${inventory.quantityReserved}, ${line.qty})`,
    quantityReserved: sql`max(0, ${inventory.quantityReserved} - ${line.qty})`,
  })
  .where(and(eq(inventory.variantId, line.variantId), exists(releasableSession)))
```

`releasableSession` wybiera checkout płatności z tym `transaction_id` i `status = "pending"`, złączonej z tym checkoutem, dopóki ten jest nadal `pending`; aktualizacje stanu wymagają, żeby istniał, a usuwanie rezerwacji ogranicza się do jego checkoutu. Aktualizacja checkoutu wymaga tej samej oczekującej płatności, a aktualizacja płatności wymaga, żeby jej checkout był już `failed`. Każda instrukcja widzi wynik poprzednich w tym samym wsadzie D1, więc stan wraca tylko, dopóki oba wiersze są `pending`, i wsad działa w całości albo wcale. Ponownie dostarczone zdarzenie, dwa dostarczenia obsługiwane równolegle i webhook wygaśnięcia sesji, którą aktualizacja checkoutu już zastąpiła (`supersedeCheckoutSession` przeniósł z niej płatność), nie znajdują nic do zwolnienia.

Aktualizacja płatności zwraca identyfikator płatności, którą ustawiła na `failed`, a `releaseCheckout` zwraca, czy taka była. `handleAsyncPaymentFailed` wysyła klientowi e-mail o nieudanej płatności tylko wtedy, więc e-mail wychodzi raz na nieudaną płatność, niezależnie od tego, co Stripe dostarczy ponownie; zobacz [E-maile transakcyjne](/docs/features/email#anulowanie-zwrot-i-nieudana-płatność). Wygasła sesja jest zwalniana tak samo i nikomu nie wysyła e-maila.

Ograniczenia `min`/`max` sprawiają, że podwójne zwolnienie nie może zawyżyć dostępnego stanu powyżej tego, co faktycznie zarezerwowano.

Linie do zwolnienia są parsowane przez `checkoutReleaseLinesSchema`, które jest `.loose()` — przyjmuje pełny kształt linii realizacji i wymaga tylko `variantId` oraz `qty`.

## Zwroty i spory

`handleChargeRefunded` rozwiązuje sesję z payment intentu obciążenia i wywołuje `refundOrder({ fullyRefunded: charge.amount_refunded >= charge.amount, refundedAmount: charge.amount_refunded, transactionId })`.

`refundOrder` (`src/modules/order/use-cases/refund-order.ts`) **nie** jest funkcją serwerową — to zwykła funkcja asynchroniczna wywoływana wyłącznie z webhooka. Wraca wcześnie, gdy płatność ma już status `refunded`, więc ponownie dostarczony pełny zwrot nic nie robi. Nigdy nie przywraca stanu magazynowego. Zwrot pieniędzy nie mówi, czy towar wrócił: zwrot za przesyłkę zagubioną przez przewoźnika, zwrot z dobrej woli i przegrany spór zostawiają egzemplarz u klienta albo nigdzie, a wystawienie unikatowego egzemplarza z powrotem na sprzedaż sprzedałoby coś, czego sklep nie ma. Administrator przywraca produkty zamówienia na stan w oknie zwrotu albo później przyciskiem Przywróć na stan (zobacz [Zamówienia](/docs/features/orders#akcje-w-panelu)).

`prepareRefundBatch` zapisuje `refundedAmount`, `refundedAt` i `status` (`refunded` przy pełnym zwrocie, w przeciwnym razie `succeeded`), i to tylko w płatności, która nie ma jeszcze statusu `refunded`: zdarzenie starszego, częściowego zwrotu, które `refundOrder` odczytało przed zapisaniem pełnego zwrotu, a którego wsad dociera po nim, zostawia płatność jako `refunded`, z jej kwotą i czasem zwrotu. `refundedAmount` staje się większą z kwot: zapisanej i tej ze zdarzenia, przez `max()` SQLite, więc tylko rośnie. Przy pełnym zwrocie płatności, która ma zamówienie, ustawia potem zamówienie na `refunded`, dopóki jego status nie jest ani `cancelled`, ani `refunded`, więc anulowane zamówienie zachowuje status `cancelled`, a `refunded` dostaje tylko jego płatność. Nie rusza `order.restocked_at`, więc zwrócone zamówienie, którego produkty nie wróciły na stan, ma na swojej stronie w panelu tag „Nie wróciło na stan” i przycisk Przywróć na stan, dopóki administrator nie zdecyduje. Ponieważ nic w sprzedaży się nie zmienia, handler odświeża listy zamówień w panelu, ale nie katalog.

Wsad zaczyna się od odczytu `refunded_amount` i statusu płatności oraz statusu jej zamówienia, który biegnie w tej samej transakcji D1 przed zapisami. Gdy ten odczyt zastaje płatność już jako `refunded`, inne zdarzenie zapisało pełny zwrot po sprawdzeniu w `refundOrder`, więc wsad niczego nie zmienił, a `refundOrder` niczego nie zwraca i nie zapisuje wpisu audytu. W przeciwnym razie `refundOrder` zwraca zwrot, o którym klient jeszcze nie wie, `{ amount, fullyRefunded, orderId }`, gdzie `amount` to `amount_refunded` płatności pomniejszone o to, co płatność miała zapisane, tylko wtedy, gdy jest większe od zera, a zamówienie nie było `cancelled`; anulowanie samo już napisało klientowi o swoim zwrocie. `handleChargeRefunded` przekazuje go do `notifyOrderRefunded` razem z `return_url` sesji, więc każdy zwrot, częściowy czy pełny, trafia do klienta e-mailem raz, niezależnie od tego, jak często i w jakiej kolejności Stripe dostarcza swoje zdarzenia: starsze zdarzenie dostarczone po nowszym zostawia większą kwotę, więc ponowne dostarczenie nowszego nie znajduje niczego nowego. Przegrany spór także wywołuje `refundOrder`, ale nie wysyła e-maila.

Spory są zapisywane w `order.metadata`, a nie w kolumnach: `flagOrderDispute` scala `{ id, reason, status, amount }` do JSON-a przez `mergeDisputeMetadata` (`order.display.utils.ts`). Przegrany spór jest traktowany jak pełny zwrot i loguje `review inventory manually` — towar zwykle przepadł, więc stan nie jest przywracany, a strona zamówienia oferuje Przywróć na stan, gdyby jednak wrócił. `clearOrderDispute` usuwa flagę, gdy spór zamyka się w inny sposób, a dopóki flaga istnieje, zwrot z panelu jest odrzucany, tak samo jak anulowanie opłaconego zamówienia, które by go zwróciło (zobacz [Zwroty z panelu](#zwroty-z-panelu)). `resolveAdminOrderDispute`, obok `mergeDisputeMetadata` w `order.display.utils.ts`, odczytuje tę flagę dla listy zamówień, strony zamówienia i zwrotu.

```bash
bun run stripe:listen
```

uruchamia `stripe listen --latest --forward-to localhost:3000/api/webhooks/stripe`. Sekret podpisu, który ta komenda wypisze, wstaw do `STRIPE_WEBHOOK_SECRET`.

## Sekrety

`STRIPE_SECRET_KEY` i `STRIPE_WEBHOOK_SECRET` są zadeklarowane na liście `secrets.required` każdego środowiska w `wrangler.jsonc`. `VITE_STRIPE_PUBLISHABLE_KEY` jest zmienną przeglądarki i musi być dostępna w czasie budowania, bo Vite wstawia ją do pakietu.

## Zwroty z panelu

`/admin/orders/$orderId` wczytuje zamówienie przez `getAdminOrderQuery`, a jego nagłówek pokazuje Drukuj podsumowanie, Zwrot, Przywróć na stan, Anuluj zamówienie, Realizuj, Oznacz jako wysłane i Oznacz jako dostarczone, o ile dana akcja ma zastosowanie; pozycja Zwrot w menu wiersza na `/admin/orders` otwiera tę stronę. Zwrot prosi o potwierdzenie w `order-refund-dialog.tsx`, które pyta też, czy produkty wróciły na stan. Pole jest na początku zaznaczone dla zamówienia, które nie zostało wysłane, i puste dla zamówienia `shipped` albo `delivered` (`refundRestocksByDefault`). Okno wywołuje `refundAdminOrder` (`src/modules/order/use-cases/refund-admin-order.ts`) z odpowiedzią jako `restock`, funkcję serwerową zabezpieczoną przez `authorized({ order: ["update"] })`. Sprawdza ona `canRefundAdminOrder` z `order.admin-actions.utils.ts` (opłacone, ani zwrócone, ani anulowane), a potem `resolveAdminOrderRefundBlocker` z tego samego pliku, które nazywa powód, dla którego Stripe nie może zwrócić płatności za zamówienie:

| Blokada           | Kiedy                                                                | Dlaczego                                                                                                                    |
| ----------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `noStripePayment` | `order.total` wynosi 0                                               | Bezpłatny checkout kończy się jako `no_payment_required`, więc Stripe nie pobrał płatności i nie ma PaymentIntent do zwrotu |
| `openDispute`     | `order.metadata` zawiera `dispute` zapisane przez `flagOrderDispute` | O losie płatności decyduje spór, dopóki `clearOrderDispute` nie usunie flagi                                                |

Wymaga też `transaction_id` w wierszu płatności. Ta kolumna trzyma opisany wyżej identyfikator sesji Checkout, którego Stripe nie przyjmuje jako `payment_intent`, więc funkcja pobiera sesję przez `stripe.checkout.sessions.retrieve(transactionId)` i odczytuje jej `payment_intent` przez `resolveStripeObjectId` (`src/integrations/stripe/stripe.utils.ts`), które zwraca identyfikator niezależnie od tego, czy Stripe przysłał go jako tekst, czy jako rozwinięty obiekt. Sesja z `payment_status` równym `no_payment_required` albo bez PaymentIntent również jest odrzucana. W przeciwnym razie funkcja wywołuje:

```ts
await stripe.refunds.create({ metadata: { orderId }, payment_intent: paymentIntentId }, { idempotencyKey: `admin-order-refund-${orderId}` })
```

co zwraca całą kwotę. Klucz idempotencji jest taki sam dla każdego żądania dotyczącego jednego zamówienia, więc podwójne kliknięcie, druga karta albo drugi administrator wysyłają do Stripe żądanie, które Stripe już zna, a Stripe odpowiada pierwszym wynikiem albo odrzuca powtórzenie, dopóki pierwsze żądanie wciąż trwa, zamiast próbować kolejnego zwrotu. Stripe przechowuje wynik dla klucza, łącznie z błędami, przez co najmniej 24 godziny, więc ponowienie zwrotu, który Stripe odrzucił, zwraca ten sam błąd, dopóki klucz nie wygaśnie.

Brak zamówienia rzuca `ERROR_CODES.NOT_FOUND` z `ORDER_NOT_FOUND`. Zwrot odrzucony z powodu otwartego sporu rzuca `ERROR_CODES.CONFLICT` z `ORDER_OPEN_DISPUTE`, a każdy inny odrzucony zwrot rzuca `ERROR_CODES.CONFLICT` z `ORDER_INVALID_STATE`; żaden nie zleca zwrotu w Stripe. Te sprawdzenia działają na serwerze przy każdym wywołaniu, niezależnie od tego, co pokazuje strona. Toast błędu w panelu nazywa spór przy `ORDER_OPEN_DISPUTE`, które dociera do niego, gdy spór otworzył się już po wczytaniu strony, a przy każdym innym konflikcie mówi, że akcja nie jest dostępna w bieżącym stanie zamówienia.

Strona uruchamia te same predykaty na wczytanym zamówieniu. Zwrot pojawia się, gdy pozwala na to `canRefundAdminOrder`. Gdy `resolveAdminOrderRefundBlocker` zwraca blokadę, `order-action-button.tsx` pozostawia przycisk widoczny, ale wyłączony i nadal osiągalny klawiaturą, a jego podpowiedź wyjaśnia blokadę komunikatami z `pages.admin.orderDetail.refundBlocked`. Anuluj zamówienie zwraca pieniądze za opłacone zamówienie, więc dostaje to samo od `resolveAdminOrderCancelBlocker`, które zwraca `openDispute` dla otwartego sporu na zamówieniu, które `cancelRefundsAdminOrderPayment` by zwróciło, z komunikatami z `pages.admin.orderDetail.cancelBlocked`; w menu wiersza na `/admin/orders` pozycja Anuluj zamówienie jest wyłączona, a pod nią widać powód z `pages.admin.orders.rowActions.cancelBlocked`.

`refundAdminOrder` niczego nie zapisuje o płatności. Statusy płatności i zamówienia, wpis audytu zwrotu i e-mail o zwrocie do klienta przychodzą z wynikowym zdarzeniem `charge.refunded`, tą samą ścieżką `refundOrder` co zwrot wykonany w panelu Stripe. O stanie magazynowym decyduje administrator: przy `restock` równym true, gdy Stripe przyjmie zwrot, `returnOrderToStock` (`src/modules/order/order.restock.server.ts`) przywraca na stan każdą pozycję, której wariant nadal istnieje, i ustawia `order.restocked_at` w jednym wsadzie strzeżonym warunkiem, że ta kolumna jest pusta, a zamówienie nie jest `cancelled`, zapisuje `order.restocked` i odświeża katalog. Zwrot odrzucony przez Stripe niczego nie przywraca, a powtórzone żądanie nie przywraca niczego więcej. Sprawdzenia blokady, `transaction_id` i sesji oraz wywołanie `stripe.refunds.create` leżą w `requestFullOrderRefund` (`src/modules/order/order.refund.server.ts`), które wywołuje też Anuluj zamówienie dla opłaconego zamówienia przed jego anulowaniem, z tym samym kluczem idempotencji, więc Zwrot i Anulowanie jednego zamówienia również nie zwrócą za nie pieniędzy dwa razy. Zwraca `amount` zwrotu utworzonego w Stripe, które podaje e-mail o anulowaniu. Obie akcje wymagają uprawnienia `order: ["refund"]` z `auth.access.ts` oprócz `order: ["update"]`: `refundAdminOrder` żąda obu w swoim middleware `authorized`, a Anuluj zamówienie żąda `order: ["refund"]`, gdy po odczytaniu zamówienia znajdzie płatność do zwrotu, zanim wywoła Stripe albo cokolwiek zmieni. Rola bez tego uprawnienia dostaje `FORBIDDEN`; rola administratora je ma.
