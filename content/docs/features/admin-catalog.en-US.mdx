## Route shape

`/admin/catalog` is a pass-through layout (`src/routes/admin.catalog.tsx`) that only declares the namespaces `pages.admin.catalog` and `pages.admin.catalog.localePicker`, and `/admin/catalog/` redirects to `ROUTES.ADMIN_PRODUCTS`.

Four tabs, rendered by `catalog/catalog-tabs.tsx` from `ROUTES.ADMIN_CATALOG`, `ADMIN_CATEGORIES`, `ADMIN_COLLECTIONS` and `ADMIN_ATTRIBUTES`:

| Tab         | Path                         | Index route                           | Module                           |
| ----------- | ---------------------------- | ------------------------------------- | -------------------------------- |
| Products    | `/admin/catalog/products`    | `admin.catalog.products.index.tsx`    | `src/modules/product`            |
| Categories  | `/admin/catalog/categories`  | `admin.catalog.categories.index.tsx`  | `src/modules/product-category`   |
| Collections | `/admin/catalog/collections` | `admin.catalog.collections.index.tsx` | `src/modules/product-collection` |
| Attributes  | `/admin/catalog/attributes`  | `admin.catalog.attributes.index.tsx`  | `src/modules/product-attribute`  |

`admin.catalog.categories.$handle.tsx` and `admin.catalog.collections.$handle.tsx` render no page: their `beforeLoad` redirects `/admin/catalog/categories/<handle>` and `/admin/catalog/collections/<handle>` to the tab's list. Categories and collections, like products and attributes, are created and edited in a sheet over their list.

The products route loader prefetches five queries in parallel, because the editor needs the pick lists:

```ts
await Promise.all([
  context.queryClient.query({ ...getAdminProductsQuery(), staleTime: "static" }),
  context.queryClient.query({ ...getProductStatsQuery(), staleTime: "static" }),
  context.queryClient.query({ ...getAdminCategoriesQuery(), staleTime: "static" }),
  context.queryClient.query({ ...getAdminCollectionsQuery(), staleTime: "static" }),
  context.queryClient.query({ ...getAdminProductAttributesQuery(), staleTime: "static" }),
])
```

## Tables

The catalog is fourteen tables. All the title-like columns are **JSON locale maps**, not plain text: `titles`, `subtitles`, `short_descriptions`, `descriptions`, `tags`, `labels`.

| Table                   | Key columns                                                                                                                                                                               |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `product`               | `handle` (unique), `titles`, `subtitles`, `descriptions`, `tags`, `thumbnail`, `status`, `rank`, `primary_category_id`, `metadata`                                                        |
| `product_variant`       | `product_id`, `title`, `sku` (unique), `barcode`, `price`, `compare_at_price`, `manage_inventory`                                                                                         |
| `inventory`             | `variant_id` (unique), `quantity_available`, `quantity_reserved`                                                                                                                          |
| `price_history`         | `variant_id`, `price`, `compare_at_price`, `changed_at`; one row per price change, written by triggers on `product_variant`                                                               |
| `product_image`         | `product_id`, `variant_id` (nullable), `url`, `alt`, `rank`                                                                                                                               |
| `product_option`        | `product_id`, `titles`                                                                                                                                                                    |
| `product_option_value`  | `option_id`, `labels`, `rank`                                                                                                                                                             |
| `option_on_variant`     | `variant_id`, `option_id`, `value_id`; unique on (`variant_id`, `option_id`)                                                                                                              |
| `product_category`      | `handle` (unique), `parent_id` (self-reference), `titles`, `subtitles`, `short_descriptions`, `descriptions`, `image`, `status`, `rank`                                                   |
| `product_collection`    | `handle` (unique), `titles`, `short_descriptions`, `descriptions`, `image`, `status`, `rank`                                                                                              |
| `product_attribute`     | `handle` (unique), `titles`, `type`, `unit`, `allowed_values` (JSON), `rank`                                                                                                              |
| `attribute_on_product`  | `product_id`, `attribute_id`, `variant_id` (nullable; set for a value that belongs to one variant), `value`, `rank`; unique on (`product_id`, `attribute_id`, `coalesce(variant_id, '')`) |
| `category_on_product`   | `product_id`, `category_id`, `is_primary`; primary key (`product_id`, `category_id`)                                                                                                      |
| `collection_on_product` | `product_id`, `collection_id`, `rank`; primary key (`product_id`, `collection_id`)                                                                                                        |

The editor's primary category and its additional categories become `category_on_product` rows, the primary one with `is_primary`, and `prepareProductOrganizationBatch` copies the primary one to `product.primary_category_id` in the same batch.

`product.status` is `draft | published | archived` with `DEFAULT_PRODUCT_STATUS = draft`. Only a `published` product is on sale. Archiving a product or returning it to draft keeps its stock, but the storefront and search stop listing it, a basket that already holds it marks the line as no longer available, and checkout refuses it with `PRODUCT_NOT_FOUND`. The same save closes the checkouts customers had already opened for it and puts the stock they held back (see [Writing](#writing)); a session the customer already paid still becomes an order (see [Cart](/docs/features/cart) and [Payments](/docs/features/payments)). Categories and collections use a different two-value status, `draft | active`, also defaulting to `draft`.

Handles are validated against the same pattern in each module, for example `PRODUCT_HANDLE_PATTERN = /^[a-z0-9]+(?:-[a-z0-9]+)*$/u`.

## Products

### Reading

| Use case                     | Permission          | Returns                                               |
| ---------------------------- | ------------------- | ----------------------------------------------------- |
| `get-admin-products-page.ts` | `product: ["read"]` | Paginated rows, `ADMIN_PRODUCTS_PAGE_SIZE = 25`       |
| `get-admin-products.ts`      | `product: ["read"]` | The unpaginated list the grid boots from              |
| `get-admin-product.ts`       | `product: ["read"]` | One product with everything the editor needs          |
| `get-product-stats.ts`       | `product: ["read"]` | The stat cards, including the low-stock count         |
| `export-admin-products.ts`   | `product: ["read"]` | Every matching row, for the export                    |
| `validate-product-skus.ts`   | `product: ["read"]` | `{ takenSkus }` from `findTakenSkus(skus, productId)` |

With no toolbar filter, search term or column filter, the grid shows the whole list from `getAdminProducts` (`getAdminProductsCatalogList` in `use-cases/list-admin-products.server.ts`) on one page, sorts it in the browser, and lets rows be dragged into a new order while it is unsorted. Any filter, search term or column filter switches it to `getAdminProductsPage`, 25 rows a page, filtered and sorted on the server, and dragging is off.

The browser turns the column filters and the sort into request parameters with `parseAdminProductsListColumnFilters` and `parseAdminProductsListSort` (`product.utils.ts`). `getAdminProductsPage` resolves the admin's time zone with `resolveRequestDisplayPreferences()` and passes it on with the filters through `buildAdminProductsFilterParams`. `queryAdminProducts` builds the statement; it lives in `use-cases/list-admin-products.server.ts` with `buildAdminProductsFilterParams` and the helpers below. Its `buildAdminProductsWhere` combines the search (`buildAdminProductSearchCondition`: the handle, the id, every locale of the title, subtitle and description, and the variants' SKUs), the status, the category, the collection and the created-at filter, which `buildAdminDateTimeFilterSql(product.createdAt, createdAt, timeZone)` reads on the admin's clock (see [Audit log](/docs/features/audit-log)). The variant kind goes through `buildAdminVariantKindFilterSql`. The count and the page's ids are read in parallel, the rows are then loaded by id, and `loadAdminListAggregates` adds each row's variant stats and SKU summary. As on the storefront, the variant-stats join is conditional: `adminProductsListNeedsVariantStatsJoin` asks for it for an inventory level, a variant kind, or a sort by price, stock or variant count, and `queryAdminProducts` also adds it for the price and stock column filters.

The tables and the stat cards of all four tabs format in the admin's own display preferences (see [Internationalization](/docs/features/internationalization)). In the products grid, the created and edited dates go through `useFormatter()` from `src/hooks/use-display-format.ts`, in the admin's format locale and time zone, the price column through `formatPrice(price, "PLN", formatLocale)`, and the stat cards' figures through `toLocaleString(formatLocale)`. The created-at column filter reads its days in the same time zone, in the browser (`matchesDateColumnFilterIn(timeZone)`) and on the server.

`PRODUCT_VARIANT_KIND` is `{ MULTI: "multi", SINGLE: "single" }` with `PRODUCT_MULTI_VARIANT_COUNT_THRESHOLD = 1`, driving `products-variant-kind-filter.tsx`.

### Writing

| Use case                     | Permission            | Notes                                                                                        |
| ---------------------------- | --------------------- | -------------------------------------------------------------------------------------------- |
| `create-complete-product.ts` | `product: ["create"]` | One call creates product, options, values, variants, inventory, images and attribute values  |
| `update-complete-product.ts` | `product: ["update"]` | Same, replacing images and attributes; saved as draft or archived, closes its open checkouts |
| `delete-products.ts`         | `product: ["delete"]` | Bulk delete by id array, refused while an open checkout holds one of the variants            |
| `reorder-products.ts`        | `product: ["update"]` | `orderedIds.map((id, index) => ({ id, rank: index }))`                                       |

Both use cases write a product in one atomic D1 batch, so a save either lands completely or leaves the product exactly as it was. They first read what the save depends on in parallel, then send the statements together:

```ts
const [rank, attributeRows] = await Promise.all([
  getNextProductRank(),
  loadAttributeOnProductRows(productId, data.attributeValues),
  assertCatalogSkusAvailable(data),
])
await runDrizzleBatch([
  ...prepareProductInsertBatch(productId, data, rank),
  ...prepareProductImagesBatch(productId, data.images),
  ...prepareAttributeOnProductBatch(productId, attributeRows),
])
```

`prepareProductInsertBatch` and `prepareProductUpdateBatch` (`use-cases/save-complete-product.server.ts`) write the product row and append `prepareProductOrganizationBatch` and `prepareProductCatalogBatch` from `product.accessors.ts`. `prepareProductImagesBatch` replaces the images and sets `product.thumbnail` to the lowest ranked one in the same batch, and `prepareAttributeOnProductBatch` replaces the attribute values. `createCompleteProduct` still calls `deleteOrphanProductByHandle(data.handle)` first, which clears a product left without variants by an older, non-atomic save.

`rethrowProductMutationError` (`product.utils.ts`) maps a D1 unique-constraint failure onto `ERROR_CODES.CONFLICT` with `PRODUCT_ERROR_CODES.DUPLICATE_HANDLE` or `DUPLICATE_SKU`, and a failed `inventory_quantity_available_non_negative` check onto `ERROR_CODES.CONFLICT` with `PRODUCT_ERROR_CODES.STOCK_CHANGED_WHILE_EDITING`. Before anything is written, `assertCatalogSkusAvailable` refuses a SKU another product already uses with the same `DUPLICATE_SKU` conflict. Each of these is an `AppError`, so `withRequest` passes its reason on to the editor instead of replacing it with `INTERNAL_ERROR`: a URL slug another product uses appears under the slug field and in the error toast as `toast.duplicateHandle`, and a taken SKU in the toast as `toast.duplicateSku`.

`updateCompleteProduct` reads the product's handle owner, its current detail and the attribute definitions in parallel, rejects a handle already taken by a different product (`ERROR_CODES.CONFLICT` with `DUPLICATE_HANDLE`), calls `assertCatalogSkusAvailable`, and builds an audit diff by reading the product before and after (`extractProductAuditSnapshot` and `buildProductAuditChange` in `product.utils.ts`).

Saving keeps every variant the product already owns under its id. The statements from `prepareProductCatalogBatch` delete only the variants the form dropped, upserts the rest by id, inserts a stock row only for a variant that has none, and changes existing stock only by the difference between the stock field and the stock the editor loaded. Order lines, cart lines and stock reservations therefore stay attached to the variants they point at. A variant id is reused only when `updateCompleteProduct` read it from this product, so a forged id never takes over another product's variant. Every multi-row insert, including images, attribute values and category and collection links, is split with `insertRowChunks` to stay within D1's 100 bound parameters per statement, so a large gallery or a long specification list saves like any other.

**Stock a customer is paying for.** Neither a delete nor a save removes a variant that a checkout the customer can still pay holds. `assertVariantsNotHeldByOpenCheckouts` (`product.accessors.ts`) asks `isAnyVariantHeldByOpenCheckout` (`payment.accessors.ts`) whether a `pending` payment of a `pending` checkout lists any of the variants in its `reserved_lines`, and if one does it throws `ERROR_CODES.CONFLICT` with `PRODUCT_ERROR_CODES.RESERVED_IN_CHECKOUT` before anything is written. `deleteProducts` checks every variant of the selected products, read with `getVariantIdsByProductIds`, so the row action and the bulk action are covered alike. `updateCompleteProduct` first builds the catalog rows with `prepareCatalogReplacePayload`, checks the variants the product owns that those rows no longer keep, and then passes the same rows to `prepareProductUpdateBatch`, so the variants it checked are exactly the ones the batch deletes. The admin sees `toast.deleteReservedInCheckoutDescription` in the product list or `toast.variantReservedInCheckout` in the editor; both say to archive the product instead and to delete once that payment has finished or expired. Saving the product as archived expires that payment, so the delete goes through right after it unless Stripe refused the expiry (see below). The check runs just before the batch, so a checkout opened in between can still pay for a variant that is then deleted; fulfilment creates that order from what the customer was charged for (see [Payments: Fulfilment](/docs/features/payments#fulfilment)).

**Stock that changed while the editor was open.** The stock field shows what is available for sale, with the units held in open checkouts under it ("1 in checkout"), and a save writes a stock field only when the admin changed it, as the difference from the stock the editor loaded, so reservations, releases and sales made in the meantime stay counted. If a customer reserved or bought the stock meanwhile and the difference would take available stock below zero, the whole save is refused, nothing is written, and the editor shows `toast.stockChangedWhileEditing`, which says so and asks the admin to reload the page to see the current stock. A new product or variant still gets the typed stock as its first stock. [Inventory: Changing stock](/docs/features/inventory#changing-stock) has the details. When the product is fetched again while the sheet is open, for example after a realtime invalidation, `ProductFormProvider` takes the new values only while the admin has changed nothing, and keeps any error the form shows, such as a taken slug. Once the admin has edited a field, the form keeps their values and the stock it loaded, so the save is still checked against that stock.

**Taking a product off sale.** A save that leaves the product `draft` or `archived` also closes the checkouts that could still pay for it. Once the batch is written, invalidated and audited, `updateCompleteProduct` passes every variant the product owned when the save began to `expireCheckoutsHoldingVariants` (`src/modules/checkout/use-cases/expire-checkouts-holding-variants.server.ts`). It asks `getOpenCheckoutSessionIdsHoldingVariants` (`payment.accessors.ts`) for the Checkout Sessions whose `pending` payment of a `pending` checkout lists one of them in `reserved_lines`, the condition `isAnyVariantHeldByOpenCheckout` uses, and expires each with `stripe.checkout.sessions.expire`. Every session Stripe expires goes to `releaseExpiredCheckoutSession`, the release a checkout update and the session check already run ahead of the webhook: `releaseCheckout` returns the lines, frees a held discount use and fails the checkout and its payment, and the `checkout.session.expired` webhook that follows finds nothing left to release and deletes the session's coupon as usual, so the stock comes back once. The failed checkout no longer counts against the open-checkout limits of the shopper's address and email (see [Checkout: Limits on holding stock](/docs/features/checkout#limits-on-holding-stock)). The shopper's payment form can no longer be paid, and a fresh checkout refuses the product. A session Stripe will not expire, such as one paid a moment earlier, is logged and left alone; if it was paid, fulfilment turns it into an order. The save answers with `closedCheckoutCount`, the number of sessions Stripe expired, and when that is above zero the editor's success toast says so with `toast.updateClosedCheckoutsDescription` ("1 open checkout for this product was closed and its stock released."). The expiry runs on every save of an unpublished product, so saving it again closes a session a failed expiry left open. A checkout that passed the published check just before the save and records its payment only after the lookup is missed, and can be paid until it expires.

**Price history.** A save that gives a variant a new `price` or `compare_at_price`, or creates a variant, adds a row to `price_history` with the new prices. The rows come from the `price_history_variant_insert` and `price_history_variant_update` triggers on `product_variant`, which run inside the batch's variant upsert, so the price and its history row are saved together or not at all, and a save that leaves both prices as they were adds nothing. The storefront uses the history to show the lowest price of the 30 days before a reduction next to a reduced price (see [Product page](/docs/features/product-page#reduced-prices-and-the-lowest-price-of-the-30-days-before)). The editor has no compare-at price field: it sends back the compare-at price it loaded.

Creating, saving and deleting a product call `scheduleProductCatalogInvalidation()` and a `recordCatalogProduct*Audit` function, and a save that leaves the product unpublished then closes its checkouts as described above. `reorderProducts` writes the ranks and schedules the invalidation only; it records no audit event, and neither do the reorders of the other three tabs.

### The form

`product.zod.ts` is the largest `*.zod.ts` file in the repository, at 491 lines. `productFormSchemaDefinition` extends the shared `catalogUpsertBaseSchema` with the locale maps, the media fields and the read-only `quantityInCheckout` of each variant, and adds three refinements:

- `refineDuplicateSkusInForm`
- `refineDuplicateProductAttributes`
- `refineCatalogUpsert`, which always requires a primary category (`refineOrganizationRelations`). A product without variants needs its `simpleVariant`, priced at least `MIN_PRICE_CENTS` (2 zł, Stripe's minimum charge; `refineSimpleProductPrice`). A product with variants needs at least one option and one variant, and an active one a variant for every combination `buildVariantCombinations` makes of its options: each combination's `buildVariantCombinationKey` must match the `optionValues` key of a submitted variant, so a variant for a combination the options no longer make does not stand in for a missing one. For an active product, `refineActiveProductPricing` also checks every price and that a compare-at price is not below its price.

All messages are keys from `PRODUCT_FORM_VALIDATION_KEYS`. The editor's status field uses `PRODUCT_ADMIN_STATUS` (`draft`, `active`, `archived`), and `toProductDbStatus` stores `active` as `published`.

`parseCatalogUpsertInput(values)` strips the media and attribute fields, parses the rest, which drops `quantityInCheckout` and keeps each variant's `loadedQuantity`, and then forces inventory tracking on:

```ts
const withInventoryAlwaysTracked = (input: CatalogUpsertInput): CatalogUpsertInput => ({
  ...input,
  simpleVariant: input.simpleVariant === undefined ? undefined : { ...input.simpleVariant, manageInventory: true },
  variants: input.variants.map((row) => ({ ...row, manageInventory: true })),
})
```

Prices are typed into `CatalogMoneyInput` (`catalog/form/components/catalog-money-input.tsx`), which the editor's price fields, the grid's price column filter and the coupon form share. It shows an amount with the decimal separator of the admin's format locale and no grouping, accepts `,` or `.` while the admin types, blocks `e`, `+` and `-`, and on blur rewrites the amount in the format locale or, when it cannot read it, puts the previous amount back. Its placeholder is an example amount formatted in the same locale.

The editor UI is a sheet, not a page. `catalog/product-editor/` has 26 files: `product-sheet.tsx` with `product-form-provider.tsx`, the sections `product-editor-basic`, `-pricing`, `-media`, `-organization`, `-status`, `-tags`, `-attributes`, `-variants-section`, `-variant-list`, `-variant-mode`, plus `product-form-locale-layout.tsx` for the per-locale fields and the `product-form.utils.ts` / `product-variant-form.utils.ts` / `product-image-form.utils.ts` helpers. `useProductsSheetState` / `ProductsSheetProvider` (`catalog/products/hooks/use-products-sheet.tsx`) own the open/close state, which is why the index route wraps the table in that provider.

Opening a product costs one read. The grid passes `prefetchEdit` as `onRowPointerDown`, so pressing a row starts `getAdminProductQuery` before the click lands. `openEdit` opens the sheet at once when the product is cached; otherwise it awaits `queryClient.query` with `staleTime: "static"`, which joins the request the press started instead of sending another. Moving a mouse over the rows or scrolling with a wheel or trackpad reads nothing. On a touchscreen a swipe that starts on a row begins as a press, so it reads that one product. Pressing a checkbox, the drag handle or the row menu prefetches nothing, because none of them opens the sheet.

## Categories

`product_category.parent_id` self-references, so categories form a tree. `collectDescendantCategoryIds` is what makes a storefront category filter include its children.

| Use case                     | Permission             | Notes                                                             |
| ---------------------------- | ---------------------- | ----------------------------------------------------------------- |
| `get-categories.ts`          | public (`withRequest`) | Storefront list                                                   |
| `get-storefront-category.ts` | public                 | One category by handle                                            |
| `get-admin-categories.ts`    | `product: ["read"]`    | Admin tree                                                        |
| `get-category-stats.ts`      | `product: ["read"]`    | Stat cards                                                        |
| `create-category.ts`         | `product: ["create"]`  | Rejects a duplicate handle and a non-existent parent              |
| `update-category.ts`         | `product: ["update"]`  |                                                                   |
| `delete-categories.ts`       | `product: ["delete"]`  | `CATEGORY_ERROR_CODES` includes `HAS_CHILDREN` and `HAS_PRODUCTS` |
| `reorder-categories.ts`      | `product: ["update"]`  | Rank within the parent                                            |

`createCategory` shows the shape all four modules follow:

```ts
const nextRank = await getNextRankForParent(parentId)
const id = uuidv7()
await db.insert(productCategory).values(toCategoryRow(data, id, nextRank))
scheduleCategoryCatalogInvalidation()
recordCatalogCategoryCreatedAudit(data.handle)
```

Ranks are assigned server-side by `getNextRankForParent`, never sent from the client.

A category's `status`, `handle` and parent decide which products the storefront lists under it: a category page lists its whole subtree, and an unknown or inactive handle lists nothing. `scheduleCategoryCatalogInvalidation()` therefore also invalidates `PRODUCT_QUERY_KEYS.STOREFRONT_PAGE`, so an open category page, or a catalogue filtered by a category, refetches its products.

## Collections

The same eight use cases without the tree: `get-collections`, `get-storefront-collection`, `get-admin-collections`, `get-collection-stats`, `create-collection`, `update-collection`, `delete-collections`, `reorder-collections`. `COLLECTION_ERROR_CODES` has `DUPLICATE_HANDLE` and `HAS_PRODUCTS`.

Collections matter beyond the catalog: the `nowosci` collection drives the landing page's new arrivals and the account overview's fallback recommendations, and `scheduleCollectionCatalogInvalidation()` therefore also invalidates `PRODUCT_QUERY_KEYS.LANDING_NEW_ARRIVALS`. A collection's `status` and `handle` also decide which products its storefront grid lists, so the same call invalidates `PRODUCT_QUERY_KEYS.STOREFRONT_PAGE` as well.

## Attributes

An attribute is a reusable specification definition. `PRODUCT_ATTRIBUTE_TYPE` is `text`, `number`, `boolean`, `select` and `multiselect`; `productAttributeTypeUsesAllowedValues(type)` decides whether `allowed_values` is persisted. `PRODUCT_ATTRIBUTE_UNIT_PRESETS` is `["mm", "cm", "m", "km", "mg", "g", "kg", "ml", "l", "szt.", "par", "%"]`, with `PRODUCT_ATTRIBUTE_UNIT_CUSTOM_SELECT_VALUE = "__custom__"` for a free-text unit.

Use cases: `get-admin-product-attributes`, `get-product-attribute-stats`, `create-product-attribute`, `update-product-attribute`, `delete-product-attributes`, `reorder-product-attributes`. They call `scheduleProductAttributeCatalogInvalidation()`, which invalidates only the admin keys — attributes are read on the storefront as part of the product query, not on their own.

`/admin/catalog/attributes?create=1` opens the tab with the create sheet open. The product editor's attributes section links there ("Create attribute in catalog") while the catalog has no attributes.

Values are attached through `src/modules/attribute-on-product`: `get-product-attributes` and `set-all-product-attributes`, with `loadAttributeOnProductRows` normalizing the values against their definitions and `prepareAttributeOnProductBatch` replacing them in one batch. A row can be scoped to a variant, which is how `mapPublishedProductForStorefront` gives a variant its own specifications with the product-level ones as a fallback.

## Images and R2

`uploadImageFn` (`src/integrations/cloudflare-r2/media.mutations.ts`) is guarded by `authorized({ product: ["update"] })` and validated against `media.zod.ts`:

- accepted MIME types: `image/jpeg`, `image/png`, `image/webp`, `image/avif`
- maximum size: `MAX_IMAGE_BYTES` = 5 MiB
- longest file name: `MAX_IMAGE_NAME_LENGTH` = 255 characters
- folders: `collections`, `products`, `categories`, `uploads` (the fallback)

A file that breaks a rule is refused with `ERROR_CODES.VALIDATION` and the rule as the message (`INVALID_FILE`, `INVALID_TYPE` or `TOO_LARGE`), before anything is stored.

The key is **content-addressed**, which makes re-uploading the same file free:

```ts
const buffer = await file.arrayBuffer()
const digest = await crypto.subtle.digest("SHA-256", buffer)
const key = `${folder}/${bufferToHex(digest)}.${MIME_EXTENSION[file.type]}`
if ((await env.IMAGES.head(key)) === null) {
  await env.IMAGES.put(key, buffer, { httpMetadata: { cacheControl: IMMUTABLE_CACHE_CONTROL, contentType: file.type } })
}
```

`IMMUTABLE_CACHE_CONTROL` is `public, max-age=31536000, immutable`, which is safe precisely because the key is the hash. The binding is `IMAGES` in `wrangler.jsonc`. Every accepted upload, including one whose bytes the bucket already held, records `image.uploaded` against the admin, with the key as the target and the file's own name as the detail. `uploadImageFn` answers with the key alone, the forms store that key, and `getAssetURL` / `resolveAssetURL` in `src/lib/url.ts` turn it into a public URL using `VITE_R2_URL` when the image is shown, so the stored rows carry no host.

`prepareProductImagesBatch` in `product-image.accessors.ts` rewrites a product's image rows and keeps `product.thumbnail` in step in the same batch, and `getProductImagesQuery` in the same file reads them back. The upload widgets live in `src/presentation/components/custom/image-upload/`.

## Shared grid infrastructure

`catalog/table/`, `catalog/toolbar/`, `catalog/form/`, `catalog/dialog/` and `catalog/lib/` hold the pieces the four tabs share. `catalog/lib/catalog-admin-datagrid.constants.ts` holds `CATALOG_ADMIN_RECORD_ID_COLUMN_WIDTH_PX` (320 px), the id column width that the categories, collections, attributes, customers, coupons and newsletter-subscriber grids take from their module constants (`user.constants.ts` for customers, `discount.constants.ts` for coupons). `product.constants.ts` sets the same 320 itself, and the orders grid, whose id column shows the order number, uses 160. `catalog/lib/catalog-record-id-column.ts` exports `CATALOG_RECORD_ID_COLUMN_META`, which gives all of these id columns, the orders' included, the same loading skeleton. The generic data grid itself is `src/presentation/components/custom/datagrid/`, translated through the `components.datagrid` namespace.

The editors open as sheets from the right and never get wider than the window, so on a phone a sheet fills the screen. A wider screen shows a drag handle on the sheet's left edge (`catalog/lib/sheet-resize.ts`), from `lg` for the product sheet and from `sm` for the others. The product sheet starts at 1040 px and can be dragged out to 98% of the window, at most 2560 px; the category, collection and attribute sheets share one width that starts at 512 px and goes up to 90% of the window, at most 1200 px. Neither can be dragged narrower than its starting width. The chosen width is kept in `localStorage` under `admin-sheet-width:admin.catalog.product-form-sheet` or `admin-sheet-width:admin.catalog.form-sheet`.

Each editor shows the fields of one locale at a time and opens on Polish. `CatalogLocalePickerLayout` (`catalog/form/components/catalog-locale-picker.tsx`, with its messages in `pages.admin.catalog.localePicker`) renders the locale select and how many locales are filled. The product, category and collection editors keep the chosen locale in `CatalogFormLocaleControlsProvider` (`catalog/form/components/catalog-form-locale-controls.tsx`). The attribute editor has its own `AttributeFormLocaleControlsProvider` (`attribute-form-locale-controls.tsx`), because an attribute is filled in a locale only when its title and every allowed value it lists have text there. When a save fails validation, the editor asks its own helper which locales lack that text (`product-form-locale.utils.ts`, `category-form-locale.utils.ts`, `collection-form-locale.utils.ts` or `attribute-form-locale.utils.ts`), switches to the first of them, lists them under the picker and names them in an error toast.

### Exporting a tab

Every tab has the shared **Export** menu in its toolbar, next to the refresh button, which downloads the table as CSV, JSON, XML or plain text (see [Data grid](/docs/ui/data-table#export)). A file holds the columns the table shows, in their order and under their headers, and every row the filters, the search, the stat card and the sort select, across all pages. Each cell is the text the table shows: a title in the page language with its handle after it, such as `Silver ring (/silver-ring)`, statuses and types by name, prices in złoty and dates in the admin's format locale. The one exception is the products' Categories column: its cell shows the main category, and the file lists every category of the product.

Categories, collections and attributes are loaded whole, so their export takes the rows the grid holds after filtering and sorting; `use-categories-export-source.ts`, `use-collections-export-source.ts` and `use-attributes-export-source.ts` name the list and describe the status, type or card filter. Products export through `exportAdminProducts`, with the filters, the search and the sort of the server list, while a stat card, a column filter or a search moves the list to the server, and from the grid otherwise, in the order its sort shows; a sort alone keeps the whole catalogue in the grid (`hasProductsServerListQuery` ignores it). `use-products-export-source.ts` names the category and the collection filter by their titles, reading the category and collection lists through their queries so the titles are there even before the filter menus load them, and words the stock level a stat card selects under "Stock level" and the amount the Stock column filter sets under "Stock". Only the products export is recorded in the audit log, as `product.list_exported`, because only it reaches the server.

The category, collection and attribute grids have a hidden title column for each shop language, such as **Category (PL)** and **Category (EN)**, built by `buildCatalogLocalizedTitleColumns` in `catalog/lib/catalog-localized-title-columns.tsx`; showing them puts the titles of every language side by side in the table and in the file.
