## Layout and guard

`src/routes/account.tsx` is the layout. Its `beforeLoad` is the guard itself, and the `{ user }` the guard resolves to becomes route context:

```ts
beforeLoad: requireCustomer,
```

`requireCustomer` (`src/integrations/better-auth/auth.routes.ts`) requires a session and then **redirects admins away**:

```ts
export const requireCustomer = async (route: AuthRouteContext): Promise<{ user: SessionUser }> => {
  const { user } = await requireSignedIn(route)

  return hasAdminAccess(user.role) ? redirectTo(ROUTES.ADMIN) : { user }
}
```

So an admin cannot browse the customer area; they land on `/admin`. `/account/overview` reads the user for its greeting with `AccountRoute.useRouteContext()`.

`requireSignedIn` only reads the session, through `loadRouteSession`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

It passes `recheck: true`, so a real navigation into `/account` re-checks the session with `staleTime: 0`; a link preload reuses a cached session younger than 60 seconds. The session stays in the TanStack Query cache and a server render dehydrates it into the page, so the account pages render signed-in on the server.

A change of user is handled in one place: `clearCacheOnUserChange` (`src/integrations/better-auth/auth.session.ts`), which `getRouter` installs in the browser only. It watches the query cache, and whenever the session switches to a different user, signing in or out included, it removes every cached query except the session itself and the translation catalogues, so nothing cached for the previous user is shown.

An anonymous visitor is redirected to `/auth/sign-in?redirect=<path>`, where `<path>` is the localized public path, such as `/en-US/account/orders/order-1`. It is kept only when it matches `SAME_SITE_PATH_PATTERN`: visible ASCII characters only, a single leading slash and no backslash. After a password, two-factor, Google or GitHub sign-in, the `/auth` guard sends the visitor back to it. See [Integrations: Better Auth](/docs/integrations/better-auth).

The layout renders the storefront `Navigation`, a two-column grid and the storefront `Footer`. Only the two grid cells are wrapped in `Suspense`: the `AccountSidebar` with the `AccountSidebarFallback` skeleton, and the outlet with the `AccountMainFallback` skeleton. It preloads four namespaces: `pages.account`, `pages.account.meta`, `pages.auth.errors` and `pages.auth.validations`.

`/account` itself only redirects:

```ts
beforeLoad: () => {
  redirect({ throw: true, to: "/account/overview" })
},
```

Every route loader prefetches with `staleTime: "static"`. `account.payment.tsx` and `account.wishlist.tsx` leave the route's `staleTime` to the router's `defaultStaleTime`, also 60 000; the other six route files set it to `CUSTOMER_ACCOUNT_QUERY_STALE_MS` (60 000).

## Authorization pattern

Every use case in `src/modules/customer-account/use-cases/` uses `authorized()` with no permission argument — any signed-in user — and then scopes the query to `context.auth.user.id` itself. There is no route-level ownership check to bypass; the server function is the boundary. `getCustomerOrder`, for example, filters on `and(eq(order.id, orderId), eq(order.userId, context.auth.user.id))`.

## Overview

`getCustomerOverview` first reads the ids and numbers of the customer's latest orders, then fans out six queries in parallel, then reads the items of the recent orders and finally builds the recommendations:

| Source                                                     | Feeds                                         |
| ---------------------------------------------------------- | --------------------------------------------- |
| `getCustomerOrderNumbers(userId)`                          | The ids and numbers of the latest orders      |
| `getCustomerOrderRows(userId, { limit: 3 })`               | The recent-orders list                        |
| `getCustomerSpendStats(userId)`                            | `totalOrders`, `totalSpentMinorUnits`         |
| `getCustomerActivityAuditRows(userId, orderIds)`           | The activity feed                             |
| `getUserById(userId)`                                      | `memberSinceYear` from `createdAt`            |
| `countWishlistItems(userId)`                               | `wishlistCount`                               |
| The `nowosci` collection                                   | The new-arrivals fallback for recommendations |
| `getOrderItemsForOrders(recentOrderIds)`                   | The items shown under each recent order       |
| `buildCustomerRecommendations(userId, collection, locale)` | `recommendations`, `recommendationsSource`    |

`getCustomerSpendStats` counts and sums only orders in `processing` or `completed` status. The limits are in `customer-account.constants.ts`: `CUSTOMER_ACCOUNT_ORDERS_LIMIT = 50` for the order numbers, `CUSTOMER_ACCOUNT_OVERVIEW_ORDERS_LIMIT = 3`, `CUSTOMER_ACCOUNT_OVERVIEW_ACTIVITY_LIMIT = 5`, `CUSTOMER_ACCOUNT_RECOMMENDATIONS_LIMIT = 3`, `CUSTOMER_ACCOUNT_RECOMMENDED_CATEGORY_LIMIT = 2`.

Two things to know:

- **Recommendations follow the customer's orders.** `buildCustomerRecommendations` takes the two categories that appear most in the customer's `processing` and `completed` orders, reads published products from them and drops every product the customer has already ordered. If any are left, the first three come back with `recommendationsSource: "orders"`. Otherwise it falls back to the first three published products of the `nowosci` collection, the same collection the landing page's new arrivals uses (`LANDING_NEW_ARRIVALS_COLLECTION_HANDLE`), with `recommendationsSource: "newArrivals"`, or to an empty list when that collection does not exist. The page picks the grid's heading and description from the source.
- **`wishlistCount` is real.** `countWishlistItems` counts the customer's `wishlist_item` rows, the same rows `/account/wishlist` lists, so a product that is no longer published still counts.

The activity feed is built from the audit log: `getCustomerActivityAuditRows` reads `audit_log` rows whose `resourceId` is the user or one of the orders from `getCustomerOrderNumbers`, limited to `auth.login`, `auth.login_failed`, `auth.logout`, `customer.cart_item_added`, `order.placed`, `order.shipped` and `order.released`. `mapAuditLogToActivityItem` turns each row into `{ actionKey, params, createdAt }`, putting the order number into `params` for order actions and dropping any row it cannot map. The page maps `actionKey` to an icon through the local `ACTIVITY_ICONS` map and formats the timestamp with `formatRelativeFromNow`.

## Profile

`getCustomerProfile` returns `{ createdAt, email, emailVerified, hasPassword, name, phone, timezone, twoFactorEnabled }` from the `user` row, with `hasPassword` from `hasCredentialAccount`.

`account.profile.tsx` passes `profile.twoFactorEnabled` to `SecuritySection` as a prop, so the two-factor status comes from the query the page loader already prefetched. Enabling or disabling two-factor invalidates the profile query, the session query and `CUSTOMER_ACCOUNT_QUERY_KEYS.SESSIONS`, because Better Auth replaces the current session when it does either. Changing the password invalidates `CUSTOMER_ACCOUNT_QUERY_KEYS.SESSIONS` as well, since "Sign out my other devices" deletes every other session; the sessions page never shows a device that is already signed out.

The change-email and change-password dialogs validate as the customer types (`mode: "onChange"`), like the two-factor and close-account dialogs, and never when a field loses focus. Validating on blur would put an error line under the field the customer has just left to press **Cancel** or the close button. The dialog is centred, so its footer would move about 12 px down while the button is held, and a press near the top of **Cancel** would be lost. The cost is that an error shows while the customer is still typing: a new email address is flagged from its first character until it is a complete address, **New password** lists what it still needs, and **Confirm new password** says the passwords must match until they do. Each time an error line appears or goes, the dialog grows or shrinks by one line and the fields move by about 12 px, as they already did in the two-factor and close-account dialogs.

`updateCustomerPhone` is the only field a customer can change here:

```ts
export const updateCustomerPhone = createServerFn({ method: "POST" })
  .middleware([withRateLimit("update-customer-phone", RATE_LIMITS.SENSITIVE), authorized()])
  .validator((input: zod.input<typeof customerAccountZodSchemas.phoneInput>) => customerAccountZodSchemas.phoneInput.parse(input))
  .handler(async ({ context, data: { phone } }): Promise<boolean> => {
    await db
      .update(user)
      .set({ phone: phone === "" ? sql`NULL` : phone })
      .where(eq(user.id, context.auth.user.id))

    return true
  })
```

`RATE_LIMITS.SENSITIVE` is three calls per minute. An empty string clears the column to `NULL` rather than storing `""`. Name, email and password changes go through Better Auth, not through this module.

`PreferencesSection` also holds `NewsletterField`, which reads `getOwnNewsletterSubscriptionQuery()` and calls `subscribeToNewsletter` with the account's own address and `source: "account"`. A `confirmationSent` answer shows a "check your inbox" toast, `alreadyConfirmed` says the customer is already subscribed, and `confirmationFailed` shows an error toast saying the email could not be sent. While the subscription is `pending`, the status reads "Not confirmed yet" rather than promising an email, and the field offers **Resend email** next to **Unsubscribe**, so a confirmation that failed or never arrived can be sent again with a fresh link. On a narrow screen the two actions wrap below the status.

## Addresses

`src/modules/address` has five use cases, all `authorized()` and all scoped to the current user:

| Use case                      | Middleware                                                                     | Notes                                                   |
| ----------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------- |
| `list-user-addresses.ts`      | `authorized()`                                                                 | `findMany` where `userId` matches                       |
| `create-user-address.ts`      | `withRateLimit("create-user-address", RATE_LIMITS.SENSITIVE)` + `authorized()` | Forces `userId` from the session                        |
| `update-user-address.ts`      | rate limited + `authorized()`                                                  |                                                         |
| `delete-user-address.ts`      | `authorized()`                                                                 |                                                         |
| `set-default-user-address.ts` | `authorized()`                                                                 | Throws `ERROR_CODES.NOT_FOUND` when nothing was updated |

**Cancel** closes the address form with a single press even when the page is still gliding after a wheel or trackpad scroll: `SmoothScroll` stops the glide on any press, so the button stays under the pointer until it is released. See [GSAP and Lenis](/docs/integrations/gsap-and-lenis).

`addressFieldsSchema` (`address.zod.ts`) requires `address1`, `city` and a two-character `countryCode`; `firstName`, `lastName`, `phone`, `postalCode`, `province` and `address2` are optional, matching the nullable columns.

The `address` table (`address.schema.ts`) has `is_default` and two indexes, `address_userId_idx` and `address_userId_isDefault_idx`. Note that checkout also writes `address` rows — with `user_id` null for a guest — and `isDefault` is set from the `saveShippingAddress` / `saveBillingAddress` checkboxes. See [Checkout](/docs/features/checkout).

## Sessions

`listCustomerSessions` selects the `session` rows for the user ordered by `updatedAt` descending and enriches each one:

```ts
return rows.map((row) => {
  const parsed = parseUserAgent(row.userAgent)

  return {
    browser: parsed.browser,
    createdAt: row.createdAt,
    device: parsed.device,
    deviceType: parsed.deviceType,
    id: row.id,
    ipAddress: row.ipAddress ?? undefined,
    isCurrent: row.id === context.auth.session.id,
    lastActiveAt: row.updatedAt,
  } satisfies CustomerAccount["session"]
})
```

`parseUserAgent` is in `customer-account.utils.ts`. `lastActiveAt` is the session row's `updatedAt`.

Two revoke mutations:

- `revokeCustomerSession({ sessionId })` — returns `false` without deleting when the id is the **current** session, so a customer cannot sign themselves out from this screen. The delete is `and(eq(session.id, sessionId), eq(session.userId, context.auth.user.id))`.
- `revokeOtherCustomerSessions()` — deletes every other session for the user and never the current one.

The page labels the bulk action "Sign out other devices" and renders it only while the list holds a session other than the current one. With a single device signed in there is nothing for it to do, so the list says the customer is signed in on this device only instead. Signing out of the current device stays with the account sidebar's sign-out link.

`listCustomerLoginHistory` reuses the same audit rows and keeps only `auth.login` and `auth.login_failed`, mapping the failure to `status: "failed"`. So the login history is a view over [the audit log](/docs/features/audit-log), not a separate table. `getCustomerLoginAuditRows` returns the newest `CUSTOMER_ACCOUNT_LOGIN_HISTORY_LIMIT` (20) rows; when the list reaches that limit, a note under it says only the most recent attempts are shown. Each row states its outcome once — "Successful sign-in" or "Failed sign-in attempt" — with the address and the date beside it.

Closing the account is not offered here. It lives only on the profile page, where `CloseAccountSection` opens the confirmation dialog that calls Better Auth's `deleteUser`.

## Saved payment methods

A signed-in customer saves a card in one of two places: at checkout, or with **Add Card** on `/account/payment`. Either way the card is attached to the customer's Stripe customer; there is no saved-card table. The sidebar entry and the browser tab title use `pages.account.sidebar.payment`, "Payment Methods" ("Metody płatności" in Polish), the same words as the page heading.

### The Stripe customer

`ensureStripeCustomer` (`src/integrations/stripe/stripe.customer.server.ts`) returns the user's `stripe_customer_id`, or creates a Stripe customer and stores its id in that column. Two requests can both find the column empty, for example after a double click or with checkout open in another tab, so the id is written with `coalesce` and the request that loses the race deletes the customer it created:

```ts
const customer = await stripe.customers.create({ email, metadata: { userId }, name })
const [stored] = await db
  .update(user)
  .set({ stripeCustomerId: sql`coalesce(${user.stripeCustomerId}, ${customer.id})`, updatedAt: new Date() })
  .where(eq(user.id, userId))
  .returning({ stripeCustomerId: user.stripeCustomerId })

if (stored?.stripeCustomerId !== customer.id) {
  await stripe.customers.del(customer.id).catch((deleteError: unknown) => {
    console.error("Failed to delete an unused Stripe customer:", deleteError)
  })
}
```

`coalesce` keeps whichever id was stored first and every caller receives that id, so a card is never saved to a customer the account has lost track of. The losing request deletes its own customer, which nothing has been attached to yet; a failed delete is only logged, because the stored customer is already correct. No idempotency key is sent: checkout creates the customer with the email typed into the checkout form and the account page with the account email, and Stripe rejects a reused key whose parameters differ, which would fail one of the two requests. A user row that no longer exists throws `ERROR_CODES.NOT_FOUND` once the new customer has been deleted.

### At checkout

For a signed-in customer, `handleCreateCheckoutSession` (`src/integrations/stripe/stripe.actions.server.ts`) calls `ensureStripeCustomer` and creates the Checkout Session for that customer with `payment_method_save` enabled, which lets the customer choose to save the card:

```ts
...(customerId === undefined
  ? { customer_email: email }
  : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
```

A guest gets `customer_email` instead and has no Stripe customer to save a card to. `handleUpdateCheckoutSession` reuses an existing customer through `getStripeCustomerId` and never creates one. See [Payments](/docs/features/payments).

### On the account page

**Add Card** calls `createCardSetupIntent` (`src/modules/payment/use-cases/create-card-setup-intent.ts`), behind `withRateLimit("create-card-setup-intent", RATE_LIMITS.SENSITIVE)` and `authorized()`. It calls `ensureStripeCustomer` with the account's email and name, so a customer who has never paid gets a Stripe customer here, and then opens a SetupIntent:

```ts
const intent = await stripe.setupIntents.create({
  customer,
  metadata: { userId },
  payment_method_types: ["card"],
  usage: "on_session",
})
```

Only cards are offered, because BLIK and Przelewy24 cannot be saved, and `on_session` matches how a saved card is reused: at checkout, with the customer present. The function returns only `{ clientSecret }` and throws `ERROR_CODES.INTERNAL_ERROR` when Stripe returns no client secret.

Before it touches Stripe, the function throws `ERROR_CODES.FORBIDDEN` for an anonymous session (`isAnonymous`, from Better Auth's `anonymous()` plugin) and for an account whose email is not verified. `authorized()` only checks that a session exists, and an anonymous session costs a single request to `/api/auth/sign-in/anonymous`. Without the check anyone could open a SetupIntent and confirm stolen cards against its client secret again and again from the browser, which the per-IP rate limit on this function never sees.

The page keeps the result of `createCardSetupIntentMutation` while it is mounted. Closing the form and opening it again reuses the same SetupIntent instead of spending another request of the rate limit; a new one is opened once a card has been saved or the form has given up on the SetupIntent. When opening the form fails, for example because the rate limit was reached, the page shows `pages.account.payment.formUnavailable`, since no card has been entered yet.

**Add Card** stays focusable while it is held: it is rendered with `focusableWhenDisabled`, so it carries `aria-disabled` instead of `disabled` while the SetupIntent is being created and while the form is open, and keyboard and screen-reader focus never drops to the page. When the Payment Element is ready, its `onReady` handler moves focus into the card fields. Cancelling, saving a card and giving up on the SetupIntent all return focus to **Add Card**. **Cancel** calls `preventDefault()` on `mousedown`, so pressing it leaves focus in the card fields. Otherwise leaving a half-typed card number makes Stripe show "Your card number is incomplete." under it and grow its iframe while the button is still held. In Chromium and WebKit that moved **Cancel** 13 to 17 px down, more than its own height, and the first press was lost.

`account.payment.tsx` renders `LazyAddCardForm` from `add-card-form-loader.client.ts` inside `ClientOnly`. The loader wraps `AddCardForm` (`add-card-form.client.tsx`) in `lazy()`, so its chunk and Stripe.js are only downloaded after the first click, and `ClientOnly` keeps the client-only module out of the server bundle, which the build's import protection requires. `AddCardForm` reads Stripe.js through `useQuery(stripeJsQuery(locale))` from `stripe.client.ts`, which wraps `getStripe(locale)` with `retry: false`. It shows a placeholder while Stripe.js downloads and `AddCardUnavailable` (`pages.account.payment.formUnavailable` and a cancel button) when the download fails, for example behind an ad blocker. `getStripe` forgets a failed download, so opening the form again downloads the script again. The form reuses the checkout setup: `getStripeAppearance(theme)` and `STRIPE_FONTS` from `stripe.appearance.ts`. It also passes `locale: toStripeLocale(locale)` to `Elements`, because `getStripe` keeps the locale Stripe.js first loaded with. `Elements` is keyed by the client secret, which cannot change once it has mounted.

`AddCardFields` (`add-card-fields.client.tsx`) renders the Payment Element without Apple Pay, Google Pay or Link and confirms with:

```ts
stripe.confirmSetup({
  confirmParams: { payment_method_data: { allow_redisplay: "always" } },
  elements,
  redirect: "if_required",
})
```

Stripe Checkout only offers saved cards whose `allow_redisplay` is `"always"`, so without it a card added here would appear in the wallet but never at checkout. With cards only and `redirect: "if_required"` the page never navigates away; a 3D Secure challenge opens in Stripe's own dialog. The form ignores a submit until the Payment Element is ready and while a save is in progress, because Stripe submits the surrounding form when Enter is pressed inside its iframe, and a second `confirmSetup` on the same SetupIntent would fail even when the first one succeeds.

A `card_error` or `validation_error` is shown with Stripe's localized message, or `pages.account.payment.addError` when it has none, and the form stays open on the same SetupIntent, which Stripe keeps in `requires_payment_method`. Any other error, and a `confirmSetup` that throws, shows `pages.account.payment.addError`, invalidates `PAYMENT_METHOD_QUERY_KEYS.SAVED` in case the card was saved after all, and calls `onFailed`: the page closes the form and opens a fresh SetupIntent next time, instead of reusing a client secret Stripe may no longer accept.

On success the form calls `removeDuplicateSavedCards` (`src/modules/payment/use-cases/remove-duplicate-saved-cards.ts`, behind `withRateLimit("remove-duplicate-saved-cards", RATE_LIMITS.SENSITIVE)` and `authorized()`) with the new card's id. It throws `ERROR_CODES.NOT_FOUND` when the user has no Stripe customer and `ERROR_CODES.FORBIDDEN` unless the card belongs to that customer, then detaches every other saved card with the same `card.fingerprint`. Adding a card that was already saved, at checkout or here, therefore replaces the old copy with the new one, including its new expiry date, instead of listing the card twice in the wallet and at checkout. Whether or not that call succeeds, the form then invalidates `PAYMENT_METHOD_QUERY_KEYS.SAVED`, shows `pages.account.payment.added` and closes; the card is saved either way. When the Payment Element reports a load error, as it does with the dummy publishable key used in development and the end-to-end tests, the form shows `pages.account.payment.formUnavailable` and keeps the save button disabled.

### Listing and removing

`listSavedPaymentMethods` (`src/modules/payment/use-cases/list-saved-payment-methods.ts`) is `authorized()` and asks Stripe for the customer's `card` payment methods with `limit: SAVED_CARDS_PAGE_LIMIT` (100, from `payment.constants.ts`), because Stripe's default page holds ten, or returns an empty list when the user has no Stripe customer. Each card becomes `{ brand, expMonth, expYear, id, isExpired, last4 }`. `isExpired` comes from `isCardExpired` (`payment.utils.ts`), which compares the expiry with today's date in the customer's own time zone: the user's `timezone` through `resolveTimezoneCode`, which falls back to `Europe/Warsaw`.

`/account/payment` prefetches `listSavedPaymentMethodsQuery()` and renders `SavedCardList`. With no cards it shows a `CreditCard` icon and `pages.account.payment.empty`; otherwise one `SavedCardRow` per card with the brand, the last four digits, the expiry as `MM/YYYY`, an expired badge when `isExpired` is set and a remove button. The heading count is `methods.length`.

Removing a card calls `deleteSavedPaymentMethod` (`delete-saved-payment-method.ts`), behind `withRateLimit("delete-saved-payment-method", RATE_LIMITS.SENSITIVE)` and `authorized()`. It throws `ERROR_CODES.NOT_FOUND` when the user has no Stripe customer and `ERROR_CODES.FORBIDDEN` unless the payment method belongs to that customer, and only then detaches it in Stripe. On success the list invalidates `PAYMENT_METHOD_QUERY_KEYS.SAVED`.

There is no default card. Nothing reads or writes `invoice_settings.default_payment_method`, and checkout lists saved cards in Stripe's order.

## Wishlist

`wishlist_item` (`src/modules/wishlist/wishlist.schema.ts`) holds one row per customer and product. `user_id` and `product_id` both cascade on delete; `wishlist_item_userId_productId_unique` keeps the pair unique and `wishlist_item_userId_createdAt_idx` serves the newest-first list.

The three use cases are all `authorized()` and scoped to the current user:

| Use case                       | Notes                                                                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list-wishlist-items.ts`       | `listWishlistItemsQuery(locale)`: newest first, up to `WISHLIST_MAX_ITEMS`, each with its localized title, cheapest variant, stock and published status |
| `list-wishlist-product-ids.ts` | `listWishlistProductIdsQuery()`: the saved product ids, which the hearts read                                                                           |
| `toggle-wishlist-item.ts`      | `toggleWishlistItemMutation`: deletes an existing row, otherwise inserts one for a published product while the list is under `WISHLIST_MAX_ITEMS` (200) |

An unpublished product throws `ERROR_CODES.NOT_FOUND`, and a full list throws `ERROR_CODES.VALIDATION` with the message `WISHLIST_FULL`.

The heart on product cards (`product-card.tsx`) and the button on the product page (`product-wishlist-button.tsx`) both use `useWishlist` (`src/hooks/use-wishlist.ts`). It reads the session from `getCurrentSessionQuery` and fetches the product ids only when someone is signed in. A signed-out shopper gets a toast whose action opens the sign-in page. For a signed-in customer it calls `toggleWishlistItem` and shows a toast with the result. A successful toggle invalidates `WISHLIST_QUERY_KEYS.ROOT`, which refreshes both wishlist queries. A full list shows the `wishlistFull` toast, which names the `WISHLIST_MAX_ITEMS` limit: `handleRequestError` keeps the `WISHLIST_FULL` reason code on its way to the browser (see [Integrations: Better Auth](/docs/integrations/better-auth)). Any other failure shows `wishlistError`.

`/account/wishlist` prefetches `listWishlistItemsQuery(locale)` and renders `WishlistGrid`. An empty wishlist shows a link to the products. Otherwise each card shows the price, the date the product was added and an out-of-stock or unavailable label, with an add-to-cart button for the cheapest variant and a remove button that calls the same `toggleWishlistItem`. A product that is no longer published stays on the list, marked unavailable, and cannot be added to the cart. The subtitle count is `items.length`.

## Activity tracking

`CustomerActivityTracker` (`src/presentation/components/custom/customer-activity-tracker.tsx`) is mounted in the storefront and records page views and cart abandonment — but only for signed-in users, and `shouldTrackStorefrontPath` skips any path containing `/admin` or `/account`, so the account area itself is not tracked.
