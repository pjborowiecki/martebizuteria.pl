---
title: "Audit log"
description: "Every significant event goes through a Cloudflare Queue into the audit_log table, feeding the admin audit screen, the customer timeline and the dashboard's page-view KPI."
---

The audit log is the shop's event history and doubles as its analytics store. It is the only part of the system that writes through a queue rather than directly to D1.

## The table

`audit_log` (`src/modules/audit-log/audit-log.schema.ts`):

| Column        | Notes                                                                         |
| ------------- | ----------------------------------------------------------------------------- |
| `id`          | Primary key; a UUIDv7, so the id itself sorts chronologically                 |
| `created_at`  | `timestampNow("created_at")`                                                  |
| `action`      | Not null; one of `AUDIT_LOG_ACTION`                                           |
| `category`    | Enum `orders \| email \| customers \| catalog \| content \| settings \| auth` |
| `severity`    | Enum `info \| success \| warning \| error`                                    |
| `actor_role`  | Enum `admin \| customer \| system \| unknown`                                 |
| `actor_id`    | Nullable                                                                      |
| `actor_name`  | Not null                                                                      |
| `target`      | Not null; the human-readable subject                                          |
| `resource_id` | Nullable; the machine id, defaulting to `target`                              |
| `detail`      | Nullable free text                                                            |
| `metadata`    | Nullable JSON string                                                          |
| `ip`          | Nullable                                                                      |

Five indexes: `audit_log_createdAt_idx`, `audit_log_category_idx`, `audit_log_severity_idx`, `audit_log_action_idx` and the composite `audit_log_resource_idx` on (`category`, `resource_id`) — which is what makes "everything that happened to this order" cheap.

## Writing an event

Never write `audit_log` directly. `audit-log.events.server.ts` exports a named recorder per action: 59 exported `record*` functions, which are 58 action recorders, two of them for `order.released` (the checkout the Stripe webhook releases and the order an admin marks delivered), plus the `recordOrderEmailOutcome` wrapper. Each recorder fills in the action, category and severity and delegates to one of three schedulers in `audit-log.record.server.ts`:

| Scheduler                     | Actor resolution                                                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `scheduleAuditLogFromRequest` | `resolveRequestAuditActor()` from the session, falling back to `SYSTEM_AUDIT_ACTOR`; IP from `resolveRequestAuditIp()` |
| `scheduleAuditLog`            | The caller supplies the actor                                                                                          |
| `scheduleSystemAuditLog`      | Always `SYSTEM_AUDIT_ACTOR` (`{ name: "System", role: "system" }`)                                                     |

All three are **fire and forget**:

```ts
export const scheduleAuditLog = (input: AuditLogEventInput): void => {
  scheduleBackgroundWork(enqueueAuditLogMessage(buildQueueMessage(input)))
}
```

`scheduleBackgroundWork` (`src/lib/background.ts`) hands the promise to the Worker's `waitUntil`, so a recorder never delays a response and a queue failure never fails a mutation. Note the return type: `void`, not `Promise<void>` — you do not `await` a recorder.

`buildQueueMessage` assigns `id: uuidv7()` and `createdAt: Date.now()` at the call site, so ordering reflects when the event happened rather than when the consumer ran. `serializeAuditMetadata` turns the metadata object into the stored JSON string.

Two helpers shape `target` and `resource_id` consistently: `withResourceId(target, options)` defaults `resourceId` to `target`, and `resolveActorAuditTarget(actor, options)` prefers the actor's email as the target and puts it in the metadata, falling back to the name.

Who an entry is credited to follows from the scheduler. Every action an admin takes on an order — fulfil, ship, mark delivered, cancel, ask Stripe for a refund (`order.refund_requested`, from both the Refund button and a cancellation) return to stock (`order.restocked`) and book an InPost shipment (`order.shipment_created`) — goes through `scheduleAuditLogFromRequest`, so the order's Activity card and `/admin/audit` name the signed-in admin and the address they acted from. The order events the Stripe webhook records, among them `order.refund_initiated` when Stripe confirms the refund, stay with `SYSTEM_AUDIT_ACTOR`. The account events, `auth.password_changed` to `auth.user_unbanned` and `customer.deleted`, take the account that changed and share `scheduleAccountAudit`: the account is the target, and the entry is credited to `options.actor` when an admin made the change and to the account holder otherwise. Customer edits (`customer.updated`), image uploads (`image.uploaded`) and deleted audit entries (`audit_log.deleted`) are credited to the admin making the request. A withdrawal from the contract (`order.withdrawal_received`), sent from the account or by order number at `/withdraw-from-contract`, is a warning credited to the consumer who signed the statement, with the order's address, the order number as its detail and the scope in its metadata, so the order's Activity card shows it beside the withdrawals card.

## The queue

The producer binding is `AUDIT_LOG_QUEUE`:

```ts
const enqueueAuditLogMessage = async (message: AuditLogQueueMessage): Promise<void> => {
  await env.AUDIT_LOG_QUEUE.send(message, { contentType: "json" })
}
```

`wrangler.jsonc` declares a producer and a consumer per environment, for example in `development`:

```jsonc
"queues": {
  "producers": [{ "binding": "AUDIT_LOG_QUEUE", "queue": "martebizuteria-audit-log-preview" }],
  "consumers": [
    {
      "queue": "martebizuteria-audit-log-preview",
      "max_batch_size": 50,
      "max_batch_timeout": 5,
      "max_retries": 3,
      "dead_letter_queue": "martebizuteria-audit-log-preview-dlq",
    },
    { "queue": "martebizuteria-audit-log-preview-dlq", "max_batch_size": 1, "max_retries": 3, "retry_delay": 300 },
  ],
},
```

The Worker consumes two queues per environment: the audit queue and its dead-letter queue, named after it with `-dlq` (`martebizuteria-audit-log-preview-dlq` for development and preview, `martebizuteria-audit-log-test-dlq` for the local test Worker, `martebizuteria-audit-log-dlq` for production). The consumer entry point for both is the `queue` export in `src/server.ts`:

```ts
async queue(batch: MessageBatch<AuditLogQueueMessage>, _env: Env, _ctx: ExecutionContext): Promise<void> {
  await processAuditLogQueueBatch(batch)
},
```

`processAuditLogQueueBatch` (`audit-log.queue.server.ts`) inserts the whole batch in one statement and only then acknowledges:

```ts
try {
  await insertAuditLogs(rows)

  for (const message of batch.messages) {
    message.ack()
  }

  const changesOrderTimeline = batch.messages.some((message) => ORDER_TIMELINE_ACTIONS.has(message.body.action))
  await publishRealtimeInvalidation({
    admin: changesOrderTimeline ? [...AUDIT_LOG_ADMIN_QUERY_KEYS, ORDER_QUERY_KEYS.ADMIN.ORDERS] : AUDIT_LOG_ADMIN_QUERY_KEYS,
  })
} catch (error) {
  console.error("[AuditLog Queue] Batch insert failed:", error)

  for (const message of batch.messages) {
    message.retry()
  }

  await notifyShopOfIncident({
    detail: error instanceof Error ? error.message : String(error),
    kind: "auditQueueFailed",
    reference: batch.queue,
  })
}
```

So up to 50 events become one D1 insert, and a failed batch is retried up to three times. A batch that still fails is not deleted: Cloudflare moves its messages to the dead-letter queue, whose consumer takes them **one at a time** (`max_batch_size: 1`) and runs each through the same `processAuditLogQueueBatch`, retrying it up to three more times five minutes apart (`retry_delay: 300`). One message the insert rejects therefore no longer takes the other 49 entries of its batch with it: they are written on their own, and only a message that still cannot be written after its third retry on the dead-letter queue is dropped, with the Worker log and an alert under the dead-letter queue's name as its record. `scripts/verify-bindings.ts` refuses a preview or production deploy whose audit consumer names no `dead_letter_queue` or whose dead-letter queue has no consumer, and each `-dlq` queue has to exist in Cloudflare before the deploy that names it (`bunx wrangler queues create martebizuteria-audit-log-dlq` for production). A failed batch also emails `RESEND_EMAIL_FROM` once the messages are marked for retry, at most once an hour for the queue, and the alert never throws, so it cannot change the retry; see [Monitoring and alerts](/docs/guides/monitoring-and-alerts). The consequence to keep in mind: **an audit entry is eventually consistent** — it can take up to `max_batch_timeout` (5 seconds) to appear, which is why the consumer publishes a realtime invalidation instead of relying on the writer to refresh the UI. `AUDIT_LOG_ADMIN_QUERY_KEYS` is the audit page and its stats. When a row in the batch is one of `ADMIN_ORDER_TIMELINE_ACTIONS`, the consumer adds `ORDER_QUERY_KEYS.ADMIN.ORDERS`. Every open admin tab then refetches the order list, stats or order page it has on screen and drops the order queries it only has cached, so a new timeline row, such as a failed order email, appears without a reload. The `email.*` actions are part of that list whatever the email was for, so a failed newsletter or Better Auth email triggers the refetch too.

## Change diffs

For update actions the recorders carry a structured diff. `audit-log.diff.utils.ts` exports three generic helpers:

- `buildAuditChangeMetadata(before, after, …)` — the changed fields
- `formatAuditDetailFromChanges(…)` — the one-line human summary
- `toAuditMetadataRecord(metadata)` — flattens it for storage

Callers build a snapshot on each side. For a product, `product-audit.utils.ts` has `extractProductAuditSnapshot` and `buildProductAuditChange`, used by `updateCompleteProduct`, which reads the product before and after the write. For a refund, `order-audit.utils.ts` has `buildOrderRefundAuditChange`.

## Automatic auth events

`audit-log.auth.server.ts` wraps the Better Auth handler so login and logout are recorded without touching Better Auth itself:

```ts
export const handleAuthRequestWithAudit = async (request: Request): Promise<Response> => {
  const authPath = resolveAuthPathname(request)
  const shouldAuditFailedLogin = isEmailSignInAttempt(authPath, request.method)
  const shouldAuditLogout = isSignOutAttempt(authPath, request.method)
  const signInEmail = shouldAuditFailedLogin ? await parseSignInEmail(request) : undefined
  ...
  const response = await auth.handler(request)
  ...
}
```

Details worth knowing:

- It matches on `ROUTES.API_AUTH.SIGN_IN_EMAIL` and `ROUTES.API_AUTH.SIGN_OUT` under the `/api/auth` prefix, so the route table stays the single source of those paths.
- The request body is read with `request.clone().json()` so the real handler still receives it.
- For a sign-out it reads the session **before** calling the handler, because afterwards there is none.
- A failed login is recorded only when the response is not `ok`, and the email becomes the `target` — which is how the log shows attempts against addresses that may not exist.

### Account security events

Changes to an account are recorded from inside Better Auth, so they are caught whichever client calls the endpoint. `auth.server.ts` registers the `accountSecurityAudit` plugin next to `signInAudit`. Its after hooks run once the endpoint has answered, skip an answer that is an error, and read the caller from `ctx.context.session` and the address from the request's `cf-connecting-ip`:

| Endpoint                                                        | Recorded                                                                                                                                                |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/change-password`                                              | `auth.password_changed`, plus `auth.sessions_revoked` when the customer asked to sign out the other devices                                             |
| `/two-factor/verify-totp`                                       | `auth.two_factor_enabled`, only for the code that turns two-factor on: the caller arrived signed in with it off and leaves with it on                   |
| `/two-factor/disable`                                           | `auth.two_factor_disabled`                                                                                                                              |
| `/revoke-session`, `/revoke-sessions`, `/revoke-other-sessions` | `auth.sessions_revoked`                                                                                                                                 |
| `/verify-email`                                                 | `auth.email_changed`, with `old → new` as the detail, when the link carries a `change-email-verification` token and the session now has the new address |
| `/admin/set-role`, `/admin/ban-user`, `/admin/unban-user`       | `auth.role_changed` (the role as the detail), `auth.user_banned` (the reason), `auth.user_unbanned`                                                     |
| `/admin/update-user`                                            | Each of `auth.role_changed`, `auth.user_banned`, `auth.user_unbanned` and `auth.email_changed` whose field the update sets                              |
| `/admin/revoke-user-sessions`, `/admin/set-user-password`       | `auth.sessions_revoked`, `auth.password_changed`                                                                                                        |

The admin endpoints look the account up by `userId` and credit the entry to the admin. Two more events need no plugin: `emailAndPassword.onPasswordReset` records `auth.password_reset` once a reset link sets the new password, and `databaseHooks.user.delete.after` records `customer.deleted` for every account Better Auth deletes except the anonymous ones it drops itself, credited to the session that asked — the admin for `/admin/remove-user`, which the admin customers page reaches through `auth.api.removeUser`, or the customer for `/delete-user` — and to the system when there is none. The account page's own server functions for signing out one device or all others, `revokeCustomerSession` and `revokeOtherCustomerSessions`, record `auth.sessions_revoked` themselves when they delete a session. Better Auth's `/admin/revoke-user-session`, which names a session by its token, and `/admin/impersonate-user` are not recorded.

## Customer activity

`recordCustomerActivity` (`src/modules/customer-activity/use-cases/record-customer-activity.ts`) is public but returns `{ ok: true, recorded: false }` without writing when there is no session, so anonymous traffic is never logged. It sits behind `withRateLimit("record-customer-activity", RATE_LIMITS.BROWSING)`: 120 calls a minute per client address, in a bucket of its own, which a shopper's page views and basket additions never reach and which keeps one address from filling the audit log. Past the limit it answers `TOO_MANY_REQUESTS` and records nothing.

It handles three kinds and formats a detail line for each:

| `kind`            | Recorder                           | Detail                         |
| ----------------- | ---------------------------------- | ------------------------------ |
| `cart_item_added` | `recordCustomerCartItemAddedAudit` | `"<title> (<variant>) ×<qty>"` |
| `cart_abandoned`  | `recordCustomerCartAbandonedAudit` | `"<n> items in cart"`          |
| `page_viewed`     | `recordCustomerPageViewedAudit`    | The path                       |

The client side is `customer-activity.tracking.ts`, whose `trackCartItemAdded`, `trackCartAbandoned` and `trackPageViewed` are wrapped in `createClientOnlyFn` and swallow their own errors (`fireAndForget`), so tracking can never break a page. Page views and abandonment are de-duplicated per session through `sessionStorage` keys prefixed `customer-activity:page-view:` and `customer-activity:cart-abandoned-sent`.

This is what makes the dashboard's "page views" KPI possible — see [Admin dashboard](/docs/features/admin-dashboard) — and it also means the figure counts distinct pages per session for signed-in customers only.

## Admin screen

`/admin/audit` (`src/routes/admin.audit.tsx`) prefetches `getAuditLogStatsQuery()` and `listAuditLogsQuery({ page: 1, pageSize: ADMIN_AUDIT_LOG_PAGE_SIZE })`. The page size is **100** and `AUDIT_LOG_QUERY_STALE_MS` is 30 000 — the shortest stale time in the codebase.

All three use cases are guarded by `authorized({ settings: ["manage"] })`, so reading the audit log is a settings-level permission rather than a per-resource one:

| Use case                 | Returns                                                                   |
| ------------------------ | ------------------------------------------------------------------------- |
| `list-audit-logs.ts`     | A page, filtered by `category`, `severity`, `createdAt` and a search term |
| `get-audit-log-stats.ts` | `{ totalCount, todayCount, warningCount, errorCount }`                    |
| `delete-audit-logs.ts`   | `{ deleted, ok }` and publishes a realtime invalidation                   |

`getAdminAuditLogStats` is one `db.batch` of four counts, with "today" coming from `resolveStartOfToday()`.

`listAuditLogs` handles a missing total gracefully:

```ts
const hasMore = total === undefined ? items.length === params.limit : params.offset + items.length < total
```

The filter constants are `AUDIT_LOG_CATEGORY_FILTER` (the categories plus `all`) and `AUDIT_LOG_DATE_RANGE` (`today`, `7d`, `30d`, `all`) with `AUDIT_LOG_DATE_RANGE_MS` for the two windows. Presentation maps: `SEVERITY_DOT_COLORS`, `SEVERITY_BADGE_COLORS`, `ACTOR_ROLE_COLORS`, plus `AUDIT_LOG_TABLE_COLUMN_ID`, `_SIZE` and `_PINNING`.

Components live in `.../admin/audit/`: `audit-log.tsx`, `components/audit-columns.tsx`, `components/audit-filters.tsx`, `components/audit-date-filter.tsx`, `components/audit-bulk-actions.tsx`, the cells in `audit-table/` (`audit-actor-cell`, `audit-target-cell`, `audit-table-cell`), and `audit-stats.config.ts`.

Deletion is the only mutation an admin can make, and it is recorded too. `deleteAuditLogs` accepts at most `LIST_PAGE_SIZE_MAX` (250) entry ids, the largest page the grid shows, and refuses anything that is not a UUID, so the entry it records always fits in a queue message. The delete returns the ids it removed, and when it removed any, `audit_log.deleted` is recorded against the admin with their number as the target and those ids in the metadata; an id that matched nothing is neither counted nor listed. The daily retention clean-up, `deleteExpiredAuditLogs` in `use-cases/delete-expired-audit-logs.server.ts`, also deletes entries: page views and cart events after 90 days, sign-ins, failed sign-ins and sign-outs after 12 months, and every other entry after 24 months. [Data retention](/docs/guides/data-retention) describes the job. Deleting an account deletes its entries too: `eraseAccountData` (`src/modules/user/user.erasure.server.ts`) deletes every row whose `resource_id` is the account's id or email address, which covers the account's activity log, its sign-in history, its registration and the auth emails that failed to reach it, and leaves order, catalogue and admin entries alone. If Stripe refuses to delete the account's customer, the account is kept and `customer.deletion_failed` records why, as an error under `customers`, against the account.

## Read as a feed elsewhere

Three other screens read `audit_log` rather than a table of their own:

- `/account/overview` — the activity feed, through `getCustomerActivityAuditRows` and `mapAuditLogToActivityItem`
- `/account/sessions` — the login history, filtered to `auth.login` and `auth.login_failed`
- `/admin/customers/$id` — the customer timeline, `getCustomerAuditTimelineQuery` with `CUSTOMER_AUDIT_TIMELINE_LIMIT = 50`

Deleting audit rows therefore also erases those views.
