M'Arte has two real legal documents, the privacy policy at `/privacy-policy` and the returns policy at `/exchanges-and-returns`. Each one is a row in the D1 `content_page` table. Admins edit them at `/admin/content` in a rich-text editor that writes Markdown, and the storefront renders that Markdown with the same typography the editor shows.

## The table

`src/modules/content-page/content-page.schema.ts` defines one row per page:

| Column         | Holds                                                                    |
| -------------- | ------------------------------------------------------------------------ |
| `handle`       | `privacy-policy` or `exchanges-and-returns`, unique                      |
| `titles`       | A JSON map from locale to the page title                                 |
| `descriptions` | A JSON map from locale to the meta description                           |
| `bodies`       | A JSON map from locale to the Markdown body                              |
| `revised_ats`  | A JSON map from locale to the epoch milliseconds of the last real change |
| `updated_at`   | The last save of any kind, used to detect conflicting saves              |

The handle column is an enum over `CONTENT_PAGE_HANDLES` in `content-page.constants.ts`, so a page the code does not know about cannot be stored or requested.

The migration `20261002120000_content_pages.sql` creates the table and seeds both pages with the text that used to live in `content/legal`. It inserts with `ON CONFLICT(handle) DO NOTHING`, so running it again never overwrites text an admin has already edited.

The Polish documents are the authoritative ones. They cite Polish statute directly, such as the 14-day right of withdrawal, art. 556⁴ of the Civil Code and the GDPR article for each processing purpose, and they name the data controller. Keep the English versions in step as translations, not as separate texts.

## The storefront pages

Both routes load the page through one query and hand rendering to a shared article:

```tsx
const PrivacyPolicyPage = (): JSX.Element => <ContentPageArticle handle={CONTENT_PAGE_HANDLE.PRIVACY_POLICY} />

export const Route = createFileRoute("/_storefront/privacy-policy")({
  component: PrivacyPolicyPage,
  head: pageHead,
  loader: async ({ context }) => {
    const page = await context.queryClient.query(getContentPageQuery(CONTENT_PAGE_HANDLE.PRIVACY_POLICY, context.locale))

    return { description: page.description, title: page.title } satisfies PageMeta
  },
})
```

`getContentPage` in `src/modules/content-page/use-cases/get-content-page.ts` is a public `GET` server function. It resolves the title, description and body for the requested locale, falling back to Polish, and throws `notFound()` for an unknown handle. It also returns `revisedAt`, the revision date for that locale.

`ContentPageArticle` reads the same query with `useSuspenseQuery`, so the loader's fetch is reused rather than repeated. It renders the title as the only `<h1>`, a "Last updated" line formatted with use-intl, and the body:

```tsx
const { Markdown } = createMarkdownRenderer({ remarkPlugins: [remarkGfm, remarkHeading] })

<Markdown components={MARKDOWN_COMPONENTS}>{page.body}</Markdown>
```

`createMarkdownRenderer` comes from `fumadocs-core` and compiles Markdown at render time, not at build time. Raw HTML in a body is dropped rather than rendered. `remarkHeading` gives every heading a slug `id`, so a link such as `/exchanges-and-returns#returning-goods` lands on its section. The only component override is the link, which adds the reader's locale prefix to store paths and leaves files such as `/forms/formularz_zwrotu.pdf` alone.

The typography lives in `CONTENT_PROSE_CLASS` in `content-page.styles.ts`. The admin editor applies the same class to its editable area, so what an admin sees while typing is what customers see.

Both routes sit under `_storefront`, so they get the navigation, the cart availability banner and the footer.

## Editing in the admin panel

The **Content** item in the admin sidebar opens `/admin/content`, which lists both pages with their last save. Each one opens `/admin/content/$handle`. The route rejects any handle outside `CONTENT_PAGE_HANDLES` with a 404.

The editor page has one tab per locale. Each tab holds three fields:

- **Title**, up to 120 characters, shown as the page heading and in the browser tab.
- **Description**, up to 300 characters with a live counter, used for search results and link previews.
- **Content**, the rich-text body.

The body field is [MDXEditor](https://mdxeditor.dev), which is built on Lexical. `src/integrations/mdxeditor/mdxeditor.plugins.ts` enables only what the storefront can show:

| Toolbar control | Markdown written                          |
| --------------- | ----------------------------------------- |
| Text style      | Paragraph, `##` heading, `###` subheading |
| Bold, Italic    | `**bold**`, `*italic*`                    |
| Lists           | `- item` and `1. item`                    |
| Link            | `[text](href)`                            |
| Divider         | `---`                                     |

Quotes are available through Markdown shortcuts, such as typing `> ` at the start of a line. Shift+Enter starts a new line inside a paragraph, which is how a postal address stays on separate lines. The editor writes it as a trailing backslash, and a custom export visitor keeps two consecutive line breaks as a paragraph break instead.

MDXEditor serialises through `mdast-util-to-markdown`, so text that would otherwise read as Markdown is escaped. A line that starts with `1.` or `-`, a trailing `#` in a heading and emphasis next to punctuation all survive a save unchanged. The editor tests load both seeded pages in both locales into the real editor and check that they come back byte-identical.

The editor's own labels, such as the link dialog and the heading names, come from `pages.admin.content.editor.mdx` in the admin message files through `useContentEditorTranslation`. The editable area takes its accessible name from the field label.

## Saving

**Save** is enabled once something has changed. Ctrl+S or ⌘+S saves too. Leaving the page with unsaved changes asks for confirmation, and closing the tab triggers the browser's own warning.

The form is validated with `contentPageZodSchemas.formValues` before anything is sent. Every locale needs a title, a description and a body. A body may not contain an image, and every link must be an `https://`, `http://`, `mailto:` or `tel:` address or a path on this site. When a locale fails, the editor switches to that tab and marks it, and the toast lists every locale with errors.

`updateContentPage` requires the `content: ["update"]` permission, which only admins have. It saves with optimistic concurrency:

```ts
.where(and(eq(contentPage.handle, handle), eq(contentPage.updatedAt, expectedUpdatedAt)))
```

If another admin saved the page after this one opened it, nothing is written and the editor shows a conflict toast with a **Reload** action. Reload fetches the latest version and replaces the form.

A save publishes immediately. It also:

- moves the "Last updated" date only for the locales whose title or body changed, so fixing a typo in a description does not change the date;
- schedules a realtime invalidation, so open storefront and admin tabs refetch the page;
- records a `content_page_updated` entry under the Content category of the [audit log](/docs/features/audit-log).

Edits typed while a save is in flight are kept after it completes.

## Adding another page

1. Add the handle to `CONTENT_PAGE_HANDLE` and `CONTENT_PAGE_HANDLES`, and its route to `ROUTES` and `CONTENT_PAGE_PATHS`.
2. Write a migration that inserts the row with every locale's title, description and body, using `ON CONFLICT(handle) DO NOTHING`.
3. Copy one of the two storefront routes and change the handle.
4. Link the page from the footer if customers should find it there.

The admin list and editor pick the new page up without changes.

## Message-only storefront pages

Three other pages in the footer's information column are not content pages and have no long-form text:

| Route               | File                               | What it renders                                                    |
| ------------------- | ---------------------------------- | ------------------------------------------------------------------ |
| `/terms-of-service` | `_storefront.terms-of-service.tsx` | `t("title")`, one `t("description")` paragraph, a link home        |
| `/faq`              | `_storefront.faq.tsx`              | The same three-element shape                                       |
| `/about`            | `_storefront.about.tsx`            | An eyebrow, a title, a lead and four paragraphs from `pages.about` |

`/about` is finished copy authored in `messages/{locale}/pages.about.json`. `/terms-of-service` and `/faq` are placeholders, and both render a centred "go home" link. Terms of service can become an editable document by following the steps above.

## Footer links

`src/presentation/components/custom/pages/landing-page/footer/footer.tsx` links these pages:

```tsx
<FooterLink to={ROUTES.TERMS_OF_SERVICE}>{t("terms")}</FooterLink>
<FooterLink to={ROUTES.PRIVACY_POLICY}>{t("privacy")}</FooterLink>
<FooterLink to={ROUTES.EXCHANGES_AND_RETURNS}>{t("returns")}</FooterLink>
```

The checkout payment step also links the terms and privacy pages through `t.rich("termsAgreement", { privacy, terms })`. See [Checkout](/docs/features/checkout).
