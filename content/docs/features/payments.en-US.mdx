Stripe is the only payment provider. There is no other adapter and `payment.provider` is typed as the literal `"stripe"`.

## Clients

| File                                           | What it is                                                                                                                                               |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/integrations/stripe/stripe.server.ts`     | The server SDK: `new StripeServer(env.STRIPE_SECRET_KEY, { apiVersion, appInfo: { name: APP_NAME }, httpClient: StripeServer.createFetchHttpClient() })` |
| `src/integrations/stripe/stripe.client.ts`     | `getStripe(locale)` — a memoised `loadStripe(import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY)`                                                               |
| `src/integrations/stripe/stripe.appearance.ts` | `getStripeAppearance("light" \| "dark")` for the Elements theme                                                                                          |

`createFetchHttpClient()` matters: the Node HTTP client does not work inside a Cloudflare Worker.

The pinned API version is in `stripe.constants.ts`:

```ts
export const STRIPE_API_VERSION = "2026-08-26.dahlia" as const
```

`getStripe` maps the app locale to a Stripe Elements locale (`pl-PL → pl`, `en-US → en`, anything else `auto`) and warns to the console when the publishable key is missing rather than throwing, so a misconfigured dev environment still renders.

## Currency and methods

```ts
const STRIPE_CURRENCY_BY_CODE = { PLN: "pln" } as const satisfies Record<SupportedCurrencyCode, string>
export const STRIPE_CURRENCY = STRIPE_CURRENCY_BY_CODE[STORE_CURRENCY_CODE]
export const CHECKOUT_PAYMENT_METHOD_ORDER = ["card", "blik", "p24"] as const
```

`STORE_CURRENCY_CODE` is `"PLN"` (`src/modules/_core/constants/currency.ts`) and `SUPPORTED_CURRENCY_CODES` contains only `PLN`, so the `satisfies` constraint forces a new currency to be added in both places at once. BLIK and Przelewy24 are the two Polish methods offered alongside cards; wallets and Link are disabled in `PAYMENT_ELEMENT_OPTIONS`.

## The session

Sessions are created with `ui_mode: "elements"`, which means the card form is embedded in `/checkout` rather than redirecting to a Stripe-hosted page:

```ts
const params: StripeType.Checkout.SessionCreateParams = {
  line_items: toLineItems(lines, shippingCost),
  metadata,
  mode: "payment",
  payment_intent_data: { metadata, receipt_email: email },
  return_url: returnUrl,
  ui_mode: "elements",
  ...(customerId === undefined
    ? { customer_email: email }
    : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
}
const discounts = await toSessionDiscounts({ checkoutId, discount })
if (discounts.length > NO_COST) {
  params.discounts = discounts
}

const session = await stripe.checkout.sessions.create(params).catch(async (error: unknown) => {
  await deleteCheckoutCoupons({ checkoutId, discounts })
  throw error
})
```

`customerId` is set only for a signed-in shopper. `handleCreateCheckoutSession` (`src/integrations/stripe/stripe.actions.server.ts`) gets it from `ensureStripeCustomer`, which creates a Stripe customer on first use and stores its id in `user.stripe_customer_id`; `handleUpdateCheckoutSession` reads the stored id through `getStripeCustomerId`. Such a session belongs to that Stripe customer and lets the shopper save the card, which then appears on `/account/payment`. A guest's session carries `customer_email` instead. A signed-in customer can also add a card on `/account/payment` itself, through a card SetupIntent on the same Stripe customer, without paying. See [Account](/docs/features/account).

`returnUrl` is `${origin}/checkout?success=true&session_id={CHECKOUT_SESSION_ID}`, with the `/en-US` prefix for an English checkout, where Stripe fills in the session id and `origin` comes from `resolveRequestOrigin(getRequest())` in `src/lib/request.ts`. It is the address the checkout request came in on, checked against the hosts this build serves, so a local checkout returns to `localhost` or `127.0.0.1`, a preview checkout to the preview host and a production checkout to `martebizuteria.pl`. The `Origin`, `Referer`, `Host` and `X-Forwarded-*` headers are never read, and a request on any other host is refused with `FORBIDDEN` before the Stripe customer, the stock reservation or the checkout row is touched.

The same `metadata` object is attached to the session and to the payment intent, so a webhook that only has the intent can still find the checkout. It carries `checkoutId`, `discountCode` and `discountTotal` (an empty string and `"0"` without a discount), `locale` (from `getCurrentLocale()`), `userId` (empty string for a guest) and the chunked `items0…N` list.

Line items are built from the server-validated prices, plus a literal `"Shipping"` line when the delivery method costs more than zero. The line-item names come from `lineTitle`, which is `"<product title> — <variant title>"` unless the variant title is empty. A discount is not a line item: `toSessionDiscounts` (`src/integrations/stripe/stripe.coupons.server.ts`) creates a one-time Stripe coupon for the amount `resolveCheckoutDiscount` computed, tagged with the checkout id and `source: "marte_checkout"`, and the session receives it in `discounts`. `createStripeSession` deletes that coupon at once when Stripe refuses the session, and the webhook deletes it once the session completes or expires. See [Discounts](/docs/features/discounts).

## The payment row

`payment` (`src/modules/payment/payment.schema.ts`):

| Column            | Notes                                                              |
| ----------------- | ------------------------------------------------------------------ |
| `checkout_id`     | `references(() => checkout.id, { onDelete: "cascade" })`, not null |
| `amount`          | Minor units, not null                                              |
| `currency`        | 3 characters, default `"PLN"`                                      |
| `provider`        | Not null; the only value written is `"stripe"`                     |
| `transaction_id`  | The Stripe **Checkout Session id**, with a unique index            |
| `status`          | `pending \| succeeded \| failed \| refunded`, default `pending`    |
| `refunded_amount` | Minor units, default `0`                                           |
| `refunded_at`     | Nullable timestamp                                                 |

`transaction_id` holding the session id — not the payment intent id — is why several webhook handlers call `resolveTransactionId(paymentIntent)`, which lists sessions filtered by `payment_intent` and takes the first one. The admin refund needs the opposite lookup: it retrieves the session to find the PaymentIntent that Stripe can refund (see [Admin refunds](#admin-refunds)).

Accessors in `payment.accessors.ts`: `createPendingPayment`, `getPaymentByTransactionId`, `getPaymentContextByTransactionId` (joins through to the checkout's `email` and `userId`) and `repointPayment` (moves a row from an expired session id to a new one, updating the amount).

## The webhook endpoint

`src/routes/api/webhooks.stripe.ts` — a `POST` route handler, not a server function:

```ts
const signature = request.headers.get("stripe-signature")

if (signature === null || !env.STRIPE_WEBHOOK_SECRET) {
  return new Response("Missing signature or webhook secret", { status: HTTP_STATUS.BAD_REQUEST })
}

const event = await verifiedStripeEvent(request, signature, env.STRIPE_WEBHOOK_SECRET)
```

`verifiedStripeEvent` uses `stripe.webhooks.constructEventAsync` — the async variant is required on Workers, where the crypto API is promise-based. A failed verification logs and returns 400.

An event type with no handler logs `[Stripe] Safely ignoring unhandled event` and returns `200`, so Stripe does not retry events the shop does not care about. A handler that throws returns `500`, so Stripe **does** retry.

## The eight handled events

`webhookHandlers` in `src/integrations/stripe/stripe.webhooks.tsx` (a `.tsx` file because it builds the confirmation email element):

| Event                                      | Handler                        | Effect                                                                              |
| ------------------------------------------ | ------------------------------ | ----------------------------------------------------------------------------------- |
| `checkout.session.completed`               | `handleFulfillCheckoutSession` | Creates the order, then `deleteCheckoutCoupons` deletes the session's tagged coupon |
| `checkout.session.async_payment_succeeded` | `handleFulfillCheckoutSession` | Same, for BLIK/P24 settling later                                                   |
| `checkout.session.async_payment_failed`    | `handleReleaseCheckoutSession` | Releases the reservation, marks payment and checkout `failed`                       |
| `checkout.session.expired`                 | `handleReleaseCheckoutSession` | Same, then `deleteCheckoutCoupons` deletes the session's tagged coupon              |
| `payment_intent.payment_failed`            | `handlePaymentIntentFailed`    | Audit entry and a warning log only — no state change                                |
| `charge.refunded`                          | `handleChargeRefunded`         | `refundOrder` with `restock: true`                                                  |
| `charge.dispute.created`                   | `handleChargeDisputeCreated`   | `flagOrderDispute`, audit entry, admin-orders invalidation                          |
| `charge.dispute.closed`                    | `handleChargeDisputeClosed`    | Lost → `refundOrder` with `restock: false`; otherwise `clearOrderDispute`           |

The keys come from `STRIPE_WEBHOOK_EVENTS` in `stripe.constants.ts`, so the constant is the list of events to register in the Stripe dashboard.

## Fulfilment

`handleFulfillCheckoutSession` first filters on payment status:

```ts
const FULFILLABLE_PAYMENT_STATUSES = new Set<StripeType.Checkout.Session["payment_status"]>(["no_payment_required", "paid"])
```

A `checkout.session.completed` with `payment_status: "unpaid"` — normal for BLIK and P24 — logs and returns, and the order is created later by `async_payment_succeeded`. The session's coupon is still deleted on `completed`, because deleting it does not change the amount Stripe has already applied to the session.

Then it parses the item lines out of the metadata, calls `fulfillCheckout` and, if an order id comes back:

1. `recordOrderPlacedAudit(orderId, …)` and `recordOrderPaymentCapturedAudit(orderId, …)` with the formatted amount.
2. `scheduleAdminOrdersInvalidation()` and `scheduleProductCatalogInvalidation()`.
3. `notifyOrderConfirmed(session, { currency, lines, orderId })`, which records the outcome on the order and never throws, so a refused confirmation still leaves the webhook answering 200. Its links use the origin of `session.return_url`, the address the checkout was made on, which `resolveDeploymentOrigin` accepts only on a host some deployment serves. Its promise goes to `scheduleBackgroundWork` before it is awaited, so the email finishes even if Stripe stops waiting.

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) resolves the pending checkout from the transaction id, loads the checkout's delivery method and discount, computes the totals, allocates an order number and runs one D1 batch built by `prepareFulfillCheckoutBatch`:

```ts
statements: [
  db.update(payment).set({ status: "succeeded" }).where(eq(payment.transactionId, transactionId)),
  db
    .update(checkout)
    .set({ status: "completed" })
    .where(and(eq(checkout.id, context.checkoutId), eq(checkout.status, "pending"))),
  db.insert(order).values({/* … */}),
  ...(addressSnapshots.length > 0 ? [db.insert(orderAddress).values(addressSnapshots)] : []),
  ...tail, // orderItem insert + one inventory update per line
]
```

The `checkout` update is conditional on `status = "pending"`, which makes the whole webhook **idempotent**: a redelivered event finds the checkout already `completed`, `resolvePendingCheckout` returns `undefined` and `fulfillCheckout` returns without writing anything.

The order totals are derived, not taken from the client: `itemsSubtotal` is the sum of `price * qty` over the metadata lines, `shippingTotal` is the price of the checkout's delivery method, and the discount is recalculated by `calculateDiscountAmount` from the checkout's `discount` row. `computeOrderTotals` (`src/modules/order/order.totals.ts`) caps the discount at items plus shipping and derives `total` and `taxTotal`. `reconcileTotals` compares that total with `session.amount_total`, passed in as `paidAmount`, and only logs an error when they differ.

When the order has a discount, `fulfillCheckout` then schedules `recordDiscountRedemption` in the background, which writes a `discount_redemption` row and increments `discount.usage_count`. See [Discounts](/docs/features/discounts).

The reservation is converted, not released: each line runs `quantityReserved = quantityReserved - qty`, leaving `quantityAvailable` as it was after the reservation. See [Inventory](/docs/features/inventory).

## Release

`prepareReleaseCheckoutBatch` sets the payment to `failed`, the checkout to `failed`, and gives the stock back:

```ts
db.update(inventory)
  .set({
    quantityAvailable: sql`${inventory.quantityAvailable} + min(${inventory.quantityReserved}, ${line.qty})`,
    quantityReserved: sql`max(0, ${inventory.quantityReserved} - ${line.qty})`,
  })
  .where(eq(inventory.variantId, line.variantId))
```

The `min`/`max` clamps mean a double release cannot inflate available stock beyond what was actually reserved.

Release lines are parsed with `checkoutReleaseLinesSchema`, which is `.loose()` — it accepts the full fulfilment line shape and only requires `variantId` and `qty`.

## Refunds and disputes

`handleChargeRefunded` resolves the session from the charge's payment intent and calls `refundOrder({ fullyRefunded: charge.amount_refunded >= charge.amount, refundedAmount: charge.amount_refunded, restock: true, transactionId })`.

`refundOrder` (`src/modules/order/use-cases/refund-order.ts`) is **not** a server function — it is a plain async function callable only from the webhook. It returns early when the payment is already `refunded`, so a redelivered refund event is a no-op. Restocking only happens for a full refund:

```ts
if (input.restock && input.fullyRefunded && settled.orderId !== undefined) {
  const lines = await getRestockLinesForOrder(settled.orderId)
  ...
}
```

`prepareRefundBatch` writes `refundedAmount`, `refundedAt` and `status` (`refunded` when fully refunded, otherwise back to `succeeded`), sets the order to `refunded` on a full refund, and adds `quantityAvailable + quantity` per restock line.

Disputes are stored in `order.metadata` rather than in columns: `flagOrderDispute` merges `{ id, reason, status, amount }` into the JSON with `mergeDisputeMetadata` (`order.display.utils.ts`). A lost dispute is treated as a full refund with `restock: false` and logs `review inventory manually` — the goods are gone, so the stock is not returned. `clearOrderDispute` removes the flag when a dispute closes any other way, and while the flag is present the admin refund is refused (see [Admin refunds](#admin-refunds)).

## Admin refunds

`/admin/orders/$orderId` loads the order through `getAdminOrderQuery`, and its header shows Print, Refund, Cancel order, Fulfill, Mark shipped and Mark delivered as each one applies; the Refund item in the `/admin/orders` row menu opens that page. Refund asks for confirmation and calls `refundAdminOrder` (`src/modules/order/use-cases/refund-admin-order.ts`), a server function guarded by `authorized({ order: ["update"] })`. It checks `canRefundAdminOrder` from `order.admin-actions.utils.ts` (paid, and neither refunded nor cancelled), then `resolveAdminOrderRefundBlocker` from the same file, which names the reason Stripe cannot refund an order:

| Blocker           | When                                                               | Why                                                                                                                   |
| ----------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `noStripePayment` | `order.total` is 0                                                 | A free checkout completes as `no_payment_required`, so Stripe took no payment and there is no PaymentIntent to refund |
| `openDispute`     | `order.metadata` carries the `dispute` that `flagOrderDispute` set | The dispute decides what happens to the payment until `clearOrderDispute` removes the flag                            |

It also requires a `transaction_id` on the payment row. That column holds the Checkout Session id described above, which Stripe does not accept as a `payment_intent`, so the function retrieves the session with `stripe.checkout.sessions.retrieve(transactionId)` and reads its `payment_intent` through `resolveStripeObjectId` (`src/integrations/stripe/stripe.utils.ts`), which returns the id whether Stripe sent it as a string or as an expanded object. A session whose `payment_status` is `no_payment_required`, or that has no PaymentIntent, is refused as well. Otherwise it calls:

```ts
await stripe.refunds.create({ metadata: { orderId }, payment_intent: paymentIntentId }, { idempotencyKey: `admin-order-refund-${orderId}` })
```

which refunds the full amount. The idempotency key is the same for every request about one order, so a double click, a second tab or a second admin sends Stripe a request it has already seen, and Stripe answers with the first result, or refuses the repeat while the first is still in flight, instead of attempting another refund. Stripe keeps a key's result, errors included, for at least 24 hours, so retrying a refund that Stripe rejected returns the same error until the key expires.

A missing order throws `ERROR_CODES.NOT_FOUND` with `ORDER_NOT_FOUND`. Every refused refund throws `ERROR_CODES.CONFLICT` with `ORDER_INVALID_STATE` without requesting a refund. These checks run on the server for every call, whatever the page shows.

The page runs the same predicates on the loaded order. Refund appears when `canRefundAdminOrder` allows it. When `resolveAdminOrderRefundBlocker` returns a blocker, `order-refund-button.tsx` keeps the button visible but disabled and still focusable, and its tooltip explains the blocker with the `pages.admin.orderDetail.refundBlocked` messages.

`refundAdminOrder` writes nothing to the database. The payment and order statuses, the audit entry and the restock arrive with the resulting `charge.refunded` event, through the same `refundOrder` path as a refund made in the Stripe dashboard. The `order: ["refund"]` permission in `auth.access.ts` is still not used by any server function.
