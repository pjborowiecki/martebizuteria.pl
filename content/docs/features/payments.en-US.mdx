Stripe is the only payment provider. There is no other adapter and `payment.provider` is typed as the literal `"stripe"`.

## Clients

| File                                           | What it is                                                                                                                                               |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/integrations/stripe/stripe.server.ts`     | The server SDK: `new StripeServer(env.STRIPE_SECRET_KEY, { apiVersion, appInfo: { name: APP_NAME }, httpClient: StripeServer.createFetchHttpClient() })` |
| `src/integrations/stripe/stripe.client.ts`     | `getStripe(locale)` — a memoised `loadStripe(import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY)`                                                               |
| `src/integrations/stripe/stripe.appearance.ts` | `getStripeAppearance("light" \| "dark")` for the Elements theme                                                                                          |

`createFetchHttpClient()` matters: the Node HTTP client does not work inside a Cloudflare Worker.

The pinned API version is in `stripe.constants.ts`:

```ts
export const STRIPE_API_VERSION = "2026-09-30.endive" as const
```

It is the version `stripe` 23.0.0 pins, and every call the server makes uses it. A webhook event is rendered in the API version of the endpoint it is sent to instead, which Stripe fixes when the endpoint is created; see [Stripe: The webhook endpoints' API version](/docs/integrations/stripe#the-webhook-endpoints-api-version).

`getStripe` maps the app locale to a Stripe Elements locale (`pl-PL → pl`, `en-US → en`, anything else `auto`) and warns to the console when the publishable key is missing rather than throwing, so a misconfigured dev environment still renders.

## Currency and methods

```ts
const STRIPE_CURRENCY_BY_CODE = { PLN: "pln" } as const satisfies Record<SupportedCurrencyCode, string>
export const STRIPE_CURRENCY = STRIPE_CURRENCY_BY_CODE[STORE_CURRENCY_CODE]
export const CHECKOUT_PAYMENT_METHOD_ORDER = ["card", "blik", "p24"] as const
```

`STORE_CURRENCY_CODE` is `"PLN"` (`src/modules/_core/constants/currency.ts`) and `SUPPORTED_CURRENCY_CODES` contains only `PLN`, so the `satisfies` constraint forces a new currency to be added in both places at once. BLIK and Przelewy24 are the two Polish methods offered alongside cards; wallets and Link are disabled in `PAYMENT_ELEMENT_OPTIONS`.

None of the three is a delayed-notification method in Stripe's sense: Stripe reports the result of each payment while the shopper is paying.

- **Card.** The payment succeeds or is declined when the shopper confirms it, after a 3-D Secure check when the card's bank asks for one.
- **BLIK.** The shopper types a six-digit code from the banking app, valid for two minutes, and then approves the payment in the app. While the app waits, the payment intent is `requires_action` with the next action `blik_authorize` and the session stays `open`. Stripe gives the shopper 60 seconds to approve; an attempt not approved by then times out, and paying again needs a new code.
- **Przelewy24.** The shopper is redirected to Przelewy24, chooses a bank, authorises the payment there and comes back to `return_url`. While the shopper is away, the payment intent is `requires_action` with the next action `redirect_to_url`.

An approved payment intent becomes `succeeded` and completes the session with `payment_status: "paid"`, so `checkout.session.completed`, or the return page before it, places the order. An attempt that is refused, fails or is not approved in time sends `payment_intent.payment_failed`, puts the intent back to `requires_payment_method` and leaves the session `open` for another try. According to Stripe, none of the three passes through `processing`. Stripe's settlement timing for Przelewy24, up to two business days, is when the money reaches the shop's Stripe balance, not when the payment is confirmed. A `complete` session with `payment_status: "unpaid"`, and the `checkout.session.async_payment_succeeded` or `async_payment_failed` event that follows it, belong to delayed-notification methods such as bank debits, whose payment stays `processing` for days. The shop offers none, and handles them so that such a method, should it ever be offered, still becomes an order only once it is paid.

## The session

Sessions are created with `ui_mode: "elements"`, which means the card form is embedded in `/checkout` rather than redirecting to a Stripe-hosted page:

```ts
const params: StripeType.Checkout.SessionCreateParams = {
  expires_at: Math.floor(Date.now() / MILLISECONDS_PER_SECOND) + CHECKOUT_SESSION_LIFETIME_SECONDS,
  line_items: toLineItems(lines, { cost: shippingCost, name: messages.deliveryLineItem[deliveryType] }),
  metadata,
  mode: "payment",
  payment_intent_data: { description: messages.paymentDescription, metadata, receipt_email: email },
  phone_number_collection: { enabled: true },
  return_url: returnUrl,
  ui_mode: "elements",
  ...(customerId === undefined
    ? { customer_email: email }
    : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
}
const discounts = await toSessionDiscounts({ checkoutId, discount })
if (discounts.length > NO_COST) {
  params.discounts = discounts
}

const session = await stripe.checkout.sessions.create(params).catch(async (error: unknown) => {
  await deleteCheckoutCoupons({ checkoutId, discounts })
  throw error
})
```

`expires_at` is `CHECKOUT_SESSION_LIFETIME_SECONDS` (1920 seconds, in `stripe.constants.ts`) from now. Stripe accepts 30 minutes to 24 hours and defaults to 24 hours, and the session holds its stock until it expires, so the default let one abandoned or scripted checkout keep a piece away from every other shopper for a day. 32 minutes is Stripe's minimum plus a margin for the time the request takes, and is ample for a card, BLIK or a Przelewy24 transfer. The expiry webhook then releases the stock (see [Inventory](/docs/features/inventory)).

`customerId` is set only for a signed-in shopper. `handleCreateCheckoutSession` (`src/integrations/stripe/stripe.actions.server.ts`) gets it from `ensureStripeCustomerWithEmail` with the email typed at checkout, which creates a Stripe customer with that email on first use and stores its id in `user.stripe_customer_id`, and otherwise sets the stored customer's email to it with `stripe.customers.update`. Stripe locks a session created with `customer` to the customer's email and bills the payment under it, so without that update a signed-in shopper who typed a different address, or whose customer dates from an earlier checkout, would be billed under the old one (see [Stripe](/docs/integrations/stripe)). `handleUpdateCheckoutSession` calls `ensureStripeCustomerWithEmail` with the edited email for every signed-in request: for a checkout the account already owns, and when it hands a guest's checkout to the account that has signed in since, which also sets the checkout's `user_id` so the order lands in that account (see [Checkout](/docs/features/checkout)). Such a session belongs to that Stripe customer and lets the shopper save the card, which then appears on `/account/payment`. A guest's session carries `customer_email` instead. A signed-in customer can also add a card on `/account/payment` itself, through a card SetupIntent on the same Stripe customer, without paying. See [Account](/docs/features/account).

`returnUrl` is `${origin}/checkout?success=true&session_id={CHECKOUT_SESSION_ID}`, with the `/en-US` prefix for an English checkout, where Stripe fills in the session id and `origin` comes from `resolveRequestOrigin(getRequest())` in `src/lib/request.ts`. It is the address the checkout request came in on, checked against the hosts this build serves, so a local checkout returns to `localhost` or `127.0.0.1`, a preview checkout to the preview host and a production checkout to `martebizuteria.pl` or `martebizuteria.pjborowiecki.workers.dev`, whichever the shopper is using (`appHostsForMode` in `src/modules/_core/constants/api.ts`). Stripe uses it for a payment that leaves the page, such as Przelewy24, whether or not the shopper paid, so the page asks `getCheckoutSessionStatus` about the returned session first and shows the confirmation only for a `complete` one; an abandoned payment goes back to the payment step with the basket kept, and one the bank is still confirming waits for the bank there (see [Checkout](/docs/features/checkout)). The `Origin`, `Referer`, `Host` and `X-Forwarded-*` headers are never read, and a request on any other host is refused with `FORBIDDEN` before the Stripe customer, the stock reservation or the checkout row is touched.

`metadata` carries `checkoutId`, `discountCode` and `discountTotal` (an empty string and `"0"` without a discount), `locale` (from `getCurrentLocale()`), `shippingTotal` (the delivery charge in minor units, `"0"` when delivery is free), `userId` (empty string for a guest) and `deployment` (see [the webhook endpoint](#the-webhook-endpoint)). The session and the payment intent get these seven fields alone, so a webhook that only has the intent can still find the checkout, and the cart stays on the session's payment row in D1 (see [Stripe: The session names the checkout, the database holds the cart](/docs/integrations/stripe#the-session-names-the-checkout-the-database-holds-the-cart)).

`payment_intent_data.description` is `paymentDescription` from `pages.checkout` in the checkout's language, "M'Arte – zamówienie w sklepie internetowym" or "M'Arte – online shop order". A BLIK banking app shows it, up to 70 characters, on the first two lines of the request to approve the payment, above the shop's web address. The session sets no statement descriptor, which Stripe refuses for a card charge, so bank and card statements show the account's own descriptor (see [Stripe: What the shopper's bank shows](/docs/integrations/stripe#what-the-shoppers-bank-shows)).

Line items are built from the server-validated prices, plus a delivery line when delivery costs more than zero, which it does not once the basket reaches the free delivery threshold (see [Shipping and delivery: Free delivery](/docs/features/shipping-and-delivery#free-delivery)). That line is named in the shopper's language: `createStripeSession` loads the `pages.checkout` messages for the checkout's locale and takes `deliveryLineItem.<type>` for the method's type, so the line on a Polish receipt reads "Dostawa kurierem" or "Dostawa do Paczkomatu InPost" and on an English one "Courier delivery" or "InPost Parcel Locker delivery". The method's own name is not used, so the line names the kind of delivery rather than the method the owner named in Settings. Each product line is named `"<product title> — <variant title>"`, with the product's title in the shopper's language and the variant's title from the catalogue, or the product title alone when the variant is `Default`; the names the basket remembers are never used. A discount is not a line item: `toSessionDiscounts` (`src/integrations/stripe/stripe.coupons.server.ts`) creates a one-time Stripe coupon for the amount `resolveCheckoutDiscount` computed, tagged with the checkout id and `source: "marte_checkout"`, and the session receives it in `discounts`. `createStripeSession` deletes that coupon at once when Stripe refuses the session, and the webhook deletes it once the session completes or expires. See [Discounts](/docs/features/discounts).

## The payment row

`payment` (`src/modules/payment/payment.schema.ts`):

| Column            | Notes                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- |
| `checkout_id`     | `references(() => checkout.id, { onDelete: "cascade" })`, not null                                                    |
| `amount`          | Minor units, not null                                                                                                 |
| `currency`        | 3 characters, default `"PLN"`                                                                                         |
| `provider`        | Not null; the only value written is `"stripe"`                                                                        |
| `transaction_id`  | The Stripe **Checkout Session id**, with a unique index                                                               |
| `status`          | `pending \| succeeded \| failed \| refunded`, default `pending`                                                       |
| `refunded_amount` | Minor units, default `0`                                                                                              |
| `refunded_at`     | Nullable timestamp                                                                                                    |
| `lines`           | JSON `{ handle, imageUrl, price, qty, title, variantId }[]`, the cart the session charges for, not null, default `[]` |
| `reserved_lines`  | JSON `{ qty, variantId }[]` the session holds in stock, not null, default `[]`                                        |

`transaction_id` holding the session id — not the payment intent id — is why several webhook handlers call `resolveCheckoutSession(paymentIntent)`, which lists sessions filtered by `payment_intent` and takes the first one. The admin refund needs the opposite lookup: it retrieves the session to find the PaymentIntent that Stripe can refund (see [Admin refunds](#admin-refunds)).

Accessors in `payment.accessors.ts`: `createPendingPayment`, which records the session's `lines` and `reserved_lines` with it, `getPaymentByTransactionId`, `getPaymentContextByTransactionId` (joins through to the checkout's `email`, `userId`, `status` and `created_at`, and returns the payment's own `status`), `getCheckoutLinesByTransactionId`, which returns the session's `lines`, and `getHeldLinesByTransactionId`, which returns `reserved_lines` only while the payment and its checkout are both `pending`. A checkout update moves the row onto its replacement session through `supersedeCheckoutSession` in `src/modules/checkout/use-cases/supersede-checkout-session.server.ts`, which moves only a `pending` payment of a `pending` checkout, updating the amount, the lines and the reserved lines.

The database, not the Stripe metadata, holds what a session sells and holds:

- Fulfilment and the order emails read `payment.lines` through `readCheckoutSessionLines` in `src/modules/checkout/checkout.session-lines.server.ts`. A session created before `20261016100000_payment_lines.sql` added the column has an empty `lines`, and for it the function parses the item lines its metadata still carries (`parseCheckoutSessionFulfillmentLines` in `checkout-metadata.zod.ts`).
- The release reads `reserved_lines` through `getHeldLinesByTransactionId`, and so does the cart's availability check, which counts a shopper's own reservation without calling Stripe.

## The webhook endpoint

`src/routes/api/webhooks.stripe.ts` — a `POST` route handler, not a server function:

```ts
const signature = request.headers.get("stripe-signature")

if (signature === null || !env.STRIPE_WEBHOOK_SECRET) {
  return new Response("Missing signature or webhook secret", { status: HTTP_STATUS.BAD_REQUEST })
}

const event = await verifiedStripeEvent(request, signature, env.STRIPE_WEBHOOK_SECRET)
```

`verifiedStripeEvent` uses `stripe.webhooks.constructEventAsync` — the async variant is required on Workers, where the crypto API is promise-based. A failed verification logs and returns 400.

A verified event must also come from the Stripe mode the environment runs in. `requiredStripeMode(env.APP_ENV)` from `stripe.keys.ts`, the rule the deploy check applies to the keys, accepts only live events (`livemode: true`) in `production` and only test events everywhere else, `test` included. An event from the other mode belongs to payments this environment never took, so before any handler runs the route logs `[Stripe] Ignoring <mode> event <id> (<type>): <APP_ENV> accepts only <mode> events` and answers `200` with `{ received: true }`, which stops Stripe redelivering it. That line means the endpoint that sent the event, whose signing secret this environment holds as `STRIPE_WEBHOOK_SECRET`, runs in the other mode.

Preview, local development and local test runs share one Stripe test account, and Stripe sends every event of the account to every endpoint registered on it, so a checkout a local test run opened also reaches the preview endpoint, whose database never held it. Each session is therefore stamped with the deployment that keeps its checkout: `createStripeSession` sets `deployment` in the `metadata` it gives the session and its payment intent to `stripeDeploymentOf(env.APP_ENV)` from `src/integrations/stripe/stripe.deployment.ts`, the D1 database name the Worker writes its checkouts to: `martebizuteria-preview` for `development` and `preview`, `martebizuteria-test` for `test` and `martebizuteria` for `production`. Development counts as preview because `bun run dev` reaches the remote preview database through `remoteBindings`, so either one can fulfil the other's session. A preview build served by `bun run start` keeps a simulated local database instead, but it never stamps a session: it runs on `127.0.0.1:3000`, a host the preview build's `resolveRequestOrigin` refuses, so it cannot open a checkout. `stripe.deployment.test.ts` reads `wrangler.jsonc` and fails when a Worker's database no longer matches its stamp. After the mode check, for a test-mode event, `foreignStripeDeployment` reads `deployment` from the event's object; when it names another deployment the route logs `[Stripe] Ignoring event <id> (<type>): its checkout belongs to <deployment>, while <APP_ENV> keeps its checkouts in <deployment>` at `info` level and answers `200` with `{ received: true }`, so no handler runs, no `order.fulfillment_failed` or `order.released` entry is written and no alert is sent. A session stamped with this deployment's own name, and a session created before the stamp existed, run their handlers as before, so a paid session of this deployment that no payment row carries still records `order.fulfillment_failed` and sends `paidCheckoutWithoutOrder`. A live event skips the check: only production accepts live events, so no other deployment can own a live session, and production handles it whatever its stamp says, also after its database is renamed and the stamp of new sessions changes.

An event type with no handler logs `[Stripe] Safely ignoring unhandled event` and returns `200`, so Stripe does not retry events the shop does not care about. A handler that throws returns `500`, so Stripe **does** retry, and the route hands `sendIncidentAlert` a `stripeWebhookFailed` incident for the event in the background, keyed by its id and kept open for the three days Stripe retries it, so `RESEND_EMAIL_FROM` hears of each failed event once, a paid session whose order could not be created included; see [Monitoring and alerts](/docs/guides/monitoring-and-alerts).

## The ten handled events

`webhookHandlers` in `src/integrations/stripe/stripe.webhooks.ts`, which leaves composing the emails to the order and checkout use cases that send them:

| Event                                      | Handler                        | Effect                                                                               |
| ------------------------------------------ | ------------------------------ | ------------------------------------------------------------------------------------ |
| `checkout.session.completed`               | `handleFulfillCheckoutSession` | Creates the order, then `deleteCheckoutCoupons` deletes the session's tagged coupon  |
| `checkout.session.async_payment_succeeded` | `handleFulfillCheckoutSession` | Same, for a delayed-notification payment; card, BLIK and Przelewy24 never send it    |
| `checkout.session.async_payment_failed`    | `handleAsyncPaymentFailed`     | Releases the reservation, marks payment and checkout `failed`, emails the customer   |
| `checkout.session.expired`                 | `handleReleaseCheckoutSession` | Same release, then `deleteCheckoutCoupons` deletes the session's tagged coupon       |
| `payment_intent.payment_failed`            | `handlePaymentIntentFailed`    | Audit entry and a warning log only — no state change                                 |
| `charge.refunded`                          | `handleChargeRefunded`         | `refundOrder`, which never restocks, then the refund email when there is news        |
| `refund.failed`                            | `handleRefundUndone`           | `undoFailedRefund` takes the refund off the order, audit entry, `refundFailed` alert |
| `refund.updated`                           | `handleRefundUndone`           | Same, when the refund is now `canceled` or `failed`; any other update is ignored     |
| `charge.dispute.created`                   | `handleChargeDisputeCreated`   | `flagOrderDispute`, audit entry, admin-orders invalidation                           |
| `charge.dispute.closed`                    | `handleChargeDisputeClosed`    | Lost → `refundOrder`; otherwise `clearOrderDispute`                                  |

The keys come from `STRIPE_WEBHOOK_EVENTS` in `stripe.constants.ts`, so the constant is the list of events to register in the Stripe dashboard. Each webhook endpoint, preview's and production's, must have all ten enabled, `refund.failed` and `refund.updated` included; an endpoint without them never tells the shop that a refund failed.

## Fulfilment

`handleFulfillCheckoutSession` first filters on payment status:

```ts
const FULFILLABLE_PAYMENT_STATUSES = new Set<StripeType.Checkout.Session["payment_status"]>(["no_payment_required", "paid"])
```

A `checkout.session.completed` with `payment_status: "unpaid"`, which only a delayed-notification method sends (see [Currency and methods](#currency-and-methods)), logs and returns, and the order is created later by `async_payment_succeeded`. A session paid by card, BLIK or Przelewy24 always completes `paid`. The session's coupon is still deleted on `completed`, because deleting it does not change the amount Stripe has already applied to the session.

Then `createOrderFromPaidSession` reads the item lines from the session's payment row with `readCheckoutSessionLines` and calls `fulfillCheckout`, and if an order id comes back, `announcePlacedOrder` does the rest. Both live in `src/integrations/stripe/stripe.fulfillment.server.ts`, which the return page uses too (see [Fulfilment from the return page](#fulfilment-from-the-return-page)):

1. `recordOrderPaymentCapturedAudit(orderId, …)` with the formatted amount. `fulfillCheckout` has already recorded `order.placed` with the checkout's e-mail, the one the order carries, once its batch committed.
2. `scheduleAdminOrdersInvalidation()` and `scheduleProductCatalogInvalidation()`.
3. `sendOrderConfirmationEmail(session, orderId)` and `sendNewOrderEmail(orderId, session.return_url)`, side by side in one `Promise.all`, which `announcePlacedOrder` returns. Each records its outcome on the order and never throws, so a refused email still leaves the webhook answering 200, and a refused email is tried twice more after the webhook has answered. Their links use the origin of `session.return_url`, the address the checkout was made on, which `resolveDeploymentOrigin` accepts only on a host some deployment serves. The webhook hands the promise to `scheduleBackgroundWork` before it awaits it, so both emails finish even if Stripe stops waiting. The shop's notice goes to `RESEND_EMAIL_FROM`; see [Transactional email](/docs/features/email#the-shops-new-order-email).

`fulfillCheckout` (`src/modules/checkout/use-cases/fulfill-checkout.server.ts`) resolves the pending checkout from the transaction id, loads the checkout's delivery method and discount, computes the totals and runs one D1 batch built by `prepareFulfillCheckoutBatch`. Completing the checkout also clears its `client_address`, which is kept only while a checkout is open (see [Checkout](/docs/features/checkout#limits-on-holding-stock)):

```ts
statements: [
  db.update(payment).set({ status: "succeeded" }).where(eq(payment.transactionId, transactionId)),
  db
    .update(checkout)
    .set({ clientAddress: sql`NULL`, status: "completed" })
    .where(and(eq(checkout.id, context.checkoutId), eq(checkout.status, "pending"))),
  orderNumberAllocation.statement, // bumps this year's order_number_sequence row
  db.insert(order).values({ /* …, */ orderNumber: orderNumberAllocation.orderNumber }),
  ...(addressSnapshots.length > 0 ? [db.insert(orderAddress).values(addressSnapshots)] : []),
  ...tail, // orderItem insert + one inventory update per line
]
```

Fulfilment is **idempotent**, so a paid session becomes exactly one order however many of its events Stripe delivers and in whatever order. A redelivered event finds the checkout already `completed`, `resolvePendingCheckout` returns `undefined` and `fulfillCheckout` returns without writing anything. Two deliveries can also run side by side, and both read the checkout as `pending`: one event that Stripe delivers twice, or the return page placing the order while the webhook does (see [Fulfilment from the return page](#fulfilment-from-the-return-page)). The first batch to commit places the order; the second fails as a whole on the unique `order.checkout_id` index, so it writes nothing, issues no order number and moves no stock. `commitFulfillment` in `fulfill-checkout.server.ts` then looks the checkout's order up with `getOrderByCheckoutId` and compares its id with the `orderId` its own batch inserted. An order with another id was placed by the other delivery, so it logs `Checkout <id> already became Order <order id> through another delivery of <session id>.` and `fulfillCheckout` returns `undefined`, exactly as for a redelivery: the handler records no `order.placed`, `order.payment_captured` or `order.fulfillment_failed` entry, sends no email, raises no alert and answers `200`. An order with its own id means D1 committed the batch and only its answer failed, as with `D1_ERROR: Network connection lost.`, which D1 does not retry for a write. `commitFulfillment` then logs `Checkout <id> became Order <order id> although its batch reported an error:` with the error at `warn` level and counts the batch as committed, so the order is audited, refreshed in the admin panel and the catalogue, and announced to the shopper and the shop once, as after a batch that answered. Only a failed batch that leaves the checkout without an order is a real failure, and so is one whose order lookup fails as well, which logs `Could not look up the order of checkout <id>:` first: either way the batch's own error is rethrown (see below). `src/integrations/stripe/__test__/stripe.webhooks.fulfillment.integration.test.ts` delivers one paid session's `checkout.session.completed` twice side by side, a redelivery, a status check from the return page during the race, the return page placing the order before the event and alongside two deliveries of it, a batch that commits and then reports an error, an unpaid `completed` followed by `async_payment_succeeded`, and an `async_payment_failed` delivered twice, against the migrated schema.

The order number comes from `prepareOrderNumberAllocation` (`src/modules/order/order.number.server.ts`): one statement bumps the counter for the current year in Poland in `order_number_sequence` and the order insert reads the number back with a subquery, formatted as `MRT-<year>-<five digits>`. Both are in the batch, so a delivery whose batch fails rolls the counter back with everything else and the retry gets the same number instead of leaving a gap.

Each order line keeps what the customer was charged for: the title, price, quantity and image come from the payment's `lines`, written when the session was created. Its `variant_id` and `product_id` are looked up in the same insert (`select id from product_variant where id = …`), so a variant or product deleted while the customer was paying leaves both `null` instead of failing the `order_item.variant_id` foreign key, and the order is still created. The admin normally cannot delete such a variant at all (see [Admin catalog](/docs/features/admin-catalog)); the lookup covers a checkout opened in the moment between that check and the delete. Fulfilment never reads `product.status` either, so a session paid before its product was archived or returned to draft, or one Stripe would not expire when that save tried to close it, still becomes an order line linked to the product. The save expires every other open session holding the product (see [Admin catalog](/docs/features/admin-catalog#writing)), and new and edited checkouts refuse an unpublished product (see [Checkout](/docs/features/checkout)).

**When a paid session creates no order**, `handleFulfillCheckoutSession` logs the error and records `order.fulfillment_failed` through `recordOrderFulfillmentFailedAudit` at `error` severity, so it shows in the admin audit log and its errors count. The entry's target is the session id and its detail reads `<amount> — <customer email> — <cause>`. Its id is `order.fulfillment_failed:<session id>`, so a session has one such entry however many times Stripe delivers its event: a retry that fails again logs its error but leaves the entry, its time and its detail as the first failure wrote them, and the errors count goes up once per session. If the admin deletes the entry and the session then fails again, a new entry is recorded. A failure from the code path or the database, including an older session's item metadata that does not parse, is then rethrown, the route answers `500` and Stripe retries the event. `resolvePendingCheckout` throws `ERROR_CODES.NOT_FOUND` when no payment row carries the session, when its checkout is gone, or when the checkout is in any state but `pending` or `completed` (for example `failed` after a release); a retry cannot change that, so after recording it the handler starts a `paidCheckoutWithoutOrder` alert to `RESEND_EMAIL_FROM` for the session in the background, answers `200`, and the admin refunds the customer in Stripe.

The order totals are derived, not taken from the client: `itemsSubtotal` is the sum of `price * qty` over the payment's `lines`, `shippingTotal` is the delivery charge the session recorded in its `shippingTotal` metadata, read by `resolveCheckoutSessionShippingTotal` (`checkout-metadata.zod.ts`), and the discount is the one the session recorded in its `discountTotal` metadata, read by `resolveCheckoutSessionDiscountTotal`. Both are taken from the session because the owner can change a method's price, the free delivery threshold or a discount code while the shopper pays, and the order has to record what the shopper was charged. A session opened before these fields existed falls back to the current price of the checkout's delivery method and to a discount recalculated by `calculateDiscountAmount` from the checkout's `discount` row. `computeOrderTotals` (`src/modules/order/order.totals.ts`) caps the discount at items plus shipping and derives `total` and `taxTotal`. `reconcileTotals` compares that total with `session.amount_total`, passed in as `paidAmount`, and only logs an error when they differ.

The same batch converts the checkout's hold on its discount code: `prepareDiscountRedemption` deletes the checkout's `discount_claim` rows and, when the order has a discount, writes a `discount_redemption` row and increments `discount.usage_count`, without checking any limit, because the customer has already paid. The order and its redemption therefore commit together, and a second delivery that loses the race on `order.checkout_id` counts nothing and audits no redemption. See [Discounts](/docs/features/discounts#on-fulfilment).

The reservation is converted, not released: each line runs `quantityReserved = quantityReserved - qty`, leaving `quantityAvailable` as it was after the reservation. See [Inventory](/docs/features/inventory).

### Fulfilment from the return page

Stripe recommends placing the order from the landing page as well, because webhooks can be late ([Fulfill orders](https://docs.stripe.com/checkout/fulfillment#trigger-fulfillment-on-landing-page)). The webhook stays the path that makes every paid session an order, also when the shopper never comes back; the return page only gets there sooner while the shopper is on it. The confirmation page asks `getOrderConfirmation` (`src/modules/order/use-cases/get-order-confirmation.ts`) for the session named by `?success=true&session_id=<id>`. That server function reads the session's payment row first. While the payment is `pending` it passes `assertWithinRateLimit("checkout-status", RATE_LIMITS.CHECKOUT, …)`, the per-address limit `getCheckoutSessionStatus` uses, and calls `fulfillReturnedCheckoutSession(sessionId)` before it reads the order. A payment that is not `pending` costs no Stripe call: a `succeeded` one already has its order, and a session no payment row in this deployment's database carries, such as another deployment's checkout, is never fulfilled here.

`fulfillReturnedCheckoutSession` takes nothing from the browser but the id. It retrieves the session from Stripe itself and goes on only when the session's `status` is `complete` and its `payment_status` is in `FULFILLABLE_PAYMENT_STATUSES`, so an open, expired or unpaid session is left to its events. For a paid session it runs `createOrderFromPaidSession`, the same `fulfillCheckout` the webhook runs, and only when that call placed the order does it hand `announcePlacedOrder` to `scheduleBackgroundWork`: the two audits, the admin and catalogue refresh and the two emails happen once, and the page's answer does not wait for Resend. Whichever of the page and the webhook commits first places the order. The other finds the checkout `completed`, or loses on `order.checkout_id` as described above, and records, refreshes and sends nothing, so a session paid while the shopper waits still gets one order, one set of audit entries and one confirmation email. The session's coupon is still deleted by the webhook's `checkout.session.completed`. A failure on this path is logged as `Paid Checkout Session <id> created no order from its return page:` and the page hears that there is no order yet. It records no `order.fulfillment_failed` entry and raises no alert, because the webhook does both and Stripe retries it. A failure to reach Stripe fails the request, and the confirmation asks again (see [Checkout: Payment step](/docs/features/checkout#payment-step)).

## Release

`releaseCheckout` runs `prepareReleaseCheckoutBatch` without reading anything first. The batch gives the stock back, deletes the checkout's `discount_claim` rows so the discount use it held is free again, then sets the checkout to `failed`, then the payment:

```ts
db.update(inventory)
  .set({
    quantityAvailable: sql`${inventory.quantityAvailable} + min(${inventory.quantityReserved}, ${line.qty})`,
    quantityReserved: sql`max(0, ${inventory.quantityReserved} - ${line.qty})`,
  })
  .where(and(eq(inventory.variantId, line.variantId), exists(releasableSession)))
```

`releasableSession` selects the checkout of the payment with this `transaction_id` and `status = "pending"`, joined to that checkout while it is still `pending`; the stock updates require it to exist and the claim delete is limited to its checkout. The checkout update requires the same pending payment, and the payment update requires its checkout to be `failed` by then. Each statement sees the ones before it in the D1 batch, so the stock goes back only while both rows are still `pending`, and the whole batch acts or none of it does. A redelivered event, two deliveries running side by side, and an expiry webhook for a session that a checkout update has already replaced (`supersedeCheckoutSession` moved the payment off it) all find nothing to release.

The payment update returns the id of the payment it failed, and `releaseCheckout` resolves to whether there was one. `handleAsyncPaymentFailed` emails the customer that the payment failed only then, so the email goes out once per failed payment whatever Stripe redelivers; see [Transactional email](/docs/features/email#cancellation-refund-and-failed-payment). An expired session is released the same way and emails nobody. Both events record the `order.released` audit entry, refresh the storefront's availability and log the release only when `releaseCheckout` reports a release, so the expiry of a session a checkout update replaced, whose payment and stock had moved to the replacement, leaves no entry.

The `min`/`max` clamps mean a double release cannot inflate available stock beyond what was actually reserved.

The lines to release come from the payment's `reserved_lines`, which `handleReleaseCheckoutSession` reads with `getHeldLinesByTransactionId` before the batch. That read returns nothing once the payment or its checkout has left `pending`, and the batch's own guards refuse the release anyway, so the handler logs `Session <id> held nothing to release: its checkout was paid, released or moved to a newer session.` and records nothing. The shop also releases a session as soon as it learns the session has expired, without waiting for the webhook: `releaseExpiredCheckoutSession` in `stripe.actions.server.ts` runs the same `releaseCheckout` with the same lines when a checkout update or the return page's status check finds the session expired, and after the shop expires it itself, as a checkout edited past its session's lifetime and an admin save that takes a product off sale do.

## Refunds and disputes

`handleChargeRefunded` resolves the session from the charge's payment intent and reads the charge's refunds from Stripe with `readStandingRefunds(charge.id)` (`src/integrations/stripe/stripe.refunds.server.ts`), which lists them through every page and adds up those whose status is not `failed` or `canceled`. It then calls `refundOrder({ fullyRefunded: total >= charge.amount, refundedAmount: total, transactionId })`. The event's own `amount_refunded` is a snapshot taken when the refund was created, so a `charge.refunded` handled after its refund already failed, or delivered late, would record money that never reached the customer; the total of the refunds that still stand is what Stripe holds when the event is handled. When no refund stands, the handler logs `Charge <id> has no refund that still stands; nothing to record.` and records nothing.

`refundOrder` (`src/modules/order/use-cases/refund-order.server.ts`) is **not** a server function — it is a plain async function callable only from the webhook. It returns early when the payment is already `refunded`, so a redelivered full refund is a no-op. It never returns stock. A refund says nothing about whether the goods came back: a refund for a parcel lost in the post, a goodwill refund and a lost dispute all leave the piece with the customer or nowhere, and putting a one-off piece back on sale would sell something the shop does not have. The admin returns an order's items to stock in the Refund dialog or later with Return to stock (see [Orders](/docs/features/orders#admin-actions)).

`prepareRefundBatch` writes `refundedAmount`, `refundedAt` and `status` (`refunded` when fully refunded, otherwise `succeeded`), and only to a payment that is not already `refunded`: an older partial refund's event that `refundOrder` read before a full refund was recorded, and whose batch lands after it, leaves the payment `refunded` with its amount and refund time. `refundedAmount` becomes the larger of the recorded amount and the event's, through SQLite's `max()`, so it only ever grows. On a full refund of a payment that has an order, it then sets the order to `refunded` while its status is neither `cancelled` nor `refunded`, so a cancelled order keeps the status `cancelled`, and only its payment becomes `refunded`. It leaves `order.restocked_at` alone, so a refunded order whose items never went back carries the "Not returned to stock" tag and a Return to stock button on its admin page until the admin decides. Since nothing on sale changes, the handler refreshes the admin's order lists but not the catalogue.

The batch opens with a select of the payment's `refunded_amount` and status and its order's status, which runs inside the same D1 transaction before the writes. When it finds the payment already `refunded`, another event recorded the full refund after `refundOrder` checked, so the batch changed nothing and `refundOrder` returns nothing and writes no audit entry. Otherwise `refundOrder` returns the refund the customer has not been told about, `{ amount, fullyRefunded, orderId }` with `amount` the total of the standing refunds minus what the payment had recorded, only when that is above zero and the order was not `cancelled`; a cancellation already emailed the customer about its own refund. `handleChargeRefunded` passes it to `sendOrderRefundedEmail` with the session's `return_url` and the id of the newest refund that stands, which keys the email, so each refund, partial or full, is emailed once, however often and in whatever order Stripe delivers its events: an older event delivered after a newer one leaves the larger amount in place, so a later redelivery of the newer one finds nothing new. A lost dispute calls `refundOrder` too but sends no email.

**A refund can still fail after `charge.refunded`.** Stripe reports a refund as soon as it is created, and the customer's bank can return it later: a closed account or card, a BLIK or Przelewy24 transfer the bank refuses (P24 refunds take up to three business days), or a card refund that waited for the shop's Stripe balance until it expired (`insufficient_funds`). A card refund can also be cancelled in the Stripe Dashboard for a short while. Stripe then moves the money back to the shop's balance and sends `refund.failed`, or `refund.updated` with the refund `canceled`, and the shop has to pay the customer back another way. `handleRefundUndone` handles both events and returns at once for any other `refund.updated`, such as the bank reference arriving. It resolves the Checkout Session from the refund's payment intent, reads the charge's refunds that still stand with `readStandingRefunds` and calls `undoFailedRefund` (`src/modules/order/use-cases/undo-failed-refund.server.ts`). That use case finds the payment and its order by the session id. When the payment records more than the standing refunds add up to, one batch sets `refunded_amount` to that total, the payment status to `succeeded` and clears `refunded_at` when nothing stands, guarded on the recorded amount still being higher, and moves an order that is `refunded` back to `completed` when it was delivered and to `processing` otherwise. A `cancelled` order stays cancelled, with its payment shown as paid. It then records `order.refund_failed`, a warning, with the refund's amount, status and Stripe's `failure_reason`, under the entry id `order.refund_failed:<refund id>`, and the handler refreshes the admin's order lists and sends a `refundFailed` alert to `RESEND_EMAIL_FROM` naming the order number, the amount, the status and the reason (see [Monitoring and alerts](/docs/guides/monitoring-and-alerts)). The customer is not emailed: they were told the money was on its way, and how to pay them back is the owner's call. Stock is left as it is.

The failure path is idempotent. Stripe may send both events for one refund, and may send either again: the guarded batch lowers the payment once, the audit entry keeps its id so the queue's insert ignores a second copy, and the alert's incident is keyed by the refund id. A failure handled before the `charge.refunded` of its refund leaves nothing to lower, and that `charge.refunded` then finds no standing refund, so the order never shows the money as returned; the entry and the alert still go out. The two events can also overlap: `charge.refunded` can read a refund while it still stands and record it after `refund.failed` has found nothing to lower. So once it has recorded a refund, `handleChargeRefunded` reads the standing refunds again, and when they now add up to less than it recorded, `lowerRefundedAmount` from `undo-failed-refund.server.ts` lowers the payment and reopens the order with the same guarded batch, and no refund email goes out; `refund.failed` has recorded the entry and sent the alert. `stripe.webhooks.refund-failure.integration.test.ts` runs that overlap against the migrated schema. Once the refund is undone the order can be refunded again, from the Refund button or the Stripe Dashboard, and that new refund's `charge.refunded` emails the customer, because the refund email is keyed by the Stripe refund (see [Transactional email](/docs/features/email#cancellation-refund-and-failed-payment)).

Disputes are stored in `order.metadata` rather than in columns: `flagOrderDispute` merges `{ id, reason, status, amount }` into the JSON with `mergeDisputeMetadata` (`order.display.utils.ts`). A lost dispute is treated as a full refund and logs `review inventory manually` — the goods are usually gone, so the stock is not returned, and the order page offers Return to stock should they come back. `clearOrderDispute` removes the flag when a dispute closes any other way, and while the flag is present the admin refund is refused, and so is the cancellation of a paid order, which would refund it (see [Admin refunds](#admin-refunds)). `resolveAdminOrderDispute`, beside `mergeDisputeMetadata` in `order.display.utils.ts`, reads the flag back for the order list, the order page and the refund.

## Local testing

```bash
bun run stripe:listen
```

runs `stripe listen --latest --forward-to localhost:3000/api/webhooks/stripe`. Put the signing secret that command prints into `STRIPE_WEBHOOK_SECRET`. It forwards every event of the test account, so the local server also receives the events of preview's and other runs' checkouts; those whose `deployment` names another database are acknowledged and ignored, and preview's sessions, which the development server can see in the shared database, are fulfilled once by whichever endpoint gets there first (see [Fulfilment](#fulfilment)).

`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are declared in the `secrets.required` list of every environment in `wrangler.jsonc`. `VITE_STRIPE_PUBLISHABLE_KEY` is a browser variable and must be present at build time, since it is inlined by Vite.

## Admin refunds

`/admin/orders/$orderId` loads the order through `getAdminOrderQuery`, and its header shows Print summary, Refund, Return to stock, Cancel order, Start fulfillment, Mark shipped and Mark delivered as each one applies; the Refund item in the `/admin/orders` row menu opens that page. Refund asks for confirmation in `order-refund-dialog.tsx`, which also asks whether the items came back to stock. Its box starts ticked for an order that has not shipped and clear for one that is `shipped` or `delivered` (`refundRestocksByDefault`). The dialog calls `refundAdminOrder` (`src/modules/order/use-cases/refund-admin-order.ts`) with the answer as `restock`, a server function guarded by `authorized({ order: ["update", "refund"] })`. It checks `canRefundAdminOrder` from `order.admin-actions.utils.ts` (paid, and neither refunded nor cancelled), then `resolveAdminOrderRefundBlocker` from the same file, which names the reason Stripe cannot refund an order:

| Blocker           | When                                                               | Why                                                                                                                   |
| ----------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `noStripePayment` | `order.total` is 0                                                 | A free checkout completes as `no_payment_required`, so Stripe took no payment and there is no PaymentIntent to refund |
| `openDispute`     | `order.metadata` carries the `dispute` that `flagOrderDispute` set | The dispute decides what happens to the payment until `clearOrderDispute` removes the flag                            |

It also requires a `transaction_id` on the payment row. That column holds the Checkout Session id described above, which Stripe does not accept as a `payment_intent`, so the function retrieves the session with `stripe.checkout.sessions.retrieve(transactionId)` and reads its `payment_intent` through `resolveStripeObjectId` (`src/integrations/stripe/stripe.utils.ts`), which returns the id whether Stripe sent it as a string or as an expanded object. A session whose `payment_status` is `no_payment_required`, or that has no PaymentIntent, is refused as well. Otherwise it calls:

```ts
await stripe.refunds.create(
  { metadata: { orderId }, payment_intent: paymentIntentId },
  { idempotencyKey: `admin-order-refund-${orderId}-${undoneRefunds.length}` },
)
```

which refunds the full amount. Before it, `listRefunds({ payment_intent })` reads the refunds Stripe already holds for the payment, and `undoneRefunds` are those that are `failed` or `canceled`. The idempotency key is therefore the same for every request about one order until one of its refunds fails, so a double click, a second tab or a second admin sends Stripe a request it has already seen, and Stripe answers with the first result, or refuses the repeat while the first is still in flight, instead of attempting another refund. Once a refund has failed and `undoFailedRefund` has reopened the order, the next request carries a new key and reaches Stripe as a new refund, instead of getting the failed refund back for the 24 hours Stripe keeps a key. Stripe keeps a key's result, errors included, for at least 24 hours, so retrying a refund that Stripe rejected outright, which creates no refund to count, returns the same error until the key expires.

A missing order throws `ERROR_CODES.NOT_FOUND` with `ORDER_NOT_FOUND`. A refund refused for an open dispute throws `ERROR_CODES.CONFLICT` with `ORDER_OPEN_DISPUTE`, and every other refused refund throws `ERROR_CODES.CONFLICT` with `ORDER_INVALID_STATE`; neither requests a refund. These checks run on the server for every call, whatever the page shows. The admin's error toast names the dispute for `ORDER_OPEN_DISPUTE`, which reaches it when a dispute opened after the page loaded, and says the action is not available for the order's current state for any other conflict.

The page runs the same predicates on the loaded order. Refund appears when `canRefundAdminOrder` allows it. When `resolveAdminOrderRefundBlocker` returns a blocker, `order-action-button.tsx` keeps the button visible but disabled and still focusable, and its tooltip explains the blocker with the `pages.admin.orderDetail.refundBlocked` messages. Cancel order refunds a paid order, so it gets the same treatment from `resolveAdminOrderCancelBlocker`, which returns `openDispute` for an open dispute on an order `cancelRefundsAdminOrderPayment` would refund, with the `pages.admin.orderDetail.cancelBlocked` messages; in the `/admin/orders` row menu the Cancel order item is disabled and the `pages.admin.orders.rowActions.cancelBlocked` reason is shown under it.

`refundAdminOrder` records nothing about the payment. The payment and order statuses, the refund's audit entry and the customer's refund email arrive with the resulting `charge.refunded` event, through the same `refundOrder` path as a refund made in the Stripe dashboard. The stock is the admin's call: with `restock` true, once Stripe has accepted the refund, `returnOrderToStock` (`src/modules/order/order.restock.server.ts`) returns each line whose variant still exists to stock and sets `order.restocked_at` in one batch guarded on that column being empty and the order not being `cancelled`, records `order.restocked` and refreshes the catalogue. A refund Stripe refuses returns nothing, and a repeated request returns nothing more. The blocker, `transaction_id` and session checks and the `stripe.refunds.create` call live in `requestFullOrderRefund` (`src/modules/order/order.refund.server.ts`), which Cancel order also calls for a paid order before cancelling it, under the same idempotency key, so a Refund and a Cancel of one order cannot refund it twice either. It returns the `amount` of the refund Stripe created, which the cancellation email states. Both actions need the `order: ["refund"]` permission from `auth.access.ts` on top of `order: ["update"]`: `refundAdminOrder` asks for both in its `authorized` middleware, and Cancel order asks for `order: ["refund"]` once it has read the order and found a payment to refund, before it calls Stripe or changes anything. A role without it gets `FORBIDDEN`; the admin role holds it.
