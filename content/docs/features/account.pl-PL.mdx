## Layout i strażnik

`src/routes/account.tsx` to layout. Jego `beforeLoad` to sam strażnik, a `{ user }` zwracane przez strażnika trafia do kontekstu trasy:

```ts
beforeLoad: requireCustomer,
```

`requireCustomer` (`src/integrations/better-auth/auth.routes.ts`) wymaga sesji, a następnie **odsyła administratorów**:

```ts
export const requireCustomer = async (route: AuthRouteContext): Promise<{ user: SessionUser }> => {
  const { user } = await requireSignedIn(route)

  return hasAdminAccess(user.role) ? redirectTo(ROUTES.ADMIN) : { user }
}
```

Administrator nie może więc przeglądać strefy klienta; trafia na `/admin`. `/account/overview` odczytuje użytkownika do powitania przez `AccountRoute.useRouteContext()`.

`requireSignedIn` tylko odczytuje sesję, przez `loadRouteSession`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

Przekazuje `recheck: true`, więc prawdziwa nawigacja do `/account` sprawdza sesję ponownie z `staleTime: 0`; preload linku korzysta z sesji z cache'u, jeśli ma ona mniej niż 60 sekund. Sesja zostaje w cache'u TanStack Query, a render serwerowy dehydratuje ją do strony, więc strony konta renderują się na serwerze jako zalogowane.

Zmiana użytkownika jest obsługiwana w jednym miejscu: w `clearCacheOnUserChange` (`src/integrations/better-auth/auth.session.ts`), które `getRouter` instaluje wyłącznie w przeglądarce. Obserwuje ono cache zapytań i za każdym razem, gdy sesja przełącza się na innego użytkownika, łącznie z zalogowaniem i wylogowaniem, usuwa z cache'u wszystkie zapytania poza samą sesją i katalogami tłumaczeń, więc nic, co zapisano dla poprzedniego użytkownika, nie zostanie pokazane.

Anonimowy gość jest przekierowywany na `/auth/sign-in?redirect=<path>`, gdzie `<path>` to zlokalizowana ścieżka publiczna, na przykład `/en-US/account/orders/order-1`. Zostaje ona zachowana tylko wtedy, gdy pasuje do `SAME_SITE_PATH_PATTERN`: wyłącznie widoczne znaki ASCII, jeden ukośnik na początku i brak ukośnika wstecznego. Po zalogowaniu hasłem, kodem dwuskładnikowym albo przez Google strażnik `/auth` odsyła gościa z powrotem pod ten adres. Zobacz [Integracje: Better Auth](/docs/integrations/better-auth).

Layout renderuje `Navigation` z witryny, pod nią komunikat o wstrzymanej sprzedaży `SalesPausedBanner`, dwukolumnową siatkę i `Footer` z witryny. Jego loader czyta teksty `pages.account.meta`, `getCollectionsQuery()`, `getSalesStatusQuery()` i `getSellerDetailsQuery()` jednocześnie, więc zdjęcia kolekcji w pełnoekranowym menu, komunikat i dane sprzedawcy w stopce przychodzą razem ze stroną (zobacz [Kasa: wstrzymanie sprzedaży](/docs/features/checkout#wstrzymanie-sprzedaży) i [Ustawienia panelu](/docs/features/admin-settings#dane-sklepu)). Błąd odczytu danych sprzedawcy pokazuje stronę błędu. W `Suspense` owinięte są tylko dwie komórki siatki: `AccountSidebar` ze szkieletem `AccountSidebarFallback` oraz outlet ze szkieletem `AccountMainFallback`. Wstępnie wczytuje pięć przestrzeni nazw: `pages.account`, `pages.account.meta`, `pages.auth.errors`, `pages.auth.validations` i `pages.cart`, w której jest tekst komunikatu.

Samo `/account` tylko przekierowuje:

```ts
beforeLoad: () => {
  redirect({ throw: true, to: "/account/overview" })
},
```

## Wzorzec autoryzacji

Każdy use case w `src/modules/customer-account/use-cases/` używa `authorized()` bez argumentu uprawnień — czyli dowolny zalogowany użytkownik — a następnie sam zawęża zapytanie do `context.auth.user.id`. Nie ma sprawdzenia własności na poziomie trasy, które można by obejść; granicą jest funkcja serwerowa. `getCustomerOrder` filtruje na przykład po `and(eq(order.id, orderId), eq(order.userId, context.auth.user.id))`.

## Podsumowanie

`getCustomerOverview` najpierw odczytuje identyfikatory i numery ostatnich zamówień klienta, potem rozsyła równolegle pięć zapytań, następnie odczytuje pozycje ostatnich zamówień, a na końcu buduje rekomendacje:

| Źródło                                           | Zasila                                             |
| ------------------------------------------------ | -------------------------------------------------- |
| `getCustomerOrderNumbers(userId)`                | identyfikatory i numery ostatnich zamówień         |
| `getCustomerOrderRows(userId, { limit: 3 })`     | listę ostatnich zamówień                           |
| `getCustomerSpendStats(userId)`                  | `totalOrders`, `totalSpentMinorUnits`              |
| `getCustomerActivityAuditRows(userId, orderIds)` | strumień aktywności                                |
| `getUserById(userId)`                            | `memberSinceYear` z `createdAt`                    |
| `countWishlistItems(userId)`                     | `wishlistCount`                                    |
| `getOrderItemsForOrders(recentOrderIds)`         | pozycje pokazywane przy każdym ostatnim zamówieniu |
| `buildCustomerRecommendations(userId, locale)`   | `recommendations`, `recommendationsSource`         |

`getCustomerSpendStats` liczy zamówienia, które przepuszcza `orderCountsAsSale`, czyli te o statusie `processing` lub `completed`, i sumuje `netSalesSum`, czyli kwotę każdego z nich pomniejszoną o to, co zwrócono z jego płatności, więc klient widzi te same łączne wydatki co administrator (zobacz [Klienci w panelu](/docs/features/admin-customers)). Limity leżą w `customer-account.constants.ts`: `CUSTOMER_ACCOUNT_ORDERS_LIMIT = 50` dla numerów zamówień, `CUSTOMER_ACCOUNT_OVERVIEW_ORDERS_LIMIT = 3`, `CUSTOMER_ACCOUNT_OVERVIEW_ACTIVITY_LIMIT = 5`, `CUSTOMER_ACCOUNT_RECOMMENDATIONS_LIMIT = 3`, `CUSTOMER_ACCOUNT_RECOMMENDED_CATEGORY_LIMIT = 2`.

Dwie rzeczy warto wiedzieć:

- **Rekomendacje wynikają z zamówień klienta.** `buildCustomerRecommendations` bierze dwie kategorie, które najczęściej występują w zamówieniach klienta o statusie `processing` i `completed`, odczytuje z nich przez `getPublishedProductsByCategoryIds` opublikowane, dostępne produkty i odrzuca każdy produkt, który klient już zamówił. Jeśli coś zostanie, pierwsze trzy wracają z `recommendationsSource: "orders"`. W przeciwnym razie sięga po pierwsze trzy opublikowane, dostępne produkty kolekcji `nowosci` z `recommendationsSource: "newArrivals"`. Korzysta przy tym z tego samego odczytu co nowości na stronie głównej, `getPublishedProductsByCollectionHandle(LANDING_NEW_ARRIVALS_COLLECTION_HANDLE, …)`, więc kieruje się tymi samymi zasadami co strona główna i zwraca pustą listę, dopóki żadna aktywna kolekcja nie ma tego handle. Każdy z tych dwóch odczytów to jedna instrukcja D1: podzapytanie wybiera produkty należące do tych kategorii albo do tej kolekcji, a zapytanie zewnętrzne odczytuje spośród nich opublikowane, dostępne produkty razem z wariantami. Strona dobiera nagłówek i opis siatki do tego źródła.
- **`wishlistCount` jest prawdziwe.** `countWishlistItems` liczy wiersze `wishlist_item` klienta, te same, które wyświetla `/account/wishlist`, więc produkt, który nie jest już opublikowany, nadal się liczy.

Strumień aktywności jest budowany z dziennika zdarzeń: `getCustomerActivityAuditRows` czyta wiersze `audit_log`, których `resourceId` to użytkownik albo jedno z zamówień z `getCustomerOrderNumbers`, ograniczone do `auth.login`, `auth.login_failed`, `auth.logout`, `customer.cart_item_added`, `order.placed`, `order.shipped` i `order.released`. `mapAuditLogToActivityItem` zamienia każdy wiersz w `{ actionKey, params, createdAt }`, wstawiając numer zamówienia do `params` przy akcjach zamówień i odrzucając każdy wiersz, którego nie potrafi zmapować. Strona mapuje `actionKey` na ikonę przez lokalną mapę `ACTIVITY_ICONS` i formatuje znacznik czasu przez `formatRelativeFromNow`.

## Profil

`getCustomerProfile` zwraca `{ createdAt, email, emailVerified, hasGoogle, hasPassword, name, phone, timezone, twoFactorEnabled }` z wiersza `user`. `hasPassword` i `hasGoogle` pochodzą z `listAccountProviderIds` (`src/modules/account/account.accessors.ts`), czyli z `provider_id` każdego wiersza `account` użytkownika: `credential` oznacza hasło, a `google` połączone konto Google.

`account.profile.tsx` przekazuje `profile.twoFactorEnabled` do `SecuritySection` jako prop, więc stan uwierzytelniania dwuskładnikowego pochodzi z zapytania, które loader strony już wczytał wstępnie. Włączenie lub wyłączenie uwierzytelniania dwuskładnikowego unieważnia zapytanie profilu, zapytanie sesji i `CUSTOMER_ACCOUNT_QUERY_KEYS.SESSIONS`, bo w obu przypadkach Better Auth zastępuje bieżącą sesję nową. Zmiana hasła również unieważnia `CUSTOMER_ACCOUNT_QUERY_KEYS.SESSIONS`, ponieważ opcja „Wyloguj moje pozostałe urządzenia” usuwa wszystkie pozostałe sesje; strona sesji nie pokazuje więc urządzenia, które jest już wylogowane. Każda z tych zmian, a także potwierdzona zmiana adresu e-mail, trafia do [dziennika zdarzeń](/docs/features/audit-log#zdarzenia-bezpieczeństwa-konta) jako wpis dotyczący konta: `auth.two_factor_enabled`, `auth.two_factor_disabled`, `auth.password_changed` (z `auth.sessions_revoked`, gdy pozostałe urządzenia zostają wylogowane) i `auth.email_changed`.

`/admin/security` renderuje tę samą `SecuritySection` dla administratora, z tego samego `getCustomerProfileQuery`, bo layout `/account` odsyła administratorów na `/admin`. Tam administrator włącza uwierzytelnianie dwuskładnikowe, którego wymaga panel; zobacz [Better Auth](/docs/integrations/better-auth#uwierzytelnianie-dwuskładnikowe-administratorów). Potem profilem, hasłem, uwierzytelnianiem dwuskładnikowym i sesjami zarządza w [Ustawieniach panelu](/docs/features/admin-settings), które otwierają te same okna w stylu panelu.

Okna zmiany adresu e-mail i zmiany hasła sprawdzają pola w trakcie pisania (`mode: "onChange"`), tak jak okna uwierzytelniania dwuskładnikowego i zamknięcia konta, a nigdy w chwili opuszczenia pola. Sprawdzanie przy utracie fokusu dodawałoby komunikat błędu pod polem, które klient właśnie opuścił, by nacisnąć **Anuluj** albo przycisk zamknięcia. Okno jest wyśrodkowane, więc jego stopka przesuwałaby się o około 12 px w dół, gdy przycisk jest jeszcze wciśnięty, a naciśnięcie przy górnej krawędzi **Anuluj** przepadałoby. Ceną jest komunikat błędu widoczny już w trakcie pisania: nowy adres e-mail jest oznaczany od pierwszego znaku, dopóki nie będzie kompletny, pole **Nowe hasło** wymienia, czego jeszcze brakuje, a **Potwierdź nowe hasło** przypomina, że hasła muszą się zgadzać, dopóki się nie zgodzą. Za każdym razem, gdy komunikat się pojawia albo znika, okno rośnie lub maleje o jedną linię, a pola przesuwają się o około 12 px, tak jak już wcześniej w oknach uwierzytelniania dwuskładnikowego i zamknięcia konta.

`updateCustomerPhone` to jedyne pole, które klient może tu zmienić:

```ts
export const updateCustomerPhone = createServerFn({ method: "POST" })
  .middleware([withRateLimit("update-customer-phone", RATE_LIMITS.SENSITIVE), authorized()])
  .validator((input: zod.input<typeof customerAccountZodSchemas.phoneInput>) => customerAccountZodSchemas.phoneInput.parse(input))
  .handler(async ({ context, data: { phone } }): Promise<boolean> => {
    await db
      .update(user)
      .set({ phone: phone === "" ? sql`NULL` : phone })
      .where(eq(user.id, context.auth.user.id))

    return true
  })
```

`RATE_LIMITS.SENSITIVE` to trzy wywołania na minutę. Pusty napis czyści kolumnę do `NULL`, a nie zapisuje `""`. Zmiany nazwy, adresu e-mail i hasła przechodzą przez Better Auth, a nie przez ten moduł.

`PreferencesSection` zaczyna się od strefy czasowej oraz formatu dat i liczb, czyli dwóch pól `DisplayPreferenceField` (`src/presentation/components/custom/display-preferences/`), z których korzystają też **Ustawienia → Moje konto** w panelu. Każda lista zaczyna się od pozycji Automatycznie, opisanej tym, co wykryto dla klienta, a `updateDisplayPreference` zapisuje wybór tak samo jak `updateCustomerPhone`, z `""` dla pozycji Automatycznie (zobacz [Internacjonalizacja](/docs/features/internationalization)).

`PreferencesSection` zawiera też `NewsletterField`, który czyta `getOwnNewsletterSubscriptionQuery()` i wywołuje `subscribeToNewsletter` z własnym adresem konta i `source: "account"`. Wynik `confirmationSent` pokazuje komunikat „sprawdź skrzynkę”, `alreadyConfirmed` informuje, że subskrypcja jest już aktywna, a `confirmationFailed` pokazuje błąd mówiący, że e-maila nie udało się wysłać. Dopóki subskrypcja ma status `pending`, status brzmi „Subskrypcja niepotwierdzona”, a nie obiecuje e-maila, a obok **Wypisz się** jest przycisk **Wyślij ponownie**, więc potwierdzenie, które nie wyszło albo nie dotarło, można wysłać jeszcze raz z nowym linkiem. Na wąskim ekranie oba przyciski przechodzą pod status. Loader `account.profile.tsx` ładuje subskrypcję razem z profilem, więc pole od razu pokazuje zapisany status, zamiast wyświetlać „Nie zasubskrybowano”, dopóki nie wróci jego własne zapytanie. Jeśli subskrypcji nie da się odczytać, strona profilu i tak się otwiera, a pole pyta ponownie po zamontowaniu.

## Adresy

`src/modules/address` ma pięć use case'ów, wszystkie z `authorized()` i wszystkie zawężone do bieżącego użytkownika:

| Use case                      | Middleware                                                                     | Uwagi                                                     |
| ----------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `list-user-addresses.ts`      | `authorized()`                                                                 | `findMany` po zgodnym `userId`                            |
| `create-user-address.ts`      | `withRateLimit("create-user-address", RATE_LIMITS.SENSITIVE)` + `authorized()` | wymusza `userId` z sesji                                  |
| `update-user-address.ts`      | z limitem żądań + `authorized()`                                               |                                                           |
| `delete-user-address.ts`      | `authorized()`                                                                 |                                                           |
| `set-default-user-address.ts` | `authorized()`                                                                 | rzuca `ERROR_CODES.NOT_FOUND`, gdy nic nie zaktualizowano |

**Anuluj** zamyka formularz adresu jednym naciśnięciem także wtedy, gdy strona jeszcze wyhamowuje po przewinięciu kółkiem albo gładzikiem: `SmoothScroll` zatrzymuje to wyhamowywanie przy każdym naciśnięciu, więc przycisk zostaje pod kursorem aż do puszczenia. Zobacz [GSAP i Lenis](/docs/integrations/gsap-and-lenis).

`addressFieldsSchema` (`address.zod.ts`) wymaga `address1`, `city` i dwuznakowego `countryCode`; `firstName`, `lastName`, `phone`, `postalCode`, `province` i `address2` są opcjonalne, zgodnie z nullowalnymi kolumnami.

Tabela `address` (`address.schema.ts`) ma `is_default` i dwa indeksy: `address_userId_idx` oraz `address_userId_isDefault_idx`. Zwróć uwagę, że wiersze `address` zapisuje również kasa — z `user_id` równym `null` dla gościa — a `isDefault` jest ustawiane z pól wyboru `saveShippingAddress` / `saveBillingAddress`. Zobacz [Kasa](/docs/features/checkout).

## Sesje

`listCustomerSessions` wybiera wiersze `session` użytkownika uporządkowane malejąco po `updatedAt` i wzbogaca każdy z nich:

```ts
return rows.map((row) => {
  const parsed = parseUserAgent(row.userAgent)

  return {
    browser: parsed.browser,
    createdAt: row.createdAt,
    device: parsed.device,
    deviceType: parsed.deviceType,
    id: row.id,
    ipAddress: row.ipAddress ?? undefined,
    isCurrent: row.id === context.auth.session.id,
    lastActiveAt: row.updatedAt,
  } satisfies CustomerAccount["session"]
})
```

`parseUserAgent` leży w `customer-account.utils.ts`. `lastActiveAt` to `updatedAt` wiersza sesji.

Dwie mutacje unieważniające:

- `revokeCustomerSession({ sessionId })` — zwraca `false` bez usuwania, gdy identyfikator wskazuje **bieżącą** sesję, więc klient nie może się z tego ekranu wylogować. Usunięcie to `and(eq(session.id, sessionId), eq(session.userId, context.auth.user.id))`.
- `revokeOtherCustomerSessions()` — usuwa wszystkie pozostałe sesje użytkownika, nigdy bieżącej.

Każda z nich, gdy usunie sesję, zapisuje `auth.sessions_revoked` przypisane klientowi, z adresem, z którego prosił; identyfikator sesji, która nie należy do klienta, niczego nie usuwa i niczego nie zapisuje.

Strona podpisuje akcję zbiorczą „Wyloguj pozostałe urządzenia” i pokazuje ją tylko wtedy, gdy na liście jest sesja inna niż bieżąca. Gdy zalogowane jest jedno urządzenie, akcja nie miałaby czego zrobić, więc zamiast niej lista informuje, że klient nie ma aktywnych sesji na innych urządzeniach. Wylogowanie bieżącego urządzenia pozostaje przy linku wylogowania w panelu bocznym konta.

`listCustomerLoginHistory` korzysta z tych samych wierszy audytu i zachowuje tylko `auth.login` oraz `auth.login_failed`, mapując niepowodzenie na `status: "failed"`. Historia logowań jest więc widokiem na [dziennik zdarzeń](/docs/features/audit-log), a nie osobną tabelą, i sięga najwyżej 12 miesięcy wstecz, bo starsze wpisy usuwa codzienne [czyszczenie po okresie przechowywania](/docs/guides/data-retention). `getCustomerLoginAuditRows` zwraca `CUSTOMER_ACCOUNT_LOGIN_HISTORY_LIMIT` (20) najnowszych wierszy; gdy lista osiąga ten limit, notka pod nią mówi, że widać tylko ostatnie próby. Każdy wiersz podaje wynik raz — „Udane logowanie” albo „Nieudana próba logowania” — z adresem i datą obok.

Zamknięcia konta nie ma na tej stronie. Znajduje się wyłącznie na stronie profilu, gdzie `CloseAccountSection` otwiera okno potwierdzenia wywołujące `deleteUser` z Better Auth; zobacz [Usunięcie konta](#usunięcie-konta).

## Usunięcie konta

**Usuń konto** na `/account/profile` otwiera `CloseAccountDialog`. Jego cztery punkty, od `pages.account.profile.closeDialogPoint1` do `closeDialogPoint4`, mówią, co zostaje usunięte, a co zachowane: profil z imieniem i nazwiskiem, adresem e-mail, numerem telefonu, hasłem, ustawieniami uwierzytelniania dwuskładnikowego i powiązaniami z dostawcami logowania, zapisane adresy, lista życzeń i subskrypcja newslettera; klient Stripe z zapisanymi kartami; historia logowania, dziennik aktywności i wszystkie sesje; oraz zamówienia i płatności, które zostają w dokumentacji księgowej przez 5 lat od końca roku każdego zamówienia, już bez powiązania z kontem. Okno wywołuje `deleteUser` z Better Auth z hasłem albo bez hasła dla konta, które loguje się tylko przez dostawcę.

Better Auth sprawdza hasło, a potem uruchamia `deleteUser.beforeDelete` (`prepareSelfServiceDeletion` w `auth.hooks.server.ts`). Konto z dostępem do panelu zatrzymuje się tu z kodem `403 CANNOT_DELETE_ADMIN` (zobacz niżej). Dla każdego innego konta wywołuje `eraseAccountData` (`src/modules/user/user.erasure.server.ts`), zanim cokolwiek zostanie usunięte:

1. `deleteStripeCustomer` (`stripe.customer.server.ts`) usuwa klienta Stripe powiązanego z kontem, a razem z nim jego zapisane karty, i czyści `stripe_customer_id`, dopóki kolumna wciąż zawiera ten identyfikator. Klient, dla którego Stripe odpowiada `resource_missing`, na przykład usunięty w panelu Stripe, liczy się jako usunięty.
2. Jeden batch D1 usuwa wiersze `audit_log`, których `resource_id` to identyfikator albo adres e-mail konta, czyli dziennik aktywności, historię logowania, rejestrację i nieudane wiadomości uwierzytelniania wysłane na ten adres, oraz wiersze `newsletter_subscriber` powiązane z kontem albo zapisane na jego adres.
3. `scheduleAdminAuditLogInvalidation` i `scheduleAdminNewsletterSubscribersInvalidation` odświeżają dziennik zdarzeń i listę subskrybentów newslettera w panelu.

Następnie Better Auth usuwa sesje, wiersze `account` (hasło i powiązanie z Google) i wiersz `user`. Klucze obce usuwają razem z nim adresy, listę życzeń i ustawienia dwuskładnikowe oraz ustawiają `user_id` na `null` w zamówieniach, kasach i użyciach kodów rabatowych, więc zamówienia zostają w dokumentacji księgowej jako zamówienia gościa. `claimGuestOrdersForUser` łączy je z nowym kontem, gdy jego adres e-mail, ten sam, zostanie zweryfikowany. `afterDelete` wysyła e-mail pożegnalny, który powtarza, co usunięto, a co zachowano, a `databaseHooks.user.delete.after` zapisuje `customer.deleted` przypisane klientowi, z adresem konta jako celem. Ten wpis powstaje po usunięciu danych, więc zostaje jako zapis sklepu o usunięciu konta, przechowywany przez dwa lata jak reszta dziennika zdarzeń (zobacz [Okresy przechowywania danych](/docs/guides/data-retention)).

Gdy Stripe nie może usunąć klienta, `eraseAccountData` loguje błąd, zapisuje w dzienniku zdarzeń `customer.deletion_failed` i zwraca `false`, a `beforeDelete` odpowiada `503` z `STRIPE_CUSTOMER_NOT_DELETED`, zanim Better Auth cokolwiek usunie. Nic nie zostaje usunięte, klient pozostaje zalogowany, a okno pokazuje `closeStripeCustomerError`: nie udało się usunąć zapisanych kart w Stripe, więc konto nie zostało usunięte. Usunięcie przez administratora najpierw uruchamia to samo `eraseAccountData`; zobacz [Klienci w panelu](/docs/features/admin-customers).

Konta z dostępem do panelu nie da się usunąć w ogóle. Strony `/account` odsyłają takie konto do `/admin`, więc okno jest zwykle poza zasięgiem, ale `/delete-user` odpowiedziałby każdemu zalogowanemu kontu, dlatego `prepareSelfServiceDeletion` odrzuca je, zanim cokolwiek zostanie wymazane, a okno pokazałoby `closeAdminAccountError`: konto ma dostęp do panelu i najpierw inna osoba z tym dostępem musi go odebrać. Ustawienia › Moje konto wyjaśniają to samo w panelu (zobacz [Ustawienia panelu: Usunięcie konta](/docs/features/admin-settings#usunięcie-konta)). Po odebraniu dostępu w Ustawienia › Zespół konto znów jest kontem klienta i ta strona usuwa je tak, jak opisano wyżej.

Dwie rzeczy podlegają okresom przechowywania z polityki prywatności, a nie temu usunięciu. Nieopłacone kasy zachowują wpisany w nich adres e-mail i adresy, już bez powiązania z kontem, bo płatność wciąż może się do nich rozliczyć. Zdarzenia audytu są zapisywane przez kolejkę, więc zdarzenie dodane do kolejki na kilka sekund przed usunięciem może trafić do tabeli po nim.

## Zapisane metody płatności

Zalogowany klient zapisuje kartę w jednym z dwóch miejsc: w kasie albo przyciskiem **Dodaj kartę** na `/account/payment`. W obu przypadkach karta trafia do jego klienta Stripe; nie ma tabeli zapisanych kart. Pozycja w panelu bocznym i tytuł karty przeglądarki korzystają z `pages.account.sidebar.payment`, czyli „Metody płatności” („Payment Methods” po angielsku), tych samych słów co nagłówek strony.

### Klient Stripe

`ensureStripeCustomer` (`src/integrations/stripe/stripe.customer.server.ts`) zwraca `stripe_customer_id` użytkownika albo tworzy klienta Stripe i zapisuje jego identyfikator w tej kolumnie. `ensureStripeCustomerWithEmail`, z którego korzysta kasa, robi to samo, tyle że klientowi, którego użytkownik już ma, ustawia też podany adres e-mail przez `stripe.customers.update`. Obie funkcje tworzą klienta tymi samymi krokami. Dwa żądania mogą jednocześnie zastać pustą kolumnę, na przykład po podwójnym kliknięciu albo przy kasie otwartej w innej karcie, dlatego identyfikator jest zapisywany przez `coalesce`, a żądanie, które przegra wyścig, usuwa utworzonego przez siebie klienta:

```ts
const customer = await stripe.customers.create({ email, metadata: { userId }, name })
const [stored] = await db
  .update(user)
  .set({ stripeCustomerId: sql`coalesce(${user.stripeCustomerId}, ${customer.id})`, updatedAt: new Date() })
  .where(eq(user.id, userId))
  .returning({ stripeCustomerId: user.stripeCustomerId })

if (stored?.stripeCustomerId !== customer.id) {
  await stripe.customers.del(customer.id).catch((deleteError: unknown) => {
    console.error("Failed to delete an unused Stripe customer:", deleteError)
  })
}
```

`coalesce` zachowuje identyfikator zapisany jako pierwszy i to on trafia do każdego wywołującego, więc karta nigdy nie zostaje zapisana u klienta, o którym konto już nie wie. Przegrane żądanie usuwa własnego klienta, do którego nic jeszcze nie dołączono; nieudane usunięcie jest tylko logowane, bo zapisany klient i tak jest właściwy. Funkcja nie wysyła klucza idempotencji: kasa tworzy klienta z adresem e-mail wpisanym w formularzu zamówienia, a strona konta z adresem konta, a Stripe odrzuca ponownie użyty klucz z innymi parametrami, przez co jedno z dwóch żądań kończyłoby się błędem. Gdy wiersz użytkownika już nie istnieje, funkcja usuwa nowego klienta i rzuca `ERROR_CODES.NOT_FOUND`.

### W kasie

Dla zalogowanego klienta `handleCreateCheckoutSession` (`src/integrations/stripe/stripe.actions.server.ts`) wywołuje `ensureStripeCustomerWithEmail` z adresem e-mail wpisanym w formularzu zamówienia i tworzy sesję Checkout dla tego klienta z włączonym `payment_method_save`, które pozwala klientowi wybrać, czy zapisać kartę:

```ts
...(customerId === undefined
  ? { customer_email: email }
  : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
```

Gość dostaje zamiast tego `customer_email` i nie ma klienta Stripe, do którego można by zapisać kartę. Sesja utworzona dla klienta Stripe pokazuje jego adres e-mail, którego kupujący nie może tam zmienić, i pod tym adresem Stripe rozlicza płatność, dlatego `ensureStripeCustomerWithEmail` najpierw przenosi istniejącego klienta na adres z tego zamówienia. Zamówienie, potwierdzenie płatności od Stripe, sama płatność i e-mail z potwierdzeniem mają wtedy adres potwierdzony przez kupującego, nawet jeśli różni się od adresu konta albo od adresu z poprzedniego zakupu. `handleUpdateCheckoutSession` wywołuje `ensureStripeCustomerWithEmail` z poprawionym adresem przy każdym zalogowanym żądaniu, więc zmiana adresu w kroku danych kontaktowych przenosi też klienta. Gość, który dojdzie do kroku płatności, a potem się zaloguje, dostaje tę samą propozycję co kupujący zalogowany od początku: aktualizacja przekazuje checkout gościa kontu i w ten sam sposób bierze klienta Stripe tego konta. Zobacz [Płatności](/docs/features/payments).

### Na stronie konta

**Dodaj kartę** wywołuje `createCardSetupIntent` (`src/modules/payment/use-cases/create-card-setup-intent.ts`), chronione przez `withRateLimit("create-card-setup-intent", RATE_LIMITS.SENSITIVE)` i `authorized()`. Funkcja wywołuje `ensureStripeCustomer` z adresem e-mail i imieniem z konta, więc klient, który jeszcze nigdy nie płacił, dostaje tu klienta Stripe, a istniejący klient zachowuje adres nadany przez ostatni checkout, a następnie otwiera SetupIntent:

```ts
const intent = await stripe.setupIntents.create({
  customer,
  metadata: { userId },
  payment_method_types: ["card"],
  usage: "on_session",
})
```

Dostępne są tylko karty, bo BLIK-a i Przelewy24 nie da się zapisać, a `on_session` odpowiada temu, jak zapisana karta jest używana ponownie: w kasie, przy obecnym kliencie. Funkcja zwraca wyłącznie `{ clientSecret }` i rzuca `ERROR_CODES.INTERNAL_ERROR`, gdy Stripe nie zwróci sekretu klienta.

Zanim funkcja wywoła Stripe, rzuca `ERROR_CODES.FORBIDDEN` dla konta z niepotwierdzonym adresem e-mail. `authorized()` sprawdza tylko, czy sesja istnieje. Bez tej kontroli każdy zalogowany na konto, którego adresu nikt nie potwierdził, mógłby otworzyć SetupIntent i raz za razem sprawdzać kradzione karty, potwierdzając je w przeglądarce sekretem klienta, czego limit żądań tej funkcji na adres IP w ogóle nie widzi. Użytkownicy pozostali po usuniętej wtyczce `anonymous()` Better Auth mają niepotwierdzone adresy, więc ich sesje też są odrzucane.

Strona przechowuje wynik `createCardSetupIntentMutation`, dopóki jest zamontowana. Zamknięcie formularza i ponowne jego otwarcie korzysta z tego samego SetupIntent, zamiast zużywać kolejne żądanie z limitu; nowy powstaje dopiero po zapisaniu karty albo gdy formularz zrezygnuje z dotychczasowego SetupIntent. Gdy otwarcie formularza się nie powiedzie, na przykład po przekroczeniu limitu, strona pokazuje `pages.account.payment.formUnavailable`, bo klient nie wpisał jeszcze żadnej karty.

Przycisk **Dodaj kartę** pozostaje osiągalny z klawiatury także wtedy, gdy jest zablokowany: ma `focusableWhenDisabled`, więc na czas tworzenia SetupIntent i przez cały czas otwarcia formularza dostaje `aria-disabled` zamiast `disabled`, a fokus klawiatury i czytnika ekranu nie spada na stronę. Gdy Payment Element jest gotowy, jego `onReady` przenosi fokus do pól karty. Anulowanie, zapisanie karty i rezygnacja z SetupIntent przywracają fokus na **Dodaj kartę**. **Anuluj** wywołuje `preventDefault()` przy `mousedown`, więc jego naciśnięcie zostawia fokus w polach karty. W przeciwnym razie opuszczenie niedokończonego numeru karty sprawia, że Stripe pokazuje pod nim komunikat o niepełnym numerze i powiększa swój iframe, gdy przycisk jest jeszcze wciśnięty. W Chromium i WebKit przesuwało to **Anuluj** o 13–17 px w dół, czyli o więcej niż jego własna wysokość, i pierwsze naciśnięcie przepadało.

`account.payment.tsx` renderuje `LazyAddCardForm` z `add-card-form-loader.client.ts` wewnątrz `ClientOnly`. Loader opakowuje `AddCardForm` (`add-card-form.client.tsx`) w `lazy()`, więc jego fragment i Stripe.js są pobierane dopiero po pierwszym kliknięciu, a `ClientOnly` trzyma moduł przeznaczony tylko dla przeglądarki poza pakietem serwera, czego wymaga ochrona importów w buildzie. `AddCardForm` wczytuje Stripe.js przez `useQuery(stripeJsQuery(locale))` ze `stripe.client.ts`, które opakowuje `getStripe(locale)` z `retry: false`. Podczas pobierania skryptu pokazuje zaślepkę, a gdy pobranie się nie uda, na przykład przez blokadę reklam, `AddCardUnavailable` z `pages.account.payment.formUnavailable` i przyciskiem anulowania. `getStripe` zapomina nieudane pobranie, więc ponowne otwarcie formularza pobiera skrypt od nowa. Formularz korzysta z tej samej konfiguracji co kasa: `getStripeAppearance(theme)` i `STRIPE_FONTS` ze `stripe.appearance.ts`. Przekazuje też `locale: toStripeLocale(locale)` do `Elements`, bo `getStripe` zachowuje język, z którym Stripe.js wczytał się za pierwszym razem. `Elements` ma klucz równy sekretowi klienta, którego nie można zmienić po zamontowaniu.

`AddCardFields` (`add-card-fields.client.tsx`) renderuje Payment Element bez Apple Pay, Google Pay i Link i potwierdza kartę wywołaniem:

```ts
stripe.confirmSetup({
  confirmParams: { payment_method_data: { allow_redisplay: "always" } },
  elements,
  redirect: "if_required",
})
```

Stripe Checkout proponuje tylko zapisane karty z `allow_redisplay` równym `"always"`, więc bez tego karta dodana tutaj byłaby widoczna w portfelu, ale nigdy w kasie. Przy samych kartach i `redirect: "if_required"` strona nigdy nie przekierowuje; weryfikacja 3D Secure otwiera się we własnym oknie Stripe. Formularz ignoruje wysłanie, dopóki Payment Element nie jest gotowy, i w trakcie zapisywania, bo Stripe wysyła otaczający formularz po naciśnięciu Enter w swoim iframe, a drugie `confirmSetup` na tym samym SetupIntent skończyłoby się błędem nawet wtedy, gdy pierwsze się powiodło.

Błąd `card_error` lub `validation_error` jest pokazywany ze zlokalizowanym komunikatem Stripe, a gdy go brak, z `pages.account.payment.addError`; formularz zostaje wtedy otwarty na tym samym SetupIntent, który Stripe utrzymuje w stanie `requires_payment_method`. Każdy inny błąd, a także `confirmSetup`, które rzuci wyjątek, pokazuje `pages.account.payment.addError`, unieważnia `PAYMENT_METHOD_QUERY_KEYS.SAVED` na wypadek, gdyby karta jednak się zapisała, i wywołuje `onFailed`: strona zamyka formularz i następnym razem otwiera nowy SetupIntent, zamiast ponownie używać sekretu klienta, którego Stripe może już nie przyjąć.

Po powodzeniu formularz wywołuje `removeDuplicateSavedCards` (`src/modules/payment/use-cases/remove-duplicate-saved-cards.ts`, chronione przez `withRateLimit("remove-duplicate-saved-cards", RATE_LIMITS.SENSITIVE)` i `authorized()`) z identyfikatorem nowej karty. Funkcja rzuca `ERROR_CODES.NOT_FOUND`, gdy użytkownik nie ma klienta Stripe. W przeciwnym razie pobiera ze Stripe jednocześnie nową kartę i zapisane karty tego klienta, rzuca `ERROR_CODES.FORBIDDEN`, chyba że karta należy do tego klienta, i dopiero wtedy odłącza każdą inną zapisaną kartę o tym samym `card.fingerprint`. Dodanie karty, która była już zapisana w kasie albo tutaj, zastępuje więc starą kopię nową, razem z nową datą ważności, zamiast pokazywać tę samą kartę dwa razy w portfelu i w kasie. Niezależnie od wyniku tego wywołania formularz unieważnia potem `PAYMENT_METHOD_QUERY_KEYS.SAVED`, pokazuje `pages.account.payment.added` i się zamyka, bo karta i tak została zapisana. Gdy Payment Element zgłosi błąd wczytywania, jak przy fikcyjnym kluczu publicznym używanym w środowisku deweloperskim i w testach end-to-end, formularz pokazuje `pages.account.payment.formUnavailable` i pozostawia przycisk zapisu wyłączony.

### Lista i usuwanie

`listSavedPaymentMethods` (`src/modules/payment/use-cases/list-saved-payment-methods.ts`) używa `authorized()` i pyta Stripe o metody płatności klienta typu `card` z `limit: SAVED_CARDS_PAGE_LIMIT` (100, z `payment.constants.ts`), bo domyślna strona Stripe mieści dziesięć, albo zwraca pustą listę, gdy użytkownik nie ma klienta Stripe. Każda karta staje się `{ brand, expMonth, expYear, id, isExpired, last4 }`. `isExpired` pochodzi z `isCardExpired` (`payment.utils.ts`), które porównuje datę ważności z dzisiejszą datą we własnej strefie czasowej klienta: `timezone` użytkownika przez `resolveTimezoneCode`, które w razie braku przyjmuje `Europe/Warsaw`.

`/account/payment` wczytuje wstępnie `listSavedPaymentMethodsQuery()` i renderuje `SavedCardList`. Bez kart pokazuje ikonę `CreditCard` i `pages.account.payment.empty`; w przeciwnym razie po jednym `SavedCardRow` na kartę z marką, czterema ostatnimi cyframi, datą ważności w formacie `MM/YYYY`, plakietką wygaśnięcia, gdy ustawione jest `isExpired`, i przyciskiem usuwania. Licznik w nagłówku to `methods.length`.

Usunięcie karty wywołuje `deleteSavedPaymentMethod` (`delete-saved-payment-method.ts`), chronione przez `withRateLimit("delete-saved-payment-method", RATE_LIMITS.SENSITIVE)` i `authorized()`. Odczytuje ono identyfikator klienta Stripe użytkownika w tym samym czasie, w którym pobiera metodę płatności ze Stripe, więc dla metody płatności, której Stripe nie zna, przekazuje dalej błąd Stripe, niezależnie od tego, czy użytkownik ma klienta Stripe. Gdy obie odpowiedzi już nadejdą, rzuca `ERROR_CODES.NOT_FOUND`, jeśli użytkownik nie ma klienta Stripe, oraz `ERROR_CODES.FORBIDDEN`, chyba że metoda płatności należy do tego klienta, i dopiero wtedy odłącza ją w Stripe. Po powodzeniu lista unieważnia `PAYMENT_METHOD_QUERY_KEYS.SAVED`.

Nie ma karty domyślnej. Nic nie odczytuje ani nie zapisuje `invoice_settings.default_payment_method`, a kasa wyświetla zapisane karty w kolejności Stripe.

## Lista życzeń

`wishlist_item` (`src/modules/wishlist/wishlist.schema.ts`) przechowuje jeden wiersz na klienta i produkt. `user_id` i `product_id` są usuwane kaskadowo; `wishlist_item_userId_productId_unique` pilnuje unikalności pary, a `wishlist_item_userId_createdAt_idx` obsługuje listę od najnowszych.

Wszystkie trzy use case'y używają `authorized()` i są zawężone do bieżącego użytkownika:

| Use case                       | Uwagi                                                                                                                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list-wishlist-items.ts`       | `listWishlistItemsQuery(locale)`: od najnowszych, najwyżej `WISHLIST_MAX_ITEMS`, każdy z tytułem w danym języku, najtańszym wariantem, stanem magazynowym i statusem publikacji    |
| `list-wishlist-product-ids.ts` | `listWishlistProductIdsQuery()`: identyfikatory zapisanych produktów, z których korzystają serduszka                                                                               |
| `toggle-wishlist-item.ts`      | `toggleWishlistItemMutation`: usuwa istniejący wiersz, a w przeciwnym razie wstawia nowy dla opublikowanego produktu, dopóki lista ma mniej niż `WISHLIST_MAX_ITEMS` (200) pozycji |

Przełączenie wysyła jeden `db.batch` z dwiema instrukcjami z `wishlist.accessors.ts`. `deleteWishlistItemQuery` usuwa wiersz wywołującego dla tego produktu i zwraca jego identyfikator. `getPublishedProductForCustomerQuery` odczytuje następnie produkt, jeśli jest opublikowany, razem z `wishlistCount`, czyli skorelowaną liczbą wierszy wywołującego. D1 wykonuje wsad jako jedną transakcję, więc liczba uwzględnia już usunięcie. Jeśli usunięcie zwróciło wiersz, produkt był zapisany i przełączenie kończy się po jednym żądaniu do D1, bez względu na status produktu i długość listy. W przeciwnym razie nieopublikowany produkt rzuca `ERROR_CODES.NOT_FOUND`, lista, która ma już `WISHLIST_MAX_ITEMS` produktów, rzuca `ERROR_CODES.VALIDATION` z komunikatem `WISHLIST_FULL`, a każdy inny produkt wstawia `insertWishlistItem`, więc zapisanie wymaga dwóch żądań do D1. Produkt jest odczytywany przez `select … limit 1`, bo może go nie być (zobacz [Drizzle ORM i D1: wsady](/docs/integrations/drizzle-orm-d1#wsady)). Te żądania liczy `toggle-wishlist-item.integration.test.ts`.

Serduszko na kafelkach produktów (`product-card.tsx`) i przycisk na karcie produktu (`product-wishlist-button.tsx`) korzystają z `useWishlist` (`src/hooks/use-wishlist.ts`). Hook odczytuje sesję z `getCurrentSessionQuery` i pobiera identyfikatory produktów tylko wtedy, gdy ktoś jest zalogowany. Niezalogowany kupujący dostaje toast, którego akcja otwiera stronę logowania. Dla zalogowanego klienta hook wywołuje `toggleWishlistItem` i pokazuje toast z wynikiem. Udane przełączenie unieważnia `WISHLIST_QUERY_KEYS.ROOT`, co odświeża oba zapytania listy życzeń. Pełna lista pokazuje toast `wishlistFull`, który podaje limit `WISHLIST_MAX_ITEMS`: `handleRequestError` przekazuje do przeglądarki kod przyczyny `WISHLIST_FULL` (zobacz [Integracje: Better Auth](/docs/integrations/better-auth)). Każde inne niepowodzenie pokazuje `wishlistError`.

`/account/wishlist` wczytuje wstępnie `listWishlistItemsQuery(locale)` i renderuje `WishlistGrid`. Pusta lista życzeń pokazuje odnośnik do produktów. W przeciwnym razie każdy kafelek pokazuje cenę, datę dodania produktu i etykietę braku w magazynie albo niedostępności, z przyciskiem dodania do koszyka dla najtańszego wariantu i przyciskiem usuwania, który wywołuje to samo `toggleWishlistItem`. Produkt, który nie jest już opublikowany, zostaje na liście oznaczony jako niedostępny i nie da się go dodać do koszyka. Licznik w podtytule to `items.length`.
