## Layout i strażnik

`src/routes/account.tsx` to layout. Jego `beforeLoad` to sam strażnik, a `{ user }` zwracane przez strażnika trafia do kontekstu trasy:

```ts
beforeLoad: requireCustomer,
```

`requireCustomer` (`src/integrations/better-auth/auth.routes.ts`) wymaga sesji, a następnie **odsyła administratorów**:

```ts
export const requireCustomer = async (route: AuthRouteContext): Promise<{ user: SessionUser }> => {
  const { user } = await requireSignedIn(route)

  return hasAdminAccess(user.role) ? redirectTo(ROUTES.ADMIN) : { user }
}
```

Administrator nie może więc przeglądać strefy klienta; trafia na `/admin`. `/account/overview` odczytuje użytkownika do powitania przez `AccountRoute.useRouteContext()`.

`requireSignedIn` tylko odczytuje sesję, przez `loadRouteSession`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

Przekazuje `recheck: true`, więc prawdziwa nawigacja do `/account` sprawdza sesję ponownie z `staleTime: 0`; preload linku korzysta z sesji z cache'u, jeśli ma ona mniej niż 60 sekund. Sesja zostaje w cache'u TanStack Query, a render serwerowy dehydratuje ją do strony, więc strony konta renderują się na serwerze jako zalogowane.

Zmiana użytkownika jest obsługiwana w jednym miejscu: w `clearCacheOnUserChange` (`src/integrations/better-auth/auth.session.ts`), które `getRouter` instaluje wyłącznie w przeglądarce. Obserwuje ono cache zapytań i za każdym razem, gdy sesja przełącza się na innego użytkownika, łącznie z zalogowaniem i wylogowaniem, usuwa z cache'u wszystkie zapytania poza samą sesją i katalogami tłumaczeń, więc nic, co zapisano dla poprzedniego użytkownika, nie zostanie pokazane.

Anonimowy gość jest przekierowywany na `/auth/sign-in?redirect=<path>`, gdzie `<path>` to zlokalizowana ścieżka publiczna, na przykład `/en-US/account/orders/order-1`. Zostaje ona zachowana tylko wtedy, gdy pasuje do `SAME_SITE_PATH_PATTERN`: wyłącznie widoczne znaki ASCII, jeden ukośnik na początku i brak ukośnika wstecznego. Po zalogowaniu hasłem, kodem dwuskładnikowym, przez Google albo przez GitHub strażnik `/auth` odsyła gościa z powrotem pod ten adres. Zobacz [Integracje: Better Auth](/docs/integrations/better-auth).

Layout renderuje `Navigation` z witryny, dwukolumnową siatkę i `Footer` z witryny. W `Suspense` owinięte są tylko dwie komórki siatki: `AccountSidebar` ze szkieletem `AccountSidebarFallback` oraz outlet ze szkieletem `AccountMainFallback`. Wstępnie wczytuje cztery przestrzenie nazw: `pages.account`, `pages.account.meta`, `pages.auth.errors` i `pages.auth.validations`.

Samo `/account` tylko przekierowuje:

```ts
beforeLoad: () => {
  redirect({ throw: true, to: "/account/overview" })
},
```

Kolejność w panelu bocznym to `ACCOUNT_OVERVIEW`, `ACCOUNT_PROFILE`, `ACCOUNT_ORDERS`, `ACCOUNT_ADDRESSES`, `ACCOUNT_PAYMENT`, `ACCOUNT_WISHLIST`, `ACCOUNT_SESSIONS` (`account-sidebar.tsx`). Przycisk wylogowania w panelu bocznym wywołuje `signOut`, a potem pełnym przeładowaniem strony wczytuje `/`, co odrzuca cache zapytań.

Każdy loader trasy wczytuje dane wstępnie z `staleTime: "static"`. `account.payment.tsx` i `account.wishlist.tsx` zostawiają `staleTime` trasy domyślnemu `defaultStaleTime` routera, również 60 000; pozostałe sześć plików tras ustawia je na `CUSTOMER_ACCOUNT_QUERY_STALE_MS` (60 000).

## Wzorzec autoryzacji

Każdy use case w `src/modules/customer-account/use-cases/` używa `authorized()` bez argumentu uprawnień — czyli dowolny zalogowany użytkownik — a następnie sam zawęża zapytanie do `context.auth.user.id`. Nie ma sprawdzenia własności na poziomie trasy, które można by obejść; granicą jest funkcja serwerowa. `getCustomerOrder` filtruje na przykład po `and(eq(order.id, orderId), eq(order.userId, context.auth.user.id))`.

## Przegląd

`getCustomerOverview` najpierw odczytuje identyfikatory i numery ostatnich zamówień klienta, potem rozsyła równolegle sześć zapytań, następnie odczytuje pozycje ostatnich zamówień, a na końcu buduje rekomendacje:

| Źródło                                                     | Zasila                                             |
| ---------------------------------------------------------- | -------------------------------------------------- |
| `getCustomerOrderNumbers(userId)`                          | identyfikatory i numery ostatnich zamówień         |
| `getCustomerOrderRows(userId, { limit: 3 })`               | listę ostatnich zamówień                           |
| `getCustomerSpendStats(userId)`                            | `totalOrders`, `totalSpentMinorUnits`              |
| `getCustomerActivityAuditRows(userId, orderIds)`           | strumień aktywności                                |
| `getUserById(userId)`                                      | `memberSinceYear` z `createdAt`                    |
| `countWishlistItems(userId)`                               | `wishlistCount`                                    |
| kolekcja `nowosci`                                         | zapasowe rekomendacje z nowości                    |
| `getOrderItemsForOrders(recentOrderIds)`                   | pozycje pokazywane przy każdym ostatnim zamówieniu |
| `buildCustomerRecommendations(userId, collection, locale)` | `recommendations`, `recommendationsSource`         |

`getCustomerSpendStats` liczy i sumuje wyłącznie zamówienia o statusie `processing` lub `completed`. Limity leżą w `customer-account.constants.ts`: `CUSTOMER_ACCOUNT_ORDERS_LIMIT = 50` dla numerów zamówień, `CUSTOMER_ACCOUNT_OVERVIEW_ORDERS_LIMIT = 3`, `CUSTOMER_ACCOUNT_OVERVIEW_ACTIVITY_LIMIT = 5`, `CUSTOMER_ACCOUNT_RECOMMENDATIONS_LIMIT = 3`, `CUSTOMER_ACCOUNT_RECOMMENDED_CATEGORY_LIMIT = 2`.

Dwie rzeczy warto wiedzieć:

- **Rekomendacje wynikają z zamówień klienta.** `buildCustomerRecommendations` bierze dwie kategorie, które najczęściej występują w zamówieniach klienta o statusie `processing` i `completed`, odczytuje z nich opublikowane produkty i odrzuca każdy produkt, który klient już zamówił. Jeśli coś zostanie, pierwsze trzy wracają z `recommendationsSource: "orders"`. W przeciwnym razie sięga po pierwsze trzy opublikowane produkty kolekcji `nowosci`, tej samej, z której korzystają nowości na stronie głównej (`LANDING_NEW_ARRIVALS_COLLECTION_HANDLE`), z `recommendationsSource: "newArrivals"`, albo zwraca pustą listę, gdy ta kolekcja nie istnieje. Strona dobiera nagłówek i opis siatki do tego źródła.
- **`wishlistCount` jest prawdziwe.** `countWishlistItems` liczy wiersze `wishlist_item` klienta, te same, które wyświetla `/account/wishlist`, więc produkt, który nie jest już opublikowany, nadal się liczy.

Strumień aktywności jest budowany z dziennika audytu: `getCustomerActivityAuditRows` czyta wiersze `audit_log`, których `resourceId` to użytkownik albo jedno z zamówień z `getCustomerOrderNumbers`, ograniczone do `auth.login`, `auth.login_failed`, `auth.logout`, `customer.cart_item_added`, `order.placed`, `order.shipped` i `order.released`. `mapAuditLogToActivityItem` zamienia każdy wiersz w `{ actionKey, params, createdAt }`, wstawiając numer zamówienia do `params` przy akcjach zamówień i odrzucając każdy wiersz, którego nie potrafi zmapować. Strona mapuje `actionKey` na ikonę przez lokalną mapę `ACTIVITY_ICONS` i formatuje znacznik czasu przez `formatRelativeFromNow`.

## Profil

`getCustomerProfile` zwraca `{ createdAt, email, emailVerified, hasPassword, name, phone, timezone, twoFactorEnabled }` z wiersza `user`, przy czym `hasPassword` pochodzi z `hasCredentialAccount`.

`account.profile.tsx` przekazuje `profile.twoFactorEnabled` do `SecuritySection` jako prop, więc stan uwierzytelniania dwuskładnikowego pochodzi z zapytania, które loader strony już wczytał wstępnie. Włączenie lub wyłączenie uwierzytelniania dwuskładnikowego unieważnia zarówno zapytanie profilu, jak i zapytanie sesji.

`updateCustomerPhone` to jedyne pole, które klient może tu zmienić:

```ts
export const updateCustomerPhone = createServerFn({ method: "POST" })
  .middleware([withRateLimit("update-customer-phone", RATE_LIMITS.SENSITIVE), authorized()])
  .validator((input: zod.input<typeof customerAccountZodSchemas.phoneInput>) => customerAccountZodSchemas.phoneInput.parse(input))
  .handler(async ({ context, data: { phone } }): Promise<boolean> => {
    await db
      .update(user)
      .set({ phone: phone === "" ? sql`NULL` : phone })
      .where(eq(user.id, context.auth.user.id))

    return true
  })
```

`RATE_LIMITS.SENSITIVE` to trzy wywołania na minutę. Pusty napis czyści kolumnę do `NULL`, a nie zapisuje `""`. Zmiany nazwy, adresu e-mail i hasła przechodzą przez Better Auth, a nie przez ten moduł.

`PreferencesSection` zawiera też `NewsletterField`, który czyta `getOwnNewsletterSubscriptionQuery()` i wywołuje `subscribeToNewsletter` z własnym adresem konta i `source: "account"`. Wynik `confirmationSent` pokazuje komunikat „sprawdź skrzynkę”, `alreadyConfirmed` informuje, że subskrypcja jest już aktywna, a `confirmationFailed` pokazuje błąd mówiący, że e-maila nie udało się wysłać. Dopóki subskrypcja ma status `pending`, status brzmi „Subskrypcja niepotwierdzona”, a nie obiecuje e-maila, a obok **Wypisz się** jest przycisk **Wyślij ponownie**, więc potwierdzenie, które nie wyszło albo nie dotarło, można wysłać jeszcze raz z nowym linkiem. Na wąskim ekranie oba przyciski przechodzą pod status.

## Adresy

`src/modules/address` ma pięć use case'ów, wszystkie z `authorized()` i wszystkie zawężone do bieżącego użytkownika:

| Use case                      | Middleware                                                                     | Uwagi                                                     |
| ----------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `list-user-addresses.ts`      | `authorized()`                                                                 | `findMany` po zgodnym `userId`                            |
| `create-user-address.ts`      | `withRateLimit("create-user-address", RATE_LIMITS.SENSITIVE)` + `authorized()` | wymusza `userId` z sesji                                  |
| `update-user-address.ts`      | z limitem żądań + `authorized()`                                               |                                                           |
| `delete-user-address.ts`      | `authorized()`                                                                 |                                                           |
| `set-default-user-address.ts` | `authorized()`                                                                 | rzuca `ERROR_CODES.NOT_FOUND`, gdy nic nie zaktualizowano |

`addressFieldsSchema` (`address.zod.ts`) wymaga `address1`, `city` i dwuznakowego `countryCode`; `firstName`, `lastName`, `phone`, `postalCode`, `province` i `address2` są opcjonalne, zgodnie z nullowalnymi kolumnami.

Tabela `address` (`address.schema.ts`) ma `is_default` i dwa indeksy: `address_userId_idx` oraz `address_userId_isDefault_idx`. Zwróć uwagę, że wiersze `address` zapisuje również kasa — z `user_id` równym `null` dla gościa — a `isDefault` jest ustawiane z pól wyboru `saveShippingAddress` / `saveBillingAddress`. Zobacz [Kasa](/docs/features/checkout).

## Sesje

`listCustomerSessions` wybiera wiersze `session` użytkownika uporządkowane malejąco po `updatedAt` i wzbogaca każdy z nich:

```ts
return rows.map((row) => {
  const parsed = parseUserAgent(row.userAgent)

  return {
    browser: parsed.browser,
    createdAt: row.createdAt,
    device: parsed.device,
    deviceType: parsed.deviceType,
    id: row.id,
    ipAddress: row.ipAddress ?? undefined,
    isCurrent: row.id === context.auth.session.id,
    lastActiveAt: row.updatedAt,
  } satisfies CustomerAccount["session"]
})
```

`parseUserAgent` leży w `customer-account.utils.ts`. `lastActiveAt` to `updatedAt` wiersza sesji.

Dwie mutacje unieważniające:

- `revokeCustomerSession({ sessionId })` — zwraca `false` bez usuwania, gdy identyfikator wskazuje **bieżącą** sesję, więc klient nie może się z tego ekranu wylogować. Usunięcie to `and(eq(session.id, sessionId), eq(session.userId, context.auth.user.id))`.
- `revokeOtherCustomerSessions()` — usuwa wszystkie pozostałe sesje użytkownika.

`listCustomerLoginHistory` korzysta z tych samych wierszy audytu i zachowuje tylko `auth.login` oraz `auth.login_failed`, mapując niepowodzenie na `status: "blocked"`. Historia logowań jest więc widokiem na [dziennik audytu](/docs/features/audit-log), a nie osobną tabelą.

## Zapisane metody płatności

Karty są zapisywane w kasie, a nie na stronie konta. Dla zalogowanego klienta `handleCreateCheckoutSession` (`src/integrations/stripe/stripe.actions.server.ts`) wywołuje `ensureStripeCustomer` (`stripe.customer.server.ts`), które zwraca `stripe_customer_id` użytkownika albo tworzy klienta Stripe i zapisuje jego identyfikator w tej kolumnie. Sesja Checkout powstaje następnie dla tego klienta z włączonym `payment_method_save`, które pozwala klientowi wybrać, czy zapisać kartę:

```ts
...(customerId === undefined
  ? { customer_email: email }
  : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
```

Gość dostaje zamiast tego `customer_email` i nie ma klienta Stripe, do którego można by zapisać kartę. `handleUpdateCheckoutSession` korzysta z istniejącego klienta przez `getStripeCustomerId` i nigdy go nie tworzy. Zobacz [Płatności](/docs/features/payments).

Nie ma tabeli zapisanych kart. `listSavedPaymentMethods` (`src/modules/payment/use-cases/list-saved-payment-methods.ts`) używa `authorized()` i pyta Stripe o metody płatności klienta typu `card` albo zwraca pustą listę, gdy użytkownik nie ma klienta Stripe. Każda karta staje się `{ brand, expMonth, expYear, id, isExpired, last4 }`. `isExpired` pochodzi z `isCardExpired` (`payment.utils.ts`), które porównuje datę ważności z dzisiejszą datą we własnej strefie czasowej klienta: `timezone` użytkownika przez `resolveTimezoneCode`, które w razie braku przyjmuje `Europe/Warsaw`.

`/account/payment` wczytuje wstępnie `listSavedPaymentMethodsQuery()` i renderuje `SavedCardList`. Bez kart pokazuje ikonę `CreditCard` i `pages.account.payment.empty`; w przeciwnym razie po jednym wierszu na kartę z marką, czterema ostatnimi cyframi, datą ważności w formacie `MM/YYYY`, plakietką wygaśnięcia, gdy ustawione jest `isExpired`, i przyciskiem usuwania. Licznik w nagłówku to `methods.length`.

Usunięcie karty wywołuje `deleteSavedPaymentMethod` (`delete-saved-payment-method.ts`), chronione przez `withRateLimit("delete-saved-payment-method", RATE_LIMITS.SENSITIVE)` i `authorized()`. Rzuca ono `ERROR_CODES.NOT_FOUND`, gdy użytkownik nie ma klienta Stripe, oraz `ERROR_CODES.FORBIDDEN`, chyba że metoda płatności należy do tego klienta, i dopiero wtedy odłącza ją w Stripe. Po powodzeniu lista unieważnia `PAYMENT_METHOD_QUERY_KEYS.SAVED`.

## Lista życzeń

`wishlist_item` (`src/modules/wishlist/wishlist.schema.ts`) przechowuje jeden wiersz na klienta i produkt. `user_id` i `product_id` są usuwane kaskadowo; `wishlist_item_userId_productId_unique` pilnuje unikalności pary, a `wishlist_item_userId_createdAt_idx` obsługuje listę od najnowszych.

Wszystkie trzy use case'y używają `authorized()` i są zawężone do bieżącego użytkownika:

| Use case                       | Uwagi                                                                                                                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list-wishlist-items.ts`       | `listWishlistItemsQuery(locale)`: od najnowszych, najwyżej `WISHLIST_MAX_ITEMS`, każdy z tytułem w danym języku, najtańszym wariantem, stanem magazynowym i statusem publikacji    |
| `list-wishlist-product-ids.ts` | `listWishlistProductIdsQuery()`: identyfikatory zapisanych produktów, z których korzystają serduszka                                                                               |
| `toggle-wishlist-item.ts`      | `toggleWishlistItemMutation`: usuwa istniejący wiersz, a w przeciwnym razie wstawia nowy dla opublikowanego produktu, dopóki lista ma mniej niż `WISHLIST_MAX_ITEMS` (200) pozycji |

Nieopublikowany produkt rzuca `ERROR_CODES.NOT_FOUND`, a pełna lista rzuca `ERROR_CODES.VALIDATION` z komunikatem `WISHLIST_FULL`.

Serduszko na kafelkach produktów (`product-card.tsx`) i przycisk na karcie produktu (`product-wishlist-button.tsx`) korzystają z `useWishlist` (`src/hooks/use-wishlist.ts`). Hook odczytuje sesję z `getCurrentSessionQuery` i pobiera identyfikatory produktów tylko wtedy, gdy ktoś jest zalogowany. Niezalogowany kupujący dostaje toast, którego akcja otwiera stronę logowania. Dla zalogowanego klienta hook wywołuje `toggleWishlistItem` i pokazuje toast z wynikiem. Udane przełączenie unieważnia `WISHLIST_QUERY_KEYS.ROOT`, co odświeża oba zapytania listy życzeń. Pełna lista pokazuje toast `wishlistFull`, który podaje limit `WISHLIST_MAX_ITEMS`: `handleRequestError` przekazuje do przeglądarki kod przyczyny `WISHLIST_FULL` (zobacz [Integracje: Better Auth](/docs/integrations/better-auth)). Każde inne niepowodzenie pokazuje `wishlistError`.

`/account/wishlist` wczytuje wstępnie `listWishlistItemsQuery(locale)` i renderuje `WishlistGrid`. Pusta lista życzeń pokazuje odnośnik do produktów. W przeciwnym razie każdy kafelek pokazuje cenę, datę dodania produktu i etykietę braku w magazynie albo niedostępności, z przyciskiem dodania do koszyka dla najtańszego wariantu i przyciskiem usuwania, który wywołuje to samo `toggleWishlistItem`. Produkt, który nie jest już opublikowany, zostaje na liście oznaczony jako niedostępny i nie da się go dodać do koszyka. Licznik w podtytule to `items.length`.

## Śledzenie aktywności

`CustomerActivityTracker` (`src/presentation/components/custom/customer-activity-tracker.tsx`) jest montowany w witrynie i zapisuje odsłony oraz porzucenie koszyka — ale tylko dla zalogowanych użytkowników, a `shouldTrackStorefrontPath` pomija każdą ścieżkę zawierającą `/admin` albo `/account`, więc sama strefa konta nie jest śledzona.
