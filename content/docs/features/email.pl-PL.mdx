## Wysyłka

Każdy e-mail wysyła jedna funkcja — `src/integrations/resend/resend.send.ts`:

```ts
const RESEND_TEST_SENDER = /@resend\.dev>?$/iu

const refusesEverySend = ({ name, statusCode }: ErrorResponse, sender: string): boolean =>
  SENDER_REFUSAL_NAMES.has(name) || (SENDER_REFUSAL_STATUSES.has(statusCode) && !RESEND_TEST_SENDER.test(sender))

const deliver = async ({ from, react, revealsAccountExistence, subject, to }: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const sender = from ?? `${APP_NAME} <${env.RESEND_EMAIL_FROM}>`
  try {
    const { error } = await resend.emails.send({ from: sender, react, subject, to })

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error, sender)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

Zwróć uwagę na kontrakt: **nigdy nie rzuca wyjątku.** Zwraca `undefined` przy sukcesie, a w przeciwnym razie komunikat błędu jako napis. SDK Resend nie ma własnego limitu czasu, więc `sendEmail` rezygnuje po `SEND_EMAIL_TIMEOUT_MS` (10 sekund) i zwraca `Resend did not answer within 10000 ms`; zawieszony Resend nie może bez końca blokować zapisu ani webhooka. Każdy wywołujący jest więc napisany jako `const failure = await sendEmail(...)`, po czym decyduje, co zrobić z `failure` — awaria poczty nie może wycofać zamówienia ani usunięcia konta.

Niektóre odmowy oznaczają, że od tego nadawcy nie wyjdzie żaden e-mail: odpowiedź 401 lub 403 z Resend (nieprawidłowy albo ograniczony klucz API lub niezweryfikowana domena nadawcy), nieprawidłowy adres `from` albo wyczerpany dzienny lub miesięczny limit. W takich przypadkach `sendEmail` uruchamia też w tle `markEmailSenderUnavailable` z `src/integrations/resend/resend.availability.server.ts`, chyba że wywołujący przekazał `revealsAccountExistence: true`. Przekazują je weryfikacja, link do zmiany hasła i potwierdzenie zmiany adresu z Better Auth, bo wychodzą tylko wtedy, gdy konto istnieje albo nie istnieje, a flaga ustawiona przez ich odmowę by to zdradziła. `markEmailSenderUnavailable` zapisuje flagę tylko wtedy, gdy nie jest jeszcze ustawiona. Funkcja zapisuje klucz `email-sender-unavailable:<APP_ENV>` w przestrzeni KV `CACHE` z pięciominutowym wygaśnięciem (`EMAIL_SENDER_UNAVAILABLE_SECONDS`). Klucz zawiera `APP_ENV`, bo development i preview korzystają z tej samej przestrzeni. Odmowa dotycząca jednej wiadomości, na przykład nieprawidłowy odbiorca, `rate_limit_exceeded`, odpowiedź 5xx, błąd sieci, przekroczony czas albo 403, które testowy nadawca Resend z domeny `resend.dev` dostaje dla każdego odbiorcy poza właścicielem konta Resend, nie ustawia flagi, więc jeden zły adres czy jeden nagły szczyt ruchu nie zatrzymuje pozostałych e-maili. Na flagę reaguje tylko blokada w Better Auth, która przepuszcza żądania, gdy KV nie da się odczytać; zobacz [Better Auth](/docs/integrations/better-auth#blokada-wysyłki-e-maili). Nic nie usuwa jej wcześniej: po naprawie nadawcy pierwsza próba po wygaśnięciu flagi wychodzi normalnie.

Klientem jest `src/integrations/resend/resend.config.ts`, jednolinijkowe `new Resend(env.RESEND_API_KEY)`. Domyślne `from` to `APP_NAME <RESEND_EMAIL_FROM>`. Zarówno `RESEND_API_KEY`, jak i `RESEND_EMAIL_FROM` są na liście `secrets.required` każdego środowiska w `wrangler.jsonc`. Domena nadawcy musi być zweryfikowana w Resend, a wdrożenie zatrzymuje się przed kompilacją, gdy nie jest; zobacz [Resend](/docs/integrations/resend#domena-nadawcy).

## Osiem szablonów

Wszystkie w `src/presentation/emails/`, zbudowane na `react-email` i renderowane po stronie serwera wewnątrz Workera:

| Szablon                             | Stała przestrzeni nazw                    | Wysyłany przez                                                                                       |
| ----------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `verify-email.tsx`                  | `VERIFY_EMAIL_NAMESPACE`                  | `sendVerificationEmail` (Better Auth)                                                                |
| `reset-password.tsx`                | `RESET_PASSWORD_NAMESPACE`                | `sendResetPassword` (Better Auth)                                                                    |
| `change-email.tsx`                  | `CHANGE_EMAIL_NAMESPACE`                  | `sendChangeEmailConfirmation` (Better Auth)                                                          |
| `account-deleted.tsx`               | `ACCOUNT_DELETED_NAMESPACE`               | `sendAccountDeletedEmail`, wywoływany przez `deleteCustomer` i `afterDelete` z oczekiwaniem na wynik |
| `order-confirmation.tsx`            | `ORDER_CONFIRMATION_NAMESPACE`            | `notifyOrderConfirmed`, z webhooka Stripe                                                            |
| `order-shipped.tsx`                 | `ORDER_SHIPPED_NAMESPACE`                 | `notifyOrderShipped`, oczekiwany przez `shipOrder`                                                   |
| `newsletter-confirmation.tsx`       | `NEWSLETTER_CONFIRMATION_NAMESPACE`       | `sendNewsletterConfirmation`, wywoływany przez `subscribeToNewsletter` z oczekiwaniem na wynik       |
| `newsletter-already-subscribed.tsx` | `NEWSLETTER_ALREADY_SUBSCRIBED_NAMESPACE` | `sendNewsletterAlreadySubscribed`, wywoływany przez `subscribeToNewsletter` z oczekiwaniem na wynik  |

Każdy szablon **eksportuje własną stałą przestrzeni nazw** obok komponentu, na przykład `export const ORDER_CONFIRMATION_NAMESPACE = "emails.order-confirmation"`. Taka jest konwencja: szablon jest właścicielem nazwy swojego katalogu komunikatów, więc nie ma osobnego mapowania, które trzeba utrzymywać w zgodzie.

Wspólne elementy: `email-layout.tsx` (sygnet, złota linia, tagline i stopka), `email-highlight-box.tsx` (`EmailBodyText`, `EmailBorderedSection` i nazwy klas przycisków) oraz `email-styles.ts` (obiekty `CSSProperties` wstawiane inline).

## Lokalizacja

E-mail nigdy nie jest renderowany hookiem Reacta. Komunikaty są wczytywane jawnie i przekazywane jako prop, a temat powstaje w samodzielnym translatorze:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await requireAuthEmailDelivery("verification", {
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verificationUrl }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

`loadNamespace` pochodzi z `src/integrations/use-intl/i18n.messages.ts`, a `createTranslator` z `use-intl` — to punkt wejścia bez Reacta, dzięki któremu to działa wewnątrz handlera webhooka, bez kontekstu żądania.

Źródło języka zależy od wyzwalacza:

| Wyzwalacz                 | Skąd język                                                                   |
| ------------------------- | ---------------------------------------------------------------------------- |
| e-maile Better Auth       | `getCurrentLocale()` — z żądania wykonywanego przez użytkownika              |
| `sendAccountDeletedEmail` | `locale` zapamiętany przed usunięciem, z fallbackiem na `getCurrentLocale()` |
| e-maile newslettera       | `locale` przesłany z zapisem, z fallbackiem na `getCurrentLocale()`          |
| potwierdzenie zamówienia  | `resolveLocale(session)` z metadanych sesji Stripe                           |
| wysyłka zamówienia        | `resolveOrderLocale(orderRow.metadata)` z zapisanego JSON-a zamówienia       |

Dwa ostatnie mają znaczenie: webhook nie ma przeglądarki, więc język musiał zostać utrwalony w momencie składania zamówienia. `createStripeSession` wkłada `locale: getCurrentLocale()` do metadanych sesji, a `prepareFulfillCheckoutBatch` kopiuje go do `order.metadata` — dlatego polski klient dostaje powiadomienie o wysyłce po polsku nawet kilka dni później.

## Stylowanie

`email-layout.tsx` owija wszystko w `<Tailwind config={EMAIL_TAILWIND_CONFIG}>` z react-email i niewielką paletę:

```ts
colors: {
  cream: "#f3f0ea",
  gold: "#b39b6d",
  ink: "#16140f",
  ...
}
```

oraz dwa bezpieczne stosy fontów: `SERIF_STACK` (Georgia, Cambria, Times New Roman, Times, serif) i `SANS_STACK` (Helvetica Neue, Helvetica, Arial, sans-serif), bo fonty webowe są w klientach pocztowych nieprzewidywalne.

Layout wymusza też renderowanie w trybie jasnym:

```tsx
<Head>
  <meta content="light only" name="color-scheme" />
  <meta content="light only" name="supported-color-schemes" />
</Head>
```

`email-styles.ts` przechowuje wartości, które muszą być inline, a nie klasami — `EMAIL_BODY_STYLE`, `EMAIL_CONTAINER_STYLE` (maksymalna szerokość 560 px, obramowanie 1 px `#e2ddd4`), `EMAIL_HIGHLIGHT_BOX_STYLE` i `EMAIL_PRODUCT_IMAGE_STYLE`.

## Potwierdzenie zamówienia w szczegółach

To najbardziej złożony szablon. `stripe.webhooks.tsx` buduje go w `buildOrderConfirmationEmailPayload`:

1. Odbiorcą jest `session.customer_email ?? session.customer_details?.email`. Jeśli go brak, nic nie jest budowane, a przy zamówieniu zapisywana jest porażka `The Stripe session has no email address`.
2. `getCheckoutEmailContext(checkoutId)` wczytuje adresy, metodę dostawy, identyfikator paczkomatu i uwagę klienta.
3. `resolveStripePaymentMethodLabel(session, messages)` zamienia metodę płatności Stripe w przetłumaczoną etykietę.
4. `buildOrderConfirmationDetails(...)` składa blok szczegółów.
5. `buildOrderConfirmationItems(order.lines, locale)` formatuje pozycje.
6. `buildOrderAccountCta({ isGuest, locale, messages, orderId })` wybiera przycisk: zalogowany klient dostaje odnośnik do `/account/orders/<id>`, a gość do `/auth/sign-up`. `isGuest` wynika z pustego `userId` w metadanych sesji.
7. Kwoty: `itemsSubtotal` z linii metadanych i `shippingTotal = Math.max(session.amount_total - itemsSubtotal, 0)`.

Pomocniki leżą w `src/integrations/resend/order-confirmation.utils.ts`, a `resolveDeliveryMethodLabel` dokleja tam identyfikator paczkomatu przy dostawie do paczkomatu.

Obietnice terminów dostawy są treścią, nie danymi — zobacz [Wysyłka i dostawa](/docs/features/shipping-and-delivery):

```ts
const deliveryType = context?.deliveryMethod?.type ?? "courier"
const { estimatedDelivery, fulfillmentTime } = messages.deliveryTiming[deliveryType]
```

## Zapis w audycie

E-maile dotyczące zamówień zapisują swój wynik w dzienniku audytu:

```ts
export const recordOrderEmailOutcome = ({
  failure,
  label,
  orderId,
}: Readonly<{ failure: string | undefined; label: string; orderId: string }>): void => {
  if (failure === undefined) {
    recordEmailSentAudit(orderId, { detail: label, resourceId: orderId })

    return
  }
  console.error(`${label} failed for order ${orderId}: ${failure}`)
  recordEmailFailedAudit(orderId, { detail: `${label} — ${failure}`, resourceId: orderId })
}
```

`label` to czytelny napis, na przykład `Order confirmation → jane@example.com`. Oba e-maile dotyczące zamówień są podzielone tak samo. `sendOrderConfirmationEmail` w `stripe.webhooks.tsx` i `sendOrderShippedEmail` w `order-shipped.notification.server.ts` zwracają `{ failure, label }`, a `notifyOrderConfirmed` i `notifyOrderShipped` przekazują tę próbę do `recordOrderEmailAttempt` w `src/integrations/resend/order-email.outcome.server.ts`:

```ts
export const recordOrderEmailAttempt = async (
  attempt: Promise<OrderEmailOutcome>,
  { label, orderId }: Readonly<{ label: string; orderId: string }>,
): Promise<boolean> => {
  const outcome = await attempt.catch((error: unknown) => {
    console.error(`${label} for order ${orderId} could not be prepared:`, error)

    return { failure: error instanceof Error ? error.message : String(error), label }
  })
  recordOrderEmailOutcome({ failure: outcome.failure, label: outcome.label, orderId })

  return outcome.failure === undefined
}
```

Wyjątek rzucony podczas przygotowywania e-maila trafia do logu razem ze stosem wywołań i też staje się wynikiem, z etykietą bez odbiorcy i opisem utworzonym tak, jak `sendEmail` opisuje przechwycony błąd. Każda próba kończy się więc wpisem:

| Co poszło nie tak                     | Szczegół wpisu `email.failed`                                                       |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| Resend odrzucił wysyłkę               | `Order confirmation → jane@example.com — The example.com domain is not verified…`   |
| Sesja Stripe nie ma adresu            | `Order confirmation — The Stripe session has no email address`                      |
| Zamówienie ma pusty adres             | `Order shipped — The order has no email address`                                    |
| Wiersza zamówienia już nie ma         | `Order shipped — The order could not be found`                                      |
| Przygotowanie e-maila rzuciło wyjątek | `Order shipped — D1_ERROR: …` albo rzucona wartość jako tekst, gdy nie jest `Error` |

Identyfikator zamówienia jest celem i `resourceId` każdego wpisu. Porażkę widać więc w karcie **Aktywność** zamówienia w panelu, jako „Błąd wysyłki e-maila” z oznaczeniem „Niepowodzenie” i szczegółem pod spodem, oraz w `/admin/audit` w kategorii `email` z poziomem `error`. Wpisy audytu trafiają do D1 przez kolejkę kilka sekund po wysyłce, dlatego `processAuditLogQueueBatch` publikuje `ORDER_QUERY_KEYS.ADMIN.ORDERS` za każdym razem, gdy partia zawiera akcję z osi czasu zamówienia: każda otwarta karta panelu pobiera ponownie listę zamówień, statystyki zamówień i otwartą stronę zamówienia, która pokazuje wtedy wpis bez przeładowania. Porażki newslettera i Better Auth używają tej samej akcji `email.failed`, więc też wywołują to odświeżenie. Wpis może jeszcze zginąć w drodze do D1, gdy nie powiedzie się wysłanie do kolejki albo partia zawiedzie trzy razy, bo nie skonfigurowano kolejki martwych wiadomości; wtedy porażkę zna tylko log Workera. Panel nie ma jeszcze przycisku ponownej wysyłki e-maila dotyczącego zamówienia: po usunięciu przyczyny sklep kontaktuje się z klientem pod adresem widocznym w zamówieniu.

E-mail newslettera odrzucony przez Resend również trafia do audytu. `subscribeToNewsletter` wywołuje `recordEmailFailedAudit(email, { detail })`: celem wpisu jest adres, a szczegół podaje rodzaj e-maila i błąd Resend, na przykład `Newsletter confirmation — The example.com domain is not verified` albo `Newsletter already-subscribed notice — …`. Niezweryfikowana domena nadawcy pojawia się więc w `/admin/audit` już przy pierwszym zapisie, a nie tylko w logu Workera. Wysłany e-mail nie jest zapisywany.

Cztery e-maile Better Auth trafiają do audytu w ten sam sposób, przez `recordAuthEmailFailure` w `auth.server.ts`:

```ts
const recordAuthEmailFailure = (kind: string, recipient: string, failure: string): void => {
  console.error(`[Auth] Failed to send ${kind} email to ${recipient}: ${failure}`)
  recordEmailFailedAudit(recipient, { detail: `Auth ${kind} email — ${failure}` })
}

const deliverAuthEmail = async (kind: string, email: Parameters<typeof sendEmail>[0]): Promise<boolean> => {
  const failure = await sendEmail(email)
  if (failure === undefined) {
    return true
  }

  recordAuthEmailFailure(kind, email.to, failure)

  return false
}
```

Celem wpisu jest adres odbiorcy, a szczegół podaje rodzaj e-maila, na przykład `Auth reset-password email — The example.com domain is not verified`. Link weryfikacyjny ani link do zmiany hasła nigdy nie trafia do audytu, bo jest poświadczeniem. To, czy osoba dowie się o porażce, zależy od punktu końcowego; [Better Auth](/docs/integrations/better-auth) opisuje odpowiedź każdego z nich.

`AUDIT_LOG_ACTION.EMAIL_DEFERRED` istnieje, ale nic go nie emituje.

## Czekanie na wysyłkę

Własne wysyłki sklepu czekają na odpowiedź Resend, więc wynik trafia do tego, kto na niego patrzy. Wyjątkiem są hooki rejestracji, resetu hasła i zmiany adresu w Better Auth: Better Auth uruchamia je przez `advanced.backgroundTasks`, czyli `scheduleBackgroundWork` (`src/lib/background.ts`, `waitUntil` Workera), co opisuje [Better Auth](/docs/integrations/better-auth).

`shipOrder`, `deleteCustomer` i webhook Stripe przekazują też wysyłkę, na którą czekają, do `scheduleBackgroundWork`, zanim zaczną na nią czekać:

```ts
const shippedEmailDelivery = notifyOrderShipped(orderId)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery
```

Gdy administrator zamknie kartę albo Stripe przestanie czekać, środowisko Workers może przerwać to, na co żądanie jeszcze czekało, ale nie obietnicę przekazaną do `waitUntil`. Dzięki temu e-mail i tak wychodzi, a jego wynik zostaje zapisany. `afterDelete` w Better Auth czeka na `sendAccountDeletedEmail` bez tego zabezpieczenia, więc klient, który zamknie kartę podczas usuwania własnego konta, nadal może przerwać e-mail pożegnalny.

`shipOrder` czeka na `notifyOrderShipped` po aktualizacji wiersza zamówienia i zwraca `shippedEmailSent`. Administrator zawsze widzi „Zamówienie oznaczono jako wysłane.”, a gdy e-mail nie wyszedł, także ostrzeżenie „Klient nie otrzymał e-maila”, które odsyła po szczegóły błędu do sekcji „Aktywność” zamówienia. Zamówienie i tak pozostaje oznaczone jako wysłane, bo `notifyOrderShipped` zapisuje porażkę i zwraca `false` zamiast rzucać wyjątek. Wysyłka z listy zamówień pokazuje te same komunikaty.

`deleteCustomer` czeka na `sendAccountDeletedEmail` po `removeUser` i zwraca `goodbyeEmailSent`. Administrator widzi „Konto zostało usunięte, a e-mail z potwierdzeniem został wysłany.” albo, gdy e-mail nie wyszedł, ostrzeżenie „Konto usunięte — klient nie otrzymał e-maila”, które odsyła do dziennika zdarzeń. Odmowa nigdy nie cofa usunięcia: `sendAccountDeletedEmail` zwraca `false` zamiast rzucać wyjątek, zarówno gdy Resend odrzuci e-mail, jak i gdy nie da się go nawet przygotować.

`subscribeToNewsletter` czeka na swój e-mail, bo osoba, która właśnie się zapisała, dowiaduje się, czy wyszedł. Nowy, oczekujący albo wypisany adres dostaje `sendNewsletterConfirmation`; adres już potwierdzony, wysłany przez kogokolwiek poza zalogowanym właścicielem, dostaje `sendNewsletterAlreadySubscribed`. Obie funkcje zwracają komunikat błędu Resend albo `undefined`, gdy wysyłka została przyjęta. Przy porażce przypadek użycia loguje ją, zapisuje w audycie i odpowiada `confirmationFailed`. Wiersz, który czekał na potwierdzenie, zostaje w stanie `pending`, więc ponowne wysłanie adresu nadaje nowy token i wysyła nowy e-mail. Żądanie trwa o jedno połączenie z Resend dłużej, najwyżej `SEND_EMAIL_TIMEOUT_MS`, co formularz pokrywa stanem „Zapisujemy...”.

Webhook Stripe też czeka na `notifyOrderConfirmed`, ale nikt nie widzi jego odpowiedzi, więc porażka pojawia się w aktywności zamówienia. `notifyOrderConfirmed` nigdy nie rzuca wyjątku: zarówno odmowa, jak i rzucony błąd kończą się wpisem `email.failed`, a webhook i tak odpowiada 200. Rzucenie wyjątku nie wysłałoby zresztą e-maila ponownie. Handler odpowiedziałby 500 i Stripe dostarczyłby zdarzenie jeszcze raz, ale przy ponownym dostarczeniu `fulfillCheckout` nie znajduje oczekującej kasy i handler kończy przed krokiem e-maila, więc jedynym skutkiem byłyby nieudane dostarczenia w Stripe i sprzątanie kuponu przesunięte na ponowną próbę.

Dlatego strona sukcesu kasy nie twierdzi, że potwierdzenie jest w drodze. Prosi kupującego o kontakt z numerem zamówienia, jeśli e-mail nie dotrze w ciągu kilku minut.

## Podglądanie

```bash
bun run dev
open http://localhost:3000/dev/emails
```

`src/routes/dev.emails.tsx` to handler `GET`, a nie strona Reacta. Jest zabezpieczony trybem budowania:

```ts
if (!import.meta.env.DEV) {
  return notFound()
}
```

więc trasa nie istnieje w buildzie preview ani produkcyjnym. Bez `?template=` renderuje indeks kart; z `?template=<slug>&locale=<locale>` renderuje dany szablon, a dodanie `&format=text` zwraca wersję tekstową zamiast HTML.

`src/integrations/resend/email-previews.tsx` to rejestr. `EMAIL_PREVIEWS` mapuje każdy slug na `{ element: async (locale) => …, label }`, a `renderEmailPreview(slug, locale, plainText)` wywołuje `render` z react-email. Dane testowe są realistyczne i polskie — `PREVIEW_ORDER_ITEMS` używa „Bransoletka Aurora” za 24 900 jednostek podrzędnych oraz „Kolczyki Luna” ×2 za 18 900, `PREVIEW_ADDRESS` to adres warszawski, a dwa zestawy CTA, `PREVIEW_GUEST_CTA` i `PREVIEW_CUSTOMER_CTA`, pozwalają zobaczyć oba warianty `buildOrderAccountCta`.

Każdy szablon poza `newsletter-confirmation` jest wymieniony w `pl-PL` i `en-US`, w HTML i w wersji tekstowej — osiem odnośników na szablon — co czyni ten indeks najszybszym sposobem sprawdzenia zmiany w tłumaczeniu.

Dodanie szablonu oznacza: komponent wraz ze stałą przestrzeni nazw w `src/presentation/emails/`, dwa pliki komunikatów w `messages/{locale}/`, wpis w `EMAIL_PREVIEWS` i wywołującego, który wczyta przestrzeń nazw i wywoła `sendEmail`.

## Czego nie ma

- Nie ma e-maila o porzuconym koszyku. Zdarzenie jest zapisywane w audycie, ale nic nie wysyła wiadomości.
- Nie ma powiadomienia o dostarczeniu ani o zwrocie. Istnieją tylko potwierdzenie i wysyłka.
- Nie ma ponawiania ani kolejki martwych listów dla poczty; porażka jest logowana i zapisywana w audycie. Ponawia sama osoba: zapis do newslettera z formularza na stronie głównej albo przyciskiem „Wyślij ponownie” w preferencjach konta, niepotwierdzone konto przyciskiem „Wyślij link potwierdzający ponownie” na stronie logowania, a zmianę hasła przyciskiem „Wyślij nowy link”.
