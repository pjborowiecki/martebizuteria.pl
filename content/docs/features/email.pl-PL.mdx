## Wysyłka

Każdy e-mail transakcyjny wysyła jedna funkcja — `src/integrations/resend/resend.send.ts`. Newslettery wychodzą partiami własną ścieżką, opisaną w części [Newsletter](#newsletter).

```ts
const RESEND_TEST_SENDER = /@resend\.dev>?$/iu

const refusesEverySend = ({ name, statusCode }: ErrorResponse, sender: string): boolean =>
  SENDER_REFUSAL_NAMES.has(name) || (SENDER_REFUSAL_STATUSES.has(statusCode) && !RESEND_TEST_SENDER.test(sender))

const deliver = async ({
  from,
  idempotencyKey,
  revealsAccountExistence,
  ...message
}: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const sender = from ?? shopSender()
  try {
    const { error } = await resend.emails.send(
      { ...message, from: sender, replyTo: BUSINESS.EMAIL },
      idempotencyKey === undefined ? {} : { idempotencyKey },
    )

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error, sender)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

Wiadomość, czyli `react`, `subject`, `to` i ewentualne `attachments`, trafia do Resend w takiej postaci, w jakiej ją przekazano. Załącznik ma tylko potwierdzenie zamówienia. `idempotencyKey`, który przekazuje każdy e-mail dotyczący zamówienia, trafia do Resend jako nagłówek `Idempotency-Key`, więc ponowna próba pod tym samym kluczem nigdy nie wysyła e-maila dwa razy; zobacz [Wysyłka i ponawianie](#wysyłka-i-ponawianie). `sendEmail` dodaje do każdej wiadomości `replyTo: BUSINESS.EMAIL`, więc odpowiedź klienta trafia na adres kontaktowy sklepu `kontakt@martebizuteria.pl`, a nie na `RESEND_EMAIL_FROM`; zobacz [Resend](/docs/integrations/resend#domena-nadawcy).

Zwróć uwagę na kontrakt: **nigdy nie rzuca wyjątku.** Zwraca `undefined` przy sukcesie, a w przeciwnym razie komunikat błędu jako napis. SDK Resend nie ma własnego limitu czasu, więc `sendEmail` rezygnuje po `SEND_EMAIL_TIMEOUT_MS` (10 sekund) i zwraca `Resend did not answer within 10000 ms`; zawieszony Resend nie może bez końca blokować zapisu ani webhooka. Każdy wywołujący jest więc napisany jako `const failure = await sendEmail(...)`, po czym decyduje, co zrobić z `failure` — awaria poczty nie może wycofać zamówienia ani usunięcia konta.

Niektóre odmowy oznaczają, że od tego nadawcy nie wyjdzie żaden e-mail: odpowiedź 401 lub 403 z Resend (nieprawidłowy albo ograniczony klucz API lub niezweryfikowana domena nadawcy), nieprawidłowy adres `from` albo wyczerpany dzienny lub miesięczny limit. W takich przypadkach `sendEmail` uruchamia też w tle `markEmailSenderUnavailable` z `src/integrations/resend/resend.availability.server.ts`, chyba że wywołujący przekazał `revealsAccountExistence: true`. Przekazują je weryfikacja, link do zmiany hasła i potwierdzenie zmiany adresu z Better Auth, bo wychodzą tylko wtedy, gdy konto istnieje albo nie istnieje, a flaga ustawiona przez ich odmowę by to zdradziła. `markEmailSenderUnavailable` zapisuje flagę tylko wtedy, gdy nie jest jeszcze ustawiona. Funkcja zapisuje klucz `email-sender-unavailable:<APP_ENV>` w przestrzeni KV `CACHE` z pięciominutowym wygaśnięciem (`EMAIL_SENDER_UNAVAILABLE_SECONDS`). Klucz zawiera `APP_ENV`, bo development i preview korzystają z tej samej przestrzeni. Odmowa dotycząca jednej wiadomości, na przykład nieprawidłowy odbiorca, `rate_limit_exceeded`, odpowiedź 5xx, błąd sieci, przekroczony czas albo 403, które testowy nadawca Resend z domeny `resend.dev` dostaje dla każdego odbiorcy poza właścicielem konta Resend, nie ustawia flagi, więc jeden zły adres czy jeden nagły szczyt ruchu nie zatrzymuje pozostałych e-maili. Na flagę reaguje tylko blokada w Better Auth, która przepuszcza żądania, gdy KV nie da się odczytać; zobacz [Better Auth](/docs/integrations/better-auth#blokada-wysyłki-e-maili). Nic nie usuwa jej wcześniej: po naprawie nadawcy pierwsza próba po wygaśnięciu flagi wychodzi normalnie.

Cztery z tych e-maili trafiają na dowolny adres wpisany przez odwiedzającego: e-mail weryfikacyjny, link do zmiany hasła i dwa e-maile newslettera. Ich żądania wymagają tokenu Cloudflare Turnstile, a funkcje, które je wysyłają, najpierw pytają `admitPublicEmail` z `src/integrations/resend/resend.public-email-limits.server.ts`, które pozwala na trzy e-maile jednego rodzaju na jeden adres na godzinę i 50 e-maili wszystkich czterech rodzajów na dobę dla całego sklepu. E-mail ponad którymś z limitów zostaje pominięty, a odwiedzający dostaje taką samą odpowiedź, jakby został wysłany, bo inna zdradzałaby, czy adres ma konto albo subskrypcję; limit dzienny zapisuje też `email.failed`. Każdy inny e-mail trafia prosto do `sendEmail`, więc pracowity dzień nigdy nie wstrzymuje e-maila o zamówieniu. Zobacz [Resend: e-maile, o które może poprosić odwiedzający](/docs/integrations/resend#e-maile-o-które-może-poprosić-odwiedzający).

Klientem jest `src/integrations/resend/resend.config.ts`, jednolinijkowe `new Resend(env.RESEND_API_KEY)`. Domyślne `from` to `APP_NAME <RESEND_EMAIL_FROM>`. Zarówno `RESEND_API_KEY`, jak i `RESEND_EMAIL_FROM` są na liście `secrets.required` każdego środowiska w `wrangler.jsonc`. Domena nadawcy musi być zweryfikowana w Resend, a wdrożenie zatrzymuje się przed kompilacją, gdy nie jest; zobacz [Resend](/docs/integrations/resend#domena-nadawcy).

## Lokalizacja

E-mail nigdy nie jest renderowany hookiem Reacta. Komunikaty są wczytywane jawnie i przekazywane jako prop, a temat powstaje w samodzielnym translatorze:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await requireAuthEmailDelivery("verification", {
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verificationUrl }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

`loadNamespace` pochodzi z `src/integrations/use-intl/i18n.messages.ts`, a `createTranslator` z `use-intl` — to punkt wejścia bez Reacta, dzięki któremu to działa wewnątrz handlera webhooka, bez kontekstu żądania.

Źródło języka zależy od wyzwalacza:

| Wyzwalacz                 | Skąd język                                                                                |
| ------------------------- | ----------------------------------------------------------------------------------------- |
| e-maile Better Auth       | `getCurrentLocale()` — z żądania wykonywanego przez użytkownika                           |
| `sendAccountDeletedEmail` | `locale` zapamiętany przed usunięciem, z fallbackiem na `getCurrentLocale()`              |
| e-maile newslettera       | `locale` przesłany z zapisem, z fallbackiem na `getCurrentLocale()`                       |
| kampania newslettera      | `newsletter_subscriber.locale` każdego subskrybenta; wysyłka testowa renderuje oba języki |
| potwierdzenie zamówienia  | `resolveLocale(session)` z metadanych sesji Stripe                                        |
| nieudana płatność         | `resolveLocale(session)` z metadanych sesji Stripe                                        |
| wysyłka zamówienia        | `resolveOrderLocale(orderRow.metadata)` z zapisanego JSON-a zamówienia                    |
| anulowanie, zwrot         | `resolveOrderLocale(orderRow.metadata)` z zapisanego JSON-a zamówienia                    |
| powiadomienie sklepu      | `I18N.DEFAULT_LOCALE`, język sklepu, niezależnie od języka klienta                        |
| alert sklepu              | `I18N.DEFAULT_LOCALE`, język sklepu                                                       |

E-maile dotyczące zamówień mają tu znaczenie: webhook nie ma przeglądarki, a język administratora nie jest językiem klienta, więc język musiał zostać utrwalony w momencie składania zamówienia. `createStripeSession` wkłada `locale: getCurrentLocale()` do metadanych sesji, a `prepareFulfillCheckoutBatch` kopiuje go do `order.metadata` — dlatego polski klient dostaje powiadomienie o wysyłce po polsku nawet kilka dni później.

## Origin linków

Linki, które sklep wpisuje do własnych e-maili, prowadzą pod adres, którego używał klient albo administrator, tak jak linki Better Auth prowadzą do hosta, na którym go wywołano. Funkcja serwerowa ustala origin, zanim cokolwiek zapisze, przez `resolveRequestOrigin(request)` (`src/lib/request.ts`): bierze go z `request.url`, akceptuje tylko hosty z listy `appHostsForMode(import.meta.env.MODE)`, a dla każdego innego rzuca `AppError(FORBIDDEN)`. Dalej origin jest przekazywany jako napis: `sendNewsletterConfirmation({ email, locale, origin, token })`, `sendNewsletterAlreadySubscribed({ email, locale, origin })`, `sendAccountDeletedEmail({ email, locale, name, origin })`, `notifyOrderShipped(orderId, origin)` i `notifyOrderCancelled({ orderId, refundedAmount }, origin)`. Po samodzielnym usunięciu konta hook `afterDelete` ustala go z żądania, które przekazuje mu Better Auth, a po resecie hasła `sendPasswordChangedEmail` robi to samo z żądaniem, które Better Auth przekazuje do `onPasswordReset`.

Potwierdzenie zamówienia wysyła webhook Stripe, którego żądanie mówi tylko, który endpoint wywołał Stripe. Dlatego bierze ono origin z `return_url` sesji: żądanie checkoutu zbudowało ten adres na własnym, sprawdzonym originie, a wraca on w zdarzeniu ze sprawdzonym podpisem. `resolveDeploymentOrigin(session.return_url)` akceptuje host obsługiwany przez dowolne wdrożenie, lokalne, preview albo produkcyjne, i wymaga `https:` wszędzie poza `localhost:3000` i `127.0.0.1:3000`. Lokalny checkout linkuje więc pod adres, na którym go złożono, choć `stripe:listen` przekazuje webhook na `localhost:3000`, i nawet wtedy, gdy realizuje go wdrożenie preview, które dzieli z developmentem testowe konto Stripe i bazę danych. E-mail o nieudanej płatności robi to samo z sesją ze swojego zdarzenia, e-mail sklepu o nowym zamówieniu z sesją, która utworzyła zamówienie, a e-mail o zwrocie z sesją Checkout, którą `resolveCheckoutSession` znajduje dla zwróconej płatności.

Używany pod `http://127.0.0.1:3000` sklep linkuje do `http://127.0.0.1:3000`. Na preview linkuje do używanego hosta preview, a na produkcji do `https://martebizuteria.pl` albo `https://martebizuteria.pjborowiecki.workers.dev`, zależnie od tego, którego używał klient albo administrator. `APP_URL` służy wyłącznie SEO. Strona [Resend](/docs/integrations/resend) opisuje, skąd origin bierze każdy przepływ.

## Potwierdzenie zamówienia w szczegółach

To najbardziej złożony szablon. `stripe.webhooks.tsx` buduje go w `buildOrderConfirmationEmailPayload`:

1. Odbiorcą jest `session.customer_email ?? session.customer_details?.email`. Jeśli go brak, nic nie jest budowane, a przy zamówieniu zapisywana jest porażka `The Stripe session has no email address`. Wcześniej `sendOrderConfirmationEmail` bierze origin linków z `session.return_url` przez `resolveDeploymentOrigin`. Sesja bez tego adresu zapisuje `The Stripe session has no return URL to link the email to`, a sesja na hoście, którego nie obsługuje żadne wdrożenie, zapisuje `FORBIDDEN`.
2. `getCheckoutEmailContext(checkoutId)` wczytuje adresy, metodę dostawy, identyfikator paczkomatu, uwagę klienta oraz firmę, na którą kupujący chce fakturę. Gdy checkout ma nazwę firmy lub NIP, `describeCompanyInvoice` umieszcza nazwę nad `NIP <cyfry>`, a blok szczegółów pokazuje je pod „Faktura na firmę” po adresie rozliczeniowym; w przeciwnym razie wiersza nie ma.
3. `resolveStripePaymentMethodLabel(session, messages)` zamienia metodę płatności Stripe w przetłumaczoną etykietę.
4. `getFulfillmentTimeAttributesByVariantId(variantIds)` czyta atrybut `czas-realizacji`, który pokazuje strona produktu każdego zamówionego wariantu, a `resolveOrderLineFulfillmentTimes(order.lines, attributes, locale)` zamienia go na etykietę w języku zamówienia. Potem `buildOrderConfirmationDetails({ context, fulfillmentTimes, messages, paymentMethod })` składa blok szczegółów.
5. `buildOrderConfirmationItems(order.lines, locale, origin)` formatuje pozycje i linkuje każdą do strony produktu na `origin`, czyli pod adresem, na którym złożono zamówienie.
6. `buildOrderAccountCta({ isGuest, locale, messages, orderId, origin })` wybiera przycisk: zalogowany klient dostaje odnośnik do `/account/orders/<id>`, a gość do `/auth/sign-up`. `isGuest` wynika z pustego `userId` w metadanych sesji.
7. Kwoty: `itemsSubtotal` z linii metadanych i `shippingTotal = Math.max(session.amount_total - itemsSubtotal, 0)`.
8. `buildOrderLegalLinks(origin, locale, orderNumber)` linkuje regulamin, stronę wymiany i zwrotów, politykę prywatności oraz formularz odstąpienia online pod `/withdraw-from-contract?order=<numer>` na `origin`, w języku zamówienia.
9. `loadWithdrawalFormAttachment(origin)` z `src/integrations/resend/withdrawal-form.attachment.server.ts` czyta `/forms/formularz_zwrotu.pdf` przez binding `ASSETS` Workera i zwraca go zakodowanego w base64 jako załącznik Resend. W developmencie binding serwuje `public/` przez Vite, a w preview i produkcji wdrożone zasoby statyczne, więc PDF jest dołączany wszędzie, także przy lokalnym zamówieniu, którego adresu `localhost` Resend nie mógłby pobrać. Jeśli formularza nie da się odczytać, wiadomość nie jest budowana, a przy zamówieniu zapisywana jest porażka, na przykład `The withdrawal form /forms/formularz_zwrotu.pdf could not be read from the static assets: HTTP 404`, zamiast potwierdzenia wysłanego bez formularza.

Pomocniki leżą w `src/integrations/resend/order-confirmation.utils.ts`, a `resolveDeliveryMethodLabel` dokleja tam identyfikator paczkomatu przy dostawie do paczkomatu.

Ten e-mail jest potwierdzeniem zawarcia umowy na trwałym nośniku, którego wymaga art. 21 ustawy o prawach konsumenta, więc pod podpisem powtarza to, na co klient się zgodził: nazwę, adres pocztowy, NIP, e-mail i telefon Sprzedawcy z `BUSINESS` w `src/presentation/branding/business.ts`, 14-dniowe prawo odstąpienia od umowy wraz ze sposobem skorzystania z niego, to, kto płaci za odesłanie towaru i jak następuje zwrot płatności, tryb reklamacji z pozasądowymi sposobami z § 10 regulaminu oraz trzy linki do dokumentów. Łączna cena z VAT i dostawą, sposób płatności i dostawy oraz termin dostawy są w podsumowaniu zamówienia powyżej. Zobacz [Strony prawne](/docs/features/legal-pages#potwierdzenie-zamówienia).

Czas doręczenia jest treścią wybieraną według rodzaju dostawy, a czas realizacji to najdłuższy z czasów podanych na stronach zamówionych produktów, zapisany jako okres, a nie odesłanie do tych stron, które mogą się zmienić po zamówieniu. Zobacz [Wysyłka i dostawa](/docs/features/shipping-and-delivery#dostawa-w-e-mailach):

```ts
const deliveryType = context?.deliveryMethod?.type ?? "courier"

return {
  estimatedDelivery: messages.estimatedDelivery[deliveryType],
  fulfillmentTime: describeOrderFulfillmentTime(fulfillmentTimes, messages),
}
```

## Anulowanie, zwrot i nieudana płatność

**Anulowanie.** `cancelOrder` wysyła `order-cancelled.tsx` dopiero wtedy, gdy jego wsad anulował zamówienie, więc anulowanie odrzucone przez wsad niczego nie wysyła. `requestFullOrderRefund` zwraca `amount` zwrotu utworzonego w Stripe, a e-mail podaje tę kwotę i mówi, jak pieniądze wracają; klient z bezpłatnym zamówieniem dowiaduje się, że nie było czego zwracać. `notifyOrderCancelled` w `order-cancelled.notification.server.ts` odczytuje adres, numer, walutę, sumę, język i konto zamówienia przez `getOrderForRefundEmail` i linkuje przycisk konta na originie administratora, tak jak e-mail o wysyłce.

**Zwrot.** Każdy zwrot dociera do sklepu jako `charge.refunded`: przycisk Zwrot, zwrot wydany przez anulowanie i zwrot zrobiony w panelu Stripe. `prepareRefundBatch` zaczyna się od odczytu `refunded_amount` płatności i statusu zamówienia, więc `refundOrder` dowiaduje się, co płatność miała zapisane przed tym zdarzeniem, w tej samej transakcji D1, która je zapisuje. Zwraca zwrot jako `Order["unannouncedRefund"]` tylko wtedy, gdy narastające `amount_refunded` płatności jest wyższe i zamówienie nie było anulowane, a e-mail podaje różnicę. Każdy częściowy zwrot jest więc ogłaszany raz, z własną kwotą, a ten, który dopełnia zwrot, mówi, że zamówienie zwrócono w całości; gdy nowsze zdarzenie wyprzedzi starsze, jego e-mail obejmuje oba zwroty. Płatność zachowuje większą z kwot: zapisanej i tej ze zdarzenia, więc ponownie dostarczone zdarzenie, starsze zdarzenie dostarczone po nowszym i `charge.refunded`, które następuje po zwrocie wydanym przez anulowanie, nie zwracają niczego, a D1 wykonuje równoczesne dostarczenia po jednym wsadzie, więc niższą kwotę widzi tylko jedno z nich. `handleChargeRefunded` wysyła wtedy e-mail przez `notifyOrderRefunded(refund, session.return_url)`. Gdy zdarzenie zwrotu dotrze przed wsadem anulowania, zamówienie jest już zwrócone, anulowanie zostaje odrzucone, a klient dostaje tylko e-mail o zwrocie.

**Nieudana płatność.** `checkout.session.async_payment_failed` przychodzi, gdy płatność odroczona nie powiedzie się już po wyjściu klienta z kasy. `releaseCheckout` zwraca, czy jego wsad przestawił płatność sesji z `pending` na `failed`, a `handleAsyncPaymentFailed` wysyła `payment-failed.tsx` tylko wtedy, więc ponownie dostarczone zdarzenie nie znajduje niczego oczekującego i niczego nie wysyła, a wygasła sesja nie wysyła nic. E-mail trafia na adres z sesji, w języku sesji, wymienia produkty z linkami do ich stron, podaje kwotę i linkuje z powrotem do `/products`. Zamówienie nie istnieje, więc `deliverOrderEmail` zapisuje wynik przy identyfikatorze sesji, który jest celem wpisu `order.released` z tego samego zwolnienia; widać go w `/admin/audit`, a nie przy zamówieniu. Odrzucony e-mail o nieudanej płatności jest ponawiany jak każdy e-mail dotyczący zamówienia, pod kluczem `payment-failed/<id sesji>`, ale bez strony zamówienia, na której mógłby się pojawić, nie da się go wysłać ponownie ręcznie.

## E-mail sklepu o nowym zamówieniu

Każde zamówienie utworzone przez webhook Stripe trafia też e-mailem do sklepu, więc właściciel dowiaduje się o nim bez pilnowania panelu. `handleFulfillCheckoutSession` uruchamia `notifyShopOfNewOrder(orderId, session.return_url)` z `src/integrations/resend/new-order.notification.server.ts` obok potwierdzenia dla klienta, przekazuje oba do `scheduleBackgroundWork` jako jedno `Promise.all` i czeka na nie. Ponownie dostarczone zdarzenie nie tworzy zamówienia i nie wysyła żadnego z tych e-maili.

Odbiorcą jest `RESEND_EMAIL_FROM`, adres, z którego sklep wysyła pocztę, wymagany w każdym środowisku, więc powiadomienie wychodzi w każdym środowisku. W środowisku `test`, które buduje zestaw testów end-to-end, `.env.test` ustawia go na `noreply@example.test`, atrapową skrzynkę przechwytywaną przez zamockowany Resend.

E-mail jest w języku sklepu, `I18N.DEFAULT_LOCALE`, niezależnie od języka klienta. Odczytuje zamówienie przez `getAdminOrderDetailRow` i `getAdminOrderItemRows`, te same odczyty, na których stoi strona zamówienia w panelu, i podaje numer zamówienia w temacie i nagłówku, każdy produkt z wariantem, SKU, ilością, ceną jednostkową i wartością pozycji (`mapAdminOrderDetailItem`), sumę z dostawą, imię i nazwisko, e-mail i telefon klienta, sposób dostawy z identyfikatorem paczkomatu, adres dostawy z kopii zapisanej przy zamówieniu (`resolveAdminOrderDetailAddresses`), firmę do faktury i uwagi klienta. Wiersz firmy pojawia się tylko wtedy, gdy zamówienie ma nazwę firmy lub NIP: `describeCompanyInvoice` podaje nazwę i `NIP <cyfry>`, a po nich adres rozliczeniowy z kopii zamówienia, więc właściciel ma wszystko, czego potrzebuje faktura. Jego przycisk otwiera `/admin/orders/<id>` (`ROUTES.ADMIN_ORDER`) na originie z `return_url` sesji, tym samym, na który prowadzą linki potwierdzenia.

Próba przechodzi przez `deliverOrderEmail` jak każdy e-mail dotyczący zamówienia, pod kluczem `new-order/<id zamówienia>` i z etykietą `New order notification → <adres>`, więc odmowa jest ponawiana, a gdy ponowienia też zawiodą, pojawia się w sekcji „Aktywność” zamówienia z przyciskiem **Wyślij ponownie** i w `/admin/audit`. Nigdy nie wpływa na zamówienie ani na potwierdzenie dla klienta: `notifyShopOfNewOrder` nie rzuca wyjątku, a webhook i tak odpowiada 200.

## Wysyłka i ponawianie

Każdy e-mail dotyczący zamówienia wychodzi przez `deliverOrderEmail` w `src/integrations/resend/order-email.delivery.server.ts`. Wywołujący przekazuje mu funkcję, która przygotowuje i wysyła e-mail pod podanym kluczem idempotencji, oraz opis wysyłki:

```ts
export const notifyOrderShipped = (orderId: string, origin: string): Promise<boolean> =>
  deliverOrderEmail((idempotencyKey) => sendOrderShippedEmail(orderId, origin, idempotencyKey), {
    idempotencyKey: `${ORDER_EMAIL_KIND.SHIPPED}/${orderId}`,
    label: ORDER_SHIPPED_LABEL,
    orderEmail: { kind: ORDER_EMAIL_KIND.SHIPPED },
    orderId,
  })
```

`sendOrderConfirmationEmail` i `sendPaymentFailedEmail` w `stripe.webhooks.tsx` oraz `sendOrderShippedEmail`, `sendOrderCancelledEmail`, `sendOrderRefundedEmail` i `sendNewOrderEmail` w swoich plikach `*.notification.server.ts` odczytują to, czego potrzebuje ich e-mail, renderują go i przekazują klucz do `sendEmail`. Zwracają `{ failure, label }`, gdzie `label` to czytelny napis, na przykład `Order confirmation → jane@example.com`.

Każdy klucz nazywa e-mail i to, czego dotyczy:

| E-mail                             | Klucz idempotencji                                                 |
| ---------------------------------- | ------------------------------------------------------------------ |
| Potwierdzenie zamówienia           | `order-confirmation/<id zamówienia>`                               |
| Powiadomienie sklepu o zamówieniu  | `new-order/<id zamówienia>`                                        |
| Wysłanie                           | `order-shipped/<id zamówienia>`                                    |
| Anulowanie                         | `order-cancelled/<id zamówienia>`                                  |
| Zwrot                              | `order-refunded/<id zamówienia>/<suma zwrotów po tym zwrocie>`     |
| Nieudana płatność                  | `payment-failed/<id sesji Checkout>`                               |
| Potwierdzenie odstąpienia          | `order-withdrawal/<id zamówienia>/<czas oświadczenia w ms>`        |
| Powiadomienie sklepu o odstąpieniu | `order-withdrawal-notice/<id zamówienia>/<czas oświadczenia w ms>` |

Resend przechowuje klucz przez 24 godziny i na żądanie z kluczem, pod którym już wysłał e-mail, odpowiada pierwotną odpowiedzią zamiast wysyłać ponownie. Ponowna próba nigdy więc nie dostarcza e-maila dwa razy, nawet gdy pierwsza tylko wyglądała na nieudaną, bo Resend odpowiedział po `SEND_EMAIL_TIMEOUT_MS`. Klucz zwrotu niesie narastające `amount_refunded` jego zdarzenia `charge.refunded`, które `refundOrder` zwraca jako `refundedTotal`, więc dwa częściowe zwroty tej samej kwoty to dwa e-maile.

`deliverOrderEmail` czeka na pierwszą próbę i zwraca, czy Resend ją przyjął. Jeśli nie, próba zostaje zapisana jako `email.deferred`, a ponowienia trafiają do `scheduleBackgroundWork`, czyli `waitUntil` żądania, więc odpowiedź na nie nie czeka i nie bierze w tym udziału żadna kolejka. E-mail jest wysyłany ponownie po `ORDER_EMAIL_RETRY_DELAY_MS` (jednej sekundzie) i jeszcze raz po czasie `ORDER_EMAIL_RETRY_BACKOFF` razy dłuższym (czterech sekundach), łącznie `ORDER_EMAIL_RETRIES` ponowienia, a każde przygotowuje e-mail od nowa i wysyła go pod tym samym kluczem. Pierwsze ponowienie przyjęte przez Resend zostaje zapisane jako `email.sent`; e-mail odrzucony także przy ostatnim zostaje zapisany jako `email.failed`, a `notifyShopOfIncident` wysyła na `RESEND_EMAIL_FROM` alert `orderEmailFailed` z kluczem idempotencji, więc każdy e-mail, który ostatecznie zawiedzie, wywołuje jeden alert, tak jak pozostałe incydenty sklepu (zobacz [Alerty sklepu o incydentach](#alerty-sklepu-o-incydentach)). Przy `SEND_EMAIL_TIMEOUT_MS` równym dziesięciu sekundom ponowienia kończą się najpóźniej około 25 sekund po odpowiedzi, w ramach 30 sekund, które środowisko Workers daje pracy w `waitUntil`. Ponawiana jest każda porażka, także ta z przygotowania e-maila, bo nieudany odczyt z D1 albo pobranie zasobu mija równie często jak limit żądań; porażka, która nie może minąć, na przykład zamówienie bez adresu, kończy się wpisem `email.failed` pięć sekund później.

Wyjątek rzucony podczas przygotowywania e-maila trafia do logu razem ze stosem wywołań jako `<etykieta> for order <id> could not be prepared:` i staje się wynikiem, z etykietą bez odbiorcy i opisem utworzonym tak, jak `sendEmail` opisuje przechwycony błąd.

## Odstąpienie od umowy

`order-withdrawal.tsx` eksportuje dwa e-maile korzystające z jednego katalogu komunikatów, `emails.order-withdrawal`, bo oba powtarzają to samo oświadczenie. `OrderWithdrawalReceived` (`received`) to potwierdzenie na trwałym nośniku, którego wymaga art. 11a dyrektywy w sprawie praw konsumentów: trafia na adres e-mail zamówienia w języku żądania, potwierdza otrzymanie oświadczenia i powtarza jego treść, a potem mówi, dokąd odesłać produkty i jak wygląda zwrot płatności. `OrderWithdrawalNotice` (`notice`) trafia na `RESEND_EMAIL_FROM` w języku sklepu z linkiem do zamówienia w panelu. Oba buduje `src/integrations/resend/order-withdrawal.notification.server.ts`, a w audycie zapisują się jako `Withdrawal acknowledgement → <adres>` i `Withdrawal notice → <adres>`. Wychodzą przez `deliverOrderEmail` jak e-maile dotyczące zamówienia, pod kluczami `order-withdrawal/<id zamówienia>/<czas oświadczenia>` i `order-withdrawal-notice/<id zamówienia>/<czas oświadczenia>`, więc odrzucony jest ponawiany jeszcze dwa razy, a potem wywołuje alert na `RESEND_EMAIL_FROM`; żaden nie niesie tego, czego potrzebuje **Wyślij ponownie**, więc karta „Aktywność” nigdy ich nie oferuje. Data i godzina są zapisane w czasie polskim przez `Intl.DateTimeFormat`, bo Worker działa w UTC. Odstąpienie z użyciem numeru zamówienia na `/withdraw-from-contract` wysyła oba tylko wtedy, gdy `admitPublicEmail` dopuści e-mail rodzaju `withdrawal` na adres zamówienia, tak jak pozostałe e-maile, o które może poprosić odwiedzający; odstąpienie na koncie wysyła je zawsze. Zobacz [Strony prawne: Funkcja odstąpienia od umowy](/docs/features/legal-pages#funkcja-odstąpienia-od-umowy).

## Alerty sklepu o incydentach

`notifyShopOfIncident` z `src/integrations/resend/incident-alert.notification.server.ts` wysyła e-mail na `RESEND_EMAIL_FROM`, gdy zawiedzie coś, czym właściciel musi się zająć: opłacona sesja Checkout, z której nie da się utworzyć zamówienia, zdarzenie Stripe, na które webhook odpowiada błędem, partia dziennika audytu, której konsument kolejki nie potrafi przetworzyć, kampania newslettera zatrzymana w połowie i e-mail do zamówienia odrzucony mimo ponowień. Szablon to `incident-alert.tsx` z katalogiem `emails.incident-alert`, w języku sklepu, z nagłówkiem i wyjaśnieniem dla każdego rodzaju incydentu, identyfikatorem, przyczyną i środowiskiem.

Alerty wysyła każde środowisko, tak jak powiadomienie sklepu o nowym zamówieniu. Każdy incydent jest zapisywany pod kluczem złożonym ze środowiska, rodzaju i identyfikatora — sesji Checkout, typu zdarzenia Stripe, kolejki, kampanii albo klucza idempotencji e-maila do zamówienia — w przestrzeni KV `CACHE` na godzinę (`INCIDENT_ALERT_SECONDS`), więc burza ponowień wysyła jeden e-mail. Alert nigdy nie rzuca wyjątku: nieudany odczyt KV, renderowanie albo wysyłka trafia do logu z prefiksem `[Alert]`, a odpowiedź webhooka i ponowienie kolejki pozostają bez zmian. W przeciwieństwie do e-maili dotyczących zamówień alerty nie są zapisywane w dzienniku audytu, bo zawieść mogła właśnie baza danych. [Monitorowanie i alerty](/docs/guides/monitoring-and-alerts) wyjaśnia, kiedy który się wysyła i co wtedy zrobić.

## Zapis w audycie

`deliverOrderEmail` zapisuje każdy wynik przez `recordOrderEmailOutcome` w `src/modules/audit-log/audit-log.events.server.ts`, z kluczem i e-mailem w metadanych wpisu:

```ts
export const recordOrderEmailOutcome = ({ failure, label, metadata, orderId, willRetry }: Readonly<OrderEmailOutcomeRecord>): void => {
  if (failure === undefined) {
    recordEmailSentAudit(orderId, { detail: label, metadata, resourceId: orderId })

    return
  }
  console.error(`${label} failed for order ${orderId}: ${failure}`)
  const options = { detail: `${label} — ${failure}`, metadata, resourceId: orderId }
  if (willRetry) {
    recordEmailDeferredAudit(orderId, options)

    return
  }
  recordEmailFailedAudit(orderId, options)
}
```

Próba, której Resend nie przyjmie, zawsze kończy się więc wpisem, najpierw `email.deferred`, a gdy ponowienia też zawiodą, `email.failed`:

| Co poszło nie tak                     | Szczegół wpisu                                                                      |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| Resend odrzucił wysyłkę               | `Order confirmation → jane@example.com — The example.com domain is not verified…`   |
| Sesja Stripe nie ma adresu            | `Order confirmation — The Stripe session has no email address`                      |
| Zamówienie ma pusty adres             | `Order shipped — The order has no email address`                                    |
| Wiersza zamówienia już nie ma         | `Order shipped — The order could not be found`                                      |
| Sesja nie ma adresu powrotu           | `Order refunded — The Stripe session has no return URL to link the email to`        |
| Przygotowanie e-maila rzuciło wyjątek | `Order shipped — D1_ERROR: …` albo rzucona wartość jako tekst, gdy nie jest `Error` |

Identyfikator zamówienia jest celem i `resourceId` każdego wpisu, a jego metadane to `{ idempotencyKey, orderEmail }`, gdzie `orderEmail` zawiera to, czego potrzebuje ponowna wysyłka, by zbudować e-mail jeszcze raz: jego rodzaj, a przy anulowaniu zwróconą kwotę, przy zwrocie kwotę tego zwrotu, to, czy dopełnił zwrot, i sumę zwrotów. Wynik widać więc w karcie **Aktywność** zamówienia w panelu, jako „E-mail opóźniony” z oznaczeniem „Opóźniono” albo „Błąd wysyłki e-maila” z oznaczeniem „Niepowodzenie” i szczegółem pod spodem, oraz w `/admin/audit` w kategorii `email` z poziomem `warning` albo `error`. Wpisy audytu trafiają do D1 przez kolejkę kilka sekund po wysyłce, dlatego `processAuditLogQueueBatch` publikuje `ORDER_QUERY_KEYS.ADMIN.ORDERS` za każdym razem, gdy partia zawiera akcję z osi czasu zamówienia: każda otwarta karta panelu pobiera ponownie widoczną listę zamówień, statystyki albo stronę zamówienia, a zapytania o zamówienia trzymane tylko w cache usuwa, więc otwarta strona zamówienia pokazuje wpis bez przeładowania. Porażki newslettera i Better Auth używają tej samej akcji `email.failed`, więc też wywołują to odświeżenie. Wpis może jeszcze zginąć w drodze do D1, gdy nie powiedzie się wysłanie do kolejki albo gdy nie da się go zapisać nawet po trzech osobnych ponowieniach w kolejce martwych listów; wtedy porażkę zna tylko log Workera, a porażki wysyłają też e-mail na `RESEND_EMAIL_FROM`, najwyżej raz na godzinę dla każdej kolejki.

## Ponowna wysyłka z zamówienia

Karta „Aktywność” pokazuje przycisk **Wyślij ponownie** pod najnowszym wpisem `email.deferred` albo `email.failed` każdego e-maila dotyczącego zamówienia, który od tamtej pory nie wyszedł. `resolveResendableOrderEmails` w `src/modules/order/order.detail.utils.ts` czyta oś czasu zamówienia od najnowszych wpisów, bierze pierwszy wpis wysyłki dla każdego klucza idempotencji, którego metadane nazywają e-mail, i proponuje go, chyba że jest to `email.sent`. Wpisy zapisane, zanim wysyłki zaczęły nieść te metadane, oraz e-mail o nieudanej płatności, który należy do sesji, a nie do zamówienia, nigdy nie dostają przycisku.

Przycisk wywołuje `resendOrderEmail` w `src/modules/order/use-cases/resend-order-email.ts` z zamówieniem i identyfikatorem wpisu. Funkcja wymaga `order: ["update"]`, ponownie czyta oś czasu i odmawia z `CONFLICT`, jeśli ten wpis nie jest już tym do ponowienia, więc druga karta albo e-mail, który w międzyczasie wyszedł, niczego nie wysyła. Zapisuje `email.resend_requested` przy zamówieniu przez `scheduleAuditLogFromRequest`, z administratorem jako sprawcą, jego adresem IP i szczegółem nieudanego wpisu, a potem buduje e-mail jeszcze raz z tych samych źródeł, z których korzystała pierwsza próba. E-maile o wysłaniu i anulowaniu linkują na originie administratora, tak jak `shipOrder` i `cancelOrder`. Potwierdzenie, powiadomienie sklepu i e-mail o zwrocie pobierają ze Stripe sesję Checkout zamówienia po `transaction_id` płatności, a zamówienie bez niej zostaje odrzucone z `CONFLICT`. Ponowna wysyłka przechodzi przez ten sam notyfikator i `deliverOrderEmail` pod tym samym kluczem, z tymi samymi ponowieniami i wpisami, więc w ciągu 24 godzin od pierwszej wysyłki e-mail, który jednak dotarł do Resend, choć jego wynik mówił co innego, nie zostaje wysłany drugi raz.

Hook `useResendOrderEmail` pokazuje „E-mail wysłany”, gdy Resend przyjął e-mail, a „E-mail jeszcze nie wysłany” z informacją o dwóch kolejnych próbach, gdy go nie przyjął. Dopóki e-mail nie wyjdzie, przycisk pojawia się znów pod jego najnowszym wpisem.

E-mail newslettera odrzucony przez Resend również trafia do audytu. `subscribeToNewsletter` wywołuje `recordEmailFailedAudit(email, { detail })`: celem wpisu jest adres, a szczegół podaje rodzaj e-maila i błąd Resend, na przykład `Newsletter confirmation — The example.com domain is not verified` albo `Newsletter already-subscribed notice — …`. Niezweryfikowana domena nadawcy pojawia się więc w `/admin/audit` już przy pierwszym zapisie, a nie tylko w logu Workera. Wysłany e-mail nie jest zapisywany.

Pięć e-maili Better Auth trafia do audytu w ten sam sposób, przez `recordAuthEmailFailure` w `auth.server.ts`:

```ts
const recordAuthEmailFailure = (kind: string, recipient: string, failure: string): void => {
  console.error(`[Auth] Failed to send ${kind} email to ${recipient}: ${failure}`)
  recordEmailFailedAudit(recipient, { detail: `Auth ${kind} email — ${failure}` })
}

const deliverAuthEmail = async (kind: string, email: Parameters<typeof sendEmail>[0]): Promise<boolean> => {
  const failure = await sendEmail(email)
  if (failure === undefined) {
    return true
  }

  recordAuthEmailFailure(kind, email.to, failure)

  return false
}
```

Celem wpisu jest adres odbiorcy, a szczegół podaje rodzaj e-maila, na przykład `Auth reset-password email — The example.com domain is not verified`. Link weryfikacyjny ani link do zmiany hasła nigdy nie trafia do audytu, bo jest poświadczeniem. To, czy osoba dowie się o porażce, zależy od punktu końcowego; [Better Auth](/docs/integrations/better-auth) opisuje odpowiedź każdego z nich.

`email.deferred` zapisuje tylko `deliverOrderEmail`. Pozostałe e-maile zapisują odmowę jako `email.failed`: e-maile Better Auth i e-maile zapisu do newslettera od razu, kampania newslettera wtedy, gdy zawiedzie trzecia próba partii.

## Czekanie na wysyłkę

Własne wysyłki sklepu czekają na odpowiedź Resend, więc wynik trafia do tego, kto na niego patrzy. Wyjątkiem są hooki rejestracji, resetu hasła i zmiany adresu w Better Auth: Better Auth uruchamia je przez `advanced.backgroundTasks`, czyli `scheduleBackgroundWork` (`src/lib/background.ts`, `waitUntil` Workera), co opisuje [Better Auth](/docs/integrations/better-auth). Drugim wyjątkiem jest e-mail o zmianie hasła: `onPasswordReset` sam przekazuje `sendPasswordChangedEmail` do `scheduleBackgroundWork` i na niego nie czeka, bo Better Auth wylogowuje wszystkie urządzenia dopiero po powrocie z hooka.

`shipOrder`, `cancelOrder`, `deleteCustomer` i webhook Stripe przekazują też wysyłkę, na którą czekają, do `scheduleBackgroundWork`, zanim zaczną na nią czekać:

```ts
const shippedEmailDelivery = notifyOrderShipped(orderId, origin)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery
```

Gdy administrator zamknie kartę albo Stripe przestanie czekać, środowisko Workers może przerwać to, na co żądanie jeszcze czekało, ale nie obietnicę przekazaną do `waitUntil`. Dzięki temu e-mail i tak wychodzi, a jego wynik zostaje zapisany. Żądanie czeka tylko na pierwszą próbę: `deliverOrderEmail` planuje ponowienia odrzuconego e-maila dotyczącego zamówienia w ten sam sposób, więc wykonują się po odpowiedzi. `afterDelete` w Better Auth czeka na `sendAccountDeletedEmail` bez tego zabezpieczenia, więc klient, który zamknie kartę podczas usuwania własnego konta, nadal może przerwać e-mail pożegnalny.

`shipOrder` czeka na `notifyOrderShipped` po aktualizacji wiersza zamówienia i zwraca `shippedEmailSent`, czyli to, czy Resend przyjął e-mail przy pierwszej próbie. Administrator zawsze widzi „Zamówienie oznaczono jako wysłane.”, a gdy nie przyjął, także ostrzeżenie „Klient jeszcze nie otrzymał e-maila”, które mówi, że sklep spróbuje jeszcze dwa razy w ciągu kilku sekund, a jeśli i to się nie uda, wiadomość można wysłać ponownie z sekcji „Aktywność” zamówienia, gdzie widać też błąd. Zamówienie i tak pozostaje oznaczone jako wysłane, bo `notifyOrderShipped` zapisuje porażkę i zwraca `false` zamiast rzucać wyjątek. Wysyłka z listy zamówień pokazuje te same komunikaty.

`cancelOrder` czeka w ten sam sposób na `notifyOrderCancelled` po wsadzie anulowania i zwraca `cancelledEmailSent`. Administrator widzi komunikat o anulowaniu, a gdy Resend nie przyjął e-maila od razu, także ostrzeżenie „Klient jeszcze nie otrzymał e-maila” z tą samą informacją o ponowieniach i ponownej wysyłce. Zamówienie pozostaje anulowane, a zwrot wydany.

`deleteCustomer` czeka na `sendAccountDeletedEmail` po `removeUser` i zwraca `goodbyeEmailSent`. Administrator widzi „Konto zostało usunięte, a e-mail z potwierdzeniem został wysłany.” albo, gdy e-mail nie wyszedł, ostrzeżenie „Konto usunięte — klient nie otrzymał e-maila”, które odsyła do dziennika zdarzeń. Odmowa nigdy nie cofa usunięcia: `sendAccountDeletedEmail` zwraca `false` zamiast rzucać wyjątek, zarówno gdy Resend odrzuci e-mail, jak i gdy nie da się go nawet przygotować. E-mail mówi, co zostało usunięte, w tym klient Stripe z zapisanymi kartami, oraz że zamówienia i płatności zostają w dokumentacji księgowej przez 5 lat od końca roku każdego zamówienia, już bez powiązania z kontem, i że nowe konto potwierdzone tym samym adresem znów je pokaże.

`subscribeToNewsletter` czeka na swój e-mail, bo osoba, która właśnie się zapisała, dowiaduje się, czy wyszedł. Nowy, oczekujący albo wypisany adres dostaje `sendNewsletterConfirmation`; adres już potwierdzony, wysłany przez kogokolwiek poza zalogowanym właścicielem, dostaje `sendNewsletterAlreadySubscribed`. Obie funkcje zwracają komunikat błędu Resend albo `undefined`, gdy wysyłka została przyjęta. Przy porażce przypadek użycia loguje ją, zapisuje w audycie i odpowiada `confirmationFailed`. Wiersz, który czekał na potwierdzenie, zostaje w stanie `pending`, więc ponowne wysłanie adresu nadaje nowy token i wysyła nowy e-mail. Żądanie trwa o jedno połączenie z Resend dłużej, najwyżej `SEND_EMAIL_TIMEOUT_MS`, co formularz pokrywa stanem „Zapisujemy...”.

Webhook Stripe też czeka na `notifyOrderConfirmed` i `notifyShopOfNewOrder`, ale nikt nie widzi jego odpowiedzi, więc porażka pojawia się w aktywności zamówienia. Żadna z nich nie rzuca wyjątku: zarówno odmowa, jak i rzucony błąd kończą się wpisem `email.deferred` i ponowieniami, a webhook i tak odpowiada 200, nie czekając na nie. Rzucenie wyjątku nie wysłałoby zresztą e-maila ponownie. Handler odpowiedziałby 500 i Stripe dostarczyłby zdarzenie jeszcze raz, ale przy ponownym dostarczeniu `fulfillCheckout` nie znajduje oczekującej kasy i handler kończy przed krokiem e-maila, więc jedynym skutkiem byłyby nieudane dostarczenia w Stripe i sprzątanie kuponu przesunięte na ponowną próbę.

Dlatego strona sukcesu kasy nie twierdzi, że potwierdzenie jest w drodze. Prosi kupującego o kontakt z numerem zamówienia, jeśli e-mail nie dotrze w ciągu kilku minut.

## Newsletter

Właściciel pisze newslettery na stronie **Marketing** panelu, `/admin/marketing`. **Nowy newsletter** otwiera `/admin/marketing/new`, zbudowaną z elementów edytora treści: karta polska i angielska, w każdej temat do 150 znaków i list do 20 000 znaków pisany w tym samym edytorze Markdown co strony informacyjne. Linki muszą być pełnymi adresami `https://`, `mailto:` albo `tel:`, bo link względny nic nie znaczy w skrzynce pocztowej, a obrazy są odrzucane tak jak na stronach treści; oba warunki sprawdza `newsletterCampaignZodSchemas.composeValues` za pomocą `hasOnlyMarkdownLinksMatching(NEWSLETTER_LINK_PATTERN)`. Wyjście ze strony z niewysłanym listem wymaga potwierdzenia.

**Wyślij test do mnie** wywołuje `sendNewsletterTest`, który wysyła obie wersje językowe na adres zalogowanego administratora, bez zapisywania kampanii i bez nagłówków wypisania. **Wyślij do subskrybentów** prosi o potwierdzenie, podając, do ilu potwierdzonych subskrybentów trafi list, i wywołuje `sendNewsletterCampaign`. Obie funkcje wymagają `content: ["update"]`.

`sendNewsletterCampaign` liczy potwierdzonych subskrybentów i odmawia z `NEWSLETTER_NO_RECIPIENTS`, gdy nie ma żadnego. Zapisuje kampanię w `newsletter_campaign` pod identyfikatorem, który edytor wygenerował przy otwarciu, z oboma tematami i listami, originem żądania administratora, na który prowadzą linki, liczbą odbiorców i statusem `sending`. Gdy ten identyfikator już istnieje, zapis nic nie robi, a funkcja odpowiada `NEWSLETTER_ALREADY_SENT`, więc podwójne kliknięcie ani ponowione żądanie nigdy nie zaczyna drugiej wysyłki. Następnie kampania trafia do kolejki Cloudflare `NEWSLETTER_QUEUE`, wysyłka jest zapisywana w audycie jako `newsletter.sent` na administratora, a otwarte strony panelu odświeżają listę. Gdy kolejka odrzuci wiadomość, `deleteUnsentNewsletterCampaign` z powrotem usuwa kampanię, chyba że wyszła już jakaś partia, więc lista nie pokazuje niczego, co się nie zaczęło, a administrator dowiaduje się, że nic nie zostało wysłane. Edytor zachowuje list i jego identyfikator, więc ponowna wysyłka zapisuje i kolejkuje kampanię od nowa, a ponowienie, którego pierwsza próba jednak trafiła do kolejki, nadal dostaje `NEWSLETTER_ALREADY_SENT`.

`processNewsletterQueueBatch` w `src/modules/newsletter-campaign/newsletter-campaign.queue.server.ts`, który `src/server.ts` wywołuje dla partii z kolejki o nazwie zaczynającej się od `martebizuteria-newsletter`, wysyła jedną partię kampanii na wiadomość. Czyta 100 (`NEWSLETTER_BATCH_SIZE`) kolejnych potwierdzonych subskrybentów w kolejności identyfikatorów po `last_recipient_id`, ostatnim, do którego dotarła kampania, a `sendNewsletterBatch` w `src/integrations/resend/newsletter-campaign.server.ts` wysyła ich jednym wywołaniem endpointu wsadowego Resend, który przyjmuje najwyżej 100 e-maili. Każdy subskrybent dostaje temat i list w języku, w którym się zapisał, wyrenderowane przez `newsletter-campaign.tsx` w szacie sklepu, a pod nimi informację, dlaczego go otrzymuje, oraz link **Wypisz się z newslettera** do `/newsletter/unsubscribe?token=<jego token>` w jego języku, który działa bez logowania. Na końcu list wskazuje nadawcę, czego art. 9 ustawy o świadczeniu usług drogą elektroniczną wymaga od informacji handlowej: firmę i adres przedsiębiorcy z `BUSINESS_POSTAL_ADDRESS_LINES`, kraj oraz adres e-mail sklepu, `BUSINESS.EMAIL`. Każdy e-mail niesie też `List-Unsubscribe: <origin/api/newsletter/unsubscribe?token=…>` i `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, więc dostawcy poczty mogą pokazać własny przycisk wypisania, który wysyła POST pod ten adres (RFC 8058).

Kampania nigdy nie wychodzi dwa razy. Każda partia trafia do Resend z kluczem idempotencji `newsletter-<id kampanii>`, a po pierwszej partii `newsletter-<id kampanii>-after-<id ostatniego subskrybenta>`, więc Resend nie wysyła partii ponownie, gdy jej wiadomość zostanie dostarczona dwa razy w ciągu 24 godzin. Kursor przesuwa tylko aktualizacja warunkowa względem kursora, od którego partia zaczęła, i tylko dostarczenie, które go przesunęło, kolejkuje następną partię, sekundę później. Konsument bierze jedną wiadomość naraz (`max_batch_size: 1`, `max_concurrency: 1`), co trzyma sklep wyraźnie poniżej domyślnego limitu Resend, dwóch żądań na sekundę. Partia mniejsza niż 100 albo brak kolejnych odbiorców oznacza kampanię jako `sent`.

Partia odrzucona przez Resend lub nieudana z innego powodu jest ponawiana po 60 sekundach. Przy trzeciej próbie (`NEWSLETTER_SEND_ATTEMPTS`) kampania dostaje status `failed` z przyczyną, w audycie pojawia się `email.failed` na kampanię, `notifyShopOfIncident` wysyła na `RESEND_EMAIL_FROM` alert `newsletterFailed` z identyfikatorem kampanii (zobacz [Monitorowanie i alerty](/docs/guides/monitoring-and-alerts#alerty-e-mail-ze-sklepu)), a reszta listy nie jest wysyłana. Wiadomość, na której konsument wciąż rzuca wyjątek, na przykład gdy D1 jest niedostępne, po `max_retries` (3) trafia do kolejki martwych listów `-dlq`. Ten sam Worker konsumuje ją tą samą funkcją, po jednej wiadomości i co pięć minut, więc kampania jest kontynuowana od ostatniego subskrybenta, do którego dotarła, albo zatrzymuje się i wysyła alert jak wyżej. Subskrybent, który potwierdzi zapis w trakcie wysyłki, dostaje kampanię, gdy jego identyfikator wypada po partiach już wysłanych; kto wypisze się przed swoją partią, zostaje pominięty.

Strona Marketing pokazuje, ilu subskrybentów jest potwierdzonych, czeka na potwierdzenie i się wypisało, oraz listę 50 ostatnich newsletterów z tematem w języku administratora, statusem (Wysyłanie, Wysłany albo Przerwany), liczbą potwierdzonych subskrybentów, do których dotarły, czasem rozpoczęcia i zakończenia oraz przyczyną przerwania. Lista odświeża się sama, gdy wychodzą kolejne partie.

### Newslettery a poczta transakcyjna

Newslettery nigdy nie przechodzą przez `sendEmail` ani `admitPublicEmail`. Dzienny limit 50 e-maili, które odwiedzający mogą kazać sklepowi wysłać, pilnowany przez `admitPublicEmail` dla e-maili weryfikacyjnych, resetu hasła, zapisu do newslettera i odstąpienia od umowy, nie liczy więc ani kampanii, ani wysyłki testowej i ich nie wstrzymuje, a kampania nigdy nie wyczerpuje dziennej puli odwiedzających; odrzucona partia newslettera nie ustawia też flagi niedostępnego nadawcy. Newslettery dzielą jednak konto Resend z pocztą transakcyjną: każdy e-mail newslettera wlicza się do dziennego i miesięcznego limitu konta i do limitu żądań. Na darmowym planie Resend, 100 e-maili dziennie, newsletter do więcej niż kilkudziesięciu subskrybentów wyczerpałby dzienny limit i e-maile zamówień nie wychodziłyby do następnego dnia, więc zanim lista urośnie, sklep potrzebuje płatnego planu Resend.

## Podglądanie

```bash
bun run dev
open http://localhost:3000/dev/emails
```

`src/routes/dev.emails.tsx` to handler `GET`, a nie strona Reacta. Jest zabezpieczony trybem budowania:

```ts
if (!import.meta.env.DEV) {
  return notFound()
}
```

więc trasa nie istnieje w buildzie preview ani produkcyjnym. Bez `?template=` renderuje indeks kart; z `?template=<slug>&locale=<locale>` renderuje dany szablon, a dodanie `&format=text` zwraca wersję tekstową zamiast HTML.

`src/integrations/resend/email-previews.tsx` to rejestr. `EMAIL_PREVIEWS` mapuje każdy slug na `{ element: async (locale) => …, label }`, a `renderEmailPreview(slug, locale, plainText)` wywołuje `render` z react-email. Dane testowe są realistyczne i polskie — `PREVIEW_ORDER_ITEMS` używa „Bransoletka Aurora” za 24 900 jednostek podrzędnych oraz „Kolczyki Luna” ×2 za 18 900, `PREVIEW_ADDRESS` to adres warszawski, a dwa zestawy CTA, `PREVIEW_GUEST_CTA` i `PREVIEW_CUSTOMER_CTA`, pozwalają zobaczyć oba warianty `buildOrderAccountCta`.

Każdy szablon poza `newsletter-confirmation` i `newsletter-campaign`, który właściciel sprawdza przyciskiem **Wyślij test do mnie**, jest wymieniony w `pl-PL` i `en-US`, w HTML i w wersji tekstowej — osiem odnośników na szablon — co czyni ten indeks najszybszym sposobem sprawdzenia zmiany w tłumaczeniu.

Dodanie szablonu oznacza: komponent wraz ze stałą przestrzeni nazw w `src/presentation/emails/`, dwa pliki komunikatów w `messages/{locale}/`, wpis w `EMAIL_PREVIEWS` i wywołującego, który wczyta przestrzeń nazw i wywoła `sendEmail`.

## Czego nie ma

- Nie ma e-maila o porzuconym koszyku. Zdarzenie jest zapisywane w audycie, ale nic nie wysyła wiadomości.
- Nie ma powiadomienia o dostarczeniu.
- Nie ma e-maila, gdy płatność nie powiedzie się w trakcie płacenia (`payment_intent.payment_failed`): błąd pokazuje formularz płatności.
- Nie ma kolejki, skrzynki nadawczej ani kolejki martwych listów dla poczty transakcyjnej. E-mail dotyczący zamówienia jest ponawiany dwa razy w ramach `waitUntil` żądania, a potem czeka na przycisk **Wyślij ponownie** administratora; e-maila o nieudanej płatności, który nie ma zamówienia, nie da się wysłać ponownie. E-maile Better Auth i e-maile zapisu do newslettera mają jedną próbę, a porażka jest logowana i zapisywana w audycie. Ponawia je sama osoba: zapis do newslettera z formularza na stronie głównej albo przyciskiem „Wyślij ponownie” w preferencjach konta, niepotwierdzone konto przyciskiem „Wyślij link potwierdzający ponownie” na stronie logowania, a zmianę hasła przyciskiem „Wyślij nowy link”.
