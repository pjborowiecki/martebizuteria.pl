## Route

`src/routes/_storefront.index.tsx` is the whole page. It renders fifteen sections from `src/presentation/components/custom/pages/landing-page/sections`, in this order:

```tsx
<main ref={rootRef} className="bg-background text-foreground" data-landing-page>
  <HeroSection />
  <VideoExperienceSection />
  <ValuesSection />
  <ManifestoSection />
  <NewArrivalsSection />
  <MobileCategoriesSection />
  <DesktopCategoriesSection />
  <ArchiveSection />
  <BreakerSection />
  <ShopCategoriesSection />
  <PhilosophySection />
  <SilverPremiumSection />
  <MaisonHeritageSection />
  <ShopCollectionsSection />
  <NewsletterSection />
</main>
```

All copy comes from the `pages.landing` namespace (`messages/{locale}/pages.landing.json`). The route declares `staticData.namespaces: ["pages.landing", "pages.categories"]`, so both catalogues are preloaded before the page renders.

The `_storefront` layout in `src/routes/_storefront.tsx` supplies the navigation, the paused-sales notice, the cart availability banner and the footer. Its loader loads `getCollectionsQuery()` for the full-screen menu's collection pictures and `getSalesStatusQuery()` for the notice, so every storefront page brings both in its server-rendered cache. If a read fails, the page still renders and the menu or the notice asks again after it mounts. The notice shows only while sales are paused; see [Checkout: Pausing sales](/docs/features/checkout#pausing-sales). `ImageShowcase` keeps its slides in the closed menu but renders their pictures only while `mounted` from `useNavigation()` is true, from the moment the menu opens until its closing animation ends. A page load therefore downloads none of the showcase pictures, and the first one is fetched with `priority` when the menu opens, while the image frame is still fading in. The menu can be opened only below the `xl` breakpoint, and the showcase shows only from `lg` up.

## What the loader fetches

The loader runs three queries in parallel and returns the page metadata:

| Query                   | Use case                                                   | Used by                                               |
| ----------------------- | ---------------------------------------------------------- | ----------------------------------------------------- |
| `messagesQueryOptions`  | `src/integrations/use-intl/i18n.messages.ts`               | `head` title and description                          |
| `getNewArrivalsQuery()` | `src/modules/product/use-cases/get-new-arrivals.ts`        | `NewArrivalsSection`                                  |
| `getCategoriesQuery()`  | `src/modules/product-category/use-cases/get-categories.ts` | `MobileCategoriesSection`, `DesktopCategoriesSection` |

Both catalog queries are fetched with `staleTime: "static"`, so the server render never refetches them. After the queries resolve, `prefetchProductThumbnails(newArrivals, context.imagePrefetchService)` from `src/lib/image.ts` warms the thumbnails of the new-arrival products.

## New arrivals

`getNewArrivals` is a `GET` server function with the `withRequest` middleware only — it is public. It lists the published, in-stock products of a single collection, named by its handle:

```ts
getPublishedProductsByCollectionHandle(LANDING_NEW_ARRIVALS_COLLECTION_HANDLE, {
  limit: LANDING_NEW_ARRIVALS_PRODUCT_LIMIT,
  offset: 0,
})
```

`getPublishedProductsByCollectionHandle` in `src/modules/product/product.accessors.ts` reads the whole section in one D1 statement. Its subquery selects the members of the collection with that handle, matched by `storefrontCollectionByHandleWhere` from `src/modules/product-collection/product-collection.server.ts`, the same rule `/collections/$handle` uses, so only an active collection counts. The outer query keeps the published, in-stock members, orders them by `rank` and then newest first, and reads their variants. Only when one of those variants is reduced does a second statement read its price history, so the card can show the lowest price of the 30 days before the reduction (see [Catalog and search](/docs/features/catalog-and-search#reduced-prices-on-cards)).

Both constants live in `src/modules/product/product.constants.ts`:

- `LANDING_NEW_ARRIVALS_COLLECTION_HANDLE = "nowosci"`
- `LANDING_NEW_ARRIVALS_PRODUCT_LIMIT = 9`

**The section is driven entirely by that collection handle.** If no collection with the handle `nowosci` is active, the grid renders empty and no error is raised. To change which products appear, change the collection's members in [the admin catalog](/docs/features/admin-catalog) — not the code.

The query key is `PRODUCT_QUERY_KEYS.LANDING_NEW_ARRIVALS`, which is one of the keys `scheduleProductCatalogInvalidation()` and `scheduleCollectionCatalogInvalidation()` push over the storefront realtime hub, so publishing a product or editing the collection refreshes open landing pages.

## Categories

`MobileCategoriesSection` and `DesktopCategoriesSection` both read `getCategoriesQuery()` with `useSuspenseQuery`, and share their copy resolution through `landing-category-panel.utils.ts` (`resolveLandingCategoryPanelCopy`).

The desktop variant pins the section and scrolls the category panels horizontally. A single `gsap.to` on the track, created in `gsap.matchMedia()` for `(min-width: 1024px) and (prefers-reduced-motion: no-preference)`, carries a `ScrollTrigger` with the id `landing-categories`, `pin: true`, `scrub: true` and `invalidateOnRefresh: true`. The pin lasts one viewport height for every panel after the first, and the track follows the scroll position directly. The helpers in `landing-category-horizontal-scroll.ts` only measure: `resolveHorizontalScrollEnd` gives the length of the pin, `resolveHorizontalTrackOffset` how far the track travels, and `resolveHorizontalPanelScrollTop` the scroll position at which a given panel reaches the left edge.

Nothing in the section refreshes `ScrollTrigger`. Each panel image is positioned `absolute inset-0` inside a fixed-ratio box, so a lazy image that arrives as its panel slides in changes no layout, while a forced refresh in the middle of a scroll stops the page dead. ScrollTrigger re-measures by itself after a resize and on the window `load` event, and `useGSAP` with `revertOnUpdate` rebuilds the scroll when the categories change.

The section is `overflow-clip`, not `overflow-hidden`, so it is not a scroll container, and moving focus into it cannot shift the panels sideways under the animation. When a **Discover** link receives keyboard focus (`:focus-visible`), the section's `onFocus` handler finds the trigger with `ScrollTrigger.getById("landing-categories")` and moves Lenis straight to that panel's scroll position with `getLenisInstance()?.scrollTo(top, { immediate: true })`. Tab and Shift+Tab therefore slide each category into view, including a Tab after a click on a panel's picture. The section's `onBlur` remembers a link that loses focus while focus goes nowhere else, which is how Chromium reports a switch to another window or tab. When focus comes back to that same link, the page stays where the shopper scrolled it. Clicking the link does not move the page.

Shoppers who ask for reduced motion get no horizontal scroll. On wide screens the desktop section is `motion-reduce:lg:hidden` and the mobile section is `motion-reduce:lg:block`. From `lg` its cards sit three to a row (`lg:grid-cols-3`), and their pictures are requested at a third of the screen width (`sizes="(min-width: 1024px) 33vw, 100vw"`).

## The guide section and the hidden blog

`ArchiveSection`, the "M'ARTE Guide" block after the categories, lists the blog's articles from `BLOG_POST_SLUGS` in `src/data/blog-posts.ts`. The blog has no articles yet, so that list is empty, and an empty list hides the whole blog:

- `ArchiveSection` renders nothing, so the home page shows fourteen sections;
- the loaders of `/blog` and `/blog/$slug` throw `notFound()`, so both answer 404;
- `STATIC_PAGES` in `src/data/static-pages.ts` leaves `/blog` out of `/sitemap.xml`;
- the navigation, the footer and `public/llms.txt` do not link the blog.

To publish an article, add its slug to `BLOG_POST_SLUGS` and give it, in both `messages/{locale}` folders, a `title` and a `description` under `posts.<slug>` in `pages.blog.json` and a home page title under `archiveSection.articles.<slug>` in `pages.landing.json`. `blog-posts.test.ts` fails while the list and the messages disagree. The article page shows only the title and the description, so the first article also needs a body in `_storefront.blog.$slug.tsx`, and the guide goes back into `public/llms.txt` with it.

## Scroll animation

`src/hooks/use-landing-animations.ts` is called once from the page component with a ref to `<main>`. It reads GSAP and `ScrollTrigger` from `src/integrations/gsap/gsap.config.ts` and wires three effects by class name:

| Class            | Effect                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------- |
| `.reveal`        | Fade and rise once, batched through `ScrollTrigger.batch`; elements already in view animate immediately |
| `.line-reveal`   | Horizontal rule scales in from the left, once                                                           |
| `.parallax-wrap` | The `.parallax-img` inside it translates as the wrapper scrolls                                         |

So a new section joins the choreography by adding `reveal` to its outer element — there is nothing to register.

Smooth scrolling itself is Lenis, mounted by `src/presentation/components/custom/smooth-scroll.tsx` and kept in step with the router by `src/hooks/use-lenis-router-scroll-sync.ts`.

## Newsletter section

`newsletter-section.tsx` renders a react-hook-form form validated by `newsletterZodSchemas.subscribeFormValues`, which trims the address and checks that it is an email. A valid address goes to the `subscribeToNewsletter` mutation from `src/modules/newsletter/use-cases/subscribe-to-newsletter.ts`:

```tsx
subscribe.mutate({
  email,
  locale: isSupportedLocale(locale) ? locale : undefined,
  requestTurnstileToken: requestToken,
  source: NEWSLETTER_SOURCE.LANDING,
})
```

`requestToken` comes from `useTurnstileToken(TURNSTILE_ACTIONS.NEWSLETTER)`, whose container sits under the field. `subscribeToNewsletterMutation` calls it when the mutation runs and sends the token as `turnstileToken`.

The server function needs no session and is rate-limited with `withRateLimit("newsletter-subscribe", RATE_LIMITS.SENSITIVE)`. It first checks the token with `verifyTurnstileToken` for the `newsletter` action on the request's host, and a token that does not pass is refused with `FORBIDDEN` and `BOT_CHECK_FAILED` before anything is read or saved; the section shows its usual retryable error. It then asks `admitPublicEmail` whether the address may get another newsletter email: at most three an hour per address, and 50 emails a day that visitors ask for across the whole shop. Past either limit it answers `confirmationSent` without saving, issuing a token or sending, so the link in the email already sent keeps working and the answer says nothing about the address (see [Resend: Emails visitors can request](/docs/integrations/resend#emails-visitors-can-request)). Otherwise it saves the address in `newsletter_subscriber` as `pending` with a new token, then awaits `sendNewsletterConfirmationEmail`, whose link opens `/newsletter/confirm` on the address the form was submitted on. That origin comes from `resolveRequestOrigin(getRequest())`, so a sign-up on `localhost:3000` gets a `localhost:3000` link, and a request on a host this build does not serve is refused with `FORBIDDEN` before anything is saved. What the section shows depends on the outcome:

| Outcome              | When                                                                                                                           | The section                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `confirmationSent`   | Resend accepted the confirmation email, or the already-subscribed notice for a confirmed address, or a limit skipped the email | Replaces the form with the "check your inbox" message                         |
| `confirmationFailed` | Resend refused either email, or did not answer within `SEND_EMAIL_TIMEOUT_MS`                                                  | Keeps the form open with the address filled in and a retryable error under it |
| `alreadyConfirmed`   | The address is confirmed and belongs to the signed-in visitor                                                                  | Replaces the form with "You are already on the list."                         |

A failed send logs the Resend error and records an `email.failed` entry in `/admin/audit`; a row that was waiting for confirmation stays `pending`. Pressing the button again resubmits the same address: the row gets a fresh token and the email is sent again, up to the third email to that address in an hour. Every attempt counts towards the three-a-minute limit and needs a new Turnstile token. The address field is read-only while a request is running, so the answer cannot be lost to an edit; editing it afterwards clears the error.

An address that is already confirmed gets `alreadyConfirmed` only when it belongs to the signed-in visitor, and nothing is sent. Anyone else gets the same treatment as a new address: the request waits for `sendNewsletterAlreadySubscribedEmail`, which tells the owner of the inbox that they are already on the list, and answers `confirmationSent` or `confirmationFailed` exactly as a new signup would. The row and its token stay as they are, so links in letters already sent keep working. The answer is therefore the same whether or not the address is on the list, both paths spend their time waiting for one Resend round trip, and a subscriber who is not signed in gets an email instead of a promise of one.

The daily retention clean-up deletes a row still `pending` 30 days after the address last asked for a confirmation, and an `unsubscribed` row 30 days after it left; see [Data retention](/docs/guides/data-retention).

## Section anchors

`NewArrivalsSection` is the only section with an `id`: `id="nowosci"`. Links elsewhere that need to reach it use that hash. The other sections are not addressable.
