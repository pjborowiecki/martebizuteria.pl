Tabela `user` jest współdzielona z Better Auth, więc „klienci” to widok na dane uwierzytelniania złączone z agregatami zamówień. Moduł to `src/modules/user`.

## Tabela user

`src/modules/user/user.schema.ts` rozszerza bazowego użytkownika Better Auth o własne kolumny M'Arte:

| Kolumna                               | Uwagi                                                                                                                   |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `email`                               | 320 znaków, unikalny, not null                                                                                          |
| `name`                                | 256 znaków, not null                                                                                                    |
| `email_verified`                      | boolean, domyślnie `false`, not null                                                                                    |
| `role`                                | `admin \| customer`, domyślnie `DEFAULT_ROLE` (`customer`)                                                              |
| `banned`, `ban_reason`, `ban_expires` | pola wtyczki admin z Better Auth                                                                                        |
| `is_anonymous`                        | boolean, domyślnie `false`; nic jej nie zapisuje (zobacz niżej)                                                         |
| `two_factor_enabled`                  | boolean, domyślnie `false`                                                                                              |
| `phone`                               | 32 znaki; zapisywane przez `updateCustomerPhone` i `updateCustomer`                                                     |
| `timezone`                            | 64 znaki; zapisana strefa czasowa klienta, zapisywana przez `updateDisplayPreference`, `NULL` dla pozycji Automatycznie |
| `format_locale`                       | 35 znaków; zapisany format dat i liczb, zapisywany w ten sam sposób                                                     |
| `image`                               | 2048 znaków                                                                                                             |
| `stripe_customer_id`                  | zapisywana przez `ensureStripeCustomerWithEmail` w kasie i `ensureStripeCustomer` na stronie konta                      |
| `metadata`                            | napis JSON z notatkami i tagami administratora                                                                          |

Jeden indeks: `user_createdAt_idx`.

`is_anonymous` została po wtyczce `anonymous()` Better Auth, której sklep już nie ładuje (zobacz [Better Auth](/docs/integrations/better-auth#brak-logowania-anonimowego)): nic jej już nie ustawia, a nowy użytkownik dostaje wartość domyślną. Nadal oznacza użytkowników utworzonych przez tę wtyczkę, którzy w siatce wyglądają jak klienci z zastępczym adresem i nazwą „Anonymous”. Zostaje w tabeli i w schemacie Drizzle, dopóki nie usunie jej osobna migracja, zastosowana dopiero po wdrożeniu kodu, który przestał ją deklarować, bo Worker z wcześniejszym kodem odczytuje ją z każdym wczytywanym wierszem użytkownika.

## Trasy

| Trasa                  | Plik                        | Uprawnienie jej funkcji serwerowych                                 |
| ---------------------- | --------------------------- | ------------------------------------------------------------------- |
| `/admin/customers`     | `admin.customers.index.tsx` | `user: ["list"]`                                                    |
| `/admin/customers/$id` | `admin.customers.$id.tsx`   | `user: ["get"]` dla szczegółów, `order: ["read"]` dla jego zamówień |

Same trasy wymagają tylko `requireAdmin` z layoutu `/admin`; każda funkcja serwerowa sprawdza własne uprawnienie. Loader indeksu wczytuje wstępnie `getAdminCustomersPageQuery({ page: 1, pageSize: ADMIN_CUSTOMER_PAGE_SIZE })` i `getAdminCustomerStatsQuery()`, a loader szczegółów `getAdminCustomerQuery(id, locale)` i pierwszą stronę zamówień klienta, `getAdminOrdersPageQuery({ page: 1, pageSize: CUSTOMER_ORDERS_VIEW.pageSize, userId: id })`, wszystkie z `staleTime: "static"`. `ADMIN_CUSTOMER_PAGE_SIZE` to 25, a `ADMIN_CUSTOMER_QUERY_STALE_MS` to 60 000. Obie trasy deklarują `staticData.namespaces: ["pages.admin.customers"]`.

## Siatka

`getAdminCustomersPage` (`use-cases/get-admin-customers-page.ts`) ma `authorized({ user: ["list"] })`. Obsługuje frazę wyszukiwania, `statFilter` i siedem filtrów kolumn:

```ts
filters: {
  averageOrderValue: input.averageOrderValue,
  banned: input.banned,
  createdAt: input.createdAt,
  emailVerified: input.emailVerified,
  lastOrderAt: input.lastOrderAt,
  role: input.role,
  totalSpent: input.totalSpent,
}
```

`createdAt` i `lastOrderAt` są filtrowane według dnia w strefie administratora przez `buildAdminDateTimeFilterSql`, tak jak na stronie zamówień i w dzienniku zdarzeń.

Fraza wyszukiwania pasuje do imienia i nazwiska, adresu e-mail, telefonu, identyfikatora i identyfikatora klienta Stripe, a także do każdego konta, które kiedykolwiek używało adresu zawierającego tę frazę (`accountsWithAddressContaining` na `user_email_history`, zobacz [Konto: Adresy używane przez konto](/docs/features/account#adresy-używane-przez-konto)), więc klienta da się znaleźć po adresie, którym już się nie loguje. Eksport stosuje to samo wyszukiwanie.

Akcesor zwraca pięć rzeczy — `rows`, `orderStats`, `defaultAddresses`, `latestShippingAddresses` i `total` — a use case zszywa je po stronie aplikacji:

```ts
const statsByUserId = mapCustomerOrderStats(orderStats)
const locationByUserId = mapCustomerLocations(defaultAddresses, latestShippingAddresses)
const items = rows.map((row) => toAdminCustomerListItem(row, statsByUserId.get(row.id), locationByUserId.get(row.id)))
```

Kolumna lokalizacji pokazuje więc miasto, województwo i kraj z **zapisanego domyślnego adresu** klienta. Może to być adres rozliczeniowy: klient, który przy zamówieniu zaznaczy „Zapisz ten adres rozliczeniowy na przyszłość”, ma ten adres zapisany również jako domyślny. Gdy checkout zostawi jako domyślne oba adresy, dostawy i rozliczeniowy, `getDefaultCustomerAddressesQuery` zwraca je w kolejności zapisu, a `mapCustomerLocations` bierze pierwszy, czyli zwykle adres dostawy, bo checkout zapisuje go jako pierwszy. Klient bez zapisanego domyślnego adresu dostaje adres dostawy (`order_address` typu `shipping`) z najnowszego zamówienia, które go ma, bez względu na status zamówienia. Zamówienie anulowane lub zwrócone daje więc lokalizację, choć nie liczy się do kolumny „Ostatnie zamówienie”, a nowsze zamówienie bez wiersza dostawy jest pomijane. Przy dwóch zamówieniach z tą samą chwilą wygrywa późniejszy numer zamówienia. Przy zamówieniu do paczkomatu adres dostawy to adres wpisany przez klienta, nie adres paczkomatu, a zamówienia sprzed zapisywania kopii adresów (bez wierszy `order_address`) nie dają lokalizacji. `getLatestOrderShippingAddressesQuery` wybiera jeden adres na klienta jednym zapytaniem z `row_number()`, dla całej strony albo całego eksportu, który pokazuje tę samą lokalizację co siatka. Czyta zamówienia klientów przez `order_userId_status_idx`, a wiersz dostawy każdego zamówienia przez `order_address_orderId_idx`. Jednoargumentowy `+` przy `order_address.type` nie pozwala SQLite zacząć od indeksu `order_address_type_idx`, który przeszedłby po wszystkich adresach dostawy w sklepie.

Liczba zamówień klienta, łączne wydatki, średnia wartość zamówienia i wartość klienta korzystają z zasady sprzedaży z pulpitu (zobacz [Pulpit admina](/docs/features/admin-dashboard#migawka)): `orderCountsAsSale` wybiera jego zamówienia w realizacji i zrealizowane, a `netSalesSum` sumuje kwotę każdego z nich pomniejszoną o to, co zwrócono z jego płatności, więc zamówienia oczekujące, anulowane i zwrócone się nie liczą, a częściowy zwrot pomniejsza sumę. Średnia wartość zamówienia dzieli tę sumę przez te same zamówienia, a „wydano łącznie” na karcie klienta w szczegółach zamówienia (`getAdminOrderCustomerStats`) to ta sama liczba. Wykres wydatków, podział na kategorie oraz ulubiona kategoria i kolekcja czytają te same zamówienia; trzy ostatnie sumują pozycje zamówień, przy których zwroty nie są zapisywane. Wyjątkiem jest siatka zamówień na ekranie szczegółów: pokazuje każde zamówienie klienta, bez względu na status.

Identyfikatory kolumn, szerokości, domyślna widoczność i przypięcia leżą w `user.constants.ts` pod `ADMIN_CUSTOMER_TABLE_COLUMN_ID`, `ADMIN_CUSTOMER_TABLE_COLUMN_SIZE`, `ADMIN_CUSTOMER_TABLE_DEFAULT_COLUMN_VISIBILITY` i obiektem przypięć. Kolumny to `select`, `customer` (imię i nazwisko z adresem e-mail pod spodem), `recordId`, `stripeCustomerId`, `role`, `phone`, `emailVerified`, `banned`, `location`, `orderCount`, `totalSpent`, `averageOrderValue`, `lastOrderAt`, `createdAt` i `actions`; `recordId` i `stripeCustomerId` są na początku ukryte. Kwoty i daty są zapisane w formacie i strefie czasowej administratora.

Siatka to `customersDataGrid` (`utils/customers-data-grid.ts`), której kolejność kolumn, szerokości i widoczność są zapamiętywane pod `admin.customers`, a steruje nią `useCustomersDataGrid` (`hooks/use-customers-data-grid.ts`) ze stronicowaniem po stronie serwera i wyszukiwaniem z opóźnieniem po imieniu i nazwisku, adresie e-mail, telefonie, identyfikatorze i identyfikatorze klienta Stripe oraz po adresach, których każde konto używało wcześniej. Kliknięcie wiersza otwiera `/admin/customers/$id`. Menu wiersza oferuje szczegóły, kopiowanie identyfikatora, adresu e-mail albo identyfikatora klienta Stripe oraz **Usuń konto**, wyszarzone w wierszu każdego konta z dostępem do panelu (zobacz [Dwie mutacje](#dwie-mutacje)).

Komponenty leżą w `.../admin/customers/components/`: `customers-table.tsx`, `customers-columns.tsx` (z definicjami kolumn w `lib/customers-column-defs.tsx`), filtry (`customers-role-filter`, `customers-banned-filter`, `customers-email-verified-filter`, `customers-date-column-filter` wraz z `customers-date-filter-form`, `customers-numeric-column-filter`), plakietki (`customer-role-badge`, `customer-banned-badge`, `customer-email-verified-badge`), `customer-name-cell`, `customer-table-cells`, `customers-row-actions`, `customers-stats` z `customer-stat-card` oraz akcja odświeżenia; eksport to wspólny `Export` z `customersDataGrid`. Karty są skonfigurowane w `.../admin/customers/customers-stats.config.ts`, a usunięcie obsługuje `hooks/use-delete-customer.ts`.

## Statystyki

`getAdminCustomerStats` uruchamia równolegle trzy zapytania i wyprowadza karty w czystej funkcji:

```ts
const [[totalRow], [rollupRow], [averageProductsPerOrderRow]] = await Promise.all([
  getAdminCustomerTotalCountQuery(),
  getAdminCustomerOrderRollupStatsQuery(),
  getAverageProductsPerOrderQuery(),
])

return computeAdminCustomerStatsFromAggregates({
  averageLtv: rollupRow?.averageLtv ?? 0,
  averageProductsPerOrder: averageProductsPerOrderRow?.value ?? 0,
  customersWithOrders: rollupRow?.customersWithOrders ?? 0,
  repeatCustomers: rollupRow?.repeatCustomers ?? 0,
  total: totalRow?.count ?? 0,
})
```

`computeAdminCustomerStatsFromAggregates` i `resolveAdminCustomerReturningRate` leżą w `user.utils.ts`, co utrzymuje arytmetykę testowalną jednostkowo. Cztery karty to liczba klientów, odsetek powracających, średnia wartość klienta i średnia liczba produktów w zamówieniu, zapisane w formacie administratora. Filtry statystyk zadeklarowane są w `ADMIN_CUSTOMER_STAT_FILTER` (`total` i `returning`), a dwie pierwsze karty działają jako filtry siatki: `total` pokazuje wszystkich klientów, a `returning` zostawia tych, którzy mają co najmniej `ADMIN_CUSTOMER_MIN_REPEAT_ORDERS` (2) zamówień sprzedażowych.

## Ekran szczegółów

`/admin/customers/$id` czyta `getAdminCustomerQuery(id, locale)` przez `useSuspenseQuery` i rzuca `notFound()` przez `ensureAdminCustomerDetail`, gdy wiersza brak.

`getAdminCustomer` (`authorized({ user: ["get"] })`) to najszerszy odczyt w całym kodzie — jedenaście odczytów, najpierw `getUserById`, a potem równolegle dziesięć pozostałych: dziewięć kolejnych akcesorów z `user.accessors.ts` i `getUserEmailHistory` z `user-email-history.accessors.ts`:

| Akcesor                               | Zasila                                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `getUserById`                         | tożsamość, rolę, weryfikację, stan bana, metadane                                                                    |
| `getCustomerOrderStatsQuery`          | liczbę zamówień, sumę wydatków i ostatnie zamówienie                                                                 |
| `getAdminCustomerOrderRowsQuery`      | wpisy „Złożono zamówienie” na osi czasu: najnowsze zamówienia sprzedażowe, `ADMIN_CUSTOMER_DETAIL_ORDERS_LIMIT = 10` |
| `getCustomerMonthlySpendingQuery`     | wykres wydatków, `ADMIN_CUSTOMER_DETAIL_MONTHS = 12`                                                                 |
| `getCustomerCategoryBreakdownQuery`   | podział na kategorie: pięć kategorii głównych z największymi wydatkami klienta                                       |
| `getCustomerPreferredCategoryQuery`   | wiersz preferowanej kategorii                                                                                        |
| `getCustomerPreferredCollectionQuery` | wiersz preferowanej kolekcji                                                                                         |
| `getDefaultCustomerAddressFullQuery`  | `formatAdminCustomerFullAddress` i pola adresu w edytorze                                                            |
| `getLatestSessionActivityQuery`       | `formatAdminCustomerLastActive`                                                                                      |
| `getCustomerAuditTimelineQuery`       | `buildAdminCustomerTimeline`                                                                                         |
| `getUserEmailHistory`                 | `buildAdminCustomerEmailHistory`: każdy adres, którego konto używało, od najnowszego                                 |

„Ostatnia aktywność” to `updatedAt` najnowszej sesji, a gdy żadna sesja nie została, ostatnie zamówienie albo `updatedAt` wiersza, zapisane przez `formatRelativeFromNow`: przez tydzień jako czas względny w języku strony, potem jako data.

Wykres wydatków liczy miesiące tak jak pulpit (zobacz [Pulpit admina](/docs/features/admin-dashboard#wykresy)). `resolveAdminDashboardMonths(now, ADMIN_CUSTOMER_DETAIL_MONTHS, timeZone)` daje ostatnie dwanaście miesięcy aż do tego, który trwa teraz w strefie administratora, każdy zaczynający się tam o północy pierwszego dnia, a `getCustomerMonthlySpendingQuery(userId, window)` sumuje sprzedaże klienta od `start` okna do jego `end`, grupując je przez `calendarPeriodKey`. Dla administratora w Polsce zamówienie złożone o 00:30 1 kwietnia liczy się więc w kwietniu, choć w UTC jest jeszcze 31 marca. `buildAdminCustomerMonthlySpendingSeries` daje każdemu miesiącowi okna jeden punkt, z zerem tam, gdzie nic nie kupiono, nazwany w formacie administratora. Data rejestracji oraz daty i kwoty na osi czasu korzystają z tych samych preferencji; nazwy kategorii zostają w języku strony. Podział na kategorie to lista, a nie wykres: każda kategoria z kwotą i paskiem w skali największej z nich.

Zamówienia klienta to sama siatka zamówień. `CustomerOrders` wywołuje `useOrdersDataGrid({ onRowClick: openOrder, userId, view: CUSTOMER_ORDERS_VIEW })`, więc `getAdminOrdersPage` czyta stronę z `userId` dodanym do warunków, a kolumny, plakietki, wyszukiwanie i akcje wiersza są te same co w `/admin/orders` (zobacz [Zamówienia: lista w panelu](/docs/features/orders#lista-w-panelu)); pasek narzędzi ma tylko wyszukiwanie, bez filtrów, odświeżania i eksportu ze strony zamówień. `CUSTOMER_ORDERS_VIEW` (`customer-detail/utils/customer-orders-data-grid.ts`) ukrywa kolumny klienta, adresu e-mail i zaznaczenia, przypina identyfikator zamówienia i akcje, zaczyna od 10 wierszy na stronę i zapamiętuje własne ustawienia kolumn pod `admin.customer-orders`. Kliknięcie wiersza otwiera `/admin/orders/$orderId`, a **Zobacz wszystko** prowadzi do `/admin/orders`. Zamówienia są nazywane numerem `orderNumber` (`MRT-2026-00001`) tutaj i we wpisach „Złożono zamówienie” na osi czasu, a wiersz nadal otwiera zamówienie po jego identyfikatorze.

Tagi są wyprowadzane, a nie przechowywane:

```ts
export const resolveAdminCustomerTags = (row: User["select"], orderCount: number): AdminCustomerDetailTag[] => {
  const tags: AdminCustomerDetailTag[] = []
  if (row.role === ROLES.ADMIN) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.ADMIN)
  } else {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.CUSTOMER)
  }
  if (orderCount >= ADMIN_CUSTOMER_MIN_REPEAT_ORDERS) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.RETURNING)
  }
  if (row.emailVerified) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.VERIFIED)
  }
  if (row.banned === true) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.BANNED)
  }

  return tags
}
```

`ADMIN_CUSTOMER_MIN_REPEAT_ORDERS` to 2. Tagi własne dodane przez administratora pochodzą z kolumny metadanych i są scalane osobno.

`buildAdminCustomerTimeline` łączy trzy źródła, od najnowszych: utworzenie konta, wpisy „Złożono zamówienie” dla najwyżej dziesięciu zamówień sprzedażowych z ich numerami i kwotami oraz najwyżej `CUSTOMER_AUDIT_TIMELINE_LIMIT` (50, `customer-activity.constants.ts`) wierszy `audit_log`, których zasobem jest użytkownik, ograniczonych do `auth.email_changed`, `auth.login`, `auth.logout`, `customer.cart_item_added`, `customer.cart_abandoned` i `customer.page_viewed`. Zmiana adresu brzmi „Zmieniono adres e-mail do logowania z X na Y”, z oboma adresami wziętymi z metadanych zmiany we wpisie albo, dla starszego wpisu, z jego szczegółu `stary → nowy`, a wpis, który nie podaje żadnego z nich, brzmi „Zmieniono adres e-mail do logowania”. Zobacz [Dziennik zdarzeń](/docs/features/audit-log).

Sekcja Adresy e-mail w panelu bocznym (`customer-email-history.tsx`) wymienia wiersze z `getUserEmailHistory` od najnowszego: obecny adres z „Obecny, od” i dniem, w którym konto zaczęło go używać, a każdy wcześniejszy z „Używany” i dniami, w których konto zaczęło go używać i z niego zrezygnowało, w formacie regionalnym i strefie czasowej administratora.

Interfejs leży w `.../admin/customers/customer-detail/`: `customer-detail-page.tsx` układa `customer-kpis.tsx`, `customer-charts.tsx` i `customer-orders.tsx` w głównej kolumnie, a obok `customer-sidebar.tsx`, który pod danymi klienta zawiera `customer-email-history.tsx` i kończy się `customer-timeline-card.tsx`; edytorem jest `edit-customer/customer-sheet.tsx`. Poniżej progu `xl` panel boczny jest pod główną kolumną, a od `xl` to kolumna o szerokości 340 px. Na ekranie `2xl` o wysokości co najmniej 57rem strona mieści się w oknie, a każda kolumna przewija się osobno.

## Notatki i tagi w `metadata`

Nie ma tabeli notatek ani tagów. Oba żyją w `user.metadata` jako JSON, z tolerancyjnym parserem:

```ts
export const parseAdminUserMetadata = (raw: string | null | undefined): User["adminUserMetadata"] => {
  const trimmed = raw?.trim()
  if (trimmed === undefined || trimmed === "") {
    return {}
  }

  const record = tryParseJsonRecord(trimmed)
  const structured =
    record === undefined || !("notes" in record || "tags" in record) ? undefined : userZodSchemas.adminUserMetadata.safeParse(record).data
  if (structured === undefined) {
    return { notes: trimmed }
  }

  const notes = structured.notes?.trim()

  return { notes: notes === "" ? undefined : notes, tags: normalizeTags(structured.tags) }
}
```

Kolumna zawierająca zwykły tekst, a nie JSON, jest traktowana jako notatka, więc stara wartość nigdy nie ginie. `serializeAdminUserMetadata` zwraca `undefined`, gdy oba pola są puste, a `updateCustomer` zapisuje wtedy SQL-owy `null`, a nie napis `"{}"`.

## Dwie mutacje

`updateCustomer` (`use-cases/update-customer.ts`), `authorized({ user: ["update"] })`:

- zwraca 404 z `USER_ERROR_CODES.NOT_FOUND`, gdy użytkownika nie ma
- zapisuje `phone` (czyszcząc do `NULL` przy pustym napisie) oraz zserializowane `metadata`
- upsertuje domyślny adres przez `upsertDefaultAddressForUser`, ale tylko gdy przejdzie `hasAddressInput` — `address1` i `city` muszą być niepuste
- gdy przysłany `countryCode` jest pusty, używa kraju z istniejącego domyślnego adresu, a nie zapisuje pustego napisu, i całkowicie pomija zapis adresu, jeśli kraju wciąż nie ma

**Nie** zmienia adresu e-mail, nazwy, roli ani stanu bana. Adres e-mail zmienia się tylko na stronie samego konta, z potwierdzeniem z obu adresów (zobacz [Konto: Zmiana adresu e-mail](/docs/features/account#zmiana-adresu-e-mail)); pozostałe to operacje Better Auth. Po zapisach zapisuje `customer.updated` przypisane administratorowi, z adresem e-mail klienta jako celem i jego identyfikatorem jako zasobem. Zapisuje wiersz bezpośrednio, a nie przez Better Auth, więc żaden hook `databaseHooks.user` się nie uruchamia: `CustomerFormProvider` unieważnia szczegóły, siatkę i statystyki w przeglądarce edytującego administratora.

`deleteCustomer` (`use-cases/delete-customer.ts`), `authorized({ user: ["delete"] })`, ma cztery zabezpieczenia:

| Warunek                                                                   | Błąd                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------ |
| żądanie na host, którego ten build nie obsługuje (`resolveRequestOrigin`) | `ERROR_CODES.FORBIDDEN`                                |
| użytkownik nie istnieje                                                   | `ERROR_CODES.NOT_FOUND` / `USER_ERROR_CODES.NOT_FOUND` |
| `targetUser.id === context.auth.user.id`                                  | `ERROR_CODES.CONFLICT` / `CANNOT_DELETE_SELF`          |
| `targetUser.role === ROLES.ADMIN`                                         | `ERROR_CODES.FORBIDDEN` / `CANNOT_DELETE_ADMIN`        |

Konta z dostępem do panelu nie da się tu usunąć. Menu wiersza pokazuje w wierszu każdego takiego konta, także własnym wierszu zalogowanej osoby, wyszarzone **Usuń konto** z dopiskiem „Najpierw odbierz dostęp do panelu w Ustawieniach › Zespół.”; gdyby serwer mimo to odmówił, komunikat brzmi „Konta z dostępem do panelu nie można usunąć. Najpierw odbierz ten dostęp w Ustawieniach › Zespół.”. Po odebraniu dostępu w [Ustawienia › Zespół](/docs/features/admin-settings#zespół) konto jest kontem klienta i można je usunąć. Własny `/admin/remove-user` z Better Auth też odrzuca konto z dostępem do panelu (zobacz [Better Auth: Role administracyjne](/docs/integrations/better-auth#role-administracyjne)).

Zapamiętuje adres e-mail, nazwę, bieżący język i origin żądania **przed** usunięciem, usuwa dane konta przez `eraseAccountData`, przekazuje usunięcie do `auth.api.removeUser`, a potem czeka na e-mail pożegnalny:

```ts
if (!(await eraseAccountData(targetUser))) {
  throw new AppError(ERROR_CODES.INTERNAL_ERROR, USER_ERROR_CODES.STRIPE_CUSTOMER_NOT_DELETED)
}

await auth.api.removeUser({ body: { userId }, headers: getRequestHeaders() })

const goodbyeEmailDelivery = sendAccountDeletedEmail(goodbyeEmail)
scheduleBackgroundWork(goodbyeEmailDelivery)
const goodbyeEmailSent = await goodbyeEmailDelivery

return { goodbyeEmailSent, ok: true as const, userId }
```

`sendAccountDeletedEmail` nigdy nie rzuca wyjątku; gdy Resend odrzuci e-mail albo nie da się go przygotować, porażka jest logowana, zapisywana w dzienniku zdarzeń jako `email.failed` i zwracana jako `false`, a usunięcie pozostaje w mocy. Przekazanie tej samej obietnicy do `scheduleBackgroundWork` umieszcza ją w `waitUntil` Workera, więc e-mail i jego wpis w audycie kończą się nawet wtedy, gdy administrator wcześniej zamknie kartę. `useDeleteCustomer` dobiera komunikat na podstawie `goodbyeEmailSent`: potwierdzenie „Konto zostało usunięte, a e-mail z potwierdzeniem został wysłany.” albo ostrzeżenie „Konto usunięte — e-mail nie został wysłany” z opisem „Nie udało się wysłać klientowi potwierdzenia usunięcia konta. Błąd zapisano w dzienniku zdarzeń.”

`eraseAccountData` to ten sam krok, który przy usunięciu konta przez klienta uruchamia `beforeDelete` w Better Auth: usuwa klienta Stripe powiązanego z kontem razem z zapisanymi kartami, a potem wpisy konta w dzienniku zdarzeń i subskrypcję newslettera (zobacz [Konto: Usunięcie konta](/docs/features/account#usunięcie-konta)). Gdy Stripe nie może usunąć klienta, nic nie zostaje usunięte, zapisuje się `customer.deletion_failed`, a `useDeleteCustomer` pokazuje „Stripe nie usunął profilu klienta ani zapisanych kart, więc konto nie zostało usunięte. Spróbuj ponownie za kilka minut. Błąd zapisano w dzienniku zdarzeń.” Okno potwierdzenia, `rowActions.deleteDescription`, wymienia, co zostanie usunięte, i mówi, że zamówienia i płatności pozostaną w dokumentacji księgowej przez 5 lat.

Ponieważ usunięcie idzie przez Better Auth, jego `databaseHooks.user.delete.after` zapisuje `customer.deleted` przypisane administratorowi, którego sesja wywołała `removeUser`, z adresem e-mail usuniętego klienta jako celem, i działają kaskady na `session`, `account`, `address`, `wishlist_item`, `two_factor` i `user_email_history`, natomiast `order.user_id`, `checkout.user_id` i `discount_redemption.user_id` mają `onDelete: "set null"` — zamówienia przeżywają więc jako zamówienia gościa. Jeśli później jakieś konto zweryfikuje ostatni adres usuniętego konta, `claimGuestOrdersForUser` przypisze mu zamówienia złożone z tego adresu jak każde inne zamówienie gościa; zamówienia złożone z wcześniejszego adresu mają `keptFromClaims` i zostają nieprzypisane (zobacz [Konto: zamówienia gości na koncie](/docs/features/account#zamówienia-gości-na-koncie)).

## Eksport

Przycisk **Eksportuj** na pasku narzędzi pobiera listę jako CSV, JSON, XML albo zwykły tekst przez eksport wspólny dla wszystkich tabel panelu (zobacz [Tabela danych](/docs/ui/data-table#eksport)). Plik zawiera wszystkich klientów wybranych filtrami roli, weryfikacji, blokady, wydatków, dat, karty i wyszukiwania, a nie tylko widoczną stronę, oraz kolumny, które pokazuje tabela, w ich kolejności i pod ich nagłówkami. Każda komórka jest zapisana tak, jak widać ją w tabeli: kolumna klienta zawiera imię i nazwisko, a widoczna domyślnie kolumna E-mail — adres, rola i kolumny tak/nie z nazwy, kwoty w złotych, a daty w formacie administratora. ID i ID klienta Stripe to ukryte kolumny, które można dodać z menu kolumn.

`exportAdminCustomers` (`use-cases/export-admin-customers.ts`) wymaga `user: ["list"]`, zwraca wszystkich pasujących klientów jako elementy listy i zapisuje `customer.list_exported`. `useCustomersExportSource` (`hooks/use-customers-export-source.ts`) przekazuje tabeli nazwę listy `customers`, tytuł strony, aktywne filtry opisane słowami i wywołanie `exportAdminCustomers`.

## Czas rzeczywisty

`USER_QUERY_KEYS.ADMIN.CUSTOMERS` występuje w `ADMIN_REALTIME_QUERY_PREFIXES`, a `scheduleAdminCustomersInvalidation()` wypycha `CUSTOMERS`, `CUSTOMERS_PAGE` i `TEAM`, czyli listę w Ustawienia › Zespół, bo rola konta, jego uwierzytelnianie dwuskładnikowe albo jego usunięcie mogą ją zmienić. Wywołują je `databaseHooks.user` z Better Auth po utworzeniu, aktualizacji albo usunięciu użytkownika (`auth.hooks.server.ts`), a `grantAdminAccess` i `revokeAdminAccess` po zmianie dostępu do panelu, więc rejestracja, zmiana wykonana przez Better Auth, na przykład zweryfikowany albo zmieniony adres e-mail, oraz usunięcie odświeżają otwartą siatkę, jej statystyki i otwarty ekran szczegółów, których klucze zaczynają się od `CUSTOMERS`. Każdy batch zapisany przez kolejkę audytu wypycha klucze dziennika zdarzeń, więc odpowiedni wpis `customer.registered` albo `customer.deleted` pojawia się też w otwartym dzienniku zdarzeń.
