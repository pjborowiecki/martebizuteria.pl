Tabela `user` jest współdzielona z Better Auth, więc „klienci” to widok na dane uwierzytelniania złączone z agregatami zamówień. Moduł to `src/modules/user`.

## Tabela user

`src/modules/user/user.schema.ts` rozszerza bazowego użytkownika Better Auth o własne kolumny M'Arte:

| Kolumna                               | Uwagi                                                                                              |
| ------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `email`                               | 320 znaków, unikalny, not null                                                                     |
| `name`                                | 256 znaków, not null                                                                               |
| `email_verified`                      | boolean, domyślnie `false`, not null                                                               |
| `role`                                | `admin \| customer`, domyślnie `DEFAULT_ROLE` (`customer`)                                         |
| `banned`, `ban_reason`, `ban_expires` | pola wtyczki admin z Better Auth                                                                   |
| `is_anonymous`                        | boolean, domyślnie `false`; nic jej nie zapisuje (zobacz niżej)                                    |
| `two_factor_enabled`                  | boolean, domyślnie `false`                                                                         |
| `phone`                               | 32 znaki; zapisywane przez `updateCustomerPhone` i `updateCustomer`                                |
| `timezone`                            | 64 znaki                                                                                           |
| `image`                               | 2048 znaków                                                                                        |
| `stripe_customer_id`                  | zapisywana przez `ensureStripeCustomerWithEmail` w kasie i `ensureStripeCustomer` na stronie konta |
| `metadata`                            | napis JSON z notatkami i tagami administratora                                                     |

Jeden indeks: `user_createdAt_idx`.

`is_anonymous` została po wtyczce `anonymous()` Better Auth, której sklep już nie ładuje (zobacz [Better Auth](/docs/integrations/better-auth#brak-logowania-anonimowego)): nic jej już nie ustawia, a nowy użytkownik dostaje wartość domyślną. Nadal oznacza użytkowników utworzonych przez tę wtyczkę, którzy w siatce wyglądają jak klienci z zastępczym adresem i nazwą „Anonymous”. Zostaje w tabeli i w schemacie Drizzle, dopóki nie usunie jej osobna migracja, zastosowana dopiero po wdrożeniu kodu, który przestał ją deklarować, bo Worker z wcześniejszym kodem odczytuje ją z każdym wczytywanym wierszem użytkownika.

| Trasa                  | Plik                        | Uprawnienie      |

Loader indeksu wczytuje wstępnie `getAdminCustomersPageQuery({ page: 1, pageSize: ADMIN_CUSTOMER_PAGE_SIZE })` i `getAdminCustomerStatsQuery()`, oba z `staleTime: "static"`. `ADMIN_CUSTOMER_PAGE_SIZE` to 25, a `ADMIN_CUSTOMER_QUERY_STALE_MS` to 60 000. ## Siatka

`getAdminCustomersPage` (`use-cases/get-admin-customers-page.ts`) ma `authorized({ user: ["list"] })`. Obsługuje frazę wyszukiwania, `statFilter` i siedem filtrów kolumn:

```ts
filters: {
  averageOrderValue: input.averageOrderValue,
  banned: input.banned,
  createdAt: input.createdAt,
  emailVerified: input.emailVerified,
  lastOrderAt: input.lastOrderAt,
  role: input.role,
  totalSpent: input.totalSpent,
}
```

Akcesor zwraca pięć rzeczy — `rows`, `orderStats`, `defaultAddresses`, `latestShippingAddresses` i `total` — a use case zszywa je po stronie aplikacji:

```ts
const statsByUserId = mapCustomerOrderStats(orderStats)
const locationByUserId = mapCustomerLocations(defaultAddresses, latestShippingAddresses)
const items = rows.map((row) => toAdminCustomerListItem(row, statsByUserId.get(row.id), locationByUserId.get(row.id)))
```

Kolumna lokalizacji pokazuje więc miasto, województwo i kraj z **zapisanego domyślnego adresu** klienta. Może to być adres rozliczeniowy: klient, który przy zamówieniu zaznaczy „Zapisz ten adres rozliczeniowy na przyszłość”, ma ten adres zapisany również jako domyślny. Gdy checkout zostawi jako domyślne oba adresy, dostawy i rozliczeniowy, `getDefaultCustomerAddressesQuery` zwraca je w kolejności zapisu, a `mapCustomerLocations` bierze pierwszy, czyli zwykle adres dostawy, bo checkout zapisuje go jako pierwszy. Klient bez zapisanego domyślnego adresu dostaje adres dostawy (`order_address` typu `shipping`) z najnowszego zamówienia, które go ma, bez względu na status zamówienia. Zamówienie anulowane lub zwrócone daje więc lokalizację, choć nie liczy się do kolumny „Ostatnie zamówienie”, a nowsze zamówienie bez wiersza dostawy jest pomijane. Przy dwóch zamówieniach z tą samą chwilą wygrywa późniejszy numer zamówienia. Przy zamówieniu do paczkomatu adres dostawy to adres wpisany przez klienta, nie adres paczkomatu, a zamówienia sprzed zapisywania kopii adresów (bez wierszy `order_address`) nie dają lokalizacji. `getLatestOrderShippingAddressesQuery` wybiera jeden adres na klienta jednym zapytaniem z `row_number()`, dla całej strony albo całego eksportu CSV, który pokazuje tę samą lokalizację co siatka. Czyta zamówienia klientów przez `order_userId_status_idx`, a wiersz dostawy każdego zamówienia przez `order_address_orderId_idx`. Jednoargumentowy `+` przy `order_address.type` nie pozwala SQLite zacząć od indeksu `order_address_type_idx`, który przeszedłby po wszystkich adresach dostawy w sklepie.

Zamówienia klienta, łączne wydatki, średnia wartość zamówienia i wartość klienta korzystają z zasady sprzedaży z pulpitu (zobacz [Pulpit admina](/docs/features/admin-dashboard#migawka)): `orderCountsAsSale` wybiera jego zamówienia w realizacji i zrealizowane, a `netSalesSum` sumuje kwotę każdego z nich pomniejszoną o to, co zwrócono z jego płatności, więc zamówienia oczekujące, anulowane i zwrócone się nie liczą, a częściowy zwrot pomniejsza sumę. Średnia wartość zamówienia dzieli tę sumę przez te same zamówienia, a „wydano łącznie” na karcie klienta w szczegółach zamówienia (`getAdminOrderCustomerStats`) to ta sama liczba. Wykres wydatków, podział na kategorie oraz ulubiona kategoria i kolekcja czytają te same zamówienia; trzy ostatnie sumują pozycje zamówień, przy których zwroty nie są zapisywane.

Identyfikatory kolumn, szerokości, domyślna widoczność i przypięcia leżą w `user.constants.ts` pod `ADMIN_CUSTOMER_TABLE_COLUMN_ID`, `ADMIN_CUSTOMER_TABLE_COLUMN_SIZE`, `ADMIN_CUSTOMER_TABLE_DEFAULT_COLUMN_VISIBILITY` i obiektem przypięć. Kolumny to m.in. `customer`, `recordId`, `email`, `phone`, `role`, `banned`, `emailVerified`, `location`, `orderCount`, `totalSpent`, `averageOrderValue`, `lastOrderAt`, `stripeCustomerId`, `createdAt` i `actions`.

Komponenty leżą w `.../admin/customers/components/`: `customers-table.tsx`, `customers-columns.tsx`, filtry (`customers-role-filter`, `customers-banned-filter`, `customers-email-verified-filter`, `customers-date-column-filter` wraz z `customers-date-filter-form`, `customers-numeric-column-filter`), plakietki (`customer-role-badge`, `customer-banned-badge`, `customer-email-verified-badge`), `customer-name-cell`, `customer-table-cells`, `customers-row-actions`, `customers-stats` z `customers-stats.config.ts` oraz akcje eksportu i odświeżenia.

## Statystyki

`getAdminCustomerStats` uruchamia równolegle trzy zapytania i wyprowadza karty w czystej funkcji:

```ts
const [[totalRow], [rollupRow], [averageProductsPerOrderRow]] = await Promise.all([
  getAdminCustomerTotalCountQuery(),
  getAdminCustomerOrderRollupStatsQuery(),
  getAverageProductsPerOrderQuery(),
])

return computeAdminCustomerStatsFromAggregates({
  averageLtv: rollupRow?.averageLtv ?? 0,
  averageProductsPerOrder: averageProductsPerOrderRow?.value ?? 0,
  customersWithOrders: rollupRow?.customersWithOrders ?? 0,
  repeatCustomers: rollupRow?.repeatCustomers ?? 0,
  total: totalRow?.count ?? 0,
})
```

`computeAdminCustomerStatsFromAggregates` i `resolveAdminCustomerReturningRate` leżą w `user.utils.ts`, co utrzymuje arytmetykę testowalną jednostkowo. Filtry statystyk zadeklarowane są w `ADMIN_CUSTOMER_STAT_FILTER` (`total` i `returning`), więc kliknięcie karty zawęża siatkę.

## Ekran szczegółów

`/admin/customers/$id` czyta `getAdminCustomerQuery(id, locale)` przez `useSuspenseQuery` i rzuca `notFound()` przez `ensureAdminCustomerDetail`, gdy wiersza brak.

`getAdminCustomer` to najszerszy odczyt w całym kodzie — jedenaście akcesorów z `user.accessors.ts`:

| Akcesor                               | Zasila                                                                |
| ------------------------------------- | --------------------------------------------------------------------- |
| `getUserById`                         | tożsamość, rolę, weryfikację, stan bana, metadane                     |
| `getCustomerOrderStatsQuery`          | liczbę zamówień i sumę wydatków                                       |
| `getAdminCustomerOrderRowsQuery`      | listę zamówień, `ADMIN_CUSTOMER_DETAIL_ORDERS_LIMIT = 10`             |
| `getOrderItemTitlesQuery`             | tytuły pozycji per zamówienie, grupowane przez `groupOrderItemTitles` |
| `getCustomerMonthlySpendingQuery`     | wykres wydatków, `ADMIN_CUSTOMER_DETAIL_MONTHS = 12`                  |
| `getCustomerCategoryBreakdownQuery`   | wykres podziału na kategorie                                          |
| `getCustomerPreferredCategoryQuery`   | wiersz preferowanej kategorii                                         |
| `getCustomerPreferredCollectionQuery` | wiersz preferowanej kolekcji                                          |
| `getDefaultCustomerAddressFullQuery`  | `formatAdminCustomerFullAddress`                                      |
| `getLatestSessionActivityQuery`       | `formatAdminCustomerLastActive`                                       |
| `getCustomerAuditTimelineQuery`       | `buildAdminCustomerTimeline`                                          |

Wykres wydatków liczy miesiące tak jak pulpit (zobacz [Pulpit admina](/docs/features/admin-dashboard#wykresy)). `resolveAdminDashboardMonths(now, ADMIN_CUSTOMER_DETAIL_MONTHS)` daje ostatnie dwanaście miesięcy aż do tego, który trwa teraz w Polsce, każdy zaczynający się o północy w Warszawie pierwszego dnia, a `getCustomerMonthlySpendingQuery(userId, window)` sumuje sprzedaże klienta od `start` okna do jego `end`, grupując je przez `calendarPeriodKey`. Zamówienie złożone o 00:30 1 kwietnia w Polsce liczy się więc w kwietniu, choć w UTC jest jeszcze 31 marca. `buildAdminCustomerMonthlySpendingSeries` daje każdemu miesiącowi okna jeden punkt, z zerem tam, gdzie nic nie kupiono, nazwany jego miesiącem w Warszawie.

Wiersze zamówień są formatowane **tymi samymi** pomocnikami, których używa siatka zamówień — `formatAdminOrderDate`, `resolveAdminOrderPaymentUiKey`, `resolveAdminOrderFulfillmentUiKey` — więc plakietki przy zamówieniach klienta zgadzają się z tymi w `/admin/orders`, a data jest zapisana w języku administratora, tak jak tam. Każdy wiersz i wpis „Złożono zamówienie” na osi czasu nazywają zamówienie jego numerem `orderNumber` (`MRT-2026-00001`); wiersz nadal otwiera zamówienie po jego identyfikatorze.

Tagi są wyprowadzane, a nie przechowywane:

```ts
export const resolveAdminCustomerTags = (row: User["select"], orderCount: number): AdminCustomerDetailTag[] => {
  const tags: AdminCustomerDetailTag[] = []
  if (row.role === ROLES.ADMIN) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.ADMIN)
  } else {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.CUSTOMER)
  }
  if (orderCount >= ADMIN_CUSTOMER_MIN_REPEAT_ORDERS) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.RETURNING)
  }
  if (row.emailVerified) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.VERIFIED)
  }
  if (row.banned === true) {
    tags.push(ADMIN_CUSTOMER_DETAIL_TAGS.BANNED)
  }

  return tags
}
```

`ADMIN_CUSTOMER_MIN_REPEAT_ORDERS` to 2. Tagi własne dodane przez administratora pochodzą z kolumny metadanych i są scalane osobno.

Oś czasu to widok na `audit_log` dla danego użytkownika, z `CUSTOMER_AUDIT_TIMELINE_LIMIT = 50` (`customer-activity.constants.ts`). Zobacz [Dziennik zdarzeń](/docs/features/audit-log).

Interfejs leży w `.../admin/customers/customer-detail/`: `customer-kpis.tsx`, `customer-charts.tsx`, `customer-orders.tsx`, `customer-sidebar.tsx` i edytor `edit-customer/customer-sheet.tsx`.

## Notatki i tagi w `metadata`

Nie ma tabeli notatek ani tagów. Oba żyją w `user.metadata` jako JSON, z tolerancyjnym parserem:

```ts
export const parseAdminUserMetadata = (raw: string | null | undefined): User["adminUserMetadata"] => {
  const trimmed = raw?.trim()
  if (trimmed === undefined || trimmed === "") {
    return {}
  }

  const record = tryParseJsonRecord(trimmed)
  const structured =
    record === undefined || !("notes" in record || "tags" in record) ? undefined : userZodSchemas.adminUserMetadata.safeParse(record).data
  if (structured === undefined) {
    return { notes: trimmed }
  }

  const notes = structured.notes?.trim()

  return { notes: notes === "" ? undefined : notes, tags: normalizeTags(structured.tags) }
}
```

Kolumna zawierająca zwykły tekst, a nie JSON, jest traktowana jako notatka, więc stara wartość nigdy nie ginie. `serializeAdminUserMetadata` zwraca `undefined`, gdy oba pola są puste, a `updateCustomer` zapisuje wtedy SQL-owy `null`, a nie napis `"{}"`.

## Dwie mutacje

`updateCustomer` (`use-cases/update-customer.ts`), `authorized({ user: ["update"] })`:

- zwraca 404 z `USER_ERROR_CODES.NOT_FOUND`, gdy użytkownika nie ma
- zapisuje `phone` (czyszcząc do `NULL` przy pustym napisie) oraz zserializowane `metadata`
- upsertuje domyślny adres przez `upsertDefaultAddressForUser`, ale tylko gdy przejdzie `hasAddressInput` — `address1` i `city` muszą być niepuste
- gdy przysłany `countryCode` jest pusty, używa kraju z istniejącego domyślnego adresu, a nie zapisuje pustego napisu, i całkowicie pomija zapis adresu, jeśli kraju wciąż nie ma

**Nie** zmienia adresu e-mail, nazwy, roli ani stanu bana; to operacje Better Auth. Po zapisach zapisuje `customer.updated` przypisane administratorowi, z adresem e-mail klienta jako celem i jego identyfikatorem jako zasobem.

`deleteCustomer` (`use-cases/delete-customer.ts`), `authorized({ user: ["delete"] })`, ma cztery zabezpieczenia:

| Warunek                                                                   | Błąd                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------ |
| żądanie na host, którego ten build nie obsługuje (`resolveRequestOrigin`) | `ERROR_CODES.FORBIDDEN`                                |
| użytkownik nie istnieje                                                   | `ERROR_CODES.NOT_FOUND` / `USER_ERROR_CODES.NOT_FOUND` |
| `targetUser.id === context.auth.user.id`                                  | `ERROR_CODES.CONFLICT` / `CANNOT_DELETE_SELF`          |
| `targetUser.role === ROLES.ADMIN`                                         | `ERROR_CODES.FORBIDDEN` / `CANNOT_DELETE_ADMIN`        |

Zapamiętuje adres e-mail, nazwę, bieżący język i origin żądania **przed** usunięciem, usuwa dane konta przez `eraseAccountData`, przekazuje usunięcie do `auth.api.removeUser`, a potem czeka na e-mail pożegnalny:

```ts
if (!(await eraseAccountData(targetUser))) {
  throw new AppError(ERROR_CODES.INTERNAL_ERROR, USER_ERROR_CODES.STRIPE_CUSTOMER_NOT_DELETED)
}

await auth.api.removeUser({ body: { userId }, headers: getRequestHeaders() })

const goodbyeEmailDelivery = sendAccountDeletedEmail(goodbyeEmail)
scheduleBackgroundWork(goodbyeEmailDelivery)
const goodbyeEmailSent = await goodbyeEmailDelivery

return { goodbyeEmailSent, ok: true as const, userId }
```

`sendAccountDeletedEmail` nigdy nie rzuca wyjątku; gdy Resend odrzuci e-mail albo nie da się go przygotować, porażka jest logowana, zapisywana w dzienniku zdarzeń jako `email.failed` i zwracana jako `false`, a usunięcie pozostaje w mocy. Przekazanie tej samej obietnicy do `scheduleBackgroundWork` umieszcza ją w `waitUntil` Workera, więc e-mail i jego wpis w audycie kończą się nawet wtedy, gdy administrator wcześniej zamknie kartę. `useDeleteCustomer` dobiera komunikat na podstawie `goodbyeEmailSent`: potwierdzenie „Konto zostało usunięte, a e-mail z potwierdzeniem został wysłany.” albo ostrzeżenie „Konto usunięte — klient nie otrzymał e-maila” z opisem „Nie udało się wysłać klientowi potwierdzenia usunięcia konta. Błąd zapisano w dzienniku zdarzeń.”

`eraseAccountData` to ten sam krok, który przy usunięciu konta przez klienta uruchamia `beforeDelete` w Better Auth: usuwa klienta Stripe powiązanego z kontem razem z zapisanymi kartami, a potem wpisy konta w dzienniku zdarzeń i subskrypcję newslettera (zobacz [Konto: Usunięcie konta](/docs/features/account#usunięcie-konta)). Gdy Stripe nie może usunąć klienta, nic nie zostaje usunięte, zapisuje się `customer.deletion_failed`, a `useDeleteCustomer` pokazuje „Stripe nie usunął profilu klienta ani zapisanych kart, więc konto nie zostało usunięte. Spróbuj ponownie za kilka minut. Błąd zapisano w dzienniku zdarzeń.” Okno potwierdzenia, `rowActions.deleteDescription`, wymienia, co zostanie usunięte, i mówi, że zamówienia i płatności pozostaną w dokumentacji księgowej przez 5 lat.

Ponieważ usunięcie idzie przez Better Auth, jego `databaseHooks.user.delete.after` zapisuje `customer.deleted` przypisane administratorowi, którego sesja wywołała `removeUser`, z adresem e-mail usuniętego klienta jako celem, i działają kaskady na `session`, `account`, `address`, `wishlist_item` i `two_factor`, natomiast `order.user_id` i `checkout.user_id` mają `onDelete: "set null"` — zamówienia przeżywają więc jako zamówienia gościa.

## Eksport

`exportAdminCustomers` (`use-cases/export-admin-customers.ts`) wymaga `user: ["list"]` i zwraca wszystkie pasujące wiersze na potrzeby pliku CSV budowanego w `customers-export-action.tsx`.

## Czas rzeczywisty

`USER_QUERY_KEYS.ADMIN.CUSTOMERS` występuje w `ADMIN_REALTIME_QUERY_PREFIXES`, a `scheduleAdminCustomersInvalidation()` wypycha zarówno `CUSTOMERS`, jak i `CUSTOMERS_PAGE`. Zdarzenia audytu rejestracji klienta unieważniają też klucze dziennika zdarzeń, więc nowa rejestracja pojawia się w otwartym panelu bez przeładowania.
