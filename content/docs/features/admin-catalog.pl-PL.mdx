## Układ tras

`/admin/catalog` to layout przepustowy (`src/routes/admin.catalog.tsx`), który deklaruje tylko przestrzenie nazw `pages.admin.catalog` i `pages.admin.catalog.localePicker`, a `/admin/catalog/` przekierowuje na `ROUTES.ADMIN_PRODUCTS`.

Cztery zakładki renderowane przez `catalog/catalog-tabs.tsx` ze stałych `ROUTES.ADMIN_CATALOG`, `ADMIN_CATEGORIES`, `ADMIN_COLLECTIONS` i `ADMIN_ATTRIBUTES`:

| Zakładka  | Ścieżka                      | Trasa indeksu                         | Moduł                            |
| --------- | ---------------------------- | ------------------------------------- | -------------------------------- |
| Produkty  | `/admin/catalog/products`    | `admin.catalog.products.index.tsx`    | `src/modules/product`            |
| Kategorie | `/admin/catalog/categories`  | `admin.catalog.categories.index.tsx`  | `src/modules/product-category`   |
| Kolekcje  | `/admin/catalog/collections` | `admin.catalog.collections.index.tsx` | `src/modules/product-collection` |
| Atrybuty  | `/admin/catalog/attributes`  | `admin.catalog.attributes.index.tsx`  | `src/modules/product-attribute`  |

Kategorie i kolekcje mają też trasę szczegółów: `admin.catalog.categories.$handle.tsx` i `admin.catalog.collections.$handle.tsx`.


## Tabele

Katalog to dwanaście tabel. Wszystkie kolumny tytułowe są **mapami lokalizacji w JSON**, a nie zwykłym tekstem: `titles`, `subtitles`, `descriptions`, `tags`, `labels`.

| Tabela                 | Kluczowe kolumny                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `product`              | `handle` (unikalny), `titles`, `subtitles`, `descriptions`, `tags`, `thumbnail`, `status`, `rank`, `primary_category_id`, `metadata`           |
| `product_variant`      | `product_id`, `title`, `sku` (unikalny), `barcode`, `price`, `compare_at_price`, `manage_inventory`                                            |
| `inventory`            | `variant_id` (unikalny), `quantity_available`, `quantity_reserved`                                                                             |
| `price_history`        | `variant_id`, `price`, `compare_at_price`, `changed_at`; jeden wiersz na zmianę ceny, zapisywany przez wyzwalacze na `product_variant`         |
| `product_image`        | `product_id`, `variant_id` (nullowalny), `url`, `alt`, `rank`                                                                                  |
| `product_option`       | `product_id`, `titles`                                                                                                                         |
| `product_option_value` | `option_id`, `labels`, `rank`                                                                                                                  |
| `option_on_variant`    | `variant_id`, `option_id`, `value_id`; unikalny na (`variant_id`, `option_id`)                                                                 |
| `product_category`     | `handle` (unikalny), `parent_id` (odwołanie do siebie), `titles`, `subtitles`, `short_descriptions`, `descriptions`, `image`, `status`, `rank` |
| `product_collection`   | `handle` (unikalny), `titles`, `descriptions`, `image`, `status`, `rank`                                                                       |
| `product_attribute`    | `handle` (unikalny), `titles`, `type`, `unit`, `allowed_values` (JSON), `rank`                                                                 |
| `attribute_on_product` | tabela łącząca; wiersz może być zawężony do wariantu                                                                                           |

Do tego `category_on_product` (z `is_primary`) i `collection_on_product`.

`product.status` to `draft | published | archived` z `DEFAULT_PRODUCT_STATUS = draft`. W sprzedaży jest tylko produkt `published`. Archiwizacja produktu albo przywrócenie go do szkicu zachowuje jego stan magazynowy, ale sklep i wyszukiwarka przestają go pokazywać, koszyk, który już go zawiera, oznacza linię jako już niedostępną, a kasa odrzuca go z `PRODUCT_NOT_FOUND`. Ten sam zapis zamyka płatności, które klienci już za niego rozpoczęli, i oddaje trzymane przez nie sztuki (zobacz [Zapis](#zapis)); sesja, którą klient już opłacił, nadal staje się zamówieniem (zobacz [Koszyk](/docs/features/cart) i [Płatności](/docs/features/payments)). Kategorie i kolekcje używają innego, dwuwartościowego statusu `draft | active`, również domyślnie `draft`.

Handle są walidowane tym samym wzorcem w każdym module, na przykład `PRODUCT_HANDLE_PATTERN = /^[a-z0-9]+(?:-[a-z0-9]+)*$/u`.

### Zapis

| Use case                     | Uprawnienie           | Uwagi                                                                                          |
| ---------------------------- | --------------------- | ---------------------------------------------------------------------------------------------- |
| `create-complete-product.ts` | `product: ["create"]` | jedno wywołanie tworzy produkt, opcje, wartości, warianty, stany, zdjęcia i wartości atrybutów |
| `update-complete-product.ts` | `product: ["update"]` | to samo, z podmianą zdjęć i atrybutów; zapis jako szkic lub archiwum zamyka otwarte płatności  |
| `delete-products.ts`         | `product: ["delete"]` | usunięcie zbiorcze po tablicy identyfikatorów, odrzucane, gdy otwarta płatność trzyma wariant  |
| `reorder-products.ts`        | `product: ["update"]` | `orderedIds.map((id, index) => ({ id, rank: index }))`                                         |

Oba use case'y zapisują produkt jednym atomowym batchem D1, więc zapis albo wchodzi w całości, albo zostawia produkt dokładnie takim, jaki był. Najpierw równolegle czytają to, od czego zapis zależy, a potem wysyłają instrukcje razem:

```ts
const [rank, attributeRows] = await Promise.all([
  getNextProductRank(),
  loadAttributeOnProductRows(productId, data.attributeValues),
  assertCatalogSkusAvailable(data),
])
await runDrizzleBatch([
  ...prepareProductInsertBatch(productId, data, rank),
  ...prepareProductImagesBatch(productId, data.images),
  ...prepareAttributeOnProductBatch(productId, attributeRows),
])
```

`prepareProductInsertBatch` i `prepareProductUpdateBatch` (`product.catalog.server.ts`) zapisują wiersz produktu i dokładają `prepareProductOrganizationBatch` oraz `prepareProductCatalogBatch` z `product.mutations.ts`. `prepareProductImagesBatch` podmienia zdjęcia i w tym samym batchu ustawia `product.thumbnail` na zdjęcie o najniższej randze, a `prepareAttributeOnProductBatch` podmienia wartości atrybutów. `createCompleteProduct` nadal najpierw wywołuje `deleteOrphanProductByHandle(data.handle)`, które usuwa produkt pozostawiony bez wariantów przez starszy, nieatomowy zapis.

`rethrowProductMutationError` (`product.mutation-errors.ts`) mapuje naruszenie unikalności w D1 na `ERROR_CODES.CONFLICT` z `PRODUCT_ERROR_CODES.DUPLICATE_HANDLE` albo `DUPLICATE_SKU`, a naruszenie ograniczenia `inventory_quantity_available_non_negative` na `ERROR_CODES.CONFLICT` z `PRODUCT_ERROR_CODES.STOCK_CHANGED_WHILE_EDITING`. Zanim cokolwiek zostanie zapisane, `assertCatalogSkusAvailable` odrzuca SKU używane już przez inny produkt tym samym konfliktem `DUPLICATE_SKU`. Każdy z tych błędów jest `AppError`, więc `withRequest` przekazuje jego przyczynę do edytora, zamiast zastąpić ją `INTERNAL_ERROR`: slug URL używany przez inny produkt pojawia się pod polem slugu i w komunikacie o błędzie jako `toast.duplicateHandle`, a zajęte SKU w komunikacie jako `toast.duplicateSku`.

`updateCompleteProduct` równolegle czyta właściciela handle, bieżące szczegóły produktu i definicje atrybutów, odrzuca handle zajęty przez inny produkt (`ERROR_CODES.CONFLICT` z `DUPLICATE_HANDLE`), wywołuje `assertCatalogSkusAvailable` i buduje różnicę do audytu, czytając produkt przed i po zapisie (`extractProductAuditSnapshot` i `buildProductAuditChange` w `product-audit.utils.ts`).

Zapis zachowuje każdy wariant, który produkt już ma, pod jego identyfikatorem. Instrukcje z `prepareProductCatalogBatch` usuwają tylko warianty usunięte w formularzu, aktualizują pozostałe po identyfikatorze (upsert), wstawiają wiersz stanu tylko dla wariantu, który go nie ma, a istniejący stan zmieniają wyłącznie o różnicę między polem stanu a stanem wczytanym przez edytor. Pozycje zamówień, pozycje koszyków i rezerwacje stanów zostają więc przypięte do swoich wariantów. Identyfikator wariantu jest użyty ponownie tylko wtedy, gdy `updateCompleteProduct` odczytał go z tego produktu, więc podrobiony identyfikator nigdy nie przejmie wariantu innego produktu. Każdy wielowierszowy insert, w tym zdjęcia, wartości atrybutów oraz powiązania z kategoriami i kolekcjami, jest dzielony przez `insertRowChunks`, żeby zmieścić się w limicie 100 parametrów na instrukcję w D1, więc duża galeria czy długa lista specyfikacji zapisuje się jak każda inna.

**Stany, za które klient właśnie płaci.** Ani usunięcie, ani zapis nie usuwa wariantu, który trzyma checkout, za który klient może jeszcze zapłacić. `assertVariantsNotHeldByOpenCheckouts` (`product.catalog.server.ts`) pyta `isAnyVariantHeldByOpenCheckout` (`payment.accessors.ts`), czy płatność w stanie `pending` należąca do checkoutu w stanie `pending` ma któryś z tych wariantów w `reserved_lines`, i jeśli tak, rzuca `ERROR_CODES.CONFLICT` z `PRODUCT_ERROR_CODES.RESERVED_IN_CHECKOUT`, zanim cokolwiek zostanie zapisane. `deleteProducts` sprawdza każdy wariant wybranych produktów, odczytany przez `getVariantIdsByProductIds`, więc tak samo chroni akcję w wierszu i akcję zbiorczą. `updateCompleteProduct` najpierw buduje wiersze katalogu przez `prepareCatalogReplacePayload`, sprawdza warianty produktu, których te wiersze już nie zawierają, a potem przekazuje te same wiersze do `prepareProductUpdateBatch`, więc sprawdzone warianty to dokładnie te, które batch usuwa. Administrator widzi `toast.deleteReservedInCheckoutDescription` na liście produktów albo `toast.variantReservedInCheckout` w edytorze; oba komunikaty każą zamiast tego zarchiwizować produkt i usunąć go dopiero po zakończeniu albo wygaśnięciu tej płatności. Zapis produktu jako zarchiwizowanego wygasza tę płatność, więc usunięcie przechodzi zaraz potem, chyba że Stripe odmówił wygaszenia (zobacz niżej). Sprawdzenie odbywa się tuż przed batchem, więc checkout otwarty w międzyczasie może jeszcze zapłacić za wariant, który potem zostanie usunięty; realizacja tworzy wtedy zamówienie z tego, za co klient zapłacił (zobacz [Płatności: realizacja](/docs/features/payments#realizacja)).

**Stan, który zmienił się przy otwartym edytorze.** Pole stanu pokazuje liczbę sztuk dostępnych do sprzedaży, a pod nim sztuki trzymane w trwających płatnościach („1 szt. w trakcie płatności”). Zapis utrwala pole stanu tylko wtedy, gdy administrator je zmienił, jako różnicę względem stanu wczytanego przez edytor, więc rezerwacje, zwolnienia i sprzedaże z międzyczasu pozostają policzone. Jeśli klient w międzyczasie zarezerwował albo kupił towar i różnica zeszłaby ze stanem dostępnym poniżej zera, cały zapis jest odrzucany, nic nie zostaje zapisane, a edytor pokazuje `toast.stockChangedWhileEditing`, który o tym mówi i prosi o odświeżenie strony, aby zobaczyć aktualny stan. Nowy produkt albo wariant nadal dostaje wpisaną liczbę jako pierwszy stan. Szczegóły opisuje [Stany magazynowe: zmiana stanu](/docs/features/inventory#zmiana-stanu).

**Wycofanie produktu ze sprzedaży.** Zapis, po którym produkt jest `draft` albo `archived`, zamyka też płatności, które mogłyby jeszcze za niego zapłacić. Po zapisaniu batcha, zleceniu unieważnienia i wpisie do dziennika audytu `updateCompleteProduct` przekazuje każdy wariant, który produkt miał na początku zapisu, do `expireCheckoutsHoldingVariants` (`src/modules/checkout/use-cases/expire-checkouts-holding-variants.server.ts`). Ta funkcja pyta `getOpenCheckoutSessionIdsHoldingVariants` (`payment.accessors.ts`) o sesje Checkout, których płatność w stanie `pending` należąca do checkoutu w stanie `pending` ma któryś z tych wariantów w `reserved_lines`, czyli o ten sam warunek, którego używa `isAnyVariantHeldByOpenCheckout`, i wygasza każdą przez `stripe.checkout.sessions.expire`. Każda sesja, którą Stripe wygasił, trafia do `releaseExpiredCheckoutSession`, tego samego zwolnienia, które aktualizacja checkoutu i sprawdzenie sesji wykonują już przed webhookiem: `releaseCheckout` oddaje linie, zwalnia trzymane użycie kodu i oznacza checkout oraz jego płatność jako `failed`, a webhook `checkout.session.expired`, który przychodzi potem, nie ma już czego zwolnić i jak zwykle usuwa kupon sesji, więc sztuki wracają raz. Checkout oznaczony jako `failed` przestaje się liczyć do limitów otwartych checkoutów adresu i e-maila kupującego (zobacz [Kasa: limity trzymania towaru](/docs/features/checkout#limity-trzymania-towaru)). Klient nie zapłaci już w otwartym formularzu płatności, a nowy checkout odrzuca produkt. Sesja, której Stripe nie wygasi, na przykład opłacona chwilę wcześniej, jest logowana i zostaje bez zmian; jeśli została opłacona, realizacja tworzy z niej zamówienie. Zapis odpowiada polem `closedCheckoutCount` z liczbą sesji wygaszonych przez Stripe, a gdy jest większa od zera, komunikat o udanym zapisie w edytorze mówi o tym przez `toast.updateClosedCheckoutsDescription` („Zamknięto 1 otwartą płatność za ten produkt i zwolniono zarezerwowane sztuki.”). Wygaszanie działa przy każdym zapisie niepublikowanego produktu, więc ponowny zapis zamyka sesję, którą zostawiło nieudane wygaszenie. Checkout, który przeszedł sprawdzenie publikacji tuż przed zapisem, a swoją płatność zapisał dopiero po wyszukaniu sesji, zostaje pominięty i można za niego zapłacić, dopóki nie wygaśnie.

**Historia cen.** Zapis, który daje wariantowi nową `price` albo `compare_at_price` albo tworzy wariant, dodaje do `price_history` wiersz z nowymi cenami. Wiersze pochodzą z wyzwalaczy `price_history_variant_insert` i `price_history_variant_update` na `product_variant`, które działają wewnątrz upsertu wariantów we wsadzie, więc cena i jej wiersz historii zapisują się razem albo wcale, a zapis zostawiający obie ceny bez zmian nie dodaje nic. Witryna korzysta z historii, żeby obok obniżonej ceny pokazać najniższą cenę z 30 dni przed obniżką (zobacz [Strona produktu](/docs/features/product-page#obniżone-ceny-i-najniższa-cena-z-30-dni-przed-obniżką)). Edytor nie ma pola ceny regularnej: odsyła cenę regularną, którą wczytał.

Każdy zapis kończy się `scheduleProductCatalogInvalidation()` i wywołaniem `recordCatalogProduct*Audit`.

### Formularz

`product.zod.ts` to największy plik `*.zod.ts` w repozytorium — 479 linii. `productFormSchemaDefinition` rozszerza wspólny `catalogUpsertBaseSchema` o mapy lokalizacji, pola mediów i tylko do odczytu `quantityInCheckout` każdego wariantu oraz dodaje trzy uściślenia:

- `refineDuplicateSkusInForm`
- `refineDuplicateProductAttributes`
- `refineCatalogUpsert`, które wymaga co najmniej jednego wariantu, a dla produktu aktywnego wariantu dla **każdej** kombinacji opcji (`buildVariantCombinations`) oraz poprawnych cen (`refineActiveProductPricing`)

Wszystkie komunikaty to klucze z `PRODUCT_FORM_VALIDATION_KEYS`.

`parseCatalogUpsertInput(values)` odcina pola mediów i atrybutów, parsuje resztę, co odrzuca `quantityInCheckout` i zachowuje `loadedQuantity` każdego wariantu, a potem wymusza śledzenie stanów:

```ts
const withInventoryAlwaysTracked = (input: CatalogUpsertInput): CatalogUpsertInput => ({
  ...input,
  simpleVariant: input.simpleVariant === undefined ? undefined : { ...input.simpleVariant, manageInventory: true },
  variants: input.variants.map((row) => ({ ...row, manageInventory: true })),
})
```

Interfejs edytora to arkusz boczny, a nie strona. `catalog/product-editor/` zawiera 26 plików: `product-sheet.tsx` z `product-form-provider.tsx`, sekcje `product-editor-basic`, `-pricing`, `-media`, `-organization`, `-status`, `-tags`, `-attributes`, `-variants-section`, `-variant-list`, `-variant-mode`, a także `product-form-locale-layout.tsx` dla pól per język oraz pomocniki `product-form.utils.ts` / `product-variant-form.utils.ts` / `product-image-form.utils.ts`. `useProductsSheetState` / `ProductsSheetProvider` (`catalog/products/hooks/use-products-sheet.tsx`) trzymają stan otwarcia — dlatego trasa indeksu owija tabelę w ten provider.

Otwarcie produktu kosztuje jeden odczyt. Tabela przekazuje `prefetchEdit` jako `onRowPointerDown`, więc naciśnięcie wiersza uruchamia `getAdminProductQuery`, zanim nastąpi kliknięcie. `openEdit` otwiera arkusz od razu, gdy produkt jest już w pamięci podręcznej; w przeciwnym razie czeka na `queryClient.query` ze `staleTime: "static"`, które dołącza do żądania rozpoczętego przez naciśnięcie, zamiast wysyłać kolejne. Przesuwanie myszy nad wierszami ani przewijanie kółkiem lub gładzikiem niczego nie odczytuje. Na ekranie dotykowym przesunięcie palcem rozpoczęte na wierszu zaczyna się od naciśnięcia, więc odczytuje ten jeden produkt. Naciśnięcie pola wyboru, uchwytu przeciągania czy menu wiersza niczego nie pobiera z wyprzedzeniem, bo żadne z nich nie otwiera arkusza.

## Kolekcje

Te same osiem use case'ów, tylko bez drzewa: `get-collections`, `get-storefront-collection`, `get-admin-collections`, `get-collection-stats`, `create-collection`, `update-collection`, `delete-collections`, `reorder-collections`. `COLLECTION_ERROR_CODES` ma `DUPLICATE_HANDLE` i `HAS_PRODUCTS`.

Kolekcje mają znaczenie poza katalogiem: kolekcja `nowosci` napędza nowości na stronie głównej oraz zapasowe rekomendacje w podsumowaniu konta, dlatego `scheduleCollectionCatalogInvalidation()` unieważnia również `PRODUCT_QUERY_KEYS.LANDING_NEW_ARRIVALS`. Od pól `status` i `handle` kolekcji zależy też, które produkty pokazuje jej siatka w sklepie, więc to samo wywołanie unieważnia także `PRODUCT_QUERY_KEYS.STOREFRONT_PAGE`.

## Atrybuty

Atrybut to definicja specyfikacji do wielokrotnego użycia. `PRODUCT_ATTRIBUTE_TYPE` to `text`, `number`, `boolean`, `select` i `multiselect`; `productAttributeTypeUsesAllowedValues(type)` decyduje, czy `allowed_values` zostanie zapisane. `PRODUCT_ATTRIBUTE_UNIT_PRESETS` to `["mm", "cm", "m", "km", "mg", "g", "kg", "ml", "l", "szt.", "par", "%"]`, a `PRODUCT_ATTRIBUTE_UNIT_CUSTOM_SELECT_VALUE = "__custom__"` służy jednostce wpisywanej ręcznie.

Use case'y: `get-admin-product-attributes`, `get-product-attribute-stats`, `create-product-attribute`, `update-product-attribute`, `delete-product-attributes`, `reorder-product-attributes`. Wywołują `scheduleProductAttributeCatalogInvalidation()`, które unieważnia tylko klucze panelu — atrybuty są czytane w witrynie jako część zapytania o produkt, a nie osobno.

Wartości są dowiązywane przez `src/modules/attribute-on-product`: `get-product-attributes` i `set-all-product-attributes`, przy czym `loadAttributeOnProductRows` normalizuje wartości względem ich definicji, a `prepareAttributeOnProductBatch` podmienia je jednym batchem. Wiersz może być zawężony do wariantu — właśnie dzięki temu `mapPublishedProductForStorefront` nadaje wariantowi własne specyfikacje z fallbackiem na te z poziomu produktu.

## Zdjęcia i R2

`uploadImageFn` (`src/integrations/cloudflare-r2/media.mutations.ts`) jest zabezpieczone przez `authorized({ product: ["update"] })` i walidowane względem `media.zod.ts`:

- akceptowane typy MIME: `image/jpeg`, `image/png`, `image/webp`, `image/avif`
- maksymalny rozmiar: `MAX_IMAGE_BYTES` = 5 MiB
- katalogi: `collections`, `products`, `categories`, `uploads` (wartość zapasowa)

Klucz jest **adresowany treścią**, co czyni ponowną wysyłkę tego samego pliku darmową:

```ts
const buffer = await file.arrayBuffer()
const digest = await crypto.subtle.digest("SHA-256", buffer)
const key = `${folder}/${bufferToHex(digest)}.${MIME_EXTENSION[file.type]}`
if ((await env.IMAGES.head(key)) === null) {
  await env.IMAGES.put(key, buffer, { httpMetadata: { cacheControl: IMMUTABLE_CACHE_CONTROL, contentType: file.type } })
}
```

`IMMUTABLE_CACHE_CONTROL` to `public, max-age=31536000, immutable`, co jest bezpieczne właśnie dlatego, że kluczem jest skrót. Bindingiem jest `IMAGES` w `wrangler.jsonc`. Każde przyjęte przesłanie, także pliku, którego bajty bucket już miał, zapisuje `image.uploaded` przypisane administratorowi, z kluczem jako celem i własną nazwą pliku jako szczegółem. `uploadImageFn` odpowiada samym kluczem, formularze zapisują ten klucz, a `getAssetURL` / `resolveAssetURL` w `src/lib/url.ts` zamieniają go w publiczny adres na podstawie `VITE_R2_URL` dopiero przy wyświetlaniu, więc zapisane wiersze nie zawierają hosta.

`product-image.persist.utils.ts` (`prepareProductImagesBatch`) przepisuje wiersze zdjęć produktu i w tym samym batchu utrzymuje `product.thumbnail` w zgodzie, a `product-image.server.ts` odczytuje je przez `getProductImagesQuery`. Widżety wysyłki leżą w `src/presentation/components/custom/image-upload/`.

## Wspólna infrastruktura siatek

`catalog/table/`, `catalog/toolbar/`, `catalog/form/`, `catalog/dialog/` i `catalog/lib/` przechowują elementy współdzielone przez cztery zakładki, w tym `catalog-admin-datagrid.constants.ts` — stąd pochodzi `CATALOG_ADMIN_RECORD_ID_COLUMN_WIDTH_PX`, importowana nawet przez `order.constants.ts` i `user.constants.ts`, żeby kolumna identyfikatora w każdej siatce miała tę samą szerokość. Sama generyczna siatka danych to `src/presentation/components/custom/datagrid/`, tłumaczona przez przestrzeń nazw `components.datagrid`.

Edycję per język w każdej zakładce wspiera `pages.admin.catalog.localePicker` oraz `product-form-locale.utils.ts`.
