## Route

`src/routes/_storefront.products.$handle.tsx`. The loader does four things:

```ts
loader: async ({ context, params }) => {
  const { locale } = context
  const [data, messages, seller] = await Promise.all([
    context.queryClient.query({ ...getProductQuery(params.handle, locale), staleTime: "static" }),
    context.queryClient.query(messagesQueryOptions<typeof productMessages>({ locale, namespace: "pages.product" })),
    context.queryClient.query(getSellerDetailsQuery()),
  ])

  if (data === false) {
    throw notFound()
  }
  prefetchSingleProductImage(data, context.imagePrefetchService)
  const deferredRelated = defer(context.queryClient.query(getRelatedProductsQuery(data.categoryId, data.id, locale)))

  return {
    deferredRelated,
    description: data.description,
    image: resolveProductSocialImageUrl(data),
    structuredData: buildProductStructuredData({
      images: resolveProductImageUrls(data),
      locale,
      product: data,
      section: messages.heroSection.breadcrumbProducts,
      seller,
    }),
    title: messages.metaTitle.replace("{title}", data.title),
  }
}
```

The related-products query is **deferred**: the hero renders as soon as the product resolves, and `<Await promise={deferredRelated}>` streams the related grid in behind a `Suspense` fallback that shows `pages.product.loadingRelated`.

`head: pageHead` from `src/lib/seo.ts` turns the returned `PageMeta` into the title and description tags, the product's main image at the 1200 × 630 social card size in `og:image` and `twitter:image`, and a JSON-LD `Product` with the seller from Settings → Store details, which the loader reads with `getSellerDetailsQuery()`, as its manufacturer, as the page's "Manufacturer" section names it, one PLN `Offer` per variant, in or out of stock by its available quantity, and the breadcrumb home › products › product. [Internationalization](/docs/features/internationalization#seo) lists the structured data of every page.

## Loading the product

`getProduct` (`src/modules/product/use-cases/get-product.ts`) is public:

```ts
const prod = await getPublishedProductByHandleQuery.execute({ handle })

if (prod === undefined || !isProductInStock(prod.variants)) {
  return false
}

return attachPriceReductions(mapPublishedProductForStorefront(prod, locale), await getPriceReductions(prod.variants))
```

Note the return type. **A missing product and an out-of-stock product are both `false`**, and the route turns `false` into `notFound()`. There is no separate "sold out" page: a product whose variants all sit at zero available is a 404 on the storefront. `isProductInStock` lives in `src/modules/inventory/inventory.utils.ts`.

`getPublishedProductByHandleQuery` is a prepared Drizzle relational query in `product.accessors.ts` that loads the product with its variants, images, options and option values, categories, collections and attribute values in one round trip. `getPriceReductions` adds a second read only when one of the variants is reduced (see [Reduced prices](#reduced-prices-and-the-lowest-price-of-the-30-days-before)).

## The storefront shape

`mapPublishedProductForStorefront` in `src/modules/product/product.utils.ts` flattens the row into `Product["storefront"]`. The rules worth knowing:

| Field                                      | How it is derived                                                                                      |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `title`, `subtitle`, `description`, `tags` | `resolveProductTitle` / `Subtitle` / `Description` / `Tags` pick the locale out of the JSON locale map |
| `categoryId`                               | `product.primary_category_id`, or `resolvePrimaryCategoryId(categoryRows)` when the column is null     |
| `sharedImageUrls`                          | images with `variant_id IS NULL` (`isProductLevelImage`)                                               |
| `variants[].imageUrls`                     | the variant's own images, falling back to `sharedImageUrls`                                            |
| `variants[].specifications`                | the variant's attribute values, falling back to the product-level ones                                 |
| `imageUrls`                                | the first variant's images, else `sharedImageUrls`, else every image row                               |
| `hasVariants`                              | `inferHasVariants(options, variants.length)`                                                           |
| `options`                                  | `{ id, title, values: [{ id, label }] }` with labels resolved for the locale                           |
| `variants[].optionValueIds`                | `resolveVariantOptionValueIds` — a `Record<optionId, valueId>` built from `option_on_variant`          |
| `variants[].priceReduction`                | `attachPriceReductions` — `{ lowestPrice }` for a variant that shows a reduction, else `undefined`     |

## Variant selection

`use-selected-product-variant.ts` holds the selection as a `Record<optionId, valueId>`:

- The initial selection is taken from the first variant with `quantityAvailable >= 1`, falling back to `variants[0]`.
- `selectOptionValue(optionId, valueId)` computes the next selection and **only commits it if a variant matches**, so the picker cannot land on a combination that does not exist.
- `selectedVariant` is `undefined` only when the product has no variants at all.

`product-variant-picker.tsx` renders the option groups; `product-hero-gallery.tsx` swaps its images when the selected variant changes, because `ProductHeroSection` recomputes `images` from `selectedVariant?.imageUrls`. Below `lg` the images sit in a looping carousel with a previous and a next button and a dot for each image. The buttons are named "Previous image" and "Next image" and the dots "Image 1", "Image 2" and so on, from `pages.product.heroSection.gallery` ("Poprzednie zdjęcie", "Następne zdjęcie", "Zdjęcie 1" in Polish), so a screen reader announces every control in the shopper's language.

The gallery renders every image twice, once in the phone carousel (`lg:hidden`) and once in the desktop column (`hidden lg:block`). The first image is the page's Largest Contentful Paint at both breakpoints, so both of its copies get `priority`, and every other image is lazy at default priority. All copies share one `sizes`, `(width < 64rem) 100vw, 58vw`, along with the same source and dimensions, so at any viewport the browser resolves both copies of the first image to the same URL: React's server render emits one image preload, and the copy that is hidden at that breakpoint costs no second download.

## Add to cart

`use-product-hero-cart.ts` is the only place the product page writes to the basket. It is stock-aware:

- `availableQuantity = getVariantQuantityAvailable(selectedVariant)`
- `isOutOfStock` is `availableQuantity < 1`
- `canPurchase = isVariantPurchasable(selectedVariant, quantity)`
- if the chosen quantity exceeds what is available, an effect clamps it down
- the quantity picker stops at the lower of `availableQuantity` and `CART_LINE_QUANTITY_MAX`, the most of one piece an order may hold
- changing the variant resets the quantity to 1

On click it pushes one line into the zustand store and fires activity tracking:

```ts
addItem({
  id: selectedVariant.id,
  image: getProductImageUrl(heroImage),
  price,
  qty: addQuantity,
  rawPrice: variantPrice,
  slug: product.handle,
  title: product.title,
  variantId: selectedVariant.id,
  variantTitle,
})
trackCartItemAdded({ productTitle: product.title, quantity: addQuantity, variantId: selectedVariant.id, variantTitle })
```

`price` is the already formatted string and `rawPrice` the minor units; the cart prefers `rawPrice` and only falls back to parsing `price`. `variantTitle` is blanked when it equals `DEFAULT_VARIANT_TITLE` (`product-variant.utils.ts`), so single-variant products do not show a meaningless variant label. `isAdded` flips true for 2000 ms to drive the button's confirmation state.

Tracking goes through `src/presentation/components/custom/customer-activity-tracking.ts` and is recorded only for signed-in users. See [Audit log](/docs/features/audit-log).

## Price display

`product-hero-info.tsx` formats the selected variant's `price` with `useFormatter().number(centsToDisplayAmount(variantPrice), { currency: "PLN", style: "currency" })`. When no variant is selected it shows `EMPTY_VALUE` from `src/modules/_core/constants/placeholder.ts`. The currency is written literally as `"PLN"` here rather than read from `STORE_CURRENCY_CODE`. It hands the price and the selected variant's `priceReduction` to `ProductPrice`, which adds the reduction described below.

## Reduced prices and the lowest price of the 30 days before

A variant is reduced when its `compare_at_price` is set and higher than its `price`; that is how the owner puts it on sale. Polish law (art. 4 ust. 2 and 3 of the ustawa o informowaniu o cenach towarów i usług, which carries art. 6a of the EU Price Indication Directive as amended by the Omnibus directive) requires the lowest price of the 30 days before a reduction next to every reduced price, and the Court of Justice held in C-330/23 Aldi Süd that an announced reduction must be measured from that lowest price. So the storefront shows a reduction only when the price is below the lowest price of the 30 days before it, and it strikes that lowest price through, not the compare-at price.

`price_history` (`src/modules/price-history/`) holds every price a variant has had: one row per change of its `price` or `compare_at_price`, with the moment the change took effect in `changed_at` and an integer `id` in the order the rows were recorded. Two triggers on `product_variant`, created by `20261010410000_price_history.sql`, write the rows. `price_history_variant_insert` records a new variant's prices, and `price_history_variant_update` records a change of either price and nothing when an update leaves both as they were. A trigger runs inside the statement that changed the variant, so the admin product editor's save batch records its price changes together with the save and a failed save records none; prices written by the seeds or straight into D1 are recorded the same way. The migration starts the history with each variant's current prices as of its `updated_at`. Deleting a variant deletes its history.

`getPriceReductions(variants)` in `price-history.accessors.ts` reads the history of the variants that are reduced in one statement, through `price_history_variantId_idx`, and reads nothing when none is. `findPriceReduction` in `price-history.utils.ts` then decides each variant's reduction:

- The reduction began with the first of the latest run of entries that carry the variant's current price and are reduced. Changing only the compare-at price during a reduction keeps that day; cutting the price again starts a new reduction.
- The lowest price is the lowest of the prices in effect at any time in the 30 days before that day (`LOWEST_PRICE_LOOKBACK_MS`), including the price that was in effect when the 30 days began.
- The variant shows a reduction only when that lowest price is above its current price. A compare-at price added without lowering the price, a price that was lower at some point in the 30 days, and a price raised while it stayed under the compare-at price all show no reduction.
- A variant first recorded at a reduced price shows no reduction, because nothing shows it ever cost more. That includes every variant that already had a compare-at price when the migration started its history.
- A variant whose latest entry does not show the price it sells at shows no reduction.

The lowest price belongs to the day of the reduction, so it stays the same while the reduction lasts. `attachPriceReductions` and, for lists, `withPriceReductions` put it on each variant as `priceReduction: { lowestPrice }`, or `undefined` when the variant shows no reduction.

`ProductPrice` (`src/presentation/components/custom/product-price.tsx`) shows the price, the lowest price of the 30 days before the reduction struck through (hidden from screen readers, which hear the same amount in the line below), and under them `components.custom.productPrice.lowestPriceBeforeReduction`: `Najniższa cena z 30 dni przed obniżką: {price}` in Polish and `Lowest price in the 30 days before the reduction: {price}` in English. The product page shows it for the selected variant, and every product card shows it for the variant the card offers (see [Catalog and search](/docs/features/catalog-and-search#reduced-prices-on-cards)). The compare-at price itself never appears on the storefront, and the JSON-LD `Product` offers each variant at the price it sells for, never at the compare-at or the lowest earlier price. The cart, the checkout, the wishlist and the account recommendations show no reduction, so they show no lowest price either. The admin product editor has no compare-at price field yet: a reduction is set on `product_variant.compare_at_price` in D1, and the editor keeps the compare-at price it loaded when it saves.

## Specifications and details

`product-hero-details.tsx` renders the details as an accordion: the description and the specification list when the product has them, then "Additional information" and "Manufacturer" on every product, with the first section open. The section titles are `<h2>` headings (`AccordionTrigger` with `heading="h2"`), one level under the product name's `<h1>`, and the four notes inside "Additional information" are `<h3>`, so the page's outline never skips a level. `product-hero-detail-line.ts` exports `resolveProductHeroDetailLine(subtitle, specifications, locale)`, which produces the single summary line under the title from the subtitle or, failing that, the specifications.

Specifications come from the product attribute system: `attribute_on_product` rows mapped by `mapAttributeRowsToSpecifications`. See [Admin catalog](/docs/features/admin-catalog) for how attributes are defined.

The "Manufacturer" section gives what the EU General Product Safety Regulation (Article 19 of Regulation (EU) 2023/988) requires an online offer to name: the manufacturer's name, postal address and electronic address. The shop makes its own pieces, so the section shows the seller saved under Settings → Store details, read with `getSellerDetailsQuery()`: the legal name, the postal address and the country, named in the shopper's language from the stored code, and the contact e-mail as a `mailto:` link. Only the labels are messages, in `pages.product.heroSection.details.manufacturer`. "Additional information" includes an invitation to write about another size or re-plating, `additionalInfo.flexibleOffer.text`, which links the same stored e-mail through `<emailLink>{email}</emailLink>`. The section shows no warnings of its own: a care note or warning that comes with a piece belongs in its specifications as a product attribute. See [Legal pages](/docs/features/legal-pages#manufacturer-on-product-pages).

## Mobile buy bar

`product-mobile-buy-bar.tsx` is a fixed bottom bar. `ProductHeroInfo` shows it with an `IntersectionObserver` on the purchase row, guarded by `matchMedia("(max-width: 1023px)")` — so it only appears on small screens once the real add-to-cart row has scrolled out of view. It is portaled into `document.body`, outside the page's landmarks, so the bar is a `<section>` named by `pages.product.heroSection.buyBar` ("Quick purchase", "Szybki zakup"), which screen readers list as a region of its own.

## Related products

`getRelatedProducts` takes `{ categoryId, excludeProductId, locale }` and returns `[]` when `categoryId` is null or undefined. Otherwise `getPublishedRelatedProducts` in `product.accessors.ts` selects the category's other products in a subquery:

```ts
.where(and(eq(categoryOnProduct.categoryId, categoryId), ne(categoryOnProduct.productId, excludeProductId)))
```

It hands them to the same storefront list read as the landing page's new arrivals, which keeps them behind `publishedInStockWhere`, orders them by `rank` and then newest first, and returns up to `RELATED_PRODUCTS_LIMIT = 3` with their variants in one D1 statement, plus a second one for the price history when one of those variants is reduced.

The route maps the rows into the shape `ProductRelatedSection` needs, resolving titles for the locale and taking the first variant's `id`, `price`, `priceReduction` and `title`.

## Animation

`hooks/use-product-animations.ts` is called with the page root and `dependencies: [handle]`, so the reveal animations replay when the visitor navigates from one product to another. It hides and fades in only the `.reveal` elements that start below the fold, such as the related products; the breadcrumb, the gallery and the buy box are on screen when the page loads and stay exactly as the server painted them, so the main image is the Largest Contentful Paint from the first frame. Under `prefers-reduced-motion: reduce` it hides and moves nothing.
