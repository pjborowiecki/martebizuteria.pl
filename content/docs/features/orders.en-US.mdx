An order is created by a Stripe webhook, never by a form. See [Payments](/docs/features/payments) for how a paid session becomes a row. The same webhook emails the shop about every new order at `RESEND_EMAIL_FROM`, with the pieces, the delivery, the customer's contact and a button that opens the order in the admin; see [Transactional email](/docs/features/email#the-shops-new-order-email).

## The tables

`order` (`src/modules/order/order.schema.ts`) carries two independent status columns:

| Column               | Values                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `status`             | `pending \| processing \| completed \| cancelled \| refunded` (default `pending`)                                  |
| `fulfillment_status` | `not_fulfilled \| partially_fulfilled \| fulfilled \| shipped \| delivered \| cancelled` (default `not_fulfilled`) |

Money columns, all integer minor units: `subtotal`, `shipping_total`, `tax_total`, `discount_total`, `total`. `currency_code` is 3 characters, default `"PLN"`.

Timestamps beyond `created_at`/`updated_at`: `fulfillment_started_at`, set when fulfilment starts and dating the stepper's In progress step, `shipped_at`, `delivered_at`, `canceled_at` (note the single `l`) and `restocked_at`, set in the batch that puts the order's items back in stock and empty while they have not gone back. The migration that added it, `20261005410000_order_restocked_at.sql`, set it on every order that was already `cancelled` or `refunded`, to when it was cancelled or its payment refunded, since the old code had restocked those, so none of them can be returned to stock a second time.

Links: `checkout_id` (with a **unique** index, so one checkout maps to at most one order), `payment_id`, `delivery_method_id`, `user_id` (null for a guest), `discount_id`. Plus `order_number`, `email`, `customer_note`, `locker_id`, `locker_point` (the locker's address as InPost gave it, a JSON string), `locker_unconfirmed`, `billing_company_name`, `billing_nip`, `tax_basis_points`, `tracking_number`, `tracking_url`, `inpost_shipment_id` (with a **unique** index, so one InPost shipment belongs to at most one order), `inpost_shipment_status` and `metadata` (a JSON string). The two InPost columns, added by `20261010400000_order_inpost_shipment.sql`, stay empty until an admin books the parcel with InPost; see [InPost](/docs/integrations/inpost#shipments-through-shipx). `order_number` reads like `MRT-2026-00042`: `prepareOrderNumberAllocation` (`order.number.server.ts`) returns an upsert that bumps the per-year counter in `order_number_sequence` and a subquery that formats the new value, and `prepareFulfillCheckoutBatch` runs both in the batch that inserts the order, so a batch that fails does not use up a number. The year is the year in Poland: `currentOrderNumberPeriod` reads it with `toCalendarDate` in `DEFAULT_TIMEZONE_CODE` (`Europe/Warsaw`), so an order placed in the first hour of 1 January Polish time, while it is still 31 December in UTC, starts the new year's series.

Indexes: `order_userId_idx`, `order_userId_status_idx`, `order_status_idx`, `order_createdAt_idx`, `order_checkoutId_unique`, `order_orderNumber_unique`.

`order_item` (`src/modules/order-item/order-item.schema.ts`) stores `order_id`, `variant_id`, `product_id`, `title`, `variant_title`, `thumbnail`, `quantity`, `unit_price`, `subtotal`, `total`, `metadata`.

**What happens to a line when its product goes.** `order_item.variant_id` references `product_variant` with `ON DELETE SET NULL`, and `product_id` is a plain column with no foreign key. Deleting a product cascades to its variants, which sets `variant_id` to `null` on every line that bought one, while `product_id`, the title, price, quantity and image stay as they were. A variant dropped in the product editor does the same. The order lists, the order details and the customer's account read lines with left joins, and cancelling an order or returning it to stock skips a line with no variant, so the history and the order's handling carry on without the catalogue row.

**What actually gets written.** `prepareFulfillCheckoutBatch` inserts `orderId`, `productId` and `variantId` (both looked up through the variant in the same insert, so `null` when the variant was deleted while the customer paid), `quantity`, `subtotal`, `thumbnail`, `title`, `total` and `unitPrice`, in chunks that keep each statement within D1's 100 bound parameters. `variant_title` is left null; the admin and customer order queries recover the variant title, and a missing thumbnail, through the variant and product behind the line. The order row is inserted as `processing`, with totals from `computeOrderTotals` (`order.totals.ts`): `discount_total` is the checkout's discount from `calculateDiscountAmount`, capped at subtotal plus shipping, and `tax_total` is the VAT contained in the gross total at `tax_basis_points` (`STANDARD_VAT_BASIS_POINTS = 2300`). See [Discounts](/docs/features/discounts).

`order_address` is declared in `src/modules/order-address/order-address.schema.ts` with a `type` of `shipping | billing`. `prepareFulfillCheckoutBatch` snapshots the checkout's shipping and billing addresses into it, and both the customer order detail and the admin order detail prefer that snapshot over `order.checkout → checkout.shippingAddress / billingAddress`, which they read only for an order placed before the snapshot was written.

## Admin list

`/admin/orders` is `src/routes/admin.orders.index.tsx`. Its loader prefetches two queries with `staleTime: "static"`:

```ts
await Promise.all([
  context.queryClient.query({ ...getAdminOrdersPageQuery({ page: 1, pageSize: ADMIN_ORDERS_PAGE_SIZE }), staleTime: "static" }),
  context.queryClient.query({ ...getAdminOrderStatsQuery(), staleTime: "static" }),
])
```

`ADMIN_ORDERS_PAGE_SIZE` is 25 and `ORDER_QUERY_STALE_MS` is 60 000.

`getAdminOrdersPage` requires the `order: ["read"]` permission via `authorized({ order: ["read"] })`. It accepts a page, a page size, a search term matched against the order's id, number, email and tracking number and the customer's name, id and email, a `tab`, a `statFilter` and five column filters (`createdAt`, `fulfillment`, `payment`, `status`, `total`), and returns a `buildListPaginationResult`.

The `createdAt` filter goes through `buildAdminDateTimeFilterSql`, the builder the audit log uses, so a picked day is the day in the admin's time zone: `on` runs from its midnight there to the next, `before` ends at that midnight, `after` starts at the next one, and `between` runs from the first day's midnight to the midnight after the last, whatever zone the Worker runs in.

Tabs are `ORDER_TABS = ["all", "pending", "unfulfilled", "shipped", "delivered"]`. Stat filters are `ADMIN_ORDER_STAT_FILTER` — `total` and `pending`, so clicking a stat card narrows the table.

## Two derived UI keys

The table does not show raw column values. `order.display.utils.ts` derives them:

```ts
export const resolveAdminOrderPaymentUiKey = (paymentStatus: string | null | undefined): AdminOrderPaymentUiKey => {
  if (paymentStatus === "succeeded") {
    return ADMIN_ORDER_PAYMENT_UI_KEY.PAID
  }
  if (paymentStatus === "refunded") {
    return ADMIN_ORDER_PAYMENT_UI_KEY.REFUNDED
  }

  return ADMIN_ORDER_PAYMENT_UI_KEY.AUTHORIZED
}
```

So `authorized` is the fallback label for any payment that is not succeeded or refunded — including `pending` and `failed`.

`resolveAdminOrderFulfillmentUiKey(orderStatus, fulfillmentStatus)` names the step the order has reached, and it is the one place that does. It returns `pending` (Awaiting payment) whenever the **order** status is `pending`, regardless of fulfilment, and `cancelled` for a cancelled order. Otherwise it returns the step of `ADMIN_ORDER_FULFILLMENT_STEPS` whose fulfilment statuses in `ADMIN_ORDER_FULFILLMENT_STATUSES_BY_STEP` hold the order's:

| Step         | `fulfillment_status`                   | Label       |
| ------------ | -------------------------------------- | ----------- |
| `confirmed`  | `not_fulfilled`, `partially_fulfilled` | Confirmed   |
| `processing` | `fulfilled`                            | In progress |
| `shipped`    | `shipped`                              | Shipped     |
| `delivered`  | `delivered`                            | Delivered   |
| `cancelled`  | `cancelled`                            | Cancelled   |

The Fulfillment column of the list, its filter (`buildAdminOrderFulfillmentUiCondition` applies the same mapping in SQL), the export, the meta strip and the stepper of the order page, the dashboard's recent orders and the customer page's order history all read this key with the `pages.admin.orders.fulfillment` labels, so an order whose fulfilment has started reads "In progress" everywhere and one that is only paid reads "Confirmed". The stepper marks every step up to the order's own as done, so a step that is undone again stops showing as done. The Status column shows the order's own `status` with labels that never read like a step: `processing` is "Open", `completed` "Completed", `pending` "Pending", `cancelled` "Cancelled" and `refunded` "Refunded". The audit log and the order's Activity card use the same words for both (`audit.details.values.orderStatus` and `audit.details.values.fulfillmentStep`), so a refund reads "Order status: Open → Refunded" and a step back "Fulfillment step: Shipped → In progress".

`toAdminOrderListItem` assembles the row: `customerName` falls back to `email`, `initials` come from `resolveAdminCustomerInitials`, `itemCount` defaults to `0`, and `hasOpenDispute` is true while `resolveAdminOrderDispute` (`order.display.utils.ts`) finds a dispute in the order's `metadata`, which the list query selects for it.

The badge styling maps for all of this are in `order.constants.ts`: `ORDER_STATUS_BADGE_STYLES`, `PAYMENT_BADGE_STYLES`, `FULFILLMENT_DOT_COLORS`, plus the label-key maps `ADMIN_ORDER_STATUS_LABEL_KEYS`, `ADMIN_ORDER_PAYMENT_LABEL_KEYS` and `ADMIN_ORDER_FULFILLMENT_LABEL_KEYS`.

## Stats

`getAdminOrderStats` runs one `db.batch` of three aggregates:

| Value                | Query                                                           |
| -------------------- | --------------------------------------------------------------- |
| `totalOrders`        | `count()` where status is in `ADMIN_ORDER_COUNTABLE_STATUSES`   |
| `pending`            | `count()` where status is `pending`                             |
| `revenueMinorUnits`  | `netSalesSum` over the sales                                    |
| `avgValueMinorUnits` | `netSalesAverage` over the same sales                           |
| `currencyCode`       | `max(currency_code)` over the sales, else `STORE_CURRENCY_CODE` |

The last three come from one query over the orders `orderCountsAsSale` accepts, left-joined to their payment, with the same rule as the dashboard (see [Admin dashboard](/docs/features/admin-dashboard#the-snapshot)): processing and completed orders, each counted at its total less what was refunded on its payment.

`ADMIN_ORDER_COUNTABLE_STATUSES` is `["completed", "processing", "pending", "cancelled", "refunded"]` — every status, so `totalOrders` is effectively the full count.

## Admin actions

Six server functions, all requiring `order: ["update"]`. `refundAdminOrder` also requires `order: ["refund"]` through `authorized({ order: ["update", "refund"] })`, and `cancelOrder` requires it for an order with a payment to refund. Four are guarded by the same pattern:

```ts
assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
  canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
)
```

`assertOrderActionState` throws `ERROR_CODES.NOT_FOUND` with `ORDER_NOT_FOUND` when the row is missing and `ERROR_CODES.CONFLICT` with `ORDER_INVALID_STATE` when the predicate fails, so the transition rules are enforced server-side and not only in the UI.

| Use case                                 | Predicate                        | Writes                                                                                                                                                                         |
| ---------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `use-cases/fulfill-order.ts`             | `canFulfillAdminOrder`           | `fulfillment_status = "fulfilled"`, `fulfillment_started_at = now`; `status` moves `pending → processing`; emails the customer once                                            |
| `use-cases/ship-order.ts`                | `canMarkAdminOrderShipped`       | `fulfillment_status = "shipped"`, `shipped_at = now`, and `tracking_number` and `tracking_url` when the admin gives them                                                       |
| `use-cases/set-order-tracking-number.ts` | `canSetAdminOrderTrackingNumber` | a shipped order's `tracking_number` and `tracking_url`, with `null` for the link when none was given; the step and `shipped_at` stay; emails the customer each new number once |
| `use-cases/mark-order-delivered.ts`      | `canMarkAdminOrderDelivered`     | `fulfillment_status = "delivered"`, `status = "completed"`, `delivered_at = now`; thanks the customer by email once                                                            |
| `use-cases/step-back-order.ts`           | `resolveAdminOrderStepBack`      | the previous step: `fulfillment_status` one step back and the date of the step it leaves cleared; a delivered order's `status` returns to `processing`; emails no one          |
| `use-cases/cancel-order.ts`              | `canCancelAdminOrder`            | `status = "cancelled"`, `fulfillment_status = "cancelled"`, `canceled_at = now`; restocks the lines and sets `restocked_at` in the same batch                                  |
| `use-cases/restock-order.ts`             | `canRestockAdminOrder`           | `restocked_at = now`; restocks the lines in the same batch                                                                                                                     |

The fifth, `refundAdminOrder` (`use-cases/refund-admin-order.ts`), reads the order's status, fulfilment status, total and metadata and its payment through `getAdminOrderRefundTarget`, checks `canRefundAdminOrder` against the payment row's real status and `resolveAdminOrderRefundBlocker` against the total and the dispute flag, retrieves the Checkout Session whose id `createPendingPayment` stored in `payment.transaction_id`, and calls `stripe.refunds.create` with `metadata: { orderId }`, that session's PaymentIntent as `payment_intent` and the idempotency key `admin-order-refund-${orderId}-${undoneRefunds.length}`, where `undoneRefunds` are the payment's refunds that Stripe reports as `failed` or `canceled`, read with `listRefunds` just before. A repeated request for the same order therefore cannot start a second refund, while a refund asked for again after the first one failed gets a new key and reaches Stripe. Once Stripe accepts it, `order.refund_requested` is recorded against the admin, from the Refund button and from a cancellation alike. It also takes `restock`, the admin's answer to whether the items came back to stock. `payment.transaction_id` is not a PaymentIntent id, so it is never passed to Stripe as one. A missing order throws `ERROR_CODES.NOT_FOUND` with `ORDER_NOT_FOUND`; the `openDispute` blocker throws `ERROR_CODES.CONFLICT` with `ORDER_OPEN_DISPUTE`, and a failed predicate, the `noStripePayment` blocker, an empty `transaction_id`, or a session that is `no_payment_required` or has no PaymentIntent throws `ERROR_CODES.CONFLICT` with `ORDER_INVALID_STATE`; none of them requests a refund. The Stripe half, from the blocker check to `stripe.refunds.create`, is `requestFullOrderRefund` in `order.refund.server.ts`. Once Stripe has accepted the refund and only when `restock` is true, it calls `returnOrderToStock` (`order.restock.server.ts`): one batch built by `prepareRestockOrderBatch` adds each line whose variant still exists back to stock and sets `restocked_at`, every statement guarded on the order not being `cancelled` and `restocked_at` still being empty, then it records `order.restocked` and refreshes the catalogue. A refund Stripe refuses returns nothing. Everything else arrives with the `charge.refunded` webhook, which runs `refundOrder`: it records the refund on the payment and, for a full refund, marks the order `refunded` while it is neither `cancelled` nor `refunded`, then writes the audit entry and emails the customer the refund (see [Transactional email](/docs/features/email#cancellation-refund-and-failed-payment)). A refund that fails or is cancelled after that arrives as `refund.failed` or `refund.updated`, and `undoFailedRefund` (`use-cases/undo-failed-refund.ts`) takes it off: the payment keeps only the refunds that still stand and is paid again, a `refunded` order goes back to `processing`, or `completed` when it was delivered, so Refund is offered again, and a `cancelled` order stays cancelled. It records `order.refund_failed` and the shop gets a `refundFailed` alert; the customer gets no email (see [Payments: Refunds and disputes](/docs/features/payments#refunds-and-disputes)). `refundOrder` never touches stock, so a refund made in the Stripe dashboard, a refund for a lost parcel and a lost dispute leave the items out of stock until the admin returns them.

The sixth, `restockOrder` (`use-cases/restock-order.ts`), is that deliberate return. It reads the order's status, fulfilment status and `restocked_at`, checks `canRestockAdminOrder`, and calls `returnOrderToStock`; when the guarded batch matched nothing because the order went back to stock after it was read, it throws `ORDER_INVALID_STATE`.

Three more belong to InPost shipments. `createInpostShipment` (`order: ["update"]`) checks `canCreateAdminOrderInpostShipment` (a locker or courier order, open, not shipped or delivered, without a shipment or with one InPost cancelled) through `assertOrderActionState`, books the parcel with ShipX and writes `inpost_shipment_id`, `inpost_shipment_status` and the new shipment's tracking details only while the order still holds no live shipment and has not shipped, recording `order.shipment_created`. `refreshInpostShipment` (`order: ["update"]`) reads the shipment back and writes its status and, once InPost has assigned the tracking number, fills in the number and link while the order has neither; a cancelled shipment's number is taken off the order instead. `getInpostShipmentLabel` (`order: ["read"]`) returns the shipment's PDF label. All three answer `ORDER_INVALID_STATE` for an order that cannot have or has no shipment; [InPost](/docs/integrations/inpost#shipments-through-shipx) describes the requests and the errors.

`resendOrderEmail` (`use-cases/resend-order-email.ts`, `order: ["update"]`) sends an order email again. It takes the order and the id of the activity entry the admin pressed **Resend email** on, answers `ORDER_INVALID_STATE` unless that entry is still the newest `email.deferred` or `email.failed` of an email that has not gone out, records `email.resend_requested` against the admin and returns `emailSent`; [Transactional email](/docs/features/email#resending-from-the-order) describes how each email is built again.

`cancelOrder` reads the same target, so it sees the payment as well as the order. When `cancelRefundsAdminOrderPayment` finds a payment to refund, it also requires `order: ["refund"]`, checked with `hasPermission` against the session `authorized` put on the context, because only the order it has read says whether the cancellation refunds; a role without it gets `ERROR_CODES.FORBIDDEN` and nothing changes, before the dispute is looked at. It then calls `requestFullOrderRefund` before it changes anything, with the same idempotency key as the Refund button: an open dispute, refused with `ORDER_OPEN_DISPUTE`, a session without a PaymentIntent or an error from Stripe leaves the order open and its stock held, so a paid order is never cancelled with its money kept. A free order, or one whose payment never settled, is cancelled without a call to Stripe and needs only `order: ["update"]`. `prepareCancelOrderBatch` then runs the statements of `prepareRestockOrderBatch` limited to an order that has not shipped, so each line whose variant still exists goes back to stock and `restocked_at` is set while the order is unshipped, not `cancelled` and not yet restocked, and cancels the order last while it is also still open, returning its id. When another cancellation closed the order after it was read, nothing in the batch matches, so the stock is not returned twice and the action throws `ORDER_INVALID_STATE` instead of recording a second cancellation. When the refund's own `charge.refunded` event marked the order `refunded` first, the batch still returns its stock, since the goods never left the shop, but does not cancel it, and the action throws `ORDER_INVALID_STATE`; `cancelOrder` schedules the catalogue refresh right after the batch, before it checks the result. An order whose items the Refund dialog already returned keeps `restocked_at`, so its cancellation does not return them again. When the `charge.refunded` event arrives afterwards, the payment becomes `refunded` and the order stays `cancelled`. Once the batch has cancelled the order, `cancelOrder` emails the customer through `sendOrderCancelledEmail`, with the amount `requestFullOrderRefund` got back from Stripe or, for a free order, the note that nothing is refunded, and returns `cancelledEmailSent`. The `charge.refunded` event of that refund sends nothing more, because `refundOrder` finds the order cancelled before the refund was recorded.

The rules live in `order.admin-actions.utils.ts`:

- `canFulfillAdminOrder` — not `cancelled`/`refunded`, and fulfilment is `not_fulfilled` or `partially_fulfilled`.
- `canMarkAdminOrderShipped` — not `cancelled`/`refunded`, fulfilment is not already `shipped`/`delivered`/`cancelled`, and is `fulfilled` or `partially_fulfilled`. You must fulfil before you can ship.
- `canMarkAdminOrderDelivered`: not `cancelled`/`refunded`, and fulfilment is `shipped`.
- `canCancelAdminOrder` — status is `pending` or `processing`, and fulfilment is neither `shipped` nor `delivered`. A parcel that has left the shop is not put back in stock by a cancellation; the admin returns its items with the refund, or later with Return to stock, once the goods come back.
- `cancelRefundsAdminOrderPayment`: payment key `paid` and a total above 0. It decides whether Cancel order asks Stripe for a refund and which text the cancel confirmations show.
- `canRefundAdminOrder`: payment key `paid`, and status is not `refunded` or `cancelled`.
- `refundRestocksByDefault`: true unless fulfilment is `shipped` or `delivered`. It is the starting answer of the refund confirmation's "The items came back to stock" box, so a parcel that left the shop is not put back on sale unless the admin says it came back.
- `canRestockAdminOrder`: status is `refunded` and `restocked_at` is empty. It decides Return to stock and the "Not returned to stock" tag.
- `resolveAdminOrderRefundBlocker`: `noStripePayment` when the total is 0, `openDispute` when the order's metadata carries a dispute flag, otherwise nothing. An order that passes `canRefundAdminOrder` can still be blocked.
- `resolveAdminOrderCancelBlocker`: `openDispute` when the order has an open dispute and `cancelRefundsAdminOrderPayment` holds, because the cancellation would ask Stripe for the refund the dispute now decides; otherwise nothing. An order that passes `canCancelAdminOrder` can still be blocked, while a disputed order with nothing to refund can be cancelled.
- `canPrintAdminOrderSummary` (status is not `cancelled`) only decides whether the UI offers the printable order summary: the Print summary link on the order page and the Print order summary item in the row menu.

`fulfillOrder` and `shipOrder` pass `paymentUiKey: "paid"` literally, and neither predicate reads it, so payment state is not checked against the row.

The four guarded actions record an audit event (`recordOrderFulfillmentStartedAudit`, `recordOrderShippedAudit`, `recordOrderDeliveredAudit`, `recordOrderCancelledAudit`), `stepBackOrder` records `recordOrderSteppedBackAudit`, which the timeline shows as "Moved back a step", `setOrderTrackingNumber` records `recordOrderTrackingUpdatedAudit` with the number as its detail, which the timeline shows as "Tracking number saved", `returnOrderToStock` records `recordOrderRestockedAudit`, which the timeline shows as "Items returned to stock", and `requestFullOrderRefund` records `recordOrderRefundRequestedAudit` once Stripe accepts the refund, which the timeline shows as "Refund requested". All of them resolve the actor from the request, so the timeline names the admin who acted rather than "System"; the entries the Stripe webhook writes, such as "Refund recorded", stay with the system. All eight actions expose mutation options keyed by `ORDER_MUTATION_KEYS`. `shipOrder` moves the order with `transitionOrder` and then waits for the shipping email:

```ts
await transitionOrder(orderId, SHIPPABLE_FULFILLMENT_STATUSES, {
  fulfillmentStatus: "shipped",
  shippedAt: new Date(),
  ...trackingColumns(trackingNumber, filledOrUndefined(tracking.trackingUrl)),
})

recordOrderShippedAudit(orderId, { detail: trackingNumber })

return { email: await announceOrderShipment(orderId, origin), ok: true, orderId }
```

`transitionOrder` (`order.admin-action.server.ts`) updates the row only while it is still at one of the steps the action leaves, here `SHIPPABLE_FULFILLMENT_STATUSES`, and the order is neither cancelled nor refunded, and throws `ORDER_INVALID_STATE` when nothing matched. Two clicks, two tabs or a race therefore ship the order once and record one `order.shipped`. `announceOrderShipment` then tells the customer at most once (see [Transactional email](/docs/features/email#order-progress-emails-once-each)) and returns `email`, `{ kind, status }`: the shipped email, or only a tracking number email when the customer had the shipped email before, as after a step back, with `status` `sent` or `failed`, or `alreadySent` when there was nothing new to tell. The senders never throw. A refusal from Resend, an order without an address and an error while the email is prepared are all recorded as `email.deferred` on the order and returned as `failed`, so the order stays shipped, and the email is tried twice more in the background under the same idempotency key, ending as `email.sent` or `email.failed`. The same promise is handed to `scheduleBackgroundWork`, the Worker's `waitUntil`, so the email and its entry finish even if the admin leaves before Resend answers. `useMarkOrderShipped` always shows "Order marked as shipped."; a failed email adds "Customer email not sent yet", which names the email and says it is tried twice more and can be resent from the order's Activity card, which shows the error, `alreadySent` adds "No repeat email", and a tracking number email "Tracking number sent". The response takes one Resend round trip longer, at most `SEND_EMAIL_TIMEOUT_MS`; the retries run after it. `cancelOrder` waits for its cancellation email the same way, and `useCancelOrder` warns "Cancellation email not sent yet" when `cancelledEmailSent` is false.

The tracking number and URL come from `order-ship-dialog.tsx`, which the order page and the row menu both open. `shipOrder` trims them and treats a blank one as not given. A given number replaces the stored number and link, with `null` for the link when none was given; with no number, the order keeps the number and link its InPost shipment stored, and a given link alone replaces only the link. A later InPost refresh or webhook never writes over a number or link the order already has. The shipped email shows the delivery method, the carrier (the courier of an InPost courier or locker method), the address the order kept, the number and a button to the tracking URL; an InPost number without a stored URL links to `inpostTrackingUrl` (`src/integrations/inpost/inpost.utils.ts`). `markOrderDelivered` is the only writer of `delivered_at`.

A shipped order that has no tracking number, or a wrong one, gets a new one through **Add tracking number** in the order's header, or **Change tracking number** when it already has one. It does not have to be stepped back and shipped again, which would log a warning and move its shipping date. `order-tracking-dialog.tsx` requires the number, says the shipping date stays and names the tracking number email. `setOrderTrackingNumber` (`order: ["update"]`) checks `canSetAdminOrderTrackingNumber`, a shipped order that is neither cancelled nor refunded, and writes the number and link through `transitionOrder` only while the order is still shipped. It then records `order.tracking_updated` and calls `announceOrderShipment`, so the customer receives the tracking number email once for each new number, and saving the same number again ends in `alreadySent`.

## Stepping an order back

A mistaken click can be undone one step at a time. The Fulfillment card on the order page offers **Back to previous step** (`order-step-back-action.tsx`) while `resolveAdminOrderStepBack` (`order.admin-actions.utils.ts`) finds a previous step: In progress goes back to Confirmed, Shipped to In progress, and Delivered to Shipped. A confirmed order has nothing to go back to, and a cancelled or refunded order is never stepped back.

The confirmation names both steps and says the customer is not emailed about the change, and that moving the order forward again sends no second email for a step the order has already been through. Stepping a shipped order back while it holds a live InPost shipment adds that the shipment is not cancelled and its tracking number stays on the order, so the admin cancels it in InPost Manager if the parcel will not be sent.

`stepBackOrder` (`use-cases/step-back-order.ts`, `order: ["update"]`) takes the order and `fromStep`, the step the admin saw it at. `assertOrderActionState` refuses the request with `ORDER_INVALID_STATE` unless the order is still at that step, so a second tab or a second click cannot step it back twice, and `transitionOrder` moves the row only while it is still there and neither cancelled nor refunded:

| From        | To          | Writes                                                                           |
| ----------- | ----------- | -------------------------------------------------------------------------------- |
| In progress | Confirmed   | `fulfillment_status = "not_fulfilled"`, `fulfillment_started_at = null`          |
| Shipped     | In progress | `fulfillment_status = "fulfilled"`, `shipped_at = null`                          |
| Delivered   | Shipped     | `fulfillment_status = "shipped"`, `delivered_at = null`, `status = "processing"` |

It then records `order.stepped_back` against the admin with the metadata of `buildOrderStepBackAuditChange`, the step and the order status before and after, so the timeline shows "Moved back a step" with, for example, "Fulfillment step: Shipped → In progress". It also calls `scheduleAdminOrdersInvalidation()`, so every open admin tab shows the order at its new step without a reload.

Nothing else moves. The tracking number and link, the InPost shipment, the stock and the payment stay as they were, and so do the email claims, `in_progress_email_at`, `shipped_email_at` and `delivered_email_at`. Starting fulfilment, shipping or marking the order delivered again therefore answers `alreadySent` instead of sending the same email twice, and shipping it again with a new tracking number sends only the tracking number email. The customer's order page reads the step dates, so it shows the order at the earlier step; the activity feed of their account keeps the entries it already listed.

## Export

**Export** in the toolbar downloads the list as CSV, JSON, XML or plain text through the export every admin grid shares (see [Data grid](/docs/ui/data-table#export)). A file holds every order the status, payment, fulfilment, total, date, card and search filters select, not only the page on screen, and the columns the table shows, in their order and under their headers, each cell written the way the table shows it: the date in the admin's time zone and format locale, the total in the order's currency, the status, payment and fulfilment by name.

The list has three columns hidden until the column menu shows them: **Company** and **NIP**, empty for an order placed without them, so the accountant can match a business buyer's order to the VAT invoice issued for it, and **Delivery**, the method's name followed by the parcel locker's code and address for a locker order, or by the shipping address for any other. Show them before exporting to have them in the file. `loadAdminOrderListItems` (`order.admin-list.server.ts`) fills them for both the page and the export: it reads the item counts with `getAdminOrderItemCountRows` and the destinations with `getAdminOrderDestinationRows` at the same time, words the destinations with `describeOrderDestination`, and adds the order's `billing_company_name` and `billing_nip` as `billingCompanyName` and `billingNip`. An order without lines counts 0 items, and an empty page reads neither.

`exportAdminOrders` (`use-cases/export-admin-orders.ts`) requires `order: ["read"]`, takes the same filters as the list without pagination, returns every matching order as a list item and records `order.list_exported`. `useOrdersExportSource` (`hooks/use-orders-export-source.ts`) gives the grid the list name `orders`, the page title, the active filters in words and the call to `exportAdminOrders`. The customer page's order list has no export.

## The order detail screen

`/admin/orders/$orderId` (`src/routes/admin.orders.$orderId.tsx`) prefetches `getAdminOrderQuery(orderId)` with `staleTime: "static"`, titles the `AdminHeader` with the order number and renders `OrderDetailPage`.

`getAdminOrder` (`use-cases/get-admin-order.ts`) requires `order: ["read"]`. `getAdminOrderDetailRow` loads the order with its `order_address` snapshots, its checkout addresses, delivery method and courier, payment and user; then four reads run in parallel: `getAdminOrderItemRows` (lines joined to their variant and product for SKU, handle and thumbnail), `getAdminOrderTimelineRows` (the order's `audit_log` rows), `getOrderWithdrawals` (the customer's statements of withdrawal) and, when the order has a `user_id`, `getAdminOrderCustomerStats`. `resolveAdminOrderDetailAddresses` (`order.detail.utils.ts`) takes each address from its snapshot, falling back to the checkout's row only when that snapshot is missing, and sets `billingSameAsShipping` by comparing the billing and shipping snapshots field by field. Only an order with no snapshots, placed before they were written, compares the checkout's `billing_address_id` with its `shipping_address_id` instead. When the order does not exist, `getAdminOrderQuery` throws `notFound()`.

| `order-meta-strip.tsx`          | `status`, `paymentUiKey`, `fulfillmentUiKey`, `createdAt`, `totalMinorUnits`                                                      |
| `order-withdrawals-card.tsx`    | `withdrawals`, shown only when the customer sent a statement of withdrawal                                                        |

When the customer asked for an invoice for a company at checkout, the billing card adds an "Invoice for a company" block under the address with the company name and `NIP <digits>`, which `getAdminOrder` reads from the order's `billing_company_name` and `billing_nip`. The block shows whichever of the two the order has and is absent when it has neither. The app issues no VAT invoice: the owner issues it in the accounting system and KSeF, from the order summary or the orders export.

When InPost could not be reached to confirm the parcel locker while the customer was paying, the checkout accepted the locker and fulfilment copied its `locker_unconfirmed` flag onto the order (see [Checkout](/docs/features/checkout#the-checkout-row)). `getAdminOrder` passes it as `delivery.lockerUnconfirmed` and to `resolveAdminOrderDetailTags`, so the shipping card shows "InPost could not be reached to confirm this parcel locker when the order was placed. Check that it exists before you send the parcel." under the locker id and the tags card shows "Locker not confirmed". Nothing changes for the customer, and nothing clears the flag on the order.

For a locker order, `resolveAdminOrderDeliveryLocker` gives the shipping card its destination. Under "Destination parcel locker" it shows the locker's code, directions and address from `delivery.lockerPoint`, with a button that copies them, or, when the order kept no address, a note to look the locker up by its code in InPost's parcel manager. The shopper's name and phone follow under "Recipient", with the note that InPost texts the pickup code to that number and that it is not the delivery address. A courier order shows the shipping address instead. `OrderAddressLines` writes the postal code, city, province and country on one line through `formatOrderAddressLocality`, with the country named in the admin's language, and `mapAdminOrderDetailAddress` treats a second line, phone, postal code or province saved blank as never given. The InPost card names the destination locker beside the shipment, and the order summary prints the same destination under Delivery.

The timeline includes the order's email entries. An `email.deferred` row reads "Email deferred" with a "Deferred" badge and is written when Resend did not take an email at the first attempt and it is being retried; an `email.failed` row reads "Email failed" with a "Failed" badge and is written when the retries failed too. Their detail carries the error, for example `Order confirmation → jane@example.com — The example.com domain is not verified…`. The newest such row of an email that has not gone out since carries **Resend email** (`order-email-resend-button.tsx`, through `useResendOrderEmail`), and pressing it adds an "Email resend requested" row under the admin's name. Audit rows reach D1 through the queue a few seconds after the action, so `processAuditLogQueueBatch` publishes `ORDER_QUERY_KEYS.ADMIN.ORDERS`, together with the overview's `ADMIN_DASHBOARD_QUERY_KEYS.ALL`, whenever a batch carries an action from `ADMIN_ORDER_TIMELINE_ACTIONS`. Every open admin tab then refetches the order list, stats, order page or overview it has on screen and drops the order and overview queries it only has cached, so an open order page shows the new rows without a reload. A failed newsletter or Better Auth email uses the same `email.failed` action and triggers the refetch too.

`OrderDetailActions` (`order-detail-actions.tsx` with `use-order-detail-actions.ts`) puts the actions in the header. Print summary is a link that opens the [order summary](#the-order-summary) in a new tab, and is absent for a cancelled order. Refund, Return to stock, Cancel order, Start fulfillment, Mark shipped and Mark delivered render only when their predicate allows; Mark shipped opens `order-ship-dialog.tsx` for the optional tracking number and URL, Add tracking number or Change tracking number opens `order-tracking-dialog.tsx` for a shipped order, and Start fulfillment, Mark delivered, Refund, Return to stock and Cancel order ask for confirmation first. Start fulfillment and Mark delivered confirm in `order-advance-dialog.tsx`, which, like the shipping dialog, names the email the customer receives through `order-customer-email-note.tsx`, or says the order already reached that step and the email is not sent again; the shipping dialog then adds that a new tracking number reaches the customer as a short message of its own. The steps whose emails are not sent again come from `emailedSteps`, the steps whose email claim is set (`resolveAdminOrderEmailedSteps` in `order.display.utils.ts`), on the order and on the list rows alike. The migrations also set those claims on older orders that passed a step before its email existed, which is why the dialog does not claim the customer received it. Refund and Cancel order are `order-action-button.tsx`: when `resolveAdminOrderRefundBlocker` returns a blocker for the order's total and `dispute`, or `resolveAdminOrderCancelBlocker` one for its payment, total and `dispute`, the button stays visible but disabled, remains focusable, and explains the blocker in a tooltip from the `refundBlocked` or `cancelBlocked` messages. The cancel confirmation, here and in the row menu of `/admin/orders`, says what the cancellation does: the order is cancelled and its items go back to stock, and the customer's payment is refunded in full through Stripe when `cancelRefundsAdminOrderPayment` holds, or there is no payment to refund when it does not. Both versions add that the customer is emailed about the cancellation, and the paid one also about the refund. The refund confirmation, `order-refund-dialog.tsx`, says the customer is emailed once Stripe confirms the refund and asks whether the items came back to stock. Its box starts at `refundRestocksByDefault` each time it opens, ticked for an order that has not shipped and clear for one that has, and its answer is sent as `restock`. Return to stock appears for a refunded order whose items never went back, such as one refunded in the Stripe dashboard, and its confirmation says the items go back on sale and that this happens only once. A refused action ends in an error toast: `ORDER_NOT_FOUND` says the order no longer exists, `ORDER_OPEN_DISPUTE` says the dispute decides the payment, so the order can be neither refunded nor cancelled until it closes, and any other conflict says the action is not available for the order's current state.

## The order summary

`/admin/orders/$orderId/summary` (`src/routes/admin_.orders.$orderId.summary.tsx`, `ROUTES.ADMIN_ORDER_SUMMARY`) is a printable summary of one order, titled "Order summary" and clearly labelled "This document is not a VAT invoice." It does not promise that an invoice will follow, because a consumer receives one only on request. The trailing underscore in `admin_` keeps it out of the `/admin` layout, so the printout carries no sidebar or header. Its `beforeLoad` is `requireAdmin`, the guard of the admin layout, and it reads the order through `getAdminOrderQuery`, whose `getAdminOrder` checks `order: ["read"]` itself. `OrderSummaryPage` (`src/presentation/components/custom/pages/admin/orders/summary/`) calls `useAdminLightTheme`, shows the order number and date, and has a Back to order link and a Print button that calls `globalThis.print()`; both are hidden when printing.

## Customer order history

`/account/orders` (`src/routes/account.orders.index.tsx`) reads `listCustomerOrdersQuery({ filter, page })`, with the filter and page kept in the URL. `listCustomerOrders` is `authorized()` (any signed-in user) and scopes to `context.auth.user.id`: it loads one page of order rows and the matching count, then the items for those ids in one query, groups them into a `Map` and maps each row through `mapCustomerOrderSummaryRow`. `CUSTOMER_ACCOUNT_ORDERS_PAGE_SIZE` is 10.

`/account/orders/$id` reads `getCustomerOrderQuery(id)`. `getCustomerOrder` filters on `and(eq(order.id, orderId), eq(order.userId, context.auth.user.id))`, so **one customer cannot read another's order even with the id**. It loads the `order_address` snapshots, the checkout with both addresses, the delivery method and the payment row, then maps with `mapCustomerOrderDetail`, preferring the snapshot to the checkout address. A locker order shows its parcel locker under Pickup Point, with the code, directions and address from `order.locker_point`, and the shopper's name and phone below it as the recipient InPost texts the pickup code to.

The order's page also offers the online withdrawal function under "Withdrawal from the contract", read through `getCustomerOrderWithdrawalQuery(id)`, which filters on the same ownership predicate. See [Legal pages: The withdrawal function](/docs/features/legal-pages#the-withdrawal-function).

Both pages show `order_number`. The filter tabs are `CUSTOMER_ACCOUNT_ORDER_FILTERS = ["all", "confirmed", "processing", "shipped", "delivered", "cancelled", "refunded"]`. `resolveCustomerAccountOrderStatus` gives each order the step `resolveAdminOrderFulfillmentUiKey` gives it in the admin, or `refunded` for a refunded order, so the shopper sees the same "Confirmed", "In progress", "Shipped" or "Delivered" as the shop; an order still awaiting payment reads "Awaiting payment" and is listed only under All. The order page's timeline shows "Fulfillment Started" at `fulfillment_started_at`, between the confirmation and the shipment.

Guest orders have `user_id = null` and appear in no account until one claims them: `claimGuestOrdersForUser` (`order.claim.server.ts`) sets `user_id` on every guest order with the same email, ignoring case, when a user is created with a verified email, verifies it, or is updated while verified, as when the account's email changes. A guest checkout paid once such an account exists needs no claim: `prepareFulfillCheckoutBatch` writes the id of the verified account with the checkout's email, ignoring case, onto the new order. An account that has not verified its address gets nothing, so typing someone else's email at checkout files no order under an account its owner has not proven, and that account claims the order once it verifies. A claim that links any order records `customer.orders_claimed` in the audit log (see [Audit log](/docs/features/audit-log)). Guest orders placed before these rules, whose address an account had already verified, were linked once by `20261016140000_claim_past_guest_orders.sql`: it gives each order to the verified account with its email, ignoring case, or to the older one when two share it, and records the same `customer.orders_claimed` entry for each account, by the system. Signing in to an existing account claims nothing, so a guest who reaches the payment step and then signs in relies on the checkout instead: the payment step continues the guest's checkout after the sign-in, and that update sets the checkout's `user_id` to the account, which fulfilment copies onto the order (see [Checkout](/docs/features/checkout)). The confirmation email's CTA follows the order's `user_id`: an order on an account links to it, and a guest order points at `/auth/sign-up` instead — see `buildOrderAccountCta` in `src/modules/order/order.email.utils.ts`, which builds both links on the origin it is given: the address the checkout was made on for the confirmation, and the admin's request for the shipping email.

## Locale on an order

`order.metadata` stores `{ "locale": "pl-PL" }` when the checkout session carried a locale. `resolveOrderLocale(metadata)` reads it back so the shipping email is sent in the language the customer bought in, falling back to `I18N.DEFAULT_LOCALE`.
