An order is created by a Stripe webhook, never by a form. See [Payments](/docs/features/payments) for how a paid session becomes a row. The same webhook emails the shop about every new order at `RESEND_EMAIL_FROM`, with the pieces, the delivery, the customer's contact and a button that opens the order in the admin; see [Transactional email](/docs/features/email#the-shops-new-order-email).

## The tables

`order` (`src/modules/order/order.schema.ts`) carries two independent status columns:

| Column               | Values                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `status`             | `pending \| processing \| completed \| cancelled \| refunded` (default `pending`)                                  |
| `fulfillment_status` | `not_fulfilled \| partially_fulfilled \| fulfilled \| shipped \| delivered \| cancelled` (default `not_fulfilled`) |

Money columns, all integer minor units: `subtotal`, `shipping_total`, `tax_total`, `discount_total`, `total`. `currency_code` is 3 characters, default `"PLN"`.

Timestamps beyond `created_at`/`updated_at`: `shipped_at`, `delivered_at`, `canceled_at` (note the single `l`).

Links: `checkout_id` (with a **unique** index, so one checkout maps to at most one order), `payment_id`, `delivery_method_id`, `user_id` (null for a guest), `discount_id`. Plus `order_number`, `email`, `customer_note`, `locker_id`, `billing_company_name`, `billing_nip`, `tax_basis_points`, `tracking_number`, `tracking_url` and `metadata` (a JSON string). `order_number` reads like `MRT-2026-00042`: `prepareOrderNumberAllocation` (`order.number.server.ts`) returns an upsert that bumps the per-year counter in `order_number_sequence` and a subquery that formats the new value, and `prepareFulfillCheckoutBatch` runs both in the batch that inserts the order, so a batch that fails does not use up a number.

Indexes: `order_userId_idx`, `order_userId_status_idx`, `order_status_idx`, `order_createdAt_idx`, `order_checkoutId_unique`, `order_orderNumber_unique`.

`order_item` (`src/modules/order-item/order-item.schema.ts`) stores `order_id`, `variant_id`, `product_id`, `title`, `variant_title`, `thumbnail`, `quantity`, `unit_price`, `subtotal`, `total`, `metadata`.

**What happens to a line when its product goes.** `order_item.variant_id` references `product_variant` with `ON DELETE SET NULL`, and `product_id` is a plain column with no foreign key. Deleting a product cascades to its variants, which sets `variant_id` to `null` on every line that bought one, while `product_id`, the title, price, quantity and image stay as they were. A variant dropped in the product editor does the same. The order lists, the order details and the customer's account read lines with left joins, and cancelling or refunding an order skips restocking a line with no variant, so the history and the order's handling carry on without the catalogue row.

**What actually gets written.** `prepareFulfillCheckoutBatch` inserts `orderId`, `productId` and `variantId` (both looked up through the variant in the same insert, so `null` when the variant was deleted while the customer paid), `quantity`, `subtotal`, `thumbnail`, `title`, `total` and `unitPrice`, in chunks that keep each statement within D1's 100 bound parameters. `variant_title` is left null; the admin and customer order queries recover the variant title, and a missing thumbnail, through the variant and product behind the line. The order row is inserted as `processing`, with totals from `computeOrderTotals` (`order.totals.ts`): `discount_total` is the checkout's discount from `calculateDiscountAmount`, capped at subtotal plus shipping, and `tax_total` is the VAT contained in the gross total at `tax_basis_points` (`STANDARD_VAT_BASIS_POINTS = 2300`). See [Discounts](/docs/features/discounts).

`order_address` is declared in `src/modules/order-address/order-address.schema.ts` with a `type` of `shipping | billing`. `prepareFulfillCheckoutBatch` snapshots the checkout's shipping and billing addresses into it, and both the customer order detail and the admin order detail prefer that snapshot over `order.checkout → checkout.shippingAddress / billingAddress`, which they read only for an order placed before the snapshot was written.

## Admin list

`/admin/orders` is `src/routes/admin.orders.index.tsx`. Its loader prefetches two queries with `staleTime: "static"`:

```ts
await Promise.all([
  context.queryClient.query({ ...getAdminOrdersPageQuery({ page: 1, pageSize: ADMIN_ORDERS_PAGE_SIZE }), staleTime: "static" }),
  context.queryClient.query({ ...getAdminOrderStatsQuery(), staleTime: "static" }),
])
```

`ADMIN_ORDERS_PAGE_SIZE` is 25 and `ORDER_QUERY_STALE_MS` is 60 000.

`getAdminOrdersPage` requires the `order: ["read"]` permission via `authorized({ order: ["read"] })`. It accepts a page, a page size, a search term, a `tab`, a `statFilter` and five column filters (`createdAt`, `fulfillment`, `payment`, `status`, `total`), and returns a `buildListPaginationResult`.

Tabs are `ORDER_TABS = ["all", "pending", "unfulfilled", "shipped", "delivered"]`. Stat filters are `ADMIN_ORDER_STAT_FILTER` — `total` and `pending`, so clicking a stat card narrows the table.

## Two derived UI keys

The table does not show raw column values. `order.display.utils.ts` derives them:

```ts
export const resolveAdminOrderPaymentUiKey = (paymentStatus: string | null | undefined): AdminOrderPaymentUiKey => {
  if (paymentStatus === "succeeded") {
    return ADMIN_ORDER_PAYMENT_UI_KEY.PAID
  }
  if (paymentStatus === "refunded") {
    return ADMIN_ORDER_PAYMENT_UI_KEY.REFUNDED
  }

  return ADMIN_ORDER_PAYMENT_UI_KEY.AUTHORIZED
}
```

So `authorized` is the fallback label for any payment that is not succeeded or refunded — including `pending` and `failed`.

`resolveAdminOrderFulfillmentUiKey(orderStatus, fulfillmentStatus)` returns `pending` whenever the **order** status is `pending`, regardless of fulfilment; then maps `shipped`, `delivered`, `cancelled → returned`, and falls back to `unfulfilled`.

`toAdminOrderListItem` assembles the row: `customerName` falls back to `email`, `initials` come from `resolveAdminCustomerInitials`, `itemCount` defaults to `0`.

The badge styling maps for all of this are in `order.constants.ts`: `ORDER_STATUS_BADGE_STYLES`, `PAYMENT_BADGE_STYLES`, `FULFILLMENT_DOT_COLORS`, plus the label-key maps `ADMIN_ORDER_STATUS_LABEL_KEYS`, `ADMIN_ORDER_PAYMENT_LABEL_KEYS` and `ADMIN_ORDER_FULFILLMENT_LABEL_KEYS`.

## Stats

`getAdminOrderStats` runs one `db.batch` of five aggregates:

| Value                | Query                                                                    |
| -------------------- | ------------------------------------------------------------------------ |
| `totalOrders`        | `count()` where status is in `ADMIN_ORDER_COUNTABLE_STATUSES`            |
| `pending`            | `count()` where status is `pending`                                      |
| `revenueMinorUnits`  | `sum(total)` where status is `completed`                                 |
| `avgValueMinorUnits` | rounded `sum(total) / count(*)` over `completed` orders                  |
| `currencyCode`       | `max(currency_code)` over `completed` orders, else `STORE_CURRENCY_CODE` |

`ADMIN_ORDER_COUNTABLE_STATUSES` is `["completed", "processing", "pending", "cancelled", "refunded"]` — every status, so `totalOrders` is effectively the full count.

## Admin actions

Five server functions, all `authorized({ order: ["update"] })`. Four are guarded by the same pattern:

```ts
assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
  canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
)
```

`assertOrderActionState` throws `ERROR_CODES.NOT_FOUND` with `ORDER_NOT_FOUND` when the row is missing and `ERROR_CODES.CONFLICT` with `ORDER_INVALID_STATE` when the predicate fails, so the transition rules are enforced server-side and not only in the UI.

| Use case                            | Predicate                    | Writes                                                                                                                |
| ----------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `use-cases/fulfill-order.ts`        | `canFulfillAdminOrder`       | `fulfillment_status = "fulfilled"`; `status` moves `pending → processing`                                             |
| `use-cases/ship-order.ts`           | `canMarkAdminOrderShipped`   | `fulfillment_status = "shipped"`, `shipped_at = now`, `tracking_number`, `tracking_url`                               |
| `use-cases/mark-order-delivered.ts` | `canMarkAdminOrderDelivered` | `fulfillment_status = "delivered"`, `status = "completed"`, `delivered_at = now`                                      |
| `use-cases/cancel-order.ts`         | `canCancelAdminOrder`        | `status = "cancelled"`, `fulfillment_status = "cancelled"`, `canceled_at = now`; restocks the lines in the same batch |

The fifth, `refundAdminOrder` (`use-cases/refund-admin-order.ts`), reads the order's status, fulfilment status, total and metadata and its payment through `getAdminOrderRefundTarget`, checks `canRefundAdminOrder` against the payment row's real status and `resolveAdminOrderRefundBlocker` against the total and the dispute flag, retrieves the Checkout Session whose id `createPendingPayment` stored in `payment.transaction_id`, and calls `stripe.refunds.create` with `metadata: { orderId }`, that session's PaymentIntent as `payment_intent` and the idempotency key `admin-order-refund-${orderId}`, so a repeated request for the same order cannot start a second refund. `payment.transaction_id` is not a PaymentIntent id, so it is never passed to Stripe as one. A missing order throws `ERROR_CODES.NOT_FOUND` with `ORDER_NOT_FOUND`; a failed predicate, a blocker, an empty `transaction_id`, or a session that is `no_payment_required` or has no PaymentIntent throws `ERROR_CODES.CONFLICT` with `ORDER_INVALID_STATE` and requests no refund. It writes nothing itself: the `charge.refunded` webhook runs `refundOrder`, which records the refund on the payment and, for a full refund, marks the order `refunded` and restocks its lines, then writes the audit entry and emails the customer the refund (see [Transactional email](/docs/features/email#cancellation-refund-and-failed-payment)). The Stripe half, from the blocker check to `stripe.refunds.create`, is `requestFullOrderRefund` in `order.refund.server.ts`. `refundOrder` restocks and marks the order `refunded` only while the order still holds its stock, so a cancelled order keeps its status and is not restocked a second time.

`cancelOrder` reads the same target, so it sees the payment as well as the order. When `cancelRefundsAdminOrderPayment` finds a payment to refund, it calls `requestFullOrderRefund` before it changes anything, with the same idempotency key as the Refund button: an open dispute, a session without a PaymentIntent or an error from Stripe leaves the order open and its stock held, so a paid order is never cancelled with its money kept. A free order, or one whose payment never settled, is cancelled without a call to Stripe. The batch then adds each line whose variant still exists back to stock and cancels the order, every statement guarded by the rule of `canCancelAdminOrder`, with the order update last and returning its id. When another cancellation or the refund's own `charge.refunded` event closed the order after it was read, nothing in the batch matches, so the stock is not returned twice and the action throws `ORDER_INVALID_STATE` instead of recording a second cancellation. When the `charge.refunded` event arrives afterwards, the payment becomes `refunded` and the order stays `cancelled`. Once the batch has cancelled the order, `cancelOrder` emails the customer through `notifyOrderCancelled`, with the amount `requestFullOrderRefund` got back from Stripe or, for a free order, the note that nothing is refunded, and returns `cancelledEmailSent`. The `charge.refunded` event of that refund sends nothing more, because `refundOrder` finds the order cancelled before the refund was recorded.

The rules live in `order.admin-actions.utils.ts`:

- `canFulfillAdminOrder` — not `cancelled`/`refunded`, and fulfilment is `not_fulfilled` or `partially_fulfilled`.
- `canMarkAdminOrderShipped` — not `cancelled`/`refunded`, fulfilment is not already `shipped`/`delivered`/`cancelled`, and is `fulfilled` or `partially_fulfilled`. You must fulfil before you can ship.
- `canMarkAdminOrderDelivered`: not `cancelled`/`refunded`, and fulfilment is `shipped`.
- `canCancelAdminOrder` — status is `pending` or `processing`, and fulfilment is neither `shipped` nor `delivered`. A parcel that has left the shop is not put back in stock by a cancellation; a refund handles it once the goods come back.
- `cancelRefundsAdminOrderPayment`: payment key `paid` and a total above 0. It decides whether Cancel order asks Stripe for a refund and which text the cancel confirmations show.
- `canRefundAdminOrder`: payment key `paid`, and status is not `refunded` or `cancelled`.
- `resolveAdminOrderRefundBlocker`: `noStripePayment` when the total is 0, `openDispute` when the order's metadata carries a dispute flag, otherwise nothing. An order that passes `canRefundAdminOrder` can still be blocked.
- `canPrintAdminOrderInvoice` (status is not `cancelled`) only enables the Print buttons in the UI.

`fulfillOrder` and `shipOrder` pass `paymentUiKey: "paid"` literally, and neither predicate reads it, so payment state is not checked against the row.

The four guarded actions record an audit event (`recordOrderFulfillmentStartedAudit`, `recordOrderShippedAudit`, `recordOrderReleasedAudit`, `recordOrderCancelledAudit`), and all five expose mutation options keyed by `ORDER_MUTATION_KEYS`. `shipOrder` additionally waits for the shipping email and returns whether it went out:

```ts
recordOrderShippedAudit(orderId, {
  detail: trackingNumber?.trim() === "" ? undefined : trackingNumber?.trim(),
})
const shippedEmailDelivery = notifyOrderShipped(orderId, origin)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery

return { ok: true, orderId, shippedEmailSent }
```

`notifyOrderShipped` never throws. A refusal from Resend, an order without an address and an error while the email is prepared are all recorded as `email.failed` on the order and returned as `false`, so the order stays shipped. The same promise is handed to `scheduleBackgroundWork`, the Worker's `waitUntil`, so the email and its entry finish even if the admin leaves before Resend answers. `useMarkOrderShipped` always shows "Order marked as shipped.", and when the email failed also a warning toast, "Shipping email not sent", that points to the order's Activity card for the error. The response takes one Resend round trip longer, at most `SEND_EMAIL_TIMEOUT_MS`. `cancelOrder` waits for its cancellation email the same way, and `useCancelOrder` warns "Cancellation email not sent" when `cancelledEmailSent` is false.

The tracking number and URL come from `order-ship-dialog.tsx`; `shipOrder` trims them and stores `null` for an empty value, and the shipped email shows the number and points its button at the tracking URL when there is one. `markOrderDelivered` is the only writer of `delivered_at`.

## Export

`exportAdminOrders` (`use-cases/export-admin-orders.ts`) requires `order: ["read"]`, takes the same filters as the list without pagination, and returns every matching row mapped through `toAdminOrderListItem`. The CSV is produced in the browser by `orders-export-action.tsx`.

## The order detail screen

`/admin/orders/$orderId` (`src/routes/admin.orders.$orderId.tsx`) prefetches `getAdminOrderQuery(orderId)` with `staleTime: "static"`, titles the `AdminHeader` with the order number and renders `OrderDetailPage`.

`getAdminOrder` (`use-cases/get-admin-order.ts`) requires `order: ["read"]`. `getAdminOrderDetailRow` loads the order with its `order_address` snapshots, its checkout addresses, delivery method and courier, payment and user; then three reads run in parallel: `getAdminOrderItemRows` (lines joined to their variant and product for SKU, handle and thumbnail), `getAdminOrderTimelineRows` (the order's `audit_log` rows) and, when the order has a `user_id`, `getAdminOrderCustomerStats`. `resolveAdminOrderDetailAddresses` (`order.detail.utils.ts`) takes each address from its snapshot, falling back to the checkout's row only when that snapshot is missing, and sets `billingSameAsShipping` by comparing the billing and shipping snapshots field by field. Only an order with no snapshots, placed before they were written, compares the checkout's `billing_address_id` with its `shipping_address_id` instead. When the order does not exist, `getAdminOrderQuery` throws `notFound()`.

| Component                       | Reads from the detail                                                        |
| ------------------------------- | ---------------------------------------------------------------------------- |
| `order-meta-strip.tsx`          | `status`, `paymentUiKey`, `fulfillmentUiKey`, `createdAt`, `totalMinorUnits` |
| `order-fulfillment-tracker.tsx` | `fulfillmentSteps` from `buildAdminOrderFulfillmentSteps`, `canceledAt`      |
| `order-line-items-card.tsx`     | `items`, `delivery` and the five `*MinorUnits` totals                        |
| `order-timeline-card.tsx`       | `timeline` from `mapAdminOrderTimeline`                                      |
| `order-customer-card.tsx`       | `customer` from `buildAdminOrderDetailCustomer`                              |
| `order-shipping-card.tsx`       | `delivery`, `shippingAddress`, `trackingNumber`, `trackingUrl`               |
| `order-billing-card.tsx`        | `billingAddress`, `billingSameAsShipping`                                    |
| `order-payment-card.tsx`        | `payment`, including the refunded amount and date                            |
| `order-tags-card.tsx`           | `tags` from `resolveAdminOrderDetailTags`                                    |
| `order-notes-card.tsx`          | `customerNote`                                                               |

The timeline includes the order's email entries. An `email.failed` row reads "Email failed" with a "Failed" badge, and its detail carries the error, for example `Order confirmation → jane@example.com — The example.com domain is not verified…`. Audit rows reach D1 through the queue a few seconds after the action, so `processAuditLogQueueBatch` publishes `ORDER_QUERY_KEYS.ADMIN.ORDERS` whenever a batch carries an action from `ADMIN_ORDER_TIMELINE_ACTIONS`. Every open admin tab then refetches the order list, stats or order page it has on screen and drops the order queries it only has cached, so an open order page shows the new rows without a reload. A failed newsletter or Better Auth email uses the same `email.failed` action and triggers the refetch too. There is no action to resend an order email.

`OrderDetailActions` (`order-detail-actions.tsx` with `use-order-detail-actions.ts`) puts the actions in the header. Print calls `globalThis.print()` and is disabled for a cancelled order. Refund, Cancel order, Fulfill, Mark shipped and Mark delivered render only when their predicate allows; Mark shipped opens `order-ship-dialog.tsx` for the optional tracking number and URL, and Refund and Cancel order ask for confirmation first. Refund is `order-refund-button.tsx`: when `resolveAdminOrderRefundBlocker` returns a blocker for the order's total and `dispute`, the button stays visible but disabled, remains focusable, and explains the blocker in a tooltip. The cancel confirmation, here and in the row menu of `/admin/orders`, says what the cancellation does: the order is cancelled and its items go back to stock, and the customer's payment is refunded in full through Stripe when `cancelRefundsAdminOrderPayment` holds, or there is no payment to refund when it does not. Both versions add that the customer is emailed about the cancellation, and the paid one also about the refund. The refund confirmation says the stock returns and the customer is emailed once Stripe confirms the refund.

## Customer order history

`/account/orders` (`src/routes/account.orders.index.tsx`) reads `listCustomerOrdersQuery({ filter, page })`, with the filter and page kept in the URL. `listCustomerOrders` is `authorized()` (any signed-in user) and scopes to `context.auth.user.id`: it loads one page of order rows and the matching count, then the items for those ids in one query, groups them into a `Map` and maps each row through `mapCustomerOrderSummaryRow`. `CUSTOMER_ACCOUNT_ORDERS_PAGE_SIZE` is 10.

`/account/orders/$id` reads `getCustomerOrderQuery(id)`. `getCustomerOrder` filters on `and(eq(order.id, orderId), eq(order.userId, context.auth.user.id))`, so **one customer cannot read another's order even with the id**. It loads the `order_address` snapshots, the checkout with both addresses, the delivery method and the payment row, then maps with `mapCustomerOrderDetail`, preferring the snapshot to the checkout address.

Both pages show `order_number`. The filter tabs are `CUSTOMER_ACCOUNT_ORDER_FILTERS = ["all", "processing", "shipped", "delivered", "cancelled", "refunded"]`.

Guest orders have `user_id = null` and appear in no account until one claims them: `claimGuestOrdersForUser` (`order.claim.server.ts`) sets `user_id` on every guest order with the same email, ignoring case, when a user is created with a verified email or verifies it. Signing in to an existing account claims nothing, so a guest who reaches the payment step and then signs in relies on the checkout instead: the payment step continues the guest's checkout after the sign-in, and that update sets the checkout's `user_id` to the account, which fulfilment copies onto the order (see [Checkout](/docs/features/checkout)). The confirmation email's CTA points a guest at `/auth/sign-up` instead — see `buildOrderAccountCta` in `src/integrations/resend/order-confirmation.utils.ts`, which builds both links on the origin it is given: the address the checkout was made on for the confirmation, and the admin's request for the shipping email.

## Locale on an order

`order.metadata` stores `{ "locale": "pl-PL" }` when the checkout session carried a locale. `resolveOrderLocale(metadata)` reads it back so the shipping email is sent in the language the customer bought in, falling back to `I18N.DEFAULT_LOCALE`.
