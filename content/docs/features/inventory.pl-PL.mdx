## Tabela

`inventory` (`src/modules/inventory/inventory.schema.ts`) to jeden wiersz na wariant:

```ts
export const inventory = sqliteTable(
  "inventory",
  {
    id: text("id", { length: INVENTORY_COLUMN_LENGTH.id })
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    quantityAvailable: integer("quantity_available").default(INVENTORY_DEFAULT_QUANTITY).notNull(),
    quantityReserved: integer("quantity_reserved").default(INVENTORY_DEFAULT_QUANTITY).notNull(),
    variantId: text("variant_id", { length: INVENTORY_COLUMN_LENGTH.variantId })
      .references(() => productVariant.id, { onDelete: "cascade" })
      .notNull(),
    ...timestamps(),
  },
  (table) => [
    uniqueIndex("inventory_variantId_unique").on(table.variantId),
    check(INVENTORY_NON_NEGATIVE_AVAILABLE_CHECK, sql`${table.quantityAvailable} >= 0`),
  ],
)
```

`INVENTORY_DEFAULT_QUANTITY` to `0` (`inventory.constants.ts`). Unikalny indeks na `variant_id` gwarantuje relację jeden do jednego, a kaskada powoduje, że usunięcie wariantu usuwa jego wiersz stanu.

Ograniczenie `inventory_quantity_available_non_negative` (`INVENTORY_NON_NEGATIVE_AVAILABLE_CHECK`, dodane przez `20261005300000_inventory_available_never_negative.sql`) utrzymuje `quantity_available` na poziomie zera lub wyżej. Instrukcja, która zeszłaby poniżej zera, kończy się błędem, a razem z nią cały wsad D1, w którym działa. Rezerwacja nigdy go nie narusza, bo jej własny warunek wymaga wystarczającego stanu; to ono odrzuca zapis produktu, którego zmianę stanu wyprzedził klient (zobacz [Zmiana stanu](#zmiana-stanu)).

Nie ma magazynów, lokalizacji ani księgi ruchów — dwa liczniki to cały model. Tabela ma jeszcze kolumnę `version integer DEFAULT 1 NOT NULL`, która została po dawnym warunku rezerwacji (zobacz [Rezerwacja stanu](#rezerwacja-stanu)), ale schemat Drizzle już jej nie deklaruje, więc żadne zapytanie jej nie odczytuje ani nie zapisuje, a nowy wiersz dostaje wartość domyślną. Usunie ją osobna migracja, zastosowana dopiero po wdrożeniu tego kodu, bo Worker z wcześniejszym kodem odczytuje ją z każdym wczytywanym wierszem stanu.

Wiersze powstają razem z wariantami: `prepareProductCatalogBatch` w `product.mutations.ts` wstawia wiersz stanu na podstawie pola `quantity` z formularza produktu, w tym samym wsadzie D1, który wstawia warianty, dla każdego wariantu, który jeszcze go nie ma, a istniejący wiersz zostawia w spokoju (`onConflictDoNothing` po `variant_id`). Każdy wariant jest zapisywany z `manageInventory: true` (`MANAGE_INVENTORY_ALWAYS` w `product.utils.ts`), więc kolumna `product_variant.manage_inventory` istnieje, ale w praktyce nigdy nie jest `false`.

## Odczyt dostępności

`inventory.availability.utils.ts` zawiera czyste pomocniki używane zarówno przez witrynę, jak i koszyk:

| Funkcja                                       | Znaczenie                                                              |
| --------------------------------------------- | ---------------------------------------------------------------------- |
| `getVariantQuantityAvailable(variant)`        | `variant?.inventory?.quantityAvailable ?? 0`                           |
| `isVariantPurchasable(variant, qty)`          | `qty > 0` i dostępne `>= qty`                                          |
| `resolveProductTotalAvailableStock(variants)` | suma po wariantach                                                     |
| `isProductInStock(variants)`                  | suma większa od zera                                                   |
| `sumHeldQuantity(heldLines, variantId)`       | sztuki wariantu trzymane przez sesję checkoutu                         |
| `quantitiesBeyond(lines, baselineLines)`      | każda linia przycięta do sztuk, których nie pokrywają już linie bazowe |

Brakujący wiersz `inventory` jest więc odczytywany jako zero, a nie jako wartość nieznana.

`getAvailabilityByVariantIds(variantIds)` w `inventory.accessors.ts` zwraca `Map<variantId, quantityAvailable>` dla partii identyfikatorów i z tego korzysta sprawdzenie dostępności koszyka, doliczając przez `sumHeldQuantity` sztuki trzymane przez otwarty checkout samego kupującego. Łączy `product_variant` i `product` i zostawia tylko produkty `published`, więc stan produktu zarchiwizowanego albo szkicu nigdy nie jest w sprzedaży: archiwizacja nie zmienia `inventory`, a koszyk zgłasza taką linię jako już niedostępną, nawet gdy trzyma ją checkout.

## Rezerwacja stanu

`reserveInventoryRows` w `inventory.accessors.ts` buduje jeden warunkowy `UPDATE` na linię, a jego `WHERE` pełni rolę kontroli współbieżności:

```ts
db.update(inventory)
  .set({
    quantityAvailable: sql`${inventory.quantityAvailable} - ${item.qty}`,
    quantityReserved: sql`${inventory.quantityReserved} + ${item.qty}`,
  })
  .where(and(eq(inventory.id, item.inventoryId), gte(inventory.quantityAvailable, item.qty)))
  .returning({ id: inventory.id })
```

Muszą zajść dwa warunki: wiersz istnieje, a w chwili wykonania instrukcji dostępnych sztuk jest dość. SQLite sprawdza warunek i wprowadza zmianę w tej samej instrukcji, a D1 ma jednego zapisującego, więc dwa checkouty, które chwilę po sobie odczytały ten sam stan, dostają swoje sztuki, gdy stan wystarcza dla obu, a odmowę dostaje tylko późniejszy, gdy nie wystarcza. Odrzucona linia zostawia swój identyfikator poza zbiorem, zamiast doprowadzić do nadsprzedaży, a za warunkiem stoi jeszcze ograniczenie nieujemności. Instrukcje wszystkich linii trafiają do D1 w jednym `db.batch`, więc koszyk dowolnej wielkości kosztuje jedną podróż do bazy, a funkcja zwraca zbiór identyfikatorów stanów, których aktualizacja trafiła w wiersz.

Dawniej warunek wymagał też, by `version` nadal równała się wartości odczytanej przez checkout podczas walidacji. Checkout był wtedy odrzucany za każdym razem, gdy inny zarezerwował ten sam wariant między jego odczytem a zapisem, a kupujący widział „Nie udało się przygotować płatności”, choć towaru zostało dużo. Nic poza tym porównaniem nie korzystało z tej kolumny, więc porównanie zniknęło i nic już nie zwiększa `version`. Odczyt przed zapisem tylko odnajduje wiersz: `validateAndCalculateItems` (`src/integrations/stripe/stripe.actions.server.ts`) zwraca obok zwalidowanej linii `inventoryId: inv.id`, a stan, który przy tym sprawdza, warunek sprawdza jeszcze raz.

## Wszystko albo nic dla wielu linii

`reserveInventoryForItems` w `inventory.utils.ts` najpierw scala linie wskazujące ten sam wiersz stanu, więc dwie linie jednego wariantu proszą o łączną ilość: wynik zawiera jeden identyfikator na wiersz i nie odróżniłby odrzuconej linii od zarezerwowanej linii tego samego wiersza. Potem rezerwuje wszystkie linie jednym wsadem i wycofuje całość, gdy którykolwiek warunek zawiódł:

```ts
const firstFailure = lines.find((line) => !reservedIds.has(line.inventoryId))
if (firstFailure !== undefined) {
  const reserved = lines.filter((line) => reservedIds.has(line.inventoryId))
  await releaseInventoryForItems(reserved).catch((error: unknown) => {
    console.error("Failed to roll back partial inventory reservation:", error)
  })

  console.warn(`Inventory reservation failed for ${firstFailure.title}. Not enough stock available.`)
  throw new AppError(ERROR_CODES.CONFLICT, CHECKOUT_ERROR_CODES.INSUFFICIENT_INVENTORY)
}
```

Warunek, który nie trafia w żaden wiersz, nie jest błędem, więc D1 zatwierdza linie, które trafiły; tę lukę zamyka kompensujące zwolnienie, samo będące jednym wsadem, a nie baza danych. Odmowa niesie `INSUFFICIENT_INVENTORY`, ten sam kod, którego walidacja używa dla koszyka proszącego o więcej, niż zostało. Kupujący, któremu ostatni egzemplarz chwilę wcześniej zarezerwował inny checkout, widzi więc komunikat o braku towaru (`errors.insufficientInventory`) zamiast ogólnego `errors.unknownError`, a koszyk ponownie sprawdza dostępność. Log podaje linię, której zabrakło.

## Przeniesienie rezerwacji na sesję zastępczą

Aktualizacja checkoutu zastępuje jego sesję Stripe, ale nigdy nie puszcza towaru, który kupujący zatrzymuje. `quantitiesBeyond(lines, baselineLines)` porównuje dwa zestawy linii po wariantach i z każdej linii zostawia tylko sztuki, których linie bazowe jeszcze nie pokrywają; bazę jednego wariantu wydaje raz na wszystkie jego linie. Aktualizacja używa jej w obie strony:

- `quantitiesBeyond(validatedItems, heldLines)` daje sztuki, które edytowany koszyk dokłada. Są rezerwowane przez `reserveInventoryForItems` na identyfikatorach stanu zwróconych przez walidację, zanim powstanie sesja zastępcza i zanim stara wygaśnie. Odmowa zostawia starą sesję, jej towar i checkout bez zmian.
- `quantitiesBeyond(heldLines, reservedLines)` daje sztuki, z których edytowany koszyk rezygnuje. `supersedeCheckoutSession` zwalnia tylko je, we wsadzie, który przenosi płatność.

Sztuk trzymanych przez obie sesje nic więc nie zwalnia, a inny checkout nie może przejąć unikatowego egzemplarza, gdy jego kupujący zmienia adres dostawy albo ilość.

## Zwolnienie jest ograniczone

Obie instrukcje zwolnienia używają `min`/`max`, więc podwójne zwolnienie nie wymyśli stanu z niczego:

```ts
.set({
  quantityAvailable: sql`${inventory.quantityAvailable} + min(${inventory.quantityReserved}, ${qty})`,
  quantityReserved: sql`max(0, ${inventory.quantityReserved} - ${qty})`,
})
```

`releaseInventoryForItems(items)` operuje po `inventoryId` i wysyła wszystkie linie jednym wsadem. `supersedeCheckoutSession` stosuje te same `inventoryReleaseValues`, po `variantId`, do sztuk trzymanych przez zastąpioną sesję checkoutu, których jej następczyni nie zatrzymuje. W przeciwieństwie do rezerwacji zwolnienie nie ma warunku — musi się zawsze udać, a ograniczenie sprawia, że powtórzone niczego nie psuje.

## Pełny cykl

| Moment                                                                                           | Efekt na wierszu                                                                                                                              |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| utworzenie sesji Stripe (`handleCreateCheckoutSession`)                                          | `available -= qty`, `reserved += qty`, tylko gdy `available >= qty`                                                                           |
| edycja checkoutu (`handleUpdateCheckoutSession`)                                                 | dokładane sztuki zarezerwowane najpierw; porzucone zwolnione przy przeniesieniu płatności (`supersedeCheckoutSession`); zatrzymane nietknięte |
| sesja opłacona (`prepareFulfillCheckoutBatch`)                                                   | `reserved -= qty`; `available` bez zmian — rezerwacja jest skonsumowana                                                                       |
| sesja wygasła albo płatność asynchroniczna nieudana (`prepareReleaseCheckoutBatch`)              | `available += min(reserved, qty)`, `reserved -= qty`                                                                                          |
| zapis produktu jako szkicu albo archiwum (`expireCheckoutsHoldingVariants`)                      | jego otwarte sesje są wygaszane, a potem zwalniane jak wyżej, przed webhookiem                                                                |
| anulowanie zamówienia przez administratora (`prepareCancelOrderBatch`)                           | `available += quantity`, dopóki zamówienie jest niewysłane, a jego towar jeszcze nie wrócił na stan                                           |
| administrator potwierdza, że produkty zwróconego zamówienia wróciły (`prepareRestockOrderBatch`) | `available += quantity`, z `getRestockLinesForOrder(orderId)`, raz na zamówienie                                                              |
| sam zwrot pieniędzy, z przycisku Zwrot, z panelu Stripe albo po przegranym sporze                | nic — `refundOrder` nigdy nie przywraca stanu                                                                                                 |
| zmiana stanu przez administratora w edytorze produktu (`prepareProductCatalogBatch`)             | `available += nowy − wczytany`; odrzucona, gdy zeszłaby poniżej zera                                                                          |

Rezerwacja trwa tylko tak długo, jak długo jej sesję Checkout da się opłacić. Każda sesja wygasa `CHECKOUT_SESSION_LIFETIME_SECONDS` (32 minuty, ze `stripe.constants.ts`) po otwarciu, a nie po domyślnych 24 godzinach Stripe, a jej webhook `checkout.session.expired` zwalnia linie. Aktualizacja checkoutu, która zastaje sesję już wygaszoną przez Stripe, sama najpierw uruchamia to samo strzeżone zwolnienie, podobnie jak sprawdzenie zapisanej sesji, które wykonuje strona kasy, więc nowy checkout kupującego nie czeka na webhook. Zapis produktu jako szkicu albo archiwum kończy jego rezerwacje wcześniej: wygasza każdą otwartą sesję trzymającą któryś z jego wariantów i dla każdej uruchamia to samo strzeżone zwolnienie, więc webhook, który przychodzi potem, nie ma już czego oddać (zobacz [Panel katalogu](/docs/features/admin-catalog#zapis)). Przeglądarka trzyma jedną otwartą sesję: kasa kontynuuje zapisaną sesję ścieżką aktualizacji, która przenosi rezerwację na sesję zastępczą, zamiast rezerwować koszyk ponownie po odświeżeniu, w drugiej karcie albo po wizycie w koszyku. Każda aktualizacja daje sesji zastępczej nowe `CHECKOUT_SESSION_LIFETIME_SECONDS`, więc ścieżka aktualizacji zmienia checkout tylko, dopóki jest od tego młodszy; starszemu checkoutowi wygasza sesję i zwalnia linie, a przeglądarka otwiera nowy checkout, który wlicza się do limitów otwartych checkoutów. Checkout trzyma więc towar najwyżej przez dwukrotność czasu życia sesji (zobacz [Kasa: limity trzymania towaru](/docs/features/checkout#limity-trzymania-towaru)).

Każde przywrócenie na stan przechodzi przez `prepareRestockOrderBatch` (`order.utils.ts`), które dodaje każdą linię tylko wtedy, gdy zamówienie nie jest `cancelled`, a jego `restocked_at` jest puste, i w tym samym wsadzie ustawia `restocked_at`, więc towar zamówienia wraca na stan najwyżej raz, niezależnie od tego, co przyjdzie pierwsze: anulowanie, okno zwrotu czy Przywróć na stan, i jak często każde z nich zostanie powtórzone. Anulowanie wymaga też, by zamówienie nie zostało wysłane. Sam zwrot pieniędzy niczego nie przywraca, bo nie mówi, gdzie jest towar: zwrot za zagubioną przesyłkę albo zwrot z dobrej woli nie może wystawić unikatowego egzemplarza z powrotem na sprzedaż. Administrator odpowiada na to pytanie w oknie zwrotu, którego pole jest na początku zaznaczone tylko dla zamówienia niewysłanego, albo później przyciskiem Przywróć na stan w zamówieniu (zobacz [Zamówienia](/docs/features/orders#akcje-w-panelu)).

Lokalna obsługa błędów w `stripe.actions.server.ts` zawsze kompensuje: porażka po rezerwacji wywołuje `releaseInventoryForItems`. Aktualizacja checkoutu rezerwuje to, co dokłada edytowany koszyk, zanim cokolwiek innego się zmieni, i oddaje to przez `releaseInventoryForItems`, gdy nie uda się utworzyć sesji zastępczej, wygasić starej sesji albo przenieść płatności. To, z czego edytowany koszyk rezygnuje, zwalnia dopiero po wygaszeniu starej sesji, w tym samym wsadzie, który przenosi płatność, i tylko dopóki checkout jest nadal `pending`. Wsad zwolnienia z webhooka wygaśnięcia ma ten sam warunek na oczekującą płatność sesji, więc linie starej sesji zwraca ten wsad, który zatwierdzi się pierwszy, a drugi nie znajduje nic, niezależnie od tego, jak przeplotą się oba żądania: webhook, który wygra, zwraca je wszystkie, a aktualizacja oddaje to, co dołożyła, i dostaje odmowę. Porażka po przeniesieniu nie przywraca ich: starej sesji nie da się już opłacić, więc `releaseCheckout` oznacza checkout jako nieudany i oddaje z sesji zastępczej cały edytowany koszyk.

## Stan decyduje o widoczności

`publishedInStockWhere` w `src/modules/product/product.stock.server.ts` warunkuje każdy odczyt witryny stanem magazynowym:

```ts
export const totalStockSubquery = () =>
  sql<number>`(
    select coalesce(sum("inventory"."quantity_available"), 0)
    from "product_variant"
    left join "inventory" on "inventory"."variant_id" = "product_variant"."id"
    where "product_variant"."product_id" = ${product.id}
  )`
```

Opublikowany produkt, którego warianty sumują się do zera dostępnych sztuk, znika z listingu katalogu, z wyszukiwania i z własnej karty — `getProduct` zwraca `false`, a trasa rzuca `notFound()`. Rezerwacja stanu na potrzeby checkoutu ukrywa więc ostatnią sztukę przed innymi kupującymi, i o to właśnie chodzi.

## Niski stan w panelu

`PRODUCT_LOW_STOCK_THRESHOLD = 10` (`product.constants.ts`), a `PRODUCT_INVENTORY_LEVEL` to `{ LOW: "low", OK: "ok", OUT: "out" }`.

```ts
export const resolveProductInventoryLevel = (status: ProductStatus, totalStock: number): ProductInventoryLevel => {
  if (status !== PRODUCT_STATUS.PUBLISHED) {
    return PRODUCT_INVENTORY_LEVEL.OK
  }
  if (totalStock <= 0) {
    return PRODUCT_INVENTORY_LEVEL.OUT
  }
  if (totalStock <= PRODUCT_LOW_STOCK_THRESHOLD) {
    return PRODUCT_INVENTORY_LEVEL.LOW
  }

  return PRODUCT_INVENTORY_LEVEL.OK
}
```

Produkty nieopublikowane są zawsze raportowane jako `ok`, więc szkic bez stanu nie jest oznaczany.

`getLowStockPublishedProductCountQuery` w `product.accessors.ts` to przygotowane zapytanie stojące za kartą na pulpicie:

```ts
.where(and(eq(product.status, PRODUCT_STATUS.PUBLISHED), sql`${totalStockSubquery()} between 1 and ${PRODUCT_LOW_STOCK_THRESHOLD}`))
```

`buildInventoryLevelStockCondition` zamienia poziom w warunek `WHERE` dla filtra stanu w siatce produktów, a kontrolką jest `products-stock-column-filter.tsx`.

## Zmiana stanu

**Nie ma dedykowanego use case'a korekty stanu.** Stan zmienia się w edytorze produktu, który działa jak w Shopify: pole pokazuje liczbę sztuk dostępnych do sprzedaży, a zapis utrwala tylko zmianę wprowadzoną przez administratora, jako różnicę.

- `mapProductDetailToFormValues` (`product-form.utils.ts`) wczytuje `quantityAvailable` do pola i zachowuje je jako `loadedQuantity`, a `quantityReserved` zachowuje jako `quantityInCheckout`. Edytor pokazuje tę liczbę pod polem („1 szt. w trakcie płatności”, „1 in checkout”), a podpowiedź mówi, że pole to stan dostępny do sprzedaży. `quantityInCheckout` istnieje tylko w schemacie formularza, więc `parseCatalogUpsertInput` je odrzuca; `loadedQuantity` jest wysyłane razem z `quantity`.
- `prepareCatalogReplacePayload` (`product.utils.ts`) zamienia wariant, który produkt już ma i którego `quantity` różni się od `loadedQuantity`, we wpis `inventoryAdjustments` równy `quantity − loadedQuantity`. Nieruszone pole albo wariant, którego stanu edytor nie wczytał, nie zapisuje stanu.
- `prepareProductCatalogBatch` stosuje każdą korektę we wsadzie zapisu jako `quantity_available = quantity_available + zmiana`, więc rezerwacja, zwolnienie albo sprzedaż, które nastąpiły przy otwartym edytorze, pozostają policzone. Nowy produkt albo nowy wariant nadal dostaje pierwszy stan z wpisanej liczby; istniejący wiersz nigdy nie jest nadpisywany.
- Gdy klient w międzyczasie zarezerwował albo kupił towar i korekta zeszłaby z `quantity_available` poniżej zera, ograniczenie kończy instrukcję błędem, a D1 wycofuje cały wsad, więc nic z produktu nie zostaje zapisane. `rethrowProductMutationError` zamienia ten błąd na `ERROR_CODES.CONFLICT` z `PRODUCT_ERROR_CODES.STOCK_CHANGED_WHILE_EDITING`; edytor zostaje otwarty z danymi administratora i pokazuje `toast.stockChangedWhileEditing`, który mówi, że nic nie zostało zapisane, i każe odświeżyć stronę, aby zobaczyć aktualny stan.

Wszystko pozostałe — rezerwacja, zamiana, zwolnienie — dzieje się automatycznie wokół checkoutu, a produkty zamówienia wracają na stan, gdy administrator je anuluje albo potwierdzi, że wróciły.

Jeśli potrzebny jest ekran korekty stanu, właściwym miejscem jest nowy use case w `src/modules/inventory/use-cases/` z `authorized({ product: ["update"] })`, zapisujący zmianę w SQL jako różnicę, tak jak zapis produktu, żeby nie mógł cofnąć rezerwacji, którą w międzyczasie zrobił trwający checkout, a ograniczenie nieujemności odrzuciło korektę zabierającą towar zarezerwowany albo sprzedany, i po zapisie wywołujący `scheduleProductCatalogInvalidation()`.
