## Tabela

`inventory` (`src/modules/inventory/inventory.schema.ts`) to jeden wiersz na wariant:

```ts
export const inventory = sqliteTable(
  "inventory",
  {
    id: text("id", { length: INVENTORY_COLUMN_LENGTH.id })
      .primaryKey()
      .$defaultFn(() => crypto.randomUUID()),
    quantityAvailable: integer("quantity_available").default(INVENTORY_DEFAULT_QUANTITY).notNull(),
    quantityReserved: integer("quantity_reserved").default(INVENTORY_DEFAULT_QUANTITY).notNull(),
    variantId: text("variant_id", { length: INVENTORY_COLUMN_LENGTH.variantId })
      .references(() => productVariant.id, { onDelete: "cascade" })
      .notNull(),
    version: integer("version").default(INVENTORY_DEFAULT_VERSION).notNull(),
    ...timestamps(),
  },
  (table) => [
    uniqueIndex("inventory_variantId_unique").on(table.variantId),
    check(INVENTORY_NON_NEGATIVE_AVAILABLE_CHECK, sql`${table.quantityAvailable} >= 0`),
  ],
)
```

`INVENTORY_DEFAULT_QUANTITY` to `0`, a `INVENTORY_DEFAULT_VERSION` to `1` (`inventory.constants.ts`). Unikalny indeks na `variant_id` gwarantuje relację jeden do jednego, a kaskada powoduje, że usunięcie wariantu usuwa jego wiersz stanu.

Ograniczenie `inventory_quantity_available_non_negative` (`INVENTORY_NON_NEGATIVE_AVAILABLE_CHECK`, dodane przez `20261005300000_inventory_available_never_negative.sql`) utrzymuje `quantity_available` na poziomie zera lub wyżej. Instrukcja, która zeszłaby poniżej zera, kończy się błędem, a razem z nią cały wsad D1, w którym działa. Rezerwacja nigdy go nie narusza, bo jej własny warunek wymaga wystarczającego stanu; to ono odrzuca zapis produktu, którego zmianę stanu wyprzedził klient (zobacz [Zmiana stanu](#zmiana-stanu)).

Nie ma magazynów, lokalizacji ani księgi ruchów — dwa liczniki i wersja to cały model.

Wiersze powstają razem z wariantami: `prepareProductCatalogBatch` w `product.mutations.ts` wstawia wiersz stanu na podstawie pola `quantity` z formularza produktu, w tym samym wsadzie D1, który wstawia warianty, dla każdego wariantu, który jeszcze go nie ma, a istniejący wiersz zostawia w spokoju (`onConflictDoNothing` po `variant_id`). Każdy wariant jest zapisywany z `manageInventory: true` (`MANAGE_INVENTORY_ALWAYS` w `product.utils.ts`), więc kolumna `product_variant.manage_inventory` istnieje, ale w praktyce nigdy nie jest `false`.

## Odczyt dostępności

`inventory.availability.utils.ts` zawiera czyste pomocniki używane zarówno przez witrynę, jak i koszyk:

| Funkcja                                       | Znaczenie                                      |
| --------------------------------------------- | ---------------------------------------------- |
| `getVariantQuantityAvailable(variant)`        | `variant?.inventory?.quantityAvailable ?? 0`   |
| `isVariantPurchasable(variant, qty)`          | `qty > 0` i dostępne `>= qty`                  |
| `resolveProductTotalAvailableStock(variants)` | suma po wariantach                             |
| `isProductInStock(variants)`                  | suma większa od zera                           |
| `sumHeldQuantity(heldLines, variantId)`       | sztuki wariantu trzymane przez sesję checkoutu |

Brakujący wiersz `inventory` jest więc odczytywany jako zero, a nie jako wartość nieznana.

`getAvailabilityByVariantIds(variantIds)` w `inventory.accessors.ts` zwraca `Map<variantId, quantityAvailable>` dla partii identyfikatorów i z tego korzysta sprawdzenie dostępności koszyka, doliczając przez `sumHeldQuantity` sztuki trzymane przez otwarty checkout samego kupującego. Łączy `product_variant` i `product` i zostawia tylko produkty `published`, więc stan produktu zarchiwizowanego albo szkicu nigdy nie jest w sprzedaży: archiwizacja nie zmienia `inventory`, a koszyk zgłasza taką linię jako już niedostępną, nawet gdy trzyma ją checkout.

## Rezerwacja optymistyczna

`reserveInventoryRows` w `inventory.accessors.ts` buduje jeden warunkowy `UPDATE` na linię, a jego `WHERE` pełni rolę kontroli współbieżności:

```ts
db.update(inventory)
  .set({
    quantityAvailable: sql`${inventory.quantityAvailable} - ${item.qty}`,
    quantityReserved: sql`${inventory.quantityReserved} + ${item.qty}`,
    version: sql`${inventory.version} + 1`,
  })
  .where(and(eq(inventory.id, item.inventoryId), eq(inventory.version, item.currentVersion), gte(inventory.quantityAvailable, item.qty)))
  .returning({ id: inventory.id })
```

Muszą zajść trzy warunki: wiersz istnieje, jego `version` nadal równa się wersji odczytanej przez wywołującego i dostępnych sztuk jest dość. Instrukcje wszystkich linii trafiają do D1 w jednym `db.batch`, więc koszyk dowolnej wielkości kosztuje jedną podróż do bazy, a funkcja zwraca zbiór identyfikatorów stanów, których aktualizacja trafiła w wiersz. Przegrany wyścig zostawia swój identyfikator poza zbiorem, zamiast doprowadzić do nadsprzedaży. Każdy udany zapis zwiększa `version`.

Wersję, z którą porównuje wywołujący, przechwytuje `validateAndCalculateItems` (`src/integrations/stripe/stripe.actions.server.ts`), zwracając obok zwalidowanej linii `currentVersion: inv.version` oraz `inventoryId: inv.id`.

## Wszystko albo nic dla wielu linii

`reserveInventoryForItems` w `inventory.utils.ts` najpierw scala linie wskazujące ten sam wiersz stanu, więc dwie linie jednego wariantu proszą o łączną ilość, zamiast żeby druga przegrała na wersji, którą właśnie przesunęła pierwsza. Potem rezerwuje wszystkie linie jednym wsadem i wycofuje całość, gdy którykolwiek warunek zawiódł:

```ts
const firstFailure = lines.find((line) => !reservedIds.has(line.inventoryId))
if (firstFailure !== undefined) {
  const reserved = lines.filter((line) => reservedIds.has(line.inventoryId))
  await releaseInventoryForItems(reserved).catch((error: unknown) => {
    console.error("Failed to roll back partial inventory reservation:", error)
  })

  throw new Error(`Inventory reservation failed for ${firstFailure.title}. Stock changed or unavailable.`)
}
```

Warunek, który nie trafia w żaden wiersz, nie jest błędem, więc D1 zatwierdza linie, które trafiły; tę lukę zamyka kompensujące zwolnienie, samo będące jednym wsadem, a nie baza danych.

`reserveInventoryByVariantLines(lines)` to wariant oparty na identyfikatorach wariantów, który rezerwuje edytowany koszyk podczas aktualizacji checkoutu, po zwolnieniu linii starej sesji i zwiększeniu ich `version`: jednym zapytaniem przez `getInventoryByVariantIds` czyta wiersz stanu i aktualną `version` każdej linii, a potem deleguje do `reserveInventoryForItems`.

## Zwolnienie jest ograniczone

Obie instrukcje zwolnienia używają `min`/`max`, więc podwójne zwolnienie nie wymyśli stanu z niczego:

```ts
.set({
  quantityAvailable: sql`${inventory.quantityAvailable} + min(${inventory.quantityReserved}, ${qty})`,
  quantityReserved: sql`max(0, ${inventory.quantityReserved} - ${qty})`,
  version: sql`${inventory.version} + 1`,
})
```

`releaseInventoryForItems(items)` operuje po `inventoryId` i wysyła wszystkie linie jednym wsadem. `supersedeCheckoutSession` stosuje te same `inventoryReleaseValues`, po `variantId`, do linii trzymanych przez zastąpioną sesję checkoutu. W przeciwieństwie do rezerwacji zwolnienie nie jest warunkowane przez `version` — musi się zawsze udać.

## Pełny cykl

| Moment                                                                                           | Efekt na wierszu                                                                                          |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| utworzenie sesji Stripe (`handleCreateCheckoutSession`)                                          | `available -= qty`, `reserved += qty`, `version += 1`                                                     |
| edycja checkoutu (`handleUpdateCheckoutSession`)                                                 | stare linie zwolnione przy przeniesieniu płatności (`supersedeCheckoutSession`), potem nowe zarezerwowane |
| sesja opłacona (`prepareFulfillCheckoutBatch`)                                                   | `reserved -= qty`; `available` bez zmian — rezerwacja jest skonsumowana                                   |
| sesja wygasła albo płatność asynchroniczna nieudana (`prepareReleaseCheckoutBatch`)              | `available += min(reserved, qty)`, `reserved -= qty`                                                      |
| anulowanie zamówienia przez administratora (`prepareCancelOrderBatch`)                           | `available += quantity`, dopóki zamówienie jest niewysłane, a jego towar jeszcze nie wrócił na stan       |
| administrator potwierdza, że produkty zwróconego zamówienia wróciły (`prepareRestockOrderBatch`) | `available += quantity`, z `getRestockLinesForOrder(orderId)`, raz na zamówienie                          |
| sam zwrot pieniędzy, z przycisku Zwrot, z panelu Stripe albo po przegranym sporze                | nic — `refundOrder` nigdy nie przywraca stanu                                                             |
| zmiana stanu przez administratora w edytorze produktu (`prepareProductCatalogBatch`)             | `available += nowy − wczytany`, `version += 1`; odrzucona, gdy zeszłaby poniżej zera                      |

Rezerwacja trwa tylko tak długo, jak długo jej sesję Checkout da się opłacić. Każda sesja wygasa `CHECKOUT_SESSION_LIFETIME_SECONDS` (32 minuty, ze `stripe.constants.ts`) po otwarciu, a nie po domyślnych 24 godzinach Stripe, a jej webhook `checkout.session.expired` zwalnia linie. Aktualizacja checkoutu, która zastaje sesję już wygaszoną przez Stripe, sama najpierw uruchamia to samo strzeżone zwolnienie, podobnie jak sprawdzenie zapisanej sesji, które wykonuje strona kasy, więc nowy checkout kupującego nie czeka na webhook. Przeglądarka trzyma jedną otwartą sesję: kasa kontynuuje zapisaną sesję ścieżką aktualizacji, która zwalnia stare linie, rezerwując nowe, zamiast rezerwować koszyk ponownie po odświeżeniu, w drugiej karcie albo po wizycie w koszyku.

Każde przywrócenie na stan przechodzi przez `prepareRestockOrderBatch` (`order.utils.ts`), które dodaje każdą linię tylko wtedy, gdy zamówienie nie jest `cancelled`, a jego `restocked_at` jest puste, i w tym samym wsadzie ustawia `restocked_at`, więc towar zamówienia wraca na stan najwyżej raz, niezależnie od tego, co przyjdzie pierwsze: anulowanie, okno zwrotu czy Przywróć na stan, i jak często każde z nich zostanie powtórzone. Anulowanie wymaga też, by zamówienie nie zostało wysłane. Sam zwrot pieniędzy niczego nie przywraca, bo nie mówi, gdzie jest towar: zwrot za zagubioną przesyłkę albo zwrot z dobrej woli nie może wystawić unikatowego egzemplarza z powrotem na sprzedaż. Administrator odpowiada na to pytanie w oknie zwrotu, którego pole jest na początku zaznaczone tylko dla zamówienia niewysłanego, albo później przyciskiem Przywróć na stan w zamówieniu (zobacz [Zamówienia](/docs/features/orders#akcje-w-panelu)).

Zwróć uwagę, że wsady realizacji i zwolnienia aktualizują `inventory` **bez** zwiększania `version`, bo działają wewnątrz wsadu D1 razem z zapisami zamówienia, a nie przez `reserveInventoryRows` i funkcje zwalniające.

Lokalna obsługa błędów w `stripe.actions.server.ts` zawsze kompensuje: porażka po rezerwacji wywołuje `releaseInventoryForItems`. Aktualizacja checkoutu zwalnia stare linie dopiero po wygaszeniu starej sesji, w tym samym wsadzie, który przenosi płatność, i tylko dopóki checkout jest nadal `pending`. Wsad zwolnienia z webhooka wygaśnięcia ma ten sam warunek na oczekującą płatność sesji, więc stare linie zwraca ten wsad, który zatwierdzi się pierwszy, a drugi nie znajduje nic, niezależnie od tego, jak przeplotą się oba żądania. Porażka po tym momencie nie przywraca ich: starej sesji nie da się już opłacić, więc `releaseCheckout` oznacza checkout jako nieudany i oddaje to, co zarezerwował edytowany koszyk.

## Stan decyduje o widoczności

`publishedInStockWhere` w `src/modules/product/product.stock.server.ts` warunkuje każdy odczyt witryny stanem magazynowym:

```ts
export const totalStockSubquery = () =>
  sql<number>`(
    select coalesce(sum("inventory"."quantity_available"), 0)
    from "product_variant"
    left join "inventory" on "inventory"."variant_id" = "product_variant"."id"
    where "product_variant"."product_id" = ${product.id}
  )`
```

Opublikowany produkt, którego warianty sumują się do zera dostępnych sztuk, znika z listingu katalogu, z wyszukiwania i z własnej karty — `getProduct` zwraca `false`, a trasa rzuca `notFound()`. Rezerwacja stanu na potrzeby checkoutu ukrywa więc ostatnią sztukę przed innymi kupującymi, i o to właśnie chodzi.

## Niski stan w panelu

`PRODUCT_LOW_STOCK_THRESHOLD = 10` (`product.constants.ts`), a `PRODUCT_INVENTORY_LEVEL` to `{ LOW: "low", OK: "ok", OUT: "out" }`.

```ts
export const resolveProductInventoryLevel = (status: ProductStatus, totalStock: number): ProductInventoryLevel => {
  if (status !== PRODUCT_STATUS.PUBLISHED) {
    return PRODUCT_INVENTORY_LEVEL.OK
  }
  if (totalStock <= 0) {
    return PRODUCT_INVENTORY_LEVEL.OUT
  }
  if (totalStock <= PRODUCT_LOW_STOCK_THRESHOLD) {
    return PRODUCT_INVENTORY_LEVEL.LOW
  }

  return PRODUCT_INVENTORY_LEVEL.OK
}
```

Produkty nieopublikowane są zawsze raportowane jako `ok`, więc szkic bez stanu nie jest oznaczany.

`getLowStockPublishedProductCountQuery` w `product.accessors.ts` to przygotowane zapytanie stojące za kartą na pulpicie:

```ts
.where(and(eq(product.status, PRODUCT_STATUS.PUBLISHED), sql`${totalStockSubquery()} between 1 and ${PRODUCT_LOW_STOCK_THRESHOLD}`))
```

`buildInventoryLevelStockCondition` zamienia poziom w warunek `WHERE` dla filtra stanu w siatce produktów, a kontrolką jest `products-stock-column-filter.tsx`.

## Zmiana stanu

**Nie ma dedykowanego use case'a korekty stanu.** Stan zmienia się w edytorze produktu, który działa jak w Shopify: pole pokazuje liczbę sztuk dostępnych do sprzedaży, a zapis utrwala tylko zmianę wprowadzoną przez administratora, jako różnicę.

- `mapProductDetailToFormValues` (`product-form.utils.ts`) wczytuje `quantityAvailable` do pola i zachowuje je jako `loadedQuantity`, a `quantityReserved` zachowuje jako `quantityInCheckout`. Edytor pokazuje tę liczbę pod polem („1 szt. w trakcie płatności”, „1 in checkout”), a podpowiedź mówi, że pole to stan dostępny do sprzedaży. `quantityInCheckout` istnieje tylko w schemacie formularza, więc `parseCatalogUpsertInput` je odrzuca; `loadedQuantity` jest wysyłane razem z `quantity`.
- `prepareCatalogReplacePayload` (`product.utils.ts`) zamienia wariant, który produkt już ma i którego `quantity` różni się od `loadedQuantity`, we wpis `inventoryAdjustments` równy `quantity − loadedQuantity`. Nieruszone pole albo wariant, którego stanu edytor nie wczytał, nie zapisuje stanu.
- `prepareProductCatalogBatch` stosuje każdą korektę we wsadzie zapisu jako `quantity_available = quantity_available + zmiana` i `version = version + 1`, więc rezerwacja, zwolnienie albo sprzedaż, które nastąpiły przy otwartym edytorze, pozostają policzone. Nowy produkt albo nowy wariant nadal dostaje pierwszy stan z wpisanej liczby; istniejący wiersz nigdy nie jest nadpisywany.
- Gdy klient w międzyczasie zarezerwował albo kupił towar i korekta zeszłaby z `quantity_available` poniżej zera, ograniczenie kończy instrukcję błędem, a D1 wycofuje cały wsad, więc nic z produktu nie zostaje zapisane. `rethrowProductMutationError` zamienia ten błąd na `ERROR_CODES.CONFLICT` z `PRODUCT_ERROR_CODES.STOCK_CHANGED_WHILE_EDITING`; edytor zostaje otwarty z danymi administratora i pokazuje `toast.stockChangedWhileEditing`, który mówi, że nic nie zostało zapisane, i każe odświeżyć stronę, aby zobaczyć aktualny stan.

Wszystko pozostałe — rezerwacja, zamiana, zwolnienie — dzieje się automatycznie wokół checkoutu, a produkty zamówienia wracają na stan, gdy administrator je anuluje albo potwierdzi, że wróciły.

Jeśli potrzebny jest ekran korekty stanu, właściwym miejscem jest nowy use case w `src/modules/inventory/use-cases/` z `authorized({ product: ["update"] })`, korzystający z tej samej przygotowanej instrukcji z kontrolą wersji, żeby nie mógł przegrać wyścigu z trwającym checkoutem, a po zapisie wywołujący `scheduleProductCatalogInvalidation()`.
