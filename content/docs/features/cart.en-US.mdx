M'Arte has no server-side cart. The basket lives in `localStorage` under the key `marte-cart` and the database's `cart` and `cart_item` tables are unused. The only server round trip is a check of the stock and the current prices.

## The store

`src/modules/cart/cart.store.ts` creates `useCartStore` with zustand's `persist` middleware:

```ts
{
  migrate: (persisted) => { /* keeps only rows that pass isPersistedCartItem */ },
  name: "marte-cart",
  version: CART_PERSIST_VERSION,
}
```

`CART_PERSIST_VERSION` is `3`. The `migrate` function does not transform old shapes — it re-validates every row with the `isPersistedCartItem` type guard and drops anything that does not match, so a stored basket from an older build degrades to an empty or partial basket rather than crashing the page. It also brings every kept line's `qty` within one and `CART_LINE_QUANTITY_MAX`; version `3` makes it run once over baskets stored before that limit existed, so none of them sends a quantity checkout would refuse.

A line is:

```ts
export interface CartItem {
  readonly id: string
  readonly variantId: string
  readonly slug: string
  readonly title: string
  readonly variantTitle: string
  readonly image: string
  readonly price: string
  readonly rawPrice: number
  readonly priceChanged?: boolean
  qty: number
}
```

`id` is always set to `variantId` by `addItem`, so **the variant is the line identity**: adding the same variant twice increments `qty` instead of creating a second line. `price` is the pre-formatted display string and `rawPrice` the minor units. `priceChanged` marks a line whose price the shop changed while it sat in the basket.

Actions: `addItem`, `applyCurrentPrices(prices)`, `removeItem(id)`, `updateQuantity(id, qty)`, `clearCart`, `itemCount()` and `cartTotal()`. `addItem` and `updateQuantity` keep a line's `qty` between one and `CART_LINE_QUANTITY_MAX` (10, in `src/modules/cart/cart.constants.ts`), the most of one piece checkout accepts in an order (see [Checkout: Limits on holding stock](/docs/features/checkout#limits-on-holding-stock)), so adding a piece the basket already holds ten of leaves it at ten.

`useCartHydrated()` is exported alongside the store. It subscribes to `useCartStore.persist.onFinishHydration` and returns `false` until rehydration completes — every consumer that must not act on an empty pre-hydration basket uses it, most importantly the checkout guard.

## Pricing

`src/modules/cart/cart.pricing.ts` holds the two functions the store and the UI share:

```ts
export const getCartLineUnitPriceCents = (item: { readonly price: string; readonly rawPrice: number }): number => {
  if (Number.isFinite(item.rawPrice) && item.rawPrice >= MIN_PRICE_CENTS) {
    return item.rawPrice
  }

  return parseMoneyInputToMinorUnits(item.price, STORE_CURRENCY_CODE) ?? 0
}

export const getCartLineTotalCents = (item: { readonly price: string; readonly qty: number; readonly rawPrice: number }): number =>
  getCartLineUnitPriceCents(item) * item.qty
```

`rawPrice` wins; the string parse is a fallback for baskets persisted before `rawPrice` existed. `MIN_PRICE_CENTS` and `parseMoneyInputToMinorUnits` come from `src/modules/_core/utils/currency.ts`.

**Prices in the basket follow the catalogue.** `rawPrice` starts as the price on the page the piece was added from. Every availability check also returns the price each variant sells for now, and every checkout session the server opens returns the prices it was quoted at. Both go through `applyCurrentPrices(prices)`, which sets `rawPrice` on each line whose displayed price differs and marks it `priceChanged`. A marked line says `pages.cart.priceChanged` in the basket and `checkoutSummary.priceChanged` in the checkout summary until it is removed or the order is placed; the old price is not shown. A line the server reports no price for keeps its own, and checkout refuses it with `INVALID_PRICE`, `VARIANT_NOT_FOUND` or `PRODUCT_NOT_FOUND`. The basket's prices are only ever displayed: the server never receives them, because `cartItemSchema` has no `price` or `rawPrice`, and it prices the Stripe session from `variant.price` in `validateAndCalculateItems` — see [Checkout](/docs/features/checkout).

## Availability check

`src/modules/cart/use-cases/check-cart-availability.ts` is the only server function in the module. It is public (`withRequest`), takes `{ heldSessionId?, lines: [{ variantId, qty }] }` and answers per line, with the current price of every variant:

```ts
const variantIds = lines.map((line) => line.variantId)
const [availabilityByVariantId, priceByVariantId, heldLines] = await Promise.all([
  getAvailabilityByVariantIds(variantIds),
  getSellPricesByVariantIds(variantIds),
  heldSessionId === undefined ? [] : getHeldLinesByTransactionId(heldSessionId),
])

const issues = lines.flatMap((line) => {
  const stockOnSale = availabilityByVariantId.get(line.variantId)
  const available = stockOnSale === undefined ? 0 : stockOnSale + sumHeldQuantity(heldLines, line.variantId)
  if (available >= line.qty) {
    return []
  }

  return [{ available, qty: line.qty, variantId: line.variantId }]
})

return {
  hasUnavailableItems: issues.length > 0,
  issues,
  prices: [...priceByVariantId].map(([variantId, unitPrice]) => ({ unitPrice, variantId })),
}
```

`getAvailabilityByVariantIds` in `inventory.accessors.ts` joins each `inventory` row to its variant and product and returns the stock of `published` products only. A variant with no `inventory` row, or whose product the shop archived or returned to draft, is missing from that map and counts as `0` available, whatever the shopper's own checkout holds: the basket marks the line `pages.cart.availability.itemUnavailable` ("No longer available", "Nie jest już dostępny"), the banner appears and the checkout sends the shopper back to the basket. The storefront listings, search and the product page hide such a product through the same status (see [Catalog and search](/docs/features/catalog-and-search)), and checkout refuses it (see [Checkout](/docs/features/checkout)). `prices` comes from `getSellPricesByVariantIds` in `src/modules/product-variant/product-variant.accessors.ts`, one query over `product_variant` that leaves out a variant whose price fails `isSellPriceCentsValid`. `heldSessionId` is the browser's open Checkout Session, which the checkout keeps in `localStorage` (see [Checkout](/docs/features/checkout)). `getHeldLinesByTransactionId` in `payment.accessors.ts` returns the `reserved_lines` of that session's payment while the payment and its checkout are both `pending`, the same condition under which a release would still return them, and nothing otherwise. Those units are added back for this browser only, so a shopper whose own checkout holds the last piece still sees it as available on the basket and the checkout after a reload, while every other shopper sees it reserved. The endpoint is public, so its input is bounded: at most `CART_LINES_MAX` lines, whole quantities of at least one, variant ids no longer than a stored id, and a session id of at most 255 characters. A session id only ever adds what that session already holds, so guessing one gains nothing.

`checkCartAvailabilityQuery(lines, heldSessionId)` is `enabled` only when there is at least one line and uses `staleTime: 0`, so the check is fresh on every mount. It sets `refetchOnWindowFocus: false` and `refetchOnReconnect: false`, so coming back to the tab or getting the connection back does not run it again. A shopper paying with BLIK on a phone leaves the payment step for the banking app and comes back while the payment completes. Once it has, the session no longer holds the piece, so a check run on the way back would find the last piece sold and the checkout guard would send its buyer to the basket before the page could show the confirmation. When the phone discards the tab meanwhile and the page reloads, the checkout asks `getCheckoutSessionStatus` about the stored session before the guard runs any check, and shows the confirmation of a paid one (see [Checkout](/docs/features/checkout)). Its key is `[...CART_QUERY_KEYS.AVAILABILITY, lines, heldSessionId]` — the lines and the held session are part of the key, so changing a quantity or opening a session refetches. `placeholderData: keepPreviousData` keeps the last answer while a new key is checked, so the checkout guard does not fall back to a first check, and unmount the form, when the payment step stores its session. `CART_QUERY_KEYS.AVAILABILITY` is `["cart", "availability"]` and is in `STOREFRONT_REALTIME_QUERY_PREFIXES`, so a stock or price change pushed from the admin console re-runs the check in open tabs, and a new price reaches the basket and the checkout without a reload.

`src/hooks/use-cart-availability.ts` reads the held session with `useSyncExternalStore(subscribeToCheckoutSessionId, loadCheckoutSessionId, …)`, with no session on the server, wraps the query and returns `{ hasUnavailableItems, isChecking, issues, issuesByVariantId }`. An effect passes each answer's `prices` to `applyCurrentPrices`, so every page that runs the check, which through `CartAvailabilityBanner` is every storefront page with a non-empty basket, keeps the basket's prices current. `isChecking` is true while `isPending || isFetching` and there is at least one line.

The cart page formats its own totals rather than going through `useFormatter`:

```ts
const CENTS_IN_ZLOTY = 100
const total = cartTotal() / CENTS_IN_ZLOTY
const subtotal = new Intl.NumberFormat("pl-PL", { currency: "PLN", style: "currency" }).format(total)
```

**That format is hard-coded to `pl-PL`**, so the English cart still shows Polish number formatting.

## The summary is a subtotal only

`cart-summary.tsx` renders three rows — subtotal, shipping and total — but shipping is the message `pages.cart.summary.shippingValue` and the total row prints the same `subtotal` value:

```tsx
<div className="flex justify-between">
  <span className="font-medium">{t("summary.total")}</span>
  <span className="font-medium">{subtotal}</span>
</div>
```

Delivery cost is not known until a delivery method is chosen, which happens in checkout. The real total including shipping is computed by Stripe from the session line items.

When `checkoutDisabled` or `salesPaused` is true the checkout link is replaced by a non-interactive `<span aria-disabled="true">`, so there is no clickable-but-dead button. With `salesPaused` the summary also says why above it, in a `role="status"` paragraph with `pages.cart.salesPaused.checkoutClosed`: "Orders are paused for now, so checkout is closed. Your cart will wait here until we reopen."

## Blocking a bad basket

Two guards use the availability result:

- `/cart` disables the checkout link while `hasUnavailableItems || isChecking`, and also while `getSalesStatusQuery()` reports that sales are paused, which it passes to the summary as `salesPaused`. The basket itself stays usable, so a shopper can keep pieces in it until the shop reopens.
- `CartAvailabilityBanner` renders an `role="alert"` strip with `pages.cart.availability.banner` when lines are unavailable. Above it, `SalesPausedBanner` renders a `role="status"` strip with `pages.cart.salesPaused.banner` on every storefront page while sales are paused. See [Checkout: Pausing sales](/docs/features/checkout#pausing-sales).
- `/checkout` redirects back to `/cart` when the hydrated basket is empty or has stock issues. See [Checkout](/docs/features/checkout).

## Abandonment tracking

`src/presentation/components/custom/customer-activity-tracker.tsx` watches the store. For a signed-in visitor, when `document.visibilityState` becomes `hidden` and the basket is not empty, it calls `trackCartAbandoned({ itemCount, lineCount })` once per session (guarded by the `sessionStorage` key `customer-activity:cart-abandoned-sent`). Emptying the basket clears that flag through `resetCartAbandonedTracking()`.

## The unused tables

`cart` and `cart_item` exist in `src/modules/cart/cart.schema.ts` and `src/modules/cart-item/cart-item.schema.ts`, with `discount_id`, `expires_at`, `session_id` and `user_id` columns and the usual indexes, and they are exported from `src/integrations/drizzle-orm/drizzle.schemas.ts`. Nothing reads or writes them. They are the schema for a server-side cart that has not been built; `checkout.cart_id` references `cart.id` but is never populated.
