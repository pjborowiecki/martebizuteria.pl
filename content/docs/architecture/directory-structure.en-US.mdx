## Placement rules

- **Files and folders use kebab-case.** Tests live in a sibling `__test__` folder and are named `*.test.ts`, `*.integration.test.ts` or `*.component.test.tsx`.
- **Routes only compose.** A route file defines the page or layout component, its `staticData.namespaces`, its `beforeLoad` guard, its `loader` and its `head`. Widgets, dialogs, forms and column definitions live in `src/presentation/components/custom`. `account.addresses.tsx` and `account.overview.tsx` are the exceptions: they define their address form and cards, and their overview sections, in the route file.
- **A module is a table.** A folder in `src/modules` exists only for a database table of the same name, so `src/modules` holds 40 table modules plus `_core`, which keeps the shared helpers that serve several tables. Each table module owns a Drizzle schema file, usually with one table; `discount` also declares `discount_redemption` and `discount_claim`, and `order` declares `order_number_sequence`. `storefront-search` declares only the FTS5 `storefront_search` index, which a hand-written migration creates. A use case goes to the module of the table it reads or writes: the customer's orders and the admin dashboard are in `order`, the signed-in devices in `session`, the sign-in history in `audit-log`, and the profile and the browsing activity in `user`.
- **`_core` is the shared kernel.** `AppError` and `ERROR_CODES`, the pagination helpers, the reusable Zod fields, the currency formatters and the column-filter builders live there. `_core/constants/timezone.ts` supplies `TIMEZONES`, the IANA zone list that the time-zone field in `custom/display-preferences/` offers, and `DEFAULT_TIMEZONE_CODE`, the shop's own zone (`Europe/Warsaw`). `allocate-order-number.server.ts` takes the order-number year in that zone, `_core/utils/polish-deadline.ts` counts the withdrawal period in it, and `resolveTimezoneCode` falls back to it for a value that names no zone in `TIMEZONES`; the first two read the Polish date through `toCalendarDate` in `_core/utils/datetime.ts`. The admin dashboard counts its days, months and year in the viewer's resolved display time zone instead. `_core/constants/country.ts` is an ISO reference table kept deliberately for planned work — outside its tests only `timezone.ts` imports it, for the `CountryCode` type alone, and it must not be deleted as dead code.
- **`src/data` holds data, not logic.** `landing.ts` and `static-pages.ts` feed real pages, and `blog-posts.ts` lists the blog's articles, none yet, which keeps the blog hidden.
- **`src/lib` holds small request-scoped helpers**, not features: `background.ts` (the `waitUntil` store), `cookie.ts`, `image.ts`, `incident-alert.server.ts` (`sendIncidentAlert`, which emails the shop once per incident), `rate-limit.ts`, `request.ts` (the client address, and `resolveRequestOrigin` and `resolveDeploymentOrigin`, the validated origins every email link and Stripe return URL are built from), `retention.ts` (the daily clean-up the `scheduled` handler runs), `security-headers.ts` (the per-request Content-Security-Policy nonce and the headers every Worker response gets), `seo.ts`, `server-timing.ts` (the `Server-Timing` header of a page load and the D1 time it adds up), `storefront-read.ts` (`readThroughStorefrontCache`, which marks a storefront server function's reads as cacheable), `storefront-cache.server.ts` (the storefront read cache behind the D1 binding), `sitemap.ts` (the pages `/sitemap.xml` lists, read from D1) and `url.ts`. `deployment.ts` is the exception: `verifyDeployment`, the live-site check that `scripts/verify-deployment.ts` runs after a deploy, which no request ever calls.
- **Generated files are never edited by hand.** The router plugin writes `src/routeTree.gen.ts`, `bun run cf-typegen` (part of `bun run typegen`) writes `src/types/worker-configuration.d.ts` (gitignored), and `bun run content` writes `.source/`, which `tsconfig.json` maps to the `collections/*` import prefix.

## Content and messages live outside `src`

`content/docs` holds these pages, one file per locale, and every folder lists its pages in order in `meta.<locale>.json`. The terms of service, the privacy policy, the exchanges-and-returns page, the FAQ and the About page are not files: their Markdown lives in the D1 `content_page` table, seeded by `src/integrations/drizzle-orm/migrations/20261002120000_content_pages.sql`, `20261005200000_terms_of_service_page.sql`, `20261010232000_faq_page.sql` and `20261018100000_about_page.sql`, rewritten for the returns page by `20261005210000_returns_and_complaints_page.sql`, for the returns page and the terms of service by `20261010231000_withdrawal_function_links.sql` (links to the withdrawal form at `/withdraw-from-contract`) and for the privacy policy by `20261010200000_privacy_policy_page.sql`, `20261010210000_privacy_policy_account_deletion.sql` and `20261012100000_privacy_policy_without_bot_check.sql`, and edited at `/admin/content`. `20261016161000_seller_placeholders.sql` put store detail placeholders in place of the seller's details in the first four. The withdrawal and complaint forms those pages link are PDFs the Worker makes from `src/presentation/pdf`. `messages/{en-US,pl-PL}` holds 60 namespace files each.
