## Placement rules

- **Files and folders use kebab-case.** Tests live in a sibling `__test__` folder and are named `*.test.ts`, `*.integration.test.ts` or `*.component.test.tsx`.
- **Routes only compose.** A route file defines the page or layout component, its `staticData.namespaces`, its `beforeLoad` guard, its `loader` and its `head`. Widgets, dialogs, forms and column definitions live in `src/presentation/components/custom`.
- **A module is a feature, not strictly a table.** Most of the 43 modules own one Drizzle table, but `admin-dashboard`, `customer-account` and `customer-activity` own read models that span several tables and have no schema file of their own. `storefront-search` declares only the FTS5 `storefront_search` index, which a hand-written migration creates.
- **`_core` is the shared kernel.** `AppError` and `ERROR_CODES`, the pagination helpers, the reusable Zod fields, the currency formatters and the column-filter builders live there. `_core/constants/timezone.ts` supplies `TIMEZONES`, the time-zone list customers pick from, and `DEFAULT_TIMEZONE_CODE`, the shop's own zone (`Europe/Warsaw`) that order numbers and the admin dashboard count years, months and days in, and that `_core/utils/polish-deadline.ts` counts the withdrawal period in; all of them read the Polish date through `toCalendarDate` in `_core/utils/datetime.ts`. `_core/constants/country.ts` is an ISO reference table kept deliberately for planned work — it has no importers and must not be deleted as dead code.
- **`src/data` holds data, not logic.** `landing.ts` and `static-pages.ts` feed real pages, and `blog-posts.ts` lists the blog's articles, none yet, which keeps the blog hidden; `settings.ts` holds the fixtures behind the admin settings page, which is still scaffolding.
- **`src/lib` holds small request-scoped helpers**, not features: `background.ts` (the `waitUntil` store), `cookie.ts`, `image.ts`, `incident-alert.server.ts` (`sendIncidentAlert`, which emails the shop once per incident), `rate-limit.ts`, `request.ts` (the client address, and `resolveRequestOrigin` and `resolveDeploymentOrigin`, the validated origins every email link and Stripe return URL are built from), `retention.ts` (the daily clean-up the `scheduled` handler runs), `security-headers.ts` (the per-request Content-Security-Policy nonce and the headers every Worker response gets), `seo.ts`, `sitemap.ts` (the pages `/sitemap.xml` lists, read from D1) and `url.ts`. `deployment.ts` is the exception: `verifyDeployment`, the live-site check that `scripts/verify-deployment.ts` runs after a deploy, which no request ever calls.
- **Generated files are never edited by hand.** The router plugin writes `src/routeTree.gen.ts`, `bun run cf-typegen` writes `src/types/worker-configuration.d.ts` (gitignored), and `bun run content` writes `.source/`, which `tsconfig.json` maps to the `collections/*` import prefix.

## Content and messages live outside `src`

`content/docs` holds these pages, one file per locale, and every folder lists its pages in order in `meta.<locale>.json`. The terms of service, the privacy policy, the exchanges-and-returns page and the FAQ are not files: their Markdown lives in the D1 `content_page` table, seeded by `src/integrations/drizzle-orm/migrations/20261002120000_content_pages.sql`, `20261005200000_terms_of_service_page.sql` and `20261010232000_faq_page.sql`, rewritten for the returns page by `20261005210000_returns_and_complaints_page.sql` and for the privacy policy by `20261010200000_privacy_policy_page.sql`, `20261010210000_privacy_policy_account_deletion.sql` and `20261012100000_privacy_policy_without_bot_check.sql`, and edited at `/admin/content`. The withdrawal and complaint forms those pages link are PDFs in `public/forms`. `messages/{en-US,pl-PL}` holds 56 namespace files each.
