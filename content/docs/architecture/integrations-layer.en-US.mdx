Every third party that needs setup owns one folder under `src/integrations`. Files are named `<prefix>.<concern>.ts`, where the prefix is the vendor's short name — `auth.*`, `drizzle.*`, `stripe.*`, `i18n.*`, `fumadocs.*`, `inpost.*`, `media.*`.

## What is not an integration

- **Cloudflare bindings need no adapter.** Server code reads `DB`, `IMAGES`, `CACHE`, `ASSETS`, `REALTIME_INVALIDATION_HUB` and `AUDIT_LOG_QUEUE` from `env` in `cloudflare:workers`.
- **Rate limiting** is `src/lib/rate-limit.ts`, backed by the `rate_limit` table, and is reached through the `withRateLimit` middleware rather than a vendor folder.
- **The Durable Object class** lives in `src/durable-objects/realtime-invalidation-hub.ts`, not in the integration folder, because Wrangler binds the class from the Worker entry.
- **SEO, sitemap and robots** are `src/lib/seo.ts`.

## Business logic stays in modules

An integration configures a vendor and hands the decision back:

- `src/routes/api/webhooks.stripe.ts` verifies the signature with `STRIPE_WEBHOOK_SECRET` and looks the event type up in `webhookHandlers`. An unknown type is logged and acknowledged with `{ received: true }`; a handler that throws returns 500 so Stripe retries.
- `stripe.webhooks.tsx` then calls the checkout and order use cases: `fulfillCheckout`, `releaseCheckout`, `refundOrder`, `flagOrderDispute`, `clearOrderDispute`. It owns none of that logic.
- `auth.server.ts` wires Better Auth's `databaseHooks` and its local `signInAudit` plugin to the audit recorders and `scheduleAdminCustomersInvalidation`, and its email callbacks to the templates in `src/presentation/emails`.
- The pattern for sending email is always: resolve the locale, load the template's namespace, render, send.

```ts
const locale = getCurrentLocale()
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
const failure = await sendEmail({
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verificationUrl }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
})
```

`sendEmail` returns a failure string rather than throwing, so the caller decides what a failed send means: an audit entry and an error for the person (`subscribeToNewsletter`), an audit entry on the order and, when an admin ships it, a warning toast (`recordOrderEmailAttempt`), or an audit entry plus a retryable `503` (`deliverAuthEmail` in `auth.server.ts`).

## Integration scope worth knowing

- **InPost is discovery only.** `fetchPointsByCity` reads the public points API; there is no shipment creation, no label generation and no API key. The checkout locker picker is built on top of it in `components/custom/checkout/components/_steps/delivery/locker/inpost`.
- **Stripe runs in Elements mode.** `stripe.checkout.sessions.create` is called with `ui_mode: "elements"` and a `return_url`, and the client secret is handed to `@stripe/react-stripe-js`. There is no redirect to Stripe-hosted Checkout.
- **R2 is served over a public bucket URL.** `VITE_R2_URL` (with `DEFAULT_R2_PUBLIC_URL` as the fallback in `branding/app.ts`) is resolved by `src/lib/url.ts`, and uploads are written with `Cache-Control: public, max-age=31536000, immutable`.
