## What is not an integration

- **Cloudflare bindings need no adapter.** Server code reads `DB`, `IMAGES`, `CACHE`, `ASSETS`, `REALTIME_INVALIDATION_HUB`, `AUDIT_LOG_QUEUE` and `NEWSLETTER_QUEUE` from `env` in `cloudflare:workers`.
- **Rate limiting** is `src/lib/rate-limit.ts`, backed by the `rate_limit` table, and is reached through the `withRateLimit` middleware rather than a vendor folder.
- **The Durable Object class** lives in `src/durable-objects/realtime-invalidation-hub.ts`, not in the integration folder, because Wrangler binds the class from the Worker entry.
- **SEO, sitemap and robots** are `src/lib/seo.ts`, with the sitemap's pages read from D1 by `src/lib/sitemap.ts`.

## Business logic stays in modules

An integration configures a vendor and hands the decision back:

- `src/routes/api/webhooks.stripe.ts` verifies the signature with `STRIPE_WEBHOOK_SECRET`, acknowledges an event from the other Stripe mode or from another deployment's test checkout without handling it, and looks the event type up in `webhookHandlers`. An unknown type is logged and acknowledged with `{ received: true }`; a handler that throws returns 500 so Stripe retries.
- `stripe.webhooks.ts` then calls the checkout and order use cases: `releaseCheckout`, `refundOrder`, `undoFailedRefund`, `lowerRefundedAmount`, `flagOrderDispute`, `clearOrderDispute`, and the e-mail use cases `sendOrderRefundedEmail` and `sendPaymentFailedEmail`. A paid session goes through `stripe.fulfillment.server.ts`, for the webhook and the checkout return page alike: `createOrderFromPaidSession` calls `fulfillCheckout`, and `announcePlacedOrder` calls `sendOrderConfirmationEmail` and `sendNewOrderEmail`. Neither file owns that logic.
- `auth.server.ts` takes Better Auth's request hook, `databaseHooks` and its password-reset, email-verified and account-deletion callbacks from `auth.hooks.server.ts`. The request hook, `guardAuthRequest`, refuses the email-sending endpoints while the sender is unavailable, a `/verify-email` link the address history has superseded (`auth.email-link.server.ts`), and Better Auth's `/admin/*` endpoints to an admin who still needs two-factor authentication. The after hook, `finishEmailChange` from `auth.email-change.server.ts`, completes a change of address with use cases of other modules: `followAccountAddressChange`, `deleteVerificationsOfUser`, `updateStripeCustomerEmail` and `sendEmailChangedEmail`. The callbacks call the audit recorders and `scheduleAdminCustomersInvalidation`, and use cases of other modules: `claimGuestOrdersForUser` and `linkSubscriberToUser` once an address is verified, `eraseAccountData` before a self-service deletion, `sendPasswordChangedEmail` after a password reset and `sendAccountDeletedEmail` after a self-service deletion. `auth.server.ts` also registers the `signInAudit` and `accountSecurityAudit` plugins from `auth.audit.server.ts` and passes the verification, reset-password and change-email senders of the verification and account modules, which render the templates in `src/presentation/emails`.
- The pattern for sending email is always: resolve the locale, load the template's namespace, render, send.

```ts
const locale = getCurrentLocale()
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
await requireAuthEmailDelivery("verification", {
  react: createElement(VerifyEmail, { locale, messages, name: user.name, verificationUrl }),
  subject: createTranslator({ locale, messages })("subject"),
  to: user.email,
  userId: user.id,
})
```

`sendEmail` returns a failure string rather than throwing, so the caller decides what a failed send means: an audit entry and an error for the person (`subscribeToNewsletter`), an audit entry on the order, two retries in the background and, when an admin ships it, a warning toast (`deliverOrderEmail`), or an audit entry plus a retryable `503` with `EMAIL_DELIVERY_FAILED` (`requireAuthEmailDelivery` in `auth.email-delivery.server.ts`, which the verification, reset-password and change-email senders use). `deliverAuthEmail` in the same file records the failure and returns `false` instead, for the password-changed and account-deleted emails.

## Integration scope worth knowing

- **InPost has a public half and a server half.** `fetchPointsByCity` reads the public points API without a key, `fetchPointByName` reads one point so the server can confirm the locker a checkout names, and the checkout locker picker is built on top of it in `components/custom/checkout/components/_steps/delivery/locker/inpost`. `inpost.shipx.server.ts` is the ShipX client the admin order page books shipments, downloads labels and reads statuses through; it needs `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID` and calls InPost's sandbox outside production. See [InPost](/docs/integrations/inpost).
- **Stripe runs in Elements mode.** `stripe.checkout.sessions.create` is called with `ui_mode: "elements"` and a `return_url`, and the client secret is handed to `@stripe/react-stripe-js`. There is no redirect to Stripe-hosted Checkout.
- **R2 is served over a public bucket URL.** `VITE_R2_URL` (with `DEFAULT_R2_PUBLIC_URL` as the fallback in `branding/app.ts`) is resolved by `src/lib/url.ts`, which also moves stored `r2.dev` URLs onto it, and `uploadImageFn` writes each upload once under a SHA-256 content key in the `products/`, `categories/` or `collections/` folder (`uploads/` for any other folder name), with `Cache-Control: public, max-age=31536000, immutable`, and stores it as a bare key. Nothing in the application deletes R2 objects: removing an image from a product, category or collection only drops the reference. The order confirmation email reads product images back with `embedEmailImages` and attaches them inline. On a custom domain, `src/lib/image.ts` resizes images there through Cloudflare Image Transformations.
