## Dwie warstwy, ale tylko jedna jest granicą

**Guardy tras** w `src/integrations/better-auth/auth.routes.ts` działają w `beforeLoad` i przekierowują. Każdy layout przekazuje sam guard, jak w `beforeLoad: requireAdmin`:

| Guard                | Używany przez                                     | Zachowanie                                                                                                   |
| -------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `requireSignedIn`    | Podstawa dla pozostałych                          | Bez sesji przekierowuje na `/auth/sign-in`                                                                   |
| `requireAdminRole`   | `admin_.security.tsx`                             | Wymaga dodatkowo `hasAdminAccess(role)`, inaczej `/account/overview`                                         |
| `requireAdmin`       | `admin.tsx`, `admin_.orders.$orderId.summary.tsx` | `requireAdminRole`, a potem wysyła administratora bez uwierzytelniania dwuskładnikowego na `/admin/security` |
| `requireCustomer`    | `account.tsx`                                     | Administratora wysyła zamiast tego na `/admin`                                                               |
| `redirectIfSignedIn` | `auth.tsx`                                        | Zalogowanego wysyła na bezpieczną ścieżkę z `?redirect`, inaczej na `postAuthRouteFor(user)`                 |

`requireSignedIn`, `requireAdminRole`, `requireAdmin` i `requireCustomer` zwracają `{ user }`, które staje się kontekstem trasy; `account.overview.tsx` czyta go przez `AccountRoute.useRouteContext()`. Guardy jedynie czytają sesję, przez `loadRouteSession`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

`requireSignedIn`, a przez nie także `requireAdminRole`, `requireAdmin` i `requireCustomer`, przekazuje `recheck: true`, więc nawigacja do `/account` lub `/admin` pobiera sesję ponownie. Wstępne ładowanie linku i `redirectIfSignedIn`, które przekazuje `recheck: false`, korzystają z sesji w cache'u młodszej niż 60 sekund. Sesja załadowana przez guard zostaje w cache'u TanStack Query, skąd czytają ją komponenty, a przy renderowaniu na serwerze jest serializowana do strony. Zmianę użytkownika obsługuje jedno miejsce, `clearCacheOnUserChange` w `auth.session.ts`: gdy sesja przełączy się na innego użytkownika, usuwa z cache'u wszystkie zapytania poza samą sesją i katalogami komunikatów tłumaczeń. Szczegóły opisuje strona [Cache i SSR](/docs/architecture/caching-and-ssr).

Anonimowy gość wchodzący na `/account` lub `/admin` trafia na `/auth/sign-in` z `?redirect=` ustawionym na `route.location.publicHref`, czyli zlokalizowaną publiczną ścieżkę, o którą prosił, na przykład `/en-US/account/orders/order-1`. Wewnętrzna dla modułu funkcja `resolveSafeRedirect` sprawdza tę wartość zarówno przy budowaniu linku do logowania, jak i zanim guard `/auth` za nią podąży. Zachowuje ją tylko wtedy, gdy jest napisem pasującym do `SAME_SITE_PATH_PATTERN`: wyłącznie drukowalne znaki ASCII, jeden ukośnik na początku i żadnego ukośnika wstecznego. Bezwzględne URL-e, wartości `//` względne wobec protokołu, białe znaki, znaki sterujące i znaki spoza ASCII są odrzucane, więc parametru nie da się zamienić w otwarte przekierowanie:

```ts
const SAME_SITE_PATH_PATTERN = /^\/(?![/\\])[!-[\]-~]*$/u
```

`redirectIfSignedIn` wysyła zalogowanego gościa pod tę wartość przez `redirect({ href })`, a w przeciwnym razie na `postAuthRouteFor(user)`: `/admin` dla administratora, `/account/overview` dla klienta. Przekierowanie wyrenderowane na serwerze zachowuje więc język gościa, a po stronie klienta router lokalizuje je ponownie do bieżącego języka.

Po udanym logowaniu hasłem lub udanym wyzwaniu dwuskładnikowym formularz woła `usePostAuthRedirect` z `src/hooks/use-post-auth-redirect.ts`:

```ts
export const usePostAuthRedirect = (): (() => Promise<void>) => {
  const queryClient = useQueryClient()
  const router = useRouter()

  return useCallback(async () => {
    queryClient.removeQueries({ exact: true, queryKey: getCurrentSessionQuery.queryKey })
    router.clearCache()
    await router.invalidate()
  }, [queryClient, router])
}
```

Hook usuwa wyłącznie wpis sesji z cache'u, a następnie czyści zapisane w routerze dopasowania i unieważnia router. Guard layoutu `/auth` uruchamia się ponownie, pobiera świeżą sesję i przekierowuje tak, jak opisano wyżej. Gdy świeża sesja dotrze, `clearCacheOnUserChange` zapomina to, co trafiło do cache'u przed zalogowaniem. Formularze nigdy same nie wybierają celu.

Logowanie przez Google, w `src/presentation/components/custom/pages/auth/hooks/use-oauth-sign-in.ts`, przekazuje jako `callbackURL` stronę, na której kliknięto przycisk: `location.publicHref` z `useLocation`, na przykład `/en-US/auth/sign-in?redirect=…`. Po powrocie od dostawcy przeglądarka trafia na tę stronę uwierzytelniania, a `redirectIfSignedIn` przekierowuje użytkownika dalej dokładnie tak, jak po logowaniu hasłem.

Wylogowanie to pełne przeładowanie strony, które porzuca cache: panel boczny konta prowadzi na `/`, a panel boczny administracyjny na `/auth/sign-in`.

Guardy decydują o tym, co użytkownik _widzi_. Działają również w przeglądarce, więc są elementem UX nawigacji, a nie zabezpieczeniem.

**Middleware funkcji serwerowych** w `auth.middleware.ts` jest prawdziwą granicą, bo funkcja serwerowa to publiczny endpoint HTTP osiągalny niezależnie od tego, czy jej strona została kiedykolwiek załadowana:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && (!hasPermission({ permission, role: session.user.role }) || needsTwoFactorSetup(session.user))) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

W `src/modules` i `src/integrations` `authorized()` występuje 96 razy: 25 razy bez argumentu (wystarcza sesja), a pozostałe z uprawnieniem — `product: ["read"]` ×14, `product: ["update"]` ×10, `product: ["create"]` ×4, `product: ["delete"]` ×4, `settings: ["manage"]` ×6, `order: ["read"]` ×7, `order: ["update"]` ×11, `order: ["update", "refund"]` ×1 (`refundAdminOrder`), `content: ["read"]` ×3, `content: ["update"]` ×3 oraz statementy administracyjne Better Auth `user: ["list" | "get" | "update" | "delete"]`.

## Role i uprawnienia

`auth.access.ts` buduje kontrolę dostępu na `createAccessControl` z Better Auth:

- **Role**: `admin` i `customer`; `DEFAULT_ROLE` to `customer`, a `ADMIN_PANEL_ROLES` to `["admin"]`.
- **Zasoby i akcje**: `order: [read, update, refund]`, `product: [create, read, update, delete, publish]`, `settings: [manage]`, plus własne `defaultStatements` Better Auth dla `user` i `session`.
- **`ROLES_CONFIG`** przyznaje roli admin wszystkie statementy oraz `adminAc.statements`; rola customer nie otrzymuje żadnego.
- **`hasAdminAccess(role)`** to zgrubne sprawdzenie używane przez guardy tras i handshake WebSocketu; `hasPermission({ permission, role })` to sprawdzenie drobnoziarniste używane przez `authorized()`.
- **`needsTwoFactorSetup({ role, twoFactorEnabled })`** jest prawdziwe dla administratora bez uwierzytelniania dwuskładnikowego. `requireAdmin` wysyła go na `/admin/security`, `authorized()` odmawia mu każdego uprawnienia, handshake administracyjnego WebSocketu odpowiada `401`, a `hooks.before` odrzuca punkty końcowe `/admin/*` Better Auth z kodem `ADMIN_TWO_FACTOR_REQUIRED`. Administratorzy logują się wyłącznie hasłem i kodem: `session.create.before` odrzuca administratorowi logowanie przez Google, bo wtyczka `twoFactor` na tej ścieżce nigdy nie prosi o kod. Zobacz [Better Auth](/docs/integrations/better-auth#uwierzytelnianie-dwuskładnikowe-administratorów).

Ponieważ rola customer nie ma żadnych statementów, macierz zasobów zachowuje się dziś jak binarne sprawdzenie „czy admin”. Warto o tym pamiętać przed dodaniem trzeciej roli: macierz już istnieje, a pieniądze mają już własną akcję, bo `refundAdminOrder` i `cancelOrder` dla opłaconego zamówienia żądają `order: ["refund"]` oprócz `order: ["update"]`, więc rola z samym `order: ["read", "update"]` mogłaby obsługiwać zamówienia bez zwracania pieniędzy.

## Własność jest wkompilowana w SQL

Odczyty i zapisy po stronie klienta nigdy nie ufają identyfikatorowi z wejścia. Filtrują po `context.auth.user.id` wewnątrz zapytania:

```ts
where: and(eq(order.id, orderId), eq(order.userId, context.auth.user.id)),
```

Ten sam wzorzec występuje w `list-customer-orders.ts`, `list-customer-sessions.ts`, `list-customer-login-history.ts`, `get-customer-overview.ts`, `revoke-customer-session.ts`, `revoke-other-customer-sessions.ts`, `update-customer-phone.ts`, `get-customer-order-withdrawal.ts`, `withdraw-from-customer-order.ts` i we wszystkich pięciu przypadkach użycia adresów. Obcy identyfikator nie zwraca żadnego wiersza, więc nie ma czego filtrować później ani czego wyciekać. Publiczny formularz odstąpienia, `withdraw-from-guest-order.ts`, znajduje zamówienie tylko po jego numerze razem z adresem e-mail, z którego je złożono, niczego nie zwraca bez względu na to, czy je znalazł, i nigdy nie zwraca zawartości zamówienia.

`revoke-customer-session.ts` odmawia dodatkowo unieważnienia własnej sesji wywołującego, a `delete-customer.ts` odmawia usunięcia działającego administratora.

## Sesje

- Better Auth przechowuje sesje w D1 przez `drizzleAdapter(db, { provider: "sqlite", schema })`, z `storeSessionInDatabase: true` i **bez `secondaryStorage`** — KV zostało odrzucone dla sesji, tokenów weryfikacyjnych i liczników limitów, bo jest spójne ostatecznie i nie umie atomowo skonsumować-i-zwiększyć wartości.
- `useSecureCookies` jest włączone poza `development` i `test` (`isLocalMode(import.meta.env.MODE)`).
- Dozwolone hosty są ustalone dla każdego trybu builda przez `appHostsForMode` w `_core/constants/api.ts`: `martebizuteria.pl` na produkcji, `preview.martebizuteria.pl` na preview, `localhost:3000` i `127.0.0.1:3000` lokalnie, plus odpowiadające im hosty `workers.dev`.
- Ta sama lista decyduje o każdym bezwzględnym linku, który aplikacja buduje sama. `resolveRequestOrigin(request)` w `src/lib/request.ts` bierze origin wyłącznie z `request.url`, nigdy z nagłówków `Host`, `Origin`, `Referer` ani `X-Forwarded-*`, i rzuca `AppError(FORBIDDEN)`, chyba że host z portem jest na liście `appHostsForMode(import.meta.env.MODE)`, a protokół to `https:` (albo `http:` na `localhost:3000` i `127.0.0.1:3000`). E-maile o newsletterze, wysyłce i pożegnaniu oraz `return_url` Stripe są budowane z tego originu, więc prowadzą pod adres, którego użyto, a podrobiony lub nieznany host jest odrzucany, zamiast trafić do linku. Potwierdzenie zamówienia wysyła webhook Stripe, więc bierze ono origin z `return_url` sesji, który zapisał checkout i który przychodzi w zdarzeniu ze sprawdzonym podpisem. `resolveDeploymentOrigin` akceptuje ten origin tylko na hoście obsługiwanym przez któreś wdrożenie (`isDeploymentHost`), bo development i preview dzielą testowe konto Stripe i bazę danych, a każdy inny odrzuca. `APP_URL` zostaje dla kanonicznego adresu produkcyjnego w metadanych SEO.
- `getRequestSession` omija cache cookie (`disableCookieCache: true`) i memoizuje wynik w `WeakMap` kluczowanej obiektem `Request`.
- `getCurrentSession`, funkcja serwerowa stojąca za `getCurrentSessionQuery`, rzutuje sesję przed zwróceniem, usuwając `session.token`:

  ```ts
  const toClientSession = ({ session: { token: _token, ...session }, user }: RequestSession) => ({ session, user })
  ```

- `tanstackStartCookies()` jest ostatnim pluginem na liście, więc cookies ustawione w trakcie funkcji serwerowej trafiają do odpowiedzi.
- `multiSession({ maximumSessions: 5 })` ogranicza liczbę równoległych sesji; `verification: { storeIdentifier: "hashed" }` oznacza, że identyfikatory weryfikacyjne są hashowane; `account.encryptOAuthTokens` szyfruje tokeny OAuth.
- Weryfikacja e-maila jest wymagana przed logowaniem (`requireEmailVerification: true`, `sendOnSignUp: true`, `autoSignInAfterVerification: true`), a `resolveEmailVerificationCallbackUrl` przepisuje callback prowadzący na stronę główną sklepu na `/account/overview?verified=true`, żeby zweryfikowany użytkownik trafił w sensowne miejsce.
- Zakończony reset hasła wylogowuje konto na wszystkich urządzeniach (`revokeSessionsOnPasswordReset: true`), więc sesja otwarta przed resetem, także sesja intruza, jest odrzucana od następnego żądania. `onPasswordReset` wysyła klientowi e-mail o zmianie hasła z radą dla kogoś, kto go nie zmieniał. Zobacz [Better Auth](/docs/integrations/better-auth#reset-hasła).
- Rejestracja, zmiana hasła i zmiana adresu zachowują ogólną odpowiedź, gdy Resend odrzuci ich e-mail, bo Better Auth wysyła go tylko wtedy, gdy konto istnieje albo nie istnieje. Z tego samego powodu takie odmowy nigdy nie ustawiają flagi nadawcy: mogą ją ustawić tylko e-maile wysyłane dla dowolnego adresu (newsletter, zamówienia, usunięcie konta) albo tylko do tego, kto właśnie użył linku do resetu hasła konta (zmiana hasła), a dopóki jest ustawiona, blokada w `hooks.before` odrzuca cztery punkty końcowe wysyłające e-maile jednakowo dla każdego adresu. Wyjątkiem jest wywołanie `/send-verification-email` bez zalogowania, gdzie Better Auth przekazuje dalej błąd hooka: gdy pojedyncze wysyłki zawodzą, niepotwierdzone konto dostaje `503 EMAIL_DELIVERY_FAILED`, a każdy inny adres `200`. Zdradza to tylko niepotwierdzone konta, tylko w czasie awarii wysyłki, przy trzech żądaniach na minutę z jednego IP. Zobacz [Better Auth](/docs/integrations/better-auth#blokada-wysyłki-e-maili).

## Limity żądań

Dwa limitery dzielą tabelę `rate_limit` i funkcję liczącą `withinRateLimit` z `src/lib/rate-limit.ts`.

**Własny limiter Better Auth**, skonfigurowany w `auth.server.ts` z `customStorage: authRateLimitStorage`, domyślnym limitem 100 żądań na okno 60 s i regułami szczegółowymi z `RATE_LIMIT_CUSTOM_RULES` w `auth.constants.ts`:

| Trasa                     | Maksymalnie na minutę |
| ------------------------- | --------------------- |
| `/sign-in/email`          | 5                     |
| `/sign-up/email`          | 3                     |
| `/request-password-reset` | 3                     |
| `/reset-password`         | 5                     |

`authRateLimitStorage` liczy każdy klucz `<ip>|<ścieżka>` według jego reguły przez `withinRateLimit` i odmawia z oknem reguły jako `X-Retry-After`. Better Auth nie używa `storage: "database"`: za każdym razem, gdy któryś z jego liczników zaczynał nowe okno, ta opcja usuwała każdy wiersz `rate_limit`, którego `last_request` był starszy niż 60 sekund, a wraz z nimi liczniki limitów e-maili opisanych niżej, minutę po ich starcie.

**Limiter aplikacji**, `withRateLimit(kind, limit)` albo, w handlerze, który liczy tylko część swoich wywołań, `assertWithinRateLimit(kind, limit, requestHeaders)`, oba nad `withinRateLimit` z `src/lib/rate-limit.ts`. `RATE_LIMITS` definiuje `SENSITIVE` (3/60 s), `TOKEN` (5/60 s), `CHECKOUT` (10/60 s) i `BROWSING` (120/60 s), a licznik to jeden atomowy upsert w D1:

```ts
.onConflictDoUpdate({
  set: {
    count: sql`case when ${rateLimit.lastRequest} <= ${windowStart} then 1 else ${rateLimit.count} + 1 end`,
    lastRequest: sql`case when ${rateLimit.lastRequest} <= ${windowStart} then ${now} else ${rateLimit.lastRequest} end`,
  },
  setWhere: sql`${rateLimit.lastRequest} <= ${windowStart} or ${rateLimit.count} < ${limit}`,
  target: rateLimit.key,
})
```

Kluczem jest `${kind}:${clientAddress(headers)}`, a `clientAddress` czyta **wyłącznie** `cf-connecting-ip`, którego klient nie może podrobić. Jeśli magazyn licznika zawiedzie, żądanie jest odrzucane, a nie dopuszczane. Obecnie stosowane do `checkout-create`, `checkout-update`, `checkout-status`, `discount-validate`, `create-user-address`, `update-customer-phone`, `revoke-other-customer-sessions`, `search-storefront`, `search-storefront-products` (tylko listingi katalogu z parametrem `q`), `record-customer-activity`, `withdraw-from-customer-order` i `withdraw-from-guest-order`. Limity są per IP; nie ma blokady per konto.

Zwróć uwagę, że `resolveRequestIp` w `src/lib/request.ts` — używane dla _dziennika audytu_ i dla podpowiedzi `remoteip`, którą kasa wysyła do siteverify Turnstile — sięga w drugiej kolejności do `x-forwarded-for`, który klient może podrobić. Limitowania żądań to nie dotyczy, bo nie korzysta z tego helpera, a limit otwartych checkoutów także wyznacza adres przez `clientAddress`; na Cloudflare `cf-connecting-ip` jest zawsze obecny, więc podpowiedź nigdy nie pochodzi tam z `x-forwarded-for`.

### Rezerwacje kasy

Nowy checkout rezerwuje towar nawet na 32 minuty, a każdy może go zacząć bez konta, więc sam limit żądań pozwoliłby jednemu skryptowi trzymać zarezerwowany katalog. Dlatego `handleCreateCheckoutSession` wymaga też tokenu Turnstile, który siteverify potwierdzi dla akcji `checkout` na hoście żądania, i odrzuca adres klienta, który ma już pięć otwartych checkoutów, albo e-mail, który ma ich trzy; liczenie otwartych checkoutów wyznacza adres tym samym `clientAddress`. Schemat funkcji serwerowej ogranicza każdą linię do dziesięciu sztuk jednego produktu. Aktualizacja otwartego checkoutu nie wymaga ani tokenu, ani liczenia, ale każda odnawia rezerwację sesją zastępczą, więc `handleUpdateCheckoutSession` odmawia z `SESSION_CLOSED`, gdy od otwarcia checkoutu minęło `CHECKOUT_SESSION_LIFETIME_SECONDS`, po wygaszeniu jego sesji i oddaniu jej towaru; dłuższe trzymanie towaru wymaga nowego checkoutu i nowego tokenu. Zobacz [Kasa: limity trzymania towaru](/docs/features/checkout#limity-trzymania-towaru) i [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile).

### E-maile, o które może poprosić każdy

Rejestracja, prośba o zmianę hasła, ponowne wysłanie weryfikacji i zapis do newslettera wysyłają e-mail na dowolny podany adres, więc same limity na IP pozwoliłyby skryptowi rozłożonemu na wiele adresów zalać czyjąś skrzynkę albo zużyć limit Resend, a razem z nim zatrzymać e-maile o zamówieniach. Dlatego każde z tych żądań wymaga tokenu Turnstile dla własnej akcji (`sign-up`, `password-reset`, `verification-resend`, `newsletter`): `hooks.before` Better Auth sprawdza nagłówek `x-turnstile-token` trzech punktów końcowych uwierzytelniania i odpowiada `403 BOT_CHECK_FAILED`, a `subscribeToNewsletter` wywołuje `verifyTurnstileToken`. Za sprawdzeniem `admitPublicEmail` pozwala na trzy e-maile jednego rodzaju na jeden adres na godzinę i 50 takich e-maili na dobę dla całego sklepu, liczone w `rate_limit` pod skrótem SHA-256 adresu. Na pominięty e-mail odpowiedź jest dokładnie taka jak na wysłany, bo link do zmiany hasła i ponowna weryfikacja wychodzą tylko dla niektórych adresów, a inna odpowiedź zdradzałaby, dla których; limit dzienny zapisuje też `email.failed` dla właściciela. Tak samo traktowane jest odstąpienie od umowy z użyciem numeru zamówienia na `/withdraw-from-contract`: `withdrawFromGuestOrder` wymaga tokenu dla `withdrawal`, wysyła potwierdzenie i powiadomienie sklepu tylko wtedy, gdy `admitPublicEmail` dopuści e-mail rodzaju `withdrawal` na adres zamówienia, i na każde oświadczenie odpowiada tak samo, więc odwiedzający nie dowie się, czy numer zamówienia i adres pasują do zamówienia ani czy od tego zamówienia można jeszcze odstąpić. E-maile, które sklep wysyła sam, o zamówieniach, zwrotach i kontach, nigdy nie przechodzą przez te limity. Zobacz [Better Auth: sprawdzenie antybotowe i limity e-maili](/docs/integrations/better-auth#sprawdzenie-antybotowe-i-limity-e-maili) i [Resend: e-maile, o które może poprosić odwiedzający](/docs/integrations/resend#e-maile-o-które-może-poprosić-odwiedzający).

## Autoryzacja WebSocketu

`fetch` Durable Objectu nie ma własnego kontekstu cookie ani sesji, dlatego hub administracyjny jest sprawdzany w Workerze **przed** zaadresowaniem obiektu: `assertAdminWebSocket` odpowiada `401`, chyba że sesja należy do administratora z włączonym uwierzytelnianiem dwuskładnikowym.

```ts
if (hubName === REALTIME_INVALIDATION_HUB.ADMIN) {
  const unauthorized = await assertAdminWebSocket(request)
  if (unauthorized !== undefined) {
    return unauthorized
  }
}

const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)

return hub.fetch(request)
```

Sprawdzanie po `getByName()` pozwoliłoby już nieuwierzytelnionemu klientowi otworzyć obiekt. Hub sklepu jest publiczny — rozgłasza wyłącznie klucze zapytań katalogu, nigdy dane.

## Webhooki

`POST /api/webhooks/stripe` wymaga nagłówka `stripe-signature` i weryfikuje go sekretem `env.STRIPE_WEBHOOK_SECRET` przez `stripe.webhooks.constructEventAsync`, zanim uruchomi jakikolwiek handler. Ciała, którego nie da się zweryfikować, kończą się kodem `400` i niczego nie dotykają. Zweryfikowane zdarzenie z drugiego trybu Stripe, testowe w `production` albo live w każdym innym środowisku, jest logowane i potwierdzane kodem `200`, zanim uruchomi się jakikolwiek handler, więc także niczego nie zmienia.

`POST /api/webhooks/inpost` nie da się zweryfikować w ten sam sposób, bo InPost nie podpisuje webhooków ShipX, więc trasa nie ufa żadnemu wywołaniu: przyjmuje tylko zdarzenie wskazujące `INPOST_ORGANIZATION_ID` sklepu i przesyłkę, którą ma któreś zamówienie, a potem odczytuje tę przesyłkę z ShipX tokenem sklepu, zanim cokolwiek zapisze. Podrobione wywołanie może sprawić, że sklep ponownie odczyta jedną ze swoich przesyłek, i nic więcej. Wszystko inne kończy się kodem `400`, a adres, który wyśle więcej niż `INPOST_WEBHOOK_RATE_LIMIT` (120) wywołań na minutę, dostaje `429` przed odczytaniem treści.

## Sprawdzenie stanu

`GET /api/health` jest publiczne i nie wymaga sesji, więc może je wywoływać monitor dostępności. Nie czyta żadnych danych — `SELECT 1`, odczyt KV i `head` w R2 dla klucza, który nie istnieje — i odpowiada tylko `ok` albo `error` dla każdego bindingu, nigdy błędem, nazwą bindingu ani konfiguracją. Błędy trafiają do logu Workera. Zobacz [Monitorowanie i alerty](/docs/guides/monitoring-and-alerts#sprawdzenie-stanu).

`POST /api/newsletter/unsubscribe` to wypisanie jednym kliknięciem, które dostawcy poczty wysyłają dla nagłówka `List-Unsubscribe` newslettera. Nie wymaga sesji ani podpisu: jedynym poświadczeniem jest `token` subskrybenta, losowy UUID w adresie, który może wypisać tylko ten adres. Nie ma też limitu żądań, bo odgadnięcie tokenu nie ma realnej szansy, a jeden dostawca poczty wysyła żądania wielu subskrybentów z tego samego adresu. Błędny token to `400`, a nieznany `404`, w obu przypadkach bez zapisu.

## Błędy

`withRequest` instaluje jeden normalizator dla każdej funkcji serwerowej:

| Rzucone                | Dociera do klienta jako                           |
| ---------------------- | ------------------------------------------------- |
| `notFound()` TanStack  | Bez zmian, więc trasa odpowiada kodem 404         |
| `AppError`             | Własny kod oraz kod przyczyny                     |
| `APIError` Better Auth | `AUTH_API_ERROR` plus klucz tłumaczenia           |
| `ZodError`             | `VALIDATION`                                      |
| Cokolwiek innego       | `INTERNAL_ERROR`, oryginał zalogowany na serwerze |

`ERROR_CODES` w `src/modules/_core/constants/errors.ts` zawiera osiem kodów, a `useActionError()` mapuje kod na `errors.action.<CODE>`. Wewnętrzne wiadomości, ślady stosu i SQL nigdy nie docierają do przeglądarki.

## Nagłówki odpowiedzi

`src/server.ts` przepuszcza każdą odpowiedź, której udziela, przez `withSecurityHeaders` z `src/lib/security-headers.ts`: strony, funkcje serwerowe, handlery uwierzytelniania i webhooków, przekierowania, `/sitemap.xml` i `/robots.txt`. Tylko dwa przejścia na WebSocket wracają nietknięte, bo odpowiedzi `101` nie da się skopiować.

| Nagłówek                    | Wartość                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `Content-Security-Policy`   | Budowany dla każdej odpowiedzi, opis niżej                                                                               |
| `X-Frame-Options`           | `DENY`, ta sama reguła co `frame-ancestors 'none'` dla przeglądarek, które jej nie znają                                 |
| `X-Content-Type-Options`    | `nosniff`                                                                                                                |
| `Referrer-Policy`           | `strict-origin-when-cross-origin`                                                                                        |
| `Permissions-Policy`        | `camera=(), geolocation=(), microphone=()`                                                                               |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains`, tylko gdy `APP_ENV` to `preview` lub `production`, a żądanie przyszło przez HTTPS |

Polityka dopuszcza to, co sklep ładuje, i nic więcej:

| Dyrektywa                    | Źródła                                                                                                                                                                                                              | Kto z nich korzysta                                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `script-src`                 | `'self'`, `'nonce-…'`, `https://js.stripe.com`, `https://*.js.stripe.com`, `https://challenges.cloudflare.com`                                                                                                      | Bundle aplikacji, skrypty inline tej odpowiedzi, Stripe.js, Turnstile                                                                         |
| `style-src`                  | `'self'`, `'unsafe-inline'`                                                                                                                                                                                         | Arkusze stylów i style inline opisane niżej                                                                                                   |
| `img-src`                    | `'self'`, `data:`, `blob:`, hosty obrazów                                                                                                                                                                           | Zdjęcia katalogu; `data:` dla ikon SVG w arkuszu MapLibre, `blob:` dla podglądu uploadu w panelu                                              |
| `media-src`                  | `'self'`, hosty obrazów                                                                                                                                                                                             | Wideo na stronie głównej                                                                                                                      |
| `connect-src`                | `'self'`, `https://api.stripe.com`, `https://fonts.googleapis.com`, `https://challenges.cloudflare.com`, `https://api-pl-points.easypack24.net`, `https://basemaps.cartocdn.com`, `https://*.basemaps.cartocdn.com` | Funkcje serwerowe i gniazda realtime, API Stripe, arkusz fontu czytany przez Stripe Elements, Turnstile, API punktów InPost, mapa paczkomatów |
| `frame-src`                  | `https://js.stripe.com`, `https://*.js.stripe.com`, `https://hooks.stripe.com`, `https://challenges.cloudflare.com`                                                                                                 | Payment Element, 3-D Secure, wyzwanie Turnstile                                                                                               |
| `font-src`, `worker-src`     | `'self'`                                                                                                                                                                                                            | Własne fonty, worker MapLibre                                                                                                                 |
| `default-src`, `form-action` | `'self'`                                                                                                                                                                                                            | Wszystko, czego nie wymieniono, i wysyłka formularzy                                                                                          |
| `object-src`, `base-uri`     | `'none'`                                                                                                                                                                                                            | Nic                                                                                                                                           |
| `frame-ancestors`            | `'none'`                                                                                                                                                                                                            | Żadna strona nie może osadzić sklepu w ramce                                                                                                  |

Hosty obrazów to originy `DEFAULT_R2_PUBLIC_URL` i `getAssetCdnBase()`, więc nowy `VITE_R2_URL` przesuwa politykę razem ze sobą: produkcyjny `https://images.martebizuteria.pl` i adres `r2.dev` bucketu preview są wpisane jako całe originy, co obejmuje zmniejszone zdjęcia pod `/cdn-cgi/image/` i oryginalny obiekt, do którego wraca `onerror=redirect`. `src/lib/__test__/security-headers.image-hosts.test.ts` sprawdza zdjęcia, o które prosi sklep, względem polityki każdego środowiska; zobacz [Dostarczanie zdjęć](/docs/guides/image-delivery). Turnstile to zabezpieczenie antybotowe kasy: krok płatności ładuje jego skrypt i ramkę wyzwania z `TURNSTILE_ORIGIN` w `src/integrations/cloudflare-turnstile/turnstile.constants.ts`, które polityka importuje. Skrypt wstawia `issueTurnstileToken` bez nonce'a i wykonuje się, bo jego host jest wymieniony w `script-src`.

**Nonce.** `createContentSecurityPolicyNonce` losuje 16 bajtów dla każdego żądania. `src/server.ts` przekazuje nonce do TanStack Start jako `RequestContext.nonce`, `getRouter` odczytuje go przez `getGlobalStartContext()` do `ssr.nonce`, a Start nadaje go swoim skryptom hydratacji, tagom renderowanym przez `<HeadContent />` i `<Scripts />` oraz znacznikowi `<meta property="csp-nonce">`, który router w przeglądarce czyta przy hydratacji. `RootDocument` dodaje go do skryptów inicjujących motyw, panel boczny i siatkę danych przez `useRouter().options.ssr?.nonce`. Skrypt inline wstrzyknięty w stronę nie ma nonce'a, więc się nie wykona.

**Style inline.** `style-src` dopuszcza `'unsafe-inline'`. React renderuje atrybuty `style` do HTML-a z serwera, a Sonner, provider motywu, MapLibre i Stripe.js wstawiają w trakcie działania elementy `<style>` bez nonce'a. Źródło nonce w `style-src` wyłącza `'unsafe-inline'` i zablokowałoby je wszystkie. Styl nie uruchomi skryptu, a skrypty nadal wymagają nonce'a.

**Sonda eval w Zod.** Zod 4 raz na stronę wywołuje `new Function("")`, żeby zdecydować, czy kompilować parsery obiektów. Polityka nie ma `'unsafe-eval'`, więc przeglądarka odmawia wywołania i zgłasza jedno naruszenie `script-src` dla `eval`; Zod łapie odmowę i parsuje bez kompilacji, tak jak już robi to na Workers. Ustawienie `jitless` w Zod pomija sondę, ale trzeba je ustawić, zanim wykona się pierwszy moduł ze schematem, a bundle klienta wykonuje chunki tras przed każdym modułem, w którym aplikacja mogłaby je ustawić.

**Pliki statyczne.** Pliki z `public/` obsługuje warstwa zasobów i nigdy nie trafiają do Workera. `public/_headers` nadaje każdemu z nich `X-Content-Type-Options: nosniff` i `Referrer-Policy: strict-origin-when-cross-origin`. HSTS zostaje przy odpowiedziach Workera, bo przeglądarka stosuje go do całego hosta.

`security-headers.test.ts` sprawdza każdy nagłówek i każdą dyrektywę, `server.test.ts` sprawdza, że każda odpowiedź Workera je niesie razem z nonce'em przekazanym aplikacji, a `e2e/specs/smoke.spec.ts` otwiera w przeglądarce stronę główną, produkt, logowanie i dokumentację i kończy się błędem, jeśli się nie zhydratują albo przeglądarka odmówi czegokolwiek poza sondą Zod.

## Indeksowanie i ekspozycja

`isNoIndexPathname` w `src/lib/seo.ts` oznacza `/account`, `/admin` i `/checkout` (wraz z poddrzewami) jako `noindex, nofollow`, a `__root.tsx` emituje dodatkowo meta noindex na każdym buildzie nieprodukcyjnym. `generateRobotsTxt` zwraca całkowite `Disallow: /`, o ile `APP_ENV` nie jest równe `production`, a na produkcji blokuje `/api/`, `/admin`, `/account` i `/checkout`.
