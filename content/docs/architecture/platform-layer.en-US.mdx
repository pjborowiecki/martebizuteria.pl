## Worker entry and bindings

`wrangler.jsonc` sets `./src/server.ts` as `main`, with `compatibility_date` `2026-04-18`, the `nodejs_compat` flag, `placement.mode: "smart"` and observability enabled, Workers Issues included. Every environment receives the same seven bindings:

| Binding                     | Type           | Used for                                                                                                                                                                                                              |
| --------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DB`                        | D1 database    | All 43 tables, including sessions, verification, rate-limit counters and the FTS5 `storefront_search` index                                                                                                           |
| `IMAGES`                    | R2 bucket      | Product images uploaded through `src/integrations/cloudflare-r2`                                                                                                                                                      |
| `CACHE`                     | KV namespace   | The five-minute email sender flag (`resend.availability.server.ts`), the open-incident keys that keep `sendIncidentAlert` to one email per incident (`src/lib/incident-alert.server.ts`), and the `/api/health` probe |
| `ASSETS`                    | Static assets  | Everything in `public/`, including the fonts of the site and of the PDF forms                                                                                                                                         |
| `REALTIME_INVALIDATION_HUB` | Durable Object | The `RealtimeInvalidationHub` class, one instance per audience name                                                                                                                                                   |
| `AUDIT_LOG_QUEUE`           | Queue          | Audit events, produced by the app and consumed by the same Worker                                                                                                                                                     |
| `NEWSLETTER_QUEUE`          | Queue          | Newsletter batches, one campaign batch per message, consumed by the same Worker                                                                                                                                       |

The Durable Object is declared as a SQLite class in the `migrations` block (`tag: "v1"`, `new_sqlite_classes: ["RealtimeInvalidationHub"]`) even though the hub keeps no durable state. Each queue's producer and consumer point at the same queue, so `src/server.ts` exports both a `fetch` and a `queue` handler, and that handler also consumes both dead-letter queues; it routes a batch to the newsletter consumer when the queue name starts with `martebizuteria-newsletter` and to the audit-log consumer otherwise. The audit-log queue has `max_batch_size: 50`, `max_batch_timeout: 5` (`1` in `test`), `max_retries: 3` and a `dead_letter_queue` named after it with `-dlq`, which is consumed one message at a time with `max_retries: 3` and `retry_delay: 300`. The newsletter queue sends one campaign batch at a time (`max_batch_size: 1`, `max_concurrency: 1`, `max_retries: 3`), and its `-dlq` queue is consumed with the same limits plus `retry_delay: 300`. Preview and production also declare `triggers.crons: ["0 3 * * *"]`, which calls its `scheduled` handler every day at 03:00 UTC for the [retention clean-up](/docs/guides/data-retention); development and test declare no trigger.

`nodejs_compat` is what makes `node:async_hooks` available, which `src/lib/background.ts` needs for its `AsyncLocalStorage`.

## Environments

`wrangler.jsonc` defines four environments and `CLOUDFLARE_ENV` selects one for `vp dev`, `vp build` and `vp preview`.

| Environment   | Worker name                  | D1 database                  | R2 bucket                    | Queues                                                                  | Used by                                             |
| ------------- | ---------------------------- | ---------------------------- | ---------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------- |
| `development` | `martebizuteria-development` | `martebizuteria-preview`     | `martebizuteria-preview`     | `martebizuteria-audit-log-preview`, `martebizuteria-newsletter-preview` | `bun run dev`                                       |
| `preview`     | `martebizuteria-preview`     | `martebizuteria-preview`     | `martebizuteria-preview`     | `martebizuteria-audit-log-preview`, `martebizuteria-newsletter-preview` | `bun run build:preview`, `deploy:preview`, `start`  |
| `test`        | `martebizuteria-test`        | `martebizuteria-test`, local | `martebizuteria-test`, local | `martebizuteria-audit-log-test`, `martebizuteria-newsletter-test`       | `bun run build:test`, `start:test`, `db:reset:test` |
| `production`  | `martebizuteria`             | `martebizuteria`             | `martebizuteria`             | `martebizuteria-audit-log`, `martebizuteria-newsletter`                 | `bun run build:production`, `deploy:production`     |

`preview` attaches `preview.martebizuteria.pl` as a custom domain through `routes` with `custom_domain: true`; `production` attaches `martebizuteria.pl` and `www.martebizuteria.pl` the same way, and the Worker sends every `www` request to the bare domain with a `308`. Both also set `workers_dev: true`, so their `workers.dev` hostnames keep answering next to the domain; see [Deploy a preview](/docs/getting-started/deploy-preview) for what the zone needs.

`test` is the local environment the end-to-end suite runs against. Its `main` is `./src/platform/testing/worker.ts`, which wraps the application Worker with emulated providers, and it sets `APP_ENV` to `test`. Its D1 database (placeholder id `00000000-0000-0000-0000-000000000001`), R2 bucket and KV namespace are `"remote": false`, and the Vite Cloudflare plugin keeps their state in `.wrangler/test` (`persistState` in `vite.config.ts`). `bun run db:reset:test` deletes that folder, applies the migrations with `db:migrate:test` and seeds the catalog and the E2E accounts, the admin with two-factor authentication enabled, with `db:seed:test` (`scripts/seed-test.ts`). Playwright's local web-server command, or the E2E workflow on CI, runs `db:reset:test` and `build:test` before `start:test` serves the build. `.env.test` supplies its dummy values.

In `development`, `preview` and `production` the D1, R2 and KV bindings are marked `"remote": true`. The Vite Cloudflare plugin only enables remote bindings when `CLOUDFLARE_ENV` is `development` (`remoteBindings` in `vite.config.ts`), so `bun run dev` talks to the real D1 database, R2 bucket and KV namespace that `development` shares with `preview` rather than local emulation. Migrations therefore have to be applied before the first run:

```sh
bun run db:migrate:development
```

`development` and `preview` share one D1 database, one R2 bucket and one KV namespace, so a schema change applied for local work is already applied for preview.

## Secrets and environment files

Each environment lists the same ten required secrets under `secrets.required`: `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `INPOST_API_TOKEN`, `INPOST_ORGANIZATION_ID`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `VITE_R2_URL`. `APP_ENV` is a plain var, not a secret.

Values come from `.env.development`, `.env.preview` and `.env.production`, which are gitignored; `.env.test` holds committed dummy values and `.env.example` is the template. Bun's automatic env loading is disabled in `bunfig.toml`, so the environment is always chosen explicitly — either by `--mode` or by `bun --env-file=`.

`VITE_`-prefixed values are browser-visible. `VITE_STRIPE_PUBLISHABLE_KEY` is declared in `src/types/vite-env.d.ts` and read through `import.meta.env`; `VITE_R2_URL` is read on the server from `env` and in the browser from `import.meta.env`, which is why `src/lib/url.ts` wraps it in `createIsomorphicFn`.

In the application and its scripts, Cloudflare management credentials (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, `CLOUDFLARE_ACCESS_TOKEN`) are read only by `drizzle.config.ts` for Drizzle Kit. The deploy workflows hand the `CLOUDFLARE_ACCESS_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets to Wrangler as `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` for the deploy step. `scripts/prepare-deploy-secrets.ts` uploads only the secrets declared in `secrets.required`, of which only the two InPost values may be blank, keeping the management credentials out of the Worker.

## Types

| File                                  | Source                                                                           |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| `src/types/worker-configuration.d.ts` | Generated by `bun run cf-typegen` from the `development` environment; gitignored |
| `src/types/router.d.ts`               | Declares the `staticData.namespaces` route option                                |
| `src/types/vite-env.d.ts`             | Declares the `VITE_`-prefixed browser variables                                  |
| `src/types/globals.d.ts`              | Narrows `Object.fromEntries` so it keeps key types                               |

`bun run typegen` runs `cf-typegen` and `content` together and is wired to `postinstall`, so a fresh clone gets both the binding types and the Fumadocs collections before the first type check.

## Deploy gates

Both deploy scripts fail rather than warn:

```sh
bun run deploy:preview      # verify-bindings → verify-stripe-keys → verify-email-sender → build:preview → prepare-deploy-secrets → db:migrate:preview → wrangler deploy → verify-deployment
bun run deploy:production   # the same, against the production environment
```

- `scripts/verify-bindings.ts` accepts only `preview` and `production`. It reads the config through Wrangler's own `unstable_readConfig` and throws unless the D1 and KV ids are real rather than placeholders, the R2 bucket is named, the `AUDIT_LOG_QUEUE` and `NEWSLETTER_QUEUE` producers each have a matching consumer whose dead-letter queue is consumed too, and the Durable Object binding points at `RealtimeInvalidationHub`. For production it also throws when the `IMAGES` bucket is the one preview binds.
- `scripts/verify-stripe-keys.ts` reads the mode of `VITE_STRIPE_PUBLISHABLE_KEY` and `STRIPE_SECRET_KEY` from their prefixes and throws unless both are live keys for production or test keys for preview; see [Stripe](/docs/integrations/stripe#secrets).
- `scripts/verify-email-sender.ts` asks Resend whether it would send as `RESEND_EMAIL_FROM` and throws when the sender's domain is missing from the Resend account or not verified; see [Resend](/docs/integrations/resend#sender-domain).
- `scripts/verify-build.ts` rejects a client bundle that still carries an unbundled `cloudflare:workers` or `node:*` import.
- `scripts/prepare-deploy-secrets.ts` writes `.wrangler/secrets.<env>.json` from the matching `.env` file, and the deploy passes it with `--secrets-file`.
- `db:migrate:<env>` applies the pending D1 migrations right before `wrangler deploy` and stops the deploy when one fails.
- `scripts/verify-deployment.ts` runs after `wrangler deploy` and throws unless the live Worker answers its home page, product listing, `robots.txt`, Stripe webhook route and health check as the shop does; see [Roll back a deploy](/docs/guides/roll-back-a-deploy).

The deploy runs against `dist/server/wrangler.json` — the config the Cloudflare Vite plugin emits — with `CLOUDFLARE_ENV` unset, so the environment baked into the build is the one that ships.

## Shared test wiring

`src/platform/testing` holds only what cannot belong to one feature:

| Path                                                                                       | Contents                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setup.ts`                                                                                 | jest-dom matchers, `IntersectionObserver`/`ResizeObserver`/`matchMedia` stubs, `HTMLDialogElement` and `elementFromPoint` shims, timer clean-up after each file, the `createServerFn` replacement and a stubbed `getRequest` |
| `vitest-env.d.ts`                                                                          | Vitest global types and the jest-dom matcher types                                                                                                                                                                           |
| `worker.ts`                                                                                | The `test` environment's Worker entry: installs the provider mocks, answers `/__test/` routes that read captured emails and settle emulated Stripe sessions, and forwards everything else to `src/server.ts`                 |
| `lib/server-function.ts`                                                                   | `withTestRpc`, which runs a server function in-process through its real middleware and validator                                                                                                                             |
| `lib/render.tsx`                                                                           | `renderWithProviders`, `TestProviders`, `createTestRouter`                                                                                                                                                                   |
| `lib/messages.ts`                                                                          | `TEST_LOCALE` and `TEST_MESSAGES` for the `IntlProvider` in tests                                                                                                                                                            |
| `lib/auth-browser.ts`                                                                      | `openAuthBrowser` and `createPasswordCustomer`, which drive the Better Auth handler with cookies for auth tests                                                                                                              |
| `lib/cut-text.ts`                                                                          | `markAsCut`, which fakes an overflowing element for truncation tests                                                                                                                                                         |
| `lib/pdf.ts`                                                                               | `readPdf`, which reads a PDF back with pdf.js, and the form fonts from `public/fonts/forms`                                                                                                                                  |
| `mocks/d1.ts`                                                                              | `createTestD1Database`, a D1-shaped transport over `node:sqlite`                                                                                                                                                             |
| `mocks/migrations.ts`                                                                      | `MIGRATION`, `applyMigration` and `applyMigrationHistory`, which run the D1 migration files against a `node:sqlite` database                                                                                                 |
| `mocks/providers.ts`                                                                       | `installProviderMocks`, which replaces `fetch` to capture Resend emails and emulate Stripe, InPost ShipX and the InPost points API, plus the helpers `worker.ts` exposes                                                     |
| `mocks/inpost-points.ts`                                                                   | `emulateInpostPoints`, the emulated InPost points responses                                                                                                                                                                  |
| `mocks/display-preferences.ts`                                                             | A `resolveRequestDisplayPreferences` stub that resolves to `pl-PL` and `Europe/Warsaw`                                                                                                                                       |
| `mocks/seller-details.ts`                                                                  | `TEST_SELLER_DETAILS`, `SELLER_DETAILS_QUERIES` and `createSellerDetailsQueryClient`, the seller's details for components and e-mails that name the seller                                                                   |
| `mocks/broadcast-channel.ts`, `mocks/intersection-observer.ts`, `mocks/resize-observer.ts` | Browser API stubs                                                                                                                                                                                                            |

`setup.ts` is registered only for the `component` project in `vite.config.ts`; node and integration tests import what they need directly. See [Testing architecture](/docs/architecture/testing-architecture).
