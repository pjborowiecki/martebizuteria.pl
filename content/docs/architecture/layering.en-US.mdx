## The layers

| Layer        | Lives in                            | Decides                                                                                    |
| ------------ | ----------------------------------- | ------------------------------------------------------------------------------------------ |
| Worker entry | `src/server.ts`                     | Which requests never reach React; locale redirects; `waitUntil` plumbing; security headers |
| Delivery     | `src/routes`, `src/router.tsx`      | URL shape, guards, what a page preloads, head tags                                         |
| Use cases    | `src/modules/*/use-cases`           | Who may call an operation, what input is valid, which query keys it owns                   |
| Data access  | `src/modules/*/*.accessors.ts`      | How a row is read or written; SQL shape; prepared statements                               |
| Presentation | `src/presentation`, `src/providers` | Markup, styles, which query options to read                                                |

Vendors sit beside these layers rather than inside them: `src/integrations/{vendor}` configures a third party and hands the domain decisions back to the module that owns the data.

## The split that does the work

An accessor is plain data access with no notion of who is asking:

```ts
export const getAvailabilityByVariantIds = async (variantIds: readonly string[]): Promise<Map<string, number>> => {
  if (variantIds.length === 0) {
    return new Map()
  }

  const rows = await db
    .select({ quantityAvailable: inventory.quantityAvailable, variantId: inventory.variantId })
    .from(inventory)
    .innerJoin(productVariant, eq(productVariant.id, inventory.variantId))
    .innerJoin(product, eq(product.id, productVariant.productId))
    .where(and(inJsonList(inventory.variantId, variantIds), eq(product.status, PRODUCT_STATUS.PUBLISHED)))
  return new Map(rows.map((row) => [row.variantId, row.quantityAvailable]))
}
```

A use case wraps data access in an RPC endpoint and is the only place authorization is expressed:

```ts
export const shipOrder = createServerFn({ method: "POST" })
  .middleware([authorized({ order: ["update"] })])
  .validator((input: zod.input<typeof orderZodSchemas.adminShipOrderInput>) => orderZodSchemas.adminShipOrderInput.parse(input))
  .handler(async ({ data: { orderId, ...tracking } }) => {
    const origin = resolveRequestOrigin(getRequest())
    const trackingNumber = filledOrUndefined(tracking.trackingNumber)
    assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
      canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
    )

    await transitionOrder(orderId, SHIPPABLE_FULFILLMENT_STATUSES, {
      fulfillmentStatus: "shipped",
      shippedAt: new Date(),
      ...trackingColumns(trackingNumber, filledOrUndefined(tracking.trackingUrl)),
    })

    recordOrderShippedAudit(orderId, { detail: trackingNumber })

    return { email: await announceOrderShipment(orderId, origin), ok: true, orderId }
  })
```

`getAdminOrderActionRow`, `assertOrderActionState` and `transitionOrder` come from `src/modules/order/use-cases/transition-order.server.ts`. `transitionOrder` is a conditional `UPDATE` that only moves an order whose fulfilment status is still one of `SHIPPABLE_FULFILLMENT_STATUSES` and which is not cancelled, and throws a conflict when no row matched. `announceOrderShipment` (`use-cases/announce-order-shipment.server.ts`) then claims and sends the shipped e-mail, or the tracking e-mail when a new tracking number follows an earlier shipped e-mail, and returns the e-mail notice that the admin order actions show as a toast.

Because there is exactly one layer where `authorized()` can be forgotten, that layer is the one the tests target. A use case that reads the caller's own data compiles the ownership predicate into the SQL rather than fetching and filtering:

```ts
where: and(eq(order.id, orderId), eq(order.userId, context.auth.user.id)),
```

A foreign order id returns no row, so there is nothing to leak.

## What the Worker decides before React runs

`src/server.ts` short-circuits four kinds of request before the TanStack Start handler is reached, because none of them needs an SSR render:

1. `GET /sitemap.xml` — `generateSitemapXml` from `src/lib/seo.ts` over the pages `listSitemapPages` reads from D1, cached for a day.
2. `GET /robots.txt` — `generateRobotsTxt`, which returns a blanket `Disallow: /` unless `APP_ENV` is `production`.
3. `ROUTES.API_REALTIME.ADMIN_WS` and `ROUTES.API_REALTIME.STOREFRONT_WS` — WebSocket upgrades, handed to `handleRealtimeInvalidationWebSocket`.
4. A locale redirect from `resolveLocale`, returned as a `301` before anything else happens.

Everything else is wrapped in `executionContextStorage.run({ waitUntil }, …)` so that background work scheduled deep inside the domain layer can still reach the Worker's `ExecutionContext`. Every response except the WebSocket upgrades, the first two short-circuits and the redirect included, leaves through `withSecurityHeaders` from `src/lib/security-headers.ts`, with a Content-Security-Policy nonce drawn for the request and handed to the Start handler in its request context; see [Security model](/docs/architecture/security-model#response-headers). The same file also exports the `queue` handler that drains the newsletter and audit-log queues and the `scheduled` handler that runs the daily [retention clean-up](/docs/guides/data-retention), and re-exports the `RealtimeInvalidationHub` class so Wrangler can bind it.

## Background work

A promise still pending when a Worker returns its response is terminated. Better Auth's hooks and the audit recorders have no access to the `ExecutionContext`, so `src/lib/background.ts` keeps it in an `AsyncLocalStorage`:

```ts
export const scheduleBackgroundWork = (task: Promise<unknown> | PromiseLike<unknown>): void => {
  const store = executionContextStorage.getStore()

  if (store === undefined) {
    void runSafely(task)

    return
  }
  store.waitUntil(runSafely(task))
}
```

With no store — the queue consumer, the `scheduled` handler, unit tests, the paths that short-circuit before the store is entered — it degrades to a fire-and-forget whose rejection is logged rather than swallowed.

## Consistency without transactions

D1 has no interactive transactions. `db.batch()` is atomic, so anything that must be all-or-nothing is assembled as an array of statements and handed to `runDrizzleBatch` from `src/integrations/drizzle-orm/drizzle.batch.ts`. Anything that must read, decide, then write puts the decision in the write instead: each inventory reserve statement in `src/modules/inventory/inventory.accessors.ts` is an `UPDATE` guarded on `quantityAvailable >= qty`, which SQLite checks and applies in one statement, and uses the length of `.returning()` as its success signal. It does not also compare a version read during validation, so a checkout is refused only when the stock has run out, not because another checkout reserved the same variant a moment earlier.

Multi-line carts reserve in one batch and compensate. `reserveInventoryForItems` releases the reservations that already succeeded when any line fails its guard — and the compensation itself is wrapped in `.catch()` and only logged, so a failed rollback leaves stock reserved. That is a saga with a known hole, not a distributed transaction.
