## Three Vitest projects

`vp test run` runs Vitest through Vite+ with three projects defined in `vite.config.ts`. Tests live in a `__test__` folder next to the code they cover and import their test APIs from `vite-plus/test`.

| Project       | Environment | Files                                             | Count |
| ------------- | ----------- | ------------------------------------------------- | ----- |
| `node`        | Node        | `*.{test,spec}.{ts,tsx}`, excluding the two below | 482   |
| `integration` | Node        | `*.integration.test.{ts,tsx}`                     | 136   |
| `component`   | jsdom       | `*.component.test.{ts,tsx}`                       | 624   |

1,242 test files in total, in 224 `__test__` folders; all but the commit message hook's test in `scripts/__test__/` live under `src/`. Only the `component` project loads `src/platform/testing/setup.ts`; node and integration tests import what they need explicitly. The `integration` project raises the test and hook timeouts to 30 seconds.

```sh
bun run test              # all three projects
bun run test:unit         # node
bun run test:integration  # integration
bun run test:component    # component
bun run test:watch
bun run test:changed
bun run test:coverage
```

The base config sets `environment: "node"`, `isolate: true`, `pool: "threads"`, `maxWorkers: "50%"` and `passWithNoTests: false`, loads `.env.test` through `loadEnv("test", …)`, and excludes `node_modules`, `opensrc`, `dist`, `scripts`, `e2e` and the generated `drizzle-orm/migrations` folder.

When `VITEST` is `true` the plugin list in `vite.config.ts` narrows to React and `fumadocs-mdx` only — no Cloudflare plugin, no TanStack Start plugin, no Tailwind — so a test run never needs a Worker runtime or a Cloudflare account.

## Server functions run in-process

`setup.ts` proxies `createServerFn` so a server function executes locally through its **real** middleware chain and validator, rather than being mocked out:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
```

`withTestRpc` wraps the builder, intercepts `.handler()` and runs the compiled function inside `runWithStartContext`, supplying a `request` from the mocked `getRequest()` — a plain `Request` for `http://127.0.0.1:3000/`. Its fake context deliberately throws if anything asks for `getRouter`, so a test that accidentally triggers route rendering fails loudly.

The practical effect: a test for `shipOrder` really passes through `withRequest`, `authorized({ order: ["update"] })` and the Zod validator. Authorization cannot be tested away. Component tests get the proxy from `setup.ts`; the 28 node and integration suites that call server functions install it with their own `vi.mock`.

`src/integrations/better-auth/__test__/use-case-authorization.test.ts` requires `authorized(` in every use case under `src/modules/` that calls `createServerFn`, except the 24 public ones on its allowlist, and forbids `assertAdmin(` in every use-case file.

## D1 over `node:sqlite`

`src/platform/testing/mocks/d1.ts` exports `createTestD1Database(sqlite, onQuery?, onRoundTrip?)`, a hand-written transport that presents the D1 `prepare/bind/all/run/raw/batch` surface over a `node:sqlite` `DatabaseSync`. `batch` runs one batch at a time and wraps the statements in `begin`/`commit` with a `rollback` on failure, so batch atomicity and ordering are emulated. As on D1, `bind` refuses more than 100 parameters and the database refuses a `LIKE` or `GLOB` pattern longer than 50 bytes. The optional `onQuery` callback records `{ sql, params }`, which lets a test assert the SQL a query compiles to. The optional `onRoundTrip` callback records one `TestD1RoundTrip` per request to D1, when the request starts: `{ kind: "batch", sql }` for each `batch` call, however many statements it carries, and `{ kind: "statement", sql: [sql] }` for each `all`, `raw` or `run` outside a batch, which lets a test assert how many round trips an operation costs. It counts separate requests and does not show which of them waited for another.

An integration test wires it in by mocking the database module:

```ts
vi.mock(import("~/src/integrations/drizzle-orm/drizzle.database"), async () => {
  const { drizzle } = await import("drizzle-orm/d1")
  const schema = await import("~/src/integrations/drizzle-orm/drizzle.schemas")
  const { createTestD1Database } = await import("~/src/platform/testing/mocks/d1")

  return { db: drizzle(createTestD1Database(sqlite), { schema }) }
})
```

65 of the 136 integration suites build their schema by replaying every migration file with `applyMigrationHistory` from `src/platform/testing/mocks/migrations.ts`; the others create the tables they need themselves, replay the history up to the migration under test with `applyMigrationHistoryBefore`, or apply only that migration with `applyMigration`.

**What this does not emulate:** D1's network latency and its concurrency characteristics. A concurrency result from the integration suite is SQLite's behaviour, not proof about D1 under production load.

## Component tests

`renderWithProviders` from `src/platform/testing/lib/render.tsx` wraps the tree in use-intl's `IntlProvider` (with `TEST_LOCALE`, `TEST_MESSAGES` and `I18N.DEFAULT_TIMEZONE`), a real `QueryClientProvider` with retries disabled, and a `RouterContextProvider` over a memory-history router. `setup.ts` also stubs `IntersectionObserver`, `ResizeObserver` and `matchMedia`, which the GSAP and Lenis code paths need in jsdom, gives `HTMLDialogElement` working `showModal` and `close`, makes `document.elementFromPoint` return `null` and mocks `getRequest`. It sets a 15-second test timeout and a 5-second Testing Library `asyncUtilTimeout`, waits after every test until the modules a component imported on demand, such as GSAP, have loaded, and clears the timers a test file left pending once the file has finished.

## What the suites are aimed at

Coverage is broad, but the suites that earn their keep are the ones where a silent regression is expensive:

- **Checkout idempotency** — `checkout-idempotency.integration.test.ts` drives two deliveries that both observe a `pending` checkout and asserts exactly one order results. The application guard in `resolvePendingCheckout` collapses Stripe's _sequential_ retries; the constraint that holds for genuinely concurrent deliveries is the database's, because `order.checkout_id` and `payment.transaction_id` are unique indexes and a D1 batch is atomic, so the losing insert rolls its whole batch back.
- **Inventory** — `inventory-reservation.integration.test.ts` and `inventory-release.integration.test.ts` exercise the guarded reserve and the `min`/`max`-clamped release; the reservation suite runs on the migrated schema, interleaves two checkouts that read the same stock before either reserves, and counts round trips, so a cart that stops being reserved in one batch fails it. It also writes a stock row through the schema and loads it back with only the columns the schema declares, while the migrated table holds the undeclared `version` column.
- **Rate limiting** — `rate-limit.integration.test.ts` fires concurrent attempts at the real limiter over in-memory SQLite and asserts the admitted and rejected counts.
- **Auth storage** — `auth.storage.integration.test.ts` pins the Better Auth configuration, including the absence of `secondaryStorage`, and shows that Better Auth's limiter, counting through `withinRateLimit`, refuses past its maximum and leaves the e-mail caps standing when one of its windows starts again.
- **Checkout batches** — `checkout-batches.integration.test.ts` runs the create, update-delivery and release batches against in-memory SQLite and asserts the rows they leave: one shared or two separate addresses, the delivery selection and note, the released discount claim, and the payment and checkout failed together.
- **Query plans** — `query-plans.integration.test.ts` replays the migrations, checks that every foreign key is indexed and that every index the schema declares exists on the same columns, and runs `explain query plan` on the statements of the hot reads, recorded through `onQuery`, to show they use an index instead of scanning a table.
- **Accessors** — 24 accessor suites run data-access modules against SQLite: account, address, audit-log (three), category-on-product, checkout, collection-on-product, delivery-method, discount, inventory, order (four), product (four), user (three), user-email-history and wishlist-item.

The integration project holds 136 suites in all. Besides those above, the largest groups cover the order module (21 suites), the checkout (14) and Better Auth (13), and some test the data migrations, such as the backfills in `src/modules/order/__test__/`.

## Coverage

```sh
bun run test:coverage
```

The v8 provider reports `text`, `html` and `json-summary` into `coverage/`, over `src/**/*.{ts,tsx}` and excluding tests, `__test__` folders, `*.d.ts`, `src/routeTree.gen.ts`, the generated `src/integrations/**/migrations/**`, `src/presentation/components/shadcn/**` and `src/platform/testing/**`.

The suite covers every statement, branch, function and line, and the thresholds hold it there: any uncovered code fails CI. A branch that no input can reach is removed rather than covered with a contrived test.

| Metric     | Threshold in `vite.config.ts` |
| ---------- | ----------------------------- |
| Lines      | 100                           |
| Statements | 100                           |
| Functions  | 100                           |
| Branches   | 100                           |

`autoUpdate` is `false`, so the thresholds only move when someone edits them.

## Browser tests

The Playwright suite in `e2e/` runs the built Worker in Chromium and WebKit against a local D1 database created from the full migration history. A dedicated test Worker, `src/platform/testing/worker.ts`, captures Resend email, emulates the Stripe API and InPost's ShipX sandbox in memory, answers the server's InPost point lookups, and signs `checkout.session.completed`, `checkout.session.expired` and `charge.dispute.created` events with the test webhook secret, so a spec covers a whole purchase: the four checkout steps, the stock reservation, the signed webhook, fulfilment, the confirmation page and email, the customer's order history and the admin's fulfilment. Courier, in-store pickup and a parcel locker chosen in the map picker, whose InPost point search the browser answers from local fixtures, are each paid for, and one full checkout runs in Polish under the default locale. Sign-up with the real verification link, protected-route redirects, coupons, search, the cart, pausing sales and both locales are covered too. Stripe's own payment form is covered only by the `stripe-test-mode` project, which pays through a Stripe sandbox by card (including declined cards and 3D Secure), BLIK and Przelewy24. It needs sandbox keys, which every E2E (full) run in CI supplies, and its specs are skipped without them. [Testing](/docs/tooling/testing#end-to-end-tests) describes the harness and how to write specs.

## CI

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main`, with concurrency cancellation. Its `verify` job has a 25-minute timeout and uses the shared composite action `.github/actions/setup`, which installs Bun 1.4.0, sets up Vite+ with Node 24, runs `bun install --frozen-lockfile --ignore-scripts`, copies `.env.test` over `.env.development` and `.env.preview` when the job passes `test-environment: "true"`, as every CI and end-to-end job does, and runs `bun run typegen`.

Then, in order:

1. `bun run check` — format, lint and type check
2. `bun run test:coverage`
3. `bun run build:preview`
4. Upload `coverage/` as an artifact

The same workflow's `e2e` job runs the Playwright suite on Chromium through `e2e-reusable.yml`, whose job has a 30-minute timeout. `e2e-full.yml` runs it on WebKit after every push to `main`, and on both browsers on the Monday 03:15 UTC schedule and on a manual run. Its `stripe-test-mode` job, also limited to 30 minutes, runs the Stripe test-mode project on every one of those runs with the sandbox keys from the `E2E_STRIPE_SECRET_KEY` and `E2E_STRIPE_PUBLISHABLE_KEY` repository secrets.

`.github/workflows/deploy-preview.yml` uses the same setup action and re-runs the full check before building. `deploy-production.yml` starts only after this workflow has passed for a push to `main`, so production never ships a commit whose tests failed.

## Local gate

```sh
bun run check        # vp check: format, lint, type check
bun run check:fix    # the same, applying fixes
```

Two Git hooks in `.vite-hooks/` run on every commit; `bun install` sets them up through the `prepare` script, `vp config --no-agent`. `pre-commit` runs `bun run check:pre-commit`, which is `vp staged`: the `staged` block in `vite.config.ts` runs `vp check --fix` on the staged files. `prepare-commit-msg` runs `bun scripts/commit-msg.ts`, which rejects a subject that does not follow `type(scope): description` with one of its eleven types and prefixes the subject with the type's emoji; see [Conventional commits](/docs/tooling/conventional-commits).

`bun run check` is the same gate CI runs. Lint is strict: six Oxlint categories set to `error` including `nursery`, `typeAware` and `typeCheck` on, `denyWarnings: true` and `reportUnusedDisableDirectives: "error"`, with an 800-line file limit, a 150-line function limit and a 20-statement function limit. Overrides are narrow and file-scoped: tests and mocks relax `no-magic-numbers` and a few others, `src/presentation` and `src/hooks` relax `typescript/consistent-return`, `src/routes/**` relaxes `sort-keys`, and `vite.config.ts` relaxes `max-lines`.
