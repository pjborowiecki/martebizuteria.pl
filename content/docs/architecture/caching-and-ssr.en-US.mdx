## The query cache

`getRouter` in `src/router.tsx` creates a new `QueryClient` for every request, so no data leaks between users on the server:

| Setting                          | Value                                       |
| -------------------------------- | ------------------------------------------- |
| Query `staleTime`                | 1 minute                                    |
| Query `gcTime`                   | 5 minutes                                   |
| Router `defaultStaleTime`        | 1 minute                                    |
| Router `defaultPreloadStaleTime` | 0                                           |
| Preloading                       | `"intent"`, 100 ms delay, 1000 px proximity |
| Pending component                | after 200 ms, shown for at least 300 ms     |
| Structural sharing               | on                                          |
| Scroll restoration               | on, `"instant"`                             |

`setupRouterSsrQueryIntegration({ queryClient, router })` serializes the server cache into the HTML and hydrates it in the browser, so a page rendered on the server does not refetch what it already has.

Loaders fill the cache with `context.queryClient.query({ ...options, staleTime: "static" })` and components read the same keys with `useSuspenseQuery(options)`. Because the query options come from the same module file, the loader and the component cannot drift apart.

A component that reads with `useQuery(options)` still gets its data from the loader when the loader warms the same key. `NewsletterField` reads `getOwnNewsletterSubscriptionQuery()`, which the `/account/profile` loader loads together with the profile, so a confirmed subscriber is shown as subscribed on the first render. The checkout form reads `listDeliveryMethodsQuery()`, which the `/checkout/` page loader loads while the `/checkout` layout loader reads the checkout messages, because the router runs both loaders at the same time. The page loader keys on `success` alone and skips the read on the confirmation Stripe returns to, where no form is shown. The full-screen menu's `ImageShowcase` reads `getCollectionsQuery()`, which every layout that renders `Navigation` loads: `_storefront.tsx`, `account.tsx`, `auth.tsx` and `docs.tsx`. Without that, each of those queries would start one round trip after the page had rendered.

The page can render without any of these three, so each loader ends its read with `.catch(noop)` (`noop` from `@tanstack/react-query`). A failed read leaves the query in the `error` state and lets the loader resolve. The SSR integration dehydrates that state, and the component's `useQuery` starts the request again when it mounts, as it did before the loader warmed the key. Data the page cannot render without, such as the profile on `/account/profile`, is still read with a bare `query()`, so its failure shows the route's error component.

`defaultPreloadStaleTime: 0` is deliberate: hovering a link runs the loader for real rather than reusing a cached result, which is what makes the storefront's on-intent image prefetching useful. `ImagePrefetchService` from `src/lib/image.ts` is created once per router and passed in the router context, and loaders call `prefetchSingleProductImage(data, context.imagePrefetchService)`.

## Per-query overrides

| Query                                         | Behaviour                                                               |
| --------------------------------------------- | ----------------------------------------------------------------------- |
| `messagesQueryOptions({ locale, namespace })` | `staleTime: Infinity`, `gcTime: Infinity` — a namespace is loaded once  |
| `getCurrentSessionQuery`                      | 60 s `staleTime`, `retry: false`, no refetch on focus or reconnect      |
| Admin list queries                            | Module `*_QUERY_STALE_MS`, `refetchOnMount: false`, no refetch on focus |
| Public catalog queries                        | Router defaults; invalidated over the realtime hub instead of polled    |

Admin lists deliberately do not refetch on mount or on window focus. Freshness comes from the Durable Object hub instead — see [Realtime invalidation](/docs/architecture/realtime-invalidation) — so a second admin's change arrives as a push rather than as a poll.

The route guards and the components share the session query. The `/account` and `/admin` guards load it with `context.queryClient.query`, overriding `staleTime` to 0 on a navigation; a link preload and the `/auth` guard reuse a session younger than 60 seconds. The entry stays in the cache, so a server render serializes it into the page and `/account` and `/admin` pages render signed-in. The navigation's account link, the translations time zone, the wishlist and the checkout prefill read the same value with `useQuery(getCurrentSessionQuery)`.

The guards only read the session. A change of user is handled in one place, `clearCacheOnUserChange(queryClient)` in `src/integrations/better-auth/auth.session.ts`. `getRouter` installs it in the browser only, next to `setupQueryClientInvalidationBroadcast`; server rendering skips it because every request starts with an empty `QueryClient`. It subscribes to the query cache:

```ts
export const clearCacheOnUserChange = (queryClient: QueryClient): (() => void) => {
  const seen: { session?: Awaited<ReturnType<typeof getCurrentSession>> } = {}

  return queryClient.getQueryCache().subscribe(({ query }) => {
    const session = query.queryHash === SESSION_QUERY_HASH ? queryClient.getQueryData(getCurrentSessionQuery.queryKey) : undefined
    if (session === undefined) {
      return
    }

    if ("session" in seen && seen.session?.user.id !== session?.user.id) {
      queryClient.removeQueries({ predicate: (cached) => cached.queryHash !== SESSION_QUERY_HASH && !isMessagesQuery(cached) })
    }
    seen.session = session
  })
}
```

Whenever the session query's data switches to a different user id, including from signed out to signed in and back, it removes every cached query except the session itself and the translation message catalogues, matched by `isMessagesQuery` in `src/integrations/use-intl/i18n.messages.ts`. It ignores the first session it sees and the session entry being removed. Because it watches the cache rather than any one caller, it catches the change whoever fetched the session: a guard, a component, a refetch after an invalidation, or hydration.

After a sign-in, `usePostAuthRedirect` removes only the session entry, so the `/auth` guard fetches the fresh session and `clearCacheOnUserChange` forgets what was cached while signed out. Signing out does a full page load, which discards the cache.

## Prepared statements

Point reads are prepared once at module load, outside any request, and executed with bound parameters:

```ts
export const getProductImagesQuery = db.query.productImage
  .findMany({
    orderBy: (images, { asc: ascOrder }) => [ascOrder(images.rank), ascOrder(images.createdAt)],
    where: eq(productImage.productId, sql.placeholder("productId")),
  })
  .prepare()
```

`product.accessors.ts`, `product-image.server.ts` and the other point reads use this: the by-handle, by-id and per-product reads are prepared, while list queries are built per request because their filters, sort and variant-stats join change the statement's shape and a prepared statement cannot. Writes that span several rows, such as the inventory reservation, are built per call and sent together in one `db.batch` instead.

## There is no prerendering

Nothing in `vite.config.ts` enables TanStack Start's prerendering, and there is no `prerender` option on any route. Every HTML response is server-rendered per request. Consequences worth knowing:

- Storefront pages reflect the catalog at request time with no purge step.
- There is no static-asset fallback in front of the application; `ASSETS` serves `public/` only.
- Cache-control on HTML is left to the platform default, so there is nothing to invalidate when a product changes.

The two responses that do set `Cache-Control` explicitly are `/sitemap.xml` and `/robots.txt`, both `public, max-age=86400`, and uploaded R2 objects, written `public, max-age=31536000, immutable`.

## Browser-side state

- **`localStorage`** holds the theme (`@wrksz/themes`, key from `theme-init.ts`), the admin sidebar preference, and each data grid's column sizing. All three are read by blocking head scripts before first paint.
- **Zustand with `persist`** holds the cart in `src/modules/cart/cart.store.ts`, with a `CART_PERSIST_VERSION` of 2 and a per-item type guard so a stale shape is dropped rather than rehydrated.
- **`BroadcastChannel`** (`marte-query-invalidation` in `query.sync.ts`) mirrors to other tabs of the same browser the invalidations of the few local mutations the realtime hub does not carry, coupons and order actions. Hub frames are not echoed on it, because every storefront and admin tab receives them on its own socket.

None of these is a source of truth. The cart is re-validated server-side by `check-cart-availability.ts` and again inside `handleCreateCheckoutSession`, which re-reads prices and inventory from D1 and refuses the checkout if anything moved.

## What is not cached

- **Sessions.** Better Auth's signed cookie cache is turned off, and `getRequestSession` also passes `disableCookieCache: true`, so every server-side check reads D1. The cost is one D1 read per request; the benefit is that a banned or signed-out user cannot ride a cached cookie. To keep that from becoming N reads, the lookup is memoized in a `WeakMap` keyed on the `Request` object — not a module global — so concurrent loaders and server functions in one request share one lookup and a new request always revalidates. The browser reads the session the same way: components use `useQuery(getCurrentSessionQuery)`, whose `getCurrentSession` goes through `getRequestSession` and skips the cookie cache. What the browser keeps is that query's result, under the rules above. `auth.client.ts` no longer exports Better Auth's `useSession`: it ran during server rendering, which TanStack Start's import protection rejects for `*.client.*` files in the server build, and it sent a second session request.
- **Permissions.** `hasPermission` is evaluated from the session's role on every call. No decision is made from cached data.
- **KV.** The `CACHE` namespace is bound in all three environments and verified by `scripts/verify-bindings.ts`. It caches no pages or data: its only key is the email sender flag that `markEmailSenderUnavailable` writes and the Better Auth gate reads (see [Resend](/docs/integrations/resend)).
