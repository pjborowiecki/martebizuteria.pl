## The query cache

`getRouter` in `src/router.tsx` creates a new `QueryClient` for every request, so no data leaks between users on the server:

| Setting                          | Value                                       |
| -------------------------------- | ------------------------------------------- |
| Query `staleTime`                | 1 minute                                    |
| Query `gcTime`                   | 5 minutes                                   |
| Router `defaultStaleTime`        | 1 minute                                    |
| Router `defaultPreloadStaleTime` | 0                                           |
| Preloading                       | `"intent"`, 100 ms delay, 1000 px proximity |
| Pending component                | after 200 ms, shown for at least 300 ms     |
| Structural sharing               | on                                          |
| Scroll restoration               | on, `"instant"`                             |

`setupRouterSsrQueryIntegration({ queryClient, router })` serializes the server cache into the HTML and hydrates it in the browser, so a page rendered on the server does not refetch what it already has.

Loaders fill the cache with `context.queryClient.query({ ...options, staleTime: "static" })` and components read the same keys with `useSuspenseQuery(options)`. Because the query options come from the same module file, the loader and the component cannot drift apart.

The `/categories/$handle` and `/collections/$handle` loaders read their row with the query's own stale time instead: `getStorefrontCategoryQuery(handle)` and `getStorefrontCollectionQuery(handle)` stay fresh for 60 seconds. No component reads those queries, so with `"static"` a cached row would serve every later sort, filter and visit for as long as it stayed in the cache. See [Catalog and search](/docs/features/catalog-and-search).

A component that reads with `useQuery(options)` still gets its data from the loader when the loader warms the same key. `NewsletterField` reads `getOwnNewsletterSubscriptionQuery()`, which the `/account/profile` loader loads together with the profile, so a confirmed subscriber is shown as subscribed on the first render. The checkout form reads `listDeliveryMethodsQuery()` and `getFreeDeliveryQuery()`, which the `/checkout/` page loader loads while the `/checkout` layout loader reads the checkout messages, because the router runs both loaders at the same time. The page loader keys on `success` alone and skips the reads on the confirmation Stripe returns to, where no form is shown. The full-screen menu's `ImageShowcase` reads `getCollectionsQuery()`, which every layout that renders `Navigation` loads: `_storefront.tsx`, `account.tsx`, `auth.tsx` and `docs.tsx`. `SalesPausedBanner` reads `getSalesStatusQuery()`, which the layouts that render it, `_storefront.tsx`, `account.tsx` and `docs.tsx`, load, and the `/checkout/` page loader loads it for `CheckoutGuard`, together with the delivery methods and the free delivery threshold. Without that, each of those queries would start one round trip after the page had rendered.

The page can render without any of these, so each loader ends its read with `.catch(noop)` (`noop` from `@tanstack/react-query`). A failed read leaves the query in the `error` state and lets the loader resolve. The SSR integration dehydrates that state, and the component's `useQuery` starts the request again when it mounts, as it would if the loader did not warm the key. Data the page cannot render without, such as the profile on `/account/profile`, is read with a bare `query()`, so its failure shows the route's error component.

`defaultPreloadStaleTime: 0` is deliberate: hovering a link runs the loader for real rather than reusing a cached result, which is what makes the storefront's on-intent image prefetching useful. `ImagePrefetchService` from `src/lib/image.ts` is created once per router and passed in the router context, and loaders call `prefetchSingleProductImage(data, context.imagePrefetchService)`.

## Per-query overrides

| Query                                         | Behaviour                                                                                |
| --------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `messagesQueryOptions({ locale, namespace })` | `staleTime: Infinity`, `gcTime: Infinity` — a namespace is loaded once                   |
| `getCurrentSessionQuery`                      | 60 s `staleTime`, `retry: false`, no refetch on focus or reconnect                       |
| `displayPreferencesQuery`                     | `staleTime: Infinity`, no refetch on focus or reconnect; loaded by the root `beforeLoad` |
| `checkCartAvailabilityQuery`                  | `staleTime: 0`, keeps the previous answer, no refetch on focus or reconnect              |
| Admin list queries                            | Module `*_QUERY_STALE_MS`, `refetchOnMount: false`, no refetch on focus                  |
| Public catalog queries                        | Router defaults; invalidated over the realtime hub instead of polled                     |

`displayPreferencesQuery` holds the formatting locale and time zone detected for the request and the ones saved on the signed-in user (see [Display preferences](/docs/architecture/i18n-architecture#display-preferences)). It never goes stale on its own: saving a preference calls `queryClient.invalidateQueries()` with no filter, so it and every query on screen refetch, including the admin queries whose server functions read the resolved preferences with `resolveRequestDisplayPreferences` to filter and group by date.

Admin lists deliberately do not refetch on mount or on window focus. Freshness comes from the Durable Object hub instead — see [Realtime invalidation](/docs/architecture/realtime-invalidation) — so a second admin's change arrives as a push rather than as a poll.

The route guards and the components share the session query. The `/account` and `/admin` guards load it with `context.queryClient.query`, overriding `staleTime` to 0 on a navigation; a link preload and the `/auth` guard reuse a session younger than 60 seconds. The entry stays in the cache, so a server render serializes it into the page and `/account` and `/admin` pages render signed-in. The navigation's account link, the wishlist, the checkout prefill, the customer activity tracker and the admin customer row actions read the same value with `useQuery(getCurrentSessionQuery)`.

The guards only read the session. A change of user is handled in one place, `clearCacheOnUserChange(queryClient)` in `src/integrations/better-auth/auth.session.ts`. `getRouter` installs it in the browser only, next to `setupQueryClientInvalidationBroadcast`; server rendering skips it because every request starts with an empty `QueryClient`. It subscribes to the query cache:

```ts
export const clearCacheOnUserChange = (queryClient: QueryClient): (() => void) => {
  const seen: { session?: Awaited<ReturnType<typeof getCurrentSession>> } = {}

  return queryClient.getQueryCache().subscribe(({ query }) => {
    const session = query.queryHash === SESSION_QUERY_HASH ? queryClient.getQueryData(getCurrentSessionQuery.queryKey) : undefined
    if (session === undefined) {
      return
    }

    if ("session" in seen && seen.session?.user.id !== session?.user.id) {
      queryClient.removeQueries({
        predicate: (cached) =>
          cached.queryHash !== SESSION_QUERY_HASH && cached.queryHash !== DISPLAY_PREFERENCES_QUERY_HASH && !isMessagesQuery(cached),
      })
      void queryClient.invalidateQueries({ exact: true, queryKey: DISPLAY_PREFERENCES_QUERY_KEY })
    }
    seen.session = session
  })
}
```

Whenever the session query's data switches to a different user id, including from signed out to signed in and back, it removes every cached query except the session itself, the display preferences and the translation message catalogues, matched by `isMessagesQuery` in `src/integrations/use-intl/i18n.messages.ts`. It then invalidates the display preferences, which `TranslationsProvider` has on screen, so they refetch with the new user's saved formatting locale and time zone instead of being removed from under it. It ignores the first session it sees and the session entry being removed. Because it watches the cache rather than any one caller, it catches the change whoever fetched the session: a guard, a component, a refetch after an invalidation, or hydration.

After a sign-in, `usePostAuthRedirect` removes only the session entry, so the `/auth` guard fetches the fresh session and `clearCacheOnUserChange` forgets what was cached while signed out. Signing out does a full page load, which discards the cache.

## The storefront read cache

A storefront page needs the layout's menu collections, sales status and seller details, then the page's own reads: three to nine D1 statements in up to four round trips one after another, each about 40-70 ms from the Warsaw data centre. On the shop's custom domains, `preview.martebizuteria.pl` and `martebizuteria.pl` once production serves it, the public catalogue reads go through a cache in the Workers Cache API, so a page whose data has not changed since the last visit makes one call to the realtime hub and reads its rows from the data centre's cache. A `*.workers.dev` address, where the Cache API stores nothing, skips the hub and the cache and reads D1.

**What is cached.** The server functions that read the public catalogue run their D1 reads inside `readThroughStorefrontCache` from `src/lib/storefront-read.ts`: `getCollections`, `getCategories`, `getStorefrontCategory`, `getStorefrontCollection`, `getNewArrivals`, `getProduct`, `getRelatedProducts`, `getStorefrontProductsPage`, `getContentPage`, `getSalesStatus`, `getSellerDetails`, `getFreeDelivery` and `listDeliveryMethods`. `cacheStorefrontReads` from `src/lib/storefront-cache.server.ts` wraps the D1 binding in `drizzle.database.ts` and answers a statement from the cache only when all three hold:

- it runs inside `readThroughStorefrontCache`;
- it is a `select` or a `with` query run with `all`, `first` or `raw`, and outside its string literals it has no `insert`, `update`, `delete`, `replace`, `upsert`, `create`, `drop` or `alter`, no comma between the tables of a `from` and no identifier quoted with backticks or brackets;
- every table it names is in `PUBLIC_CATALOG_TABLES`: the products, variants, stock, images, options, specifications, categories and collections with the tables that link them, price history, content pages, store settings, delivery methods and couriers. A common table expression the statement defines itself and `json_each` do not count as tables.

The cached unit is one statement's answer exactly as D1 returned it, stored under `https://<host>/__storefront-cache/<BUILD_ID>/<version>/<digest>`, where the digest is a SHA-256 of the method, the SQL, the bound values and the call's arguments. Because the key is the statement itself, two reads never share an answer they should not, and Drizzle maps a cached answer the same way as a fresh one, dates included.

**What is never cached.** Every other statement reads D1: the admin console, which reads the settings through its own `getAdminSalesStatus`, `getAdminSellerDetails` and `getAdminFreeDelivery` so a save always shows the stored value; the account; the cart availability check; creating or updating a Checkout Session, which re-reads prices and stock; the webhooks and the queues; and every write. A statement that touches a table outside the list — sessions, users, carts, wishlists, orders, payments, rate limits or the search index — reads D1 even inside a storefront read, so nothing about one visitor can reach the cache. HTML is not cached either: every page carries its own Content-Security-Policy nonce.

**How it stays fresh.** The storefront `RealtimeInvalidationHub` keeps one value in its storage, the catalogue version, a random UUID. `notifyInvalidation` on the storefront hub writes a new one before it sends the frame, so every change that tells open storefront tabs to refetch also starts a new version, and a tab that refetches because of that frame already reads the new one. A request asks the hub for the version once (`storefrontCacheVersion()` over RPC, kept per `Request` like the session), waits at most 100 ms for it and reads D1 when it does not come, and only looks up keys under it, so the first request after a change misses and reads D1. `publishRealtimeInvalidation` tries each hub up to three times, 50 and 100 ms apart, so one failed call to the hub does not leave the old version in place. Nothing is purged: answers under an old version are never asked for again and age out.

| Change                                                                                                                                                                                 | Publisher that moves the version                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A product created, edited (titles, prices, stock, images, specifications, categories, collections), deleted or reordered                                                               | `scheduleProductCatalogInvalidation`                                                                       |
| Stock moved by a checkout created or updated, its reservation given back after a failure, a session expired or released, a paid order, a cancelled order or an order returned to stock | `scheduleProductCatalogInvalidation`                                                                       |
| A category or collection created, edited, deleted or reordered                                                                                                                         | `scheduleCategoryCatalogInvalidation`, `scheduleCollectionCatalogInvalidation`                             |
| A product's specifications replaced from the product editor (`setAllProductAttributes`)                                                                                                | `scheduleProductCatalogInvalidation`                                                                       |
| A specification created, edited, deleted or reordered                                                                                                                                  | `scheduleProductAttributeCatalogInvalidation`                                                              |
| A content page saved, or a legal page dated by a change of the seller's details                                                                                                        | `scheduleContentPageInvalidation`                                                                          |
| The seller's details, sales paused or resumed, the free delivery threshold                                                                                                             | `scheduleSellerDetailsInvalidation`, `scheduleSalesStatusInvalidation`, `scheduleFreeDeliveryInvalidation` |
| A delivery method created, edited, archived or reordered                                                                                                                               | `scheduleDeliveryMethodsInvalidation`                                                                      |

Changes only admins see — orders, customers, the team, newsletter subscribers, the audit log — publish to the admin hub alone and keep the version. `src/lib/__test__/storefront-cache.mutations.integration.test.ts` runs every use case above against a real database and the real hub class and checks that the version moved.

The publish runs in `waitUntil` right after the change is written, so the delay between a save and the storefront showing it is that one call to the hub, a few milliseconds; a request already under way may still finish with the earlier answers.

**Limits.**

- Answers are stored with `Cache-Control: public, max-age=600`. A change made outside the application, such as a SQL statement run in the Cloudflare dashboard, shows within ten minutes, or at once after any storefront-visible save in the admin console.
- Each build has its own `import.meta.env.BUILD_ID`, set in `vite.config.ts`, so a deploy and the migrations it applies start from an empty cache.
- The Cache API is local to each Cloudflare data centre and drops what nobody asks for; a miss reads D1.
- `bun run dev` writes the preview database but has a hub of its own, so a change saved there reaches the preview deployment's cache with the deployment's next change or within ten minutes.
- When the hub cannot be reached or does not answer within 100 ms, the cache cannot be opened or an answer cannot be read, the statement reads D1 and the error is logged with `[Storefront Cache]`; a failed write is logged as `[Background Work Failed]` and the answer is still returned (see [Monitoring and alerts](/docs/guides/monitoring-and-alerts)).

## Prepared statements

Point reads are prepared once at module load, outside any request, and executed with bound parameters:

```ts
export const getProductImagesQuery = db.query.productImage
  .findMany({
    orderBy: (images, { asc: ascOrder }) => [ascOrder(images.rank), ascOrder(images.createdAt)],
    where: eq(productImage.productId, sql.placeholder("productId")),
  })
  .prepare()
```

`product.accessors.ts`, `product-image.accessors.ts` and the other point reads use this: the by-handle, by-id and per-product reads are prepared, while list queries are built per request because their filters, sort and variant-stats join change the statement's shape and a prepared statement cannot. Writes that span several rows, such as the inventory reservation, are built per call and sent together in one `db.batch` instead.

## There is no prerendering

Nothing in `vite.config.ts` enables TanStack Start's prerendering, and there is no `prerender` option on any route. Every HTML response is server-rendered per request. Consequences worth knowing:

- Storefront pages reflect the catalog at request time with no purge step: their public reads go through the [storefront read cache](#the-storefront-read-cache), which a change replaces by moving the catalogue version.
- There is no static-asset fallback in front of the application; `ASSETS` serves only the client build. `wrangler.jsonc` names `./public`, and the build writes `dist/server/wrangler.json` with `dist/client`, the hashed bundles under `assets/` plus the files copied from `public/`, which `scripts/verify-build.ts` checks.
- Cache-control on HTML is left to the platform default, so there is nothing to invalidate when a product changes.

The responses that set `Cache-Control` explicitly are `/sitemap.xml` and `/robots.txt`, both `public, max-age=86400`; `/api/health`, `no-store`; the two PDF forms, `public, max-age=300, must-revalidate` with an `ETag` from the last save of the seller details (see [Legal pages](/docs/features/legal-pages#how-the-forms-are-made)); uploaded R2 objects, written `public, max-age=31536000, immutable`; and, through `public/_headers`, the bundles under `/assets/` and the fonts under `/fonts/` (`public, max-age=31536000, immutable`) and `/favicon.svg` and `/og.png` (`public, max-age=86400`).

## Browser-side state

- **`localStorage`** holds the theme (`@wrksz/themes`, key from `theme-init.ts`), the admin sidebar preference (`sidebar_state`), and each data grid's column order, sizing and visibility (`marte:datagrid:v1:` keys). All three are read by blocking head scripts before first paint; the data-grid script applies the column widths.
- **`localStorage`** also holds the width an admin dragged a catalog form sheet to, under `admin-sheet-width:` keys.
- **`localStorage`** also holds `marte-checkout-session`, the id of the browser's open Checkout Session together with the basket it was opened for, which the payment step writes and the checkout page's session check, the availability check and the next payment step read (see [Checkout](/docs/features/checkout)). Nothing reads it before first paint. The server trusts it only as far as a payment with that id exists: a pending one for the availability check and the update path, and any one for the session check and the confirmation, which treat holding the id as proof of having started the checkout.
- **`sessionStorage`** holds `marte-checkout-draft`, the checkout form's unsent values, and the customer activity flags: `customer-activity:page-view:` plus the path, so a page view is recorded once per tab session, and `customer-activity:cart-abandoned-sent`, so an abandoned cart is reported once.
- **The `marte_time_zone` cookie** holds the browser's IANA time zone. `TranslationsProvider` writes it on the client so the server can format dates in that zone on the next request; see [Display preferences](/docs/architecture/i18n-architecture#display-preferences).
- **Zustand with `persist`** holds the cart in `src/hooks/use-cart-store.ts`, with a `CART_PERSIST_VERSION` of 3 and a per-item type guard so a stale shape is dropped rather than rehydrated.
- **`BroadcastChannel`** (`marte-query-invalidation` in `query.sync.ts`) mirrors to other tabs of the same browser the invalidations of a few admin mutations: coupon changes, which the realtime hub does not carry, and the newsletter subscriber, order and InPost shipment actions. Hub frames are not echoed on it, because every storefront and admin tab receives them on its own socket.

None of these is a source of truth. The cart is re-validated server-side by `check-cart-availability.ts` and again inside `handleCreateCheckoutSession`, which re-reads prices and inventory from D1 and refuses the checkout if anything moved.

## What is not cached

- **Sessions.** Better Auth's signed cookie cache is turned off, and `getRequestSession` also passes `disableCookieCache: true`, so every server-side check reads D1. The cost is one D1 read per request; the benefit is that a banned or signed-out user cannot ride a cached cookie. To keep that from becoming N reads, the lookup is memoized in a `WeakMap` keyed on the `Request` object — not a module global — so concurrent loaders and server functions in one request share one lookup and a new request always revalidates. The browser reads the session the same way: components use `useQuery(getCurrentSessionQuery)`, whose `getCurrentSession` goes through `getRequestSession` and skips the cookie cache. What the browser keeps is that query's result, under the rules above. `auth.client.ts` does not export Better Auth's `useSession`: it would run during server rendering, which TanStack Start's import protection rejects for `*.client.*` files in the server build, and it would send a second session request.
- **Permissions.** `hasPermission` is evaluated from the session's role on every call. No decision is made from cached data.
- **KV.** The `CACHE` namespace is bound in all four environments (development, preview, test and production), and `scripts/verify-bindings.ts` checks that preview and production name a real namespace. It caches no pages or data. Its keys are the email sender flag `email-sender-unavailable:<APP_ENV>`, which `markEmailSenderUnavailable` writes for five minutes and the Better Auth gate reads (see [Resend](/docs/integrations/resend)), and the `incident-alert:<APP_ENV>:<kind>:<reference>` markers that let `sendIncidentAlert` mail each incident once (an hour, or three days for a failed Stripe event). `GET /api/health` reads `health-check`, a key that is never written.
