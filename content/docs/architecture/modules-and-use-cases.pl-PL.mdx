## Sufiksy plików

| Plik                       | Zawiera                                                                        |
| -------------------------- | ------------------------------------------------------------------------------ |
| `<feature>.schema.ts`      | Definicję `sqliteTable`, jej indeksy i `relations`                             |
| `<feature>.zod.ts`         | Schematy wejścia wspólne dla react-hook-form i walidatorów funkcji serwerowych |
| `<feature>.constants.ts`   | Klucze zapytań i mutacji, enumy, rozmiary stron, czasy stale, metadane kolumn  |
| `<feature>.types.ts`       | Typy wiersza i wejścia wyprowadzone ze schematu i kształtów Zod                |
| `<feature>.utils.ts`       | Czyste helpery bez dostępu do bazy i żądania                                   |

## Przypadek użycia mutujący

```ts
const trimmedOrNull = (value: string | undefined) => {
  const trimmed = value?.trim()

  return trimmed === undefined || trimmed === "" ? sql`null` : trimmed
}

export const shipOrder = createServerFn({ method: "POST" })
  .middleware([authorized({ order: ["update"] })])
  .validator((input: zod.input<typeof orderZodSchemas.adminShipOrderInput>) => orderZodSchemas.adminShipOrderInput.parse(input))
  .handler(async ({ data: { orderId, trackingNumber, trackingUrl } }) => {
    const origin = resolveRequestOrigin(getRequest())
    assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
      canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
    )

    await db
      .update(order)
      .set({
        fulfillmentStatus: "shipped",
        shippedAt: new Date(),
        trackingNumber: trimmedOrNull(trackingNumber),
        trackingUrl: trimmedOrNull(trackingUrl),
        updatedAt: new Date(),
      })
      .where(eq(order.id, orderId))

    recordOrderShippedAudit(orderId, {
      detail: trackingNumber?.trim() === "" ? undefined : trackingNumber?.trim(),
    })
    const shippedEmailDelivery = sendOrderShippedEmail(orderId, origin)
    scheduleBackgroundWork(shippedEmailDelivery)
    const shippedEmailSent = await shippedEmailDelivery

    return { ok: true, orderId, shippedEmailSent }
  })

export const shipOrderMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof shipOrder>[0]["data"]) => shipOrder({ data }),
  mutationKey: ORDER_MUTATION_KEYS.SHIP,
})
```

Każdy element jest tu istotny:

- **Middleware** pochodzi z `src/integrations/better-auth/auth.middleware.ts`. `withRequest` przechwytuje nagłówki żądania i normalizuje błędy; `authorized()` wymaga sesji; `authorized({ order: ["update"] })` sprawdza dodatkowo uprawnienie roli z `auth.access.ts`; `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` liczy próby na operację i adres IP.
- **Walidacja** parsuje wejście schematem Zod modułu przed uruchomieniem handlera, więc handler otrzymuje typy `zod.output`.
- **Guardy stanu** mieszkają w module, nie w komponencie. `assertOrderActionState` odrzuca przejścia, które `order.admin-actions.utils.ts` uznaje za niemożliwe.
- **Linki idą za żądaniem.** `resolveRequestOrigin(getRequest())` działa na samym początku, więc żądanie na host, którego ten build nie obsługuje, jest odrzucane z `FORBIDDEN`, zanim zamówienie się zmieni, a e-mail o wysyłce linkuje do wdrożenia, z którego korzysta administrator. Zobacz [Model bezpieczeństwa](/docs/architecture/security-model).
- **Audyt to praca w tle, a na e-mail handler czeka.** Rejestrator wysyła zdarzenie do kolejki Cloudflare, więc nie opóźnia odpowiedzi. Na e-mail handler czeka, bo administrator dowiaduje się, czy wyszedł: `sendOrderShippedEmail` zapisuje porażkę przy zamówieniu i zwraca `false` zamiast rzucać wyjątek, więc odrzucony e-mail nigdy nie cofa wysyłki zamówienia. Ta sama obietnica trafia też do `scheduleBackgroundWork`, więc wysyłka i jej wpis w audycie kończą się nawet wtedy, gdy administrator wcześniej się rozłączy.
- **Opcje mutacji są eksportowane obok funkcji**, z kluczem `ORDER_MUTATION_KEYS.SHIP`.

## Przypadek użycia odczytujący

Odczyty eksportują zamiast tego `queryOptions`, zwykle jako funkcję swojego wejścia, żeby klucz je zawierał:

```ts
export const getAdminOrdersPageQuery = (input: Order["adminPageInput"]) =>
  queryOptions({
    queryFn: () => getAdminOrdersPage({ data: input }),
    queryKey: [...ORDER_QUERY_KEYS.ADMIN.PAGE, input],
    refetchOnMount: false,
    refetchOnWindowFocus: false,
    staleTime: ORDER_QUERY_STALE_MS,
  })
```

Wszystkie paginowane listy administracyjne zwracają `{ hasMore, items, limit, offset, total }` przez `buildListPaginationResult` i `listPaginationParamsFromPage` z `src/modules/_core/utils/pagination.ts`, więc siatka danych nie musi wiedzieć, jaką encję pokazuje.

Publiczne odczyty sklepu używają samego `withRequest` — sesja nie jest wymagana — i zwracają `false` zamiast rzucać wyjątek, gdy nic nie pasuje. Tak `get-product.ts` odróżnia „nie ma takiego opublikowanego produktu” od błędu:

```ts
export const getProduct = createServerFn({ method: "GET" })
  .middleware([withRequest])
  .validator((input: zod.input<typeof productZodSchemas.productByHandleInput>) => productZodSchemas.productByHandleInput.parse(input))
  .handler(async ({ data }) => {
    const prod = await getPublishedProductByHandleQuery.execute({ handle: data.handle })

    if (prod === undefined || !isProductInStock(prod.variants)) {
      return false
    }

    return mapPublishedProductForStorefront(prod, data.locale ?? I18N.DEFAULT_LOCALE)
  })
```

## Klucze zapytań

Klucze to krotki należące do `*.constants.ts` modułu, zagnieżdżone według odbiorcy:

```ts
export const PRODUCT_QUERY_KEYS = {

    BY_HANDLE: ["admin", "products", "by-handle"] as const,
    PAGE: ["admin", "products", "page"] as const,
    STATS: ["admin", "products", "stats"] as const,
  },
  ALL: ["products"] as const,

  LANDING_NEW_ARRIVALS: ["products", "landing-new-arrivals"] as const,
```

Przy przenoszeniu kodu zachowuj wartości krotek. Z tych samych stałych korzystają loadery, komponenty, prefiksy unieważniania w `realtime-invalidation.subscriptions.ts` oraz publikatory w `realtime-invalidation.catalog.server.ts`, więc zmiana krotki po cichu psuje unieważnianie w czasie rzeczywistym.

## Funkcje serwerowe bez granicy RPC

Nie każda operacja jest funkcją serwerową. Dziewięć plików w `src/modules/checkout/use-cases/*.server.ts` eksportuje zwykłe funkcje asynchroniczne. `fulfillCheckout` i `sendPaymentFailedEmail` wołane są wyłącznie z handlera webhooka Stripe, który jest już uwierzytelniony weryfikacją podpisu. `createCheckout`, `supersedeCheckoutSession` i `updateCheckoutDelivery` wołane są z `src/integrations/stripe/stripe.actions.server.ts`, za objętymi limitem żądań `createCheckoutSessionFn` i `updateCheckoutSessionFn`. `countOpenCheckouts` wołany jest z tego samego pliku przed utworzeniem nowego checkoutu, aby policzyć otwarte checkouty adresu i e-maila kupującego. `releaseCheckout` wołany jest z obu miejsc: przez handler webhooka, przez aktualizację checkoutu, która nie powiodła się po wygaszeniu starej sesji, oraz przez taką, która zastaje starą sesję już wygaszoną przez Stripe. `getCheckoutSessionStatus` dociera do tej ostatniej ścieżki przez `releaseExpiredCheckoutSession`, za własnym limitem żądań. `anonymizeEndedCheckouts` wołany jest wyłącznie przez codzienne czyszczenie w `src/lib/retention.ts`, które uruchamia handler `scheduled` Workera. `expireCheckoutsHoldingVariants` wołany jest z `updateCompleteProduct`, za jego `authorized({ product: ["update"] })`, gdy zapis wycofuje produkt ze sprzedaży, i tą samą drogą dociera do `releaseCheckout` dla każdej sesji, którą wygasi. Wystawienie którejkolwiek z nich jako osobnego endpointu tylko poszerzyłoby powierzchnię ataku. E-maile wysyłane przez inne moduły to przypadki użycia tego samego rodzaju, działające tylko na serwerze, na przykład `src/modules/order/use-cases/send-order-shipped-email.server.ts`, wołane przez przypadki użycia, webhooki i konsumentów kolejek, które uznają, że e-mail ma wyjść.

## Wywołanie przypadku użycia z komponentu

Komponenty rozwijają wyeksportowane opcje, tłumaczą błędy przez `useActionError()` z `src/hooks/use-action-error.ts` i unieważniają klucze modułu po sukcesie. `useActionError` mapuje kod `AppError` na `errors.action.<CODE>`, a błąd Better Auth na `pages.auth.errors.<key>`, z `INTERNAL_ERROR` jako wartością domyślną.
