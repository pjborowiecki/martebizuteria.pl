## Moduły

```text
_core                   account                 address
attribute-on-product    audit-log               cart
cart-item               category-on-product     checkout
collection-on-product   content-page            courier
delivery-method         discount                inventory
newsletter-campaign     newsletter-subscriber   option-on-variant
order                   order-address           order-item
order-withdrawal        payment                 price-history
product                 product-attribute       product-category
product-collection      product-image           product-option
product-option-value    product-variant         rate-limit
session                 store-setting           storefront-search
two-factor              user                    user-email-history
verification            wishlist-item
```

Folder w `src/modules` istnieje tylko dla tabeli bazy danych o tej samej nazwie: `product-category` jest właścicielem `product_category`, a `wishlist-item` tabeli `wishlist_item`. Wspólne helpery, które obsługują kilka tabel, trafiają do `_core`, nigdy do osobnego folderu. Przypadek użycia mieszka w module tabeli, którą czyta lub zapisuje, więc lista zamówień klienta jest w `order`, zalogowane urządzenia w `session`, historia logowań w `audit-log`, a profil w `user`; panel administratora, czyli przegląd sprzedaży sklepu, jest w `order`.

39 z nich eksportuje tabele Drizzle, łącznie 42, a `src/integrations/drizzle-orm/drizzle.schemas.ts` re-eksportuje każdą z nich, żeby klient Drizzle, adapter Better Auth i `drizzle-kit` widziały jeden rejestr schematu. `storefront-search` deklaruje wirtualną tabelę FTS5 `storefront_search`, którą tworzy ręcznie napisana migracja i która pozostaje poza tym rejestrem. `_core` jest współdzielonym jądrem i jedynym folderem bez tabeli.

## Sufiksy plików

| Plik                              | Zawiera                                                                                              |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `<module>.schema.ts`              | Definicję `sqliteTable`, jej indeksy i `relations`                                                   |
| `<module>.types.ts`               | Typy wiersza i wejścia wyprowadzone ze schematu i kształtów Zod                                      |
| `<module>.zod.ts`                 | Schematy wejścia wspólne dla react-hook-form i walidatorów funkcji serwerowych                       |
| `<module>.constants.ts`           | Klucze zapytań i mutacji, enumy, kody błędów, rozmiary stron, czasy stale, metadane kolumn           |
| `<module>.accessors.ts`           | Dostęp do danych po stronie serwera: zapytania Drizzle, prepared statements, buildery batchy         |
| `<module>.utils.ts`               | Czyste helpery bez dostępu do bazy, żądania i `cloudflare:workers`, bezpieczne w paczce przeglądarki |
| `use-cases/<verb-noun>.ts`        | Jedno `createServerFn` plus opcje zapytania lub mutacji, które je wołają                             |
| `use-cases/<verb-noun>.server.ts` | Jedną operację wyłącznie serwerową, wołaną przez inny kod serwera; bez endpointu RPC                 |
| `__test__/`                       | Testy, obok modułu i w `use-cases/__test__/`, każdy nazwany od pliku, który testuje                  |

Żaden inny rodzaj pliku nie jest dozwolony w folderze modułu. Gdy zapytanie służy jednej operacji, a accessors przekroczyłyby limit 800 linii, trafia do `use-cases/<verb-noun>.server.ts` tej operacji; gdy limit przekroczyłyby utils, helper potrzebny tylko jednemu przypadkowi użycia leży obok niego. Operacja wyłącznie serwerowa, jak rejestrator dziennika zdarzeń, konsument kolejki albo usunięcie danych konta, to jeden plik `use-cases/<verb-noun>.server.ts`, a helper potrzebujący importu wyłącznie serwerowego nie jest czysty i trafia do accessors albo do przypadku użycia. Stan przeglądarki, jak store Zustanda koszyka w `src/hooks/use-cart-store.ts`, nie jest kodem modułu, podobnie jak śledzenie aktywności w sklepie w `src/presentation/components/custom/customer-activity-tracking.ts`, a buildery treści e-maili zamówień leżą przy szablonach e-maili w `src/presentation/emails/order-email-content.ts`.

`order` to dobry moduł do przeczytania od początku do końca: `order.schema.ts`, `order.types.ts`, `order.zod.ts`, `order.constants.ts`, `order.accessors.ts`, `order.utils.ts` i czterdzieści osiem plików w `use-cases/`.

## Przypadek użycia mutujący

```ts
const filledOrUndefined = (value: string | undefined): string | undefined => {
  const trimmed = value?.trim()

  return trimmed === "" ? undefined : trimmed
}

const trackingColumns = (trackingNumber: string | undefined, trackingUrl: string | undefined) => {
  if (trackingNumber !== undefined) {
    return { trackingNumber, trackingUrl: trackingUrl ?? sql`null` }
  }

  return trackingUrl === undefined ? {} : { trackingUrl }
}

export const shipOrder = createServerFn({ method: "POST" })
  .middleware([authorized({ order: ["update"] })])
  .validator((input: zod.input<typeof orderZodSchemas.adminShipOrderInput>) => orderZodSchemas.adminShipOrderInput.parse(input))
  .handler(async ({ data: { orderId, ...tracking } }) => {
    const origin = resolveRequestOrigin(getRequest())
    const trackingNumber = filledOrUndefined(tracking.trackingNumber)
    assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
      canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
    )

    await transitionOrder(orderId, SHIPPABLE_FULFILLMENT_STATUSES, {
      fulfillmentStatus: "shipped",
      shippedAt: new Date(),
      ...trackingColumns(trackingNumber, filledOrUndefined(tracking.trackingUrl)),
    })

    recordOrderShippedAudit(orderId, { detail: trackingNumber })

    return { email: await announceOrderShipment(orderId, origin), ok: true, orderId }
  })

export const shipOrderMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof shipOrder>[0]["data"]) => shipOrder({ data }),
  mutationKey: ORDER_MUTATION_KEYS.SHIP,
})
```

Każdy element jest tu istotny:

- **Middleware** pochodzi z `src/integrations/better-auth/auth.middleware.ts`. `withRequest` przechwytuje nagłówki żądania i normalizuje błędy; `authorized()` wymaga sesji; `authorized({ order: ["update"] })` sprawdza dodatkowo uprawnienie roli z `auth.access.ts` i odmawia z `FORBIDDEN`, dopóki zachodzi `needsTwoFactorSetup` — czyli dla konta z rolą administracyjną bez uwierzytelniania dwuskładnikowego w buildzie, który go wymaga (production i test); `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` liczy próby na operację i adres IP.
- **Walidacja** parsuje wejście schematem Zod modułu przed uruchomieniem handlera, więc handler otrzymuje typy `zod.output`.
- **Guardy stanu** mieszkają w module, nie w komponencie. `assertOrderActionState` odrzuca przejścia, które `order.utils.ts` uznaje za niemożliwe, a `transitionOrder` z `transition-order.server.ts` powtarza to sprawdzenie w samym zapisie: jego `UPDATE` pasuje tylko do zamówienia, którego status realizacji nadal należy do `SHIPPABLE_FULFILLMENT_STATUSES` i które nie jest anulowane, a gdy żaden wiersz nie pasuje, rzuca błąd konfliktu.
- **Linki idą za żądaniem.** `resolveRequestOrigin(getRequest())` działa na samym początku, więc żądanie na host, którego ten build nie obsługuje, jest odrzucane z `FORBIDDEN`, zanim zamówienie się zmieni, a e-mail o wysyłce linkuje do wdrożenia, z którego korzysta administrator. Zobacz [Model bezpieczeństwa](/docs/architecture/security-model).
- **Audyt to praca w tle, a na e-mail handler czeka.** Rejestrator wysyła zdarzenie do kolejki Cloudflare, więc nie opóźnia odpowiedzi. Na e-mail handler czeka, bo administrator dowiaduje się, czy wyszedł. `announceOrderShipment` najpierw rezerwuje e-mail warunkowym `UPDATE` (`shippedEmailAt` dla e-maila o wysyłce, `trackingEmailNumber` dla późniejszego e-maila z numerem śledzenia), więc powtórne wywołanie zgłasza `alreadySent` zamiast wysyłać drugi raz. `sendOrderShippedEmail` przechodzi przez `deliverOrderEmail` z `deliver-order-email.server.ts`, który zapisuje wynik w dzienniku zdarzeń i zwraca `false` zamiast rzucać wyjątek; nieudana wysyłka jest ponawiana dwa razy w tle, a potem wywołuje alert o incydencie, i odrzucony e-mail nigdy nie cofa wysyłki zamówienia. `awaitOrderEmailNotice` przekazuje obietnicę wysyłki do `scheduleBackgroundWork`, więc wysyłka kończy się nawet wtedy, gdy administrator wcześniej się rozłączy, i zwraca `{ kind, status }` ze `status` równym `sent` lub `failed`, co akcje zamówień w panelu pokazują jako toast.
- **Opcje mutacji są eksportowane obok funkcji**, z kluczem `ORDER_MUTATION_KEYS.SHIP`.

## Przypadek użycia odczytujący

Odczyty eksportują zamiast tego `queryOptions`, zwykle jako funkcję swojego wejścia, żeby klucz je zawierał:

```ts
export const getAdminOrdersPageQuery = (input: Order["adminPageInput"]) =>
  queryOptions({
    queryFn: () => getAdminOrdersPage({ data: input }),
    queryKey: [...ORDER_QUERY_KEYS.ADMIN.PAGE, input],
    refetchOnMount: false,
    refetchOnWindowFocus: false,
    staleTime: ORDER_QUERY_STALE_MS,
  })
```

Wszystkie paginowane listy administracyjne zwracają `{ hasMore, items, limit, offset, total }` przez `buildListPaginationResult` i `listPaginationParamsFromPage` z `src/modules/_core/utils/pagination.ts`, więc siatka danych nie musi wiedzieć, jaką encję pokazuje.

Publiczne odczyty sklepu nie wymagają sesji: większość używa samego `withRequest`, a `search-storefront.ts` zamiast niego `withRateLimit()`. Odczyty produktu, kategorii i kolekcji zwracają `false` zamiast rzucać wyjątek, gdy nic nie pasuje. Tak `get-product.ts` odróżnia „nie ma takiego opublikowanego produktu” od błędu:

```ts
export const getProduct = createServerFn({ method: "GET" })
  .middleware([withRequest])
  .validator((input: zod.input<typeof productZodSchemas.productByHandleInput>) => productZodSchemas.productByHandleInput.parse(input))
  .handler(async ({ data }) => {
    const { handle } = data
    const locale = data.locale ?? I18N.DEFAULT_LOCALE

    const prod = await getPublishedProductByHandleQuery.execute({ handle })

    if (prod === undefined || !isProductInStock(prod.variants)) {
      return false
    }

    return attachPriceReductions(mapPublishedProductForStorefront(prod, locale), await getPriceReductions(prod.variants))
  })
```

`getPriceReductions` czyta historię cen wariantów, których cena jest obniżona, a `attachPriceReductions` ustawia `priceReduction` każdego wariantu w zmapowanym produkcie; obie funkcje pochodzą z modułu `price-history`.

## Klucze zapytań

Klucze to krotki należące do `*.constants.ts` modułu, zagnieżdżone według odbiorcy:

```ts
export const PRODUCT_QUERY_KEYS = {
  ADMIN: {
    ALL: ["admin", "products"] as const,
    BY_HANDLE: ["admin", "products", "by-handle"] as const,
    PAGE: ["admin", "products", "page"] as const,
    STATS: ["admin", "products", "stats"] as const,
  },
  ALL: ["products"] as const,
  BY_HANDLE: ["product"] as const,
  LANDING_NEW_ARRIVALS: ["products", "landing-new-arrivals"] as const,
  RELATED_BY_CATEGORY: ["related-products"] as const,
  STOREFRONT_PAGE: ["products", "storefront-page"] as const,
} as const
```

Przy przenoszeniu kodu zachowuj wartości krotek. Z tych samych stałych korzystają loadery, komponenty, prefiksy unieważniania w `realtime-invalidation.subscriptions.ts` oraz publikatory w `realtime-invalidation.catalog.server.ts`, więc zmiana krotki po cichu psuje unieważnianie w czasie rzeczywistym.

## Funkcje serwerowe bez granicy RPC

Nie każda operacja jest funkcją serwerową. Dwanaście plików w `src/modules/checkout/use-cases/*.server.ts` eksportuje zwykłe funkcje asynchroniczne. `sendPaymentFailedEmail` wołany jest wyłącznie z handlera webhooka Stripe, który jest już uwierzytelniony weryfikacją podpisu. `fulfillCheckout` wołany jest z tego handlera oraz ze strony potwierdzenia zamówienia: gdy `getOrderConfirmation` zastaje płatność wciąż w stanie `pending`, sprawdza limit żądań `checkout-status` i woła `fulfillReturnedCheckoutSession` z `src/integrations/stripe/stripe.fulfillment.server.ts`, który pobiera sesję ze Stripe i tworzy zamówienie tylko wtedy, gdy Stripe zgłasza ją jako zakończoną i opłaconą. `createCheckout`, `supersedeCheckoutSession` i `updateCheckoutDelivery` wołane są z `src/integrations/stripe/stripe.actions.server.ts`, za objętymi limitem żądań `createCheckoutSessionFn` i `updateCheckoutSessionFn`. `countOpenCheckouts` wołany jest z tego samego pliku przed utworzeniem nowego checkoutu, aby policzyć otwarte checkouty adresu i e-maila kupującego. `releaseCheckout` wołany jest z obu miejsc: przez handler webhooka, przez aktualizację checkoutu, która nie powiodła się po wygaszeniu starej sesji, oraz przez taką, która zastaje starą sesję już wygaszoną przez Stripe. `getCheckoutSessionStatus` dociera do tej ostatniej ścieżki przez `releaseExpiredCheckoutSession`, za własnym limitem żądań. `anonymizeEndedCheckouts` wołany jest wyłącznie przez codzienne czyszczenie w `src/lib/retention.ts`, które uruchamia handler `scheduled` Workera. `expireCheckoutsHoldingVariants` wołany jest z `updateCompleteProduct`, za jego `authorized({ product: ["update"] })`, gdy zapis wycofuje produkt ze sprzedaży, i tą samą drogą dociera do `releaseCheckout` dla każdej sesji, którą wygasi. Cztery przypadki użycia zamówień to zwykłe funkcje tego samego rodzaju: `refund-order.server.ts`, `flag-order-dispute.server.ts`, `clear-order-dispute.server.ts` i `undo-failed-refund.server.ts` wołane są wyłącznie z handlera webhooka Stripe w `src/integrations/stripe/stripe.webhooks.ts`. Wystawienie którejkolwiek z nich jako osobnego endpointu tylko poszerzyłoby powierzchnię ataku. E-maile wysyłane przez inne moduły to przypadki użycia tego samego rodzaju, działające tylko na serwerze, na przykład `src/modules/order/use-cases/send-order-shipped-email.server.ts`, wołane przez przypadki użycia, webhooki i konsumentów kolejek, które uznają, że e-mail ma wyjść.

## Wywołanie przypadku użycia z komponentu

Komponenty rozwijają wyeksportowane opcje, tłumaczą błędy przez `useActionError()` z `src/hooks/use-action-error.ts` i unieważniają klucze modułu po sukcesie. `useActionError` mapuje kod `AppError` na `errors.action.<CODE>`, a błąd Better Auth na `pages.auth.errors.<key>`, z `INTERNAL_ERROR` jako wartością domyślną.
