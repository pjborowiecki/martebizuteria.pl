## Sufiksy plików

| Plik                              | Zawiera                                                                              |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| `<feature>.schema.ts`             | Definicję `sqliteTable`, jej indeksy i `relations`                                   |
| `<feature>.zod.ts`                | Schematy wejścia wspólne dla react-hook-form i walidatorów funkcji serwerowych       |
| `<feature>.constants.ts`          | Klucze zapytań i mutacji, enumy, rozmiary stron, czasy stale, metadane kolumn        |
| `<feature>.types.ts`              | Typy wiersza i wejścia wyprowadzone ze schematu i kształtów Zod                      |
| `<feature>.utils.ts`              | Czyste helpery bez dostępu do bazy i żądania                                         |
| `<feature>.accessors.ts`          | Dostęp do danych: zapytania Drizzle, prepared statements, buildery batchy            |
| `<feature>.*.server.ts`           | Helpery wyłącznie serwerowe, które nie są endpointami RPC                            |
| `use-cases/<verb-noun>.ts`        | Jedno `createServerFn` plus opcje zapytania lub mutacji, które je wołają             |
| `use-cases/<verb-noun>.server.ts` | Jedną operację wyłącznie serwerową, wołaną przez inny kod serwera; bez endpointu RPC |

## Przypadek użycia mutujący

```ts
const filledOrUndefined = (value: string | undefined): string | undefined => {
  const trimmed = value?.trim()

  return trimmed === "" ? undefined : trimmed
}

const trackingColumns = (trackingNumber: string | undefined, trackingUrl: string | undefined) => {
  if (trackingNumber !== undefined) {
    return { trackingNumber, trackingUrl: trackingUrl ?? sql`null` }
  }

  return trackingUrl === undefined ? {} : { trackingUrl }
}

export const shipOrder = createServerFn({ method: "POST" })
  .middleware([authorized({ order: ["update"] })])
  .validator((input: zod.input<typeof orderZodSchemas.adminShipOrderInput>) => orderZodSchemas.adminShipOrderInput.parse(input))
  .handler(async ({ data: { orderId, ...tracking } }) => {
    const origin = resolveRequestOrigin(getRequest())
    const trackingNumber = filledOrUndefined(tracking.trackingNumber)
    assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
      canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
    )

    await transitionOrder(orderId, SHIPPABLE_FULFILLMENT_STATUSES, {
      fulfillmentStatus: "shipped",
      shippedAt: new Date(),
      ...trackingColumns(trackingNumber, filledOrUndefined(tracking.trackingUrl)),
    })

    recordOrderShippedAudit(orderId, { detail: trackingNumber })

    return { email: await announceOrderShipment(orderId, origin), ok: true, orderId }
  })

export const shipOrderMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof shipOrder>[0]["data"]) => shipOrder({ data }),
  mutationKey: ORDER_MUTATION_KEYS.SHIP,
})
```

Każdy element jest tu istotny:

- **Middleware** pochodzi z `src/integrations/better-auth/auth.middleware.ts`. `withRequest` przechwytuje nagłówki żądania i normalizuje błędy; `authorized()` wymaga sesji; `authorized({ order: ["update"] })` sprawdza dodatkowo uprawnienie roli z `auth.access.ts` i odmawia z `FORBIDDEN`, dopóki zachodzi `needsTwoFactorSetup` — czyli dla konta z rolą administracyjną bez uwierzytelniania dwuskładnikowego w buildzie, który go wymaga (production i test); `withRateLimit(kind, RATE_LIMITS.SENSITIVE)` liczy próby na operację i adres IP.
- **Walidacja** parsuje wejście schematem Zod modułu przed uruchomieniem handlera, więc handler otrzymuje typy `zod.output`.
- **Guardy stanu** mieszkają w module, nie w komponencie. `assertOrderActionState` odrzuca przejścia, które `order.admin-actions.utils.ts` uznaje za niemożliwe, a `transitionOrder` z `order.admin-action.server.ts` powtarza to sprawdzenie w samym zapisie: jego `UPDATE` pasuje tylko do zamówienia, którego status realizacji nadal należy do `SHIPPABLE_FULFILLMENT_STATUSES` i które nie jest anulowane, a gdy żaden wiersz nie pasuje, rzuca błąd konfliktu.
- **Linki idą za żądaniem.** `resolveRequestOrigin(getRequest())` działa na samym początku, więc żądanie na host, którego ten build nie obsługuje, jest odrzucane z `FORBIDDEN`, zanim zamówienie się zmieni, a e-mail o wysyłce linkuje do wdrożenia, z którego korzysta administrator. Zobacz [Model bezpieczeństwa](/docs/architecture/security-model).
- **Audyt to praca w tle, a na e-mail handler czeka.** Rejestrator wysyła zdarzenie do kolejki Cloudflare, więc nie opóźnia odpowiedzi. Na e-mail handler czeka, bo administrator dowiaduje się, czy wyszedł. `announceOrderShipment` najpierw rezerwuje e-mail warunkowym `UPDATE` (`shippedEmailAt` dla e-maila o wysyłce, `trackingEmailNumber` dla późniejszego e-maila z numerem śledzenia), więc powtórne wywołanie zgłasza `alreadySent` zamiast wysyłać drugi raz. `sendOrderShippedEmail` przechodzi przez `deliverOrderEmail` z `order.email-delivery.server.ts`, który zapisuje wynik w dzienniku zdarzeń i zwraca `false` zamiast rzucać wyjątek; nieudana wysyłka jest ponawiana dwa razy w tle, a potem wywołuje alert o incydencie, i odrzucony e-mail nigdy nie cofa wysyłki zamówienia. `awaitOrderEmailNotice` przekazuje obietnicę wysyłki do `scheduleBackgroundWork`, więc wysyłka kończy się nawet wtedy, gdy administrator wcześniej się rozłączy, i zwraca `{ kind, status }` ze `status` równym `sent` lub `failed`, co akcje zamówień w panelu pokazują jako toast.
- **Opcje mutacji są eksportowane obok funkcji**, z kluczem `ORDER_MUTATION_KEYS.SHIP`.

## Przypadek użycia odczytujący

Odczyty eksportują zamiast tego `queryOptions`, zwykle jako funkcję swojego wejścia, żeby klucz je zawierał:

```ts
export const getAdminOrdersPageQuery = (input: Order["adminPageInput"]) =>
  queryOptions({
    queryFn: () => getAdminOrdersPage({ data: input }),
    queryKey: [...ORDER_QUERY_KEYS.ADMIN.PAGE, input],
    refetchOnMount: false,
    refetchOnWindowFocus: false,
    staleTime: ORDER_QUERY_STALE_MS,
  })
```

Wszystkie paginowane listy administracyjne zwracają `{ hasMore, items, limit, offset, total }` przez `buildListPaginationResult` i `listPaginationParamsFromPage` z `src/modules/_core/utils/pagination.ts`, więc siatka danych nie musi wiedzieć, jaką encję pokazuje.

Publiczne odczyty sklepu nie wymagają sesji: większość używa samego `withRequest`, a `search-storefront.ts` zamiast niego `withRateLimit()`. Odczyty produktu, kategorii i kolekcji zwracają `false` zamiast rzucać wyjątek, gdy nic nie pasuje. Tak `get-product.ts` odróżnia „nie ma takiego opublikowanego produktu” od błędu:

```ts
export const getProduct = createServerFn({ method: "GET" })
  .middleware([withRequest])
  .validator((input: zod.input<typeof productZodSchemas.productByHandleInput>) => productZodSchemas.productByHandleInput.parse(input))
  .handler(async ({ data }) => {
    const { handle } = data
    const locale = data.locale ?? I18N.DEFAULT_LOCALE

    const prod = await getPublishedProductByHandleQuery.execute({ handle })

    if (prod === undefined || !isProductInStock(prod.variants)) {
      return false
    }

    return attachPriceReductions(mapPublishedProductForStorefront(prod, locale), await getPriceReductions(prod.variants))
  })
```

`getPriceReductions` czyta historię cen wariantów, których cena jest obniżona, a `attachPriceReductions` ustawia `priceReduction` każdego wariantu w zmapowanym produkcie; obie funkcje pochodzą z modułu `price-history`.

## Klucze zapytań

Klucze to krotki należące do `*.constants.ts` modułu, zagnieżdżone według odbiorcy:

```ts
export const PRODUCT_QUERY_KEYS = {
  ADMIN: {
    ALL: ["admin", "products"] as const,
    BY_HANDLE: ["admin", "products", "by-handle"] as const,
    PAGE: ["admin", "products", "page"] as const,
    STATS: ["admin", "products", "stats"] as const,
  },
  ALL: ["products"] as const,
  BY_HANDLE: ["product"] as const,
  LANDING_NEW_ARRIVALS: ["products", "landing-new-arrivals"] as const,
  RELATED_BY_CATEGORY: ["related-products"] as const,
  STOREFRONT_PAGE: ["products", "storefront-page"] as const,
} as const
```

Przy przenoszeniu kodu zachowuj wartości krotek. Z tych samych stałych korzystają loadery, komponenty, prefiksy unieważniania w `realtime-invalidation.subscriptions.ts` oraz publikatory w `realtime-invalidation.catalog.server.ts`, więc zmiana krotki po cichu psuje unieważnianie w czasie rzeczywistym.

## Funkcje serwerowe bez granicy RPC

Nie każda operacja jest funkcją serwerową. Dziewięć plików w `src/modules/checkout/use-cases/*.server.ts` eksportuje zwykłe funkcje asynchroniczne. `sendPaymentFailedEmail` wołany jest wyłącznie z handlera webhooka Stripe, który jest już uwierzytelniony weryfikacją podpisu. `fulfillCheckout` wołany jest z tego handlera oraz ze strony potwierdzenia zamówienia: gdy `getOrderConfirmation` zastaje płatność wciąż w stanie `pending`, sprawdza limit żądań `checkout-status` i woła `fulfillReturnedCheckoutSession` z `src/integrations/stripe/stripe.fulfillment.server.ts`, który pobiera sesję ze Stripe i tworzy zamówienie tylko wtedy, gdy Stripe zgłasza ją jako zakończoną i opłaconą. `createCheckout`, `supersedeCheckoutSession` i `updateCheckoutDelivery` wołane są z `src/integrations/stripe/stripe.actions.server.ts`, za objętymi limitem żądań `createCheckoutSessionFn` i `updateCheckoutSessionFn`. `countOpenCheckouts` wołany jest z tego samego pliku przed utworzeniem nowego checkoutu, aby policzyć otwarte checkouty adresu i e-maila kupującego. `releaseCheckout` wołany jest z obu miejsc: przez handler webhooka, przez aktualizację checkoutu, która nie powiodła się po wygaszeniu starej sesji, oraz przez taką, która zastaje starą sesję już wygaszoną przez Stripe. `getCheckoutSessionStatus` dociera do tej ostatniej ścieżki przez `releaseExpiredCheckoutSession`, za własnym limitem żądań. `anonymizeEndedCheckouts` wołany jest wyłącznie przez codzienne czyszczenie w `src/lib/retention.ts`, które uruchamia handler `scheduled` Workera. `expireCheckoutsHoldingVariants` wołany jest z `updateCompleteProduct`, za jego `authorized({ product: ["update"] })`, gdy zapis wycofuje produkt ze sprzedaży, i tą samą drogą dociera do `releaseCheckout` dla każdej sesji, którą wygasi. Cztery przypadki użycia zamówień to zwykłe funkcje tego samego rodzaju: `refund-order.server.ts`, `flag-order-dispute.server.ts`, `clear-order-dispute.server.ts` i `undo-failed-refund.server.ts` wołane są wyłącznie z handlera webhooka Stripe w `src/integrations/stripe/stripe.webhooks.ts`. Wystawienie którejkolwiek z nich jako osobnego endpointu tylko poszerzyłoby powierzchnię ataku. E-maile wysyłane przez inne moduły to przypadki użycia tego samego rodzaju, działające tylko na serwerze, na przykład `src/modules/order/use-cases/send-order-shipped-email.server.ts`, wołane przez przypadki użycia, webhooki i konsumentów kolejek, które uznają, że e-mail ma wyjść.

## Wywołanie przypadku użycia z komponentu

Komponenty rozwijają wyeksportowane opcje, tłumaczą błędy przez `useActionError()` z `src/hooks/use-action-error.ts` i unieważniają klucze modułu po sukcesie. `useActionError` mapuje kod `AppError` na `errors.action.<CODE>`, a błąd Better Auth na `pages.auth.errors.<key>`, z `INTERNAL_ERROR` jako wartością domyślną.
