## Kierunki importów

| Katalog                      | Może importować                                                                                                                                                                                                               | Nie może importować                                                                     |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `src/routes`                 | warstwę prezentacji, opcje zapytań i mutacji modułów, guardy tras, i18n, Fumadocs, `src/data`, `src/lib`, współdzielone hooki, oba providery (w `__root.tsx`), nazwy hubów i prefiksy zapytań realtime, `stripe.constants.ts` | `db` ani żadnego klienta dostawcy poza funkcją serwerową lub serwerowym handlerem trasy |
| `src/presentation`           | opcje zapytań modułów, schematy Zod, stałe, typy, czyste helpery i magazyny klienta, hooki, `src/data`, `src/lib`, tablicę `ROUTES`, integracje bezpieczne dla przeglądarki                                                   | `drizzle.database.ts`, `auth.server.ts`, `stripe.server.ts`, Resend                     |
| `src/modules/*/use-cases`    | integracje (`db`, `authorized`, `sendEmail`, Stripe, R2), `_core`, akcesory i schematy modułu, szablony e-maili, `src/presentation/branding`                                                                                  | komponentów                                                                             |
| `src/modules/*.accessors.ts` | `db`, `drizzle.utils.ts` i `drizzle.batch.ts`, schematy, stałe, typy i helpery modułów, akcesory innych modułów, narzędzia `_core`                                                                                            | guardów tras, komponentów, przypadków użycia innych modułów                             |
| `src/integrations`           | `_core`, schematy, stałe i akcesory modułów, helpery `*.server.ts` i przypadki użycia, do których dostawca wraca zwrotnie, `src/presentation/branding`                                                                        | komponentów, poza jednym, który `fumadocs.docs.ts` ładuje leniwie                       |
| `src/server.ts`              | handler Start, `resolveLocale`, handler WebSocket realtime, konsumentów kolejek newslettera i dziennika zdarzeń, `src/lib`                                                                                                    | bazy danych, Better Auth ani SDK Stripe bezpośrednio                                    |

Z modułów i integracji do warstwy prezentacji prowadzą dwa rodzaje importów. `_core/constants/api.ts`, `auth.server.ts`, `stripe.server.ts`, `resend.send.ts` i `resend.sender.ts` czytają nazwę sklepu albo domenę z `src/presentation/branding/app.ts`. Sześć plików stałych modułów (`discount`, `newsletter-subscriber`, `product-attribute`, `product-category`, `product-collection` i `user`) bierze `CATALOG_ADMIN_RECORD_ID_COLUMN_WIDTH_PX` z `src/presentation/components/custom/pages/admin/catalog/lib/catalog-admin-datagrid.constants.ts` dla kolumny identyfikatora rekordu w swoich siatkach panelu. Wyjątkiem dotyczącym komponentów jest `loadDocsPage` w `fumadocs.docs.ts`, który dynamicznie importuje `custom/docs-content.tsx`, żeby wstępnie załadować skompilowaną stronę przed jej renderem.

Integracje bezpieczne dla przeglądarki to te bez odczytu `env` i bez markera server-only. Kod klienta importuje je bezpośrednio: `i18n.config.ts`, `i18n.paths.ts`, `i18n.utils.ts`, `i18n.display.ts`, `i18n.messages.ts`, `auth.client.ts`, `auth.access.ts`, `auth.errors.ts`, `auth.zod.ts`, `auth.constraints.ts`, `auth.routes.ts`, `stripe.client.ts`, `stripe.appearance.ts`, `stripe.checkout.ts`, `stripe.checkout.processing.ts`, `stripe.constants.ts`, `stripe.errors.ts`, `stripe.utils.ts`, `inpost.constants.ts`, `inpost.queries.ts`, `inpost.utils.ts`, `inpost.zod.ts`, `media.zod.ts`, `gsap.config.ts`, `lenis.instance.ts`, `lenis.scroll.ts`, `mdxeditor.plugins.ts`, `react-day-picker.locale.ts`, `realtime-invalidation.protocol.ts`, `realtime-invalidation.subscriptions.ts`, `query.invalidation.ts` i `query.sync.ts`. Komponenty importują też `auth.session.ts`, `i18n.display-preferences.ts`, `media.mutations.ts` i `fumadocs.docs.ts` ze względu na eksportowane przez nie funkcje serwerowe i opcje zapytań; handlery z tych plików są usuwane z bundla klienta przy kompilacji.

## Granice kodu wyłącznie serwerowego

- **Funkcje serwerowe.** TanStack Start usuwa z bundla przeglądarki każdy handler `createServerFn` i zastępuje wywołanie żądaniem RPC. Dlatego `src/hooks/use-wishlist.ts` i `wishlist-grid.tsx` mogą zaimportować `toggleWishlistItemMutation` z `toggle-wishlist-item.ts`, który importuje też `db`.
- **Ochrona importów.** Ochrona importów TanStack Start działa z ustawieniami domyślnymi (`vite.config.ts` jej nie konfiguruje). W środowisku klienta blokuje pliki o nazwach `*.server.*`, pliki importujące marker `@tanstack/react-start/server-only` oraz `@tanstack/react-start/server`. Zablokowany import, który przetrwa kompilację funkcji serwerowych, przerywa `vp build`; w `vp dev` zastępuje go mock, który loguje błąd przy użyciu. Importy używane wyłącznie przez usunięty przy kompilacji handler nie są naruszeniem.
- **Marker server-only.** Sześć plików zaczyna się od `import "@tanstack/react-start/server-only"`: `drizzle.database.ts`, `src/lib/rate-limit.ts`, `src/lib/background.ts`, `src/lib/retention.ts`, `src/lib/sitemap.ts` i `src/lib/request.ts`. Inne pliki odczytujące bindingi lub sekrety nie mają markera: większość nosi nazwę `*.server.ts` (`auth.server.ts`, `stripe.server.ts`), `resend.config.ts` i `resend.send.ts` importują wyłącznie pliki `*.server.ts`, a `media.mutations.ts` czyta `env` tylko wewnątrz handlera swojej funkcji serwerowej.
- **Sufiks `.server.ts`** oznacza pliki modułów i integracji osiągalne wyłącznie z funkcji serwerowej, trasy serwerowej albo punktu wejścia Workera — `find-settled-order.server.ts`, `find-pending-checkout.server.ts`, `schedule-audit-log.server.ts`, `save-complete-product.server.ts` i pozostałe. Sufiks mówi czytającemu, gdzie plik działa, a zarazem jest wzorcem plików, który ochrona importów blokuje po stronie klienta.
- **Funkcje zależne od środowiska.** `createServerOnlyFn` opakowuje kod działający wyłącznie na serwerze (`getRequestSession`). `createIsomorphicFn` dostarcza osobne implementacje dla każdego środowiska (`getCurrentLocale`, `getCurrentPathname` w `i18n.utils.ts`, `getAssetCdnBase` w `src/lib/url.ts`). `createClientOnlyFn` opakowuje wywołania działające wyłącznie w przeglądarce, na przykład żądania klienta Better Auth w formularzach uwierzytelniania.
- **Bindingi i sekrety** pochodzą z `env` w `cloudflare:workers`. Odczytuje go wyłącznie kod serwerowy: klienci integracji i pliki `*.server.ts`, pliki funkcji serwerowych, takie jak `media.mutations.ts`, serwerowe handlery `src/routes/api/health.ts`, `webhooks.stripe.ts` i `webhooks.inpost.ts` oraz Durable Object. `src/lib/url.ts` czyta go tylko w gałęzi `.server()` funkcji `getAssetCdnBase`; gałąź `.client()` czyta `import.meta.env.VITE_R2_URL`. `src/server.ts` dostaje `env` jako argument `fetch` i przekazuje go dalej w kontekście żądania.

```ts
import "@tanstack/react-start/server-only"

import { env } from "cloudflare:workers"

import { drizzle } from "drizzle-orm/d1"

import * as schema from "~/src/integrations/drizzle-orm/drizzle.schemas"

export const db = drizzle(env.DB, { schema })
```

`bun run build:preview` i `bun run build:production` kończą się wywołaniem `bun scripts/verify-build.ts <environment>`, które przerywa build, jeśli bundle klienta wciąż zawiera niezbundlowany import `cloudflare:workers` lub `node:*`. Ten skrypt jest mechaniczną kontrolą stojącą za powyższymi regułami.

## Kolejność importów jest diagramem warstw

`vite.config.ts` definiuje 17 własnych grup importów w `fmt.sortImports`, a formater je stosuje. Czytanie grup od góry do dołu to czytanie kierunku zależności:

```text
server-only → cloudflare → react → builtin/external → platform → providers →
integrations → modules → routes → hooks → constants → types → lib → branding →
components-shadcn → components-custom → components-other → styles → relatywne
```

`bun run format` (albo `bun run check:fix`) przepisuje blok importów do tej kolejności, a `bun run check` kończy się błędem, dopóki kolejność się nie zgadza, więc plik, którego importy wyglądają dziwnie, to zwykle plik w niewłaściwej warstwie.

## Aliasy

`tsconfig.json` mapuje dwa prefiksy:

| Prefiks         | Wskazuje na   | Używany do                                               |
| --------------- | ------------- | -------------------------------------------------------- |
| `~/*`           | `./*`         | Każdy import wewnętrzny, zawsze od katalogu repozytorium |
| `collections/*` | `./.source/*` | Kolekcje Fumadocs generowane przez `bun run content`     |

Ręcznie pisany kod aplikacji w `src` importuje wyłącznie przez `~/`. Ścieżki relatywne zostają w plikach generowanych (`src/routeTree.gen.ts`, `src/types/worker-configuration.d.ts` oraz `schema.ts` i `relations.ts` z drizzle-kit w `src/integrations/drizzle-orm/migrations`), we wzorcach `import.meta.glob` w `src/integrations/use-intl/i18n.messages.ts`, `src/platform/testing/lib/messages.ts` i `src/platform/testing/mocks/migrations.ts`, które Vite rozwiązuje względem pliku, oraz w około 80 plikach testów, które relatywnie importują sąsiednie fixture'y albo testowany plik. `src/integrations/fumadocs/fumadocs.config.ts`, który `fumadocs-mdx` ładuje jeszcze przed dostępnością aliasu, importuje wyłącznie pakiety.
