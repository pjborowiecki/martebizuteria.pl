## Two layers, only one of which is a boundary

**Route guards** in `src/integrations/better-auth/auth.routes.ts` run in `beforeLoad` and redirect. Each layout passes the guard itself, as in `beforeLoad: requireAdmin`:

| Guard                | Used by                                           | Behaviour                                                                                      |
| -------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `requireSignedIn`    | Building block for the others                     | Redirects to `/auth/sign-in` without a session                                                 |
| `requireAdminRole`   | `admin_.security.tsx`                             | Also requires `hasAdminAccess(role)`, otherwise `/account/overview`                            |
| `requireAdmin`       | `admin.tsx`, `admin_.orders.$orderId.summary.tsx` | `requireAdminRole`, then sends an admin without two-factor authentication to `/admin/security` |
| `requireCustomer`    | `account.tsx`                                     | Sends an admin to `/admin` instead                                                             |
| `redirectIfSignedIn` | `auth.tsx`                                        | Sends a signed-in user to a safe `?redirect` path, otherwise to `postAuthRouteFor(user)`       |

`requireSignedIn`, `requireAdminRole`, `requireAdmin` and `requireCustomer` resolve to `{ user }`, which becomes route context; `account.overview.tsx` reads it with `AccountRoute.useRouteContext()`. The guards only read the session, through `loadRouteSession`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

`requireSignedIn`, and through it `requireAdminRole`, `requireAdmin` and `requireCustomer`, passes `recheck: true`, so a navigation into `/account` or `/admin` fetches the session again. A link preload and `redirectIfSignedIn`, which passes `recheck: false`, reuse a cached session younger than 60 seconds. The session a guard loads stays in the TanStack Query cache for components to read and, on a server render, is serialized into the page. A change of user is handled in one place, `clearCacheOnUserChange` in `auth.session.ts`: when the session switches to a different user, it removes every cached query except the session itself and the translation message catalogues. See [Caching and SSR](/docs/architecture/caching-and-ssr) for the details.

An anonymous visitor to `/account` or `/admin` is sent to `/auth/sign-in` with `?redirect=` set to `route.location.publicHref`, the localized public path they asked for, such as `/en-US/account/orders/order-1`. `resolveSafeRedirect`, internal to the module, checks the value both when the sign-in link is built and before the `/auth` guard follows it. It keeps the value only when it is a string matching `SAME_SITE_PATH_PATTERN`: printable ASCII only, a single leading slash and no backslash. Absolute URLs, protocol-relative `//` values, whitespace, control characters and non-ASCII characters are dropped, so the parameter cannot become an open redirect:

```ts
const SAME_SITE_PATH_PATTERN = /^\/(?![/\\])[!-[\]-~]*$/u
```

`redirectIfSignedIn` sends a signed-in visitor to that value with `redirect({ href })`, otherwise to `postAuthRouteFor(user)`: `/admin` for an admin, `/account/overview` for a customer. A server-rendered redirect therefore keeps the visitor's language, and on the client the router re-localizes it to the current language.

After a successful password sign-in or two-factor challenge, the form calls `usePostAuthRedirect` from `src/hooks/use-post-auth-redirect.ts`:

```ts
export const usePostAuthRedirect = (): (() => Promise<void>) => {
  const queryClient = useQueryClient()
  const router = useRouter()

  return useCallback(async () => {
    queryClient.removeQueries({ exact: true, queryKey: getCurrentSessionQuery.queryKey })
    router.clearCache()
    await router.invalidate()
  }, [queryClient, router])
}
```

It removes the cached session entry only, then clears the router's cached matches and invalidates the router. The `/auth` layout guard runs again, fetches the fresh session and redirects as described above. When the fresh session arrives, `clearCacheOnUserChange` forgets what was cached while signed out. The forms never choose a destination themselves.

Google sign-in, in `src/presentation/components/custom/pages/auth/hooks/use-oauth-sign-in.ts`, passes the page the button was clicked on as the `callbackURL`: `location.publicHref` from `useLocation`, for example `/en-US/auth/sign-in?redirect=…`. After the provider round trip the browser lands on that auth page, and `redirectIfSignedIn` sends the user on exactly as after a password sign-in.

Signing out is a full page load that discards the cache: the account sidebar goes to `/`, the admin sidebar to `/auth/sign-in`.

Guards decide what a user _sees_. They also run in the browser, so they are navigation UX, not protection.

**Server function middleware** in `auth.middleware.ts` is the actual boundary, because a server function is a public HTTP endpoint that is reachable whether or not its page was ever loaded:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && (!hasPermission({ permission, role: session.user.role }) || needsTwoFactorSetup(session.user))) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

Across `src/modules` and `src/integrations`, `authorized()` appears 116 times: 28 bare (a session is enough; one of them is inside `recentSignIn`), and the rest with a permission — `product: ["read"]` ×14, `product: ["update"]` ×10, `product: ["create"]` ×4, `product: ["delete"]` ×4, `settings: ["manage"]` ×14, `order: ["read"]` ×7, `order: ["update"]` ×13, `order: ["update", "refund"]` ×1 (`refundAdminOrder`), `content: ["read"]` ×3, `content: ["update"]` ×3, and the Better Auth admin statements `user: ["list"]` ×8, `user: ["get"]` ×1, `user: ["update"]` ×2, `user: ["delete"]` ×2 and `user: ["set-role"]` ×2.

## Roles and permissions

`auth.access.ts` builds the access control from Better Auth's `createAccessControl`:

- **Roles**: `admin` and `customer`; `DEFAULT_ROLE` is `customer` and `ADMIN_PANEL_ROLES` is `["admin"]`.
- **Resources and actions**: `order: [read, update, refund]`, `product: [create, read, update, delete, publish]`, `settings: [manage]`, plus Better Auth's own `defaultStatements` for `user` and `session`.
- **`ROLES_CONFIG`** grants the admin role every statement plus `adminAc.statements`; the customer role is granted nothing.
- **`hasAdminAccess(role)`** is the coarse check used by the route guards and the WebSocket handshake; `hasPermission({ permission, role })` is the fine-grained check used by `authorized()`.
- **`needsTwoFactorSetup({ role, twoFactorEnabled })`** is true for an admin without two-factor authentication. `requireAdmin` sends that admin to `/admin/security`, `authorized()` refuses them every permission, the admin WebSocket handshake answers `401`, and `hooks.before` refuses Better Auth's `/admin/*` endpoints with `ADMIN_TWO_FACTOR_REQUIRED`. Admins sign in with a password and a two-factor code only: `session.create.before` refuses a Google sign-in for an admin, because the `twoFactor` plugin never asks for the code on that path. See [Better Auth](/docs/integrations/better-auth#two-factor-authentication-for-admins).

Because the customer role holds no statements, the resource matrix currently behaves as a binary admin check. It is worth keeping in mind before adding a third role: the matrix is already there, and money already has its own action, since `refundAdminOrder` and `cancelOrder` on a paid order ask for `order: ["refund"]` on top of `order: ["update"]`, so a role granted only `order: ["read", "update"]` could run orders without refunding them.

## Admin access

Who holds the `admin` role changes in one place, **Settings › Team**, through `grantAdminAccess` and `revokeAdminAccess` in `src/modules/user/use-cases/`. Both require `user: ["set-role"]` and the `recentSignIn` middleware, refuse the caller's own account, give access only to a verified, unblocked customer account, and never remove the last admin: removing access is one conditional `UPDATE` that goes through only while the acting admin, someone other than the account, still holds the role, and it deletes the account's sessions. See [Admin settings: Team](/docs/features/admin-settings#team).

Better Auth's admin plugin can change roles as well, so `guardAuthRequest` (the `hooks.before` in `auth.hooks.server.ts`) refuses `/admin/set-role`, and `/admin/update-user` and `/admin/create-user` when their body carries `role` or `data.role`, with `403 ROLE_MANAGED_IN_TEAM_SETTINGS`, whoever calls them. Otherwise an admin could skip every rule above with a direct request. Nothing in the app calls those paths with a role.

Admin accounts cannot be deleted. The self-service `/delete-user` refuses an account with admin access in `prepareSelfServiceDeletion` before anything is erased, `deleteCustomer` refuses an admin target, and `guardAuthRequest` refuses `/admin/remove-user` for one, all with `CANNOT_DELETE_ADMIN`. The admin access has to be removed first, and the Team rules never remove the last admin's.

`recentSignIn` (`auth.middleware.ts`) runs `authorized()` and then refuses a session created more than `SESSION_FRESH_AGE_IN_SECONDS` (24 hours) ago with `403 SESSION_NOT_FRESH`, so a stolen older session cookie cannot hand out admin access or add a password. It guards the two role changes and `setAccountPassword`, and `isRecentSignIn` lets `listAdminTeam` tell the page beforehand.

## Ownership is compiled into the SQL

Customer-facing reads and writes never trust an id from the input. They filter by `context.auth.user.id` inside the query:

```ts
where: and(eq(order.id, orderId), eq(order.userId, context.auth.user.id)),
```

The same pattern appears in `list-customer-orders.ts`, `list-customer-sessions.ts`, `list-customer-login-history.ts`, `get-customer-overview.ts`, `revoke-customer-session.ts`, `revoke-other-customer-sessions.ts`, `update-customer-phone.ts`, `get-customer-order-withdrawal.ts`, `withdraw-from-customer-order.ts` and all five address use cases. A foreign id returns no row, so there is nothing to filter out afterwards and nothing to leak. The public withdrawal form, `withdraw-from-guest-order.ts`, finds an order only by its number together with the e-mail address it was placed with, returns nothing whether or not it found one, and never returns the order's contents.

`revoke-customer-session.ts` additionally refuses to revoke the caller's own session, and `delete-customer.ts` refuses to delete the acting admin or any other admin account.

## Sessions

- Better Auth stores sessions in D1 through `drizzleAdapter(db, { provider: "sqlite", schema })`, with `storeSessionInDatabase: true` and **no `secondaryStorage`** — KV was rejected for sessions, verification tokens and rate-limit counters because it is eventually consistent and cannot do an atomic consume-and-increment.
- `useSecureCookies` is on outside `development` and `test` (`isLocalMode(import.meta.env.MODE)`).
- Allowed hosts are fixed per build mode by `appHostsForMode` in `_core/constants/api.ts`: `martebizuteria.pl` in production, `preview.martebizuteria.pl` in preview, `localhost:3000` and `127.0.0.1:3000` locally, plus the matching `workers.dev` hostnames.
- The same list decides every absolute link the app builds itself. `resolveRequestOrigin(request)` in `src/lib/request.ts` takes the origin from `request.url` only, never from the `Host`, `Origin`, `Referer` or `X-Forwarded-*` headers, and throws `AppError(FORBIDDEN)` unless the host and port are on `appHostsForMode(import.meta.env.MODE)` and the protocol is `https:` (or `http:` on `localhost:3000` and `127.0.0.1:3000`). The newsletter, shipping and goodbye emails and the Stripe `return_url` are built from that origin, so they point at the address that was used, and a forged or unknown host is refused instead of being echoed into a link. The order confirmation is sent from the Stripe webhook, so it takes the origin of the session's `return_url` instead, which the checkout wrote and which arrives inside the signature-checked event. `resolveDeploymentOrigin` accepts that origin only on a host some deployment serves (`isDeploymentHost`), because development and preview share the Stripe test account and the database, and refuses anything else. `APP_URL` is kept for the canonical production address in SEO metadata.
- `getRequestSession` bypasses the cookie cache (`disableCookieCache: true`) and memoizes the result in a `WeakMap` keyed on the `Request`.
- `getCurrentSession`, the server function behind `getCurrentSessionQuery`, projects the session before returning it, dropping `session.token`:

  ```ts
  const toClientSession = ({ session: { token: _token, ...session }, user }: RequestSession) => ({ session, user })
  ```

- `tanstackStartCookies()` is the last plugin in the list, so cookies set during a server function reach the response.
- `multiSession({ maximumSessions: 5 })` caps concurrent sessions; `verification: { storeIdentifier: "hashed" }` means verification identifiers are hashed at rest; `account.encryptOAuthTokens` encrypts OAuth tokens.
- Email verification is required before sign-in (`requireEmailVerification: true`, `sendOnSignUp: true`, `autoSignInAfterVerification: true`), and `resolveEmailVerificationCallbackUrl` rewrites a storefront-home callback to `/account/overview?verified=true` so a verified user lands somewhere useful.
- A completed password reset signs the account out on every device (`revokeSessionsOnPasswordReset: true`), so a session opened before the reset, an intruder's included, is refused from its next request. `onPasswordReset` emails the customer that the password changed, with advice for someone who did not change it. See [Better Auth](/docs/integrations/better-auth#password-reset).
- Sign-up, password reset and change-email keep their generic answer when Resend refuses their email, because Better Auth sends it only when an account does or does not exist. For the same reason those refusals never set the email sender flag: only emails that go out for any address (newsletter, order, account-deleted), or only to whoever just used the account's reset link (password-changed), can set it, and while it is set the `hooks.before` gate refuses the four email-sending endpoints for every address alike. The exception is a signed-out call to `/send-verification-email`, where Better Auth passes the hook's error through: while single sends fail, an unconfirmed account gets `503 EMAIL_DELIVERY_FAILED` where any other address gets `200`. That reveals only unconfirmed accounts, only during a delivery failure, at three requests per minute per IP. See [Better Auth](/docs/integrations/better-auth#email-delivery-gate).

## Rate limits

Two limiters share the `rate_limit` table and its counting function, `withinRateLimit` in `src/lib/rate-limit.ts`.

**Better Auth's own**, configured in `auth.server.ts` with `customStorage: authRateLimitStorage`, a 100-request default per 60 s window and the custom rules of `RATE_LIMIT_CUSTOM_RULES` in `auth.constants.ts`:

| Route                     | Max per minute |
| ------------------------- | -------------- |
| `/sign-in/email`          | 5              |
| `/sign-up/email`          | 3              |
| `/request-password-reset` | 3              |
| `/reset-password`         | 5              |

`authRateLimitStorage` counts each `<ip>|<path>` key under its rule with `withinRateLimit` and refuses with the rule's window as `X-Retry-After`. Better Auth's `storage: "database"` is not used: whenever one of its counters started a new window it deleted every `rate_limit` row whose `last_request` was more than 60 seconds old, which would have taken the e-mail caps below with it a minute after they began.

**The application's own**, `withRateLimit(kind, limit)`, or `assertWithinRateLimit(kind, limit, requestHeaders)` for a handler that counts only some of its calls, both over `withinRateLimit` in `src/lib/rate-limit.ts`. `RATE_LIMITS` defines `SENSITIVE` (3/60 s), `TOKEN` (5/60 s), `CHECKOUT` (10/60 s) and `BROWSING` (120/60 s), and the counter is a single atomic D1 upsert:

```ts
.onConflictDoUpdate({
  set: {
    count: sql`case when ${rateLimit.lastRequest} <= ${windowStart} then 1 else ${rateLimit.count} + 1 end`,
    lastRequest: sql`case when ${rateLimit.lastRequest} <= ${windowStart} then ${now} else ${rateLimit.lastRequest} end`,
  },
  setWhere: sql`${rateLimit.lastRequest} <= ${windowStart} or ${rateLimit.count} < ${limit}`,
  target: rateLimit.key,
})
```

The key is `${kind}:${clientAddress(headers)}`, and `clientAddress` reads **only** `cf-connecting-ip`, which a client cannot spoof. If the counter storage fails the request is refused, not admitted. Currently applied to `checkout-create`, `checkout-update`, `checkout-status`, `discount-validate`, `create-user-address`, `update-customer-phone`, `revoke-other-customer-sessions`, `search-storefront`, `search-storefront-products` (only catalog listings that carry `q`), `record-customer-activity`, `withdraw-from-customer-order` and `withdraw-from-guest-order`. Limits are per IP; there is no per-account lockout.

Note that `resolveRequestIp` in `src/lib/request.ts` — used only for the _audit log_ — falls back to `x-forwarded-for`, which is client-spoofable. Rate limiting is unaffected because it does not use that helper, and the open-checkout limit keys the address with `clientAddress` too.

### Checkout holds

A new checkout reserves stock for up to 32 minutes, and anyone can start one as a guest, so the rate limit alone would let one script keep the catalogue reserved. `handleCreateCheckoutSession` therefore also refuses a client address that already has five open checkouts or an email that has three; the open-checkout count keys the address with the same `clientAddress`. Each line is capped at ten of one piece by the server function's schema. Updating an open checkout is not counted, but every update renews the hold with a replacement session, so `handleUpdateCheckoutSession` refuses with `SESSION_CLOSED` once the checkout is `CHECKOUT_SESSION_LIFETIME_SECONDS` old, after expiring its session and returning its stock; holding stock longer takes a new checkout, which the caps count again, so one checkout holds stock for at most about an hour. Nothing tells a person from a script, so a script can hold stock up to these caps from every client address it uses. The count and the reservation are separate statements, so simultaneous requests can each pass the count, and the per-address rate limit bounds how many get through. See [Checkout: Limits on holding stock](/docs/features/checkout#limits-on-holding-stock).

### Emails anyone can request

Sign-up, the password-reset request, the verification resend and the newsletter sign-up send an email to whatever address they are given, so the per-IP limits alone would let a script spread over many addresses flood an inbox or use up the Resend quota and stop the order emails with it. Their senders therefore first ask `admitPublicEmail`, which allows three emails of one kind to one address an hour and 50 of these emails a day for the whole shop, counted in `rate_limit` under a SHA-256 of the address. A skipped email is answered exactly like a sent one, because the reset and the resend are sent only for some addresses and a different answer would reveal which; the daily limit also records `email.failed` for the owner. Nothing tells a person from a script, so a flood of these requests can use up the daily limit and delay real sign-ups for the rest of that day. A withdrawal sent by order number at `/withdraw-from-contract` is treated the same way: `withdrawFromGuestOrder` sends the acknowledgement and the shop's notice only when `admitPublicEmail` admits a `withdrawal` email to the order's address, and answers every statement alike, so a visitor learns neither whether an order number and address match an order nor whether that order can still be withdrawn from. Emails the shop sends on its own, about orders, refunds and accounts, never pass through these limits. See [Better Auth: Email limits](/docs/integrations/better-auth#email-limits) and [Resend: Emails visitors can request](/docs/integrations/resend#emails-visitors-can-request).

## WebSocket authorization

A Durable Object `fetch` has no cookie or session context of its own, so the admin hub is checked in the Worker **before** the object is addressed: `assertAdminWebSocket` answers `401` unless the session belongs to an admin with two-factor authentication on.

```ts
if (hubName === REALTIME_INVALIDATION_HUB.ADMIN) {
  const unauthorized = await assertAdminWebSocket(request)
  if (unauthorized !== undefined) {
    return unauthorized
  }
}

const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)

return hub.fetch(request)
```

Checking after `getByName()` would already have let an unauthenticated client open the object. The storefront hub is public — it only ever broadcasts catalog query keys, never data.

## Webhooks

`POST /api/webhooks/stripe` requires a `stripe-signature` header and verifies it with `env.STRIPE_WEBHOOK_SECRET` through `stripe.webhooks.constructEventAsync` before any handler runs. An unverifiable body is a `400` and nothing is touched. A verified event from the other Stripe mode, test in `production` or live anywhere else, is logged and acknowledged with `200` before any handler runs, so it changes nothing either.

`POST /api/webhooks/inpost` cannot be verified the same way, because InPost does not sign ShipX webhooks, so the route trusts no call: it accepts only an event naming the shop's `INPOST_ORGANIZATION_ID` and a shipment some order holds, and then reads that shipment from ShipX with the shop's token before writing anything. A forged call can make the shop read one of its own shipments again and nothing more. Anything else is a `400`, and an address that sends more than `INPOST_WEBHOOK_RATE_LIMIT` (120) calls a minute is answered `429` before the body is read.

## Health check

`GET /api/health` is public and needs no session, so an uptime monitor can call it. It reads no data — `SELECT 1`, a KV lookup and an R2 `head` of a key that does not exist — and answers only `ok` or `error` per binding, never the error, a binding name or any configuration. Errors go to the Worker log. See [Monitoring and alerts](/docs/guides/monitoring-and-alerts#the-health-check).

`POST /api/newsletter/unsubscribe` is the one-click unsubscribe that mail providers post for a newsletter's `List-Unsubscribe` header. It takes no session and no signature: the subscriber's `token`, a random UUID in the query string, is the only credential, and it can only unsubscribe that address. It takes no rate limit either, because a guess has no realistic chance and one mail provider posts for many subscribers from the same address. A malformed token is a `400` and an unknown one a `404`, both without a write.

## Errors

`withRequest` installs one normalizer for every server function:

| Thrown                 | Reaches the client as                         |
| ---------------------- | --------------------------------------------- |
| TanStack `notFound()`  | Unchanged, so the route answers 404           |
| `AppError`             | Its code, plus a reason code message          |
| Better Auth `APIError` | `AUTH_API_ERROR` plus a translation key       |
| `ZodError`             | `VALIDATION`                                  |
| Anything else          | `INTERNAL_ERROR`, original logged server-side |

`ERROR_CODES` in `src/modules/_core/constants/errors.ts` holds the eight codes, and `useActionError()` maps a code to `errors.action.<CODE>`. Internal messages, stack traces and SQL never reach the browser.

## Response headers

`src/server.ts` passes every response it answers through `withSecurityHeaders` from `src/lib/security-headers.ts`: pages, server functions, the auth and webhook handlers, redirects, `/sitemap.xml` and `/robots.txt`. Only the two WebSocket upgrades go back untouched, because a `101` response cannot be copied.

| Header                      | Value                                                                                                                   |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `Content-Security-Policy`   | Built for each response, below                                                                                          |
| `X-Frame-Options`           | `DENY`, the same rule as `frame-ancestors 'none'` for browsers that predate it                                          |
| `X-Content-Type-Options`    | `nosniff`                                                                                                               |
| `Referrer-Policy`           | `strict-origin-when-cross-origin`                                                                                       |
| `Permissions-Policy`        | `camera=(), geolocation=(), microphone=()`                                                                              |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains`, only when `APP_ENV` is `preview` or `production` and the request came over HTTPS |

The policy allows what the shop loads and nothing else:

| Directive                    | Sources                                                                                                                                                                        | Loaded by                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `script-src`                 | `'self'`, `'nonce-…'`, `https://js.stripe.com`, `https://*.js.stripe.com`                                                                                                      | The bundles, the inline scripts of this response, Stripe.js                                                                                 |
| `style-src`                  | `'self'`, `'unsafe-inline'`                                                                                                                                                    | The stylesheets, and the inline styles explained below                                                                                      |
| `img-src`                    | `'self'`, `data:`, `blob:`, the image hosts                                                                                                                                    | Catalogue images; `data:` for the SVG icons in the MapLibre stylesheet, `blob:` for the admin upload preview                                |
| `media-src`                  | `'self'`, the image hosts                                                                                                                                                      | The landing-page video                                                                                                                      |
| `connect-src`                | `'self'`, `https://api.stripe.com`, `https://fonts.googleapis.com`, `https://api-pl-points.easypack24.net`, `https://basemaps.cartocdn.com`, `https://*.basemaps.cartocdn.com` | Server functions and the realtime sockets, the Stripe API, the font stylesheet Stripe Elements reads, the InPost points API, the locker map |
| `frame-src`                  | `https://js.stripe.com`, `https://*.js.stripe.com`, `https://hooks.stripe.com`                                                                                                 | The Payment Element, 3-D Secure                                                                                                             |
| `font-src`, `worker-src`     | `'self'`                                                                                                                                                                       | The self-hosted fonts, the MapLibre worker                                                                                                  |
| `default-src`, `form-action` | `'self'`                                                                                                                                                                       | Everything not listed, and form posts                                                                                                       |
| `object-src`, `base-uri`     | `'none'`                                                                                                                                                                       | Nothing                                                                                                                                     |
| `frame-ancestors`            | `'none'`                                                                                                                                                                       | No site may frame the shop                                                                                                                  |

The image hosts are the origins of `DEFAULT_R2_PUBLIC_URL` and of `getAssetCdnBase()`, so a new `VITE_R2_URL` moves the policy with it: production's `https://images.martebizuteria.pl` and preview's `r2.dev` bucket address are each listed as a whole origin, which covers the resized images under `/cdn-cgi/image/` and the original object `onerror=redirect` falls back to. `src/lib/__test__/security-headers.image-hosts.test.ts` checks the images the storefront asks for against the policy of each environment; see [Image delivery](/docs/guides/image-delivery).

**The nonce.** `createContentSecurityPolicyNonce` draws 16 random bytes for every request. `src/server.ts` hands the nonce to TanStack Start as `RequestContext.nonce`, `getRouter` reads it back with `getGlobalStartContext()` into `ssr.nonce`, and Start stamps it on its hydration scripts, on the tags `<HeadContent />` and `<Scripts />` render, and on a `<meta property="csp-nonce">` the browser router reads when it hydrates. `RootDocument` puts it on the theme, sidebar and data-grid init scripts with `useRouter().options.ssr?.nonce`. An inline script injected into a page has no nonce, so it does not run.

**Inline styles.** `style-src` allows `'unsafe-inline'`. React renders `style` attributes into the server HTML, and Sonner, the theme provider, MapLibre and Stripe.js insert `<style>` elements at runtime that carry no nonce. A nonce source in `style-src` switches `'unsafe-inline'` off and would block all of them. A style cannot run script, and scripts stay nonce-only.

**Zod's eval probe.** Zod 4 calls `new Function("")` once per page to decide whether to compile its object parsers. The policy has no `'unsafe-eval'`, so the browser refuses the call and reports one `script-src` violation for `eval`; Zod catches the refusal and parses without compiling, as it already does on Workers. Zod's `jitless` setting skips the probe, but it has to be set before the first schema module runs, and the client bundle evaluates the route chunks before any module the app could set it in.

**Static files.** Files under `public/` are answered by the assets layer and never reach the Worker. `public/_headers` gives every one of them `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`. HSTS is left to the Worker's responses, because the browser applies it to the whole host. The two PDF forms at `/forms/…` are not static files: the Worker makes them, so they carry the same headers as a page.

`security-headers.test.ts` checks every header and directive, `server.test.ts` checks that each Worker response carries them with the nonce the application was handed, and `e2e/specs/smoke.spec.ts` loads the home, product, sign-in and documentation pages in a browser and fails if they do not hydrate or if the browser refuses anything other than Zod's probe.

## Indexing and exposure

`isNoIndexPathname` in `src/lib/seo.ts` marks `/account`, `/admin` and `/checkout` (and their subtrees) `noindex, nofollow`, and `__root.tsx` additionally emits the noindex meta on every non-production build. `generateRobotsTxt` returns a blanket `Disallow: /` unless `APP_ENV` is `production`, and in production disallows `/api/`, `/admin`, `/account` and `/checkout`.
