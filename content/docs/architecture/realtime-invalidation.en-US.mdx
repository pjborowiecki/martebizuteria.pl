Admin dashboards go stale the moment a second person is working, and the admin list queries deliberately do not refetch on mount or on focus. Freshness is pushed instead of polled.

## Two audiences, one object each

`REALTIME_INVALIDATION_HUB` has two names, `admin` and `storefront`, and the object is addressed by name with `env.REALTIME_INVALIDATION_HUB.getByName(hubName)`. The hub holds no durable state — it is a broadcaster, not a store — and it accepts sockets with a tag equal to its own name so `ctx.getWebSockets(hubName)` can resolve exactly its audience.

The upgrade handshake has to go through `fetch`, because a WebSocket upgrade has no alternative. Invalidations do not: they use a **native RPC method** on the Durable Object stub, which avoids constructing a `Request` and a `Response` on the hot path.

```ts
const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)
await hub.notifyInvalidation(toSerializedTopicPrefixes(queryKeys))
```

`notifyInvalidation` serializes one payload, iterates its sockets and swallows a per-socket send failure so one dead connection cannot abort the broadcast.

## The topic is a serialized query key

A topic is just `JSON.stringify(queryKey)`, so the wire format and the cache keys can never drift:

```ts
export const serializeQueryKeyPrefix = (queryKey: QueryKey): string => JSON.stringify(queryKey)
```

A tab invalidates the narrower key of each overlapping topic and subscription, once. `resolveInvalidatedQueryKeys` matches them with TanStack Query's own one-directional prefix test, `partialMatchKey`, applied in both directions:

```ts
const queryKeysInvalidatedByTopic = (subscriptions: readonly QueryKey[], topic: QueryKey): readonly QueryKey[] =>
  subscriptions.some((subscription) => partialMatchKey(topic, subscription))
    ? [topic]
    : subscriptions.filter((subscription) => partialMatchKey(subscription, topic))
```

A topic that falls under a subscription is invalidated as itself: `["admin", "products", "page"]` under the `["admin", "products"]` subscription refreshes the product list pages and leaves the product stats alone. A topic broader than a subscription is narrowed to the subscriptions it covers: `["admin"]` refreshes every admin subscription and nothing else the tab has cached. A topic that overlaps no subscription, or does not parse as a query key, is ignored. The hub broadcasts to the whole audience and each tab discards what does not overlap its own list.

`toMinimalQueryKeyPrefixes` then reduces the frame to a minimal set of keys. It drops duplicates, compared with `hashKey`, and every key that another key in the set already covers, so a frame that names both `["products"]` and `["products", "storefront-page"]` invalidates `["products"]` once. Invalidating the nested key as well would cancel the catalogue fetch the first invalidation started and start it again.

## Subscriptions

`ADMIN_REALTIME_QUERY_PREFIXES` has 14 entries: the audit log page and stats, admin orders, admin customers, the `ALL`/`STATS` pair for categories, collections, products and product attributes, and the content page `ADMIN.ALL`/`ADMIN.BY_HANDLE` pair. `STOREFRONT_REALTIME_QUERY_PREFIXES` has 11: the product keys (`ALL`, `BY_HANDLE`, `LANDING_NEW_ARRIVALS`, `RELATED_BY_CATEGORY`, `STOREFRONT_PAGE`), cart availability, the category and collection `ALL`/`BY_HANDLE` pairs, and the content page `BY_HANDLE`.

Both lists are built from the modules' own `*_QUERY_KEYS` constants and typed `as const satisfies readonly QueryKey[]`, so a renamed key is a type error rather than a silently dead subscription.

## Publishing

`realtime-invalidation.catalog.server.ts` exposes the seven publishers the domain layer calls, each naming the audiences it affects:

| Publisher                                     | Admin keys                                     | Storefront keys                                                                  |
| --------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------- |
| `scheduleProductCatalogInvalidation`          | product `ADMIN.ALL`, `ADMIN.STATS`             | the five product keys plus cart availability                                     |
| `scheduleCategoryCatalogInvalidation`         | category `ADMIN.ALL`, `ADMIN.STATS`            | category `ALL`, `BY_HANDLE`                                                      |
| `scheduleCollectionCatalogInvalidation`       | collection `ADMIN.ALL`, `ADMIN.STATS`          | collection `ALL`, `BY_HANDLE`, product `LANDING_NEW_ARRIVALS`, `STOREFRONT_PAGE` |
| `scheduleContentPageInvalidation`             | content page `ADMIN.ALL`, `ADMIN.BY_HANDLE`    | content page `BY_HANDLE`                                                         |
| `scheduleProductAttributeCatalogInvalidation` | attribute `ADMIN.ALL`, `ADMIN.STATS`           | —                                                                                |
| `scheduleAdminCustomersInvalidation`          | user `ADMIN.CUSTOMERS`, `ADMIN.CUSTOMERS_PAGE` | —                                                                                |
| `scheduleAdminOrdersInvalidation`             | order `ADMIN.ORDERS`                           | —                                                                                |

The `schedule*` form hands the publish to `scheduleBackgroundWork`, so it runs under `waitUntil` and never delays the response. `publishRealtimeInvalidation` is the awaited form, used where there is no request to return from — the audit-log queue consumer awaits it after a successful batch insert.

Callers worth knowing: the Stripe webhook handlers (`scheduleAdminOrdersInvalidation` and `scheduleProductCatalogInvalidation` after a fulfil, refund or dispute), `handleCreateCheckoutSession` and `handleUpdateCheckoutSession` (product catalog, because inventory moved), Better Auth's user create/update/delete hooks (`scheduleAdminCustomersInvalidation`), and the admin catalog mutations.

## The client side

`useRealtimeQuerySync({ hub, subscriptions })` is mounted exactly twice: in `admin.tsx` with the admin prefixes and in `_storefront.tsx` with the storefront prefixes.

```ts
useRealtimeQuerySync({
  hub: REALTIME_INVALIDATION_HUB.ADMIN,
  subscriptions: ADMIN_REALTIME_QUERY_PREFIXES,
})
```

The hook opens `wss://<host>/api/realtime/{admin,storefront}/ws`, validates each message with `isRealtimeInvalidationPayload`, resolves its topics with `resolveInvalidatedQueryKeys`, and calls `invalidateQueryPrefix(queryClient, queryKey)` once for each key it returns. A frame that names `["admin", "products"]` therefore refreshes the product list and its stats once, not once more through the nested `["admin", "products", "stats"]` subscription, which would cancel and restart the stats fetch, and a frame that names only `["admin", "products", "stats"]` refreshes the stats and not the list. Reconnect is exponential backoff from 1 s, doubling, capped at 30 s, reset to zero on a successful `open`, and the cleanup function closes the socket and clears any pending timer.

`invalidateQueryPrefix` refreshes only what a screen needs. It first removes every query under the prefix that has no observer and no fetch in flight, except an infinite list. It then calls `invalidateQueries` with `refetchType: "active"`, which marks what is left invalid and refetches the queries on screen, and `refetchQueries` with `type: "inactive"` and `fetchStatus: "fetching"`, which restarts the unobserved fetches already in flight. A query on screen refetches at once. A query that is cached but off screen is gone, so the next loader or mount fetches it fresh, even when the loader reads with `staleTime: "static"` and the query sets `refetchOnMount: false`. An infinite list off screen, the storefront catalogue, keeps the pages the shopper loaded and is only marked invalid: going back to it shows those pages at the same scroll position, and the next read, by its loader or by `useSuspenseInfiniteQuery`, refetches all of them, because both use a numeric stale time. A query that is observed but disabled is marked invalid and refetches when it is enabled. A fetch already in flight is never removed, because removing a query cancels its fetch and the loader awaiting it would reject: an unobserved fetch that started from cached data is restarted, so its caller gets the post-event response, and a first fetch finishes as it is. `refetchType: "active"` alone is not enough, because a `staleTime: "static"` loader would then return the stale cached entry when the admin opens the page again.

The hook never posts to the `BroadcastChannel`. Every tab under the storefront and admin layouts (`_storefront.tsx`, `admin.tsx`) holds its own socket and receives every frame itself, so echoing a frame to the browser's other tabs would only make each of them fetch the same queries again. Tabs on `/checkout`, `/account`, `/auth` and `/docs` hold no socket and pick up a change on their next fetch; `handleCreateCheckoutSession` re-reads prices and stock from D1 and refuses a checkout if anything moved. The channel (`marte-query-invalidation` in `query.sync.ts`) stays for local mutations whose keys the server does not publish yet: coupon changes in `useCouponActions`, and order actions in `useOrderRowActions`, which otherwise reach other browsers only through the audit-log queue. `syncQueryInvalidation` applies `invalidateQueryPrefix` locally and posts the key, and `setupQueryClientInvalidationBroadcast` — wired in `getRouter` for the browser only — applies `invalidateQueryPrefix` to every key it receives. Both sides are guarded with try/catch and a `WeakSet` so the listener is installed once per `QueryClient`. The refresh buttons of the order, product, audit and customer tables, and customer deletion, call `invalidateQueryPrefix` directly: they refresh only the tab they were used in, and customer changes reach other admins through the Better Auth hooks.

The tab that made a change still fetches its one or two queries on screen twice, once from its own `onSuccess` and once from the hub frame. That is deliberate: skipping the second fetch with `cancelRefetch: false` could let another tab join a fetch that started before the write was committed.

## Operational notes

- The hub is declared as a SQLite Durable Object class in `wrangler.jsonc` (`tag: "v1"`) even though it stores nothing. That is the migration contract, not a hint that state exists.
- There is no delivery guarantee and no replay. A tab that was disconnected when a publish happened will not learn about it on reconnect; it recovers on its next navigation or manual refetch.
- The storefront hub accepts any client. It only ever carries query-key prefixes, never row data.
