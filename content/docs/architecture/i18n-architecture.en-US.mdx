M'Arte serves two locales: **`pl-PL` (default)** and **`en-US`**. Both are BCP-47 tags — there is no bare `pl` or `en`. The default locale has no URL prefix, so `/products` (Polish) and `/en-US/products` (English) are the same route. Path segments themselves are not translated — `ROUTES` in `src/routes.ts` holds one English path per page, and only the prefix changes with the locale.

## Configuration

`src/integrations/use-intl/i18n.config.ts` is the single source:

```ts
export const I18N = {
  COOKIE_NAME: "marte_locale",
  DEFAULT_LOCALE: "pl-PL",
  DEFAULT_TIMEZONE: "Europe/Warsaw",
  SUPPORTED_LOCALES: ["pl-PL", "en-US"],
} as const
```

`SupportedLocale` is derived from `SUPPORTED_LOCALES`, so adding a locale starts with a one-line change. It also needs a new `messages/<locale>` folder, a new `.mdx` file for every page in `content/docs`, a value for the new locale in every `content_page` row, and an entry in every map typed `Record<SupportedLocale, …>`, which the type check then reports: the react-day-picker locale in `react-day-picker.locale.ts`, the Stripe Elements locale in `stripe.client.ts`, the title separator in `src/lib/seo.ts`, the fallback messages in `default-messages.ts` and the catalog form fields in `catalog-locale-fields.tsx`. A few places name `pl-PL` and `en-US` directly, such as the admin catalog forms, the newsletter composer and `src/presentation/document-assets.ts`, which picks the Latin Extended font subset for `pl-PL`.

## URLs

| File                          | Exports                                                                                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `i18n.paths.ts`               | `localizePathname`, `deLocalizePathname`, `canonicalizePathname`, `extractLocaleFromPath`, `isSupportedLocale`, `shouldIgnorePath`, `localeLinks` |
| `i18n.utils.ts`               | `getCurrentLocale`, `getCurrentPathname`, `localizeUrl`, `deLocalizeUrl`, `parseLocaleCookie`                                                     |
| `i18n.middleware.ts`          | `resolveLocale`, used by the Worker for the redirect and the cookie                                                                               |
| `i18n.messages.ts`            | `loadNamespace`, `messagesQueryOptions`, `preloadNamespaces`, `ROOT_NAMESPACES`, `getRouteNamespaces`, `buildMessageTree`, `isMessagesQuery`      |
| `i18n.display.ts`             | `detectDisplayPreferences`, `toSavedDisplayPreferences`, `resolveDisplayPreferences`, `TIME_ZONE_COOKIE_NAME`, `FORMAT_LOCALES`, the fallbacks    |
| `i18n.display-preferences.ts` | `getDisplayPreferences`, `displayPreferencesQuery`, `resolveRequestDisplayPreferences`                                                            |

`shouldIgnorePath` excludes `/api`, `/rpc`, `/_serverFn`, `/assets` and `/forms` from all locale handling.

`canonicalizePathname` collapses a language-only alias and the redundant default prefix: `/pl/products` and `/pl-PL/products` both canonicalize to `/products`, and the Worker answers with a `301`. `localeLinks` builds the `rel="canonical"` link, one `rel="alternate"` per locale and an `x-default` alternate, which `__root.tsx` and `buildPageHead` both emit.

## Route files carry no locale

The router does the translation, in `src/router.tsx`:

```ts
rewrite: {
  input: ({ url }) => deLocalizeUrl(url),
  output: ({ url }) => localizeUrl(url),
},
```

`rewrite.input` strips the prefix before matching, so `_storefront.products.$handle.tsx` serves both `/products/<handle>` and `/en-US/products/<handle>`. `rewrite.output` re-applies the current locale when the router generates a href, so `<Link to={ROUTES.PRODUCT}>` needs no locale handling at all.

**The consequence worth knowing:** because the router only ever sees the de-localized path, anything that derives the locale from the router's location silently yields the default. `getCurrentLocale()` is the single derivation used everywhere. It is an isomorphic function: on the server it reads the real request URL (or the cookie for ignored paths), and in the browser it reads `location.pathname` (or `document.cookie`).

`localizePathname` is for raw paths that bypass the router, such as canonical links and hand-built `<a href>` elements. `src/presentation/components/custom/mdx.tsx` applies it to every internal link in an MDX page, which is why the links in these docs are written without a prefix. Links inside emails and the sign-up `callbackURL` are built with `buildLocalizedUrl` from `src/lib/seo.ts`. The sign-in `?redirect` value and the Google sign-in `callbackURL` start from the router's `location.publicHref` instead, which is already the localized public path, such as `/en-US/account/orders/order-1`. A server-rendered redirect to it therefore keeps the visitor's language, and on the client the router re-localizes it to the current language; see [Security model](/docs/architecture/security-model).

## The cookie

`marte_locale` is written from two places: `resolveLocale` appends a `Set-Cookie` when the URL locale differs from the cookie, and `TranslationsProvider` writes `document.cookie` in an effect whenever the active locale changes. The cookie only matters for requests where the URL has no locale to read — `/api/*` and server function calls.

Server functions that return localized content take the locale as an explicit input rather than relying on the cookie. `localeField` in `src/modules/_core/utils/zod-fields.ts` is the shared validator:

```ts
export const localeField = zod.enum(I18N.SUPPORTED_LOCALES)
```

`getProductQuery(handle, locale)` follows that pattern, and the locale is part of its query key so switching language does not serve a cached translation. The documentation routes call `loadDocsPage(splat)` and `loadDocsNavigation()` from `fumadocs.docs.ts`, which pass `getCurrentLocale()` to the `getDocsPage` and `getDocsNavigation` server functions as `localeField` input; neither goes through the query cache.

## Display preferences

Dates, times and numbers are formatted with a **formatting locale** and a **time zone** that are separate from the interface language. `src/integrations/use-intl/i18n.display.ts` holds the rules:

- `detectDisplayPreferences({ acceptLanguage, cookieHeader, edgeTimeZone })` reads the request. The formatting locale is the first `Accept-Language` entry the runtime's `Intl` supports, else `FALLBACK_FORMAT_LOCALE` (`en-US`). The time zone is the first valid one of the `marte_time_zone` cookie (`TIME_ZONE_COOKIE_NAME`) and the Cloudflare edge time zone (`RequestContext.edgeTimeZone`, `request.cf?.timezone`), else `FALLBACK_TIME_ZONE` (`UTC`).
- `toSavedDisplayPreferences(user)` reads the signed-in user's `formatLocale` and `timezone` (the `format_locale` and `timezone` columns of `user`) and ignores a value `Intl` does not accept.
- `resolveDisplayPreferences({ detected, saved })` lets a saved value win over a detected one.

The time zone is therefore the saved preference, then the `marte_time_zone` cookie, then the edge time zone, then `UTC`; the formatting locale is the saved preference, then `Accept-Language`, then `en-US`.

`src/integrations/use-intl/i18n.display-preferences.ts` serves them. `getDisplayPreferences` is a `GET` server function that returns `{ detected, saved }`, and `displayPreferencesQuery` caches it under `DISPLAY_PREFERENCES_QUERY_KEY` (`["i18n", "displayPreferences"]`); the root `beforeLoad` loads it and `TranslationsProvider` reads it, see [Caching and SSR](/docs/architecture/caching-and-ssr). `resolveRequestDisplayPreferences` is a server-only function that returns the resolved `{ formatLocale, timeZone }` to the admin use cases that filter or group by date: the dashboard snapshot and chart range, the admin order, customer and product pages and their exports, the admin customer, and the audit log list and stats.

`TranslationsProvider` passes the resolved time zone to `IntlProvider` and the resolved pair to `DisplayPreferencesContext`, which `src/hooks/use-display-format.ts` reads with `useDisplayPreferences`, `useFormatLocale`, `useDisplayTimeZone` and `useFormatter`, a use-intl `createFormatter` bound to both. In the browser it writes the browser's IANA time zone into the `marte_time_zone` cookie (`Secure` on HTTPS) and, when that zone differs from the detected one, patches `detected.timeZone` in the cached query, so the page switches to the visitor's zone after hydration and the next request detects it on the server.

A signed-in user can override both. `updateDisplayPreference` in `src/modules/user/use-cases/update-display-preference.ts` (`withRateLimit("update-display-preference", RATE_LIMITS.SENSITIVE)` and `authorized()`) writes `formatLocale` or `timezone`; an empty value stores `NULL`, which means automatic. The fields in `src/presentation/components/custom/display-preferences/` offer the 18 `FORMAT_LOCALES` and the `TIMEZONES` from `src/modules/_core/constants/timezone.ts`, appear in the account profile and the admin settings, and invalidate every query once a choice is saved.

## Messages

Translations live in `messages/<locale>/<namespace>.json` — 61 files per locale. The file name **is** the namespace, and dots are nesting: `pages.admin.catalog.products.json` is read by `useTranslations("pages.admin.catalog.products")`. `buildMessageTree` expands each dotted namespace back into a nested object and merges them, so the provider sees one message tree.

Namespace families:

| Prefix         | Examples                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------- |
| `common`       | Shared labels                                                                             |
| `errors`       | `errors.action.<ERROR_CODE>` for `useActionError`                                         |
| `components.*` | `components.custom`, `components.shadcn`, `components.datagrid`, `components.defaults`    |
| `pages.*`      | One per page or area, e.g. `pages.product`, `pages.checkout`, `pages.admin`, `pages.docs` |
| `emails.*`     | One per template, e.g. `emails.order-confirmation`                                        |

Page namespaces also carry the strings their loaders turn into the page's `title` and `description`, under keys that vary by namespace: top-level `title` and `description` (`pages.products`, `pages.cart`), a `meta` object (`pages.landing` and the `pages.auth.*` forms), a `metadata` object (`pages.withdrawal`, or nested as in `pages.newsletter`), `metaTitle` and `metaDescription` (`pages.categories`; `metaTitle` alone, as a template, in `pages.product`), or `index.title` and `index.description` (`pages.blog`).

## Loading

- **Root namespaces** are discovered by `import.meta.glob` in `i18n.messages.ts` and exported as `ROOT_NAMESPACES`: `common`, `components.custom`, `components.shadcn`, `errors`, `pages.auth.errors` and `pages.auth.toast`. They are always loaded.
- **Every route declares its own** in `staticData.namespaces`, for example `["pages.product"]` on the product page, `["pages.admin", "components.datagrid"]` on the admin layout, `["pages.checkout", "pages.cart"]` on the checkout layout.
- **`__root.tsx`'s `beforeLoad`** calls `getRouteNamespaces(matches)`, which unions `ROOT_NAMESPACES` with every matched route's declaration, then `preloadNamespaces` resolves them all into the request's `QueryClient` in parallel.
- **`TranslationsProvider`** re-reads the same list with `useMatches` and `useSuspenseQueries`, builds the tree and passes it to use-intl's `IntlProvider` together with the time zone resolved from `displayPreferencesQuery`, which the root route loads with the namespaces. The format locale from the same query goes to `DisplayPreferencesContext` beside it (see [Internationalization](/docs/features/internationalization)). Because it wraps the document body in the root shell, even error and not-found screens are translated.
- **Emails** load their namespace on the server with `loadNamespace` in the code that sends them, and translate with `createTranslator`.

A page therefore ships the six root namespaces plus what its own route and its layout ancestors declared — not the whole catalogue.

The catalogues also survive a change of user. When the session switches to a different user, `clearCacheOnUserChange` removes every cached query except the session, the display preferences and the queries matched by `isMessagesQuery`, so the translations do not load again, and then invalidates the display preferences so the new user's saved ones load; see [Caching and SSR](/docs/architecture/caching-and-ssr).

## Documentation and legal content

Fumadocs is configured with the same locale list in `src/integrations/fumadocs/fumadocs.i18n.ts`:

```ts
export const i18n = defineI18n({
  defaultLanguage: I18N.DEFAULT_LOCALE,
  fallbackLanguage: I18N.DEFAULT_LOCALE,
  hideLocale: "always",
  languages: [...I18N.SUPPORTED_LOCALES],
  parser: "dot",
})
```

`parser: "dot"` is what makes `<page>.<locale>.mdx` and `meta.<locale>.json` work, and `hideLocale: "always"` keeps the locale out of the Fumadocs URLs because the router prefix already carries it. `docsSource.getPage(slugs, locale)` and `docsSource.getPageTree(locale)` are both called with the locale from `getCurrentLocale()`.

Both locales must list the same slugs in `meta.<locale>.json`: a page added in English has to be added in Polish too, or the sidebar differs between languages.
