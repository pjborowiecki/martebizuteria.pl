## Punkt wejścia Workera i bindingi

`wrangler.jsonc` ustawia `./src/server.ts` jako `main`, z `compatibility_date` `2026-04-18`, flagą `nodejs_compat`, `placement.mode: "smart"` i włączoną obserwowalnością, razem z Workers Issues. Każde środowisko otrzymuje te same sześć bindingów:

| Binding                     | Typ              | Służy do                                                                                    |
| --------------------------- | ---------------- | ------------------------------------------------------------------------------------------- |
| `DB`                        | Baza D1          | Wszystkich 41 tabel, w tym sesji, weryfikacji i liczników limitów żądań                     |
| `IMAGES`                    | Bucket R2        | Zdjęć produktów uploadowanych przez `src/integrations/cloudflare-r2`                        |
| `CACHE`                     | Namespace KV     | Przechowuje pięciominutową flagę nadawcy e-maili (`resend.availability.server.ts`)          |
| `ASSETS`                    | Zasoby statyczne | Wszystkiego z `public/`, w tym fontów i PDF formularza odstąpienia od umowy                 |
| `REALTIME_INVALIDATION_HUB` | Durable Object   | Klasy `RealtimeInvalidationHub`, jedna instancja na odbiorcę                                |
| `AUDIT_LOG_QUEUE`           | Kolejka          | Zdarzeń audytowych, produkowanych i konsumowanych przez ten sam Worker                      |
| `NEWSLETTER_QUEUE`          | Kolejka          | Partii newslettera, jednej partii kampanii na wiadomość, konsumowanych przez ten sam Worker |

Durable Object jest zadeklarowany jako klasa SQLite w bloku `migrations` (`tag: "v1"`, `new_sqlite_classes: ["RealtimeInvalidationHub"]`), mimo że hub nie trzyma żadnego trwałego stanu. Kolejka jest skonfigurowana z `max_batch_size: 50`, `max_batch_timeout: 5`, `max_retries: 3` i `dead_letter_queue` nazwaną od niej z przyrostkiem `-dlq`, a producent i konsument wskazują tę samą kolejkę, dlatego `src/server.ts` eksportuje zarówno handler `fetch`, jak i `queue`. Ten sam handler `queue` konsumuje też kolejkę martwych listów, po jednej wiadomości, z `max_retries: 3` i `retry_delay: 300`. Preview i produkcja deklarują też `triggers.crons: ["0 3 * * *"]`, który codziennie o 03:00 UTC wywołuje jego handler `scheduled` na potrzeby [czyszczenia po okresie przechowywania](/docs/guides/data-retention); development i test nie deklarują triggera.

Flaga `nodejs_compat` udostępnia `node:async_hooks`, którego `src/lib/background.ts` potrzebuje do swojego `AsyncLocalStorage`.

## Środowiska

`wrangler.jsonc` definiuje trzy środowiska, a `CLOUDFLARE_ENV` wybiera jedno dla `vp dev` i `vp build`.

| Środowisko    | Nazwa Workera                | Baza D1                  | Bucket R2                | Kolejki                                                                 | Używane przez                                      |
| ------------- | ---------------------------- | ------------------------ | ------------------------ | ----------------------------------------------------------------------- | -------------------------------------------------- |
| `development` | `martebizuteria-development` | `martebizuteria-preview` | `martebizuteria-preview` | `martebizuteria-audit-log-preview`, `martebizuteria-newsletter-preview` | `bun run dev`                                      |
| `preview`     | `martebizuteria-preview`     | `martebizuteria-preview` | `martebizuteria-preview` | `martebizuteria-audit-log-preview`, `martebizuteria-newsletter-preview` | `bun run build:preview`, `deploy:preview`, `start` |
| `production`  | `martebizuteria`             | `martebizuteria`         | `martebizuteria`         | `martebizuteria-audit-log`, `martebizuteria-newsletter`                 | `bun run build:production`, `deploy:production`    |

`preview` podłącza `preview.martebizuteria.pl` jako domenę własną przez `routes` z `custom_domain: true`; `production` ma puste `routes` i do startu sprzedaży na `martebizuteria.pl` odpowiada tylko pod swoją nazwą `workers.dev`. Oba ustawiają też `workers_dev: true`, więc ich nazwy `workers.dev` nadal odpowiadają obok domeny; czego potrzebuje strefa, opisuje [Wdrożenie podglądu](/docs/getting-started/deploy-preview).

Każdy binding jest oznaczony `"remote": true`, więc `bun run dev` łączy się z prawdziwym D1, R2 i KV środowiska development, a nie z lokalną emulacją. Plugin Cloudflare dla Vite włącza zdalne bindingi tylko wtedy, gdy `CLOUDFLARE_ENV` ma wartość `development`. Migracje muszą więc być zastosowane przed pierwszym uruchomieniem:

```sh
bun run db:migrate:development
```

`development` i `preview` dzielą jedną bazę D1, więc zmiana schematu zastosowana do pracy lokalnej jest już zastosowana dla preview.

## Sekrety i pliki środowiskowe

Każde środowisko wymienia swoje sekrety w `secrets.required`: `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `TURNSTILE_SECRET_KEY` i `VITE_R2_URL`. `APP_ENV` jest zwykłą zmienną, nie sekretem.

Wartości pochodzą z `.env.development`, `.env.preview` i `.env.production`, które są poza repozytorium; `.env.test` zawiera zacommitowane wartości pozorne, a `.env.example` jest szablonem. Automatyczne ładowanie zmiennych przez Bun jest wyłączone w `bunfig.toml`, więc środowisko zawsze wybiera się jawnie — przez `--mode` albo przez `bun --env-file=`.

Wartości z prefiksem `VITE_` są widoczne w przeglądarce. `VITE_STRIPE_PUBLISHABLE_KEY` jest zadeklarowany w `src/types/vite-env.d.ts` i czytany przez `import.meta.env`; `VITE_R2_URL` jest czytany na serwerze z `env`, a w przeglądarce z `import.meta.env`, dlatego `src/lib/url.ts` opakowuje go w `createIsomorphicFn`.

Dane dostępowe do zarządzania Cloudflare (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, `CLOUDFLARE_ACCESS_TOKEN`) czyta wyłącznie `drizzle.config.ts` na potrzeby Drizzle Kit. `scripts/prepare-deploy-secrets.ts` wysyła tylko zadeklarowane sekrety aplikacji, trzymając dane zarządcze poza Workerem.

## Typy

| Plik                                  | Źródło                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| `src/types/worker-configuration.d.ts` | Generowany przez `bun run cf-typegen` ze środowiska `development`; poza repozytorium |
| `src/types/router.d.ts`               | Deklaruje opcję trasy `staticData.namespaces`                                        |
| `src/types/vite-env.d.ts`             | Deklaruje zmienne przeglądarkowe z prefiksem `VITE_`                                 |
| `src/types/globals.d.ts`              | Zawęża `Object.fromEntries`, żeby zachowywał typy kluczy                             |

`bun run typegen` uruchamia razem `cf-typegen` i `content` i jest podłączony do `postinstall`, więc świeży klon ma zarówno typy bindingów, jak i kolekcje Fumadocs przed pierwszym sprawdzeniem typów.

## Bramki wdrożenia

Oba skrypty wdrożeniowe przerywają pracę, a nie tylko ostrzegają:

```sh
bun run deploy:preview      # verify-bindings → verify-stripe-keys → verify-turnstile-keys → verify-email-sender → build:preview → prepare-deploy-secrets → db:migrate:preview → wrangler deploy → verify-deployment
bun run deploy:production   # to samo, względem środowiska production
```

- `scripts/verify-bindings.ts` czyta konfigurację przez własną funkcję Wranglera `unstable_readConfig` i rzuca wyjątek, o ile identyfikatory D1 i KV nie są prawdziwe (a nie pozorne), bucket R2 nie jest nazwany, kolejka audytu nie ma zarówno producenta, jak i pasującego konsumenta, którego kolejka martwych listów również jest konsumowana, oraz binding Durable Object nie wskazuje na `RealtimeInvalidationHub`. Dla produkcji rzuca wyjątek także wtedy, gdy bucket `IMAGES` jest tym, który wiąże preview.
- `scripts/verify-stripe-keys.ts` rozpoznaje tryb `VITE_STRIPE_PUBLISHABLE_KEY` i `STRIPE_SECRET_KEY` po przedrostkach i rzuca wyjątek, o ile oba nie są kluczami live dla produkcji albo kluczami testowymi dla preview; zobacz [Stripe](/docs/integrations/stripe#sekrety).
- `scripts/verify-turnstile-keys.ts` rzuca wyjątek, gdy brakuje `VITE_TURNSTILE_SITE_KEY` albo `TURNSTILE_SECRET_KEY`, gdy klucz testowy jest w parze z kluczem widżetu i gdy produkcja ma testowe klucze Cloudflare; zobacz [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile#klucze).
- `scripts/verify-email-sender.ts` pyta Resend, czy wyśle pocztę z `RESEND_EMAIL_FROM`, i rzuca wyjątek, gdy domeny nadawcy nie ma na koncie Resend albo nie jest zweryfikowana; zobacz [Resend](/docs/integrations/resend#domena-nadawcy).
- `scripts/verify-build.ts` odrzuca bundle klienta, który wciąż zawiera niezbundlowany import `cloudflare:workers` lub `node:*`.
- `scripts/prepare-deploy-secrets.ts` zapisuje `.wrangler/secrets.<env>.json` z odpowiedniego pliku `.env`, a wdrożenie przekazuje go przez `--secrets-file`.
- `db:migrate:<env>` nakłada oczekujące migracje D1 tuż przed `wrangler deploy` i zatrzymuje wdrożenie, gdy któraś zawiedzie.
- `scripts/verify-deployment.ts` działa po `wrangler deploy` i rzuca wyjątek, chyba że działający Worker odpowie na stronę główną, listę produktów, `robots.txt`, trasę webhooka Stripe i kontrolę stanu tak jak sklep; zobacz [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

Wdrożenie działa na `dist/server/wrangler.json` — konfiguracji emitowanej przez plugin Cloudflare dla Vite — z odpiętą zmienną `CLOUDFLARE_ENV`, więc na produkcję trafia środowisko wbudowane w build.

## Współdzielona infrastruktura testowa

`src/platform/testing` zawiera wyłącznie to, co nie może należeć do jednej funkcjonalności:

| Ścieżka                                                      | Zawiera                                                                                                   |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| `setup.ts`                                                   | Matchery jest-dom, stuby `IntersectionObserver`/`ResizeObserver`/`matchMedia` i podmianę `createServerFn` |
| `lib/server-function.ts`                                     | `withTestRpc`, uruchamiający funkcję serwerową w procesie przez jej prawdziwe middleware i walidator      |
| `lib/render.tsx`                                             | `renderWithProviders`, `TestProviders`, `createTestRouter`                                                |
| `lib/messages.ts`                                            | `TEST_LOCALE` i `TEST_MESSAGES` dla `IntlProvider` w testach                                              |
| `mocks/d1.ts`                                                | `createTestD1Database`, transport w kształcie D1 nad `node:sqlite`                                        |
| `mocks/intersection-observer.ts`, `mocks/resize-observer.ts` | Stuby API przeglądarki                                                                                    |

`setup.ts` jest zarejestrowany tylko dla projektu `component` w `vite.config.ts`; testy node i integracyjne importują to, czego potrzebują, bezpośrednio. Zobacz [Architektura testów](/docs/architecture/testing-architecture).
