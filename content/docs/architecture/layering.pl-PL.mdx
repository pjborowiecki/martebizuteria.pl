## Warstwy

| Warstwa          | Znajduje się w                      | Decyduje o                                                                                                       |
| ---------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Wejście Workera  | `src/server.ts`                     | Które żądania nigdy nie dotrą do Reacta; przekierowania locale; przekazanie `waitUntil`; nagłówki bezpieczeństwa |
| Dostarczanie     | `src/routes`, `src/router.tsx`      | Kształt URL-i, guardy, co strona wstępnie ładuje, tagi head                                                      |
| Przypadki użycia | `src/modules/*/use-cases`           | Kto może wywołać operację, jakie wejście jest poprawne, które klucze zapytań posiada                             |
| Dostęp do danych | `src/modules/*/*.accessors.ts`      | Jak wiersz jest czytany lub zapisywany; kształt SQL; prepared statements                                         |
| Prezentacja      | `src/presentation`, `src/providers` | Markup, style, które opcje zapytań odczytać                                                                      |

Dostawcy stoją obok tych warstw, nie w nich: `src/integrations/{vendor}` konfiguruje usługę zewnętrzną i oddaje decyzje domenowe modułowi, który jest właścicielem danych.

## Podział, który wykonuje pracę

Akcesor to zwykły dostęp do danych bez pojęcia o tym, kto pyta:

```ts
export const getAvailabilityByVariantIds = async (variantIds: readonly string[]): Promise<Map<string, number>> => {
  if (variantIds.length === 0) {
    return new Map()
  }

  const rows = await db
    .select({ quantityAvailable: inventory.quantityAvailable, variantId: inventory.variantId })
    .from(inventory)
    .innerJoin(productVariant, eq(productVariant.id, inventory.variantId))
    .innerJoin(product, eq(product.id, productVariant.productId))
    .where(and(inJsonList(inventory.variantId, variantIds), eq(product.status, PRODUCT_STATUS.PUBLISHED)))
  return new Map(rows.map((row) => [row.variantId, row.quantityAvailable]))
}
```

Przypadek użycia opakowuje dostęp do danych w endpoint RPC i jest jedynym miejscem, w którym wyrażana jest autoryzacja:

```ts
export const shipOrder = createServerFn({ method: "POST" })
  .middleware([authorized({ order: ["update"] })])
  .validator((input: zod.input<typeof orderZodSchemas.adminShipOrderInput>) => orderZodSchemas.adminShipOrderInput.parse(input))
  .handler(async ({ data: { orderId, ...tracking } }) => {
    const origin = resolveRequestOrigin(getRequest())
    const trackingNumber = filledOrUndefined(tracking.trackingNumber)
    assertOrderActionState(await getAdminOrderActionRow(orderId), (snapshot) =>
      canMarkAdminOrderShipped({ fulfillmentStatus: snapshot.fulfillmentStatus, paymentUiKey: "paid", status: snapshot.status }),
    )

    await transitionOrder(orderId, SHIPPABLE_FULFILLMENT_STATUSES, {
      fulfillmentStatus: "shipped",
      shippedAt: new Date(),
      ...trackingColumns(trackingNumber, filledOrUndefined(tracking.trackingUrl)),
    })

    recordOrderShippedAudit(orderId, { detail: trackingNumber })

    return { email: await announceOrderShipment(orderId, origin), ok: true, orderId }
  })
```

`getAdminOrderActionRow`, `assertOrderActionState` i `transitionOrder` pochodzą z `src/modules/order/use-cases/transition-order.server.ts`. `transitionOrder` to warunkowy `UPDATE`, który przesuwa tylko zamówienie, którego status realizacji nadal należy do `SHIPPABLE_FULFILLMENT_STATUSES` i które nie jest anulowane, a gdy żaden wiersz nie pasuje, rzuca błąd konfliktu. `announceOrderShipment` (`use-cases/announce-order-shipment.server.ts`) rezerwuje potem i wysyła e-mail o wysyłce albo — gdy po wcześniejszym e-mailu o wysyłce pojawi się nowy numer przesyłki — e-mail z numerem śledzenia, i zwraca informację o e-mailu, którą akcje zamówień w panelu pokazują jako toast.

Ponieważ istnieje dokładnie jedna warstwa, w której można zapomnieć o `authorized()`, to właśnie ją celują testy. Przypadek użycia czytający dane samego wywołującego wkompilowuje predykat własności w SQL, a nie pobiera i filtruje:

```ts
where: and(eq(order.id, orderId), eq(order.userId, context.auth.user.id)),
```

Obce `orderId` nie zwraca żadnego wiersza, więc nie ma czego wyciekać.

## O czym decyduje Worker przed uruchomieniem Reacta

`src/server.ts` skraca obsługę czterech rodzajów żądań, zanim zostanie osiągnięty handler TanStack Start, bo żadne z nich nie potrzebuje renderu SSR:

1. `GET /sitemap.xml` — `generateSitemapXml` z `src/lib/seo.ts` ze stron, które `listSitemapPages` czyta z D1, cache'owane na dobę.
2. `GET /robots.txt` — `generateRobotsTxt`, który zwraca całkowite `Disallow: /`, o ile `APP_ENV` nie jest równe `production`.
3. `ROUTES.API_REALTIME.ADMIN_WS` i `ROUTES.API_REALTIME.STOREFRONT_WS` — upgrade'y WebSocket przekazywane do `handleRealtimeInvalidationWebSocket`.
4. Przekierowanie locale z `resolveLocale`, zwracane jako `301` przed czymkolwiek innym.

Wszystko pozostałe jest owinięte w `executionContextStorage.run({ waitUntil }, …)`, żeby praca w tle zaplanowana głęboko w warstwie domenowej wciąż mogła dosięgnąć `ExecutionContext` Workera. Każda odpowiedź poza przejściami na WebSocket, łącznie z dwoma pierwszymi skrótami i przekierowaniem, wychodzi przez `withSecurityHeaders` z `src/lib/security-headers.ts`, z nonce'em Content-Security-Policy wylosowanym dla żądania i przekazanym handlerowi Start w kontekście żądania; zobacz [Model bezpieczeństwa](/docs/architecture/security-model#nagłówki-odpowiedzi). Ten sam plik eksportuje również handler `queue`, który opróżnia kolejki newslettera i dziennika zdarzeń, i handler `scheduled`, który uruchamia codzienne [czyszczenie po okresie przechowywania](/docs/guides/data-retention), oraz re-eksportuje klasę `RealtimeInvalidationHub`, żeby Wrangler mógł ją zbindować.

## Praca w tle

Obietnica wciąż oczekująca, gdy Worker zwraca odpowiedź, jest przerywana. Hooki Better Auth i rejestratory audytu nie mają dostępu do `ExecutionContext`, dlatego `src/lib/background.ts` trzyma go w `AsyncLocalStorage`:

```ts
export const scheduleBackgroundWork = (task: Promise<unknown> | PromiseLike<unknown>): void => {
  const store = executionContextStorage.getStore()

  if (store === undefined) {
    void runSafely(task)

    return
  }
  store.waitUntil(runSafely(task))
}
```

Bez magazynu — konsument kolejki, handler `scheduled`, testy jednostkowe, ścieżki skracane przed wejściem w magazyn — degraduje się do „odpal i zapomnij”, ale odrzucenie jest logowane, a nie milcząco tracone.

## Spójność bez transakcji

D1 nie ma transakcji interaktywnych. `db.batch()` jest atomowy, więc wszystko, co musi być „wszystko albo nic”, składa się w tablicę instrukcji i przekazuje do `runDrizzleBatch` z `src/integrations/drizzle-orm/drizzle.batch.ts`. Wszystko, co musi przeczytać, zdecydować, a potem zapisać, przenosi zamiast tego decyzję do zapisu: każda instrukcja rezerwacji stanu magazynowego w `src/modules/inventory/inventory.accessors.ts` to `UPDATE` warunkowany `quantityAvailable >= qty`, który SQLite sprawdza i stosuje w jednej instrukcji, a sygnałem sukcesu jest długość `.returning()`. Nie porównuje przy tym wersji odczytanej podczas walidacji, więc checkout dostaje odmowę tylko wtedy, gdy towar się skończył, a nie dlatego, że inny checkout chwilę wcześniej zarezerwował ten sam wariant.

Koszyki z wieloma pozycjami rezerwują jednym wsadem i kompensują. `reserveInventoryForItems` zwalnia rezerwacje, które już się udały, gdy którakolwiek pozycja nie przejdzie swojego warunku — a sama kompensacja jest owinięta w `.catch()` i tylko logowana, więc nieudane wycofanie zostawia towar zarezerwowany. To saga ze znaną dziurą, a nie transakcja rozproszona.
