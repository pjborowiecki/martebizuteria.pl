Kontrola dostępu jest zdefiniowana raz, w `src/integrations/better-auth/auth.access.ts`, przy użyciu wtyczki kontroli dostępu Better Auth. Z tych samych definicji korzystają middleware serwerowe, strażnicy tras i klient Better Auth.

Najważniejszy fakt strukturalny: **funkcja serwerowa jest publicznym endpointem HTTP.** Jest osiągalna niezależnie od tego, czy trasa, która zwykle ją wywołuje, została kiedykolwiek załadowana — dlatego strażnik trasy nie może jej chronić. Autoryzację wymusza middleware `authorized` na początku każdego przypadku użycia, przed jakimkolwiek dostępem do bazy. Jedyne uprawnienie zależne od wiersza, `order: ["refund"]`, gdy `cancel-order` trafia na opłacone zamówienie, jest sprawdzane w handlerze po odczytaniu zamówienia, zanim cokolwiek się zmieni.

## Role

```ts
export const ROLES = {
  ADMIN: "admin",
  CUSTOMER: "customer",
} as const

export const DEFAULT_ROLE = ROLES.CUSTOMER

export const ADMIN_PANEL_ROLES = [ROLES.ADMIN] as const
```

| Rola   | Kod        | Otrzymuje                                                                                         |
| ------ | ---------- | ------------------------------------------------------------------------------------------------- |
| Admin  | `admin`    | Wszystkie deklaracje aplikacyjne oraz deklaracje `adminAc` Better Auth dla `user` i `session`     |
| Klient | `customer` | Żadnych deklaracji. Klient może wywoływać wyłącznie endpointy wymagające sesji, a nie uprawnienia |

Nowe konta dostają rolę `customer` przez `DEFAULT_ROLE`. `hasAdminAccess(role)` to wąski predykat używany tam, gdzie liczy się tylko „czy to odbiorca panelu administracyjnego" — w strażnikach tras i w uzgadnianiu administracyjnego WebSocketa.

Administrator potrzebuje też włączonego uwierzytelniania dwuskładnikowego. `needsTwoFactorSetup({ role, twoFactorEnabled })` jest prawdziwe dla administratora bez niego, a taki administrator nie ma żadnego uprawnienia: `authorized(permission)` odpowiada `FORBIDDEN`, punkty końcowe `/admin/*` Better Auth odpowiadają `ADMIN_TWO_FACTOR_REQUIRED`, a strażnik trasy wysyła go na `/admin/security`, żeby je włączył. Zobacz [Better Auth](/docs/integrations/better-auth#uwierzytelnianie-dwuskładnikowe-administratorów).

## Deklaracje uprawnień

Deklaracje aplikacyjne pochodzą z `PERMISSIONS_STATEMENTS`, które rozwija `defaultStatements` wtyczki admin Better Auth i dodaje cztery zasoby:

| Zasób      | Akcje                                           |
| ---------- | ----------------------------------------------- |
| `content`  | `read`, `update`                                |
| `order`    | `read`, `update`, `refund`                      |
| `product`  | `create`, `read`, `update`, `delete`, `publish` |
| `settings` | `manage`                                        |

Własne deklaracje Better Auth, przyznane roli `admin` przez `...adminAc.statements`:

| Zasób     | Akcje                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| `user`    | `create`, `list`, `set-role`, `ban`, `impersonate`, `delete`, `set-password`, `set-email`, `get`, `update` |
| `session` | `list`, `revoke`, `delete`                                                                                 |

Zwróć uwagę, że `product` obejmuje cały katalog, nie tylko tabelę `product`: kategorie, kolekcje, atrybuty i zdjęcia produktów są bramkowane akcjami `product`. Nie ma osobnego zasobu `category` ani `collection`.

## Jak sprawdza się uprawnienie

Funkcje serwerowe korzystają z middleware:

```ts
export const createCategory = createServerFn({ method: "POST" })
  .middleware([authorized({ product: ["create"] })])
  .validator((input) => productCategoryZodSchemas.createInput.parse(input))
  .handler(async ({ data }) => {
    /* ... */
  })
```

`authorized` zbudowane jest na `withRequest`, więc normalizuje też błędy. Odczytuje sesję przez `getRequestSession()`, rzuca `AppError(ERROR_CODES.UNAUTHORIZED)`, gdy sesji nie ma, rzuca `AppError(ERROR_CODES.FORBIDDEN)`, gdy rola nie ma uprawnienia, a w pozostałych przypadkach umieszcza sesję w `context.auth`:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && (!hasPermission({ permission, role: session.user.role }) || needsTwoFactorSetup(session.user))) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

Wywołanie `authorized()` bez argumentu znaczy „dowolny zalogowany użytkownik". Tak robią przypadki użycia w `customer-account` i `address`; zawężają one dostęp tożsamością w SQL, a nie rolą. Wpuszcza ono też administratora bez uwierzytelniania dwuskładnikowego i dzięki temu `/admin/security` wczytuje jego własny profil przez `getCustomerProfile`.

Kod poza ścieżką middleware wywołuje `hasPermission({ permission, role })`, `hasAdminAccess(role)` albo `needsTwoFactorSetup(user)` bezpośrednio. `hasPermission` dla nieznanej roli zwraca `false`, a nie rzuca wyjątkiem.

## Własność, nie tylko rola

Odczyty dostępne dla klienta nie pobierają wiersza, żeby potem porównać jego właściciela. Predykat własności jest wkompilowany w zapytanie, więc obce `id` nie zwraca żadnego wiersza. Wzorcem jest `customer-account/use-cases/get-customer-order.ts`:

```ts
const orderRow = await db.query.order.findFirst({
  where: and(eq(order.id, orderId), eq(order.userId, context.auth.user.id)),
  with: { checkout: { with: { billingAddress: true, shippingAddress: true } }, payment: true },
})
```

Dlatego wywołania `authorized()` w `customer-account` i `address` nie noszą uprawnienia: autoryzacją jest SQL. Podanie cudzego identyfikatora zamówienia zwraca `undefined`, a opcje zapytania zamieniają to na `notFound()`.

## Obsługa sesji

`getRequestSession` w `src/integrations/better-auth/auth.session.ts` zapamiętuje wynik odczytu sesji per `Request` w `WeakMap` i przekazuje `disableCookieCache: true`, więc każdy odczyt serwerowy weryfikuje sesję w D1, a równoległe loadery w jednym zapytaniu dzielą jedno wyszukanie.

Better Auth jest skonfigurowany w `auth.server.ts` z wyłączonym podpisanym cache cookie (`cookieCache: { enabled: false }`), `storeSessionInDatabase: true` i najwyżej pięcioma równoległymi sesjami na użytkownika (`multiSession({ maximumSessions: 5 })`). Strażnicy tras i komponenty czytają sesję przez `getCurrentSessionQuery`, którego funkcja serwerowa `getCurrentSession` również przechodzi przez `getRequestSession`, więc sesja w przeglądarce także omija cache cookie. TanStack Query uznaje ten wynik za świeży przez 60 sekund i nie pobiera go ponownie po powrocie do okna, więc komponent może jeszcze wyrenderować stan zalogowania, który serwer już zakończył. Prawdziwa nawigacja do `/account` lub `/admin` sprawdza sesję ponownie ze `staleTime: 0`, a każda chroniona funkcja serwerowa sama odczytuje sesję przez `authorized()`, więc nieaktualny wpis w cache nigdy nie daje dostępu.

`getCurrentSession` usuwa token sesji przed zwróceniem danych do przeglądarki — `toClientSession` odcina pole `token` — więc klient nigdy go nie otrzymuje.

## Limity zapytań

Dwie warstwy, obie zapisujące do tabeli `rate_limit`.

**Własny limiter Better Auth**, liczony tym samym `withinRateLimit` co middleware poniżej i skonfigurowany z `customStorage: authRateLimitStorage`, globalnym limitem 100 zapytań na 60 sekund i czterema regułami per endpoint:

| Endpoint                           | Maks. na 60 s |
| ---------------------------------- | ------------- |
| `/api/auth/sign-in/email`          | 5             |
| `/api/auth/sign-up/email`          | 3             |
| `/api/auth/request-password-reset` | 3             |
| `/api/auth/reset-password`         | 5             |

**Middleware aplikacji `withRateLimit`**, z czterema nazwanymi budżetami w `auth.middleware.ts`, wszystkie w oknie 60 sekund:

| Budżet      | Maks. | Zastosowany do                                                                                                                                                                                               |
| ----------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `BROWSING`  | 120   | `search-storefront` w `search-storefront.ts`, `search-storefront-products` w `get-storefront-products-page.ts` dla listingu z parametrem `q` oraz `record-customer-activity` w `record-customer-activity.ts` |
| `CHECKOUT`  | 10    | `checkout-create` i `checkout-update` w `src/integrations/stripe/stripe.actions.ts` oraz `discount-validate` w `validate-discount-code.ts`                                                                   |
| `SENSITIVE` | 3     | `create-user-address`, `update-customer-phone`, `revoke-other-customer-sessions`                                                                                                                             |
| `TOKEN`     | 5     | Na razie do niczego; sprawdzany tylko względem `SENSITIVE` w `auth.middleware.test.ts`                                                                                                                       |

Obie warstwy kluczują po adresie IP klienta. `clientAddress` w `src/lib/rate-limit.ts` czyta wyłącznie nagłówek `cf-connecting-ip`, który ustawia brzeg sieci i którego klient nie podrobi. Sam licznik to jedno `INSERT ... ON CONFLICT DO UPDATE` ze strażnikiem `setWhere`, więc reset okna i inkrementacja są jedną atomową instrukcją. Jeśli tabela jest niedostępna, helper loguje `Rate-limit storage unavailable` i zwraca `false`, więc middleware rzuca `TOO_MANY_REQUESTS` — zawodzi w stronę zamkniętą.
