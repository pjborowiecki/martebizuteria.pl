title: "Trasy"
description: "Każda ścieżka w aplikacji, jej stała w ROUTES, plik trasy i strażnik."
---

Każdy literał ścieżki w aplikacji leży w `ROUTES` w `src/routes.ts`. Komponenty linkują przez stałą — `<Link to={ROUTES.CART}>` — a router dokłada prefiks lokalizacji na wyjściu.

Pliki tras w `src/routes` **nie zawierają segmentu lokalizacji**. `src/router.tsx` instaluje przepisywanie adresów:

```ts
rewrite: {
  input: ({ url }) => deLocalizeUrl(url),
  output: ({ url }) => localizeUrl(url),
}
```

dzięki czemu `_storefront.products.$handle.tsx` obsługuje zarówno `/products/kolczyki` (polski, lokalizacja domyślna, bez prefiksu), jak i `/en-US/products/kolczyki`. Nadmiarowy adres `/pl-PL/...` jest przekierowywany kodem 301 w `src/server.ts`, jeszcze przed uruchomieniem routera, przez `resolveLocale` z `src/integrations/use-intl/i18n.middleware.ts`.

## Sklep

Wszystkie strony sklepu leżą pod layoutem bez ścieżki `_storefront.tsx`, który dostarcza `Navigation`, `Footer`, banner dostępności koszyka, tracker aktywności klienta, subskrypcję realtime dla sklepu oraz `storefront.css`. Żadna z nich nie ma strażnika.

## Proces zamówienia

| Ścieżka     | Stała w `ROUTES` | Plik trasy                           | Uwagi                                                                          |
| ----------- | ---------------- | ------------------------------------ | ------------------------------------------------------------------------------ |
| `/checkout` | `CHECKOUT`       | `checkout.tsx`, `checkout.index.tsx` | Własny layout, bez chromu sklepu; brak strażnika — zamówienie działa dla gości |

`checkout.tsx` waliduje dwa parametry wyszukiwania: `step`, liczbę całkowitą ograniczoną do zakresu 1–4, oraz `success`, opcjonalną wartość logiczną. Numer kroku żyje w adresie URL, więc odświeżenie strony zachowuje miejsce, w którym był klient.

## Uwierzytelnianie

Layoutem `/auth` jest `auth.tsx`, a jego `beforeLoad` uruchamia `redirectAuthenticated`, który odsyła już zalogowaną osobę do `/admin` albo `/account/overview`, zależnie od roli.

| Ścieżka                 | Stała w `ROUTES`       | Plik trasy                 |
| ----------------------- | ---------------------- | -------------------------- |
| `/auth/sign-in`         | `AUTH_SIGN_IN`         | `auth.sign-in.tsx`         |
| `/auth/sign-up`         | `AUTH_SIGN_UP`         | `auth.sign-up.tsx`         |
| `/auth/forgot-password` | `AUTH_FORGOT_PASSWORD` | `auth.forgot-password.tsx` |
| `/auth/reset-password`  | `AUTH_RESET_PASSWORD`  | `auth.reset-password.tsx`  |

`ROUTES.AUTH_EMAIL_VERIFICATION` (`/auth/email-verification`) jest zadeklarowana, ale nie ma pliku trasy i nic się do niej nie odwołuje, więc ta ścieżka zwraca obecnie 404.

`ROUTES.API_AUTH` to zagnieżdżony obiekt ze ścieżkami endpointów Better Auth względem `/api/auth` — `/sign-in/email`, `/sign-up/email`, `/sign-out`, `/request-password-reset`, `/reset-password`. Służą do konfigurowania limitów zapytań per endpoint, a nie do budowania odnośników.

## API i ścieżki obsługiwane na poziomie Workera

Ścieżki API nigdy nie są lokalizowane — `shouldIgnorePath` w `src/integrations/use-intl/i18n.paths.ts` wyłącza `/api`, `/rpc`, `/_serverFn` i `/assets` z obsługi lokalizacji.

| Ścieżka                       | Obsługiwana przez                                     | Uwagi                                                                           |
| ----------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| `/api/auth/*`                 | `src/routes/api/auth.$.ts`                            | Własny handler Better Auth                                                      |
| `/api/webhooks/stripe`        | `src/routes/api/webhooks.stripe.ts`                   | Zdarzenia Stripe z weryfikacją podpisu                                          |
| `/api/realtime/admin/ws`      | `src/server.ts` → `ROUTES.API_REALTIME.ADMIN_WS`      | Upgrade WebSocket, rola sprawdzana w Workerze przed adresowaniem Durable Object |
| `/api/realtime/storefront/ws` | `src/server.ts` → `ROUTES.API_REALTIME.STOREFRONT_WS` | Upgrade WebSocket, otwarty dla wszystkich                                       |
| `/sitemap.xml`                | `src/server.ts` → `generateSitemapXml`                | Cache na jeden dzień                                                            |
| `/robots.txt`                 | `src/server.ts` → `generateRobotsTxt`                 | Treść zależy od `env.APP_ENV`                                                   |

Cztery ostatnie ścieżki są sprawdzane w `src/server.ts`, zanim zapytanie dotrze do TanStack Start, więc żadna z nich nie płaci za render SSR. `/api/auth/*` oraz `/api/webhooks/stripe` to trasy serwerowe TanStack Start w `src/routes/api/`, więc przechodzą przez router, ale nigdy nie renderują strony.

## Strażnicy

Wszyscy czterej strażnicy leżą w `src/integrations/better-auth/auth.routes.ts`.

| Strażnik                | Zachowanie                                                                                                                | Używany przez           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `requireUser`           | Przekierowuje do `/auth/sign-in`, gdy nie ma sesji                                                                        | Przez dwóch pozostałych |
| `requireAdmin`          | `requireUser`, a potem przekierowuje osobę bez roli admina do `/account/overview`                                         | `admin.tsx`             |
| `requireCustomer`       | `requireUser`, a potem przekierowuje administratora do `/admin`                                                           | `account.tsx`           |
| `redirectAuthenticated` | Odsyła zalogowaną osobę do `postAuthRouteFor(user)` — `/admin` dla administratora, w przeciwnym razie `/account/overview` | `auth.tsx`              |

Strażnicy działają w `beforeLoad`, co oznacza, że uruchamiają się również w przeglądarce podczas nawigacji po stronie klienta. **Są elementem doświadczenia nawigacji, nie autoryzacją.** Funkcja serwerowa jest publicznym endpointem HTTP niezależnie od tego, czy jej trasa została załadowana, dlatego autoryzację wymusza middleware `authorized` wewnątrz każdego przypadku użycia — zobacz [Uprawnienia](/docs/reference/permissions).
