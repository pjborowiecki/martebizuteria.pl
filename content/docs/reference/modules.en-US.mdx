description: "All 43 modules in src/modules, the database tables each one owns, and every use case it exports."
---

`src/modules` holds 43 folders. Thirty-eight own the 41 tables registered with Drizzle, since `order` also owns `order_number_sequence` and `discount` also owns `discount_redemption` and `discount_claim`. `storefront-search` owns the FTS5 virtual table `storefront_search`, which is declared in its schema file but not registered. Four own no table and exist because they group operations that read across several of them. Together they export 176 use cases, of which 138 are `createServerFn` endpoints and 38 are plain server-side functions.

Every table except `storefront_search` is re-exported from `src/integrations/drizzle-orm/drizzle.schemas.ts`, which is what makes it part of the Drizzle schema and therefore part of the relational query API (`db.query.<table>`). A table that is not listed there does not exist for `db.query` or drizzle-kit: `storefront_search` is created by the hand-written `20261002100000_storefront_search.sql` migration and queried with `db.select().from(storefrontSearch)` in `storefront-search.accessors.server.ts`.

## Modules with no table

Four modules exist for operations rather than for rows.

| Module              | Why it has no table                                                                                                     |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `_core`             | Shared kernel: error codes, currency and country catalogs, table export, pagination, column filters, datetime helpers   |
| `admin-dashboard`   | Aggregates over `order`, `payment`, `product` and `user` for the admin overview cards and charts                        |
| `customer-account`  | The customer-facing view of `user`, `order`, `session` and `address`, always scoped to the signed-in user               |
| `customer-activity` | Records browsing activity; state lives in `src/modules/customer-activity/customer-activity.tracking.ts`, not in a table |

## Inside `_core`

`_core` is the only module allowed to be generic, and it is deliberately small.

`_core/constants/`:

| File             | Exports                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `errors.ts`      | `ERROR_CODES`, the `AppError` class and `errorCode`                                                                                                                                                                                                                                                                                               |
| `api.ts`         | `HTTP_STATUS`, `WORKERS_DEV_HOSTS` — the `workers.dev` host of the preview and production Workers, which the deploy's live-site check asks — `isLocalMode`, `appHostsForMode` — the host allowlist Better Auth is built with and `resolveRequestOrigin` checks — and `isLocalHost` and `isDeploymentHost`, which `resolveDeploymentOrigin` checks |
| `currency.ts`    | `CURRENCIES`, the ISO 4217 table with numeric codes and exponents                                                                                                                                                                                                                                                                                 |
| `country.ts`     | The ISO country reference table                                                                                                                                                                                                                                                                                                                   |
| `timezone.ts`    | The IANA timezone reference table                                                                                                                                                                                                                                                                                                                 |
| `placeholder.ts` | Placeholder image data                                                                                                                                                                                                                                                                                                                            |
| `tax.ts`         | `STANDARD_VAT_BASIS_POINTS` (23%), `BASIS_POINTS_SCALE` and `VAT_COUNTRY_CODE`                                                                                                                                                                                                                                                                    |

`country.ts` is reference data: `COUNTRIES` is the list the seller's country is chosen from under Settings → Store details, checked by `storeSettingZodSchemas.sellerDetails` and listed by the form's country select, and `timezone.ts` imports its `CountryCode` type. `timezone.ts` is in use: the time zone field on the profile page and in the admin's Settings → My account lists `TIMEZONES`, `list-saved-payment-methods` resolves the customer's zone with `resolveTimezoneCode` to decide whether a saved card has expired, and `DEFAULT_TIMEZONE_CODE` (`Europe/Warsaw`) is the shop's own zone for the order-number year and the legal deadlines. The admin's days and months follow each admin's own time zone.

`_core/utils/` holds `column-filters.ts` and `column-filters.server.ts`, `datetime-column-filter.ts` and its `.server` twin, `search-conditions.server.ts`, `pagination.ts`, `currency.ts`, `datetime.ts`, `download.ts`, `iso-date.ts`, `iso-datetime.ts`, `json.ts`, `country-name.ts`, `polish-business-ids.ts`, `polish-deadline.ts`, `table-export.ts`, `tax.ts` and `zod-fields.ts`. The `.server` halves build SQL; the plain halves are shared with the browser. `table-export.ts` turns an admin table export into CSV, JSON, XML or plain text and names its file, and `download.ts` hands a text file to the browser. `country-name.ts` names a country code in a language with `Intl.DisplayNames`, for the order addresses and the seller's details, and `polish-business-ids.ts` normalises and checks NIP and REGON numbers, for the checkout's company invoice and the seller's details.

## Tables written from outside their own module

Several tables have no use cases of their own because they are only ever written as part of an atomic `db.batch`:

- `product_option`, `product_option_value`, `product_variant`, `option_on_variant`, `product_image`, `category_on_product`, `collection_on_product` and `attribute_on_product` are replaced wholesale by `product/use-cases/create-complete-product.ts` and `update-complete-product.ts`.
- `order`, `order_item`, `order_address` and `payment` are written by `checkout/use-cases/fulfill-checkout.server.ts`, which delegates statement building to `prepareFulfillCheckoutBatch` and runs them through `runDrizzleBatch`. The batch also takes the next number from `order_number_sequence` through `prepareOrderNumberAllocation`, so a failed batch keeps the number for its retry. `prepareDiscountRedemption` adds the discount's statements to the same batch: it deletes the checkout's `discount_claim` rows and, when a discount applied, writes `discount_redemption` and increments `discount.usage_count`.
- `discount_claim` is written by `prepareDiscountClaim` (`discount/discount.claim.server.ts`), from the create batch and from `claimCheckoutDiscount` when a session is edited, and deleted by the release, supersede and fulfilment batches and by `releaseDiscountClaims` and `releaseUnappliedDiscountClaims` when building a session fails.
- `inventory` is reserved, consumed and released by the batches built in `checkout/checkout.utils.ts` (`prepareCreateCheckoutBatch`, `prepareFulfillCheckoutBatch`, `prepareReleaseCheckoutBatch`) and restocked by `prepareRestockOrderBatch` in `order/order.utils.ts`, which `prepareCancelOrderBatch` and `returnOrderToStock` (`order/order.restock.server.ts`) run, at most once per order as `order.restocked_at` records. A refund alone never restocks. The product editor changes it only by the difference between the stock field and the stock it loaded, in `prepareProductCatalogBatch` (`product/product.mutations.ts`), and a check refuses any change that would take available stock below zero.
- `price_history` is written only by the `price_history_variant_insert` and `price_history_variant_update` triggers on `product_variant`, so the product batch records a variant's new prices in the statement that writes them, and so does any other write to a variant's prices.
- `account`, `session`, `verification` and `two_factor` are Better Auth's tables. Application code reads them, and writes to them directly only when the retention clean-up deletes expired `session` and `verification` rows.
- `order.user_id` of a guest order is set outside any use case: the fulfilment batch files a guest checkout under the account that has verified the same e-mail address, and `claimGuestOrdersForUser` (`order/order.claim.server.ts`), which Better Auth's user and e-mail-verification hooks in `auth.hooks.server.ts` call, moves earlier guest orders onto an account once its address is verified. The `20261016140000_claim_past_guest_orders.sql` migration did the same once for orders placed before that existed. Each claim is recorded as `customer.orders_claimed`.
