title: "Module catalog"
description: "All 41 modules in src/modules, the database tables each one owns, and every use case it exports."
---

`src/modules` holds 41 folders, and a folder exists only for a database table of the same name. Thirty-nine own the 42 tables registered with Drizzle, since `order` also owns `order_number_sequence` and `discount` also owns `discount_redemption` and `discount_claim`. `storefront-search` owns the FTS5 virtual table `storefront_search`, which is declared in its schema file but not registered. `_core` alone owns no table: it holds the helpers that several tables share. Together they export 219 use cases, of which 139 are `createServerFn` endpoints and 80 are plain server-side functions.

Every table except `storefront_search` is re-exported from `src/integrations/drizzle-orm/drizzle.schemas.ts`, which is what makes it part of the Drizzle schema and therefore part of the relational query API (`db.query.<table>`). A table that is not listed there does not exist for `db.query` or drizzle-kit: `storefront_search` is created by the hand-written `20261002100000_storefront_search.sql` migration and queried with `db.select().from(storefrontSearch)` in `storefront-search.accessors.ts`.

## The folder with no table

Only `_core` has no table. Code that serves the tables of several modules goes there instead of into a folder of its own; the customer account pages, for example, share their stale time (`CUSTOMER_ACCOUNT_QUERY_STALE_MS` in `_core/constants/customer-account.ts`) from it. Code that serves no table stays out of `src/modules`: the account page titles are `accountPageMeta` in `src/lib/seo.ts`, and the table export and file download of the admin data grid sit in `src/presentation/components/custom/datagrid/lib`.

| Module  | Why it has no table                                                                                                   |
| ------- | --------------------------------------------------------------------------------------------------------------------- |
| `_core` | Shared kernel: error codes, currency and country catalogs, table export, pagination, column filters, datetime helpers |

## Inside `_core`

`_core` is the only module allowed to be generic, and it is deliberately small.

`_core/constants/`:

`country.ts` is reference data: `COUNTRIES` is the list the seller's country is chosen from under Settings → Store details, checked by `storeSettingZodSchemas.sellerDetails` and listed by the form's country select, and `timezone.ts` imports its `CountryCode` type. `timezone.ts` is in use: the time zone field on the profile page and in the admin's Settings → My account lists `TIMEZONES`, and `DEFAULT_TIMEZONE_CODE` (`Europe/Warsaw`) is the shop's own zone for the order-number year and the legal deadlines. Its `resolveTimezoneCode`, which maps a stored value to one of those zones or to the default, has no caller outside its tests: the admin's days and months and the expiry of a customer's saved cards follow the display time zone `resolveRequestDisplayPreferences()` resolves.

`_core/utils/` holds `column-filters.ts` and `column-filters.server.ts`, `datetime-column-filter.ts` and its `.server` twin, `search-conditions.server.ts`, `pagination.ts`, `currency.ts`, `datetime.ts`, `iso-date.ts`, `iso-datetime.ts`, `json.ts`, `country-name.ts`, `polish-business-ids.ts`, `polish-deadline.ts`, `tax.ts` and `zod-fields.ts`. The `.server` halves build SQL; the plain halves are shared with the browser. `country-name.ts` names a country code in a language with `Intl.DisplayNames`, for the order addresses and the seller's details, and `polish-business-ids.ts` normalises and checks NIP and REGON numbers, for the checkout's company invoice and the seller's details.

## Tables written from outside their own module

Several tables have no use cases of their own because they are only ever written as part of an atomic `db.batch`:

- `product_option`, `product_option_value`, `product_variant`, `option_on_variant`, `product_image`, `category_on_product`, `collection_on_product` and `attribute_on_product` are replaced wholesale by `product/use-cases/create-complete-product.ts` and `update-complete-product.ts`.
- `order`, `order_item`, `order_address` and `payment` are written by `checkout/use-cases/fulfill-checkout.server.ts`, which delegates statement building to `prepareFulfillCheckoutBatch` and runs them through `runDrizzleBatch`. The batch also takes the next number from `order_number_sequence` through `prepareOrderNumberAllocation`, so a failed batch keeps the number for its retry. `prepareDiscountRedemption` adds the discount's statements to the same batch: it deletes the checkout's `discount_claim` rows and, when a discount applied, writes `discount_redemption` and increments `discount.usage_count`.
- `discount_claim` is written by `prepareDiscountClaim` (`discount/use-cases/claim-checkout-discount.server.ts`), from the create batch and from `claimCheckoutDiscount` when a session is edited, and deleted by the release, supersede and fulfilment batches and by `releaseDiscountClaims` and `releaseUnappliedDiscountClaims` when building a session fails.
- `inventory` is reserved, consumed and released by the batches built in `checkout/checkout.accessors.ts` (`prepareCreateCheckoutBatch`, `prepareFulfillCheckoutBatch`, `prepareReleaseCheckoutBatch`) and restocked by `prepareRestockOrderBatch` in `order/use-cases/return-order-to-stock.server.ts`, which `prepareCancelOrderBatch` (`order/use-cases/cancel-order.server.ts`) and `returnOrderToStock` run, at most once per order as `order.restocked_at` records. A refund alone never restocks. The product editor changes it only by the difference between the stock field and the stock it loaded, in `prepareProductCatalogBatch` (`product/product.accessors.ts`), and a check refuses any change that would take available stock below zero.
- `price_history` is written only by the `price_history_variant_insert` and `price_history_variant_update` triggers on `product_variant`, so the product batch records a variant's new prices in the statement that writes them, and so does any other write to a variant's prices.
- `account`, `session`, `verification` and `two_factor` are Better Auth's tables. Application code reads them, and writes to them directly only when the retention clean-up deletes expired `session` and `verification` rows and when a completed change of address deletes the account's `verification` rows (`deleteVerificationsOfUser`) and its other `session` rows (`finishEmailChange`).
- `user_email_history` is written only by the `user_email_history_user_insert` and `user_email_history_user_update` triggers on `user`, so every path that creates an account or changes its address, Better Auth's or any other, records the address in the same statement.
- `order.user_id` of a guest order is set outside any server function: the fulfilment batch files a guest checkout under the account that has verified the checkout's e-mail address, and `claimGuestOrdersForUser` (`order/use-cases/claim-guest-orders.server.ts`), which Better Auth's user and e-mail-verification hooks in `auth.hooks.server.ts` call, moves the earlier guest orders that belong to an account by its address history onto it once its address is verified. The `20261016140000_claim_past_guest_orders.sql` migration did the same once for orders placed before that existed. Each claim is recorded as `customer.orders_claimed`.
