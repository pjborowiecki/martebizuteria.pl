`src/modules` zawiera 36 katalogów. Trzydzieści jeden z nich jest właścicielem tabeli w bazie danych; pięć nie ma własnej tabeli i istnieje, bo grupuje operacje czytające z kilku tabel jednocześnie. Razem eksportują 82 przypadki użycia, z czego 75 to endpointy `createServerFn`, a 7 to zwykłe funkcje serwerowe.

Każda tabela jest re-eksportowana z `src/integrations/drizzle-orm/drizzle.schemas.ts` — to właśnie sprawia, że należy do schematu Drizzle, a więc również do relacyjnego API zapytań (`db.query.<tabela>`). Tabela, której tam nie ma, dla Drizzle nie istnieje.

## Moduły bez tabeli

Pięć modułów istnieje dla operacji, a nie dla wierszy.

| Moduł               | Dlaczego nie ma tabeli                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `_core`             | Wspólny rdzeń: kody błędów, katalogi walut i krajów, CSV, paginacja, filtry kolumn, helpery daty i czasu                     |
| `admin-dashboard`   | Agregaty po `order`, `payment`, `product` i `user` dla kart i wykresów w przeglądzie panelu                                  |
| `customer-account`  | Widok `user`, `order`, `session` i `address` dostępny dla klienta, zawsze zawężony do zalogowanego użytkownika               |
| `customer-activity` | Rejestruje aktywność przeglądania; stan leży w `src/modules/customer-activity/customer-activity.tracking.ts`, a nie w tabeli |
| `storefront-search` | Wyszukiwanie po kolumnach JSON katalogu oraz odczyt popularnych fraz                                                         |

## Wewnątrz `_core`

`_core` to jedyny moduł, któremu wolno być generyczny — i jest świadomie mały.

`_core/constants/`:

| Plik             | Eksportuje                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| `errors.ts`      | `ERROR_CODES`, klasę `AppError` i `errorCode`                                                                 |
| `api.ts`         | `HTTP_STATUS`, `isLocalMode`, `appHostsForMode` — listę dozwolonych hostów, z którą budowany jest Better Auth |
| `currency.ts`    | `CURRENCIES`, tabelę ISO 4217 z kodami numerycznymi i wykładnikami                                            |
| `country.ts`     | Tabelę referencyjną krajów ISO                                                                                |
| `timezone.ts`    | Tabelę referencyjną stref czasowych IANA                                                                      |
| `placeholder.ts` | Dane obrazu zastępczego                                                                                       |

`country.ts` i `timezone.ts` to dane referencyjne trzymane świadomie, nawet tam, gdzie nic ich jeszcze nie importuje.

`_core/utils/` zawiera `column-filters.ts` i `column-filters.server.ts`, `datetime-column-filter.ts` wraz z bliźniakiem `.server`, `search-conditions.server.ts`, `pagination.ts`, `csv.ts`, `currency.ts`, `datetime.ts`, `iso-date.ts`, `iso-datetime.ts`, `json.ts` oraz `zod-fields.ts`. Połówki `.server` budują SQL; zwykłe połówki są dzielone z przeglądarką.

## Przypadki użycia bez endpointu RPC

Siedem plików w `use-cases` eksportuje zwykłą funkcję `async`, a nie `createServerFn`. Wywołuje je handler webhooka Stripe lub inny kod serwerowy i nie są osiągalne po HTTP:

| Plik                                                    | Wywoływany z                                     |
| ------------------------------------------------------- | ------------------------------------------------ |
| `checkout/use-cases/create-checkout.server.ts`          | Akcji serwerowych procesu zamówienia             |
| `checkout/use-cases/update-checkout-delivery.server.ts` | Akcji serwerowych procesu zamówienia             |
| `checkout/use-cases/fulfill-checkout.server.ts`         | Zdarzenia `checkout.session.completed` ze Stripe |
| `checkout/use-cases/release-checkout.server.ts`         | Zdarzenia `checkout.session.expired` ze Stripe   |
| `order/use-cases/refund-order.ts`                       | Zdarzeń zwrotu płatności ze Stripe               |
| `order/use-cases/flag-order-dispute.ts`                 | Zdarzeń sporu ze Stripe                          |
| `order/use-cases/clear-order-dispute.ts`                | Zdarzeń zamknięcia sporu ze Stripe               |

Test w `src/integrations/better-auth/__test__/use-case-authorization.test.ts` przechodzi po każdym pliku w `src/modules/*/use-cases/` i pomija te bez `createServerFn` — dlatego nie potrzebują one middleware autoryzacji.

## Tabele zapisywane spoza własnego modułu

Kilka tabel nie ma własnych przypadków użycia, bo są zapisywane wyłącznie w ramach atomowego `db.batch`:

- `product_option`, `product_option_value`, `product_variant`, `option_on_variant`, `product_image`, `category_on_product`, `collection_on_product` i `attribute_on_product` są podmieniane w całości przez `product/use-cases/create-complete-product.ts` oraz `update-complete-product.ts`.
- `order`, `order_item` i `payment` zapisuje `checkout/use-cases/fulfill-checkout.server.ts`, który budowanie instrukcji zleca `prepareFulfillCheckoutBatch`, a następnie uruchamia je przez `runDrizzleBatch`.
- `inventory` jest rezerwowana, konsumowana i zwalniana przez wsady budowane w `checkout/checkout.utils.ts` (`prepareCreateCheckoutBatch`, `prepareFulfillCheckoutBatch`, `prepareReleaseCheckoutBatch`), a uzupełniana przez `prepareRefundBatch` w `order/order.utils.ts`.
- `account`, `session`, `verification` i `two_factor` to tabele Better Auth. Kod aplikacji je czyta, ale nigdy nie zapisuje bezpośrednio.
