Every path literal in the application lives in `ROUTES` in `src/routes.ts`. Components link with the constant — `<Link to={ROUTES.CART}>` — and the router adds the locale prefix on the way out.

Route files in `src/routes` carry **no locale segment**. `src/router.tsx` installs a rewrite:

```ts
rewrite: {
  input: ({ url }) => deLocalizeUrl(url),
  output: ({ url }) => localizeUrl(url),
}
```

so `_storefront.products.$handle.tsx` serves both `/products/kolczyki` (Polish, the default locale, no prefix) and `/en-US/products/kolczyki`. A redundant `/pl-PL/...` URL is redirected with a 301 in `src/server.ts` before the router ever runs, by `resolveLocale` in `src/integrations/use-intl/i18n.middleware.ts`.

## Storefront

All storefront pages sit under the pathless layout `_storefront.tsx`, which supplies `Navigation`, `Footer`, the cart-availability banner, the customer-activity tracker and the storefront realtime subscription. Its loader loads `getCollectionsQuery()` for the full-screen menu, so the menu's collection pictures are in the server-rendered cache. None of them has a guard.

## Checkout

| Path        | `ROUTES` constant | Route file                           | Notes                                                                                                                                                 |
| ----------- | ----------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/checkout` | `CHECKOUT`        | `checkout.tsx`, `checkout.index.tsx` | Own layout, no storefront chrome, its own realtime subscription to the delivery methods and free delivery; no route guard — checkout works for guests |

`checkout.tsx` validates three search parameters: `step`, an integer clamped to 1–4, `success`, an optional boolean, and `session_id`, the Checkout Session id that Stripe adds to the session's `return_url` and the payment step adds after a payment confirmed on the page, at most 255 characters. With `success`, the page shows the confirmation only once `getCheckoutSessionStatus` reports that session `complete`, and otherwise returns to `step=4`. The step lives in the URL so a reload keeps the customer where they were.

## Authentication

The `/auth` layout is `auth.tsx` and its `beforeLoad` runs `redirectIfSignedIn`, which sends an already signed-in visitor to the `?redirect` search parameter when it is a safe same-site path, and otherwise to `/admin` or `/account/overview` depending on their role. `auth.sign-in.tsx` declares that parameter in `validateSearch`. The layout renders the storefront `Navigation`, and its loader loads `getCollectionsQuery()` for the full-screen menu.

After a successful password sign-in or two-factor challenge, the form calls `usePostAuthRedirect` from `src/hooks/use-post-auth-redirect.ts`. It removes the cached session entry only, clears the router's cached matches and invalidates the router. The `/auth` layout guard then runs again, fetches the fresh session and redirects, so the forms never choose a destination themselves. When the fresh session arrives, `clearCacheOnUserChange`, described under Guards below, forgets what was cached while signed out.

Google sign-in goes through `useOAuthSignIn` in `src/presentation/components/custom/pages/auth/hooks/use-oauth-sign-in.ts`. Its `callbackURL` is the page the button was clicked on (`location.publicHref` from `useLocation`), for example `/en-US/auth/sign-in?redirect=...`. After the provider round trip the browser lands back on that auth page, and `redirectIfSignedIn` sends the user on exactly as after a password sign-in.

| Path                    | `ROUTES` constant      | Route file                 |
| ----------------------- | ---------------------- | -------------------------- |
| `/auth/sign-in`         | `AUTH_SIGN_IN`         | `auth.sign-in.tsx`         |
| `/auth/sign-up`         | `AUTH_SIGN_UP`         | `auth.sign-up.tsx`         |
| `/auth/forgot-password` | `AUTH_FORGOT_PASSWORD` | `auth.forgot-password.tsx` |
| `/auth/reset-password`  | `AUTH_RESET_PASSWORD`  | `auth.reset-password.tsx`  |

`ROUTES.AUTH_EMAIL_VERIFICATION` (`/auth/email-verification`) is declared but has no route file and nothing references it, so that path currently 404s.

`ROUTES.API_AUTH` is a nested object of Better Auth endpoint paths relative to `/api/auth` — `/change-email`, `/request-password-reset`, `/reset-password`, `/send-verification-email`, `/sign-in/email`, `/sign-out`, `/sign-up/email`. They configure per-endpoint rate limiting, the sign-in and sign-out audit entries and the email delivery gate in `auth.constants.ts`, rather than build links.

## Guards

All five guards live in `src/integrations/better-auth/auth.routes.ts`. A layout route passes the guard itself, as in `beforeLoad: requireAdmin`.

| Guard                | Behaviour                                                                                                                                    | Used by                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `requireSignedIn`    | Redirects to `/auth/sign-in` with the requested path in `?redirect` when there is no session                                                 | Via the others                                    |
| `requireAdminRole`   | `requireSignedIn`, then redirects a non-admin to `/account/overview`                                                                         | `admin_.security.tsx`                             |
| `requireAdmin`       | `requireAdminRole`, then redirects an admin without two-factor authentication to `/admin/security`                                           | `admin.tsx`, `admin_.orders.$orderId.summary.tsx` |
| `requireCustomer`    | `requireSignedIn`, then redirects an admin to `/admin`                                                                                       | `account.tsx`                                     |
| `redirectIfSignedIn` | Sends a signed-in visitor to the `?redirect` path, or else to `postAuthRouteFor(user)`: `/admin` for an admin, `/account/overview` otherwise | `auth.tsx`                                        |

`needsTwoFactorSetup`, which `requireAdmin` consults, holds only when the build's mode is `production` or `test` (`isAdminTwoFactorRequired` in `auth.access.ts`); in development and preview an admin passes `requireAdmin` without two-factor authentication.

`requireSignedIn`, `requireAdminRole`, `requireAdmin` and `requireCustomer` take the `beforeLoad` options (`{ context, location, preload }`) and resolve to `{ user }`. That becomes route context, so a page under the layout reads the signed-in user with `Route.useRouteContext().user`.

`requireSignedIn` puts `location.publicHref` in `?redirect`: the localized public path, such as `/en-US/account/orders/order-1`. The value is kept only when it is a string matching `SAME_SITE_PATH_PATTERN`, `/^\/(?![/\\])[!-[\]-~]*$/u`: printable ASCII only, a single leading slash and no backslash. An absolute URL, a protocol-relative `//`, a backslash, whitespace or a control character is dropped: `requireSignedIn` then redirects to `/auth/sign-in` without it, and `redirectIfSignedIn` falls back to `postAuthRouteFor(user)`. Otherwise `redirectIfSignedIn` sends the visitor there with `redirect({ href })`, so a server-rendered redirect keeps the visitor's language, and on the client the router re-localizes it to the current language.

Guards only read the session, through `loadRouteSession`: `queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)`. `requireSignedIn`, `requireAdminRole`, `requireAdmin` and `requireCustomer` pass `recheck: true`, so a real navigation into `/account` or `/admin` re-checks the session with `staleTime: 0`; a link preload, and `redirectIfSignedIn` with `recheck: false`, reuse a cached session younger than 60 seconds. The session a guard loads stays in the TanStack Query cache, so the navigation's account link, the wishlist and the checkout prefill read the same value through `useQuery(getCurrentSessionQuery)`. `TranslationsProvider` in `__root.tsx` reads `displayPreferencesQuery` instead: `getDisplayPreferences` resolves the viewer's time zone and format locale on the server from the user's saved choices, the `marte_time_zone` cookie, Cloudflare's `request.cf.timezone` and `Accept-Language`, and the provider passes them to `IntlProvider`. A server render dehydrates it into the page, so guarded pages render signed-in on the server.

A change of user is handled in one place, `clearCacheOnUserChange(queryClient)` in `src/integrations/better-auth/auth.session.ts`. `getRouter` in `src/router.tsx` installs it in the browser only, next to `setupQueryClientInvalidationBroadcast`; server rendering skips it because every request starts with an empty `QueryClient`. It subscribes to the query cache, and whenever the session query's data switches to a different user id, including signed out to signed in and back, it removes every cached query except the session itself, the display preferences and the translation message catalogues (`isMessagesQuery` from `src/integrations/use-intl/i18n.messages.ts`), then invalidates the display preferences so the new user's saved time zone and format locale load. It ignores the first session it sees and the session entry being removed. Because it watches the cache, it catches a change whoever fetched the session: a guard, a component, a refetch after invalidation, or hydration.

Sign-out is a full page load that discards the whole cache: the account sidebar goes to `/`, the admin sidebar to `/auth/sign-in`.

Guards run in `beforeLoad`, which means they also run in the browser during client-side navigation. **They are navigation UX, not authorization.** A server function is a public HTTP endpoint whether or not its route was loaded, so authorization is enforced by the `authorized` middleware inside each use case — see [Permissions](/docs/reference/permissions).
