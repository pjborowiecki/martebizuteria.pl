Every path literal in the application lives in `ROUTES` in `src/routes.ts`. Components link with the constant — `<Link to={ROUTES.CART}>` — and the router adds the locale prefix on the way out.

Route files in `src/routes` carry **no locale segment**. `src/router.tsx` installs a rewrite:

```ts
rewrite: {
  input: ({ url }) => deLocalizeUrl(url),
  output: ({ url }) => localizeUrl(url),
}
```

so `_storefront.products.$handle.tsx` serves both `/products/kolczyki` (Polish, the default locale, no prefix) and `/en-US/products/kolczyki`. A redundant `/pl-PL/...` URL is redirected with a 301 in `src/server.ts` before the router ever runs, by `resolveLocale` in `src/integrations/use-intl/i18n.middleware.ts`.

## Storefront

## Checkout

| Path        | `ROUTES` constant | Route file                           | Notes                                                                        |
| ----------- | ----------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| `/checkout` | `CHECKOUT`        | `checkout.tsx`, `checkout.index.tsx` | Own layout, no storefront chrome; no route guard — checkout works for guests |

`checkout.tsx` validates two search parameters: `step`, an integer clamped to 1–4, and `success`, an optional boolean. The step lives in the URL so a reload keeps the customer where they were.

## Authentication

The `/auth` layout is `auth.tsx` and its `beforeLoad` runs `redirectAuthenticated`, which sends an already signed-in visitor to `/admin` or `/account/overview` depending on their role.

| Path                    | `ROUTES` constant      | Route file                 |
| ----------------------- | ---------------------- | -------------------------- |
| `/auth/sign-in`         | `AUTH_SIGN_IN`         | `auth.sign-in.tsx`         |
| `/auth/sign-up`         | `AUTH_SIGN_UP`         | `auth.sign-up.tsx`         |
| `/auth/forgot-password` | `AUTH_FORGOT_PASSWORD` | `auth.forgot-password.tsx` |
| `/auth/reset-password`  | `AUTH_RESET_PASSWORD`  | `auth.reset-password.tsx`  |

`ROUTES.AUTH_EMAIL_VERIFICATION` (`/auth/email-verification`) is declared but has no route file and nothing references it, so that path currently 404s.

`ROUTES.API_AUTH` is a nested object of Better Auth endpoint paths relative to `/api/auth` — `/sign-in/email`, `/sign-up/email`, `/sign-out`, `/request-password-reset`, `/reset-password`. They are used to configure per-endpoint rate limiting rather than to build links.

## Documentation

| Path      | `ROUTES` constant | Route file                            |
| --------- | ----------------- | ------------------------------------- |
| `/docs`   | `DOCS`            | `docs.tsx` (layout), `docs.index.tsx` |
| `/docs/*` | `DOCS_PAGE`       | `docs.$.tsx`                          |

`docs.tsx` loads the sidebar from `buildDocsNavigation`, which walks the Fumadocs page tree for the reader's locale and turns each top-level folder in `content/docs` into a section. `docs.$.tsx` resolves the splat to a page with `loadDocsPage` and throws `notFound()` when no page matches.

## API and Worker-level paths

API paths are never localized — `shouldIgnorePath` in `src/integrations/use-intl/i18n.paths.ts` exempts `/api`, `/rpc`, `/_serverFn` and `/assets` from locale handling.

| Path                          | Handled by                                            | Notes                                                                   |
| ----------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| `/api/auth/*`                 | `src/routes/api/auth.$.ts`                            | Better Auth's own handler                                               |
| `/api/webhooks/stripe`        | `src/routes/api/webhooks.stripe.ts`                   | Signature-verified Stripe events                                        |
| `/api/realtime/admin/ws`      | `src/server.ts` → `ROUTES.API_REALTIME.ADMIN_WS`      | WebSocket upgrade, role-checked in the Worker before the Durable Object |
| `/api/realtime/storefront/ws` | `src/server.ts` → `ROUTES.API_REALTIME.STOREFRONT_WS` | WebSocket upgrade, open to anyone                                       |
| `/sitemap.xml`                | `src/server.ts` → `generateSitemapXml`                | Cached for a day                                                        |
| `/robots.txt`                 | `src/server.ts` → `generateRobotsTxt`                 | Content depends on `env.APP_ENV`                                        |

The last four are checked in `src/server.ts` before the request reaches TanStack Start, so none of them pays for an SSR render. `/api/auth/*` and `/api/webhooks/stripe` are TanStack Start server routes under `src/routes/api/`, so they go through the router but never render a page.

## Guards

All four guards live in `src/integrations/better-auth/auth.routes.ts`.

| Guard                   | Behaviour                                                                                                    | Used by           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------- |
| `requireUser`           | Redirects to `/auth/sign-in` when there is no session                                                        | Via the other two |
| `requireAdmin`          | `requireUser`, then redirects a non-admin to `/account/overview`                                             | `admin.tsx`       |
| `requireCustomer`       | `requireUser`, then redirects an admin to `/admin`                                                           | `account.tsx`     |
| `redirectAuthenticated` | Sends a signed-in visitor to `postAuthRouteFor(user)` — `/admin` for an admin, `/account/overview` otherwise | `auth.tsx`        |

Guards run in `beforeLoad`, which means they also run in the browser during client-side navigation. **They are navigation UX, not authorization.** A server function is a public HTTP endpoint whether or not its route was loaded, so authorization is enforced by the `authorized` middleware inside each use case — see [Permissions](/docs/reference/permissions).
