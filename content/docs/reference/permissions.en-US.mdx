Access control is defined once in `src/integrations/better-auth/auth.access.ts` using Better Auth's access-control plugin, and the same definitions are used by the server middleware, the route guards and the Better Auth client.

The important structural fact: **a server function is a public HTTP endpoint.** It is reachable whether or not the route that normally calls it was ever loaded, so a route guard cannot protect it. Authorization is enforced by the `authorized` middleware at the top of each use case, before any database access. The one permission that depends on the row, `order: ["refund"]` when `cancel-order` meets a paid order, is checked in the handler once the order is read, before anything changes.

## Roles

```ts
export const ROLES = {
  ADMIN: "admin",
  CUSTOMER: "customer",
} as const

export const DEFAULT_ROLE = ROLES.CUSTOMER

export const ADMIN_PANEL_ROLES = [ROLES.ADMIN] as const
```

| Role     | Code       | Gets                                                                                             |
| -------- | ---------- | ------------------------------------------------------------------------------------------------ |
| Admin    | `admin`    | Every application statement, plus Better Auth's `adminAc` statements for `user` and `session`    |
| Customer | `customer` | No statements at all. Customers can only call endpoints that require a session, not a permission |

New accounts get `customer` through `DEFAULT_ROLE`. `hasAdminAccess(role)` is the narrow predicate used where only "is this the admin console audience" matters — the route guards and the admin WebSocket handshake.

In production and in the end-to-end test build an admin also needs two-factor authentication on. `needsTwoFactorSetup({ role, twoFactorEnabled })` is true for an admin without it there — `isAdminTwoFactorRequired()` holds only when the build's mode is `production` or `test`, so in development and preview it is always false — and such an admin holds no permission: `authorized(permission)` answers `FORBIDDEN`, Better Auth's `/admin/*` endpoints answer `ADMIN_TWO_FACTOR_REQUIRED`, and the route guard sends them to `/admin/security` to turn it on. See [Better Auth](/docs/integrations/better-auth#two-factor-authentication-for-admins).

## Statements

Application statements come from `PERMISSIONS_STATEMENTS`, which spreads Better Auth's admin `defaultStatements` and adds four resources:

| Resource   | Actions                                         |
| ---------- | ----------------------------------------------- |
| `content`  | `read`, `update`                                |
| `order`    | `read`, `update`, `refund`                      |
| `product`  | `create`, `read`, `update`, `delete`, `publish` |
| `settings` | `manage`                                        |

Better Auth's own statements, granted to `admin` through `...adminAc.statements`:

| Resource  | Actions                                                                                                    |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| `user`    | `create`, `list`, `set-role`, `ban`, `impersonate`, `delete`, `set-password`, `set-email`, `get`, `update` |
| `session` | `list`, `revoke`, `delete`                                                                                 |

Note that `product` covers the whole catalog, not only the `product` table: categories, collections, attributes and product images are all gated on `product` actions. There is no separate `category` or `collection` resource.

## Checking a permission

Server functions use the middleware:

```ts
export const createCategory = createServerFn({ method: "POST" })
  .middleware([authorized({ product: ["create"] })])
  .validator((input) => productCategoryZodSchemas.createInput.parse(input))
  .handler(async ({ data }) => {
    /* ... */
  })
```

`authorized` is built on `withRequest`, so it also normalises errors. It reads the session with `getRequestSession()`, throws `AppError(ERROR_CODES.UNAUTHORIZED)` when there is none, throws `AppError(ERROR_CODES.FORBIDDEN)` when the role lacks the permission, and otherwise puts the session on `context.auth`:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && (!hasPermission({ permission, role: session.user.role }) || needsTwoFactorSetup(session.user))) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

Calling `authorized()` with no argument means "any signed-in user". That is what the customer-account and address use cases do; they then narrow by identity in SQL rather than by role. It also admits an admin without two-factor authentication, which is how `/admin/security` loads that admin's own profile through `getCustomerProfile`.

`recentSignIn` is a second middleware for changes that need a recent sign-in. It runs `authorized()` and then refuses a session created more than `SESSION_FRESH_AGE_IN_SECONDS` (24 hours) ago with `403 SESSION_NOT_FRESH`, which the browser shows as "sign out and sign in again before making this change". `set-account-password`, `grant-admin-access` and `revoke-admin-access` use it, after their own `authorized(...)`. `isRecentSignIn(session)` is the same test as a function, which `list-admin-team` uses to tell the Team tab beforehand.

Code outside the middleware path calls `hasPermission({ permission, role })`, `hasAdminAccess(role)` or `needsTwoFactorSetup(user)` directly. `hasPermission` returns `false` for an unknown role rather than throwing.

## Ownership, not just roles

Customer-facing reads do not fetch a row and then compare its owner. The ownership predicate is compiled into the query, so a foreign id returns no row at all. `customer-account/use-cases/get-customer-order.ts` is the pattern:

```ts
const orderRow = await db.query.order.findFirst({
  where: and(eq(order.id, orderId), eq(order.userId, context.auth.user.id)),
  with: { checkout: { with: { billingAddress: true, shippingAddress: true } }, payment: true },
})
```

That is why the `authorized()` calls in `customer-account` and `address` carry no permission: the SQL is the authorization. Passing someone else's order id returns `undefined`, and the query options turn that into `notFound()`.

## Session handling

`getRequestSession` in `src/integrations/better-auth/auth.session.ts` memoizes the session lookup per `Request` in a `WeakMap`, and passes `disableCookieCache: true`, so every server-side read revalidates against D1 while concurrent loaders in one request share a single lookup.

Better Auth is configured in `auth.server.ts` with the signed cookie cache turned off (`cookieCache: { enabled: false }`), `storeSessionInDatabase: true` and at most five concurrent sessions per user (`multiSession({ maximumSessions: 5 })`). Route guards and components read the session through `getCurrentSessionQuery`, whose `getCurrentSession` server function also goes through `getRequestSession`, so the browser's session skips the cookie cache too. TanStack Query keeps that result fresh for 60 seconds and does not refetch it on window focus, so a component can still render a signed-in state the server has already ended. A real navigation into `/account` or `/admin` re-checks the session with `staleTime: 0`, and every protected server function reads its own session through `authorized()`, so a stale cache entry never grants access.

`getCurrentSession` strips the session token before returning to the browser — `toClientSession` destructures `token` away — so the client never receives it.

## Rate limits

Two layers, both writing to the `rate_limit` table.

**Better Auth's own limiter**, counted with the same `withinRateLimit` as the middleware below and configured with `customStorage: authRateLimitStorage`, a global 100 requests per 60 seconds, and four per-endpoint rules:

| Endpoint                           | Max per 60s |
| ---------------------------------- | ----------- |
| `/api/auth/sign-in/email`          | 5           |
| `/api/auth/sign-up/email`          | 3           |
| `/api/auth/request-password-reset` | 3           |
| `/api/auth/reset-password`         | 5           |

**The application's `withRateLimit` middleware**, with four named budgets in `auth.middleware.ts`, all over a 60-second window:

| Budget      | Max | Applied to                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------- | --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BROWSING`  | 120 | `search-storefront` in `search-storefront.ts`, `search-storefront-products` in `get-storefront-products-page.ts` for a listing that carries `q`, and `record-customer-activity` in `record-customer-activity.ts`                                                                                                                                                                                                                                                                                                                                                                          |
| `CHECKOUT`  | 10  | `checkout-create` and `checkout-update` in `src/integrations/stripe/stripe.actions.ts`, `discount-validate` in `validate-discount-code.ts`, and `checkout-status`, shared by `get-checkout-session-status.ts` and `get-order-confirmation.ts`                                                                                                                                                                                                                                                                                                                                             |
| `SENSITIVE` | 3   | `create-user-address`, `update-customer-phone`, `revoke-other-customer-sessions`, `set-account-password`, `update-display-preference`, `create-card-setup-intent`, `delete-saved-payment-method`, `remove-duplicate-saved-cards`, `withdraw-from-customer-order`, `withdraw-from-guest-order`, each in the use case of that name, and `newsletter-subscribe`, `newsletter-confirm`, `newsletter-unsubscribe` and `newsletter-unsubscribe-own` in `subscribe-to-newsletter.ts`, `confirm-newsletter-subscription.ts`, `unsubscribe-from-newsletter.ts` and `unsubscribe-own-newsletter.ts` |
| `TOKEN`     | 5   | Nothing yet; only asserted against `SENSITIVE` in `auth.middleware.test.ts`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

Two more counters use the same table and the same `withinRateLimit` helper. `/api/webhooks/inpost` admits 120 calls a minute from one address (`INPOST_WEBHOOK_RATE_LIMIT`), and `resend.public-email-limits.server.ts` caps the e-mails a visitor can make the shop send — verification, password reset, newsletter and the guest withdrawal acknowledgement — at three per recipient and kind an hour and 50 a day per environment; a skipped e-mail is recorded as `email.failed`.

The two layers and the InPost webhook's counter key on the client IP; the e-mail caps key on the recipient and the environment. `clientAddress` in `src/lib/rate-limit.ts` reads only the `cf-connecting-ip` header, which the edge sets and a client cannot spoof. The counter itself is a single `INSERT ... ON CONFLICT DO UPDATE` with a `setWhere` guard, so the window reset and the increment are one atomic statement. If the table is unreachable the helper logs `Rate-limit storage unavailable` and returns `false`, so the middleware throws `TOO_MANY_REQUESTS` — it fails closed.
