Each entry names the symptom as you will actually see it, then the fix. Where a message is quoted, it is the string the code throws.

## Development server

**The dev server will not start.** `vite.config.ts` sets `server: { port: 3000, strictPort: true }`, so Vite refuses to fall back to another port. Something else is on 3000 — stop it. The port matters beyond convenience: `appHostsForMode` in `src/modules/_core/constants/api.ts` only allows `localhost:3000` and `127.0.0.1:3000` for local modes, and Better Auth is built with that allowlist, so authentication breaks on any other port. `resolveRequestOrigin` uses the same list for email links and the Stripe return URL, so on another port the newsletter sign-up and checkout are refused with `FORBIDDEN` too. Emails link back to the exact address you used: open the app on `127.0.0.1:3000` and the links say `127.0.0.1:3000`, open it on `localhost:3000` and they say `localhost:3000`. That holds for the order confirmation too. `stripe:listen` forwards the webhook to `localhost:3000`, but the confirmation takes its origin from the session's `return_url`, so a checkout on `127.0.0.1:3000` links to `127.0.0.1:3000` even when the preview deployment, which shares the Stripe test account and the database, fulfils it.

**`bun run dev` cannot reach the database, R2 or KV.** The `development` Wrangler environment uses **remote** bindings (`remote: true` on every resource, and `remoteBindings` is enabled for that mode in `vite.config.ts`). You need to be authenticated against the Cloudflare account:

```sh
vp exec wrangler login
```

There is no fully local option wired up for `dev` — the local D1 file only gets migrations through `bun run db:migrate:local`, which targets the `development` environment with `--local`. The one fully local run is a build, not the dev server: the `test` environment, prepared with `bun run db:reset:test` and `bun run build:test` and served with `bun run start:test` (see [First run](/docs/getting-started/first-run#a-seeded-local-run)).

**`Cannot find module 'collections/server'` or `'collections/browser'`.** `.source/` has not been generated. `tsconfig.json` maps `collections/*` to `./.source/*`, and Fumadocs writes that directory:

```sh
bun run content
```

`bun run dev`, `bun run build:*` and `bun run typegen` all run it for you, so this usually means a `bun run clean` without a follow-up.

## Database

**`no such table` at runtime.** Migrations have not been applied to the database the current environment points at. `development` and `preview` share `martebizuteria-preview`:

```sh
bun run db:migrate:development   # remote preview database
bun run db:migrate:local         # the local .wrangler copy
bun run db:migrate:production    # production
```

`bun run db:migrations:development` lists what has and has not been applied.

**A schema change is not reflected anywhere.** Editing a `*.schema.ts` file changes types, not the database. Generate a migration and apply it:

```sh
bun run db:generate
bun run db:migrate:development
```

`db:push:*` exists for the same schema but pushes without a migration file; prefer `db:generate` so the change is recorded in `src/integrations/drizzle-orm/migrations/`.

**Drizzle Kit cannot connect.** `src/integrations/drizzle-orm/drizzle.config.ts` uses the D1 HTTP driver and reads `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` and `CLOUDFLARE_ACCESS_TOKEN` from `process.env`. Because `bunfig.toml` disables automatic env loading, those come only from the `--env-file=.env.<environment>` that each `db:studio:*`, `db:push:*` and `db:introspect:*` script passes. An empty value falls back to `""` and the request fails; fill the file in.

**Never run the seed scripts against a live database.** `db:seed:preview` and `db:seed:production` execute the SQL files in `src/integrations/drizzle-orm/seeds/` against the remote database with `wrangler d1 execute --remote`. Those files are stale relative to the real catalog, so running them overwrites real data. They are only appropriate against a database you have deliberately emptied.

**Migration count does not match Drizzle's journal.** `wrangler d1 migrations apply` walks the `.sql` files in `src/integrations/drizzle-orm/migrations` in filename order; Drizzle Kit's `meta/_journal.json` tracks only the ones it generated itself. The directory is authoritative for what is applied.

## Tests

**An integration test fails with `no such table` or `no such column`.** Each suite builds its schema in an in-memory `node:sqlite` database in one of two ways. Seventy-six of the 123 take it from the migrations through `src/platform/testing/mocks/migrations.ts` — 58 replay the whole directory with `applyMigrationHistory`, the others apply chosen files with `applyMigration` — so they see a schema change once its migration exists. The other 47 create the tables they need by hand with `sqlite.exec`, as the `create table` blocks in `src/modules/checkout/__test__/checkout-idempotency.integration.test.ts` do; after a schema change, update the DDL in those.

**A component test fails on `IntersectionObserver`, `ResizeObserver` or `matchMedia`.** Those are stubbed in `src/platform/testing/setup.ts`, which only the `component` project loads. A test that needs them must be named `*.component.test.tsx`, or it will land in the `node` project instead.

**A server function returns something unexpected in a test.** `src/platform/testing/setup.ts` proxies `createServerFn` through `withTestRpc` and stubs `getRequest` to return `new Request("http://127.0.0.1:3000/")`. Tests that depend on headers, cookies or a session must override `getRequest` themselves.

**`test:coverage` fails on thresholds.** `vite.config.ts` sets branches, functions, lines and statements to 100, so a single uncovered line fails the run. Read `coverage/index.html` to find what is uncovered, then add a test for it or remove a branch no input can reach. `autoUpdate` is `false`, so the values never move on their own.

**`passWithNoTests` fails the run.** It is set to `false`, so a project matching no files is an error. Check the file name suffix against the project globs.

**The end-to-end suite tests the wrong server, or its sign-ins and payments fail at once.** Outside CI, `playwright.config.ts` sets `reuseExistingServer`, so whatever already answers on port 3000 — `bun run dev` with its remote bindings, or an older `start:test` built with other keys — is tested as it is. Stop it and run the suite again, so that Playwright runs `db:reset:test`, `build:test` and `start:test` itself.

**Every `stripe-test-mode` spec is reported skipped.** They run only when `STRIPE_SECRET_KEY` (`sk_test_` or `rk_test_`) and `VITE_STRIPE_PUBLISHABLE_KEY` (`pk_test_`) hold a Stripe sandbox's keys rather than the dummies in `.env.test`. Set both for the command, and build the test Worker with them too, because the client bundle and the Worker take the keys at build time. See [Testing](/docs/tooling/testing#stripe-test-mode).

## Checks and types

**`bun run check` reports a warning and exits non-zero.** `denyWarnings: true`. There is no warning level in this repository; fix it or it does not merge.

**`Unused eslint-disable directive`-style failure.** `reportUnusedDisableDirectives: "error"`. A suppression that no longer suppresses anything must be deleted.

**`max-lines`, `max-lines-per-function` or `max-statements` fails.** The limits are 800 lines per file, 150 lines per function and 20 statements per function. Split the file or extract a function; do not add an override. The narrow overrides that exist are listed in [Conventions](/docs/reference/conventions).

**Worker types are missing a binding or a secret.** `src/types/worker-configuration.d.ts` is generated and gitignored. After editing `wrangler.jsonc`:

```sh
bun run typegen
```

which runs `cf-typegen` (`wrangler types --env development`) and then `content`.

**`noUncheckedIndexedAccess` or `exactOptionalPropertyTypes` complains about code that looks fine.** Both are on. An array access is `T | undefined`, and `{ key: undefined }` is not the same as omitting the key — which is why the codebase builds optional payloads with conditional assignment rather than spreading `undefined`, as in `address.accessors.ts`.

## Translations

**`Missing translation namespace: messages/pl-PL/pages.x.json`.** Thrown by `loadNamespace` in `src/integrations/use-intl/i18n.messages.ts`. A route declared the namespace in `staticData.namespaces` but the file does not exist for that locale. Create it in **both** `messages/en-US/` and `messages/pl-PL/`.

**A key renders as its own path.** The key is missing in the active locale, or the component is reading outside the scope of its `useTranslations` call. `src/integrations/use-intl/__test__/i18n.messages.test.ts` asserts that Polish contains every English key, so run the test suite to find the gap.

**Text appears in the wrong language on an API-like path.** `shouldIgnorePath` exempts `/api`, `/rpc`, `/_serverFn`, `/assets` and `/forms` from locale resolution, and `getCurrentLocale` falls back to the `marte_locale` cookie for those paths. Anything deriving a locale from the router's location will see the de-localized path and therefore the default locale — use `getCurrentLocale()` instead.

## Documentation

**A docs page returns 404.** Three things must all be true: the file is named `<slug>.<locale>.mdx` under `content/docs/`, the slug appears in the `pages` array of that folder's `meta.<locale>.json`, and `.source/` has been regenerated with `bun run content`. `docs.$.tsx` throws `notFound()` when `docsSource.getPage` finds nothing.

**A page exists but does not appear in the sidebar.** `buildDocsNavigation` in `src/integrations/fumadocs/fumadocs.docs.ts` only turns **top-level folders** of `content/docs` into sections, and within a folder only its `index` page and its direct page children. A page nested two folders deep will resolve by URL but will not be listed.

**A page renders but its heading is duplicated.** `src/presentation/components/custom/docs-content.tsx` renders `frontmatter.title` as the `h1` above the MDX body. Do not add your own `#` heading at the top of a page.

**A capitalised JSX tag in MDX breaks the page.** The docs renderer maps plain HTML elements only — `src/presentation/components/custom/docs-mdx.tsx` extends `mdxComponents` with `a`, `h1`–`h4`, `p`, `ul`, `ol`, `li`, `strong`, `blockquote`, `code`, `pre`, `table`, `th`, `td` and `hr`. There is no component registry, so `<Callout>` or `<Tabs>` has nothing to resolve to. Use Markdown.

## Authentication and payments

**Sign-in fails locally.** Check `AUTH_SECRET` and the OAuth credentials in `.env.development`, and that the provider's callback URL points at `/api/auth/callback/<provider>` on a host Better Auth accepts — locally only `localhost:3000` and `127.0.0.1:3000`.

**`TOO_MANY_REQUESTS` while testing by hand.** Two limiters are in play. Better Auth allows 5 sign-ins, 3 sign-ups, 3 password-reset requests and 5 password resets per 60 seconds, plus a global 100 per 60 seconds. The application middleware allows 3 calls per 60 seconds to each sensitive action — saving an address or the phone number, revoking sessions, adding a password, saving a display preference, adding or removing a card, withdrawing from an order and the newsletter's sign-up, confirmation and unsubscribe — and 10 to each of the checkout actions, the discount check and the checkout status; [Permissions](/docs/reference/permissions#rate-limits) lists the buckets. Counters live in the `rate_limit` table, keyed by `cf-connecting-ip`. An old row stops counting once its 60-second window has passed, and the daily [retention clean-up](/docs/guides/data-retention) deletes it a day after its last request.

**The checkout toasts "Several payments started for this email address or from your connection have not been paid yet".** The server refused a new checkout with `TOO_MANY_OPEN_CHECKOUTS`: the client address already has five open checkouts or the email three. Testing by hand, every browser profile or private window that reaches the payment step opens one. Pay them, expire them in Stripe's test dashboard with `stripe:listen` forwarding the webhook, wait until their sessions expire 32 minutes after their last change, or use another email. See [Checkout: Limits on holding stock](/docs/features/checkout#limits-on-holding-stock).

**A verification, password-reset or newsletter email never arrives, though the page said it was on its way.** Look for `[Email] Skipped a <kind> email to <address>` in the Worker logs. "the address reached its hourly limit for this email" means that address already received three emails of that kind in the last hour; it gets the next one an hour after the first. "the shop reached its daily limit of 50 emails that visitors can request" is also recorded as `email.failed` in `/admin/audit`, and these emails resume a day after the first one of the day; order emails were never held back. If real sign-ups reach that limit, raise `PUBLIC_EMAILS_DAILY_MAX` in `src/integrations/resend/resend.public-email-limits.server.ts`, keeping it within the Resend plan. See [Resend: Emails visitors can request](/docs/integrations/resend#emails-visitors-can-request).

**Stripe webhooks are rejected.** `src/routes/api/webhooks.stripe.ts` answers `400 Missing signature or webhook secret` when the `stripe-signature` header is absent or `STRIPE_WEBHOOK_SECRET` is empty, and `400 Webhook Error: Invalid Signature` when `constructEventAsync` rejects the payload. Locally, run `bun run stripe:listen` and paste the signing secret it prints into `.env.development`. An event type with no entry in `webhookHandlers` is logged and acknowledged with `{ received: true }` rather than failing. So is a verified event from the wrong Stripe mode, test in `production` or live anywhere else, which logs `[Stripe] Ignoring <mode> event …` and is never handled: the endpoint or `stripe listen` session that sent it runs in the other mode, so give this environment the signing secret of an endpoint in its own mode. A test-mode event whose checkout belongs to another deployment is acknowledged the same way and logs `[Stripe] Ignoring event … its checkout belongs to <deployment>`: every Checkout Session carries the creating Worker's `deployment` metadata, so when one Stripe sandbox serves several deployments, such as preview and the `stripe-test-mode` run of the test Worker, each acts only on its own checkouts.

**An order is paid but nothing happened.** Fulfilment is driven entirely by the webhook path: `fulfill-checkout.server.ts` for `checkout.session.completed` and `release-checkout.server.ts` for `checkout.session.expired`. If the forwarder was not running, the checkout row stays `pending` and no order exists. `fulfillCheckout` also returns early when `findPendingCheckoutByTransaction` finds the checkout already `completed`, which is what makes Stripe's sequential retries idempotent. A paid session that reached the webhook but created no order leaves one `order.fulfillment_failed` entry at `error` severity in the admin audit log, with the amount, the customer's email and the cause of the first failed delivery, however often Stripe retried it (the Worker logs hold the error of every attempt); a session that no pending checkout can take is acknowledged after that entry, so refund it in Stripe. Both also email `RESEND_EMAIL_FROM`; see [Monitoring and alerts](/docs/guides/monitoring-and-alerts).

## E-mail

**No e-mail arrives, and the log says `The <domain> domain is not verified`.** Resend refuses every message from a domain that is not verified in the account behind `RESEND_API_KEY`, so verification, reset, newsletter, order and shipping e-mails all fail the same way. Each failure is logged and recorded in `/admin/audit` as `email.failed`. Verify the domain of `RESEND_EMAIL_FROM` as described in [Resend](/docs/integrations/resend#sender-domain), then run `bun run email:verify <environment>` until it reports the domain as verified.

**`You can only send testing emails to your own email address`.** `RESEND_EMAIL_FROM` is `onboarding@resend.dev`, which delivers only to the owner of the Resend account. Use that address while developing, or verify a domain of your own. The refusal concerns that recipient alone, so it does not mark the sender unavailable, and auth e-mails to the owner keep going out.

## Build and deploy

**`Missing database, cache, images, audit, newsletter, or realtime binding for preview`.** From `scripts/verify-bindings.ts`. The target environment in `wrangler.jsonc` is missing a binding, still carries a placeholder id (the check rejects ids made only of `0` and `-`), or the consumer of its audit or newsletter queue names no `dead_letter_queue` with a consumer of its own. Create the resource in Cloudflare and paste the real id, or restore the queue's `-dlq` consumer.

**`Production and preview share the images bucket <name>`.** From `scripts/verify-bindings.ts production`. The production `IMAGES` binding in `wrangler.jsonc` names the bucket preview binds, so a production deploy would serve and write preview's images. Production uses `martebizuteria` and preview `martebizuteria-preview`; restore the production `bucket_name`.

**Images are broken on preview or in `bun run dev`.** `martebizuteria-preview` is missing, has no public `r2.dev` address, lacks the objects the preview database points at, or `VITE_R2_URL` is not its address. [Image delivery](/docs/guides/image-delivery) has the steps for each.

**Production images load at full size, and their `/cdn-cgi/image/` requests answer with a redirect.** Cloudflare could not transform them, and `onerror=redirect` sent the browser to the original object. On the Images Free plan the usual cause is that the month's 5,000 unique transformations are used up; new sizes are transformed again from the start of the next month, or at once after moving the account to Images Paid. [Image delivery](/docs/guides/image-delivery) shows how the storefront reaches that count.

**`production needs live Stripe keys, but VITE_STRIPE_PUBLISHABLE_KEY and STRIPE_SECRET_KEY are test keys`** or **`preview needs test Stripe keys, but … are live keys`**. From `scripts/verify-stripe-keys.ts`. The keys come from the wrong Stripe mode for the target. Put the live keys from dashboard.stripe.com/apikeys into the `production` GitHub environment, `VITE_STRIPE_PUBLISHABLE_KEY` as a variable and `STRIPE_SECRET_KEY` as a secret, or the test keys from dashboard.stripe.com/test/apikeys into `preview`. Each mode has its own webhook endpoints, so set `STRIPE_WEBHOOK_SECRET` to the signing secret of an endpoint in the same mode.

**`VITE_STRIPE_PUBLISHABLE_KEY is a test key but STRIPE_SECRET_KEY is a live key`**, or the reverse. Only one of the two keys was changed. Copy both from the same mode of the same Stripe account.

**`VITE_STRIPE_PUBLISHABLE_KEY is missing for preview`**, **`STRIPE_SECRET_KEY is missing for preview`** or **`… is not a Stripe secret key`**. Also from `verify-stripe-keys.ts`. A missing key is empty in the process environment, or unset there and blank or missing in `.env.preview`. In GitHub Actions `VITE_STRIPE_PUBLISHABLE_KEY` comes from the environment's variables and `STRIPE_SECRET_KEY` from its secrets, and either arrives as an empty string when it is not set there. A key that is not of its kind usually means the values were swapped, or the `whsec_` webhook secret was pasted into `STRIPE_SECRET_KEY`.

**`<domain> is not_started in Resend, so every e-mail from <address> is refused`.** From `scripts/verify-email-sender.ts`. The domain is in the Resend account, but its DKIM or SPF records are not verified; the lines under the message are the records still to publish, with their current status. `pending` or `failed` can stand in place of `not_started`. When the message says instead that `Resend does not list both a DKIM and an SPF record for it yet`, open the domain on resend.com/domains, which shows the records to publish. Add the records at the domain's DNS provider, press Verify on resend.com/domains and deploy again once `bun run email:verify <environment>` passes.

**`Resend refuses to send as <address>: The <domain> domain is not verified…`.** Also from `verify-email-sender.ts`, with the same cause. `RESEND_API_KEY` may only send and `RESEND_MANAGEMENT_API_KEY` is not set, so the check could not read the domain's records and tried a test send instead; the records are on the domain's page at resend.com/domains. Set `RESEND_MANAGEMENT_API_KEY` to a Full access key and the check prints them.

**`<domain> is not a domain of this Resend account`.** The domain of `RESEND_EMAIL_FROM` was never added to the Resend account that owns `RESEND_API_KEY`, the key belongs to another account, or the sender is on a subdomain of the verified domain, which Resend treats as a domain of its own. Add the exact domain on resend.com/domains or change the sender.

**`RESEND_API_KEY is missing for preview`** or **`RESEND_EMAIL_FROM is missing for preview`**. From `verify-email-sender.ts`. The value is empty in the process environment, or unset there and blank or missing in `.env.preview`; a variable exported but empty takes precedence over the file. In GitHub Actions a secret that is not set for the `preview` environment arrives as an empty string, so add it to that environment's secrets.

**`RESEND_EMAIL_FROM must be a bare address`** or **`onboarding@resend.dev only delivers to the owner of the Resend account`.** Set the secret to the address alone, such as `sklep@martebizuteria.pl`, because `sendEmail` adds `M'Arte` itself. `onboarding@resend.dev` passes the check only for development.

**`Resend rejected RESEND_API_KEY (<code>)`** or **`Resend rejected RESEND_MANAGEMENT_API_KEY (<code>)`**. The key is invalid, revoked or, for the management key, limited to sending (`restricted_api_key`). Create a new key at resend.com/api-keys; the management key needs Full access.

**`Resend could not list the domains of RESEND_API_KEY (<code>)`** or **`Resend did not answer within 30000 ms`**. Resend was rate limited (`rate_limit_exceeded`) or failing (`application_error`, `internal_server_error`) on both attempts, or did not answer at all. Retry the deploy in a moment.

**`Missing STRIPE_SECRET_KEY in .env.preview or the process environment`.** From `scripts/prepare-deploy-secrets.ts`. Every name under `secrets.required` for that environment must have a non-blank value in the matching `.env` file or in the process environment. `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID` may be blank, but their lines must still be there, as in `.env.example`.

**`Server-only import in client asset: <file>.js`.** From `scripts/verify-build.ts`. A client bundle ended up importing `cloudflare:workers` or a `node:*` module, which means a server-only module was reached from a component. Trace the import chain from the named asset; the usual cause is importing from a `*.server.ts` file or from `drizzle.database.ts` in a component instead of going through a use case.

**`Worker build does not target preview`** or **`Worker deployment points outside the current server build`.** Also from `verify-build.ts`. The build output in `dist/` does not match the environment being deployed, usually because `CLOUDFLARE_ENV` leaked in from the shell or a stale `dist/` was reused. `build:preview` and `build:production` both start with `rm -rf dist`; run the matching script rather than `wrangler deploy` by hand.

**`Missing client JavaScript` / `Missing client CSS`.** `dist/client/assets` has no `.js` or `.css` file. The client build failed earlier in the pipeline — scroll back through the build output.

**`Migration <name> failed with the following errors:`.** From Wrangler, in the deploy's `db:migrate:<environment>` stage. Wrangler rolled that migration back, kept the ones before it and stopped the deploy before `wrangler deploy`, so the previous Worker is still live. The lines under the message are D1's error for the failing statement. A migration that another database, such as the shared preview one, has already applied is never edited; correct it with a new migration and deploy again.

**`The production Worker at https://martebizuteria.pjborowiecki.workers.dev is deployed but does not answer like the shop:`.** From `scripts/verify-deployment.ts`, which runs after `wrangler deploy`, so the new version is already live. Each line under it names a page and what it answered. `vp exec wrangler tail --env production` shows the exceptions behind a `500`, and a `200 text/html` from `/api/webhooks/stripe` means the request rendered a page instead of reaching the route's own handler. When the shop is down, roll the Worker back before looking further; see [Roll back a deploy](/docs/guides/roll-back-a-deploy).
