title: "Environment and bindings"
description: "Environment files, variables, secrets and Cloudflare bindings for every Wrangler environment."
---

There are four environments — `development`, `preview`, `production` and `test` — each with a matching Vite mode and a matching `env` block in `wrangler.jsonc`. The first three have a gitignored `.env.<name>` file and real Cloudflare resources. `test` takes its values from the committed `.env.test`, which also feeds the Vitest projects, binds only local resources and exists for the Playwright suite: its Worker, `martebizuteria-test`, runs `src/platform/testing/worker.ts`, which installs in-memory emulators for Stripe, Resend and InPost ShipX before handing requests to `src/server.ts`. `bun run build:test` and `bun run start:test` build and serve it, `bun run db:migrate:test`, `db:seed:test` and `db:reset:test` prepare its database under `.wrangler/test`, and no script deploys it.

Bun's automatic env loading is switched off in `bunfig.toml`:

```toml
# Let Vite and Wrangler choose the requested mode. Drizzle scripts opt in with --env-file.
env = false
```

so nothing is ever loaded implicitly. Vite and Wrangler pick the file from the requested mode, and the Drizzle Kit scripts opt in explicitly with `bun --env-file=.env.<environment>`.

## Environment files

| File               | Committed | Used by                                                                                                                                                                                                                                                                                                                     |
| ------------------ | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.env.example`     | Yes       | The template; lists every variable with a placeholder or empty value                                                                                                                                                                                                                                                        |
| `.env.development` | No        | `bun run dev`, `email:verify development`, `verify-stripe-keys.ts development`, the `:development` Drizzle scripts                                                                                                                                                                                                          |
| `.env.preview`     | No        | `build:preview`, `deploy:preview`, `email:verify preview`, the `:preview` Drizzle scripts                                                                                                                                                                                                                                   |
| `.env.production`  | No        | `build:production`, `deploy:production`, `email:verify production`, the `:production` Drizzle scripts                                                                                                                                                                                                                       |
| `.env.test`        | Yes       | Vitest, via `env: loadEnv("test", import.meta.dirname, "")` in `vite.config.ts`; `vp build --mode test` for the end-to-end test Worker; `scripts/seed-test.ts`, for the `AUTH_SECRET` that encrypts the seeded admin's two-factor secret; CI, which copies it over `.env.development` and `.env.preview`. Dummy values only |

Start from the template:

```sh
cp .env.example .env.development
```

## Variables

| Variable                      | Read by                                                                                                                                             | Worker secret |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| `AUTH_SECRET`                 | Better Auth signing and encryption                                                                                                                  | Yes           |
| `AUTH_GOOGLE_CLIENT_ID`       | Google OAuth                                                                                                                                        | Yes           |
| `AUTH_GOOGLE_CLIENT_SECRET`   | Google OAuth                                                                                                                                        | Yes           |
| `INPOST_API_TOKEN`            | The ShipX client in `src/integrations/inpost/inpost.shipx.server.ts`; blank turns InPost shipments off                                              | Yes           |
| `INPOST_ORGANIZATION_ID`      | The ShipX organisation for shipments and webhooks; blank turns InPost shipments off                                                                 | Yes           |
| `RESEND_API_KEY`              | The Resend client in `src/integrations/resend/resend.config.ts`                                                                                     | Yes           |
| `RESEND_EMAIL_FROM`           | The default sender, a bare address on a domain verified in Resend, and the recipient of the shop's notices and incident alerts in every environment | Yes           |
| `STRIPE_SECRET_KEY`           | The Stripe server client in `src/integrations/stripe/stripe.server.ts`; `scripts/verify-stripe-keys.ts` checks its mode                             | Yes           |
| `STRIPE_WEBHOOK_SECRET`       | Signature verification in `src/routes/api/webhooks.stripe.ts`                                                                                       | Yes           |
| `VITE_R2_URL`                 | Public base URL of the environment's R2 bucket, read as `import.meta.env["VITE_R2_URL"]` in `src/lib/url.ts`                                        | Yes           |
| `VITE_STRIPE_PUBLISHABLE_KEY` | `src/integrations/stripe/stripe.client.ts`, inlined into the client bundle at build time; `scripts/verify-stripe-keys.ts` checks its mode           | No            |
| `CLOUDFLARE_ACCOUNT_ID`       | Drizzle Kit's D1 HTTP driver in `src/integrations/drizzle-orm/drizzle.config.ts`                                                                    | No            |
| `CLOUDFLARE_DATABASE_ID`      | Drizzle Kit's D1 HTTP driver                                                                                                                        | No            |
| `CLOUDFLARE_ACCESS_TOKEN`     | Drizzle Kit's D1 HTTP driver                                                                                                                        | No            |
| `RESEND_MANAGEMENT_API_KEY`   | Optional. `scripts/verify-email-sender.ts` reads the sender domain with this Full access key when `RESEND_API_KEY` may only send                    | No            |

Only variables listed under `secrets.required` in `wrangler.jsonc` are uploaded on deploy. Every environment declares the same ten names. The three `CLOUDFLARE_*` variables are Drizzle Kit credentials and stay on the machine that runs the CLI; `prepare-deploy-secrets.ts` writes only the declared set into `.wrangler/secrets.<environment>.json` with mode `0600` and fails loudly if one is blank, except `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID`, which it uploads blank so a shop without InPost credentials can still deploy:

```
Missing STRIPE_SECRET_KEY in .env.preview or the process environment
```

### Browser-visible values

Only `VITE_`-prefixed names reach the client bundle. `src/types/vite-env.d.ts` declares one of them on `ImportMetaEnv`:

```ts
interface ImportMetaEnv {
  readonly VITE_STRIPE_PUBLISHABLE_KEY: string | undefined
}
```

`VITE_R2_URL` is read through the index form `import.meta.env["VITE_R2_URL"]`, which is why it does not need a declaration. `src/lib/image.ts` also reads `import.meta.env["VITE_IMAGE_CDN_DOMAIN"]`, which is not declared in `.env.example`, `.env.test` or `wrangler.jsonc` — that path is inert unless someone sets the variable by hand.

## Bindings

`wrangler.jsonc` gives every environment the same seven bindings, `ASSETS` included, so `wrangler types --env development` declares all of them on `Env`. Only the underlying resources differ.

| Binding                     | Type           | `development`                           | `preview`                               | `test`                              | `production`                |
| --------------------------- | -------------- | --------------------------------------- | --------------------------------------- | ----------------------------------- | --------------------------- |
| `DB`                        | D1             | `martebizuteria-preview`, remote        | `martebizuteria-preview`, remote        | `martebizuteria-test`, local        | `martebizuteria`, remote    |
| `CACHE`                     | KV             | `d6727c71…`, remote                     | `d6727c71…`, remote                     | placeholder id, local               | `4126270a…`, remote         |
| `IMAGES`                    | R2             | bucket `martebizuteria-preview`, remote | bucket `martebizuteria-preview`, remote | bucket `martebizuteria-test`, local | bucket `martebizuteria`     |
| `AUDIT_LOG_QUEUE`           | Queue producer | `martebizuteria-audit-log-preview`      | `martebizuteria-audit-log-preview`      | `martebizuteria-audit-log-test`     | `martebizuteria-audit-log`  |
| `NEWSLETTER_QUEUE`          | Queue producer | `martebizuteria-newsletter-preview`     | `martebizuteria-newsletter-preview`     | `martebizuteria-newsletter-test`    | `martebizuteria-newsletter` |
| `REALTIME_INVALIDATION_HUB` | Durable Object | class `RealtimeInvalidationHub`         | same                                    | same                                | same                        |
| `ASSETS`                    | Static assets  | `./public`, in each environment block   | same                                    | same                                | same                        |

`development` and `preview` point at the **same** D1 database, KV namespace, R2 bucket and queues. `bun run dev` therefore writes to the preview database, and `vite.config.ts` turns remote bindings on only for that mode, and keeps the `test` environment's local state in its own folder:

```ts
persistState: process.env["CLOUDFLARE_ENV"] === "test" ? { path: ".wrangler/test" } : true,
remoteBindings: process.env["CLOUDFLARE_ENV"] === "development",
```

Each environment also declares one plain variable, `vars.APP_ENV`, set to its own name. `src/server.ts` passes it to `generateRobotsTxt`, so only production serves an indexable `robots.txt`; it also decides the accepted Stripe mode and the Checkout Sessions' `deployment` metadata, the ShipX API, `Strict-Transport-Security` and the prefix of the KV and e-mail rate-limit keys, as [Environment variables](/docs/getting-started/environment-variables#plain-vars-not-secrets) lists. Only `preview` and `production` declare a Cron Trigger, `0 3 * * *`, which runs the daily retention clean-up.

Each environment declares four queue consumers, all handled by the `queue` export in `src/server.ts`. The audit-log queue is consumed in batches (`max_batch_size: 50`, `max_batch_timeout: 5`, or `1` in `test`, `max_retries: 3`) with a `dead_letter_queue` named after it with `-dlq`, which the Worker consumes one message at a time (`max_batch_size: 1`, `max_retries: 3`, `retry_delay: 300`). The newsletter queue, whose every message is one batch of up to 100 recipients, is consumed one message at a time and never in parallel (`max_batch_size: 1`, `max_concurrency: 1`, `max_retries: 3`), with its own `-dlq` consumed the same way after a `retry_delay` of 300 seconds. The Durable Object class is created by migration tag `v1` (`new_sqlite_classes: ["RealtimeInvalidationHub"]`).

Other top-level settings worth knowing: `compatibility_date` is `2026-04-18` with the `nodejs_compat` flag, `keep_vars` is on, observability is enabled with Workers Issues (`observability.issues.enabled`) and `placement.mode` is `smart`.

## Types

`Env` is generated, not written. `bun run cf-typegen` runs `wrangler types --env development` into `src/types/worker-configuration.d.ts`, which is gitignored and regenerated by `postinstall` through `bun run typegen` (which also runs `bun run content`). After changing a binding or a secret in `wrangler.jsonc`:

```sh
bun run typegen
```

Worker code reads bindings and secrets from `env` in `cloudflare:workers`. The generated declaration also extends `ProcessEnv` with the secret names, so `process.env` is typed for the few places that use it.

## Deploy-time checks

Both deploy scripts run five gates around the build and one check after the deploy, and each one throws rather than warning. Between the gates and the deploy, `db:migrate:<environment>` applies the pending D1 migrations.

| Script                              | Checks                                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scripts/verify-bindings.ts`        | Reads `wrangler.jsonc` with Wrangler's own loader and rejects a missing or placeholder `DB` id, `CACHE` id, `IMAGES` bucket, `AUDIT_LOG_QUEUE` or `NEWSLETTER_QUEUE` producer/consumer pair, a consumer without a consumed dead-letter queue, or `REALTIME_INVALIDATION_HUB` class, and a production `IMAGES` bucket that is preview's |
| `scripts/verify-stripe-keys.ts`     | Reads the mode of `VITE_STRIPE_PUBLISHABLE_KEY` and `STRIPE_SECRET_KEY` from their prefixes and rejects a missing key, a pair from different modes, test keys for production or live keys for preview, printing the mode and never a key                                                                                               |
| `scripts/verify-email-sender.ts`    | Asks Resend whether it would send as `RESEND_EMAIL_FROM` and rejects a display-name sender, `onboarding@resend.dev`, or an unknown or unverified domain, printing the DNS records to publish                                                                                                                                           |
| `scripts/verify-build.ts`           | Confirms `dist/server/wrangler.json` targets the right environment and Worker name, that `dist/client` holds JS, CSS and fonts, and that no client asset imports `cloudflare:workers` or `node:*` or contains Drizzle ORM                                                                                                              |
| `scripts/prepare-deploy-secrets.ts` | Writes only the declared secrets to `.wrangler/secrets.<environment>.json` and fails on a blank value other than the two InPost ones                                                                                                                                                                                                   |
| `scripts/verify-deployment.ts`      | After `wrangler deploy`, asks the environment's `workers.dev` host for `/`, `/products`, `/robots.txt`, `/api/webhooks/stripe` and `/api/health` and rejects any answer other than the shop's                                                                                                                                          |

The full sequence is visible in `package.json`:

```sh
bun run deploy:preview
# verify-bindings.ts → verify-stripe-keys.ts → verify-email-sender.ts → build:preview → prepare-deploy-secrets.ts → db:migrate:preview → wrangler deploy → verify-deployment.ts
```

The deploy step passes `--config dist/server/wrangler.json --secrets-file .wrangler/secrets.preview.json` and unsets `CLOUDFLARE_ENV` first, because the built config already carries the environment.

## Local Stripe webhooks

`bun run stripe:listen` forwards live test events to the local Worker:

```sh
stripe listen --latest --forward-to localhost:3000/api/webhooks/stripe
```

The signing secret the CLI prints must go into `STRIPE_WEBHOOK_SECRET` in `.env.development`.
