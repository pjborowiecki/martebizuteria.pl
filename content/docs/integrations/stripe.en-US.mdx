Stripe is the only payment provider. The store charges in PLN, and payment happens inside the storefront using Stripe's embedded Checkout Elements — the customer never leaves `/checkout`. An order row is created only when Stripe confirms payment via webhook; until then the data lives in a `checkout` row plus a `payment` row in the `pending` state, with inventory reserved.

## Server client

```ts
export const stripe = new StripeServer(env.STRIPE_SECRET_KEY, {
  apiVersion: STRIPE_API_VERSION,
  appInfo: { name: APP_NAME },
  httpClient: StripeServer.createFetchHttpClient(),
})
```

`createFetchHttpClient()` is required: the Node HTTP client does not exist on Workers. `STRIPE_API_VERSION` is pinned in `stripe.constants.ts` to `"2026-08-26.dahlia"` — changing it means re-reading every webhook payload shape.

## Constants

```ts
export const CHECKOUT_PAYMENT_METHOD_ORDER = ["card", "blik", "p24"] as const

const STRIPE_CURRENCY_BY_CODE = { PLN: "pln" } as const satisfies Record<SupportedCurrencyCode, string>

export const STRIPE_CURRENCY = STRIPE_CURRENCY_BY_CODE[STORE_CURRENCY_CODE]
```

BLIK and Przelewy24 sit next to card because they are what Polish customers expect; the `satisfies` clause means adding a currency to `SupportedCurrencyCode` in `src/modules/_core/constants/currency.ts` without adding a Stripe code here is a type error. `STRIPE_WEBHOOK_EVENTS` enumerates the ten events the application handles.

## Browser client

`stripe.client.ts` lazily loads Stripe.js once per page and maps the application locale onto Stripe's own:

```ts
const STRIPE_LOCALES = { "en-US": "en", "pl-PL": "pl" } as const satisfies Record<SupportedLocale, StripeElementLocale>
```

It reads `import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY`, warns to the console if it is missing, and memoizes the `loadStripe` promise in a module-level `stripeRef` so a locale change does not reload the script. A rejected download is dropped from `stripeRef`, so the next call downloads Stripe.js again instead of handing out the same failure until the page reloads; the payment step's **Try again** makes that call. `stripeJsQuery(locale)` wraps `getStripe` in query options keyed by `STRIPE_QUERY_KEYS.JS` and the locale, with `retry: false`, for a component that has to show its own state while the script downloads or after it fails; the account page's card form uses it. Because `stripeRef` keeps the locale of the first call, `toStripeLocale` is exported too: the account page's card form passes `locale: toStripeLocale(locale)` to its own `Elements`, so it follows the shopper's current language.

## The two server functions

`stripe.actions.ts` exposes exactly two entry points, both rate-limited at ten calls per 60 seconds and both lazily importing the heavy server module:

```ts
export const createCheckoutSessionFn = createServerFn({ method: "POST" })
  .middleware([withRateLimit("checkout-create", RATE_LIMITS.CHECKOUT)])
  .validator((data: unknown) => createCheckoutSessionInputSchema.parse(data))
  .handler(async ({ data }) => {
    const { handleCreateCheckoutSession } = await import("~/src/integrations/stripe/stripe.actions.server")

    return handleCreateCheckoutSession(data)
  })
```

`stripe.actions.schemas.ts` defines the payload: `{ checkoutValues: checkoutSchema, items: cartItemSchema[] }` with at least one item and at most `CART_LINES_MAX` (`src/modules/cart/cart.constants.ts`), plus `sessionId` for the update variant. `CART_LINES_MAX` is `STRIPE_CHECKOUT_LINE_ITEMS_MAX` minus the shipping line, because a Checkout Session in payment mode takes at most 100 line items. Every quantity must be a whole number from 1 to `CART_LINE_QUANTITY_MAX` (10), the most of one piece an order may hold. `checkoutSchema` comes from `src/modules/checkout/checkout.zod.ts`, so the address, delivery and billing rules are validated in exactly one place.

## Creating a session

`handleCreateCheckoutSession` in `stripe.actions.server.ts` first calls `admitNewCheckout`, which refuses the request before the Stripe customer, the catalogue, the discount or the stock is touched in two cases. `assertSalesOpen()` reads `store_setting.sales_paused` through `isSalesPaused()` and, while sales are paused, refuses with `CONFLICT` and `SALES_PAUSED` (see [Checkout: Pausing sales](/docs/features/checkout#pausing-sales)). `countOpenCheckouts` refuses with `TOO_MANY_REQUESTS` and `TOO_MANY_OPEN_CHECKOUTS` when the request's client address already has five open checkouts or its email three (see [Checkout: Limits on holding stock](/docs/features/checkout#limits-on-holding-stock)). Otherwise it runs this sequence:

1. `resolveDelivery(checkoutValues)` reads the chosen method with `getOfferedDeliveryMethodByIdQuery`, which only finds a method that is active and whose courier is active, the rule the delivery step lists by. Anything else is refused with `DELIVERY_METHOD_UNAVAILABLE` before Stripe is called, so a withdrawn or invented method can no longer ship for free. When the method's `type` in the database is `locker`, the request needs a `lockerId` shaped like an InPost point name or it is refused with `LOCKER_REQUIRED`, and InPost is asked whether that point exists: one it does not list is refused with `LOCKER_NOT_FOUND`, and when InPost cannot answer within three seconds the locker is accepted and the checkout flagged `locker_unconfirmed` for the shop to check (see [InPost](/docs/integrations/inpost#how-it-reaches-the-order)); for any other type the `lockerId` is dropped. The method's `price` is the shipping cost.
2. `validateAndCalculateItems(items)` loads the products with their inventory by handle, only those whose `status` is `published` (`getPublishedProductsWithInventoryByHandles`), resolves each variant, and **reads the price from the database** — `cartItemSchema` has no `price` or `rawPrice`, so the basket's price never reaches the handler. It rejects with `PRODUCT_NOT_FOUND`, which is also the answer for a product archived or returned to draft while it sat in a basket, `VARIANT_NOT_FOUND`, `INVALID_PRICE` (via `isSellPriceCentsValid`) or `INSUFFICIENT_INVENTORY`, and returns each line enriched with `inventoryId`. `toMetaItems` then writes the priced lines into the session's `items*` metadata, and refuses with `VALIDATION` and `CART_TOO_LARGE` a cart whose lines need more keys than Stripe leaves beside the checkout's own (see [Metadata is the fulfilment contract](#metadata-is-the-fulfilment-contract)), before the discount, the stock or the checkout row is touched.
3. `resolveCheckoutDiscount(...)` checks `checkoutValues.discountCode` again against the subtotal of the database prices and the shipping cost; a code that does not apply is dropped. See [Discounts](/docs/features/discounts).
4. `reserveInventoryForItems(validatedItems)` takes the stock with an `UPDATE` guarded on `quantity_available >= qty`, so it succeeds whenever enough is left at that moment, however many other checkouts reserved the same variant since step 2. When another checkout took the last units since then, it is refused with `CONFLICT` and `INSUFFICIENT_INVENTORY`, like step 2, so the shopper sees the out-of-stock message.
5. `createCheckout({ checkoutValues, clientAddress, discountId, lockerUnconfirmed, userEmail, userId })` writes the address rows and the `checkout` row, with the client address the open-checkout limit counts by and whether InPost could confirm its locker, and, with a code, claims one of its uses in `discount_claim` in the same batch, setting `discount_id` only when the claim was written. A code whose remaining uses other open checkouts hold is dropped here, and the session is built at the full price. If step 6 or 7 fails, `releaseDiscountClaims` gives the use back with the stock. See [Discounts: Holding a use while the shopper pays](/docs/features/discounts#holding-a-use-while-the-shopper-pays).
6. `createStripeSession(...)` creates the Stripe Checkout Session, expiring `CHECKOUT_SESSION_LIFETIME_SECONDS` (32 minutes) from now rather than after Stripe's 24-hour default, with a one-time coupon when a discount applies. If Stripe refuses the session, the coupon is deleted again before the error propagates.
7. `createPendingPayment(...)` writes the `payment` row with `provider: "stripe"`, `currency: "PLN"`, `transactionId` set to the Stripe session id and `reservedLines` set to the lines step 4 reserved.
8. `scheduleProductCatalogInvalidation()` pushes the new availability to connected storefronts.

If anything after step 4 throws, the handler releases the reservation with `releaseInventoryForItems(validatedItems)` and rethrows. That compensation is the reason a failed payment attempt does not leave stock locked.

The session itself:

```ts
const params: StripeType.Checkout.SessionCreateParams = {
  expires_at: Math.floor(Date.now() / MILLISECONDS_PER_SECOND) + CHECKOUT_SESSION_LIFETIME_SECONDS,
  line_items: toLineItems(lines, { cost: shippingCost, name: messages.deliveryLineItem[deliveryType] }),
  metadata: { ...metadata, ...itemsMetadata },
  mode: "payment",
  payment_intent_data: { description: messages.paymentDescription, metadata, receipt_email: email },
  phone_number_collection: { enabled: true },
  return_url: returnUrl,
  ui_mode: "elements",
  ...(customerId === undefined
    ? { customer_email: email }
    : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
}
const discounts = await toSessionDiscounts({ checkoutId, discount })
if (discounts.length > NO_COST) {
  params.discounts = discounts
}

const session = await stripe.checkout.sessions.create(params).catch(async (error: unknown) => {
  await deleteCheckoutCoupons({ checkoutId, discounts })
  throw error
})
```

`customerId` is set only for a signed-in shopper: before step 1, `handleCreateCheckoutSession` calls `ensureStripeCustomerWithEmail` (`stripe.customer.server.ts`) with the e-mail typed into the checkout form. On first use it creates a Stripe customer with that e-mail and stores its id in `user.stripe_customer_id`; for an account that already has a customer it calls `stripe.customers.update(customerId, { email })`. That update keeps Stripe in step with the order. Stripe prefills a session created with `customer` with the customer's e-mail, does not let the shopper change it, and returns it as `customer_details.email`; `customer_email` only seeds a customer that Checkout creates itself, and `customer_update` can save the address, name and shipping details to the customer but not the e-mail. Without the update, a customer created at an earlier checkout or from the account page would keep its old e-mail, and the payment's billing e-mail and Stripe's record of the payer would use that old address, while the order and the Stripe receipt (`receipt_email`) used the one the shopper typed. Stripe takes the customer's e-mail as it stands when the payment is confirmed, not when the session is created: `customer_details.email` and the payment method's billing e-mail both follow a change made to the customer while the session is open. Two checkouts that one account keeps open at the same time, in two browsers and with different e-mails, share the customer, so the one paid later is billed under the e-mail of the session that was created or updated last. The shop's own e-mails do not follow it: the order confirmation goes to the order's e-mail and the payment-failed e-mail to the checkout's (see [Transactional email](/docs/features/email)), and `fulfillCheckout` records `order.placed` with the checkout's e-mail. The session belongs to that Stripe customer and lets the shopper save the card, which `/account/payment` lists afterwards. A guest's session carries `customer_email` instead. `handleUpdateCheckoutSession` calls `ensureStripeCustomerWithEmail` the same way for every signed-in request, with the edited e-mail: for a checkout the account already owns, which moves its customer to that e-mail, and when it hands a guest's checkout to the account that has signed in since (see [Updating a session](#updating-a-session)). `ensureStripeCustomerWithEmail` and `ensureStripeCustomer`, described below, create a customer through the same steps: they store the new id with `coalesce`, and a request that finds another id already stored deletes the customer it just created, so parallel first requests end up with one customer. The account page is the other caller: `createCardSetupIntent` calls `ensureStripeCustomer`, which creates the customer with the account's e-mail when there is none and otherwise leaves its e-mail as the last checkout set it, and opens a card SetupIntent for that customer, which `stripe.confirmSetup` confirms in the browser. Deleting the account calls `deleteStripeCustomer`, which deletes that customer, and with it the saved cards, with `stripe.customers.del` and clears `user.stripe_customer_id`; a `resource_missing` answer counts as deleted, and any other error keeps the account. See [Account](/docs/features/account) and [Closing the account](/docs/features/account#closing-the-account).

`ui_mode: "elements"` is what gives the embedded experience. `return_url` is `${origin}/checkout?success=true&session_id={CHECKOUT_SESSION_ID}`, where Stripe fills in the session id and `origin` is `resolveRequestOrigin(getRequest())`: the address the checkout request came in on, refused with `FORBIDDEN` unless it is one of the hosts this build serves. See [Security model](/docs/architecture/security-model). The success page uses `session_id` to load the order through `getOrderConfirmationQuery`, and while the session's payment is still `pending` its server function retrieves the session and places the order of one Stripe reports paid, before the webhook arrives (see [Payments: Fulfilment from the return page](/docs/features/payments#fulfilment-from-the-return-page)). Shipping is added as an extra line item rather than as a Stripe shipping rate. Its name comes from `deliveryLineItem` in `pages.checkout` for the delivery method's type, in the shopper's language, so the line on the Stripe receipt is in the language of the checkout. A discount goes into `discounts`: for every session that carries one, `toSessionDiscounts` (`stripe.coupons.server.ts`) calls `stripe.coupons.create` with `amount_off: discount.amountMinorUnits`, `currency: STRIPE_CURRENCY`, `duration: "once"`, `metadata: { checkoutId, source: STRIPE_COUPON_SOURCE }` and `name: discount.code`. That metadata is how `deleteCheckoutCoupons` recognises the coupons it may delete: it deletes a session's coupon only when the coupon carries `source: "marte_checkout"` and the session's own `checkoutId`, and leaves every other coupon in the account alone. See [Discounts](/docs/features/discounts) for when it runs.

### What the shopper's bank shows

`payment_intent_data.description` is `paymentDescription` from `pages.checkout` in the checkout's language: "M'Arte – zamówienie w sklepie internetowym" or "M'Arte – online shop order". Stripe's BLIK guide shows it on the first two of the four lines a banking app displays when it asks the shopper to approve the payment, up to 70 characters, and a test keeps both translations within that; the guide does not say what those lines show without one. The fourth line is the shop's web address, which Stripe fills in itself. The text names the shop and no products, because a payment for a gift may show in a bank history someone else reads, and it carries no order number, because the order and its number are created only once the payment has gone through. The description also shows on the payment in the Stripe Dashboard.

The session sets no `statement_descriptor`: Stripe refuses one for a card charge, and the session offers cards beside BLIK and Przelewy24. The bank statement of a BLIK or Przelewy24 payment therefore shows the account's statement descriptor, after the Przelewy24 reference for a transfer, and a card statement starts with the account's shortened descriptor, or the statement descriptor cut to 10 characters. The BLIK guide puts a descriptor on the approval's third line only when the payment passes one, and does not say what that line shows otherwise. No `statement_descriptor_suffix` is set for cards either, because the only per-order value known when the session is created is the checkout id, which the shopper never sees. Both descriptors are set in the Stripe Dashboard's business details (`dashboard.stripe.com/settings/business-details`), in Latin characters and without `'`, so as "MARTE BIZUTERIA" rather than "M'Arte" (see [Go-live checklist](/docs/guides/go-live-checklist)).

### Metadata is the fulfilment contract

The session's `metadata` carries `checkoutId`, `deployment`, `discountCode`, `discountTotal`, `locale` and `userId`, typed as `CheckoutPaymentMetadata`, and the cart itself in `items0`, `items1`, …. The PaymentIntent gets only the six fields of `CheckoutPaymentMetadata`: Stripe copies the intent's metadata onto each of its charges, and nothing reads the cart from an intent or a charge. The webhook's deployment check and `payment_intent.payment_failed` read `deployment` and `checkoutId`, which the intent still has.

Stripe accepts at most 50 metadata keys, each at most 40 characters, with values of at most 500 characters. `toCheckoutSessionItemsMetadata` in `src/modules/checkout/checkout-metadata.zod.ts` splits the cart's JSON into values of at most `STRIPE_METADATA_VALUE_LENGTH_MAX` (500) characters, ending a value one character early rather than between the two halves of a character such as an emoji, which `encodeURIComponent` in Stripe's client would refuse. It allows the cart `STRIPE_METADATA_KEYS_MAX` (50) keys less the six of `CheckoutPaymentMetadata`, so 44, and refuses a cart that needs more with `VALIDATION` and `CART_TOO_LARGE`, which the payment step shows as `errors.cartTooLarge`. `readCheckoutSessionItemsJson` reassembles the values, still accepting a single legacy `items` key. A line of the catalogue's usual length, with a handle and title of about 35 characters and its image on `images.martebizuteria.pl`, takes about 300 characters, so about 74 such lines fit; the 99 lines `CART_LINES_MAX` allows fit only when they are shorter. Moving the cart's lines into D1, with only `checkoutId` in metadata, would lift that limit.

The webhook reads nothing else to know what was bought, so anything the confirmation e-mail or the order lines need has to be in there. `discountCode` and `discountTotal` are not read back: fulfilment recalculates the discount from the checkout's `discount_id`.

## Updating a session

When the cart or the form changes, the client does not create a second session — it updates the existing one. `stripe.checkout.ts` decides this with two fingerprints:

```ts
export const buildCheckoutLinesFingerprint = (lines: readonly CheckoutSessionLine[]): string =>
  lines
    .map((line) => `${line.variantId}:${line.qty}:${line.unitPrice}`)
    .toSorted((left, right) => left.localeCompare(right))
    .join("|")

export const buildCheckoutValuesFingerprint = (values: CheckoutFormSchema): string =>
  JSON.stringify(Object.fromEntries(Object.entries(values).toSorted(([left], [right]) => left.localeCompare(right))))
```

`ensureCheckoutSession` takes the session on screen and `heldSessionId`, the id the browser stored for its open session. It continues the held session, or the one on screen when nothing is stored, calling `updateCheckoutSessionFn` when either fingerprint has moved or when the held session is not the one on screen, and creates a session only when the browser holds none. So a reload, a second tab or a return from the basket replace the open session instead of reserving the basket again. Before any of that, the checkout page asks `getCheckoutSessionStatus` whether the stored session is still open, and shows the confirmation of one that was paid instead of reaching this update (see [Checkout](/docs/features/checkout)). `isCheckoutSessionFor` builds the session's lines fingerprint from the `lines` the server quoted and the basket's from its current prices, so a price the shop changed, which the availability check writes into the basket, replaces the session too. `resetCheckoutSession` forces the update of the held session, which the UI uses after a declined payment and when the shopper restarts a payment whose session expired. Each returned session keeps the server's `lines` and `totals`, which the checkout summary and the basket take their prices from, and carries `expiresAt`, `CHECKOUT_SESSION_LIFETIME_SECONDS` after it arrived, which the payment step uses to show that the session has expired.

Server-side, `handleUpdateCheckoutSession` is the most delicate function in the codebase:

1. `getPaymentContextByTransactionId(sessionId)` resolves the `checkout`, its owning `userId`, when it was created and the statuses of the checkout and its payment. A session that belongs to a signed-in user can only be updated by that user, otherwise `FORBIDDEN` with the reason `SESSION_CLOSED`, so a browser that has signed out starts a checkout of its own. A guest's checkout can be continued by whoever holds its session id, and when that request is signed in, as after a guest reaches the payment step and then signs in, the update hands the checkout to that account: the replacement session carries the account's `userId` in its metadata and its Stripe customer from `ensureStripeCustomerWithEmail`, and step 4 sets the checkout's `user_id`. The order then lands in the account, the shopper keeps the stock the guest session held, and the saved cards are offered. An unknown session id is refused with `NOT_FOUND`, and a checkout or payment that is no longer `pending` and was not paid with `CONFLICT`, both carrying the reason `SESSION_CLOSED`. A payment that has `succeeded` or been `refunded` is refused with `CONFLICT` and the reason `SESSION_COMPLETE` instead, before the ownership check, because the confirmation page shows that order to whoever holds the session id anyway.
2. The old Stripe session is retrieved with its payment intent expanded. A session whose payment `isCheckoutSessionProcessing` (`stripe.utils.ts`) reports under way is refused first, with `SESSION_PROCESSING`, so replacing it never cancels a payment the bank may still complete: an `open` session whose payment intent is `processing` or a BLIK payment waiting for approval in the banking app (`requires_action` with `blik_authorize`), and a `complete` session whose `payment_status` is still `unpaid` because its BLIK or Przelewy24 payment has not settled. Any other `complete` session, paid before its webhook has arrived, is refused with `SESSION_COMPLETE`, and any other status but `open` with `SESSION_CLOSED`. When the status is `expired`, `releaseExpiredCheckoutSession` first runs `releaseCheckout` to return the session's lines, guarded like the expiry webhook's own release, so the stock is free for the fresh checkout the client opens next and the webhook, whenever it arrives, releases nothing. Otherwise its `items*` metadata is parsed into the lines it holds. Only then, with the session known to be open, `assertSalesOpen()` refuses the update with `SALES_PAUSED` while sales are paused, so the old session, its stock and its claim stay as they were, and a session paid before the pause still answers `SESSION_COMPLETE`. Then `assertCheckoutStillEditable` refuses with `SESSION_CLOSED` a checkout created `CHECKOUT_SESSION_LIFETIME_SECONDS` or more ago, because each update gives the replacement a fresh hold and the edit is not counted against the open-checkout caps: `stripe.checkout.sessions.expire` closes the open session first and the expired session goes through `releaseExpiredCheckoutSession`, so the fresh checkout, which the caps count again, finds its stock free. If Stripe will not expire it, the error propagates and the stock stays with the session. A session whose payment is under way never reaches this check, so the 32 minutes never expire a payment the bank is still confirming.
3. `validateAndCalculateItems` checks the edited cart against the available stock plus what the old session holds, and `toMetaItems` refuses an edited cart that no longer fits Stripe's metadata with `CART_TOO_LARGE` while nothing has changed. The delivery and the discount are resolved again, with the same refusals as above, and `claimCheckoutDiscount` claims the code for the checkout (a checkout that already holds it keeps its claim, and a code whose uses are held elsewhere is dropped). `handOverCheckoutSession` then reserves what the edited cart adds, `quantitiesBeyond(validatedItems, heldLines)`, with `reserveInventoryForItems` on the inventory ids validation returned, and creates the replacement Stripe session. The units the old session holds and the edited cart keeps are never released and reserved again, so no other checkout can take them during the hand-over (see [Inventory: Moving a hold to a replacement session](/docs/features/inventory#moving-a-hold-to-a-replacement-session)). When another checkout took the added units since validation, the reservation is refused with `CONFLICT` and `INSUFFICIENT_INVENTORY`. Nothing else has changed yet, so a failure here leaves the old session open and its stock reserved, `releaseInventoryForItems` gives back what was added, and `releaseUnappliedDiscountClaims` gives back a claim made for a different code than the one in `checkout.discount_id`.
4. `retireCheckoutSession` expires the old session with `stripe.checkout.sessions.expire(...)`, so it can no longer be paid, then calls `supersedeCheckoutSession`. That use case moves the `payment` row onto the replacement session, with the edited cart's lines as its `reserved_lines`, and releases what the edited cart dropped, `quantitiesBeyond(heldLines, reservedLines)`, in one D1 batch, only while the payment and its checkout are still `pending`. The same batch deletes the checkout's claims of every code but the one the replacement applies. When the request is signed in, it also sets the checkout's `user_id` to that account, only while the checkout is `pending`, has no owner and its payment now carries the replacement session, so an owned checkout never changes hands. If either step fails, or the expiry webhook released the checkout first, the replacement is expired, what the edited cart added is given back and the update fails. Expiring the old session sends its `checkout.session.expired` webhook while the update is still running, and `prepareReleaseCheckoutBatch` acts only while the session's payment and its checkout are `pending`: a release that commits before the move returns all the old lines, fails the checkout and makes `supersedeCheckoutSession` refuse, and one that commits after it finds no payment on the old session, changes nothing and records no `order.released` entry. The old lines are never released twice.
5. `saveReplacementDelivery` updates the checkout's delivery, `discount_id` and `locker_unconfirmed`. If that fails, `releaseCheckout` on the replacement session fails the checkout and returns the whole edited cart, and the replacement is expired.

When `updateCheckoutSessionFn` answers with `SESSION_CLOSED`, `ensureCheckoutSession` and `resetCheckoutSession` call `createCheckoutSessionFn` for a fresh checkout instead of failing. When it answers with `SESSION_COMPLETE` they open nothing and throw `PaidCheckoutSessionError` with the id of the session they tried to continue, and the payment step shows that session's confirmation, so a session paid in the moment between the checkout page's session check and this update never leads to a second payment form. When it answers with `SESSION_PROCESSING` they open nothing either and throw `ProcessingCheckoutSessionError` (`stripe.checkout.processing.ts`) with that session's id, and the payment step waits for the bank on it until `getCheckoutSessionStatus` reports it `complete`, `open` again or `closed`.

`getCheckoutSessionStatus` (`src/modules/checkout/use-cases/get-checkout-session-status.ts`) answers the checkout page's question about a stored or returned session with `"complete"`, `"open"`, `"processing"` or `"closed"`. It reads the payment first and calls `stripe.checkout.sessions.retrieve`, with the payment intent expanded, only for a `pending` one. A session whose payment is under way by the same `isCheckoutSessionProcessing` as step 2, an `open` one or a `complete` one still `unpaid`, is reported as `"processing"` first, so `complete` is passed on only for a paid session, and `open` as it is; an `expired` session goes through `releaseExpiredCheckoutSession` exactly as in step 2. A paid session is `"complete"` to whoever holds its id, as on the confirmation page. The ownership rule of step 1 applies only to an open or processing session: a request not signed in as the owning account is told it is `"closed"` instead of being refused. It is rate-limited as `checkout-status`.

`expireCheckoutsHoldingVariants` (`src/modules/checkout/use-cases/expire-checkouts-holding-variants.server.ts`) is a third caller of `releaseExpiredCheckoutSession`, after step 2 and `getCheckoutSessionStatus`. When the admin saves a product as draft or archived, it expires each open session holding one of the product's variants with `stripe.checkout.sessions.expire` and hands the expired session Stripe returns to `releaseExpiredCheckoutSession`, so the `checkout.session.expired` webhook that follows finds the stock already returned. A session Stripe will not expire is logged and left as it is (see [Admin catalog](/docs/features/admin-catalog#writing)).

Preserve this ordering when you touch it. The `payment` row is moved rather than recreated because `20260924120000_checkout_idempotency_constraints.sql` puts a unique index on `payment.transaction_id` (and on `order.checkout_id`); inserting a second payment row for the replacement session would violate it.

## Confirming in the browser

`confirmCheckoutSession` wraps `checkout.confirm({ billingAddress, redirect: "if_required" })` and classifies the outcome:

```ts
export type ConfirmOutcome =
  { status: "declined"; message: string } | { status: "failed"; message: string } | { status: "processing" } | { status: "success" }
```

A confirmation that goes through is `success` only when the session Stripe returns is `complete` and its `paymentStatus` is not `unpaid`. A BLIK or Przelewy24 payment that has not settled yet is `processing`, and the payment step waits for the bank on it instead of opening the confirmation. An error with code `paymentFailed` is `declined`. Every other error, which Stripe.js returns with code `null`, is `failed`, and the payment step reads the session's status before it decides between keeping the session with Stripe's message, waiting for the bank, opening the confirmation and resetting a closed session (see [Checkout](/docs/features/checkout)). `buildCheckoutContact(values)` picks the billing address when `sameAsShipping === false` and the shipping address otherwise.

`PaymentStep` in `src/presentation/components/custom/checkout/components/_steps/payment-step.client.tsx` mounts `CheckoutElementsProvider` keyed by `sessionId` through `PaymentElementsProvider`, which asks `getStripe(locale)` for Stripe.js once per mount, passes `getStripeAppearance(theme)` and `STRIPE_FONTS`, and renders the Payment Element as an accordion with wallets and Link disabled and `paymentMethodOrder` taken from `CHECKOUT_PAYMENT_METHOD_ORDER`. The provider keeps an error state until it is mounted again, and the Payment Element reports a failed load only through `loaderror`, so both show a notice that the payment form did not load. The notice is announced as an alert and takes focus. Its **Try again** reads the session's status and, for a session that is still open, mounts a new provider, and with it a new `getStripe` call, in a container keyed by the attempt; a replacement session's provider makes its own call, so it never inherits a failed download (see [Checkout](/docs/features/checkout)). The pay button looks disabled until `checkout.canConfirm` is true but stays pressable, and a press before then calls `checkout.validateElements()` so Stripe marks what is missing.

`stripe.appearance.ts` exports `getStripeAppearance("light" | "dark")`, a full Elements `Appearance` with the storefront's flat, square, border-first visual language, and `STRIPE_FONTS`, the Manrope stylesheet the appearance's font stack needs inside Stripe's iframes. Checkout and the account page's card form both use them. Its colours are literal hex values matching the design tokens, so when a token changes the values here have to be changed with it.

## Webhooks

`src/routes/api/webhooks.stripe.ts` verifies the signature before anything else:

```ts
const event = await verifiedStripeEvent(request, signature, env.STRIPE_WEBHOOK_SECRET)
```

A missing `stripe-signature` header or a missing `STRIPE_WEBHOOK_SECRET` returns 400; a failed `constructEventAsync` returns 400; an event whose `livemode` does not match the environment, live in `production` and test everywhere else, is logged and answered `{ received: true }` without running a handler; a test-mode event whose object carries `deployment` metadata naming another deployment, such as a local test run's checkout reaching preview, is logged at `info` level as `[Stripe] Ignoring event <id> (<type>): its checkout belongs to <deployment>, …` and answered the same way (see [Payments](/docs/features/payments#the-webhook-endpoint)); an unknown event type is logged and answered `{ received: true }`; a handler that throws returns 500 so Stripe retries, and emails `RESEND_EMAIL_FROM` in the background once per event, however often Stripe retries it. Handlers live in `stripe.webhooks.ts` as a plain map:

| Event                                      | Handler behaviour                                                                                                                                                                                                             |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkout.session.completed`               | `handleFulfillCheckoutSession` — only if `payment_status` is `paid` or `no_payment_required`, otherwise logs and waits for the async event; then `deleteCheckoutCoupons` deletes the session's tagged coupon either way       |
| `checkout.session.async_payment_succeeded` | The same fulfilment path (BLIK and P24 settle asynchronously)                                                                                                                                                                 |
| `checkout.session.async_payment_failed`    | `handleAsyncPaymentFailed` — releases the reservation and, only when this delivery released it, audits `orderReleased` and emails the customer                                                                                |
| `checkout.session.expired`                 | The same release path, which audits `orderReleased` only when it released something, so a session a checkout update replaced leaves no entry; then `deleteCheckoutCoupons` deletes the session's tagged coupon                |
| `payment_intent.payment_failed`            | Audits `orderPaymentFailed` with `last_payment_error.message`; no state change                                                                                                                                                |
| `charge.refunded`                          | `refundOrder({ fullyRefunded, refundedAmount, transactionId })` with the total of the charge's refunds that still stand, which never restocks, then `sendOrderRefundedEmail` for a refund the customer was not told about yet |
| `refund.failed`                            | `handleRefundUndone` — `undoFailedRefund` lowers the payment to the refunds that still stand and reopens a refunded order, audits `order.refund_failed` and sends the shop a `refundFailed` alert; never emails the customer  |
| `refund.updated`                           | The same, when the refund is now `canceled` or `failed`; returns at once for any other update                                                                                                                                 |
| `charge.dispute.created`                   | `flagOrderDispute(...)` — freezes the order and audits `orderDisputeOpened`                                                                                                                                                   |
| `charge.dispute.closed`                    | If `status === "lost"`, records the refund through `refundOrder`; otherwise `clearOrderDispute(...)`                                                                                                                          |

Fulfilment parses the metadata lines, calls `fulfillCheckout({ currency, lines, locale, paidAmount, transactionId })` with `paidAmount` set to `session.amount_total`, and — only if that returned a new `orderId`, which makes the handler idempotent against Stripe's retries — records `orderPaymentCaptured` (`fulfillCheckout` has recorded `orderPlaced` with the checkout's e-mail once its batch committed), schedules admin-orders and product-catalog invalidation, and sends the confirmation e-mail, together with the shop's new-order notice to `RESEND_EMAIL_FROM`. That e-mail links to the origin of the session's `return_url`, the address the checkout was made on, not to the host Stripe called, and `resolveDeploymentOrigin` refuses it unless some deployment serves that host. The e-mail step never throws: a refused or unpreparable confirmation is recorded as `email.failed` on the order and the handler still succeeds, so Stripe does not redeliver the event over an e-mail. The send is also handed to `scheduleBackgroundWork`, so it finishes and is recorded even if Stripe drops the connection before the handler answers. For a discounted order, `fulfillCheckout` writes the `discount_redemption` row and counts the use in the order's own batch. If parsing the metadata or `fulfillCheckout` fails, the handler records an `order.fulfillment_failed` audit at `error` severity naming the amount, the customer's email and the cause, then rethrows so Stripe retries, and a retry that fails again adds no second entry, because the entry is keyed by the session; when `fulfillCheckout` reports with `ERROR_CODES.NOT_FOUND` that no pending checkout can take the session, it records the same audit, emails `RESEND_EMAIL_FROM` about the session in the background and answers `200`, because a retry cannot help (see [Payments: Fulfilment](/docs/features/payments#fulfilment)). The order step and the audits, refreshes and e-mails after it are `createOrderFromPaidSession` and `announcePlacedOrder` in `stripe.fulfillment.server.ts`, which the return page runs too when Stripe reports the session paid before its webhook arrives; whichever of the two places the order announces it, and the other does nothing.

`charge.refunded`, the refund events and the dispute handlers only receive a PaymentIntent, so `resolveCheckoutSession` lists Checkout Sessions filtered by `payment_intent` with `limit: 1` to recover the session whose id the `payment` row is keyed by. The refund handler also takes the session's `return_url` as the origin of the refund e-mail. If no session is found the handler logs and returns rather than failing. The refund handlers then read the charge's refunds with `readStandingRefunds` from `stripe.refunds.server.ts`, which lists them with `stripe.refunds.list({ charge, limit: 100 })` through every page and adds up those that are not `failed` or `canceled`, because the charge in a `charge.refunded` event is a snapshot from when the refund was created and a refund can fail after it (see [Payments: Refunds and disputes](/docs/features/payments#refunds-and-disputes)).

The two customer e-mails these events send go out once per event. The failed-payment e-mail is sent only when `releaseCheckout` reports that this delivery moved the session's payment from `pending` to `failed`. The refund e-mail is sent only when `refundOrder` reports that the charge's refunds that still stand add up to more than the payment had recorded before the event, for an order the shop had not cancelled; a cancellation e-mails the customer about its own refund. Its key names the newest of those refunds, so a refund issued again after one failed is e-mailed even when its amount is the same. A refund that fails or is cancelled e-mails the shop, not the customer. See [Transactional email](/docs/features/email#cancellation-refund-and-failed-payment).

Stripe sends a related object either as its id or, when expanded, as the object itself. `resolveStripeObjectId` in `stripe.utils.ts` returns the id in both cases and `undefined` for `null`. `resolveCheckoutSession` uses it for the PaymentIntent, the order confirmation e-mail for the session's PaymentIntent, the saved card removal for the card's customer, and the admin refund in `refund-admin-order.ts` for the PaymentIntent of the Checkout Session it retrieves from `payment.transaction_id`, since Stripe refunds a PaymentIntent and not a session. See [Payments](/docs/features/payments).

No refund event returns stock, because a refund does not say whether the goods came back: the admin decides that in the Refund dialog or with Return to stock on the order (see [Orders](/docs/features/orders#admin-actions)). A lost dispute also logs `review inventory manually`, because the goods are usually gone.

## Local development

```bash
bun run stripe:listen
# stripe listen --latest --forward-to localhost:3000/api/webhooks/stripe
```

The `STRIPE_WEBHOOK_SECRET` printed by that command is the one your local environment file needs. Without it the webhook route answers 400 and nothing is fulfilled.

The browser tests emulate Stripe in the test Worker. One Playwright project, `stripe-test-mode`, pays a checkout in the real Payment Element with Stripe's test card when it is built and run with a Stripe sandbox's keys, and forwards the sandbox's `checkout.session.completed` event to the local webhook itself, so it needs no Stripe CLI; see [Stripe test mode](/docs/tooling/testing#stripe-test-mode).

## Secrets

`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are Worker secrets listed in `wrangler.jsonc`; `VITE_STRIPE_PUBLISHABLE_KEY` is a browser variable in the environment files.

The two keys have to come from the same Stripe mode, and the mode has to match the environment. `deploy:preview` and `deploy:production` run `scripts/verify-stripe-keys.ts <environment>` right after `verify-bindings.ts` and before the build, and it stops the deploy unless both keys pass `verifyStripeKeys` in `stripe.keys.ts`:

| Environment              | `VITE_STRIPE_PUBLISHABLE_KEY` | `STRIPE_SECRET_KEY`      |
| ------------------------ | ----------------------------- | ------------------------ |
| `production`             | `pk_live_`                    | `sk_live_` or `rk_live_` |
| `preview`, `development` | `pk_test_`                    | `sk_test_` or `rk_test_` |

A live publishable key next to a test secret key, or the reverse, is refused in every environment, because the payment form could not open the Checkout Sessions the server creates. Test keys in production would accept Stripe's test cards for real orders, and live keys in preview would charge a real card for a test order. A missing or blank key, or a value that is not the kind of key its variable holds, such as a secret key in `VITE_STRIPE_PUBLISHABLE_KEY`, is refused too. The script reads each key from the process environment first and `.env.<environment>` second, as the deploy workflows supply it, and prints the variables and their mode, never a key. `bun scripts/verify-stripe-keys.ts development` runs the same check against `.env.development`. The rules are unit tested in `__test__/stripe.keys.test.ts`.

The check reads only the prefixes. It does not ask Stripe whether the keys are still valid, whether a restricted key may write the Checkout Sessions, coupons, customers, payment methods, refunds and SetupIntents the shop manages and read its PaymentIntents, or whether the live webhook endpoint exists. Before the first production deploy, create the live endpoint at `https://<host>/api/webhooks/stripe`, subscribe it to the ten events in `STRIPE_WEBHOOK_EVENTS`, `refund.failed` and `refund.updated` included, store its own `whsec_` as the production `STRIPE_WEBHOOK_SECRET`, and turn on BLIK and Przelewy24 in live mode. A `whsec_` secret does not say which mode its endpoint runs in, so the deploy cannot check `STRIPE_WEBHOOK_SECRET`; the webhook route instead logs and ignores every event from the other mode (see [Webhooks](#webhooks)). The [Go-live checklist](/docs/guides/go-live-checklist) lists these steps with everything else production needs before it takes real orders.
