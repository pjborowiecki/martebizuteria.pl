Sklep jest polski w pierwszej kolejności, a angielski w drugiej. `pl-PL` jest domyślnym językiem i serwowany jest bez prefiksu, więc `/products` jest po polsku, a `/en-US/products` po angielsku. Katalog `src/integrations/use-intl/` zawiera siedem plików. Pięć z nich definiuje języki, przepisuje adresy, ładuje przestrzenie nazw komunikatów i przechowuje wybór w ciasteczku; `i18n.display.ts` i `i18n.display-preferences.ts` ustalają strefę czasową i format, w których każdy użytkownik widzi daty i liczby.

## Konfiguracja

Plik `i18n.config.ts` zawiera całą definicję języków:

```ts
const COOKIE_NAME = "marte_locale"

const SUPPORTED_LOCALES = ["pl-PL", "en-US"] as const

export type SupportedLocale = (typeof SUPPORTED_LOCALES)[number]

const DEFAULT_LOCALE: SupportedLocale = "pl-PL"

const DEFAULT_TIMEZONE = "Europe/Warsaw"

export const I18N = { COOKIE_NAME, DEFAULT_LOCALE, DEFAULT_TIMEZONE, SUPPORTED_LOCALES } as const
```

Typ `SupportedLocale` wyprowadzany jest z krotki, więc dodanie tu języka sprawia, że system typów domaga się reszty: języka Stripe w `stripe.client.ts`, języka `react-day-picker` w `react-day-picker.locale.ts`, pliku JSON na każdą przestrzeń nazw w `messages/<locale>/`, drugiego pliku MDX dla każdej strony w `content/docs` oraz tytułu, opisu i treści w tym języku dla każdego wiersza `content_page`, wpisywanych w edytorze pod `/admin/content`.

`DEFAULT_TIMEZONE` to strefa czasowa sklepu. Korzystają z niej testowy provider renderowania w `src/platform/testing/lib/render.tsx` oraz szablon e-maila o odstąpieniu, `order-withdrawal.tsx`, który podaje, kiedy złożono oświadczenie. Własne daty biznesowe sklepu używają tej samej strefy przez `DEFAULT_TIMEZONE_CODE` z `src/modules/_core/constants/timezone.ts`: rok w numerze zamówienia i terminy odstąpienia w `polish-deadline.ts`. Strefa czasowa i format, w których wyświetla się strona, pochodzą z preferencji użytkownika (zobacz [Preferencje wyświetlania](#preferencje-wyświetlania)); listy do wyboru to `TIMEZONES` w `src/modules/_core/constants/timezone.ts` i `FORMAT_LOCALES` w `src/integrations/use-intl/i18n.display.ts`.

## Kształt adresów

Plik `i18n.paths.ts` implementuje reguły prefiksów. Wzorzec ignorowanych ścieżek to istotny punkt wyjścia:

```ts
const IGNORED_PATHS_REGEX = /^\/(?:api|rpc|_serverFn|assets|forms)(?:\/|$)/u
```

Te prefiksy nigdy nie otrzymują segmentu języka, ponieważ są punktami końcowymi dla maszyn albo, w przypadku `/forms`, formularzami PDF, które są takie same w każdym języku.

| Eksport                                  | Zachowanie                                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `isSupportedLocale(locale)`              | Predykat typu wobec zbioru wspieranych języków                                                       |
| `shouldIgnorePath(pathname)`             | Wzorzec powyżej                                                                                      |
| `extractLocaleFromPath(pathname)`        | Język z prefiksu albo `undefined` — **także wtedy, gdy prefiksem jest `pl-PL`**                      |
| `deLocalizePathname(pathname)`           | Usuwa dowolny wspierany prefiks, zwracając `/`, gdy nic nie zostaje                                  |
| `localizePathname({ locale, pathname })` | Dodaje prefiks, z wyjątkiem języka domyślnego oraz ścieżek ignorowanych i względnych wobec protokołu |
| `canonicalizePathname(pathname)`         | Przepisuje alias językowy lub zbędny prefiks domyślny na ścieżkę kanoniczną                          |
| `localeLinks({ origin, pathname })`      | Odnośnik `canonical` oraz po jednym `alternate` na język i jeden `x-default`                         |

Dwie subtelności decydują o większości zachowania:

- `extractLocaleFromPath` zwraca `undefined` dla prefiksu `pl-PL`, traktując `/pl-PL/products` jako „brak języka w adresie". `canonicalizePathname` przepisuje to następnie na `/products`, więc polski prefiks nigdy nie może stać się drugim, zdublowanym adresem tej samej strony.
- `LANGUAGE_ALIASES` mapuje sam podtag języka na pełny kod (`pl` → `pl-PL`, `en` → `en-US`), a `canonicalizePathname` z tego korzysta, więc `/en/products` przekierowuje na `/en-US/products`.

## Middleware

Plik `i18n.middleware.ts` działa w `src/server.ts` przed handlerem Start. `resolveLocale(request)` zwraca co najwyżej jedno z dwojga: przekierowanie albo ciasteczko:

```ts
if ((request.method !== "GET" && request.method !== "HEAD") || !isDocumentRequest(request) || shouldIgnorePath(pathname)) {
  return {}
}

const canonical = canonicalizePathname(pathname)

if (canonical !== pathname) {
  url.pathname = canonical

  return { redirect: Response.redirect(url.href, HTTP_MOVED_PERMANENTLY) }
}
```

Działa wyłącznie na żądaniach dokumentów `GET` i `HEAD`. `isDocumentRequest` preferuje nagłówek `sec-fetch-dest` (`document`, `frame`, `iframe`), a w jego braku dopasowuje `text/html` lub `application/xhtml+xml` w `accept`, traktując brak `accept` jako dokument. Ścieżka niekanoniczna otrzymuje **301**, co ma znaczenie dla SEO: `/pl-PL/products` i `/en/products` trwale zwijają się do swoich form kanonicznych.

Gdy ścieżka jest już kanoniczna, ale język z adresu i ciasteczko `marte_locale` się nie zgadzają, middleware zwraca `{ setCookie }`, a `src/server.ts` dołącza je do odpowiedzi. Adres zawsze wygrywa z ciasteczkiem.

## Odczyt bieżącego języka

Plik `i18n.utils.ts` udostępnia język izomorficznie, przez `createIsomorphicFn`, więc to samo wywołanie działa w loaderze i w komponencie:

```ts
export const getCurrentLocale = createIsomorphicFn()
  .server((): SupportedLocale => {
    const request = getRequest()
    const { pathname } = new URL(request.url)

    if (shouldIgnorePath(pathname)) {
      return parseLocaleCookie(request.headers.get("cookie")) ?? I18N.DEFAULT_LOCALE
    }

    return extractLocaleFromPath(pathname) ?? I18N.DEFAULT_LOCALE
  })
  .client(/* to samo, z globalThis.location i document.cookie */)
```

Ciasteczko jest czytane wyłącznie dla ścieżek ignorowanych — i to jest właśnie przypadek, który ma znaczenie, ponieważ funkcja serwerowa wysyła żądanie na `/_serverFn/...` i nie ma języka w swoim adresie. Dlatego funkcja serwerowa taka jak `createCheckoutSessionFn` może wywołać `getCurrentLocale()` i wciąż wpisać język klienta do metadanych sesji Stripe. `getCurrentPathname`, `localizeUrl` i `deLocalizeUrl` to odpowiedniki działające na adresach; dwie ostatnie przekazuje `src/router.tsx` do opcji `rewrite` routera.

## Komunikaty

`messages/<locale>/<namespace>.json` — 61 przestrzeni nazw na język, o identycznych nazwach plików w obu. Przestrzeń nazw _jest_ nazwą pliku, z kropkami jako zagnieżdżeniem: `pages.admin.catalog.products.json` to `pages.admin.catalog.products`.

Plik `i18n.messages.ts` robi cztery rzeczy.

**Odnajduje pliki w czasie budowania.** `import.meta.glob("../../../messages/*/*.json", { import: "default" })` tworzy leniwy loader dla każdego pliku, więc przestrzeń nazw to jeden osobny fragment kodu. `loadNamespace` odnajduje ścieżkę i rzuca precyzyjny błąd, gdy jej brakuje:

```ts
const load = messageModules[modulePath({ locale, namespace })]

if (load === undefined) {
  throw new Error(`Missing translation namespace: messages/${locale}/${namespace}.json`)
}
```

**Definiuje przestrzenie nazw korzenia** — sześć, których potrzebuje każda strona, wypisanych jako jawny glob, aby zbiór był sprawdzany wobec systemu plików, a nie utrzymywany ręcznie:

```ts
const rootMessagePaths = Object.keys(
  import.meta.glob([
    "../../../messages/*/common.json",
    "../../../messages/*/components.custom.json",
    "../../../messages/*/components.shadcn.json",
    "../../../messages/*/errors.json",
    "../../../messages/*/pages.auth.errors.json",
    "../../../messages/*/pages.auth.toast.json",
  ]),
)

export const ROOT_NAMESPACES = [...new Set(rootMessagePaths.map((path) => toNamespace(path)))]
```

**Zamienia płaskie przestrzenie nazw w zagnieżdżone drzewo.** `buildMessageTree` dzieli każdą przestrzeń nazw po `.`, owija komunikaty w tę ścieżkę i głęboko scala gałęzie, więc `pages.admin.json` i `pages.admin.catalog.json` współistnieją w jednym obiekcie `pages.admin`.

**Udostępnia opcje zapytania.** `messagesQueryOptions({ locale, namespace })` z `staleTime` i `gcTime` równymi `Infinity` oraz `preloadNamespaces({ locale, namespaces, queryClient })`, które rozwiązuje je wszystkie równolegle.

`getRouteNamespaces(matches)` jest klejem: przyjmuje dopasowane trasy i zwraca `ROOT_NAMESPACES` wraz z każdym wpisem `staticData.namespaces`, bez duplikatów.

## Jak strona otrzymuje tłumaczenia

1. Trasa deklaruje, czego potrzebuje: `staticData: { namespaces: ["pages.products"] }`.
2. `beforeLoad` w `__root.tsx` wywołuje `preloadNamespaces({ locale, namespaces: getRouteNamespaces(matches), queryClient })`, więc wszystko jest w cache zapytań przed wyrenderowaniem jakiegokolwiek komponentu.
3. `TranslationsProvider` w `src/providers/translations-provider.tsx` czyta te same przestrzenie nazw przez `useSuspenseQueries`, scala je `buildMessageTree` i renderuje dostawcę z `use-intl`:

```tsx
<IntlProvider locale={locale} messages={messages} timeZone={timeZone}>
  {children}
</IntlProvider>
```

`timeZone` to zapisana strefa czasowa użytkownika, strefa wykryta dla żądania albo `UTC`. Format dat i liczb trafia do `DisplayPreferencesContext` wewnątrz providera, a nie do niego, bo `locale` providera wybiera też formy liczby mnogiej w komunikatach. Zobacz [Preferencje wyświetlania](#preferencje-wyświetlania).

Zapisuje też język z powrotem do ciasteczka `marte_locale` w efekcie, więc bezpośrednie wejście na `/en-US/...` jest pamiętane.

4. Komponent wywołuje `useTranslations("pages.products")` i otrzymuje `t("title")`.

Loader trasy często potrzebuje też komunikatu do swojego `head`, który uzyskuje, czekając na te same opcje zapytania — dzięki cache jest to darmowe:

```ts
const [messages] = await Promise.all([
  context.queryClient.query(messagesQueryOptions<typeof productsMessages>({ locale: context.locale, namespace: "pages.products" })),
  prefetchProductsCatalogPage(/* … */),
])
```

Zwróć uwagę na argument typu `<typeof productsMessages>`, pobrany z importu wyłącznie typu z angielskiego pliku JSON. To projektowa konwencja typowanego dostępu do komunikatów poza kontekstem Reacta i dlatego klucz obecny po angielsku, a brakujący po polsku, jest błędem typowania.

## Preferencje wyświetlania

Język strony wynika z adresu, ale strefa czasowa i format, czyli ustawienia regionalne decydujące o zapisie dat, godzin i liczb, należą do użytkownika. `i18n.display.ts` zawiera reguły, a `i18n.display-preferences.ts` funkcję serwerową i zapytanie, które dostarczają je stronie. Co widzą kupujący i administrator, opisuje [Internacjonalizacja](/docs/features/internationalization).

### Kolejność wykrywania

`detectDisplayPreferences({ acceptLanguage, cookieHeader, edgeTimeZone })` odczytuje to, co ujawnia żądanie, a `toSavedDisplayPreferences(user)` to, co zalogowany użytkownik ma zapisane w `user.timezone` i `user.format_locale`. `resolveDisplayPreferences({ detected, saved })` pozwala każdej zapisanej wartości wygrać z jej wykrytym odpowiednikiem, niezależnie od drugiej:

| Preferencja    | Kolejność                                                                                                                                                                                                                                                                                                                  |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Strefa czasowa | Zapisana `user.timezone`; ciasteczko `marte_time_zone` (`TIME_ZONE_COOKIE_NAME`), w którym przeglądarka zgłasza własną strefę; `edgeTimeZone`, strefa, którą Cloudflare wyprowadza z adresu odwiedzającego (`request.cf?.timezone`, wpisana do kontekstu żądania przez `src/server.ts`); `FALLBACK_TIME_ZONE`, czyli `UTC` |
| Format         | Zapisany `user.format_locale`; pierwszy wpis `Accept-Language`, w kolejności z nagłówka i bez wag `q`, który przyjmuje `toFormatLocale`; `FALLBACK_FORMAT_LOCALE`, czyli `en-US`                                                                                                                                           |

Każdy kandydat jest sprawdzany przed użyciem, także zapisany, więc wartość, z którą środowisko nie umie formatować, jest pomijana. `isTimeZone` przyjmuje najwyżej 64 znaki, które `Intl.DateTimeFormat` akceptuje jako `timeZone`. `toFormatLocale` kanonizuje najwyżej 35 znaków przez `Intl.getCanonicalLocales` i zachowuje znacznik tylko wtedy, gdy obsługuje go `Intl.DateTimeFormat.supportedLocalesOf`.

### Zapytanie i jego cache

`getDisplayPreferences` to funkcja serwerowa `GET`, która zwraca obie połowy, `{ detected, saved }`: nagłówki czyta przez `getRequest()`, sesję przez `getRequestSession()`, zapamiętywaną na czas żądania, a `edgeTimeZone` przez `getGlobalStartContext()`. Odwiedzający nie ma nic zapisanego. `displayPreferencesQuery` trzyma odpowiedź w cache pod `DISPLAY_PREFERENCES_QUERY_KEY`, czyli `["i18n", "displayPreferences"]`, ze `staleTime: Infinity` i bez ponownego pobierania przy powrocie do okna lub odzyskaniu połączenia. `beforeLoad` w `__root.tsx` czeka na nie w tym samym `Promise.all` co na przestrzenie nazw, więc render na serwerze i strona po hydracji formatują z tymi samymi wartościami.

Wpis zmienia się na trzy sposoby:

- W przeglądarce `useBrowserTimeZone` w `TranslationsProvider` po pierwszym renderze odczytuje `Intl.DateTimeFormat().resolvedOptions().timeZone`. Gdy to poprawna strefa, zapisuje ją w `marte_time_zone`, jeśli ciasteczko ma inną wartość (rok, `Path=/`, `SameSite=Lax`, `Secure` przez HTTPS), a gdy różni się od wykrytej, podmienia `detected.timeZone` we wpisie w cache przez `setQueryData`. Użytkownik bez zapisanej strefy od razu widzi strefę przeglądarki, a następne żądanie wykrywa ją z ciasteczka.
- Gdy sesja przełącza się na innego użytkownika, `clearCacheOnUserChange` zachowuje wpis i go unieważnia, więc zastępują go wartości zapisane przez nowego użytkownika (zobacz [TanStack Query](/docs/integrations/tanstack-query#preferencje-wyświetlania)).
- Zapisanie preferencji unieważnia każde zapytanie w cache, co opisano niżej.

### Kontekst i hooki

`TranslationsProvider` przekazuje `IntlProvider` ustaloną `timeZone` i renderuje wewnątrz niego `DisplayPreferencesContext` z `src/hooks/use-display-format.ts`, z ustalonym `{ formatLocale, timeZone }`. Czytają go hooki z tego samego pliku:

| Hook                      | Zwraca                                                                                                |
| ------------------------- | ----------------------------------------------------------------------------------------------------- |
| `useDisplayPreferences()` | `{ formatLocale, timeZone }`; poza kontekstem język strony i strefę czasową `IntlProvider` albo `UTC` |
| `useFormatLocale()`       | Format, dla kodu, który formatuje sam, na przykład `formatPrice(amount, currency, formatLocale)`      |
| `useDisplayTimeZone()`    | Strefę czasową                                                                                        |
| `useFormatter()`          | `createFormatter({ locale: formatLocale, timeZone })` z `use-intl`, zapamiętany dla obu wartości      |

Kod aplikacji formatuje przez ten `useFormatter`. Własny `useFormatter` z `use-intl` formatowałby w języku strony, bo czyta `locale` z `IntlProvider`.

### Na serwerze

`resolveRequestDisplayPreferences()`, `createServerOnlyFn` z `i18n.display-preferences.ts`, wykonuje te same odczyty dla bieżącego żądania i zwraca ustalone `{ formatLocale, timeZone }`. Funkcje serwerowe wywołują ją, gdy ich odpowiedź zależy od tego, gdzie zaczyna się dzień, albo zawiera datę lub etykietę, którą formatują same: strony zamówień, klientów i produktów w panelu oraz ich eksporty, lista dziennika zdarzeń i jej licznik dzisiejszych wpisów, migawka i zakres wykresów panelu, szczegóły klienta oraz zapisane karty na stronie płatności w koncie, których ważność ocenia. Testy przypadków użycia mockują `i18n.display-preferences.ts` modułem `src/platform/testing/mocks/display-preferences.ts`, którego `resolveRequestDisplayPreferences` odpowiada `pl-PL` i `Europe/Warsaw`.

### Zapisanie preferencji

`updateDisplayPreference` w `src/modules/user/use-cases/update-display-preference.ts` to funkcja serwerowa `POST` za `withRateLimit("update-display-preference", RATE_LIMITS.SENSITIVE)`, trzy wywołania na minutę, i `authorized()`, więc każdy zalogowany użytkownik może zmienić swój wiersz i tylko swój. `userZodSchemas.displayPreferenceInput` przyjmuje `{ preference: "formatLocale" | "timeZone", value }`, gdzie `value` to `""` dla opcji Automatycznie, zapisywane jako `NULL`, albo wartość, którą `toFormatLocale` zwraca bez zmian lub którą przyjmuje `isTimeZone`. Better Auth deklaruje obie kolumny z `input: false`, więc jego własne endpointy nie mogą ich zapisać.

Wyborem jest `DisplayPreferenceField` z `src/presentation/components/custom/display-preferences/`. `useDisplayPreferenceOptions` wymienia najpierw opcję Automatycznie, opisaną wykrytą wartością, potem osiemnaście `FORMAT_LOCALES`, każdy z przykładową datą i liczbą, albo każdą strefę z `TIMEZONES`, a do tego zapisaną wartość, której nie ma na liście. `useSaveDisplayPreference` wysyła wybór, a po sukcesie wywołuje `queryClient.invalidateQueries()` bez filtra, więc każde zapytanie, którego wynik datowano lub sformatowano poprzednią wartością, jest pobierane ponownie.

## Poza Reactem

E-maile i webhooki renderują się na Workerze bez dostawcy, więc używają `createTranslator({ locale, messages })` z `use-intl` bezpośrednio. Zobacz [Resend](/docs/integrations/resend).

## Inne adaptery świadome języka

| Adapter                                                        | Co mapuje                                                                |
| -------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `src/integrations/stripe/stripe.client.ts`                     | `pl-PL` → `pl`, `en-US` → `en` dla Stripe Elements                       |
| `src/integrations/react-day-picker/react-day-picker.locale.ts` | `pl-PL` → `pl`, `en-US` → `enUS` dla kalendarza                          |
| `src/integrations/fumadocs/fumadocs.i18n.ts`                   | Przekazuje `I18N.SUPPORTED_LOCALES` do Fumadocs z `hideLocale: "always"` |

Pierwsze dwa używają `satisfies Record<SupportedLocale, …>` i jawnego `Record<SupportedLocale, …>`, więc nowy język psuje budowanie do momentu wypełnienia obu mapowań. `fumadocs.i18n.ts` rozwija `I18N.SUPPORTED_LOCALES` do `languages`, więc przyjmuje nowy język bez zmian, a strona bez pliku MDX w tym języku wraca do `pl-PL` (`fallbackLanguage`).

## Treści tłumaczone w bazie danych

Teksty katalogu nie znajdują się w plikach komunikatów. `product.titles`, `product.subtitles`, `product.descriptions` i `product.tags` to kolumny JSON przechowujące mapę językową kluczowaną znacznikiem BCP 47, podobnie jak ich odpowiedniki w `product_category`, `product_collection` i `product_attribute`. Migracja `20260925000000_locale_maps_bcp47.sql` przeniosła te klucze na pełne znaczniki. Formularze katalogu w panelu edytują oba języki obok siebie — `catalog-locale-picker.tsx` i `product-form-locale-layout.tsx` iterują `I18N.SUPPORTED_LOCALES` i pokazują, ile jest wypełnionych. Trzy strony prawne dla klientów działają tak samo: każdy wiersz `content_page` trzyma `titles`, `descriptions` i `bodies` w Markdownie jako mapy językowe, a `/admin/content/$handle` edytuje je w osobnej zakładce dla każdego języka. Metoda dostawy trzyma nazwę tak samo, w `delivery_method.names`, które Ustawienia → Dostawa edytują polem dla każdego języka.

## Nie ma przełącznika języka

Warto to wiedzieć, zanim zaczniesz go szukać: sklep nie ma kontrolki zmiany języka. Nic w `src/presentation` nie wywołuje `localizePathname`, aby zbudować przełącznik, a nawigacja i stopka go nie oferują. Odwiedzający trafia na wersję angielską adresem, a ciasteczko następnie ją pamięta. Odnośniki `hreflang` emitowane z `__root.tsx` informują wyszukiwarki o wersji angielskiej. Jeśli przełącznik będzie potrzebny, `localizePathname` i `getCurrentPathname` to dwie funkcje, z których należy go zbudować.

## Testy

Katalog `src/integrations/use-intl/__test__/` zawiera osiem plików obejmujących ustalanie języka na serwerze, ustalanie języka na kliencie, ustalanie ścieżki na kliencie, reguły routingu i kanonizacji, pomocniki nawigacji, drzewo komunikatów, reguły preferencji wyświetlania w `i18n.display.ts` oraz funkcję serwerową, ustalanie po stronie serwera i zapytanie z `i18n.display-preferences.ts`.
