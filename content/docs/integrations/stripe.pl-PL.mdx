Stripe jest jedynym dostawcą płatności. Sklep pobiera opłaty w PLN, a płatność odbywa się wewnątrz sklepu przy użyciu wbudowanych Checkout Elements od Stripe — klient nigdy nie opuszcza strony `/checkout`. Wiersz zamówienia tworzony jest dopiero wtedy, gdy Stripe zgłosi płatność: przez webhook albo przez stronę powrotu, gdy Stripe już zgłasza sesję jako opłaconą (`getOrderConfirmation` wywołuje `fulfillReturnedCheckoutSession`, które uruchamia `createOrderFromPaidSession`). Do tego momentu dane żyją w wierszu `checkout` oraz wierszu `payment` w stanie `pending`, przy zarezerwowanym stanie magazynowym.

## Klient serwerowy

```ts
export const stripe = new StripeServer(env.STRIPE_SECRET_KEY, {
  apiVersion: STRIPE_API_VERSION,
  appInfo: { name: APP_NAME },
  httpClient: StripeServer.createFetchHttpClient(),
})
```

`createFetchHttpClient()` jest wymagane: klient HTTP z Node nie istnieje na Workerach. `STRIPE_API_VERSION` jest przypięte w `stripe.constants.ts` do `"2026-09-30.endive"`, wersji, którą przypina `stripe` 23.0.0. Jego zmiana oznacza ponowne przeczytanie kształtu każdego ładunku webhooka i ponowne utworzenie endpointów webhooka w nowej wersji (zobacz [Wersja API endpointów webhooka](#wersja-api-endpointów-webhooka)).

## Stałe

```ts
export const CHECKOUT_PAYMENT_METHOD_ORDER = ["card", "blik", "p24"] as const

const STRIPE_CURRENCY_BY_CODE = { PLN: "pln" } as const satisfies Record<SupportedCurrencyCode, string>

export const STRIPE_CURRENCY = STRIPE_CURRENCY_BY_CODE[STORE_CURRENCY_CODE]
```

BLIK i Przelewy24 stoją obok karty, ponieważ tego oczekują polscy klienci; klauzula `satisfies` sprawia, że dodanie waluty do `SupportedCurrencyCode` w `src/modules/_core/constants/currency.ts` bez dodania tu kodu Stripe jest błędem typowania. `STRIPE_WEBHOOK_EVENTS` wylicza dziesięć zdarzeń, które obsługuje aplikacja.

## Klient przeglądarkowy

Plik `stripe.client.ts` leniwie ładuje Stripe.js raz na stronę i mapuje język aplikacji na własny język Stripe:

```ts
const STRIPE_LOCALES = { "en-US": "en", "pl-PL": "pl" } as const satisfies Record<SupportedLocale, StripeElementLocale>
```

Czyta `import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY`, ostrzega w konsoli, jeśli klucza brakuje, i memoizuje obietnicę `loadStripe` w `stripeRef` na poziomie modułu, więc zmiana języka nie przeładowuje skryptu. Odrzucone pobranie znika ze `stripeRef`, więc następne wywołanie pobiera Stripe.js od nowa, zamiast zwracać ten sam błąd aż do przeładowania strony; to wywołanie wykonuje przycisk **Spróbuj ponownie** w kroku płatności. `stripeJsQuery(locale)` opakowuje `getStripe` w opcje zapytania z kluczem `STRIPE_QUERY_KEYS.JS` i językiem oraz z `retry: false`, dla komponentu, który podczas pobierania skryptu lub po błędzie musi pokazać własny stan; korzysta z niego formularz karty na stronie konta. Ponieważ `stripeRef` zachowuje język pierwszego wywołania, eksportowane jest też `toStripeLocale`: formularz karty na stronie konta przekazuje `locale: toStripeLocale(locale)` do własnego `Elements`, więc mówi w bieżącym języku klienta.

## Dwie funkcje serwerowe

Plik `stripe.actions.ts` udostępnia dokładnie dwa punkty wejścia, oba z limitem dziesięciu wywołań na 60 sekund i oba leniwie importujące ciężki moduł serwerowy:

```ts
export const createCheckoutSessionFn = createServerFn({ method: "POST" })
  .middleware([withRateLimit("checkout-create", RATE_LIMITS.CHECKOUT)])
  .validator((data: unknown) => createCheckoutSessionInputSchema.parse(data))
  .handler(async ({ data }) => {
    const { handleCreateCheckoutSession } = await import("~/src/integrations/stripe/stripe.actions.server")

    return handleCreateCheckoutSession(data)
  })
```

Plik `stripe.actions.schemas.ts` definiuje ładunek: `{ checkoutValues: checkoutSchema, items: cartItemSchema[] }` z co najmniej jedną i co najwyżej `CART_LINES_MAX` pozycjami (`src/modules/cart/cart.constants.ts`) oraz `sessionId` w wariancie aktualizacji. `CART_LINES_MAX` to `STRIPE_CHECKOUT_LINE_ITEMS_MAX` pomniejszone o linię wysyłki, bo Checkout Session w trybie płatności przyjmuje najwyżej 100 pozycji. Każda ilość musi być liczbą całkowitą od 1 do `CART_LINE_QUANTITY_MAX` (10), czyli najwyższej liczby sztuk jednego produktu w zamówieniu. Pozycja niesie tylko `slug` produktu (najwyżej `PRODUCT_COLUMN_LENGTH.handle`, czyli 255 znaków), `variantId` (najwyżej `PRODUCT_VARIANT_COLUMN_LENGTH.id`, czyli 36) i `qty`; wszystko inne, co pamięta linia koszyka, jak tytuł, zdjęcie czy cena, jest odrzucane. `sessionId` wariantu aktualizacji ma najwyżej `CHECKOUT_SESSION_ID_MAX_LENGTH` (255) znaków, tak jak parametr `session_id` strony checkoutu. `checkoutSchema` pochodzi z `src/modules/checkout/checkout.zod.ts`, więc reguły adresu, dostawy i danych do faktury walidowane są w dokładnie jednym miejscu.

## Tworzenie sesji

Funkcja `handleCreateCheckoutSession` w `stripe.actions.server.ts` najpierw wywołuje `admitNewCheckout`, które w dwóch przypadkach odrzuca żądanie, zanim dotknie klienta Stripe, katalogu, rabatu czy stanu magazynowego. `assertSalesOpen()` odczytuje `store_setting.sales_paused` przez `isSalesPaused()` i, dopóki sprzedaż jest wstrzymana, odrzuca żądanie z `CONFLICT` i `SALES_PAUSED` (zobacz [Kasa: wstrzymanie sprzedaży](/docs/features/checkout#wstrzymanie-sprzedaży)). `countOpenCheckouts` odrzuca z `TOO_MANY_REQUESTS` i `TOO_MANY_OPEN_CHECKOUTS`, gdy adres klienta żądania ma już pięć otwartych checkoutów albo jego e-mail trzy (zobacz [Kasa: limity trzymania towaru](/docs/features/checkout#limity-trzymania-towaru)). W przeciwnym razie wykonuje następującą sekwencję:

1. `resolveDelivery(checkoutValues)` odczytuje wybraną metodę przez `getOfferedDeliveryMethodByIdQuery`, który znajduje tylko metodę włączoną i niezarchiwizowaną, której przewoźnik jest aktywny, czyli według reguły, którą listuje krok dostawy, i w tym samym batchu odczytuje próg darmowej dostawy. Wszystko inne dostaje odmowę `DELIVERY_METHOD_UNAVAILABLE`, zanim padnie wywołanie Stripe, więc wycofana albo zmyślona metoda nie wysyła już za darmo. Gdy `type` metody w bazie to `locker`, żądanie potrzebuje `lockerId` w kształcie nazwy punktu InPost, inaczej dostaje odmowę `LOCKER_REQUIRED`, a InPost jest pytany, czy taki punkt istnieje: punkt, którego nie ma na liście, dostaje odmowę `LOCKER_NOT_FOUND`, a gdy InPost nie odpowie w ciągu trzech sekund, paczkomat zostaje przyjęty, a checkout oznaczony `locker_unconfirmed`, by sklep go sprawdził (zobacz [InPost](/docs/integrations/inpost#jak-to-trafia-na-zamówienie)). Punkt potwierdzony przez InPost zostaje zachowany jako `lockerPoint`, czyli jego adres i opis zserializowane przez `serializeInpostLockerPoint`. Dla każdego innego typu `lockerId` jest porzucany. Kosztem dostawy jest `price` metody albo zero, gdy produkty, pomniejszone o kod obniżający ich cenę, osiągną próg darmowej dostawy (`resolveDeliveryPrice`, zobacz [Wysyłka i dostawa: Darmowa dostawa](/docs/features/shipping-and-delivery#darmowa-dostawa)).
2. `validateAndCalculateItems(items)` ładuje produkty wraz ze stanem magazynowym po identyfikatorze `handle`, tylko te o statusie `published` (`getPublishedProductsWithInventoryByHandles`), rozwiązuje każdy wariant i **czyta cenę z bazy** — `cartItemSchema` nie ma `price` ani `rawPrice`, więc cena z koszyka w ogóle nie dociera do handlera. Odrzuca z błędem `PRODUCT_NOT_FOUND`, którym kończy się też próba zakupu produktu zarchiwizowanego albo przywróconego do szkicu, gdy leżał w koszyku, `VARIANT_NOT_FOUND`, `INVALID_PRICE` (przez `isSellPriceCentsValid`) lub `INSUFFICIENT_INVENTORY`, a zwraca każdą pozycję z `inventoryId` oraz z nazwą, `handle` i zdjęciem wziętymi z wczytanych wierszy katalogu, których zdjęcia przychodzą w tym samym zapytaniu, a nigdy z żądania. Następnie `toCheckoutLines` zamienia następnie wycenione pozycje w koszyk, który przechowuje wiersz płatności sesji (zobacz [Sesja wskazuje checkout, koszyk trzyma baza danych](#sesja-wskazuje-checkout-koszyk-trzyma-baza-danych)).
3. `resolveCheckoutDiscount(...)` ponownie sprawdza `checkoutValues.discountCode` względem sumy cen z bazy i kosztu dostawy przed jakimkolwiek kodem; kod, który nie obowiązuje, jest pomijany. Zobacz [Rabaty](/docs/features/discounts).
4. `reserveInventoryForItems(lines)` zajmuje stan magazynowy instrukcją `UPDATE` warunkowaną `quantity_available >= qty`, więc udaje się zawsze, gdy w tej chwili zostało dość towaru, niezależnie od tego, ile innych checkoutów zarezerwowało ten sam wariant od kroku 2. Gdy inny checkout zajął w tym czasie ostatnie sztuki, odmawia z `CONFLICT` i `INSUFFICIENT_INVENTORY`, tak jak krok 2, więc kupujący widzi komunikat o braku towaru.
5. `createCheckout({ checkoutValues, clientAddress, discountId, lockerPoint, lockerUnconfirmed, userEmail, userId })` zapisuje wiersze adresów i wiersz `checkout` z adresem klienta, według którego liczony jest limit otwartych checkoutów, z `locker_point` potwierdzonego paczkomatu i z informacją, czy InPost potwierdził jego paczkomat, a z kodem w tym samym wsadzie rezerwuje jedno jego wykorzystanie w `discount_claim` i ustawia `discount_id` tylko wtedy, gdy rezerwacja została zapisana. Kod, którego pozostałe wykorzystania trzymają inne otwarte checkouty, jest tu pomijany, a sesja powstaje w pełnej cenie. Jeśli krok 6 albo 7 się nie uda, `releaseDiscountClaims` oddaje wykorzystanie razem z towarem. Zobacz [Rabaty: utrzymanie wykorzystania na czas płatności](/docs/features/discounts#utrzymanie-wykorzystania-na-czas-płatności).
6. `createStripeSession(...)` tworzy sesję Stripe Checkout, wygasającą `CHECKOUT_SESSION_LIFETIME_SECONDS` (32 minuty) od teraz, a nie po domyślnych 24 godzinach Stripe, z jednorazowym kuponem, gdy obowiązuje rabat. Jeśli Stripe odmówi utworzenia sesji, kupon jest usuwany, zanim błąd pójdzie dalej.
7. `createPendingPayment(...)` zapisuje wiersz `payment` z `provider: "stripe"`, `currency: "PLN"`, `transactionId` ustawionym na identyfikator sesji Stripe, `lines` z wycenionym koszykiem z kroku 2 i `reservedLines` z liniami zarezerwowanymi w kroku 4.
8. `scheduleProductCatalogInvalidation()` wypycha nową dostępność do podłączonych sklepów.

Jeśli cokolwiek po kroku 4 rzuci wyjątek, handler zwalnia rezerwację przez `releaseInventoryForItems(lines)` i rzuca dalej. Ta kompensacja jest powodem, dla którego nieudana próba płatności nie zostawia zablokowanego towaru.

Sama sesja:

```ts
const params: StripeType.Checkout.SessionCreateParams = {
  expires_at: Math.floor(Date.now() / MILLISECONDS_PER_SECOND) + CHECKOUT_SESSION_LIFETIME_SECONDS,
  line_items: toLineItems(lines, { cost: shippingCost, name: messages.deliveryLineItem[deliveryType] }),
  metadata,
  mode: "payment",
  payment_intent_data: { description: messages.paymentDescription, metadata, receipt_email: email },
  phone_number_collection: { enabled: true },
  return_url: returnUrl,
  ui_mode: "elements",
  ...(customerId === undefined
    ? { customer_email: email }
    : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
}
const discounts = await toSessionDiscounts({ checkoutId, discount })
if (discounts.length > NO_COST) {
  params.discounts = discounts
}

const session = await stripe.checkout.sessions.create(params).catch(async (error: unknown) => {
  await deleteCheckoutCoupons({ checkoutId, discounts })
  throw error
})
```

`customerId` jest ustawiane tylko dla zalogowanego kupującego: po kroku 1, a przed krokiem 2, `handleCreateCheckoutSession` wywołuje `ensureStripeCustomerWithEmail` (`stripe.customer.server.ts`) z adresem e-mail wpisanym w formularzu kasy. Przy pierwszym użyciu tworzy ono klienta Stripe z tym adresem i zapisuje jego identyfikator w `user.stripe_customer_id`, a dla konta, które ma już klienta, wywołuje `stripe.customers.update(customerId, { email })`. Ta aktualizacja utrzymuje Stripe w zgodzie z zamówieniem. Sesję utworzoną z `customer` Stripe wypełnia adresem e-mail klienta, nie pozwala kupującemu go zmienić i zwraca go jako `customer_details.email`; `customer_email` ustawia tylko adres klienta, którego Checkout tworzy sam, a `customer_update` może zapisać u klienta adres, imię i nazwisko oraz dane wysyłki, ale nie e-mail. Bez tej aktualizacji klient utworzony przy wcześniejszym zakupie albo na stronie konta zachowałby stary adres, a e-mail rozliczeniowy płatności i zapis płatnika w Stripe używałyby tego starego adresu, podczas gdy zamówienie i potwierdzenie płatności od Stripe (`receipt_email`) miałyby adres wpisany przez kupującego. Stripe bierze adres klienta taki, jaki jest w chwili potwierdzenia płatności, a nie przy tworzeniu sesji: `customer_details.email` i e-mail rozliczeniowy metody płatności idą za zmianą wprowadzoną u klienta, gdy sesja jest otwarta. Dwa checkouty, które jedno konto trzyma otwarte jednocześnie, w dwóch przeglądarkach i z różnymi adresami, mają wspólnego klienta, więc ten opłacony później zostaje rozliczony na adres sesji utworzonej lub zaktualizowanej jako ostatnia. Własne e-maile sklepu za nim nie idą: potwierdzenie zamówienia trafia na adres zamówienia, a e-mail o nieudanej płatności na adres checkoutu (zobacz [E-maile transakcyjne](/docs/features/email)), a `fulfillCheckout` zapisuje `order.placed` z adresem checkoutu. Sesja należy do tego klienta Stripe i pozwala kupującemu zapisać kartę, którą potem wyświetla `/account/payment`. Sesja gościa dostaje zamiast tego `customer_email`. `handleUpdateCheckoutSession` wywołuje `ensureStripeCustomerWithEmail` tak samo przy każdym zalogowanym żądaniu, z poprawionym adresem e-mail: dla checkoutu, który już należy do konta, co przenosi jego klienta na ten adres, i gdy przekazuje checkout gościa kontu, na które od tego czasu się zalogowano (zobacz [Aktualizacja sesji](#aktualizacja-sesji)). `ensureStripeCustomerWithEmail` i opisane niżej `ensureStripeCustomer` tworzą klienta tymi samymi krokami: zapisują nowy identyfikator przez `coalesce`, a żądanie, które zastanie już zapisany inny identyfikator, usuwa właśnie utworzonego klienta, więc równoległe pierwsze żądania kończą się jednym klientem. Drugim wywołującym jest strona konta: `createCardSetupIntent` wywołuje `ensureStripeCustomer`, które tworzy klienta z adresem e-mail konta, gdy go nie ma, a w przeciwnym razie zostawia adres ustawiony przez ostatni checkout, i otwiera dla tego klienta SetupIntent na kartę, który `stripe.confirmSetup` potwierdza w przeglądarce. Usunięcie konta wywołuje `deleteStripeCustomer`, które usuwa tego klienta, a razem z nim zapisane karty, przez `stripe.customers.del` i czyści `user.stripe_customer_id`; odpowiedź `resource_missing` liczy się jako usunięcie, a każdy inny błąd zostawia konto. Zobacz [Konto](/docs/features/account) i [Usunięcie konta](/docs/features/account#usunięcie-konta).

`ui_mode: "elements"` daje wbudowane doświadczenie płatności. `return_url` to `${origin}/checkout?success=true&session_id={CHECKOUT_SESSION_ID}`, gdzie Stripe wstawia identyfikator sesji, a `origin` to `resolveRequestOrigin(getRequest())`: adres, na który przyszło żądanie checkoutu, odrzucany z `FORBIDDEN`, jeśli nie jest jednym z hostów obsługiwanych przez ten build. Zobacz [Model bezpieczeństwa](/docs/architecture/security-model). Strona sukcesu używa `session_id`, aby wczytać zamówienie przez `getOrderConfirmationQuery`, a dopóki płatność sesji jest `pending`, jego funkcja serwerowa pobiera sesję i składa zamówienie sesji, którą Stripe zgłasza jako opłaconą, zanim dotrze webhook (zobacz [Płatności: realizacja ze strony powrotu](/docs/features/payments#realizacja-ze-strony-powrotu)). Koszt dostawy dodawany jest jako dodatkowa pozycja, a nie jako stawka wysyłki Stripe, i tylko wtedy, gdy jest większy od zera, więc darmowa dostawa nie zostawia pozycji. Jej nazwa pochodzi z `deliveryLineItem` w `pages.checkout` według typu metody dostawy, w języku kupującego, więc ta pozycja na potwierdzeniu płatności Stripe jest w języku checkoutu. Rabat trafia do `discounts`: dla każdej sesji, która go ma, `toSessionDiscounts` (`stripe.coupons.server.ts`) wywołuje `stripe.coupons.create` z `amount_off: discount.amountMinorUnits`, `currency: STRIPE_CURRENCY`, `duration: "once"`, `metadata: { checkoutId, source: STRIPE_COUPON_SOURCE }` i `name: discount.code`. Po tych metadanych `deleteCheckoutCoupons` rozpoznaje kupony, które może usunąć: usuwa kupon sesji tylko wtedy, gdy kupon niesie `source: "marte_checkout"` i `checkoutId` tej samej sesji, a każdy inny kupon na koncie zostawia w spokoju. Kiedy to się dzieje, opisuje strona [Rabaty](/docs/features/discounts).

### Co widzi bank kupującego

`payment_intent_data.description` to `paymentDescription` z `pages.checkout` w języku checkoutu: „M'Arte – zamówienie w sklepie internetowym” albo „M'Arte – online shop order”. Według przewodnika Stripe po BLIK-u ten tekst wypełnia dwa pierwsze z czterech wierszy, które aplikacja bankowa pokazuje, prosząc kupującego o zatwierdzenie płatności, do 70 znaków, a test pilnuje, żeby oba tłumaczenia się w tym mieściły; przewodnik nie mówi, co te wiersze pokazują bez opisu. Czwarty wiersz to adres strony sklepu, który Stripe uzupełnia sam. Tekst nazywa sklep, ale nie produkty, bo płatność za prezent może trafić do historii konta, którą czyta ktoś inny, i nie zawiera numeru zamówienia, bo zamówienie i jego numer powstają dopiero po udanej płatności. Opis widać też przy płatności w panelu Stripe.

Sesja nie ustawia `statement_descriptor`: Stripe odrzuca go przy płatności kartą, a sesja oferuje karty obok BLIK-a i Przelewy24. Na wyciągu bankowym płatność BLIK-iem albo przez Przelewy24 pokazuje więc deskryptor wyciągu konta, przy przelewie Przelewy24 po numerze referencyjnym P24, a wyciąg karty zaczyna się od skróconego deskryptora konta albo od deskryptora wyciągu przyciętego do 10 znaków. Przewodnik po BLIK-u umieszcza deskryptor w trzecim wierszu zatwierdzenia tylko wtedy, gdy płatność go przekazuje, i nie mówi, co ten wiersz pokazuje w przeciwnym razie. Dla kart nie jest ustawiany także `statement_descriptor_suffix`, bo jedyną wartością właściwą dla zamówienia, znaną w chwili tworzenia sesji, jest identyfikator checkoutu, którego kupujący nigdy nie widzi. Oba deskryptory ustawia się w danych firmy w panelu Stripe (`dashboard.stripe.com/settings/business-details`), literami łacińskimi i bez `'`, czyli jako „MARTE BIZUTERIA”, a nie „M'Arte” (zobacz [Lista kontrolna przed startem sprzedaży](/docs/guides/go-live-checklist)).

### Sesja wskazuje checkout, koszyk trzyma baza danych

`metadata` sesji niesie `checkoutId`, `deployment`, `discountCode`, `discountTotal`, `locale`, `shippingTotal` i `userId`, opisane typem `CheckoutPaymentMetadata`, a PaymentIntent dostaje te same siedem pól, więc webhook, który ma tylko intent, wciąż znajdzie checkout. Sprawdzenie wdrożenia w webhooku i `payment_intent.payment_failed` czytają `deployment` i `checkoutId`, a realizacja zamówienia czyta `discountTotal` i `shippingTotal`.

Koszyk nie trafia do Stripe. Zostaje w wierszu płatności sesji w D1, zapisany przy otwarciu sesji i przy edycji, która ją zastępuje, a realizacja zamówienia, potwierdzenie zamówienia i e-mail o nieudanej płatności odczytują go po identyfikatorze sesji (zobacz [Kasa: koszyk w wierszu płatności](/docs/features/checkout#koszyk-w-wierszu-płatności)). Limit Stripe wynoszący 50 kluczy metadanych po najwyżej 500 znaków nie ogranicza więc już liczby produktów w jednej płatności. Sesja otwarta przed tą zmianą wciąż niesie koszyk w `items` albo `items0`, `items1`, …, który jest wtedy czytany. `discountCode` nie jest odczytywany z powrotem. `shippingTotal` i `discountTotal` są, jako opłata za dostawę i rabat w jednostkach podrzędnych: odczytują je `resolveCheckoutSessionShippingTotal` i `resolveCheckoutSessionDiscountTotal` (`checkout-metadata.zod.ts`), a realizacja zapisuje je jako koszt dostawy i rabat zamówienia, więc cena metody, próg darmowej dostawy albo kod rabatowy zmienione w trakcie płatności nie zmieniają tego, co zamówienie podaje jako pobraną kwotę. Sesja otwarta, zanim te pola istniały, albo taka, której wartość nie jest liczbą całkowitą, sięga po obecną cenę metody dostawy checkoutu i po rabat przeliczony na podstawie `discount_id` checkoutu.

## Aktualizacja sesji

Gdy zmieni się koszyk lub formularz, klient nie tworzy drugiej sesji — aktualizuje istniejącą. `stripe.checkout.ts` decyduje o tym na podstawie dwóch odcisków:

```ts
export const buildCheckoutLinesFingerprint = (lines: readonly CheckoutSessionLine[]): string =>
  lines
    .map((line) => `${line.variantId}:${line.qty}:${line.unitPrice}`)
    .toSorted((left, right) => left.localeCompare(right))
    .join("|")

export const buildCheckoutValuesFingerprint = (values: CheckoutFormSchema): string =>
  JSON.stringify(Object.fromEntries(Object.entries(values).toSorted(([left], [right]) => left.localeCompare(right))))
```

`ensureCheckoutSession` przyjmuje sesję z ekranu oraz `heldSessionId`, czyli identyfikator, który przeglądarka zapisała dla swojej otwartej sesji. Kontynuuje trzymaną sesję albo tę z ekranu, gdy nic nie zapisano, wywołując `updateCheckoutSessionFn`, gdy zmienił się którykolwiek odcisk albo gdy trzymana sesja nie jest tą z ekranu, a tworzy sesję tylko wtedy, gdy przeglądarka żadnej nie trzyma. Dzięki temu odświeżenie, druga karta czy powrót z koszyka zastępują otwartą sesję, zamiast ponownie rezerwować koszyk. Zanim do tego dojdzie, strona kasy pyta `getCheckoutSessionStatus`, czy zapisana sesja jest nadal otwarta, i pokazuje potwierdzenie sesji opłaconej, zamiast dochodzić do tej aktualizacji (zobacz [Kasa](/docs/features/checkout)). `isCheckoutSessionFor` buduje odcisk linii sesji z `lines` wycenionych przez serwer, a odcisk koszyka z jego aktualnych cen, więc cena zmieniona przez sklep, którą sprawdzenie dostępności zapisuje w koszyku, również zastępuje sesję. `resetCheckoutSession` wymusza aktualizację trzymanej sesji — interfejs korzysta z tego po odrzuconej płatności i wtedy, gdy kupujący ponawia płatność, której sesja wygasła. Każda zwrócona sesja zachowuje `lines` i `totals` z serwera, z których podsumowanie kasy i koszyk biorą ceny, oraz niesie `expiresAt`, `CHECKOUT_SESSION_LIFETIME_SECONDS` od chwili odebrania, z którego krok płatności korzysta, by pokazać, że sesja wygasła.

Po stronie serwera `handleUpdateCheckoutSession` jest najdelikatniejszą funkcją w bazie kodu:

1. `getPaymentContextByTransactionId(sessionId)` odnajduje `checkout`, właścicielski `userId`, czas utworzenia checkoutu oraz statusy checkoutu i jego płatności. Sesja należąca do zalogowanego użytkownika może być aktualizowana tylko przez tego użytkownika, w przeciwnym razie `FORBIDDEN` z powodem `SESSION_CLOSED`, więc przeglądarka po wylogowaniu zaczyna własny checkout. Checkout gościa może kontynuować każdy, kto zna identyfikator jego sesji, a gdy to żądanie jest zalogowane, jak wtedy, gdy gość dochodzi do kroku płatności, a potem się loguje, aktualizacja przekazuje checkout temu kontu: zastępcza sesja niesie w metadanych `userId` konta i jego klienta Stripe z `ensureStripeCustomerWithEmail`, a krok 4 ustawia `user_id` checkoutu. Zamówienie trafia wtedy na konto, kupujący zachowuje towar trzymany przez sesję gościa, a zapisane karty są proponowane. Nieznany identyfikator sesji jest odrzucany z `NOT_FOUND`, a checkout lub płatność, które nie są już `pending` i nie zostały opłacone, z `CONFLICT`, oba z powodem `SESSION_CLOSED`. Płatność `succeeded` albo `refunded` jest zamiast tego odrzucana z `CONFLICT` i powodem `SESSION_COMPLETE`, jeszcze przed sprawdzeniem własności, bo strona potwierdzenia i tak pokazuje to zamówienie każdemu, kto ma identyfikator sesji.
2. Stara sesja Stripe jest pobierana z rozwiniętym payment intentem. Sesja, której płatność według `isCheckoutSessionProcessing` (`stripe.utils.ts`) jest w toku, jest odrzucana najpierw, z `SESSION_PROCESSING`, więc jej zastąpienie nigdy nie anuluje płatności, którą bank może jeszcze dokończyć: sesja `open`, której payment intent jest `processing` albo jest płatnością BLIK czekającą na zatwierdzenie w aplikacji banku (`requires_action` z `blik_authorize`), oraz sesja `complete`, której `payment_status` to wciąż `unpaid`, co zostawia tylko metoda z opóźnionym powiadomieniem, a żadna z metod sklepu nią nie jest (zobacz [Płatności: Waluta i metody](/docs/features/payments#waluta-i-metody)). Każda inna sesja `complete`, opłacona, zanim dotarł jej webhook, jest odrzucana z `SESSION_COMPLETE`, a każdy inny status niż `open` z `SESSION_CLOSED`. Gdy status to `expired`, `releaseExpiredCheckoutSession` najpierw uruchamia `releaseCheckout`, który oddaje linie sesji, strzeżony tak samo jak zwolnienie z webhooka wygaśnięcia, więc towar jest wolny dla nowego checkoutu, który klient otworzy zaraz potem, a webhook, kiedykolwiek dotrze, niczego nie zwalnia. W przeciwnym razie `getHeldLinesByTransactionId` odczytuje trzymane przez nią linie z `reserved_lines` wiersza płatności sesji, dopóki płatność i jej checkout są nadal `pending`. Dopiero wtedy, gdy wiadomo, że sesja jest otwarta, `assertSalesOpen()` odrzuca aktualizację z `SALES_PAUSED`, dopóki sprzedaż jest wstrzymana, więc stara sesja, jej towar i rezerwacja kodu zostają bez zmian, a sesja opłacona przed wstrzymaniem nadal odpowiada `SESSION_COMPLETE`. Potem `assertCheckoutStillEditable` odrzuca z `SESSION_CLOSED` checkout utworzony `CHECKOUT_SESSION_LIFETIME_SECONDS` temu lub dawniej, bo każda aktualizacja daje sesji zastępczej nową rezerwację, a zmiana nie wlicza się do limitów otwartych checkoutów: `stripe.checkout.sessions.expire` najpierw zamyka otwartą sesję, a wygaszona sesja przechodzi przez `releaseExpiredCheckoutSession`, więc nowy checkout, który znów wlicza się do limitów, zastaje jej towar wolny. Jeśli Stripe nie chce jej wygasić, błąd jest przekazywany dalej, a towar zostaje przy sesji. Sesja z płatnością w toku nigdy nie dochodzi do tego sprawdzenia, więc te 32 minuty nigdy nie wygaszają płatności, którą bank wciąż potwierdza.
3. `validateAndCalculateItems` sprawdza edytowany koszyk względem dostępnego stanu powiększonego o to, co trzyma stara sesja, które `getHeldLinesByTransactionId` odczytuje z wiersza płatności sesji. Dostawa i rabat są ustalane ponownie, z tymi samymi odmowami co wyżej, a `claimCheckoutDiscount` rezerwuje kod dla checkoutu (checkout, który już go trzyma, zachowuje rezerwację, a kod, którego wykorzystania trzymają inne checkouty, jest pomijany). Potem `handOverCheckoutSession` rezerwuje to, co dokłada edytowany koszyk, czyli `quantitiesBeyond(lines, heldLines)`, przez `reserveInventoryForItems` na identyfikatorach stanu zwróconych przez walidację, i tworzy zastępczą sesję Stripe. Sztuk, które trzyma stara sesja i które edytowany koszyk zatrzymuje, nic nie zwalnia ani nie rezerwuje ponownie, więc żaden inny checkout nie może ich przejąć w trakcie przekazania (zobacz [Stany magazynowe: przeniesienie rezerwacji na sesję zastępczą](/docs/features/inventory#przeniesienie-rezerwacji-na-sesję-zastępczą)). Gdy inny checkout zajął dokładane sztuki od walidacji, rezerwacja kończy się odmową z `CONFLICT` i `INSUFFICIENT_INVENTORY`. Nic poza tym jeszcze się nie zmieniło, więc porażka na tym etapie zostawia starą sesję otwartą, a jej stan zarezerwowany, `releaseInventoryForItems` oddaje to, co dołożono, a `releaseUnappliedDiscountClaims` oddaje rezerwację zrobioną dla innego kodu niż ten z `checkout.discount_id`.
4. `retireCheckoutSession` wygasza starą sesję przez `stripe.checkout.sessions.expire(...)`, żeby nie dało się jej już opłacić, a potem wywołuje `supersedeCheckoutSession`. Ten przypadek użycia jednym wsadem D1 przenosi wiersz `payment` na zastępczą sesję, z kwotą sesji zastępczej, edytowanym koszykiem jako jego `lines` i ilościami edytowanego koszyka jako jego `reserved_lines`, i zwalnia to, z czego edytowany koszyk zrezygnował, czyli `quantitiesBeyond(heldLines, reservedLines)`, tylko dopóki płatność i jej checkout są nadal `pending`. Ten sam wsad usuwa rezerwacje checkoutu dla wszystkich kodów poza tym, który stosuje sesja zastępcza. Gdy żądanie jest zalogowane, ustawia też `user_id` checkoutu na to konto, tylko dopóki checkout jest `pending`, nie ma właściciela, a jego płatność niesie już zastępczą sesję, więc checkout z właścicielem nigdy nie zmienia rąk. Jeśli któryś krok się nie uda albo webhook wygaśnięcia zwolnił checkout wcześniej, zastępcza sesja jest wygaszana, to, co dołożył edytowany koszyk, wraca na stan, a aktualizacja kończy się błędem. Wygaszenie starej sesji wysyła jej webhook `checkout.session.expired`, gdy aktualizacja jeszcze trwa, a `prepareReleaseCheckoutBatch` działa tylko, dopóki płatność sesji i jej checkout są `pending`: zwolnienie zatwierdzone przed przeniesieniem oddaje wszystkie stare linie, oznacza checkout jako nieudany i sprawia, że `supersedeCheckoutSession` odmawia, a zatwierdzone po nim nie znajduje płatności starej sesji, niczego nie zmienia i nie zapisuje wpisu `order.released`. Stare linie nigdy nie są zwalniane dwa razy.
5. `saveReplacementDelivery` aktualizuje dostawę, `discount_id`, `locker_point` oraz `locker_unconfirmed` checkoutu. Jeśli to się nie uda, `releaseCheckout` na zastępczej sesji oznacza checkout jako nieudany i oddaje cały edytowany koszyk, a zastępcza sesja jest wygaszana.

Gdy `updateCheckoutSessionFn` odpowiada `SESSION_CLOSED`, `ensureCheckoutSession` i `resetCheckoutSession` wywołują `createCheckoutSessionFn`, żeby zacząć nowy checkout, zamiast zgłaszać błąd. Gdy odpowiada `SESSION_COMPLETE`, niczego nie otwierają i rzucają `PaidCheckoutSessionError` z identyfikatorem sesji, którą próbowały kontynuować, a krok płatności pokazuje potwierdzenie tej sesji, więc sesja opłacona w chwili między sprawdzeniem sesji na stronie kasy a tą aktualizacją nigdy nie prowadzi do drugiego formularza płatności. Gdy odpowiada `SESSION_PROCESSING`, też niczego nie otwierają i rzucają `ProcessingCheckoutSessionError` (`stripe.checkout.processing.ts`) z identyfikatorem tej sesji, a krok płatności czeka na niej na bank, dopóki `getCheckoutSessionStatus` nie zgłosi jej jako `complete`, znów `open` albo `closed`.

`getCheckoutSessionStatus` (`src/modules/checkout/use-cases/get-checkout-session-status.ts`) odpowiada na pytanie strony kasy o zapisaną albo zwróconą sesję wartością `"complete"`, `"open"`, `"processing"` albo `"closed"`. Najpierw czyta płatność i wywołuje `stripe.checkout.sessions.retrieve`, z rozwiniętym payment intentem, tylko dla płatności `pending`. Sesję, której płatność jest w toku według tego samego `isCheckoutSessionProcessing` co w kroku 2, `open` albo `complete` wciąż `unpaid`, zgłasza najpierw jako `"processing"`, więc `complete` przekazuje dalej tylko dla opłaconej sesji, a `open` bez zmian; sesja `expired` przechodzi przez `releaseExpiredCheckoutSession` dokładnie jak w kroku 2. Opłacona sesja jest `"complete"` dla każdego, kto ma jej identyfikator, tak jak na stronie potwierdzenia. Reguła własności z kroku 1 dotyczy tylko sesji otwartej albo czekającej na bank: żądanie niezalogowane na konto będące właścicielem dostaje zamiast odmowy odpowiedź `"closed"`. Jej limit żądań to `checkout-status`.

`expireCheckoutsHoldingVariants` (`src/modules/checkout/use-cases/expire-checkouts-holding-variants.server.ts`) to trzecie miejsce, które woła `releaseExpiredCheckoutSession`, po kroku 2 i `getCheckoutSessionStatus`. Gdy administrator zapisuje produkt jako szkic albo archiwum, funkcja wygasza przez `stripe.checkout.sessions.expire` każdą otwartą sesję trzymającą któryś z wariantów produktu i przekazuje wygaszoną sesję zwróconą przez Stripe do `releaseExpiredCheckoutSession`, więc webhook `checkout.session.expired`, który przychodzi potem, zastaje sztuki już oddane. Sesja, której Stripe nie wygasi, jest logowana i zostaje bez zmian (zobacz [Panel katalogu](/docs/features/admin-catalog#zapis)).

Zachowaj tę kolejność, gdy będziesz to zmieniać. Wiersz `payment` jest przenoszony, a nie tworzony ponownie, ponieważ migracja `20260924120000_checkout_idempotency_constraints.sql` nakłada unikalny indeks na `payment.transaction_id` (oraz na `order.checkout_id`); wstawienie drugiego wiersza płatności dla zastępczej sesji naruszyłoby go.

## Potwierdzenie w przeglądarce

`confirmCheckoutSession` owija `checkout.confirm({ billingAddress, redirect: "if_required" })` i klasyfikuje wynik:

```ts
export type ConfirmOutcome =
  { status: "declined"; message: string } | { status: "failed"; message: string } | { status: "processing" } | { status: "success" }
```

Potwierdzenie, które przejdzie, daje `success` tylko wtedy, gdy sesja zwrócona przez Stripe jest `complete`, a jej `paymentStatus` nie jest `unpaid`. Wszystko inne daje `processing`, a krok płatności czeka wtedy na bank zamiast otwierać potwierdzenie, więc strona nigdy nie potwierdza sesji, której Stripe nie zgłosił jako opłaconej. Płatność kartą, BLIK-iem albo przez Przelewy24 kończy sesję dopiero wtedy, gdy się powiedzie, więc sesja `complete`, która wciąż jest `unpaid`, mogłaby pochodzić tylko od metody z opóźnionym powiadomieniem. Błąd z kodem `paymentFailed` to `declined`. Każdy inny błąd, który Stripe.js zwraca z kodem `null`, to `failed`, a krok płatności odczytuje wtedy status sesji, zanim zdecyduje, czy zostawić sesję z komunikatem Stripe, czekać na bank, otworzyć potwierdzenie, czy zresetować zamkniętą sesję (zobacz [Kasa](/docs/features/checkout)). `buildCheckoutContact(values)` wybiera adres do faktury, gdy `sameAsShipping === false`, a w przeciwnym razie adres dostawy.

Komponent `PaymentStep` w `src/presentation/components/custom/checkout/components/_steps/payment-step.client.tsx` montuje `CheckoutElementsProvider` kluczowany przez `sessionId` przez `PaymentElementsProvider`, który raz na zamontowanie prosi `getStripe(locale)` o Stripe.js, przekazuje `getStripeAppearance(theme)` oraz `STRIPE_FONTS` i renderuje Payment Element jako akordeon z wyłączonymi portfelami i Link, a `paymentMethodOrder` bierze z `CHECKOUT_PAYMENT_METHOD_ORDER`. Provider trzyma stan błędu, dopóki nie zostanie zamontowany od nowa, a Payment Element zgłasza nieudane wczytanie tylko przez `loaderror`, więc w obu przypadkach krok pokazuje komunikat, że formularz płatności się nie wczytał. Komunikat jest ogłaszany jako alert i przejmuje fokus. Jego przycisk **Spróbuj ponownie** odczytuje status sesji, a dla sesji wciąż otwartej montuje nowy provider, a z nim nowe wywołanie `getStripe`, w kontenerze kluczowanym numerem próby; provider sesji zastępczej robi własne wywołanie, więc nigdy nie dziedziczy nieudanego pobrania (zobacz [Kasa](/docs/features/checkout)). Przycisk płatności wygląda na nieaktywny, dopóki `checkout.canConfirm` nie jest `true`, ale da się go nacisnąć, a naciśnięcie przed tym czasem wywołuje `checkout.validateElements()`, żeby Stripe oznaczył, czego brakuje.

Plik `stripe.appearance.ts` eksportuje `getStripeAppearance("light" | "dark")` — pełny obiekt `Appearance` dla Elements, w płaskim, kanciastym języku wizualnym sklepu opartym na obramowaniach — oraz `STRIPE_FONTS`, arkusz stylów Manrope potrzebny czcionce z wyglądu wewnątrz ramek Stripe. Korzystają z nich zarówno kasa, jak i formularz karty na stronie konta. Jego kolory to dosłowne wartości szesnastkowe odpowiadające tokenom projektowym, więc zmiana tokenu wymaga zmiany także tych wartości.

## Webhooki

Plik `src/routes/api/webhooks.stripe.ts` weryfikuje podpis przed czymkolwiek innym:

```ts
const event = await verifiedStripeEvent(request, signature, env.STRIPE_WEBHOOK_SECRET)
```

Brak nagłówka `stripe-signature` lub brak `STRIPE_WEBHOOK_SECRET` zwraca 400; nieudane `constructEventAsync` zwraca 400; zdarzenie, którego `livemode` nie pasuje do środowiska, live w `production` i testowe wszędzie indziej, jest logowane i odpowiadane `{ received: true }` bez uruchamiania handlera; zdarzenie z trybu testowego, którego obiekt niesie w metadanych `deployment` wskazujące inne wdrożenie, na przykład checkout lokalnego przebiegu testów docierający do preview, jest logowane na poziomie `info` jako `[Stripe] Ignoring event <id> (<typ>): its checkout belongs to <wdrożenie>, …` i odpowiadane tak samo (zobacz [Płatności](/docs/features/payments#punkt-końcowy-webhooka)); nieznany typ zdarzenia jest logowany i odpowiadany `{ received: true }`; handler, który rzuci wyjątek, zwraca 500, więc Stripe ponawia próbę, a w tle idzie e-mail na `RESEND_EMAIL_FROM`, raz na zdarzenie, niezależnie od tego, ile razy Stripe je ponowi. Handlery żyją w `stripe.webhooks.ts` jako zwykła mapa:

| Zdarzenie                                  | Zachowanie handlera                                                                                                                                                                                                                           |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkout.session.completed`               | `handleFulfillCheckoutSession` — tylko jeśli `payment_status` to `paid` lub `no_payment_required`, w przeciwnym razie loguje i czeka na zdarzenie asynchroniczne; potem w obu przypadkach `deleteCheckoutCoupons` usuwa oznaczony kupon sesji |
| `checkout.session.async_payment_succeeded` | Ta sama ścieżka realizacji, dla płatności z opóźnionym powiadomieniem, która powiedzie się po tym, jak jej sesja zakończyła się jako `unpaid`; karta, BLIK i Przelewy24 podają wynik od razu i nigdy go nie wysyłają                          |
| `checkout.session.async_payment_failed`    | `handleAsyncPaymentFailed` — zwalnia rezerwację i tylko wtedy, gdy to dostarczenie ją zwolniło, zapisuje audyt `orderReleased` i pisze do klienta                                                                                             |
| `checkout.session.expired`                 | Ta sama ścieżka zwolnienia, która zapisuje audyt `orderReleased` tylko wtedy, gdy coś zwolniła, więc sesja zastąpiona przez aktualizację checkoutu nie zostawia wpisu; potem `deleteCheckoutCoupons` usuwa oznaczony kupon sesji              |
| `payment_intent.payment_failed`            | Zapisuje audyt `orderPaymentFailed` z `last_payment_error.message`; bez zmiany stanu                                                                                                                                                          |
| `charge.refunded`                          | `refundOrder({ fullyRefunded, refundedAmount, transactionId })` z sumą zwrotów obciążenia, które nadal obowiązują, który nie przywraca stanu, potem `sendOrderRefundedEmail` dla zwrotu, o którym klient jeszcze nie wie                      |
| `refund.failed`                            | `handleRefundUndone` — `undoFailedRefund` obniża płatność do obowiązujących zwrotów i otwiera ponownie zwrócone zamówienie, zapisuje audyt `order.refund_failed` i wysyła sklepowi alert `refundFailed`; nigdy nie pisze do klienta           |
| `refund.updated`                           | To samo, gdy zwrot ma teraz status `canceled` albo `failed`; przy każdej innej zmianie od razu kończy                                                                                                                                         |
| `charge.dispute.created`                   | `flagOrderDispute(...)` — zamraża zamówienie i zapisuje audyt `orderDisputeOpened`                                                                                                                                                            |
| `charge.dispute.closed`                    | Jeśli `status === "lost"`, zapisuje zwrot przez `refundOrder`; w przeciwnym razie `clearOrderDispute(...)`                                                                                                                                    |

Realizacja odczytuje pozycje przez `readCheckoutSessionLines` (`src/modules/checkout/checkout.session-lines.server.ts`), które bierze je z wiersza płatności sesji, a dla sesji utworzonej, zanim wiersz je przechowywał, sięga po metadane, wywołuje `fulfillCheckout({ currency, lines, locale, paidAmount, shippingTotal, transactionId })` z `paidAmount` równym `session.amount_total` i `shippingTotal` odczytanym z metadanych, a następnie — tylko jeśli funkcja zwróciła nowy `orderId`, co czyni handler idempotentnym wobec ponowień Stripe — zapisuje audyt `orderPaymentCaptured` (`fulfillCheckout` zapisało `orderPlaced` z adresem checkoutu, gdy tylko zatwierdził się jego wsad), planuje unieważnienie zamówień w panelu i katalogu produktów oraz wysyła e-mail potwierdzający, a razem z nim powiadomienie sklepu o nowym zamówieniu na `RESEND_EMAIL_FROM`. Ten e-mail linkuje do originu `return_url` sesji, czyli pod adres, na którym złożono zamówienie, a nie do hosta wywołanego przez Stripe, a `resolveDeploymentOrigin` go odrzuca, jeśli tego hosta nie obsługuje żadne wdrożenie. Krok e-maila nigdy nie rzuca wyjątku: odrzucone albo niemożliwe do przygotowania potwierdzenie jest zapisywane przy zamówieniu jako `email.failed`, a handler i tak kończy się sukcesem, więc Stripe nie dostarcza zdarzenia ponownie z powodu e-maila. Wysyłka trafia też do `scheduleBackgroundWork`, więc kończy się i zostaje zapisana nawet wtedy, gdy Stripe zerwie połączenie, zanim handler odpowie. Dla zamówienia z rabatem `fulfillCheckout` zapisuje wiersz `discount_redemption` i liczy wykorzystanie we własnym wsadzie zamówienia. Jeśli odczyt pozycji albo `fulfillCheckout` się nie powiedzie, handler zapisuje audyt `order.fulfillment_failed` z poziomem `error`, podając kwotę, e-mail klienta i przyczynę, a potem rzuca błąd dalej, żeby Stripe ponowił zdarzenie, a ponowienie, które znów się nie powiedzie, nie dodaje drugiego wpisu, bo wpis ma klucz sesji; gdy `fulfillCheckout` zgłasza przez `ERROR_CODES.NOT_FOUND`, że żaden oczekujący checkout nie może przyjąć tej sesji, zapisuje ten sam audyt, w tle wysyła e-mail o tej sesji na `RESEND_EMAIL_FROM` i odpowiada `200`, bo ponowienie nic nie da (zobacz [Płatności: realizacja](/docs/features/payments#realizacja)). Krok zamówienia oraz następujące po nim audyty, odświeżenia i e-maile to `createOrderFromPaidSession` i `announcePlacedOrder` w `stripe.fulfillment.server.ts`, które uruchamia też strona powrotu, gdy Stripe zgłosi sesję jako opłaconą, zanim dotrze jej webhook; zamówienie ogłasza ta ścieżka, która je złożyła, a druga nic nie robi.

Zdarzenie `charge.refunded`, zdarzenia zwrotów i handlery sporów otrzymują tylko PaymentIntent, więc `resolveCheckoutSession` listuje sesje Checkout filtrowane po `payment_intent` z `limit: 1`, aby odzyskać sesję, której identyfikatorem kluczowany jest wiersz `payment`. Handler zwrotu bierze też `return_url` sesji jako origin e-maila o zwrocie. Jeśli nie znajdzie sesji, handler loguje i kończy, zamiast zawodzić. Handlery zwrotów odczytują potem zwroty obciążenia przez `readStandingRefunds` z `stripe.refunds.server.ts`, które pobiera je przez `stripe.refunds.list({ charge, limit: 100 })` ze wszystkich stron i sumuje te, które nie są `failed` ani `canceled`, bo obciążenie w zdarzeniu `charge.refunded` to obraz z chwili utworzenia zwrotu, a zwrot może się nie powieść później (zobacz [Płatności: zwroty i spory](/docs/features/payments#zwroty-i-spory)).

Dwa e-maile do klienta wysyłane przez te zdarzenia wychodzą raz na zdarzenie. E-mail o nieudanej płatności wychodzi tylko wtedy, gdy `releaseCheckout` zgłosi, że to dostarczenie przestawiło płatność sesji z `pending` na `failed`. E-mail o zwrocie wychodzi tylko wtedy, gdy `refundOrder` zgłosi, że obowiązujące zwroty obciążenia sumują się do więcej, niż płatność miała zapisane przed zdarzeniem, a sklep nie anulował zamówienia; anulowanie samo pisze do klienta o swoim zwrocie. Jego klucz wskazuje najnowszy z tych zwrotów, więc zwrot zlecony ponownie po nieudanym trafia do klienta e-mailem, nawet gdy ma tę samą kwotę. Zwrot, który się nie powiódł albo został anulowany, wysyła e-mail do sklepu, nie do klienta. Zobacz [E-maile transakcyjne](/docs/features/email#anulowanie-zwrot-i-nieudana-płatność).

Stripe przysyła powiązany obiekt albo jako jego identyfikator, albo, po rozwinięciu, jako sam obiekt. `resolveStripeObjectId` w `stripe.utils.ts` zwraca identyfikator w obu przypadkach, a dla `null` zwraca `undefined`. Używa go `resolveCheckoutSession` dla PaymentIntent, e-mail potwierdzający zamówienie dla PaymentIntent sesji, usuwanie zapisanej karty dla klienta karty oraz zwrot z panelu w `refund-admin-order.ts` dla PaymentIntent sesji Checkout, którą pobiera na podstawie `payment.transaction_id`, ponieważ Stripe zwraca PaymentIntent, a nie sesję. Zobacz [Płatności](/docs/features/payments).

Żadne zdarzenie zwrotu nie przywraca stanu magazynowego, bo zwrot pieniędzy nie mówi, czy towar wrócił: decyduje o tym administrator w oknie zwrotu albo przyciskiem Przywróć na stan w zamówieniu (zobacz [Zamówienia](/docs/features/orders#akcje-w-panelu)). Przegrany spór dodatkowo loguje `review inventory manually`, ponieważ towaru zwykle już nie ma.

### Wersja API endpointów webhooka

Stripe buduje treść każdego zdarzenia w wersji API endpointu, do którego je wysyła, a tę wersję ustala przy tworzeniu endpointu: `api_version` endpointu nie da się później zmienić. To, co handler pobiera sam, na przykład sesje, które wypisuje `resolveCheckoutSession`, albo zwroty, które sumuje `readStandingRefunds`, przychodzi w wersji `STRIPE_API_VERSION`.

| `production` | live        | `we_1URCUkJhNVr9Gkhk2gFlLYQD` | `2026-09-30.endive` | `https://martebizuteria.pjborowiecki.workers.dev/api/webhooks/stripe` |

#### Zmiana wersji API endpointu

Wersja jest ustalana przy tworzeniu, więc jej zmiana oznacza utworzenie nowego endpointu. Nowy endpoint ma własny sekret podpisu, a Worker sprawdza każde zdarzenie jednym `STRIPE_WEBHOOK_SECRET`. Przed przejściem na nowe wydanie porównaj jego listę zmian z polami, które handlery czytają z obiektu zdarzenia. Potem, dla każdego środowiska, w trybie Stripe jego endpointu:

1. W panelu Stripe przejrzyj dostarczenia zdarzeń starego endpointu, znajdź nieudane, które wciąż czekają na ponowienie, i wyślij je ponownie: zdarzenie utworzone, zanim powstał nowy endpoint, nigdy do niego nie trafi.
2. Utwórz endpoint pod tym samym adresem albo pod `https://martebizuteria.pl/api/webhooks/stripe`, gdy produkcja przechodzi na własną domenę (zobacz [Listę kontrolną przed startem sprzedaży](/docs/guides/go-live-checklist)), z dziesięcioma zdarzeniami ze `STRIPE_WEBHOOK_EVENTS` i nową wersją API. Panel może utworzyć endpoint w najnowszej wersji; dokładną wersję ustawia przy tworzeniu `api_version` w API. Skopiuj sekret podpisu nowego endpointu, `whsec_…`.
3. Od razu ustaw go jako `STRIPE_WEBHOOK_SECRET` środowiska: w środowisku GitHuba, `preview` albo `production`, w `.env.preview` albo `.env.production`, skąd wgrywa go kolejne wdrożenie, oraz w działającym Workerze przez `bunx wrangler secret put STRIPE_WEBHOOK_SECRET --env preview` albo `--env production`.
4. Wyłącz stary endpoint, a usuń go, gdy nowy będzie dostarczał zdarzenia od kilku dni.

Między krokami 2 i 4 Stripe wysyła każde nowe zdarzenie do obu endpointów. Weryfikację podpisu przechodzi tylko dostarczenie z endpointu, którego sekret ma Worker; drugie dostaje odpowiedź `400`, a Stripe je ponawia. Zdarzenie, które stary endpoint dostarczył przed krokiem 3, przychodzi więc ponownie z nowego, gdy jego sekret jest już na miejscu, i zostaje obsłużone jak ponowne dostarczenie: zamówienia, stan magazynowy, zwroty, e-maile i alerty dzieją się raz, a zdarzenie `payment_intent.payment_failed` albo zdarzenie sporu obsłużone dwa razy może zostawić dwa wpisy audytu. Wyłączenie starego endpointu kończy ponawianie jego odrzuconych dostarczeń, a wszystkie ich zdarzenia trafiły też do nowego endpointu. Wykonaj te kroki jeden po drugim, w porze małego ruchu.

## Praca lokalna

```bash
bun run stripe:listen
# stripe listen --latest --forward-to localhost:3000/api/webhooks/stripe
```

Sekret `STRIPE_WEBHOOK_SECRET` wypisany przez to polecenie jest tym, którego potrzebuje Twój lokalny plik środowiska. Bez niego trasa webhooka odpowiada 400 i nic nie jest realizowane.

Testy przeglądarkowe emulują Stripe'a w testowym Workerze. Jeden projekt Playwrighta, `stripe-test-mode`, płaci w prawdziwym Payment Element, gdy jest zbudowany i uruchomiony z kluczami sandboxa Stripe'a: testowymi kartami Stripe'a, także odrzucanymi i z weryfikacją 3D Secure, którą kupujący kończy, oblewa albo zamyka, kodem BLIK 123456 i symulowanymi odmowami BLIK-a oraz przez Przelewy24 zatwierdzone albo odrzucone na testowej stronie Stripe'a. Każda odmowa karty albo BLIK-a musi zostawić kupującego w tej samej sesji z komunikatem Stripe'a i z koszykiem, a nieudana płatność Przelewy24 musi przywrócić go do kroku płatności z koszykiem. Projekt sam przekazuje zdarzenie `checkout.session.completed` sandboxa do lokalnego webhooka, więc nie potrzebuje Stripe CLI; zobacz [Tryb testowy Stripe](/docs/tooling/testing#tryb-testowy-stripe).

## Błędy

Plik `stripe.errors.ts` mapuje wewnętrzne kody na klucze komunikatów:

```ts
export const CHECKOUT_ERROR_CODES = {
  DELIVERY_METHOD_UNAVAILABLE: "DELIVERY_METHOD_UNAVAILABLE",
  INSUFFICIENT_INVENTORY: "INSUFFICIENT_INVENTORY",
  INVALID_PRICE: "INVALID_PRICE",
  LOCKER_NOT_FOUND: "LOCKER_NOT_FOUND",
  LOCKER_REQUIRED: "LOCKER_REQUIRED",
  PRODUCT_NOT_FOUND: "PRODUCT_NOT_FOUND",
  SALES_PAUSED: "SALES_PAUSED",
  SESSION_CLOSED: "SESSION_CLOSED",
  SESSION_COMPLETE: "SESSION_COMPLETE",
  SESSION_PROCESSING: "SESSION_PROCESSING",
  TOO_MANY_OPEN_CHECKOUTS: "TOO_MANY_OPEN_CHECKOUTS",
  UNKNOWN_ERROR: "UNKNOWN_ERROR",
  VARIANT_NOT_FOUND: "VARIANT_NOT_FOUND",
} as const
```

`CHECKOUT_ERRORS` przypisuje każdemu kodowi klucz, na przykład `SESSION_PROCESSING` → `sessionProcessing` i `TOO_MANY_OPEN_CHECKOUTS` → `tooManyOpenCheckouts`, a `getCheckoutErrorKey(error)` zwraca `errors.<key>` dla przestrzeni nazw komunikatów koszyka, z wartością domyślną `unknownError`.

## Sekrety

`STRIPE_SECRET_KEY` i `STRIPE_WEBHOOK_SECRET` to sekrety Workera wymienione w `wrangler.jsonc`; `VITE_STRIPE_PUBLISHABLE_KEY` to zmienna przeglądarkowa w plikach środowiska.

Oba klucze muszą pochodzić z tego samego trybu Stripe, a tryb musi odpowiadać środowisku. `deploy:preview` i `deploy:production` uruchamiają `scripts/verify-stripe-keys.ts <środowisko>` zaraz po `verify-bindings.ts`, przed kompilacją, i skrypt przerywa wdrożenie, jeśli klucze nie przejdą `verifyStripeKeys` z `stripe.keys.ts`:

| Środowisko               | `VITE_STRIPE_PUBLISHABLE_KEY` | `STRIPE_SECRET_KEY`        |
| ------------------------ | ----------------------------- | -------------------------- |
| `production`             | `pk_live_`                    | `sk_live_` albo `rk_live_` |
| `preview`, `development` | `pk_test_`                    | `sk_test_` albo `rk_test_` |

Klucz publiczny live obok testowego klucza tajnego, albo odwrotnie, jest odrzucany w każdym środowisku, bo formularz płatności nie otworzyłby sesji Checkout, które tworzy serwer. Klucze testowe na produkcji przyjmowałyby testowe karty Stripe przy prawdziwych zamówieniach, a klucze live w preview obciążyłyby prawdziwą kartę za testowe zamówienie. Odrzucany jest też brakujący lub pusty klucz oraz wartość, która nie jest kluczem właściwym dla swojej zmiennej, na przykład klucz tajny w `VITE_STRIPE_PUBLISHABLE_KEY`. Skrypt czyta każdy klucz najpierw ze środowiska procesu, potem z `.env.<środowisko>`, tak jak dostarczają je przepływy wdrożeniowe, i wypisuje nazwy zmiennych oraz ich tryb, nigdy sam klucz. `bun scripts/verify-stripe-keys.ts development` uruchamia tę samą kontrolę dla `.env.development`. Reguły mają testy jednostkowe w `__test__/stripe.keys.test.ts`.

Kontrola czyta tylko przedrostki. Nie pyta Stripe, czy klucze są nadal ważne, czy klucz ograniczony może zapisywać sesje Checkout, kupony, klientów, metody płatności, zwroty i SetupIntents, którymi zarządza sklep, i odczytywać jego PaymentIntents, ani czy istnieje produkcyjny endpoint webhooka. Przed pierwszym wdrożeniem produkcyjnym utwórz endpoint live pod `https://<host>/api/webhooks/stripe` w wersji API `2026-09-30.endive`, zasubskrybuj w nim dziesięć zdarzeń z `STRIPE_WEBHOOK_EVENTS`, łącznie z `refund.failed` i `refund.updated`, zapisz jego własny `whsec_` jako produkcyjny `STRIPE_WEBHOOK_SECRET` i włącz BLIK oraz Przelewy24 w trybie live. Zarejestrowany dziś endpoint live to `we_1URCUkJhNVr9Gkhk2gFlLYQD` w wersji `2026-09-30.endive`, pod adresem `workers.dev`; jak zastąpić endpoint, czego będzie wymagać przejście produkcji na własną domenę, opisuje [Wersja API endpointów webhooka](#wersja-api-endpointów-webhooka). Sekret `whsec_` nie zdradza, w którym trybie działa jego endpoint, więc wdrożenie nie może sprawdzić `STRIPE_WEBHOOK_SECRET`; zamiast tego trasa webhooka loguje i pomija każde zdarzenie z drugiego trybu (zobacz [Webhooki](#webhooki)). [Lista kontrolna przed startem sprzedaży](/docs/guides/go-live-checklist) zbiera te kroki ze wszystkim innym, czego produkcja potrzebuje, zanim przyjmie prawdziwe zamówienia.
