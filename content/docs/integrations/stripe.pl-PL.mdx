Stripe jest jedynym dostawcą płatności. Sklep pobiera opłaty w PLN, a płatność odbywa się wewnątrz sklepu przy użyciu wbudowanych Checkout Elements od Stripe — klient nigdy nie opuszcza strony `/checkout`. Wiersz zamówienia tworzony jest wyłącznie wtedy, gdy Stripe potwierdzi płatność webhookiem; do tego momentu dane żyją w wierszu `checkout` oraz wierszu `payment` w stanie `pending`, przy zarezerwowanym stanie magazynowym.

## Klient serwerowy

```ts
export const stripe = new StripeServer(env.STRIPE_SECRET_KEY, {
  apiVersion: STRIPE_API_VERSION,
  appInfo: { name: APP_NAME },
  httpClient: StripeServer.createFetchHttpClient(),
})
```

`createFetchHttpClient()` jest wymagane: klient HTTP z Node nie istnieje na Workerach. `STRIPE_API_VERSION` jest przypięte w `stripe.constants.ts` do `"2026-08-26.dahlia"` — jego zmiana oznacza ponowne przeczytanie kształtu każdego ładunku webhooka.

## Stałe

```ts
export const CHECKOUT_PAYMENT_METHOD_ORDER = ["card", "blik", "p24"] as const

const STRIPE_CURRENCY_BY_CODE = { PLN: "pln" } as const satisfies Record<SupportedCurrencyCode, string>

export const STRIPE_CURRENCY = STRIPE_CURRENCY_BY_CODE[STORE_CURRENCY_CODE]
```

BLIK i Przelewy24 stoją obok karty, ponieważ tego oczekują polscy klienci; klauzula `satisfies` sprawia, że dodanie waluty do `SupportedCurrencyCode` w `src/modules/_core/constants/currency.ts` bez dodania tu kodu Stripe jest błędem typowania. `STRIPE_WEBHOOK_EVENTS` wylicza osiem zdarzeń, które obsługuje aplikacja.

## Klient przeglądarkowy

Plik `stripe.client.ts` leniwie ładuje Stripe.js raz na stronę i mapuje język aplikacji na własny język Stripe:

```ts
const STRIPE_LOCALES = { "en-US": "en", "pl-PL": "pl" } as const satisfies Record<SupportedLocale, StripeElementLocale>
```

Czyta `import.meta.env.VITE_STRIPE_PUBLISHABLE_KEY`, ostrzega w konsoli, jeśli klucza brakuje, i memoizuje obietnicę `loadStripe` w `stripeRef` na poziomie modułu, więc zmiana języka nie przeładowuje skryptu. Odrzucone pobranie znika ze `stripeRef`, więc następne wywołanie pobiera Stripe.js od nowa, zamiast zwracać ten sam błąd aż do przeładowania strony. `stripeJsQuery(locale)` opakowuje `getStripe` w opcje zapytania z kluczem `STRIPE_QUERY_KEYS.JS` i językiem oraz z `retry: false`, dla komponentu, który podczas pobierania skryptu lub po błędzie musi pokazać własny stan; korzysta z niego formularz karty na stronie konta. Ponieważ `stripeRef` zachowuje język pierwszego wywołania, eksportowane jest też `toStripeLocale`: formularz karty na stronie konta przekazuje `locale: toStripeLocale(locale)` do własnego `Elements`, więc mówi w bieżącym języku klienta.

## Dwie funkcje serwerowe

Plik `stripe.actions.ts` udostępnia dokładnie dwa punkty wejścia, oba z limitem dziesięciu wywołań na 60 sekund i oba leniwie importujące ciężki moduł serwerowy:

```ts
export const createCheckoutSessionFn = createServerFn({ method: "POST" })
  .middleware([withRateLimit("checkout-create", RATE_LIMITS.CHECKOUT)])
  .validator((data: unknown) => createCheckoutSessionInputSchema.parse(data))
  .handler(async ({ data }) => {
    const { handleCreateCheckoutSession } = await import("~/src/integrations/stripe/stripe.actions.server")

    return handleCreateCheckoutSession(data)
  })
```

Plik `stripe.actions.schemas.ts` definiuje ładunek: `{ checkoutValues: checkoutSchema, items: cartItemSchema[] }` z co najmniej jedną i co najwyżej `CART_LINES_MAX` pozycjami (`src/modules/cart/cart.constants.ts`) oraz `sessionId` w wariancie aktualizacji. `CART_LINES_MAX` to `STRIPE_CHECKOUT_LINE_ITEMS_MAX` pomniejszone o linię wysyłki, bo Checkout Session w trybie płatności przyjmuje najwyżej 100 pozycji. Każda ilość musi być liczbą całkowitą od 1 do `CART_LINE_QUANTITY_MAX` (10), czyli najwyższej liczby sztuk jednego produktu w zamówieniu. `checkoutSchema` pochodzi z `src/modules/checkout/checkout.zod.ts`, więc reguły adresu, dostawy i danych do faktury walidowane są w dokładnie jednym miejscu.

## Tworzenie sesji

Funkcja `handleCreateCheckoutSession` w `stripe.actions.server.ts` najpierw wywołuje `admitNewCheckout`, które w dwóch przypadkach odrzuca żądanie, zanim dotknie klienta Stripe, katalogu, rabatu czy stanu magazynowego. `assertSalesOpen()` odczytuje `store_setting.sales_paused` przez `isSalesPaused()` i, dopóki sprzedaż jest wstrzymana, odrzuca żądanie z `CONFLICT` i `SALES_PAUSED` (zobacz [Kasa: wstrzymanie sprzedaży](/docs/features/checkout#wstrzymanie-sprzedaży)). `countOpenCheckouts` odrzuca z `TOO_MANY_REQUESTS` i `TOO_MANY_OPEN_CHECKOUTS`, gdy adres klienta żądania ma już pięć otwartych checkoutów albo jego e-mail trzy (zobacz [Kasa: limity trzymania towaru](/docs/features/checkout#limity-trzymania-towaru)). W przeciwnym razie wykonuje następującą sekwencję:

1. `resolveDelivery(checkoutValues)` odczytuje wybraną metodę przez `getOfferedDeliveryMethodByIdQuery`, który znajduje tylko metodę aktywną, której przewoźnik też jest aktywny, czyli według reguły, którą listuje krok dostawy. Wszystko inne dostaje odmowę `DELIVERY_METHOD_UNAVAILABLE`, zanim padnie wywołanie Stripe, więc wycofana albo zmyślona metoda nie wysyła już za darmo. Gdy `type` metody w bazie to `locker`, żądanie potrzebuje `lockerId` w kształcie nazwy punktu InPost, inaczej dostaje odmowę `LOCKER_REQUIRED`, a InPost jest pytany, czy taki punkt istnieje: punkt, którego nie ma na liście, dostaje odmowę `LOCKER_NOT_FOUND`, a gdy InPost nie odpowie w ciągu trzech sekund, paczkomat zostaje przyjęty, a checkout oznaczony `locker_unconfirmed`, by sklep go sprawdził (zobacz [InPost](/docs/integrations/inpost#jak-to-trafia-na-zamówienie)); dla każdego innego typu `lockerId` jest porzucany. `price` metody jest kosztem dostawy.
2. `validateAndCalculateItems(items)` ładuje produkty wraz ze stanem magazynowym po identyfikatorze `handle`, tylko te o statusie `published` (`getPublishedProductsWithInventoryByHandles`), rozwiązuje każdy wariant i **czyta cenę z bazy** — `cartItemSchema` nie ma `price` ani `rawPrice`, więc cena z koszyka w ogóle nie dociera do handlera. Odrzuca z błędem `PRODUCT_NOT_FOUND`, którym kończy się też próba zakupu produktu zarchiwizowanego albo przywróconego do szkicu, gdy leżał w koszyku, `VARIANT_NOT_FOUND`, `INVALID_PRICE` (przez `isSellPriceCentsValid`) lub `INSUFFICIENT_INVENTORY`, a zwraca każdą pozycję wzbogaconą o `inventoryId`.
3. `resolveCheckoutDiscount(...)` ponownie sprawdza `checkoutValues.discountCode` względem sumy cen z bazy i kosztu dostawy; kod, który nie obowiązuje, jest pomijany. Zobacz [Rabaty](/docs/features/discounts).
4. `reserveInventoryForItems(validatedItems)` zajmuje stan magazynowy instrukcją `UPDATE` warunkowaną `quantity_available >= qty`, więc udaje się zawsze, gdy w tej chwili zostało dość towaru, niezależnie od tego, ile innych checkoutów zarezerwowało ten sam wariant od kroku 2. Gdy inny checkout zajął w tym czasie ostatnie sztuki, odmawia z `CONFLICT` i `INSUFFICIENT_INVENTORY`, tak jak krok 2, więc kupujący widzi komunikat o braku towaru.
5. `createCheckout({ checkoutValues, clientAddress, discountId, lockerUnconfirmed, userEmail, userId })` zapisuje wiersze adresów i wiersz `checkout` z adresem klienta, według którego liczony jest limit otwartych checkoutów, i informacją, czy InPost potwierdził jego paczkomat, a z kodem w tym samym wsadzie rezerwuje jedno jego wykorzystanie w `discount_claim` i ustawia `discount_id` tylko wtedy, gdy rezerwacja została zapisana. Kod, którego pozostałe wykorzystania trzymają inne otwarte checkouty, jest tu pomijany, a sesja powstaje w pełnej cenie. Jeśli krok 6 albo 7 się nie uda, `releaseDiscountClaims` oddaje wykorzystanie razem z towarem. Zobacz [Rabaty: utrzymanie wykorzystania na czas płatności](/docs/features/discounts#utrzymanie-wykorzystania-na-czas-płatności).
6. `createStripeSession(...)` tworzy sesję Stripe Checkout, wygasającą `CHECKOUT_SESSION_LIFETIME_SECONDS` (32 minuty) od teraz, a nie po domyślnych 24 godzinach Stripe, z jednorazowym kuponem, gdy obowiązuje rabat. Jeśli Stripe odmówi utworzenia sesji, kupon jest usuwany, zanim błąd pójdzie dalej.
7. `createPendingPayment(...)` zapisuje wiersz `payment` z `provider: "stripe"`, `currency: "PLN"`, `transactionId` ustawionym na identyfikator sesji Stripe i `reservedLines` z liniami zarezerwowanymi w kroku 4.
8. `scheduleProductCatalogInvalidation()` wypycha nową dostępność do podłączonych sklepów.

Jeśli cokolwiek po kroku 4 rzuci wyjątek, handler zwalnia rezerwację przez `releaseInventoryForItems(validatedItems)` i rzuca dalej. Ta kompensacja jest powodem, dla którego nieudana próba płatności nie zostawia zablokowanego towaru.

Sama sesja:

```ts
const params: StripeType.Checkout.SessionCreateParams = {
  expires_at: Math.floor(Date.now() / MILLISECONDS_PER_SECOND) + CHECKOUT_SESSION_LIFETIME_SECONDS,
  line_items: toLineItems(lines, { cost: shippingCost, name: messages.deliveryLineItem[deliveryType] }),
  metadata,
  mode: "payment",
  payment_intent_data: { metadata, receipt_email: email },
  return_url: returnUrl,
  ui_mode: "elements",
  ...(customerId === undefined
    ? { customer_email: email }
    : { customer: customerId, saved_payment_method_options: { payment_method_save: "enabled" } }),
}
const discounts = await toSessionDiscounts({ checkoutId, discount })
if (discounts.length > NO_COST) {
  params.discounts = discounts
}

const session = await stripe.checkout.sessions.create(params).catch(async (error: unknown) => {
  await deleteCheckoutCoupons({ checkoutId, discounts })
  throw error
})
```

`customerId` jest ustawiane tylko dla zalogowanego kupującego: przed krokiem 1 `handleCreateCheckoutSession` wywołuje `ensureStripeCustomer` (`stripe.customer.server.ts`), które przy pierwszym użyciu tworzy klienta Stripe i zapisuje jego identyfikator w `user.stripe_customer_id`. Sesja należy wtedy do tego klienta Stripe i pozwala kupującemu zapisać kartę, którą potem wyświetla `/account/payment`. Sesja gościa dostaje zamiast tego `customer_email`. `handleUpdateCheckoutSession` odczytuje zapisany identyfikator przez `getStripeCustomerId` dla checkoutu, który już należy do konta, a wywołuje `ensureStripeCustomer`, gdy przekazuje checkout gościa kontu, na które od tego czasu się zalogowano (zobacz [Aktualizacja sesji](#aktualizacja-sesji)). `ensureStripeCustomer` zapisuje nowy identyfikator przez `coalesce`, a żądanie, które zastanie już zapisany inny identyfikator, usuwa właśnie utworzonego klienta, więc równoległe pierwsze żądania kończą się jednym klientem. Drugim wywołującym jest strona konta: `createCardSetupIntent` otwiera dla tego samego klienta SetupIntent na kartę, który `stripe.confirmSetup` potwierdza w przeglądarce. Usunięcie konta wywołuje `deleteStripeCustomer`, które usuwa tego klienta, a razem z nim zapisane karty, przez `stripe.customers.del` i czyści `user.stripe_customer_id`; odpowiedź `resource_missing` liczy się jako usunięcie, a każdy inny błąd zostawia konto. Zobacz [Konto](/docs/features/account) i [Usunięcie konta](/docs/features/account#usunięcie-konta).

`ui_mode: "elements"` daje wbudowane doświadczenie płatności. `return_url` to `${origin}/checkout?success=true&session_id={CHECKOUT_SESSION_ID}`, gdzie Stripe wstawia identyfikator sesji, a `origin` to `resolveRequestOrigin(getRequest())`: adres, na który przyszło żądanie checkoutu, odrzucany z `FORBIDDEN`, jeśli nie jest jednym z hostów obsługiwanych przez ten build. Zobacz [Model bezpieczeństwa](/docs/architecture/security-model). Strona sukcesu używa `session_id`, aby wczytać zamówienie przez `getOrderConfirmationQuery`. Koszt dostawy dodawany jest jako dodatkowa pozycja, a nie jako stawka wysyłki Stripe. Jej nazwa pochodzi z `deliveryLineItem` w `pages.checkout` według typu metody dostawy, w języku kupującego, więc ta pozycja na potwierdzeniu płatności Stripe jest w języku checkoutu. Rabat trafia do `discounts`: dla każdej sesji, która go ma, `toSessionDiscounts` (`stripe.coupons.server.ts`) wywołuje `stripe.coupons.create` z `amount_off: discount.amountMinorUnits`, `currency: STRIPE_CURRENCY`, `duration: "once"`, `metadata: { checkoutId, source: STRIPE_COUPON_SOURCE }` i `name: discount.code`. Po tych metadanych `deleteCheckoutCoupons` rozpoznaje kupony, które może usunąć: usuwa kupon sesji tylko wtedy, gdy kupon niesie `source: "marte_checkout"` i `checkoutId` tej samej sesji, a każdy inny kupon na koncie zostawia w spokoju. Kiedy to się dzieje, opisuje strona [Rabaty](/docs/features/discounts).

### Metadane są kontraktem realizacji zamówienia

`metadata` niesie `checkoutId`, `discountCode`, `discountTotal`, `locale`, `userId` oraz sam koszyk, a ten sam obiekt kopiowany jest na PaymentIntent. Ponieważ wartość metadanych Stripe ograniczona jest do 500 znaków, `toCheckoutSessionItemsMetadata` w `src/modules/checkout/checkout-metadata.zod.ts` dzieli JSON na `items0`, `items1`, …, a `readCheckoutSessionItemsJson` składa je ponownie, wciąż akceptując pojedynczy, starszy klucz `items`. Webhook nie czyta niczego innego, aby dowiedzieć się, co zostało kupione, więc wszystko, czego potrzebuje e-mail potwierdzający lub pozycje zamówienia, musi się tam znaleźć. `discountCode` i `discountTotal` nie są odczytywane z powrotem: realizacja wylicza rabat ponownie na podstawie `discount_id` checkoutu.

## Aktualizacja sesji

Gdy zmieni się koszyk lub formularz, klient nie tworzy drugiej sesji — aktualizuje istniejącą. `stripe.checkout.ts` decyduje o tym na podstawie dwóch odcisków:

```ts
export const buildCheckoutLinesFingerprint = (lines: readonly CheckoutSessionLine[]): string =>
  lines
    .map((line) => `${line.variantId}:${line.qty}:${line.unitPrice}`)
    .toSorted((left, right) => left.localeCompare(right))
    .join("|")

export const buildCheckoutValuesFingerprint = (values: CheckoutFormSchema): string =>
  JSON.stringify(Object.fromEntries(Object.entries(values).toSorted(([left], [right]) => left.localeCompare(right))))
```

`ensureCheckoutSession` przyjmuje sesję z ekranu oraz `heldSessionId`, czyli identyfikator, który przeglądarka zapisała dla swojej otwartej sesji. Kontynuuje trzymaną sesję albo tę z ekranu, gdy nic nie zapisano, wywołując `updateCheckoutSessionFn`, gdy zmienił się którykolwiek odcisk albo gdy trzymana sesja nie jest tą z ekranu, a tworzy sesję tylko wtedy, gdy przeglądarka żadnej nie trzyma. Dzięki temu odświeżenie, druga karta czy powrót z koszyka zastępują otwartą sesję, zamiast ponownie rezerwować koszyk. Zanim do tego dojdzie, strona kasy pyta `getCheckoutSessionStatus`, czy zapisana sesja jest nadal otwarta, i pokazuje potwierdzenie sesji opłaconej, zamiast dochodzić do tej aktualizacji (zobacz [Kasa](/docs/features/checkout)). `isCheckoutSessionFor` buduje odcisk linii sesji z `lines` wycenionych przez serwer, a odcisk koszyka z jego aktualnych cen, więc cena zmieniona przez sklep, którą sprawdzenie dostępności zapisuje w koszyku, również zastępuje sesję. `resetCheckoutSession` wymusza aktualizację trzymanej sesji — interfejs korzysta z tego po odrzuconej płatności i wtedy, gdy kupujący ponawia płatność, której sesja wygasła. Każda zwrócona sesja zachowuje `lines` i `totals` z serwera, z których podsumowanie kasy i koszyk biorą ceny, oraz niesie `expiresAt`, `CHECKOUT_SESSION_LIFETIME_SECONDS` od chwili odebrania, z którego krok płatności korzysta, by pokazać, że sesja wygasła.

Po stronie serwera `handleUpdateCheckoutSession` jest najdelikatniejszą funkcją w bazie kodu:

1. `getPaymentContextByTransactionId(sessionId)` odnajduje `checkout`, właścicielski `userId`, czas utworzenia checkoutu oraz statusy checkoutu i jego płatności. Sesja należąca do zalogowanego użytkownika może być aktualizowana tylko przez tego użytkownika, w przeciwnym razie `FORBIDDEN` z powodem `SESSION_CLOSED`, więc przeglądarka po wylogowaniu zaczyna własny checkout. Checkout gościa może kontynuować każdy, kto zna identyfikator jego sesji, a gdy to żądanie jest zalogowane, jak wtedy, gdy gość dochodzi do kroku płatności, a potem się loguje, aktualizacja przekazuje checkout temu kontu: zastępcza sesja niesie w metadanych `userId` konta i jego klienta Stripe z `ensureStripeCustomer`, a krok 4 ustawia `user_id` checkoutu. Zamówienie trafia wtedy na konto, kupujący zachowuje towar trzymany przez sesję gościa, a zapisane karty są proponowane. Nieznany identyfikator sesji jest odrzucany z `NOT_FOUND`, a checkout lub płatność, które nie są już `pending` i nie zostały opłacone, z `CONFLICT`, oba z powodem `SESSION_CLOSED`. Płatność `succeeded` albo `refunded` jest zamiast tego odrzucana z `CONFLICT` i powodem `SESSION_COMPLETE`, jeszcze przed sprawdzeniem własności, bo strona potwierdzenia i tak pokazuje to zamówienie każdemu, kto ma identyfikator sesji.
2. Stara sesja Stripe jest pobierana z rozwiniętym payment intentem. Sesja, której płatność według `isCheckoutSessionProcessing` (`stripe.utils.ts`) jest w toku, jest odrzucana najpierw, z `SESSION_PROCESSING`, więc jej zastąpienie nigdy nie anuluje płatności, którą bank może jeszcze dokończyć: sesja `open`, której payment intent jest `processing` albo jest płatnością BLIK czekającą na zatwierdzenie w aplikacji banku (`requires_action` z `blik_authorize`), oraz sesja `complete`, której `payment_status` to wciąż `unpaid`, bo jej płatność BLIK albo Przelewy24 jeszcze się nie rozliczyła. Każda inna sesja `complete`, opłacona, zanim dotarł jej webhook, jest odrzucana z `SESSION_COMPLETE`, a każdy inny status niż `open` z `SESSION_CLOSED`. Gdy status to `expired`, `releaseExpiredCheckoutSession` najpierw uruchamia `releaseCheckout`, który oddaje linie sesji, strzeżony tak samo jak zwolnienie z webhooka wygaśnięcia, więc towar jest wolny dla nowego checkoutu, który klient otworzy zaraz potem, a webhook, kiedykolwiek dotrze, niczego nie zwalnia. W przeciwnym razie metadane `items*` sesji są parsowane na trzymane przez nią linie. Dopiero wtedy, gdy wiadomo, że sesja jest otwarta, `assertSalesOpen()` odrzuca aktualizację z `SALES_PAUSED`, dopóki sprzedaż jest wstrzymana, więc stara sesja, jej towar i rezerwacja kodu zostają bez zmian, a sesja opłacona przed wstrzymaniem nadal odpowiada `SESSION_COMPLETE`. Potem `assertCheckoutStillEditable` odrzuca z `SESSION_CLOSED` checkout utworzony `CHECKOUT_SESSION_LIFETIME_SECONDS` temu lub dawniej, bo każda aktualizacja daje sesji zastępczej nową rezerwację, a zmiana nie wlicza się do limitów otwartych checkoutów: `stripe.checkout.sessions.expire` najpierw zamyka otwartą sesję, a wygaszona sesja przechodzi przez `releaseExpiredCheckoutSession`, więc nowy checkout, który znów wlicza się do limitów, zastaje jej towar wolny. Jeśli Stripe nie chce jej wygasić, błąd jest przekazywany dalej, a towar zostaje przy sesji. Sesja z płatnością w toku nigdy nie dochodzi do tego sprawdzenia, więc te 32 minuty nigdy nie wygaszają płatności, którą bank wciąż potwierdza.
3. `validateAndCalculateItems` sprawdza edytowany koszyk względem dostępnego stanu powiększonego o to, co trzyma stara sesja, dostawa i rabat są ustalane ponownie, z tymi samymi odmowami co wyżej, a `claimCheckoutDiscount` rezerwuje kod dla checkoutu (checkout, który już go trzyma, zachowuje rezerwację, a kod, którego wykorzystania trzymają inne checkouty, jest pomijany). Potem `handOverCheckoutSession` rezerwuje to, co dokłada edytowany koszyk, czyli `quantitiesBeyond(validatedItems, heldLines)`, przez `reserveInventoryForItems` na identyfikatorach stanu zwróconych przez walidację, i tworzy zastępczą sesję Stripe. Sztuk, które trzyma stara sesja i które edytowany koszyk zatrzymuje, nic nie zwalnia ani nie rezerwuje ponownie, więc żaden inny checkout nie może ich przejąć w trakcie przekazania (zobacz [Stany magazynowe: przeniesienie rezerwacji na sesję zastępczą](/docs/features/inventory#przeniesienie-rezerwacji-na-sesję-zastępczą)). Gdy inny checkout zajął dokładane sztuki od walidacji, rezerwacja kończy się odmową z `CONFLICT` i `INSUFFICIENT_INVENTORY`. Nic poza tym jeszcze się nie zmieniło, więc porażka na tym etapie zostawia starą sesję otwartą, a jej stan zarezerwowany, `releaseInventoryForItems` oddaje to, co dołożono, a `releaseUnappliedDiscountClaims` oddaje rezerwację zrobioną dla innego kodu niż ten z `checkout.discount_id`.
4. `retireCheckoutSession` wygasza starą sesję przez `stripe.checkout.sessions.expire(...)`, żeby nie dało się jej już opłacić, a potem wywołuje `supersedeCheckoutSession`. Ten przypadek użycia jednym wsadem D1 przenosi wiersz `payment` na zastępczą sesję, z liniami edytowanego koszyka jako jego `reserved_lines`, i zwalnia to, z czego edytowany koszyk zrezygnował, czyli `quantitiesBeyond(heldLines, reservedLines)`, tylko dopóki płatność i jej checkout są nadal `pending`. Ten sam wsad usuwa rezerwacje checkoutu dla wszystkich kodów poza tym, który stosuje sesja zastępcza. Gdy żądanie jest zalogowane, ustawia też `user_id` checkoutu na to konto, tylko dopóki checkout jest `pending`, nie ma właściciela, a jego płatność niesie już zastępczą sesję, więc checkout z właścicielem nigdy nie zmienia rąk. Jeśli któryś krok się nie uda albo webhook wygaśnięcia zwolnił checkout wcześniej, zastępcza sesja jest wygaszana, to, co dołożył edytowany koszyk, wraca na stan, a aktualizacja kończy się błędem. Wygaszenie starej sesji wysyła jej webhook `checkout.session.expired`, gdy aktualizacja jeszcze trwa, a `prepareReleaseCheckoutBatch` działa tylko, dopóki płatność sesji i jej checkout są `pending`: zwolnienie zatwierdzone przed przeniesieniem oddaje wszystkie stare linie, oznacza checkout jako nieudany i sprawia, że `supersedeCheckoutSession` odmawia, a zatwierdzone po nim nie znajduje płatności starej sesji, niczego nie zmienia i nie zapisuje wpisu `order.released`. Stare linie nigdy nie są zwalniane dwa razy.
5. `saveReplacementDelivery` aktualizuje dostawę, `discount_id` oraz `locker_unconfirmed` checkoutu. Jeśli to się nie uda, `releaseCheckout` na zastępczej sesji oznacza checkout jako nieudany i oddaje cały edytowany koszyk, a zastępcza sesja jest wygaszana.

Gdy `updateCheckoutSessionFn` odpowiada `SESSION_CLOSED`, `ensureCheckoutSession` i `resetCheckoutSession` wywołują `createCheckoutSessionFn`, żeby zacząć nowy checkout, zamiast zgłaszać błąd. Gdy odpowiada `SESSION_COMPLETE`, niczego nie otwierają i rzucają `PaidCheckoutSessionError` z identyfikatorem sesji, którą próbowały kontynuować, a krok płatności pokazuje potwierdzenie tej sesji, więc sesja opłacona w chwili między sprawdzeniem sesji na stronie kasy a tą aktualizacją nigdy nie prowadzi do drugiego formularza płatności. Gdy odpowiada `SESSION_PROCESSING`, też niczego nie otwierają i rzucają `ProcessingCheckoutSessionError` (`stripe.checkout.processing.ts`) z identyfikatorem tej sesji, a krok płatności czeka na niej na bank, dopóki `getCheckoutSessionStatus` nie zgłosi jej jako `complete`, znów `open` albo `closed`.

`getCheckoutSessionStatus` (`src/modules/checkout/use-cases/get-checkout-session-status.ts`) odpowiada na pytanie strony kasy o zapisaną albo zwróconą sesję wartością `"complete"`, `"open"`, `"processing"` albo `"closed"`. Najpierw czyta płatność i wywołuje `stripe.checkout.sessions.retrieve`, z rozwiniętym payment intentem, tylko dla płatności `pending`. Sesję, której płatność jest w toku według tego samego `isCheckoutSessionProcessing` co w kroku 2, `open` albo `complete` wciąż `unpaid`, zgłasza najpierw jako `"processing"`, więc `complete` przekazuje dalej tylko dla opłaconej sesji, a `open` bez zmian; sesja `expired` przechodzi przez `releaseExpiredCheckoutSession` dokładnie jak w kroku 2. Opłacona sesja jest `"complete"` dla każdego, kto ma jej identyfikator, tak jak na stronie potwierdzenia. Reguła własności z kroku 1 dotyczy tylko sesji otwartej albo czekającej na bank: żądanie niezalogowane na konto będące właścicielem dostaje zamiast odmowy odpowiedź `"closed"`. Jej limit żądań to `checkout-status`.

`expireCheckoutsHoldingVariants` (`src/modules/checkout/use-cases/expire-checkouts-holding-variants.server.ts`) to trzecie miejsce, które woła `releaseExpiredCheckoutSession`, po kroku 2 i `getCheckoutSessionStatus`. Gdy administrator zapisuje produkt jako szkic albo archiwum, funkcja wygasza przez `stripe.checkout.sessions.expire` każdą otwartą sesję trzymającą któryś z wariantów produktu i przekazuje wygaszoną sesję zwróconą przez Stripe do `releaseExpiredCheckoutSession`, więc webhook `checkout.session.expired`, który przychodzi potem, zastaje sztuki już oddane. Sesja, której Stripe nie wygasi, jest logowana i zostaje bez zmian (zobacz [Panel katalogu](/docs/features/admin-catalog#zapis)).

Zachowaj tę kolejność, gdy będziesz to zmieniać. Wiersz `payment` jest przenoszony, a nie tworzony ponownie, ponieważ migracja `20260924120000_checkout_idempotency_constraints.sql` nakłada unikalny indeks na `payment.transaction_id` (oraz na `order.checkout_id`); wstawienie drugiego wiersza płatności dla zastępczej sesji naruszyłoby go.

## Potwierdzenie w przeglądarce

`confirmCheckoutSession` owija `checkout.confirm({ billingAddress, redirect: "if_required" })` i klasyfikuje wynik:

```ts
export type ConfirmOutcome =
  { status: "declined"; message: string } | { status: "failed"; message: string } | { status: "processing" } | { status: "success" }
```

Potwierdzenie, które przejdzie, daje `success` tylko wtedy, gdy sesja zwrócona przez Stripe jest `complete`, a jej `paymentStatus` nie jest `unpaid`. Płatność BLIK albo Przelewy24, która jeszcze się nie rozliczyła, daje `processing`, a krok płatności czeka wtedy na bank zamiast otwierać potwierdzenie. Błąd z kodem `paymentFailed` to `declined`. Każdy inny błąd, który Stripe.js zwraca z kodem `null`, to `failed`, a krok płatności odczytuje wtedy status sesji, zanim zdecyduje, czy zostawić sesję z komunikatem Stripe, czekać na bank, otworzyć potwierdzenie, czy zresetować zamkniętą sesję (zobacz [Kasa](/docs/features/checkout)). `buildCheckoutContact(values)` wybiera adres do faktury, gdy `sameAsShipping === false`, a w przeciwnym razie adres dostawy.

Komponent `PaymentStep` w `src/presentation/components/custom/checkout/components/_steps/payment-step.client.tsx` montuje `CheckoutElementsProvider` kluczowany przez `sessionId`, przekazuje `getStripeAppearance(theme)` oraz `STRIPE_FONTS` i renderuje Payment Element jako akordeon z wyłączonymi portfelami i Link, a `paymentMethodOrder` bierze z `CHECKOUT_PAYMENT_METHOD_ORDER`.

Plik `stripe.appearance.ts` eksportuje `getStripeAppearance("light" | "dark")` — pełny obiekt `Appearance` dla Elements, w płaskim, kanciastym języku wizualnym sklepu opartym na obramowaniach — oraz `STRIPE_FONTS`, arkusz stylów Manrope potrzebny czcionce z wyglądu wewnątrz ramek Stripe. Korzystają z nich zarówno kasa, jak i formularz karty na stronie konta. Jego kolory to dosłowne wartości szesnastkowe odpowiadające tokenom projektowym, więc zmiana tokenu wymaga zmiany także tych wartości.

## Webhooki

Plik `src/routes/api/webhooks.stripe.ts` weryfikuje podpis przed czymkolwiek innym:

```ts
const event = await verifiedStripeEvent(request, signature, env.STRIPE_WEBHOOK_SECRET)
```

Brak nagłówka `stripe-signature` lub brak `STRIPE_WEBHOOK_SECRET` zwraca 400; nieudane `constructEventAsync` zwraca 400; zdarzenie, którego `livemode` nie pasuje do środowiska, live w `production` i testowe wszędzie indziej, jest logowane i odpowiadane `{ received: true }` bez uruchamiania handlera; zdarzenie z trybu testowego, którego obiekt niesie w metadanych `deployment` wskazujące inne wdrożenie, na przykład checkout lokalnego przebiegu testów docierający do preview, jest logowane na poziomie `info` jako `[Stripe] Ignoring event <id> (<typ>): its checkout belongs to <wdrożenie>, …` i odpowiadane tak samo (zobacz [Płatności](/docs/features/payments#punkt-końcowy-webhooka)); nieznany typ zdarzenia jest logowany i odpowiadany `{ received: true }`; handler, który rzuci wyjątek, zwraca 500, więc Stripe ponawia próbę, a w tle idzie e-mail na `RESEND_EMAIL_FROM`, raz na zdarzenie, niezależnie od tego, ile razy Stripe je ponowi. Handlery żyją w `stripe.webhooks.ts` jako zwykła mapa:

| Zdarzenie                                  | Zachowanie handlera                                                                                                                                                                                                                           |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkout.session.completed`               | `handleFulfillCheckoutSession` — tylko jeśli `payment_status` to `paid` lub `no_payment_required`, w przeciwnym razie loguje i czeka na zdarzenie asynchroniczne; potem w obu przypadkach `deleteCheckoutCoupons` usuwa oznaczony kupon sesji |
| `checkout.session.async_payment_succeeded` | Ta sama ścieżka realizacji (BLIK i P24 rozliczają się asynchronicznie)                                                                                                                                                                        |
| `checkout.session.async_payment_failed`    | `handleAsyncPaymentFailed` — zwalnia rezerwację i tylko wtedy, gdy to dostarczenie ją zwolniło, zapisuje audyt `orderReleased` i pisze do klienta                                                                                             |
| `checkout.session.expired`                 | Ta sama ścieżka zwolnienia, która zapisuje audyt `orderReleased` tylko wtedy, gdy coś zwolniła, więc sesja zastąpiona przez aktualizację checkoutu nie zostawia wpisu; potem `deleteCheckoutCoupons` usuwa oznaczony kupon sesji              |
| `payment_intent.payment_failed`            | Zapisuje audyt `orderPaymentFailed` z `last_payment_error.message`; bez zmiany stanu                                                                                                                                                          |
| `charge.refunded`                          | `refundOrder({ fullyRefunded, refundedAmount, transactionId })`, który nie przywraca stanu, potem `sendOrderRefundedEmail` dla zwrotu, o którym klient jeszcze nie wie                                                                        |
| `charge.dispute.created`                   | `flagOrderDispute(...)` — zamraża zamówienie i zapisuje audyt `orderDisputeOpened`                                                                                                                                                            |
| `charge.dispute.closed`                    | Jeśli `status === "lost"`, zapisuje zwrot przez `refundOrder`; w przeciwnym razie `clearOrderDispute(...)`                                                                                                                                    |

Realizacja parsuje pozycje z metadanych, wywołuje `fulfillCheckout({ currency, lines, locale, paidAmount, transactionId })` z `paidAmount` równym `session.amount_total`, a następnie — tylko jeśli funkcja zwróciła nowy `orderId`, co czyni handler idempotentnym wobec ponowień Stripe — zapisuje audyty `orderPlaced` i `orderPaymentCaptured`, planuje unieważnienie zamówień w panelu i katalogu produktów oraz wysyła e-mail potwierdzający, a razem z nim powiadomienie sklepu o nowym zamówieniu na `RESEND_EMAIL_FROM`. Ten e-mail linkuje do originu `return_url` sesji, czyli pod adres, na którym złożono zamówienie, a nie do hosta wywołanego przez Stripe, a `resolveDeploymentOrigin` go odrzuca, jeśli tego hosta nie obsługuje żadne wdrożenie. Krok e-maila nigdy nie rzuca wyjątku: odrzucone albo niemożliwe do przygotowania potwierdzenie jest zapisywane przy zamówieniu jako `email.failed`, a handler i tak kończy się sukcesem, więc Stripe nie dostarcza zdarzenia ponownie z powodu e-maila. Wysyłka trafia też do `scheduleBackgroundWork`, więc kończy się i zostaje zapisana nawet wtedy, gdy Stripe zerwie połączenie, zanim handler odpowie. Dla zamówienia z rabatem `fulfillCheckout` zapisuje wiersz `discount_redemption` i liczy wykorzystanie we własnym wsadzie zamówienia. Jeśli parsowanie metadanych albo `fulfillCheckout` się nie powiedzie, handler zapisuje audyt `order.fulfillment_failed` z poziomem `error`, podając kwotę, e-mail klienta i przyczynę, a potem rzuca błąd dalej, żeby Stripe ponowił zdarzenie, a ponowienie, które znów się nie powiedzie, nie dodaje drugiego wpisu, bo wpis ma klucz sesji; gdy `fulfillCheckout` zgłasza przez `ERROR_CODES.NOT_FOUND`, że żaden oczekujący checkout nie może przyjąć tej sesji, zapisuje ten sam audyt, w tle wysyła e-mail o tej sesji na `RESEND_EMAIL_FROM` i odpowiada `200`, bo ponowienie nic nie da (zobacz [Płatności: realizacja](/docs/features/payments#realizacja)).

Zdarzenie `charge.refunded` i handlery sporów otrzymują tylko PaymentIntent, więc `resolveCheckoutSession` listuje sesje Checkout filtrowane po `payment_intent` z `limit: 1`, aby odzyskać sesję, której identyfikatorem kluczowany jest wiersz `payment`. Handler zwrotu bierze też `return_url` sesji jako origin e-maila o zwrocie. Jeśli nie znajdzie sesji, handler loguje i kończy, zamiast zawodzić.

Dwa e-maile do klienta wysyłane przez te zdarzenia wychodzą raz na zdarzenie. E-mail o nieudanej płatności wychodzi tylko wtedy, gdy `releaseCheckout` zgłosi, że to dostarczenie przestawiło płatność sesji z `pending` na `failed`. E-mail o zwrocie wychodzi tylko wtedy, gdy `refundOrder` zgłosi, że `amount_refunded` płatności przekracza to, co płatność miała zapisane przed zdarzeniem, a sklep nie anulował zamówienia; anulowanie samo pisze do klienta o swoim zwrocie. Zobacz [E-maile transakcyjne](/docs/features/email#anulowanie-zwrot-i-nieudana-płatność).

Stripe przysyła powiązany obiekt albo jako jego identyfikator, albo, po rozwinięciu, jako sam obiekt. `resolveStripeObjectId` w `stripe.utils.ts` zwraca identyfikator w obu przypadkach, a dla `null` zwraca `undefined`. Używa go `resolveCheckoutSession` dla PaymentIntent, e-mail potwierdzający zamówienie dla PaymentIntent sesji, usuwanie zapisanej karty dla klienta karty oraz zwrot z panelu w `refund-admin-order.ts` dla PaymentIntent sesji Checkout, którą pobiera na podstawie `payment.transaction_id`, ponieważ Stripe zwraca PaymentIntent, a nie sesję. Zobacz [Płatności](/docs/features/payments).

Żadne zdarzenie zwrotu nie przywraca stanu magazynowego, bo zwrot pieniędzy nie mówi, czy towar wrócił: decyduje o tym administrator w oknie zwrotu albo przyciskiem Przywróć na stan w zamówieniu (zobacz [Zamówienia](/docs/features/orders#akcje-w-panelu)). Przegrany spór dodatkowo loguje `review inventory manually`, ponieważ towaru zwykle już nie ma.

## Sekrety

`STRIPE_SECRET_KEY` i `STRIPE_WEBHOOK_SECRET` to sekrety Workera wymienione w `wrangler.jsonc`; `VITE_STRIPE_PUBLISHABLE_KEY` to zmienna przeglądarkowa w plikach środowiska.

Oba klucze muszą pochodzić z tego samego trybu Stripe, a tryb musi odpowiadać środowisku. `deploy:preview` i `deploy:production` uruchamiają `scripts/verify-stripe-keys.ts <środowisko>` zaraz po `verify-bindings.ts`, przed kompilacją, i skrypt przerywa wdrożenie, jeśli klucze nie przejdą `verifyStripeKeys` z `stripe.keys.ts`:

| Środowisko               | `VITE_STRIPE_PUBLISHABLE_KEY` | `STRIPE_SECRET_KEY`        |
| ------------------------ | ----------------------------- | -------------------------- |
| `production`             | `pk_live_`                    | `sk_live_` albo `rk_live_` |
| `preview`, `development` | `pk_test_`                    | `sk_test_` albo `rk_test_` |

Klucz publiczny live obok testowego klucza tajnego, albo odwrotnie, jest odrzucany w każdym środowisku, bo formularz płatności nie otworzyłby sesji Checkout, które tworzy serwer. Klucze testowe na produkcji przyjmowałyby testowe karty Stripe przy prawdziwych zamówieniach, a klucze live w preview obciążyłyby prawdziwą kartę za testowe zamówienie. Odrzucany jest też brakujący lub pusty klucz oraz wartość, która nie jest kluczem właściwym dla swojej zmiennej, na przykład klucz tajny w `VITE_STRIPE_PUBLISHABLE_KEY`. Skrypt czyta każdy klucz najpierw ze środowiska procesu, potem z `.env.<środowisko>`, tak jak dostarczają je przepływy wdrożeniowe, i wypisuje nazwy zmiennych oraz ich tryb, nigdy sam klucz. `bun scripts/verify-stripe-keys.ts development` uruchamia tę samą kontrolę dla `.env.development`. Reguły mają testy jednostkowe w `__test__/stripe.keys.test.ts`.

Kontrola czyta tylko przedrostki. Nie pyta Stripe, czy klucze są nadal ważne, czy klucz ograniczony może zapisywać sesje Checkout, kupony, klientów, metody płatności, zwroty i SetupIntents, którymi zarządza sklep, i odczytywać jego PaymentIntents, ani czy istnieje produkcyjny endpoint webhooka. Przed pierwszym wdrożeniem produkcyjnym utwórz endpoint live pod `https://<host>/api/webhooks/stripe`, zasubskrybuj w nim osiem zdarzeń z `STRIPE_WEBHOOK_EVENTS`, zapisz jego własny `whsec_` jako produkcyjny `STRIPE_WEBHOOK_SECRET` i włącz BLIK oraz Przelewy24 w trybie live. Sekret `whsec_` nie zdradza, w którym trybie działa jego endpoint, więc wdrożenie nie może sprawdzić `STRIPE_WEBHOOK_SECRET`; zamiast tego trasa webhooka loguje i pomija każde zdarzenie z drugiego trybu (zobacz [Webhooki](#webhooki)). [Lista kontrolna przed startem sprzedaży](/docs/guides/go-live-checklist) zbiera te kroki ze wszystkim innym, czego produkcja potrzebuje, zanim przyjmie prawdziwe zamówienia.
