All persistent data lives in one Cloudflare D1 database, reached through Drizzle ORM. The adapter in `src/integrations/drizzle-orm/` is small on purpose: it creates the client, re-exports the table definitions that live in the feature modules, provides a few column helpers, and holds the drizzle-kit configuration and the migration files.

## The client

```ts
import "@tanstack/react-start/server-only"

import { env } from "cloudflare:workers"

import { drizzle } from "drizzle-orm/d1"

import * as schema from "~/src/integrations/drizzle-orm/drizzle.schemas"

export const db = drizzle(env.DB, { schema })
```

That is the whole of `drizzle.database.ts`. The `server-only` import makes any client-side import a build error. `env.DB` is the D1 binding declared per environment in `wrangler.jsonc`. Because the schema is passed in, `db.query.<table>` relational queries work everywhere.

## Where schemas actually live

`drizzle.schemas.ts` is a barrel and contains no table definitions. Each table is defined in the module that owns it, as `src/modules/{feature}/{feature}.schema.ts`, and re-exported here together with its relations:

```ts
export { product, productRelations } from "~/src/modules/product/product.schema"
export { productVariant, productVariantRelations } from "~/src/modules/product-variant/product-variant.schema"
export { inventory, inventoryRelations } from "~/src/modules/inventory/inventory.schema"
```

The barrel exports 41 tables. Drizzle needs a single object graph to resolve relations and drizzle-kit needs a single entry point, which is why this one file exists despite the project's usual rule against barrels.

| Area          | Tables                                                                                                                                                                                            |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity      | `user`, `session`, `account`, `verification`, `two_factor`, `rate_limit`                                                                                                                          |
| Catalog       | `product`, `product_variant`, `product_image`, `product_option`, `product_option_value`, `option_on_variant`, `product_category`, `product_collection`, `product_attribute`                       |
| Catalog joins | `category_on_product`, `collection_on_product`, `attribute_on_product`                                                                                                                            |
| Prices        | `price_history`                                                                                                                                                                                   |
| Commerce      | `cart`, `cart_item`, `checkout`, `payment`, `order`, `order_item`, `order_address`, `order_number_sequence`, `order_withdrawal`, `inventory`, `discount`, `discount_redemption`, `discount_claim` |
| Fulfilment    | `delivery_method`, `courier`                                                                                                                                                                      |
| Customer data | `address`, `wishlist_item`, `newsletter_subscriber`                                                                                                                                               |
| Content       | `content_page`, `newsletter_campaign`                                                                                                                                                             |
| Operations    | `audit_log`, `store_setting`                                                                                                                                                                      |

`storefront_search`, the FTS5 index behind storefront search, is the one table the barrel leaves out. `storefront-search.schema.ts` declares it for the search accessors, and the hand-written `20261002100000_storefront_search.sql` migration creates it together with the triggers that keep it in step with `product`, `product_category` and `product_collection`.

`price_history` is registered like any other table, but no application code writes it. `20261010410000_price_history.sql` creates it with two triggers on `product_variant`, `price_history_variant_insert` and `price_history_variant_update`, that add a row whenever a variant is created or its `price` or `compare_at_price` changes, and starts it with every variant's current prices. A migration that rebuilds `product_variant` drops those triggers with the old table and has to create them again.

A table definition reads like this, with its column lengths, defaults and indexes taken from the module's own constants:

```ts
export const product = sqliteTable(
  "product",
  {
    descriptions: text("descriptions", { mode: "json" }).$type<Product["localeMap"] | null>(),
    handle: text("handle", { length: PRODUCT_COLUMN_LENGTH.handle }).notNull().unique(),
    id: text("id", { length: PRODUCT_COLUMN_LENGTH.id }).primaryKey(),
    rank: integer("rank").notNull().default(PRODUCT_DEFAULT_RANK),
    status: text("status", { enum: PRODUCT_STATUSES }).default(DEFAULT_PRODUCT_STATUS).notNull(),
    titles: text("titles", { mode: "json" }).$type<Product["localeMap"]>().notNull(),
    ...timestamps(),
  },
  (table) => [
    index("product_primary_category_id_idx").on(table.primaryCategoryId),
    index("product_status_rank_idx").on(table.status, table.rank),
  ],
)
```

Translated fields are stored as JSON locale maps (`titles`, `subtitles`, `descriptions`, `tags`) rather than as separate translation rows. See [Internationalization](/docs/architecture/i18n-architecture) for how they are read.

## Column helpers

`drizzle.utils.ts` keeps the conventions in one place:

| Export                               | What it does                                                                                                                      |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `UUID_STRING_LENGTH`                 | `36`, the length every id column uses                                                                                             |
| `timestamp(name)`                    | An `integer` column with `{ mode: "timestamp_ms" }`                                                                               |
| `timestampNow(name)`                 | The same, defaulting to `(unixepoch() * 1000)` in SQL and `new Date()` in JS, `notNull`                                           |
| `timestamps()`                       | Spreads `createdAt` and `updatedAt`, where `updatedAt` also carries `$onUpdateFn(() => new Date())`                               |
| `calendarPeriodKey(column, periods)` | `(select key from json_each(?) where value <= column order by value desc limit 1)` for grouping by periods whose starts are given |

Timestamps are milliseconds since the epoch stored as integers, so any raw SQL you write against them has to divide by 1000 before `strftime`. `strftime` reads the time in UTC, and D1 has no other time zone, so grouping by the shop's own calendar goes through `calendarPeriodKey` instead: it takes periods as `{ key, start }`, sends their keys and start times as one JSON object, and gives each row the key of the last period that started at or before it. The admin dashboard builds its days, its months and the start of its year with `startOfCalendarDate` from `src/modules/_core/utils/datetime.ts`, in the time zone `resolveRequestDisplayPreferences()` resolves for the admin's request, and a customer's spending chart uses the same months. Each period therefore starts at midnight in the admin's own time zone, on both sides of a clock change; see [Admin dashboard](/docs/features/admin-dashboard#charts) and [use-intl](/docs/integrations/use-intl#display-preferences). Primary keys are UUIDv7 strings generated with `v7 as uuidv7` from the `uuid` package, both in use cases and in Better Auth's `advanced.database.generateId`.

## Batches

D1 supports batching several statements into one round trip. `drizzle.batch.ts` wraps it so callers do not have to handle the empty case:

```ts
export const runDrizzleBatch = async (statements: readonly DrizzleBatchStatement[]): Promise<void> => {
  if (statements.length === 0) {
    return
  }

  const [first, ...rest] = statements
  if (first === undefined) {
    return
  }
  await db.batch([first, ...rest])
}
```

`DrizzleBatchStatement` is `BatchItem<"sqlite">`. A D1 batch is applied as a single implicit transaction, which makes `runDrizzleBatch` the atomicity tool of this codebase. Nothing in `src/` calls `db.transaction()`: the D1 driver implements it by emitting separate `begin` and `commit` statements, and D1 does not offer interactive transactions across separate statements. Multi-step writes therefore either go into one batch, or compensate explicitly on failure the way the checkout flow releases reserved inventory.

A read that may match no row goes into a batch as a query-builder `select … limit 1`, never as `db.query.<table>.findFirst`. Awaited on its own, a `findFirst` that matches nothing resolves to `undefined`. Inside `db.batch`, the D1 driver of Drizzle 0.45 passes the empty result to the relational mapper as `[undefined]`, so `db.batch` throws after D1 has already run and committed every statement in it. The wishlist toggle reads its product this way (`getPublishedProductForCustomerQuery` in `wishlist.accessors.ts`).

### Staying within 100 bound parameters

D1 refuses a statement that binds more than 100 parameters, and the limit applies to every statement inside a batch. Two rules keep each statement under it, whatever the size of the shop:

- A list of ids built at runtime is bound once, as JSON, through `inJsonList` or `notInJsonList` from `drizzle.utils.ts`. They compile to `column in (select value from json_each(?))`, which SQLite still answers with one index seek per id, so a page of 250 rows and a whole catalog cost the same single parameter. `inArray` stays for fixed lists such as order statuses and for subqueries.
- Multi-row writes are split in `drizzle.batch.ts`: `insertRowChunks(table, rows)` sizes each insert by the table's column count, `chunkRankUpdates(idColumn, updates)` builds the `case … when` rank expression 49 rows at a time for the reorder use cases, and `chunkByBoundParameters` covers any other shape. The chunks go into one `runDrizzleBatch`, so the write stays atomic and still costs one round trip.

The D1 test double enforces the same limit, so an integration test that uses a full page of rows fails the way D1 would.

D1 also refuses a `LIKE` or `GLOB` pattern longer than 50 bytes with "LIKE or GLOB pattern too complex", which a full e-mail address can exceed. Admin search therefore finds a term with `instr(lower(cast(column as text)), lower(?)) > 0` (`containsAdminSearchTerm` in `src/modules/_core/utils/search-conditions.server.ts`), which takes a term of any length and matches `%` and `_` literally. The test double sets `likePatternLength` to 50 on the SQLite database it wraps, so a long `LIKE` pattern fails there as well.

## Prepared statements

Hot read paths precompile their SQL with `.prepare()` and `sql.placeholder()`. `src/modules/product/product.accessors.ts` is the densest example:

```ts
export const getProductVariantStatsQuery = db
  .select({
    minPrice: sql<number | null>`min(${productVariant.price})`,
    productId: productVariant.productId,
    totalStock: sql<number>`coalesce(sum(${inventory.quantityAvailable}), 0)`,
    variantCount: sql<number>`count(${productVariant.id})`,
  })
  .from(productVariant)
  .leftJoin(inventory, eq(inventory.variantId, productVariant.id))
  .where(sql`${productVariant.productId} in (select value from json_each(${sql.placeholder("productIds")}))`)
  .groupBy(productVariant.productId)
  .prepare()
```

Prepared queries are called with `.execute({ productIds: … })`. The `json_each` trick keeps a variable-length `IN` list inside a prepared statement, which a plain `inArray` cannot do.

| `preview`     | `martebizuteria-preview` | `1660d0df-fff9-463b-bbc6-dec65f754302` |
| `test`        | `martebizuteria-test`    | `00000000-0000-0000-0000-000000000001` |
| `production`  | `martebizuteria`         | `2bf4f35e-0a01-43c0-8a10-df5cc84ceb89` |

`development` and `preview` point at the **same remote database**, and they and `production` set `"remote": true`. There is no local SQLite file in the normal workflow: `bun run dev` talks to the real preview database. Treat preview data as shared state.

`test` is the exception. Its binding sets `"remote": false` and its id is a placeholder, because the database exists only on your machine: `db:reset:test` rebuilds it in `.wrangler/test`, and the end-to-end build (`build:test`, `start:test`) runs against it. Playwright resets it before a local run.

## drizzle-kit configuration

`drizzle.config.ts` uses the HTTP driver, so drizzle-kit can reach D1 from your machine without Wrangler:

```ts
export default defineConfig({
  dbCredentials: {
    accountId: process.env["CLOUDFLARE_ACCOUNT_ID"] ?? "",
    databaseId: process.env["CLOUDFLARE_DATABASE_ID"] ?? "",
    token: process.env["CLOUDFLARE_ACCESS_TOKEN"] ?? "",
  },
  dialect: "sqlite",
  driver: "d1-http",
  migrations: { prefix: "timestamp", schema: "public", table: "__drizzle_migrations__" },
  out: "./src/integrations/drizzle-orm/migrations",
  schema: "./src/integrations/drizzle-orm/drizzle.schemas.ts",
  strict: true,
  verbose: true,
})
```

Those three variables come from the environment file, which is why the `db:*` scripts pass `--env-file=.env.development`, `.env.preview` or `.env.production`. They are management credentials and live only in local tooling — they are not Worker secrets.

## Scripts

| Script                           | What it does                                                                                                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bun run db:generate`            | `drizzle-kit generate` — writes a new SQL migration plus a snapshot from the schema                                                                                  |
| `bun run db:migrate:local`       | `wrangler d1 migrations apply DB --env development --local`                                                                                                          |
| `bun run db:migrate:preview`     | The same `--remote` against the preview database (also the default `db:migrate`)                                                                                     |
| `bun run db:migrate:production`  | The same against the production database                                                                                                                             |
| `bun run db:migrate:development` | The same `--remote` against the `development` binding, which is the preview database                                                                                 |
| `bun run db:migrate:test`        | `--env test --local --persist-to .wrangler/test` — the local end-to-end test database                                                                                |
| `bun run db:seed:test`           | `scripts/seed-test.ts` — the eleven catalogue seeds, the test accounts, the admin's two-factor secret and a customer's saved time zone, into the local test database |
| `bun run db:reset:test`          | Deletes `.wrangler/test`, then runs `db:migrate:test` and `db:seed:test`                                                                                             |
| `bun run db:migrations:<env>`    | `wrangler d1 migrations list` — shows what has not been applied yet                                                                                                  |
| `bun run db:push:<env>`          | `drizzle-kit push` — pushes the schema without a migration file                                                                                                      |
| `bun run db:introspect:<env>`    | `drizzle-kit introspect` — regenerates `migrations/schema.ts` and `relations.ts`                                                                                     |
| `bun run db:studio:<env>`        | `drizzle-kit studio`                                                                                                                                                 |

`migrations/schema.ts` and `migrations/relations.ts` are introspection output, not hand-written sources. `src/integrations/**/migrations/**` is excluded from the formatter, the linter and the test run in `vite.config.ts`.

## Seeds

`migrations/../seeds/` contains eleven `.sql` files and `db:seed:preview` / `db:seed:production` apply them in dependency order. **These files are stale against the live databases and would overwrite real catalogue data.** Do not run them against preview or production. `db:seed:test` reads the same files, in the same order, into the local test database.

## Adding a migration

1. Change or add the table in `src/modules/{feature}/{feature}.schema.ts` and re-export it from `drizzle.schemas.ts` if it is new.
2. Run `bun run db:generate`.
3. Read the generated SQL. SQLite cannot drop or alter most constraints in place, so drizzle-kit sometimes emits a table rebuild — check that it preserves your data.
4. Apply it with `bun run db:migrate:preview`, verify against the preview database, then `bun run db:migrate:production`.
5. Run `bun run check` and `bun run test`. `src/integrations/drizzle-orm/__test__/query-plans.integration.test.ts` replays the whole migration history through `applyMigrationHistory` and fails when a foreign key has no index to serve it, when an index the schema declares is missing from the migrations or covers other columns or expressions there, when a hot read stops seeking through the index it relies on, or when the storefront product search stops collecting its matches in one step before it walks the catalogue.
