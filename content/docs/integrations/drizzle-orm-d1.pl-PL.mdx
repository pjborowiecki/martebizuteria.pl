Wszystkie trwałe dane mieszkają w jednej bazie Cloudflare D1, do której sięgamy przez Drizzle ORM. Adapter w `src/integrations/drizzle-orm/` jest celowo mały: tworzy klienta, ponownie eksportuje definicje tabel żyjące w modułach funkcjonalnych, dostarcza kilka pomocników kolumn oraz przechowuje konfigurację drizzle-kit i pliki migracji.

## Klient

```ts
import "@tanstack/react-start/server-only"

import { env } from "cloudflare:workers"

import { drizzle } from "drizzle-orm/d1"

import * as schema from "~/src/integrations/drizzle-orm/drizzle.schemas"

import { timeD1Statements } from "~/src/lib/server-timing"
import { cacheStorefrontReads } from "~/src/lib/storefront-cache.server"

const instrumentedBinding = (): D1Database => cacheStorefrontReads(timeD1Statements(env.DB))

class DeferredD1Database implements D1Database {
  batch = <TResult = unknown>(statements: D1PreparedStatement[]): Promise<D1Result<TResult>[]> =>
    instrumentedBinding().batch<TResult>(statements)

  dump = (): Promise<ArrayBuffer> => Promise.reject(new Error("D1 dump only applies to alpha databases"))

  exec = (query: string): Promise<D1ExecResult> => instrumentedBinding().exec(query)

  prepare = (query: string): D1PreparedStatement => instrumentedBinding().prepare(query)

  withSession = (constraintOrBookmark?: Parameters<D1Database["withSession"]>[0]): D1DatabaseSession =>
    instrumentedBinding().withSession(constraintOrBookmark)
}

export const db = drizzle(new DeferredD1Database(), { schema })
```

To cała treść `drizzle.database.ts`. Import `server-only` zamienia każdy import po stronie klienta w błąd budowania. `env.DB` to powiązanie D1 deklarowane osobno dla każdego środowiska w `wrangler.jsonc`. `timeD1Statements` z `src/lib/server-timing.ts` opakowuje je i dolicza czas każdej instrukcji i każdej partii do wpisu `d1` nagłówka `Server-Timing` wczytania strony (zobacz [Czasy żądań](/docs/guides/monitoring-and-alerts#czasy-żądań)); samej instrukcji nic nie zmienia. Całość opakowuje `cacheStorefrontReads` z `src/lib/storefront-cache.server.ts`, który publiczny odczyt katalogu wykonany wewnątrz `readThroughStorefrontCache` obsługuje z cache'u odczytów sklepu zamiast z D1 (zobacz [Cache i SSR](/docs/architecture/caching-and-ssr#cache-odczytów-sklepu)); każda inna instrukcja przechodzi prosto do D1. drizzle dostaje `DeferredD1Database`, którego metody opakowują `env.DB` przy każdym wywołaniu: gdy Cloudflare sprawdza przesłany skrypt, powiązanie nie jest jeszcze obiektem, więc opakowanie go przy ładowaniu modułu przerwałoby wdrożenie. Ponieważ schemat jest przekazywany do klienta, zapytania relacyjne `db.query.<table>` działają wszędzie.

## Gdzie naprawdę mieszkają schematy

`drizzle.schemas.ts` jest zbiorczym eksportem i nie zawiera żadnych definicji tabel. Każda tabela definiowana jest w module, który jest jej właścicielem, jako `src/modules/{feature}/{feature}.schema.ts`, i eksportowana tutaj ponownie wraz z relacjami:

```ts
export { product, productRelations } from "~/src/modules/product/product.schema"
export { productVariant, productVariantRelations } from "~/src/modules/product-variant/product-variant.schema"
export { inventory, inventoryRelations } from "~/src/modules/inventory/inventory.schema"
```

Zbiorczy eksport udostępnia 42 tabele. Drizzle potrzebuje jednego grafu obiektów do rozwiązania relacji, a drizzle-kit jednego punktu wejścia — dlatego ten plik istnieje, mimo ogólnej zasady projektu, by nie tworzyć zbiorczych eksportów.

| Obszar              | Tabele                                                                                                                                                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tożsamość           | `user`, `user_email_history`, `session`, `account`, `verification`, `two_factor`, `rate_limit`                                                                                                    |
| Katalog             | `product`, `product_variant`, `product_image`, `product_option`, `product_option_value`, `option_on_variant`, `product_category`, `product_collection`, `product_attribute`                       |
| Powiązania katalogu | `category_on_product`, `collection_on_product`, `attribute_on_product`                                                                                                                            |
| Ceny                | `price_history`                                                                                                                                                                                   |
| Sprzedaż            | `cart`, `cart_item`, `checkout`, `payment`, `order`, `order_item`, `order_address`, `order_number_sequence`, `order_withdrawal`, `inventory`, `discount`, `discount_redemption`, `discount_claim` |
| Realizacja dostaw   | `delivery_method`, `courier`                                                                                                                                                                      |
| Dane klienta        | `address`, `wishlist_item`, `newsletter_subscriber`                                                                                                                                               |
| Treści              | `content_page`, `newsletter_campaign`                                                                                                                                                             |
| Operacje            | `audit_log`, `store_setting`                                                                                                                                                                      |

`storefront_search`, indeks FTS5 stojący za wyszukiwarką sklepu, to jedyna tabela pominięta w zbiorczym eksporcie. `storefront-search.schema.ts` deklaruje ją na potrzeby akcesorów wyszukiwania, a ręcznie napisana migracja `20261002100000_storefront_search.sql` tworzy ją razem z wyzwalaczami, które utrzymują ją w zgodzie z `product`, `product_category` i `product_collection`.

`price_history` jest zarejestrowana jak każda inna tabela, ale nie zapisuje do niej żaden kod aplikacji. `20261010410000_price_history.sql` tworzy ją razem z dwoma wyzwalaczami na `product_variant`, `price_history_variant_insert` i `price_history_variant_update`, które dodają wiersz przy każdym utworzeniu wariantu i każdej zmianie jego `price` albo `compare_at_price`, i zaczyna ją od obecnych cen każdego wariantu. Migracja, która przebudowuje `product_variant`, usuwa te wyzwalacze razem ze starą tabelą i musi utworzyć je na nowo.

`user_email_history` też jest zarejestrowana jak każda inna tabela i też nie zapisuje do niej żaden kod aplikacji. `20261017140000_user_email_history.sql` tworzy ją razem z dwoma wyzwalaczami na `user`, `user_email_history_user_insert` i `user_email_history_user_update`, które dodają wiersz z adresem nowego konta, a gdy `email` zmienia się inaczej niż tylko wielkością liter, w tej samej instrukcji zamykają bieżący wiersz i otwierają wiersz nowego adresu, i zaczyna ją od obecnego adresu każdego konta oraz wcześniejszych adresów, które dziennik zdarzeń jeszcze zapisywał. Migracja, która przebudowuje `user`, usuwa te wyzwalacze razem ze starą tabelą i musi utworzyć je na nowo. Zobacz [Konto: Adresy używane przez konto](/docs/features/account#adresy-używane-przez-konto).

Definicja tabeli wygląda tak, a długości kolumn, wartości domyślne i indeksy pochodzą ze stałych własnego modułu:

```ts
export const product = sqliteTable(
  "product",
  {
    descriptions: text("descriptions", { mode: "json" }).$type<Product["localeMap"] | null>(),
    handle: text("handle", { length: PRODUCT_COLUMN_LENGTH.handle }).notNull().unique(),
    id: text("id", { length: PRODUCT_COLUMN_LENGTH.id }).primaryKey(),
    rank: integer("rank").notNull().default(PRODUCT_DEFAULT_RANK),
    status: text("status", { enum: PRODUCT_STATUSES }).default(DEFAULT_PRODUCT_STATUS).notNull(),
    titles: text("titles", { mode: "json" }).$type<Product["localeMap"]>().notNull(),
    ...timestamps(),
  },
  (table) => [
    index("product_primary_category_id_idx").on(table.primaryCategoryId),
    index("product_status_rank_idx").on(table.status, table.rank),
  ],
)
```

Pola tłumaczone przechowywane są jako mapy językowe w JSON (`titles`, `subtitles`, `descriptions`, `tags`), a nie jako osobne wiersze tłumaczeń. Sposób ich odczytu opisuje strona [Internacjonalizacja](/docs/architecture/i18n-architecture).

## Pomocniki kolumn

`drizzle.utils.ts` trzyma konwencje w jednym miejscu:

| Eksport                              | Działanie                                                                                                                          |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `UUID_STRING_LENGTH`                 | `36`, długość używana przez każdą kolumnę identyfikatora                                                                           |
| `timestamp(name)`                    | Kolumna `integer` z `{ mode: "timestamp_ms" }`                                                                                     |
| `timestampNow(name)`                 | To samo, z domyślną wartością `(unixepoch() * 1000)` w SQL i `new Date()` w JS, `notNull`                                          |
| `timestamps()`                       | Rozwija `createdAt` i `updatedAt`, gdzie `updatedAt` nosi dodatkowo `$onUpdateFn(() => new Date())`                                |
| `calendarPeriodKey(column, periods)` | `(select key from json_each(?) where value <= column order by value desc limit 1)` do grupowania po okresach o podanych początkach |

`UUID_STRING_LENGTH` importują pliki stałych, które wczytuje przeglądarka, więc moduł przy wczytaniu niczego z Drizzle nie wywołuje; build klienta pomija wtedy `drizzle-orm`, a `scripts/verify-build.ts` przerywa build, którego JavaScript klienta nadal go zawiera (zobacz [Baza danych](/docs/tooling/database)).

Znaczniki czasu to milisekundy od epoki przechowywane jako liczby całkowite, więc każde surowe SQL pisane przeciwko nim musi dzielić przez 1000 przed `strftime`. `strftime` odczytuje czas w UTC, a D1 nie zna innej strefy, więc grupowanie według kalendarza sklepu idzie przez `calendarPeriodKey`: przyjmuje okresy jako `{ key, start }`, wysyła ich klucze i początki jako jeden obiekt JSON i nadaje każdemu wierszowi klucz ostatniego okresu, który zaczął się nie później niż on. Panel administracyjny buduje swoje dni, miesiące i początek roku przez `startOfCalendarDate` z `src/modules/_core/utils/datetime.ts`, w strefie czasowej, którą `resolveRequestDisplayPreferences()` ustala dla żądania administratora, a wykres wydatków klienta korzysta z tych samych miesięcy. Każdy okres zaczyna się więc o północy we własnej strefie czasowej administratora, po obu stronach zmiany czasu; zobacz [Panel administracyjny](/docs/features/admin-dashboard#wykresy) i [use-intl](/docs/integrations/use-intl#preferencje-wyświetlania). Klucze główne to łańcuchy UUIDv7 generowane przez `v7 as uuidv7` z paczki `uuid`, zarówno w przypadkach użycia, jak i w `advanced.database.generateId` w Better Auth.

## Wsady

D1 obsługuje łączenie kilku instrukcji w jedno okrążenie sieciowe. `drizzle.batch.ts` owija tę funkcję, aby wywołujący nie musieli obsługiwać pustego przypadku:

```ts
export const runDrizzleBatch = async (statements: readonly DrizzleBatchStatement[]): Promise<void> => {
  if (statements.length === 0) {
    return
  }

  const [first, ...rest] = statements
  if (first === undefined) {
    return
  }
  await db.batch([first, ...rest])
}
```

`DrizzleBatchStatement` to `BatchItem<"sqlite">`. Wsad D1 wykonywany jest jako jedna niejawna transakcja, co czyni `runDrizzleBatch` narzędziem atomowości w tej bazie kodu. Nic w `src/` nie wywołuje `db.transaction()`: sterownik D1 realizuje tę metodę przez wysłanie osobnych instrukcji `begin` i `commit`, a D1 nie udostępnia transakcji interaktywnych rozciągniętych na osobne instrukcje. Zapisy wieloetapowe albo trafiają więc do jednego wsadu, albo jawnie kompensują błąd — tak jak proces zamówienia zwalnia zarezerwowany stan magazynowy.

Odczyt, który może nie znaleźć żadnego wiersza, trafia do wsadu jako `select … limit 1` z konstruktora zapytań, nigdy jako `db.query.<table>.findFirst`. Wykonany samodzielnie `findFirst`, który niczego nie znajduje, zwraca `undefined`. Wewnątrz `db.batch` sterownik D1 w Drizzle 0.45 przekazuje pusty wynik do mapera relacyjnego jako `[undefined]`, więc `db.batch` rzuca wyjątek, gdy D1 wykonał już i zatwierdził wszystkie instrukcje wsadu. W ten sposób przełączanie listy życzeń odczytuje produkt (`getPublishedProductForCustomerQuery` w `wishlist-item.accessors.ts`).

### Limit 100 parametrów

D1 odrzuca instrukcję, która wiąże więcej niż 100 parametrów, a limit obowiązuje każdą instrukcję wewnątrz wsadu. Dwie zasady utrzymują każdą instrukcję poniżej niego, niezależnie od wielkości sklepu:

- Lista identyfikatorów zbudowana w czasie działania jest wiązana raz, jako JSON, przez `inJsonList` albo `notInJsonList` z `drizzle.utils.ts`. Kompilują się do `column in (select value from json_each(?))`, na co SQLite nadal odpowiada jednym wyszukiwaniem w indeksie na identyfikator, więc strona 250 wierszy i cały katalog kosztują tak samo jeden parametr. `inArray` zostaje dla stałych list, takich jak statusy zamówień, i dla podzapytań.
- Zapisy wielowierszowe są dzielone w `drizzle.batch.ts`: `insertRowChunks(table, rows)` dobiera wielkość każdego insertu do liczby kolumn tabeli, `chunkRankUpdates(idColumn, updates)` buduje wyrażenie rangi `case … when` po 49 wierszy dla use case'ów zmiany kolejności, a `chunkByBoundParameters` obsługuje każdy inny kształt. Fragmenty trafiają do jednego `runDrizzleBatch`, więc zapis pozostaje atomowy i nadal kosztuje jedną podróż do bazy.

Testowy zamiennik D1 egzekwuje ten sam limit, więc test integracyjny na pełnej stronie wierszy zawodzi tak, jak zawiódłby D1.

D1 odrzuca też wzorzec `LIKE` lub `GLOB` dłuższy niż 50 bajtów komunikatem "LIKE or GLOB pattern too complex", a pełny adres e-mail potrafi go przekroczyć. Dlatego wyszukiwanie w panelu znajduje frazę przez `instr(lower(cast(column as text)), lower(?)) > 0` (`containsAdminSearchTerm` w `src/modules/_core/utils/search-conditions.server.ts`), które przyjmuje frazę dowolnej długości i dopasowuje `%` oraz `_` dosłownie. Testowy zamiennik ustawia `likePatternLength` na 50 w bazie SQLite, którą obsługuje, więc długi wzorzec `LIKE` zawodzi także tam.

## Instrukcje przygotowane

Gorące ścieżki odczytu prekompilują swoje SQL przez `.prepare()` i `sql.placeholder()`. Plik `src/modules/product/product.accessors.ts` jest najgęstszym przykładem:

```ts
export const getProductVariantStatsQuery = db
  .select({
    minPrice: sql<number | null>`min(${productVariant.price})`,
    productId: productVariant.productId,
    totalStock: sql<number>`coalesce(sum(${inventory.quantityAvailable}), 0)`,
    variantCount: sql<number>`count(${productVariant.id})`,
  })
  .from(productVariant)
  .leftJoin(inventory, eq(inventory.variantId, productVariant.id))
  .where(sql`${productVariant.productId} in (select value from json_each(${sql.placeholder("productIds")}))`)
  .groupBy(productVariant.productId)
  .prepare()
```

Przygotowane zapytania wywołuje się przez `.execute({ productIds: … })`. Sztuczka z `json_each` pozwala trzymać listę `IN` o zmiennej długości wewnątrz instrukcji przygotowanej, czego zwykłe `inArray` nie potrafi.

| `preview`           | `martebizuteria-preview` | `1660d0df-fff9-463b-bbc6-dec65f754302` |

Środowiska `development` i `preview` wskazują na **tę samą zdalną bazę**, a one i `production` mają `"remote": true`. W normalnym trybie pracy nie ma lokalnego pliku SQLite: `bun run dev` rozmawia z prawdziwą bazą preview. Traktuj dane preview jako stan współdzielony.

Wyjątkiem jest `test`. Jego powiązanie ma `"remote": false`, a identyfikator jest zaślepką, bo baza istnieje tylko na Twojej maszynie: `db:reset:test` odbudowuje ją w `.wrangler/test`, a build testów end-to-end (`build:test`, `start:test`) działa na niej. Playwright resetuje ją przed lokalnym uruchomieniem.

## Konfiguracja drizzle-kit

`drizzle.config.ts` korzysta ze sterownika HTTP, więc drizzle-kit dosięga D1 z Twojej maszyny bez Wranglera:

```ts
const accountId = process.env["CLOUDFLARE_ACCOUNT_ID"]
const databaseId = process.env["CLOUDFLARE_DATABASE_ID"]
const token = process.env["CLOUDFLARE_ACCESS_TOKEN"]

export default defineConfig({
  ...(accountId === undefined || databaseId === undefined || token === undefined
    ? {}
    : { dbCredentials: { accountId, databaseId, token } }),
  dialect: "sqlite",
  driver: "d1-http",
  migrations: { prefix: "timestamp", schema: "public", table: "__drizzle_migrations__" },
  out: "./src/integrations/drizzle-orm/migrations",
  schema: "./src/integrations/drizzle-orm/drizzle.schemas.ts",
  strict: true,
  verbose: true,
})
```

Te trzy zmienne pochodzą z pliku środowiska — dlatego skrypty `db:*` przekazują `--env-file=.env.development`, `.env.preview` lub `.env.production`. Są to dane uwierzytelniające do zarządzania i żyją wyłącznie w lokalnym oprzyrządowaniu; nie są sekretami Workera. Konfiguracja przekazuje je tylko wtedy, gdy ustawione są wszystkie trzy: `db:generate` ich nie potrzebuje, a `db:push`, `db:studio` i `db:introspect` bez nich kończą się komunikatem drizzle-kit, który wymienia brakujące `accountId`, `databaseId` i `token`.

## Skrypty

| Skrypt                           | Działanie                                                                                                                                                                    |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bun run db:generate`            | `drizzle-kit generate` — zapisuje nową migrację SQL wraz ze zrzutem stanu ze schematu                                                                                        |
| `bun run db:migrate:local`       | `wrangler d1 migrations apply DB --env development --local`                                                                                                                  |
| `bun run db:migrate:preview`     | To samo z `--remote` na bazie preview (jest to również domyślne `db:migrate`)                                                                                                |
| `bun run db:migrate:production`  | To samo na bazie produkcyjnej                                                                                                                                                |
| `bun run db:migrate:development` | To samo z `--remote` na powiązaniu `development`, czyli na bazie preview                                                                                                     |
| `bun run db:migrate:test`        | `--env test --local --persist-to .wrangler/test` — lokalna baza testów end-to-end                                                                                            |
| `bun run db:seed:test`           | `scripts/seed-test.ts` — jedenaście plików danych katalogu, konta testowe, sekret dwuskładnikowy administratora i zapisana strefa czasowa klienta, do lokalnej bazy testowej |
| `bun run db:reset:test`          | Usuwa `.wrangler/test`, a potem uruchamia `db:migrate:test` i `db:seed:test`                                                                                                 |
| `bun run db:migrations:<env>`    | `wrangler d1 migrations list` — pokazuje, czego jeszcze nie zastosowano                                                                                                      |
| `bun run db:push:<env>`          | `drizzle-kit push` — wypycha schemat bez pliku migracji                                                                                                                      |
| `bun run db:introspect:<env>`    | `drizzle-kit introspect` — odtwarza `migrations/schema.ts` i `relations.ts`                                                                                                  |
| `bun run db:studio:<env>`        | `drizzle-kit studio`                                                                                                                                                         |

Pliki `migrations/schema.ts` i `migrations/relations.ts` są wynikiem introspekcji, nie źródłami pisanymi ręcznie. Ścieżka `src/integrations/**/migrations/**` jest wyłączona z formattera, lintera i uruchomienia testów w `vite.config.ts`.

```
20261018100000_about_page
```

Migracje pisane ręcznie, takie jak `20260927120000_fix_silver_collection_handle.sql`, są w tym repozytorium normalne: naprawy danych, zmiany dotyczące wyłącznie indeksów i nowsze tabele, takie jak `order_number_sequence`, `discount_redemption`, `discount_claim`, `newsletter_subscriber`, `wishlist_item`, `storefront_search`, `content_page`, `store_setting`, `order_withdrawal`, `price_history`, `newsletter_campaign` i `user_email_history`, pisze się bezpośrednio i stosuje Wranglerem. Dziennikowi brakuje jednak także całego indeksu 38 (numeracja biegnie 0–52 z luką), a najnowszy zrzut, `meta/20260930151544_snapshot.json`, jest starszy od każdej z tych tabel, co oznacza, że `drizzle-kit generate` liczy różnicę ze zrzutu, który nie obejmuje wszystkiego, co faktycznie jest w bazie. Po `db:generate` przeczytaj wygenerowane SQL przed zastosowaniem i usuń wszystko, co ponownie tworzy już istniejący obiekt.

## Dane początkowe

Katalog `seeds/` zawiera jedenaście plików `.sql`, a skrypty `db:seed:preview` i `db:seed:production` stosują je w kolejności zależności. **Te pliki są przestarzałe wobec działających baz i nadpisałyby prawdziwe dane katalogu.** Nie uruchamiaj ich na preview ani na produkcji. `db:seed:test` wczytuje te same pliki, w tej samej kolejności, do lokalnej bazy testowej.

## Dodawanie migracji

1. Zmień lub dodaj tabelę w `src/modules/{feature}/{feature}.schema.ts` i ponownie wyeksportuj ją z `drizzle.schemas.ts`, jeśli jest nowa.
2. Uruchom `bun run db:generate`.
3. Przeczytaj wygenerowane SQL. SQLite nie potrafi usuwać ani zmieniać większości ograniczeń w miejscu, więc drizzle-kit czasem emituje przebudowę tabeli — sprawdź, czy zachowuje Twoje dane.
4. Zastosuj przez `bun run db:migrate:preview`, zweryfikuj na bazie preview, a następnie wykonaj `bun run db:migrate:production`.
5. Uruchom `bun run check` i `bun run test`. `src/integrations/drizzle-orm/__test__/query-plans.integration.test.ts` odtwarza całą historię migracji przez `applyMigrationHistory` i zawodzi, gdy klucz obcy nie ma obsługującego go indeksu, gdy indeks zadeklarowany w schemacie nie powstaje w migracjach albo obejmuje w nich inne kolumny lub wyrażenia, gdy gorący odczyt przestaje korzystać z indeksu, na którym polega, albo gdy wyszukiwanie produktów w sklepie przestaje zbierać dopasowania w jednym kroku, zanim przejdzie po katalogu.
