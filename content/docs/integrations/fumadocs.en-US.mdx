Fumadocs turns the MDX files under `content/docs` into the documentation site you are reading. The pattern is a collection defined in `src/integrations/fumadocs/`, a localized `loader`, a server function that resolves a page, and a client loader that renders the compiled MDX.

The legal pages at `/privacy-policy` and `/exchanges-and-returns` are not MDX files. Their Markdown is stored in D1 and edited in the admin panel, and the storefront renders it with `createMarkdownRenderer` from `fumadocs-core`. See [Legal pages](/docs/features/legal-pages).

## Collections

`fumadocs.config.ts` declares one:

```ts
export const docs = defineDocs({
  dir: "./content/docs",
})

export default defineConfig()
```

Documentation pages use the default schema: `title` is required, `description` is optional.

## Localization

`fumadocs.i18n.ts` is four lines of configuration that carry a lot of behaviour:

```ts
export const i18n = defineI18n({
  defaultLanguage: I18N.DEFAULT_LOCALE,
  fallbackLanguage: I18N.DEFAULT_LOCALE,
  hideLocale: "always",
  languages: [...I18N.SUPPORTED_LOCALES],
  parser: "dot",
})
```

- **`parser: "dot"`** is why files are named `page.pl-PL.mdx` rather than living in `pl-PL/page.mdx`. Both locales of a page sit next to each other in the same directory.
- **`hideLocale: "always"`** means Fumadocs never puts a locale into the URLs it generates. The locale prefix is entirely the application's business — see [use-intl](/docs/integrations/use-intl).
- **`fallbackLanguage`** is `pl-PL`, so an English page that has not been written yet resolves to the Polish one rather than 404ing. This is convenient and also a trap: a missing English translation looks like a working page. Both locale files are expected for every page.
- **`languages`** is spread from `I18N.SUPPORTED_LOCALES`, so the locale list has exactly one source of truth.

## The source

`fumadocs.docs.ts` builds the docs source at `ROUTES.DOCS`:

```ts
export const docsSource = loader({
  baseUrl: ROUTES.DOCS,
  i18n,
  source: docs.toFumadocsSource(),
})
```

It imports `docs` from `collections/server`, which is a `tsconfig.json` path alias pointing at `./.source/*` — the directory `fumadocs-mdx` generates.

## Generated output

```bash
bun run content
# fumadocs-mdx ./src/integrations/fumadocs/fumadocs.config.ts .source
```

That writes `.source/server.ts`, `.source/browser.ts` and `.source/dynamic.ts`. `bun run dev`, `bun run typegen` and both build scripts run it first, so you rarely call it by hand — but if TypeScript cannot resolve `collections/server`, that is the command. `.source` is listed in `.gitignore` and on the formatter's and linter's `ignorePatterns` list, and `bun run clean` deletes it.

The Vite side is a lazy plugin in `vite.config.ts`:

```ts
const { fumadocsMdx } = await import("fumadocs-mdx/vite")
const fumadocs = fumadocsMdx({ configPath: "./src/integrations/fumadocs/fumadocs.config.ts" })
```

It is included in both the normal plugin list and the Vitest-only list, which is what lets the component tests render real MDX pages.

## Resolving a documentation page

`fumadocs.docs.ts` exposes two server functions behind two thin wrappers.

`loadDocsPage(splat)` resolves the page and preloads its compiled module in parallel:

```ts
export const loadDocsPage = async (splat?: string) => {
  const [{ docsContent }, page] = await Promise.all([
    import("~/src/presentation/components/custom/docs-content"),
    getDocsPage({ data: { locale: getCurrentLocale(), slugs: docsSlugsOf(splat) } }),
  ])
  await docsContent.preload(page.path)

  return page
}
```

`getDocsPage` throws `notFound()` when the slug does not exist and otherwise returns only `{ description, path, title }` — the page _content_ is never serialized into the SSR payload, because the client loader imports the compiled module itself. `docsSlugsOf` converts a splat into slug segments (`undefined` or `""` becomes `[]`, the root page), and `docsSplatOf` does the reverse for links.

`loadDocsNavigation()` builds the sidebar. `buildDocsNavigation(locale)` walks the page tree, keeps only folders, and turns each into a section whose first link is the folder's own index page:

```ts
const folderPages = (folder: Folder): Item[] => [
  ...(folder.index === undefined ? [] : [folder.index]),
  ...folder.children.filter(isPageNode),
]
```

This is why `index` must **not** be listed in a folder's `meta.<locale>.json` `pages` array — Fumadocs already treats it as the folder index, and listing it would place it twice.

## The routes

| Route     | File                        | What it does                                                                                                               |
| --------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `/docs`   | `src/routes/docs.tsx`       | The layout: navigation, `DocsSidebar`, footer; the loader runs `loadDocsNavigation()` and `getCollectionsQuery()` together |
| `/docs`   | `src/routes/docs.index.tsx` | The root page, `loadDocsPage()` with no splat                                                                              |
| `/docs/$` | `src/routes/docs.$.tsx`     | Every other page, `loadDocsPage(params._splat)`                                                                            |

The layout declares `staticData: { namespaces: ["pages.docs"] }`, which is where the sidebar's own labels come from (`messages/{locale}/pages.docs.json`: `navigation.title`, `navigation.label`, `navigation.overview`). The page routes both set `head: pageHead` and `wrapInSuspense: false`.

`DocsSidebar` in `src/presentation/components/custom/pages/docs/docs-sidebar.tsx` renders an "Overview" link to `ROUTES.DOCS` followed by one group per section, using `LocalizedLink` with `activeOptions={{ exact: true }}`.

## Rendering MDX

`src/presentation/components/custom/docs-content.tsx` is the client loader:

```tsx
export const docsContent = browserCollections.docs.createClientLoader({
  component: ({ default: Mdx, frontmatter }) => (
    <article className="min-w-0 pb-16">
      <h1 className="font-serif text-4xl leading-tight tracking-tight md:text-5xl">{frontmatter.title}</h1>
      <Mdx components={docsMdxComponents} />
    </article>
  ),
  id: "docs",
})
```

The `<h1>` comes from the frontmatter `title`, which is why a page body should start at `##`.

### What components are available in a page

This is the most important constraint to know before writing a page. `docsMdxComponents` in `docs-mdx.tsx` spreads `mdxComponents` from `mdx.tsx` and adds a few more, and the whole map contains **only HTML element overrides**:

`a`, `h1`, `h2`, `h3`, `h4`, `p`, `ul`, `ol`, `li`, `strong`, `blockquote`, `code`, `pre`, `hr`, `table`, `th`, `td`.

There is **no `Callout`, `Cards`, `Steps`, `Tabs`, `Accordion` or `File`** component registered. Fumadocs' UI component library is not a dependency of this project — only `fumadocs-core` and `fumadocs-mdx` are. Writing `<Callout>` in a page would not render a callout. Documentation pages are therefore plain Markdown: headings, paragraphs, lists, tables, fenced code blocks and blockquotes, all styled by the map above.

`MdxLink` is the one component with behaviour. It localizes any href that starts with `/` and does not look like a file:

```ts
const ASSET_PATH_PATTERN = /\.[a-z0-9]+$/iu

href={isLocalizablePath(href) ? localizePathname({ locale: getCurrentLocale(), pathname: href }) : href}
```

So always write internal links without a locale — `/docs/integrations/stripe`, not `/en-US/docs/integrations/stripe` — and the reader's prefix is added for them. An external URL or a path ending in an extension (`/forms/formularz_zwrotu.pdf`) is left alone.

The legal pages reuse only the link from `mdxComponents`. Their article passes `{ a: mdxComponents.a }` to the Markdown renderer, so store paths in a legal page are localized the same way.

## Markdown at render time

`createMarkdownRenderer` from `fumadocs-core/content/md` compiles a Markdown string on render instead of at build time. `ContentPageArticle` creates one with `remarkGfm` and `remarkHeading`, which gives every heading a slug `id`. Raw HTML in the string is dropped. It is the right tool for text that lives in the database, while `fumadocs-mdx` remains the tool for files in the repository.

## Adding a documentation page

1. Create `content/docs/<section>/<slug>.en-US.mdx` **and** `<slug>.pl-PL.mdx`. Frontmatter is `title` and `description`.
2. Add `"<slug>"` to the `pages` array in **both** `content/docs/<section>/meta.en-US.json` and `meta.pl-PL.json`, in reading order. Do not list `index`.
3. Write plain Markdown. Start the body at `##`. Write internal links without a locale prefix.
4. Run `bun run content` (or restart `bun run dev`) so `.source` picks the files up.
5. Run `bun run format`, `bun run check` and `bun run test`.

## No search

The application has no `/api/search` route and does not use `fumadocs-core/search`. The documentation is navigated by the sidebar only. Adding search would mean a new handler route plus a client search component.

## Tests

`src/integrations/fumadocs/__test__/` holds three files. `fumadocs.config.test.ts` checks the collection directory. `fumadocs.docs.source.component.test.ts` checks that every page is served under the docs route, that the page tree turns each folder into a section with its index first, and the `docsSplatOf` / `docsSlugsOf` round trip — and it asserts that an unprefixed URL resolves the **Polish** page while an English URL resolves the English one. `fumadocs.docs.component.test.tsx` renders a real page and checks the body is rendered inside one `<article>`.
