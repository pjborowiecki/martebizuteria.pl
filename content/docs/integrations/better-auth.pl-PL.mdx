Better Auth odpowiada za tożsamość: logowanie e-mailem i hasłem, OAuth Google, weryfikację adresu e-mail, reset hasła, zmianę adresu e-mail, dwa czynniki, wiele sesji równocześnie oraz model roli administratora. Wszystko zapisuje w D1 przez adapter Drizzle i jest źródłem middleware `authorized()`, które deklaruje każda chroniona funkcja serwerowa.

## Instancja

Plik `src/integrations/better-auth/auth.server.ts` konfiguruje jedną instancję `betterAuth(...)` i nie zawiera niczego więcej: limity, ścieżki i odmowy, których używa, leżą w `auth.constants.ts`, logika jego hooków w `auth.hooks.server.ts`, jego wtyczki audytu w `auth.audit.server.ts`, a jego callbacki e-mailowe to przypadki użycia modułów verification, account i user. Elementy warte poznania:

| Opcja                          | Wartość                                                                                                                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `database`                     | `drizzleAdapter(db, { provider: "sqlite", schema })`                                                                                                                                                                                  |

| `advanced.ipAddress`           | Czyta `cf-connecting-ip` (`IP_ADDRESS_HEADER` z `src/lib/rate-limit.ts`)                                                                                                                                                              |

Ostatnia sprawia, że ciasteczka Better Auth współpracują z obsługą odpowiedzi w TanStack Start, i musi pozostać ostatnia w tablicy.

### Wbudowane ograniczanie liczby żądań

Własny limiter Better Auth jest włączony z `customStorage: authRateLimitStorage` z `src/lib/rate-limit.ts`, globalnym limitem 100 żądań na 60 sekund oraz regułami per punkt końcowy budowanymi z `ROUTES.API_AUTH` (`RATE_LIMIT_CUSTOM_RULES` w `auth.constants.ts`):

| Punkt końcowy             | Limit na 60 s |
| ------------------------- | ------------- |
| `/sign-in/email`          | 5             |
| `/sign-up/email`          | 3             |
| `/request-password-reset` | 3             |
| `/reset-password`         | 5             |

Jest to mechanizm odrębny od własnego middleware `withRateLimit` opisanego poniżej, ale oba liczą przez `withinRateLimit` w tabeli `rate_limit`. `authRateLimitStorage` przekazuje mu klucz Better Auth `<ip>|<ścieżka>` i pasującą regułę, a odmowa kończy się odpowiedzią 429 z oknem reguły w `X-Retry-After`. Better Auth nie używa `storage: "database"`, bo za każdym razem, gdy któryś z jego liczników zaczynał nowe okno, ta opcja usuwała każdy wiersz `rate_limit`, którego `last_request` był starszy niż najdłuższe okno Better Auth, czyli 60 sekund. `withinRateLimit` trzyma w `last_request` początek okna, więc godzinny i dzienny limit e-maili, o które może poprosić odwiedzający, znikałyby mniej więcej minutę po rozpoczęciu.

### Hooki bazodanowe

`databaseHooks` to miejsce, w którym zdarzenia konta docierają do reszty aplikacji, przez `handleUserCreated`, `handleUserUpdated` i `handleUserDeleted` z `auth.hooks.server.ts`:

- `user.create.after` wywołuje `scheduleAdminCustomersInvalidation()` oraz `recordCustomerRegisteredAudit(...)`.
- `user.update.after` i `user.delete.after` wywołują `scheduleAdminCustomersInvalidation()`, więc lista klientów w panelu odświeża się bez odpytywania.
- `user.delete.after` zapisuje też `customer.deleted` dla każdego konta poza anonimowym i przypisuje wpis sesji endpointu, który je usunął: administratorowi dla `/admin/remove-user`, które `deleteCustomer` wywołuje przez `auth.api.removeUser`, klientowi dla `/delete-user`, a systemowi, gdy żadna sesja o to nie prosiła.

### Usunięcie konta

`user.deleteUser.beforeDelete`, czyli `requireAccountDataErased` z `auth.hooks.server.ts`, wywołuje `eraseAccountData(user)` (`src/modules/user/user.erasure.server.ts`), które usuwa klienta Stripe powiązanego z kontem razem z zapisanymi kartami, a potem wpisy konta w dzienniku zdarzeń i subskrypcję newslettera. Gdy Stripe nie może usunąć klienta, funkcja zwraca `false`, a hook rzuca `APIError.from("SERVICE_UNAVAILABLE", { code: "STRIPE_CUSTOMER_NOT_DELETED" })`, więc żądanie kończy się odpowiedzią `503`, a Better Auth niczego nie usuwa. To usuwanie nie może być w `databaseHooks.user.delete.before`: `internalAdapter.deleteUser` usuwa sesje i wiersze `account`, zanim uruchomi ten hook, więc porażka Stripe zostawiłaby tam konto bez hasła. `auth.api.removeUser` nie ma `beforeDelete`, więc `deleteCustomer` sam wywołuje przed nim `eraseAccountData`. Zobacz [Konto: Usunięcie konta](/docs/features/account#usunięcie-konta).

### Audyt logowań

Nowa sesja nie zawsze oznacza logowanie. Better Auth tworzy ją także na etapie hasła przy logowaniu dwuskładnikowym (wtyczka `twoFactor` od razu ją usuwa), przy włączaniu i wyłączaniu uwierzytelniania dwuskładnikowego oraz przy zmianie hasła, która wylogowuje pozostałe urządzenia. Dlatego wtyczka `signInAudit` zapisuje `auth.login` z hooka „after”, a nie z `databaseHooks`. Dopasowuje ścieżki logowania (`/sign-in/`, `/sign-up/`, `/callback/`, `/verify-email` i `/two-factor/verify-`), działa po `twoFactor`, więc oczekujące wyzwanie dwuskładnikowe zdążyło już wyzerować `newSession`, i wywołuje `recordAuthLoginAudit(...)` dla każdego `ctx.context.newSession` poza takim, które kontynuuje sesję, z którą przyszło żądanie. Robią tak dwa żądania: potwierdzenie nowego adresu e-mail wydaje ponownie tę samą sesję, a potwierdzenie konfiguracji uwierzytelniania dwuskładnikowego przez `/two-factor/verify-*` zamienia zalogowaną sesję na nową. Dokończenie logowania dwuskładnikowego przychodzi bez sesji i zapisuje jedno logowanie; tak samo ponowne zalogowanie w przeglądarce, która wciąż jest zalogowana, bo klient znów podał hasło.

### Łączenie kont

Logowanie przez Google z adresem e-mail, który należy już do konta w sklepie, dołącza do tego konta tylko wtedy, gdy Google zgłasza ten adres jako zweryfikowany przez pole `email_verified` w swoim tokenie ID, i gdy własny adres konta w sklepie jest zweryfikowany (`requireLocalEmailVerified` w Better Auth, domyślnie włączone). W przeciwnym razie callback niczego nie łączy, nie tworzy sesji i przekierowuje na stronę błędu Better Auth z `error=account_not_linked`. `trustedProviders` pozostaje nieustawione: dla zaufanego dostawcy Better Auth pomija sprawdzenie po stronie dostawcy, więc każdy, kto dopisałby adres klienta do konta Google bez jego weryfikacji, zostałby zalogowany na konto tego klienta w sklepie. `auth.account-linking.integration.test.ts` przechodzi przez callback Google z adresem niezweryfikowanym i zweryfikowanym.

### Brak logowania anonimowego

Goście przeglądają sklep, kompletują koszyk i składają zamówienie bez logowania, więc Better Auth nie ładuje wtyczki `anonymous()`. Z nią każdy mógł wywołać `/api/auth/sign-in/anonymous` i dostać wiersz użytkownika z domyślną rolą `customer` oraz sesję, która przechodzi `authorized()`, a każde takie wywołanie zapisywało też `customer.registered` w dzienniku zdarzeń i dodawało wiersz do listy klientów w panelu. Ten endpoint odpowiada teraz 404, co sprawdza `auth.anonymous-sign-in.integration.test.ts`. Kolumna `user.is_anonymous` po tej wtyczce nadal oznacza utworzonych przez nią użytkowników; zobacz [Klienci w panelu](/docs/features/admin-customers).

### Reset hasła

Zakończony reset przez `/reset-password` wylogowuje konto wszędzie. Z `emailAndPassword.revokeSessionsOnPasswordReset: true` Better Auth usuwa wszystkie wiersze sesji użytkownika, gdy tylko zapisze nowe hasło, więc przeglądarka, która została zalogowana, także przeglądarka intruza, zostaje odrzucona przy następnym żądaniu, zamiast zachować dostęp do konta, dopóki jej sesja nie wygaśnie. Sama strona resetu jest niezalogowana, bo `/auth` odsyła zalogowanego odwiedzającego dalej, a jej komunikat o powodzeniu mówi klientowi, że konto zostało wylogowane na wszystkich urządzeniach. Zmiana hasła z profilu to inny punkt końcowy, `/change-password`, gdzie klient sam decyduje polem „Wyloguj moje pozostałe urządzenia”.

Better Auth czeka na `emailAndPassword.onPasswordReset({ user }, request)` po zapisaniu hasła, a przed usunięciem sesji. Hook przekazuje `sendPasswordChangedEmail({ request, user })` do `scheduleBackgroundWork` i od razu wraca, więc wylogowanie nigdy nie czeka na Resend, a e-mail i tak kończy się po odpowiedzi. E-mail mówi, że hasło zostało zmienione, a konto wylogowane na wszystkich urządzeniach, linkuje do `/auth/sign-in` pod adresem, na który przyszedł reset, a komuś, kto tej zmiany nie robił, każe zabezpieczyć skrzynkę, ustawić nowe hasło przez „Nie pamiętasz hasła?” i odpisać sklepowi. `sendPasswordChangedEmail` nigdy nie rzuca wyjątku, bo hook, który by go rzucił, odpowiedziałby na zakończony reset błędem 500 i pominął wylogowanie. Odmowa Resend, host spoza `appHostsForMode` i błąd przy przygotowaniu e-maila trafiają do logu i do audytu jako `email.failed`, a reset, który przyszedł bez żądania, co mogłoby się zdarzyć tylko przy wywołaniu `auth.api.resetPassword` po stronie serwera, jest zapisywany tak samo, bez wysyłki.

`auth.password-reset.integration.test.ts` loguje klienta w dwóch przeglądarkach, resetuje hasło z trzeciej przez `/request-password-reset` i `/reset-password` i sprawdza, że obie stare sesje są odrzucane i usunięte, że nowe hasło pozwala się zalogować, że e-mail linkuje do `http://localhost:3000/en-US/auth/sign-in` i że odrzucony e-mail nadal zostawia wszystkie urządzenia wylogowane. Test przeglądarkowy w `e2e/specs/auth.spec.ts` robi to samo przez formularze przypomnienia i resetu hasła.

### Audyt bezpieczeństwa konta

Wtyczka `accountSecurityAudit` zapisuje zmiany konta dokonywane przez Better Auth w hookach `after`, więc zostają odnotowane niezależnie od tego, który klient wywołuje endpoint. Hook niczego nie zapisuje, gdy endpoint odpowiedział błędem albo nie wywołała go żadna sesja. `/change-password` zapisuje `auth.password_changed`, a także `auth.sessions_revoked`, gdy treść żądania prosi o unieważnienie pozostałych sesji; `/two-factor/disable` zapisuje `auth.two_factor_disabled`, a `/revoke-session`, `/revoke-sessions` i `/revoke-other-sessions` zapisują `auth.sessions_revoked`, za każdym razem przypisane zalogowanemu kontu. `/two-factor/verify-totp` zapisuje `auth.two_factor_enabled` tylko wtedy, gdy wywołujący przyszedł z wyłączonym 2FA, a `newSession` wychodzi z włączonym, więc kod kończący logowanie dwuskładnikowe niczego tu nie zapisuje. `/verify-email` ponownie weryfikuje swój token przez `verifyJWT` z `better-auth/crypto` i zapisuje `auth.email_changed` ze szczegółem `stary → nowy` tylko dla tokenu `change-email-verification`, którego nowy adres ma już ponownie wydana sesja; potwierdzenie wysłane na stary adres i zwykła weryfikacja adresu niczego nie zapisują. Endpointy administracyjne `/admin/set-role`, `/admin/ban-user`, `/admin/unban-user`, `/admin/update-user`, `/admin/revoke-user-sessions` i `/admin/set-user-password` wyszukują konto wskazane przez `userId` i zapisują dla niego odpowiednie zdarzenie roli, blokady, adresu e-mail, sesji albo hasła, przypisane administratorowi. `/admin/revoke-user-session`, który wskazuje sesję tylko jej tokenem, oraz `/admin/impersonate-user` nie są zapisywane. Rejestratory są wybierane według ścieżki wewnątrz hooków, a nie trzymane w tabeli na poziomie modułu, bo `auth.server.ts`, `auth.audit.server.ts`, `audit-log.events.server.ts`, `audit-log.record.server.ts` i `auth.session.ts` importują się nawzajem, a tabela budowana w trakcie ładowania tego cyklu mogłaby przechwycić rejestrator, który nie jest jeszcze zdefiniowany. Pełną listę podaje [Dziennik zdarzeń](/docs/features/audit-log#zdarzenia-bezpieczeństwa-konta).

### Uwierzytelnianie dwuskładnikowe administratorów

W wersji produkcyjnej panel administracyjny otwiera się tylko administratorowi z włączonym uwierzytelnianiem dwuskładnikowym. `isAdminTwoFactorRequired()` w `auth.access.ts` jest prawdziwe dla buildu `production` i dla buildu `test`, na którym działa zestaw E2E, a fałszywe dla `preview` i `development`, gdzie uwierzytelnianie dwuskładnikowe pozostaje opcjonalne. `needsTwoFactorSetup({ role, twoFactorEnabled })` jest prawdziwe, gdy jest ono wymagane, a `user.two_factor_enabled` administratora nie wynosi `1`, i stosują je cztery miejsca:

| Gdzie                                             | Co dostaje administrator bez uwierzytelniania dwuskładnikowego                                          |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `requireAdmin` na layoucie `/admin`               | Przekierowanie na `/admin/security` zamiast panelu                                                      |
| `authorized(permission)`                          | `FORBIDDEN` dla każdego uprawnienia administracyjnego; `authorized()` bez uprawnienia nadal go wpuszcza |
| Uzgadnianie administracyjnego WebSocketu realtime | `401`                                                                                                   |
| `hooks.before` na `/admin/*` Better Auth          | `403` z `ADMIN_TWO_FACTOR_REQUIRED`; klient nadal dostaje odmowę samej wtyczki admin                    |

Administrator nigdy nie zostaje zablokowany. `/admin/security` to `admin_.security.tsx`, trasa poza layoutem `/admin` strzeżona przez `requireAdminRole`, który sprawdza tylko rolę. Renderuje `AdminSecurityPage`, która używa ponownie `SecuritySection` z konta: ten sam `TwoFactorDialog` włącza uwierzytelnianie dwuskładnikowe hasłem, kodem QR lub kluczem konfiguracyjnym, sześciocyfrowym kodem i kodami odzyskiwania, a wyłącza je hasłem. Profil pochodzi z `getCustomerProfileQuery`, którego `authorized()` nie wymaga uprawnienia. Po włączeniu strona prowadzi do panelu, a pozycja **Bezpieczeństwo** w sidebarze prowadzi z powrotem na nią. Administrator, który je wyłączy, wraca na tę stronę przy następnym otwarciu panelu. Poza wersją produkcyjną strona informuje, że uwierzytelnianie dwuskładnikowe jest opcjonalne, i od razu prowadzi do panelu. Strona pozwala też się wylogować. Konto założone przez Google nie ma hasła, a włączenie uwierzytelniania dwuskładnikowego go wymaga, więc `SecuritySection` pokazuje takiemu kontu **Ustaw** zamiast **Zmień** i blokuje **Włącz**, dopóki hasło nie istnieje. `SetPasswordDialog` wywołuje `setAccountPassword` (`src/modules/account/use-cases/set-account-password.ts`), które uruchamia dostępne tylko na serwerze `auth.api.setPassword` Better Auth na sesji wywołującego: tworzy brakujące konto `credential` i odmawia kontu, które ma już hasło, kodem `PASSWORD_ALREADY_SET`. Better Auth sprawdza tylko, czy sesja istnieje, więc `setAccountPassword` najpierw odmawia sesji starszej niż `SESSION_FRESH_AGE_IN_SECONDS` (24 godziny, to także `freshAge`, które Better Auth stosuje przy usuwaniu konta) kodem `SESSION_NOT_FRESH`: skradzione starsze ciasteczko sesji nie doda trwałego hasła, a właściciel zostaje poproszony o ponowne zalogowanie. Zmiana trafia do dziennika jako `auth.password_changed`. Strona konta używa tego samego `SecuritySection`, więc klienci zarejestrowani przez Google też mogą tam dodać hasło.

Administratorzy logują się hasłem i kodem uwierzytelniania dwuskładnikowego albo przez Google. Wtyczka `twoFactor` prosi o kod z hooka „after”, którego matcher obejmuje wyłącznie `/sign-in/email`, `/sign-in/username` i `/sign-in/phone-number` (`node_modules/better-auth/dist/plugins/two-factor/index.mjs`, Better Auth 1.7.5). Logowanie przez Google kończy się w `/callback/google`, którego ten hook nie widzi, więc otwiera pełną sesję bez kodu: administratorowi, który loguje się przez Google, kod sklepu zastępuje weryfikacja dwuetapowa jego konta Google. Łączenie kont dołącza też do administratora przy pierwszym logowaniu konto Google, którego zweryfikowany adres jest adresem administratora (zobacz [Łączenie kont](#łączenie-kont)), więc panel może otworzyć każdy, kto kontroluje to konto Google. Panel nadal wymaga włączonego uwierzytelniania dwuskładnikowego na koncie, niezależnie od sposobu logowania. Klienci logują się przez Google tak samo, więc na każdym koncie uwierzytelnianie dwuskładnikowe chroni tylko logowanie hasłem.

Pozostałe sposoby, w jakie Better Auth otwiera sesję istniejącemu administratorowi, nie pomijają kodu: zaufane urządzenie ustawia tylko logowanie dwuskładnikowe w tej przeglądarce, link weryfikacyjny loguje tylko niezweryfikowany adres, a potwierdzenie nowego adresu zaczyna się od zalogowanej sesji. Reset hasła nie otwiera sesji.

### E-maile transakcyjne

Pięć z szesnastu e-maili aplikacji wysyłanych jest na callbackach Better Auth, każdy przez przypadek użycia modułu, którego dotyczy: `sendVerifyEmail` i `sendResetPasswordEmail` w `src/modules/verification/use-cases/`, `sendChangeEmailConfirmationEmail` i `sendPasswordChangedEmail` w `src/modules/account/use-cases/` oraz `sendAccountDeletedEmail` w `src/modules/user/use-cases/`. Każda z tych funkcji ładuje własną przestrzeń nazw komunikatów, renderuje swój komponent React Email i przekazuje go do `deliverAuthEmail` z `auth.email-delivery.server.ts`, która wywołuje `sendEmail`. Gdy Resend odrzuci wiadomość, `recordAuthEmailFailure` loguje `[Auth] Failed to send <kind> email to <address>: <error>` i zapisuje wpis `email.failed` w dzienniku zdarzeń. Dodatkowo `resolveEmailVerificationCallbackUrl` z `send-verify-email.server.ts` przepisuje link weryfikacyjny, który prowadziłby na stronę główną sklepu, tak aby prowadził na `/account/overview?verified=true`. Zobacz [Resend](/docs/integrations/resend).

Linki w pierwszych trzech pochodzą z `url`, który Better Auth buduje na hoście żądania po sprawdzeniu go z `baseURL.allowedHosts`. `sendAccountDeletedEmail` linkuje do strony głównej sklepu na `origin`, który dostaje, a `deleteCustomer` ustala go przez `resolveRequestOrigin(getRequest())` przed `removeUser`. Po samodzielnym usunięciu konta `afterDelete(user, request)` ustala go przez `resolveRequestOrigin(request)` z żądania, które Better Auth przekazuje hookowi. Host spoza listy albo usunięcie, które przyszło bez żądania, jest logowane i zapisywane w audycie jako niewysłany e-mail pożegnalny, zamiast zamieniać zakończone usunięcie w 500. `sendPasswordChangedEmail` ustala origin linku do logowania tak samo, przez `resolveRequestOrigin(request)` z żądania, które Better Auth przekazuje do `onPasswordReset`.

Pierwsze trzy hooki przechodzą przez `requireAuthEmailDelivery`, która wysyła z `revealsAccountExistence: true` (zobacz [Blokada wysyłki e-maili](#blokada-wysyłki-e-maili)) i rzuca `APIError.from("SERVICE_UNAVAILABLE", { code: "EMAIL_DELIVERY_FAILED" })`, gdy Resend odrzuci e-mail. To, co zobaczy osoba, zależy od tego, jak Better Auth uruchamia hook:

| Punkt końcowy                                    | Gdy Resend odrzuci e-mail                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/send-verification-email`                       | Better Auth czeka na hook, więc żądanie odpowiada `503` z `EMAIL_DELIVERY_FAILED`. Formularze pokazują „Nie udało się teraz wysłać wiadomości. Spróbuj ponownie za kilka minut.”                                                                                                                                                       |
| `/sign-up/email`                                 | Better Auth uruchamia hook w tle i pomija jego błąd. Konto powstaje jako niepotwierdzone, a ogólna odpowiedź zostaje. Osoba prosi o nowy link na stronie logowania.                                                                                                                                                                    |
| `/request-password-reset`                        | Również w tle, a ogólna odpowiedź musi zostać: inna odpowiedź dla adresu z kontem zdradziłaby, że konto istnieje.                                                                                                                                                                                                                      |
| `/change-email`                                  | Również w tle. Gdy nowy adres jest już zajęty, Better Auth niczego nie wysyła, więc komunikat brzmi „Jeśli nowy adres jest dostępny, wysłaliśmy link potwierdzający na …” i prosi o ponowną próbę, jeśli nic nie dotrze. Weryfikacja wysyłana na nowy adres po potwierdzeniu zmiany także idzie w tle, już po przekierowaniu.          |
| `/reset-password` (`onPasswordReset`)            | `sendPasswordChangedEmail` działa w tle i nigdy nie rzuca wyjątku, bo hasło jest już zmienione, a Better Auth wylogowuje wszystkie urządzenia dopiero po powrocie z hooka. Reset odpowiada `200`, wszystkie urządzenia są wylogowane, a odmowa trafia do logu i dziennika zdarzeń.                                                     |
| `/delete-user` (`afterDelete`), `deleteCustomer` | `sendAccountDeletedEmail` zwraca `false` i nigdy nie rzuca wyjątku, bo konta już nie ma. Tak samo przechwytuje odmowę Resend i błąd przy przygotowaniu e-maila, a oba trafiają do logu i dziennika zdarzeń. Wyjątek z `afterDelete` zamieniłby zakończone usunięcie w błąd 500. `deleteCustomer` zwraca wynik jako `goodbyeEmailSent`. |

Usunięcie `advanced.backgroundTasks` nie zmieniłoby wierszy z wysyłką w tle: bez handlera Better Auth czeka na hook, ale nadal przechwytuje i loguje jego błąd.

### Blokada wysyłki e-maili

`sendEmail` oznacza nadawcę jako niedostępnego na pięć minut, gdy Resend odrzuca każdy e-mail, na przykład dlatego, że domena nadawcy nie jest zweryfikowana (zobacz [Resend](/docs/integrations/resend)). Dopóki flaga jest ustawiona, `hooks.before`, czyli `guardAuthRequest` z `auth.hooks.server.ts`, odrzuca `/sign-up/email`, `/request-password-reset`, `/send-verification-email` i `/change-email`, zanim punkt końcowy się wykona:

```ts
export const guardAuthRequest = createAuthMiddleware(async (ctx) => {
  if (EMAIL_SENDING_AUTH_PATHS.has(ctx.path) && (await isEmailSenderUnavailable())) {
    throw APIError.from("SERVICE_UNAVAILABLE", EMAIL_DELIVERY_UNAVAILABLE)
  }

  if (!ctx.path.startsWith(ADMIN_PLUGIN_PATH_PREFIX)) {
    return
  }

  const caller = await getSessionFromCtx<{ role?: string | null; twoFactorEnabled?: boolean | null }>(ctx)
  if (caller !== null && needsTwoFactorSetup(caller.user)) {
    throw APIError.from("FORBIDDEN", ADMIN_TWO_FACTOR_REQUIRED)
  }
})
```

Odpowiedzią jest `503` z `EMAIL_DELIVERY_UNAVAILABLE`, pokazywane jako „Chwilowo nie możemy wysyłać wiadomości e-mail, więc niczego nie zmieniliśmy. Spróbuj ponownie za kilka minut.” Nie powstaje żadne konto, nie jest zapisywany żaden token, a znane i nieznane adresy dostają tę samą odpowiedź. Ścieżki pochodzą z `ROUTES.API_AUTH`. Logowanie, linki weryfikacyjne, usuwanie konta i wszystkie pozostałe punkty końcowe przechodzą od razu, bez odczytu z KV. Drugie sprawdzenie w tym hooku odrzuca punkty końcowe `/admin/*` Better Auth dla administratora bez uwierzytelniania dwuskładnikowego; zobacz [Uwierzytelnianie dwuskładnikowe administratorów](#uwierzytelnianie-dwuskładnikowe-administratorów).

Flagę może ustawić tylko e-mail, którego wysłanie nic nie mówi o tym, jakie konta istnieją: e-maile newslettera (dostaje je każdy podany adres), potwierdzenie zamówienia, informacja o wysyłce, e-mail o usunięciu konta i e-mail o zmianie hasła, który trafia tylko do konta, którego link do resetu właśnie użyto, więc temu, kto go użył, nie mówi niczego nowego. Weryfikacja, link do zmiany hasła i potwierdzenie zmiany adresu wychodzą tylko wtedy, gdy konto istnieje albo nie istnieje, więc `requireAuthEmailDelivery` wysyła je z `revealsAccountExistence: true`, a `sendEmail` nie rusza wtedy flagi. Inaczej flaga zdradzałaby to, co ukrywają ogólne odpowiedzi: w czasie awarii wystarczyłoby poprosić o zmianę hasła dla jednego adresu, potem dla przypadkowego, a `503` przy drugim oznaczałoby, że pierwszy ma konto. Takie odmowy nadal trafiają do logu i dziennika zdarzeń.

Blokada włącza się więc dopiero wtedy, gdy Resend odrzuci któryś z pozostałych e-maili. Do tego czasu rejestracja, zmiana hasła i zmiana adresu zachowują ogólną odpowiedź o powodzeniu, choć ich e-maile nie wychodzą, bo inna odpowiedź na to jedno żądanie zdradziłaby, czy adres ma konto. Każda porażka jest w dzienniku zdarzeń, a komunikaty mówią osobie, żeby się zalogowała po nowy link potwierdzający albo poprosiła o nowy link do zmiany hasła, jeśli nic nie dotrze. Blokada tylko ogranicza szkody; zapobiega im sprawdzenie przed wdrożeniem, czy domena nadawcy jest zweryfikowana. Po wygaśnięciu flagi jedna prawdziwa próba znowu przechodzi; jeśli nadawca nadal nie działa, kolejny odrzucony e-mail ustawia flagę ponownie.

Jeśli KV nie da się odczytać, `isEmailSenderUnavailable` loguje `[Resend] Email sender availability unreadable` razem z błędem i odpowiada `false`, więc blokada przepuszcza żądanie. Zmiana hasła to droga powrotu do konta i nie może zależeć od KV; jeśli wysyłka potem się nie powiedzie, trafi do logu i dziennika zdarzeń jak każda inna.

Na stronie logowania logowanie odrzucone z `EMAIL_NOT_VERIFIED` pokazuje `UnverifiedEmailNotice` z przyciskiem „Wyślij link potwierdzający ponownie”. To wywołanie trafia do `/send-verification-email`, więc komunikat o powodzeniu, „Nowy link potwierdzający jest już w drodze na adres …”, pojawia się dopiero wtedy, gdy Resend przyjął e-mail albo gdy opisany niżej limit na adres po cichu go pominął. Better Auth zwraca `EMAIL_NOT_VERIFIED` dopiero po sprawdzeniu hasła, więc ta informacja nic nie zdradza komuś, kto hasła nie zna.

Sam punkt końcowy można jednak wywołać bez formularza i tam szczera odpowiedź ma swoją cenę. Bez zalogowania Better Auth wywołuje hook tylko dla adresu z niepotwierdzonym kontem, a dla każdego innego odpowiada `200`. Gdy pojedyncze wysyłki się nie udają (limit lub awaria po stronie Resend albo odmowa nadawcy, zanim flaga zostanie ustawiona), niepotwierdzone konto dostaje więc `503 EMAIL_DELIVERY_FAILED`, a nieznany lub potwierdzony adres `200`. Tak Better Auth traktuje hook, który rzuca wyjątek, i taka jest cena powiedzenia osobie prawdy o ponownej wysyłce. Zdradza to tylko niepotwierdzone konta, tylko gdy wysyłki zawodzą, przy domyślnym limicie Better Auth trzech żądań na minutę z jednego IP, a gdy flaga jest ustawiona, blokada odpowiada wszystkim adresom tak samo.

### Limity e-maili

Rejestracja, prośba o zmianę hasła i ponowne wysłanie weryfikacji każą sklepowi wysłać e-mail na dowolny adres podany w żądaniu. Powtarzane zalałyby czyjąś skrzynkę albo zużyły limit Resend, a wtedy przestałyby wychodzić także e-maile o zamówieniach. Oprócz opisanych wyżej limitów na IP ograniczają je dwie rzeczy.

**E-maile na adres.** `sendVerifyEmail` i `sendResetPasswordEmail` najpierw pytają `admitPublicEmail` z `src/integrations/resend/resend.public-email-limits.server.ts`, z rodzajem `verification` albo `password-reset`. Jeden adres dostaje najwyżej trzy e-maile każdego rodzaju na godzinę. Powyżej tego hook wraca bez wysyłki i loguje `[Email] Skipped a <kind> email to <address>: the address reached its hourly limit for this email`, a punkt końcowy odpowiada dokładnie tak jak po wysyłce: rejestracja i prośba o zmianę hasła zachowują ogólne odpowiedzi, a ponowne wysłanie weryfikacji odpowiada `200`. Odmowa padałaby tam tylko dla adresu z kontem albo z niepotwierdzonym kontem i by je zdradzała.

**E-maile na dobę.** To samo wywołanie liczy wszystkie e-maile, o które mogą poprosić odwiedzający, czyli te dwa rodzaje i e-maile newslettera, w ramach 50 na dobę dla całego sklepu. Powyżej tego e-mail zostaje pominięty z tą samą odpowiedzią, zalogowany przez `console.error` i zapisany jako `email.failed` ze szczegółem `Public <kind> email — the shop reached its daily limit of 50 emails that visitors can request`, więc dziennik zdarzeń pokazuje, że klienci nie dostają e-maili. Rejestracja nadal tworzy konto, a jego właściciel może poprosić o nowy link, gdy doba minie. E-maile o zamówieniach, o zmianie hasła, o usunięciu konta i potwierdzenie zmiany adresu nigdy nie przechodzą przez `admitPublicEmail`. Przechodzi przez nie e-mail weryfikacyjny, który Better Auth wysyła na nowy adres po potwierdzeniu jego zmiany, bo to także `sendVerifyEmail`. Zobacz [Resend: e-maile, o które może poprosić odwiedzający](/docs/integrations/resend#e-maile-o-które-może-poprosić-odwiedzający).

`auth.hooks.server.test.ts` obejmuje blokadę wysyłki na czterech punktach końcowych wysyłających e-maile i ścieżki, których hook nie rusza, a `auth.email-delivery.integration.test.ts` pokazuje, że prośba o zmianę hasła i ponowne wysłanie weryfikacji ponad limitem godzinowym dostają taką samą odpowiedź jak każda inna, że rejestracja w wyczerpany dzień nadal tworzy konto i że e-mail o zamówieniu w taki dzień nadal wychodzi.

## Role i uprawnienia

Plik `auth.access.ts` buduje model kontroli dostępu przy pomocy `createAccessControl` z Better Auth:

```ts
export const ROLES = { ADMIN: "admin", CUSTOMER: "customer" } as const

export const RESOURCES = { ORDER: "order", PRODUCT: "product", SETTINGS: "settings", USER: "user" } as const

export const ACTIONS = {
  CREATE: "create",
  DELETE: "delete",
  MANAGE: "manage",
  PUBLISH: "publish",
  READ: "read",
  REFUND: "refund",
  UPDATE: "update",
} as const

export const PERMISSIONS_STATEMENTS = {
  ...defaultStatements,
  [RESOURCES.ORDER]: [ACTIONS.READ, ACTIONS.UPDATE, ACTIONS.REFUND],
  [RESOURCES.PRODUCT]: [ACTIONS.CREATE, ACTIONS.READ, ACTIONS.UPDATE, ACTIONS.DELETE, ACTIONS.PUBLISH],
  [RESOURCES.SETTINGS]: [ACTIONS.MANAGE],
} as const
```

`ROLES_CONFIG.admin` otrzymuje wszystkie te uprawnienia oraz `adminAc.statements` (własne uprawnienia Better Auth do zarządzania `user` i `session`). `ROLES_CONFIG.customer` otrzymuje puste tablice dla każdego zasobu — klient nie ma żadnego uprawnienia administracyjnego. `DEFAULT_ROLE` to `customer`, a `ADMIN_PANEL_ROLES` to `["admin"]`.

Eksportowane są trzy predykaty, używane wszędzie:

```ts
export const hasAdminAccess = (role: string | null | undefined): role is Role =>
  typeof role === "string" && (ADMIN_PANEL_ROLES as readonly string[]).includes(role)

export const needsTwoFactorSetup = ({ role, twoFactorEnabled }: Readonly<TwoFactorAccessUser>): boolean =>
  hasAdminAccess(role) && twoFactorEnabled !== true

export const hasPermission = ({ permission, role }: { permission: Permission; role: string | null | undefined }): boolean =>
  isKnownRole(role) && ROLES_CONFIG[role].authorize(permission).success
```

## Middleware funkcji serwerowych

Plik `auth.middleware.ts` eksportuje trzy warstwy middleware, z których komponuje się każda funkcja serwerowa.

`withRequest` umieszcza nagłówki żądania w kontekście i przepuszcza każdy rzucony błąd przez jeden translator:

```ts
export const withRequest = createMiddleware({ type: "function" }).server(({ next }) =>
  next({ context: { requestHeaders: getRequest().headers } }).catch(handleRequestError),
)
```

`handleRequestError` najpierw rzuca dalej bez zmian `notFound()` z TanStack (`isNotFound`), więc trasa odpowiada kodem 404 zamiast 500. Następnie odtwarza `AppError` z jego kodu i zachowuje komunikat tylko wtedy, gdy jest on kodem przyczyny zapisanym wielkimi literami z podkreśleniami, na przykład `WISHLIST_FULL` lub `HAS_CHILDREN`, aby przeglądarka mogła wyjaśnić niepowodzenie. Każdy komunikat w postaci zwykłego tekstu zostaje zastąpiony kodem. `APIError` z Better Auth mapuje na `AppError(AUTH_API_ERROR, authErrorKey(error))`, `ZodError` na `AppError(VALIDATION)`, a wszystko inne na `AppError(INTERNAL_ERROR)` po zalogowaniu. Klient nigdy nie widzi surowego stosu wywołań ani komunikatu dostawcy.

`authorized(permission?)` nadbudowuje `withRequest`, ładuje sesję i albo ją odrzuca, albo umieszcza w kontekście:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && (!hasPermission({ permission, role: session.user.role }) || needsTwoFactorSetup(session.user))) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

Wywołane bez argumentu wymaga jedynie zalogowanego użytkownika; wywołane jako `authorized({ product: ["create"] })` wymaga także tego uprawnienia oraz uwierzytelniania dwuskładnikowego u administratora, który je ma. Przypadek użycia deklaruje więc swoją autoryzację w sygnaturze:

```ts
export const createCompleteProduct = createServerFn({ method: "POST" }).middleware([authorized({ product: ["create"] })])
```

Uprawnienie zależne od wiersza jest sprawdzane w handlerze przez `hasPermission` i sesję, którą `authorized` umieścił w `context.auth`. Jedynym takim przypadkiem jest `cancelOrder`: od middleware żąda `order: ["update"]`, a gdy po odczytaniu zamówienia znajdzie płatność do zwrotu, wymaga też `order: ["refund"]` i rzuca `AppError(FORBIDDEN)`, zanim wywoła Stripe albo cokolwiek zmieni.

`withRateLimit(kind, { max, window })` również nadbudowuje `withRequest` i stosuje własny limiter aplikacji, kluczowany przez `kind` i adres klienta:

```ts
export const RATE_LIMITS = {
  BROWSING: { max: 120, window: RATE_LIMIT_WINDOW_SECONDS },
  CHECKOUT: { max: 10, window: RATE_LIMIT_WINDOW_SECONDS },
  SENSITIVE: { max: 3, window: RATE_LIMIT_WINDOW_SECONDS },
  TOKEN: { max: 5, window: RATE_LIMIT_WINDOW_SECONDS },
} as const
```

Okno wynosi 60 sekund. Funkcja `withinRateLimit` w `src/lib/rate-limit.ts` realizuje limit jako jeden warunkowy upsert do tabeli `rate_limit` z `onConflictDoUpdate` i `setWhere`, więc licznik i okno przewijają się w jednej instrukcji. Jeśli tabela jest nieosiągalna, pomocnik zwraca `false` — limiter zawodzi w stronę odmowy.

## Strażnicy tras

Plik `auth.routes.ts` zawiera strażników _nawigacji_. Decydują o tym, co wyrenderować, nigdy o tym, czy operacja jest dozwolona; chronione funkcje serwerowe autoryzują się same przez `authorized()`. Każda trasa układu przekazuje swojego strażnika bezpośrednio jako `beforeLoad`: `/account` ma `beforeLoad: requireCustomer`, `/admin` ma `beforeLoad: requireAdmin`, a `/auth` ma `beforeLoad: redirectIfSignedIn`.

| Eksport                     | Zachowanie                                                                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `requireSignedIn(route)`    | Zwraca `{ user }` lub przekierowuje na `/auth/sign-in`                                                                              |
| `requireAdminRole(route)`   | Zwraca `{ user }`, jeśli `hasAdminAccess`, w przeciwnym razie przekierowuje na `/account/overview`; strzeże tylko `/admin/security` |
| `requireAdmin(route)`       | `requireAdminRole`, a potem przekierowuje na `/admin/security` administratora, dla którego zachodzi `needsTwoFactorSetup`           |
| `requireCustomer(route)`    | Zwraca `{ user }`, o ile użytkownik nie jest administratorem; administratora przekierowuje na `/admin`                              |
| `redirectIfSignedIn(route)` | Używane na stronach uwierzytelniania; odsyła zalogowanego gościa pod `?redirect` lub na jego stronę startową                        |
| `postAuthRouteFor(user)`    | `/admin` dla administratora, `/account/overview` dla klienta                                                                        |
| `authEntryRouteFor(user)`   | `/auth/sign-in`, gdy nie ma użytkownika, w przeciwnym razie `postAuthRouteFor`                                                      |

`route` to argument `beforeLoad`, czyli `{ context, location, preload }`. Obiekt `{ user }` zwracany przez strażnika staje się kontekstem trasy, więc strona odczytuje użytkownika typu `SessionUser` przez `Route.useRouteContext().user`.

Strażnicy czytają sesję przez `context.queryClient.query(getCurrentSessionQuery)`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

`requireSignedIn`, `requireAdminRole`, `requireAdmin` i `requireCustomer` przekazują `recheck: true`, więc prawdziwa nawigacja do `/account` lub `/admin` sprawdza sesję ponownie ze `staleTime: 0`. Wstępne ładowanie linku oraz `redirectIfSignedIn` na `/auth` z `recheck: false` korzystają z sesji z cache, jeśli ma ona mniej niż 60 sekund. Sesja załadowana przez strażnika zostaje w cache TanStack Query, więc komponenty, które ją czytają, widzą tę samą wartość, a przy renderowaniu na serwerze jest serializowana do strony, więc chronione strony renderują się na serwerze jako zalogowane. Strażnicy jedynie czytają sesję. Zmianę użytkownika obsługuje jedno miejsce, `clearCacheOnUserChange` w `auth.session.ts`: gdy sesja w cache przełącza się na innego użytkownika, niezależnie od tego, kto ją pobrał, funkcja usuwa z cache wszystkie pozostałe zapytania poza katalogami komunikatów tłumaczeń. Opisuje ją strona [TanStack Query](/docs/integrations/tanstack-query).

### Przekierowania po zalogowaniu

Anonimowy gość wchodzący na `/account` lub `/admin` jest przekierowywany na `/auth/sign-in?redirect=<ścieżka>`. `requireSignedIn` przekazuje `route.location.publicHref`, czyli zlokalizowaną ścieżkę publiczną, taką jak `/en-US/account/orders/order-1`. Jest ona zachowywana tylko wtedy, gdy jest łańcuchem pasującym do `SAME_SITE_PATH_PATTERN`:

```ts
const SAME_SITE_PATH_PATTERN = /^\/(?![/\\])[!-[\]-~]*$/u
```

Wzorzec dopuszcza wyłącznie drukowalne znaki ASCII (bez spacji), jeden ukośnik na początku i żadnego ukośnika wstecznego, więc bezwzględne URL-e, `//` bez protokołu, ukośniki wsteczne, białe znaki i znaki sterujące są odrzucane, a gość trafia na `/auth/sign-in` bez parametru. `redirectIfSignedIn` sprawdza parametr w ten sam sposób i odsyła zalogowanego gościa pod tę wartość przez `redirect({ href })`, w przeciwnym razie na `postAuthRouteFor(user)`. Ponieważ wartością jest ścieżka publiczna, przekierowanie wyrenderowane na serwerze zachowuje język gościa, a na kliencie router ponownie lokalizuje ją do bieżącego języka.

Po udanym logowaniu hasłem lub weryfikacji dwuskładnikowej formularz wywołuje `usePostAuthRedirect` z `src/hooks/use-post-auth-redirect.ts`:

```ts
export const usePostAuthRedirect = (): (() => Promise<void>) => {
  const queryClient = useQueryClient()
  const router = useRouter()

  return useCallback(async () => {
    queryClient.removeQueries({ exact: true, queryKey: getCurrentSessionQuery.queryKey })
    router.clearCache()
    await router.invalidate()
  }, [queryClient, router])
}
```

Hook usuwa z cache wyłącznie wpis sesji, a następnie czyści zapamiętane dopasowania routera i unieważnia router. Strażnik układu `/auth` uruchamia się ponownie, pobiera świeżą sesję i przekierowuje pod `?redirect`, jeśli jest to bezpieczna ścieżka w obrębie tej samej witryny, a w przeciwnym razie na `postAuthRouteFor(user)`. Gdy nadejdzie świeża sesja, `clearCacheOnUserChange` zapomina to, co trafiło do cache przed zalogowaniem. Formularze nigdy same nie wybierają celu.

Logowanie przez Google kończy się tak samo. `useOAuthSignIn` w `src/presentation/components/custom/pages/auth/hooks/use-oauth-sign-in.ts` przekazuje jako `callbackURL` stronę, na której kliknięto przycisk, odczytaną przez `useLocation` jako `location.publicHref`, na przykład `/en-US/auth/sign-in?redirect=...`. Po powrocie od dostawcy przeglądarka trafia na tę stronę uwierzytelniania, a `redirectIfSignedIn` kieruje użytkownika dalej dokładnie tak, jak po logowaniu hasłem.

Wylogowanie to pełne przeładowanie strony, które odrzuca cache: pasek boczny konta prowadzi na `/`, a pasek boczny panelu administracyjnego na `/auth/sign-in`.

## Czytanie sesji

Plik `auth.session.ts` unika dwukrotnego pytania Better Auth o tę samą sesję w jednym żądaniu, memoizując wynik na obiekcie `Request`:

```ts
const requestSessions = new WeakMap<Request, ReturnType<typeof auth.api.getSession>>()

export const getRequestSession = createServerOnlyFn((request: Request = getRequest()) => {
  const cached = requestSessions.get(request)
  if (cached) {
    return cached
  }

  const session = auth.api.getSession({ headers: request.headers, query: { disableCookieCache: true } })
  requestSessions.set(request, session)

  return session
})
```

`disableCookieCache: true` oznacza, że autoryzacja po stronie serwera zawsze czyta bazę, a nie ufa podpisanemu cache w ciasteczku. Cache w ciasteczku jest też wyłączony w `auth.server.ts`, więc własne punkty końcowe Better Auth za jego middleware sesji — `/update-user`, trasy uwierzytelniania dwuskładnikowego, `/get-session` — również czytają wiersz sesji: przeglądarka wylogowana z innego urządzenia zostaje od razu odrzucona, zamiast cieszyć się zaufaniem tak długo, jak żyło jej zapisane ciasteczko. `getCurrentSession` to opakowanie w funkcję serwerową, które przed zwróceniem usuwa `session.token` — token nigdy nie trafia do danych przesyłanych do przeglądarki. `getCurrentSessionQuery` to odpowiadający mu obiekt opcji zapytania i jedyna droga, którą trasy i komponenty czytają sesję: ładują ją strażnicy tras, a komponenty czytają ją przez `useQuery(getCurrentSessionQuery)`. Opisuje go strona [TanStack Query](/docs/integrations/tanstack-query).

## Klient

Plik `auth.client.ts` odzwierciedla wtyczki serwera i eksportuje tylko to, czego potrzebuje interfejs:

```ts
export const authClient = createAuthClient({
  plugins: [adminClient({ ac, roles: ROLES_CONFIG }), inferAdditionalFields<typeof auth>(), multiSessionClient(), twoFactorClient()],
})

export const { signIn, signOut, signUp, resetPassword } = authClient
```

`inferAdditionalFields<typeof auth>()` daje klientowi pole `timezone` bez drugiej deklaracji.

Hook `useSession` z Better Auth celowo nie jest eksportowany: uruchamiałby się podczas renderowania na serwerze, czego ochrona importów TanStack Start zabrania plikom `*.client.*` w buildzie serwerowym, i dodawałby drugie żądanie o sesję. Komponenty czytają sesję przez `useQuery(getCurrentSessionQuery)`.

## Walidacja i błędy

Plik `auth.constraints.ts` trzyma surowe limity (`EMAIL_MAX_LENGTH` 64, `NAME_MAX_LENGTH` 32, `PASSWORD_MIN_LENGTH` 8, `PASSWORD_MAX_LENGTH` 1024 oraz wzorce wielkiej litery i znaku specjalnego) wraz z `AUTH_VALIDATION_PARAMS`, które wstrzykuje te liczby do przetłumaczonych komunikatów.

Plik `auth.zod.ts` buduje z nich schematy formularzy: `signInWithPasswordSchema`, `signUpWithPasswordSchema`, `forgotPasswordSchema` i `resetPasswordSchema`. Każdy `message` jest _kluczem tłumaczenia_, a nie tekstem po angielsku — `"passwordMinLength"`, `"passwordsMustMatch"`, `"invalidEmail"` — który warstwa formularza rozwiązuje w `messages/{locale}/pages.auth.*.json`. Logowanie używa łagodnego `signInPasswordSchema` (niepuste), a rejestracja i reset hasła — `strictPasswordSchema`, więc istniejące słabe hasło nadal pozwala się zalogować.

Plik `auth.errors.ts` mapuje kody błędów Better Auth na te same klucze komunikatów przez `AUTH_ERRORS`, a `authErrorKey(error)` parsuje zarówno `{ code }`, jak i `{ body: { code } }`, z wartością domyślną `unknownError`.

## Punkt końcowy HTTP

`src/routes/api/auth.$.ts` to trasa złożona wyłącznie z handlera, która nie wywołuje `auth.handler` bezpośrednio, ale go owija:

```ts
export const Route = createFileRoute("/api/auth/$")({
  server: {
    handlers: {
      GET: ({ request }) => handleAuthRequestWithAudit(request),
      POST: ({ request }) => handleAuthRequestWithAudit(request),
    },
  },
})
```

Funkcja `handleAuthRequestWithAudit` w `src/modules/audit-log/audit-log.auth.server.ts` sprawdza ścieżkę przed delegacją: dla `POST /sign-in/email` klonuje żądanie, aby odczytać adres e-mail, i zapisuje wpis audytu o nieudanym logowaniu, jeśli odpowiedź nie jest poprawna; dla `POST /sign-out` najpierw pobiera sesję i zapisuje wpis wylogowania, jeśli odpowiedź jest poprawna. Udane logowania audytuje natomiast wtyczka `signInAudit` (zobacz sekcję „Audyt logowań” wyżej).

## Tabele

`user`, `session`, `account`, `verification`, `two_factor` i `rate_limit`. Każda z nich definiowana jest we własnym module (`src/modules/user/user.schema.ts` i tak dalej) i ponownie eksportowana z `drizzle.schemas.ts`. Tabela `user` nosi dodatki aplikacji wykraczające poza własne kolumny Better Auth: `role` (wyliczenie `admin` / `customer`), `phone`, `timezone`, `stripe_customer_id`, `metadata` oraz flagi blokady i dwóch czynników. `session.token` to unikalna kolumna tekstowa o długości 16 KiB, a `session.user_id` kaskaduje przy usuwaniu.

## Sekrety

`AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID` i `AUTH_GOOGLE_CLIENT_SECRET` — wszystkie wymienione pod `secrets.required` dla każdego środowiska w `wrangler.jsonc`.
