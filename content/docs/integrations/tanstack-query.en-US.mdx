TanStack Query is the only data cache in the application. Route loaders prime it on the server, components read it on the client, mutations invalidate it, and two separate channels push invalidations in from outside: a WebSocket hub from the Worker, and a `BroadcastChannel` between tabs for the few local changes the hub does not carry.

## One client per request

`getRouter()` in `src/router.tsx` builds a fresh `QueryClient` for every request, so nothing leaks between visitors on the Worker:

```tsx
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      gcTime: FIVE_MINS_IN_MS,
      staleTime: ONE_MIN_IN_MS,
    },
  },
})
```

`setupRouterSsrQueryIntegration({ queryClient, router })` dehydrates whatever the loaders fetched into the SSR payload and rehydrates it in the browser, so a loader's work is not repeated on hydration. The client is exposed through the router context as `context.queryClient`, which is how loaders reach it.

## Query options live with the use case

There is no central query registry. Each feature exports its query options from the same file as the server function they call, in `src/modules/{feature}/use-cases/{verb-noun}.ts`:

```ts
export const getCategories = createServerFn({ method: "GET" })
  .middleware([withRequest])
  .handler(async () => {
    /* … */
  })

export const getCategoriesQuery = () =>
  queryOptions({
    queryFn: () => getCategories(),
    queryKey: CATEGORY_QUERY_KEYS.ALL,
    staleTime: CATEGORY_QUERY_STALE_MS,
  })
```

Loaders, components and cache operations all use that same `getCategoriesQuery()`, so a key and a stale time are never written twice. Infinite lists use `infiniteQueryOptions` the same way — `getStorefrontProductsPageQuery(search, scope)` in `src/modules/product/use-cases/get-storefront-products-page.ts` derives its key from the normalized search object:

```ts
queryKey: [...PRODUCT_QUERY_KEYS.STOREFRONT_PAGE, effective],
getNextPageParam: (lastPage, _allPages, lastPageParam) =>
  (!filtered && lastPage.hasMore ? lastPageParam + LIST_PAGE_STEP : undefined),
initialPageParam: LIST_PAGE_FIRST,
```

## Query keys

Keys belong to the feature that owns the data, in `src/modules/{feature}/{feature}.constants.ts`, as `as const` tuples:

```ts
export const PRODUCT_QUERY_KEYS = {
  ADMIN: {
    ALL: ["admin", "products"] as const,
    BY_HANDLE: ["admin", "products", "by-handle"] as const,
    PAGE: ["admin", "products", "page"] as const,
    STATS: ["admin", "products", "stats"] as const,
  },
  ALL: ["products"] as const,
  BY_HANDLE: ["product"] as const,
  LANDING_NEW_ARRIVALS: ["products", "landing-new-arrivals"] as const,
  RELATED_BY_CATEGORY: ["related-products"] as const,
  STOREFRONT_PAGE: ["products", "storefront-page"] as const,
} as const
```

The `ADMIN` sub-object prefixes every admin key with `"admin"`, which is what lets the two realtime hubs invalidate disjoint sets of keys. Mutation keys live beside them as `PRODUCT_MUTATION_KEYS`. When you move code, preserve the tuple values: a changed key silently orphans cache entries and breaks the prefix matching described below.

## Prefetching in loaders

Loaders call `queryClient.query(...)` for a single query and `queryClient.infiniteQuery(...)` for a paginated one, then let the component subscribe to the already-warm cache. `src/presentation/components/custom/pages/products-catalog/products-catalog.loader.ts` shows the shape:

```ts
const [infiniteData] = await Promise.all([
  queryClient.infiniteQuery(getStorefrontProductsPageQuery(normalizedSearch, scope)),
  scope?.categoryHandle === undefined ? queryClient.query({ ...getCategoriesQuery(), staleTime: "static" }) : undefined,
  scope?.collectionHandle === undefined ? queryClient.query({ ...getCollectionsQuery(), staleTime: "static" }) : undefined,
])
```

`staleTime: "static"` marks the categories and collections as reference data that should not refetch on this navigation. The first page's thumbnails are then handed to `prefetchProductThumbnails` so the image requests start before the component mounts.

## Message loading

Translations use the same cache. `messagesQueryOptions` in `src/integrations/use-intl/i18n.messages.ts` sets both `staleTime` and `gcTime` to `Infinity`, because a JSON namespace never changes within a deployment:

```ts
queryOptions({
  gcTime: Infinity,
  queryFn: () => loadNamespace<TMessages>({ locale, namespace }),
  queryKey: [MESSAGES_QUERY_KEY, locale, namespace],
  staleTime: Infinity,
})
```

`TranslationsProvider` reads them with `useSuspenseQueries` and combines the results into one message tree. See [use-intl](/docs/integrations/use-intl).

## The session query

`src/integrations/better-auth/auth.session.ts` exports `getCurrentSessionQuery`, which deliberately opts out of background refetching so a signed-in header does not flicker:

```ts
export const getCurrentSessionQuery = queryOptions({
  queryFn: () => getCurrentSession(),
  queryKey: SESSION_QUERY_KEYS.CURRENT,
  refetchOnReconnect: false,
  refetchOnWindowFocus: false,
  retry: false,
  staleTime: SESSION_STALE_TIME_MS,
})
```

It is the only way routes and components read the session. The route guards in `src/integrations/better-auth/auth.routes.ts` load it with `context.queryClient.query(getCurrentSessionQuery)`: a real navigation into `/account` or `/admin` re-checks with `staleTime: 0`, while a link preload and the `/auth` guard reuse a cached session younger than 60 seconds. On a server render the session is dehydrated into the page with the loaders' data, so guarded pages render signed-in on the server. Components read the same entry with `useQuery(getCurrentSessionQuery)`; the navigation link, the translations time zone, the wishlist and the checkout prefill all do.

The guards only read the session. A change of user is handled in one place: `clearCacheOnUserChange(queryClient)`, also exported from `auth.session.ts`, subscribes to the query cache. Whenever the session query's data switches to a different user id, including signed out to signed in and back, it removes every cached query except the session itself and the translation message catalogues, matched by `isMessagesQuery` from `src/integrations/use-intl/i18n.messages.ts`. It ignores the first session it sees and the session entry being removed:

```ts
export const clearCacheOnUserChange = (queryClient: QueryClient): (() => void) => {
  const seen: { session?: Awaited<ReturnType<typeof getCurrentSession>> } = {}

  return queryClient.getQueryCache().subscribe(({ query }) => {
    const session = query.queryHash === SESSION_QUERY_HASH ? queryClient.getQueryData(getCurrentSessionQuery.queryKey) : undefined
    if (session === undefined) {
      return
    }

    if ("session" in seen && seen.session?.user.id !== session?.user.id) {
      queryClient.removeQueries({ predicate: (cached) => cached.queryHash !== SESSION_QUERY_HASH && !isMessagesQuery(cached) })
    }
    seen.session = session
  })
}
```

Because it watches the cache, it catches a change whoever fetched the session: a guard, a component such as the navigation link, the wishlist or the translations time zone, a refetch after invalidation, or hydration. `getRouter` in `src/router.tsx` installs it in the browser only, next to `setupQueryClientInvalidationBroadcast`. Server rendering skips it, because every request starts with an empty `QueryClient`.

After a password sign-in or a two-factor challenge, `usePostAuthRedirect` removes only the cached session entry, then clears the router's cached matches and invalidates the router. The `/auth` guard fetches the fresh session, and `clearCacheOnUserChange` forgets what was cached while signed out. Sign-out is a full page load, which discards the whole cache. The guards and the redirect flow are described in [Better Auth](/docs/integrations/better-auth).

## Invalidating a prefix

`src/integrations/tanstack-query/query.invalidation.ts` holds the policy that every pushed or cross-tab invalidation applies:

```ts
export const invalidateQueryPrefix = async (queryClient: QueryClient, queryKey: QueryKey): Promise<void> => {
  queryClient.removeQueries({
    fetchStatus: "idle",
    predicate: (query) => query.getObserversCount() === 0 && query.queryType !== "infinite",
    queryKey,
  })

  await Promise.all([
    queryClient.invalidateQueries({ queryKey, refetchType: "active" }),
    queryClient.refetchQueries({ fetchStatus: "fetching", queryKey, type: "inactive" }),
  ])
}
```

Removing the idle queries that nothing observes comes first. Removing a query whose fetch is in flight would cancel it silently and make the loader awaiting it reject, which is why only `fetchStatus: "idle"` queries go. An infinite list is kept as well: its entry holds every page the visitor loaded, which one fetch cannot rebuild, so the storefront catalogue keeps its pages and scroll position when the shopper comes back to it. `query.queryType` is the marker query-core sets on every infinite query; it is marked internal, so the `query.invalidation` tests fail if an upgrade renames it.

`invalidateQueries` with `refetchType: "active"` then marks every remaining query invalid and refetches the ones on screen. A kept infinite list is only marked invalid, and its next loader or mount refetches all its pages. An observed but disabled query is only marked invalid and refetches once it is enabled. `refetchQueries` with `type: "inactive"` and `fetchStatus: "fetching"` restarts the unobserved fetches already in flight, so the loader awaiting one resolves with the post-event response. query-core skips a query that was never fetched, so a first fetch in flight finishes as it is.

Every removed query is fetched fresh by the next loader or mount, even when the loader reads with `staleTime: "static"` and the query sets `refetchOnMount: false`. `refetchType: "active"` alone would leave such a loader returning the stale entry, because a `"static"` stale time never looks at `isInvalidated`. Call `invalidateQueryPrefix` directly for a refresh only this tab needs, such as the refresh buttons of the admin tables.

## Cross-tab invalidation

`src/integrations/tanstack-query/query.sync.ts` mirrors invalidations across browser tabs of the same origin over a `BroadcastChannel` named `marte-query-invalidation`:

```ts
export const syncQueryInvalidation = (queryClient: QueryClient, queryKey: QueryKey): Promise<void> => {
  const invalidation = invalidateQueryPrefix(queryClient, queryKey)

  try {
    getInvalidationChannel()?.postMessage({ queryKey })
  } catch {
    return invalidation
  }

  return invalidation
}
```

`setupQueryClientInvalidationBroadcast(queryClient)` installs the listener, which applies `invalidateQueryPrefix` to every key it receives, and `src/router.tsx` calls it once per client, guarded by `if (!import.meta.env.SSR)`. Both functions are defensive: `getInvalidationChannel` returns `undefined` when `document` or `BroadcastChannel` is missing, a `WeakSet` prevents a duplicate listener on the same client, and the message handler ignores anything without an array `queryKey`.

Use `syncQueryInvalidation` only for a local mutation whose keys the server does not publish over the realtime hub: today the coupon actions (`DISCOUNT_QUERY_KEYS.ADMIN.ALL`) and the order row actions (`ORDER_QUERY_KEYS.ADMIN.ORDERS`, which otherwise reach other browsers only after an audit-log queue batch). A change the server publishes already reaches every storefront and admin tab on its own socket, so posting it as well would make every other tab of the browser fetch the same queries again.

## Server-pushed invalidation

Writes on the Worker cannot reach a browser's cache directly. They publish a set of query-key prefixes into a Durable Object hub, which fans them out over WebSocket to every connected client; `useRealtimeQuerySync` resolves the prefixes against the layout's subscription list with `resolveInvalidatedQueryKeys` and calls `invalidateQueryPrefix` once for each resulting key: the narrower key of each overlapping topic and subscription, without duplicates or keys another key already covers. It never posts to the `BroadcastChannel`, because every tab that mounts it receives the frame on its own socket. The whole mechanism is documented in [Realtime invalidation](/docs/integrations/realtime-invalidation).
