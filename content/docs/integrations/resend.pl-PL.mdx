Każdy e-mail wysyłany przez sklep przechodzi przez Resend. Adapter w `src/integrations/resend/` zawiera klienta, jeden pomocnik `sendEmail`, budowniki zamieniające wiersze zamówień na właściwości szablonów oraz renderer podglądów dla programisty. Same szablony React Email mieszkają w `src/presentation/emails/`, ponieważ należą do warstwy prezentacji.

## Klient i pomocnik wysyłki

```ts
import { env } from "cloudflare:workers"

import { Resend } from "resend"

export const resend = new Resend(env.RESEND_API_KEY)
```

Plik `resend.send.ts` jest jedynym, który go wywołuje, i nigdy nie rzuca wyjątku:

```ts
const deliver = async ({ from, react, revealsAccountExistence, subject, to }: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  try {
    const { error } = await resend.emails.send({
      from: from ?? `${APP_NAME} <${env.RESEND_EMAIL_FROM}>`,
      react,
      subject,
      to,
    })

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

Zwraca `undefined` przy sukcesie i komunikat błędu w przeciwnym razie. SDK Resend nie ma limitu czasu i nie przyjmuje sygnału przerwania, więc wywołanie, na które nie przyszła odpowiedź po `SEND_EMAIL_TIMEOUT_MS` (10 sekund), też jest porażką, zgłaszaną jako `Resend did not answer within 10000 ms`. Ta sygnatura niesie ciężar projektowy: awaria poczty nigdy nie może wycofać rejestracji ani zamówienia. Wywołujący logują komunikat albo zapisują go w dzienniku audytu i idą dalej. Domyślne `from` to `M'Arte <${env.RESEND_EMAIL_FROM}>`, zbudowane z `APP_NAME` w `src/presentation/branding/app.ts`.

### Nadawca, który nie może wysłać niczego

`refusesEverySend` wyłapuje odmowy, które powtórzą się przy każdej wiadomości, dopóki ktoś nie poprawi konfiguracji: każde 401 lub 403 (nieprawidłowy albo ograniczony klucz API lub niezweryfikowana domena nadawcy, którą Resend zgłasza jako `validation_error` z kodem 403), `invalid_from_address` oraz `daily_quota_exceeded` albo `monthly_quota_exceeded`. W takich przypadkach `markEmailSenderUnavailable(message)` z `resend.availability.server.ts` zapisuje klucz `email-sender-unavailable:<APP_ENV>` w przestrzeni KV `CACHE` z `expirationTtl: 300` (`EMAIL_SENDER_UNAVAILABLE_SECONDS`), przez `scheduleBackgroundWork`, więc błąd KV jest tylko logowany i nigdy nie zastępuje komunikatu Resend. Najpierw odczytuje flagę i zapisuje ją tylko wtedy, gdy nie jest jeszcze ustawiona, więc seria odmów kosztuje jeden zapis do KV na pięć minut zamiast jednego na każdy e-mail; KV przyjmuje około jednego zapisu na sekundę do jednego klucza i ma dzienny limit zapisów. `isEmailSenderUnavailable()` odczytuje flagę z powrotem; gdy KV nie da się odczytać, loguje `[Resend] Email sender availability unreadable` i odpowiada `false`. Klucz zawiera `APP_ENV`, bo development i preview są podpięte do tej samej przestrzeni.

Brakujący klucz API nigdy nie dociera do Resend: `new Resend(undefined)` rzuca wyjątek już przy ładowaniu `resend.config.ts`, a `scripts/prepare-deploy-secrets.ts` nie przygotuje wdrożenia bez `RESEND_API_KEY`.

Wywołujący przekazuje `revealsAccountExistence: true`, gdy to, czy e-mail w ogóle zostanie wysłany, zależy od istnienia konta. Tak jest z weryfikacją, linkiem do zmiany hasła i potwierdzeniem zmiany adresu z Better Auth: Better Auth wysyła je tylko dla adresu, który ma konto albo go nie ma. Ich odmowy nigdy nie ustawiają flagi, bo jej stan zdradzałby komuś z zewnątrz, czy taka wysyłka w ogóle nastąpiła. E-maile newslettera, zamówień i o usunięciu konta wychodzą dla każdego adresu, który je uruchomi, więc ich odmowy flagę ustawiają.

Odmowa dotycząca jednej wiadomości nie zmienia flagi: błąd odbiorcy 422, `rate_limit_exceeded`, odpowiedź 5xx, błąd sieci albo dziesięciosekundowy limit czasu. Gdyby limit liczby żądań traktować jak awarię nadawcy, jeden nagły szczyt blokowałby wszystkie e-maile na pięć minut.

Na flagę reaguje tylko blokada w Better Auth. Dopóki jest ustawiona, rejestracja, zmiana hasła, ponowne wysłanie weryfikacji i zmiana adresu odpowiadają `503 EMAIL_DELIVERY_UNAVAILABLE`, zamiast tworzyć token dla e-maila, który nie może wyjść; zobacz [Better Auth](/docs/integrations/better-auth#blokada-wysyłki-e-maili). E-maile newslettera i zamówień nie są blokowane, bo o każdej porażce i tak informują osobę albo dziennik audytu. Flaga wyłapuje zepsutego nadawcę po pierwszej odmowie któregoś z tych e-maili; domena, której nigdy nie zweryfikowano, nadal kosztuje każdą osobę, która wcześniej uruchomi e-mail uwierzytelniania, więc zweryfikuj domenę w Resend przed wdrożeniem.

Każdy szablon eksportuje własną stałą przestrzeni nazw obok komponentu, więc wywołujący nie może rozjechać się z komunikatami, które renderuje:

```ts
export const ORDER_SHIPPED_NAMESPACE = "emails.order-shipped"
```

## Składanie i dlaczego komunikaty są przekazywane w propsach

E-mail renderowany jest na Workerze, poza kontekstem Reacta, więc nie ma `IntlProvider`, z którego można czytać. Każdy szablon przyjmuje zatem `locale` i `messages` jako właściwości, a temat powstaje przez `createTranslator`:

```ts
const messages = await loadNamespace<typeof orderShippedMessages>({ locale, namespace: ORDER_SHIPPED_NAMESPACE })
const failure = await sendEmail({
  react: createElement(OrderShipped, {
    accountCta,
    details,
    locale,
    messages,
    orderNumber: orderRow.orderNumber,
  }),
  subject: createTranslator({ locale, messages })("subject"),
  to: orderRow.email,
})
```

Import `typeof orderShippedMessages` jest importem _wyłącznie typu_ z angielskiego pliku JSON (`import type orderShippedMessages from "~/messages/en-US/emails.order-shipped.json"`), więc obiekt komunikatów szablonu jest w pełni typowany, a brakujący klucz po polsku jest błędem typowania, nie pustym miejscem w czasie działania.

Plik `src/presentation/emails/email-layout.tsx` otacza każdy szablon: znak słowny `M'ARTE`, złota linia, przetłumaczony podtytuł, treść i stopka, wewnątrz komponentu `Tailwind` z `react-email` z wbudowaną konfiguracją z `email-styles.ts`. Wymusza `color-scheme: light only`, ponieważ odwracanie kolorów w trybie ciemnym klientów pocztowych niszczy projekt.

## Budowniki e-maili o zamówieniu

Plik `order-confirmation.utils.ts` zamienia wiersze bazy na właściwości szablonów:

| Eksport                                                        | Przeznaczenie                                                                              |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `formatEmailAddress(addressRow)`                               | Jeden wielolinijkowy łańcuch z adresem pocztowym albo `undefined`                          |
| `resolveDeliveryMethodLabel(context, unavailable)`             | Etykieta dostawy widziana przez klienta, z zapasowym przetłumaczonym tekstem „niedostępne" |
| `buildOrderConfirmationDetails(...)`                           | Cały blok szczegółów: adresy, metoda dostawy, metoda płatności, uwaga klienta              |
| `buildOrderConfirmationItems(lines, locale)`                   | Wiersze pozycji, ze sformatowanymi cenami i adresami produktów                             |
| `buildOrderAccountCta({ isGuest, locale, messages, orderId })` | Albo „załóż konto i śledź zamówienie", albo link do `/account/orders/<id>`                 |
| `resolveStripePaymentMethodLabel(session, messages)`           | Czyta PaymentIntent, aby nazwać metodę, której klient faktycznie użył (karta, BLIK, P24)   |

Plik `order-shipped.utils.ts` używa ich ponownie dla e-maila o wysyłce: `buildOrderShippedDetails` wybiera tekst o czasie dostawy według `type` metody (`courier`, `locker` lub `in_store`), a `buildOrderShippedAccountCta` deleguje do `buildOrderAccountCta`.

Plik `order-shipped.notification.server.ts` zawiera cały przepływ e-maila o wysyłce. `sendOrderShippedEmail(orderId)` ładuje zamówienie przez `getOrderForShippedEmail`, ustala język z `order.metadata` przez `resolveOrderLocale`, ładuje kontekst zamówienia, gdy istnieje `checkoutId`, renderuje i wysyła. Zwraca wynik zamiast go zapisywać, a brak zamówienia albo pusty adres też jest wynikiem. `notifyOrderShipped(orderId)` przekazuje tę próbę do `recordOrderEmailAttempt` z `order-email.outcome.server.ts`, z którego korzysta też e-mail z potwierdzeniem:

```ts
export const notifyOrderShipped = (orderId: string): Promise<boolean> =>
  recordOrderEmailAttempt(sendOrderShippedEmail(orderId), { label: ORDER_SHIPPED_LABEL, orderId })
```

`recordOrderEmailAttempt` loguje rzucony błąd razem ze stosem wywołań jako `Order shipped for order <id> could not be prepared:` i zamienia go w wynik, zapisuje wynik przy zamówieniu i mówi wywołującemu, czy e-mail wyszedł.

Język pochodzi z zamówienia, a nie z bieżącego żądania, więc klient, który złożył zamówienie po polsku, otrzymuje polską wiadomość także wtedy, gdy przycisk kliknie administrator pracujący po angielsku.

## Czekanie na e-maile o zamówieniu

Na oba e-maile o zamówieniu kod czeka i żaden nie może wywrócić swojego wywołującego. `ship-order.ts` czeka na e-mail o wysyłce i przekazuje wynik administratorowi:

```ts
recordOrderShippedAudit(orderId, {
  detail: trackingNumber?.trim() === "" ? undefined : trackingNumber?.trim(),
})
const shippedEmailDelivery = notifyOrderShipped(orderId)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery

return { ok: true, orderId, shippedEmailSent }
```

`scheduleBackgroundWork` przekazuje tę samą obietnicę do `ctx.waitUntil`, więc wysyłka i jej wpis w audycie kończą się nawet wtedy, gdy administrator zamknie kartę, zanim Resend odpowie. `useMarkOrderShipped` zawsze pokazuje „Zamówienie oznaczono jako wysłane.”, a gdy `shippedEmailSent` jest fałszem, także ostrzeżenie „Klient nie otrzymał e-maila”, które odsyła po szczegóły błędu do sekcji „Aktywność” zamówienia. Żądanie administratora trwa o jedno połączenie z Resend dłużej, najwyżej `SEND_EMAIL_TIMEOUT_MS`.

Webhook Stripe w ten sam sposób rejestruje `notifyOrderConfirmed` przez `scheduleBackgroundWork` i czeka na wynik. Zapisuje on każdy wynik i nigdy nie rzuca wyjątku, więc webhook odpowiada 200 nawet wtedy, gdy Resend odrzuci potwierdzenie, a e-mail kończy się także wtedy, gdy Stripe przestanie czekać. Ponownie dostarczone zdarzenie i tak by go nie wysłało: `fulfillCheckout` zwraca `undefined` dla kasy, która nie jest już oczekująca, a handler kończy przed krokiem e-maila.

## Ślad w audycie

Wysyłki są zapisywane, a nie tylko logowane. `recordOrderEmailAttempt` przekazuje każdy wynik do `recordOrderEmailOutcome({ failure, label, orderId })` w `src/modules/audit-log/audit-log.events.server.ts`, który zapisuje przy zamówieniu `email.sent` albo `email.failed`. Przechodzi przez niego każdy sposób, w jaki e-mail o zamówieniu może zawieść: odmowa Resend lub brak odpowiedzi na czas, sesja Stripe albo zamówienie bez adresu, brak zamówienia oraz błąd podczas przygotowywania e-maila, na przykład nieudany odczyt z bazy. Wpisy z treścią błędu pojawiają się w karcie Aktywność zamówienia i w `/admin/audit`; szczegóły opisują [Szablony e-maili](/docs/features/email).

E-maile Better Auth są zapisywane tylko wtedy, gdy się nie powiodą, przez `deliverAuthEmail` w `auth.server.ts`: celem wpisu jest adres, a szczegół wygląda jak `Auth verification email — The example.com domain is not verified`. Link z e-maila nigdy nie trafia do wpisu.

E-maile newslettera są zapisywane tylko wtedy, gdy się nie powiodą. `subscribeToNewsletter` wywołuje `recordEmailFailedAudit(email, { detail })`, gdy Resend odrzuci potwierdzenie albo informację o tym, że adres jest już na liście, lub nie odpowie na czas; celem wpisu jest adres, a szczegół wygląda jak `Newsletter confirmation — The example.com domain is not verified`. Do logu trafia też `[Newsletter] Failed to send confirmation to <adres>: <błąd>`, a odwiedzający dowiaduje się, że e-maila nie udało się wysłać.

## Podglądanie szablonów

Plik `email-previews.tsx` deklaruje po jednym wpisie na szablon, z wyjątkiem `newsletter-confirmation`:

```ts
export const EMAIL_PREVIEWS = {
  "account-deleted": { element: async (locale) => <AccountDeleted … />, label: "Account deleted" },
  "change-email": { … },
  "newsletter-already-subscribed": { … },
  "order-confirmation": { … },
  "order-shipped": { … },
  "reset-password": { … },
  "verify-email": { … },
} satisfies Record<string, EmailPreview>
```

Każde `element` ładuje prawdziwą przestrzeń nazw komunikatów dla żądanego języka i wypełnia właściwości danymi zastępczymi — `PREVIEW_NAME`, `PREVIEW_ORDER_ID`, polski `PREVIEW_ADDRESS`, dwie pozycje zamówienia wycenione w groszach. `renderEmailPreview(slug, locale, plainText)` renderuje przez `render` z `react-email`, więc widzisz to, co zobaczy odbiorca, wraz z alternatywą tekstową.

Plik `src/routes/dev.emails.tsx` je udostępnia:

```bash
bun run dev
# http://localhost:3000/dev/emails
# http://localhost:3000/dev/emails?template=order-confirmation&locale=pl-PL
# http://localhost:3000/dev/emails?template=order-confirmation&locale=pl-PL&format=text
```

Bez parametru `template` renderowany jest indeks z odnośnikami do każdego szablonu z podglądem w obu językach, w HTML i jako czysty tekst. Handler zwraca 404, o ile nie jest ustawione `import.meta.env.DEV`, więc trasa jest martwa w środowisku preview i na produkcji. Nic nie jest wysyłane — to renderer, nie wysyłka testowa.

## Zmiana szablonu

1. Zmień komponent w `src/presentation/emails/`.
2. Dodaj lub zmień klucze w **obu** plikach: `messages/en-US/emails.<name>.json` i `messages/pl-PL/emails.<name>.json`. Klucz brakujący po polsku jest błędem typowania, bo właściwości typowane są na podstawie pliku angielskiego.
3. Sprawdź oba języki i oba formaty pod `/dev/emails`.
4. Jeśli zmieniły się właściwości, zaktualizuj dane zastępcze w `email-previews.tsx`. Plik `src/integrations/resend/__test__/email-previews.test.ts` sprawdza dokładną listę identyfikatorów i etykiet, renderuje podglądy do czystego tekstu i porównuje je z prawdziwymi tekstami z `messages/en-US/emails.*.json` oraz `messages/pl-PL/emails.verify-email.json`, więc zepsuty szablon lub zmieniona nazwa klucza powoduje niepowodzenie testów.
