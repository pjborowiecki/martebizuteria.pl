Każdy e-mail wysyłany przez sklep przechodzi przez Resend. Adapter w `src/integrations/resend/` zawiera klienta, jeden pomocnik `sendEmail`, budowniki zamieniające wiersze zamówień na właściwości szablonów oraz renderer podglądów dla programisty. Same szablony React Email mieszkają w `src/presentation/emails/`, ponieważ należą do warstwy prezentacji.

## Klient i pomocnik wysyłki

```ts
import { env } from "cloudflare:workers"

import { Resend } from "resend"

export const resend = new Resend(env.RESEND_API_KEY)
```

Plik `resend.send.ts` jest jedynym, który go wywołuje, i nigdy nie rzuca wyjątku:

```ts
const deliver = async ({ from, react, revealsAccountExistence, subject, to }: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const sender = from ?? `${APP_NAME} <${env.RESEND_EMAIL_FROM}>`
  try {
    const { error } = await resend.emails.send({ from: sender, react, subject, to })

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error, sender)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

Zwraca `undefined` przy sukcesie i komunikat błędu w przeciwnym razie. SDK Resend nie ma limitu czasu i nie przyjmuje sygnału przerwania, więc wywołanie, na które nie przyszła odpowiedź po `SEND_EMAIL_TIMEOUT_MS` (10 sekund), też jest porażką, zgłaszaną jako `Resend did not answer within 10000 ms`. Ta sygnatura niesie ciężar projektowy: awaria poczty nigdy nie może wycofać rejestracji ani zamówienia. Wywołujący logują komunikat albo zapisują go w dzienniku audytu i idą dalej. Domyślne `from` to `M'Arte <${env.RESEND_EMAIL_FROM}>`, zbudowane z `APP_NAME` w `src/presentation/branding/app.ts`.

### Nadawca, który nie może wysłać niczego

`refusesEverySend` wyłapuje odmowy, które powtórzą się przy każdej wiadomości, dopóki ktoś nie poprawi konfiguracji: każde 401 lub 403 (nieprawidłowy albo ograniczony klucz API lub niezweryfikowana domena nadawcy, którą Resend zgłasza jako `validation_error` z kodem 403; nie dotyczy to nadawcy z testowej domeny Resend, `resend.dev`), `invalid_from_address` oraz `daily_quota_exceeded` albo `monthly_quota_exceeded`. W takich przypadkach `markEmailSenderUnavailable(message)` z `resend.availability.server.ts` zapisuje klucz `email-sender-unavailable:<APP_ENV>` w przestrzeni KV `CACHE` z `expirationTtl: 300` (`EMAIL_SENDER_UNAVAILABLE_SECONDS`), przez `scheduleBackgroundWork`, więc błąd KV jest tylko logowany i nigdy nie zastępuje komunikatu Resend. Najpierw odczytuje flagę i zapisuje ją tylko wtedy, gdy nie jest jeszcze ustawiona, więc seria odmów kosztuje jeden zapis do KV na pięć minut zamiast jednego na każdy e-mail; KV przyjmuje około jednego zapisu na sekundę do jednego klucza i ma dzienny limit zapisów. `isEmailSenderUnavailable()` odczytuje flagę z powrotem; gdy KV nie da się odczytać, loguje `[Resend] Email sender availability unreadable` i odpowiada `false`. Klucz zawiera `APP_ENV`, bo development i preview są podpięte do tej samej przestrzeni.

Brakujący klucz API nigdy nie dociera do Resend: `new Resend(undefined)` rzuca wyjątek już przy ładowaniu `resend.config.ts`, a `scripts/prepare-deploy-secrets.ts` nie przygotuje wdrożenia bez `RESEND_API_KEY`.

Wywołujący przekazuje `revealsAccountExistence: true`, gdy to, czy e-mail w ogóle zostanie wysłany, zależy od istnienia konta. Tak jest z weryfikacją, linkiem do zmiany hasła i potwierdzeniem zmiany adresu z Better Auth: Better Auth wysyła je tylko dla adresu, który ma konto albo go nie ma. Ich odmowy nigdy nie ustawiają flagi, bo jej stan zdradzałby komuś z zewnątrz, czy taka wysyłka w ogóle nastąpiła. E-maile newslettera, zamówień i o usunięciu konta wychodzą dla każdego adresu, który je uruchomi, więc ich odmowy flagę ustawiają.

Odmowa dotycząca jednej wiadomości nie zmienia flagi: błąd odbiorcy 422, `rate_limit_exceeded`, odpowiedź 5xx, błąd sieci albo dziesięciosekundowy limit czasu. Gdyby limit liczby żądań traktować jak awarię nadawcy, jeden nagły szczyt blokowałby wszystkie e-maile na pięć minut. To samo dotyczy odpowiedzi 401 lub 403 bez żadnego z powyższych kodów, gdy nadawca jest w domenie `resend.dev` (`RESEND_TEST_SENDER`): testowy nadawca Resend dostarcza pocztę wyłącznie właścicielowi konta Resend, a każdemu innemu odbiorcy odpowiada `validation_error` z kodem 403, `You can only send testing emails to your own email address`, co nic nie mówi o kolejnym e-mailu do właściciela. Odmowy dotyczące klucza i limitu mają własne kody i nadal ustawiają flagę.

Na flagę reaguje tylko blokada w Better Auth. Dopóki jest ustawiona, rejestracja, zmiana hasła, ponowne wysłanie weryfikacji i zmiana adresu odpowiadają `503 EMAIL_DELIVERY_UNAVAILABLE`, zamiast tworzyć token dla e-maila, który nie może wyjść; zobacz [Better Auth](/docs/integrations/better-auth#blokada-wysyłki-e-maili). E-maile newslettera i zamówień nie są blokowane, bo o każdej porażce i tak informują osobę albo dziennik audytu. Flaga wyłapuje zepsutego nadawcę po pierwszej odmowie któregoś z tych e-maili; domena, której nigdy nie zweryfikowano, nadal kosztowałaby każdą osobę, która wcześniej uruchomi e-mail uwierzytelniania, dlatego wdrożenie najpierw sprawdza nadawcę; zobacz [Domena nadawcy](#domena-nadawcy).

export const ORDER_SHIPPED_NAMESPACE = "emails.order-shipped"

## Składanie i dlaczego komunikaty są przekazywane w propsach

E-mail renderowany jest na Workerze, poza kontekstem Reacta, więc nie ma `IntlProvider`, z którego można czytać. Każdy szablon przyjmuje zatem `locale` i `messages` jako właściwości, a temat powstaje przez `createTranslator`:

```ts
const messages = await loadNamespace<typeof orderShippedMessages>({ locale, namespace: ORDER_SHIPPED_NAMESPACE })
const failure = await sendEmail({
  react: createElement(OrderShipped, {
    accountCta,
    details,
    locale,
    messages,
    orderNumber: orderRow.orderNumber,
  }),
  subject: createTranslator({ locale, messages })("subject"),
  to: orderRow.email,
})
```

Import `typeof orderShippedMessages` jest importem _wyłącznie typu_ z angielskiego pliku JSON (`import type orderShippedMessages from "~/messages/en-US/emails.order-shipped.json"`), więc obiekt komunikatów szablonu jest w pełni typowany, a brakujący klucz po polsku jest błędem typowania, nie pustym miejscem w czasie działania.

Plik `src/presentation/emails/email-layout.tsx` otacza każdy szablon: znak słowny `M'ARTE`, złota linia, przetłumaczony podtytuł, treść i stopka, wewnątrz komponentu `Tailwind` z `react-email` z wbudowaną konfiguracją z `email-styles.ts`. Wymusza `color-scheme: light only`, ponieważ odwracanie kolorów w trybie ciemnym klientów pocztowych niszczy projekt.

## Dokąd prowadzą linki

Każdy link, który aplikacja sama wpisuje do e-maila, prowadzi pod adres, którego używał klient albo administrator: lokalnie i w testach do `http://localhost:3000` albo `http://127.0.0.1:3000`, na preview do hosta preview, a na produkcji do `https://martebizuteria.pl` albo `https://martebizuteria.pjborowiecki.workers.dev`, zależnie od tego, którego użyto. Origin jest ustalany, zanim powstanie e-mail, i przekazywany dalej jako napis. Żaden budownik nie czyta `APP_URL`.

| Przepływ                                                         | Skąd pochodzi origin                                                                                                                                                                     |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Potwierdzenie newslettera i informacja o istniejącej subskrypcji | `subscribeToNewsletter`, przez `resolveRequestOrigin(getRequest())`                                                                                                                      |
| Potwierdzenie zamówienia                                         | `return_url` sesji, zbudowany przez żądanie checkoutu: `resolveDeploymentOrigin(session.return_url)` w `sendOrderConfirmationEmail`                                                      |
| Zamówienie wysłane                                               | `shipOrder`, przez `resolveRequestOrigin(getRequest())` na żądaniu administratora                                                                                                        |
| Konto usunięte                                                   | `deleteCustomer`, przez `resolveRequestOrigin(getRequest())` przed `removeUser`; po samodzielnym usunięciu konta `afterDelete` ustala go z żądania, które Better Auth przekazuje hookowi |

Obie funkcje leżą w `src/lib/request.ts`. Czytają wyłącznie adres URL, nigdy nagłówków `Host`, `Origin`, `Referer` ani `X-Forwarded-*`, wymagają `https:` wszędzie poza `localhost:3000` i `127.0.0.1:3000` i rzucają `AppError(FORBIDDEN)` dla hosta, którego nie akceptują. `resolveRequestOrigin(request)` akceptuje hosty z listy `appHostsForMode(import.meta.env.MODE)`, więc funkcja serwerowa odrzuca żądanie na każdym innym hoście, zanim cokolwiek zapisze. `resolveDeploymentOrigin(url)` akceptuje hosty wszystkich wdrożeń (`isDeploymentHost` w `src/modules/_core/constants/api.ts`), ponieważ webhook, który realizuje checkout, może należeć do innego wdrożenia: development i preview dzielą testowe konto Stripe i bazę danych, a `stripe:listen` zawsze przekazuje na `localhost:3000`.

W webhooku odrzucony host albo sesja bez `return_url` zatrzymuje tylko próbę wysłania e-maila, więc zamówienie i tak zostaje zrealizowane, webhook i tak odpowiada 200, a niewysłane potwierdzenie jest zapisywane przy zamówieniu. W `afterDelete` odrzucony host albo usunięcie, które przyszło bez żądania, jest logowane i audytowane jako niewysłany e-mail pożegnalny, a usunięcie konta i tak się udaje. Better Auth buduje własne linki weryfikacji, resetu hasła i zmiany adresu z listy hostów dla danego trybu. Praca przekazywana do `scheduleBackgroundWork` dostaje już ustalony origin, więc nic nie czyta żądania po wysłaniu odpowiedzi. Przyszły konsument kolejki, który wysyła e-maile, musi nieść origin w wiadomości.

## Budowniki e-maili o zamówieniu

Plik `order-confirmation.utils.ts` zamienia wiersze bazy na właściwości szablonów:

| Eksport                                                                | Przeznaczenie                                                                              |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `formatEmailAddress(addressRow)`                                       | Jeden wielolinijkowy łańcuch z adresem pocztowym albo `undefined`                          |
| `resolveDeliveryMethodLabel(context, unavailable)`                     | Etykieta dostawy widziana przez klienta, z zapasowym przetłumaczonym tekstem „niedostępne" |
| `buildOrderConfirmationDetails(...)`                                   | Cały blok szczegółów: adresy, metoda dostawy, metoda płatności, uwaga klienta              |
| `buildOrderConfirmationItems(lines, locale, origin)`                   | Wiersze pozycji, ze sformatowanymi cenami i adresami produktów                             |
| `buildOrderAccountCta({ isGuest, locale, messages, orderId, origin })` | Albo „załóż konto i śledź zamówienie", albo link do `/account/orders/<id>`                 |
| `resolveStripePaymentMethodLabel(session, messages)`                   | Czyta PaymentIntent, aby nazwać metodę, której klient faktycznie użył (karta, BLIK, P24)   |

Plik `order-shipped.utils.ts` używa ich ponownie dla e-maila o wysyłce: `buildOrderShippedDetails` wybiera tekst o czasie dostawy według `type` metody (`courier`, `locker` lub `in_store`), a `buildOrderShippedAccountCta` deleguje do `buildOrderAccountCta`.

Plik `order-shipped.notification.server.ts` zawiera cały przepływ e-maila o wysyłce. `sendOrderShippedEmail(orderId, origin)` ładuje zamówienie przez `getOrderForShippedEmail`, ustala język z `order.metadata` przez `resolveOrderLocale`, ładuje kontekst zamówienia, gdy istnieje `checkoutId`, renderuje i wysyła. Zwraca wynik zamiast go zapisywać, a brak zamówienia albo pusty adres też jest wynikiem. `notifyOrderShipped(orderId, origin)` przekazuje tę próbę do `recordOrderEmailAttempt` z `order-email.outcome.server.ts`, z którego korzysta też e-mail z potwierdzeniem:

```ts
export const notifyOrderShipped = (orderId: string, origin: string): Promise<boolean> =>
  recordOrderEmailAttempt(sendOrderShippedEmail(orderId, origin), { label: ORDER_SHIPPED_LABEL, orderId })
```

`recordOrderEmailAttempt` loguje rzucony błąd razem ze stosem wywołań jako `Order shipped for order <id> could not be prepared:` i zamienia go w wynik, zapisuje wynik przy zamówieniu i mówi wywołującemu, czy e-mail wyszedł.

Język pochodzi z zamówienia, a nie z bieżącego żądania, więc klient, który złożył zamówienie po polsku, otrzymuje polską wiadomość także wtedy, gdy przycisk kliknie administrator pracujący po angielsku.

## Czekanie na e-maile o zamówieniu

Na oba e-maile o zamówieniu kod czeka i żaden nie może wywrócić swojego wywołującego. `ship-order.ts` czeka na e-mail o wysyłce i przekazuje wynik administratorowi:

```ts
recordOrderShippedAudit(orderId, {
  detail: trackingNumber?.trim() === "" ? undefined : trackingNumber?.trim(),
})
const shippedEmailDelivery = notifyOrderShipped(orderId, origin)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery

return { ok: true, orderId, shippedEmailSent }
```

`scheduleBackgroundWork` przekazuje tę samą obietnicę do `ctx.waitUntil`, więc wysyłka i jej wpis w audycie kończą się nawet wtedy, gdy administrator zamknie kartę, zanim Resend odpowie. `useMarkOrderShipped` zawsze pokazuje „Zamówienie oznaczono jako wysłane.”, a gdy `shippedEmailSent` jest fałszem, także ostrzeżenie „Klient nie otrzymał e-maila”, które odsyła po szczegóły błędu do sekcji „Aktywność” zamówienia. Żądanie administratora trwa o jedno połączenie z Resend dłużej, najwyżej `SEND_EMAIL_TIMEOUT_MS`.

Webhook Stripe w ten sam sposób rejestruje `notifyOrderConfirmed` przez `scheduleBackgroundWork` i czeka na wynik. Zapisuje on każdy wynik i nigdy nie rzuca wyjątku, więc webhook odpowiada 200 nawet wtedy, gdy Resend odrzuci potwierdzenie, a e-mail kończy się także wtedy, gdy Stripe przestanie czekać. Ponownie dostarczone zdarzenie i tak by go nie wysłało: `fulfillCheckout` zwraca `undefined` dla kasy, która nie jest już oczekująca, a handler kończy przed krokiem e-maila.

## Ślad w audycie

Wysyłki są zapisywane, a nie tylko logowane. `recordOrderEmailAttempt` przekazuje każdy wynik do `recordOrderEmailOutcome({ failure, label, orderId })` w `src/modules/audit-log/audit-log.events.server.ts`, który zapisuje przy zamówieniu `email.sent` albo `email.failed`. Przechodzi przez niego każdy sposób, w jaki e-mail o zamówieniu może zawieść: odmowa Resend lub brak odpowiedzi na czas, sesja Stripe albo zamówienie bez adresu, brak zamówienia oraz błąd podczas przygotowywania e-maila, na przykład nieudany odczyt z bazy. Wpisy z treścią błędu pojawiają się w karcie Aktywność zamówienia i w `/admin/audit`; szczegóły opisują [Szablony e-maili](/docs/features/email).

E-maile Better Auth są zapisywane tylko wtedy, gdy się nie powiodą, przez `deliverAuthEmail` w `auth.server.ts`: celem wpisu jest adres, a szczegół wygląda jak `Auth verification email — The example.com domain is not verified`. Link z e-maila nigdy nie trafia do wpisu.

E-maile newslettera są zapisywane tylko wtedy, gdy się nie powiodą. `subscribeToNewsletter` wywołuje `recordEmailFailedAudit(email, { detail })`, gdy Resend odrzuci potwierdzenie albo informację o tym, że adres jest już na liście, lub nie odpowie na czas; celem wpisu jest adres, a szczegół wygląda jak `Newsletter confirmation — The example.com domain is not verified`. Do logu trafia też `[Newsletter] Failed to send confirmation to <adres>: <błąd>`, a odwiedzający dowiaduje się, że e-maila nie udało się wysłać.

## Domena nadawcy

Resend odrzuca każdą wiadomość, której domena w polu `from` nie jest zweryfikowana na koncie, do którego należy `RESEND_API_KEY`. Odmowa to `validation_error` z kodem 403, `The <domain> domain is not verified. Please, add and verify your domain on https://resend.com/domains`, i powtarza się przy każdym e-mailu, dopóki domena nie zostanie zweryfikowana. Sklep widzi ją w logu serwera i w dzienniku audytu; osoba, która czekała na e-mail, widzi błąd albo nie widzi niczego.

`RESEND_API_KEY` i `RESEND_EMAIL_FROM` są w `secrets.required` dla wszystkich trzech środowisk w `wrangler.jsonc`. `RESEND_EMAIL_FROM` to sam adres, na przykład `noreply@martebizuteria.pl`, bez nazwy wyświetlanej, bo nazwę dodaje `sendEmail` i wysyła jako `M'Arte <noreply@martebizuteria.pl>`. Jego domena musi dokładnie odpowiadać domenie zweryfikowanej w Resend: subdomena, na przykład `mail.martebizuteria.pl`, to w Resend osobna domena z własnymi rekordami.

### Weryfikacja domeny

1. Na [resend.com/domains](https://resend.com/domains) dodaj domenę z `RESEND_EMAIL_FROM` i wybierz region. `eu-west-1` (Irlandia) sprawia, że poczta sklepu pozostaje w UE.
2. Opublikuj u dostawcy DNS domeny rekordy, które poda Resend:

| Rekord           | Typ | Nazwa               | Wartość                                                     |
| ---------------- | --- | ------------------- | ----------------------------------------------------------- |
| DKIM             | TXT | `resend._domainkey` | Klucz publiczny wygenerowany przez Resend dla domeny, `p=…` |
| SPF              | MX  | `send`              | `feedback-smtp.<region>.amazonses.com`, priorytet `10`      |
| SPF              | TXT | `send`              | `v=spf1 include:amazonses.com ~all`                         |
| DMARC (zalecany) | TXT | `_dmarc`            | `v=DMARC1; p=none;`                                         |

3. Naciśnij **Verify** na stronie domeny. Zmiany DNS rozchodzą się od kilku minut do kilku godzin; domena przechodzi w stan `verified`, gdy Resend odczyta rekordy DKIM i SPF.

Rekordy SPF znajdują się w subdomenie `send`, której Resend używa jako adresu zwrotnego, więc nie kolidują z własnymi rekordami MX ani SPF domeny głównej. Klucz DKIM i region w wartości MX są inne dla każdej domeny, dlatego kopiuj dokładne wartości z panelu albo z kontroli przed wdrożeniem, która wypisuje brakujące rekordy. Resend nie wymaga DMARC, ale Gmail i Yahoo oczekują go od nadawców masowych.

### Środowisko lokalne

W `.env.development` można ustawić `RESEND_EMAIL_FROM=onboarding@resend.dev` — wspólnego nadawcę testowego Resend, który nie wymaga własnej domeny. Dostarcza on pocztę wyłącznie na adres właściciela konta Resend, więc podczas pracy rejestruj się, resetuj hasła i zapisuj do newslettera właśnie tym adresem. Każdemu innemu odbiorcy Resend odpowiada kodem 403, `You can only send testing emails to your own email address`. Taki e-mail zawodzi i jest zgłaszany jak każdy inny odrzucony, ale odmowa dotyczy tylko tego odbiorcy, więc `sendEmail` nie oznacza nadawcy jako niedostępnego, a e-maile uwierzytelniania do właściciela nadal wychodzą. Kontrola przed wdrożeniem odrzuca `onboarding@resend.dev` dla preview i produkcji, gdzie klienci nie dostaliby niczego.

### Kontrola przed wdrożeniem

`deploy:preview` i `deploy:production` uruchamiają `scripts/verify-email-sender.ts <środowisko>` zaraz po `verify-bindings.ts`, przed kompilacją, więc nadawca, którego Resend by odrzucił, zatrzymuje wdrożenie w kilka sekund, a działający Worker zostaje bez zmian. Skrypt czyta `RESEND_API_KEY`, `RESEND_EMAIL_FROM` i opcjonalny `RESEND_MANAGEMENT_API_KEY` tak samo jak `prepare-deploy-secrets.ts`, najpierw ze środowiska procesu, potem z `.env.<środowisko>`, więc sprawdza dokładnie te wartości, które za chwilę zostaną wysłane. Zmienna wyeksportowana, ale pusta, ma pierwszeństwo przed plikiem, a brakujący plik liczy się jako pusty. Przepływy wdrożeniowe przekazują wszystkie trzy sekrety do kroku, który uruchamia skrypt wdrożenia. Logika to `verifyEmailSender` w `src/integrations/resend/resend.sender.ts`, z testami jednostkowymi w `__test__/resend.sender.test.ts`, w których klient Resend jest zamockowany.

Kontrola przerywa wdrożenie z komunikatem, co poprawić, gdy:

- brakuje `RESEND_API_KEY` albo jest pusty;
- brakuje `RESEND_EMAIL_FROM`, zawiera nazwę wyświetlaną lub spacje albo nie ma domeny;
- `RESEND_EMAIL_FROM` jest w domenie `resend.dev` poza środowiskiem development;
- Resend odrzuca klucz (`invalid_api_key`, `missing_api_key`, `validation_error`, a dla klucza zarządzającego także `restricted_api_key`) albo nadal nie może wypisać domen konta po drugiej próbie;
- domeny nadawcy nie ma na koncie; wielkość liter nie ma znaczenia, poza tym nazwa musi się zgadzać dokładnie, więc subdomena potrzebuje własnego wpisu;
- wysyłka jest wyłączona dla tej domeny;
- domena nie jest `verified`, a jej rekordy wysyłki tego nie równoważą: któryś rekord DKIM lub SPF nie jest `verified` albo Resend nie podaje dla domeny żadnego rekordu DKIM lub żadnego rekordu SPF. Komunikat wypisuje rekordy do opublikowania z typem, nazwą, wartością, priorytetem i stanem. Rekordy odbioru i śledzenia się nie liczą;
- Resend nie odpowiada w ciągu `VERIFY_EMAIL_SENDER_TIMEOUT_MS` (30 sekund).

Domena, którą Resend zgłasza jako `verified`, przechodzi bez sprawdzania rekordów. Stany rekordów rozstrzygają tylko dla domeny w innym stanie, na przykład `partially_verified`, gdy rekord odbioru wciąż czeka na weryfikację.

Klucz z uprawnieniem **Sending access** w Resend, właściwym dla Workera, nie może wypisać domen: Resend odpowiada `restricted_api_key`, co SDK loguje jako `[Resend API Error]` i co zarazem potwierdza, że sam klucz jest prawidłowy. Kontrola odczytuje wtedy domenę kluczem `RESEND_MANAGEMENT_API_KEY`, jeśli jest ustawiony: to opcjonalny klucz **Full access** tego samego zespołu Resend, używany wyłącznie przez ten skrypt. Podobnie jak dane dostępowe `CLOUDFLARE_*` nie ma go w `secrets.required`, więc nigdy nie trafia do Workera; w GitHubie dodaj go jako sekret środowisk `preview` i `production`.

Bez niego kontrola wysyła jeden e-mail od `M'Arte <RESEND_EMAIL_FROM>` na `delivered@resend.dev`, testową skrzynkę Resend, i przerywa z komunikatem samego Resend, gdy wysyłka zostanie odrzucona. Ten e-mail liczy się do tego samego dziennego i miesięcznego limitu co poczta sklepu, a wysyła go każde wdrożenie preview, czyli każdy push do pull requesta. Gdy limit się wyczerpie, wysyłki na żywo dostają `daily_quota_exceeded` albo `monthly_quota_exceeded`, `sendEmail` oznacza nadawcę jako niedostępnego, a rejestracja, zmiana hasła i zmiana adresu odpowiadają `503 EMAIL_DELIVERY_UNAVAILABLE`. Ustaw `RESEND_MANAGEMENT_API_KEY` wszędzie tam, gdzie wdrożenia są częste. Dla `onboarding@resend.dev` w środowisku development kontrola sprawdza tylko, czy Resend przyjmuje klucz, bo ten nadawca nie dociera do żadnej skrzynki poza skrzynką właściciela.

Uruchom ją ręcznie na prawdziwym API Resend:

```sh
bun run email:verify development
bun run email:verify preview
bun run email:verify production
```

Limit żądań Resend jest wspólny z wysyłkami działającego Workera, więc każde żądanie jest ponawiane raz, po `RESEND_RETRY_DELAY_MS` (jednej sekundzie), gdy Resend odpowie `rate_limit_exceeded`, `application_error` albo `internal_server_error`. SDK Resend nie ma limitu czasu, dlatego cała kontrola rezygnuje po 30 sekundach. Poza tym w razie wątpliwości kontrola blokuje, a nie przepuszcza: awaria albo ponowne przekroczenie limitu żądań również przerywa wdrożenie i nie ma flagi, która by ją pomijała. W nagłej sytuacji uruchom pozostałe kroki skryptu wdrożenia ręcznie. Pozytywny wynik to stan z chwili wdrożenia; rekord DNS usunięty później znów zablokuje wysyłkę, a żadna kontrola tego nie wychwyci — porażki pojawią się wtedy w dzienniku audytu, jak opisano wyżej.
