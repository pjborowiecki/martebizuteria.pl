---
title: "Unieważnianie w czasie rzeczywistym"
description: "Hub w Durable Object, który wypycha unieważnienia cache zapytań do podłączonych przeglądarek."
---

Zapis na Workerze nie może dosięgnąć cache zapytań w przeglądarce innej osoby. Gdy administrator opublikuje produkt, każdy otwarty sklep powinien to zauważyć, a jego własna lista produktów powinna odświeżyć się w każdej otwartej karcie. Ten adapter jest właśnie tym mechanizmem: kod serwerowy publikuje zbiór prefiksów kluczy zapytań do huba w Durable Object, hub rozsyła je przez WebSocket, a każdy klient unieważnia tylko te zapytania, które faktycznie subskrybuje.

Świadomie _nie_ jest to kanał danych. Przez połączenie przechodzą wyłącznie klucze zapytań — żadnych wierszy, ładunków ani identyfikatorów. Klient, który otrzyma powiadomienie, pobiera dane ponownie przez zwykłe funkcje serwerowe, więc autoryzacja wymuszana jest dokładnie tak jak zawsze.

## Dwa huby

Plik `realtime-invalidation.subscriptions.ts` nazywa je i wypisuje, co każdy z nich niesie:

```ts
export const REALTIME_INVALIDATION_HUB = { ADMIN: "admin", STOREFRONT: "storefront" } as const
```

| Hub          | Subskrybowane prefiksy                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin`      | `ADMIN_REALTIME_QUERY_PREFIXES` — strona i statystyki dziennika zdarzeń, zamówienia panelu, `ADMIN_DASHBOARD_QUERY_KEYS.ALL` pulpitu przeglądu, klienci panelu, zespół panelu, klucze `ALL` i `STATS` kategorii, kolekcji, produktów i atrybutów produktów, klucze `ADMIN.ALL` i `ADMIN.BY_HANDLE` stron treści, klucze `ADMIN.SALES`, `ADMIN.FREE_DELIVERY` i `ADMIN.SELLER_DETAILS` ustawień sklepu, klucz `ADMIN.ALL` metod dostawy, klucz `ADMIN.LIST` kampanii newslettera oraz klucze `ADMIN.PAGE` i `ADMIN.STATS` subskrybentów newslettera |
| `storefront` | `STOREFRONT_REALTIME_QUERY_PREFIXES` — produkty `ALL`, `BY_HANDLE`, `LANDING_NEW_ARRIVALS`, `RELATED_BY_CATEGORY`, `STOREFRONT_PAGE`, koszyk `AVAILABILITY`, kategorie i kolekcje `ALL` / `BY_HANDLE`, strony treści `BY_HANDLE`, ustawienia sklepu `SALES`, `FREE_DELIVERY` i `SELLER_DETAILS` oraz metody dostawy `ALL`                                                                                                                                                                                                                          |

Kasa także łączy się z hubem sklepu, z własną listą `CHECKOUT_REALTIME_QUERY_PREFIXES`: ustawienia sklepu `FREE_DELIVERY` i `SELLER_DETAILS` oraz metody dostawy `ALL`, nic więcej, więc otwarta kasa pokazuje zmiany dostawy i aktualny adres odbioru, a zmiana stanu magazynowego gdzie indziej nigdy nie uruchamia ponownie jej sprawdzenia dostępności. Wszystkie trzy listy to `as const satisfies readonly QueryKey[]`, więc zmiana nazwy stałej klucza jest błędem typowania, a nie cicho martwą subskrypcją. Podział ma znaczenie zarówno dla prywatności, jak i dla ograniczenia szumu: hub sklepu nigdy nie niesie prefiksu `["admin", …]`, więc przeglądarka klienta nie dowiaduje się niczego o działaniach administratora.

## Protokół

Plik `realtime-invalidation.protocol.ts` to klucz zapytania serializowany jako JSON oraz reguła, która zamienia ramkę tematów na klucze unieważniane przez kartę:

```ts
export const serializeQueryKeyPrefix = (queryKey: QueryKey): string => JSON.stringify(queryKey)

export const resolveInvalidatedQueryKeys = (subscriptions: readonly QueryKey[], topics: readonly string[]): QueryKey[] =>
  toMinimalQueryKeyPrefixes(
    topics
      .map((topic) => parseSerializedQueryKeyPrefix(topic))
      .filter((topic): topic is QueryKey => topic !== undefined)
      .flatMap((topic) => queryKeysInvalidatedByTopic(subscriptions, topic)),
  )
```

Dla każdego tematu, który nakłada się na subskrypcję, karta unieważnia węższy z dwóch kluczy, porównanych przez `partialMatchKey` z TanStack Query: temat, gdy mieści się w subskrypcji, a subskrypcję, gdy temat jest szerszy. Dzięki temu publikujący może podać prefiks szeroki, a subskrybent węższy, albo odwrotnie, bez wiedzy żadnej ze stron o dokładnym kształcie drugiej, a wąski temat pozostaje wąski: `["admin", "products", "stats"]` odświeża statystyki, a nie wszystko w subskrypcji `["admin", "products"]`. Następnie `toMinimalQueryKeyPrefixes` usuwa powtórzone klucze i klucze, które obejmuje już inny klucz z ramki, więc każde zapytanie jest unieważniane najwyżej raz na ramkę.

Wiadomość na łączu jest minimalna:

```ts
export interface RealtimeInvalidationPayload {
  readonly topics: readonly string[]
  readonly type: typeof REALTIME_INVALIDATION_MESSAGE.INVALIDATE
}
```

`isRealtimeInvalidationPayload` waliduje ją strukturalnie na kliencie, a `parseSerializedQueryKeyPrefix` zwraca `undefined`, zamiast rzucać wyjątek przy zniekształconym JSON.

## Publikowanie

Plik `realtime-invalidation.publish.server.ts` adresuje hub po nazwie i wywołuje metodę Durable Object bezpośrednio przez powiązanie RPC:

```ts
const publishToHub = async (hubName: RealtimeInvalidationHubName, queryKeys: readonly QueryKey[]): Promise<void> => {
  if (queryKeys.length === 0) {
    return
  }

  const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)
  await hub.notifyInvalidation(toSerializedTopicPrefixes(queryKeys))
}
```

`getByName` oznacza, że istnieją dokładnie dwie instancje obiektu, po jednej na nazwę huba — i to właśnie umożliwia rozsyłanie.

`publishRealtimeInvalidation({ admin?, storefront? })` publikuje do obu równolegle, a `scheduleRealtimeInvalidation(input)` owija to w `scheduleBackgroundWork`, aby żądanie nie czekało:

```ts
export const scheduleRealtimeInvalidation = (input: PublishRealtimeInvalidationInput): void => {
  scheduleBackgroundWork(publishRealtimeInvalidation(input))
}
```

Kod serwerowy prawie nigdy nie wywołuje żadnej z tych funkcji bezpośrednio. Plik `realtime-invalidation.catalog.server.ts` dostarcza zamiast tego nazwane intencje:

### Kto je wywołuje

- **Każda mutacja katalogu.** Wszystkie przypadki użycia `create-`, `update-`, `delete-` i `reorder-` w `src/modules/product/`, `product-category/`, `product-collection/` i `product-attribute/`.
- **Zamówienie.** `stripe.actions.server.ts` wywołuje `scheduleProductCatalogInvalidation()` przy tworzeniu i aktualizacji sesji, ponieważ rezerwacja towaru zmienia dostępność.
- **Realizacja.** `announcePlacedOrder` w `stripe.fulfillment.server.ts` wywołuje `scheduleAdminOrdersInvalidation()` i `scheduleProductCatalogInvalidation()`, gdy opłacona sesja stała się zamówieniem, niezależnie od tego, czy złożył je webhook Stripe, czy strona powrotu z checkoutu.
- **Webhooki.** `stripe.webhooks.ts` wywołuje `scheduleAdminOrdersInvalidation()` przy zwrocie, nieudanym albo anulowanym zwrocie i sporze, a `scheduleProductCatalogInvalidation()` przy zwolnieniu; `webhooks.inpost.ts` wywołuje `scheduleAdminOrdersInvalidation()` po odczytaniu nowego statusu przesyłki z ShipX. Zwrot pieniędzy nie odświeża katalogu, bo nigdy nie przywraca stanu; robią to `cancelOrder` i `returnOrderToStock`, gdy administrator przywraca produkty zamówienia na stan.
- **Cofnięcie etapu zamówienia.** `stepBackOrder` wywołuje `scheduleAdminOrdersInvalidation()` zaraz po przeniesieniu zamówienia, więc każda otwarta karta panelu pokazuje wcześniejszy etap bez czekania na wpis audytu.
- **Odstąpienia od umowy.** `order-withdrawal.record.server.ts` wywołuje `scheduleAdminOrdersInvalidation()` po zapisaniu oświadczenia klienta o odstąpieniu od umowy, żeby otwarta strona zamówienia w panelu pokazała kartę odstąpienia.
- **Tożsamość.** Hooki tworzenia, aktualizacji i usuwania użytkownika w `auth.hooks.server.ts` wywołują `scheduleAdminCustomersInvalidation()`, podobnie jak `grantAdminAccess` i `revokeAdminAccess`, które zmieniają rolę bez Better Auth.
- **Strony treści.** `update-content-page.ts` wywołuje `scheduleContentPageInvalidation()` po zapisie, a `update-seller-details.ts`, gdy zapis danych sprzedawcy przesunął datę strony.
- **Przełącznik sprzedaży.** `set-sales-paused.ts` wywołuje `scheduleSalesStatusInvalidation()`, gdy administrator wstrzymuje albo wznawia sprzedaż, więc komunikat o wstrzymaniu pojawia się albo znika w każdej otwartej karcie sklepu, a inne karty panelu przestawiają przełącznik.
- **Ustawienia dostawy.** `create-delivery-method.ts`, `update-delivery-method.ts`, `archive-delivery-method.ts` i `reorder-delivery-methods.ts` wywołują `scheduleDeliveryMethodsInvalidation()`, a `set-free-delivery-threshold.ts` wywołuje `scheduleFreeDeliveryInvalidation()`, gdy próg się zmienia, więc inne karty panelu pokazują zmianę, a otwarta kasa ponownie pobiera metody dostawy albo próg.
- **Dane sprzedawcy.** `update-seller-details.ts` wywołuje `scheduleSellerDetailsInvalidation()` po zapisie, który coś zmienił, więc inne karty panelu pokazują nowe dane, a stopka, strony produktów i krok odbioru osobistego w kasie idą za nimi w otwartych kartach sklepu i kasy.
- **Newsletter.** `send-newsletter-campaign.ts` odświeża listę kampanii w panelu, gdy newsletter rusza, a `newsletter-campaign.queue.server.ts` po każdej wysłanej partii i po zatrzymaniu kampanii, więc strona Marketing pokazuje postęp każdego newslettera. `scheduleAdminNewsletterSubscribersInvalidation()` jest wywoływane przy każdej zmianie wiersza subskrybenta: przez `subscribe-to-newsletter.ts` po zapisaniu adresu, `confirm-newsletter-subscription.ts` po potwierdzeniu, `unsubscribeSubscriber` z `newsletter-subscriber.unsubscribe.server.ts`, z którego korzystają link do wypisania się, trasa jednego kliknięcia, preferencje konta i panel, `erase-newsletter-subscriber.ts`, `followAccountAddressChange`, gdy zmiana adresu konta przenosi jego subskrypcję, oraz `eraseAccountData`, więc otwarte karty panelu odświeżają listę subskrybentów i jej liczniki, gdy klienci się zapisują, potwierdzają i wypisują.
- **Usuwanie danych.** `erase-newsletter-subscriber.ts` i `eraseAccountData` z `user.erasure.server.ts` wywołują też `scheduleAdminAuditLogInvalidation()`, bo razem z subskrybentem albo kontem usuwają wpisy dziennika zdarzeń tej osoby.
- **Dziennik zdarzeń.** `delete-audit-logs.ts` wywołuje `scheduleAdminAuditLogInvalidation()` po usunięciu wpisów przez administratora. `audit-log.queue.server.ts`, który dodaje `ORDER_CHANGE_ADMIN_QUERY_KEYS` dla wsadu z akcją z osi czasu zamówienia, wywołuje `publishRealtimeInvalidation` bezpośrednio i na nie czeka, bo konsument kolejki nie ma odpowiedzi, której mógłby przekazać publikację.

## Durable Object

Plik `src/durable-objects/realtime-invalidation-hub.ts` korzysta z hibernowanych połączeń WebSocket, więc bezczynny hub nic nie kosztuje:

```ts
export class RealtimeInvalidationHub extends DurableObject<Env> {
  fetch(request: Request): Response {
    if (request.headers.get("Upgrade") !== "websocket") {
      return new Response("Expected WebSocket", { status: HTTP_STATUS.UPGRADE_REQUIRED })
    }

    const hubName = this.ctx.id.name
    if (hubName === undefined) {
      return new Response("Hub name required", { status: HTTP_STATUS.BAD_REQUEST })
    }

    const { client, server } = splitWebSocketPair(new WebSocketPair())
    this.ctx.acceptWebSocket(server, [hubName])

    return new Response(undefined, { status: HTTP_STATUS.SWITCHING_PROTOCOLS, webSocket: client })
  }
  // …
}
```

`acceptWebSocket(server, [hubName])` oznacza każde gniazdo nazwą jego huba, a `notifyInvalidation` pobiera tylko gniazda z tą etykietą przez `ctx.getWebSockets(hubName)`, wracając do wszystkich gniazd, gdyby nazwa okazała się nierozpoznana. Wysyłki owinięte są w puste `try`/`catch`, więc jedno martwe gniazdo nie zatrzyma pętli. `webSocketError` zamyka połączenie kodem 1011.

Klasa rejestrowana jest w dwóch miejscach. `src/server.ts` eksportuje ją ponownie:

```ts
export { RealtimeInvalidationHub } from "~/src/durable-objects/realtime-invalidation-hub"
```

a `wrangler.jsonc` deklaruje powiązanie w każdym środowisku wraz z migracją opartą na SQLite:

```jsonc
"migrations": [{ "tag": "v1", "new_sqlite_classes": ["RealtimeInvalidationHub"] }],
"durable_objects": {
  "bindings": [{ "name": "REALTIME_INVALIDATION_HUB", "class_name": "RealtimeInvalidationHub" }]
}
```

## Punkt końcowy podniesienia połączenia

Plik `realtime-invalidation.ws.server.ts` pełni rolę odźwiernego:

```ts
export const handleRealtimeInvalidationWebSocket = async (request, env, hubName) => {
  if (request.headers.get("Upgrade") !== "websocket") {
    return new Response("Expected WebSocket", { status: HTTP_STATUS.UPGRADE_REQUIRED })
  }

  if (hubName === REALTIME_INVALIDATION_HUB.ADMIN) {
    const unauthorized = await assertAdminWebSocket(request)
    if (unauthorized !== undefined) {
      return unauthorized
    }
  }

  const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)

  return hub.fetch(request)
}
```

Hub panelu wymaga sesji, której użytkownik przechodzi `hasAdminAccess(role)` i dla którego `needsTwoFactorSetup(user)` jest fałszywe, co w buildach `production` i `test` oznacza włączone uwierzytelnianie dwuskładnikowe, a w przeciwnym razie zwraca 401. Hub sklepu jest otwarty, i słusznie — rozgłasza wyłącznie publiczne klucze katalogu.

Trasy te obsługiwane są w `src/server.ts` przed handlerem TanStack Start, ponieważ na podniesienie połączenia WebSocket musi odpowiedzieć Durable Object, a nie komponent trasy:

```ts
if (pathname === ROUTES.API_REALTIME.ADMIN_WS) {
  return handleRealtimeInvalidationWebSocket(request, env, REALTIME_INVALIDATION_HUB.ADMIN)
}
```

Dwie ścieżki to `/api/realtime/admin/ws` i `/api/realtime/storefront/ws`, obie z `ROUTES.API_REALTIME`.

## Klient

Hook `src/hooks/use-realtime-query-sync.ts` utrzymuje połączenie. Używają go trzy układy:

```tsx
// src/routes/_storefront.tsx
useRealtimeQuerySync({ hub: REALTIME_INVALIDATION_HUB.STOREFRONT, subscriptions: STOREFRONT_REALTIME_QUERY_PREFIXES })

// src/routes/checkout.tsx
useRealtimeQuerySync({ hub: REALTIME_INVALIDATION_HUB.STOREFRONT, subscriptions: CHECKOUT_REALTIME_QUERY_PREFIXES })

// src/routes/admin.tsx
useRealtimeQuerySync({ hub: REALTIME_INVALIDATION_HUB.ADMIN, subscriptions: ADMIN_REALTIME_QUERY_PREFIXES })
```

Hook buduje `wss://` lub `ws://` z `globalThis.location.protocol`, łączy się, a przy każdej wiadomości parsuje ładunek, zamienia tematy na klucze przez `resolveInvalidatedQueryKeys`, biorąc węższy klucz z każdej pary tematu i subskrypcji, które się nakładają, i każdy klucz tylko raz, i stosuje do każdego klucza `invalidateQueryPrefix`: zapytania widoczne na ekranie pobierają się ponownie, te, które są tylko w cache, zostają usunięte, więc następna wizyta pobiera je od nowa, a lista nieskończona, taka jak katalog sklepu, zachowuje wczytane strony i pobiera je ponownie przy następnej wizycie. Do pozostałych kart odwiedzającego nic nie trafia: każda karta sklepu i panelu, a karta kasy dla trzech śledzonych kluczy, odbiera tę samą ramkę przez własne gniazdo, a karty poza tymi układami nie mają gniazda i widzą zmianę przy następnym pobraniu. Zobacz [TanStack Query](/docs/integrations/tanstack-query).

Ponowne łączenie jest wykładnicze z górnym ograniczeniem:

```ts
const BASE_RECONNECT_DELAY_MS = 1000

const MAX_RECONNECT_DELAY_MS = 30_000

const RECONNECT_BACKOFF_FACTOR = 2
```

Udane `open` zeruje licznik prób, funkcja czyszczenia ustawia flagę `disposed`, aby oczekujący licznik czasu nie wskrzesił zamkniętego połączenia, a zniekształcona wiadomość jest pochłaniana. Efekt zależy od `[hub, queryClient, subscriptions]`, a obie tablice subskrypcji są stałymi na poziomie modułu, więc gniazdo otwierane jest raz na zamontowanie układu, a nie przy każdym renderowaniu.

## Dodawanie nowego unieważnienia

1. Upewnij się, że klucz zapytania jest stabilną krotką `as const` w pliku `{feature}.constants.ts` właściwej funkcji.
2. Dodaj prefiks do `ADMIN_REALTIME_QUERY_PREFIXES` lub `STOREFRONT_REALTIME_QUERY_PREFIXES` w `realtime-invalidation.subscriptions.ts`, aby był nasłuchiwany przez klientów.
3. Dodaj nazwaną funkcję `schedule…Invalidation()` w `realtime-invalidation.catalog.server.ts` albo rozszerz istniejącą, której intencja pasuje.
4. Wywołaj ją z przypadku użycia, po udanym zapisie i przed zwróceniem wyniku.
5. Nigdy nie wywołuj `publishRealtimeInvalidation` z przypadku użycia z `await` — używaj formy `schedule…`, aby żądanie klienta nie czekało na rozsyłanie.

Prefiks publikowany, ale niesubskrybowany jest po cichu ignorowany przez każdego klienta; prefiks subskrybowany, ale nigdy niepublikowany po prostu nigdy się nie uruchamia. Żaden z tych przypadków nie zawodzi głośno, więc gdy coś się nie odświeża, sprawdź obie listy.
