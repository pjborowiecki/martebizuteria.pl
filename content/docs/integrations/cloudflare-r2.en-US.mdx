Product photography, category and collection imagery and the marketing assets live in R2, in the bucket bound to the Worker as `IMAGES`: `martebizuteria` in production and `martebizuteria-preview` in development and preview. The adapter in `src/integrations/cloudflare-r2/` has exactly one job: accept an image from the admin console, validate it, and put it in the bucket under a content-addressed key. Reading is not its job — the bucket is served publicly and read through the URL helpers in `src/lib/url.ts`.

## The binding

`wrangler.jsonc` binds one bucket per environment:

| Environment   | `bucket_name`            | `remote` |
| ------------- | ------------------------ | -------- |
| `development` | `martebizuteria-preview` | `true`   |
| `preview`     | `martebizuteria-preview` | `true`   |
| `test`        | `martebizuteria-test`    | `false`  |
| `production`  | `martebizuteria`         | `true`   |

`development` and `preview` share a bucket because they share the D1 database whose rows point at its objects, and `"remote": true` means even `bun run dev` writes to the real preview bucket. Content-addressed keys are what make that safe: a re-upload of the same bytes is a no-op rather than an overwrite. Production has a bucket of its own, and `scripts/verify-bindings.ts production` refuses a configuration that gives it the preview one. [Image delivery](/docs/guides/image-delivery) creates the preview bucket and copies the images into it.

## Upload

`media.mutations.ts` exports one server function:

```ts
export const uploadImageFn = createServerFn({ method: "POST" })
  .middleware([authorized({ product: ["update"] })])
  .validator((data: FormData) => data)
  .handler(async ({ data }) => {
    /* … */
  })
```

Authorization is the `product: ["update"]` permission, so only the admin role can upload. The validator passes the `FormData` through — the shape cannot be described by a Zod object, so the handler does the checking itself, in this order:

1. `data.get("file")` must be a `File`, else `TypeError(INVALID_FILE)`.
2. `isAcceptedImageMime(file.type)` must hold, else `INVALID_TYPE`.
3. The size must be greater than zero and at most `MAX_IMAGE_BYTES`, else `TOO_LARGE`.
4. `data.get("folder")` is used when `isMediaFolder` accepts it, otherwise it silently falls back to `"uploads"`.

Then the key is derived from the bytes:

```ts
const buffer = await file.arrayBuffer()
const digest = await crypto.subtle.digest("SHA-256", buffer)
const key = `${folder}/${bufferToHex(digest)}.${MIME_EXTENSION[file.type]}`
if ((await env.IMAGES.head(key)) === null) {
  await env.IMAGES.put(key, buffer, {
    httpMetadata: {
      cacheControl: IMMUTABLE_CACHE_CONTROL,
      contentType: file.type,
    },
  })
}

return { key }
```

Three consequences worth internalizing:

- **The key is the SHA-256 of the file contents**, hex-encoded, plus the extension. Uploading the same photograph twice produces the same key.
- **The `head` check makes the write idempotent.** An existing object is not rewritten, so the upload costs one cheap metadata request.
- **`Cache-Control: public, max-age=31536000, immutable`** is set at upload time. This is only correct because the key changes whenever the bytes change. Never write a mutable key into this bucket.
- **Only the key is returned and stored.** No host reaches the database, so serving the bucket from another address needs no data rewrite.

## Rules

`media.zod.ts` holds the constraints. Despite the file name it contains no Zod schema — only constants and two type predicates:

| Export                                 | Value                                                        |
| -------------------------------------- | ------------------------------------------------------------ |
| `ACCEPTED_IMAGE_MIME_TYPES`            | `image/jpeg`, `image/png`, `image/webp`, `image/avif`        |
| `ACCEPTED_IMAGE_ACCEPT_ATTR`           | The same list joined with commas, for the `accept` attribute |
| `MAX_IMAGE_BYTES`                      | 5 MiB (`5 * 1024 * 1024`)                                    |
| `MEDIA_FOLDERS`                        | `collections`, `products`, `categories`, `uploads`           |
| `MIME_EXTENSION`                       | The MIME-to-extension map (`image/jpeg` → `jpg`)             |
| `MEDIA_ERROR_CODES`                    | `INVALID_FILE`, `INVALID_TYPE`, `TOO_LARGE`, `UNAUTHORIZED`  |
| `isMediaFolder`, `isAcceptedImageMime` | The predicates the handler and the UI share                  |

## The admin-side upload flow

`src/presentation/components/custom/image-upload/` owns the UI. `hooks/use-image-upload.ts` takes a `MediaFolder`, re-runs the **same** `isAcceptedImageMime` and `MAX_IMAGE_BYTES` checks in the browser so the user gets a toast before a wasted round trip, and then uploads with `Promise.allSettled` so one bad file does not lose the others:

```ts
const formData = new FormData()
formData.append("file", file)
formData.append("folder", folder)

return uploadImageFn({ data: formData })
```

The successful `key` values are collected and the failures counted into a single toast. `components/image-upload.tsx` and `components/gallery-add-tile.tsx` set `accept={ACCEPTED_IMAGE_ACCEPT_ATTR}` on their file inputs. The key is what gets written to `product.thumbnail`, a `product_image` row or a category's or collection's `image`.

## Reading assets

`src/lib/url.ts` resolves a stored key or URL into something a browser can fetch:

| Export                       | Behaviour                                                                                                                                                                          |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getAssetCdnBase()`          | An isomorphic function: reads `env.VITE_R2_URL` on the server and `import.meta.env.VITE_R2_URL` in the browser, strips a trailing slash, and falls back to `DEFAULT_R2_PUBLIC_URL` |
| `getAssetURL(path)`          | Returns `path` unchanged if it is already absolute, otherwise `${base}/${path}` with any leading slash removed                                                                     |
| `resolveAssetURL(pathOrUrl)` | Resolves a stored key like `getAssetURL`, moves a stored `*.r2.dev` URL onto the configured base keeping its path, and leaves any other absolute URL as it is                      |
| `isAssetCdnUrl(url)`         | True for any `*.r2.dev` host or for the configured base's host                                                                                                                     |

`DEFAULT_R2_PUBLIC_URL` in `src/presentation/branding/app.ts` is the production bucket's `r2.dev` endpoint, `https://pub-a9ce13f98e72423eb72107a4e696f2e0.r2.dev`. `isConfiguredAssetCdnBase` additionally rejects a base containing the placeholder host `your-production-cdn-domain.com`, so a half-filled environment file falls back to the working default rather than producing dead image URLs.

`VITE_R2_URL` appears in both `secrets.required` in `wrangler.jsonc` and the `VITE_`-prefixed browser variables, because both sides need it. The two values must name the same host: the Content-Security-Policy is built on the server and lets pages load images and video only from the origin of `DEFAULT_R2_PUBLIC_URL` and from the origin `getAssetCdnBase()` returns there, so a bundle built with a different host would have its images refused. See [Security model](/docs/architecture/security-model#response-headers).

Rows written before uploads stored keys, and every seed file, hold full `r2.dev` URLs. Because `resolveAssetURL` moves them onto the configured base, they follow `VITE_R2_URL` like keys do: production serves them from its custom domain and preview from the preview bucket.

### Resizing

`getOptimizedImageUrl` in `src/lib/image.ts` rewrites an image URL through `unpic`'s Cloudflare transform. For a URL on the configured base, which `isAssetCdnUrl` recognises, it transforms on that host with the object's path as the source, so `https://images.martebizuteria.pl/products/<sha256>.webp` becomes `https://images.martebizuteria.pl/cdn-cgi/image/width=600,height=750,quality=75,onerror=redirect,fit=cover,f=auto/products/<sha256>.webp`, and `<Image>` (`src/presentation/components/custom/image.tsx`, built on `@unpic/react`) writes the `srcset` from it. Every transformation asks for `onerror=redirect`, so when Cloudflare cannot transform an image on the custom domain, for instance once the month's free transformations are used up, it redirects the browser to the original object instead of failing. An `r2.dev` host cannot run Image Transformations, so a URL there is returned untouched and served at its original dimensions; so is an Unsplash URL. Any other URL is transformed through the shop's own host. The zone needs Image Transformations turned on before `VITE_R2_URL` points at the custom domain; [Image delivery](/docs/guides/image-delivery) has the steps.

`PLACEHOLDER_IMAGE` is `getAssetURL("placeholder.svg")`, and `src/data/landing.ts` pulls the landing hero, the video and its poster from the same bucket.

## What is missing on purpose

There is **no delete path**. Nothing in the repository calls `env.IMAGES.delete`. Removing a product image removes the `product_image` row and leaves the object in the bucket. Because keys are content hashes this is safe — another product may reference the same bytes — but it does mean the bucket only grows, and pruning is a manual operation against R2.

There is also no signed-URL or private-object handling: every object in this bucket is public.
