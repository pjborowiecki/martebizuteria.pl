Every e-mail the shop sends goes out through Resend. The adapter in `src/integrations/resend/` holds the client, one `sendEmail` helper, the newsletter's batch sender, the builders that turn order rows into e-mail props, and the developer preview renderer. The React Email templates themselves live in `src/presentation/emails/`, because they are presentation.

## The client and the send helper

```ts
import { env } from "cloudflare:workers"

import { Resend } from "resend"

export const resend = new Resend(env.RESEND_API_KEY)
```

`resend.send.ts` sends every transactional e-mail with it, and never throws. The newsletter is the one other caller; see [The newsletter](#the-newsletter).

```ts
const deliver = async ({ from, revealsAccountExistence, ...message }: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const sender = from ?? `${APP_NAME} <${env.RESEND_EMAIL_FROM}>`
  try {
    const { error } = await resend.emails.send({ ...message, from: sender, replyTo: BUSINESS.EMAIL })

    if (error !== null && revealsAccountExistence !== true && refusesEverySend(error, sender)) {
      scheduleBackgroundWork(markEmailSenderUnavailable(error.message))
    }

    return error?.message
  } catch (error) {
    return error instanceof Error ? error.message : String(error)
  }
}

export const sendEmail = async (options: Readonly<SendEmailOptions>): Promise<string | undefined> => {
  const timeout = Promise.withResolvers<string>()
  const timer = setTimeout(() => {
    timeout.resolve(`Resend did not answer within ${SEND_EMAIL_TIMEOUT_MS} ms`)
  }, SEND_EMAIL_TIMEOUT_MS)

  try {
    return await Promise.race([deliver(options), timeout.promise])
  } finally {
    clearTimeout(timer)
  }
}
```

It returns `undefined` on success and the failure message otherwise. The Resend SDK has no timeout and accepts no abort signal, so a call that has not answered after `SEND_EMAIL_TIMEOUT_MS` (10 seconds) is also a failure, reported as `Resend did not answer within 10000 ms`. This signature is load-bearing: a mail outage must never roll back a registration or an order. Callers log the message, or record it in the audit log, and carry on. The default `from` is `M'Arte <${env.RESEND_EMAIL_FROM}>`, built from `APP_NAME` in `src/presentation/branding/app.ts`. Every message also carries `replyTo: BUSINESS.EMAIL`, the shop's contact address `kontakt@martebizuteria.pl` from `src/presentation/branding/business.ts`, so a customer who answers an e-mail, as the order confirmation, the shipping notice and the account-deleted notice invite them to, writes to the shop whatever address `RESEND_EMAIL_FROM` names. `SendEmailOptions` has no field for it, so no caller can send without it.

### Attachments

`attachments` goes to Resend unchanged. Resend can fetch an attachment from a `path` URL, but not from `localhost` or `127.0.0.1`, so a file the shop serves is read inside the Worker and sent as base64 `content` instead. The order confirmation attaches the model withdrawal form this way: `loadWithdrawalFormAttachment(origin)` in `withdrawal-form.attachment.server.ts` fetches `/forms/formularz_zwrotu.pdf` from `env.ASSETS`, the static assets binding every environment in `wrangler.jsonc` declares. `vp dev` answers it from `public/` through Vite, and a deployed Worker from the uploaded assets. A form the binding does not return throws, and the confirmation is recorded as failed rather than sent without it.

### A sender that cannot send at all

`refusesEverySend` picks out the refusals that will repeat for every message until someone fixes the configuration: any 401 or 403 (an invalid or restricted API key, or a sending domain that is not verified, which Resend reports as a 403 `validation_error`; not for a sender on Resend's `resend.dev` test domain), `invalid_from_address`, and `daily_quota_exceeded` or `monthly_quota_exceeded`. For those, `markEmailSenderUnavailable(message)` from `resend.availability.server.ts` writes `email-sender-unavailable:<APP_ENV>` to the `CACHE` KV namespace with `expirationTtl: 300` (`EMAIL_SENDER_UNAVAILABLE_SECONDS`), through `scheduleBackgroundWork`, so a KV error is logged and never replaces Resend's message. It reads the flag first and writes only when it is not set yet, so a stream of refusals costs one KV write per five minutes instead of one per email; KV accepts about one write per second to a key and has a daily write quota. `isEmailSenderUnavailable()` reads it back; when KV cannot be read it logs `[Resend] Email sender availability unreadable` and answers `false`. The key carries `APP_ENV` because development and preview are bound to the same namespace.

A missing API key never gets as far as Resend: `new Resend(undefined)` throws while `resend.config.ts` loads, and `scripts/prepare-deploy-secrets.ts` refuses to prepare a deploy without `RESEND_API_KEY`.

A caller passes `revealsAccountExistence: true` when whether the email is sent at all depends on an account existing. Better Auth's verification, reset and change-email confirmation do: Better Auth sends them only for an address that has, or has not, an account. Their refusals never set the flag, because its state would otherwise tell an outsider whether such a send was attempted. The newsletter, order and account-deleted emails go out for any address that triggers them, and the password-changed email only to an account whose reset link was just used, which tells whoever used it nothing new, so their refusals do set it.

A refusal about one message leaves the flag alone: a 422 recipient error, `rate_limit_exceeded`, a 5xx, a network error or the 10-second timeout. Treating a rate limit as sender-wide would let one burst block every email for five minutes. The same goes for a 401 or 403 without one of the codes above when the sender is on `resend.dev` (`RESEND_TEST_SENDER`): Resend's test sender delivers only to the owner of the Resend account and answers any other recipient with a 403 `validation_error`, `You can only send testing emails to your own email address`, which says nothing about the next email to the owner. Its key and quota refusals carry their own codes and still set the flag.

Only the Better Auth gate acts on the flag. While it is set, sign-up, password reset, resend-verification and change-email answer `503 EMAIL_DELIVERY_UNAVAILABLE` instead of creating a token for an email that cannot leave; see [Better Auth](/docs/integrations/better-auth#email-delivery-gate). Newsletter confirmations and order emails are not gated, and a newsletter batch never sets the flag, because they already tell the person or the audit log about each failure. The flag catches a broken sender after the first refusal of one of those emails; a domain that was never verified would still cost every person who triggers an auth email before then, which is why a deploy first checks the sender; see [Sender domain](#sender-domain).

### Emails visitors can request

Four e-mails go to whatever address a visitor types in, with no account or order behind the request: the verification e-mail, the password-reset link, the newsletter confirmation and the newsletter's already-subscribed notice. A fifth, the acknowledgement of a withdrawal sent by order number at `/withdraw-from-contract`, goes to the address of whatever order the visitor names by its number and address, so anyone who knows both can repeat it. Repeated, they would flood someone's inbox and use up the Resend quota, after which the order e-mails stop as well. Their senders therefore ask `admitPublicEmail({ kind, to })` from `resend.public-email-limits.server.ts` first, and send only when it answers `true`:

| Limit                                                                          | Key in `rate_limit`                                      | Window                 |
| ------------------------------------------------------------------------------ | -------------------------------------------------------- | ---------------------- |
| `PUBLIC_EMAILS_PER_RECIPIENT_HOURLY_MAX`: 3 e-mails of one kind to one address | `public-email:<APP_ENV>:<kind>:<SHA-256 of the address>` | An hour from the first |
| `PUBLIC_EMAILS_DAILY_MAX`: 50 such e-mails from the whole shop                 | `public-email:<APP_ENV>:daily`                           | A day from the first   |

The kinds are `verification`, `password-reset`, `newsletter` and `withdrawal`; the confirmation and the already-subscribed notice share `newsletter`, so alternating them gains nothing. The address is trimmed and lower-cased before it is hashed, and the table holds only the hash. Both counters use `withinRateLimit` from `src/lib/rate-limit.ts`, a fixed window that starts with the first e-mail after the previous one ended, and the daily counter is consulted only for an e-mail the address limit let through. When `rate_limit` cannot be read, `withinRateLimit` answers `false` and nothing is sent. `APP_ENV` keeps development and preview, which share a D1 database, on separate counters.

A refusal sends nothing, and the caller answers as if the e-mail had gone out. `withdrawFromGuestOrder` asks only once a statement is recorded, and a refusal holds back both the acknowledgement and the shop's notice; the statement stays on the order, where the admin order page shows it. The senders run only for some addresses, a reset only for an account and a resend only for an unconfirmed one, so a different answer would reveal which. An address past its hourly limit is logged as `[Email] Skipped a <kind> email to <address>: the address reached its hourly limit for this email`. The daily limit is the shop's problem rather than one visitor's, so it is logged with `console.error` and recorded as `email.failed` with the detail `Public <kind> email — the shop reached its daily limit of 50 emails that visitors can request`. Fifty is half of the 100 e-mails a day Resend's free plan sends, which leaves the other half for the order e-mails; on a paid plan without a daily quota it still bounds what a flood costs. Raise the constant if real sign-ups and newsletter confirmations ever come close to it.

Nothing else asks. The order, shipped, cancelled, refunded, payment-failed, new-order, password-changed, account-deleted and change-email e-mails, the incident alerts, and the acknowledgement of a withdrawal sent from the account, go straight to `sendEmail`, so a used-up day never holds them back; a withdrawal from the account needs a session and reaches only the address of the customer's own order. The verification e-mail Better Auth sends to a new address once a change of address is confirmed goes through `sendVerificationEmail` and is counted with the others. The requests behind these e-mails also need a Turnstile token; see [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile).

`src/integrations/resend/__test__/resend.public-email-limits.integration.test.ts` runs the limits against a `rate_limit` table: the fourth e-mail of a kind to an address in an hour, the case and spaces of an address, separate kinds and addresses, the hour and the day rolling over, the hash in place of the address, the audit entry for the daily limit, and an unreadable table.

## The newsletter

`newsletter-campaign.server.ts` sends newsletters, and it is the only other code that uses the client. `sendNewsletterBatch({ content, idempotencyKey, recipients })` renders `newsletter-campaign.tsx` for each recipient in their language, with the subject and the Markdown letter the owner wrote, and sends them all with one `resend.batch.send(emails, { idempotencyKey })`, Resend's batch endpoint, which takes up to 100 e-mails a call. Like `sendEmail` it returns `undefined` on success and the failure message otherwise, and never throws. Each e-mail is sent from `M'Arte <RESEND_EMAIL_FROM>` with `Reply-To: kontakt@martebizuteria.pl`, as the transactional mail is.

A recipient with an unsubscribe token gets two headers:

```
List-Unsubscribe: <https://martebizuteria.pl/api/newsletter/unsubscribe?token=…>
List-Unsubscribe-Post: List-Unsubscribe=One-Click
```

Gmail, Yahoo and Apple Mail show their own unsubscribe button for them and send `POST List-Unsubscribe=One-Click` to that address (RFC 8058). `src/routes/api/newsletter.unsubscribe.ts` answers it without a session or a redirect: it unsubscribes the subscriber holding the token through `unsubscribeByToken`, the same function behind the `/newsletter/unsubscribe` page, and answers 200, 404 for a token nobody holds and 400 for a missing or malformed one. It takes no rate limit, because the token is a random UUID and a mail provider may send many of these from one address. The letter itself also carries a visible link to `/newsletter/unsubscribe?token=…` in the subscriber's language, and ends with the trader's legal name, address and e-mail. The admin's test send passes no token, so its e-mails carry no unsubscribe headers and link to the unsubscribe page without one.

The send is not gated by the sender-unavailable flag and does not set it, and it does not pass through `sendEmail` or `admitPublicEmail`, so the visitors' daily cap neither counts it nor holds it back, but it shares the account's quota and rate limit. [E-mail](/docs/features/email#the-newsletter) describes the campaign, the queue and why a newsletter is never sent twice.

## Composition, and why messages are passed in

An e-mail is rendered on the Worker, outside React context, so there is no `IntlProvider` to read. Every template therefore takes `locale` and `messages` as props, and the subject is produced with `createTranslator`:

```ts
const messages = await loadNamespace<typeof orderShippedMessages>({ locale, namespace: ORDER_SHIPPED_NAMESPACE })
const failure = await sendEmail({
  react: createElement(OrderShipped, {
    accountCta,
    details,
    locale,
    messages,
    orderNumber: orderRow.orderNumber,
  }),
  subject: createTranslator({ locale, messages })("subject"),
  to: orderRow.email,
})
```

The `typeof orderShippedMessages` import is a _type-only_ import of the English JSON file (`import type orderShippedMessages from "~/messages/en-US/emails.order-shipped.json"`), so the template's message object is fully typed and a missing Polish key is a type error rather than a runtime blank.

`src/presentation/emails/email-layout.tsx` wraps every template: the `M'ARTE` wordmark, a gold rule, a translated tagline, the body and a footer, inside `react-email`'s `Tailwind` with an inline config from `email-styles.ts`. It forces `color-scheme: light only`, because mail clients' dark-mode inversion destroys the design.

## Where the links point

Every link the app writes into an e-mail itself points at the address the customer or admin was using: `http://localhost:3000` or `http://127.0.0.1:3000` locally and in tests, the preview host on preview, and `https://martebizuteria.pl` or `https://martebizuteria.pjborowiecki.workers.dev` in production, whichever was used. The origin is resolved before the e-mail is built and passed down as a string. No builder reads `APP_URL`.

| Flow                                                  | Where the origin comes from                                                                                                                                                                                       |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Newsletter confirmation and already-subscribed notice | `subscribeToNewsletter`, with `resolveRequestOrigin(getRequest())`                                                                                                                                                |
| Newsletter and its test                               | `sendNewsletterCampaign` and `sendNewsletterTest`, with `resolveRequestOrigin(getRequest())` on the admin's request; the campaign stores it in `newsletter_campaign.origin` for the batches its queue sends later |
| Order confirmation                                    | The session's `return_url`, which the checkout request built: `resolveDeploymentOrigin(session.return_url)` in `sendOrderConfirmationEmail`                                                                       |
| Order shipped                                         | `shipOrder`, with `resolveRequestOrigin(getRequest())` on the admin's request                                                                                                                                     |
| Order cancelled                                       | `cancelOrder`, with `resolveRequestOrigin(getRequest())` on the admin's request                                                                                                                                   |
| Order refunded                                        | The `return_url` of the Checkout Session `resolveCheckoutSession` finds for the refunded charge: `resolveDeploymentOrigin(returnUrl)` in `sendOrderRefundedEmail`                                                 |
| Payment failed                                        | The session's `return_url`: `resolveDeploymentOrigin(session.return_url)` in `sendPaymentFailedEmail`                                                                                                             |
| New order, to the shop                                | The `return_url` of the session that created the order: `resolveDeploymentOrigin(returnUrl)` in `sendNewOrderEmail`, which links `/admin/orders/<id>`                                                             |
| Withdrawal, to the shop                               | `withdrawFromCustomerOrder` and `withdrawFromGuestOrder`, with `resolveRequestOrigin(getRequest())`, which links `/admin/orders/<id>`                                                                             |
| Account deleted                                       | `deleteCustomer`, with `resolveRequestOrigin(getRequest())` before `removeUser`; after a self-service deletion, `afterDelete` resolves it from the request Better Auth passes the hook                            |
| Password changed                                      | `sendPasswordChangedEmail`, with `resolveRequestOrigin(request)` on the request Better Auth passes `onPasswordReset`; the e-mail links `/auth/sign-in`                                                            |

Both resolvers live in `src/lib/request.ts`. They read only a URL, never the `Host`, `Origin`, `Referer` or `X-Forwarded-*` headers, require `https:` everywhere but `localhost:3000` and `127.0.0.1:3000`, and throw `AppError(FORBIDDEN)` for a host they do not accept. `resolveRequestOrigin(request)` accepts the hosts on `appHostsForMode(import.meta.env.MODE)`, so a server function refuses a request on any other host before it writes anything. `resolveDeploymentOrigin(url)` accepts the hosts of every deployment (`isDeploymentHost` in `src/modules/_core/constants/api.ts`), because the webhook that fulfils a checkout can belong to another deployment: development and preview share the Stripe test account and the database, and `stripe:listen` always forwards to `localhost:3000`.

In the webhook, a refused host or a session with no `return_url` stops only the e-mail attempt, so the order is still fulfilled, the refund still recorded and the session still released, the webhook still answers 200, and the unsent e-mail is recorded against the order, or against the session for a failed payment. In `afterDelete`, a refused host or a deletion that came with no request is logged and audited as an unsent goodbye e-mail, and the deletion still succeeds. In `onPasswordReset` the same is recorded as an unsent password-changed e-mail, and the reset still succeeds and still signs every device out. Better Auth builds its own verify, reset and change-email links from the per-mode host list. Work handed to `scheduleBackgroundWork` gets the origin already resolved, or, like `sendPasswordChangedEmail`, resolves it before its first `await`, so nothing reads the request after the response. A future queue consumer that sends e-mail must carry the origin in its message.

## Order e-mail builders

`order-confirmation.utils.ts` turns database rows into template props:

| Export                                                                                  | Purpose                                                                                                                |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `formatEmailAddress(addressRow)`                                                        | One multi-line postal address string, or `undefined`                                                                   |
| `resolveDeliveryMethodLabel(context, unavailable)`                                      | The customer-facing delivery label, falling back to the translated "unavailable" text                                  |
| `describeCompanyInvoice({ billingCompanyName, billingNip }, nipLabel)`                  | The company to invoice and `NIP <digits>`, one per line, or `undefined` when neither was given                         |
| `buildOrderConfirmationDetails({ context, fulfillmentTimes, messages, paymentMethod })` | The whole details block: addresses, company to invoice, delivery method, payment method, delivery and fulfilment times |
| `buildOrderConfirmationItems(lines, locale, origin)`                                    | The item rows, with formatted prices and product URLs                                                                  |
| `buildOrderAccountCta({ isGuest, locale, messages, orderId, origin })`                  | Either "create an account and track this order" or a link into `/account/orders/<id>`                                  |
| `buildOrderLegalLinks(origin, locale)`                                                  | Links to the terms of service, the exchanges-and-returns page and the privacy policy                                   |
| `resolveStripePaymentMethodLabel(session, messages)`                                    | Reads the PaymentIntent to name the method the customer actually used (card, BLIK, P24)                                |

`order-fulfillment-time.utils.ts` turns the ordered products' `czas-realizacji` attribute into the fulfilment time the confirmation states:

| Export                                                                   | Purpose                                                                                                                                                  |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resolveOrderLineFulfillmentTimes(lines, attributesByVariantId, locale)` | Each line's title with the time its product page shows, labelled in the order's locale, or `undefined` when it shows none                                |
| `describeOrderFulfillmentTime(lines, messages)`                          | The longest of those times, 10 business days for a line without one, then the note on when it runs; each product's own time when they cannot be compared |

`order-shipped.utils.ts` reuses the order-confirmation builders for the shipped e-mail: `buildOrderShippedDetails` picks the delivery timing string by the method's `type` (`courier`, `locker` or `in_store`), and `buildOrderShippedAccountCta` delegates to `buildOrderAccountCta`.

`order-shipped.notification.server.ts` is the whole shipped-e-mail flow. `sendOrderShippedEmail(orderId, origin)` loads the order with `getOrderForShippedEmail`, resolves the locale from `order.metadata` with `resolveOrderLocale`, loads the checkout context when there is a `checkoutId`, renders and sends. It returns the outcome instead of recording it, and a missing order or a blank address is an outcome too. `notifyOrderShipped(orderId, origin)` hands that attempt to `recordOrderEmailAttempt` from `order-email.outcome.server.ts`, which the confirmation e-mail uses as well:

```ts
export const notifyOrderShipped = (orderId: string, origin: string): Promise<boolean> =>
  recordOrderEmailAttempt(sendOrderShippedEmail(orderId, origin), { label: ORDER_SHIPPED_LABEL, orderId })
```

`recordOrderEmailAttempt` logs a thrown error with its stack as `Order shipped for order <id> could not be prepared:` and turns it into an outcome, records the outcome against the order and tells the caller whether the e-mail went out.

`order-cancelled.notification.server.ts` and `order-refunded.notification.server.ts` follow the same shape. Both read the order with `getOrderForRefundEmail`, which selects the address, number, currency, total, metadata and account of the order, and both build the button with `buildOrderAccountCta`. `notifyOrderCancelled({ orderId, refundedAmount }, origin)` states the refund `requestFullOrderRefund` got back from Stripe, or that a free order has nothing to refund. `notifyOrderRefunded(refund, returnUrl)` takes the `Order["unannouncedRefund"]` that `refundOrder` returns, so it states the amount of this refund against the order's total and whether the order is now refunded in full, and it resolves its origin from `returnUrl` inside the attempt, so a missing or refused URL is recorded like any other failure. The failed-payment e-mail has no order to read: `sendPaymentFailedEmail` in `stripe.webhooks.tsx` builds it from the session, listing its metadata lines with `buildOrderConfirmationItems`.

`new-order.notification.server.ts` writes to the shop rather than the customer. `notifyShopOfNewOrder(orderId, returnUrl)` sends the notice to `RESEND_EMAIL_FROM`: `sendNewOrderEmail` resolves the origin from `returnUrl` inside the attempt, reads the order with `getAdminOrderDetailRow` and `getAdminOrderItemRows`, the reads behind the admin order page, and renders `new-order.tsx`. The delivery line reuses `resolveDeliveryMethodLabel`, the item rows `mapAdminOrderDetailItem` and the shipping address `resolveAdminOrderDetailAddresses`, and the button opens `ROUTES.ADMIN_ORDER` on that origin.

`incident-alert.notification.server.ts` writes to the shop as well. `notifyShopOfIncident({ detail, kind, reference })` looks the incident up in the `CACHE` KV namespace under `incident-alert:<APP_ENV>:<kind>:<reference>`, returns if the key is there, writes it with a one-hour `expirationTtl` (`INCIDENT_ALERT_SECONDS`) and only then renders `incident-alert.tsx` and sends it to `RESEND_EMAIL_FROM`. A refused send is logged as `[Alert] The <kind> alert to <address> was not sent: …`, and anything thrown on the way is logged as `[Alert] The <kind> alert could not be sent:` and swallowed, so an alert can never fail the webhook or the queue batch that raised it. See [Monitoring and alerts](/docs/guides/monitoring-and-alerts).

The locale comes from the order rather than from the current request, so a customer who ordered in Polish is written to in Polish even when an English-speaking admin clicks the button. The shop's new-order notice and incident alerts are always in the shop's language, `I18N.DEFAULT_LOCALE`.

## Waiting for the order e-mails

Every order e-mail is awaited, and none can fail its caller. `ship-order.ts` waits for the shipped e-mail and hands the result to the admin:

```ts
recordOrderShippedAudit(orderId, {
  detail: trackingNumber?.trim() === "" ? undefined : trackingNumber?.trim(),
})
const shippedEmailDelivery = notifyOrderShipped(orderId, origin)
scheduleBackgroundWork(shippedEmailDelivery)
const shippedEmailSent = await shippedEmailDelivery

return { ok: true, orderId, shippedEmailSent }
```

`scheduleBackgroundWork` puts the same promise on `ctx.waitUntil`, so the send and its audit entry finish even if the admin closes the tab while Resend is answering. `useMarkOrderShipped` always shows "Order marked as shipped.", and when `shippedEmailSent` is false also a warning toast, "Shipping email not sent", that points to the order's Activity card for the error. The admin's request takes one Resend round trip longer, at most `SEND_EMAIL_TIMEOUT_MS`. `cancel-order.ts` does the same with `notifyOrderCancelled` and returns `cancelledEmailSent`, and `useCancelOrder` warns "Cancellation email not sent" when it is false.

The Stripe webhook registers `notifyOrderConfirmed` together with `notifyShopOfNewOrder`, `notifyOrderRefunded` and the failed-payment attempt with `scheduleBackgroundWork` and awaits them the same way. It records every outcome and never throws, so the webhook answers 200 even when Resend refuses the confirmation, and the e-mail still finishes if Stripe stops waiting. A redelivered event would not send the confirmation or the shop's notice again: `fulfillCheckout` returns `undefined` for a checkout that is no longer pending, and the handler stops before the e-mail step. The other two have the same guard: `releaseCheckout` reports whether this delivery failed the session's payment, and `refundOrder` returns a refund only when the charge refunded more than the payment had recorded for an order the shop had not cancelled.

## Audit trail

Sends are recorded, not just logged. `recordOrderEmailAttempt` passes every outcome to `recordOrderEmailOutcome({ failure, label, orderId })` in `src/modules/audit-log/audit-log.events.server.ts`, which writes `email.sent` or `email.failed` against the order. Every way an order e-mail can fail goes through it: a Resend refusal or timeout, a Stripe session or order without an address, a missing order, and an error while the e-mail is prepared, such as a failed database read. The entries appear with the error text in the order's Activity card and in `/admin/audit`; [E-mail templates](/docs/features/email) lists the details.

Better Auth's e-mails are recorded only when they fail, by `deliverAuthEmail` in `auth.server.ts`: the address is the target and the detail reads like `Auth verification email — The example.com domain is not verified`. The link in the e-mail is never part of the entry.

A newsletter send is recorded as `newsletter.sent` against the admin who sent it, and a campaign the queue stops as `email.failed` against the campaign. Newsletter confirmations are recorded only when they fail. `subscribeToNewsletter` calls `recordEmailFailedAudit(email, { detail })` when Resend refuses or times out on the confirmation or the already-subscribed notice, with the address as the target and a detail such as `Newsletter confirmation — The example.com domain is not verified`. It also logs `[Newsletter] Failed to send confirmation to <address>: <error>`, and the visitor is told the email could not be sent.

## Sender domain

Resend refuses every message whose `from` domain is not verified in the account that owns `RESEND_API_KEY`. The refusal is a 403 `validation_error`, `The <domain> domain is not verified. Please, add and verify your domain on https://resend.com/domains`, and it repeats for every e-mail until the domain is verified. The shop sees it in the server log and the audit log; the person who was waiting for the e-mail sees an error or nothing at all.

`RESEND_API_KEY` and `RESEND_EMAIL_FROM` are in `secrets.required` for all three environments in `wrangler.jsonc`. `RESEND_EMAIL_FROM` is a bare address such as `noreply@martebizuteria.pl`, with no display name, because `sendEmail` adds the name itself and sends as `M'Arte <noreply@martebizuteria.pl>`. Its domain must match a domain verified in Resend exactly: a subdomain such as `mail.martebizuteria.pl` is a separate Resend domain with its own records.

Replies never go to that address. `sendEmail` passes `replyTo: BUSINESS.EMAIL` with every message, so each e-mail carries `Reply-To: kontakt@martebizuteria.pl` and the recipient's mail client addresses an answer there. `kontakt@martebizuteria.pl` must therefore be a mailbox the shop reads: customers send questions, cancellations, withdrawals and complaints there. Which domain the shop sends from is a setting for the owner. The [deploy check](#deploy-check) confirms that Resend would send as `RESEND_EMAIL_FROM`, not that its domain is `martebizuteria.pl`.

Both the shop's own notice of each new order and the incident alerts go to `RESEND_EMAIL_FROM` itself, in every environment, so that address needs a mailbox the owner reads as well.

### Verifying a domain

1. On [resend.com/domains](https://resend.com/domains), add the domain of `RESEND_EMAIL_FROM` and choose a region. `eu-west-1` (Ireland) keeps the shop's mail in the EU.
2. Publish the records Resend lists at the domain's DNS provider:

| Record              | Type | Name                | Value                                                         |
| ------------------- | ---- | ------------------- | ------------------------------------------------------------- |
| DKIM                | TXT  | `resend._domainkey` | The public key Resend generates for the domain, starting `p=` |
| SPF                 | MX   | `send`              | `feedback-smtp.<region>.amazonses.com`, priority `10`         |
| SPF                 | TXT  | `send`              | `v=spf1 include:amazonses.com ~all`                           |
| DMARC (recommended) | TXT  | `_dmarc`            | `v=DMARC1; p=none;`                                           |

3. Press **Verify** on the domain's page. DNS changes take from a few minutes to a few hours to propagate; the domain turns `verified` once Resend can read the DKIM and SPF records.

The SPF records sit on the `send` subdomain, which Resend uses as the bounce address, so they do not clash with the root domain's own MX or SPF records. The DKIM key and the region in the MX value differ per domain, so copy the exact values from the dashboard, or from the deploy check, which prints the records still missing. Resend does not require DMARC, but Gmail and Yahoo expect it from bulk senders.

### Local development

`.env.development` may set `RESEND_EMAIL_FROM=onboarding@resend.dev`, Resend's shared test sender, which needs no domain of your own. It delivers only to the e-mail address of the Resend account owner, so sign up, reset passwords and subscribe with that address while developing. Resend answers any other recipient with a 403, `You can only send testing emails to your own email address`. That e-mail fails and is reported like any other refused one, but the refusal concerns that recipient alone, so `sendEmail` does not mark the sender unavailable and auth e-mails to the owner keep going out. The deploy check refuses `onboarding@resend.dev` for preview and production, where customers would receive nothing.

### Deploy check

`deploy:preview` and `deploy:production` run `scripts/verify-email-sender.ts <environment>` right after `verify-bindings.ts`, `verify-stripe-keys.ts` and `verify-turnstile-keys.ts` and before the build, so a sender Resend would refuse stops the deploy within seconds and the live Worker stays as it was. The script reads `RESEND_API_KEY`, `RESEND_EMAIL_FROM` and the optional `RESEND_MANAGEMENT_API_KEY` the way `prepare-deploy-secrets.ts` does, the process environment first and `.env.<environment>` second, so it checks the values that are about to be uploaded. A variable exported but empty takes precedence over the file, and a missing file counts as empty. The deploy workflows pass all three secrets to the step that runs the deploy script. The logic is `verifyEmailSender` in `src/integrations/resend/resend.sender.ts`, unit tested in `__test__/resend.sender.test.ts` with the Resend client mocked.

The check fails, with a message that says what to fix, when:

- `RESEND_API_KEY` is missing or blank;
- `RESEND_EMAIL_FROM` is missing, carries a display name or spaces, or has no domain;
- `RESEND_EMAIL_FROM` is on `resend.dev` outside development;
- Resend rejects the key (`invalid_api_key`, `missing_api_key`, `validation_error`, or `restricted_api_key` for the management key), or still cannot list the account's domains after asking twice;
- the sender's domain is not in the account, compared without case but otherwise exactly, so a subdomain needs its own entry;
- sending is disabled for the domain;
- the domain is not `verified` and its sending records do not make up for it: a DKIM or SPF record is not `verified`, or Resend lists no DKIM or no SPF record for the domain. The message lists the records still to publish with their type, name, value, priority and status. Receiving and tracking records do not count;
- Resend does not answer within `VERIFY_EMAIL_SENDER_TIMEOUT_MS` (30 seconds).

A domain Resend reports as `verified` passes without a look at its records. The record statuses decide only for a domain in another state, such as `partially_verified` while a receiving record is still pending.

A key with Resend's **Sending access** permission, the right one for the Worker, may not list domains: Resend answers `restricted_api_key`, which the SDK logs as `[Resend API Error]` and which also shows that the key itself is valid. The check then reads the domain with `RESEND_MANAGEMENT_API_KEY` when it is set: an optional **Full access** key of the same Resend team, used by this script alone. Like the `CLOUDFLARE_*` credentials it is not in `secrets.required`, so it never reaches the Worker; in GitHub, add it as a secret of the `preview` and `production` environments.

Without it, the check sends one e-mail from `M'Arte <RESEND_EMAIL_FROM>` to `delivered@resend.dev`, Resend's test inbox, and fails with Resend's own message when the send is refused. That e-mail counts against the same daily and monthly quota as the shop's mail, and every preview deploy, which means every push to a pull request, sends one. Once the quota runs out, live sends get `daily_quota_exceeded` or `monthly_quota_exceeded`, `sendEmail` marks the sender unavailable, and sign-up, password reset and change-email answer `503 EMAIL_DELIVERY_UNAVAILABLE`. Set `RESEND_MANAGEMENT_API_KEY` wherever deploys are frequent. For `onboarding@resend.dev` in development the check only confirms that Resend accepts the key, because that sender can reach no inbox but the owner's.

Run it by hand against the real Resend API:

```sh
bun run email:verify development
bun run email:verify preview
bun run email:verify production
```

Resend's rate limit is shared with the live Worker's sends, so each request is asked again once, after `RESEND_RETRY_DELAY_MS` (one second), when Resend answers `rate_limit_exceeded`, `application_error` or `internal_server_error`. The Resend SDK has no timeout, so the whole check gives up after 30 seconds. Beyond that the check fails closed: an outage or a second rate limit fails the deploy as well, and there is no bypass flag. In an emergency, run the remaining steps of the deploy script by hand. A pass is a snapshot of the moment of the deploy; a DNS record removed later breaks sending again with no check running, and the failures then show in the audit log as described above.
