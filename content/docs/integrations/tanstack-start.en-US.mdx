The application is one TanStack Start app that Cloudflare runs as a single Worker. Three files describe it: `src/router.tsx` builds the router, `src/server.ts` is the Worker's `ExportedHandler`, and `vite.config.ts` wires the Start plugin together with the Cloudflare plugin.

## The router

`getRouter()` in `src/router.tsx` creates a fresh `QueryClient` and a fresh `ImagePrefetchService` per request, puts both into the router context, and registers the SSR query integration:

```tsx
const router = createRouter({
  context: { imagePrefetchService, queryClient },
  defaultErrorComponent: DefaultErrorComponent,
  defaultNotFoundComponent: DefaultNotFoundComponent,
  defaultPendingComponent: DefaultPendingComponent,
  defaultPendingMinMs: PENDING_MIN_DISPLAY_MS,
  defaultPendingMs: PENDING_SHOW_DELAY_MS,
  defaultPreload: "intent",
  defaultPreloadDelay: 100,
  defaultPreloadIntentProximity: 1000,
  defaultPreloadStaleTime: 0,
  defaultStaleTime: ONE_MIN_IN_MS,
  defaultStructuralSharing: true,
  rewrite: {
    input: ({ url }) => deLocalizeUrl(url),
    output: ({ url }) => localizeUrl(url),
  },
  routeTree,
  scrollRestoration: true,
  scrollRestorationBehavior: "instant",
  ssr: nonce === undefined ? {} : { nonce },
})
setupRouterSsrQueryIntegration({ queryClient, router })
```

On the server, `nonce` is the Content-Security-Policy nonce `src/server.ts` drew for the request, read with `getGlobalStartContext()` inside `createIsomorphicFn().server(…)`. Start stamps `ssr.nonce` on its hydration scripts, on the tags `<HeadContent />` and `<Scripts />` render and on a `<meta property="csp-nonce">`, from which the browser router takes it back when it hydrates. See [Security model](/docs/architecture/security-model#response-headers).

The `rewrite` pair is what makes locale prefixes invisible to the route tree: an incoming `/en-US/products` is de-localized to `/products` before matching, and every generated href is re-localized on the way out. See [use-intl](/docs/integrations/use-intl) for `deLocalizeUrl` and `localizeUrl`.

Pending, error and not-found components are global defaults from `src/presentation/components/custom/defaults/`. A pending component appears only after 200 ms and then stays for at least 300 ms, so fast navigations never flash. `ReactQueryDevtools` is mounted through `Wrap` but only under `import.meta.env.DEV`.

## The Worker entry point

`wrangler.jsonc` points `main` at `./src/server.ts`. That file handles four things before the Start handler ever sees the request:

| Path                          | Behaviour                                                                                        |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `/sitemap.xml`                | `generateSitemapXml(origin, await listSitemapPages())`, the pages read from D1, cached for a day |
| `/robots.txt`                 | `generateRobotsTxt(origin, env.APP_ENV)`, cached for a day                                       |
| `/api/realtime/admin/ws`      | WebSocket upgrade into the admin invalidation hub                                                |
| `/api/realtime/storefront/ws` | WebSocket upgrade into the storefront invalidation hub                                           |

Everything else goes through `resolveLocale(request)`, which can return a 301 to the canonical locale path or a `Set-Cookie` to be appended to the response, and is then handed to `renderPage` inside `executionContextStorage.run({ waitUntil }, …)`. `renderPage` is the Start handler that `createStartHandler` from `@tanstack/react-start/server` builds around `defaultStreamHandler`, the same pair the default server entry uses, with the render step timed for the `Server-Timing` header. That `AsyncLocalStorage` store is how `scheduleBackgroundWork` in `src/lib/background.ts` reaches `ctx.waitUntil` from deep inside a use case, which the audit log, the transactional emails and [realtime invalidation](/docs/integrations/realtime-invalidation) all rely on. Every response except the WebSocket upgrades then goes through `withSecurityHeaders` from `src/lib/security-headers.ts`, which sets the Content-Security-Policy with the request's nonce and the other security headers, and `src/server.ts` adds a `Server-Timing` header to a page load (see [Request timings](/docs/guides/monitoring-and-alerts#request-timings)).

The same file exports the Durable Object class, a `queue` handler and a `scheduled` handler:

```ts
export { RealtimeInvalidationHub } from "~/src/durable-objects/realtime-invalidation-hub"

async queue(batch: MessageBatch<WorkerQueueMessage>, _env: Env, _ctx: ExecutionContext): Promise<void> {
  if (isNewsletterQueueBatch(batch)) {
    const { processNewsletterQueueBatch } = await import("~/src/modules/newsletter-campaign/use-cases/process-newsletter-queue.server")
    await processNewsletterQueueBatch(batch)
  }

  if (isAuditLogQueueBatch(batch)) {
    const { processAuditLogQueueBatch } = await import("~/src/modules/audit-log/use-cases/process-audit-log-queue.server")
    await processAuditLogQueueBatch(batch)
  }
},
async scheduled(controller: ScheduledController, _env: Env, _ctx: ExecutionContext): Promise<void> {
  const { enforceRetentionPeriods } = await import("~/src/lib/retention")
  await enforceRetentionPeriods(new Date(controller.scheduledTime))
},
```

`WorkerQueueMessage` is the union of an audit-log message and a newsletter campaign message. One Worker consumes both queues, so `queue` tells them apart by the batch's queue name: `isNewsletterQueueBatch` matches the names that start with `martebizuteria-newsletter`, and every other batch is the audit log's. Each processor, and the retention code behind `scheduled`, is imported lazily, so none of it is loaded for an ordinary request.

The preview and production Cron Triggers (`0 3 * * *`) call `scheduled` once a day for the retention clean-up described in [Data retention](/docs/guides/data-retention).

`RequestContext` is declared into `@tanstack/react-start` in the same file, so `edgeTimeZone`, `env`, `nonce`, `waitUntil` and `passThroughOnException` are typed everywhere a server function reads the request context. `edgeTimeZone` is `request.cf?.timezone`, the time zone Cloudflare derives from the visitor's address; [use-intl](/docs/integrations/use-intl#display-preferences) uses it when the browser has not yet reported its own.

## File routes

`src/routes/` holds flat file routes. `admin.catalog.products.tsx` serves `/admin/catalog/products`, `_storefront.tsx` is a pathless layout that wraps the public pages, `docs.$.tsx` is a splat route and `api/webhooks.stripe.ts` is a handler-only route. `routeFileIgnorePattern: "__test__"` in `vite.config.ts` keeps the colocated test folders out of the route tree, and `src/routeTree.gen.ts` is generated — never edit it by hand.

Code splitting is configured explicitly:

```ts
codeSplittingOptions: {
  defaultBehavior: [["component"], ["loader"], ["errorComponent"], ["notFoundComponent"]],
}
```

Every deploy publishes new, hashed chunk files and drops the old ones, so a tab opened before a deploy can no longer load the chunk of a page, or the message file of a namespace, that it has not loaded yet. Vite's preload helper reports such a failed import with a `vite:preloadError` event. `listenForStaleChunks` (`src/lib/stale-chunk.ts`), which `getRouter()` installs in the browser, then asks the server for the chunk it is itself part of (`import.meta.url`), with a `HEAD` request that skips the cache. Only when the server no longer serves that file, because a deploy has replaced the tab's code, does it reload the page once, so the tab fetches the current deploy's files instead of showing the error screen. A failed import while the server still serves the tab's code, and a check that cannot reach the server, leave the page alone. Imports that a navigation away aborts look exactly like that, and the `beforeunload` guard described below does not always catch them: `getRouter()` installs the listeners when the page hydrates, often only after the `load` event, so a navigation that starts earlier has fired `beforeunload` before they exist, and a page cut short before it finished loading fires its first `pageshow` after `beforeunload`, which lifts the guard again. Reloading such a page would cancel the navigation. It records the reload in `sessionStorage` and leaves a second failure within ten seconds to the error screen, so a chunk that is really missing cannot reload the page in a loop. Once the page fires `beforeunload` or `pagehide` it reloads nothing, because a browser also reports the imports a navigation away aborts, and reloading then would cancel that navigation; `pageshow` lifts this again for a page the back-forward cache restores.

TanStack Router has a reload of its own: when the chunk of a page component fails with a message it takes for a missing module, such as Safari's `Importing a module script failed.`, `lazyRouteComponent` reloads the page once per tab session, which would cancel such a navigation away as well. `getRouter()` therefore also listens for `vite:preloadError` and writes the `sessionStorage` key the router checks before that reload (`tanstack_router_reload:` followed by the error message), so the router shows the page's error screen instead and only `listenForStaleChunks` decides on a reload.

`src/routes.ts` exports `ROUTES`, the single table of path constants. Links, guards, `head` tags, the sitemap and the WebSocket paths all read from it, so a path is written once:

```ts
export const ROUTES = {
  ACCOUNT_ORDER: "/account/orders/$id",
  ADMIN_PRODUCTS: "/admin/catalog/products",
  API_REALTIME: {
    ADMIN_WS: "/api/realtime/admin/ws",
    STOREFRONT_WS: "/api/realtime/storefront/ws",
  },
  DOCS_PAGE: "/docs/$",
  PRODUCT: "/products/$handle",
} as const
```

## What belongs in a route file

A route file composes a page and nothing more. It declares its component, its `staticData.namespaces`, a loader that runs message loading and data prefetching in one `Promise.all`, and a `head`. `src/routes/_storefront.products.index.tsx` is representative:

```ts
beforeLoad: ({ search }) => ({
  catalogSearch: normalizeStorefrontProductsSearch(search),
}),
loader: async ({ context, deps }) => {
  const [messages] = await Promise.all([
    context.queryClient.query(messagesQueryOptions<typeof productsMessages>({ locale: context.locale, namespace: "pages.products" })),
    prefetchProductsCatalogPage(context.queryClient, context.imagePrefetchService, { search: context.catalogSearch }),
  ])

  const t = createTranslator({ locale: context.locale, messages })

  return {
    description: messages.description,
    structuredData: buildBreadcrumbStructuredData({ leaf: messages.title, locale: context.locale, sections: [] }),
    title: deps.q === undefined ? messages.title : t("search.pageTitle", { query: deps.q }),
  }
},
loaderDeps: ({ search }: { search: StorefrontProductsSearch }) => ({ q: search.q }),
staticData: { namespaces: ["pages.products"] },
validateSearch: storefrontProductsSearchSchema,
```

Widgets, dialogs, forms and table columns live under `src/presentation/components/custom/` and read their own translations and their own queries. The simpler routes use `head: pageHead` from `src/lib/seo.ts`, which turns the loader's `{ title, description }` into `<title>`, `description` and the two matching Open Graph tags, plus the page's own `og:image` and `twitter:image` when the loader returns an `image` and a JSON-LD script when it returns `structuredData`.

`src/routes/__root.tsx` owns the document shell: `beforeLoad` resolves the locale and, in one `Promise.all`, preloads every namespace the matched routes ask for and the user's `displayPreferencesQuery`, `shellComponent` renders `<html lang>` with the Zod configuration script and the theme, sidebar and datagrid init scripts, and `head` assembles the canonical and `hreflang` links from `localeLinks`. Storefront pages are wrapped in `SmoothScroll`; admin pages are not.

## Server functions

Mutations and server-side reads are native `createServerFn` functions exported from module use cases, so the application exposes no REST surface for them. A use case declares its own authorization and validation:

```ts
export const createCompleteProduct = createServerFn({ method: "POST" })
  .middleware([authorized({ product: ["create"] })])
  .validator((input: zod.input<typeof productZodSchemas.createCompleteInput>) => productZodSchemas.createCompleteInput.parse(input))
  .handler(async ({ data }) => {
    /* … */
  })
```

Route guards in `beforeLoad` only decide what to render; they never stand in for authorization. See [Better Auth](/docs/integrations/better-auth) for `authorized`, `withRequest` and `withRateLimit`.

Where a handler would pull heavy server-only code into the client graph, the module splits into `x.ts` and `x.server.ts` and imports lazily. `src/integrations/stripe/stripe.actions.ts` does exactly this:

```ts
.handler(async ({ data }) => {
  const { handleCreateCheckoutSession } = await import("~/src/integrations/stripe/stripe.actions.server")

  return handleCreateCheckoutSession(data)
})
```

## HTTP handlers

Only six routes declare `server.handlers`:

| Route                         | File                                       | Handler                                                                                      |
| ----------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `/api/auth/$`                 | `src/routes/api/auth.$.ts`                 | `handleAuthRequestWithAudit(request)` for `GET` and `POST`                                   |
| `/api/webhooks/stripe`        | `src/routes/api/webhooks.stripe.ts`        | `POST` checks `stripe-signature`, runs `webhookHandlers`; `GET` gets `405`                   |
| `/api/webhooks/inpost`        | `src/routes/api/webhooks.inpost.ts`        | `POST` is rate limited per address and reads the shipment back from ShipX; `GET` answers 200 |
| `/api/newsletter/unsubscribe` | `src/routes/api/newsletter.unsubscribe.ts` | `POST` unsubscribes the `token`'s subscriber, the one-click unsubscribe of RFC 8058          |
| `/api/health`                 | `src/routes/api/health.ts`                 | `GET`; reads D1, KV and R2 and answers 200 or 503                                            |
| `/dev/emails`                 | `src/routes/dev.emails.tsx`                | `GET`; returns 404 unless `import.meta.env.DEV`                                              |

```ts
export const Route = createFileRoute("/api/auth/$")({
  server: {
    handlers: {
      GET: ({ request }) => handleAuthRequestWithAudit(request),
      POST: ({ request }) => handleAuthRequestWithAudit(request),
    },
  },
})
```

The realtime WebSocket endpoints are deliberately _not_ file routes — they are matched in `src/server.ts` before the Start handler, because a WebSocket upgrade has to be answered by the Durable Object itself.

## No prerendering

`vite.config.ts` does not enable prerendering, and no script prerenders pages. Every page, including the storefront and these documentation pages, is server-rendered on the Worker for each request. Caching therefore comes from the query layer and from HTTP cache headers rather than from a build-time HTML snapshot.
