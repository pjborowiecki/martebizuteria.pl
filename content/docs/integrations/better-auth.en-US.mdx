Better Auth owns identity: e-mail and password sign-in, Google and GitHub OAuth, e-mail verification, password reset, e-mail change, two-factor, anonymous sessions, multi-session and the admin role model. It stores everything in D1 through the Drizzle adapter, and it is the source of the `authorized()` middleware that every protected server function declares.

## The instance

`src/integrations/better-auth/auth.server.ts` configures one `betterAuth(...)` instance. The pieces worth knowing:

| Option                         | Value                                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------------- |
| `database`                     | `drizzleAdapter(db, { provider: "sqlite", schema })`                                            |
| `advanced.database.generateId` | `() => uuidv7()`, with `joins: true`                                                            |
| `advanced.ipAddress`           | Reads `cf-connecting-ip` (`IP_ADDRESS_HEADER` from `src/lib/rate-limit.ts`)                     |
| `advanced.useSecureCookies`    | `!isLocalMode(import.meta.env.MODE)`                                                            |
| `advanced.backgroundTasks`     | `{ handler: scheduleBackgroundWork }`, so Better Auth's own async work rides on `ctx.waitUntil` |
| `baseURL.allowedHosts`         | `appHostsForMode(import.meta.env.MODE)` from `src/modules/_core/constants/api.ts`               |
| `emailAndPassword`             | Enabled, `requireEmailVerification: true`, min 8 / max 1024 characters                          |
| `emailVerification`            | `sendOnSignUp: true`, `autoSignInAfterVerification: true`                                       |
| `hooks.before`                 | Refuses the four email-sending endpoints while the email sender is marked unavailable           |
| `session`                      | `storeSessionInDatabase: true`, cookie cache turned off (`cookieCache: { enabled: false }`)     |
| `verification`                 | `storeIdentifier: "hashed"`, `storeInDatabase: true`                                            |
| `socialProviders`              | `google` and `github`, with `account.accountLinking.trustedProviders` covering both             |
| `account.encryptOAuthTokens`   | `true`                                                                                          |
| `telemetry`                    | Disabled                                                                                        |
| `user.additionalFields`        | `timezone` (string, optional, accepted as input)                                                |
| `user.changeEmail`             | Enabled, with `sendChangeEmailConfirmation`                                                     |

Plugins: `admin({ ac, adminRoles, defaultRole, roles })`, `anonymous()`, `multiSession({ maximumSessions: 5 })`, `twoFactor({ issuer: APP_NAME })`, the local `signInAudit` and `tanstackStartCookies()`. The last one is what makes Better Auth's cookies work with TanStack Start's response handling, and it must stay last in the array.

### Built-in rate limiting

Better Auth's own limiter is enabled with `storage: "database"`, a global 100 requests per 60 seconds, plus per-endpoint rules keyed off `ROUTES.API_AUTH`:

| Endpoint                  | Limit per 60 s |
| ------------------------- | -------------- |
| `/sign-in/email`          | 5              |
| `/sign-up/email`          | 3              |
| `/request-password-reset` | 3              |
| `/reset-password`         | 5              |

This is separate from the application's own `withRateLimit` middleware described below; both write to the `rate_limit` table.

### Database hooks

`databaseHooks` is where account events reach the rest of the application:

- `user.create.after` calls `scheduleAdminCustomersInvalidation()` and `recordCustomerRegisteredAudit(...)`.
- `user.update.after` and `user.delete.after` both call `scheduleAdminCustomersInvalidation()`, so the admin customer list refreshes without a poll.

### Sign-in audit

A new session is not always a sign-in. Better Auth also creates one when the password step of a two-factor sign-in starts (and the `twoFactor` plugin deletes it again), when two-factor is turned on or off, and when a password change signs the other devices out. The `signInAudit` plugin therefore records `auth.login` from an after hook rather than from `databaseHooks`. It matches the sign-in paths (`/sign-in/`, `/sign-up/`, `/callback/`, `/verify-email` and `/two-factor/verify-`), runs after `twoFactor` so a pending two-factor challenge has already cleared `newSession`, and calls `recordAuthLoginAudit(...)` for every `ctx.context.newSession` except one that continues the session the request arrived with. Two requests do that: confirming a new e-mail address re-issues the same session, and confirming two-factor set-up through `/two-factor/verify-*` swaps the signed-in session for a fresh one. Completing a two-factor sign-in arrives without a session and records one login, and so does signing in again on a browser that is still signed in, because the customer entered their password again.

### Transactional e-mail

Four of the eight application e-mails are sent from this file: `sendVerificationEmail`, `sendResetPassword`, `sendChangeEmailConfirmation` and `sendAccountDeletedEmail`. Each loads its own message namespace, renders its React Email component and hands it to `deliverAuthEmail`, which calls `sendEmail`. When Resend refuses the message, `recordAuthEmailFailure` logs `[Auth] Failed to send <kind> email to <address>: <error>` and records an `email.failed` audit entry. `resolveEmailVerificationCallbackUrl` additionally rewrites a verification link that would land on the storefront home so it lands on `/account/overview?verified=true` instead. See [Resend](/docs/integrations/resend).

The first three hooks go through `requireAuthEmailDelivery`, which sends with `revealsAccountExistence: true` (see [Email delivery gate](#email-delivery-gate)) and throws `APIError.from("SERVICE_UNAVAILABLE", { code: "EMAIL_DELIVERY_FAILED" })` when Resend refuses the email. What the person sees depends on how Better Auth runs the hook:

| Endpoint                                         | When Resend refuses the email                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/send-verification-email`                       | Better Auth awaits the hook, so the request answers `503` with `EMAIL_DELIVERY_FAILED`. The forms show "We couldn't send the email just now. Please try again in a few minutes."                                                                                                                                                                          |
| `/sign-up/email`                                 | Better Auth runs the hook in the background and drops its error. The account is created unverified and the generic answer stands. The person asks for a new link from the sign-in page.                                                                                                                                                                   |
| `/request-password-reset`                        | Background as well, and the generic answer must stand: a different answer for an address with an account would reveal that the account exists.                                                                                                                                                                                                            |
| `/change-email`                                  | Background as well. Better Auth sends nothing when the new address is already taken, so the toast says "If the new address is available, we've sent a confirmation link to …" and asks the person to try again if nothing arrives. The verification sent to the new address once the change is confirmed also runs in the background, after the redirect. |
| `/delete-user` (`afterDelete`), `deleteCustomer` | `sendAccountDeletedEmail` returns `false` and never throws, because the account is already gone. It catches a refusal from Resend and an error while preparing the email alike, and both are logged and audited. A throw from `afterDelete` would turn a finished deletion into a 500. `deleteCustomer` returns the result as `goodbyeEmailSent`.         |

Removing `advanced.backgroundTasks` would not change the background rows: without a handler Better Auth awaits the hook but still catches and logs its error.

### Email delivery gate

`sendEmail` marks the sender unavailable for five minutes when Resend refuses every email, for example because the sending domain is not verified (see [Resend](/docs/integrations/resend)). While the flag is set, `hooks.before` refuses `/sign-up/email`, `/request-password-reset`, `/send-verification-email` and `/change-email` before the endpoint runs:

```ts
hooks: {
  before: createAuthMiddleware(async (ctx) => {
    if (EMAIL_SENDING_AUTH_PATHS.has(ctx.path) && (await isEmailSenderUnavailable())) {
      throw APIError.from("SERVICE_UNAVAILABLE", EMAIL_DELIVERY_UNAVAILABLE)
    }
  }),
},
```

The answer is `503` with `EMAIL_DELIVERY_UNAVAILABLE`, shown as "We can't send emails at the moment, so nothing has been changed. Please try again in a few minutes." No account is created, no token is stored, and known and unknown addresses get the same answer. The paths come from `ROUTES.API_AUTH`. Sign-in, verification links, account deletion and every other endpoint pass straight through without reading KV.

Only an email whose sending says nothing about which accounts exist may set the flag: the newsletter emails (every submitted address gets one), the order confirmation and shipped emails, and the account-deleted email. The verification, reset and change-email confirmation go out only when an account does or does not exist, so `requireAuthEmailDelivery` sends them with `revealsAccountExistence: true` and `sendEmail` leaves the flag alone. Otherwise the flag would answer the question the generic responses hide: during an outage, request a reset for an address, then one for a random address, and a `503` on the second would mean the first has an account. Those refusals are still logged and audited.

So the gate closes only once one of the other emails has been refused. Until then, sign-up, password reset and change-email keep their generic success while their emails fail, because a different answer for that one request would reveal whether the address has an account. The audit log has every failure, and the copy tells the person to sign in for a new confirmation link or to request a new reset link if nothing arrives. The gate only limits the damage; checking that the sending domain is verified before a deploy is what prevents it. After the flag expires, one real attempt goes through again; if the sender is still broken, the next refused email sets the flag again.

If KV cannot be read, `isEmailSenderUnavailable` logs `[Resend] Email sender availability unreadable` with the error and answers `false`, so the gate lets the request through. Password reset is the way back into an account and must not depend on KV; a send that then fails is still logged and audited like any other.

On the sign-in page, a sign-in refused with `EMAIL_NOT_VERIFIED` shows `UnverifiedEmailNotice` with "Send the confirmation link again". That call goes to `/send-verification-email`, so its success toast, "A new confirmation link is on its way to …", only appears after Resend has accepted the email. Better Auth returns `EMAIL_NOT_VERIFIED` only after the password has been checked, so the notice reveals nothing to someone who does not know the password.

The endpoint itself can be called without the form, and there the honest answer has a cost. Signed out, Better Auth calls the hook only for an address with an unconfirmed account and answers `200` for any other address. While single sends fail (a Resend rate limit or outage, or a sender refusal before the flag is set), an unconfirmed account therefore gets `503 EMAIL_DELIVERY_FAILED` where an unknown or confirmed address gets `200`. This is how Better Auth treats a hook that throws, and it is the price of telling the person the truth about their resend. It reveals only unconfirmed accounts, only while sends are failing, at Better Auth's default limit of three requests per minute per IP, and while the flag is set the gate answers every address alike.

## Roles and permissions

`auth.access.ts` builds the access-control model with Better Auth's `createAccessControl`:

```ts
export const ROLES = { ADMIN: "admin", CUSTOMER: "customer" } as const

export const RESOURCES = { ORDER: "order", PRODUCT: "product", SETTINGS: "settings", USER: "user" } as const

export const ACTIONS = {
  CREATE: "create",
  DELETE: "delete",
  MANAGE: "manage",
  PUBLISH: "publish",
  READ: "read",
  REFUND: "refund",
  UPDATE: "update",
} as const

export const PERMISSIONS_STATEMENTS = {
  ...defaultStatements,
  [RESOURCES.ORDER]: [ACTIONS.READ, ACTIONS.UPDATE, ACTIONS.REFUND],
  [RESOURCES.PRODUCT]: [ACTIONS.CREATE, ACTIONS.READ, ACTIONS.UPDATE, ACTIONS.DELETE, ACTIONS.PUBLISH],
  [RESOURCES.SETTINGS]: [ACTIONS.MANAGE],
} as const
```

`ROLES_CONFIG.admin` receives all of those plus `adminAc.statements` (Better Auth's own `user` and `session` management statements). `ROLES_CONFIG.customer` receives empty arrays for every resource — a customer holds no administrative permission at all. `DEFAULT_ROLE` is `customer` and `ADMIN_PANEL_ROLES` is `["admin"]`.

Two predicates are exported and used everywhere:

```ts
export const hasAdminAccess = (role: string | null | undefined): role is Role =>
  typeof role === "string" && (ADMIN_PANEL_ROLES as readonly string[]).includes(role)

export const hasPermission = ({ permission, role }: { permission: Permission; role: string | null | undefined }): boolean =>
  isKnownRole(role) && ROLES_CONFIG[role].authorize(permission).success
```

## Server-function middleware

`auth.middleware.ts` exports the three middlewares every server function composes from.

`withRequest` puts the request headers into context and funnels every thrown error through one translator:

```ts
export const withRequest = createMiddleware({ type: "function" }).server(({ next }) =>
  next({ context: { requestHeaders: getRequest().headers } }).catch(handleRequestError),
)
```

`handleRequestError` first rethrows a TanStack `notFound()` unchanged (`isNotFound`), so a route answers 404 instead of a 500. It then rebuilds an `AppError` from its code, and keeps its message only when that message is a reason code in upper snake case, such as `WISHLIST_FULL` or `HAS_CHILDREN`, so the browser can explain the failure. Any free-text message is replaced by the code. It maps a Better Auth `APIError` to `AppError(AUTH_API_ERROR, authErrorKey(error))`, a `ZodError` to `AppError(VALIDATION)` and everything else to `AppError(INTERNAL_ERROR)` after logging it. The client never sees a raw stack trace or a vendor error string.

`authorized(permission?)` builds on `withRequest`, loads the session and either rejects or puts it into context:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && !hasPermission({ permission, role: session.user.role })) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

Called without an argument it only requires a signed-in user; called as `authorized({ product: ["create"] })` it also requires that permission. A use case therefore declares its own authorization in its signature:

```ts
export const createCompleteProduct = createServerFn({ method: "POST" }).middleware([authorized({ product: ["create"] })])
```

`withRateLimit(kind, { max, window })` also builds on `withRequest` and applies the application's own limiter, keyed by `kind` plus the client address:

```ts
export const RATE_LIMITS = {
  CHECKOUT: { max: 10, window: RATE_LIMIT_WINDOW_SECONDS },
  SENSITIVE: { max: 3, window: RATE_LIMIT_WINDOW_SECONDS },
  TOKEN: { max: 5, window: RATE_LIMIT_WINDOW_SECONDS },
} as const
```

The window is 60 seconds. `withinRateLimit` in `src/lib/rate-limit.ts` implements it as a single conditional upsert into the `rate_limit` table with `onConflictDoUpdate` and a `setWhere`, so the counter and the window roll over in one statement. If the table is unreachable, the helper returns `false` — the limiter fails closed.

### This is enforced by a test

`src/integrations/better-auth/__test__/use-case-authorization.test.ts` walks every file under `src/modules/**/use-cases/`, and for each one that contains `createServerFn` asserts that it also contains `authorized(` — unless it is on an explicit allowlist of 19 deliberately public use cases (`get-product.ts`, `search-storefront.ts`, `check-cart-availability.ts` and so on). It also asserts that no use case asserts authorization inside its handler, and that every entry on the allowlist still exists. Adding a protected use case without middleware fails the test suite.

## Route guards

`auth.routes.ts` holds the _navigation_ guards. They decide what to render, never whether an operation is allowed; protected server functions authorize themselves through `authorized()`. Each layout route passes its guard as `beforeLoad` directly: `/account` has `beforeLoad: requireCustomer`, `/admin` has `beforeLoad: requireAdmin` and `/auth` has `beforeLoad: redirectIfSignedIn`.

| Export                      | Behaviour                                                                              |
| --------------------------- | -------------------------------------------------------------------------------------- |
| `requireSignedIn(route)`    | Resolves to `{ user }`, or redirects to `/auth/sign-in`                                |
| `requireAdmin(route)`       | Resolves to `{ user }` if `hasAdminAccess`, otherwise redirects to `/account/overview` |
| `requireCustomer(route)`    | Resolves to `{ user }` unless they are an admin, who is redirected to `/admin`         |
| `redirectIfSignedIn(route)` | Used on the auth pages; sends a signed-in visitor to `?redirect` or to their home      |
| `postAuthRouteFor(user)`    | `/admin` for an admin, `/account/overview` for a customer                              |
| `authEntryRouteFor(user)`   | `/auth/sign-in` when there is no user, otherwise `postAuthRouteFor`                    |

`route` is the `beforeLoad` argument, `{ context, location, preload }`. The `{ user }` a guard resolves to becomes route context, so a page reads the `SessionUser` with `Route.useRouteContext().user`.

The guards read the session through `context.queryClient.query(getCurrentSessionQuery)`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

`requireSignedIn`, `requireAdmin` and `requireCustomer` pass `recheck: true`, so a real navigation into `/account` or `/admin` re-checks with `staleTime: 0`. A link preload, and `redirectIfSignedIn` on `/auth` with `recheck: false`, reuse a cached session younger than 60 seconds. The session a guard loads stays in the TanStack Query cache, so the components that read it see the same value, and on a server render it is dehydrated into the page, so guarded pages render signed-in on the server. The guards only read the session. A change of user is handled in one place, `clearCacheOnUserChange` in `auth.session.ts`: whenever the cached session switches to a different user, whoever fetched it, it removes every other cached query except the translation message catalogues. It is described in [TanStack Query](/docs/integrations/tanstack-query).

### Sign-in redirects

An anonymous visitor to `/account` or `/admin` is redirected to `/auth/sign-in?redirect=<path>`. `requireSignedIn` passes `route.location.publicHref`, the localized public path such as `/en-US/account/orders/order-1`. It is only kept when it is a string matching `SAME_SITE_PATH_PATTERN`:

```ts
const SAME_SITE_PATH_PATTERN = /^\/(?![/\\])[!-[\]-~]*$/u
```

The pattern allows printable ASCII only (no spaces), a single leading slash and no backslash, so absolute URLs, protocol-relative `//`, backslashes, whitespace and control characters are dropped, and the visitor lands on `/auth/sign-in` without the parameter. `redirectIfSignedIn` checks the parameter the same way and sends a signed-in visitor to it with `redirect({ href })`, otherwise to `postAuthRouteFor(user)`. Because the value is the public path, a server-rendered redirect keeps the visitor's language, and on the client the router re-localizes it to the current language.

After a successful password sign-in or two-factor challenge, the form calls `usePostAuthRedirect` from `src/hooks/use-post-auth-redirect.ts`:

```ts
export const usePostAuthRedirect = (): (() => Promise<void>) => {
  const queryClient = useQueryClient()
  const router = useRouter()

  return useCallback(async () => {
    queryClient.removeQueries({ exact: true, queryKey: getCurrentSessionQuery.queryKey })
    router.clearCache()
    await router.invalidate()
  }, [queryClient, router])
}
```

It removes the cached session entry only, then clears the router's cached matches and invalidates the router. The `/auth` layout guard runs again, fetches the fresh session and redirects to `?redirect` when it is a safe same-site path, otherwise to `postAuthRouteFor(user)`. When the fresh session arrives, `clearCacheOnUserChange` forgets what was cached while signed out. The forms never choose a destination themselves.

Google and GitHub sign-in end the same way. `useOAuthSignIn` in `src/presentation/components/custom/pages/auth/hooks/use-oauth-sign-in.ts` passes the page the button was clicked on as `callbackURL`, read with `useLocation` as `location.publicHref`, for example `/en-US/auth/sign-in?redirect=...`. After the provider round trip the browser lands on that auth page, and `redirectIfSignedIn` sends the user on exactly as after a password sign-in.

Sign-out is a full page load that discards the cache: the account sidebar goes to `/`, the admin sidebar to `/auth/sign-in`.

## Reading the session

`auth.session.ts` avoids asking Better Auth for the same session twice in one request by memoizing on the `Request` object:

```ts
const requestSessions = new WeakMap<Request, ReturnType<typeof auth.api.getSession>>()

export const getRequestSession = createServerOnlyFn((request: Request = getRequest()) => {
  const cached = requestSessions.get(request)
  if (cached) {
    return cached
  }

  const session = auth.api.getSession({ headers: request.headers, query: { disableCookieCache: true } })
  requestSessions.set(request, session)

  return session
})
```

`disableCookieCache: true` means server-side authorization always reads the database rather than trusting a signed cookie cache. The cookie cache is also turned off in `auth.server.ts`, so Better Auth's own endpoints behind its session middleware — `/update-user`, the two-factor routes, `/get-session` — read the session row too: a browser signed out from another device is refused at once instead of being trusted for as long as its cached cookie lived. `getCurrentSession` is the server function wrapper, and it strips `session.token` before returning — the token never reaches the browser payload. `getCurrentSessionQuery` is the matching query options object and the only way routes and components read the session: the route guards load it, and components read it with `useQuery(getCurrentSessionQuery)`. It is described in [TanStack Query](/docs/integrations/tanstack-query).

## The client

`auth.client.ts` mirrors the server plugins and re-exports only what the UI needs:

```ts
export const authClient = createAuthClient({
  plugins: [
    adminClient({ ac, roles: ROLES_CONFIG }),
    anonymousClient(),
    inferAdditionalFields<typeof auth>(),
    multiSessionClient(),
    twoFactorClient(),
  ],
})

export const { signIn, signOut, signUp, resetPassword } = authClient
```

`inferAdditionalFields<typeof auth>()` is what gives the client the `timezone` field without a second declaration.

Better Auth's `useSession` hook is deliberately not exported: it would run during server rendering, which TanStack Start's import protection rejects for `*.client.*` files in the server build, and it would add a second session request. Components read the session with `useQuery(getCurrentSessionQuery)` instead.

## Validation and errors

`auth.constraints.ts` holds the raw limits (`EMAIL_MAX_LENGTH` 64, `NAME_MAX_LENGTH` 32, `PASSWORD_MIN_LENGTH` 8, `PASSWORD_MAX_LENGTH` 1024, and the uppercase and special-character patterns) plus `AUTH_VALIDATION_PARAMS`, which feeds the numbers into the translated messages.

`auth.zod.ts` builds the form schemas from them: `signInWithPasswordSchema`, `signUpWithPasswordSchema`, `forgotPasswordSchema` and `resetPasswordSchema`. Every `message` is a _translation key_, not English prose — `"passwordMinLength"`, `"passwordsMustMatch"`, `"invalidEmail"` — which the form layer resolves against `messages/{locale}/pages.auth.*.json`. Sign-in uses the permissive `signInPasswordSchema` (non-empty) while sign-up and reset use `strictPasswordSchema`, so an existing weak password can still be used to log in.

`auth.errors.ts` maps Better Auth's error codes onto the same kind of message keys through `AUTH_ERRORS`, and `authErrorKey(error)` parses either `{ code }` or `{ body: { code } }` and falls back to `unknownError`.

## The HTTP endpoint

`src/routes/api/auth.$.ts` is a handler-only route that does not call `auth.handler` directly but wraps it:

```ts
export const Route = createFileRoute("/api/auth/$")({
  server: {
    handlers: {
      GET: ({ request }) => handleAuthRequestWithAudit(request),
      POST: ({ request }) => handleAuthRequestWithAudit(request),
    },
  },
})
```

`handleAuthRequestWithAudit` in `src/modules/audit-log/audit-log.auth.server.ts` inspects the path before delegating: for `POST /sign-in/email` it clones the request to read the e-mail, and records a failed-login audit entry if the response is not OK; for `POST /sign-out` it captures the session first and records a logout entry if the response is OK. Successful sign-ins are audited by the `signInAudit` plugin instead (see "Sign-in audit" above).

## Tables

`user`, `session`, `account`, `verification`, `two_factor` and `rate_limit`. Each is defined in its own module (`src/modules/user/user.schema.ts` and so on) and re-exported from `drizzle.schemas.ts`. `user` carries the application's additions beyond Better Auth's own columns: `role` (enumerated `admin` / `customer`), `phone`, `timezone`, `stripe_customer_id`, `metadata`, and the ban and two-factor flags. `session.token` is a 16 KiB unique text column and `session.user_id` cascades on delete.

## Secrets

`AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `AUTH_GITHUB_CLIENT_ID` and `AUTH_GITHUB_CLIENT_SECRET`, all listed under `secrets.required` for each environment in `wrangler.jsonc`.
