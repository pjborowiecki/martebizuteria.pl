Better Auth owns identity: e-mail and password sign-in, Google OAuth, e-mail verification, password reset, e-mail change, two-factor, multi-session and the admin role model. It stores everything in D1 through the Drizzle adapter, and it is the source of the `authorized()` middleware that every protected server function declares.

## The instance

`src/integrations/better-auth/auth.server.ts` configures one `betterAuth(...)` instance. The pieces worth knowing:

| Option                         | Value                                                                                                                                                                                                                                                                   |

| `advanced.ipAddress`           | Reads `cf-connecting-ip` (`IP_ADDRESS_HEADER` from `src/lib/rate-limit.ts`)                                                                                                                                                                                             |
| `advanced.useSecureCookies`    | `!isLocalMode(import.meta.env.MODE)`                                                                                                                                                                                                                                    |

The last one is what makes Better Auth's cookies work with TanStack Start's response handling, and it must stay last in the array.

### Built-in rate limiting

Better Auth's own limiter is enabled with `customStorage: authRateLimitStorage` from `src/lib/rate-limit.ts`, a global 100 requests per 60 seconds, plus per-endpoint rules keyed off `ROUTES.API_AUTH`:

| Endpoint                  | Limit per 60 s |
| ------------------------- | -------------- |
| `/sign-in/email`          | 5              |
| `/sign-up/email`          | 3              |
| `/request-password-reset` | 3              |
| `/reset-password`         | 5              |

This is separate from the application's own `withRateLimit` middleware described below, but both count with `withinRateLimit` in the `rate_limit` table. `authRateLimitStorage` passes Better Auth's `<ip>|<path>` key and the matching rule to it, and a refusal answers 429 with the rule's window in `X-Retry-After`. Better Auth's `storage: "database"` is not used, because whenever one of its counters started a new window it deleted every `rate_limit` row whose `last_request` was older than its longest window, 60 seconds. `withinRateLimit` keeps the start of a window in `last_request`, so the hourly and daily caps on the e-mails visitors can request would have gone about a minute after they began.

### Database hooks

`databaseHooks` is where account events reach the rest of the application:

- `user.create.after` calls `scheduleAdminCustomersInvalidation()` and `recordCustomerRegisteredAudit(...)`.
- `user.update.after` and `user.delete.after` both call `scheduleAdminCustomersInvalidation()`, so the admin customer list refreshes without a poll.
- `user.delete.after` also records `customer.deleted` for every account except an anonymous one, credited to the session of the endpoint that deleted it: the admin for `/admin/remove-user`, which `deleteCustomer` calls through `auth.api.removeUser`, the customer for `/delete-user`, and the system when no session asked.
- `session.create.before` refuses the session a provider sign-in (`/callback/*`, or `/sign-in/social` with an ID token) would open for an admin, with `ADMIN_PASSWORD_SIGN_IN_REQUIRED`. See [Two-factor authentication for admins](#two-factor-authentication-for-admins).

### Account deletion

`user.deleteUser.beforeDelete` calls `eraseAccountData(user)` (`src/modules/user/user.erasure.server.ts`), which deletes the account's Stripe customer with its saved cards and then the account's audit log entries and newsletter subscription. When Stripe cannot delete the customer, it returns `false` and the hook throws `APIError.from("SERVICE_UNAVAILABLE", { code: "STRIPE_CUSTOMER_NOT_DELETED" })`, so the request answers `503` and Better Auth deletes nothing. The erasure cannot live in `databaseHooks.user.delete.before`: `internalAdapter.deleteUser` deletes the sessions and `account` rows before it runs that hook, so a Stripe failure there would leave an account without its password. `auth.api.removeUser` has no `beforeDelete`, so `deleteCustomer` calls `eraseAccountData` itself before it. See [Account: Closing the account](/docs/features/account#closing-the-account).

### Sign-in audit

A new session is not always a sign-in. Better Auth also creates one when the password step of a two-factor sign-in starts (and the `twoFactor` plugin deletes it again), when two-factor is turned on or off, and when a password change signs the other devices out. The `signInAudit` plugin therefore records `auth.login` from an after hook rather than from `databaseHooks`. It matches the sign-in paths (`/sign-in/`, `/sign-up/`, `/callback/`, `/verify-email` and `/two-factor/verify-`), runs after `twoFactor` so a pending two-factor challenge has already cleared `newSession`, and calls `recordAuthLoginAudit(...)` for every `ctx.context.newSession` except one that continues the session the request arrived with. Two requests do that: confirming a new e-mail address re-issues the same session, and confirming two-factor set-up through `/two-factor/verify-*` swaps the signed-in session for a fresh one. Completing a two-factor sign-in arrives without a session and records one login, and so does signing in again on a browser that is still signed in, because the customer entered their password again.

### Account linking

A Google sign-in whose e-mail address already belongs to a shop account joins that account only when Google reports the address as verified, through the `email_verified` field of its ID token, and when the shop account's own address is verified (Better Auth's `requireLocalEmailVerified`, on by default). Otherwise the callback links nothing, creates no session and redirects to Better Auth's error page with `error=account_not_linked`. `trustedProviders` stays unset: Better Auth skips the provider's check for a trusted provider, so anyone who put a customer's address on a Google account without verifying it would be signed in to that customer's shop account. `auth.account-linking.integration.test.ts` goes through the Google callback with an unverified and a verified address.

### No anonymous sign-in

Guests browse, fill a cart and check out without signing in, so Better Auth loads no `anonymous()` plugin. With it, anyone could call `/api/auth/sign-in/anonymous` and get a user row with the default `customer` role and a session that passes `authorized()`, and every call also recorded `customer.registered` in the audit log and added a row to the admin customer list. The endpoint now answers 404, which `auth.anonymous-sign-in.integration.test.ts` checks. The plugin's `user.is_anonymous` column still marks the users it created; see [Admin customers](/docs/features/admin-customers).

### Password reset

A completed reset through `/reset-password` signs the account out everywhere. With `emailAndPassword.revokeSessionsOnPasswordReset: true`, Better Auth deletes every session row of the user once the new password is stored, so a browser that stayed signed in, an intruder's included, is refused on its next request instead of keeping the account until its session expires. The reset page itself is signed out, because `/auth` sends a signed-in visitor away, and its success toast tells the customer that every device was signed out. Changing the password from the profile is a different endpoint, `/change-password`, where the customer chooses with "Sign out my other devices".

Better Auth awaits `emailAndPassword.onPasswordReset({ user }, request)` after storing the password and before deleting the sessions. The hook hands `sendPasswordChangedEmail({ request, user })` to `scheduleBackgroundWork` and returns at once, so the sign-out never waits for Resend and the email still finishes after the response. The email says the password was changed and every device signed out, links to `/auth/sign-in` on the address the reset came in on, and tells someone who did not make the change to secure their inbox, set a new password with "Forgot password?" and reply to the shop. `sendPasswordChangedEmail` never throws, because a hook that threw would answer the finished reset with a 500 and skip the sign-out. A refusal from Resend, a host outside `appHostsForMode` and an error while the email is prepared are logged and audited as `email.failed`, and a reset that came with no request, which only a server-side `auth.api.resetPassword` call could make, is recorded the same way without a send.

`auth.password-reset.integration.test.ts` signs a customer in on two browsers, resets the password from a third through `/request-password-reset` and `/reset-password`, and checks that both old sessions are refused and deleted, that the new password signs in, that the email links to `http://localhost:3000/en-US/auth/sign-in`, and that a refused email still leaves every device signed out. The browser test in `e2e/specs/auth.spec.ts` does the same through the forgot-password and reset forms.

### Account security audit

The `accountSecurityAudit` plugin records the changes to an account that Better Auth makes, from after hooks, so they are caught whichever client calls the endpoint. A hook records nothing when the endpoint answered with an error or no session called it. `/change-password` records `auth.password_changed`, and `auth.sessions_revoked` too when the body asks to revoke the other sessions; `/two-factor/disable` records `auth.two_factor_disabled`; and `/revoke-session`, `/revoke-sessions` and `/revoke-other-sessions` record `auth.sessions_revoked`, each credited to the signed-in account. `/two-factor/verify-totp` records `auth.two_factor_enabled` only when the caller arrived with two-factor off and `newSession` leaves with it on, so the code that completes a two-factor sign-in records nothing here. `/verify-email` verifies its token again with `verifyJWT` from `better-auth/crypto` and records `auth.email_changed`, with `old → new` as the detail, only for a `change-email-verification` token whose new address the re-issued session now carries; the confirmation sent to the old address and an ordinary address verification record nothing. The admin endpoints `/admin/set-role`, `/admin/ban-user`, `/admin/unban-user`, `/admin/update-user`, `/admin/revoke-user-sessions` and `/admin/set-user-password` look up the account named by `userId` and record the matching role, ban, e-mail, session or password event against it, credited to the admin. `/admin/revoke-user-session`, which names a session only by its token, and `/admin/impersonate-user` are not recorded. The recorders are chosen per path inside the hooks rather than kept in a module-level table, because `auth.server.ts`, `audit-log.events.server.ts`, `audit-log.record.server.ts` and `auth.session.ts` import one another, and a table built while the cycle is still loading could capture a recorder that is not defined yet. See [Audit log](/docs/features/audit-log#account-security-events) for the full list.

### Two-factor authentication for admins

The admin panel opens only for an admin with two-factor authentication on. `needsTwoFactorSetup({ role, twoFactorEnabled })` in `auth.access.ts` is true for an admin whose `user.two_factor_enabled` is not `1`, and four places apply it:

| Where                                      | What an admin without two-factor authentication gets                                         |
| ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `requireAdmin` on the `/admin` layout      | A redirect to `/admin/security` instead of the admin panel                                   |
| `authorized(permission)`                   | `FORBIDDEN` for every admin permission; `authorized()` without one still admits them         |
| The admin realtime WebSocket handshake     | `401`                                                                                        |
| `hooks.before` on Better Auth's `/admin/*` | `403` with `ADMIN_TWO_FACTOR_REQUIRED`; a customer still gets the admin plugin's own refusal |

The admin is never locked out. `/admin/security` is `admin_.security.tsx`, a route outside the `/admin` layout guarded by `requireAdminRole`, which checks the role only. It renders `AdminSecurityPage`, which reuses the account's `SecuritySection`: the same `TwoFactorDialog` turns two-factor authentication on with a password, a QR code or setup key, a six-digit code and the recovery codes, and turns it off again with the password. Its profile comes from `getCustomerProfileQuery`, whose `authorized()` needs no permission. Once two-factor authentication is on, the page links to the panel, and the sidebar's **Security** item leads back to it. An admin who turns it off is sent back to the page the next time they open the panel. The page also signs out, and an account without a password, which cannot turn two-factor authentication on, is told to sign out and set one with **Forgot password?**: Better Auth's reset creates the missing credential account.

Admins sign in with their password and a two-factor code, never with Google. The `twoFactor` plugin asks for the code from an after hook whose matcher is `/sign-in/email`, `/sign-in/username` and `/sign-in/phone-number` only (`node_modules/better-auth/dist/plugins/two-factor/index.mjs`, Better Auth 1.7.5). A Google sign-in finishes in `/callback/google`, which that hook never sees, so it opens a full session without the code. Account linking also joins a Google account whose verified address is the admin's to the admin on its first sign-in (see [Account linking](#account-linking)). The shop cannot see whether that Google account has its own 2-Step Verification. `session.create.before` therefore refuses a provider sign-in for an admin, whether or not their two-factor authentication is on, and Better Auth sends the browser to `/api/auth/error?error=ADMIN_PASSWORD_SIGN_IN_REQUIRED`. Customers keep Google sign-in, and for them it still skips the code, so a customer's two-factor authentication covers password sign-in only.

Better Auth's other ways to open a session for an existing admin do not skip the code: a trusted device is set only by a two-factor sign-in on that browser, the verification link signs in only an unverified address, and confirming a new address starts from a signed-in session. Password reset opens no session.

### Transactional e-mail

Five of the sixteen application e-mails are sent from this file: `sendVerificationEmail`, `sendResetPassword`, `sendChangeEmailConfirmation`, `sendPasswordChangedEmail` and `sendAccountDeletedEmail`. Each loads its own message namespace, renders its React Email component and hands it to `deliverAuthEmail`, which calls `sendEmail`. When Resend refuses the message, `recordAuthEmailFailure` logs `[Auth] Failed to send <kind> email to <address>: <error>` and records an `email.failed` audit entry. `resolveEmailVerificationCallbackUrl` additionally rewrites a verification link that would land on the storefront home so it lands on `/account/overview?verified=true` instead. See [Resend](/docs/integrations/resend).

The links in the first three come from Better Auth's `url`, which it builds on the request host after checking it against `baseURL.allowedHosts`. `sendAccountDeletedEmail` links to the storefront home on the `origin` it is given, which `deleteCustomer` resolves with `resolveRequestOrigin(getRequest())` before `removeUser`. After a self-service deletion, `afterDelete(user, request)` resolves it with `resolveRequestOrigin(request)` from the request Better Auth passes the hook. A host outside the list, or a deletion that came with no request, is logged and audited as an unsent goodbye email instead of turning the finished deletion into a 500. `sendPasswordChangedEmail` resolves the origin of its sign-in link the same way, with `resolveRequestOrigin(request)` on the request Better Auth passes `onPasswordReset`.

The first three hooks go through `requireAuthEmailDelivery`, which sends with `revealsAccountExistence: true` (see [Email delivery gate](#email-delivery-gate)) and throws `APIError.from("SERVICE_UNAVAILABLE", { code: "EMAIL_DELIVERY_FAILED" })` when Resend refuses the email. What the person sees depends on how Better Auth runs the hook:

| Endpoint                                         | When Resend refuses the email                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/send-verification-email`                       | Better Auth awaits the hook, so the request answers `503` with `EMAIL_DELIVERY_FAILED`. The forms show "We couldn't send the email just now. Please try again in a few minutes."                                                                                                                                                                          |
| `/sign-up/email`                                 | Better Auth runs the hook in the background and drops its error. The account is created unverified and the generic answer stands. The person asks for a new link from the sign-in page.                                                                                                                                                                   |
| `/request-password-reset`                        | Background as well, and the generic answer must stand: a different answer for an address with an account would reveal that the account exists.                                                                                                                                                                                                            |
| `/change-email`                                  | Background as well. Better Auth sends nothing when the new address is already taken, so the toast says "If the new address is available, we've sent a confirmation link to …" and asks the person to try again if nothing arrives. The verification sent to the new address once the change is confirmed also runs in the background, after the redirect. |
| `/reset-password` (`onPasswordReset`)            | `sendPasswordChangedEmail` runs in the background and never throws, because the password has already changed and Better Auth signs every device out only after the hook returns. The reset answers `200`, every device is signed out, and the refusal is logged and audited.                                                                              |
| `/delete-user` (`afterDelete`), `deleteCustomer` | `sendAccountDeletedEmail` returns `false` and never throws, because the account is already gone. It catches a refusal from Resend and an error while preparing the email alike, and both are logged and audited. A throw from `afterDelete` would turn a finished deletion into a 500. `deleteCustomer` returns the result as `goodbyeEmailSent`.         |

Removing `advanced.backgroundTasks` would not change the background rows: without a handler Better Auth awaits the hook but still catches and logs its error.

### Email delivery gate

`sendEmail` marks the sender unavailable for five minutes when Resend refuses every email, for example because the sending domain is not verified (see [Resend](/docs/integrations/resend)). While the flag is set, `hooks.before` refuses `/sign-up/email`, `/request-password-reset`, `/send-verification-email` and `/change-email` before the endpoint runs:

```ts
hooks: {
  before: createAuthMiddleware(async (ctx) => {
    if (EMAIL_SENDING_AUTH_PATHS.has(ctx.path) && (await isEmailSenderUnavailable())) {
      throw APIError.from("SERVICE_UNAVAILABLE", EMAIL_DELIVERY_UNAVAILABLE)
    }

    const botCheckAction = BOT_CHECKED_AUTH_PATHS.get(ctx.path)
    if (botCheckAction !== undefined && !(await passesBotCheck(ctx.request, botCheckAction))) {
      throw APIError.from("FORBIDDEN", BOT_CHECK_FAILED)
    }
  }),
},
```

The answer is `503` with `EMAIL_DELIVERY_UNAVAILABLE`, shown as "We can't send emails at the moment, so nothing has been changed. Please try again in a few minutes." No account is created, no token is stored, and known and unknown addresses get the same answer. The paths come from `ROUTES.API_AUTH`. Sign-in, verification links, account deletion and every other endpoint pass straight through without reading KV. The second check in the hook is the bot check; see [Bot check and email limits](#bot-check-and-email-limits).

Only an email whose sending says nothing about which accounts exist may set the flag: the newsletter emails (every submitted address gets one), the order confirmation and shipped emails, the account-deleted email, and the password-changed email, which goes only to an account whose reset link was just used and so tells whoever used it nothing new. The verification, reset and change-email confirmation go out only when an account does or does not exist, so `requireAuthEmailDelivery` sends them with `revealsAccountExistence: true` and `sendEmail` leaves the flag alone. Otherwise the flag would answer the question the generic responses hide: during an outage, request a reset for an address, then one for a random address, and a `503` on the second would mean the first has an account. Those refusals are still logged and audited.

So the gate closes only once one of the other emails has been refused. Until then, sign-up, password reset and change-email keep their generic success while their emails fail, because a different answer for that one request would reveal whether the address has an account. The audit log has every failure, and the copy tells the person to sign in for a new confirmation link or to request a new reset link if nothing arrives. The gate only limits the damage; checking that the sending domain is verified before a deploy is what prevents it. After the flag expires, one real attempt goes through again; if the sender is still broken, the next refused email sets the flag again.

If KV cannot be read, `isEmailSenderUnavailable` logs `[Resend] Email sender availability unreadable` with the error and answers `false`, so the gate lets the request through. Password reset is the way back into an account and must not depend on KV; a send that then fails is still logged and audited like any other.

On the sign-in page, a sign-in refused with `EMAIL_NOT_VERIFIED` shows `UnverifiedEmailNotice` with "Send the confirmation link again". That call goes to `/send-verification-email`, so its success toast, "A new confirmation link is on its way to …", appears only after Resend has accepted the email, or after the address limit below has quietly skipped it. Better Auth returns `EMAIL_NOT_VERIFIED` only after the password has been checked, so the notice reveals nothing to someone who does not know the password.

The endpoint itself can be called without the form, and there the honest answer has a cost. Signed out, Better Auth calls the hook only for an address with an unconfirmed account and answers `200` for any other address. While single sends fail (a Resend rate limit or outage, or a sender refusal before the flag is set), an unconfirmed account therefore gets `503 EMAIL_DELIVERY_FAILED` where an unknown or confirmed address gets `200`. This is how Better Auth treats a hook that throws, and it is the price of telling the person the truth about their resend. It reveals only unconfirmed accounts, only while sends are failing, at Better Auth's default limit of three requests per minute per IP, and while the flag is set the gate answers every address alike.

### Bot check and email limits

Sign-up, the password-reset request and the verification resend make the shop send an email to whatever address the request names. Repeated, they would flood someone's inbox or use up the Resend quota, after which the order emails stop too. Three things bound them, on top of the per-IP limits above.

**Bot check.** After the email delivery gate, `hooks.before` looks the path up in `BOT_CHECKED_AUTH_PATHS`, which maps `/sign-up/email`, `/request-password-reset` and `/send-verification-email` to the Turnstile actions `sign-up`, `password-reset` and `verification-resend`. `passesBotCheck` reads the token from the `x-turnstile-token` header (`TURNSTILE_TOKEN_HEADER`), refuses a missing, empty or overlong one with `turnstileTokenSchema`, and refuses a call that reached the hook without a request. Otherwise it asks `passesTurnstile` whether siteverify confirms the token for that action on the hostname of the request URL. A refusal is `403` with `BOT_CHECK_FAILED`, before an account, a reset token or an email exists, and it reads the same for every address. `SignUpWithPasswordForm`, `ForgotPasswordForm` and `UnverifiedEmailNotice` each run `useTurnstileToken` with their action, keep its container above their button and send the token in `fetchOptions.headers`; a widget that fails and a refused token both show "We could not finish the check that keeps bots out. Please try again." `/change-email` needs a session and is not checked. See [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile).

**Emails per address.** `sendVerificationEmail` and `sendResetPassword` first ask `admitPublicEmail` from `src/integrations/resend/resend.public-email-limits.server.ts`, with the kind `verification` or `password-reset`. One address gets at most three emails of each kind an hour. Past that, the hook returns without sending and logs `[Email] Skipped a <kind> email to <address>: the address reached its hourly limit for this email`, and the endpoint answers exactly as it does after a send: sign-up and the reset request keep their generic answers, and the resend answers `200`. A refusal there would be given only for an address with an account, or with an unconfirmed one, and would reveal it.

**Emails per day.** The same call counts every email visitors can make the shop send, these two kinds and the newsletter's, against 50 a day for the whole shop. Past that, the email is skipped with the same answer, logged with `console.error` and recorded as `email.failed` with the detail `Public <kind> email — the shop reached its daily limit of 50 emails that visitors can request`, so the audit log shows that customers are missing emails. A sign-up still creates the account, and its owner can ask for a new link once the day has passed. The order, password-changed, account-deleted and change-email confirmation emails never go through `admitPublicEmail`. The verification email Better Auth sends to a new address once a change of address is confirmed does, because it is also `sendVerificationEmail`. See [Resend: Emails visitors can request](/docs/integrations/resend#emails-visitors-can-request).

`auth.server.test.ts` covers the hook's three paths, the token checks and the paths it leaves alone. `auth.bot-check.integration.test.ts` sends forged and missing tokens through the real handler, and `auth.email-delivery.integration.test.ts` shows a reset request and a resend past the hourly limit answering like any other, a sign-up on a used-up day still creating the account, and an order email still going out on that day.

## Roles and permissions

`auth.access.ts` builds the access-control model with Better Auth's `createAccessControl`:

```ts
export const ROLES = { ADMIN: "admin", CUSTOMER: "customer" } as const

export const RESOURCES = { ORDER: "order", PRODUCT: "product", SETTINGS: "settings", USER: "user" } as const

export const ACTIONS = {
  CREATE: "create",
  DELETE: "delete",
  MANAGE: "manage",
  PUBLISH: "publish",
  READ: "read",
  REFUND: "refund",
  UPDATE: "update",
} as const

export const PERMISSIONS_STATEMENTS = {
  ...defaultStatements,
  [RESOURCES.ORDER]: [ACTIONS.READ, ACTIONS.UPDATE, ACTIONS.REFUND],
  [RESOURCES.PRODUCT]: [ACTIONS.CREATE, ACTIONS.READ, ACTIONS.UPDATE, ACTIONS.DELETE, ACTIONS.PUBLISH],
  [RESOURCES.SETTINGS]: [ACTIONS.MANAGE],
} as const
```

`ROLES_CONFIG.admin` receives all of those plus `adminAc.statements` (Better Auth's own `user` and `session` management statements). `ROLES_CONFIG.customer` receives empty arrays for every resource — a customer holds no administrative permission at all. `DEFAULT_ROLE` is `customer` and `ADMIN_PANEL_ROLES` is `["admin"]`.

Three predicates are exported and used everywhere:

```ts
export const hasAdminAccess = (role: string | null | undefined): role is Role =>
  typeof role === "string" && (ADMIN_PANEL_ROLES as readonly string[]).includes(role)

export const needsTwoFactorSetup = ({ role, twoFactorEnabled }: Readonly<TwoFactorAccessUser>): boolean =>
  hasAdminAccess(role) && twoFactorEnabled !== true

export const hasPermission = ({ permission, role }: { permission: Permission; role: string | null | undefined }): boolean =>
  isKnownRole(role) && ROLES_CONFIG[role].authorize(permission).success
```

## Server-function middleware

`auth.middleware.ts` exports the three middlewares every server function composes from.

`withRequest` puts the request headers into context and funnels every thrown error through one translator:

```ts
export const withRequest = createMiddleware({ type: "function" }).server(({ next }) =>
  next({ context: { requestHeaders: getRequest().headers } }).catch(handleRequestError),
)
```

`handleRequestError` first rethrows a TanStack `notFound()` unchanged (`isNotFound`), so a route answers 404 instead of a 500. It then rebuilds an `AppError` from its code, and keeps its message only when that message is a reason code in upper snake case, such as `WISHLIST_FULL` or `HAS_CHILDREN`, so the browser can explain the failure. Any free-text message is replaced by the code. It maps a Better Auth `APIError` to `AppError(AUTH_API_ERROR, authErrorKey(error))`, a `ZodError` to `AppError(VALIDATION)` and everything else to `AppError(INTERNAL_ERROR)` after logging it. The client never sees a raw stack trace or a vendor error string.

`authorized(permission?)` builds on `withRequest`, loads the session and either rejects or puts it into context:

```ts
export const authorized = (permission?: Permission) =>
  createMiddleware({ type: "function" })
    .middleware([withRequest])
    .server(async ({ next }) => {
      const session = await getRequestSession()
      if (session === null) {
        throw new AppError(ERROR_CODES.UNAUTHORIZED)
      }

      if (permission !== undefined && (!hasPermission({ permission, role: session.user.role }) || needsTwoFactorSetup(session.user))) {
        throw new AppError(ERROR_CODES.FORBIDDEN)
      }

      return next({ context: { auth: session } })
    })
```

Called without an argument it only requires a signed-in user; called as `authorized({ product: ["create"] })` it also requires that permission, and two-factor authentication on the admin who holds it. A use case therefore declares its own authorization in its signature:

```ts
export const createCompleteProduct = createServerFn({ method: "POST" }).middleware([authorized({ product: ["create"] })])
```

A permission that depends on the row is checked in the handler with `hasPermission` and the session `authorized` put on `context.auth`. `cancelOrder` is the one case: it asks the middleware for `order: ["update"]`, and once it has read the order and found a payment to refund it also requires `order: ["refund"]`, throwing `AppError(FORBIDDEN)` before it calls Stripe or changes anything.

`withRateLimit(kind, { max, window })` also builds on `withRequest` and applies the application's own limiter, keyed by `kind` plus the client address:

```ts
export const RATE_LIMITS = {
  BROWSING: { max: 120, window: RATE_LIMIT_WINDOW_SECONDS },
  CHECKOUT: { max: 10, window: RATE_LIMIT_WINDOW_SECONDS },
  SENSITIVE: { max: 3, window: RATE_LIMIT_WINDOW_SECONDS },
  TOKEN: { max: 5, window: RATE_LIMIT_WINDOW_SECONDS },
} as const
```

The window is 60 seconds. `withinRateLimit` in `src/lib/rate-limit.ts` implements it as a single conditional upsert into the `rate_limit` table with `onConflictDoUpdate` and a `setWhere`, so the counter and the window roll over in one statement. If the table is unreachable, the helper returns `false` — the limiter fails closed.

### This is enforced by a test

`src/integrations/better-auth/__test__/use-case-authorization.test.ts` walks every file under `src/modules/**/use-cases/`, and for each one that contains `createServerFn` asserts that it also contains `authorized(` — unless it is on an explicit allowlist of 22 deliberately public use cases (`get-product.ts`, `search-storefront.ts`, `check-cart-availability.ts`, `get-checkout-session-status.ts` and so on). It also asserts that no use case falls back to an `assertAdmin` role check inside its handler, and that every entry on the allowlist still exists. Adding a protected use case without middleware fails the test suite.

## Route guards

`auth.routes.ts` holds the _navigation_ guards. They decide what to render, never whether an operation is allowed; protected server functions authorize themselves through `authorized()`. Each layout route passes its guard as `beforeLoad` directly: `/account` has `beforeLoad: requireCustomer`, `/admin` has `beforeLoad: requireAdmin` and `/auth` has `beforeLoad: redirectIfSignedIn`.

| Export                      | Behaviour                                                                                                             |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `requireSignedIn(route)`    | Resolves to `{ user }`, or redirects to `/auth/sign-in`                                                               |
| `requireAdminRole(route)`   | Resolves to `{ user }` if `hasAdminAccess`, otherwise redirects to `/account/overview`; guards `/admin/security` only |
| `requireAdmin(route)`       | `requireAdminRole`, then redirects an admin for whom `needsTwoFactorSetup` holds to `/admin/security`                 |
| `requireCustomer(route)`    | Resolves to `{ user }` unless they are an admin, who is redirected to `/admin`                                        |
| `redirectIfSignedIn(route)` | Used on the auth pages; sends a signed-in visitor to `?redirect` or to their home                                     |
| `postAuthRouteFor(user)`    | `/admin` for an admin, `/account/overview` for a customer                                                             |
| `authEntryRouteFor(user)`   | `/auth/sign-in` when there is no user, otherwise `postAuthRouteFor`                                                   |

`route` is the `beforeLoad` argument, `{ context, location, preload }`. The `{ user }` a guard resolves to becomes route context, so a page reads the `SessionUser` with `Route.useRouteContext().user`.

The guards read the session through `context.queryClient.query(getCurrentSessionQuery)`:

```ts
const loadRouteSession = ({ context: { queryClient }, preload }: AuthRouteContext, { recheck }: { readonly recheck: boolean }) =>
  queryClient.query(recheck && !preload ? { ...getCurrentSessionQuery, staleTime: 0 } : getCurrentSessionQuery)
```

`requireSignedIn`, `requireAdminRole`, `requireAdmin` and `requireCustomer` pass `recheck: true`, so a real navigation into `/account` or `/admin` re-checks with `staleTime: 0`. A link preload, and `redirectIfSignedIn` on `/auth` with `recheck: false`, reuse a cached session younger than 60 seconds. The session a guard loads stays in the TanStack Query cache, so the components that read it see the same value, and on a server render it is dehydrated into the page, so guarded pages render signed-in on the server. The guards only read the session. A change of user is handled in one place, `clearCacheOnUserChange` in `auth.session.ts`: whenever the cached session switches to a different user, whoever fetched it, it removes every other cached query except the translation message catalogues. It is described in [TanStack Query](/docs/integrations/tanstack-query).

### Sign-in redirects

An anonymous visitor to `/account` or `/admin` is redirected to `/auth/sign-in?redirect=<path>`. `requireSignedIn` passes `route.location.publicHref`, the localized public path such as `/en-US/account/orders/order-1`. It is only kept when it is a string matching `SAME_SITE_PATH_PATTERN`:

```ts
const SAME_SITE_PATH_PATTERN = /^\/(?![/\\])[!-[\]-~]*$/u
```

The pattern allows printable ASCII only (no spaces), a single leading slash and no backslash, so absolute URLs, protocol-relative `//`, backslashes, whitespace and control characters are dropped, and the visitor lands on `/auth/sign-in` without the parameter. `redirectIfSignedIn` checks the parameter the same way and sends a signed-in visitor to it with `redirect({ href })`, otherwise to `postAuthRouteFor(user)`. Because the value is the public path, a server-rendered redirect keeps the visitor's language, and on the client the router re-localizes it to the current language.

After a successful password sign-in or two-factor challenge, the form calls `usePostAuthRedirect` from `src/hooks/use-post-auth-redirect.ts`:

```ts
export const usePostAuthRedirect = (): (() => Promise<void>) => {
  const queryClient = useQueryClient()
  const router = useRouter()

  return useCallback(async () => {
    queryClient.removeQueries({ exact: true, queryKey: getCurrentSessionQuery.queryKey })
    router.clearCache()
    await router.invalidate()
  }, [queryClient, router])
}
```

It removes the cached session entry only, then clears the router's cached matches and invalidates the router. The `/auth` layout guard runs again, fetches the fresh session and redirects to `?redirect` when it is a safe same-site path, otherwise to `postAuthRouteFor(user)`. When the fresh session arrives, `clearCacheOnUserChange` forgets what was cached while signed out. The forms never choose a destination themselves.

Google sign-in ends the same way. `useOAuthSignIn` in `src/presentation/components/custom/pages/auth/hooks/use-oauth-sign-in.ts` passes the page the button was clicked on as `callbackURL`, read with `useLocation` as `location.publicHref`, for example `/en-US/auth/sign-in?redirect=...`. After the provider round trip the browser lands on that auth page, and `redirectIfSignedIn` sends the user on exactly as after a password sign-in.

Sign-out is a full page load that discards the cache: the account sidebar goes to `/`, the admin sidebar to `/auth/sign-in`.

## Reading the session

`auth.session.ts` avoids asking Better Auth for the same session twice in one request by memoizing on the `Request` object:

```ts
const requestSessions = new WeakMap<Request, ReturnType<typeof auth.api.getSession>>()

export const getRequestSession = createServerOnlyFn((request: Request = getRequest()) => {
  const cached = requestSessions.get(request)
  if (cached) {
    return cached
  }

  const session = auth.api.getSession({ headers: request.headers, query: { disableCookieCache: true } })
  requestSessions.set(request, session)

  return session
})
```

`disableCookieCache: true` means server-side authorization always reads the database rather than trusting a signed cookie cache. The cookie cache is also turned off in `auth.server.ts`, so Better Auth's own endpoints behind its session middleware — `/update-user`, the two-factor routes, `/get-session` — read the session row too: a browser signed out from another device is refused at once instead of being trusted for as long as its cached cookie lived. `getCurrentSession` is the server function wrapper, and it strips `session.token` before returning — the token never reaches the browser payload. `getCurrentSessionQuery` is the matching query options object and the only way routes and components read the session: the route guards load it, and components read it with `useQuery(getCurrentSessionQuery)`. It is described in [TanStack Query](/docs/integrations/tanstack-query).

## The client

`auth.client.ts` mirrors the server plugins and re-exports only what the UI needs:

```ts
export const authClient = createAuthClient({
  plugins: [adminClient({ ac, roles: ROLES_CONFIG }), inferAdditionalFields<typeof auth>(), multiSessionClient(), twoFactorClient()],
})

export const { signIn, signOut, signUp, resetPassword } = authClient
```

`inferAdditionalFields<typeof auth>()` is what gives the client the `timezone` field without a second declaration.

Better Auth's `useSession` hook is deliberately not exported: it would run during server rendering, which TanStack Start's import protection rejects for `*.client.*` files in the server build, and it would add a second session request. Components read the session with `useQuery(getCurrentSessionQuery)` instead.

## Validation and errors

`auth.constraints.ts` holds the raw limits (`EMAIL_MAX_LENGTH` 64, `NAME_MAX_LENGTH` 32, `PASSWORD_MIN_LENGTH` 8, `PASSWORD_MAX_LENGTH` 1024, and the uppercase and special-character patterns) plus `AUTH_VALIDATION_PARAMS`, which feeds the numbers into the translated messages.

`auth.zod.ts` builds the form schemas from them: `signInWithPasswordSchema`, `signUpWithPasswordSchema`, `forgotPasswordSchema` and `resetPasswordSchema`. Every `message` is a _translation key_, not English prose — `"passwordMinLength"`, `"passwordsMustMatch"`, `"invalidEmail"` — which the form layer resolves against `messages/{locale}/pages.auth.*.json`. Sign-in uses the permissive `signInPasswordSchema` (non-empty) while sign-up and reset use `strictPasswordSchema`, so an existing weak password can still be used to log in.

`auth.errors.ts` maps Better Auth's error codes onto the same kind of message keys through `AUTH_ERRORS`, and `authErrorKey(error)` parses either `{ code }` or `{ body: { code } }` and falls back to `unknownError`.

## The HTTP endpoint

`src/routes/api/auth.$.ts` is a handler-only route that does not call `auth.handler` directly but wraps it:

```ts
export const Route = createFileRoute("/api/auth/$")({
  server: {
    handlers: {
      GET: ({ request }) => handleAuthRequestWithAudit(request),
      POST: ({ request }) => handleAuthRequestWithAudit(request),
    },
  },
})
```

`handleAuthRequestWithAudit` in `src/modules/audit-log/audit-log.auth.server.ts` inspects the path before delegating: for `POST /sign-in/email` it clones the request to read the e-mail, and records a failed-login audit entry if the response is not OK; for `POST /sign-out` it captures the session first and records a logout entry if the response is OK. Successful sign-ins are audited by the `signInAudit` plugin instead (see "Sign-in audit" above).

## Tables

`user`, `session`, `account`, `verification`, `two_factor` and `rate_limit`. Each is defined in its own module (`src/modules/user/user.schema.ts` and so on) and re-exported from `drizzle.schemas.ts`. `user` carries the application's additions beyond Better Auth's own columns: `role` (enumerated `admin` / `customer`), `phone`, `timezone`, `stripe_customer_id`, `metadata`, and the ban and two-factor flags. `session.token` is a 16 KiB unique text column and `session.user_id` cascades on delete.
