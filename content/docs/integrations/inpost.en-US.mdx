title: "InPost"
description: "Parcel-locker lookup for the checkout delivery step, and ShipX shipments, labels and tracking for the admin."
---

Polish customers expect to choose an InPost _paczkomat_, and the shop sends its parcels with InPost. The `src/integrations/inpost/` adapter covers both: a read-only lookup of pickup points by city, cached in TanStack Query, feeding a map-and-list picker in the checkout delivery step, a lookup of one point by name that the server uses to confirm the chosen locker when the payment session is opened or replaced, and a small client for InPost's ShipX API that the admin order page uses to book a shipment, download its label and read back its status.

## Two APIs

| Part         | Files                                                      | API                                                                                                                                  | Credentials                                  |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| Point lookup | `inpost.api.ts`, `inpost.queries.ts`                       | `https://api-pl-points.easypack24.net/v1/points`, called from the browser                                                            | None, the endpoint is public                 |
| Shipments    | `inpost.shipx.server.ts`, the use cases in `modules/order` | ShipX: `https://api-shipx-pl.easypack24.net` in production, InPost's sandbox `https://sandbox-api-shipx-pl.easypack24.net` elsewhere | `INPOST_API_TOKEN`, `INPOST_ORGANIZATION_ID` |

The order stores the locker the customer picked, as `checkout.locker_id` and `order.locker_id`, the locker's address as InPost gave it, as `checkout.locker_point` and `order.locker_point`, whether InPost could confirm it when the payment session was opened, as `checkout.locker_unconfirmed` and `order.locker_unconfirmed`, and once a shipment is booked, its ShipX id and last reported status in `order.inpost_shipment_id` and `order.inpost_shipment_status`, with the tracking number and link in `order.tracking_number` and `order.tracking_url`.

## The lookup

`inpost.api.ts` is 46 lines and calls one public endpoint in two ways. The picker searches it by city:

```ts
const url = `${INPOST_API_BASE}?city=${encodeURIComponent(capitalizeCity(trimmed))}&per_page=1000`
const response = await fetch(url)
if (!response.ok) {
  throw new Error(`InPost API error: ${String(response.status)}`)
}
```

`INPOST_API_BASE` is `https://api-pl-points.easypack24.net/v1/points`, built from `INPOST_POINTS_API_ORIGIN` in `inpost.constants.ts`, which the Content-Security-Policy's `connect-src` also imports for the browser's search. Three details matter:

- **`capitalizeCity`** lowercases the input and then upper-cases the first letter of every word, including after a hyphen, with a Unicode-aware regex — `"jelenia-góra"` becomes `"Jelenia-Góra"`. The endpoint is case-sensitive about city names, so without this the search silently returns nothing.
- **Fewer than three characters returns an empty array** without a request (`MIN_CITY_LENGTH = 3`).
- **A response that fails schema validation returns an empty array**, not an error. Only a non-OK HTTP status throws. This means a change in the upstream payload shape degrades to "no lockers found" rather than a broken checkout — which is the right trade-off, but it also means such a break is silent. If the picker shows nothing for a city you know has lockers, check the parse result first.

The server looks one point up by name with `fetchPointByName`:

```ts
const response = await fetch(`${INPOST_API_BASE}/${encodeURIComponent(name)}`, { signal: AbortSignal.timeout(POINT_LOOKUP_TIMEOUT_MS) })
if (response.status === HTTP_STATUS.NOT_FOUND) {
  return undefined
}
```

- **A 404 returns `undefined`**: InPost has no point with that name.
- **Any other non-OK status throws**, and so does a reply that fails `inpostPointSchema.parse`, a network failure, or `POINT_LOOKUP_TIMEOUT_MS` (three seconds) passing without an answer. Unlike the city search, a malformed reply is not read as "nothing found", because the caller would then refuse a real locker; it means InPost could not answer.

## The schemas

`inpost.zod.ts` keeps InPost's own `snake_case` field names rather than renaming them, so the shapes can be compared against the upstream response directly:

```ts
export const inpostPointSchema = z.object({
  address_details: inpostAddressDetailsSchema,
  location: inpostLocationSchema,
  location_description: z
    .string()
    .nullable()
    .optional()
    .transform((val) => val ?? ""),
  location_type: z.string().optional(),
  name: z.string(),
  opening_hours: z.string().optional(),
  payment_available: z.boolean().optional(),
  status: z.string().optional(),
})
```

`address_details` requires `city`, `post_code`, `province` and `street`, and allows `building_number` to be `null` and `flat_number` to be absent. `location` requires `latitude` and `longitude` as numbers — those are what place the marker. Everything the UI can live without is optional, and `location_description` is normalized from `null | undefined` to `""` so the component never has to branch.

`inpostApiResponseSchema` wraps `{ count, items }`, and `fetchPointsByCity` returns `parsed.data.items`.

## Caching

`inpost.queries.ts` is the only place a query is defined:

```ts
export const inpostPointsByCityQueryOptions = (city: string) =>
  queryOptions({
    enabled: city.trim().length >= MIN_CITY_LENGTH,
    gcTime: TWO_DAYS_IN_MS,
    queryFn: () => fetchPointsByCity(city),
    queryKey: [...INPOST_QUERY_KEYS.BY_CITY, city.trim().toLowerCase()],
    staleTime: ONE_DAY_IN_MS,
  })
```

`INPOST_QUERY_KEYS.BY_CITY` is `["inpost-points", "city"]` from `inpost.constants.ts`. A day of staleness and two days of garbage-collection time are deliberate: the locker network barely moves, and the customer may open and close the picker several times while filling the form. The key is lower-cased and trimmed so `"Kraków"`, `"kraków "` and `"KRAKÓW"` share one cache entry even though the request itself sends the capitalized form.

Note that `MIN_CITY_LENGTH` is declared twice — exported from `inpost.queries.ts` and declared privately in `inpost.api.ts`. Both are `3`; keep them in step if you change one.

## The picker

The UI lives under `src/presentation/components/custom/checkout/components/_steps/delivery/locker/`:

| File                                                      | Role                                                                              |
| --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `delivery-locker.tsx`                                     | The form field. Binds `lockerId` with `useController` and shows the chosen locker |
| `inpost/inpost-selector.tsx`                              | The dialog: a MapLibre map beside the sidebar list                                |
| `inpost/inpost-provider.tsx`                              | Owns the city input, debounces it and runs the query                              |
| `inpost/inpost-sidebar.tsx` and `inpost-sidebar-item.tsx` | The scrollable result list                                                        |
| `inpost/inpost-marker.tsx`                                | A `Marker` from `react-map-gl/maplibre` per point                                 |
| `inpost/inpost-popup.tsx`                                 | The hover popup                                                                   |
| `inpost/inpost-map-updater.tsx`                           | Moves the viewport when the result set changes                                    |
| `inpost/inpost-point-details.tsx`                         | Renders one point's address and opening hours                                     |

`InpostProvider` is the only consumer of the query. It debounces the typed city by 400 ms into a separate `searchQuery` state before the query sees it, and exposes `{ cityInput, hoveredPointId, isLoading, points, setCityInput, setHoveredPointId }` through context:

```ts
const { data: points, isLoading } = useQuery(inpostPointsByCityQueryOptions(searchQuery))
```

The map is `react-map-gl/maplibre` over `maplibre-gl`, with a free CARTO Voyager basemap at `https://basemaps.cartocdn.com/gl/voyager-gl-style/style.json`, attribution disabled, and `maxBounds` clamped to a Poland-sized box. Clicking the map background clears `lockerId`; clicking a marker or a sidebar row sets it. `point.name` — InPost's locker code, such as `KRA010` — is both the React key and the stored value, which is why the selected-locker panel simply prints `field.value`.

## How it reaches the order

`delivery_method` rows carry a `type` from `DELIVERY_METHOD` in `src/modules/delivery-method/delivery-method.constants.ts`:

```ts
export const DELIVERY_METHOD = { COURIER: "courier", IN_STORE: "in_store", LOCKER: "locker" } as const
```

`checkout.zod.ts` makes `lockerId` and `lockerCity` optional in general but required when the chosen method is a locker:

```ts
if (data.deliveryMethodType === "locker" && (typeof data.lockerId !== "string" || data.lockerId.trim().length === 0)) {
  // issue at path ["lockerId"] with message "validation.lockerIdRequired"
}
```

That check reads the `deliveryMethodType` the browser keeps, so it only guides the form. When a payment session is opened or replaced, `resolveDelivery` in `stripe.actions.server.ts` reads the method's `type` from the database instead: a `locker` method needs a `lockerId` that, trimmed, matches `INPOST_POINT_NAME_PATTERN` from `inpost.constants.ts` (3 to 32 letters, digits, `_` or `-`, starting with a letter or digit), or the session is refused with `LOCKER_REQUIRED`, and any other method drops the `lockerId`. A well-formed id then goes to `fetchPointByName`. When InPost answers that the point does not exist, the session is refused with `LOCKER_NOT_FOUND`, and the payment step sends the shopper back to the delivery step to choose another locker. When InPost cannot answer, the checkout goes ahead rather than turning every locker order away while InPost is down: the id is accepted, the failure is logged as "InPost could not confirm parcel locker …", and the checkout is saved with `locker_unconfirmed` set. Fulfilment copies the flag onto the order, and the admin order page shows a "Locker not confirmed" tag and a note on the shipping card asking the admin to check the locker before sending the parcel. See [Checkout and payments](/docs/features/checkout#server-side).

From there `lockerId` is persisted on the `checkout` row and copied onto the order at fulfilment. When InPost confirms the point, `serializeInpostLockerPoint` in `inpost.utils.ts` also keeps the address InPost gave for it, the street, building number, postal code, city and the directions in `location_description`, as a JSON string in `checkout.locker_point` (`20261015400000_locker_point.sql`), and fulfilment copies it to `order.locker_point`. A locker accepted unconfirmed, and an order placed before the column, has none. `parseInpostLockerPoint` reads it back through `inpostLockerPointSchema` and treats anything it cannot read as missing, and `resolveOrderLocker` in `order.detail.utils.ts` gives a locker order its destination: the code with that address.

The admin order page, the InPost card, the printed order summary, the confirmation and shipped e-mails, the shop's new-order e-mail, the checkout confirmation, the order in the shopper's account and the orders export all show the locker as the place the parcel goes. The shopper's name and phone appear only as the recipient InPost texts the pickup code to, never as a delivery address. Where the order kept no locker address, they show the code alone, and the admin page says to look it up in InPost's parcel manager. See [Resend](/docs/integrations/resend) and [Checkout and payments](/docs/features/checkout).

## Shipments through ShipX

### Which orders InPost carries

Shipments, labels and the InPost tracking link apply only to an order whose delivery method's carrier is InPost. `isInpostDelivery` in `order.admin-actions.utils.ts` requires the courier's `internal_code` to be `inpost` (`INPOST_COURIER_CODE` in `src/modules/courier/courier.constants.ts`) and the method's type to be `courier` or `locker`. The owner can add methods with other carriers in Settings (see [Shipping and delivery](/docs/features/shipping-and-delivery#managing-delivery-methods)), so the delivery type alone does not decide it. An order with another carrier gets no InPost card unless it already holds a shipment, and its tracking number links only to the link the admin saves with it. A parcel locker method always uses InPost, because Settings refuses any other carrier for it.

### Credentials

`INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID` are Worker secrets, declared under `secrets.required` in every `wrangler.jsonc` environment like the others. `isInpostShipxConfigured()` in `inpost.shipx.server.ts` is true only when both hold a value. Without them the order page offers no shipment action and explains that automatic InPost shipping is not connected: the admin creates the parcel in InPost Manager and pastes its tracking number when marking the order shipped, and for a method whose carrier is InPost the customer's email, the account's order page and the admin's order page link that number to InPost's tracking page through `resolveOrderTrackingUrl` (`order.display.utils.ts`). The webhook refuses every event; nothing else in the shop needs them. `scripts/prepare-deploy-secrets.ts` lets both be blank (`SECRETS_THAT_MAY_BE_BLANK`), so a deploy without InPost credentials still goes out. A blank value is uploaded as an empty secret, because Wrangler requires every declared secret to exist.

`APP_ENV` picks the API. `production` calls `https://api-shipx-pl.easypack24.net`; every other environment calls the sandbox at `https://sandbox-api-shipx-pl.easypack24.net`, so a preview or a local run never books a real parcel. The sandbox has its own InPost Manager at `https://sandbox-manager.paczkomaty.pl`, with its own token and organisation id, and its account needs its details and a virtual top-up before it can create shipments. In both, the token and the organisation id are in the API section of the account settings (My Account, API).

### Creating a shipment

The InPost shipment card on `/admin/orders/$orderId` appears for a locker or courier order whose carrier is InPost, and for any order that already holds a shipment. It offers **Create shipment** while the order is open (`pending` or `processing`), not yet shipped or delivered, and holds no live shipment: none at all, or one InPost reports as `canceled` (`canCreateAdminOrderInpostShipment` in `order.admin-actions.utils.ts`). The dialog asks for the parcel size, A, B or C (`INPOST_PARCEL_TEMPLATES`, with the largest dimensions in `INPOST_PARCEL_DIMENSIONS_MM`), and for a courier parcel its weight in kilograms, up to 25.

`createInpostShipment` (`src/modules/order/use-cases/create-inpost-shipment.ts`, guarded by `order: ["update"]`) checks that state again on the server, takes the receiver from the order's shipping address snapshot, or the checkout's address for an order placed before snapshots, and the address the order's e-mails go to (see [Orders: Where an order's e-mails go](/docs/features/orders#where-an-orders-e-mails-go)), and calls `postShipxShipment`, which posts to `/v1/organizations/{INPOST_ORGANIZATION_ID}/shipments`:

| Field               | Locker order                         | Courier order                                                                          |
| ------------------- | ------------------------------------ | -------------------------------------------------------------------------------------- |
| `service`           | `inpost_locker_standard`             | `inpost_courier_standard`                                                              |
| `receiver`          | first and last name, email and phone | the same, plus `address` with `line1`, `line2`, `city`, `post_code` and `country_code` |
| `parcels`           | `{ template }` for the chosen size   | `{ dimensions, weight }` from the chosen size and the weight                           |
| `custom_attributes` | `{ target_point: order.locker_id }`  | none                                                                                   |
| `reference`         | the order number                     | the order number                                                                       |

The phone is sent as its national number, read with `libphonenumber-js`. The request names no sender, so ShipX uses the organisation's own details, and no `sending_method`, which ShipX documents as required only for its Allegro services. It adds no insurance and no cash on delivery.

The shipment's id and status are written to the order only while it still holds no live shipment (`inpost_shipment_id IS NULL` or `inpost_shipment_status = 'canceled'`) and has not shipped, and a unique index on `inpost_shipment_id` keeps one shipment to one order. The booking also replaces the order's tracking number and link: with the new shipment's when ShipX assigns one straight away, and otherwise with none, so nothing a cancelled shipment left behind outlives it. Until the order ships, only its shipment writes those columns. When two admins book at once, or the order is marked shipped while ShipX books, the booking sees `ORDER_INVALID_STATE` and its extra ShipX shipment is logged by id to be cancelled in InPost Manager. The order's activity records `order.shipment_created` with the ShipX id.

To replace a shipment, because the parcel needs another size or ShipX never confirmed it (for example for lack of funds), cancel it in InPost Manager. Once its status reads Cancelled, through the webhook or **Refresh status**, the card offers **Create shipment** again below it while the order is open and not shipped, and the new shipment takes its place on the order.

### Status and tracking

ShipX confirms a new shipment shortly after it is created and assigns the tracking number then. **Refresh status** calls `refreshInpostShipment` (`order: ["update"]`), and `syncOrderInpostShipment` in `src/modules/order/order.shipment.server.ts` reads `/v1/shipments/{id}` and writes its status, and once ShipX has one the tracking number with its link `https://inpost.pl/sledzenie-przesylek?number=…`, onto the order that holds the shipment. The number and link are filled in only while the order has neither, so a number the admin typed when marking the order shipped is never written over, and a `canceled` shipment takes its own number and link off the order instead of writing them. The card names the common statuses, such as `created`, `confirmed`, `ready_to_pickup` and `delivered`, in both languages and shows any other ShipX status as InPost writes it. A status never moves the order itself: the admin still marks it shipped and delivered.

**Mark shipped** keeps the tracking number and link the shipment stored when its fields are left blank, so the shipped email links to InPost's tracking page. A number typed into the dialog replaces the stored one, and later refreshes and webhooks leave it alone. When a refresh or a webhook brings the first number of an order already marked shipped, `announceOrderShipment` sends the customer a tracking number email once, in the background; see [Transactional email](/docs/features/email#order-progress-emails-once-each).

On an order already marked shipped, **Save tracking number** sets or edits the number by hand: `setOrderTrackingNumber` (`src/modules/order/use-cases/set-order-tracking-number.ts`, `order: ["update"]`) replaces the stored number and link, clearing the link when none is given, records `order.tracking_updated` and awaits `announceOrderShipment`, so the customer gets the tracking number email for a number they were not sent yet, and the admin is told whether it went out. Without a stored link, `resolveOrderTrackingUrl` links an InPost order's number to InPost's tracking page.

### Label

**Download label** calls `getInpostShipmentLabel` (`order: ["read"]`), which fetches `/v1/shipments/{id}/label` in InPost's default PDF layout and returns it base64-encoded; the browser saves it as `<order number>-inpost.pdf`. ShipX has a label only once it has confirmed the shipment, and until then the admin is told to refresh the status first.

### Webhook

`src/routes/api/webhooks.inpost.ts` serves `/api/webhooks/inpost`, the address registered in InPost Manager as `https://<host>/api/webhooks/inpost`. ShipX does not sign its webhooks and the address carries no secret, so the route never trusts the payload. Every `POST` first counts against its sending address with `withinRateLimit`, keyed by `clientAddress`, and an address past `INPOST_WEBHOOK_RATE_LIMIT` (120) calls in the one-minute `RATE_LIMIT_WINDOW_SECONDS.REQUEST` window is answered 429 before the route reads the body, looks up an order or calls ShipX; InPost sends from a few addresses, and a small shop's real traffic stays far below that. The route then acts only when the JSON names this shop's `organization_id` and a `payload.shipment_id`, finds the order holding that shipment, and calls `syncOrderInpostShipment`, which reads the shipment back from ShipX with the shop's token. A forged call can at most make the shop read again a shipment it already has. An event for a shipment no order holds, such as one booked in InPost Manager, is acknowledged and ignored, and a failed read answers 500 so InPost sends it again. After an update the route calls `scheduleAdminOrdersInvalidation`, so open admin order pages show the new status, and hands `announceOrderShipment` to `scheduleBackgroundWork` with the origin of the request's URL, so a tracking number the customer of a shipped order was not sent goes out once. It answers `GET` with 200, which InPost Manager uses to check the address.

### Errors

`requestShipx` turns ShipX's answers into reasons the admin sees as a toast: `INPOST_NOT_CONFIGURED` without credentials, `INPOST_CREDENTIALS_REJECTED` for a 401 or 403, `INPOST_REQUEST_REFUSED` for any other 4xx, `INPOST_UNAVAILABLE` for a 5xx, no answer within 15 seconds or an answer it cannot read, and `INPOST_WEIGHT_REQUIRED` for a courier parcel without a weight. Every refusal is logged with ShipX's response body, which names the field InPost objected to.

## Tests

`src/integrations/inpost/__test__/` covers both halves. `inpost.api.test.ts` covers the request URL, capitalization of multi-part and hyphenated city names, the throw on a non-OK status, and the empty-array fallback for both a wrong response shape and a single malformed point; for `fetchPointByName` it covers the point URL, the three-second timeout signal, `undefined` on a 404 and the throw on any other error status or a reply that is not a point. `inpost.queries.test.ts` covers the trimmed lower-cased key, the namespace prefix and the one-day / two-day cache times. `inpost.zod.test.ts` covers a full point, a point stripped to its required fields, rejection when coordinates, city or name are missing, and the ShipX shipment and webhook shapes. `inpost.shipx.server.test.ts` runs the ShipX client against the responses in `__test__/fixtures/shipx.ts`: the sandbox and production URLs, the locker and courier bodies, the phone number, and each refusal. The use cases, the shared sync, the webhook route and the order card have their own suites. `inpost-shipment.integration.test.ts` books, refreshes and ships against a migrated SQLite database: a number typed when shipping survives the old shipment's later reports, a cancelled shipment's number leaves the order and a new booking takes its place, and a booking that finishes after the order shipped is refused. The browser suite books, refreshes, prints and ships a parcel against the ShipX emulator in the test Worker.

The browser tests never call InPost. `e2e/fixtures/inpost.ts` answers the point search with the lockers in `e2e/data/inpost.ts` whose city matches, and a checkout spec searches Warszawa in the picker, chooses a locker from the list and pays; see [Testing](/docs/tooling/testing#end-to-end-tests). The test Worker answers the server's own point lookups with `emulateInpostPoints` (`src/platform/testing/mocks/inpost-points.ts`): the two lockers in `e2e/data/inpost.ts` are listed, `WAW503` gets a 503 as if InPost were down, and any other name a 404.
