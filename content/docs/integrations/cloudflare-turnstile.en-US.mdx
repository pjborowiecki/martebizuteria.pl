Some requests cost the shop something whoever sends them. A guest checkout holds stock for up to 32 minutes, and sign-up, the password-reset request, the verification resend and the newsletter sign-up each send an email to whatever address they name, and a withdrawal by order number records a statement against any order whose number and address the visitor knows and emails an acknowledgement. `src/integrations/cloudflare-turnstile/` puts a Cloudflare Turnstile check in front of all six:

| Request                    | Action                | Where the token travels                                               | Checked by                                                                                                 |
| -------------------------- | --------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Creating a checkout        | `checkout`            | `turnstileToken` in the input of `createCheckoutSessionFn`            | `admitNewCheckout` in `handleCreateCheckoutSession`, before it counts open checkouts or reserves anything  |
| Sign-up                    | `sign-up`             | The `x-turnstile-token` header of `/api/auth/sign-up/email`           | Better Auth's `hooks.before` (`guardAuthRequest` in `auth.hooks.server.ts`), before the account is created |
| Password-reset request     | `password-reset`      | The `x-turnstile-token` header of `/api/auth/request-password-reset`  | The same hook, before a reset token exists                                                                 |
| Verification resend        | `verification-resend` | The `x-turnstile-token` header of `/api/auth/send-verification-email` | The same hook                                                                                              |
| Newsletter sign-up         | `newsletter`          | `turnstileToken` in the input of `subscribeToNewsletter`              | `subscribeToNewsletter`, before it reads or writes a subscriber                                            |
| Withdrawal by order number | `withdrawal`          | `turnstileToken` in the input of `withdrawFromGuestOrder`             | `withdrawFromGuestOrder`, before it looks for the order                                                    |

Updating an open checkout needs no token, but each update gives the checkout a replacement session with a fresh 32-minute hold, so `handleUpdateCheckoutSession` edits a checkout only while it is younger than `CHECKOUT_SESSION_LIFETIME_SECONDS`. An older one is refused with `SESSION_CLOSED` after its session is expired and its stock returned, and the browser opens a new checkout, which needs a new token. One passed check therefore holds stock for at most about an hour. See [Checkout: Limits on holding stock](/docs/features/checkout#limits-on-holding-stock). The emails behind the other five are also limited per address and per day, and a solved check does not lift those limits; see [Resend: Emails visitors can request](/docs/integrations/resend#emails-visitors-can-request) and [Better Auth: Bot check and email limits](/docs/integrations/better-auth#bot-check-and-email-limits).

## In the browser

`issueTurnstileToken` loads `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` the first time a token is asked for and keeps the loaded API for the rest of the visit; a script that fails to load is removed, so the next request tries again. It then renders a fresh widget into the container it is given, with `action`, `sitekey` set to `VITE_TURNSTILE_SITE_KEY`, `appearance: "interaction-only"` and `size: "flexible"`, and resolves with the token the widget's `callback` receives, taking the widget down again. Turnstile decides per visitor whether to ask anything: most shoppers pass without seeing the widget, and it appears only when Turnstile wants the visitor to act. The `error-callback` takes the widget down, logs `Turnstile could not check this visitor: <code>` to the console and rejects with `BOT_CHECK_FAILED`, and a build without a site key rejects the same way without loading anything. Siteverify accepts a token once, so every request renders a new widget.

Components ask for a token through `useTurnstileToken(action)` in `src/hooks/use-turnstile-token.ts`. It returns a `containerRef` for the element the widget renders into and a `requestToken()` that stays the same across renders. `requestToken` rejects with `BOT_CHECK_FAILED` while that element is not on the page and otherwise calls `issueTurnstileToken` with it. The call is wrapped in `createClientOnlyFn`, because server-rendered forms such as the landing page's newsletter section import the hook, and TanStack Start keeps `*.client.*` files out of the server build. Each form keeps its container, with `empty:hidden`, beside its button and asks for a token only when the visitor submits:

| Component                              | Action                | How the token is sent                                                                                                                                            |
| -------------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PaymentStep`                          | `checkout`            | Through `ensureCheckoutSession` and `resetCheckoutSession`, only when they create a checkout; see [Checkout: Payment step](/docs/features/checkout#payment-step) |
| `SignUpWithPasswordForm`               | `sign-up`             | `useSignUpWithPassword(requestToken)` puts it in `fetchOptions.headers`                                                                                          |
| `ForgotPasswordForm`                   | `password-reset`      | In `fetchOptions.headers` of `requestPasswordReset`                                                                                                              |
| `UnverifiedEmailNotice`                | `verification-resend` | `useResendVerification(requestToken)` puts it in `fetchOptions.headers`                                                                                          |
| `NewsletterSection`, `NewsletterField` | `newsletter`          | `subscribeToNewsletterMutation` takes `requestTurnstileToken` and calls it inside the mutation                                                                   |
| `GuestWithdrawalForm`                  | `withdrawal`          | `withdrawFromGuestOrderMutation` takes `requestTurnstileToken` and calls it inside the mutation                                                                  |

A widget that fails and a token the server refuses read the same to the visitor. The checkout shows "We could not finish the check that keeps bots out of checkout. Please try again." and offers Try again. The auth forms show "We could not finish the check that keeps bots out. Please try again." (`pages.auth.errors.botCheckFailed`, which `authErrorKey` also finds for an `Error` whose message is `BOT_CHECK_FAILED`). The newsletter forms show their usual retryable error, and the withdrawal form shows the auth forms' message in a toast.

The Content-Security-Policy lists `challenges.cloudflare.com` in `script-src`, `frame-src` and `connect-src`, so the script, which is inserted without a nonce, and its challenge frame load (see [Security model](/docs/architecture/security-model#response-headers)).

## On the server

`passesTurnstile` posts the token, `TURNSTILE_SECRET_KEY` and the visitor's IP as `remoteip` (from `resolveRequestIp`, left out when the request carries none) to siteverify as a form, with a ten-second timeout. A token passes only when the verdict says `success` and, with the secret of the shop's own widget, names the action the caller expects and the hostname the request came in on, so a token solved on another site or for another action, such as a newsletter token replayed at sign-up, is refused. Cloudflare's testing secrets answer with a placeholder action and hostname, so with a testing secret only `success` counts. A siteverify that cannot be reached, answers with an error status or answers something that is not a verdict is logged as `Turnstile siteverify could not check a token` and counts as a failed check: the request fails closed rather than letting a script through during an outage.

`verifyTurnstileToken` turns a failed check into `FORBIDDEN` with `BOT_CHECK_FAILED` for the server functions; the checkout, the newsletter and the guest withdrawal take the hostname from `resolveRequestOrigin(getRequest())`. Better Auth's hook needs an `APIError` instead, so it calls `passesTurnstile` itself with the hostname of the request URL and answers `403` with `{ code: "BOT_CHECK_FAILED" }`. It refuses a missing, empty or overlong header without asking siteverify, and it refuses a call that reaches the hook with no request, as a server-side `auth.api` call would.

## Keys

| Environment                         | `VITE_TURNSTILE_SITE_KEY`         | `TURNSTILE_SECRET_KEY`                |
| ----------------------------------- | --------------------------------- | ------------------------------------- |
| `production`                        | The site key of the shop's widget | The secret key of the same widget     |
| `preview`, `development` and `test` | `1x00000000000000000000AA`        | `1x0000000000000000000000000000000AA` |

`VITE_TURNSTILE_SITE_KEY` is a browser variable, inlined into the client bundle. `TURNSTILE_SECRET_KEY` is a Worker secret, declared under `secrets.required` in every environment of `wrangler.jsonc`. The testing pair is Cloudflare's always-passing one: its site key issues the dummy token `XXXX.DUMMY.TOKEN.XXXX`, and its secret accepts only that token. `.env.example` and `.env.test` carry it, so development, preview and the test build need no widget.

`deploy:preview` and `deploy:production` run `scripts/verify-turnstile-keys.ts <environment>` after the Stripe key check and before the build. `verifyTurnstileKeys` refuses a missing or blank key, a testing key paired with a widget's key, whose secret would refuse every token the site key issues, and, in production, Cloudflare's testing keys, which pass every visitor. `isTurnstileTestingKey` recognises those by their shape: `1x`, `2x` or `3x`, zeros, then two capital letters. The script prints the kind of keys, never a key, and calls no Cloudflare API, so it cannot tell whether the widget exists or lists the shop's hostname.

The production widget is created by hand in the Cloudflare dashboard, under Turnstile, in managed mode, for the hosts production serves: `martebizuteria.pl` and `martebizuteria.pjborowiecki.workers.dev`, the two `appHostsForMode("production")` accepts. Its site key goes into the `production` GitHub environment as the variable `VITE_TURNSTILE_SITE_KEY` and its secret key as the secret `TURNSTILE_SECRET_KEY`, and the pair into `.env.production` for a deploy from a laptop.

## Tests

`src/integrations/cloudflare-turnstile/__test__/` holds four files. `turnstile.client.component.test.ts` covers loading the script once, the render options, the token, the widget's error, a script that fails to load and the retry after it, and a build without a site key. `turnstile.server.test.ts` covers the form sent to siteverify, a token for another action or host, a rejected token, an unreachable or failing siteverify, the testing secret and the answers of `passesTurnstile`. `turnstile.zod.test.ts` covers the bounds of a token. `turnstile.keys.test.ts` covers every environment's rules and that no message prints a key.

`src/hooks/__test__/use-turnstile-token.component.test.tsx` covers the hook, and each form's own test checks its container, its action and where its token goes. `auth.bot-check.integration.test.ts` runs sign-up, the reset request and the resend through Better Auth's handler with the real `passesTurnstile` against the siteverify double: no token or a forged one creates no account and sends nothing, alike for known and unknown addresses, and the dummy token goes through.

The test Worker answers siteverify from `src/platform/testing/mocks/providers.ts`, and the end-to-end browser gets a widget double from `e2e/fixtures/turnstile.ts`, so no test reaches Cloudflare; see [Testing](/docs/tooling/testing). `openAuthBrowser` in `src/platform/testing/lib/auth-browser.ts` sends the dummy token with every request.
