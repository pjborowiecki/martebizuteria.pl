---
title: "Realtime invalidation"
description: "The Durable Object hub that pushes query-cache invalidations to connected browsers."
---

A write on the Worker cannot reach the query cache in someone else's browser. When an admin publishes a product, every open storefront should notice, and the admin's own product list should refresh in every tab they have open. This adapter is the mechanism: server code publishes a set of query-key prefixes to a Durable Object hub, the hub fans them out over WebSocket, and each client invalidates only the queries it actually subscribes to.

It is deliberately _not_ a data channel. Nothing but query keys crosses the wire — no rows, no payloads, no ids. A client that receives a notification refetches through the normal server functions, so authorization is enforced exactly as it always is.

## The two hubs

`realtime-invalidation.subscriptions.ts` names them and lists what each one carries:

```ts
export const REALTIME_INVALIDATION_HUB = { ADMIN: "admin", STOREFRONT: "storefront" } as const
```

| Hub          | Subscribed prefixes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin`      | `ADMIN_REALTIME_QUERY_PREFIXES` — the audit log page and stats, admin orders, the overview dashboard's `ADMIN_DASHBOARD_QUERY_KEYS.ALL`, admin customers, the admin team, the `ALL` and `STATS` keys of categories, collections, products and product attributes, the content page `ADMIN.ALL` and `ADMIN.BY_HANDLE` keys, the store setting `ADMIN.SALES`, `ADMIN.FREE_DELIVERY` and `ADMIN.SELLER_DETAILS` keys, the delivery method `ADMIN.ALL` key, the newsletter campaign `ADMIN.LIST` key, and the newsletter subscriber `ADMIN.PAGE` and `ADMIN.STATS` keys |
| `storefront` | `STOREFRONT_REALTIME_QUERY_PREFIXES` — product `ALL`, `BY_HANDLE`, `LANDING_NEW_ARRIVALS`, `RELATED_BY_CATEGORY`, `STOREFRONT_PAGE`, cart `AVAILABILITY`, category and collection `ALL` / `BY_HANDLE`, content page `BY_HANDLE`, store setting `SALES`, `FREE_DELIVERY` and `SELLER_DETAILS`, and delivery method `ALL`                                                                                                                                                                                                                                             |

The checkout connects to the storefront hub too, with its own list, `CHECKOUT_REALTIME_QUERY_PREFIXES`: the store setting `FREE_DELIVERY` and `SELLER_DETAILS` and the delivery method `ALL`, and nothing else, so an open checkout shows delivery changes and the current pickup address while a stock change elsewhere never re-runs its availability check. All three lists are `as const satisfies readonly QueryKey[]`, so a renamed key constant is a type error rather than a silently dead subscription. The split matters for privacy as well as noise: the storefront hub never carries an `["admin", …]` prefix, so a customer's browser learns nothing about admin activity.

## The protocol

`realtime-invalidation.protocol.ts` is a query key serialized as JSON, and the rule that turns a frame of topics into the keys a tab invalidates:

```ts
export const serializeQueryKeyPrefix = (queryKey: QueryKey): string => JSON.stringify(queryKey)

export const resolveInvalidatedQueryKeys = (subscriptions: readonly QueryKey[], topics: readonly string[]): QueryKey[] =>
  toMinimalQueryKeyPrefixes(
    topics
      .map((topic) => parseSerializedQueryKeyPrefix(topic))
      .filter((topic): topic is QueryKey => topic !== undefined)
      .flatMap((topic) => queryKeysInvalidatedByTopic(subscriptions, topic)),
  )
```

For each topic that overlaps a subscription, the tab invalidates the narrower of the two, compared with TanStack Query's `partialMatchKey`: the topic when it falls under the subscription, the subscription when the topic is broader. That lets a publisher name a broad prefix and a subscriber a narrow one, or the reverse, without either side knowing the other's exact shape, and it keeps a narrow topic narrow: `["admin", "products", "stats"]` refreshes the stats, not everything under the `["admin", "products"]` subscription. `toMinimalQueryKeyPrefixes` then drops duplicate keys and keys that another key in the frame already covers, so each query is invalidated at most once per frame.

The message on the wire is minimal:

```ts
export interface RealtimeInvalidationPayload {
  readonly topics: readonly string[]
  readonly type: typeof REALTIME_INVALIDATION_MESSAGE.INVALIDATE
}
```

`isRealtimeInvalidationPayload` validates it structurally on the client, and `parseSerializedQueryKeyPrefix` returns `undefined` rather than throwing on malformed JSON.

## Publishing

`realtime-invalidation.publish.server.ts` addresses a hub by name and calls the Durable Object method directly through the RPC binding:

```ts
const notifyHub = async (hubName: RealtimeInvalidationHubName, topicPrefixes: readonly string[], attempt: number): Promise<void> => {
  try {
    const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)
    await hub.notifyInvalidation(topicPrefixes)
  } catch (error) {
    if (attempt >= NOTIFY_ATTEMPTS) {
      throw error
    }

    await pause(NOTIFY_BACKOFF_MS * attempt)
    await notifyHub(hubName, topicPrefixes, attempt + 1)
  }
}
```

`getByName` means there are exactly two object instances in existence, one per hub name, which is what makes the fan-out possible at all. A failed call is tried again on a fresh stub, three attempts in all (`NOTIFY_ATTEMPTS`), 50 and then 100 ms apart, before the error reaches the caller.

`publishRealtimeInvalidation({ admin?, storefront? })` publishes to both in parallel, and `scheduleRealtimeInvalidation(input)` wraps it in `scheduleBackgroundWork` so the request does not wait:

```ts
export const scheduleRealtimeInvalidation = (input: PublishRealtimeInvalidationInput): void => {
  scheduleBackgroundWork(publishRealtimeInvalidation(input))
}
```

Server code almost never calls either of these directly. `realtime-invalidation.catalog.server.ts` provides the named intentions instead:

| Function                                           | Admin keys invalidated                     | Storefront keys invalidated                                                                                       |
| -------------------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `scheduleProductCatalogInvalidation()`             | product `ALL`, `STATS`                     | product `ALL`, `BY_HANDLE`, `LANDING_NEW_ARRIVALS`, `RELATED_BY_CATEGORY`, `STOREFRONT_PAGE`, cart `AVAILABILITY` |
| `scheduleCategoryCatalogInvalidation()`            | category `ALL`, `STATS`                    | category `ALL`, `BY_HANDLE`, product `STOREFRONT_PAGE`                                                            |
| `scheduleCollectionCatalogInvalidation()`          | collection `ALL`, `STATS`                  | collection `ALL`, `BY_HANDLE`, product `LANDING_NEW_ARRIVALS`, `STOREFRONT_PAGE`                                  |
| `scheduleContentPageInvalidation()`                | content-page `ALL`, `BY_HANDLE`            | content-page `BY_HANDLE`                                                                                          |
| `scheduleProductAttributeCatalogInvalidation()`    | product-attribute `ALL`, `STATS`           | product `BY_HANDLE`                                                                                               |
| `scheduleAdminCustomersInvalidation()`             | user `CUSTOMERS`, `CUSTOMERS_PAGE`, `TEAM` | —                                                                                                                 |
| `scheduleAdminNewsletterSubscribersInvalidation()` | newsletter `ADMIN.PAGE`, `ADMIN.STATS`     | —                                                                                                                 |
| `scheduleAdminAuditLogInvalidation()`              | audit-log `ADMIN.PAGE`, `ADMIN.STATS`      | —                                                                                                                 |
| `scheduleAdminOrdersInvalidation()`                | order `ORDERS`, admin dashboard `ALL`      | —                                                                                                                 |
| `scheduleDeliveryMethodsInvalidation()`            | delivery-method `ADMIN.ALL`                | delivery-method `ALL`                                                                                             |
| `scheduleFreeDeliveryInvalidation()`               | store-setting `ADMIN.FREE_DELIVERY`        | store-setting `FREE_DELIVERY`                                                                                     |
| `scheduleSalesStatusInvalidation()`                | store-setting `ADMIN.SALES`                | store-setting `SALES`                                                                                             |
| `scheduleSellerDetailsInvalidation()`              | store-setting `ADMIN.SELLER_DETAILS`       | store-setting `SELLER_DETAILS`                                                                                    |

Note that `scheduleCollectionCatalogInvalidation` also invalidates the storefront's new-arrivals key, because the landing section is driven by the `nowosci` collection, and the catalogue page key, because a collection's `status` and `handle` decide which products its storefront grid lists; and that `scheduleProductCatalogInvalidation` invalidates the cart's availability key, because a stock change can make a cart line unpurchasable. `scheduleAdminOrdersInvalidation` publishes `ORDER_CHANGE_ADMIN_QUERY_KEYS`, the admin order keys together with the overview dashboard's, because every order event changes the overview's figures, chart or recent orders.

### Who calls them

- **Every catalogue mutation.** All the `create-`, `update-`, `delete-` and `reorder-` use cases under `src/modules/product/`, `product-category/`, `product-collection/` and `product-attribute/`, and `set-all-product-attributes.ts` under `attribute-on-product/`.
- **Checkout.** `stripe.actions.server.ts` calls `scheduleProductCatalogInvalidation()` when a session is created or updated, because reserving stock changes availability, and again when a failed checkout gives back the stock it reserved; `reserveInventoryForItems` calls it after rolling back a partial reservation.
- **Fulfilment.** `announcePlacedOrder` in `stripe.fulfillment.server.ts` calls `scheduleAdminOrdersInvalidation()` and `scheduleProductCatalogInvalidation()` once a paid session has become an order, whether the Stripe webhook or the checkout's return page placed it.
- **Webhooks.** `stripe.webhooks.ts` calls `scheduleAdminOrdersInvalidation()` on a refund, a failed or cancelled refund and a dispute, and `scheduleProductCatalogInvalidation()` on release; `webhooks.inpost.ts` calls `scheduleAdminOrdersInvalidation()` after it reads a shipment's new status back from ShipX. A refund does not refresh the catalogue, because it never returns stock; `cancelOrder` and `returnOrderToStock` do when the admin puts an order's items back.
- **Stepping an order back.** `stepBackOrder` calls `scheduleAdminOrdersInvalidation()` right after it moves the order, so every open admin tab shows the earlier step without waiting for the audit entry.
- **Withdrawals.** `record-order-withdrawal.server.ts` calls `scheduleAdminOrdersInvalidation()` once a customer's statement of withdrawal is recorded, so an open admin order page shows the withdrawal card.
- **Identity.** The `user` create, update and delete hooks in `auth.hooks.server.ts` call `scheduleAdminCustomersInvalidation()`, and so do `grantAdminAccess` and `revokeAdminAccess`, which change the role without Better Auth.
- **Content pages.** `update-content-page.ts` calls `scheduleContentPageInvalidation()` after a save, and `update-seller-details.ts` when a save of the seller's details dated a page.
- **Sales switch.** `set-sales-paused.ts` calls `scheduleSalesStatusInvalidation()` when an admin pauses or resumes sales, so the paused notice appears or goes in every open storefront tab and other admin tabs move their switch.
- **Delivery settings.** `create-delivery-method.ts`, `update-delivery-method.ts`, `archive-delivery-method.ts` and `reorder-delivery-methods.ts` call `scheduleDeliveryMethodsInvalidation()`, and `set-free-delivery-threshold.ts` calls `scheduleFreeDeliveryInvalidation()` when the threshold changes, so other admin tabs show the change and an open checkout fetches the delivery methods or the threshold again.
- **Seller details.** `update-seller-details.ts` calls `scheduleSellerDetailsInvalidation()` after a save that changed something, so other admin tabs show the new details and the footer, the product pages and the checkout's pickup step follow in open storefront and checkout tabs.
- **Newsletter.** `send-newsletter-campaign.ts` refreshes the admin campaign list when a newsletter starts, and `process-newsletter-queue.server.ts` after every batch it sends and when it stops a campaign, so the Marketing page shows each newsletter's progress. `scheduleAdminNewsletterSubscribersInvalidation()` is called on every change to a subscriber row: by `subscribe-to-newsletter.ts` after it saves a sign-up, `confirm-newsletter-subscription.ts` after a confirmation, `unsubscribeSubscriber` in `unsubscribe-subscriber.server.ts`, which the unsubscribe link, the one-click route, the account preferences and the admin all use, `erase-newsletter-subscriber.ts`, `followAccountAddressChange` when a change of an account's address moves its subscription, and `eraseAccountData`, so open admin tabs update the subscriber list and its counts as shoppers sign up, confirm and leave.
- **Erasure.** `erase-newsletter-subscriber.ts` and `eraseAccountData` in `erase-account-data.server.ts` also call `scheduleAdminAuditLogInvalidation()`, because they delete the person's audit entries along with the subscriber or the account.
- **Audit.** `delete-audit-logs.ts` calls `scheduleAdminAuditLogInvalidation()` after an admin deletes entries. `process-audit-log-queue.server.ts`, which adds `ORDER_CHANGE_ADMIN_QUERY_KEYS` for a batch that carries an order timeline action, calls `publishRealtimeInvalidation` directly and awaits it, because a queue consumer has no response to hand the publish to.

## The Durable Object

`src/durable-objects/realtime-invalidation-hub.ts` uses hibernatable WebSockets, so an idle hub costs nothing:

```ts
export class RealtimeInvalidationHub extends DurableObject<Env> {
  fetch(request: Request): Response {
    if (request.headers.get("Upgrade") !== "websocket") {
      return new Response("Expected WebSocket", { status: HTTP_STATUS.UPGRADE_REQUIRED })
    }

    const hubName = this.ctx.id.name
    if (hubName === undefined) {
      return new Response("Hub name required", { status: HTTP_STATUS.BAD_REQUEST })
    }

    const { client, server } = splitWebSocketPair(new WebSocketPair())
    this.ctx.acceptWebSocket(server, [hubName])

    return new Response(undefined, { status: HTTP_STATUS.SWITCHING_PROTOCOLS, webSocket: client })
  }
  // …
}
```

`acceptWebSocket(server, [hubName])` tags each socket with its hub name, and `notifyInvalidation` retrieves only the sockets with that tag via `ctx.getWebSockets(hubName)`, falling back to all sockets if the name is somehow unrecognized. Sends are wrapped in a bare `try`/`catch` so one dead socket cannot stop the loop. `webSocketError` closes with 1011. On the storefront hub, `notifyInvalidation` first writes a new catalogue version for the [storefront read cache](/docs/architecture/caching-and-ssr#the-storefront-read-cache) to `ctx.storage.kv`, and `storefrontCacheVersion()` returns the current one, so every frame the storefront receives comes after the version it invalidates.

The class is registered in two places. `src/server.ts` re-exports it:

```ts
export { RealtimeInvalidationHub } from "~/src/durable-objects/realtime-invalidation-hub"
```

and `wrangler.jsonc` declares the binding in every environment plus a SQLite-backed migration:

```jsonc
"migrations": [{ "tag": "v1", "new_sqlite_classes": ["RealtimeInvalidationHub"] }],
"durable_objects": {
  "bindings": [{ "name": "REALTIME_INVALIDATION_HUB", "class_name": "RealtimeInvalidationHub" }]
}
```

## The upgrade endpoint

`realtime-invalidation.ws.server.ts` is the gatekeeper:

```ts
export const handleRealtimeInvalidationWebSocket = async (request, env, hubName) => {
  if (request.headers.get("Upgrade") !== "websocket") {
    return new Response("Expected WebSocket", { status: HTTP_STATUS.UPGRADE_REQUIRED })
  }

  if (hubName === REALTIME_INVALIDATION_HUB.ADMIN) {
    const unauthorized = await assertAdminWebSocket(request)
    if (unauthorized !== undefined) {
      return unauthorized
    }
  }

  const hub = env.REALTIME_INVALIDATION_HUB.getByName(hubName)

  return hub.fetch(request)
}
```

The admin hub requires a session whose user passes `hasAdminAccess(role)` and for whom `needsTwoFactorSetup(user)` is false, which in the `production` and `test` builds means two-factor authentication is on, and returns 401 otherwise. The storefront hub is open, which is correct — it only ever broadcasts public catalogue keys.

These are routed in `src/server.ts` before the TanStack Start handler, because a WebSocket upgrade has to be answered by the Durable Object rather than by a route component:

```ts
if (pathname === ROUTES.API_REALTIME.ADMIN_WS) {
  return handleRealtimeInvalidationWebSocket(request, env, REALTIME_INVALIDATION_HUB.ADMIN)
}
```

The two paths are `/api/realtime/admin/ws` and `/api/realtime/storefront/ws`, both from `ROUTES.API_REALTIME`.

## The client

`src/hooks/use-realtime-query-sync.ts` holds the connection. It is used in three layouts:

```tsx
// src/routes/_storefront.tsx
useRealtimeQuerySync({ hub: REALTIME_INVALIDATION_HUB.STOREFRONT, subscriptions: STOREFRONT_REALTIME_QUERY_PREFIXES })

// src/routes/checkout.tsx
useRealtimeQuerySync({ hub: REALTIME_INVALIDATION_HUB.STOREFRONT, subscriptions: CHECKOUT_REALTIME_QUERY_PREFIXES })

// src/routes/admin.tsx
useRealtimeQuerySync({ hub: REALTIME_INVALIDATION_HUB.ADMIN, subscriptions: ADMIN_REALTIME_QUERY_PREFIXES })
```

The hook builds `wss://` or `ws://` from `globalThis.location.protocol`, connects, and on each message parses the payload, resolves its topics against the subscription list with `resolveInvalidatedQueryKeys`, taking the narrower key of each overlapping topic and subscription, each key once, and applies `invalidateQueryPrefix` to each key: queries on screen refetch, queries that are only cached are dropped, so the next visit fetches them fresh, and an infinite list such as the storefront catalogue keeps its loaded pages and refetches them on the next visit. Nothing is posted to the viewer's other tabs: every storefront and admin tab, and every checkout tab for the three keys it follows, receives the same frame on its own socket, and tabs outside those layouts hold no socket and see the change on their next fetch. See [TanStack Query](/docs/integrations/tanstack-query).

Reconnection is exponential with a ceiling:

```ts
const BASE_RECONNECT_DELAY_MS = 1000

const MAX_RECONNECT_DELAY_MS = 30_000

const RECONNECT_BACKOFF_FACTOR = 2
```

A successful `open` resets the attempt counter, the cleanup function sets a `disposed` flag so a pending timer cannot resurrect a torn-down connection, and a malformed message is swallowed. The effect depends on `[hub, queryClient, subscriptions]`, and the two subscription arrays are module-level constants, so the socket is opened once per layout mount rather than on every render.

## Adding a new invalidation

1. Make sure the query key is a stable `as const` tuple in the owning feature's `{feature}.constants.ts`.
2. Add the prefix to `ADMIN_REALTIME_QUERY_PREFIXES` or `STOREFRONT_REALTIME_QUERY_PREFIXES` in `realtime-invalidation.subscriptions.ts`, so clients listen for it.
3. Add a named `schedule…Invalidation()` function in `realtime-invalidation.catalog.server.ts`, or extend the existing one whose intention matches.
4. Call it from the use case, after the write has succeeded and before the return.
5. Never call `publishRealtimeInvalidation` from a use case and `await` it — use the `schedule…` form, so the customer's request is not waiting on a fan-out.

A prefix that is published but not subscribed is silently ignored by every client; a prefix that is subscribed but never published simply never fires. Neither fails loudly, so check both lists when something does not refresh.
