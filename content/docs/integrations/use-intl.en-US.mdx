The shop is Polish first and English second. `pl-PL` is the default locale and is served without a prefix, so `/products` is Polish and `/en-US/products` is English. `src/integrations/use-intl/` holds seven files. Five define the locales, rewrite the URLs, load the message namespaces and keep the choice in a cookie; `i18n.display.ts` and `i18n.display-preferences.ts` decide the time zone and the format locale each user sees dates and numbers in.

## Configuration

`i18n.config.ts` is the whole of the locale definition:

```ts
const COOKIE_NAME = "marte_locale"

const SUPPORTED_LOCALES = ["pl-PL", "en-US"] as const

export type SupportedLocale = (typeof SUPPORTED_LOCALES)[number]

const DEFAULT_LOCALE: SupportedLocale = "pl-PL"

const DEFAULT_TIMEZONE = "Europe/Warsaw"

export const I18N = { COOKIE_NAME, DEFAULT_LOCALE, DEFAULT_TIMEZONE, SUPPORTED_LOCALES } as const
```

`SupportedLocale` is derived from the tuple, so adding a locale here is what makes the type system demand the rest: a Stripe locale in `stripe.client.ts`, a `react-day-picker` locale in `react-day-picker.locale.ts`, a JSON file per namespace under `messages/<locale>/`, a second MDX file for every page in `content/docs`, and a title, description and body in that locale for every `content_page` row, entered in the editor at `/admin/content`.

`DEFAULT_TIMEZONE` is the store's time zone. The test render provider in `src/platform/testing/lib/render.tsx` and the withdrawal e-mail template, `order-withdrawal.tsx`, which states when the statement was submitted, use it. The shop's own business dates use the same zone through `DEFAULT_TIMEZONE_CODE` in `src/modules/_core/constants/timezone.ts`: the year in an order number and the withdrawal deadlines in `polish-deadline.ts`. The time zone and format locale a page is shown in come from the user's preferences (see [Display preferences](#display-preferences)); the lists users choose from are `TIMEZONES` in `src/modules/_core/constants/timezone.ts` and `FORMAT_LOCALES` in `src/integrations/use-intl/i18n.display.ts`.

## URL shape

`i18n.paths.ts` implements the prefix rules. The ignored-path pattern is the important starting point:

```ts
const IGNORED_PATHS_REGEX = /^\/(?:api|rpc|_serverFn|assets|forms)(?:\/|$)/u
```

Those prefixes never get a locale segment, because they are machine endpoints, or, for `/forms`, PDF forms that are the same in every language.

| Export                                   | Behaviour                                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `isSupportedLocale(locale)`              | Type predicate against the supported set                                                         |
| `shouldIgnorePath(pathname)`             | The pattern above                                                                                |
| `extractLocaleFromPath(pathname)`        | The prefix locale, or `undefined` — **including when the prefix is `pl-PL`**                     |
| `deLocalizePathname(pathname)`           | Strips any supported prefix, returning `/` when nothing is left                                  |
| `localizePathname({ locale, pathname })` | Adds the prefix, except for the default locale and except for ignored or protocol-relative paths |
| `canonicalizePathname(pathname)`         | Rewrites a language alias or a redundant default prefix into the canonical path                  |
| `localeLinks({ origin, pathname })`      | The `canonical` link plus one `alternate` per locale plus an `x-default`                         |

Two subtleties decide most of the behaviour:

- `extractLocaleFromPath` returns `undefined` for a `pl-PL` prefix, treating `/pl-PL/products` as "no locale in the URL". `canonicalizePathname` then rewrites it to `/products`, so the Polish prefix can never become a second, duplicate URL for the same page.
- `LANGUAGE_ALIASES` maps the bare language subtag to the full locale (`pl` → `pl-PL`, `en` → `en-US`), and `canonicalizePathname` uses it, so `/en/products` redirects to `/en-US/products`.

## The middleware

`i18n.middleware.ts` runs in `src/server.ts` before the Start handler. `resolveLocale(request)` returns at most one of a redirect and a cookie:

```ts
if ((request.method !== "GET" && request.method !== "HEAD") || !isDocumentRequest(request) || shouldIgnorePath(pathname)) {
  return {}
}

const canonical = canonicalizePathname(pathname)

if (canonical !== pathname) {
  url.pathname = canonical

  return { redirect: Response.redirect(url.href, HTTP_MOVED_PERMANENTLY) }
}
```

It only acts on `GET` and `HEAD` document requests. `isDocumentRequest` prefers the `sec-fetch-dest` header (`document`, `frame`, `iframe`) and falls back to matching `text/html` or `application/xhtml+xml` in `accept`, treating a missing `accept` as a document. A non-canonical path gets a **301**, which matters for SEO: `/pl-PL/products` and `/en/products` permanently collapse onto their canonical forms.

When the path is already canonical but the URL locale and the `marte_locale` cookie disagree, the middleware returns `{ setCookie }` and `src/server.ts` appends it to the response. The URL always wins over the cookie.

## Reading the current locale

`i18n.utils.ts` exposes the locale isomorphically, with `createIsomorphicFn` so the same call works in a loader and in a component:

```ts
export const getCurrentLocale = createIsomorphicFn()
  .server((): SupportedLocale => {
    const request = getRequest()
    const { pathname } = new URL(request.url)

    if (shouldIgnorePath(pathname)) {
      return parseLocaleCookie(request.headers.get("cookie")) ?? I18N.DEFAULT_LOCALE
    }

    return extractLocaleFromPath(pathname) ?? I18N.DEFAULT_LOCALE
  })
  .client(/* the same, from globalThis.location and document.cookie */)
```

The cookie is consulted only for ignored paths — which is exactly the case that matters, because a server function posts to `/_serverFn/...` and has no locale in its URL. This is why a server function such as `createCheckoutSessionFn` can call `getCurrentLocale()` and still get the customer's language into the Stripe session metadata. `getCurrentPathname`, `localizeUrl` and `deLocalizeUrl` are the URL equivalents; the last two are what `src/router.tsx` passes to the router's `rewrite` option.

## Messages

`messages/<locale>/<namespace>.json` — 61 namespaces per locale, identical file names in both. The namespace _is_ the file name, with dots for nesting: `pages.admin.catalog.products.json` becomes `pages.admin.catalog.products`.

`i18n.messages.ts` does four things.

**It finds the files at build time.** `import.meta.glob("../../../messages/*/*.json", { import: "default" })` produces a lazy loader per file, so a namespace is one code-split chunk. `loadNamespace` looks up the path and throws a precise error when it is missing:

```ts
const load = messageModules[modulePath({ locale, namespace })]

if (load === undefined) {
  throw new Error(`Missing translation namespace: messages/${locale}/${namespace}.json`)
}
```

**It defines the root namespaces** — the six every page needs, listed as an explicit glob so the set is checked against the filesystem rather than hand-maintained:

```ts
const rootMessagePaths = Object.keys(
  import.meta.glob([
    "../../../messages/*/common.json",
    "../../../messages/*/components.custom.json",
    "../../../messages/*/components.shadcn.json",
    "../../../messages/*/errors.json",
    "../../../messages/*/pages.auth.errors.json",
    "../../../messages/*/pages.auth.toast.json",
  ]),
)

export const ROOT_NAMESPACES = [...new Set(rootMessagePaths.map((path) => toNamespace(path)))]
```

**It turns flat namespaces into a nested tree.** `buildMessageTree` splits each namespace on `.`, wraps the messages in that path, and deep-merges the branches, so `pages.admin.json` and `pages.admin.catalog.json` coexist under one `pages.admin` object.

**It exposes the query options.** `messagesQueryOptions({ locale, namespace })` with `staleTime` and `gcTime` of `Infinity`, and `preloadNamespaces({ locale, namespaces, queryClient })` which resolves them all in parallel.

`getRouteNamespaces(matches)` is the glue: it takes the matched routes and returns `ROOT_NAMESPACES` plus every `staticData.namespaces` entry, de-duplicated.

## How a page gets its translations

1. A route declares what it needs: `staticData: { namespaces: ["pages.products"] }`.
2. `__root.tsx`'s `beforeLoad` calls `preloadNamespaces({ locale, namespaces: getRouteNamespaces(matches), queryClient })`, so everything is in the query cache before any component renders.
3. `TranslationsProvider` in `src/providers/translations-provider.tsx` reads the same namespaces with `useSuspenseQueries`, combines them with `buildMessageTree`, and renders `use-intl`'s provider:

```tsx
<IntlProvider locale={locale} messages={messages} timeZone={timeZone}>
  {children}
</IntlProvider>
```

`timeZone` is the user's saved time zone, or the one detected for the request, or `UTC`. The format locale goes to `DisplayPreferencesContext` inside the provider rather than into it, because the provider's `locale` also picks the plural forms of the messages. See [Display preferences](#display-preferences).

It also writes the locale back into the `marte_locale` cookie from an effect, so a direct visit to `/en-US/...` is remembered.

4. A component calls `useTranslations("pages.products")` and gets `t("title")`.

A route's own loader often also needs a message for its `head`, which it gets by awaiting the same query options — the cache means this is free:

```ts
const [messages] = await Promise.all([
  context.queryClient.query(messagesQueryOptions<typeof productsMessages>({ locale: context.locale, namespace: "pages.products" })),
  prefetchProductsCatalogPage(/* … */),
])
```

Note the `<typeof productsMessages>` type argument, taken from a type-only import of the English JSON. That is the project's convention for typed message access outside React context, and it is why a key present in English but missing in Polish is a type error.

## Display preferences

The page's language comes from the URL, but the time zone and the format locale, which decides how dates, times and numbers are written, belong to the user. `i18n.display.ts` holds the rules and `i18n.display-preferences.ts` the server function and query that bring them to the page. [Internationalization](/docs/features/internationalization) describes what the shopper and the admin see.

### Detection order

`detectDisplayPreferences({ acceptLanguage, cookieHeader, edgeTimeZone })` reads what the request reveals, and `toSavedDisplayPreferences(user)` what the signed-in user saved in `user.timezone` and `user.format_locale`. `resolveDisplayPreferences({ detected, saved })` lets each saved value win over its detected one on its own:

| Preference    | Used in this order                                                                                                                                                                                                                                                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Time zone     | The saved `user.timezone`; the `marte_time_zone` cookie (`TIME_ZONE_COOKIE_NAME`), where the browser reports its own zone; `edgeTimeZone`, the zone Cloudflare derives from the visitor's address (`request.cf?.timezone`, put into the request context by `src/server.ts`); `FALLBACK_TIME_ZONE`, `UTC` |
| Format locale | The saved `user.format_locale`; the first `Accept-Language` entry, in header order with `q` weights ignored, that `toFormatLocale` accepts; `FALLBACK_FORMAT_LOCALE`, `en-US`                                                                                                                            |

Every candidate is checked before it is used, a saved one included, so a value the runtime cannot format with is skipped. `isTimeZone` accepts at most 64 characters that `Intl.DateTimeFormat` takes as a `timeZone`. `toFormatLocale` canonicalizes at most 35 characters with `Intl.getCanonicalLocales` and keeps the tag only when `Intl.DateTimeFormat.supportedLocalesOf` supports it.

### The query and its cache

`getDisplayPreferences` is a `GET` server function that returns both halves, `{ detected, saved }`: it reads the headers with `getRequest()`, the session with `getRequestSession()`, which is memoized per request, and `edgeTimeZone` with `getGlobalStartContext()`. A visitor has nothing saved. `displayPreferencesQuery` caches the answer under `DISPLAY_PREFERENCES_QUERY_KEY`, `["i18n", "displayPreferences"]`, with `staleTime: Infinity` and no refetch on window focus or reconnect. `__root.tsx`'s `beforeLoad` awaits it in the same `Promise.all` as the namespaces, so the server render and the hydrated page format with the same values.

The entry changes in three ways:

- In the browser, `useBrowserTimeZone` in `TranslationsProvider` reads `Intl.DateTimeFormat().resolvedOptions().timeZone` after the first render. When it is a valid zone, it writes it to `marte_time_zone` if the cookie holds something else (a year, `Path=/`, `SameSite=Lax`, `Secure` over HTTPS), and when it differs from the detected zone it patches `detected.timeZone` in the cached entry with `setQueryData`. A user with no saved zone sees the browser's zone at once, and the next request detects it from the cookie.
- When the session switches to another user, `clearCacheOnUserChange` keeps the entry and invalidates it, so the new user's saved values replace it (see [TanStack Query](/docs/integrations/tanstack-query#display-preferences)).
- Saving a preference invalidates every cached query, described below.

### The context and the hooks

`TranslationsProvider` gives `IntlProvider` the resolved `timeZone` and renders `DisplayPreferencesContext` from `src/hooks/use-display-format.ts` inside it, with the resolved `{ formatLocale, timeZone }`. The hooks in the same file read it:

| Hook                      | Returns                                                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `useDisplayPreferences()` | `{ formatLocale, timeZone }`; outside the context, the page's locale and `IntlProvider`'s time zone, or `UTC` |
| `useFormatLocale()`       | The format locale, for code that formats by hand, such as `formatPrice(amount, currency, formatLocale)`       |
| `useDisplayTimeZone()`    | The time zone                                                                                                 |
| `useFormatter()`          | `createFormatter({ locale: formatLocale, timeZone })` from `use-intl`, memoized on both values                |

Application code formats through this `useFormatter`. `use-intl`'s own `useFormatter` would format in the page's language, because it reads `IntlProvider`'s `locale`.

### On the server

`resolveRequestDisplayPreferences()`, a `createServerOnlyFn` in `i18n.display-preferences.ts`, makes the same reads for the current request and returns the resolved `{ formatLocale, timeZone }`. Server functions call it when their answer depends on where a day begins or holds a date or label they format themselves: the admin orders, customers and products pages and their exports, the audit log list and its count for today, the dashboard snapshot and chart range, the customer detail, and the saved cards on the account's payment page, whose expiry it judges. Use-case tests mock `i18n.display-preferences.ts` with `src/platform/testing/mocks/display-preferences.ts`, whose `resolveRequestDisplayPreferences` answers `pl-PL` and `Europe/Warsaw`.

### Saving a preference

`updateDisplayPreference` in `src/modules/user/use-cases/update-display-preference.ts` is a `POST` server function behind `withRateLimit("update-display-preference", RATE_LIMITS.SENSITIVE)`, three calls a minute, and `authorized()`, so every signed-in user may change their own and only their own row. `userZodSchemas.displayPreferenceInput` accepts `{ preference: "formatLocale" | "timeZone", value }`, where `value` is `""` for Automatic, stored as `NULL`, or a value `toFormatLocale` returns unchanged or `isTimeZone` accepts. Better Auth declares both columns with `input: false`, so its own endpoints cannot write them.

`DisplayPreferenceField` in `src/presentation/components/custom/display-preferences/` is the picker. `useDisplayPreferenceOptions` lists Automatic first, labelled with the detected value, then the eighteen `FORMAT_LOCALES`, each with a sample date and number, or every zone in `TIMEZONES`, plus a saved value the list does not hold. `useSaveDisplayPreference` sends the choice and, on success, calls `queryClient.invalidateQueries()` with no filter, so every query whose result was dated or formatted with the old value is fetched again.

## Outside React

E-mails and webhooks render on the Worker without a provider, so they use `createTranslator({ locale, messages })` from `use-intl` directly. See [Resend](/docs/integrations/resend).

## Other locale-aware adapters

| Adapter                                                        | What it maps                                                             |
| -------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `src/integrations/stripe/stripe.client.ts`                     | `pl-PL` → `pl`, `en-US` → `en` for Stripe Elements                       |
| `src/integrations/react-day-picker/react-day-picker.locale.ts` | `pl-PL` → `pl`, `en-US` → `enUS` for the calendar                        |
| `src/integrations/fumadocs/fumadocs.i18n.ts`                   | Feeds `I18N.SUPPORTED_LOCALES` into Fumadocs with `hideLocale: "always"` |

The first two use `satisfies Record<SupportedLocale, …>` and an explicit `Record<SupportedLocale, …>`, so a new locale breaks the build until both mappings are filled in. `fumadocs.i18n.ts` spreads `I18N.SUPPORTED_LOCALES` into `languages`, so it takes a new locale without a change, and a page that has no MDX file in that locale falls back to `pl-PL` (`fallbackLanguage`).

## Translated content in the database

Catalogue text is not in the message files. `product.titles`, `product.subtitles`, `product.descriptions` and `product.tags` are JSON columns holding a locale map keyed by the BCP 47 tag, as are the equivalents on `product_category`, `product_collection` and `product_attribute`. The `20260925000000_locale_maps_bcp47.sql` migration is what moved those keys to full tags. The admin catalogue forms edit both locales side by side — `catalog-locale-picker.tsx` and `product-form-locale-layout.tsx` iterate `I18N.SUPPORTED_LOCALES` and show how many are filled. The three customer legal pages work the same way: each `content_page` row keeps `titles`, `descriptions` and Markdown `bodies` as locale maps, and `/admin/content/$handle` edits them one locale tab at a time. A delivery method keeps its name the same way, in `delivery_method.names`, which Settings → Delivery edits with a field per language.

## There is no locale switcher

Worth knowing before you go looking for it: the storefront has no language-switch control. Nothing in `src/presentation` calls `localizePathname` to build a switch, and the navigation and footer do not offer one. A visitor reaches English by URL, and the cookie then remembers it. The `hreflang` links emitted from `__root.tsx` are what tell search engines about the English version. If a switcher is wanted, `localizePathname` plus `getCurrentPathname` are the two functions to build it from.
