M'Arte przechowuje wszystko w Cloudflare D1 (SQLite) i sięga tam przez Drizzle ORM. Biorą w tym udział dwa narzędzia i robią różne rzeczy:

- **drizzle-kit** czyta schemat w TypeScripcie i _zapisuje_ pliki migracji SQL. W tym repozytorium nigdy ich nie nakłada.
- **Wrangler** _nakłada_ pliki migracji na bazę D1 i zapisuje je w tabeli `d1_migrations`, którą sam utrzymuje.

Rozdzielenie tych rzeczy ma znaczenie: `bun run db:generate` jest bezpieczny i działa offline, natomiast każdy skrypt `db:migrate:*` zmienia bazę, a wszystkie poza `db:migrate:local` i `db:migrate:test` — bazę zdalną.

## Gdzie leży schemat

Każdy moduł funkcjonalny posiada własną tabelę. Plik schematu leży w katalogu modułu i eksportuje swoje tabele wraz z ich relacjami; `order.schema.ts` zawiera też `order_number_sequence`:

```
src/modules/order/
  order.schema.ts        → export const order, orderNumberSequence, orderRelations
  order.types.ts
  order.zod.ts
  order.accessors.ts
  use-cases/
```

`src/integrations/drizzle-orm/drizzle.schemas.ts` re-eksportuje 42 z 43 tabel i wszystkie 32 obiekty relacji; jedenaście tabel, na przykład `audit_log`, `store_setting` i `user_email_history`, nie deklaruje relacji. To jedyny plik, który czyta drizzle-kit, i jedyna rzecz, która czyni nową tabelę widoczną dla generowania migracji:

```ts
export { order, orderNumberSequence, orderRelations } from "~/src/modules/order/order.schema"
```

Pomija tylko tabelę `storefrontSearch`. `storefront_search` to tabela wirtualna FTS5, którą tworzy ręcznie napisana migracja `20261002100000_storefront_search.sql` razem z wyzwalaczami, które ją wypełniają, a jej plik schematu daje jedynie akcesorom wyszukiwania typowane kolumny.

`src/integrations/drizzle-orm/drizzle.database.ts` buduje jedynego klienta uruchomieniowego:

```ts
import "@tanstack/react-start/server-only"

import { env } from "cloudflare:workers"

import { drizzle } from "drizzle-orm/d1"

import * as schema from "~/src/integrations/drizzle-orm/drizzle.schemas"

import { timeD1Statements } from "~/src/lib/server-timing"

const instrumentedBinding = (): D1Database => timeD1Statements(env.DB)

class DeferredD1Database implements D1Database {
  prepare = (query: string): D1PreparedStatement => instrumentedBinding().prepare(query)
  // batch, exec and withSession forward the same way; dump rejects
}

export const db = drizzle(new DeferredD1Database(), { schema })
```

Import `server-only` sprawia, że pakiet klienta, który sięgnąłby po `db`, wysypie się już na etapie kompilacji, a nie w czasie działania, a `scripts/verify-build.ts` sprawdza to samo założenie powtórnie, skanując skompilowane zasoby klienta w poszukiwaniu importów `cloudflare:workers` i `node:` oraz samego Drizzle ORM.

### Wspólne pomocniki kolumn

`src/integrations/drizzle-orm/drizzle.utils.ts` zawiera wspólne konwencje kolumn i pomocniki SQL:

| Eksport                              | Co robi                                                                                                                                                                                                                                                                                                         |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `timestamp(name)`                    | `integer(name, { mode: "timestamp_ms" })` — wszystkie czasy to milisekundy epoki                                                                                                                                                                                                                                |
| `timestampNow(name)`                 | To samo, z domyślną wartością `(unixepoch() * 1000)` w SQL i `new Date()` w JS, `notNull`                                                                                                                                                                                                                       |
| `timestamps()`                       | Rozwija `created_at` i `updated_at`; `updated_at` nosi `$onUpdateFn`                                                                                                                                                                                                                                            |
| `UUID_STRING_LENGTH`                 | `36`, długość używana dla kolumn identyfikatorów                                                                                                                                                                                                                                                                |
| `calendarPeriodKey(column, periods)` | Klucz ostatniego z `periods` (`{ key, start }`), który zaczyna się nie później niż `column`, przekazany jednym parametrem JSON, do grupowania po dniach lub miesiącach w danej strefie, takich jak wykres zamówień na pulpicie panelu i miesięczne wydatki klienta w strefie czasowej wyświetlania oglądającego |
| `inJsonList(column, values)`         | `column in (select value from json_each(...))`, z całą listą przekazaną jednym parametrem JSON, więc lista dowolnej długości zajmuje jeden ze 100 parametrów D1                                                                                                                                                 |
| `notInJsonList(column, values)`      | To samo z `not in`                                                                                                                                                                                                                                                                                              |

Pliki stałych modułów i `product-attribute.zod.ts` importują z tego pliku `UUID_STRING_LENGTH`, a one trafiają do przeglądarki. Dlatego plik deklaruje tylko stałe i funkcje i przy wczytaniu niczego z Drizzle nie wywołuje, więc build klienta pomija `drizzle-orm`, zamiast wysyłać go razem ze stałą.

Nowa tabela kończy się na `...timestamps()` i używa `timestamp(...)` dla każdej innej kolumny daty. Robi tak 35 z 43 tabel; `audit_log`, `category_on_product`, `collection_on_product`, `order_number_sequence`, `price_history`, `rate_limit`, `storefront_search` i `user_email_history` nie mają `timestamps()`. 21 tabel generuje klucz główny przez `text("id").primaryKey().$defaultFn(() => crypto.randomUUID())`. Pozostałe klucze tekstowe nadaje kod, który zapisuje wiersz — Better Auth na przykład wydaje identyfikatory UUIDv7 przez `generateId` w `auth.server.ts` — a kilka tabel ma inny klucz: całkowitoliczbowe `id` w `price_history` i `user_email_history`, `period` w `order_number_sequence`, klucz złożony z produktu i kategorii albo kolekcji w `category_on_product` i `collection_on_product`, a `storefront_search` nie ma żadnego.

### Partie

D1 nie ma interaktywnych transakcji. `db.batch()` to jedyny prymityw atomowy, a `src/integrations/drizzle-orm/drizzle.batch.ts` go opakowuje:

```ts
export const runDrizzleBatch = async (statements: readonly DrizzleBatchStatement[]): Promise<void> => {
  if (statements.length === 0) {
    return
  }

  const [first, ...rest] = statements
  if (first === undefined) {
    return
  }
  await db.batch([first, ...rest])
}
```

Destrukturyzacja istnieje, bo `db.batch` wymaga niepustej krotki. `runDrizzleBatch` niczego nie zwraca, więc niesie zapisy typu „wszystko albo nic”, których wyników nikt nie potrzebuje, takie jak realizacja zamówienia, zwolnienie stanów magazynowych i zapisy edytorów katalogu. Kod, który czyta to, co zwraca partia, sam wywołuje `db.batch`: warunkowa rezerwacja stanu, tworzenie i zwalnianie checkoutu, anulowanie, przywracanie stanu i zwrot zamówienia oraz listy w panelu, które pobierają stronę wierszy i ich liczbę w jednym żądaniu.

Ten sam plik utrzymuje instrukcje poniżej limitu 100 parametrów D1 (`D1_MAX_BOUND_PARAMETERS`): `chunkByBoundParameters` dzieli wiersze na mieszczące się porcje, `insertRowChunks` dobiera ich wielkość do liczby kolumn tabeli przy wielowierszowych insertach, a `chunkRankUpdates` buduje wyrażenia `case` do zmian rang.

## Generowanie migracji

```sh
bun run db:generate
```

To uruchamia `vp exec drizzle-kit generate --config src/integrations/drizzle-orm/drizzle.config.ts`. Konfiguracja:

```ts
const accountId = process.env["CLOUDFLARE_ACCOUNT_ID"]
const databaseId = process.env["CLOUDFLARE_DATABASE_ID"]
const token = process.env["CLOUDFLARE_ACCESS_TOKEN"]

export default defineConfig({
  ...(accountId === undefined || databaseId === undefined || token === undefined
    ? {}
    : { dbCredentials: { accountId, databaseId, token } }),
  dialect: "sqlite",
  driver: "d1-http",
  migrations: { prefix: "timestamp", schema: "public", table: "__drizzle_migrations__" },
  out: "./src/integrations/drizzle-orm/migrations",
  schema: "./src/integrations/drizzle-orm/drizzle.schemas.ts",
  strict: true,
  verbose: true,
})
```

`db:generate` nie potrzebuje żadnych danych uwierzytelniających — porównuje schemat ze zrzutami w `src/integrations/drizzle-orm/migrations/meta/` i zapisuje nowy plik SQL z prefiksem czasowym oraz nowy zrzut, dodając wpis do `meta/_journal.json`. Ustawienie `migrations.table` wskazuje na `__drizzle_migrations__`, ale nic w tym repozytorium nie uruchamia `drizzle-kit migrate`, więc ta tabela nie istnieje w żadnej bazie M'Arte; tabelą, która jest faktycznie używana, jest `d1_migrations` Wranglera.

Wygenerowane nazwy plików wyglądają jak `20260612120000_product_variants_enhanced.sql`. Wiele migracji w drzewie ma nazwy nadane ręcznie (`20260604120000_catalog_indexes_and_integrity.sql`, `20260925000000_locale_maps_bcp47.sql`, `20260927120000_fix_silver_collection_handle.sql`), bo powstały ręcznie na potrzeby indeksów albo naprawy danych, czego różnica schematów nie wyrazi. Wrangler nakłada oba rodzaje identycznie — po prostu uruchamia pliki z katalogu w kolejności nazw.

> Księgowość drizzle-kit nie zgadza się z katalogiem. W chwili pisania `migrations/` zawiera 108 plików `.sql`, `meta/_journal.json` wymienia 52 wpisy, a `meta/` zawiera 37 zrzutów. Pięćdziesięciu pięciu plików brakuje w dzienniku, w tym wszystkich 49 po `20260930151544_collection_short_descriptions`. Oznacza to, że `db:generate` porównuje schemat z najnowszym _zrzutem_, a nie z faktyczną zawartością katalogu, i może wygenerować SQL dla zmiany, którą późniejsza ręczna migracja już wprowadziła. Czytaj każdą wygenerowaną migrację i usuwaj instrukcje opisujące pracę już wykonaną.

Wygenerowany SQL czytaj przed commitem także z drugiego powodu: SQLite nie umie usunąć ani zmienić kolumny w miejscu, więc drizzle-kit przepisuje całą tabelę. Na żywej bazie to właśnie ten krok najłatwiej prowadzi do utraty danych.

## Nakładanie migracji

```sh
bun run db:migrate:local        # lokalne D1 w .wrangler, środowisko development
bun run db:migrate:development  # zdalnie — baza preview
bun run db:migrate:preview      # zdalne preview
bun run db:migrate:production   # zdalna produkcja
bun run db:migrate:test         # lokalne testowe D1 w .wrangler/test
```

Każdy z nich to `vp exec wrangler d1 migrations apply DB --env <środowisko>` z `--local` albo `--remote`; `db:migrate:test` przekazuje też `--persist-to .wrangler/test`. `bun run db:reset:test` usuwa `.wrangler/test` i uruchamia `db:migrate:test` oraz `db:seed:test`, co daje zestawowi end-to-end świeżą bazę; zobacz [Testy](/docs/tooling/testing#dane). Wrangler czyta katalog z `wrangler.jsonc`, gdzie każde środowisko ustawia `"migrations_dir": "./src/integrations/drizzle-orm/migrations"`.

`bun run db:migrate` bez sufiksu jest aliasem `db:migrate:preview`, czyli działa **zdalnie**. Nie ma trybu próbnego; najpierw upewnij się, o które środowisko Ci chodzi.

Aby zobaczyć, co dana baza już nałożyła:

```sh
bun run db:migrations:development
bun run db:migrations:preview
bun run db:migrations:production
```

Uruchamiają one `wrangler d1 migrations list DB --env <środowisko> --remote`.

CI niczego nie migruje. `deploy:preview` i `deploy:production` same uruchamiają `db:migrate:preview` albo `db:migrate:production`, po kompilacji i tuż przed `wrangler deploy`, a nieudana migracja zatrzymuje wdrożenie. W tej chwili sklep obsługuje jeszcze poprzedni Worker, więc migracja musi zachować jego działanie; zobacz [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

### Która baza jest która

| Środowisko    | Nazwa bazy D1            | Uwagi                                                                                    |
| ------------- | ------------------------ | ---------------------------------------------------------------------------------------- |
| `development` | `martebizuteria-preview` | Ta sama baza co preview, z bindingami `"remote": true`                                   |
| `preview`     | `martebizuteria-preview` | Wspólna dla każdego wdrożenia preview                                                    |
| `production`  | `martebizuteria`         | Żywy sklep                                                                               |
| `test`        | `martebizuteria-test`    | Tylko lokalna (`"remote": false`), zapisywana w `.wrangler/test`, dla zestawu end-to-end |

`development` i `preview` wskazują tę samą bazę D1, tę samą przestrzeń KV i ten sam zasobnik R2, `martebizuteria-preview`; produkcja ma własne, a `test` ma lokalne pod nazwami `martebizuteria-test` z zastępczymi identyfikatorami. `bun run dev` zapisuje więc do bazy preview, a `bun run db:migrate:local` **nie** wpływa na to, co widzi serwer deweloperski — robi to `db:migrate:development`.

## Push, pull i Studio

Te komendy korzystają ze sterownika D1 HTTP drizzle-kita, więc wymagają `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` i `CLOUDFLARE_ACCESS_TOKEN` z odpowiedniego pliku środowiska. Dlatego to jedyne skrypty, które jawnie włączają wczytywanie zmiennych przez `bun --env-file=.env.<środowisko>` — `bunfig.toml` ustawia globalnie `env = false`.

| Skrypt                                           | Uruchamia                                 |
| ------------------------------------------------ | ----------------------------------------- |
| `db:push`, `db:push:development`                 | `drizzle-kit push` na bazie preview       |
| `db:push:preview`                                | `drizzle-kit push` na bazie preview       |
| `db:push:production`                             | `drizzle-kit push` na produkcji           |
| `db:pull`, `db:introspect:development`           | `drizzle-kit introspect` na bazie preview |
| `db:introspect:preview`                          | `drizzle-kit introspect` na bazie preview |
| `db:pull:production`, `db:introspect:production` | `drizzle-kit introspect` na produkcji     |
| `db:studio`, `db:studio:*`                       | `drizzle-kit studio`                      |

> `drizzle-kit push` nakłada różnicę schematu bezpośrednio i całkowicie pomija pliki migracji, więc baza trafia w stan, którego nie opisuje żadna zacommitowana migracja. Wybieraj `db:generate` plus `db:migrate:*`. Zwłaszcza `db:push:production` nie ma żadnej siatki bezpieczeństwa.

`db:introspect:*` zapisuje `src/integrations/drizzle-orm/migrations/schema.ts` i `migrations/relations.ts` — zrzut żywej bazy tak, jak widzi ją Drizzle. Te dwa pliki są wynikiem, a nie źródłem: nic ich nie importuje, a pliki schematów modułów pozostają autorytatywne. Przydają się do sprawdzenia, czy żywa baza nie rozjechała się ze schematem w TypeScripcie, i są nadpisywane przy każdej introspekcji.

Drizzle Studio (`bun run db:studio`) otwiera interfejs w przeglądarce na bazie danego środowiska. Wariant `development` jest domyślny i rozmawia z bazą preview.

## Seedy

`src/integrations/drizzle-orm/seeds/` zawiera jedenaście plików SQL, które zapisują wiersze ze stałymi UUID-ami:

```
delivery-methods.sql   product-categories.sql   product-collections.sql
product-attributes.sql products.sql             product-variants.sql
inventory.sql          product-images.sql       category-on-product.sql
collection-on-product.sql                       attribute-on-product.sql
```

Tylko `delivery-methods.sql`, który dodaje dwóch przewoźników i metody dostawy, używa `INSERT OR IGNORE` i zostawia istniejące wiersze bez zmian. Pozostałe dziesięć najpierw usuwa wiersze, które kolidowałyby z seedem — wiersze z handle'em albo SKU z seeda pod innym identyfikatorem, pozostałe zdjęcia i powiązania atrybutów dwóch zaseedowanych produktów, wszystkie ich powiązania z kategoriami i kolekcjami oraz inne wiersze stanów ich wariantów — a potem zapisuje swoje wiersze na miejsce tych o tym samym identyfikatorze: osiem przez `INSERT … ON CONFLICT(id) DO UPDATE`, a `category-on-product.sql` i `collection-on-product.sql` przez `INSERT OR REPLACE`.

`db:seed:preview` i `db:seed:production` łączą w łańcuch `wrangler d1 execute DB --env <środowisko> --remote --file=<każdy plik>` w tej kolejności — kolejności zależności, bo tabele złączeń odwołują się do produktów, kategorii i kolekcji tworzonych przez wcześniejsze pliki. `bun run db:seed` bez sufiksu jest aliasem `db:seed:preview`.

> **Nie uruchamiaj `bun run db:seed`, `bun run db:seed:preview` ani `bun run db:seed:production`.** Na żywej bazie usunęłyby wiersze, z którymi kolidują, nadpisały zaseedowane produkty, warianty, kategorie, kolekcje, atrybuty i zdjęcia wartościami z seeda, co koliduje z prawdziwymi danymi, którymi zarządza się z panelu administracyjnego, i przywróciły stan obu zaseedowanych wariantów do 99 dostępnych i 0 zarezerwowanych.

`bun run db:seed:test` to seed lokalny. Uruchamia `scripts/seed-test.ts`, który wczytuje te same jedenaście plików oraz konta zestawu end-to-end do lokalnej bazy `test` w `.wrangler/test`; zobacz [Testy](/docs/tooling/testing#dane).

## Bezpieczna zmiana schematu

1. Zmień plik `*.schema.ts` modułu — dodaj albo zmień kolumnę, indeks lub relację.
2. Dodaj tabelę do `drizzle.schemas.ts`, jeśli jest nowa.
3. Zaktualizuj `*.zod.ts` i `*.types.ts` modułu, aby walidacja i typy poszły za kolumną.
4. Uruchom `bun run db:generate` i przeczytaj wygenerowany SQL.
5. Zaktualizuj `*.schema.test.ts` modułu, jeśli go ma (ma go 29 z 40 plików schematów modułów) — lista kolumn i klucze obce, a w niektórych także relacje, są sprawdzane jawnie, więc test będzie się wysypywał, dopóki tego nie zrobisz.
6. Zaktualizuj instrukcje `create table` w każdym `*.integration.test.ts`, który pisze własne tabele dla zmienionej tabeli. Zestawy integracyjne wywołujące `applyMigrationHistory` odtwarzają każdy plik migracji, także nowy.
7. Uruchom `bun run check` i `bun run test`.
8. Zachowaj zgodność migracji wstecz z Workerem wdrożonym przed nią: dodawaj, nie usuwaj i nie zmieniaj nazw, a to, czego nic już nie czyta, usuń w późniejszym wydaniu. Wdrożenie nakłada ją tuż przed `wrangler deploy`; zobacz [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

## Kopie zapasowe

D1 Time Travel pozwala cofnąć produkcyjną bazę do dowolnej minuty z ostatnich 30 dni na planie Workers Paid, a regularny eksport trzyma jej kopię poza Cloudflare. Zwykły `wrangler d1 export` produkcji się nie udaje, bo `storefront_search` to tabela wirtualna FTS5; [Kopie zapasowe i przywracanie](/docs/guides/backup-and-restore) opisują kroki wokół niej, przywracanie z eksportu i to, co kasuje przywrócenie przez Time Travel.
