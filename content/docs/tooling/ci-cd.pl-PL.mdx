`.github/workflows/` zawiera pięć przepływów. Wszystkie instalują zestaw narzędzi przez akcję złożoną `.github/actions/setup`. Testy uruchamiają `ci.yml` i `e2e-full.yml`. Produkcja wdraża tylko commit, którego przebieg `ci.yml` się powiódł; wdrożenie podglądu uruchamia tylko `bun run check`.

| Przepływ                | Wyzwalacz                                                                    | Co robi                                                                                          |
| ----------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `ci.yml`                | Każdy pull request; pushe do `main`                                          | `check`, `test:coverage`, `build:preview`, wysyła raport pokrycia; zestaw Playwrighta w Chromium |
| `e2e-full.yml`          | Pushe do `main`; poniedziałki o 03:15 UTC; ręcznie                           | Zestaw Playwrighta w WebKicie po pushu, inaczej w Chromium i WebKicie; tryb testowy Stripe'a     |
| `e2e-reusable.yml`      | Wywoływany przez `ci.yml` i `e2e-full.yml`                                   | Buduje testowego Workera i uruchamia zestaw Playwrighta w jednej przeglądarce                    |
| `deploy-preview.yml`    | Pull requesty do `main` (opened, synchronize, reopened)                      | `check`, potem `deploy:preview`, potem komentarz z adresem podglądu                              |
| `deploy-production.yml` | Udany `ci.yml` dla pusha do `main`; ręcznie, dla commita, który go przeszedł | `deploy:production`                                                                              |

## Akcja setup

`.github/actions/setup/action.yml` to pięć kroków, w tym jeden warunkowy, i jedno wejście:

```yaml
- uses: oven-sh/setup-bun@v2
  with:
    bun-version: "1.4.0"
- uses: voidzero-dev/setup-vp@v1.20.0
  with:
    node-version: "24"
    cache: true
    run-install: false
- name: Install dependencies
  run: bun install --frozen-lockfile --ignore-scripts
- name: Configure test environment
  if: inputs.test-environment == 'true'
  run: |
    cp .env.test .env.development
    cp .env.test .env.preview
- name: Generate binding types
  run: bun run typegen
```

Dwa szczegóły mają znaczenie:

- **`--ignore-scripts`** oznacza, że skrypty cyklu życia `prepare` i `postinstall` się nie uruchamiają, więc na runnerze nie instalują się hooki Gita, a `typegen` wywoływany jest jawnie jako osobny krok. `typegen` to `bun run cf-typegen && bun run content`, co zapisuje `src/types/worker-configuration.d.ts` i `.source/`. Oba są w `.gitignore`, a `bun run check` nie wykona kontroli typów bez nich.
- **`test-environment`** (domyślnie `"false"`) kopiuje `.env.test` na `.env.development` i `.env.preview`, gdy ma wartość `"true"`. Ustawiają je zadanie `verify` w `ci.yml`, `e2e-reusable.yml` i zadanie `stripe-test-mode` w `e2e-full.yml`; dwa przepływy wdrożeniowe nie, bo wstrzykują prawdziwe wartości jako zmienne środowiskowe.

## ci.yml

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
permissions:
  contents: read
```

Zadanie `verify`, z limitem 25 minut, na `ubuntu-latest`, z `persist-credentials: false` przy checkoucie. Kroki to `bun run check`, `bun run test:coverage`, `bun run build:preview` oraz wysłanie `coverage/` jako artefaktu `coverage` z siedmiodniowym okresem przechowywania (`if: ${{ !cancelled() }}`, `if-no-files-found: ignore`).

Drugie zadanie, `e2e`, wywołuje `e2e-reusable.yml` z `browser: chromium`.

Krok kompilacji działa na atrapowym `.env.preview`, który akcja setup skopiowała z `.env.test`, i to wystarcza, bo `scripts/verify-build.ts` sprawdza kształt wyniku — konfigurację wdrożenia, nazwę Workera, zmienną `APP_ENV`, obecność fontów, JS-a i CSS-a klienta oraz brak importów `cloudflare:workers` i `node:` w zasobach klienta — a nie wartości jakichkolwiek danych uwierzytelniających.

## Przepływy end-to-end

`e2e-reusable.yml` przyjmuje wejście `browser` i opcjonalną ścieżkę `suite` (domyślnie `e2e/specs`). Uruchamia akcję setup z `test-environment: "true"`, następnie `bun run db:reset:test`, które tworzy i seeduje lokalną bazę D1, `bun run build:test`, przywraca pamięć podręczną przeglądarek Playwrighta (klucz `<os>-playwright-chromium-<browser>-<skrót bun.lock>`), instaluje Chromium i wskazaną przeglądarkę z ich zależnościami systemowymi (`bunx playwright install --with-deps chromium <browser>`; Chromium jest potrzebne zawsze, bo działa na nim projekt `setup`, który loguje seedowanego administratora i klienta) i uruchamia `bunx playwright test <suite> --project=<browser> --project=<browser>-shop-wide` z limitem 30 minut, więc specyfikacje ogólnosklepowe działają po zestawie danej przeglądarki (zobacz [Testowanie](/docs/tooling/testing#projekty)). Przy ustawionym `CI` Playwright tylko uruchamia zbudowanego Workera, powtarza nieudany test dwa razy i pracuje na dwóch workerach. Po błędzie wysyła na siedem dni `playwright-report/` i `test-results/` ze śladami, zrzutami ekranu i nagraniami.

`e2e-full.yml` uruchamia ten sam przepływ jako macierz z `fail-fast: false`: po pushu do `main` w WebKicie, bo pull request przeszedł już Chromium, a w cotygodniowym harmonogramie lub ręcznie w obu przeglądarkach. Ma ten sam blok `concurrency` co `ci.yml` (grupa `${{ github.workflow }}-${{ github.ref }}`, `cancel-in-progress: true`), więc nowszy przebieg na `main`, czy to po pushu, z harmonogramu, czy uruchomiony ręcznie, anuluje trwający, i nadaje wyłącznie `contents: read`.

Jego drugie zadanie, `stripe-test-mode`, przy każdym uruchomieniu przepływu płaci przez sandbox Stripe'a: kartą, kartami odrzucanymi i wymagającymi 3D Secure, BLIK-iem i przez Przelewy24. Ustawia dla całego zadania `STRIPE_SECRET_KEY` i `VITE_STRIPE_PUBLISHABLE_KEY` z sekretów repozytorium `E2E_STRIPE_SECRET_KEY` i `E2E_STRIPE_PUBLISHABLE_KEY`. Tak jak `e2e-reusable.yml` ma limit 30 minut, uruchamia akcję setup z `test-environment: "true"` i tworzy oraz seeduje lokalną bazę D1 przez `bun run db:reset:test`; potem `bun run build:test` wpisuje klucz publiczny sandboxa do pakietu klienta i daje testowemu Workerowi jego klucz tajny. Zadanie przywraca własną pamięć podręczną Playwrighta (klucz `<os>-playwright-chromium-<skrót bun.lock>`), instaluje Chromium i uruchamia `bun run test:e2e:stripe`. Oba sekrety są ustawione, więc każde uruchomienie płaci przez sandbox. Krok zaraz po pobraniu repozytorium, **Report missing Stripe sandbox keys**, działa tylko wtedy, gdy któryś sekret jest pusty: build i tak by się wtedy wykonał, Playwright zgłosiłby każdą specyfikację jako pominiętą z podanym powodem, a zadanie zakończyłoby się sukcesem, więc krok dodaje do podsumowania uruchomienia ostrzeżenie, że żadna płatność nie dotarła do Stripe'a. Gdy testowy Worker już działa, przeglądarka nie sięga do żadnego zewnętrznego hosta poza tymi w domenach `stripe.com`, `stripe.network`, `stripecdn.com` i `hcaptcha.com` (`STRIPE_ORIGINS` w `e2e/fixtures/stripe-test-mode.ts`), które serwują API Stripe'a, Stripe.js, jego ramki i testowe strony płatności Stripe'a; wspólna fikstura blokuje każde inne żądanie na zewnątrz. Specyfikacje opisuje [Tryb testowy Stripe](/docs/tooling/testing#tryb-testowy-stripe). Po błędzie zadanie wysyła swój raport jako `playwright-report-stripe-test-mode`.

## Przepływy wdrożeniowe

Oba przepływy wdrożeniowe mają ten sam kształt: `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true` na poziomie przepływu, środowisko GitHuba (`preview` albo `production`), akcja setup, a następnie jeden krok, który tworzy pusty plik środowiska i uruchamia skrypt wdrożeniowy. Podgląd uruchamia przed tym krokiem `bun run check`; produkcja nie, bo jej zadanie wdrożeniowe działa tylko dla commita, który przeszedł już CI, a wybiera go pierwsze zadanie, `choose-commit`:

```yaml
run: |
  touch .env.preview
  bun run deploy:preview
```

`touch` istnieje, bo `scripts/prepare-deploy-secrets.ts` czyta ten plik bezwarunkowo (`scripts/verify-stripe-keys.ts` i `scripts/verify-email-sender.ts` traktują brakujący plik jak pusty); same wartości pochodzą z bloku `env:` tego kroku, który wszystkie trzy skrypty przedkładają nad plik:

```ts
const value = process.env[name] ?? values[name]
```

Współbieżność różni się celowo. Podgląd grupuje po numerze pull requesta i anuluje trwające przebiegi (`preview-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`), więc kolejny push do gałęzi zastępuje jej podgląd. Zadanie wdrożeniowe produkcji używa stałej grupy `production` z `cancel-in-progress: false`, więc wdrożenia ustawiają się w kolejce, zamiast przerywać się w połowie. Grupa jest ustawiona na zadaniu wdrożeniowym, a nie na całym przepływie, więc nie czeka w niej ani `choose-commit`, ani przebieg, który nie wybrał żadnego commita.

`deploy-preview.yml` bierze dodatkowo `pull-requests: write` i kończy krokiem `actions/github-script@v7`, który publikuje — albo aktualizuje, szukając w istniejących komentarzach napisu `Preview Deployment` — komentarz z odnośnikiem do `https://martebizuteria-preview.pjborowiecki.workers.dev`.

### Na co czeka wdrożenie produkcyjne

`deploy-production.yml` nie startuje po pushu. Startuje przez `workflow_run`, gdy przepływ `CI` zakończy się na `main`, a jego pierwsze zadanie, `choose-commit`, działa tylko wtedy, gdy tamten przebieg dotyczył pusha i zakończył się wynikiem `success`. Commit trafia więc na produkcję dopiero wtedy, gdy na tym właśnie commicie przeszły `check`, `test:coverage`, `build:preview` i zestaw end-to-end w Chromium. Pull request z gałęzi, która przypadkiem nazywa się `main`, go nie uruchomi, bo jego przebieg CI ma zdarzenie `pull_request`. Gdy CI zawiedzie albo zostanie anulowane, nic się nie wdraża. Przebieg `e2e-full.yml` w WebKicie po pushu nie należy do tej bramki.

`choose-commit` przekazuje zadaniu wdrożeniowemu `github.event.workflow_run.head_sha`, czyli commit przetestowany przez CI, ale tylko wtedy, gdy wciąż jest on najnowszym commitem na `main`, co sprawdza przez `gh api repos/<owner>/<repo>/commits/main`. Gdy na `main` jest już nowszy commit, zapisuje ostrzeżenie, a zadanie wdrożeniowe zostaje pominięte; nowszy commit wdroży się, gdy przejdzie jego własne CI. Ponowne uruchomienie CI starszego commita, na przykład po niestabilnym teście end-to-end, nigdy więc nie wdroży go w miejsce commitów scalonych po nim, a razem z tym, że `ci.yml` anuluje swój przebieg na `main`, gdy przychodzi nowszy push, produkcja sama z siebie przesuwa się tylko do przodu. Powrót do starszego commita wymaga ręcznego uruchomienia. Zadanie wdrożeniowe pobiera przekazany mu commit, a nie to, co jest na `main` w chwili, gdy rusza.

`workflow_dispatch` przyjmuje jedno wejście, `commit`, czyli pełny SHA commita do wdrożenia. Zamiast sprawdzać najnowszy commit, `choose-commit` pyta `gh run list --workflow ci.yml --branch main --event push --commit <sha> --status success`, czy CI przeszło dla pusha tego commita do `main` (stąd uprawnienie `actions: read` tego zadania), i kończy się błędem, jeśli nie przeszło, więc nic się nie wdraża. Tak wdraża się ponownie sprawdzony commit; zobacz [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

GitHub uruchamia `workflow_run` wyłącznie z pliku przepływu na `main`, więc zmiana w `deploy-production.yml` działa od chwili scalenia.

Podgląd jest jednym wspólnym wdrożeniem: każdy pull request wdraża się na tego samego Workera (`martebizuteria-preview`) opartego na tej samej bazie D1 preview, przestrzeni KV i zasobniku R2 (`martebizuteria-preview`), więc na żywo jest ostatnie wdrożenie podglądu.

## Co dokładnie robi wdrożenie

```json
"deploy:preview": "bun scripts/verify-bindings.ts preview && bun scripts/verify-stripe-keys.ts preview && bun scripts/verify-email-sender.ts preview && bun run build:preview && bun scripts/prepare-deploy-secrets.ts preview && bun run db:migrate:preview && env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.preview.json && bun scripts/verify-deployment.ts preview"
```

Osiem etapów połączonych `&&`, więc pierwszy, który zawiedzie, zatrzymuje wdrożenie.

### 1. verify-bindings.ts

Czyta `wrangler.jsonc` dla docelowego środowiska przez `unstable_readConfig` i odmawia kontynuacji, dopóki każdy binding nie jest obecny i prawdziwy:

- binding D1 `DB` z `database_id`, który nie składa się z samych zer i myślników,
- binding KV `CACHE` z prawdziwym `id`,
- binding R2 `IMAGES` z `bucket_name`,
- producent `AUDIT_LOG_QUEUE` **oraz** konsument tej samej kolejki, który wskazuje `dead_letter_queue` konsumowaną przez drugiego konsumenta,
- producent `NEWSLETTER_QUEUE` **oraz** konsument tej samej kolejki, który wskazuje `dead_letter_queue` konsumowaną przez kolejnego konsumenta,
- binding Durable Object `REALTIME_INVALIDATION_HUB`, którego `class_name` to `RealtimeInvalidationHub`,
- dla produkcji bucket `IMAGES` inny niż ten, który wiąże preview.

To ta kontrola wyłapuje zastępczy identyfikator albo bucket skopiowany między środowiskami.

### 2. verify-stripe-keys.ts

Czyta `VITE_STRIPE_PUBLISHABLE_KEY` i `STRIPE_SECRET_KEY` najpierw z `process.env`, potem z `.env.<środowisko>`, i przekazuje je do `verifyStripeKeys` z `src/integrations/stripe/stripe.keys.ts`, które rozpoznaje tryb każdego klucza po przedrostku. Produkcja wymaga kluczy live: `pk_live_` oraz `sk_live_` albo ograniczonego `rk_live_`. Preview, a także development, gdy skrypt uruchamia się ręcznie, wymagają kluczy testowych: `pk_test_` z `sk_test_` albo `rk_test_`. Przerywa przy brakującym lub pustym kluczu, przy wartości, która nie jest kluczem właściwym dla swojej zmiennej, przy kluczu publicznym w innym trybie niż klucz tajny, w każdym środowisku, oraz przy kluczach w trybie niewłaściwym dla celu. Wynik i komunikaty błędów podają nazwy zmiennych i ich tryb, nigdy sam klucz.

Czyta tylko przedrostki i nie łączy się z żadną zewnętrzną usługą, więc nie sprawdza, czy Stripe nadal przyjmuje klucze ani czy klucz ograniczony ma uprawnienia potrzebne przy zamówieniu. Działa przed kompilacją, bo `VITE_STRIPE_PUBLISHABLE_KEY` trafia do pakietu klienta, więc klucze testowe w środowisku produkcyjnym wdrożyłyby sklep, którego kasa przyjmuje testowe karty Stripe. Zobacz [Stripe](/docs/integrations/stripe#sekrety).

### 3. verify-email-sender.ts

Czyta `RESEND_API_KEY` i `RESEND_EMAIL_FROM` najpierw z `process.env`, potem z `.env.<środowisko>`, i pyta Resend, czy wyśle pocztę z tego adresu. Przerywa przy braku klucza, nadawcy z nazwą wyświetlaną, `onboarding@resend.dev` poza środowiskiem development, domenie, której nie ma na koncie Resend przypisanym do klucza, oraz domenie z niezweryfikowanymi rekordami DKIM lub SPF — wtedy wypisuje rekordy, które trzeba jeszcze opublikować. Klucz tylko do wysyłki nie może czytać domen, więc kontrola odczytuje je kluczem `RESEND_MANAGEMENT_API_KEY` — opcjonalnym kluczem z pełnym dostępem, który krok bierze z sekretów środowiska w GitHubie i który nigdy nie trafia do Workera. Bez niego kontrola wysyła jeden testowy e-mail na `delivered@resend.dev` i przerywa, jeśli Resend go odrzuci. Każde żądanie do Resend jest ponawiane raz po przekroczeniu limitu żądań albo odpowiedzi 5xx, a cała kontrola rezygnuje po 30 sekundach.

Działa przed kompilacją, żeby nadawca, którego Resend by odrzucił, zatrzymał wdrożenie w kilka sekund. To jedyny etap przed kompilacją, który łączy się z zewnętrzną usługą, i nie należy do `build:*`, więc `ci.yml` nigdy nie wywołuje Resend z atrapowymi wartościami z `.env.test`. Rekordy i lokalną konfigurację z `onboarding@resend.dev` opisuje [Resend](/docs/integrations/resend#domena-nadawcy).

### 4. kompilacja

`bun run build:preview` usuwa `dist`, odtwarza `.source/`, uruchamia `CLOUDFLARE_ENV=preview vp build --mode preview`, a potem `bun scripts/verify-build.ts preview`. `verify-build.ts` czyta `.wrangler/deploy/config.json`, idzie za jego `configPath` i sprawdza, że wskazuje dokładnie na `dist/server/wrangler.json`; że `vars.APP_ENV` skompilowanej konfiguracji odpowiada celowi, a jej `name` to `martebizuteria-preview` (albo `martebizuteria` dla produkcji); że istnieje jej `main`, a katalog zasobów wskazuje na `dist/client`; że istnieje `dist/client/fonts`; że `dist/client/assets` zawiera co najmniej jeden plik `.js` i jeden `.css`; a na koniec skanuje każdy plik `.js` klienta przez `new Bun.Transpiler({ loader: "js" })` i przerywa przy jakimkolwiek imporcie `cloudflare:workers` lub modułu `node:`.

### 5. prepare-deploy-secrets.ts

Czyta `secrets.required` z bloku danego środowiska w `wrangler.jsonc`, rozwiązuje każdą nazwę najpierw z `process.env`, a potem z `.env.<środowisko>`, przerywa na pierwszej brakującej wartości albo pustej wartości innej niż `INPOST_API_TOKEN` i `INPOST_ORGANIZATION_ID` (`SECRETS_THAT_MAY_BE_BLANK`, wysyłane puste, więc przesyłki InPost i ich webhook pozostają wyłączone) i zapisuje `.wrangler/secrets.<środowisko>.json` z uprawnieniami `0o600`.

Zapisywane są wyłącznie nazwy zadeklarowane w `wrangler.jsonc`. `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` i `CLOUDFLARE_ACCESS_TOKEN` celowo nie są na tej liście: to dane uwierzytelniające do zarządzania, potrzebne drizzle-kitowi i Wranglerowi, a nie sekrety uruchomieniowe Workera, i wysłanie ich do Workera byłoby wyciekiem uprawnień.

### 6. db:migrate:preview

`bun run db:migrate:preview` to `vp exec wrangler d1 migrations apply DB --env preview --remote`, a `deploy:production` uruchamia w tym miejscu `db:migrate:production`. Przy tej komendzie Wrangler czyta `wrangler.jsonc`, a nie skompilowaną konfigurację, i nakłada w kolejności nazw każdy plik z `src/integrations/drizzle-orm/migrations/`, którego nie ma jeszcze w tabeli `d1_migrations` bazy, albo wypisuje `No migrations to apply!`. Gdy migracja zawiedzie, Wrangler wycofuje tę jedną, zachowuje wcześniejsze i kończy się błędem, więc Worker nie zostaje wdrożony. Na runnerze Wrangler nakłada migracje bez pytania; w terminalu najpierw pyta, a odpowiedź „nie” pomija migracje, ale nie wdrożenie, więc zamiast tego przerwij Ctrl+C.

Etap działa po kompilacji i po pliku sekretów, więc wdrożenie, które zawiedzie wcześniej, nigdy nie dotyka bazy, i przed `wrangler deploy`, więc nowy Worker nigdy nie startuje na schemacie, którego nie zna. W czasie migracji sklep obsługuje poprzedni Worker, dlatego każda migracja musi zachować jego działanie; zobacz [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

### 7. wrangler deploy

```sh
env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.preview.json
```

`CLOUDFLARE_ENV` jest dla tej komendy usuwane, bo skompilowany `dist/server/wrangler.json` jest już spłaszczony do jednego środowiska — zostawienie tej zmiennej kazałoby Wranglerowi szukać sekcji środowiska w konfiguracji, która jej już nie ma. Plik sekretów jest wysyłany razem z wdrożeniem, więc dziesięć zadeklarowanych sekretów ustawia się atomowo wraz z nową wersją.

### 8. verify-deployment.ts

Wywołuje `verifyDeployment` z `src/lib/deployment.ts`, które pyta własny host `workers.dev` środowiska, z `WORKERS_DEV_HOSTS` w `src/modules/_core/constants/api.ts`, o pięć ścieżek, bez podążania za przekierowaniami. `/` i `/products` muszą odpowiedzieć `200` z `text/html`, `/robots.txt` musi odpowiedzieć `200` z `text/plain`, `/api/webhooks/stripe` musi odrzucić `GET` kodem `405` z `text/plain`, co pokazuje, że żądanie dotarło do własnego handlera trasy, a nie do wyrenderowanej strony, a `/api/health` musi odpowiedzieć `200` z `application/json`, co robi tylko wtedy, gdy odpowiadają D1, KV i R2; jej `503` przerywa wdrożenie. Każde żądanie rezygnuje po 15 sekundach, a o stronę, która zawiedzie, kontrola pyta łącznie najwyżej trzy razy, co pięć sekund. Strona, która dalej zawodzi, przerywa wdrożenie, a komunikat ma po jednym wierszu na stronę. Nowa wersja działa już wtedy na żywo, więc następnym krokiem jest [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

Kontrola tylko czyta publiczne strony: nikogo nie loguje, nie otwiera zamówienia i niczego nie zapisuje. Pyta host `workers.dev`, który `workers_dev: true` w `wrangler.jsonc` zostawia włączony w obu środowiskach, obok domeny własnej preview `preview.martebizuteria.pl` (lista `routes` produkcji jest pusta), więc kontrola nie zależy od DNS strefy ani od certyfikatu, który Cloudflare może jeszcze wystawiać dla świeżo podłączonej domeny.

## Konfiguracja repozytorium

| Rodzaj                                                     | Nazwy                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Secrets** w Actions                                      | `CLOUDFLARE_ACCESS_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `INPOST_API_TOKEN`, `INPOST_ORGANIZATION_ID`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `RESEND_MANAGEMENT_API_KEY` (opcjonalny), `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` |
| **Secrets** w Actions dla zadania trybu testowego Stripe'a | `E2E_STRIPE_SECRET_KEY`, `E2E_STRIPE_PUBLISHABLE_KEY`                                                                                                                                                                                                                                                |
| **Vars** w Actions                                         | `VITE_APP_URL`, `VITE_R2_URL`, `VITE_STRIPE_PUBLISHABLE_KEY`                                                                                                                                                                                                                                         |

`CLOUDFLARE_ACCESS_TOKEN` jest przekazywany do kroku jako `CLOUDFLARE_API_TOKEN`, bo taką nazwę czyta Wrangler. Poza wdrażaniem Workera token potrzebuje uprawnienia do edycji D1, bo wdrożenie nakłada nim migracje, oraz, przy wdrożeniu podglądu, uprawnień Workers Routes (edycja) i Zone (odczyt) do strefy `martebizuteria.pl`, bo to wdrożenie podłącza domenę własną `preview.martebizuteria.pl` z `routes` środowiska preview w `wrangler.jsonc`. Lista `routes` produkcji jest pusta, więc wdrożenie produkcyjne nie podłącza żadnej domeny własnej. Oba przepływy wdrożeniowe korzystają ze środowisk GitHuba (`preview`, `production`), więc sekrety można tam zawęzić do środowiska.

Zadanie trybu testowego Stripe'a czyta dwa sekrety repozytorium spoza tych środowisk i oba są ustawione: `E2E_STRIPE_SECRET_KEY`, klucz tajny sandboxa Stripe'a (`sk_test_`), oraz `E2E_STRIPE_PUBLISHABLE_KEY`, klucz `pk_test_` tego samego sandboxa. Weź je z sandboxa bez endpointu webhooka i z włączonymi w ustawieniach metod płatności kartami, BLIK-iem i Przelewy24, a nie z konta, którego używa preview, żeby płatności testowe nie trafiały na konto preview ani do jego dziennika zdarzeń. Endpoint wskazujący Workera preview i tak tylko zalogowałby i potwierdził ich zdarzenia, bo ich metadane `deployment` wskazują `martebizuteria-test` (zobacz [Płatności: punkt końcowy webhooka](/docs/features/payments#punkt-końcowy-webhooka)).

`VITE_R2_URL` jest wymieniony w `secrets.required` w `wrangler.jsonc`, ale dostarczany z **vars** Actions, a nie z secrets — to publiczny adres zasobnika, który dodatkowo musi być widoczny dla pakietu klienta przez przedrostek `VITE_`. `prepare-deploy-secrets.ts` czyta go z `process.env`, więc to działa. Preview i produkcja czytają różne zasobniki, więc ustaw go w środowiskach GitHub `preview` i `production`, a nie raz dla repozytorium; wartości wymienia [Dostarczanie zdjęć](/docs/guides/image-delivery).

`VITE_APP_URL` jest przekazywany do obu kroków wdrożeniowych, ale nic go nie czyta: nie ma go w `secrets.required` i nie używa go żaden kod w `src/` ani `scripts/`. Kanoniczny adres sklepu to `APP_URL` z `src/presentation/branding/app.ts`.

## Migracje a CI

`ci.yml` i przepływy end-to-end nigdy nie dotykają wdrożonej bazy; przepływ end-to-end odtwarza całą historię we własnej lokalnej bazie, co przy okazji dowodzi, że historia wciąż buduje bazę od zera. Wdrożone bazy migrują same skrypty wdrożeniowe, tuż przed `wrangler deploy`: wspólną bazę preview każde wdrożenie podglądu, więc migracja z pull requesta trafia do niej, gdy tylko wdroży się podgląd tego pull requesta, a produkcję każde wdrożenie produkcyjne. `bun run db:migrate:<środowisko>` nadal nakłada migracje ręcznie, a `bun run db:migrations:<środowisko>` pokazuje, co baza ma już nałożone.

Migracja nałożona przez wdrożenie podglądu zostaje nałożona, nawet gdy jej pull request się zmieni albo zostanie zamknięty, więc nie edytuj migracji, której podgląd już się wdrożył; dodaj kolejną. Zobacz [Baza danych](/docs/tooling/database) i [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).
