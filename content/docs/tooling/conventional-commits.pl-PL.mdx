Tematy commitów trzymają się formatu Conventional Commits:

```
<type>(<scope>): <description>
```

Zakres jest opcjonalny, a `!` przed dwukropkiem oznacza zmianę łamiącą zgodność. Temat pisz **bez** emoji — doda je hook:

```sh
git commit -m "fix(checkout): keep the reserved quantity when a card is declined"
```

Taki commit wyląduje jako:

```
🐛 fix(checkout): keep the reserved quantity when a card is declined
```

## Hook

`.vite-hooks/prepare-commit-msg` ma jedną linię:

```sh
bun scripts/commit-msg.ts "$1" "$2"
```

Git przekazuje ścieżkę do pliku z komunikatem jako `$1`, a źródło komunikatu jako `$2`. `scripts/commit-msg.ts` czyta plik, znajduje pierwszą linię, która nie jest pusta ani komentarzem `#`, i decyduje, co z nią zrobić.

| Typ        | Emoji |
| ---------- | ----- |
| `build`    | 🛠️    |
| `chore`    | ♻️    |
| `ci`       | ⚙️    |
| `docs`     | 📚    |
| `feat`     | ✨    |
| `fix`      | 🐛    |
| `perf`     | 🚀    |
| `refactor` | 📦    |
| `revert`   | 🗑️    |
| `style`    | 💎    |
| `test`     | 🚨    |

Jedenaście typów i nic poza nimi — w każdym temacie, który hook waliduje; temat, który już zaczyna się od emoji takiego jak 📚 albo 🐛, nie jest walidowany wcale (zobacz [Czego hook nie rusza](#czego-hook-nie-rusza)). Hook dokleja odpowiednie emoji na początku linii tematu i nie rusza treści commita.

## Co powoduje odrzucenie

Dwie rzeczy przerywają commit z kodem wyjścia 1.

**Temat, który nie pasuje do wzorca konwencji** — hook sprawdza go wyrażeniem `/^([a-z]+)(?:\([^)]*\))?!?:\s/`, więc typ musi składać się z małych liter, zakres musi być w nawiasach, jeśli występuje, a po dwukropku musi być spacja:

```
❌  Commit message does not follow conventional format.
   Expected: <type>(<scope>): <description>
   Allowed types: build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test
```

**Poprawnie zbudowany temat z nieznanym typem** — na przykład `wip: …` albo `feature: …`:

```
❌  Unknown commit type: "feature"
   Allowed types: build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test
```

## Czego hook nie rusza

Hook kończy działanie bez zmiany komunikatu w pięciu przypadkach:

- źródłem komunikatu jest `squash`, `merge` albo `template`;
- komunikat jest pusty lub nie ma żadnej linii innej niż komentarz;
- temat już zaczyna się od znaku z właściwością Unicode `Emoji_Presentation`, co sprawdza `/^\p{Emoji_Presentation}/u`. Obejmuje to 📚, ✨, 🐛, 🚀, 📦, 💎 i 🚨, więc poprawianie commita `docs`, `feat`, `fix`, `perf`, `refactor`, `style` albo `test`, który hook już ozdobił, zostawia jego temat bez zmian. Oznacza to też, że taki temat w ogóle pomija walidację: `🐛 cokolwiek` przechodzi bez zmian;
- temat pasuje do `/^(?:Merge |Revert "|fixup! |squash! )/`, co pokrywa tematy generowane przez samego Gita;
- nie przekazano ścieżki do pliku z komunikatem.

Pozostałe cztery emoji, 🛠️, ♻️, ⚙️ i 🗑️, to znaki w stylu tekstowym z selektorem wariantu U+FE0F, do których `Emoji_Presentation` nie pasuje. Poprawianie commita `build`, `chore`, `ci` albo `revert` (przy `--amend`, `-c` i `-C` Git przekazuje źródło `commit`) bez zmiany tematu przepuszcza więc ozdobiony temat przez wzorzec konwencji, który odrzuca początkowe emoji, a hook przerywa commit komunikatem `Commit message does not follow conventional format.` Hook działa, zanim otworzy się edytor, więc podaj temat ponownie bez emoji, na przykład `git commit --amend -m "chore(deps): …"`; hook doda emoji z powrotem.

Jeśli skrypt wyrzuci wyjątek z jakiegokolwiek innego powodu, wypisuje `❌  Failed to process commit message:` i kończy się kodem 1 — zepsuty hook przerywa pracę głośno, zamiast przepuszczać zdeformowany temat.

## Przed hookiem komunikatu

`.vite-hooks/pre-commit` uruchamia się pierwszy:

```sh
bun run check:pre-commit
```

To `vp staged`, który stosuje blok `staged` z `vite.config.ts` — `vp check --fix` na każdym pliku w przechowalni. Commita nie da się więc utworzyć, dopóki pliki w przechowalni nie przejdą formatowania, lintu i kontroli typów.

Nie pomijaj kontroli przed commitem przez `--no-verify`. Pomija ono tylko `.vite-hooks/pre-commit`; Git nie wyłącza nim `prepare-commit-msg`, więc temat i tak jest walidowany i ozdabiany. `ci.yml` i `deploy-preview.yml` uruchamiają `bun run check` ponownie, więc commit, który pominął kontrolę, wysypie się tam, później i drożej.

Oba hooki instaluje `vp config --no-agent`, uruchamiany przez `bun install` w skrypcie `prepare`. `vp hooks status` pokaże, czy są aktywne w Twoim klonie.

## Zakresy w praktyce

Zakresy nie są walidowane. Najnowsza historia używa przeważnie jednego płaskiego zakresu na obszar funkcjonalny; najczęstsze to `checkout`, `orders`, `account`, `admin`, `auth`, `catalog`, `audit` i `email`, a commity `docs` podają obszar dokumentacji, który zmieniają, na przykład `docs(testing)` albo `docs(payments)`. Zakresy zagnieżdżone, takie jak `admin/orders` czy `admin/catalog/products`, pojawiają się w historii, ale rzadko. Używaj obszaru funkcjonalnego, do którego należy zmiana:

```sh
git commit -m "fix(orders): show the admin order's VAT as included in the total"
git commit -m "feat(i18n): resolve each user's time zone and format locale, their own choice first"
git commit -m "docs(testing): state the current test counts and coverage thresholds"
```
