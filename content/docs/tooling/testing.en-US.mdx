Vite+ runs Vitest 5 with the configuration in the `test` block of `vite.config.ts`. Tests live in a `__test__` folder next to the code they cover and import their API from `vite-plus/test`, never from `vitest`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"
```

Run them with `bun run test`, not `bun test`. Bun's own runner ignores the Vitest projects, the jsdom environment and the setup file, so a large part of the suite would silently fail or be skipped.

## The three projects

The suite is split by filename, and each split gets its own environment.

| Project       | Files                                                         | Environment | Setup file                      |
| ------------- | ------------------------------------------------------------- | ----------- | ------------------------------- |
| `node`        | `src/**/*.{test,spec}.{ts,tsx}` except the two patterns below | `node`      | none                            |
| `integration` | `src/**/*.integration.test.{ts,tsx}`                          | `node`      | none                            |
| `component`   | `src/**/*.component.test.{ts,tsx}`                            | `jsdom`     | `src/platform/testing/setup.ts` |

```sh
bun run test              # vp test run — all three projects
bun run test:unit         # vp test run --project node
bun run test:integration  # vp test run --project integration
bun run test:component    # vp test run --project component
bun run test:changed      # vp test run --changed
bun run test:coverage     # vp test run --coverage
```

The repository holds 1,104 test files: 574 component tests, 98 integration tests and 432 unit tests in the `node` project.

> `bun run test:watch` maps to `vp test` with no subcommand. Per `vp test --help`, `vp test` "runs tests once by default" and watch mode is the separate `vp test watch` subcommand, so this script is a second single-shot run rather than a watcher. Use `vp test watch` (or `vp test --watch`) when you want watch mode.

## Shared test configuration

Everything the projects have in common lives in the top-level `test` block and is inherited through `extends: true`:

| Setting           | Value                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| `environment`     | `"node"` (the `component` project overrides it to `"jsdom"`)                                                      |
| `env`             | `loadEnv("test", import.meta.dirname, "")` — loads `.env.test`, which is committed and contains dummy values only |
| `pool`            | `"threads"`                                                                                                       |
| `maxWorkers`      | `"50%"`                                                                                                           |
| `isolate`         | `true`                                                                                                            |
| `passWithNoTests` | `false`                                                                                                           |
| `exclude`         | `node_modules/**`, `opensrc/**`, `dist/**`, `scripts/**`, `e2e/**`, `src/integrations/drizzle-orm/migrations/**`  |

Because `test.env` loads `.env.test`, no test needs real credentials. `scripts/` is excluded from the suite, so `scripts/commit-msg.ts`, `scripts/verify-build.ts` and friends are not covered by tests.

## The test platform

`src/platform/testing/` holds the shared infrastructure. Everything else is colocated with the code it exercises.

| File                             | What it provides                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------------------- |
| `setup.ts`                       | jest-dom matchers, DOM observer stubs, `matchMedia`, and the `createServerFn` proxy                |
| `vitest-env.d.ts`                | `vite-plus/test/globals` reference and the jest-dom matcher types on Vitest's `Matchers` interface |
| `mocks/d1.ts`                    | `createTestD1Database(sqlite, onQuery?, onRoundTrip?)` — a `D1Database` backed by `node:sqlite`    |
| `mocks/migrations.ts`            | `applyMigration` for one migration and `applyMigrationHistory` to build the production schema      |
| `mocks/intersection-observer.ts` | `StubIntersectionObserver` — no-op `observe`, `unobserve`, `disconnect`, `takeRecords`             |
| `mocks/resize-observer.ts`       | `StubResizeObserver` — reports a fixed 1024 × 768 content rect on `observe`                        |
| `lib/render.tsx`                 | `renderWithProviders`, `TestProviders`, `createTestRouter`                                         |
| `lib/messages.ts`                | `TEST_LOCALE` (`en-US`) and `TEST_MESSAGES`, built from the real `messages/en-US/*.json` files     |
| `lib/server-function.ts`         | `withTestRpc` — drives server functions through their real middleware and validation pipeline      |
| `lib/auth-browser.ts`            | `openAuthBrowser(ip)`, a cookie-keeping `auth.handler` client, and `createPasswordCustomer`        |

### setup.ts

The `component` project's setup file does four things. It extends `expect` with the jest-dom matchers, stubs `IntersectionObserver`, `ResizeObserver` and `matchMedia` (which jsdom does not implement and which the GSAP and Lenis-driven components ask for), and then patches TanStack Start:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
```

It also replaces `getRequest` from `@tanstack/react-start/server` with a stub returning `new Request("http://127.0.0.1:3000/")`.

### Testing server functions

`withTestRpc` wraps the `createServerFn` builder in a proxy. It passes `inputValidator`, `middleware` and `validator` through untouched, and intercepts `.handler()` so the compiled server function is invoked through `runWithStartContext` with a synthetic start context and the real `__executeServer` entry point. The practical consequence is that a test calling a use case exercises its validators and its `assertAdmin` middleware for real — the authorization checks are not bypassed by the test harness, which is the whole point, since the use-case layer is where authorization lives.

### Testing components

`renderWithProviders` renders a component inside the same three providers the application uses — `IntlProvider` with the real English messages and `I18N.DEFAULT_TIMEZONE`, a `QueryClientProvider` with retries disabled, and a `RouterContextProvider` over a memory-history router — and returns the Testing Library result plus the `queryClient` and `router` it created, so a test can assert on cache state or navigation:

```ts
const { queryClient, router } = renderWithProviders(<ProductCard product={product} />)
```

`createTestRouter(path)` builds the memory router; pass a path when the component depends on the current location.

Messages are not fixtures. `lib/messages.ts` globs `messages/en-US/*.json` eagerly and feeds them through the application's own `buildMessageTree` and `toNamespace`, so a missing or renamed translation key fails a component test.

### Testing database code

There is no global D1 mock. Each integration test builds its own in-memory database and swaps out the Drizzle instance:

```ts
const { sqlite } = await vi.hoisted(async () => {
  const { DatabaseSync } = await import("node:sqlite")

  return { sqlite: new DatabaseSync(":memory:") }
})

vi.mock(import("~/src/integrations/drizzle-orm/drizzle.database"), async () => {
  const { drizzle } = await import("drizzle-orm/d1")
  const { createTestD1Database } = await import("~/src/platform/testing/mocks/d1")

  return { db: drizzle(createTestD1Database(sqlite)) }
})
```

`createTestD1Database` implements enough of the `D1Database` surface for Drizzle: `prepare`, `bind`, `all`, `raw`, `run` and `batch`. Like D1, `bind` refuses a statement with more than 100 bound parameters, and the database refuses a `LIKE` or `GLOB` pattern longer than 50 bytes, both of which local SQLite and Miniflare would accept, so a test with production-sized input catches a statement that would fail on D1. Multi-row inserts and rank updates are therefore chunked in `drizzle.batch.ts` and sent in one `db.batch`, and an id list built at runtime is bound as a single JSON parameter through `inJsonList`; [Drizzle ORM and D1](/docs/integrations/drizzle-orm-d1) describes both. `batch` runs one batch at a time, as D1 does, wraps the statements in `begin` / `commit` and rolls back on failure, which is what makes the checkout idempotency tests meaningful — D1's atomic batch is the constraint those tests rely on. The optional `onQuery` callback receives every `{ sql, params }` pair. `src/modules/product/__test__/product.accessors.integration.test.ts` collects them and asserts exactly how many statements a catalog read issues (`expect(queries).toHaveLength(3)`) and that no statement binds more than 100 parameters — that is how the N+1 and D1 parameter-limit regressions are caught.

The optional `onRoundTrip` callback counts requests rather than statements, because a batch of five statements costs D1 one round trip and five separate statements cost five. It receives a `TestD1RoundTrip`: `{ kind: "batch", sql }` once per `batch` call, with `sql` listing the statements' SQL in order, and `{ kind: "statement", sql: [sql] }` once per `all`, `raw` or `run` outside a batch, including a statement run on its own after a batch carried it. It fires when the request is issued, so a test that holds a promise of its own, such as a mocked dependency it has not resolved yet, can read the trips at that point to see which requests went out before it. It cannot show whether one database request waited for another: the mock answers every standalone statement at once, so `Promise.all` over two Drizzle selects and two selects awaited one after the other record the same two trips. Use it to count separate round trips, not to measure how deep they chain. `inventory-reservation.integration.test.ts` uses it to assert that a whole cart is reserved in one batch carrying both lines and that an empty input never reaches the database. `onQuery` still sees every statement, batched or not.

The tables themselves are created by the test with `sqlite.exec(...)`, matching the columns the migrations produce. The Vitest suites do not apply the migration files, so a schema change means updating both the migration and the `create table` statements in the tests that touch it. The end-to-end suite does apply the whole history to a fresh database on every run, which is what keeps it replayable.

Separately, every module has a `*.schema.test.ts` in the `node` project that reads the Drizzle table metadata with `getTableConfig` and asserts the table name, the full ordered column list, the foreign keys with their `onDelete` behaviour and the declared relations. Those tests are the reason a column rename cannot land silently.

## Coverage

```sh
bun run test:coverage
```

Provider `v8`, reporters `text`, `html` and `json-summary`, output in `coverage/`, which is cleaned on each run.

| Metric     | Threshold |
| ---------- | --------- |
| Statements | 100       |
| Lines      | 100       |
| Functions  | 100       |
| Branches   | 100       |

Every statement, branch, function and line is covered, so all four thresholds are 100 and any new code arrives with its tests. `thresholds.autoUpdate` is `false`.

Coverage includes `src/**/*.{ts,tsx}` and excludes tests, `__test__` folders, `*.d.ts`, `src/routeTree.gen.ts`, `src/integrations/**/migrations/**` (drizzle-kit introspection output, which lint and format ignore too), `src/presentation/components/shadcn/**` (vendored primitives) and `src/platform/testing/**`.

Cover real behaviour. If a branch cannot be reached, delete the branch rather than stubbing a global to reach it.

## End-to-end tests

Playwright drives the built Worker in Chromium and WebKit. The suite lives in `e2e/` and is configured in `playwright.config.ts`:

```sh
bun run test:e2e:install  # once: the Chromium and WebKit browsers
bun run test:e2e          # resets the test database, builds the test Worker, serves it and runs every spec
bun run test:e2e:pr       # the same on Chromium only, as CI runs it on pull requests
bun run test:e2e:smoke    # e2e/specs/smoke.spec.ts on Chromium
bun run test:e2e:stripe   # the stripe-test-mode project, which pays by card, BLIK and Przelewy24 through a Stripe sandbox when its keys are set
bun run test:e2e:ui       # Playwright UI mode
```

The `chromium` and `webkit` projects ignore every `e2e/specs/*stripe-test-mode.spec.ts`, which only the `stripe-test-mode` project runs, so the default suite never calls Stripe. See [Stripe test mode](#stripe-test-mode).

Outside CI, Playwright's `webServer` runs `db:reset:test`, `build:test` and `start:test` itself and reuses a server already listening on port 3000; in CI the workflow prepares the database and the build, and Playwright only starts the server.

### Projects

`playwright.config.ts` defines six projects:

| Project                                  | Runs                                                              | Depends on                           |
| ---------------------------------------- | ----------------------------------------------------------------- | ------------------------------------ |
| `setup`                                  | `*.setup.ts`, which signs in the seeded admin and customer        | —                                    |
| `chromium`, `webkit`                     | every `*.spec.ts` but `*stripe-test-mode.spec.ts`, fully parallel | `setup`                              |
| `stripe-test-mode`                       | `*stripe-test-mode.spec.ts`, against a Stripe sandbox             | —                                    |
| `chromium-shop-wide`, `webkit-shop-wide` | every `*.shop-wide.ts`                                            | `chromium` and `webkit` respectively |

A shop-wide spec changes state that every other spec reads, such as the sales switch, so it must never run beside them. Playwright runs projects in phases and starts a phase only once the previous one has finished, so a shop-wide project starts after every browser suite in the run, not only its own. Its tests also take the `shop-wide` lock, which keeps the Chromium and WebKit shop-wide projects, which share a phase, from running at the same time. Selecting a shop-wide project always runs its browser project in full first, because Playwright runs a project's dependencies whatever the file filter. `bun run test:e2e` runs all six projects, `test:e2e:pr` selects `chromium` and `chromium-shop-wide`, and `e2e-reusable.yml` selects `<browser>` and `<browser>-shop-wide` (see [CI/CD](/docs/tooling/ci-cd#the-end-to-end-workflows)).

### The test Worker

`wrangler.jsonc` has a `test` environment whose `main` is `src/platform/testing/worker.ts` and whose D1, KV, R2, Durable Object and audit queue are all local (`remote: false`), persisted under `.wrangler/test`. `bun run build:test` builds it with `CLOUDFLARE_ENV=test` and `--mode test`, so every secret comes from the committed `.env.test`. The shop's new-order notice goes to its `RESEND_EMAIL_FROM`, `noreply@example.test`, which is `ORDER_NOTIFICATION_INBOX` in `e2e/data/accounts.ts`, so every order a spec places also sends the notice there, and the shop's incident alerts go there too.

The test Worker installs `src/platform/testing/mocks/providers.ts` before it loads the application, so nothing leaves the machine:

- **Resend.** Requests to `api.resend.com` are captured instead of sent, single sends and the newsletter's batch sends alike, with each email's headers. `GET /__test/emails?to=<address>` returns the captured messages for a recipient. `POST /__test/emails/refusals?to=<address>` makes the emulator answer every single send to that address with Resend's `internal_server_error` until `DELETE` on the same address ends it, which `refuseEmailsTo` and `acceptEmailsTo` in `e2e/fixtures/emails.ts` wrap. Like Resend, it answers a send whose `Idempotency-Key` it has already captured with the first email's id and captures nothing new. A newsletter spec sends to every confirmed subscriber in the shared test database, so it asserts only on the addresses it subscribed itself.
- **Stripe.** Requests to `api.stripe.com` made with the `.env.test` key, `sk_test_local_fixture`, reach an in-memory emulator of the calls the server makes: Checkout Sessions (create, retrieve, list, expire), coupons, customers (create, update, which changes the email that later sessions for the customer carry, and delete, which detaches their payment methods), payment intents, payment methods (list by customer, retrieve, detach), setup intents and refunds (create, and list by payment intent, which returns the refunds it created). Any other Stripe call answers 400, so new Stripe usage fails a spec instead of passing silently. Like Stripe, it refuses a Checkout Session whose `expires_at` is less than 30 minutes or more than 24 hours away, and it keeps `created` and `expires_at` on the session so a spec can check the hold. A retrieve that asks to expand `payment_intent` gets the session's payment intent inline, as Stripe returns it. `GET /__test/stripe/checkout-sessions?email=<address>` lists the sessions opened for a shopper, which `openCheckoutSessions` in `e2e/fixtures/stripe.ts` narrows to the open ones, and `POST /__test/stripe/checkout-sessions/<id>/complete` marks one paid and returns a `checkout.session.completed` event signed with `STRIPE_WEBHOOK_SECRET`. `POST /__test/stripe/checkout-sessions/<id>/expire` expires one the same way and returns a signed `checkout.session.expired` event, which `expireCheckoutSession` in `e2e/fixtures/stripe.ts` delivers to the webhook. `POST /__test/stripe/checkout-sessions/<id>/dispute` returns a signed `charge.dispute.created` event, a fraud dispute that needs a response, for the payment intent of a paid session, and `disputeCheckoutPayment` in `e2e/fixtures/stripe.ts` delivers it, so the order is flagged as disputed through the real webhook. `POST /__test/stripe/checkout-sessions/<id>/await-blik-approval` gives a session a BLIK payment intent waiting for approval in the banking app (`requires_action` with `blik_authorize`), and `POST /__test/stripe/checkout-sessions/<id>/decline-blik-approval` has the bank decline it (`requires_payment_method`); `awaitBlikApproval` and `declineBlikApproval` in `e2e/fixtures/stripe.ts` call them, so a spec can reload the checkout while the bank is still deciding. `GET /__test/stripe/setup-intents?email=<address>` lists the card setup intents opened from the account page, and `POST /__test/stripe/setup-intents/<id>/succeed` stands in for the browser's `stripe.confirmSetup`: it attaches a Visa ending 4242 to the customer and marks the intent succeeded. `GET /__test/stripe/customers?email=<address>` lists the customers that still exist for a shopper, which `stripeCustomerIds` in `e2e/fixtures/stripe.ts` reads to check that deleting an account deleted its Stripe customer.
- **InPost ShipX.** Requests to `sandbox-api-shipx-pl.easypack24.net`, the API every environment but production calls, reach an in-memory emulator: creating a shipment answers `created` without a tracking number, the first read of it confirms it and assigns a tracking number starting `6026772171316303`, and its label is a small PDF once it is confirmed and a 400 before. `.env.test` sets dummy `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID`, so the admin order page offers InPost shipments in the test build.
- **InPost points.** The server's point lookups on `api-pl-points.easypack24.net` (`/v1/points/<name>`) are answered by `emulateInpostPoints` in `src/platform/testing/mocks/inpost-points.ts`: `WAW01M` and `WAW02M`, the lockers the browser's point search offers, are listed, `WAW503` answers 503 as if InPost were down, and any other name answers 404. `INPOST_POINTS` in `e2e/data/inpost.ts` names a listed, an unanswered and an unlisted point, and `lockerCheckoutDraft` in `e2e/fixtures/checkout-draft.ts` builds a saved checkout that names one of them for the parcel-locker method.

A spec posts that signed event to `/api/webhooks/stripe` like Stripe would, so the webhook route verifies the signature, accepts the event's `livemode: false` as the `test` environment requires, and fulfils the order through the real code. `completeCheckoutSessionBeforeItsWebhook` in `e2e/fixtures/stripe.ts` marks the session paid and returns the signed event without posting it, and `deliverStripeEvent` posts it later, so a spec can reload the checkout while Stripe already reports the session `complete` and the order does not exist yet. The return page then places the order itself, so the spec that reloads before the webhook expects the order and its confirmation email before it delivers the event, and still one confirmation email after it. The payment form itself, Stripe.js with its card, BLIK and Przelewy24 flows, is exercised only by the [Stripe test mode](#stripe-test-mode) project.

InPost is called from the browser, not the Worker: the locker picker asks `api-pl-points.easypack24.net/v1/points?city=<city>` for the points in a city. The network isolation in `e2e/fixtures/test.ts` answers that search through `e2e/fixtures/inpost.ts` with the lockers in `e2e/data/inpost.ts` whose city matches, in InPost's response shape, so the picker lists them and a spec can choose one. The map's style and tiles stay blocked, so a spec chooses a locker from the list beside the map, not from a marker.

### Stripe test mode

Four specs pay in the real Payment Element against a Stripe sandbox. Each test is a guest (or, once, a new account) with its own e-mail and its own Checkout Session, so the tests run in parallel and do not depend on one another. They run only when `STRIPE_SECRET_KEY` (`sk_test_` or `rk_test_`) and `VITE_STRIPE_PUBLISHABLE_KEY` (`pk_test_`) are set in the environment to keys other than the dummies in `.env.test`; otherwise Playwright reports them skipped with that reason.

| Spec                                  | What it pays and expects                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stripe-test-mode.spec.ts`            | Stripe's test card 4242 4242 4242 4242 as a guest, and as a signed-in shopper who types another e-mail at checkout.                                                                                                                                                                                                                                                                                                                                                                                        |
| `card.stripe-test-mode.spec.ts`       | The decline cards 4000 0000 0000 0002 (generic decline), …9995 (insufficient funds), …0069 (expired) and …0127 (incorrect CVC), each followed by 4242 on the same session; an incomplete card number; and the 3D Secure card 4000 0027 6000 3184, whose challenge is completed (the charge reports `three_d_secure.result` `authenticated`), failed, or closed with **Cancel**.                                                                                                                            |
| `blik.stripe-test-mode.spec.ts`       | The BLIK code 123456, which the sandbox approves after about ten seconds, and three of the failures Stripe simulates from the contact e-mail: `invalid_code` (refused at once), `customer_declined` (after about eight seconds, then paid by card on the same session) and `customer_timeout` (once the approval window ends). `stripeOutcomeEmail` in `e2e/fixtures/unique.ts` builds an address whose local part ends in the outcome, as Stripe's patterns (`.*customer_declined@.*` and so on) require. |
| `przelewy24.stripe-test-mode.spec.ts` | Przelewy24 with mBank chosen in the bank list, answered on Stripe's test payment page with **Authorize test payment** or **Fail test payment**.                                                                                                                                                                                                                                                                                                                                                            |

Every refused payment must leave the shopper on the payment step with Stripe's own message as a notice, never the shop's "This payment session is no longer active." notice, and `expectPaymentRefusedOnSession` in `e2e/fixtures/stripe-test-mode.ts` checks the same session is still held (the `marte-checkout-session` entry in local storage), the basket is still in the summary, the pay button is back instead of **Processing…**, and Stripe reports the session `open` with a `requires_payment_method` payment whose `last_payment_error` carries the documented code. After a card decline the Payment Element marks the card number with Stripe's reason and keeps the pay button disabled until the shopper changes the card, which is Stripe's behaviour, so the specs pay again by typing 4242 over it. In the card, BLIK and Przelewy24 specs every payment that goes through, including the one made with another card after a refusal, ends in `expectOrderPaidOnSession`: the confirmation page for that same session with an order number. A failed Przelewy24 payment returns from the bank to the payment step with "Your payment was not completed. Choose a payment method to try again." and the basket; the step then replaces the returned session, which Stripe reports `expired`, with an open one for the same checkout, and the spec pays that one by card and expects a single confirmation e-mail.

`CheckoutPage` in `e2e/pages/checkout-page.ts` drives Stripe's frames: `fillCard` and `fillBlikCode` fill the Payment Element, `answerThreeDSecure` presses **Complete** or **Fail** on Stripe's 3D Secure test page inside the challenge frame and `cancelThreeDSecure` presses the challenge's **Cancel**, each once the test page has stopped moving and again if the button is still there after ten seconds, because a press while Stripe is still opening the challenge does nothing, and `payWithPrzelewy24` picks the bank before paying, because the pay button stays disabled until a bank is chosen.

The same two variables must be set when the test Worker is built. The build prefers the process environment to `.env.test`, so the client bundle gets the publishable key and the Worker the secret key, and the Stripe emulator, which answers only `sk_test_local_fixture`, lets the Worker's calls through to Stripe. Email is still captured. Each spec sets `test.use({ reachableOrigins: [STRIPE_ORIGINS] })`, so the browser may load Stripe.js and its frames from `stripe.com`, `stripe.network` and `stripecdn.com`, and follow Przelewy24's redirect through `payments.stripe.com` and `checkout.stripe.com` back to the shop.

Stripe cannot reach a Worker on `127.0.0.1`, so `forwardCheckoutCompletion` in `e2e/fixtures/stripe-test-mode.ts` does what `stripe listen` would: it reads the session's `checkout.session.completed` event from Stripe's Events API, signs it with the `STRIPE_WEBHOOK_SECRET` the Worker was built with (the environment's, else `.env.test`'s) and posts it to `/api/webhooks/stripe`. The card, BLIK and Przelewy24 specs that check the whole purchase expect the confirmation page with an order number and the confirmation email, which names the payment method, before they forward anything, because the return page places the order once Stripe reports the session paid. They then forward the event, expect Stripe to report the session paid for PLN 398.99, and after a reload still one order and one confirmation email.

The signed-in spec registers an account and reaches the payment step under the account's email, which creates the account's Stripe customer with it. It then edits the contact step to another email, waits for the replacement session and pays it by card. It expects the confirmation page to name the new email and the confirmation email to reach it, the forwarded session to belong to a Stripe customer and report the new email as `customer_details.email`, and no confirmation email at the account's address. Without the update in `ensureStripeCustomerWithEmail`, Stripe would bill that payment under the account's address.

Use the keys of a Stripe sandbox with no webhook endpoint, and with Cards, BLIK and Przelewy24 turned on under its payment method settings: the Checkout Sessions use dynamic payment methods, so a method the sandbox has turned off is missing from the Payment Element and its specs fail. An endpoint pointing at the preview Worker would receive these payments too, but it only logs and acknowledges their events, because their `deployment` metadata names `martebizuteria-test` (see [Payments: The webhook endpoint](/docs/features/payments#the-webhook-endpoint)); a separate sandbox keeps the test payments out of preview's account and its event log. Locally, stop any server on port 3000 first, because Playwright reuses one outside CI and an earlier build carries the dummy keys, and set the keys for this command only:

```sh
STRIPE_SECRET_KEY=sk_test_… VITE_STRIPE_PUBLISHABLE_KEY=pk_test_… bun run test:e2e:stripe
```

A test Worker built with them sends every Stripe call to Stripe, so the other specs, which settle payments through the emulator, fail against it. In CI, `e2e-full.yml` runs the project with the `E2E_STRIPE_SECRET_KEY` and `E2E_STRIPE_PUBLISHABLE_KEY` repository secrets; see [CI/CD](/docs/tooling/ci-cd#the-end-to-end-workflows).

### Data

`bun run db:reset:test` deletes `.wrangler/test`, applies the whole migration history with `wrangler d1 migrations apply --local`, and runs `scripts/seed-test.ts`. The seed loads the same catalog files as `db:seed:preview` (two necklaces with stock, categories, collections, attributes and delivery methods) and three verified accounts from `e2e/data/accounts.ts`: `admin@marte.example.test`, `new-admin@marte.example.test` and `customer@marte.example.test`. The first admin has two-factor authentication on: the seed stores `ADMIN_TOTP_SECRET` in `two_factor`, encrypted with the `AUTH_SECRET` from `.env.test` as the test Worker expects. `new-admin@marte.example.test` has it off, so a spec can show that such an admin is sent to `/admin/security`. The customer has `Europe/Warsaw` saved as their time zone, so the profile's time zone list opens on a saved choice rather than on Automatic.

### Writing specs

- Import `test` and `expect` from `e2e/fixtures/test.ts`. Its automatic fixtures block every request that does not go to the local app (images get a 1×1 PNG, an InPost point search gets the lockers in `e2e/data/inpost.ts`, everything else is aborted) and fail a test whose pages log a missing or malformed translation. A spec that must reach another origin lists it in the `reachableOrigins` option; only the Stripe test-mode spec does.
- Each test sends its own `cf-connecting-ip`, so the per-IP rate limits on sign-in, sign-up and checkout never couple tests together.
- The `setup` project signs the seeded admin and customer in once and stores their sessions in `playwright/.auth/`; use them with `test.use({ storageState: STORAGE_STATE.admin })`. The admin answers the two-factor challenge with `currentTotpCode(ADMIN_TOTP_SECRET)` from `e2e/fixtures/totp.ts`, through `AuthPage.enterTwoFactorCode`. Never sign out, change the password or turn off two-factor authentication of a seeded account in a spec, because every worker shares those sessions, and never turn it on for `new-admin@marte.example.test`, whose spec expects it off.
- A spec that changes an account, an order or a coupon creates its own: `registerCustomer` signs up and verifies a new customer, `uniqueEmail` and `uniqueCode` name the data, and `placeOrder` buys a product and pays for it through the emulator. Specs run fully parallel and must not depend on counts other specs can change.
- A spec that changes something every other spec reads, such as the sales switch, would break the specs running beside it, so it goes in a `*.shop-wide.ts` file instead of a `*.spec.ts` one and wraps its tests in `test.describe(title, { lock: "shop-wide" }, …)` (see [Projects](#projects)). There are two. In `e2e/specs/sales.shop-wide.ts` the admin pauses sales on the dashboard with `setSalesPaused` on `AdminDashboardPage`, and a signed-in customer in a second browser context sees the notice appear on an open product page without a reload, then on the account overview, the documentation, the checkout, which shows "Orders are paused", and the cart, which says checkout is closed and has no checkout link. Once the admin reopens sales the notice leaves the open cart, the checkout link comes back and leads to the contact step, and the account and documentation pages load without the notice. An `afterEach` turns the switch off again, so a failed run does not leave the shop paused for the next one. In `e2e/specs/delivery.shop-wide.ts` the admin adds a courier method with a new carrier under Settings → Delivery, a guest shopper in a second browser context picks it at its price in the checkout, and archiving it takes it out of that checkout; then the admin offers free delivery from 1 zł, and the shopper's courier options and summary read Free. Its `afterEach` archives the test method and turns free delivery off again.
- Wait for state with web-first assertions and `expect.poll`, never fixed timeouts. A click that lands before React has hydrated the page is dropped without sending a request, so page objects in `e2e/pages/` wait for hydration: open and reload pages through them (`open`, `reload`), and call `waitForAppReady()` after any `page.goto` a spec makes itself, before it interacts with the page.
- A spec that counts requests first calls `muteRealtime(context)` from `e2e/fixtures/test.ts`. It routes the `/api/realtime/` sockets to a Playwright mock that never connects to the server, so the page's socket stays open and silent and a change another worker makes cannot trigger a refetch. `recordServerFunctionCalls(page)` from `e2e/fixtures/server-functions.ts` then lists the server functions a document called, matched by their request's referer. A built server function is addressed by a SHA-256 of its file and export, so `SERVER_FUNCTIONS` names the ones specs look for. The cart spec uses both to show that a full load of `/en-US/cart` calls only `checkCartAvailability` and `getCurrentSession`. It first expects `checkCartAvailability` among the recorded calls, so a recorder that saw nothing fails instead of passing. It then opens the full-screen menu at a width where the showcase is shown and expects the new-arrivals picture from the collections the page brought, still without a `getCollections` call.
- Any refetch of an admin list shows skeleton rows in place of its rows, which closes a row menu that is open. The admin spec that reads the Cancel order item of a disputed order's row menu therefore calls `muteRealtime(context)`, so an order another worker places cannot refetch the list, and waits for the `getAdminOrdersPage` response of its search before it opens the menu.
- The checkout spec in which a guest approves a payment in the banking app counts availability checks on a page whose realtime socket follows only the delivery methods and the free delivery threshold, which only the `*.shop-wide.ts` specs change, so it needs no `muteRealtime`. `recordServerFunctionRequests(page, id)` from `e2e/fixtures/server-functions.ts` keeps every request to one server function, so the spec can wait for the check that carries the held session id and for every answer before it counts. `leaveTab()` and `returnToTab()` on `BasePage` stand in for switching apps: they take the browser context offline and back, and report the document hidden and then visible with a `visibilitychange` event, which is what TanStack Query's focus and online managers listen for. The spec pays the session through the emulator while the tab is away and expects no further check before the confirmation.
- The checkout specs in which a paid session comes back, by a reload, a reload before the webhook or a second tab, record the requests to `createCheckoutSession`, `updateCheckoutSession` and `checkCartAvailability` from `SERVER_FUNCTIONS` after paying and expect none, together with the confirmation and no open session left, so no second payment form was opened. They first wait for the payment step's intro, which renders once the session is stored. The spec that returns from the bank without paying opens `?success=true&session_id=<id>` for an open session and expects `?step=4`, the toast, the basket and one open session continuing the same checkout.
- Four more checkout specs cover what happens after that check. `runBeforeServerFunction(page, id, run)` from `e2e/fixtures/server-functions.ts` holds the next request to one server function until `run` has finished, so the spec in which the payment completes while the reloaded checkout continues its session pays it through the emulator just as `updateCheckoutSession` is sent, after the session check found it open, and expects the confirmation, the order, no `createCheckoutSession` request and no open session. The spec in which a guest paid in the banking app and later checks out another basket adds a second piece, expects the checkout with both pieces instead of the old confirmation, and a fresh checkout with its own `checkoutId` for the whole basket. The spec in which a guest reopens an old order confirmation pays, sees the confirmation empty the basket, adds another piece and opens the same `?success=true&session_id=<id>` address again, then expects the order and a basket that still holds the new piece. The spec for a signed-in customer whose bank returns them to a browser where they are not signed in opens the return address in a new browser context with no cookies or storage, as the admin spec does for its shoppers, and expects the confirmation and the order rather than the not-completed toast.
- The checkout limit spec opens checkouts for one email from three browser contexts with their own `cf-connecting-ip`, as the admin spec does for its shoppers, and expects a fourth to be refused with the open-checkout toast and no fourth session. The cart spec raises a line to ten and expects the plus button disabled and the limit note.
- The limits on emails visitors can request have their own spec. The newsletter spec signs one address up from four browser contexts with their own `cf-connecting-ip`, so the three-a-minute limit per IP does not interfere, expects the "check your inbox" answer every time, and finds three confirmation emails for the address with `sentEmails` from `e2e/fixtures/emails.ts`. One browser's run of the whole suite asks for about fifteen of these emails, so a test server reused across several runs needs `bun run db:reset:test` before it reaches the shop's limit of 50 a day.
- Two checkout specs reload the payment step while a BLIK payment waits for approval in the banking app. They start it with `awaitBlikApproval` and expect the waiting-for-the-bank state instead of the payment form, with the same session still the only open one. One pays the session through the emulator while the tab is away and expects the confirmation with the order and no `createCheckoutSession` request; the other has the bank decline it with `declineBlikApproval` and expects the not-completed toast, the payment step and one open session continuing the same checkout. Both come back with `returnToTab()`, which makes the waiting step ask again at once instead of at its next eight-second poll.
- A spec about realtime invalidation keeps the sockets live and makes its own event, for example by placing an order, because checkout publishes the product catalogue to the admin hub. Events from other workers can arrive at any moment, so it asserts only what they cannot change. The admin spec opens two admin tabs in one browser with a listener on the `marte-query-invalidation` channel, added with `context.addInitScript`, waits with `waitForServerFunctionResponse(page, id)` from `e2e/fixtures/server-functions.ts` until each tab has refetched the product list, and expects the listener to have received nothing, so the tabs do not echo hub events to each other. Another browser context cannot post on that channel, so other workers cannot change the result. The spec does not count the product list requests: a second event that arrives while a refetch is in flight restarts it, so the count depends on other workers.
- The parcel-locker checkout chooses its locker as a shopper does: `chooseParcelLocker(locker)` on `CheckoutPage` picks the Parcel Locker option, opens the map, searches the locker's city and clicks the locker in the list, then continues to payment. The spec expects the locker in the delivery step's summary and a PLN 393.99 session, pays it through the emulator, and expects `Paczkomat InPost` at PLN 14.99 on the confirmation page and `Paczkomat InPost · <locker>` in the confirmation email.
- The Polish checkout in `e2e/specs/locales.spec.ts` buys at `/checkout`, the default locale without a prefix, filling every step through its Polish labels. It expects a session with `locale` `pl-PL` and a return address without `/en-US`, the confirmation page in Polish with the total as `398,99 zł`, and the email `Potwierdzenie zamówienia — M'Arte` naming the Polish product and linking to it without a prefix.
- The landing page keeps each section hidden until it scrolls into view, so a spec reaches one the way a visitor does: `scrollUntilVisible(locator)` on the page object turns the mouse wheel until the element is visible.
- The smoke spec opens the home, product, sign-in and documentation pages with a `securitypolicyviolation` listener added by `page.addInitScript`, waits for hydration, checks that the page's `csp-nonce` meta is the nonce its `Content-Security-Policy` allows, and expects the browser to have refused nothing but Zod's `eval` probe. The policy is enforced before a request reaches the network, so the automatic blocking of outside requests does not hide a refusal. A page that starts loading a new third-party script, frame, image host or API fails it until the host is added to `src/lib/security-headers.ts`. Another smoke test reads the headers of a page and of `/favicon.svg`, which `public/_headers` serves.
- Read an email with `waitForEmail` and take a link from it with `linkIn`. Check the link's origin as well as its path: the checkout, admin and newsletter specs assert that the order confirmation, the shipping email, the shop's new-order notice and the newsletter confirmation all link to `http://127.0.0.1:3000`, the address the suite uses, the admin spec follows the notice's link to the order and the newsletter spec follows its link to the confirmed page. The admin spec that resends an order confirmation refuses its shopper's address before the order is placed, waits up to 30 seconds for "Email failed" while the retries run, accepts the address again and expects exactly one confirmation after **Resend email**.

## Conventions

- One `__test__/` folder per feature, beside the code: `src/modules/order/__test__/order.accessors.integration.test.ts`.
- Database suites end in `*.integration.test.ts`; anything rendering React ends in `*.component.test.tsx`; everything else is a plain `*.test.ts`.
- Mock external providers. Stripe, Resend, InPost and R2 are never called from a test; the end-to-end suite talks to the emulators in the test Worker and the InPost double in the browser instead. The one exception is the opt-in [Stripe test mode](#stripe-test-mode) project, which calls Stripe only when its keys are set.
- Fixtures are local to the test file or the feature's `__test__` folder. Shared infrastructure — and only infrastructure — belongs in `src/platform/testing/`.
