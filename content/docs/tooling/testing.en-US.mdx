Vite+ runs Vitest 5 with the configuration in the `test` block of `vite.config.ts`. Tests live in a `__test__` folder next to the code they cover and import their API from `vite-plus/test`, never from `vitest`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"
```

Run them with `bun run test`, not `bun test`. Bun's own runner ignores the Vitest projects, the jsdom environment and the setup file, so a large part of the suite would silently fail or be skipped.

## The three projects

The suite is split by filename, and each split gets its own environment.

| Project       | Files                                                         | Environment | Setup file                      |
| ------------- | ------------------------------------------------------------- | ----------- | ------------------------------- |
| `node`        | `src/**/*.{test,spec}.{ts,tsx}` except the two patterns below | `node`      | none                            |
| `integration` | `src/**/*.integration.test.{ts,tsx}`                          | `node`      | none                            |
| `component`   | `src/**/*.component.test.{ts,tsx}`                            | `jsdom`     | `src/platform/testing/setup.ts` |

```sh
bun run test              # vp test run — all three projects
bun run test:unit         # vp test run --project node
bun run test:integration  # vp test run --project integration
bun run test:component    # vp test run --project component
bun run test:changed      # vp test run --changed
bun run test:coverage     # vp test run --coverage
```

At the time of writing the repository holds roughly 890 test files: about 515 component tests, 35 integration tests and the rest unit tests in the `node` project.

> `bun run test:watch` maps to `vp test` with no subcommand. Per `vp test --help`, `vp test` "runs tests once by default" and watch mode is the separate `vp test watch` subcommand, so this script is a second single-shot run rather than a watcher. Use `vp test watch` (or `vp test --watch`) when you want watch mode.

## Shared test configuration

Everything the projects have in common lives in the top-level `test` block and is inherited through `extends: true`:

| Setting           | Value                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| `environment`     | `"node"` (the `component` project overrides it to `"jsdom"`)                                                      |
| `env`             | `loadEnv("test", import.meta.dirname, "")` — loads `.env.test`, which is committed and contains dummy values only |
| `pool`            | `"threads"`                                                                                                       |
| `maxWorkers`      | `"50%"`                                                                                                           |
| `isolate`         | `true`                                                                                                            |
| `passWithNoTests` | `false`                                                                                                           |
| `exclude`         | `node_modules/**`, `opensrc/**`, `dist/**`, `scripts/**`, `e2e/**`, `src/integrations/drizzle-orm/migrations/**`  |

Because `test.env` loads `.env.test`, no test needs real credentials. `scripts/` is excluded from the suite, so `scripts/commit-msg.ts`, `scripts/verify-build.ts` and friends are not covered by tests.

## The test platform

`src/platform/testing/` holds the shared infrastructure. Everything else is colocated with the code it exercises.

| File                             | What it provides                                                                                   |
| -------------------------------- | -------------------------------------------------------------------------------------------------- |
| `setup.ts`                       | jest-dom matchers, DOM observer stubs, `matchMedia`, and the `createServerFn` proxy                |
| `vitest-env.d.ts`                | `vite-plus/test/globals` reference and the jest-dom matcher types on Vitest's `Matchers` interface |
| `mocks/d1.ts`                    | `createTestD1Database(sqlite, onQuery?, onRoundTrip?)` — a `D1Database` backed by `node:sqlite`    |
| `mocks/migrations.ts`            | `applyMigration` for one migration and `applyMigrationHistory` to build the production schema      |
| `mocks/intersection-observer.ts` | `StubIntersectionObserver` — no-op `observe`, `unobserve`, `disconnect`, `takeRecords`             |
| `mocks/resize-observer.ts`       | `StubResizeObserver` — reports a fixed 1024 × 768 content rect on `observe`                        |
| `lib/render.tsx`                 | `renderWithProviders`, `TestProviders`, `createTestRouter`                                         |
| `lib/messages.ts`                | `TEST_LOCALE` (`en-US`) and `TEST_MESSAGES`, built from the real `messages/en-US/*.json` files     |
| `lib/server-function.ts`         | `withTestRpc` — drives server functions through their real middleware and validation pipeline      |
| `lib/auth-browser.ts`            | `openAuthBrowser(ip)`, a cookie-keeping `auth.handler` client, and `createPasswordCustomer`        |

### setup.ts

The `component` project's setup file does four things. It extends `expect` with the jest-dom matchers, stubs `IntersectionObserver`, `ResizeObserver` and `matchMedia` (which jsdom does not implement and which the GSAP and Lenis-driven components ask for), and then patches TanStack Start:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
```

It also replaces `getRequest` from `@tanstack/react-start/server` with a stub returning `new Request("http://127.0.0.1:3000/")`.

### Testing server functions

`withTestRpc` wraps the `createServerFn` builder in a proxy. It passes `inputValidator`, `middleware` and `validator` through untouched, and intercepts `.handler()` so the compiled server function is invoked through `runWithStartContext` with a synthetic start context and the real `__executeServer` entry point. The practical consequence is that a test calling a use case exercises its validators and its `assertAdmin` middleware for real — the authorization checks are not bypassed by the test harness, which is the whole point, since the use-case layer is where authorization lives.

### Testing components

`renderWithProviders` renders a component inside the same three providers the application uses — `IntlProvider` with the real English messages and `I18N.DEFAULT_TIMEZONE`, a `QueryClientProvider` with retries disabled, and a `RouterContextProvider` over a memory-history router — and returns the Testing Library result plus the `queryClient` and `router` it created, so a test can assert on cache state or navigation:

```ts
const { queryClient, router } = renderWithProviders(<ProductCard product={product} />)
```

`createTestRouter(path)` builds the memory router; pass a path when the component depends on the current location.

Messages are not fixtures. `lib/messages.ts` globs `messages/en-US/*.json` eagerly and feeds them through the application's own `buildMessageTree` and `toNamespace`, so a missing or renamed translation key fails a component test.

### Testing database code

There is no global D1 mock. Each integration test builds its own in-memory database and swaps out the Drizzle instance:

```ts
const { sqlite } = await vi.hoisted(async () => {
  const { DatabaseSync } = await import("node:sqlite")

  return { sqlite: new DatabaseSync(":memory:") }
})

vi.mock(import("~/src/integrations/drizzle-orm/drizzle.database"), async () => {
  const { drizzle } = await import("drizzle-orm/d1")
  const { createTestD1Database } = await import("~/src/platform/testing/mocks/d1")

  return { db: drizzle(createTestD1Database(sqlite)) }
})
```

`createTestD1Database` implements enough of the `D1Database` surface for Drizzle: `prepare`, `bind`, `all`, `raw`, `run` and `batch`. Like D1, `bind` refuses a statement with more than 100 bound parameters, which local SQLite and Miniflare would accept, so a test with production-sized input catches a statement that would fail on D1. Multi-row inserts and rank updates are therefore chunked in `drizzle.batch.ts` and sent in one `db.batch`, and an id list built at runtime is bound as a single JSON parameter through `inJsonList`; [Drizzle ORM and D1](/docs/integrations/drizzle-orm-d1) describes both. `batch` runs one batch at a time, as D1 does, wraps the statements in `begin` / `commit` and rolls back on failure, which is what makes the checkout idempotency tests meaningful — D1's atomic batch is the constraint those tests rely on. The optional `onQuery` callback receives every `{ sql, params }` pair. `src/modules/product/__test__/product.accessors.integration.test.ts` collects them and asserts exactly how many statements a catalog read issues (`expect(queries).toHaveLength(3)`) and that no statement binds more than 100 parameters — that is how the N+1 and D1 parameter-limit regressions are caught.

The optional `onRoundTrip` callback counts requests rather than statements, because a batch of five statements costs D1 one round trip and five separate statements cost five. It receives a `TestD1RoundTrip`: `{ kind: "batch", sql }` once per `batch` call, with `sql` listing the statements' SQL in order, and `{ kind: "statement", sql: [sql] }` once per `all`, `raw` or `run` outside a batch, including a statement run on its own after a batch carried it. It fires when the request is issued, so a test that holds a promise of its own, such as a mocked dependency it has not resolved yet, can read the trips at that point to see which requests went out before it. It cannot show whether one database request waited for another: the mock answers every standalone statement at once, so `Promise.all` over two Drizzle selects and two selects awaited one after the other record the same two trips. Use it to count separate round trips, not to measure how deep they chain. `inventory-reservation.integration.test.ts` uses it to assert that a whole cart is reserved in one batch carrying both lines and that an empty input never reaches the database. `onQuery` still sees every statement, batched or not.

The tables themselves are created by the test with `sqlite.exec(...)`, matching the columns the migrations produce. The Vitest suites do not apply the migration files, so a schema change means updating both the migration and the `create table` statements in the tests that touch it. The end-to-end suite does apply the whole history to a fresh database on every run, which is what keeps it replayable.

Separately, every module has a `*.schema.test.ts` in the `node` project that reads the Drizzle table metadata with `getTableConfig` and asserts the table name, the full ordered column list, the foreign keys with their `onDelete` behaviour and the declared relations. Those tests are the reason a column rename cannot land silently.

## Coverage

```sh
bun run test:coverage
```

Provider `v8`, reporters `text`, `html` and `json-summary`, output in `coverage/`, which is cleaned on each run.

| Metric     | Threshold |
| ---------- | --------- |
| Statements | 100       |
| Lines      | 100       |
| Functions  | 100       |
| Branches   | 100       |

Every statement, branch, function and line is covered, so all four thresholds are 100 and any new code arrives with its tests. `thresholds.autoUpdate` is `false`.

Coverage includes `src/**/*.{ts,tsx}` and excludes tests, `__test__` folders, `*.d.ts`, `src/routeTree.gen.ts`, `src/integrations/**/migrations/**` (drizzle-kit introspection output, which lint and format ignore too), `src/presentation/components/shadcn/**` (vendored primitives) and `src/platform/testing/**`.

Cover real behaviour. If a branch cannot be reached, delete the branch rather than stubbing a global to reach it.

## End-to-end tests

Playwright drives the built Worker in Chromium and WebKit. The suite lives in `e2e/` and is configured in `playwright.config.ts`:

```sh
bun run test:e2e:install  # once: the Chromium and WebKit browsers
bun run test:e2e          # resets the test database, builds the test Worker, serves it and runs every spec
bun run test:e2e:pr       # the same on Chromium only, as CI runs it on pull requests
bun run test:e2e:smoke    # e2e/specs/smoke.spec.ts on Chromium
bun run test:e2e:ui       # Playwright UI mode
```

Outside CI, Playwright's `webServer` runs `db:reset:test`, `build:test` and `start:test` itself and reuses a server already listening on port 3000; in CI the workflow prepares the database and the build, and Playwright only starts the server.

### The test Worker

`wrangler.jsonc` has a `test` environment whose `main` is `src/platform/testing/worker.ts` and whose D1, KV, R2, Durable Object and audit queue are all local (`remote: false`), persisted under `.wrangler/test`. `bun run build:test` builds it with `CLOUDFLARE_ENV=test` and `--mode test`, so every secret comes from the committed `.env.test`.

The test Worker installs `src/platform/testing/mocks/providers.ts` before it loads the application, so nothing leaves the machine:

- **Resend.** Requests to `api.resend.com` are captured instead of sent. `GET /__test/emails?to=<address>` returns the captured messages for a recipient.
- **Stripe.** Requests to `api.stripe.com` reach an in-memory emulator of the calls the server makes: Checkout Sessions (create, retrieve, list, expire), coupons, customers, payment intents, payment methods (list by customer, retrieve, detach), setup intents and refunds. Any other Stripe call answers 400, so new Stripe usage fails a spec instead of passing silently. `GET /__test/stripe/checkout-sessions?email=<address>` lists the sessions opened for a shopper, and `POST /__test/stripe/checkout-sessions/<id>/complete` marks one paid and returns a `checkout.session.completed` event signed with `STRIPE_WEBHOOK_SECRET`. `GET /__test/stripe/setup-intents?email=<address>` lists the card setup intents opened from the account page, and `POST /__test/stripe/setup-intents/<id>/succeed` stands in for the browser's `stripe.confirmSetup`: it attaches a Visa ending 4242 to the customer and marks the intent succeeded.

A spec posts that signed event to `/api/webhooks/stripe` like Stripe would, so the webhook route verifies the signature and fulfils the order through the real code. Only the card form itself, Stripe.js, is not exercised.

### Data

`bun run db:reset:test` deletes `.wrangler/test`, applies the whole migration history with `wrangler d1 migrations apply --local`, and runs `scripts/seed-test.ts`. The seed loads the same catalog files as `db:seed:preview` (two necklaces with stock, categories, collections, attributes and delivery methods) and two verified accounts from `e2e/data/accounts.ts`: `admin@marte.example.test` and `customer@marte.example.test`.

### Writing specs

- Import `test` and `expect` from `e2e/fixtures/test.ts`. Its automatic fixtures block every request that does not go to the local app (images get a 1×1 PNG, everything else is aborted) and fail a test whose pages log a missing or malformed translation.
- Each test sends its own `cf-connecting-ip`, so the per-IP rate limits on sign-in, sign-up and checkout never couple tests together.
- The `setup` project signs the seeded admin and customer in once and stores their sessions in `playwright/.auth/`; use them with `test.use({ storageState: STORAGE_STATE.admin })`. Never sign out or change the password of a seeded account in a spec, because every worker shares those sessions.
- A spec that changes an account, an order or a coupon creates its own: `registerCustomer` signs up and verifies a new customer, `uniqueEmail` and `uniqueCode` name the data, and `placeOrder` buys a product and pays for it through the emulator. Specs run fully parallel and must not depend on counts other specs can change.
- Wait for state with web-first assertions and `expect.poll`, never fixed timeouts. A click that lands before React has hydrated the page is dropped without sending a request, so page objects in `e2e/pages/` wait for hydration: open and reload pages through them (`open`, `reload`), and call `waitForAppReady()` after any `page.goto` a spec makes itself, before it interacts with the page.
- The landing page keeps each section hidden until it scrolls into view, so a spec reaches one the way a visitor does: `scrollUntilVisible(locator)` on the page object turns the mouse wheel until the element is visible.
- Read an email with `waitForEmail` and take a link from it with `linkIn`. Check the link's origin as well as its path: the checkout, admin and newsletter specs assert that the order confirmation, the shipping email and the newsletter confirmation all link to `http://127.0.0.1:3000`, the address the suite uses, and the newsletter spec follows its link to the confirmed page.

## Conventions

- One `__test__/` folder per feature, beside the code: `src/modules/order/__test__/order.accessors.integration.test.ts`.
- Database suites end in `*.integration.test.ts`; anything rendering React ends in `*.component.test.tsx`; everything else is a plain `*.test.ts`.
- Mock external providers. Stripe, Resend, InPost and R2 are never called from a test; the end-to-end suite talks to the emulators in the test Worker instead.
- Fixtures are local to the test file or the feature's `__test__` folder. Shared infrastructure — and only infrastructure — belongs in `src/platform/testing/`.
