---

`.github/workflows/` holds five workflows. All of them install the toolchain through the composite action `.github/actions/setup`. `ci.yml` and `e2e-full.yml` run the tests. Production deploys only a commit whose `ci.yml` run passed; the preview deploy runs `bun run check` only.

| Workflow                | Trigger                                                              | What it does                                                                                             |
| ----------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `ci.yml`                | Every pull request; pushes to `main`                                 | `check`, `test:coverage`, `build:preview`, uploads the coverage report; the Playwright suite on Chromium |
| `e2e-full.yml`          | Pushes to `main`; Mondays at 03:15 UTC; manual                       | The Playwright suite on WebKit after a push, on Chromium and WebKit otherwise; the Stripe test-mode job  |
| `e2e-reusable.yml`      | Called by `ci.yml` and `e2e-full.yml`                                | Builds the test Worker and runs the Playwright suite in one browser                                      |
| `deploy-preview.yml`    | Pull requests to `main` (opened, synchronize, reopened)              | `check`, then `deploy:preview`, then comments the preview URL on the PR                                  |
| `deploy-production.yml` | `ci.yml` passing for a push to `main`; manual, for a commit that did | `deploy:production`                                                                                      |

## The setup action

`.github/actions/setup/action.yml` is four steps and one input:

```yaml
- uses: oven-sh/setup-bun@v2
  with:
    bun-version: "1.4.0"
- uses: voidzero-dev/setup-vp@v1.20.0
  with:
    node-version: "24"
    cache: true
    run-install: false
- run: bun install --frozen-lockfile --ignore-scripts
- run: bun run typegen # when test-environment == 'true', preceded by the .env.test copies
```

Two details matter:

- **`--ignore-scripts`** means the `prepare` and `postinstall` lifecycle scripts do not run, so no Git hooks are installed on the runner and `typegen` is invoked explicitly as its own step. `typegen` is `bun run cf-typegen && bun run content`, which writes `src/types/worker-configuration.d.ts` and `.source/`. Both are gitignored, and `bun run check` cannot type check without them.
- **`test-environment`** (default `"false"`) copies `.env.test` over `.env.development` and `.env.preview` when set to `"true"`. `ci.yml` sets it; the two deploy workflows do not, because they inject the real values as environment variables instead.

## ci.yml

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
permissions:
  contents: read
```

The `verify` job, with a 15-minute timeout, running on `ubuntu-latest` with `persist-credentials: false` on the checkout. The steps are `bun run check`, `bun run test:coverage`, `bun run build:preview`, and an upload of `coverage/` as the `coverage` artifact with a seven-day retention (`if: ${{ !cancelled() }}`, `if-no-files-found: ignore`).

A second job, `e2e`, calls `e2e-reusable.yml` with `browser: chromium`.

The build step runs against the dummy `.env.preview` the setup action copied from `.env.test`, which is enough because `scripts/verify-build.ts` checks the shape of the output — the deployment config, the Worker name, the `APP_ENV` var, the presence of fonts, client JS and CSS, and the absence of `cloudflare:workers` or `node:` imports in any client asset — not the values of any credential.

## The end-to-end workflows

`e2e-reusable.yml` takes a `browser` input and an optional `suite` path (default `e2e/specs`). It runs the setup action with `test-environment: "true"`, then `bun run db:reset:test` to create and seed the local D1 database, `bun run build:test`, restores the Playwright browser cache keyed on the browser and `bun.lock`, installs the browser with its system dependencies, and runs `bunx playwright test <suite> --project=<browser>` with a 30-minute timeout. With `CI` set, Playwright only starts the built Worker, retries a failed test twice and runs two workers. On failure it uploads `playwright-report/` and `test-results/`, which hold traces, screenshots and videos, for seven days.

`e2e-full.yml` runs the same workflow as a matrix with `fail-fast: false`: WebKit after a push to `main`, because the pull request already ran Chromium, and both browsers on the weekly schedule or a manual run.

Its second job, `stripe-test-mode`, pays one checkout through a Stripe sandbox on every run of the workflow. It sets `STRIPE_SECRET_KEY` and `VITE_STRIPE_PUBLISHABLE_KEY` from the repository secrets `E2E_STRIPE_SECRET_KEY` and `E2E_STRIPE_PUBLISHABLE_KEY` for the whole job, so `bun run build:test` bakes the sandbox's publishable key into the client and gives the test Worker its secret key. The job then installs Chromium and runs `bun run test:e2e:stripe`. Without those secrets the build still runs and Playwright reports the spec skipped with the reason. Once the test Worker is serving, the spec reaches nothing outside the runner but the Stripe API, Stripe.js and its frames; [Stripe test mode](/docs/tooling/testing#stripe-test-mode) describes it. On failure the job uploads its report as `playwright-report-stripe-test-mode`.

## The deploy workflows

Both deploy workflows share the same shape: `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true` at workflow level, a GitHub `environment` (`preview` or `production`), the setup action, and then a single step that creates an empty env file and runs the deploy script. Preview runs `bun run check` before that step; production does not, because its deploy job only runs for a commit that has already passed CI, which a first job, `choose-commit`, picks:

```yaml
run: |
  touch .env.preview
  bun run deploy:preview
```

The `touch` exists because `scripts/prepare-deploy-secrets.ts` reads the file unconditionally (`scripts/verify-stripe-keys.ts`, `scripts/verify-turnstile-keys.ts` and `scripts/verify-email-sender.ts` treat a missing file as empty); the values themselves come from the step's `env:` block, which all four scripts prefer over the file:

```ts
const value = process.env[name] ?? values[name]
```

Concurrency differs on purpose. Preview groups by pull request number and cancels in-progress runs (`preview-${{ github.event.pull_request.number }}`, `cancel-in-progress: true`), so pushing again to a branch replaces its preview. Production's deploy job uses the fixed group `production` with `cancel-in-progress: false`, so deploys queue rather than interrupt each other mid-deploy. The group is set on the deploy job, not on the workflow, so `choose-commit` and a run that chose no commit never wait in it.

`deploy-preview.yml` additionally takes `pull-requests: write` and finishes with an `actions/github-script@v7` step that posts — or updates, by searching existing comments for the string `Preview Deployment` — a comment linking to `https://martebizuteria-preview.pjborowiecki.workers.dev`.

### What a production deploy waits for

`deploy-production.yml` does not run on a push. It starts on `workflow_run` when the `CI` workflow completes on `main`, and its first job, `choose-commit`, runs only when that run was for a push and concluded `success`. So a commit reaches production only after `check`, `test:coverage`, `build:preview` and the Chromium end-to-end suite have passed on that very commit. A pull request from a branch that happens to be called `main` cannot start it, because its CI run's event is `pull_request`. When CI fails or is cancelled, nothing deploys. The WebKit run of `e2e-full.yml` after the push is not part of the gate.

`choose-commit` hands the deploy job `github.event.workflow_run.head_sha`, the commit CI tested, but only while it is still the tip of `main`, which it reads with `gh api repos/<owner>/<repo>/commits/main`. When `main` has moved on, it writes a warning and the deploy job is skipped; the newer commit deploys once its own CI passes. So re-running an older commit's CI, for example after a flaky end-to-end test, never deploys it over the commits merged after it, and together with `ci.yml` cancelling its run on `main` when a newer push arrives, production only moves forward on its own. Going back to an older commit takes a manual run. The deploy job checks out the commit it was handed, not whatever is on `main` by the time it runs.

`workflow_dispatch` takes one input, `commit`, the full SHA of a commit to deploy. Instead of the tip check, `choose-commit` asks `gh run list --workflow ci.yml --branch main --event push --commit <sha> --status success` whether CI passed for a push of that commit to `main`, which is why that job has the `actions: read` permission, and fails when it did not, so nothing deploys. That is how a known-good commit is redeployed; see [Roll back a deploy](/docs/guides/roll-back-a-deploy).

GitHub only starts `workflow_run` from the workflow file on `main`, so a change to `deploy-production.yml` takes effect once it is merged.

Preview is a single shared deployment: every pull request deploys to the same Worker (`martebizuteria-preview`) backed by the same preview D1 database, KV namespace and R2 bucket (`martebizuteria-preview`), so the most recent preview deploy is the one that is live.

## What a deploy actually runs

```json
"deploy:preview": "bun scripts/verify-bindings.ts preview && bun scripts/verify-stripe-keys.ts preview && bun scripts/verify-turnstile-keys.ts preview && bun scripts/verify-email-sender.ts preview && bun run build:preview && bun scripts/prepare-deploy-secrets.ts preview && bun run db:migrate:preview && env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.preview.json && bun scripts/verify-deployment.ts preview"
```

Nine stages, chained with `&&`, so the first one that fails stops the deploy.

### 1. verify-bindings.ts

Reads `wrangler.jsonc` for the target environment with `unstable_readConfig` and refuses to continue unless every binding is present and real:

- a `DB` D1 binding with a `database_id` that is not all zeroes or dashes,
- a `CACHE` KV binding with a real `id`,
- an `IMAGES` R2 binding with a `bucket_name`,
- an `AUDIT_LOG_QUEUE` producer **and** a consumer for the same queue that names a `dead_letter_queue`, which a second consumer consumes,
- a `NEWSLETTER_QUEUE` producer **and** a consumer for the same queue that names a `dead_letter_queue`, which another consumer consumes,
- a `REALTIME_INVALIDATION_HUB` Durable Object binding whose `class_name` is `RealtimeInvalidationHub`,
- for production, an `IMAGES` bucket other than the one preview binds.

This is the check that catches a placeholder id or a bucket copied between environments.

### 2. verify-stripe-keys.ts

Reads `VITE_STRIPE_PUBLISHABLE_KEY` and `STRIPE_SECRET_KEY` from `process.env` first and `.env.<environment>` second, and passes them to `verifyStripeKeys` in `src/integrations/stripe/stripe.keys.ts`, which reads each key's mode from its prefix. Production needs live keys: `pk_live_` and either `sk_live_` or a restricted `rk_live_`. Preview, and development when the script is run by hand, need test keys: `pk_test_` with `sk_test_` or `rk_test_`. It fails on a missing or blank key, on a value that is not the kind of key its variable holds, on a publishable key whose mode differs from the secret key's in any environment, and on keys of the wrong mode for the target. Its output and errors name the variables and their mode, never a key.

It reads only the prefixes and calls no outside service, so it cannot tell whether Stripe still accepts the keys or whether a restricted key has the permissions checkout needs. It runs before the build because `VITE_STRIPE_PUBLISHABLE_KEY` is baked into the client bundle, so test keys in the production environment would otherwise go live with a checkout that takes Stripe's test cards. See [Stripe](/docs/integrations/stripe#secrets).

### 3. verify-turnstile-keys.ts

Reads `VITE_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` from `process.env` first and `.env.<environment>` second, and passes them to `verifyTurnstileKeys` in `src/integrations/cloudflare-turnstile/turnstile.keys.ts`. Cloudflare's testing keys (`1x…`, `2x…` and `3x…` followed by zeros) pass every visitor, so production needs the keys of the shop's own widget; preview, and development when the script is run by hand, accept either kind. It fails on a missing or blank key in any environment, and on a testing key paired with a widget's key, because the secret would then refuse every token the site key issues. Its output and errors name the variables and the kind of keys, never a key. It calls no outside service, so it cannot tell whether the widget still exists or lists the shop's hostname. It runs before the build because `VITE_TURNSTILE_SITE_KEY` is baked into the client bundle. See [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile#keys).

### 4. verify-email-sender.ts

Reads `RESEND_API_KEY` and `RESEND_EMAIL_FROM` from `process.env` first and `.env.<environment>` second, then asks Resend whether it would send as that address. It fails on a missing key, a sender with a display name, `onboarding@resend.dev` outside development, a domain that is not in the key's Resend account, and a domain whose DKIM or SPF records are not verified, in which case it prints the records still to publish. A sending-only key cannot read domains, so the check reads them with `RESEND_MANAGEMENT_API_KEY`, an optional Full access key that the step takes from the environment's GitHub secrets and that never reaches the Worker. Without it, the check sends one test e-mail to `delivered@resend.dev` and fails if Resend refuses it. Each Resend request is asked again once after a rate limit or a 5xx, and the whole check gives up after 30 seconds.

It runs before the build so that a sender Resend would refuse stops the deploy within seconds. It is the only stage before the build that calls an outside service, and it is not part of `build:*`, so `ci.yml` never calls Resend with the dummy `.env.test` values. See [Resend](/docs/integrations/resend#sender-domain) for the records and the local `onboarding@resend.dev` setup.

### 5. build

`bun run build:preview` removes `dist`, regenerates `.source/`, runs `CLOUDFLARE_ENV=preview vp build --mode preview`, and then `bun scripts/verify-build.ts preview`. `verify-build.ts` reads `.wrangler/deploy/config.json`, follows its `configPath`, and asserts it resolves to exactly `dist/server/wrangler.json`; that the built config's `vars.APP_ENV` matches the target and its `name` is `martebizuteria-preview` (or `martebizuteria` for production); that `main` and `dist/client` exist; that `dist/client/fonts` exists; that `dist/client/assets` contains at least one `.js` and one `.css`; and finally it scans every client `.js` file with `new Bun.Transpiler({ loader: "js" })` and fails on any import of `cloudflare:workers` or a `node:` module.

### 6. prepare-deploy-secrets.ts

Reads `secrets.required` from the environment's `wrangler.jsonc` block, resolves each name from `process.env` first and `.env.<environment>` second, throws on the first missing value or blank value other than `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID` (`SECRETS_THAT_MAY_BE_BLANK`, uploaded blank so InPost shipments and their webhook stay off), and writes `.wrangler/secrets.<environment>.json` with mode `0o600`.

Only the names declared in `wrangler.jsonc` are written. `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` and `CLOUDFLARE_ACCESS_TOKEN` are deliberately not in that list: they are management credentials for drizzle-kit and Wrangler, not Worker runtime secrets, and uploading them to the Worker would be a privilege leak.

### 7. db:migrate:preview

`bun run db:migrate:preview` is `vp exec wrangler d1 migrations apply DB --env preview --remote`, and `deploy:production` runs `db:migrate:production` in its place. Wrangler reads `wrangler.jsonc` for this command, not the built config, and applies in filename order every file in `src/integrations/drizzle-orm/migrations/` that the database's `d1_migrations` table does not list yet, or prints `No migrations to apply!`. When a migration fails, Wrangler rolls that one back, keeps the ones before it and exits non-zero, so the Worker is not deployed. On a runner Wrangler applies without asking; in a terminal it asks first, and answering no skips the migrations but not the deploy, so stop with Ctrl+C instead.

The stage runs after the build and the secrets file, so a deploy that fails earlier never touches the database, and before `wrangler deploy`, so the new Worker never starts on a schema it does not know. The Worker serving the shop while the migrations run is the previous one, which is why every migration has to keep it working; see [Roll back a deploy](/docs/guides/roll-back-a-deploy).

### 8. wrangler deploy

```sh
env -u CLOUDFLARE_ENV vp exec wrangler deploy --config dist/server/wrangler.json --secrets-file .wrangler/secrets.preview.json
```

`CLOUDFLARE_ENV` is unset for this command because the built `dist/server/wrangler.json` is already flattened to one environment — leaving the variable set would have Wrangler look for an environment section inside a config that no longer has one. The secrets file is uploaded with the deploy, so the eleven declared secrets are set atomically with the new version.

### 9. verify-deployment.ts

Calls `verifyDeployment` in `src/lib/deployment.ts`, which asks the environment's own `workers.dev` host, from `WORKERS_DEV_HOSTS` in `src/modules/_core/constants/api.ts`, for five paths without following redirects. `/` and `/products` must answer `200` with `text/html`, `/robots.txt` must answer `200` with `text/plain`, `/api/webhooks/stripe` must refuse a `GET` with `405` and `text/plain`, which shows the request reached the route's own handler rather than a rendered page, and `/api/health` must answer `200` with `application/json`, which it does only when D1, KV and R2 all answer; its `503` fails the deploy. Each request gives up after 15 seconds, and a page that fails is asked up to three times in all, five seconds apart. A page still failing then fails the deploy with one line per page. The new version is already live by then, so the next step is [Roll back a deploy](/docs/guides/roll-back-a-deploy).

It only reads public pages: it signs nobody in, opens no checkout and writes nothing. It asks the `workers.dev` host, which `workers_dev: true` in `wrangler.jsonc` keeps on next to the custom domain, so the check does not depend on the zone's DNS or on a certificate Cloudflare may still be issuing for a newly attached domain.

## Repository configuration

| Kind                | Names                                                                                                                                                                                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actions **secrets** | `CLOUDFLARE_ACCESS_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `AUTH_SECRET`, `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `INPOST_API_TOKEN`, `INPOST_ORGANIZATION_ID`, `RESEND_API_KEY`, `RESEND_EMAIL_FROM`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `TURNSTILE_SECRET_KEY` |
| Actions **vars**    | `VITE_APP_URL`, `VITE_R2_URL`, `VITE_STRIPE_PUBLISHABLE_KEY`, `VITE_TURNSTILE_SITE_KEY`                                                                                                                                                                                            |

`CLOUDFLARE_ACCESS_TOKEN` is passed to the step as `CLOUDFLARE_API_TOKEN`, which is the name Wrangler reads. Besides deploying the Worker, the token needs the D1 edit permission, because the deploy applies the migrations with it, and the Workers Routes edit and Zone read permissions on the `martebizuteria.pl` zone, because the deploy attaches the custom domains from `routes` in `wrangler.jsonc`. Both deploy workflows use GitHub environments (`preview`, `production`), so the secrets can be scoped per environment there.

The Stripe test-mode job reads two repository secrets outside those environments: `E2E_STRIPE_SECRET_KEY`, a Stripe sandbox's secret key (`sk_test_`), and `E2E_STRIPE_PUBLISHABLE_KEY`, the same sandbox's `pk_test_` key. Take them from a sandbox with no webhook endpoint, not from the account preview uses: an endpoint pointing at the preview Worker would receive these payments, find no checkout for them and email `RESEND_EMAIL_FROM`.

`VITE_R2_URL` is listed in `secrets.required` in `wrangler.jsonc` but supplied from Actions **vars**, not secrets — it is a public bucket URL and also needs to be visible to the client bundle through its `VITE_` prefix. `prepare-deploy-secrets.ts` reads it from `process.env`, so this works. Preview and production read different buckets, so set it on the GitHub `preview` and `production` environments rather than once for the repository; [Image delivery](/docs/guides/image-delivery) lists the values.

## Migrations and CI

`ci.yml` and the end-to-end workflows never touch a deployed database; the end-to-end workflow replays the full history into its own local one, which also proves the history still builds a database from scratch. The deployed databases are migrated by the deploy scripts, right before `wrangler deploy`: the shared preview database by every preview deploy, so a pull request's migration reaches it as soon as that pull request's preview deploys, and production by every production deploy. `bun run db:migrate:<environment>` still applies migrations by hand, and `bun run db:migrations:<environment>` lists what a database has applied.

A migration that a preview deploy applied stays applied even if its pull request changes or closes, so never edit a migration once its preview has deployed; add another one. See [Database](/docs/tooling/database) and [Roll back a deploy](/docs/guides/roll-back-a-deploy).
