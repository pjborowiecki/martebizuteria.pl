Vite+ uruchamia Vitest 5 z konfiguracją z bloku `test` w `vite.config.ts`. Testy leżą w katalogu `__test__` obok kodu, który sprawdzają, i importują swoje API z `vite-plus/test`, nigdy z `vitest`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"
```

Uruchamiaj je przez `bun run test`, a nie `bun test`. Własny runner Buna ignoruje projekty Vitest, środowisko jsdom i plik setup, więc duża część zestawu po cichu by się wysypała albo została pominięta.

## Trzy projekty

Zestaw jest dzielony po nazwie pliku, a każdy podział dostaje własne środowisko.

| Projekt       | Pliki                                                       | Środowisko | Plik setup                      |
| ------------- | ----------------------------------------------------------- | ---------- | ------------------------------- |
| `node`        | `src/**/*.{test,spec}.{ts,tsx}` poza dwoma wzorcami poniżej | `node`     | brak                            |
| `integration` | `src/**/*.integration.test.{ts,tsx}`                        | `node`     | brak                            |
| `component`   | `src/**/*.component.test.{ts,tsx}`                          | `jsdom`    | `src/platform/testing/setup.ts` |

```sh
bun run test              # vp test run — wszystkie trzy projekty
bun run test:unit         # vp test run --project node
bun run test:integration  # vp test run --project integration
bun run test:component    # vp test run --project component
bun run test:changed      # vp test run --changed
bun run test:coverage     # vp test run --coverage
```

W chwili pisania repozytorium ma około 890 plików testowych: około 515 testów komponentowych, 35 testów integracyjnych, a pozostałe to testy jednostkowe w projekcie `node`.

> `bun run test:watch` odwzorowuje się na `vp test` bez podkomendy. Zgodnie z `vp test --help` `vp test` „uruchamia testy raz domyślnie”, a tryb obserwowania to osobna podkomenda `vp test watch` — ten skrypt jest więc drugim jednorazowym przebiegiem, a nie obserwatorem. Gdy chcesz trybu obserwowania, użyj `vp test watch` (albo `vp test --watch`).

## Wspólna konfiguracja testów

Wszystko, co projekty mają ze sobą wspólne, leży w bloku `test` na najwyższym poziomie i jest dziedziczone przez `extends: true`:

| Ustawienie        | Wartość                                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `environment`     | `"node"` (projekt `component` nadpisuje to na `"jsdom"`)                                                                           |
| `env`             | `loadEnv("test", import.meta.dirname, "")` — wczytuje `.env.test`, który jest w repozytorium i zawiera wyłącznie wartości atrapowe |
| `pool`            | `"threads"`                                                                                                                        |
| `maxWorkers`      | `"50%"`                                                                                                                            |
| `isolate`         | `true`                                                                                                                             |
| `passWithNoTests` | `false`                                                                                                                            |
| `exclude`         | `node_modules/**`, `opensrc/**`, `dist/**`, `scripts/**`, `e2e/**`, `src/integrations/drizzle-orm/migrations/**`                   |

Ponieważ `test.env` wczytuje `.env.test`, żaden test nie potrzebuje prawdziwych danych uwierzytelniających. `scripts/` jest wykluczony z zestawu, więc `scripts/commit-msg.ts`, `scripts/verify-build.ts` i pozostałe nie są pokryte testami.

## Infrastruktura testowa

`src/platform/testing/` zawiera wspólną infrastrukturę. Wszystko poza nią jest współlokowane z kodem, który sprawdza.

| Plik                             | Co dostarcza                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `setup.ts`                       | Matchery jest-dom, atrapy obserwatorów DOM, `matchMedia` oraz proxy na `createServerFn`                                         |
| `vitest-env.d.ts`                | Referencję `vite-plus/test/globals` i typy matcherów jest-dom na interfejsie `Matchers` Vitesta                                 |
| `mocks/d1.ts`                    | `createTestD1Database(sqlite, onQuery?, onRoundTrip?)` — `D1Database` oparty na `node:sqlite`                                   |
| `mocks/migrations.ts`            | `applyMigration` dla jednej migracji i `applyMigrationHistory`, które buduje schemat produkcyjny                                |
| `mocks/intersection-observer.ts` | `StubIntersectionObserver` — puste `observe`, `unobserve`, `disconnect`, `takeRecords`                                          |
| `mocks/resize-observer.ts`       | `StubResizeObserver` — przy `observe` zgłasza stały prostokąt 1024 × 768                                                        |
| `lib/render.tsx`                 | `renderWithProviders`, `TestProviders`, `createTestRouter`                                                                      |
| `lib/messages.ts`                | `TEST_LOCALE` (`en-US`) i `TEST_MESSAGES`, zbudowane z prawdziwych plików `messages/en-US/*.json`                               |
| `lib/server-function.ts`         | `withTestRpc` — przepuszcza funkcje serwerowe przez ich prawdziwy łańcuch middleware i walidacji                                |
| `lib/auth-browser.ts`            | `openAuthBrowser(ip)`, klient `auth.handler` z ciasteczkami, który wysyła token-atrapę Turnstile, oraz `createPasswordCustomer` |

### setup.ts

Plik setup projektu `component` robi cztery rzeczy. Rozszerza `expect` matcherami jest-dom, podstawia atrapy `IntersectionObserver`, `ResizeObserver` i `matchMedia` (których jsdom nie implementuje, a których oczekują komponenty oparte na GSAP i Lenis), a następnie łata TanStack Start:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
```

Podmienia też `getRequest` z `@tanstack/react-start/server` na atrapę zwracającą `new Request("http://127.0.0.1:3000/")`.

### Testowanie funkcji serwerowych

`withTestRpc` owija builder `createServerFn` w proxy. Przepuszcza `inputValidator`, `middleware` i `validator` bez zmian, a przechwytuje `.handler()`, tak aby skompilowana funkcja serwerowa była wywoływana przez `runWithStartContext` ze sztucznym kontekstem startowym i prawdziwym wejściem `__executeServer`. Praktyczny skutek jest taki, że test wywołujący przypadek użycia faktycznie wykonuje jego walidatory i middleware `assertAdmin` — infrastruktura testowa nie obchodzi kontroli autoryzacji, i o to właśnie chodzi, bo warstwa przypadków użycia jest miejscem, w którym autoryzacja żyje.

### Testowanie komponentów

`renderWithProviders` renderuje komponent wewnątrz tych samych trzech dostawców, których używa aplikacja — `IntlProvider` z prawdziwymi komunikatami angielskimi i `I18N.DEFAULT_TIMEZONE`, `QueryClientProvider` z wyłączonymi ponowieniami oraz `RouterContextProvider` nad routerem z historią w pamięci — i zwraca wynik Testing Library wraz z utworzonymi `queryClient` i `router`, więc test może sprawdzać stan cache'u albo nawigację:

```ts
const { queryClient, router } = renderWithProviders(<ProductCard product={product} />)
```

`createTestRouter(path)` buduje router w pamięci; przekaż ścieżkę, gdy komponent zależy od bieżącej lokalizacji.

Komunikaty nie są danymi testowymi. `lib/messages.ts` zaciąga `messages/en-US/*.json` przez `import.meta.glob` z opcją `eager` i przepuszcza je przez własne funkcje aplikacji `buildMessageTree` i `toNamespace`, więc brakujący albo zmieniony klucz tłumaczenia wysypuje test komponentowy.

### Testowanie kodu bazodanowego

Nie ma globalnego mocka D1. Każdy test integracyjny buduje własną bazę w pamięci i podmienia instancję Drizzle:

```ts
const { sqlite } = await vi.hoisted(async () => {
  const { DatabaseSync } = await import("node:sqlite")

  return { sqlite: new DatabaseSync(":memory:") }
})

vi.mock(import("~/src/integrations/drizzle-orm/drizzle.database"), async () => {
  const { drizzle } = await import("drizzle-orm/d1")
  const { createTestD1Database } = await import("~/src/platform/testing/mocks/d1")

  return { db: drizzle(createTestD1Database(sqlite)) }
})
```

`createTestD1Database` implementuje tyle powierzchni `D1Database`, ile potrzebuje Drizzle: `prepare`, `bind`, `all`, `raw`, `run` i `batch`. Tak jak D1, `bind` odrzuca instrukcję z więcej niż 100 parametrami, które lokalne SQLite i Miniflare by przyjęły, więc test z danymi wielkości produkcyjnej wyłapuje instrukcję, która na D1 by się nie powiodła. Dlatego wielowierszowe inserty i zmiany rang są dzielone w `drizzle.batch.ts` i wysyłane w jednym `db.batch`, a lista identyfikatorów zbudowana w czasie działania jest wiązana jako jeden parametr JSON przez `inJsonList`; oba mechanizmy opisuje [Drizzle ORM i D1](/docs/integrations/drizzle-orm-d1). `batch` wykonuje wsady po kolei, tak jak D1, owija instrukcje w `begin` / `commit` i wycofuje je przy błędzie — i to właśnie czyni testy idempotencji checkoutu sensownymi, bo atomowa partia D1 jest ograniczeniem, na którym te testy się opierają. Opcjonalne wywołanie `onQuery` otrzymuje każdą parę `{ sql, params }`. `src/modules/product/__test__/product.accessors.integration.test.ts` zbiera je i sprawdza dokładnie, ile instrukcji wykonuje odczyt katalogu (`expect(queries).toHaveLength(3)`) oraz że żadna instrukcja nie wiąże więcej niż 100 parametrów — tak wyłapywane są regresje typu N+1 i przekroczenia limitu parametrów D1.

Opcjonalne wywołanie `onRoundTrip` liczy żądania, a nie instrukcje, bo partia pięciu instrukcji kosztuje D1 jedno żądanie, a pięć osobnych instrukcji kosztuje pięć. Otrzymuje `TestD1RoundTrip`: `{ kind: "batch", sql }` raz na każde wywołanie `batch`, gdzie `sql` to SQL instrukcji w kolejności, oraz `{ kind: "statement", sql: [sql] }` raz na każde `all`, `raw` lub `run` poza partią, także dla instrukcji wykonanej osobno po tym, jak niosła ją partia. Wywołuje się w chwili wysłania żądania, więc test, który sam trzyma obietnicę, na przykład jeszcze nierozwiązaną zamockowaną zależność, może w tym momencie odczytać zapisane żądania i zobaczyć, które wyszły przed nią. Nie pokaże natomiast, czy jedno żądanie do bazy czekało na inne: mock odpowiada na każdą samodzielną instrukcję od razu, więc `Promise.all` dwóch selectów Drizzle i dwa selecty, na które czeka się po kolei przez `await`, zapisują te same dwa żądania. Służy do liczenia osobnych żądań, a nie do mierzenia, jak głęboko się łańcuchują. `inventory-reservation.integration.test.ts` sprawdza nim, że cały koszyk jest rezerwowany w jednej partii z obiema pozycjami i że pusta lista nigdy nie dociera do bazy. `onQuery` nadal widzi każdą instrukcję, w partii czy poza nią.

Same tabele tworzy test przez `sqlite.exec(...)`, odwzorowując kolumny, które produkują migracje. Zestawy Vitesta nie nakładają plików migracji, więc zmiana schematu oznacza aktualizację zarówno migracji, jak i instrukcji `create table` w testach dotykających tej tabeli. Zestaw end-to-end przy każdym uruchomieniu nakłada całą historię na świeżą bazę i to właśnie utrzymuje ją odtwarzalną.

Niezależnie od tego każdy moduł ma w projekcie `node` plik `*.schema.test.ts`, który czyta metadane tabeli Drizzle przez `getTableConfig` i sprawdza nazwę tabeli, pełną uporządkowaną listę kolumn, klucze obce razem z zachowaniem `onDelete` oraz zadeklarowane relacje. Te testy są powodem, dla którego zmiana nazwy kolumny nie może przejść niezauważona.

## Pokrycie

```sh
bun run test:coverage
```

Dostawca `v8`, raportery `text`, `html` i `json-summary`, wynik w `coverage/`, czyszczonym przy każdym przebiegu.

| Metryka    | Próg |
| ---------- | ---- |
| Instrukcje | 100  |
| Linie      | 100  |
| Funkcje    | 100  |
| Gałęzie    | 100  |

Pokryta jest każda instrukcja, gałąź, funkcja i linia, więc wszystkie cztery progi wynoszą 100 i każdy nowy kod przychodzi razem ze swoimi testami. `thresholds.autoUpdate` ma wartość `false`.

Pokrycie obejmuje `src/**/*.{ts,tsx}` i wyklucza testy, katalogi `__test__`, `*.d.ts`, `src/routeTree.gen.ts`, `src/integrations/**/migrations/**` (wynik introspekcji drizzle-kit, który pomijają też lint i formatowanie), `src/presentation/components/shadcn/**` (vendorowane prymitywy) oraz `src/platform/testing/**`.

Testuj rzeczywiste zachowanie. Jeśli jakaś gałąź jest nieosiągalna, usuń gałąź, zamiast podstawiać atrapę globalnej wartości, żeby do niej dotrzeć.

## Testy end-to-end

Playwright steruje zbudowanym Workerem w Chromium i WebKicie. Zestaw leży w `e2e/`, a jego konfiguracja w `playwright.config.ts`:

```sh
bun run test:e2e:install  # jednorazowo: przeglądarki Chromium i WebKit
bun run test:e2e          # resetuje testową bazę, buduje testowego Workera, serwuje go i uruchamia wszystkie specyfikacje
bun run test:e2e:pr       # to samo tylko w Chromium, tak jak CI na pull requestach
bun run test:e2e:smoke    # e2e/specs/smoke.spec.ts w Chromium
bun run test:e2e:ui       # tryb UI Playwrighta
```

Poza CI `webServer` Playwrighta sam uruchamia `db:reset:test`, `build:test` i `start:test` oraz używa serwera, który już słucha na porcie 3000; w CI bazę i build przygotowuje przepływ, a Playwright tylko uruchamia serwer.

### Testowy Worker

`wrangler.jsonc` ma środowisko `test`, którego `main` to `src/platform/testing/worker.ts`, a D1, KV, R2, Durable Object i kolejka audytu są w nim lokalne (`remote: false`) i zapisywane w `.wrangler/test`. `bun run build:test` buduje je z `CLOUDFLARE_ENV=test` i `--mode test`, więc każdy sekret pochodzi z commitowanego `.env.test`. Powiadomienie sklepu o nowym zamówieniu trafia na jego `RESEND_EMAIL_FROM`, `noreply@example.test`, czyli `ORDER_NOTIFICATION_INBOX` z `e2e/data/accounts.ts`, więc każde zamówienie złożone przez specyfikację wysyła tam też to powiadomienie.

Testowy Worker instaluje `src/platform/testing/mocks/providers.ts`, zanim wczyta aplikację, więc nic nie opuszcza maszyny:

- **Resend.** Żądania do `api.resend.com` są przechwytywane zamiast wysyłane. `GET /__test/emails?to=<adres>` zwraca przechwycone wiadomości do danego odbiorcy.
- **Stripe.** Żądania do `api.stripe.com` trafiają do działającego w pamięci emulatora wywołań, które wykonuje serwer: sesji Checkout (tworzenie, odczyt, lista, wygaszanie), kuponów, klientów (tworzenie i usuwanie, które odłącza ich metody płatności), płatności, metod płatności (lista dla klienta, odczyt, odłączanie), SetupIntentów i zwrotów. Każde inne wywołanie Stripe'a dostaje 400, więc nowe użycie Stripe'a oblewa specyfikację, zamiast przejść po cichu. Tak jak Stripe odrzuca sesję Checkout, której `expires_at` jest bliżej niż za 30 minut albo dalej niż za 24 godziny, i trzyma w sesji `created` oraz `expires_at`, żeby specyfikacja mogła sprawdzić czas rezerwacji. `GET /__test/stripe/checkout-sessions?email=<adres>` wypisuje sesje otwarte dla kupującego, a `openCheckoutSessions` z `e2e/fixtures/stripe.ts` zawęża je do tych wciąż otwartych, a `POST /__test/stripe/checkout-sessions/<id>/complete` oznacza jedną jako opłaconą i zwraca zdarzenie `checkout.session.completed` podpisane `STRIPE_WEBHOOK_SECRET`. `POST /__test/stripe/checkout-sessions/<id>/expire` tak samo wygasza sesję i zwraca podpisane zdarzenie `checkout.session.expired`, które `expireCheckoutSession` z `e2e/fixtures/stripe.ts` dostarcza do webhooka. `GET /__test/stripe/setup-intents?email=<adres>` wypisuje SetupIntenty na kartę otwarte ze strony konta, a `POST /__test/stripe/setup-intents/<id>/succeed` zastępuje przeglądarkowe `stripe.confirmSetup`: dołącza do klienta kartę Visa kończącą się na 4242 i oznacza SetupIntent jako udany. `GET /__test/stripe/customers?email=<adres>` wypisuje klientów, którzy wciąż istnieją dla kupującego, a `stripeCustomerIds` z `e2e/fixtures/stripe.ts` odczytuje ich, żeby sprawdzić, że usunięcie konta usunęło jego klienta Stripe.
- **Turnstile.** Żądania do `challenges.cloudflare.com`, czyli wyłącznie do `siteverify`, dostają odpowiedź taką, jaką daje zawsze przepuszczający testowy klucz tajny Cloudflare: sukces, z zastępczą akcją `test` i hostem `localhost`, dla testowego klucza tajnego i tokenu-atrapy `XXXX.DUMMY.TOKEN.XXXX`, który wydaje jego testowy klucz witryny, a `invalid-input-response` dla każdego innego tokenu, więc specyfikacja może podrobić token i zobaczyć, że kasa albo rejestracja go odrzuca.

Specyfikacja wysyła to podpisane zdarzenie do `/api/webhooks/stripe` tak jak Stripe, więc trasa webhooka weryfikuje podpis i realizuje zamówienie prawdziwym kodem. `completeCheckoutSessionBeforeItsWebhook` z `e2e/fixtures/stripe.ts` oznacza sesję jako opłaconą i zwraca podpisane zdarzenie, nie wysyłając go, a `deliverStripeEvent` wysyła je później, więc specyfikacja może przeładować kasę, gdy Stripe zgłasza już sesję jako `complete`, a zamówienie jeszcze nie istnieje. Poza zasięgiem zostaje tylko sam formularz karty, czyli Stripe.js.

### Dane

`bun run db:reset:test` usuwa `.wrangler/test`, nakłada całą historię migracji przez `wrangler d1 migrations apply --local` i uruchamia `scripts/seed-test.ts`. Seed wczytuje te same pliki katalogu co `db:seed:preview` (dwa naszyjniki ze stanem, kategorie, kolekcje, atrybuty i metody dostawy) oraz dwa zweryfikowane konta z `e2e/data/accounts.ts`: `admin@marte.example.test` i `customer@marte.example.test`.

### Pisanie specyfikacji

- Importuj `test` i `expect` z `e2e/fixtures/test.ts`. Jego automatyczne fixtures blokują każde żądanie, które nie idzie do lokalnej aplikacji (obrazy dostają PNG 1×1, skrypt Turnstile dostaje `TURNSTILE_WIDGET_DOUBLE` z `e2e/fixtures/turnstile.ts`, reszta jest przerywana), i oblewają test, którego strony zalogują brakujące lub błędne tłumaczenie. Dubel widżetu definiuje `window.turnstile` z `render`, które przekazuje callbackowi widżetu token-atrapę `XXXX.DUMMY.TOKEN.XXXX`, tak jak testowy klucz witryny Cloudflare, więc krok płatności oraz formularze rejestracji, zmiany hasła, ponownej weryfikacji i newslettera uruchamiają prawdziwy kod zabezpieczenia antybotowego bez łączenia się z Cloudflare.
- Każdy test wysyła własny `cf-connecting-ip`, więc limity na IP przy logowaniu, rejestracji i checkoucie nigdy nie wiążą testów ze sobą.
- Projekt `setup` raz loguje zaseedowanego administratora i klienta i zapisuje ich sesje w `playwright/.auth/`; używaj ich przez `test.use({ storageState: STORAGE_STATE.admin })`. Nigdy nie wylogowuj zaseedowanego konta ani nie zmieniaj jego hasła w specyfikacji, bo te sesje współdzielą wszyscy workerzy.
- Specyfikacja, która zmienia konto, zamówienie albo kupon, tworzy własne: `registerCustomer` rejestruje i weryfikuje nowego klienta, `uniqueEmail` i `uniqueCode` nazywają dane, a `placeOrder` kupuje produkt i płaci za niego przez emulator. Specyfikacje działają w pełni równolegle i nie mogą zależeć od liczb, które zmieniają inne specyfikacje.
- Na stan czekaj asercjami web-first i `expect.poll`, nigdy stałymi opóźnieniami. Kliknięcie, które trafi na stronę, zanim React ją zhydratuje, przepada bez wysłania żądania, dlatego obiekty stron w `e2e/pages/` czekają na hydratację: otwieraj i przeładowuj strony przez nie (`open`, `reload`), a po każdym `page.goto` użytym bezpośrednio w specyfikacji wywołaj `waitForAppReady()`, zanim zaczniesz działać na stronie.
- Specyfikacja, która liczy żądania, najpierw wywołuje `muteRealtime(context)` z `e2e/fixtures/test.ts`. Kieruje ono gniazda `/api/realtime/` do atrapy Playwrighta, która nigdy nie łączy się z serwerem, więc gniazdo strony zostaje otwarte i milczy, a zmiana wprowadzona przez inny proces testowy nie wywoła ponownego pobrania. `recordServerFunctionCalls(page)` z `e2e/fixtures/server-functions.ts` wypisuje następnie funkcje serwerowe wywołane przez dany dokument, rozpoznane po nagłówku referer żądania. Zbudowana funkcja serwerowa ma adres będący skrótem SHA-256 jej pliku i eksportu, dlatego `SERVER_FUNCTIONS` nazywa te, których szukają specyfikacje. Specyfikacja koszyka używa obu, by pokazać, że pełne wczytanie `/en-US/cart` wywołuje tylko `checkCartAvailability` i `getCurrentSession`. Najpierw oczekuje `checkCartAvailability` wśród zapisanych wywołań, więc rejestrator, który niczego nie zobaczył, kończy test błędem, zamiast go zaliczyć. Potem otwiera pełnoekranowe menu przy szerokości, na której pokaz jest widoczny, i oczekuje zdjęcia nowości z kolekcji, które przyniosła strona, nadal bez wywołania `getCollections`.
- Specyfikacja checkoutu, w której gość zatwierdza płatność w aplikacji banku, liczy sprawdzenia dostępności na stronie bez gniazda realtime, więc nie potrzebuje `muteRealtime`. `recordServerFunctionRequests(page, id)` z `e2e/fixtures/server-functions.ts` zachowuje każde żądanie do jednej funkcji serwerowej, więc specyfikacja może poczekać na sprawdzenie niosące identyfikator trzymanej sesji i na wszystkie odpowiedzi, zanim zacznie liczyć. `leaveTab()` i `returnToTab()` w `BasePage` zastępują przełączenie aplikacji: przełączają kontekst przeglądarki w tryb offline i z powrotem oraz zgłaszają dokument jako ukryty, a potem widoczny zdarzeniem `visibilitychange`, czyli tym, czego nasłuchują menedżery fokusu i połączenia TanStack Query. Specyfikacja opłaca sesję przez emulator, gdy karta jest w tle, i oczekuje, że do potwierdzenia nie będzie już żadnego sprawdzenia.
- Specyfikacje checkoutu, w których opłacona sesja wraca, przez przeładowanie, przeładowanie przed webhookiem albo drugą kartę, po zapłacie zapisują żądania do `createCheckoutSession`, `updateCheckoutSession` i `checkCartAvailability` z `SERVER_FUNCTIONS` i nie oczekują żadnego, a do tego potwierdzenia i braku otwartej sesji, więc nie otwarto drugiego formularza płatności. Najpierw czekają na wstęp kroku płatności, który renderuje się, gdy sesja jest już zapisana. Specyfikacja powrotu z banku bez zapłaty otwiera `?success=true&session_id=<id>` dla otwartej sesji i oczekuje `?step=4`, toastu, koszyka i jednej otwartej sesji kontynuującej ten sam checkout.
- Trzy kolejne specyfikacje checkoutu sprawdzają, co dzieje się po tym sprawdzeniu. `runBeforeServerFunction(page, id, run)` z `e2e/fixtures/server-functions.ts` wstrzymuje najbliższe żądanie do jednej funkcji serwerowej, dopóki `run` się nie zakończy, więc specyfikacja, w której płatność kończy się, gdy przeładowany checkout kontynuuje swoją sesję, opłaca ją przez emulator dokładnie wtedy, gdy wychodzi `updateCheckoutSession`, już po tym, jak sprawdzenie sesji zastało ją otwartą, i oczekuje potwierdzenia, zamówienia po dostarczeniu webhooka, braku żądania `createCheckoutSession` i braku otwartej sesji. Specyfikacja, w której gość zapłacił w aplikacji banku, a później kupuje inny koszyk, dodaje drugą sztukę, oczekuje kasy z obiema sztukami zamiast starego potwierdzenia oraz nowego checkoutu z własnym `checkoutId` za cały koszyk. Specyfikacja zalogowanej klientki, którą bank odsyła do przeglądarki, w której nie jest zalogowana, otwiera adres powrotu w nowym kontekście przeglądarki bez ciasteczek i magazynu, tak jak specyfikacja panelu robi to dla swoich kupujących, i oczekuje potwierdzenia i zamówienia zamiast toastu o niedokończonej płatności.
- Specyfikacje limitów kasy korzystają z tych samych narzędzi. Jedna przepisuje najbliższe żądanie `createCheckoutSession` przez `rewriteNextServerFunctionRequest`, żeby niosło podrobiony token Turnstile, i oczekuje toastu o zabezpieczeniu, braku otwartej sesji i sesji po naciśnięciu Try again. Druga otwiera checkouty dla jednego adresu e-mail z trzech kontekstów przeglądarki z własnym `cf-connecting-ip`, tak jak specyfikacja panelu robi to dla swoich kupujących, i oczekuje, że czwarty dostanie odmowę z toastem o otwartych checkoutach, a czwarta sesja nie powstanie. Specyfikacja koszyka podnosi linię do dziesięciu sztuk i oczekuje wyłączonego przycisku plusa i komunikatu o limicie.
- Limity e-maili, o które mogą poprosić odwiedzający, mają własne specyfikacje. Specyfikacja uwierzytelniania przepuszcza najbliższe żądanie `/api/auth/sign-up/email` przez `page.route` z podrobionym `x-turnstile-token`, oczekuje toastu o zabezpieczeniu i strony rejestracji, a potem wysyła formularz ponownie i oczekuje e-maila weryfikacyjnego, co dowodzi, że pierwsza próba nie utworzyła konta. Specyfikacja newslettera zapisuje jeden adres z czterech kontekstów przeglądarki z własnym `cf-connecting-ip`, żeby limit trzech na minutę na IP nie przeszkadzał, za każdym razem oczekuje odpowiedzi „sprawdź skrzynkę” i znajduje dla tego adresu trzy e-maile z potwierdzeniem przez `sentEmails` z `e2e/fixtures/emails.ts`. Przebieg całego zestawu w jednej przeglądarce prosi o około piętnaście takich e-maili, więc serwer testowy używany przez kilka przebiegów wymaga `bun run db:reset:test`, zanim dojdzie do sklepowego limitu 50 na dobę.
- Specyfikacja dotycząca unieważniania w czasie rzeczywistym zostawia gniazda aktywne i sama wywołuje zdarzenie, na przykład składając zamówienie, bo checkout publikuje katalog produktów do huba panelu. Zdarzenia z innych procesów testowych mogą nadejść w każdej chwili, więc sprawdza tylko to, czego nie są w stanie zmienić. Specyfikacja panelu otwiera w jednej przeglądarce dwie karty panelu z nasłuchem na kanale `marte-query-invalidation`, dodanym przez `context.addInitScript`, czeka przez `waitForServerFunctionResponse(page, id)` z `e2e/fixtures/server-functions.ts`, aż każda karta ponownie pobierze listę produktów, i oczekuje, że nasłuch nic nie odebrał, więc karty nie powielają między sobą zdarzeń z huba. Inny kontekst przeglądarki nie może publikować na tym kanale, więc inne procesy testowe nie zmienią wyniku. Specyfikacja nie liczy żądań listy produktów: drugie zdarzenie, które nadejdzie w trakcie ponownego pobierania, uruchamia je od nowa, więc liczba zależy od innych procesów testowych.
- Strona główna ukrywa każdą sekcję, dopóki nie wjedzie w widok, więc specyfikacja dociera do niej tak jak odwiedzający: `scrollUntilVisible(locator)` na obiekcie strony kręci kółkiem myszy, aż element stanie się widoczny.
- Specyfikacja smoke otwiera stronę główną, produkt, logowanie i dokumentację z nasłuchem `securitypolicyviolation` dodanym przez `page.addInitScript`, czeka na hydratację, sprawdza, że meta `csp-nonce` strony to nonce dopuszczony przez jej `Content-Security-Policy`, i oczekuje, że przeglądarka nie odmówiła niczego poza sondą `eval` w Zod. Polityka działa, zanim żądanie trafi do sieci, więc automatyczne blokowanie żądań na zewnątrz nie ukrywa odmowy. Strona, która zacznie ładować nowy zewnętrzny skrypt, ramkę, host obrazów albo API, nie przejdzie testu, dopóki host nie trafi do `src/lib/security-headers.ts`. Kolejny test smoke czyta nagłówki strony i pliku `/favicon.svg`, który serwuje `public/_headers`.
- E-mail odczytuj przez `waitForEmail`, a link z niego wyciągaj przez `linkIn`. Sprawdzaj origin linku, nie tylko ścieżkę: specyfikacje checkoutu, panelu administratora i newslettera sprawdzają, że potwierdzenie zamówienia, e-mail o wysyłce, powiadomienie sklepu o nowym zamówieniu i potwierdzenie newslettera linkują do `http://127.0.0.1:3000`, adresu używanego przez testy, specyfikacja panelu przechodzi linkiem z powiadomienia do zamówienia, a specyfikacja newslettera przechodzi linkiem na stronę potwierdzenia.

## Konwencje

- Jeden katalog `__test__/` na funkcjonalność, obok kodu: `src/modules/order/__test__/order.accessors.integration.test.ts`.
- Zestawy bazodanowe kończą się na `*.integration.test.ts`; wszystko, co renderuje Reacta, na `*.component.test.tsx`; pozostałe to zwykłe `*.test.ts`.
- Mockuj zewnętrznych dostawców. Stripe, Resend, Turnstile, InPost i R2 nigdy nie są wywoływane z testu; zestaw end-to-end rozmawia zamiast nich z emulatorami w testowym Workerze i z dublem widżetu Turnstile, który podaje fixture przeglądarki.
- Dane testowe są lokalne dla pliku testu albo dla katalogu `__test__` funkcjonalności. Do `src/platform/testing/` należy wyłącznie wspólna infrastruktura.
