Vite+ uruchamia Vitest 5 z konfiguracją z bloku `test` w `vite.config.ts`. Testy leżą w katalogu `__test__` obok kodu, który sprawdzają, i importują swoje API z `vite-plus/test`, nigdy z `vitest`:

```ts
import { describe, expect, it, vi } from "vite-plus/test"
```

Uruchamiaj je przez `bun run test`, a nie `bun test`. Własny runner Buna ignoruje projekty Vitest, środowisko jsdom i plik setup, więc duża część zestawu po cichu by się wysypała albo została pominięta.

## Trzy projekty

Zestaw jest dzielony po nazwie pliku, a każdy podział dostaje własne środowisko.

| Projekt       | Pliki                                                                                            | Środowisko | Plik setup                      |
| ------------- | ------------------------------------------------------------------------------------------------ | ---------- | ------------------------------- |
| `node`        | `src/**/*.{test,spec}.{ts,tsx}` poza dwoma wzorcami poniżej oraz `scripts/**/__test__/*.test.ts` | `node`     | brak                            |
| `integration` | `src/**/*.integration.test.{ts,tsx}`                                                             | `node`     | brak                            |
| `component`   | `src/**/*.component.test.{ts,tsx}`                                                               | `jsdom`    | `src/platform/testing/setup.ts` |

```sh
bun run test              # vp test run — wszystkie trzy projekty
bun run test:unit         # vp test run --project node
bun run test:integration  # vp test run --project integration
bun run test:component    # vp test run --project component
bun run test:changed      # vp test run --changed
bun run test:coverage     # vp test run --coverage
bun run test:all          # bun run test, a potem test:e2e:smoke
```

Repozytorium ma 1231 plików testowych: 623 testy komponentowe, 130 testów integracyjnych i 478 testów jednostkowych w projekcie `node`, w tym test hooka komunikatu commita w `scripts/__test__/`.

Projekt `integration` podnosi limity czasu testów i hooków do 30 sekund (`INTEGRATION_TEST_TIMEOUT_MS` w `vite.config.ts`). Plik setup projektu `component` ustawia własny limit czasu testu, 15 sekund.

`bun run test:watch` uruchamia `vp test watch`, który zostaje otwarty i po każdej zmianie ponownie uruchamia testy, których ona dotyczy. Samo `vp test` bez podkomendy uruchamia zestaw raz.

## Wspólna konfiguracja testów

Wszystko, co projekty mają ze sobą wspólne, leży w bloku `test` na najwyższym poziomie i jest dziedziczone przez `extends: true`:

| Ustawienie        | Wartość                                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `environment`     | `"node"` (projekt `component` nadpisuje to na `"jsdom"`)                                                                           |
| `env`             | `loadEnv("test", import.meta.dirname, "")` — wczytuje `.env.test`, który jest w repozytorium i zawiera wyłącznie wartości atrapowe |
| `pool`            | `"threads"`                                                                                                                        |
| `maxWorkers`      | `"50%"`                                                                                                                            |
| `isolate`         | `true`                                                                                                                             |
| `passWithNoTests` | `false`                                                                                                                            |
| `exclude`         | `node_modules/**`, `opensrc/**`, `dist/**`, `e2e/**`, `src/integrations/drizzle-orm/migrations/**`                                 |

Ponieważ `test.env` wczytuje `.env.test`, żaden test nie potrzebuje prawdziwych danych uwierzytelniających. Spośród skryptów testy ma tylko hook komunikatu commita: `scripts/__test__/commit-msg.test.ts` uruchamia `scripts/commit-msg.ts` przez `bun` na pliku z komunikatem, tak jak robi to `.vite-hooks/prepare-commit-msg`. `scripts/verify-build.ts` i pozostałe skrypty testów nie mają, a pokrycie liczy tylko `src/`.

### setup.ts

Plik setup projektu `component` rozszerza `expect` matcherami jest-dom, ustawia `asyncUtilTimeout` Testing Library na 5 sekund, a limit czasu testu na 15 sekund, i zapisuje każde `setTimeout` i `setInterval`, które uruchomi plik testowy, żeby `afterAll` wyczyściło te wciąż oczekujące i przywróciło natywne funkcje. Podstawia atrapy `IntersectionObserver`, `ResizeObserver` i `matchMedia` (których jsdom nie implementuje, a których oczekują komponenty oparte na GSAP i Lenis), daje `HTMLDialogElement` metodę `showModal`, która ustawia `open`, i `close`, która go usuwa i wysyła zdarzenie `close`, sprawia, że `document.elementFromPoint` zwraca `null`, a następnie łata TanStack Start:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
```

Podmienia też `getRequest` z `@tanstack/react-start/server` na atrapę zwracającą `new Request("http://127.0.0.1:3000/")`.

### Testowanie funkcji serwerowych

`withTestRpc` owija builder `createServerFn` w proxy. Przekazuje `inputValidator`, `middleware` i `validator` prawdziwemu builderowi i owija builder, który każde z nich zwraca, a przechwytuje `.handler()`, tak aby skompilowana funkcja serwerowa była wywoływana przez `runWithStartContext` ze sztucznym kontekstem startowym i prawdziwym wejściem `__executeServer`. Praktyczny skutek jest taki, że test wywołujący przypadek użycia faktycznie wykonuje jego walidator i middleware `authorized(...)` — infrastruktura testowa nie obchodzi kontroli autoryzacji, i o to właśnie chodzi, bo warstwa przypadków użycia jest miejscem, w którym autoryzacja żyje.

`setup.ts` należy tylko do projektu `component`. Zestaw `node` albo `integration`, który wywołuje funkcję serwerową, instaluje to samo proxy własnym `vi.mock(import("@tanstack/react-start"), …)`, tak jak robi to 28 zestawów.

`src/integrations/better-auth/__test__/use-case-authorization.test.ts` sprawdza tę zasadę we wszystkich przypadkach użycia. Czyta każdy plik `.ts` w katalogu `use-cases/` pod `src/modules/`: plik, który wywołuje `createServerFn`, musi zawierać `authorized(`, z wyjątkiem 24 publicznych przypadków użycia z jego listy dozwolonych, które nie mogą go zawierać, a żaden plik przypadku użycia nie może zawierać `assertAdmin(`, więc autoryzacja nigdy nie jest sprawdzana wewnątrz handlera. Każdy plik z listy dozwolonych musi istnieć.

### Testowanie komponentów

`renderWithProviders` renderuje komponent wewnątrz tych samych trzech dostawców, których używa aplikacja — `IntlProvider` z prawdziwymi komunikatami angielskimi i `I18N.DEFAULT_TIMEZONE`, `QueryClientProvider` z wyłączonymi ponowieniami oraz `RouterContextProvider` nad routerem z historią w pamięci — i zwraca wynik Testing Library wraz z utworzonymi `queryClient` i `router`, więc test może sprawdzać stan cache'u albo nawigację:

```ts
const { queryClient, router } = renderWithProviders(<ProductCard product={product} />)
```

`createTestRouter(path)` buduje router w pamięci; przekaż ścieżkę, gdy komponent zależy od bieżącej lokalizacji.

Komunikaty nie są danymi testowymi. `lib/messages.ts` zaciąga `messages/en-US/*.json` przez `import.meta.glob` z opcją `eager` i przepuszcza je przez własne funkcje aplikacji `buildMessageTree` i `toNamespace`. `IntlProvider` w `TestProviders` dostaje `onError`, który rzuca błąd, więc komponent proszący o brakujący albo zmieniony klucz tłumaczenia wysypuje swój test z `MISSING_MESSAGE`, zamiast wyświetlić ścieżkę klucza, jak domyślnie robi use-intl. Test, który owija drzewo we własny `IntlProvider`, na przykład żeby wyrenderować wersję polską, dziedziczy ten `onError` i musi przekazać każdą przestrzeń nazw, którą czyta komponent. Tę ochronę sprawdza `lib/__test__/render.component.test.tsx`.

### Testowanie kodu bazodanowego

Nie ma globalnego mocka D1. Każdy test integracyjny buduje własną bazę w pamięci i podmienia instancję Drizzle:

```ts
const { sqlite } = await vi.hoisted(async () => {
  const { DatabaseSync } = await import("node:sqlite")

  return { sqlite: new DatabaseSync(":memory:") }
})

vi.mock(import("~/src/integrations/drizzle-orm/drizzle.database"), async () => {
  const { drizzle } = await import("drizzle-orm/d1")
  const { createTestD1Database } = await import("~/src/platform/testing/mocks/d1")

  return { db: drizzle(createTestD1Database(sqlite)) }
})
```

`createTestD1Database` implementuje tyle powierzchni `D1Database`, ile potrzebuje Drizzle: `prepare`, `bind`, `all`, `raw`, `run` i `batch`. Tak jak D1, `bind` odrzuca instrukcję z więcej niż 100 parametrami, a baza odrzuca wzorzec `LIKE` lub `GLOB` dłuższy niż 50 bajtów, choć lokalne SQLite i Miniflare przyjęłyby jedno i drugie, więc test z danymi wielkości produkcyjnej wyłapuje instrukcję, która na D1 by się nie powiodła. Dlatego wielowierszowe inserty i zmiany rang są dzielone w `drizzle.batch.ts` i wysyłane w jednym `db.batch`, a lista identyfikatorów zbudowana w czasie działania jest wiązana jako jeden parametr JSON przez `inJsonList`; oba mechanizmy opisuje [Drizzle ORM i D1](/docs/integrations/drizzle-orm-d1). `batch` wykonuje wsady po kolei, tak jak D1, owija instrukcje w `begin` / `commit` i wycofuje je przy błędzie — i to właśnie czyni testy idempotencji checkoutu sensownymi, bo atomowa partia D1 jest ograniczeniem, na którym te testy się opierają. Opcjonalne wywołanie `onQuery` otrzymuje każdą parę `{ sql, params }`. `src/modules/product/__test__/product.accessors.integration.test.ts` zbiera je i sprawdza, ile instrukcji wykonuje operacja — jedną dla liczby produktów sklepu w każdej kategorii głównej, dwie dla zmiany rang 75 atrybutów, żadnej dla pustej zmiany kolejności — że żadna instrukcja nie wiąże więcej niż 100 parametrów i że lista 120 identyfikatorów produktów jest wiązana jako jeden parametr. Tak wyłapywane są regresje typu N+1 i przekroczenia limitu parametrów D1.

Opcjonalne wywołanie `onRoundTrip` liczy żądania, a nie instrukcje, bo partia pięciu instrukcji kosztuje D1 jedno żądanie, a pięć osobnych instrukcji kosztuje pięć. Otrzymuje `TestD1RoundTrip`: `{ kind: "batch", sql }` raz na każde wywołanie `batch`, gdzie `sql` to SQL instrukcji w kolejności, oraz `{ kind: "statement", sql: [sql] }` raz na każde `all`, `raw` lub `run` poza partią, także dla instrukcji wykonanej osobno po tym, jak niosła ją partia. Wywołuje się w chwili wysłania żądania, więc test, który sam trzyma obietnicę, na przykład jeszcze nierozwiązaną zamockowaną zależność, może w tym momencie odczytać zapisane żądania i zobaczyć, które wyszły przed nią. Nie pokaże natomiast, czy jedno żądanie do bazy czekało na inne: mock odpowiada na każdą samodzielną instrukcję od razu, więc `Promise.all` dwóch selectów Drizzle i dwa selecty, na które czeka się po kolei przez `await`, zapisują te same dwa żądania. Służy do liczenia osobnych żądań, a nie do mierzenia, jak głęboko się łańcuchują. `inventory-reservation.integration.test.ts` sprawdza nim, że cały koszyk jest rezerwowany w jednej partii z obiema pozycjami i że pusta lista nigdy nie dociera do bazy. `onQuery` nadal widzi każdą instrukcję, w partii czy poza nią.

Każdy zestaw sam tworzy tabele. 61 ze 130 zestawów integracyjnych odtwarza całą historię migracji przez `applyMigrationHistory` z `mocks/migrations.ts`, więc działa na schemacie, który produkują migracje. Pozostałych 69 buduje tabele własnymi instrukcjami `create table` przez `sqlite.exec(...)`, przez `createTables` z `src/modules/product/__test__/product-sqlite-schema.ts`, które wyprowadza je z definicji tabel Drizzle, przez `applyMigration` dla testowanej migracji, jak robią to zestawy uzupełnień danych w `src/modules/order/__test__/`, albo przez `applyMigrationHistoryBefore`, który odtwarza historię do testowanej migracji. Zmiana schematu wymaga więc migracji, a w zestawach, które piszą własne instrukcje `create table` dla tej tabeli, także aktualizacji tych instrukcji. Zestaw end-to-end również nakłada przy każdym uruchomieniu całą historię na świeżą bazę i to właśnie utrzymuje ją odtwarzalną.

Niezależnie od tego 28 z 39 plików schematów modułów ma w projekcie `node` plik `*.schema.test.ts`. 27 z nich czyta metadane tabeli Drizzle przez `getTableConfig` i sprawdza nazwę tabeli, pełną uporządkowaną listę kolumn oraz klucze obce razem z zachowaniem `onDelete`, a siedem z nich sprawdza też zadeklarowane relacje; `two-factor.schema.test.ts` sprawdza nazwę kolumny każdej właściwości przez `getTableColumns`. Te testy są powodem, dla którego zmiana nazwy kolumny w ich tabelach nie może przejść niezauważona.

| Metryka    | Próg |
| ---------- | ---- |
| Instrukcje | 100  |
| Linie      | 100  |

Pokryta jest każda instrukcja, gałąź, funkcja i linia, więc wszystkie cztery progi wynoszą 100 i każdy nowy kod przychodzi razem ze swoimi testami. `thresholds.autoUpdate` ma wartość `false`.

Testuj rzeczywiste zachowanie. Jeśli jakaś gałąź jest nieosiągalna, usuń gałąź, zamiast podstawiać atrapę globalnej wartości, żeby do niej dotrzeć.

## Testy end-to-end

Playwright steruje zbudowanym Workerem w Chromium i WebKicie. Zestaw leży w `e2e/`, a jego konfiguracja w `playwright.config.ts`:

```sh
bun run test:e2e:install  # jednorazowo: przeglądarki Chromium i WebKit
bun run test:e2e          # resetuje testową bazę, buduje testowego Workera, serwuje go i uruchamia wszystkie specyfikacje
bun run test:e2e:headed   # to samo z widocznymi oknami przeglądarki
bun run test:e2e:pr       # to samo tylko w Chromium, tak jak CI na pull requestach
bun run test:e2e:smoke    # e2e/specs/smoke.spec.ts w Chromium
bun run test:e2e:stripe   # projekt stripe-test-mode, który płaci kartą, BLIK-iem i Przelewy24 przez sandbox Stripe'a, gdy ustawione są jego klucze
bun run test:e2e:ui       # tryb UI Playwrighta
```

Projekty `chromium` i `webkit` pomijają wszystkie `e2e/specs/*stripe-test-mode.spec.ts`, które uruchamia tylko projekt `stripe-test-mode`, więc domyślny zestaw nigdy nie wywołuje Stripe'a. Zobacz [Tryb testowy Stripe](#tryb-testowy-stripe).

Poza CI `webServer` Playwrighta sam uruchamia `db:reset:test`, `build:test` i `start:test` oraz używa serwera, który już słucha na porcie 3000; w CI bazę i build przygotowuje przepływ, a Playwright tylko uruchamia serwer. `webServer` ma dziesięć minut na odpowiedź pod `PLAYWRIGHT_BASE_URL`, domyślnie `http://127.0.0.1:3000`.

Każdy test ma 60 sekund, tak samo każda nawigacja; asercje web-first czekają do 10 sekund. Przeglądarki działają z językiem `en-US` i strefą czasową `Europe/Warsaw`, a dwa procesy testowe uruchamiają testy w pełni równolegle. W CI nieudany test jest ponawiany dwa razy, `test.only` przerywa przebieg, a Playwright zachowuje ślad pierwszego ponowienia oraz nagranie i zrzut ekranu każdego błędu; lokalnie nic nie jest ponawiane, a dla każdego błędu zostają ślad i zrzut ekranu.

### Projekty

`playwright.config.ts` definiuje sześć projektów:

| Projekt                                  | Uruchamia                                                                  | Zależy od                         |
| ---------------------------------------- | -------------------------------------------------------------------------- | --------------------------------- |
| `setup`                                  | `*.setup.ts`, który loguje zaseedowanego administratora i klienta          | —                                 |
| `chromium`, `webkit`                     | wszystkie `*.spec.ts` poza `*stripe-test-mode.spec.ts`, w pełni równolegle | `setup`                           |
| `stripe-test-mode`                       | `*stripe-test-mode.spec.ts`, w sandboxie Stripe'a                          | —                                 |
| `chromium-shop-wide`, `webkit-shop-wide` | wszystkie `*.shop-wide.ts`                                                 | odpowiednio `chromium` i `webkit` |

Specyfikacja ogólnosklepowa zmienia stan, który czytają wszystkie inne specyfikacje, na przykład przełącznik sprzedaży, więc nie może działać obok nich. Playwright uruchamia projekty fazami i zaczyna fazę dopiero po zakończeniu poprzedniej, więc projekt ogólnosklepowy startuje po wszystkich zestawach przeglądarkowych w danym uruchomieniu, nie tylko po swoim. Jego testy biorą też blokadę `shop-wide`, dzięki której projekty ogólnosklepowe Chromium i WebKita, należące do tej samej fazy, nie działają jednocześnie. Wybranie projektu ogólnosklepowego zawsze najpierw uruchamia w całości projekt jego przeglądarki, bo Playwright uruchamia zależności projektu niezależnie od filtra plików. `bun run test:e2e` uruchamia wszystkie sześć projektów, `test:e2e:pr` wybiera `chromium` i `chromium-shop-wide`, a `e2e-reusable.yml` wybiera `<browser>` i `<browser>-shop-wide` (zobacz [CI/CD](/docs/tooling/ci-cd#przepływy-end-to-end)).

### Testowy Worker

`wrangler.jsonc` ma środowisko `test`, którego `main` to `src/platform/testing/worker.ts`. Jego baza D1, przestrzeń KV i zasobnik R2 ustawiają `remote: false`, jego Durable Object oraz kolejki dziennika audytu i newslettera, nazwane z przyrostkiem `-test`, też działają lokalnie, bo `vite.config.ts` włącza zdalne bindingi tylko dla `development`, a stan lokalny jest zapisywany w `.wrangler/test`. Poza opisanymi niżej punktami `/__test/` Worker przekazuje każde żądanie i każdą partię kolejki aplikacji z `src/server.ts` i re-eksportuje jej Durable Object `RealtimeInvalidationHub`. `bun run build:test` buduje go z `CLOUDFLARE_ENV=test` i `--mode test`, więc każdy sekret pochodzi z commitowanego `.env.test`. Powiadomienie sklepu o nowym zamówieniu trafia na jego `RESEND_EMAIL_FROM`, `noreply@example.test`, czyli `ORDER_NOTIFICATION_INBOX` z `e2e/data/accounts.ts`, więc każde zamówienie złożone przez specyfikację wysyła tam też to powiadomienie, a alerty sklepu o incydentach trafiają tam również.

Testowy Worker instaluje `src/platform/testing/mocks/providers.ts`, zanim wczyta aplikację, więc nic nie opuszcza maszyny:

- **Resend.** Żądania do `api.resend.com` są przechwytywane zamiast wysyłane, zarówno pojedyncze wysyłki, jak i wysyłki wsadowe newslettera, razem z nagłówkami każdego e-maila. `GET /__test/emails?to=<adres>` zwraca przechwycone wiadomości do danego odbiorcy. `POST /__test/emails/refusals?to=<adres>` sprawia, że emulator odpowiada na każdą pojedynczą wysyłkę na ten adres błędem Resend `internal_server_error`, dopóki `DELETE` na ten sam adres tego nie zakończy; opakowują to `refuseEmailsTo` i `acceptEmailsTo` w `e2e/fixtures/emails.ts`. Tak jak Resend, na wysyłkę z `Idempotency-Key`, który już przechwycił, odpowiada identyfikatorem pierwszego e-maila i niczego nowego nie przechwytuje. Specyfikacja newslettera wysyła do wszystkich potwierdzonych subskrybentów we wspólnej testowej bazie, więc sprawdza tylko adresy, które sama zapisała.
- **Stripe.** Żądania do `api.stripe.com` wysłane z kluczem z `.env.test`, `sk_test_local_fixture`, trafiają do działającego w pamięci emulatora wywołań, które wykonuje serwer: sesji Checkout (tworzenie, odczyt, lista, wygaszanie), kuponów, klientów (tworzenie, aktualizacja, która zmienia adres e-mail, jaki dostają późniejsze sesje tego klienta, i usuwanie, które odłącza ich metody płatności), payment intentów, metod płatności (lista dla klienta, odczyt, odłączanie), SetupIntentów i zwrotów (tworzenie i lista dla payment intentu, która zwraca utworzone przez emulator zwroty). Każde inne wywołanie Stripe'a dostaje 400, więc nowe użycie Stripe'a oblewa specyfikację, zamiast przejść po cichu. Tak jak Stripe, emulator odrzuca sesję Checkout, której `expires_at` jest bliżej niż za 30 minut albo dalej niż za 24 godziny, i trzyma w sesji `created` oraz `expires_at`, żeby specyfikacja mogła sprawdzić czas rezerwacji. Odczyt, który prosi o rozwinięcie `payment_intent`, dostaje payment intent sesji w treści odpowiedzi, tak jak zwraca go Stripe. `GET /__test/stripe/checkout-sessions?email=<adres>` wypisuje sesje otwarte dla kupującego, a `openCheckoutSessions` z `e2e/fixtures/stripe.ts` zawęża je do tych wciąż otwartych, a `POST /__test/stripe/checkout-sessions/<id>/complete` oznacza jedną jako opłaconą i zwraca zdarzenie `checkout.session.completed` podpisane `STRIPE_WEBHOOK_SECRET`. `POST /__test/stripe/checkout-sessions/<id>/expire` tak samo wygasza sesję i zwraca podpisane zdarzenie `checkout.session.expired`, które `expireCheckoutSession` z `e2e/fixtures/stripe.ts` dostarcza do webhooka. `POST /__test/stripe/checkout-sessions/<id>/dispute` zwraca podpisane zdarzenie `charge.dispute.created`, spór o oszustwo czekający na odpowiedź, dla payment intentu opłaconej sesji, a `disputeCheckoutPayment` z `e2e/fixtures/stripe.ts` je dostarcza, więc zamówienie zostaje oznaczone jako sporne przez prawdziwy webhook. `POST /__test/stripe/checkout-sessions/<id>/await-blik-approval` daje sesji payment intent BLIK czekający na zatwierdzenie w aplikacji banku (`requires_action` z `blik_authorize`), a `POST /__test/stripe/checkout-sessions/<id>/decline-blik-approval` sprawia, że bank go odrzuca (`requires_payment_method`); wywołują je `awaitBlikApproval` i `declineBlikApproval` z `e2e/fixtures/stripe.ts`, więc specyfikacja może przeładować kasę, gdy bank jeszcze decyduje. `GET /__test/stripe/setup-intents?email=<adres>` wypisuje SetupIntenty na kartę otwarte ze strony konta, a `POST /__test/stripe/setup-intents/<id>/succeed` zastępuje przeglądarkowe `stripe.confirmSetup`: dołącza do klienta kartę Visa kończącą się na 4242 i oznacza SetupIntent jako udany. `GET /__test/stripe/customers?email=<adres>` wypisuje klientów, którzy wciąż istnieją dla kupującego, a `stripeCustomerIds` z `e2e/fixtures/stripe.ts` odczytuje ich, żeby sprawdzić, że usunięcie konta usunęło jego klienta Stripe.
- **InPost ShipX.** Żądania do `sandbox-api-shipx-pl.easypack24.net`, API wywoływanego we wszystkich środowiskach poza produkcją, trafiają do działającego w pamięci emulatora: utworzenie przesyłki odpowiada statusem `created` bez numeru do śledzenia, pierwszy jej odczyt ją potwierdza i nadaje numer zaczynający się od `6026772171316303`, a jej etykieta to mały PDF po potwierdzeniu i 400 przed nim. `.env.test` ustawia zastępcze `INPOST_API_TOKEN` i `INPOST_ORGANIZATION_ID`, więc strona zamówienia w panelu oferuje przesyłki InPost w testowym buildzie.
- **Punkty InPost.** Zapytania serwera o punkty w `api-pl-points.easypack24.net` (`/v1/points/<nazwa>`) dostają odpowiedź od `emulateInpostPoints` z `src/platform/testing/mocks/inpost-points.ts`: `WAW01M` i `WAW02M`, paczkomaty, które proponuje wyszukiwanie punktów w przeglądarce, są na liście, `WAW503` odpowiada 503, jakby InPost nie działał, a każda inna nazwa odpowiada 404. `INPOST_POINTS` w `e2e/data/inpost.ts` nazywa punkt z listy, punkt bez odpowiedzi i punkt spoza listy, a `lockerCheckoutDraft` w `e2e/fixtures/checkout-draft.ts` buduje zapisany checkout, który wskazuje jeden z nich dla metody paczkomatowej.

Specyfikacja wysyła to podpisane zdarzenie do `/api/webhooks/stripe` tak jak Stripe, więc trasa webhooka weryfikuje podpis, przyjmuje zdarzenie z `livemode: false`, jak wymaga środowisko `test`, i realizuje zamówienie prawdziwym kodem. `completeCheckoutSessionBeforeItsWebhook` z `e2e/fixtures/stripe.ts` oznacza sesję jako opłaconą i zwraca podpisane zdarzenie, nie wysyłając go, a `deliverStripeEvent` wysyła je później, więc specyfikacja może przeładować kasę, gdy Stripe zgłasza już sesję jako `complete`, a zamówienie jeszcze nie istnieje. Strona powrotu sama składa wtedy zamówienie, więc specyfikacja, która przeładowuje kasę przed webhookiem, oczekuje zamówienia i e-maila z potwierdzeniem, zanim dostarczy zdarzenie, a po nim nadal jednego e-maila z potwierdzeniem. Sam formularz płatności, czyli Stripe.js z obsługą karty, BLIK-a i Przelewy24, sprawdza tylko projekt [Tryb testowy Stripe](#tryb-testowy-stripe).

InPost wywołuje przeglądarka, nie Worker: wybór paczkomatu pyta `api-pl-points.easypack24.net/v1/points?city=<miasto>` o punkty w danym mieście. Izolacja sieci w `e2e/fixtures/test.ts` odpowiada na to wyszukiwanie przez `e2e/fixtures/inpost.ts` paczkomatami z `e2e/data/inpost.ts`, których miasto się zgadza, w kształcie odpowiedzi InPostu, więc wybór paczkomatu je wypisuje, a specyfikacja może jeden wybrać. Styl i kafelki mapy zostają zablokowane, więc specyfikacja wybiera paczkomat z listy obok mapy, a nie ze znacznika.

### Tryb testowy Stripe

Cztery specyfikacje płacą w prawdziwym Payment Element w sandboxie Stripe'a. Każdy test to gość (albo, raz, nowe konto) z własnym adresem e-mail i własną sesją Checkout, więc testy działają równolegle i nie zależą od siebie. Działają tylko wtedy, gdy `STRIPE_SECRET_KEY` (`sk_test_` albo `rk_test_`) i `VITE_STRIPE_PUBLISHABLE_KEY` (`pk_test_`) są ustawione w środowisku na klucze inne niż atrapy z `.env.test`; w przeciwnym razie Playwright zgłasza je jako pominięte z tym powodem.

| Specyfikacja                          | Czym płaci i czego oczekuje                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stripe-test-mode.spec.ts`            | Testowa karta Stripe'a 4242 4242 4242 4242: jako gość oraz jako zalogowany kupujący, który wpisuje w kasie inny adres e-mail.                                                                                                                                                                                                                                                                                                                                                                                                       |
| `card.stripe-test-mode.spec.ts`       | Karty odmowy 4000 0000 0000 0002 (odmowa ogólna), …9995 (brak środków), …0069 (karta wygasła) i …0127 (błędny kod CVC), po każdej 4242 w tej samej sesji; niepełny numer karty; przycisk płatności osiągnięty klawiaturą i naciśnięty przed wpisaniem jakiejkolwiek karty, na co Stripe odpowiada oznaczeniem brakującego numeru karty; oraz karta 3D Secure 4000 0027 6000 3184, której weryfikację kupujący kończy (obciążenie zgłasza `three_d_secure.result` równe `authenticated`), oblewa albo zamyka przyciskiem **Cancel**. |
| `blik.stripe-test-mode.spec.ts`       | Kod BLIK 123456, który sandbox zatwierdza po około dziesięciu sekundach, oraz trzy błędy, które Stripe symuluje na podstawie adresu e-mail z danych kontaktowych: `invalid_code` (odrzucony od razu), `customer_declined` (po około ośmiu sekundach, a potem opłacony kartą w tej samej sesji) i `customer_timeout` (gdy minie czas na zatwierdzenie). `stripeOutcomeEmail` z `e2e/fixtures/unique.ts` buduje adres, którego część przed `@` kończy się nazwą wyniku, jak wymagają wzorce Stripe'a (`.*customer_declined@.*` itd.). |
| `przelewy24.stripe-test-mode.spec.ts` | Przelewy24 z mBankiem wybranym z listy banków, z odpowiedzią na testowej stronie płatności Stripe'a **Authorize test payment** albo **Fail test payment**.                                                                                                                                                                                                                                                                                                                                                                          |

Każda odrzucona płatność musi zostawić kupującego w kroku płatności z komunikatem samego Stripe'a, nigdy z komunikatem sklepu „Ta sesja płatności jest już nieaktywna.”, a `expectPaymentRefusedOnSession` z `e2e/fixtures/stripe-test-mode.ts` sprawdza, że trzymana jest wciąż ta sama sesja (wpis `marte-checkout-session` w local storage), koszyk jest nadal w podsumowaniu, przycisk płatności wrócił zamiast **Przetwarzanie…**, a Stripe zgłasza sesję jako `open` z płatnością `requires_payment_method`, której `last_payment_error` ma udokumentowany kod. Po odmowie karty Payment Element oznacza numer karty powodem podanym przez Stripe'a i trzyma przycisk płatności nieaktywny, dopóki kupujący nie zmieni karty, co jest zachowaniem Stripe'a, więc specyfikacje płacą ponownie, wpisując w to pole 4242. W specyfikacjach karty, BLIK-a i Przelewy24 każda płatność, która przechodzi, także ta drugą kartą po odmowie, kończy się w `expectOrderPaidOnSession`: na stronie potwierdzenia tej samej sesji z numerem zamówienia. Nieudana płatność Przelewy24 wraca z banku do kroku płatności z komunikatem „Płatność nie została dokończona. Wybierz metodę płatności, aby spróbować ponownie.” i z koszykiem; krok zastępuje wtedy zwróconą sesję, którą Stripe zgłasza jako `expired`, otwartą sesją tego samego checkoutu, a specyfikacja opłaca ją kartą i oczekuje jednego e-maila z potwierdzeniem.

`CheckoutPage` z `e2e/pages/checkout-page.ts` obsługuje ramki Stripe'a: `fillCard` i `fillBlikCode` wypełniają Payment Element, `answerThreeDSecure` naciska **Complete** albo **Fail** na testowej stronie 3D Secure Stripe'a w ramce weryfikacji, a `cancelThreeDSecure` naciska **Cancel** w tej ramce, za każdym razem dopiero gdy strona testowa przestanie się przesuwać, i ponownie, jeśli przycisk po dziesięciu sekundach nadal tam jest, bo naciśnięcie, gdy Stripe dopiero otwiera weryfikację, nic nie robi, a `payWithPrzelewy24` wybiera bank przed zapłatą, bo do wyboru banku przycisk płatności pozostaje nieaktywny.

Te same dwie zmienne muszą być ustawione przy budowaniu testowego Workera. Build przedkłada środowisko procesu nad `.env.test`, więc pakiet klienta dostaje klucz publiczny, a Worker klucz tajny, a emulator Stripe'a, który odpowiada tylko na `sk_test_local_fixture`, przepuszcza wywołania Workera do Stripe'a. E-maile nadal są przechwytywane. Każda specyfikacja ustawia `test.use({ reachableOrigins: [STRIPE_ORIGINS] })`, więc przeglądarka może wczytać Stripe.js i jego ramki z `stripe.com`, `stripe.network`, `stripecdn.com` i `hcaptcha.com` oraz przejść przekierowanie Przelewy24 przez `payments.stripe.com` i `checkout.stripe.com` z powrotem do sklepu.

Stripe nie dosięgnie Workera na `127.0.0.1`, więc `forwardCheckoutCompletion` z `e2e/fixtures/stripe-test-mode.ts` robi to, co `stripe listen`: odczytuje zdarzenie `checkout.session.completed` sesji z Events API Stripe'a, podpisuje je `STRIPE_WEBHOOK_SECRET`, z którym zbudowano Workera (ze środowiska, a w przeciwnym razie z `.env.test`), i wysyła je do `/api/webhooks/stripe`. Testy, które sprawdzają cały zakup, czyli płatność gościa kartą w `stripe-test-mode.spec.ts`, zatwierdzony kod BLIK i autoryzowana płatność Przelewy24, oczekują strony potwierdzenia z numerem zamówienia i e-maila z potwierdzeniem, który podaje metodę płatności, zanim cokolwiek przekażą, bo strona powrotu składa zamówienie, gdy tylko Stripe zgłosi sesję jako opłaconą. Potem przekazują zdarzenie, oczekują, że Stripe zgłosi sesję jako opłaconą na 398,99 zł, a po przeładowaniu nadal jednego zamówienia i jednego e-maila z potwierdzeniem.

Specyfikacja zalogowanego kupującego zakłada konto i dochodzi do kroku płatności z adresem e-mail konta, co tworzy klienta Stripe tego konta z tym adresem. Potem zmienia w kroku danych kontaktowych adres na inny, czeka na zastępczą sesję i opłaca ją kartą. Oczekuje, że strona potwierdzenia poda nowy adres i że e-mail z potwierdzeniem do niego dotrze, że przekazana sesja należy do klienta Stripe i zgłasza nowy adres jako `customer_details.email` oraz że na adres konta nie przyjdzie żadne potwierdzenie. Bez aktualizacji w `ensureStripeCustomerWithEmail` Stripe rozliczyłby tę płatność pod adresem konta.

Użyj kluczy sandboxa Stripe'a bez endpointu webhooka i z włączonymi w ustawieniach metod płatności kartami, BLIK-iem i Przelewy24: sesje Checkout korzystają z dynamicznych metod płatności, więc metody wyłączonej w sandboxie brakuje w Payment Element, a jej specyfikacje nie przechodzą. Endpoint wskazujący Workera preview też dostałby te płatności, ale ich zdarzenia tylko zaloguje i potwierdzi, bo ich metadane `deployment` wskazują `martebizuteria-test` (zobacz [Płatności: punkt końcowy webhooka](/docs/features/payments#punkt-końcowy-webhooka)); osobny sandbox trzyma płatności testowe z dala od konta preview i jego dziennika zdarzeń. Lokalnie najpierw zatrzymaj serwer na porcie 3000, bo poza CI Playwright używa już działającego, a wcześniejszy build ma atrapowe klucze, i ustaw klucze tylko dla tego polecenia:

```sh
STRIPE_SECRET_KEY=sk_test_… VITE_STRIPE_PUBLISHABLE_KEY=pk_test_… bun run test:e2e:stripe
```

Testowy Worker zbudowany z nimi wysyła każde wywołanie Stripe'a do Stripe'a, więc pozostałe specyfikacje, które rozliczają płatności przez emulator, na nim nie przejdą. W CI zadanie `stripe-test-mode` w `e2e-full.yml` uruchamia ten projekt przy każdym przebiegu tego przepływu — po każdym pushu do `main`, w harmonogramie w poniedziałki o 03:15 UTC i przy ręcznym uruchomieniu — na własnym testowym Workerze zbudowanym z sekretami repozytorium `E2E_STRIPE_SECRET_KEY` i `E2E_STRIPE_PUBLISHABLE_KEY`; zobacz [CI/CD](/docs/tooling/ci-cd#przepływy-end-to-end).

### Dane

`bun run db:reset:test` usuwa `.wrangler/test`, nakłada całą historię migracji przez `wrangler d1 migrations apply --local --persist-to .wrangler/test` (`db:migrate:test`) i uruchamia `scripts/seed-test.ts` (`db:seed:test`). Seed wczytuje te same pliki katalogu co `db:seed:preview` (dwa naszyjniki ze stanem, kategorie, kolekcje, atrybuty i metody dostawy) oraz trzy zweryfikowane konta z `e2e/data/accounts.ts`: `admin@marte.example.test`, `new-admin@marte.example.test` i `customer@marte.example.test`. Pierwszy administrator ma włączone uwierzytelnianie dwuskładnikowe: seed zapisuje `ADMIN_TOTP_SECRET` w `two_factor`, zaszyfrowany `AUTH_SECRET` z `.env.test`, tak jak oczekuje tego testowy Worker. `new-admin@marte.example.test` ma je wyłączone, więc specyfikacja może pokazać, że taki administrator trafia na `/admin/security`. Klient ma zapisaną strefę czasową `Europe/Warsaw`, więc lista stref w profilu otwiera się na zapisanym wyborze, a nie na opcji Automatycznie. Seed łączy pliki katalogu i instrukcje kont w jeden plik SQL i uruchamia go przez `wrangler d1 execute DB --env test --local --persist-to .wrangler/test`.

Administratorzy muszą używać uwierzytelniania dwuskładnikowego tylko wtedy, gdy tryb Vite to `production` albo `test` (`isAdminTwoFactorRequired` w `src/integrations/better-auth/auth.access.ts`), więc testowy Worker, budowany z `--mode test`, wymusza je tak jak produkcja, a buildy preview i development nie.

### Pisanie specyfikacji

- Importuj `test` i `expect` z `e2e/fixtures/test.ts`. Jego automatyczne fixtures blokują każde żądanie, które nie idzie do lokalnej aplikacji (obrazy dostają PNG 1×1, wyszukiwanie punktów InPostu dostaje paczkomaty z `e2e/data/inpost.ts`, reszta jest przerywana), i oblewają test, którego strony zalogują brakujące lub błędne tłumaczenie. Specyfikacja, która musi dosięgnąć innego originu, wymienia go w opcji `reachableOrigins`; robią to tylko cztery specyfikacje trybu testowego Stripe'a.
- Każdy test wysyła własny `cf-connecting-ip`, więc limity na IP przy logowaniu, rejestracji i checkoucie nigdy nie wiążą testów ze sobą.
- Projekt `setup` raz loguje zaseedowanego administratora i klienta i zapisuje ich sesje w `playwright/.auth/`; używaj ich przez `test.use({ storageState: STORAGE_STATE.admin })`. Administrator odpowiada na wyzwanie dwuskładnikowe kodem `currentTotpCode(ADMIN_TOTP_SECRET)` z `e2e/fixtures/totp.ts`, przez `AuthPage.enterTwoFactorCode`. Nigdy nie wylogowuj zaseedowanego konta, nie zmieniaj jego hasła ani nie wyłączaj mu uwierzytelniania dwuskładnikowego w specyfikacji, bo te sesje współdzielą wszyscy workerzy, i nigdy nie włączaj go dla `new-admin@marte.example.test`, którego specyfikacja oczekuje, że jest wyłączone.
- Specyfikacja, która zmienia konto, zamówienie albo kupon, tworzy własne: `registerCustomer` rejestruje i weryfikuje nowego klienta, `uniqueEmail` i `uniqueCode` nazywają dane, a `placeOrder` kupuje produkt i płaci za niego przez emulator. Specyfikacje działają w pełni równolegle i nie mogą zależeć od liczb, które zmieniają inne specyfikacje.
- Specyfikacja, która zmienia coś, co czytają wszystkie inne, na przykład przełącznik sprzedaży, zepsułaby specyfikacje działające obok niej, więc trafia do pliku `*.shop-wide.ts` zamiast `*.spec.ts` i owija swoje testy w `test.describe(title, { lock: "shop-wide" }, …)` (zobacz [Projekty](#projekty)). Są trzy takie. W `e2e/specs/sales.shop-wide.ts` administrator wstrzymuje sprzedaż na pulpicie przez `setSalesPaused` z `AdminDashboardPage`, a zalogowany klient w drugim kontekście przeglądarki widzi, jak komunikat pojawia się bez przeładowania na otwartej stronie produktu, a potem na przeglądzie konta, w dokumentacji, w kasie, która pokazuje „Orders are paused”, oraz w koszyku, który mówi, że kasa jest zamknięta, i nie ma odnośnika do kasy. Gdy administrator wznowi sprzedaż, komunikat znika z otwartego koszyka, odnośnik do kasy wraca i prowadzi do kroku kontaktu, a strony konta i dokumentacji wczytują się bez komunikatu. `afterEach` z powrotem wyłącza przełącznik, więc nieudane uruchomienie nie zostawia sklepu wstrzymanego na następne. ## Konwencje

- Katalog `__test__/` leży w katalogu kodu, który pokrywa, więc pod `src/` jest ich 221: `src/modules/order/__test__/order.accessors.integration.test.ts`.
- Zestawy bazodanowe kończą się na `*.integration.test.ts`; wszystko, co potrzebuje DOM-u albo API przeglądarki z jsdom, na `*.component.test.tsx`, albo `*.component.test.ts`, gdy plik nie ma JSX; pozostałe to zwykłe `*.test.ts`, albo `*.test.tsx`, gdy renderują Reacta bez DOM-u, jak szablony e-maili przez `render` z react-email i testy renderowania na serwerze przez `renderToString`.
- Mockuj zewnętrznych dostawców. Stripe, Resend, InPost i R2 nigdy nie są wywoływane z testu; zestaw end-to-end rozmawia zamiast nich z emulatorami w testowym Workerze i z atrapą InPostu w przeglądarce. Jedynym wyjątkiem jest projekt [Tryb testowy Stripe](#tryb-testowy-stripe), który wywołuje sandbox Stripe'a, gdy ustawione są jego klucze, a w CI są one ustawione w każdym przebiegu E2E (full).
- Dane testowe są lokalne dla pliku testu albo dla katalogu `__test__` funkcjonalności. Do `src/platform/testing/` należy wyłącznie wspólna infrastruktura.
