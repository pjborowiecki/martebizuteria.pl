M'Arte is a full-stack jewellery shop: a Polish-language storefront, a customer account area and an admin console, served from one Cloudflare Worker. The repository is the whole product — there is no separate backend, no separate admin app and no separate CMS. `src/server.ts` is the single entry point, and everything the shop does happens behind it.

The codebase exists for two reasons at once. It runs a real jewellery brand's shop, and it is written as a study in how far a commerce application can be pushed on a runtime with no filesystem, no long-lived Node process and no interactive database transactions. Most of the design decisions documented in [Architecture](/docs/architecture) trace back to those constraints rather than to taste.

## The shop

| Fact                | Value                                                                                                                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Locales             | `pl-PL` (default, no URL prefix) and `en-US` — `I18N` in `src/integrations/use-intl/i18n.config.ts`                                                                                    |
| Time zone           | `Europe/Warsaw` for the shop itself: the year in order numbers and the Polish legal deadlines. Dates on screen follow each viewer's own time zone                                      |
| Currency            | `PLN` only — `STORE_CURRENCY_CODE` in `src/modules/_core/constants/currency.ts`                                                                                                        |
| Payment             | Stripe, card and Stripe-hosted methods, webhook-driven fulfilment                                                                                                                      |
| Delivery            | Rows of the `delivery_method` table managed in Settings, seeded as InPost parcel locker, InPost courier and pickup at the atelier in Bochnia, with an optional free delivery threshold |
| Transactional email | Resend, nineteen React Email templates in `src/presentation/emails/`                                                                                                                   |
| Worker name         | `martebizuteria` in production, `martebizuteria-preview`, `martebizuteria-development`, and `martebizuteria-test`, which runs only locally for the end-to-end suite                    |

`wrangler.jsonc` attaches `preview.martebizuteria.pl` to the preview Worker as a custom domain and keeps both Workers on their `*.workers.dev` hostnames; the production Worker gets `martebizuteria.pl` when the shop goes live. The production URL recorded in `package.json` is `https://martebizuteria.pl`, the canonical address `APP_URL` gives every page.

## One Worker, one route tree

Route files live flat in `src/routes/` and carry no locale segment. The router de-localizes the URL before matching and re-applies the prefix when generating links, so `_storefront.products.index.tsx` serves both `/products` (Polish, the default locale, which takes no prefix) and `/en-US/products`. Path segments themselves are never translated. See [i18n architecture](/docs/architecture/i18n-architecture) for the mechanism.

## Bindings

`wrangler.jsonc` declares the same six application bindings in all four environments — `development`, `preview`, `test` and `production` — plus `ASSETS`, which serves the static files in `./public`:

| Binding                     | Resource         | Used for                                                                                                                                                                          |
| --------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DB`                        | D1 database      | Every table — 42, including the `storefront_search` FTS5 index                                                                                                                    |
| `IMAGES`                    | R2 bucket        | Product image uploads                                                                                                                                                             |
| `CACHE`                     | KV namespace     | The email sender flag (`resend.availability.server.ts`), the keys that limit incident alerts to one per incident (`src/lib/incident-alert.server.ts`) and the `/api/health` probe |
| `AUDIT_LOG_QUEUE`           | Cloudflare Queue | Audit events, drained by the `queue` handler in `src/server.ts`; a batch that still fails moves to its dead-letter queue                                                          |
| `NEWSLETTER_QUEUE`          | Cloudflare Queue | Newsletter batches, sent by the same `queue` handler, one batch at a time, with a dead-letter queue                                                                               |
| `REALTIME_INVALIDATION_HUB` | Durable Object   | WebSocket fan-out for realtime cache invalidation                                                                                                                                 |

## What works, and what does not

Being precise about the boundary is more useful than a feature list.

### Wired end to end

Catalog (products, variants, options, attributes, categories, collections, search, filtering, pagination), the cart kept in the browser with live availability and price checks, the four-step checkout, discount codes (percentage, fixed amount or free shipping) checked at checkout, recomputed on the server, held for the open checkout so usage limits hold under concurrent checkouts, applied to the Stripe session as a one-off coupon and recorded in `discount_redemption` with the order, Stripe payment with webhook-driven fulfilment, inventory reservation with compensation, order placement, delivery to an InPost parcel locker, by courier or by pickup at the atelier, with delivery methods named in both languages and a free delivery threshold, both set in Settings, order fulfilment from the admin console — starting work, shipping with an optional tracking number that can be added or corrected later, and marking delivery, each announced to the customer by e-mail and each undoable one step at a time without one — InPost shipments booked through ShipX or, without its credentials, by hand in InPost Manager with the tracking number linked to InPost's tracking page, and parcels with another carrier shipped by hand with the tracking number and link the admin enters, refunds issued from the admin console or in Stripe, with the items returned to stock only when the admin says they came back, withdrawals from a contract sent online, customer accounts (orders, addresses, sessions, profile, two-factor sign-in with backup codes, a password added to an account created with Google), guest orders filed under the verified account with the same e-mail address, display preferences per user (a time zone and a format locale for dates, prices and numbers, detected when not chosen), a wishlist kept in the `wishlist_item` table, saved cards attached at checkout to the customer's Stripe customer and removable from `/account/payment`, transactional email in both locales, the double opt-in newsletter with campaigns sent through a Cloudflare Queue, the audit log behind a Cloudflare Queue, a daily clean-up that deletes or anonymises personal data once its retention period ends, realtime cache invalidation over WebSockets, and admin management of products, categories, collections, attributes, customers, orders, discount codes, delivery methods, the seller's details, who has admin access, the terms of service, privacy policy, returns and FAQ pages, newsletter subscribers, and audit.

### Scaffolded, not finished

| Area           | State                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| InPost         | Parcel-locker lookup at checkout (`fetchPointsByCity`) and ShipX shipments, labels and tracking from the admin order page; InPost's status does not move the order |
| Admin settings | The admin's own account, the shop's details, its delivery and its team; staff notifications are not there yet                                                      |

### Absent

Pull requests never load Stripe.js: payments by card, BLIK and Przelewy24 in Stripe's real Payment Element are exercised only by the `stripe-test-mode` project, which the **E2E (full)** workflow runs against a Stripe sandbox on every push to `main`, weekly and by hand. No reconciliation job: the only Cron Trigger runs the [retention clean-up](/docs/guides/data-retention), which releases no stock. An audit entry that still cannot be written after the dead-letter queue retries it on its own is dropped, although the failures email `RESEND_EMAIL_FROM`. No third-party error reporting service: failures go to Workers Logs and Issues, and the ones the owner must act on to `RESEND_EMAIL_FROM`; see [Monitoring and alerts](/docs/guides/monitoring-and-alerts).

[Roadmap](/docs/project/roadmap) lists these in the order they are worth fixing.

## How the code is written

Four conventions are visible within the first file you open. They are house rules that review keeps, not lint rules:

- **Modules own tables.** `src/modules/{feature}/` holds the Drizzle table, the Zod schemas, the query-key tuples, the inferred types, the pure helpers and the accessors for exactly one table. One operation per file under `use-cases/`, named `{verb-noun}.ts`, exporting a server function next to the TanStack Query options that fetch it.
- **Authorization lives on the server function.** A server function is a public HTTP endpoint, so route guards cannot protect it. The `authorized(permission)` middleware in `src/integrations/better-auth/auth.middleware.ts` is applied at 116 call sites — 28 of them as bare `authorized()`, which only requires a valid session (one of them inside `recentSignIn`, which also wants a sign-in from the last 24 hours), and 88 with a permission such as `authorized({ order: ["update"] })`, checked against the role matrix in `auth.access.ts` and, in production and the end-to-end test build, against the admin's two-factor authentication.
- **The presentation layer never touches the database.** Everything under `src/presentation/` imports use cases, never `db`.
- **The code carries no narration.** Five comments exist in the whole of `src/`, three in TypeScript and two in CSS, each explaining a constraint that names and types cannot express. Intent goes in names and types.

The lint baseline is six Oxlint categories as errors — including `nursery` — with type-aware linting and type checking on, warnings failing the build, and hard limits of 800 lines per file, 150 lines per function and 20 statements per function. See [Conventions](/docs/reference/conventions) and [Vite+](/docs/tooling/vite-plus).
