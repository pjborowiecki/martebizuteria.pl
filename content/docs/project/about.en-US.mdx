M'Arte is a full-stack jewellery shop: a Polish-language storefront, a customer account area and an admin console, served from one Cloudflare Worker. The repository is the whole product — there is no separate backend, no separate admin app and no separate CMS. `src/server.ts` is the single entry point, and everything the shop does happens behind it.

The codebase exists for two reasons at once. It runs a real jewellery brand's shop, and it is written as a study in how far a commerce application can be pushed on a runtime with no filesystem, no long-lived Node process and no interactive database transactions. Most of the design decisions documented in [Architecture](/docs/architecture) trace back to those constraints rather than to taste.

## The shop

| Fact                | Value                                                                                               |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| Locales             | `pl-PL` (default, no URL prefix) and `en-US` — `I18N` in `src/integrations/use-intl/i18n.config.ts` |
| Time zone           | `Europe/Warsaw`                                                                                     |
| Currency            | `PLN` only — `STORE_CURRENCY_CODE` in `src/modules/_core/constants/currency.ts`                     |
| Payment             | Stripe, card and Stripe-hosted methods, webhook-driven fulfilment                                   |
| Delivery            | Courier and InPost parcel lockers, seeded into the `delivery_method` table                          |
| Transactional email | Resend, eight React Email templates in `src/presentation/emails/`                                   |
| Worker name         | `martebizuteria` in production, `martebizuteria-preview`, `martebizuteria-development`              |

`wrangler.jsonc` declares no `routes` block and no custom domain, so each environment is served on its `*.workers.dev` hostname. The production URL recorded in `package.json` is `https://martebizuteria.pjborowiecki.workers.dev`.

## One Worker, one route tree

Route files live flat in `src/routes/` and carry no locale segment. The router de-localizes the URL before matching and re-applies the prefix when generating links, so `_storefront.products.index.tsx` serves both `/products` (Polish, the default locale, which takes no prefix) and `/en-US/products`. Path segments themselves are never translated. See [i18n architecture](/docs/architecture/i18n-architecture) for the mechanism.

| Prefix              | Files                             | What it serves                                                 |
| ------------------- | --------------------------------- | -------------------------------------------------------------- |
| `_storefront.*.tsx` | 18 files                          | Landing page, catalog, product pages, cart, blog, legal pages  |
| `checkout.*.tsx`    | 2 files                           | The four-step checkout flow                                    |
| `account.*.tsx`     | 10 files                          | Signed-in customer area — orders, addresses, sessions, profile |
| `admin.*.tsx`       | 25 files                          | Admin console — catalog, orders, customers, audit, settings    |
| `auth.*.tsx`        | 5 files                           | Sign in, sign up, forgot and reset password                    |
| `docs.*.tsx`        | 3 files                           | These documentation pages                                      |
| `api/`              | `auth.$.ts`, `webhooks.stripe.ts` | Better Auth handler and the Stripe webhook endpoint            |

`__root.tsx` and `dev.emails.tsx` complete the 67 files; `dev.emails.tsx` is a development-only email preview that returns 404 unless `import.meta.env.DEV` is true.

Four request paths short-circuit inside `src/server.ts` before the React framework is reached — `/sitemap.xml`, `/robots.txt`, the two WebSocket upgrades — plus the locale redirect, because none of them need an SSR render.

## What works, and what does not

Being precise about the boundary is more useful than a feature list.

### Wired end to end

Catalog (products, variants, options, attributes, categories, collections, search, filtering, pagination), cart, the four-step checkout, discount codes (percentage, fixed amount or free shipping) checked at checkout, recomputed on the server, applied to the Stripe session as a one-off coupon and recorded in `discount_redemption`, Stripe payment with webhook-driven fulfilment, inventory reservation with compensation, order placement, order fulfilment, shipping with an optional tracking number and delivery from the admin console, refunds issued from the admin console or in Stripe with optional restock, customer accounts (orders, addresses, sessions, profile, two-factor sign-in with backup codes), a wishlist kept in the `wishlist_item` table, saved cards attached at checkout to the customer's Stripe customer and removable from `/account/payment`, transactional email in both locales, the audit log behind a Cloudflare Queue, realtime cache invalidation over WebSockets, and admin management of products, categories, collections, attributes, customers, orders, discount codes, the privacy and returns pages, and audit.

### Scaffolded, not finished

| Area                      | State                                                                                                                            |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| InPost                    | Parcel-locker _discovery_ only — `fetchPointsByCity` in `src/integrations/inpost/inpost.api.ts`. No shipment creation, no labels |
| Admin marketing, settings | Render from fixtures in `src/data/`                                                                                              |

### Absent

No end-to-end or browser tests. No cron triggers or reconciliation job — `wrangler.jsonc` declares no `crons`. No dead-letter queue, so an audit batch that fails its three retries is dropped. No error reporting service is initialised. No expiry sweep for `session`, `verification` or `rate_limit` rows.

[Roadmap](/docs/project/roadmap) lists these in the order they are worth fixing.

## How the code is written

Four conventions are visible within the first file you open, and all four are enforced by `bun run check` rather than by review:

- **Modules own tables.** `src/modules/{feature}/` holds the Drizzle table, the Zod schemas, the query-key tuples, the inferred types, the pure helpers and the accessors for exactly one table. One operation per file under `use-cases/`, named `{verb-noun}.ts`, exporting a server function next to the TanStack Query options that fetch it.
- **Authorization lives on the server function.** A server function is a public HTTP endpoint, so route guards cannot protect it. The `authorized(permission)` middleware in `src/integrations/better-auth/auth.middleware.ts` is applied at 83 call sites — 21 of them as bare `authorized()`, which only requires a valid session, and 62 with a permission such as `authorized({ order: ["update"] })`, checked against the role matrix in `auth.access.ts`.
- **The presentation layer never touches the database.** Everything under `src/presentation/` imports use cases, never `db`.
- **The code carries no narration.** Five comments exist in the whole of `src/`, three in TypeScript and two in CSS, each explaining a constraint that names and types cannot express. Intent goes in names and types.

The lint baseline is six Oxlint categories as errors — including `nursery` — with type-aware linting and type checking on, warnings failing the build, and hard limits of 800 lines per file, 150 lines per function and 20 statements per function. See [Conventions](/docs/reference/conventions) and [Vite+](/docs/tooling/vite-plus).
