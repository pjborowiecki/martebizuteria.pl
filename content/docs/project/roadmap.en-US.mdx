This page is derived from the code, not from a product plan. Every item below was found by reading the repository, and each one names the file that demonstrates it. Nothing here is a promise about dates.

Read it together with [About](/docs/project/about), which draws the same boundary from the other side — what already works.

## Priority 1 — correctness in the order lifecycle

These change what customers and the shop owner see. They are first because the shop is live.

### Inventory compensation is best-effort

`reserveInventoryForItems` in `src/modules/inventory/inventory.utils.ts` reserves every cart line in one batch of guarded `UPDATE`s, and if any line fails its guard it releases the ones that succeeded:

```ts
await releaseInventoryForItems(reserved).catch((error: unknown) => {
  console.error("Failed to roll back partial inventory reservation:", error)
})
```

The rollback's own failure is caught and logged. A failed rollback therefore leaves stock reserved against nothing, with no alert and no reconciliation pass to find it. This is a saga with a known hole, and closing it needs either a compensation log or the reconciliation job below.

### A partial return has no restock path

Stock goes back per order, every line at once: `returnOrderToStock` in `src/modules/order/order.restock.server.ts` runs when the admin ticks "The items came back to stock" in the Refund dialog or presses Return to stock, and `canRestockAdminOrder` in `src/modules/order/order.admin-actions.utils.ts` offers Return to stock only for an order whose status is `refunded`. A partial refund made in the Stripe dashboard keeps the order open, so when one piece of a larger order comes back, the admin has to raise that variant's stock in the product editor by hand.

### The confirmation email is attempted once

`notifyOrderConfirmed` in `src/integrations/stripe/stripe.webhooks.tsx` sends the confirmation and passes the attempt to `recordOrderEmailAttempt`, which writes an `email.failed` entry with the error on failure. There is no outbox, no retry and no resend action in the admin, so a Resend outage during a purchase means the customer has an order and no email. The shop sees it in the order's activity and in `/admin/audit`, and has to contact the customer by hand. The shipped, cancellation, refund and failed-payment emails and the shop's new-order notice have the same gap, although the admin who ships or cancels the order is told at once.

### `isAdminPathname` matches too broadly

```ts
export const isAdminPathname = (pathname: string): boolean => pathname.includes(ROUTES.ADMIN)
```

`src/presentation/components/custom/pages/admin/lib/admin-route.ts` uses `includes`, not `startsWith`, so any storefront URL containing the substring `/admin` — a product handle, a blog slug — is treated as an admin route. Two places consume it: the pending component in `src/presentation/components/custom/defaults/default-pending-component.tsx` and `src/presentation/theme/theme-init.ts`, so the symptom is the wrong loading chrome and the wrong theme initialisation rather than a security hole. A one-line fix, and the existing test file already covers the shape.

## Priority 2 — missing infrastructure

### No reservation reconciliation

`src/server.ts` has a `scheduled` handler, but its daily Cron Trigger only enforces the [retention periods](/docs/guides/data-retention) and releases no stock. Stale reservations are released only when Stripe emits `checkout.session.expired`, 32 minutes after a session opens, and a reservation orphaned by a failed compensation is never reclaimed. A reconciliation job would run from the same handler.

### No dead-letter queue

`wrangler.jsonc` sets `max_retries: 3` on the `AUDIT_LOG_QUEUE` consumer with no `dead_letter_queue`. An audit batch that fails three times is dropped. Each failed batch emails `RESEND_EMAIL_FROM`, so the owner hears of it, but the entries themselves are gone. The audit log is the record of who changed what, so losing a batch is worse than it looks.

### The `refund` permission is never checked

The admin console now issues refunds. The Refund button on `/admin/orders/$orderId` calls `refundAdminOrder` in `src/modules/order/use-cases/refund-admin-order.ts`, which asks Stripe for a full refund with `stripe.refunds.create`, and the `charge.refunded` webhook then records it through `handleChargeRefunded` in `src/integrations/stripe/stripe.webhooks.tsx`, exactly as it does for a refund issued in Stripe. `refundAdminOrder` is guarded by `authorized({ order: ["update"] })`, so the `order: ["refund"]` permission declared in `auth.access.ts` is still never checked anywhere. Cancel order on a paid order requests the same refund through `requestFullOrderRefund` and is guarded the same way. Either check it in both or remove it.

## Priority 3 — features that are scaffolded

Each of these already has some of its groundwork in place (an integration function or a complete UI), which makes them cheaper than they look.

| Feature                   | What exists                                                                                                                | What is missing                                          |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| InPost shipments          | `fetchPointsByCity` in `src/integrations/inpost/inpost.api.ts` — parcel-locker discovery by city, minimum three characters | Shipment creation, label generation, tracking write-back |
| Admin marketing, settings | Complete UI                                                                                                                | Both read fixtures from `src/data/`                      |

`src/data/` is the honest marker for this whole category: five fixture files, and every screen importing one is a screen that looks finished and is not. [Shipping and delivery](/docs/features/shipping-and-delivery) covers the InPost work.

## Priority 4 — testing

889 test files exist: 339 unit, 35 integration, 515 component. The distribution is the thing to fix rather than the count.

- **No end-to-end or browser tests.** `vite.config.ts` already excludes an `e2e` directory and a `playwright/` cache that do not exist, so the intent was there. For a checkout flow this is the gap that matters most.
- **The ratio is inverted relative to the risk.** Component tests mostly assert rendering; commerce correctness lives in checkout, inventory compensation and refunds, which the 35 integration suites cover. More integration coverage of the money paths is worth more than more component coverage.
- **Integration suites run on `node:sqlite`.** The transport in `src/platform/testing/mocks/d1.ts` emulates D1's batch atomicity and its 100-parameter ceiling but not its concurrency, so concurrency results are SQLite's behaviour, not proof against D1 under production load.
- **The coverage ratchet needs turning.** Thresholds sit at 72 statements, 71 lines, 68 functions, 69 branches with `autoUpdate: false`. They are a floor to raise, not a target that has been met.

- **The git history does not match the code.** Several commits touch over two thousand files. Nothing to fix retroactively, but worth not repeating — see [Contributing](/docs/project/contributing).

## Scaling work measured but not yet done

A load model of the real schema (5,000 products, 20,000 customers, 200,000 orders and a year of activity log, and ten times that) found the costs below. None of them is a problem at the shop's current size; each line says when it becomes one.

- **Admin CSV exports** load the whole table and send every id to D1 as one value, which D1 refuses above about 51,000 rows. Stream the CSV from the server in pages of 1,000 before any table nears that size.
- **The admin dashboard** recomputes Top products and the date-bounded figures from the whole order history on every visit: about 2 s at 200,000 orders. Add an `order(status, created_at)` index and trigger-maintained daily and per-product summary tables before it reaches that.
- **The activity log** takes in about 2.6 GB a year at that traffic, mostly page views, and counts the whole table on every load. The daily clean-up deletes page views after 90 days, but at that traffic they arrive faster than the 2,500 audit-log entries one run deletes. Raise `RETENTION_BATCHES_PER_RUN` in `src/lib/retention.ts` once the shop is on Workers Paid, which allows 1,000 D1 queries per invocation, or run the trigger more often; add `(category, created_at)` and `(severity, created_at)` indexes and cap the counts.
- **The admin customers page** sums every order per customer for its cards and filters: 1.25M rows per visit at 20,000 customers. A per-customer summary table maintained by triggers fixes it.
- **Storefront listings** recompute each product's stock and price range from every variant: 40,000 rows per listing at 5,000 products. Store total stock and the lowest price on the product, kept exact by triggers, when the catalogue grows.
- **Smaller round trips** remain in address saves, dispute and refund webhooks, admin order transitions, checkout create and update, and fulfilment, where independent reads could share one batch. Realtime still lacks per-tab throttling and a catch-up refresh after a reconnect.
