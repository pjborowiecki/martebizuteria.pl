M'Arte jest dwujęzyczne: polski (`pl-PL`) jest domyślny, a angielski (`en-US`) drugorzędny. Tłumaczenia są podzielone na 60 plików przestrzeni nazw na język, w katalogach `messages/pl-PL/` i `messages/en-US/`, ładowanych per trasa i dostarczanych przez `use-intl`.

`src/integrations/use-intl/i18n.config.ts` konfiguruje języki:

```ts
const COOKIE_NAME = "marte_locale"

const SUPPORTED_LOCALES = ["pl-PL", "en-US"] as const

const DEFAULT_LOCALE: SupportedLocale = "pl-PL"

const DEFAULT_TIMEZONE = "Europe/Warsaw"
```

Wygląd dat, liczb i cen konfiguruje się osobno, w `src/integrations/use-intl/i18n.display.ts` — zobacz [Formatowanie liczb, dat i pieniędzy](#formatowanie-liczb-dat-i-pieniędzy). `DEFAULT_TIMEZONE` do tego nie należy: używają go tylko testowe providery i znacznik czasu w e-mailu o odstąpieniu od umowy.

## Przestrzenie nazw

Przestrzeń nazw to jeden plik JSON, a jego nazwa _jest_ jego ścieżką z kropkami. `messages/pl-PL/pages.admin.catalog.categories.json` to przestrzeń `pages.admin.catalog.categories`, dostępna jako `useTranslations("pages.admin.catalog.categories")`.

Tych 60 plików dzieli się na pięć grup:

| Prefiks       | Przykłady                                                                                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `common`      | `common.json` — tak, nie, potwierdź, anuluj, ładowanie                                                                                                                                |
| `components.` | `components.custom`, `components.datagrid`, `components.defaults`, `components.shadcn`                                                                                                |
| `emails.`     | 19 plików, po jednym na szablon e-maila: `emails.order-confirmation`, `emails.order-shipped`, `emails.verify-email`, `emails.reset-password`, `emails.newsletter-campaign`, …         |
| `errors`      | `errors.json` — zdania pod `action.<CODE>`                                                                                                                                            |
| `pages.`      | 35 plików, po jednym na stronę albo jej sekcję: `pages.home`, `pages.product`, `pages.checkout`, `pages.admin`, `pages.admin.catalog.products`, `pages.auth.sign-in`, `pages.docs`, … |

Oba katalogi językowe zawsze trzymają dokładnie ten sam zestaw nazw plików. Dodanie pliku tylko do jednego oznacza, że `loadNamespace` rzuci wyjątek dla brakującego języka:

```ts
if (load === undefined) {
  throw new Error(`Missing translation namespace: messages/${locale}/${namespace}.json`)
}
```

## Przestrzenie główne

Sześć przestrzeni nazw ładuje się na każdej stronie, bo wszędzie może pojawić się powiadomienie albo błąd. `i18n.messages.ts` wymienia je globem:

```ts
const rootMessagePaths = Object.keys(
  import.meta.glob([
    "../../../messages/*/common.json",
    "../../../messages/*/components.custom.json",
    "../../../messages/*/components.shadcn.json",
    "../../../messages/*/errors.json",
    "../../../messages/*/pages.auth.errors.json",
    "../../../messages/*/pages.auth.toast.json",
  ]),
)

export const ROOT_NAMESPACES = [...new Set(rootMessagePaths.map((path) => toNamespace(path)))]
```

Wszystko pozostałe deklaruje się per trasa.

## Deklarowanie przestrzeni nazw na trasie

Trasa wymienia to, czego potrzebuje jej poddrzewo, w `staticData.namespaces`:

```ts
export const Route = createFileRoute("/admin/catalog/categories")({
  component: CategoriesSectionLayoutRoute,
  staticData: {
    namespaces: ["pages.admin.catalog.categories", "pages.admin.catalog.products", "pages.admin.catalog.products.catalogList"],
  },
})
```

`getRouteNamespaces(matches)` łączy deklaracje wszystkich dopasowanych tras z `ROOT_NAMESPACES`, więc strona dziedziczy przestrzenie swoich układów. `/admin/catalog/categories` dostaje sześć przestrzeni głównych, plus `pages.admin` i `components.datagrid` z `admin.tsx`, plus `pages.admin.catalog` i `pages.admin.catalog.localePicker` z `admin.catalog.tsx`, plus własne trzy.

**Zapomniana deklaracja przestrzeni nazw wychodzi przy renderowaniu, nie przy budowaniu.** use-intl nie rzuca wyjątku: `IntlProvider` nie ustawia `onError` ani `getMessageFallback`, więc domyślne zachowanie use-intl zgłasza błąd `MISSING_MESSAGE` przez `console.error` i zamiast tekstu renderuje ścieżkę klucza, na przykład `pages.admin.catalog.categories.title`. Gdy strona pokazuje ścieżki kluczy, deklaracja przestrzeni nazw jest pierwszą rzeczą do sprawdzenia, a sam klucz drugą.

## Jak tłumaczenia docierają do komponentu

1. `beforeLoad` trasy głównej wywołuje `preloadNamespaces({ locale, namespaces: getRouteNamespaces(matches), queryClient })`, które rozgrzewa po jednym zapytaniu na przestrzeń nazw, a obok ładuje `displayPreferencesQuery`.
2. Każda przestrzeń to wpis TanStack Query z `gcTime: Infinity` i `staleTime: Infinity`, kluczowany `["messages", locale, namespace]`. Przestrzeń pobiera się raz na język na sesję.
3. `TranslationsProvider` w `src/providers/translations-provider.tsx` odczytuje dopasowane przestrzenie przy każdej nawigacji i składa je razem:

```tsx
const messages = useSuspenseQueries({
  combine: (results) => buildMessageTree(results.map((result) => result.data)),
  queries: namespaces.map((namespace) =>
    Object.assign(messagesQueryOptions({ locale, namespace }), {
      select: (data: AbstractIntlMessages): NamespaceEntry => [namespace, data],
    }),
  ),
})
```

4. `buildMessageTree` zamienia płaską listę par `["pages.admin.catalog.categories", {...}]` w zagnieżdżony obiekt, jakiego oczekuje `use-intl`, dzieląc każdą przestrzeń po kropkach, zagnieżdżając od środka i scalając głęboko.
5. `IntlProvider` otrzymuje to drzewo, język i strefę czasową wyznaczoną z `displayPreferencesQuery`; wewnątrz niego `DisplayPreferencesContext` przekazuje wyznaczony format i strefę czasową hookom formatującym.

Ponieważ właściwy JSON ładuje się przez `import.meta.glob`, każda przestrzeń nazw jest osobnym fragmentem paczki. Gość witryny sklepowej nigdy nie pobiera napisów katalogu w panelu.

## Używanie tłumaczenia

```tsx
const t = useTranslations("pages.admin.catalog.categories")

t("title")
t("columns.createdAt")
t("form.validation.titleTooLong")
```

`useTranslations()` bez argumentu zwraca tłumacza głównego przyjmującego pełne ścieżki. `useActionError` używa go, żeby z dowolnego miejsca dostać się do `errors.action.*` i `pages.auth.errors.*`, a `ValidationFieldError` — żeby dostać się do `<namespace>.<message>` w przekazanej mu przestrzeni walidacji, na przykład `pages.auth.validations`.

`t.has(key)` sprawdza istnienie klucza przed użyciem — `ValidationFieldError` opiera się na tym, żeby sięgnąć po ogólne zdanie `errors.action.VALIDATION`, zamiast wyrenderować ścieżkę klucza.

Placeholdery ICU działają normalnie:

```tsx
tLocale("incompleteToastDescription", {
  locales: formatCatalogLocaleList(incompleteLocales, (locale) => tLocale(`localeNames.${locale}`)),
})
```

## Formatowanie liczb, dat i pieniędzy

Język strony i format wyświetlania to osobne ustawienia. Język, `pl-PL` albo `en-US`, wynika ze ścieżki i wybiera tłumaczenia. **Format**, który decyduje o wyglądzie dat i liczb, oraz **strefa czasowa** to osobne preferencje wyświetlania, więc odwiedzający może czytać polską witrynę z brytyjskimi datami albo angielską w czasie warszawskim.

Nigdy nie wywołuj `Intl` bezpośrednio w komponencie. Używaj hooków z `src/hooks/use-display-format.ts`:

| Hook                   | Zwraca                                                                        | Do czego                                                                   |
| ---------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `useFormatter()`       | `createFormatter({ locale: formatLocale, timeZone })` z use-intl, memoizowane | Daty, godziny, liczby                                                      |
| `useFormatLocale()`    | Format, na przykład `en-GB`                                                   | Funkcje pomocnicze przyjmujące locale, na przykład `formatPrice`           |
| `useDisplayTimeZone()` | Strefę czasową IANA, na przykład `Europe/Warsaw`                              | Rachunki kalendarzowe, na przykład który dzień jest dla użytkownika „dziś” |

Importuj `useFormatter` z tego pliku, nie z `use-intl/react`: własne `useFormatter` z use-intl formatuje według języka strony.

```tsx
const format = useFormatter()

format.dateTime(new Date(getValue()), { dateStyle: "medium" })
```

Ceny są zapisywane jako całkowite jednostki podrzędne — `1499` to 14,99 zł — więc formatowanie jest przeliczeniem, nie rzutowaniem. Formatuj je przez `formatPrice(amountInMinorUnits, currency, locale)` z `src/modules/_core/utils/currency.ts`, przekazując format, tak jak `src/presentation/components/custom/checkout/components/checkout-success.tsx`:

```tsx
const formatLocale = useFormatLocale()

formatPrice(order.totalMinorUnits, order.currencyCode, formatLocale)
```

Pozostałe funkcje walutowe leżą w tym samym pliku, a stałe w `src/modules/_core/constants/currency.ts`, gdzie `CURRENCIES` przechowuje kod numeryczny i wykładnik ISO każdej waluty.

Dla daty, którą się oblicza, a nie wyświetla, bierz strefę z `useDisplayTimeZone()`. Wybór własnego zakresu na pulpicie panelu ustala z nim „dziś” użytkownika:

```tsx
const timeZone = useDisplayTimeZone()
const todayIso = formatCalendarDateToIsoDate(toCalendarDate(new Date(), timeZone))
```

### Skąd biorą się preferencje

`src/integrations/use-intl/i18n.display.ts` przechowuje konfigurację wyświetlania:

```ts
export const FALLBACK_FORMAT_LOCALE = "en-US"

export const FALLBACK_TIME_ZONE = "UTC"

export const TIME_ZONE_COOKIE_NAME = "marte_time_zone"
```

Eksportuje też `FORMAT_LOCALES`, osiemnaście formatów do wyboru dla użytkownika. `resolveDisplayPreferences` wyznacza każdą preferencję osobno, w tej kolejności:

1. **Zapisana** u zalogowanego użytkownika, w kolumnach `formatLocale` i `timezone`. `toSavedDisplayPreferences` pomija wartość, której nie przyjmuje `Intl`.
2. **Wykryta** z żądania przez `detectDisplayPreferences`: format z pierwszego użytecznego wpisu `Accept-Language`, a strefa czasowa z ciasteczka `marte_time_zone`, a w jego braku ze strefy, którą Cloudflare podaje dla lokalizacji odwiedzającego (`request.cf.timezone`).
3. **Wartości zastępcze**: `en-US` i `UTC`.

Przeglądarka poprawia wykrytą strefę. Po hydratacji strony `TranslationsProvider` zapisuje własną strefę przeglądarki w ciasteczku `marte_time_zone`, a gdy różni się ona od wykrytej, aktualizuje zapisane w pamięci podręcznej `displayPreferencesQuery` (klucz `["i18n", "displayPreferences"]`). Użytkownik bez zapisanej strefy od razu widzi czas w strefie przeglądarki, a następny render na serwerze wykrywa ją z ciasteczka.

Użytkownik zmienia preferencje na stronie profilu konta, `/account/profile`, w sekcji **Preferencje**, w polach **Strefa czasowa** i **Format dat i liczb**; każde z nich ma opcję **Automatycznie (…)**, która podaje wykrytą wartość. Wybór wartości zapisuje ją przez `updateDisplayPreference` (`src/modules/user/use-cases/update-display-preference.ts`); wybór opcji automatycznej czyści zapisaną wartość. Zapis unieważnia wszystkie zapytania, więc dane sformatowane przez serwer są pobierane ponownie w nowym formacie.

### Na serwerze

Funkcja serwerowa, która formatuje datę albo filtruje po niej, czyta te same preferencje przez `resolveRequestDisplayPreferences()` z `src/integrations/use-intl/i18n.display-preferences.ts`, czyli `createServerOnlyFn` zwracające `{ formatLocale, timeZone }` dla bieżącego żądania: preferencje zapisane, a w ich braku wykryte. Filtry dat przekazują strefę czasową do `buildAdminDateTimeFilterSql(column, filter, timeZone)` z `src/modules/_core/utils/datetime-column-filter.server.ts`, więc „3 października” obejmuje 3 października od północy do północy w strefie czasowej administratora. Z `src/modules/audit-log/use-cases/list-audit-logs.ts`:

```ts
.handler(async ({ data }): Promise<AdminAuditLogsPageResult> => {
  const preferences = await resolveRequestDisplayPreferences()
  const params = buildAdminAuditLogsListParams(data, preferences.timeZone)
  const { rows, total } = await auditLogGetAdminAuditLogsPage(params)
  const items = rows.map((row) => toAdminAuditListItem(row, preferences))

  return buildAdminAuditLogsPageResult(items, total, params)
})
```

Ten sam wzorzec stosują przypadki użycia list, eksportów, pulpitu i klientów w panelu. Ich testy zastępują tę funkcję przez `src/platform/testing/mocks/display-preferences.ts`; zobacz [Pisanie testów](/docs/guides/writing-tests#testowanie-funkcji-serwerowej).

## Typowanie pliku tłumaczeń

Kiedy loader potrzebuje wartości komunikatu, a nie tłumacza w komponencie, zaimportuj plik angielski jako **typ** i przekaż go do `messagesQueryOptions`. Z `src/routes/_storefront.products.index.tsx`:

```ts
import type productsMessages from "~/messages/en-US/pages.products.json"

const [messages] = await Promise.all([
  context.queryClient.query(messagesQueryOptions<typeof productsMessages>({ locale: context.locale, namespace: "pages.products" })),
  prefetchProductsCatalogPage(context.queryClient, context.imagePrefetchService, {
    search: deps,
  }),
])

const t = createTranslator({ locale: context.locale, messages })

return {
  description: messages.description,
  structuredData: buildBreadcrumbStructuredData({ leaf: messages.title, locale: context.locale, sections: [] }),
  title: deps.q === undefined ? messages.title : t("search.pageTitle", { query: deps.q }),
}
```

Plik angielski jest źródłem typów dla obu języków, co jest kolejnym powodem, żeby oba katalogi pozostały strukturalnie identyczne. W ten sposób tłumaczą się tytuły stron, opisy meta i dane strukturalne; `createTranslator` z `use-intl` obsługuje komunikat z placeholderami, tutaj tytuł wyników wyszukiwania.

## Ustalanie języka

Język wynika ze ścieżki, nie z nagłówka ani parametru zapytania. `getCurrentLocale` w `src/integrations/use-intl/i18n.utils.ts` jest funkcją izomorficzną: na serwerze czyta URL żądania, na kliencie `location.pathname`, a w obu przypadkach sięga po ciasteczko `marte_locale` dla ścieżek bez języka (`/api`, `/rpc`, `/_serverFn`, `/assets`, `/forms`).

`resolveLocale(request)` w `i18n.middleware.ts` wykonuje się w punkcie wejścia Workera, przed routerem, i robi dwie rzeczy, wyłącznie dla żądań dokumentów:

- **Kanonizuje ścieżkę.** Jeśli `canonicalizePathname` ją zmieni — `/pl/products` na `/products`, `/en/products` na `/en-US/products` — zwraca odpowiedź 301.
- **Synchronizuje ciasteczko.** Kiedy język z adresu różni się od ciasteczka, zwraca `Set-Cookie` z językiem z adresu, które `src/server.ts` dokłada do odpowiedzi.

W interfejsie witryny sklepowej nie ma obecnie przełącznika języka; gość zmienia język, odwiedzając adres z prefiksem, a `TranslationsProvider` zapisuje potem ciasteczko w efekcie.

## Wiadomości e-mail

Szablony e-mail w `src/presentation/emails/` eksportują stałą z nazwą przestrzeni i przyjmują tłumaczenia jako właściwość, bo renderują się poza drzewem providerów React:

```ts
const messages = await loadNamespace<typeof verifyEmailMessages>({ locale, namespace: VERIFY_EMAIL_NAMESPACE })
```

Przypadki użycia wysyłające e-maile, na przykład `src/modules/verification/use-cases/send-verify-email.server.ts`, wywołują `loadNamespace` bezpośrednio i przekazują do szablonu zarówno `locale`, jak i `messages`, używając po stronie serwera `createTranslator` z `use-intl`. Oba języki każdego szablonu podejrzysz pod `/dev/emails` — zobacz [Debugowanie lokalne](/docs/guides/local-debugging).

## Dodawanie przestrzeni nazw: lista kontrolna

1. Utwórz `messages/pl-PL/<namespace>.json` i `messages/en-US/<namespace>.json` z tymi samymi kluczami.
2. Dodaj przestrzeń nazw do `staticData.namespaces` na trasie, która jej potrzebuje — na trasie układu, jeśli dzieli ją kilka stron.
3. Użyj `useTranslations("<namespace>")` w komponencie.
4. Uruchom `bun run test`. `src/integrations/use-intl/__test__/i18n.messages.test.ts` ładuje każdą przestrzeń nazw obu języków przez loader używany w aplikacji i zawodzi, gdy brakuje pliku polskiego albo brakuje w nim klucza, który ma plik angielski. Testy komponentów budują swoje drzewo tłumaczeń ze wszystkich plików w `messages/en-US/` przez `src/platform/testing/lib/messages.ts`, ale brakujący tam klucz renderuje się tylko jako jego ścieżka, więc test komponentu wyłapie go wtedy, gdy sprawdza angielski tekst.
5. Ścisłym sprawdzianem jest zestaw end-to-end: automatyczna fikstura `checkTranslations` w `e2e/fixtures/test.ts` oblewa każdy test, którego strona zaloguje w konsoli przeglądarki `MISSING_MESSAGE`, `INVALID_MESSAGE`, `FORMATTING_ERROR` albo `INVALID_KEY`.
