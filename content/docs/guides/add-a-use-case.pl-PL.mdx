description: "Dodaj jedną operację: funkcję serwerową z middleware, walidatorem, opcjami zapytania lub mutacji, śladem audytowym i unieważnianiem cache'u."
---

Przypadek użycia to jedna operacja w jednym module. Mieszka w `src/modules/{feature}/use-cases/{verb-noun}.ts` i zwykle eksportuje dwie rzeczy: funkcję serwerową oraz opcje TanStack Query, których loadery tras i komponenty używają, żeby ją wywołać. Nic innego w repozytorium nie buduje własnych `queryOptions` dla danych modułu — moduł jest ich właścicielem.

Istnieją dwa warianty. 21 ze 128 plików `{verb-noun}.ts` nie eksportuje opcji zapytania ani mutacji, bo ich wywołujący sięgają po funkcję bezpośrednio — na przykład funkcję z `create-category.ts` provider formularza kategorii owija we własne `useMutation`. Operacja, którą wywołuje wyłącznie inny kod serwerowy — webhook, konsument kolejki, sprzątanie danych — w ogóle nie jest funkcją serwerową, tylko zwykłą funkcją async w `{verb-noun}.server.ts`; opisuje je [Dodawanie modułu](/docs/guides/add-a-module).

Szczegóły middleware, błędów i kontekstu, których używa ta strona, opisują [Funkcje serwerowe](/docs/guides/server-functions).

## Napisz zapytanie

`src/modules/address/use-cases/list-user-addresses.ts` to absolutne minimum:

```ts
import { queryOptions } from "@tanstack/react-query"
import { createServerFn } from "@tanstack/react-start"
import { eq } from "drizzle-orm"

import { authorized } from "~/src/integrations/better-auth/auth.middleware"
import { db } from "~/src/integrations/drizzle-orm/drizzle.database"

import { ADDRESS_QUERY_KEYS } from "~/src/modules/address/address.constants"
import { address } from "~/src/modules/address/address.schema"

export const listUserAddresses = createServerFn({ method: "GET" })
  .middleware([authorized()])
  .handler(({ context }) => db.query.address.findMany({ where: eq(address.userId, context.auth.user.id) }))

export const listUserAddressesQuery = () =>
  queryOptions({
    queryFn: () => listUserAddresses(),
    queryKey: ADDRESS_QUERY_KEYS.ALL,
  })
```

Zasady, które obowiązują ogólnie:

- Odczyty używają `method: "GET"`, zapisy `method: "POST"`.
- Handler pobiera wywołującego z `context.auth.user.id`. Nigdy nie bierze identyfikatora użytkownika z wejścia.
- Opcje zapytania eksportujemy jako **funkcję**, nawet gdy nie przyjmuje argumentów. Wywołania wyglądają tak: `listUserAddressesQuery()`.

Zapytania panelu dodają uprawnienie, czas świeżości i politykę ponownego pobierania, jak w `src/modules/product-category/use-cases/get-admin-categories.ts`:

```ts
export const getAdminCategories = createServerFn({ method: "GET" })
  .middleware([authorized({ product: ["read"] })])
  .handler(async () => {
    const [categories, counts] = await Promise.all([productCategoryGetAdminCategoriesQuery.execute(), getProductCountsQuery.execute()])
    const countByCategoryId = new Map(counts.map((entry) => [entry.categoryId, entry.count]))
    const titlesById = new Map(categories.map((row) => [row.id, coerceCategoryLocaleMap(row.titles)]))

    return categories.map((row) => toAdminCategoryListItem(row, countByCategoryId.get(row.id) ?? 0, titlesById))
  })

export const getAdminCategoriesQuery = () =>
  queryOptions({
    queryFn: () => getAdminCategories(),
    queryKey: CATEGORY_QUERY_KEYS.ADMIN.ALL,
    refetchOnMount: false,
    refetchOnWindowFocus: false,
    staleTime: CATEGORY_QUERY_STALE_MS,
  })
```

Handler kształtuje wiersze pod swojego konsumenta — `toAdminCategoryListItem` leży w `product-category.utils.ts`, a zapytania przygotowane w `product-category.accessors.ts`. Sam handler powinien być krótkim ciągiem nazwanych wywołań; limit 20 instrukcji powie Ci, kiedy przestał być krótki.

### Zapytania stronicowane

Kiedy wejście się zmienia, klucz musi zmieniać się razem z nim. `src/modules/product/use-cases/get-admin-products-page.ts` wkłada sparsowane wejście do klucza:

```ts
export const getAdminProductsPageQuery = (input: Product["adminProductsPageInput"]) =>
  queryOptions({
    queryFn: () => getAdminProductsPage({ data: input }),
    queryKey: [...PRODUCT_QUERY_KEYS.ADMIN.PAGE, input],
    refetchOnMount: false,
    refetchOnWindowFocus: false,
    staleTime: PRODUCT_QUERY_STALE_MS,
  })
```

Jego handler:

```ts
.handler(async ({ data }) => {
  const { timeZone } = await resolveRequestDisplayPreferences()
  const params = buildAdminProductsListParams(data, timeZone)
  const { rows, total } = await productGetAdminProductsPage(params)
  const aggregates = await loadAdminListAggregates(rows)
  const items = rows.map((row) => toAdminProductListItem(row, aggregates.statsByProductId, aggregates.skuSummaryByProductId))

  return buildListPaginationResult(items, total, params)
})
```

`buildAdminProductsListParams`, zdefiniowane w tym samym pliku, zamienia numer strony na offset i limit przy pomocy `listPaginationParamsFromPage` i dokłada filtry; `buildListPaginationResult` owija wiersze. Obie funkcje pomocnicze pochodzą z `src/modules/_core/utils/pagination.ts`. Wynik zawiera `items`, `total`, `limit`, `offset` i `hasMore`, czyli dokładnie to, czego oczekuje ręczne stronicowanie tabeli danych.

### Filtry dat działają w strefie czasowej administratora

Filtr kolumny daty (`dateColumnFilterField` albo `dateTimeColumnFilterField` tam, gdzie liczy się minuta, jak w dzienniku audytu) przychodzi jako dzień kalendarzowy lub minuta czasu lokalnego, bez strefy. „Utworzone 3 marca” oznacza 3 marca tam, gdzie jest administrator, a nie w UTC, więc handler filtrujący po dacie robi dwie rzeczy:

1. Wywołuje `resolveRequestDisplayPreferences()` z `src/integrations/use-intl/i18n.display-preferences.ts` — `createServerOnlyFn`, który zwraca `{ formatLocale, timeZone }` dla bieżącego żądania: zapisane preferencje zalogowanego użytkownika, a w ich braku te wykryte z żądania (dla strefy: ciasteczko `marte_time_zone`, potem strefa czasowa, którą Cloudflare podaje dla żądania, a na końcu `UTC`).
2. Przekazuje `timeZone` do akcesora, który buduje warunek przez `buildAdminDateTimeFilterSql(column, filter, timeZone)` z `src/modules/_core/utils/datetime-column-filter.server.ts`, tak jak robi to `product.accessors.ts`:

```ts
if (params.createdAt !== undefined) {
  conditions.push(buildAdminDateTimeFilterSql(product.createdAt, params.createdAt, params.timeZone))
}
```

`buildAdminDateTimeFilterSql` zamienia każdy dzień na chwilę, w której się zaczyna, i chwilę, w której zaczyna się dzień następny w tej strefie, więc „w dniu”, „przed”, „po” i „pomiędzy” odpowiadają kalendarzowi administratora. Nie porównuj filtra z północą UTC na własną rękę.

`resolveRequestDisplayPreferences()` wywołuje jedenaście przypadków użycia panelu. Strony list zamówień, produktów, klientów i dziennika audytu oraz eksporty zamówień, produktów i klientów przekazują strefę do swoich filtrów dat; `src/modules/audit-log/use-cases/list-audit-logs.ts` przekazuje też cały obiekt `preferences` do `toAdminAuditListItem`, żeby sformatować każdy wiersz. Migawka pulpitu, zakres wykresu pulpitu, statystyki dziennika audytu i szczegóły klienta używają strefy do wyznaczania granic dni i miesięcy. Wywołuje go też jeden przypadek użycia sklepu: `listSavedPaymentMethods` ocenia w strefie klienta, czy minął miesiąc ważności zapisanej karty. Testy podmieniają ten moduł na fiksturę z `src/platform/testing/mocks/display-preferences.ts`, która odpowiada `{ formatLocale: "pl-PL", timeZone: "Europe/Warsaw" }`:

```ts
vi.mock("~/src/integrations/use-intl/i18n.display-preferences", () => import("~/src/platform/testing/mocks/display-preferences"))
```

## Napisz mutację

`src/modules/address/use-cases/set-default-user-address.ts` pokazuje pełny kształt zapisu:

```ts
import { mutationOptions } from "@tanstack/react-query"
import { createServerFn } from "@tanstack/react-start"
import type * as zod from "zod"

import { authorized } from "~/src/integrations/better-auth/auth.middleware"

import { AppError, ERROR_CODES } from "~/src/modules/_core/constants/errors"
import { setDefaultUserAddress as addressSetDefaultUserAddress } from "~/src/modules/address/address.accessors"
import { ADDRESS_MUTATION_KEYS } from "~/src/modules/address/address.constants"
import { addressIdInputSchema } from "~/src/modules/address/address.zod"

export const setDefaultUserAddress = createServerFn({ method: "POST" })
  .middleware([authorized()])
  .validator((input: zod.input<typeof addressIdInputSchema>) => addressIdInputSchema.parse(input))
  .handler(async ({ context, data: { addressId } }) => {
    const updated = await addressSetDefaultUserAddress(context.auth.user.id, addressId)
    if (!updated) {
      throw new AppError(ERROR_CODES.NOT_FOUND)
    }

    return { ok: true as const }
  })

export const setDefaultUserAddressMutation = mutationOptions({
  mutationFn: (data: Parameters<typeof setDefaultUserAddress>[0]["data"]) => setDefaultUserAddress({ data }),
  mutationKey: ADDRESS_MUTATION_KEYS.SET_DEFAULT,
})
```

- Parametr walidatora ma typ `zod.input<typeof schema>` — importowany jako `import type * as zod from "zod"` — a jego ciało wywołuje `schema.parse(input)`. Handler dostaje już sparsowane wyjście.
- Akcesor zwraca wartość logiczną; przypadek użycia zamienia brak trafienia w `AppError(ERROR_CODES.NOT_FOUND)`.
- `mutationOptions` eksportujemy jako zwykły obiekt (nie funkcję), a typ jego `mutationFn` wyprowadzamy przez `Parameters<typeof fn>[0]["data"]`, zamiast powtarzać go ręcznie.
- Operacje publiczne albo kosztowne dokładają ograniczanie liczby żądań przed strażnikiem: `createUserAddress` używa `.middleware([withRateLimit("create-user-address", RATE_LIMITS.SENSITIVE), authorized()])`.

### Efekty uboczne, które zapis musi wykonać

`src/modules/product-category/use-cases/create-category.ts` pokazuje, za co odpowiada zapis w katalogu poza samym wstawieniem wiersza:

```ts
const nextRank = await getNextRankForParent(parentId)
const id = uuidv7()
await db.insert(productCategory).values(toCategoryRow(data, id, nextRank))
scheduleCategoryCatalogInvalidation()
recordCatalogCategoryCreatedAudit(data.handle)

return { handle: data.handle, id }
```

Trzy obowiązki:

1. **Najpierw sprawdzenie unikalności i spójności odwołań.** Zduplikowany handle rzuca `AppError(ERROR_CODES.CONFLICT, CATEGORY_ERROR_CODES.DUPLICATE_HANDLE)`; brakujący rodzic rzuca `AppError(ERROR_CODES.VALIDATION, CATEGORY_ERROR_CODES.INVALID_PARENT)`. Drugi argument to przyczyna specyficzna dla modułu. Formularz kategorii przypina błąd do właściwego pola na podstawie pierwszego argumentu, czyli kodu: `CONFLICT` oznacza `handle`, a `VALIDATION` — `parentId`.
2. **Unieważnianie w czasie rzeczywistym.** `scheduleCategoryCatalogInvalidation()` z `src/integrations/realtime-invalidation/realtime-invalidation.catalog.server.ts` publikuje prefiksy kluczy zapytań panelu i witryny do Durable Object `RealtimeInvalidationHub`, żeby każda inna otwarta karta pobrała dane ponownie. Pozostałe funkcje w tym pliku to `scheduleProductCatalogInvalidation`, `scheduleCollectionCatalogInvalidation`, `scheduleContentPageInvalidation`, `scheduleProductAttributeCatalogInvalidation`, `scheduleAdminCustomersInvalidation`, `scheduleAdminNewsletterSubscribersInvalidation`, `scheduleAdminAuditLogInvalidation`, `scheduleAdminOrdersInvalidation` (publikuje `ORDER_CHANGE_ADMIN_QUERY_KEYS`, czyli prefiksy zamówień i pulpitu) oraz `scheduleSalesStatusInvalidation`. Każda z nich owija jedno wywołanie `scheduleRealtimeInvalidation({ admin, storefront })` z `realtime-invalidation.publish.server.ts`, które przypadek użycia może też wywołać bezpośrednio z własnymi kluczami, jak robi to `send-newsletter-campaign.ts`. Karta pobiera ponownie tylko klucze objęte jej listą subskrypcji — `ADMIN_REALTIME_QUERY_PREFIXES` albo `STOREFRONT_REALTIME_QUERY_PREFIXES` w `realtime-invalidation.subscriptions.ts` — więc prefiks nowego modułu trzeba dopisać także tam. Zobacz [Unieważnianie w czasie rzeczywistym](/docs/architecture/realtime-invalidation).
3. **Ślad audytowy.** `recordCatalogCategoryCreatedAudit(...)` z `src/modules/audit-log/use-cases/record-catalog-audit.server.ts` wstawia wiadomość do kolejki `AUDIT_LOG_QUEUE` przez `scheduleBackgroundWork`, które przekazuje ją do `waitUntil` Workera. Żadne z tych wywołań nie jest oczekiwane i żadne nie może zepsuć żądania.

Oba są celowo w trybie „wyślij i zapomnij”. Nie dodawaj do nich `await` ani nie owijaj ich w `try`.

## Użyj w komponencie

Rozwiń wyeksportowane opcje operatorem spread. Zapytanie w komponencie używa `useSuspenseQuery`, jeśli loader trasy pobrał je już wcześniej:

```tsx
const { data: categories, isFetching } = useSuspenseQuery(getAdminCategoriesQuery())
```

Handlery zwykle zwracają surowe wartości — znaczniki czasu jako `Date`, ceny w jednostkach podrzędnych — a komponent formatuje je według preferencji wyświetlania oglądającego, które są niezależne od języka interfejsu. `src/hooks/use-display-format.ts` udostępnia `useFormatter()`, formatter use-intl zbudowany dla formatu regionalnego i strefy czasowej oglądającego (importuj go z tego pliku, nie z `use-intl`), oraz `useFormatLocale()`, czyli napis z formatem regionalnym, który przyjmuje `formatPrice(amountInMinorUnits, currency, locale)` z `src/modules/_core/utils/currency.ts`. `src/presentation/components/custom/checkout/components/checkout-success.tsx` używa obu:

```tsx
const format = useFormatter()
const formatLocale = useFormatLocale()

<p className="mt-1 text-sm">{format.dateTime(order.createdAt, { day: "numeric", month: "long", year: "numeric" })}</p>
<SummaryRow label={t("subtotalLabel")} value={formatPrice(order.subtotalMinorUnits, order.currencyCode, formatLocale)} />
```

Handler, który sam musi zwrócić sformatowany tekst, bierze format regionalny i strefę z `resolveRequestDisplayPreferences()`, tak jak `getAdminCustomer` przy dacie dołączenia klienta.

Mutacja rozwija `mutationOptions`, tłumaczy błąd i unieważnia tylko to, co się zmieniło:

```tsx
const queryClient = useQueryClient()
const actionError = useActionError()

const setDefault = useMutation({
  ...setDefaultUserAddressMutation,
  onError: (error) => {
    toast.error(actionError(error))
  },
  onSuccess: async () => {
    await queryClient.invalidateQueries({ queryKey: ADDRESS_QUERY_KEYS.ALL })
  },
})
```

`useActionError` w `src/hooks/use-action-error.ts` czyta `message` błędu: wartość z `ERROR_CODES` zamienia na `errors.action.<CODE>`, a klucz komunikatu Better Auth (to, co niesie `AppError(AUTH_API_ERROR, key)`) na `pages.auth.errors.<key>`. Błąd o nazwie `ZodError` lub `ValidationError` daje `errors.action.VALIDATION`, błąd, którego `code` jest kodem błędu Better Auth, daje swój wpis w `pages.auth.errors`, a wszystko inne — `errors.action.INTERNAL_ERROR`. Nigdy nie pokazuj `error.message` bezpośrednio.

Ta kolejność ma znaczenie, gdy handler rzuca przyczynę specyficzną dla modułu. `AppError(ERROR_CODES.CONFLICT, CATEGORY_ERROR_CODES.DUPLICATE_HANDLE)` dociera z `DUPLICATE_HANDLE` jako komunikatem, którego `useActionError` nie zna, więc pokazałby ogólne zdanie o błędzie wewnętrznym. Rozgałęź się na przyczynie i kodzie samodzielnie, zanim sięgniesz po ogólny komunikat, tak jak robi to `src/presentation/components/custom/pages/admin/orders/hooks/use-order-row-actions.ts`:

```ts
const resolveOrderActionErrorMessage = (error: Error, t: ReturnType<typeof useTranslations<"pages.admin.orders.rowActions">>): string => {
  const code = errorCode(error)

  if (code === ERROR_CODES.NOT_FOUND) {
    return t("toast.notFoundDescription")
  }

  if (error.message === ORDER_ERROR_CODES.OPEN_DISPUTE) {
    return t("toast.openDisputeDescription")
  }

  if (code === ERROR_CODES.CONFLICT) {
    return t("toast.invalidStateDescription")
  }

  return t("toast.errorDescription")
}
```

## Pobierz z wyprzedzeniem w loaderze trasy

Loadery tras wywołują `context.queryClient.query(...)` z tym samym obiektem opcji:

```ts
const prefetchCategoriesQueries = async (context: { queryClient: QueryClient }): Promise<void> => {
  await Promise.all([
    context.queryClient.query({ ...getAdminCategoriesQuery(), staleTime: "static" }),
    context.queryClient.query({ ...getCategoryStatsQuery(), staleTime: "static" }),
  ])
}
```

`staleTime: "static"` mówi loaderowi, żeby nie pobierał danych ponownie podczas nawigacji; potem przejmuje to czas świeżości ustawiony w komponencie. Pobierz z wyprzedzeniem każde zapytanie potrzebne do pierwszego renderowania, w jednym `Promise.all`.

## Przetestuj

Dodaj test w `use-cases/__test__/`. Do handlera można dotrzeć na dwa sposoby.

**Zastąp budowniczego.** `src/modules/address/use-cases/__test__/address-use-cases.test.ts` i `src/modules/payment/use-cases/__test__/create-card-setup-intent.test.ts` mockują moduł middleware i moduły wywoływane przez handler, a `createServerFn` zastępują budowniczym, który wstrzykuje ustalone `context.auth`. Mock `auth.middleware`, który dostarcza `RATE_LIMITS`, powinien odwzorowywać prawdziwy kształt `{ max, window }`, tak jak w `create-card-setup-intent.test.ts`:

```ts
vi.mock("~/src/integrations/better-auth/auth.middleware", () => ({
  RATE_LIMITS: { SENSITIVE: { max: 3, window: 60 } },
  authorized: () => ({}),
  withRateLimit: calls.withRateLimit,
}))
```

**Uruchom prawdziwy łańcuch.** Żeby sprawdzić prawdziwe middleware i walidator, owiń rzeczywiste `createServerFn` przez `withTestRpc` z `src/platform/testing/lib/server-function.ts` i zastąp tylko sesję oraz warstwę danych, tak jak robi to `src/modules/discount/use-cases/__test__/create-discount.test.ts`:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
vi.mock(import("@tanstack/react-start/server"), async (importOriginal) => {
  const actual = await importOriginal()

  return { ...actual, getRequest: () => new Request("https://marte.test/admin/coupons") }
})
vi.mock("~/src/integrations/better-auth/auth.session", () => ({ getRequestSession: stubs.getRequestSession }))
vi.mock("~/src/lib/rate-limit", () => ({}))
```

`withTestRpc` uruchamia każde wywołanie w kontekście żądania TanStack Start, więc `authorized(...)`, walidator i tłumaczenie błędów z `withRequest` działają tak jak w Workerze: sesja `null` dostaje `UNAUTHORIZED`, klient — `FORBIDDEN`, a nieprawidłowe wejście — `VALIDATION`. Vitest działa z `import.meta.env.MODE` równym `"test"`, czyli w jednym z trybów, w których administrator musi mieć uwierzytelnianie dwuskładnikowe, więc atrapa sesji administratora potrzebuje `twoFactorEnabled: true`, inaczej każde sprawdzenie uprawnień odpowie `FORBIDDEN`. Plik konfiguracyjny projektu testów komponentów, `src/platform/testing/setup.ts`, nakłada tę samą otoczkę `withTestRpc` na każdy test komponentu.

Pokryj ścieżkę powodzenia, każdy kod rzucany przez handler, fakt, że identyfikator wywołującego pochodzi z sesji, a nie z wejścia, oraz to, że ogranicznik żądań został skonfigurowany z oczekiwanym rodzajem i limitami. Zobacz [Pisanie testów](/docs/guides/writing-tests).
