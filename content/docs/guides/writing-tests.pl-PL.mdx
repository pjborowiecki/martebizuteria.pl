W `src/` jest 1227 plików testowych. Testy leżą obok kodu, który pokrywają, w katalogu `__test__/`, i nazywają się od pliku źródłowego. Uruchamiają się przez `vite-plus/test` — `describe`, `it`, `expect` i `vi` importuj zawsze stamtąd, nigdy wprost z `vitest`. Uruchamiaj je przez `bun run test`, nie `bun test`: własny runner Buna pomija projekty Vitest, środowisko jsdom i plik konfiguracyjny.

## Trzy projekty

`vite.config.ts` definiuje trzy projekty Vitest, rozróżniane nazwą pliku:

| Projekt       | Pliki                                              | Środowisko | Plik konfiguracyjny             | Liczba |
| ------------- | -------------------------------------------------- | ---------- | ------------------------------- | ------ |
| `node`        | `*.test.ts` / `*.test.tsx`, poza dwoma pozostałymi | `node`     | brak                            | 477    |
| `integration` | `*.integration.test.{ts,tsx}`                      | `node`     | brak                            | 127    |
| `component`   | `*.component.test.{ts,tsx}`                        | `jsdom`    | `src/platform/testing/setup.ts` | 623    |

```sh
bun run test              # wszystkie trzy
bun run test:unit         # tylko node
bun run test:integration  # tylko integration
bun run test:component    # tylko component
bun run test:changed      # tylko testy dotknięte Twoimi zmianami
bun run test:coverage     # wszystkie trzy, z pokryciem
vp test watch             # tryb obserwowania
```

`bun run test:watch` to `vp test watch`, który działa dalej i po każdej zmianie ponownie uruchamia testy, których ona dotyczy; `vp test` bez podkomendy uruchamia testy raz, tak jak `bun run test`.

Projekty dziedziczą główny blok `test` (`extends: true`). `passWithNoTests: false` sprawia, że projekt, który nic nie dopasuje, oznacza porażkę. `env: loadEnv("test", ...)` ładuje `.env.test`, zawierający atrapy wszystkich sekretów — dzięki temu moduły uwierzytelniania i Stripe można zaimportować bez prawdziwych danych dostępowych. Wyszukiwanie testów pomija `e2e/`, `opensrc/`, `dist/` i katalog migracji, a poza `src/` znajduje tylko test hooka komunikatu commita w `scripts/__test__/`, który uruchamia projekt `node`. Projekt `integration` podnosi limity czasu testów i hooków do 30 s (`INTEGRATION_TEST_TIMEOUT_MS`); plik konfiguracyjny testów komponentów ustawia limit testu na 15 s.

## Test jednostkowy

Zwykłe funkcje nie wymagają ceremonii. `src/modules/_core/utils/__test__/table-export.csv.test.ts`:

```ts
import { describe, expect, it } from "vite-plus/test"

import { serializeTableExportCsv } from "~/src/modules/_core/utils/table-export"

import { singleCellDocument } from "./table-export.fixtures"

describe("serializeTableExportCsv", () => {
  it("turns a value that starts like a formula into text so a spreadsheet does not run it", () => {
    expect(serializeTableExportCsv(singleCellDocument("=SUM(A1:A2)"))).toContain("\r\n'=SUM(A1:A2)\r\n")
  })
})
```

Dwie rzeczy warte skopiowania. Po pierwsze, opis w `it` mówi o **zachowaniu i o tym, dlaczego jest ważne**, a nie o mechanice — „turns a value that starts like a formula into text so a spreadsheet does not run it”, nie „prefixes an apostrophe”. Po drugie, globalne obiekty przeglądarki podstawia się przez `vi.stubGlobal` i zwalnia w `afterEach` przez `vi.unstubAllGlobals()`, tak jak robi to `download.test.ts` dla `downloadTextFile`:

```ts
vi.stubGlobal("URL", { createObjectURL, revokeObjectURL })
vi.stubGlobal("document", { createElement: vi.fn(() => anchor) })
```

## Testowanie funkcji serwerowej

Testy przypadków użycia mockują moduły, do których sięga handler — zawsze moduł middleware, a do tego moduły bazy danych, akcesorów albo dostawców, które wywołuje — i zastępują `createServerFn` sztucznym budowniczym wstrzykującym znaną sesję.

Mockuj `auth.middleware` z `RATE_LIMITS` o kształcie prawdziwej stałej, `{ max, window }` (`SENSITIVE` to `{ max: 3, window: 60 }`), i śledź `withRateLimit`, żeby sprawdzić regułę, którą stosuje przypadek użycia. Z `src/modules/payment/use-cases/__test__/remove-duplicate-saved-cards.test.ts`:

```ts
const calls = vi.hoisted(() => ({
  detach: vi.fn<(id: string) => Promise<unknown>>(),
  getCustomerId: vi.fn<(userId: string) => Promise<string | undefined>>(),
  list: vi.fn<(params: object) => Promise<{ data: StoredCard[] }>>(),
  retrieve: vi.fn<(id: string) => Promise<StoredCard>>(),
  withRateLimit: vi.fn<(kind: string, limit: object) => object>(() => ({})),
}))

vi.mock("~/src/integrations/better-auth/auth.middleware", () => ({
  RATE_LIMITS: { SENSITIVE: { max: 3, window: 60 } },
  authorized: () => ({}),
  withRateLimit: calls.withRateLimit,
}))

const rateLimitsAppliedOnLoad = [...calls.withRateLimit.mock.calls]

it("is rate limited like the other card endpoints", () => {
  expect(rateLimitsAppliedOnLoad).toStrictEqual([["remove-duplicate-saved-cards", { max: 3, window: 60 }]])
})
```

`withRateLimit` wywołuje się przy imporcie modułu przypadku użycia, więc test kopiuje jego wywołania, zanim `beforeEach` z `vi.clearAllMocks()` je wyczyści.

Resztę wzorca pokazują testy adresów. Z `src/modules/address/use-cases/__test__/address-use-cases.test.ts`, którego własny mock `auth.middleware` używa tego samego kształtu `{ max, window }`:

```ts
vi.mock("~/src/integrations/drizzle-orm/drizzle.database", () => ({
  db: { query: { address: { findMany: database.findMany } } },
}))
vi.mock("~/src/modules/address/address.accessors", () => ({
  createUserAddress: accessors.create,
  deleteUserAddress: accessors.delete,
  setDefaultUserAddress: accessors.setDefault,
  updateUserAddress: accessors.update,
}))
vi.mock("@tanstack/react-start", () => ({
  createServerFn: () => {
    const builder = {
      handler: (handler: (options: { context: unknown; data: unknown }) => unknown) => (options?: { data?: unknown }) =>
        handler({ context: { auth: { user: { id: USER_ID } } }, data: options?.data }),
      middleware: () => builder,
      validator: (validate: (input: unknown) => unknown) => {
        const validating = {
          handler: (handler: (options: { context: unknown; data: unknown }) => unknown) => (options?: { data?: unknown }) =>
            handler({ context: { auth: { user: { id: USER_ID } } }, data: validate(options?.data) }),
          middleware: () => validating,
          validator: () => validating,
        }

        return validating
      },
    }

    return builder
  },
}))
```

Sztuczny budowniczy wciąż uruchamia **prawdziwy walidator**, więc niepowodzenia schematu są testowane. Mocki deklaruje się przez `vi.hoisted`, żeby istniały przed uruchomieniem fabryk modułów:

```ts
const accessors = vi.hoisted(() => ({
  create: vi.fn(),
  delete: vi.fn(),
  setDefault: vi.fn(),
  update: vi.fn(),
}))
```

Co taki test powinien pokryć:

- **Użytkownika dostarcza sesja, nie wejście.** `expect(accessors.create).toHaveBeenCalledExactlyOnceWith({ ...fields, userId: USER_ID })`.
- **Pola opcjonalne przechodzą dalej.** Przekaż `phone` i `postalCode` i sprawdź, że dotarły do akcesora.
- **Ogranicznik żądań jest skonfigurowany.** `expect(rateLimitsAppliedOnLoad).toStrictEqual([["remove-duplicate-saved-cards", { max: 3, window: 60 }]])`.
- **Nieprawidłowe wejście jest odrzucane**, przy pomocy `it.each` po błędnych przypadkach.
- **Każdy kod rzucany przez handler.** Brakujący wiersz musi dać `NOT_FOUND`, zduplikowany handle `CONFLICT`, i tak dalej.

Funkcja serwerowa, która filtruje albo formatuje według daty, czyta strefę czasową administratora przez `resolveRequestDisplayPreferences()`. Zastąp ją stałymi preferencjami z `src/platform/testing/mocks/display-preferences.ts` (`{ formatLocale: "pl-PL", timeZone: "Europe/Warsaw" }`):

```ts
vi.mock("~/src/integrations/use-intl/i18n.display-preferences", () => import("~/src/platform/testing/mocks/display-preferences"))
```

## Testowanie z prawdziwym SQL-em

Dla zapytania, w którym poprawność _tkwi_ w SQL-u — escapowanie znaków specjalnych, semantyka `LIKE`, kolejność zależna od indeksu — napisz test integracyjny na prawdziwej bazie SQLite w pamięci:

```ts
import { drizzle } from "drizzle-orm/d1"
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core"
import { DatabaseSync } from "node:sqlite"
import { afterAll, beforeAll, describe, expect, it } from "vite-plus/test"

import { createTestD1Database } from "~/src/platform/testing/mocks/d1"

import { buildAdminSearchOrCondition } from "~/src/modules/_core/utils/search-conditions.server"

const sqlite = new DatabaseSync(":memory:")

const database = drizzle(createTestD1Database(sqlite))
```

`createTestD1Database` w `src/platform/testing/mocks/d1.ts` dostosowuje moduł Node'a `node:sqlite` do interfejsu `D1Database` — `prepare`, `bind`, `all`, `run`, `raw` oraz `batch`, które owija instrukcje w prawdziwe `begin`/`commit`/`rollback` i wykonuje jedną paczkę naraz. Egzekwuje dwa limity D1, których lokalny SQLite by nie postawił: `bind` rzuca `D1_ERROR` przy więcej niż 100 parametrach, a wzorce `LIKE` są ograniczone do 50 bajtów. Przyjmuje też opcjonalne wywołanie zwrotne `onQuery`, więc test może sprawdzić, jaki SQL faktycznie poszedł do bazy, oraz opcjonalne `onRoundTrip`, wywoływane raz na każde `batch` i raz na każdą instrukcję wykonaną poza nim, więc test może sprawdzić, ile żądań dotarło do D1.

Deklaruj tabelę lokalnie, zamiast importować schemat produkcyjny, kiedy potrzebujesz tylko kilku kolumn, utwórz ją w `beforeAll` i zamknij bazę przez `sqlite.close()` w `afterAll`. Wspomniany test wyszukiwania dobrze pokazuje, _do czego_ służą testy integracyjne: podaje `100%`, `ring_1`, `path\`, `%_\` i `x' OR 1=1 --` i sprawdza, że każdy z nich jest dopasowywany jako dosłowny tekst.

### Na zmigrowanym schemacie

Gdy test potrzebuje prawdziwych tabel, odtwórz migracje zamiast deklarować tabele. `src/platform/testing/mocks/migrations.ts` czyta każdy plik `.sql` z `src/integrations/drizzle-orm/migrations/` i eksportuje:

- `applyMigrationHistory(sqlite)`, które wykonuje je wszystkie w kolejności nazw plików, dzieląc każdy plik po `--> statement-breakpoint`, więc baza ma ten sam schemat co produkcja;
- `applyMigration(sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)`, które wykonuje jedną; `MIGRATION` nazywa migracje, które testy odtwarzają osobno.

Korzysta z nich 78 plików testowych. `src/modules/verification/use-cases/__test__/delete-expired-verifications.integration.test.ts` podmienia instancję Drizzle na taką, która działa na zmigrowanej bazie w pamięci, i wywołuje prawdziwy przypadek użycia:

```ts
const { sqlite } = await vi.hoisted(async () => {
  const { DatabaseSync } = await import("node:sqlite")

  return { sqlite: new DatabaseSync(":memory:", { enableDoubleQuotedStringLiterals: true }) }
})

vi.mock(import("~/src/integrations/drizzle-orm/drizzle.database"), async () => {
  const { drizzle } = await import("drizzle-orm/d1")
  const schema = await import("~/src/integrations/drizzle-orm/drizzle.schemas")
  const { createTestD1Database } = await import("~/src/platform/testing/mocks/d1")

  return { db: drizzle(createTestD1Database(sqlite), { schema }) }
})

beforeAll(() => {
  applyMigrationHistory(sqlite)
})
```

Otwieraj bazę z `enableDoubleQuotedStringLiterals: true`, tak jak każdy test odtwarzający historię.

### Testowanie migracji danych

Migracja, która zmienia wiersze, dostaje test integracyjny i wpis w `MIGRATION`. `src/modules/order/__test__/order.past-guest-claim-backfill.integration.test.ts` pokrywa `20261016140000_claim_past_guest_orders.sql`: `beforeEach` tworzy tylko kolumny, które migracja czyta i zapisuje, i wstawia przypadki, każdy test wykonuje `applyMigration(database.sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)` i odczytuje wiersze zwykłym SQL-em, parsując je przez Zod. Jego cztery testy to dobra lista kontrolna — wiersze, które musi zmienić, wiersze, które musi zostawić, wpisy audytu, które zapisuje, i to, że ponowne uruchomienie niczego nie zmienia:

```ts
it("claims nothing more when it runs again", () => {
  applyMigration(database.sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)
  const ordersAfterFirstRun = readOrders()

  applyMigration(database.sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)

  expect(readOrders()).toStrictEqual(ordersAfterFirstRun)
  expect(readClaims()).toHaveLength(2)
})
```

Samą migrację opisuje przewodnik [Migracje bazy danych](/docs/guides/database-migrations).

## Testowanie komponentu

`renderWithProviders` w `src/platform/testing/lib/render.tsx` owija drzewo w `IntlProvider`, `QueryClientProvider` i `RouterContextProvider`:

```tsx
const { queryClient, router } = renderWithProviders(<CategoriesTable />)
```

Domyślnie dostajesz świeży `QueryClient` z wyłączonymi ponowieniami zapytań i mutacji oraz router na historii w pamięci pod `/`. Przekaż `queryClient` albo `router`, żeby to nadpisać, a `createTestRouter("/some/path")` dla innej ścieżki startowej. Dla hooka owiń `renderHook` w `TestProviders` z tego samego pliku, tak jak `src/hooks/__test__/use-cart-availability.component.test.tsx`.

Tłumaczenia pochodzą z `src/platform/testing/lib/messages.ts`, które zachłannie globuje **wszystkie** pliki w `messages/en-US/` i buduje całe drzewo przez `buildMessageTree`. Językiem testów jest więc zawsze `en-US`, a strefą czasową `I18N.DEFAULT_TIMEZONE` (`Europe/Warsaw`). Testowe providery nie renderują `DisplayPreferencesContext`, więc `useFormatter()` i `useFormatLocale()` z `src/hooks/use-display-format.ts` sięgają po ten język i tę strefę.

Klucz, którego brakuje w katalogu angielskim, oblewa test. W aplikacji use-intl tylko zgłasza błąd `MISSING_MESSAGE` przez `console.error` i zamiast tekstu renderuje ścieżkę klucza, na przykład `pages.admin.catalog.categories.title`; `IntlProvider` w `TestProviders` dostaje `onError`, który rzuca każdy błąd use-intl, więc zamiast tego renderowanie kończy się błędem. Test, który owija komponent we własny `IntlProvider`, na przykład żeby wyrenderować wersję polską, dziedziczy ten `onError` i musi przekazać każdą przestrzeń nazw, którą czyta komponent. Zestaw E2E stosuje tę samą zasadę do prawdziwych stron: oblewa test, którego strona zaloguje błąd tłumaczenia (zobacz [Tłumaczenia](/docs/guides/i18n-messages)).

`src/platform/testing/setup.ts` wykonuje się przed każdym testem komponentu. Rozszerza `expect` o matchery jest-dom i podstawia to, czego brakuje w jsdom: `IntersectionObserver`, `ResizeObserver` (atrapa raportuje stałe 1024×768, czego potrzebuje mierzenie kolumn w tabeli), `matchMedia` (zawsze `matches: false`), `showModal` i `close` z `HTMLDialogElement` (ustawiają albo usuwają `open`, a `close` wysyła zdarzenie `close`) oraz `Document.elementFromPoint` (zwraca `null`). Ustawia `asyncUtilTimeout` Testing Library na 5 s i limit testu na 15 s, a po zakończeniu testów pliku czyści każdy pozostawiony przez niego timeout i interwał. Instaluje też dwa globalne mocki:

```ts
vi.mock(import("@tanstack/react-start"), async (importOriginal) => {
  const actual = await importOriginal()
  const { withTestRpc } = await import("~/src/platform/testing/lib/server-function")

  return {
    ...actual,
    createServerFn: new Proxy(actual.createServerFn, {
      apply: (target, thisArg, args: unknown[]) => withTestRpc(Reflect.apply(target, thisArg, args)),
    }),
  }
})
```

`withTestRpc` w `src/platform/testing/lib/server-function.ts` owija każdą funkcję serwerową tak, że jej wywołanie uruchamia handler w tym samym procesie, wewnątrz `runWithStartContext`, zamiast próbować wykonać żądanie HTTP. `getRequest` jest również mockowane i zwraca ustalone `Request` dla `http://127.0.0.1:3000/`. Zatem w teście komponentu funkcja serwerowa **wykonuje się naprawdę, przez swoje prawdziwe middleware i walidator** — jeśli chcesz, żeby się nie wykonała, zamockuj jej moduł.

## Testowanie trasy

Trasy testuje się przez przechwycenie `createFileRoute` i uchwycenie obiektu opcji:

```tsx
const captured: { current: CategoriesRouteDefinition | undefined } = { current: undefined }

vi.mock("@tanstack/react-router", async (importOriginal) => {
  const actual = await importOriginal<typeof ReactRouter>()

  return {
    ...actual,
    createFileRoute: () => (options: CategoriesRouteDefinition) => {
      captured.current = options

      return { options }
    },
  }
})

await import("~/src/routes/admin.catalog.categories.index")

const route = captured.current
```

Zwróć uwagę na `await import(...)` **po** mockach — moduł trasy musi zostać załadowany, gdy przechwycenie jest już na miejscu, dlatego te pliki mają importy poniżej swoich wywołań `vi.mock`. Ta odwrócona kolejność jest celowa, a nie przeoczeniem.

Mając opcje, możesz sprawdzić `staleTime`, `shouldReload` i `staticData.namespaces`, wywołać `loader({ context: { queryClient } })` i zweryfikować, które zapytania zostały rozgrzane, oraz wyrenderować `component` przez `renderWithProviders`. Ciężkie komponenty potomne zwykle się podstawia:

```tsx
vi.mock("~/src/presentation/components/custom/pages/admin/catalog/categories/components/categories-table", async () => {
  const { useCategoriesSheet } =
    await import("~/src/presentation/components/custom/pages/admin/catalog/categories/hooks/use-categories-sheet")

  return {
    CategoriesTableContent: (): JSX.Element => {
      const { mode, open } = useCategoriesSheet()

      return <p>{`${mode}|${String(open)}`}</p>
    },
  }
})
```

Ta atrapa renderuje badany stan jako tekst, więc asercja to jedno `screen.getByText("closed|false")`.

## Pokrycie

`bun run test:coverage` używa dostawcy v8 i wymusza progi:

```ts
thresholds: {
  autoUpdate: false,
  branches: 100,
  functions: 100,
  lines: 100,
  statements: 100,
}
```

Pokrycie liczy `src/**/*.{ts,tsx}`, z wyłączeniem plików testowych, katalogów `__test__/`, plików `.d.ts`, `src/routeTree.gen.ts`, `src/integrations/**/migrations/**`, `src/presentation/components/shadcn/**` (komponenty podstawowe skopiowane z zewnątrz) oraz `src/platform/testing/**`. Każdy próg wynosi 100, więc zmiana, która zostawia jakikolwiek kod bez pokrycia, nie przechodzi; dopisz testy albo usuń gałąź, do której nie prowadzi żadne wejście, zamiast obniżać próg. `autoUpdate: false` sprawia, że liczby nie zmieniają się same.

CI (`.github/workflows/ci.yml`) uruchamia `bun run check`, potem `bun run test:coverage`, potem `bun run build:preview`, i wysyła raport pokrycia jako artefakt. Drugie zadanie w tym samym przepływie uruchamia zestaw end-to-end w Chromium.

## Asercje warte poznania

- `toHaveBeenCalledExactlyOnceWith(...)` — używane w całym repozytorium i mocniejsze niż `toHaveBeenCalledWith` plus osobne sprawdzenie liczby wywołań.
- `toStrictEqual` zamiast `toEqual`, żeby przypadkowa właściwość `undefined` zawiodła test.
- `it.each([...])("refuses the incomplete address %j", (data) => ...)` dla przypadków sterowanych tabelą.
- Matchery jsdom z `@testing-library/jest-dom` są rozszerzane w pliku konfiguracyjnym i typowane przez `src/platform/testing/vitest-env.d.ts`, więc `toBeInTheDocument()` i pokrewne działają w testach komponentów.

## Testy end-to-end

Playwright steruje zbudowaną kopią sklepu w Chromium i WebKit. Specyfikacje leżą w `e2e/specs/`, obiekty stron w `e2e/pages/`, a fikstury w `e2e/fixtures/`; specyfikacja importuje `test` i `expect` z `e2e/fixtures/test.ts`.

```sh
bun run test:e2e:install  # raz: przeglądarki Chromium i WebKit
bun run test:e2e          # wszystkie projekty
bun run test:e2e:pr       # chromium i chromium-shop-wide, tak jak CI na pull requestach
bun run test:e2e:smoke    # e2e/specs/smoke.spec.ts w Chromium
bun run test:e2e:stripe   # projekt stripe-test-mode
bun run test:all          # bun run test, potem test:e2e:smoke
```

`playwright.config.ts` definiuje sześć projektów: `setup` loguje zaseedowanego administratora i klienta; `chromium` i `webkit` uruchamiają każdy `*.spec.ts` poza specyfikacjami trybu testowego Stripe; `stripe-test-mode` uruchamia tylko `*stripe-test-mode.spec.ts`, na sandboksie Stripe; a `chromium-shop-wide` i `webkit-shop-wide` uruchamiają specyfikacje `*.shop-wide.ts`, które zmieniają stan czytany przez wszystkie inne, po zestawie swojej przeglądarki.

Zestaw działa na testowym Workerze, nie na serwerze deweloperskim. Poza CI `webServer` Playwrighta uruchamia `bun run db:reset:test && bun run build:test && bun run start:test`: świeże lokalne D1 w `.wrangler/test` z każdą migracją i danymi z `scripts/seed-test.ts`, build `--mode test`, którego punktem wejścia Workera jest `src/platform/testing/worker.ts`, serwowany pod `http://127.0.0.1:3000`. Ten Worker odpowiada za Stripe, Resend i InPost z emulatorów w pamięci i serwuje trasy `/__test/...`, przez które specyfikacje czytają przechwycone e-maile i rozliczają płatności. Playwright używa ponownie serwera, który już odpowiada pod tym adresem, więc najpierw zatrzymaj `bun run dev` albo starsze `start:test`. [Debugowanie lokalne](/docs/guides/local-debugging#lokalne-środowisko-testowe) uruchamia ten sam build ręcznie.

CI uruchamia zestaw w dwóch miejscach:

- `ci.yml`, przy każdym pull requeście i pushu do `main`: zadanie „Build and E2E” uruchamia projekty `chromium` i `chromium-shop-wide` przez `e2e-reusable.yml`.
- „E2E (full)” (`e2e-full.yml`), przy każdym pushu do `main` (WebKit, bo Chromium przeszło już w CI), co tydzień i na żądanie (obie przeglądarki). Każdy przebieg ma też zadanie `stripe-test-mode`, które buduje testowego Workera z sekretami repozytorium `E2E_STRIPE_SECRET_KEY` i `E2E_STRIPE_PUBLISHABLE_KEY` i uruchamia `bun run test:e2e:stripe`. Sekrety są ustawione, więc zadanie płaci przez sandbox przy każdym przebiegu; bez nich zgłosiłoby ostrzeżenie, a specyfikacje zostałyby pominięte.

[Testy](/docs/tooling/testing#testy-end-to-end) opisują projekty, emulatory, tryb testowy Stripe, dane startowe i zasady pisania specyfikacji.
