description: "Build an admin grid on the shared datagrid: columns, the grid instance, persisted preferences, toolbar actions, the export and server-side pagination."
---

Every admin list in M'Arte is built on one shared data grid in `src/presentation/components/custom/datagrid/`. It wraps TanStack Table v9 and adds column resizing, drag reordering, pinning, per-user persisted preferences, a skeleton loading state, a debounced search box, row drag-and-drop and pagination.

The clearest end-to-end example is the categories grid, in `src/presentation/components/custom/pages/admin/catalog/categories/`. This guide follows it.

## The pieces

| File                                             | Role                                                       |
| ------------------------------------------------ | ---------------------------------------------------------- |
| `datagrid/components/create-data-grid.tsx`       | `createDataGrid<TRow>({ persistenceKey })` — the factory   |
| `datagrid/hooks/use-data-grid-instance.ts`       | `useDataGridInstance` — builds the TanStack table          |
| `datagrid/hooks/use-data-grid-preferences.ts`    | Column order, sizing and visibility, persisted             |
| `datagrid/components/data-grid-shell.tsx`        | `DataGridShell` — the card with a three-row grid layout    |
| `datagrid/components/selection-column.tsx`       | `selectionColumn(...)` — the checkbox column               |
| `datagrid/lib/data-grid.features.ts`             | The `tableFeatures(...)` set and the filter/sort functions |
| `datagrid/lib/data-grid.types.ts`                | `DataGridContextValue`, `DataGridColumnMeta`, reorder APIs |
| `datagrid/components/data-grid-export.tsx`       | `DataGridExport` — the export menu of the toolbar          |
| `datagrid/lib/data-grid-export.ts`               | `DataGridExportSource`, the exported columns and filters   |
| `datagrid/lib/catalog-table-global-filter.ts`    | `createCatalogTableGlobalFilterFn`                         |
| `datagrid/lib/data-grid-pagination.constants.ts` | Page sizes: 10, 25, 50, 100, 250, default 10               |

## 1. Create the grid namespace

One file, exporting one grid. From `.../categories/utils/categories-data-grid.ts`:

```ts
import { type ProductCategory } from "~/src/modules/product-category/product-category.types"

import { createDataGrid } from "~/src/presentation/components/custom/datagrid/components/create-data-grid"

export const CATEGORIES_DATA_GRID_KEY = "admin.catalog.categories"

export const categoriesDataGrid = createDataGrid<ProductCategory["adminListItem"]>({
  persistenceKey: CATEGORIES_DATA_GRID_KEY,
})
```

`createDataGrid` returns `{ Body, Export, Pagination, Provider, Toolbar, persistenceKey, useDataGrid }` — a private React context plus the five components that read from it. Each grid gets its own context, so two grids on one page never share state.

The `persistenceKey` is the storage key. Preferences are saved under `marte:datagrid:v1:<persistenceKey>` in `localStorage`, and the inline script in `datagrid/datagrid-init.ts` — injected by `src/routes/__root.tsx` — reads them before hydration and writes `--marte-dg-<slug>-<column>` CSS variables on `<html>`, so column widths do not jump on first paint. **Changing a `persistenceKey` discards every user's saved layout for that grid.**

## 2. Define the columns

Columns live in a hook so headers can be translated and cells can use `useFormatter`. From `.../categories/components/categories-columns.tsx`:

```tsx
const columnHelper = createColumnHelper<DataGridFeatures, ProductCategory["adminListItem"]>()

columnHelper.accessor("createdAt", {
  cell: ({ getValue }) => <span className="text-muted-foreground">{format.dateTime(new Date(getValue()), { dateStyle: "medium" })}</span>,
  header: t("columns.createdAt"),
  id: CATEGORY_TABLE_COLUMN_ID.createdAt,
  maxSize: 320,
  meta: {
    skeletonVariant: "date",
  },
  minSize: CATEGORY_TABLE_COLUMN_SIZE.createdAt,
  size: CATEGORY_TABLE_COLUMN_SIZE.createdAt,
})
```

Conventions:

- `id` comes from the module's `*_TABLE_COLUMN_ID` map and `size`/`minSize` from `*_TABLE_COLUMN_SIZE`, both in the module's constants file. The persisted preferences key off the column id, so an id is as durable as a `persistenceKey`.
- `meta` is typed by `DataGridColumnMeta`. The options are `cellClassName`, `headClassName`, `fillsRemainingWidth`, `absorbsTrailingSlack`, `exportValue`, `filterOnly`, `preventRowClick` and `skeletonVariant`. `exportValue` makes the column exportable; step 5 describes it. `skeletonVariant` picks the placeholder shape while the query is fetching: `badge`, `checkbox`, `date`, `icon`, `iconEnd`, `number`, `recordId`, `text`, `thumbnail` or `title`.
- Utility columns are `select`, `drag`, `image` and `actions` — the ids listed in `DATAGRID_UTILITY_COLUMN_IDS`. They are never resizable, never reorderable and excluded from persisted sizing. Give them a fixed width with `fixedDataGridColumnWidth(size)`, which returns matching `size`, `minSize` and `maxSize`.
- The checkbox column is `selectionColumn(columnHelper, { all: t(...), row: t(...) })`, with the labels taken from the module's `*_TABLE_A11Y_KEYS`.
- Cells are small components declared above the column builder, not inline closures, so they can be memoised and stay under the function-length limit.

Because a real catalog grid has more columns than a 150-line function allows, split the builder: `buildCategoryTimestampColumns(context)` and `buildCategoryDataGridColumns(context)` in that file both return `columnHelper.columns([...])` and are composed by the hook.

## 3. Build the grid instance

A `use-<entity>-data-grid.ts` hook loads the data and returns a `DataGridContextValue`:

```ts
const { data: categories, isFetching } = useSuspenseQuery(getAdminCategoriesQuery())
const columns = useCategoryColumns()
const initialColumnOrder = useMemo(() => getDataGridColumnIds(columns), [columns])

const { columnReorder, hasPreferenceOverrides, resetPreferences, table } = useDataGridInstance({
  columns,
  data: ordering.items,
  defaultColumnVisibility: CATEGORY_TABLE_DEFAULT_COLUMN_VISIBILITY,
  getRowId: (row) => row.id,
  globalFilterFn,
  initialColumnOrder,
  initialColumnPinning: CATEGORY_TABLE_COLUMN_PINNING,
  persistenceKey: categoriesDataGrid.persistenceKey,
})
```

`useDataGridInstance` sets `columnResizeMode: "onChange"`, enables pinning, resizing and row selection, applies the `dataGridFeatures` set, computes min and max sizes from the column definitions, and hands the resulting state to `useDataGridPreferences`. Everything it needs is in the options; do not build a `useTable` call of your own.

The hook returns the context value the grid components expect:

```ts
return useMemo(
  () => ({
    columnReorder,
    hasPreferenceOverrides,
    isLoading: showSkeletonRows,
    onRowClick,
    persistenceKey: categoriesDataGrid.persistenceKey,
    resetPreferences,
    rowReorder,
    searchPlaceholder: t("searchPlaceholder"),
    table,
  }),
  [columnReorder, hasPreferenceOverrides, onRowClick, resetPreferences, rowReorder, showSkeletonRows, t, table],
)
```

### Client-side search

`createCatalogTableGlobalFilterFn` takes a function from a row to the strings that should match, and the filter lowercases, joins and substring-matches them:

```ts
const globalFilterFn = useMemo(
  () =>
    createCatalogTableGlobalFilterFn<ProductCategory["adminListItem"]>((row) => {
      const statusLabel = t(row.status === CATEGORY_STATUS.ACTIVE ? CATEGORY_STATUS_LABEL_KEYS.active : CATEGORY_STATUS_LABEL_KEYS.draft)

      return getCategoryAdminSearchParts(row, statusLabel)
    }),
  [t],
)
```

Passing the translated status label in means a Polish admin can search for "aktywna" and an English one for "active", against the same rows.

### Row drag-and-drop

Reorderable grids expose a `RowReorderApi`, and only when the natural order is visible — dragging rows while a sort or a filter is applied would be meaningless:

```ts
const columnFilters = table.atoms.columnFilters.get()
const sorting = table.atoms.sorting.get()
const search = String(table.atoms.globalFilter.get() ?? "").trim()
const naturalOrder = sorting.length === 0 && columnFilters.length === 0 && search === ""
```

The drag handlers themselves come from a `use-<entity>-ordering.ts` hook that keeps an optimistic local order and calls the reorder mutation.

## 4. Compose the table

Destructure the grid's components once, at the bottom of the file, and lay them out inside `DataGridShell`:

```tsx
const { Body, Export, Pagination, Provider, Toolbar } = categoriesDataGrid
```

```tsx
<Provider value={grid}>
  <div className={ADMIN_CATALOG_DATAGRID_PAGE_CLASS}>
    <CategoriesStats />
    <DataGridShell>
      <Toolbar actions={toolbarActions}>
        <CategoriesRefreshAction />
        <Export />
        <CategoriesStatusFilter />
      </Toolbar>
      <Body />
      <Pagination />
    </DataGridShell>
  </div>
</Provider>
```

`DataGridShell` is a card with `grid-rows-[auto_minmax(0,1fr)_auto]`, so the toolbar and pagination keep their height and the body scrolls. The three `Toolbar` slots are `children` (inline controls, rendered next to the search box), `filters` and `actions` (right-aligned). When `hasPreferenceOverrides` is true the toolbar shows a reset control wired to `resetPreferences`.

## 5. Let the admin export the table

The toolbar's **Export** menu downloads the table as CSV, JSON, XML or plain text. A file holds the columns the admin can see, in the order they see them, under the headers they read, and every row the current filters and search select — not only the page on screen. A grid loaded whole exports its rows in the order its sort shows them. A server-paged grid — the audit log, orders, customers and newsletter subscribers — exports in the server's order, because a header sort there only reorders the page on screen; the products grid sends its sort to the server and exports in that order.

A column takes part when its `meta` has an `exportValue`: a function from the row to the text its cell shows, or `undefined` for an empty cell. Write what the admin sees — translated labels, prices through `formatPrice` with the format locale, dates through `useFormatter` — because the file keeps no raw values. Columns without one, such as `select`, `drag`, `image` and `actions`, are never exported, and a column whose header is not a plain string would be exported under its id, so give an exportable column a translated `header`. From `.../audit/lib/audit-column-defs.tsx`:

```tsx
columnHelper.accessor("detail", {
  cell: ({ getValue }) => <AuditDetailCell detail={getValue()} />,
  header: t("audit.columns.detail"),
  id: AUDIT_LOG_TABLE_COLUMN_ID.detail,
  meta: {
    exportValue: (row) => (row.detail === undefined ? undefined : formatAuditLogDetail(row.detail, { locale: formatLocale, t })),
    skeletonVariant: "text",
  },
  size: AUDIT_LOG_TABLE_COLUMN_SIZE.detail,
})
```

`exportValue` is typed with the grid's row: `data-grid.types.ts` declares it on TanStack's own `ColumnMeta` interface, which knows the row type, and that interface extends `DataGridColumnMeta` for the other options.

Then the grid hook says what is exported by adding an `exportSource` to its context value:

| Field      | Meaning                                                                                                                                                        |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list`     | A stable name for the file name and the metadata, such as `audit-log`                                                                                          |
| `title`    | The page title in the page language                                                                                                                            |
| `filters`  | The active filters in words, as `{ label, value }`. `exportFilter(label, value)` leaves out a filter that is not set and `describeDateFilter` words a date one |
| `loadRows` | For a server-paged grid, loads every row through the list's export server function with the filters, search and sort of the page query but no page             |
| `search`   | For a source with `loadRows`, the search it sent to the server — the debounced value, not the text still being typed in the search box                         |

The export adds the search to the filters: the `search` of a source with `loadRows`, or the search box of a grid loaded whole. Such a grid leaves `loadRows` out, and the export takes the rows it holds after its filters and sort, across all pages. A list too long for one Worker request reads its export in pages: the audit log's `loadRows` asks `exportAuditLogs` for one `LIST_PAGE_SIZE_MAX` page at a time until a page comes back short, and every page after the first reads only entries recorded before the moment the first page fixed, so entries recorded meanwhile do not shift the pages. Abridged from `.../audit/hooks/use-audit-export-source.ts`:

```ts
const loadAuditLogPages = async (input: AuditExportInput, page: number, until?: number): Promise<AuditLog["adminListItem"][]> => {
  const result = await exportAuditLogs({ data: { ...input, page, until } })

  return result.hasMore ? [...result.items, ...(await loadAuditLogPages(input, page + LIST_PAGE_STEP, result.until))] : result.items
}

return useMemo(
  () => ({
    filters: [
      ...exportFilter(t("audit.columns.category"), input.category === undefined ? undefined : t(`audit.categories.${input.category}`)),
      ...exportFilter(t("audit.columns.status"), input.severity === undefined ? undefined : t(`audit.severity.${input.severity}`)),
    ],
    list: AUDIT_LOG_EXPORT_LIST,
    loadRows: () => loadAuditLogPages(input, LIST_PAGE_FIRST),
    search: input.search,
    title: t("audit.title"),
  }),
  [input, t],
)
```

The export server function lives with the list in `use-cases/export-<entity>.ts`. It is guarded like the list, takes the list's input without `page` and `pageSize`, returns the rows mapped like the list items, and records the export through `recordListExportedAudit` with an entry for the list in `LIST_EXPORT_AUDIT_EVENTS` and a `*_LIST_EXPORTED` action with its labels in both locales.

Last, put `<Export />` in the toolbar, next to the refresh button. `Export` throws when the context value has no `exportSource`, so a grid that should not be exported simply leaves the component out.

The serializers are plain functions in `src/modules/_core/utils/table-export.ts`, tested in its `__test__/` folder:

- **CSV**: a UTF-8 byte order mark so Excel reads Polish letters, CRLF line endings and RFC 4180 quoting. The fields are separated by semicolons when the admin's format locale writes decimals with a comma, as Polish does, so a double-clicked file opens in columns in a Polish Excel, and by commas otherwise; a field holding the separator is quoted. A value that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`, so a spreadsheet shows it instead of running it as a formula.
- **JSON**: pretty-printed, a `metadata` object (`list`, `title`, `exportedAt` in ISO UTC, `timeZone`, `rowCount`, `filters`, `columns`) and `rows` keyed by column id.
- **XML**: XML 1.0 with an `<export>` root holding `<metadata>` and `<rows>`, one `<row>` per row with an element per column id; the five special characters are escaped and characters XML 1.0 forbids are dropped.
- **TXT**: a header with the title, the export time and time zone, the row count and the filters, then one record per row as `Column: value` lines, a blank line between records.

Files are named `<list>-<YYYY-MM-DD-HHmm>.<ext>` on the admin's clock and saved through `downloadTextFile` from `src/modules/_core/utils/download.ts`. The menu's text lives under `export` in the `components.datagrid` namespace.

## 6. Add the row actions and bulk actions

Each grid has two sibling components:

- `<entity>-row-actions.tsx` — the per-row menu, rendered by the `actions` column with `meta.preventRowClick` so the menu does not also open the edit sheet.
- `<entity>-bulk-actions.tsx` — reads `table.getSelectedRowModel()` and acts on the selection, passed to the toolbar's `actions` slot.

Both call a `use-delete-<entity>.ts` or `use-reorder-<entity>.ts` hook that owns the mutation, the toast and the invalidation.

## 7. Server-side pagination, if the table is large

Categories, collections and attributes are loaded whole and filtered in the browser. Products are not: `src/routes/admin.catalog.products.index.tsx` drives a server query. The difference is four flags on `useDataGridInstance` plus controlled state:

```ts
manualFiltering, manualPagination, manualSorting,
pagination, sorting, pageCount, rowCount,
onPaginationChange, onSortingChange, onColumnFiltersChange,
```

`use-products-list-data.ts` then holds the two queries and switches between them:

```ts
const pageQueryOptions = getAdminProductsPageQuery({
  categoryId: filters.categoryId,
  createdAt: columnFilters.createdAt,
  page: pagination.pageIndex + LIST_PAGE_STEP,
  pageSize: pagination.pageSize,
  search,
  sort,
  status: filters.status,
})
```

`LIST_PAGE_STEP` from `src/modules/_core/utils/pagination.ts` is the 0-based-to-1-based conversion. `placeholderData: keepPreviousData` keeps the old page visible while the next one loads. `use-products-server-list-sync.ts` resets `pageIndex` to 0 whenever the search text, the column filters or the sort change — without it, a filter applied on page 7 would show an empty table.

Searches are debounced before they reach the query, through `use-admin-debounced-table-search.ts`, which builds on `src/hooks/use-debounce.ts`.

## 8. Test it

The grid hooks and components have tests under `datagrid/**/__test__/`, and each admin grid has its own under its feature folder. Grid tests run in the `component` Vitest project (`*.component.test.tsx`), which uses `jsdom` and `src/platform/testing/setup.ts` — that setup stubs `ResizeObserver` and `IntersectionObserver`, both of which the grid needs for column measurement. See [Writing tests](/docs/guides/writing-tests).
