---

Moduł to jedna funkcjonalność zbudowana wokół jednej tabeli bazy danych. Mieszka w `src/modules/{feature}/` i jest właścicielem wszystkiego, co jest prawdą o tej tabeli: jej kolumn, reguł walidacji, kluczy zapytań, typów wierszy i operacji. W `src/modules/` są obecnie 44 foldery: `_core` i 43 moduły funkcjonalne, z których 40 definiuje tabelę w `{feature}.schema.ts`. Najmniejszy kompletny moduł, od którego warto zacząć lekturę, to `src/modules/address`; najbogatszy to `src/modules/order` (53 pliki źródłowe, w tym 30 w `use-cases/`), a po nim `src/modules/product`.

Logika serwerowa, która nie należy do żadnej tabeli, nie dostaje modułu. Funkcje pomocnicze związane z żądaniem trafiają do `src/lib/`, adaptery dostawców do `src/integrations/{vendor}/`, a wspólne elementy potrzebne wielu modułom do `src/modules/_core/`. Folder w `src/modules` istnieje tylko dla tabeli bazy danych o tej samej nazwie, a `_core` jest jedynym folderem bez tabeli. Operacja czytająca kilka tabel trafia do modułu tabeli, której dotyczy: lista zamówień klienta jest w `order`, panel administratora, czyli przegląd sprzedaży sklepu, także w `order`, a aktywność przeglądania zapisywana przez klienta w `user`.

## Pliki

| Plik                              | Zawartość                                                                                                                                                                     |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{feature}.schema.ts`             | Tabela Drizzle `sqliteTable`, jej indeksy i `relations(...)`                                                                                                                  |
| `{feature}.zod.ts`                | Po jednym ręcznie pisanym schemacie Zod wejścia lub formularza na operację, bez importu tabeli                                                                                |
| `{feature}.constants.ts`          | Krotki kluczy zapytań i mutacji, limity długości kolumn, krotki wartości wyliczeniowych, czasy świeżości                                                                      |
| `{feature}.types.ts`              | Typy wierszy wywnioskowane z tabeli, eksportowane jako jeden interfejs na moduł                                                                                               |
| `{feature}.utils.ts`              | Czyste funkcje — mapowanie wierszy, normalizacja, wyznaczanie etykiet                                                                                                         |
| `{feature}.accessors.ts`          | Odczyty i zapisy do bazy, zapytania przygotowane i budowniki wsadów, tylko po stronie serwera                                                                                 |
| `use-cases/{verb-noun}.ts`        | Jedna funkcja serwerowa na plik, razem z opcjami zapytania lub mutacji                                                                                                        |
| `use-cases/{verb-noun}.server.ts` | Jedna operacja wyłącznie serwerowa na plik, eksportowana jako zwykła funkcja async: e-maile, sprzątanie, kroki zamówienia, konsumenci kolejek, rejestratory dziennika zdarzeń |
| `__test__/`                       | Testy nazwane od pliku źródłowego                                                                                                                                             |

Inne rodzaje plików nie należą do modułu: helper potrzebujący importów wyłącznie serwerowych trafia do akcesorów albo do use case'u, a kod działający tylko w przeglądarce do `src/presentation`.

`.server.` w nazwie pliku to nie tylko etykieta: ochrona importów TanStack Start odrzuca każdy plik `*.server.*` w buildzie klienckim, więc taki plik można importować tylko z kodu, który wykonuje się na serwerze. Co to umożliwia, wyjaśniają [Funkcje serwerowe](/docs/guides/server-functions#kod-serwerowy-poza-pakietem-klienta).

Nie każdy moduł potrzebuje wszystkich plików. `src/modules/two-factor` i `src/modules/courier` to po jednym pliku `{feature}.schema.ts`, a `src/modules/session` to schemat, plik stałych i jeden przypadek użycia wyłącznie serwerowy (`delete-expired-sessions.server.ts`), bo nic więcej nie jest o nich jeszcze prawdą.

## 1. Zdefiniuj tabelę

`src/modules/address/address.schema.ts` pokazuje cały wzorzec na jednym ekranie:

```ts
import { relations } from "drizzle-orm"
import { index, integer, sqliteTable, text } from "drizzle-orm/sqlite-core"

import { timestamps } from "~/src/integrations/drizzle-orm/drizzle.utils"

import { user } from "~/src/modules/user/user.schema"

export const address = sqliteTable(
  "address",
  {
    address1: text("address1", { length: 512 }).notNull(),
    address2: text("address2", { length: 512 }),
    city: text("city", { length: 256 }).notNull(),
    countryCode: text("country_code", { length: 2 }).notNull(),
    firstName: text("first_name", { length: 256 }),
    id: text("id").primaryKey(),
    isDefault: integer("is_default", { mode: "boolean" }).default(false).notNull(),
    lastName: text("last_name", { length: 256 }),
    phone: text("phone", { length: 32 }),
    postalCode: text("postal_code", { length: 32 }),
    province: text("province", { length: 256 }),
    userId: text("user_id").references(() => user.id, { onDelete: "cascade" }),
    ...timestamps(),
  },
  (table) => [index("address_userId_idx").on(table.userId), index("address_userId_isDefault_idx").on(table.userId, table.isDefault)],
)

export const addressRelations = relations(address, ({ one }) => ({
  user: one(user, {
    fields: [address.userId],
    references: [user.id],
  }),
}))
```

Konwencje obowiązujące w całym schemacie:

- Nazwy kolumn zapisujemy w snake_case, a właściwości TypeScriptu w camelCase. Właściwości są posortowane alfabetycznie — wymusza to reguła `sort-keys` Oxlinta wszędzie poza `src/routes/` — a `...timestamps()` jest na końcu.
- `id` to klucz główny typu `text` wypełniany przez `v7()` z pakietu `uuid`, importowany jako `v7 as uuidv7`. Nigdy nie pozwalamy generować go SQLite.
- `createdAt` i `updatedAt` pochodzą z `timestamps()` w `src/integrations/drizzle-orm/drizzle.utils.ts`. Oba to niepuste kolumny `integer(..., { mode: "timestamp_ms" })` z domyślną wartością SQL `(unixepoch() * 1000)` i z `$defaultFn(() => new Date())`, które Drizzle stosuje przy wstawianiu, a `updatedAt` dodatkowo ma `$onUpdateFn(() => new Date())`.
- Wartości logiczne to `integer(..., { mode: "boolean" })`.
- Klucze obce używają `.references(() => other.id, { onDelete: "cascade" })`, a `relations(...)` deklaruje złączenia, którymi może chodzić `db.query.<table>`.
- Nazwy indeksów mają wzór `<table>_<column>_idx`, a złożone wymieniają wszystkie kolumny: `address_userId_isDefault_idx`.

## 2. Zarejestruj tabelę

`src/integrations/drizzle-orm/drizzle.schemas.ts` to jedyny plik czytany przez klienta Drizzle i przez drizzle-kit. Wyeksportuj tam tabelę i jej relacje:

```ts
export { address, addressRelations } from "~/src/modules/address/address.schema"
```

Ten plik nie jest ułożony w kolejności zależności — `account` stoi przed `user`, a `productVariant` przed `product` — więc umieść swój eksport obok tabel, z którymi jest związany. Bez tej linii tabela jest niewidoczna dla `db.query`, dla `bun run db:generate` i dla `bun run db:push`, bo `drizzle.database.ts` przekazuje ten moduł do `drizzle(cacheStorefrontReads(timeD1Statements(env.DB)), { schema })`, a `src/integrations/drizzle-orm/drizzle.config.ts` wskazuje go drizzle-kitowi jako `schema`.

## 3. Napisz schematy Zod

`{feature}.zod.ts` importuje `zod/v4` (nie samo `zod`) i każdy schemat pisze ręcznie. Nigdy nie importuje `{feature}.schema.ts` swojego modułu ani `drizzle-zod`: formularze i parametry wyszukiwania tras walidują się w przeglądarce tymi schematami, więc import tabeli wysłałby Drizzle ORM na każdą stronę, która z nich korzysta. Typy wierszy pochodzą z tabeli przez `$inferSelect` i `$inferInsert` w `{feature}.types.ts`, a limity długości z pliku stałych, który czyta też tabela:

```ts
import zod from "zod/v4"

export const COUNTRY_CODE_LENGTH = 2

export const addressFieldsSchema = zod.object({
  address1: zod.string().min(1),
  address2: zod.string().optional(),
  city: zod.string().min(1),
  countryCode: zod.string().length(COUNTRY_CODE_LENGTH),
  firstName: zod.string().optional(),
  isDefault: zod.boolean().optional(),
  lastName: zod.string().optional(),
  phone: zod.string().optional(),
  postalCode: zod.string().optional(),
  province: zod.string().optional(),
})

export const addressIdInputSchema = zod.object({ addressId: zod.string().min(1) })
```

Gotowe budowniki pól leżą w `src/modules/_core/utils/zod-fields.ts`: `idField`, `uuidField`, `handleField`, `localeField`, `searchTermField`, `pageField`, `pageSizeField`, `dateColumnFilterField`, `numericColumnFilterField` i `dateTimeColumnFilterField`. Używaj ich, zamiast powtarzać to samo `zod.string().trim().min(1)`.

Większe moduły grupują wszystko w jednym eksportowanym obiekcie — `productCategoryZodSchemas` w `src/modules/product-category/product-category.zod.ts` udostępnia `createInput`, `updateInput`, `formValues` i inne — a limity długości biorą ze pliku stałych, żeby schemat i kolumna nigdy się nie rozjechały:

```ts
const categoryCreateInputSchema = zod.object({
  handle: zod.string().trim().min(CATEGORY_MIN_LENGTH).regex(CATEGORY_HANDLE_PATTERN),
  status: zod.enum(CATEGORY_STATUSES),
  titles: categoryTitlesSchema,
})
```

## 4. Zadeklaruj stałe

`{feature}.constants.ts` przechowuje wartości, co do których pozostałe warstwy muszą się zgadzać. Nic w tym pliku nie może importować z `src/presentation`. Jedynym istniejącym wyjątkiem jest `CATALOG_ADMIN_RECORD_ID_COLUMN_WIDTH_PX` — zwykła liczba z `src/presentation/components/custom/pages/admin/catalog/lib/catalog-admin-datagrid.constants.ts`, której sześć plików stałych (`discount`, `newsletter-subscriber`, `product-attribute`, `product-category`, `product-collection` i `user`) używa jako szerokości kolumny z identyfikatorem rekordu w swojej tabeli panelu; to nie jest wzorzec do naśladowania.

```ts
export const ADDRESS_QUERY_KEYS = {
  ALL: ["userAddresses"] as const,
} as const

export const ADDRESS_MUTATION_KEYS = {
  DELETE: ["address", "deleteUserAddress"] as const,
  SET_DEFAULT: ["address", "setDefaultUserAddress"] as const,
} as const
```

Moduły z powierzchnią administracyjną zagnieżdżają grupę `ADMIN`, bo cache panelu i cache witryny sklepowej unieważnia się niezależnie:

```ts
export const CATEGORY_QUERY_KEYS = {
  ADMIN: {
    ALL: ["admin", "categories"] as const,
    STATS: ["admin", "categories", "stats"] as const,
  },
  ALL: ["categories"] as const,
  BY_HANDLE: ["category"] as const,
} as const
```

Klucze zapytań są publicznym kontraktem modułu. `src/integrations/realtime-invalidation/realtime-invalidation.subscriptions.ts` wymienia je, żeby zdecydować, co unieważnia wiadomość WebSocket, więc przenosząc kod zachowaj wartości krotek bez zmian. Tutaj trzymamy również krotki wartości wyliczeniowych (`CATEGORY_STATUSES`), limity kolumn (`CATEGORY_COLUMN_LENGTH`), wzorce (`CATEGORY_HANDLE_PATTERN`) i czasy świeżości (`CATEGORY_QUERY_STALE_MS`).

## 5. Wywnioskuj typy

`{feature}.types.ts` eksportuje jeden interfejs na moduł i wyprowadza każdy jego element z tabeli albo ze schematu. Nie ma tu ręcznie pisanych kształtów wierszy:

```ts
import { type address } from "~/src/modules/address/address.schema"

export interface Address {
  insert: typeof address.$inferInsert
  select: typeof address.$inferSelect
}
```

Konsumenci piszą wtedy `Address["select"]`. Bogatsze moduły dodają elementy pochodne — `ProductCategory["adminListItem"]`, czyli wiersz `select` tabeli z wyliczanymi `parentTitles` i `productCount`, oraz `ProductCategory["formValues"]`, wywnioskowane ze schematu Zod, to właśnie to, czym posługują się tabela i formularz w panelu.

## 6. Dodaj akcesory, jeśli niosą zachowanie

`{feature}.accessors.ts` jest dla pracy z bazą, której potrzebuje więcej niż jedno miejsce, albo która jest zbyt złożona, żeby siedzieć wewnątrz handlera. `src/modules/address/address.accessors.ts` jest dobrym przykładem: `setDefaultUserAddress` musi wyczyścić poprzedni adres domyślny przed ustawieniem nowego, a `updateUserAddress` musi zawęzić zarówno odczyt, jak i zapis do `userId`:

```ts
export const setDefaultUserAddress = async (userId: string, addressId: string): Promise<boolean> => {
  const existing = await db
    .select()
    .from(address)
    .where(and(eq(address.id, addressId), eq(address.userId, userId)))
    .limit(1)
  if (existing[0] === undefined) {
    return false
  }
  await clearDefaultAddressesForUser(userId)
  await db
    .update(address)
    .set({ isDefault: true })
    .where(and(eq(address.id, addressId), eq(address.userId, userId)))
  return true
}
```

Akcesory zwracają wartości domenowe — wiersz, `undefined`, wartość logiczną — i nie rzucają `AppError`. Zamiana `false` na `NOT_FOUND` to zadanie przypadku użycia. Jednoinstrukcyjny odczyt potrzebny tylko jednemu przypadkowi użycia nie zasługuje na akcesor — zostaw go w handlerze.

## 7. Napisz przypadki użycia

Jedna operacja na plik w `use-cases/`, nazwana `{verb-noun}.ts`: `create-user-address.ts`, `list-user-addresses.ts`, `set-default-user-address.ts`. Każda z nich to funkcja serwerowa, którą może wywołać przeglądarka. Pełny przepis znajdziesz w [Dodawaniu przypadku użycia](/docs/guides/add-a-use-case).

Operacja, którą wywołuje wyłącznie inny kod serwerowy — webhook, konsument kolejki, codzienne sprzątanie danych albo inny przypadek użycia — nie jest funkcją serwerową. Trafia do `use-cases/{verb-noun}.server.ts` i eksportuje zwykłą funkcję async bez middleware i bez opcji zapytania, więc nigdy nie staje się punktem końcowym RPC. `src/modules/session/use-cases/delete-expired-sessions.server.ts`, wywoływany przez sprzątanie w `src/lib/retention.ts`, pokazuje cały wzorzec:

```ts
export const deleteExpiredSessions = async ({ expiredBefore, limit }: DeleteExpiredSessionsInput): Promise<number> => {
  const expired = db.select({ id: session.id }).from(session).where(lt(session.expiresAt, expiredBefore)).limit(limit)
  const deleted = await db.delete(session).where(inArray(session.id, expired)).returning({ id: session.id })

  return deleted.length
}
```

E-maile wysyłane przez poszczególne moduły to pliki tego samego rodzaju, na przykład `src/modules/order/use-cases/send-order-shipped-email.server.ts`. Takich plików jest dziś 33.

## 8. Wygeneruj migrację

Kiedy tabela jest już w `drizzle.schemas.ts`:

```sh
bun run db:generate
```

To zapisze nowy plik SQL w `src/integrations/drizzle-orm/migrations/` oraz snapshot w `migrations/meta/`. Przeczytaj wygenerowany SQL przed zastosowaniem — SQLite nie potrafi zmienić większości definicji kolumn w miejscu, a D1 ma własne ograniczenia. [Migracje bazy danych](/docs/guides/database-migrations) opisują ich stosowanie i pisanie ręczne.

## 9. Przetestuj

Dodaj `__test__/{feature}.schema.test.ts` i `__test__/{feature}.zod.test.ts` dla powierzchni modułu oraz `use-cases/__test__/` dla operacji. `src/modules/address/use-cases/__test__/address-use-cases.test.ts` pokrywa wszystkie pięć operacji adresowych w jednym pliku, co jest konwencją dla małych modułów. Testy wykonujące prawdziwy SQL mają nazwy `*.integration.test.ts` i działają w projekcie Vitest `integration`: `src/modules/address/__test__/address.accessors.integration.test.ts` mockuje `drizzle.database` bazą `node:sqlite` w pamięci, opakowaną przez `createTestD1Database` z `src/platform/testing/mocks/d1.ts`, i uruchamia na niej prawdziwe akcesory. [Pisanie testów](/docs/guides/writing-tests) wyjaśnia trzy projekty Vitest i funkcje pomocnicze do mockowania.
