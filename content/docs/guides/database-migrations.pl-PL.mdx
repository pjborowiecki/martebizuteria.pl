Bazą danych jest Cloudflare D1 (SQLite). Schemat jest zdefiniowany w TypeScripcie w 39 plikach schematów modułów, ponownie eksportowanych z `src/integrations/drizzle-orm/drizzle.schemas.ts` z wyjątkiem tabeli FTS5 `storefront_search`, i stosowany jako zwykłe pliki SQL w `src/integrations/drizzle-orm/migrations/`.

Ten katalog dzielą dwa narzędzia, a wiedza, które co robi, oszczędza wiele nieporozumień:

- **drizzle-kit** _generuje_ migracje, porównując Twój schemat TypeScript z ostatnim snapshotem w `migrations/meta/`.
- **Wrangler** _stosuje_ je, w kolejności nazw plików, zapisując stan w tabeli `d1_migrations` w D1. Nigdy nie czyta dziennika drizzle.

## Środowiska

Istnieją dwie zdalne bazy danych i jedna lokalna baza testowa oraz cztery środowiska Wranglera, które na nie wskazują:

| Środowisko    | Nazwa bazy D1                                       | Używane przez                                                            |
| ------------- | --------------------------------------------------- | ------------------------------------------------------------------------ |
| `development` | `martebizuteria-preview` (zdalna)                   | `bun run dev` (z `remoteBindings: true`)                                 |
| `preview`     | `martebizuteria-preview` (zdalna)                   | `bun run build:preview`, `bun run deploy:preview`                        |
| `test`        | `martebizuteria-test` (lokalna, w `.wrangler/test`) | `bun run db:reset:test`, `bun run build:test`, `bun run start:test`, E2E |
| `production`  | `martebizuteria` (zdalna)                           | `bun run deploy:production`                                              |

**`development` i `preview` to ta sama baza.** Praca lokalna działa na zdalnej instancji preview D1 — binding `development` ma `remote: true`, a `vite.config.ts` ustawia `remoteBindings: process.env["CLOUDFLARE_ENV"] === "development"`, więc `bun run dev` nie ma lokalnego pliku SQLite do zabawy. Wszystko, co zapiszesz podczas pracy, jest widoczne dla wdrożenia preview, a wszystko, co usuniesz, jest usunięte naprawdę. `bun run db:migrate:local` buduje wprawdzie lokalną kopię w `.wrangler/state`, ale `bun run dev` czyta zdalną bazę, nie tę kopię.

**`test` to baza, którą można wyrzucić.** Jej binding ma `remote: false`, a jej skrypty trzymają ją w `.wrangler/test`: `db:migrate:test` nakłada tam migracje, a `db:reset:test` usuwa ten katalog, nakłada całą historię na pustą bazę i wypełnia ją danymi (zobacz [Dane startowe](/docs/guides/seeding-data#lokalna-baza-testowa)). `build:test` i `start:test` budują testowego Workera i serwują go pod `127.0.0.1:3000` na tej bazie. Serwer WWW Playwrighta uruchamia wszystkie trzy przed lokalnym przebiegiem E2E; w CI dwa pierwsze uruchamiają jako kroki workflowy E2E. Środowisko `test` nigdy nie jest wdrażane.

## Generowanie migracji

Po zmianie pliku schematu i wyeksportowaniu go z `drizzle.schemas.ts`:

```sh
bun run db:generate
```

To uruchamia `drizzle-kit generate` z `src/integrations/drizzle-orm/drizzle.config.ts`, skonfigurowanym tak:

```ts
const accountId = process.env["CLOUDFLARE_ACCOUNT_ID"]
const databaseId = process.env["CLOUDFLARE_DATABASE_ID"]
const token = process.env["CLOUDFLARE_ACCESS_TOKEN"]

export default defineConfig({
  ...(accountId === undefined || databaseId === undefined || token === undefined
    ? {}
    : { dbCredentials: { accountId, databaseId, token } }),
  dialect: "sqlite",
  driver: "d1-http",
  migrations: {
    prefix: "timestamp",
    schema: "public",
    table: "__drizzle_migrations__",
  },
  out: "./src/integrations/drizzle-orm/migrations",
  schema: "./src/integrations/drizzle-orm/drizzle.schemas.ts",
  strict: true,
  verbose: true,
})
```

`db:generate` porównuje tylko pliki, więc działa bez tych danych uwierzytelniających; potrzebują ich komendy z sekcji [Podgląd schematu wdrożonej bazy](#podgląd-schematu-wdrożonej-bazy).

`prefix: "timestamp"` jest przyczyną nazw w postaci `20260612120000_product_variants_enhanced.sql`. Znacznik czasu wyznacza kolejność stosowania, więc nigdy nie zmieniaj nazwy migracji, która została gdziekolwiek zastosowana (zobacz [Historia musi zbudować pustą bazę](#historia-musi-zbudować-pustą-bazę)).

**Przeczytaj wygenerowany SQL przed zastosowaniem.** Zwróć szczególną uwagę na przebudowę tabeli: SQLite nie potrafi zmienić typu kolumny ani dodać kolumny `NOT NULL` bez wartości domyślnej, więc drizzle-kit generuje sekwencję utwórz-skopiuj-usuń-zmień nazwę. Na tabeli z prawdziwymi wierszami to migracja danych, nie schematu, i wymaga przemyślenia kluczy obcych oraz indeksów.

## Stosowanie migracji

```sh
bun run db:migrate:local         # wrangler d1 migrations apply DB --env development --local
bun run db:migrate:development   # --env development --remote
bun run db:migrate:preview       # --env preview --remote   (bun run db:migrate to jego alias)
bun run db:migrate:production    # --env production --remote
bun run db:migrate:test          # --env test --local --persist-to .wrangler/test
```

Najpierw sprawdź, co czeka i co jest już zastosowane:

```sh
bun run db:migrations:preview
bun run db:migrations:production
```

Skrypty wdrożeniowe same nakładają oczekujące migracje, tuż przed `wrangler deploy`: wdrożenie podglądu z pull requesta nakłada je na wspólną bazę preview, a wdrożenie produkcyjne po scaleniu na produkcję. Normalna kolejność jest więc taka: wygeneruj, przeczytaj, otwórz pull request, przetestuj aplikację na preview, scal. Powyższe komendy zostają do ręcznego nakładania migracji.

W czasie migracji, a także tak długo, jak wydanie pozostaje wycofane, sklep obsługuje poprzedni Worker na nowym schemacie. Migracja nie może więc usuwać, zmieniać nazw ani zaostrzać niczego, co ten Worker wciąż czyta; taką zmianę wydaje się w krokach rozszerz, wdróż, zawęź, opisanych w [Wycofaniu wdrożenia](/docs/guides/roll-back-a-deploy).

## Migracje pisane ręcznie

Wiele ze 105 migracji w katalogu napisano ręcznie, a nie wygenerowano, i ich nazwy mówią, co robią, zamiast nieść kryptonim nadany przez drizzle: `20260604120000_catalog_indexes_and_integrity.sql`, `20260924120000_checkout_idempotency_constraints.sql`, `20260925000000_locale_maps_bcp47.sql`, `20261016140000_claim_past_guest_orders.sql` i inne. Tak nazwana jest każda migracja dodana od końca września. Pisanie ręczne jest właściwym wyborem dla:

- **Zmian nazw.** drizzle-kit widzi zmianę nazwy jako usunięcie plus dodanie, co niszczy dane. Koniec `20260604232955_curved_wallow.sql` zmienia nazwę tabeli, a potem dopasowuje do niej nazwy jej indeksów:

```sql
ALTER TABLE `attribute` RENAME TO `product_attribute`;
DROP INDEX IF EXISTS `attribute_handle_unique`;
DROP INDEX IF EXISTS `attribute_rank_idx`;
CREATE UNIQUE INDEX IF NOT EXISTS `product_attribute_handle_unique` ON `product_attribute` (`handle`);
CREATE INDEX IF NOT EXISTS `product_attribute_rank_idx` ON `product_attribute` (`rank`);
```

- **Zmian indeksów.** `20261015100000_newsletter_subscriber_status_index.sql` zastępuje indeks szerszym:

```sql
DROP INDEX IF EXISTS `newsletter_subscriber_status_idx`;
--> statement-breakpoint
CREATE INDEX IF NOT EXISTS `newsletter_subscriber_status_createdAt_idx` ON `newsletter_subscriber` (`status`,`created_at`);
```

- **Napraw danych.** `20260927120000_fix_silver_collection_handle.sql` poprawia jedną literówkę w jednym wierszu:

```sql
UPDATE product_collection
SET handle = 'srebro-925',
    titles = json_set(titles, '$."pl-PL"', 'Srebro 925'),
    updated_at = unixepoch() * 1000
WHERE handle = 'serbro-925';
```

- **Uzupełnień danych.** Nowa kolumna zwykle potrzebuje wartości dla wierszy, które już istnieją. `20261015150000_order_shipped_email.sql` dodaje dwie kolumny i wypełnia je dla zamówień już wysłanych:

```sql
ALTER TABLE `order` ADD `shipped_email_at` integer;
--> statement-breakpoint
ALTER TABLE `order` ADD `tracking_email_number` text;
--> statement-breakpoint
UPDATE `order` SET `shipped_email_at` = coalesce(`shipped_at`, `delivered_at`, `updated_at`), `tracking_email_number` = `tracking_number` WHERE `fulfillment_status` IN ('shipped', 'delivered');
```

Nawyki z nowszych plików warte skopiowania:

- **Bez komentarzy.** Nazwa pliku mówi, co migracja robi, a commit, który ją dodaje, mówi dlaczego. Dwanaście starszych plików, z których ostatni to `20261001090000_newsletter_subscribers.sql`, wciąż ma komentarze `--`; żadna z 38 migracji po nim ich nie ma. Linie `--> statement-breakpoint` to separator, a nie komentarz do treści: drizzle-kit wpisuje je między instrukcje, SQLite pomija je jako komentarze, a pomocnicze funkcje testów dzielą po nich plik.
- **`IF EXISTS` i `IF NOT EXISTS` wszędzie, gdzie SQLite na to pozwala** — przy `CREATE TABLE`, `CREATE INDEX`, `CREATE TRIGGER` i instrukcjach `DROP` — żeby ponowne uruchomienie migracji na częściowo zmigrowanej bazie nie zawiodło. Dla `ALTER TABLE … ADD` SQLite takiego zabezpieczenia nie ma.
- **Migracje danych, które przy ponownym uruchomieniu niczego nie zmieniają.** Zawęź `WHERE` do wierszy, które wciąż wymagają zmiany: `20261016140000_claim_past_guest_orders.sql` dotyka tylko zamówień, których `user_id` jest wciąż `NULL`, więc drugie uruchomienie nie ma nic do zrobienia.

Żeby napisać migrację ręcznie, utwórz `src/integrations/drizzle-orm/migrations/<RRRRMMDDGGMMSS>_<opis>.sql` ze znacznikiem czasu późniejszym niż w każdym istniejącym pliku. Wrangler podnosi ją po nazwie pliku; dla Wranglera nie ma nic do rejestrowania. Migracja danych dostaje też wpis w mapie `MIGRATION` pomocniczych funkcji testów i własny test (zobacz [Testowanie migracji danych](#testowanie-migracji-danych)).

### Historia musi zbudować pustą bazę

Wrangler nakłada pliki w kolejności nazw na bazę, która nie ma żadnego z nich: lokalną bazę testową przy każdym `bun run db:reset:test` albo bazę nowego środowiska. Wdrożone bazy nie pokażą, czy to działa, bo każdy plik nałożyły raz, w kolejności, w jakiej pliki powstawały. Te dwie kolejności kiedyś się rozjechały: trzy ręcznie napisane migracje katalogu zostały nałożone na preview i produkcję przed wygenerowanymi `20260604232955_curved_wallow.sql` i `20260606084825_fuzzy_miek.sql`, które już zakładały ich zmiany. W kolejności nazw `curved_wallow` idzie przed wszystkimi trzema, więc pusta baza zatrzymywała się na nim z błędem `no such table: product_attribute`. Commit 5801445b przeniósł ręcznie napisane instrukcje do plików, w których kolejność nazw po raz pierwszy ich potrzebuje, a trzy pierwotne pliki zostawił puste, żeby ich nazwy pozostały zapisane:

- `20260605120000_attribute_titles_and_allowed_values.sql`
- `20260606120000_rename_attribute_to_product_attribute.sql`
- `20260608120000_product_locale_maps.sql`

Wynikają z tego dwie zasady:

- Nadaj nowej migracji znacznik czasu późniejszy niż w każdym istniejącym pliku i nigdy nie zmieniaj nazwy ani nie usuwaj migracji już nałożonej. Wrangler zapisuje migracje po nazwie w `d1_migrations`, więc plik o zmienionej nazwie jest nową migracją i wykona się ponownie.
- Edycja nałożonej migracji nigdzie nie uruchamia jej ponownie; zmienia tylko to, co dostanie nowa baza. Tak naprawia się zepsutą historię i dlatego taka edycja wymaga `bun run db:reset:test`, żeby ponownie dowieść, że historia działa.

### Uwaga o dzienniku drizzle

`migrations/meta/_journal.json` wymienia obecnie 52 znaczniki, podczas gdy w katalogu jest 105 plików `.sql`, w tym trzy puste pliki opisane wyżej, a w `meta/` 37 snapshotów. Do dziennika nigdy nie dopisano 53 plików, w tym wszystkich migracji po `20260930151544_collection_short_descriptions.sql`, a kilka generowanych nie ma snapshotu. Wranglerowi to nie przeszkadza — trzyma własny stan w D1. Ale **drizzle-kit to obchodzi**: `bun run db:generate` porównuje z najnowszym snapshotem, `meta/20260930151544_snapshot.json`, który jest starszy niż 47 migracji po nim, więc może wygenerować SQL dla zmian już zastosowanych.

Przed zaufaniem wygenerowanej migracji albo porównaj ją z aktualnym schematem wdrożonej bazy przez `bun run db:introspect:preview` (co zapisuje `schema.ts` i `relations.ts` do katalogu migracji), albo przeczytaj ją linia po linii. Zarówno `schema.ts`, jak i `relations.ts` w `src/integrations/drizzle-orm/migrations/` są wynikiem introspekcji, a nie kodem utrzymywanym ręcznie.

## Podgląd schematu wdrożonej bazy

```sh
bun run db:introspect:development   # albo :preview, :production
bun run db:pull                     # alias dla :development
bun run db:pull:production
bun run db:studio                   # Drizzle Studio na środowisku development
```

Te komendy czytają dane uwierzytelniające z `.env.<environment>` przez `bun --env-file` i potrzebują `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID` oraz `CLOUDFLARE_ACCESS_TOKEN` — sterownik `d1-http` rozmawia z API Cloudflare, a nie z bindingiem.

## `db:push` — do czego służy

```sh
bun run db:push:development
```

`drizzle-kit push` stosuje schemat TypeScript wprost do bazy, bez zapisania pliku migracji. Jest przydatny do jednorazowego eksperymentu, a w pozostałych przypadkach niebezpieczny: nie pozostawia zapisu, więc następne środowisko nie dostanie zmiany, a na wspólnej bazie preview może usunąć kolumnę, na której wciąż opiera się produkcja. Wybieraj `db:generate` plus `db:migrate`.

## Jak pisać schemat, który dobrze się migruje

- Nadaj każdej kolumnie długość: `text("handle", { length: 255 })`. Długości pochodzą ze stałej `*_COLUMN_LENGTH` modułu, więc schemat Zod i kolumna się zgadzają.
- Dodawaj znaczniki czasu przez `...timestamps()`, żeby `created_at` i `updated_at` były zawsze `integer(..., { mode: "timestamp_ms" })` z wartością domyślną `(unixepoch() * 1000)`.
- Dodawaj nową kolumnę jako dopuszczającą `NULL` albo z wartością domyślną. Kolumna `NOT NULL` bez domyślnej wymusza przebudowę tabeli.
- Nazywaj indeksy `<table>_<column>_idx`, a unikalne `<table>_<column>_unique`. Większość schematów zapisuje część z kolumną jako nazwę jej właściwości w TypeScripcie, więc nazwy wyglądają jak `order_userId_status_idx` czy `inventory_variantId_unique`. Kilka migracji istnieje wyłącznie po to, żeby naprawić nazwy indeksów, które tego nie przestrzegały.
- Deklaruj `.references(..., { onDelete: "cascade" })`, żeby usunięcia porządkowały dane. SQLite wymusza klucze obce tylko przy włączonej pragmie — w D1 jest włączona — więc brak kaskady objawia się osieroconymi wierszami, a nie błędem.
- Przechowuj tłumaczony tekst jako mapę JSON kluczowaną znacznikiem lokalizacji BCP 47 (`json_object('pl-PL', …, 'en-US', …)`): `titles`, `subtitles` i `descriptions` na produktach; `titles`, `subtitles`, `short_descriptions` i `descriptions` na kategoriach; `titles`, `short_descriptions` i `descriptions` na kolekcjach. `20260925000000_locale_maps_bcp47.sql` zmigrowało te klucze z samych kodów języka na pełne znaczniki.
- Przechowuj pieniądze jako całkowite jednostki podrzędne. Metody dostawy mają `price` równe `1499`, co oznacza 14,99 zł.

## Testowanie migracji danych

Migracja, która zmienia albo wstawia wiersze, dostaje test integracyjny, bo nic innego nie sprawdza, co robi z istniejącymi danymi. Pomocnicze funkcje są w `src/platform/testing/mocks/migrations.ts`:

- `MIGRATION` nazywa każdy plik migracji, który test nakłada osobno. Dodaj wpis dla swojej, tak jak razem z tamtą migracją dodano `CLAIM_PAST_GUEST_ORDERS: "20261016140000_claim_past_guest_orders"`.
- `applyMigration(sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)` czyta plik przez `import.meta.glob`, dzieli go po `--> statement-breakpoint` i wykonuje każdą część na `DatabaseSync` z `node:sqlite`.
- `applyMigrationHistory(sqlite)` wykonuje każdy plik migracji w kolejności nazw, tej samej, której używa Wrangler, co buduje pełny schemat.

Wzorcem jest `src/modules/order/__test__/order.past-guest-claim-backfill.integration.test.ts`, dodany w tym samym commicie co `20261016140000_claim_past_guest_orders.sql`. Tworzy tylko tabele i kolumny, które migracja czyta i zapisuje, wstawia po jednym wierszu na każdy przypadek, nakłada migrację i porównuje wynik:

```ts
beforeEach(() => {
  database.sqlite = new DatabaseSync(":memory:", { enableDoubleQuotedStringLiterals: true })
  database.sqlite.exec(`
    create table user (id text primary key, email text not null unique, email_verified integer not null, created_at integer not null);
    create table "order" (id text primary key, email text not null, user_id text, updated_at integer not null);
    …
  `)
})

it("claims nothing more when it runs again", () => {
  applyMigration(database.sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)
  const ordersAfterFirstRun = readOrders()

  applyMigration(database.sqlite, MIGRATION.CLAIM_PAST_GUEST_ORDERS)

  expect(readOrders()).toStrictEqual(ordersAfterFirstRun)
  expect(readClaims()).toHaveLength(2)
})
```

Pozostałe przypadki obejmują to, co migracja ma zmienić (zamówienia gości, których e-mail, bez względu na wielkość liter, należy do zweryfikowanego konta, oraz starsze konto, gdy dwa mają ten sam adres), to, czego ma nie ruszać (konta niezweryfikowane, zamówienia już przypisane do konta, adresy bez konta), i wpisy audytu, które zapisuje. Dla swojej migracji pokryj te same trzy rzeczy oraz drugie uruchomienie.

Gdy migracja zależy od prawdziwego schematu albo od wierszy z danych startowych, zbuduj schemat przez `applyMigrationHistory`, jak robi to `src/modules/delivery-method/__test__/delivery-method.descriptions-migration.integration.test.ts`. Historia zawiera już testowaną migrację, więc ten test przywraca wiersze, które migracja czyta, i dopiero wtedy nakłada ją ponownie przez `applyMigration`. Wszystkie 61 zestawów, które wywołują `applyMigrationHistory`, otwiera `DatabaseSync` z `enableDoubleQuotedStringLiterals: true`; zrób tak samo.

Umieść test w katalogu `__test__/` modułu, którego tabelę zmienia migracja, i nazwij go `*.integration.test.ts`, żeby trafił do projektu `integration` (`bun run test:integration` oraz `bun run test`).

## Lista kontrolna migracji

- [ ] Tabela jest wyeksportowana z `drizzle.schemas.ts`.
- [ ] `bun run db:generate` się wykonało, a każda linia jego wyniku została przeczytana.
- [ ] Nic w nim nie przebudowuje przypadkiem wypełnionej tabeli.
- [ ] Nazwy indeksów i ograniczeń zgadzają się z konwencją.
- [ ] Znacznik czasu pliku jest późniejszy niż w każdej istniejącej migracji, a żadnej nałożonej migracji nie zmieniono nazwy ani jej nie usunięto.
- [ ] Migracja danych ma test integracyjny, który nakłada ją przez `applyMigration` i sprawdza, co zmienia, czego nie rusza i że drugie uruchomienie niczego nie zmienia.
- [ ] Cała historia wciąż buduje pustą bazę: `bun run db:reset:test` nakłada każdą migrację w kolejności nazw na świeżą lokalną bazę, tak jak robi to zadanie E2E przy każdym pull requeście.
- [ ] Wdrożenie podglądu z pull requesta ją nałożyło, a `bun run db:migrations:preview` to potwierdza.
- [ ] Aplikacja została przetestowana na preview przed produkcją.
- [ ] Tylko dodaje to, z czym poradzi sobie Worker wdrożony przed nią, i nie usuwa ani nie zmienia nazwy niczego, co ten Worker wciąż czyta.
- [ ] `bun run check` i `bun run test` przechodzą. `vite.config.ts` wyłącza katalog migracji z lintu, formatowania i wyszukiwania testów, więc SQL jest sprawdzany tylko tam, gdzie się go nakłada: w zestawach integracyjnych opartych na `applyMigrationHistory`, we własnym teście migracji i w `db:reset:test`.
