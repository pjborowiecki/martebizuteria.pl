Sklep pilnuje się na trzy sposoby i żaden z nich nie wymaga konta w usłudze raportowania błędów. Cloudflare przechowuje logi Workera i grupuje jego błędy, `/api/health` mówi monitorowi dostępności, czy Worker sięga do swoich magazynów danych, a Worker wysyła e-mail na `RESEND_EMAIL_FROM`, gdy błąd wymaga uwagi właściciela.

## Workers Logs i Issues

Najwyższy poziom `wrangler.jsonc` włącza oba, a każde środowisko go dziedziczy, więc mają je wdrożenia preview i produkcyjne:

```jsonc
"observability": {
  "enabled": true,
  "issues": {
    "enabled": true,
  },
},
```

`enabled` zachowuje w Workers Logs logi każdego wywołania, w tym każde `console.error`. `issues.enabled` włącza Workers Issues, które zapisuje nieprzechwycony wyjątek, nieudane wywołanie, odpowiedź `5xx` albo zalogowany błąd jako wystąpienie i grupuje wystąpienia jednego błędu w jedno zgłoszenie. Issues wymaga Wranglera 4.134.0 lub nowszego; repozytorium używa 4.149.0. Cloudflare opisuje Issues jako otwartą betę, darmową do jej końca. Oba widać w panelu Cloudflare pod **Workers & Pages**, Worker (`martebizuteria` dla produkcji, `martebizuteria-preview` dla preview), **Observability**. Plik `dist/server/wrangler.json` z buildu pokazuje blok `observability`, który wysyła wdrożenie.

Linie logu związane z tą stroną:

| Prefiks                                                                | Źródło                                                                                                                                                |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[Health] D1 did not answer:` (albo `KV`, `R2`)                        | `/api/health` przechwyciło błąd tego bindingu                                                                                                         |
| `[Alert] The <kind> alert to <address> was not sent: …`                | Resend odrzucił alert o incydencie albo nie odpowiedział na czas                                                                                      |
| `[Alert] The <kind> alert could not be sent:`                          | Odczyt KV albo renderowanie alertu rzuciło wyjątek; błąd jest dalej w linii                                                                           |
| `[Stripe] Signature verification failed`                               | Zdarzenie nie przeszło weryfikacji z `STRIPE_WEBHOOK_SECRET`; trasa odpowiedziała 400 i nie wysłała alertu                                            |
| `[Stripe] Ignoring <mode> event <id> (<type>): …`                      | Do tego środowiska trafiło zdarzenie z drugiego trybu Stripe; trasa je potwierdziła i nic nie zrobiła                                                 |
| `[Stripe] Domain logic failed for <type>:`                             | Handler webhooka rzucił wyjątek, trasa odpowiedziała 500, a Stripe ponowi zdarzenie                                                                   |
| `Paid Checkout Session <id> created no order:`                         | `handleFulfillCheckoutSession` nie mógł utworzyć zamówienia dla opłaconej sesji                                                                       |
| `Paid Checkout Session <id> created no order from its return page:`    | Strona powrotu nie mogła utworzyć zamówienia dla opłaconej sesji; jeśli webhook też zawiedzie, to on zapisuje błąd i wysyła alert                     |
| `Refund <id> did not reach the customer; the shop was alerted: …`      | `handleRefundUndone` cofnął nieudany albo anulowany zwrot i wysłał alert `refundFailed`                                                               |
| `<label> failed for order <id>: …`                                     | Pierwsza próba wysłania e-maila dotyczącego zamówienia zawiodła i zostanie ponowiona albo zawiodło ostatnie ponowienie i następuje `orderEmailFailed` |
| `<label> for order <id> could not be prepared:`                        | Przygotowanie e-maila dotyczącego zamówienia rzuciło wyjątek, zanim dotarł do Resend; liczy się to jako nieudana próba                                |
| `[AuditLog Queue] Batch insert failed:`                                | `processAuditLogQueueBatch` nie zapisał partii i poprosił kolejkę o jej ponowienie                                                                    |
| `[Newsletter] Campaign <id> will retry its batch after attempt <n>: …` | Partia newslettera zawiodła, a kolejka ponowi ją minutę później                                                                                       |
| `[Newsletter] Campaign <id> stopped after <n> attempts: …`             | Trzecia próba zawiodła; kampania zostaje oznaczona jako nieudana i następuje `newsletterFailed`                                                       |
| `[Retention] <kind> could not be cleared:`                             | Czyszczenie danych zawiodło dla jednego rodzaju wierszy; uruchomienie też zawodzi                                                                     |

`vp exec wrangler tail --env production` pokazuje te same linie na żywo; zobacz [Debugowanie lokalne](/docs/guides/local-debugging#obserwowanie-workera-we-wdrożonym-środowisku).

## Sprawdzenie stanu

`GET /api/health` to handler TanStack Start w `src/routes/api/health.ts`. Odczytuje każdy binding magazynu raz, wszystkie trzy równolegle, operacjami, które nie dotykają danych:

```ts
const [d1, kv, r2] = await Promise.all([
  probe("D1", () => env.DB.prepare("SELECT 1").first()),
  probe("KV", () => env.CACHE.get(PROBE_KEY)),
  probe("R2", () => env.IMAGES.head(PROBE_KEY)),
])
```

`PROBE_KEY` to `health-check`, klucz i obiekt, które nie istnieją, więc KV odpowiada `null`, R2 odpowiada `null` i to jest wynik pozytywny. Sprawdzenie zawodzi tylko przy rzuconym błędzie. Odpowiedź to `200`, gdy przechodzą wszystkie trzy, i `503`, gdy zawiedzie którekolwiek:

```json
{ "checks": { "d1": "ok", "kv": "ok", "r2": "ok" }, "status": "ok" }
```

```json
{ "checks": { "d1": "error", "kv": "ok", "r2": "ok" }, "status": "error" }
```

Treść nigdy nie zawiera błędu, nazwy bindingu ani żadnej konfiguracji; błąd trafia do logu jako `[Health] D1 did not answer:`. Odpowiedź ma nagłówek `Cache-Control: no-store`, więc ani Cloudflare, ani proxy nie poda nieaktualnego `200`. Żądanie `HEAD` dostaje ten sam status, bo TanStack Start odpowiada na `HEAD` handlerem `GET`.

Czego `200` nie mówi: Stripe, Resend, Durable Object odświeżania na żywo i kolejka audytu nie są sprawdzane, więc oznacza ono, że Worker działa i sięga do bazy danych, cache'u i zdjęć, a nie, że zamówienie by się udało. Endpoint nie ma limitu żądań i nie wymaga logowania. Każde wywołanie kosztuje jedno zapytanie D1, które nie czyta żadnych wierszy, jeden odczyt KV i jedną operację R2 klasy B, czyli około 43 200 każdej z nich miesięcznie przy sprawdzaniu co minutę.

Pyta go też każde wdrożenie: ostatni krok wdrożenia, `scripts/verify-deployment.ts`, kończy się błędem, chyba że `/api/health` nowego Workera na jego hoście `workers.dev` odpowie `200`, obok strony głównej, listy produktów, `robots.txt` i trasy webhooka Stripe. Nowa wersja działa już wtedy na żywo, więc `503` w tym miejscu oznacza wycofanie; zobacz [Wycofanie wdrożenia](/docs/guides/roll-back-a-deploy).

## Podłączenie monitora dostępności

Każdy monitor dostępności HTTP zadziała z takimi ustawieniami:

| Ustawienie        | Wartość                                                                                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| URL               | Produkcja: `https://martebizuteria.pjborowiecki.workers.dev/api/health`, dopóki nie zacznie działać pod `https://martebizuteria.pl/api/health`. Preview: `https://preview.martebizuteria.pl/api/health` |
| Metoda            | `GET` (`HEAD` też działa)                                                                                                                                                                               |
| Oczekiwany status | `200`; wszystko inne, także przekroczenie czasu, traktuj jako awarię                                                                                                                                    |
| Słowo kluczowe    | `"status":"ok"`, jeśli monitor potrafi sprawdzić treść                                                                                                                                                  |
| Interwał          | Od jednej do pięciu minut                                                                                                                                                                               |
| Kogo powiadomić   | E-mail właściciela; własny alert monitora obejmuje Workera, który w ogóle nie działa                                                                                                                    |

Produkcja ma w `wrangler.jsonc` `routes: []` i `workers_dev: true`, więc na razie odpowiada tylko pod swoim hostem `workers.dev`, tym, który podaje `WORKERS_DEV_HOSTS` w `src/modules/_core/constants/api.ts`. Gdy zacznie obsługiwać `martebizuteria.pl`, przenieś monitor tam, bo to adres, którego używają klienci; host `workers.dev` też dalej odpowiada.

To monitor zauważa awarię, której Worker sam nie zgłosi: nieudane wdrożenie, zepsutą trasę albo incydent po stronie Cloudflare.

**Cloudflare Health Checks.** Jeśli strefa `martebizuteria.pl` jest na planie Pro lub wyższym, monitorem może być Cloudflare; plan Free nie ma samodzielnych Health Checks. Opisane niżej sprawdzenie odpytuje `martebizuteria.pl`, więc pilnuje produkcji dopiero wtedy, gdy produkcja obsługuje tę domenę. W panelu otwórz strefę, przejdź do **Health Checks**, wybierz **Create** i skieruj sprawdzenie na `martebizuteria.pl` przez HTTPS ze ścieżką `/api/health`, oczekiwanym kodem `200` i `"status":"ok"` jako **Response body**, czyli fragmentem, który musi się pojawić w pierwszych 10 KB odpowiedzi. Zostaw **Interval** na minucie lub dłużej, a **Check regions** nieliczne, bo każdy region wysyła własne żądania. Potem na tej samej stronie wybierz **Configure an alert**, dodaj adres e-mail i to sprawdzenie i wybierz wyzwalacz. Cloudflare wysyła powiadomienie dopiero, gdy status zmieni się w większości wybranych regionów.

**Na planie Free** użyj hostowanego monitora dostępności z ustawieniami powyżej. To jedyna część tej strony, która wymaga konta poza Cloudflare, a nic w kodzie nie zależy od tego, który monitor zostanie wybrany.

## Czasy żądań

Każde wczytanie strony — żądanie `GET`, na które Worker odpowiada HTML-em — ma nagłówek `Server-Timing` z trzema wpisami. Trasy API pod `/api/`, wywołania funkcji serwerowych, przekierowania, `robots.txt` i mapa witryny nie mają go wcale, więc nagłówek nie mówi nic o logowaniu, resecie hasła ani zapisie do newslettera. `src/lib/server-timing.ts` zbiera czasy w magazynie `AsyncLocalStorage`, który `src/server.ts` otwiera dla każdego żądania:

| Wpis     | Co mierzy                                                                                                                                                                                                                    |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `d1`     | Zsumowany czas wszystkich instrukcji i partii D1 wykonanych przy wczytaniu strony, a w `desc` ich liczbę (`statements: 6`). `timeD1Statements` opakowuje binding D1 w `drizzle.database.ts`, więc liczy się też odczyt sesji |
| `render` | `defaultStreamHandler`, od końca loaderów tras do pierwszego bajtu HTML. Dla robota trwa do końca strony, bo TanStack Start, zanim odpowie botowi, czeka na każdą odroczoną obietnicę                                        |
| `total`  | Całe żądanie wewnątrz Workera, od `fetch` do odpowiedzi                                                                                                                                                                      |

Nagłówek nie wymienia żadnej instrukcji ani tabeli. Odczytasz go przez `curl -s -o /dev/null -D - https://preview.martebizuteria.pl/products | grep -i server-timing` albo w narzędziach deweloperskich przeglądarki: **Network**, żądanie dokumentu, **Timing**.

Przy liczbach z wdrożenia trzeba pamiętać o dwóch rzeczach. Zegar wdrożonego Workera przesuwa się tylko wtedy, gdy Worker czeka na wejście-wyjście — to obrona Cloudflare przed atakami czasowymi — więc praca, która zajmuje tylko procesor, jak `render`, pokazuje tam prawie `0`, a `total` liczy samo czekanie; ten sam build uruchomiony na własnym komputerze mierzy też pracę procesora (zobacz [Uruchomienie buildu produkcyjnego lokalnie](/docs/guides/local-debugging#uruchomienie-buildu-produkcyjnego-lokalnie)). Czas sprzed uruchomienia Workera — uzgadnianie TLS, droga do centrum danych i wczytanie Workera przez zimny izolat — jest poza nagłówkiem: porównaj `total` z czasem do pierwszego bajtu zmierzonym przez przeglądarkę.

## Alerty e-mail ze sklepu

`sendIncidentAlert` z `src/lib/incident-alert.server.ts` wysyła e-mail na `RESEND_EMAIL_FROM` w języku sklepu, szablonem `incident-alert.tsx`. Każdy e-mail podaje rodzaj incydentu, jego identyfikator, przyczynę i środowisko:

| Incydent                   | Wysyłany, gdy                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Identyfikator                                                                | Co zrobić                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `paidCheckoutWithoutOrder` | `handleFulfillCheckoutSession` w `stripe.webhooks.ts` dostaje z realizacji `NOT_FOUND` dla opłaconej sesji: nie niesie jej żadna oczekująca płatność albo jej checkout został zwolniony lub zniknął. Webhook odpowiada 200, więc Stripe nie wyśle go ponownie. Sesja, której metadane `deployment` wskazują inne wdrożenie, na przykład lokalny przebieg testów, jest potwierdzana bez tego alertu (zobacz [Płatności](/docs/features/payments#punkt-końcowy-webhooka)).                                                                                                                                                                                                             | Id sesji Checkout                                                            | Znajdź płatność w panelu Stripe po id sesji, a następnie zwróć pieniądze albo ustal zamówienie z klientem. | `stripeWebhookFailed`      | Dowolny handler z `webhookHandlers` rzuca wyjątek, więc `src/routes/api/webhooks.stripe.ts` odpowiada 500, a Stripe ponawia zdarzenie, w trybie live przez maksymalnie trzy dni. Trafia tu też opłacona sesja, z której nie dało się utworzyć zamówienia z innego powodu, razem z `order.fulfillment_failed` w `/admin/audit`.                                                                                                                                                                                                                                                                                                                                                       | Identyfikator zdarzenia Stripe                                               | Przyczyna zaczyna się od typu zdarzenia. Przeczytaj stos w Workers Logs, usuń przyczynę i pozwól, by kolejne ponowienie Stripe albo **Resend** przy zdarzeniu w panelu Stripe dostarczyło je ponownie.                                                                                                                                                             |
| `refundFailed`             | `handleRefundUndone` w `stripe.webhooks.ts` obsługuje `refund.failed` albo `refund.updated` ze zwrotem w statusie `canceled` lub `failed` dla zwrotu jednego z zamówień sklepu. `undoFailedRefund` sprawiło już, że zamówienie liczy tylko obowiązujące zwroty i jest znów otwarte, chyba że zostało anulowane, i zapisało `order.refund_failed`. Klient nie dostaje e-maila o niepowodzeniu; historia zamówienia pokazuje, czy wcześniej dotarła do klienta wiadomość, że zwrot jest w drodze, czego nigdy nie ogłoszono dla zwrotu, który nie powiódł się przed obsłużeniem jego `charge.refunded`. Przyczyna podaje numer zamówienia, kwotę, status i `failure_reason` ze Stripe. | Identyfikator zwrotu w Stripe, `re_…` albo `pyr_…`                           | Stripe oddał pieniądze na saldo sklepu. Znajdź płatność w panelu Stripe i oddaj klientowi pieniądze w inny sposób: gdy przyczyna zniknie, zleć zwrot ponownie tam albo przyciskiem Zwrot w zamówieniu, albo uzgodnij z klientem przelew. Sprawdź stan magazynowy zamówienia, jeśli jego produkty wróciły na stan razem ze zwrotem.                                 |
| `auditQueueFailed`         | `processAuditLogQueueBatch` w `process-audit-log-queue.server.ts` nie może zapisać partii, oznacza każdą wiadomość do ponowienia, a potem wysyła alert. Kolejka ponawia partię trzy razy (`max_retries: 3`), a potem przenosi jej wiadomości do kolejki martwych listów, która ponawia każdą osobno jeszcze trzy razy co pięć minut i wysyła alert pod własną nazwą.                                                                                                                                                                                                                                                                                                                 | Nazwa kolejki                                                                | Sprawdź D1 w panelu Cloudflare. Zatrzymanej kampanii nie da się wznowić; nowa trafi ponownie do wszystkich potwierdzonych subskrybentów.                                                                          |
| `orderEmailFailed`         | `deliverOrderEmail` w `deliver-order-email.server.ts` zapisuje e-mail dotyczący zamówienia jako `email.failed`, gdy Resend odrzucił pierwszą próbę i oba ponowienia: potwierdzenie, powiadomienie sklepu o nowym zamówieniu, e-maile o rozpoczęciu realizacji, wysyłce, numerze przesyłki, doręczeniu, anulowaniu, zwrocie i nieudanej płatności oraz oba e-maile o odstąpieniu od umowy.                                                                                                                                                                                                                                                                                            | Klucz idempotencji e-maila, na przykład `order-confirmation/<id zamówienia>` | Sprawdź stan Resend, limit wysyłki i domenę nadawcy. Potem naciśnij **Wyślij ponownie** w sekcji „Aktywność” zamówienia, co wysyła pod tym samym kluczem; ponownie da się tam wysłać każdy e-mail dotyczący zamówienia poza e-mailem o nieudanej płatności i dwoma e-mailami o odstąpieniu, więc w ich przypadku napisz do klienta.                                |

**Najwyżej raz na incydent.** Incydent to jego środowisko, rodzaj i identyfikator. Pierwszy błąd zapisuje `incident-alert:<APP_ENV>:<kind>:<reference>` w przestrzeni KV `CACHE` z godzinnym wygaśnięciem (`INCIDENT_ALERT_SECONDS`) i dopiero potem wysyła e-mail; incydent `stripeWebhookFailed` jest trzymany przez trzy dni (`STRIPE_EVENT_RETRY_SECONDS`), czyli tak długo, jak Stripe w trybie live ponawia zdarzenie. Incydent `refundFailed` ma klucz zwrotu, więc `refund.failed` i `refund.updated` dla jednego zwrotu wysyłają jeden e-mail. Kolejne błędy pod tym samym kluczem, dopóki jest trzymany, trafiają do logu, ale nie do skrzynki, więc wszystkie ponowienia jednego zdarzenia przez Stripe, także opłaconej sesji, z której nie dało się utworzyć zamówienia, wysyłają jeden e-mail, a ponowienia jednej partii przez kolejkę jeden. Nowa sesja Checkout, inne zdarzenie albo błąd po wygaśnięciu incydentu to nowy incydent. KV jest spójne ostatecznie między lokalizacjami Cloudflare, więc dwa błędy, które w tej samej chwili trafią do różnych lokalizacji, mogą wysłać po jednym e-mailu.

**Alert nigdy nie psuje pracy, która go wywołała.** `sendIncidentAlert` przechwytuje wszystko: błąd KV, błąd renderowania i odrzuconą wysyłkę loguje z prefiksem `[Alert]` i połyka. Trasa webhooka przekazuje alert do `scheduleBackgroundWork`, więc Stripe od razu dostaje swoje 500, a realizacja robi to samo, zanim odpowie 200. Konsument kolejki czeka na alert dopiero wtedy, gdy każda wiadomość jest już oznaczona do ponowienia. Alerty nie są zapisywane w dzienniku zdarzeń, bo zawieść mogła właśnie baza danych.

**Dokąd trafiają alerty.** Alerty trafiają na `RESEND_EMAIL_FROM`, adres, z którego sklep wysyła pocztę, w każdym środowisku, więc development i preview też je wysyłają. W środowisku `test` to `noreply@example.test` z `.env.test`, atrapowa skrzynka przechwytywana przez zamockowany Resend. Alerty idą przez Resend z tego samego adresu, więc zepsuty nadawca zatrzymuje także je; monitor dostępności i własne powiadomienia Cloudflare od niego nie zależą.

## Powiadomienia Cloudflare

Powiadomienia ustawia się dla konta w panelu Cloudflare pod **Notifications**, **Add**. Każdy plan może je dostarczać e-mailem albo webhookiem. Warte dodania dla tego sklepu:

- **Health Checks status**, jeśli strefa ma opisane wyżej sprawdzenie. Utworzenie go przez **Configure an alert** na stronie Health Checks dodaje je tutaj.
- **Custom Alerts** (beta), które wykonują zapytanie SQL API według harmonogramu i powiadamiają, gdy wynik przekroczy próg. Zapytanie liczące odpowiedzi `5xx` z ostatnich pięciu minut z alertem powyżej zera wyłapie błędy, które padają, zanim kod zdąży wysłać e-mail, na przykład zepsute wdrożenie. Przykład Cloudflare czyta `events.httpRequests` z filtrem na identyfikator konta i `edgeResponseStatus >= 500`; to, które zbiory danych Custom Alert może czytać, zależy od planu, a panel wymienia dostępne.
- **Automatyzacje Workers Issues**, ustawiane w panelu Issues, które wysyłają nowe zgłoszenie na webhook, do komunikatora albo narzędzia do obsługi incydentów.

Zostaw co najmniej jeden z alertów po stronie Cloudflare albo monitor dostępności. Własne e-maile sklepu obejmują sześć opisanych wyżej rodzajów błędów, czyli unię `IncidentKind` w `src/presentation/emails/incident-alert.tsx`, ale nie zgłoszą Workera, który nie działa, ani zdarzenia Stripe, które trasa odrzuca, zanim uruchomi jakikolwiek handler, na przykład takiego, które nie przeszło weryfikacji podpisu.
