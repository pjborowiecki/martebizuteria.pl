The shop watches itself in three ways, and none of them needs an account with an error-reporting service. Cloudflare keeps the Worker's logs and groups its failures, `/api/health` tells an uptime monitor whether the Worker can reach its storage, and the Worker emails `RESEND_EMAIL_FROM` when a failure needs the owner.

## Workers Logs and Issues

The top level of `wrangler.jsonc` turns both on, and every environment inherits it, so the preview and production deployments have them:

```jsonc
"observability": {
  "enabled": true,
  "issues": {
    "enabled": true,
  },
},
```

`enabled` keeps every invocation's logs, including each `console.error`, in Workers Logs. `issues.enabled` turns on Workers Issues, which records an uncaught exception, a failed invocation, a `5xx` response or a logged error as an occurrence and groups the occurrences of one failure into an issue. Issues needs Wrangler 4.134.0 or later; the repository is on 4.149.0. Cloudflare describes Issues as an open beta that is free while the beta lasts. Both appear in the Cloudflare dashboard under **Workers & Pages**, the Worker (`martebizuteria` for production, `martebizuteria-preview` for preview), **Observability**. A build's `dist/server/wrangler.json` shows the `observability` block the deploy uploads.

The log lines that belong to this page:

| Prefix                                                                 | Source                                                                                                                    |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `[Health] D1 did not answer:` (or `KV`, `R2`)                          | `/api/health` caught an error from that binding                                                                           |
| `[Alert] The <kind> alert to <address> was not sent: …`                | Resend refused or timed out on an incident alert                                                                          |
| `[Alert] The <kind> alert could not be sent:`                          | Reading KV or rendering the alert threw; the error follows                                                                |
| `[Stripe] Signature verification failed`                               | An event did not verify against `STRIPE_WEBHOOK_SECRET`; the route answered 400 and sent no alert                         |
| `[Stripe] Ignoring <mode> event <id> (<type>): …`                      | An event from the other Stripe mode reached this environment; the route acknowledged it and did nothing                   |
| `[Stripe] Domain logic failed for <type>:`                             | A webhook handler threw, the route answered 500 and Stripe will retry                                                     |
| `Paid Checkout Session <id> created no order:`                         | `handleFulfillCheckoutSession` could not create the order for a paid session                                              |
| `Paid Checkout Session <id> created no order from its return page:`    | The return page could not create the order for a paid session; its webhook records the failure and alerts if it fails too |
| `Refund <id> did not reach the customer; the shop was alerted: …`      | `handleRefundUndone` undid a failed or cancelled refund and sent the `refundFailed` alert                                 |
| `<label> failed for order <id>: …`                                     | The first attempt at an order e-mail failed and will be retried, or its last retry failed and `orderEmailFailed` follows  |
| `<label> for order <id> could not be prepared:`                        | Building an order e-mail threw before it reached Resend; it counts as a failed attempt                                    |
| `[AuditLog Queue] Batch insert failed:`                                | `processAuditLogQueueBatch` could not write a batch and asked the queue to retry it                                       |
| `[Newsletter] Campaign <id> will retry its batch after attempt <n>: …` | A newsletter batch failed and the queue retries it a minute later                                                         |
| `[Newsletter] Campaign <id> stopped after <n> attempts: …`             | The third attempt failed; the campaign is marked failed and `newsletterFailed` follows                                    |
| `[Retention] <kind> could not be cleared:`                             | The daily retention clean-up failed for one kind of row; the run then fails                                               |

`vp exec wrangler tail --env production` streams the same lines live; see [Local debugging](/docs/guides/local-debugging#watching-the-worker-in-a-deployed-environment).

## The health check

`GET /api/health` is the TanStack Start handler in `src/routes/api/health.ts`. It reads each storage binding once, all three in parallel, with operations that touch no data:

```ts
const [d1, kv, r2] = await Promise.all([
  probe("D1", () => env.DB.prepare("SELECT 1").first()),
  probe("KV", () => env.CACHE.get(PROBE_KEY)),
  probe("R2", () => env.IMAGES.head(PROBE_KEY)),
])
```

`PROBE_KEY` is `health-check`, a key and an object that do not exist, so KV answers `null` and R2 answers `null`, and that is a pass. Only a thrown error fails a check. The answer is `200` when all three pass and `503` when any fails:

```json
{ "checks": { "d1": "ok", "kv": "ok", "r2": "ok" }, "status": "ok" }
```

```json
{ "checks": { "d1": "error", "kv": "ok", "r2": "ok" }, "status": "error" }
```

The body never carries the error, a binding name or any configuration; the error goes to the log as `[Health] D1 did not answer:`. The response is sent with `Cache-Control: no-store`, so neither Cloudflare nor a proxy can serve a stale `200`. A `HEAD` request gets the same status, because TanStack Start answers `HEAD` with the `GET` handler.

What a `200` does not say: Stripe, Resend, the realtime Durable Object and the audit queue are not checked, so it means the Worker runs and reaches its database, cache and images, not that a checkout would succeed. The endpoint has no rate limit and needs no sign-in. Each call costs one D1 query that reads no rows, one KV read and one R2 Class B operation, about 43,200 of each a month for a check every minute.

Every deploy asks it once as well: the deploy's last step, `scripts/verify-deployment.ts`, fails unless the new Worker's `/api/health` on its `workers.dev` host answers `200`, next to the home page, the product listing, `robots.txt` and the Stripe webhook route. The new version is live by then, so a `503` there means rolling back; see [Roll back a deploy](/docs/guides/roll-back-a-deploy).

## Pointing an uptime monitor at it

Any HTTP uptime monitor works with these settings:

| Setting         | Value                                                                                                                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| URL             | Production: `https://martebizuteria.pjborowiecki.workers.dev/api/health` until it goes live on `https://martebizuteria.pl/api/health`. Preview: `https://preview.martebizuteria.pl/api/health` |
| Method          | `GET` (`HEAD` also works)                                                                                                                                                                      |
| Expected status | `200`; treat anything else, a timeout included, as down                                                                                                                                        |
| Keyword         | `"status":"ok"`, if the monitor can check the body                                                                                                                                             |
| Interval        | One to five minutes                                                                                                                                                                            |
| Who to alert    | The owner's e-mail; the monitor's own alert covers a Worker that cannot run at all                                                                                                             |

Production keeps `routes: []` in `wrangler.jsonc` with `workers_dev: true`, so for now it answers only on its `workers.dev` host, the one `WORKERS_DEV_HOSTS` in `src/modules/_core/constants/api.ts` names. Once it serves `martebizuteria.pl`, move the monitor there, since that is the address customers use; the `workers.dev` host keeps answering too.

The monitor is what notices an outage the Worker cannot report itself: a failed deploy, a broken route or a Cloudflare incident.

**Cloudflare Health Checks.** If the `martebizuteria.pl` zone is on the Pro plan or higher, Cloudflare can be the monitor; the Free plan has no standalone Health Checks. The check below probes `martebizuteria.pl`, so it watches production only once production serves that domain. In the dashboard, open the zone, go to **Health Checks**, select **Create**, and point it at `martebizuteria.pl` over HTTPS with the path `/api/health`, the expected code `200` and `"status":"ok"` as the **Response body**, a substring that must appear in the first 10 KB. Keep the **Interval** at a minute or more and the **Check regions** few, since each region sends its own requests. Then select **Configure an alert** on the same page, add the notification e-mail and the health check, and choose the trigger. Cloudflare sends it only after the status changes in the majority of the selected regions.

**On the Free plan**, use a hosted uptime monitor with the settings above. That is the only part of this page that needs an account outside Cloudflare, and nothing in the code depends on which one is used.

## E-mail alerts from the shop

`sendIncidentAlert` in `src/lib/incident-alert.server.ts` emails `RESEND_EMAIL_FROM` in the shop's language with the `incident-alert.tsx` template. Each e-mail names the kind of incident, its reference, the cause and the environment:

| Incident                   | Sent when                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Reference                                                            | What to do                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `paidCheckoutWithoutOrder` | `handleFulfillCheckoutSession` in `stripe.webhooks.ts` gets `NOT_FOUND` from fulfilment for a paid session: no pending payment carries it, or its checkout was released or is gone. The webhook answers 200, so Stripe will not send it again. A session whose `deployment` metadata names another deployment, such as a local test run's, is acknowledged without this alert (see [Payments](/docs/features/payments#the-webhook-endpoint)).                                                                                                                                                                                                                    | The Checkout Session id                                              | Find the payment in the Stripe Dashboard by the session id, then refund it or arrange the order with the customer. The `order.fulfillment_failed` entry in `/admin/audit` has the amount and the customer's e-mail.                                                                                                                                                |
| `stripeWebhookFailed`      | Any handler in `webhookHandlers` throws, so `src/routes/api/webhooks.stripe.ts` answers 500 and Stripe retries the event, in live mode for up to three days. A paid session whose order could not be created for any other reason lands here, with `order.fulfillment_failed` in `/admin/audit` too.                                                                                                                                                                                                                                                                                                                                                             | The Stripe event id                                                  | The cause starts with the event type. Read the stack in Workers Logs, fix the cause, and let Stripe's next retry, or **Resend** on the event in the Stripe Dashboard, deliver it again.                                                                                                                                                                            |
| `refundFailed`             | `handleRefundUndone` in `stripe.webhooks.ts` handles `refund.failed`, or `refund.updated` with the refund `canceled` or `failed`, for a refund on one of the shop's orders. `undoFailedRefund` has already made the order count only the refunds that still stand, reopening it unless it was cancelled, and recorded `order.refund_failed`. The customer is not emailed about the failure; the order's history shows whether they were told earlier that the refund is on its way, which a refund that failed before its `charge.refunded` was handled never announced. The cause names the order number, the amount, the status and Stripe's `failure_reason`. | The Stripe refund id, `re_…` or `pyr_…`                              | Stripe has put the money back in the shop's balance. Find the payment in the Stripe Dashboard and pay the customer back another way: once the cause is fixed, refund again there or with the order's Refund button, or agree a bank transfer with the customer. Check the order's stock if its items were returned with the refund.                                |
| `auditQueueFailed`         | `processAuditLogQueueBatch` in `audit-log.queue.server.ts` cannot write a batch, marks every message for retry and then alerts. The queue retries a batch three times (`max_retries: 3`), then moves its messages to the dead-letter queue, which retries each one on its own three more times, five minutes apart, and alerts under its own name.                                                                                                                                                                                                                                                                                                               | The queue name                                                       | Check D1 in the Cloudflare dashboard. An alert from the audit queue means a batch is being retried, and after its third retry its entries go to the dead-letter queue. An alert from `…-dlq` means an entry failed on its own; one still failing after its third retry there, about 15 minutes later, is lost from `/admin/audit`, with its error in Workers Logs. |
| `newsletterFailed`         | `processNewsletterQueueBatch` in `newsletter-campaign.queue.server.ts` stops a campaign on its third failed attempt at a batch, after it marks the campaign failed and audits `email.failed`. A message the consumer still throws on goes to the newsletter queue's dead-letter queue, whose consumer carries on from the last subscriber the campaign reached.                                                                                                                                                                                                                                                                                                  | The campaign id                                                      | Open Marketing in the admin panel to see how many subscribers the campaign reached and why it stopped, and check the Resend account's status and sending quota. A stopped campaign cannot be resumed; a new one goes to every confirmed subscriber again.                                                                                                          |
| `orderEmailFailed`         | `deliverOrderEmail` in `deliver-order-email.server.ts` records an order email as `email.failed` after Resend refused its first attempt and both retries: the confirmation, the shop's new-order notice, the in-progress, shipped, tracking, delivered, cancelled, refunded and failed-payment emails, and the two withdrawal emails.                                                                                                                                                                                                                                                                                                                             | The email's idempotency key, such as `order-confirmation/<order id>` | Check Resend's status, its sending quota and the sender domain. Then press **Resend email** on the order's Activity card, which sends under the same key; every order email can be resent there except the failed-payment and the two withdrawal emails, so for those write to the customer.                                                                       |

**At most once per incident.** An incident is its environment, kind and reference. The first failure writes `incident-alert:<APP_ENV>:<kind>:<reference>` to the `CACHE` KV namespace with a one-hour expiry (`INCIDENT_ALERT_SECONDS`) and only then sends; a `stripeWebhookFailed` incident is kept for three days (`STRIPE_EVENT_RETRY_SECONDS`), the time Stripe goes on retrying an event in live mode. A `refundFailed` incident is keyed by the refund, so `refund.failed` and `refund.updated` for one refund send one e-mail. Further failures under the same key while it is kept are logged and not emailed, so all of Stripe's retries of one event, a paid session whose order could not be created among them, send one e-mail, and the queue's retries of one batch send one. A new Checkout Session, another event or a failure after the incident has expired is a new incident. KV is eventually consistent between Cloudflare locations, so two failures that land at the same moment in different locations can each send one.

**An alert never breaks the work that raised it.** `sendIncidentAlert` catches everything: a KV error, a rendering error and a refused send are logged with `[Alert]` and swallowed. The webhook route hands the alert to `scheduleBackgroundWork`, so Stripe gets its 500 at once, and fulfilment does the same before it answers 200. The queue consumer awaits the alert only after every message is marked for retry. Alerts are not recorded in the audit log, because the database may be what failed.

**Where alerts go.** Alerts go to `RESEND_EMAIL_FROM`, the address the shop sends from, in every environment, so development and preview send them too. In the `test` environment it is `noreply@example.test` from `.env.test`, a dummy inbox the mocked Resend captures. Alerts are sent through Resend from that same address, so a broken sender also stops them; the uptime monitor and Cloudflare's own notifications do not depend on it.

## Cloudflare notifications

Notifications are set up per account in the Cloudflare dashboard under **Notifications**, **Add**. Every plan can deliver them by e-mail or webhook. The ones worth adding for this shop:

- **Health Checks status**, if the zone has the health check above. Creating it from **Configure an alert** on the Health Checks page adds it here.
- **Custom Alerts** (beta), which run a SQL API query on a schedule and notify when the result meets a threshold. A query that counts `5xx` responses in the last five minutes and alerts above zero catches failures that throw before the code can email, such as a broken deploy. Cloudflare's own example reads `events.httpRequests` filtered on the account tag and `edgeResponseStatus >= 500`; which datasets a Custom Alert can read depends on the plan, and the dashboard lists the ones available.
- **Workers Issues automations**, set up in the Issues dashboard, which send a new issue to a webhook, a chat service or an incident-management tool.

Keep at least one of the Cloudflare-side alerts or the uptime monitor in place. The shop's own e-mails cover the six kinds of failure above, the `IncidentKind` union in `src/presentation/emails/incident-alert.tsx`, but they cannot report a Worker that does not run, nor a Stripe event the route refuses before any handler runs, such as one that fails signature verification.
