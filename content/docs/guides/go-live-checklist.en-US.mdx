---
title: "Go-live checklist"
description: "One ordered list of everything that must be true before the shop takes real orders: domains, database, images, queues, secrets, Stripe, e-mail, the shop's mailbox, Turnstile, InPost, the deploy, the dropped inventory column, the daily clean-up, admin two-factor sign-in, monitoring, backups, leftover data, the shop's texts and products, a legal review, a rehearsal on preview and a live test order with a refund."
---

Work through the list in order. Each item says what must be true, how to check it, and which page has the details. Later items build on earlier ones: the deploy in item 12 needs every value set before it, and the checks after it need the deploy. Open sales only once every item holds. The steps that stay with the shop after launch are listed at the end.

1. **The shop's domains reach their Workers.** `wrangler.jsonc` lists `martebizuteria.pl` under the `routes` of `production` and `preview.martebizuteria.pl` under those of `preview`, as custom domains, so every deploy attaches them and Cloudflare creates the DNS record and the certificate for each. Before the first deploy, `martebizuteria.pl` is an active zone in the account that holds both Workers, and the API token in `CLOUDFLARE_ACCESS_TOKEN`, in both the `preview` and the `production` GitHub environments, has the Workers Routes edit and Zone read permissions on it and the D1 edit permission, because every deploy also applies the migrations (item 2). Nothing still depends on an A, AAAA or CNAME record on either hostname, because a deploy from CI replaces such a record without asking; the MX and TXT records of the mailbox and the Resend sender are not touched. Look at the custom domains the dashboard lists on the `martebizuteria` and `martebizuteria-preview` Workers: any other than these two is detached by the next deploy, and the `workers.dev` addresses keep working. Only the hosts in `HOSTS_BY_MODE` can sign in, check out or get e-mail links, so if `www.martebizuteria.pl` should work, serve it from the zone with a proxied DNS record and a redirect rule to `https://martebizuteria.pl` rather than attaching it (see [Deploy a preview](/docs/getting-started/deploy-preview#the-custom-domains)). Every subdomain of `martebizuteria.pl` that serves web pages answers over HTTPS: the shop sends `Strict-Transport-Security` with `includeSubDomains` for a year, so after one visit a browser refuses plain HTTP on all of them. Check: `curl -sI https://martebizuteria.pl/api/health` answers `200`.

2. **The production database has every migration.** Every deploy applies the migrations the database has not recorded, with `bun run db:migrate:production`, right before `wrangler deploy`, and a failing one stops the deploy before the Worker is uploaded; every preview deploy does the same to the database development and preview share. Before merging a branch that adds migrations, `bun run db:migrations:production` and `bun run db:migrations:preview` list what the next deploys will apply. After the deploy in item 12, `bun run db:migrations:production` answers `No migrations to apply!`. The terms of service, the privacy policy, the returns page and the FAQ reach the live shop only through migrations, so `/faq` answers `404` until its migration has run. A migration that rewrites one of these pages skips a language whose text was already edited at `/admin/content`, so read each page on the live site afterwards, in both languages; item 19 lists what to look for. See [Database migrations](/docs/guides/database-migrations).

3. **Images come from the shop's own image domain, and preview has its own bucket.** Development and preview bind `martebizuteria-preview`, production binds `martebizuteria`, and the production deploy refuses a configuration that gives both the same bucket. [Image delivery](/docs/guides/image-delivery#one-time-setup) has every step with its commands:
   - Before the next preview deploy or `bun run dev`, create `martebizuteria-preview` and turn on its `r2.dev` address with `bunx wrangler r2 bucket create martebizuteria-preview` and `bunx wrangler r2 bucket dev-url enable martebizuteria-preview`. Until it exists, `bun run dev` cannot reach `IMAGES` and a preview deploy fails.
   - Copy every object from `martebizuteria` into it with `rclone copy` and a temporary R2 API token limited to those two buckets, confirm the copy with `rclone check`, then delete the token.
   - Set `VITE_R2_URL` to the preview bucket's `r2.dev` address in `.env.development`, `.env.preview` and the GitHub `preview` environment, and deploy preview.
   - Attach `images.martebizuteria.pl` to `martebizuteria` as a custom domain, with the status **Active**, and leave the bucket's `r2.dev` address on, because order confirmations already sent load their images from it.
   - Turn on Image Transformations for the zone, and move the account to the Images Paid plan before switching production: about 200 products can use up the Free plan's 5,000 unique transformations in a month, after which new sizes are served at full size until the month ends.
   - Check that `https://images.martebizuteria.pl/cdn-cgi/image/width=256,f=auto/marketing/hero.webp` answers `200` with an image, then set `VITE_R2_URL` to `https://images.martebizuteria.pl` in `.env.production` and the GitHub `production` environment. The deploy builds the bundle and uploads the Worker secret from this one value, and the Content-Security-Policy follows the Worker's copy, so never set the two from different values.

4. **The audit and newsletter queues and their dead-letter queues exist.** Each consumer of an audit or newsletter queue in `wrangler.jsonc` names a `-dlq` queue as its `dead_letter_queue`, which the same Worker consumes one message at a time. An audit batch the consumer still cannot write after `max_retries` (3) is retried message by message rather than deleted (see [Audit log](/docs/features/audit-log#the-queue)), and a newsletter message the consumer keeps throwing on is picked up again rather than lost (see [E-mail](/docs/features/email#the-newsletter)). `scripts/verify-bindings.ts` refuses a preview or production deploy without them, and a deploy fails while a queue it names does not exist in Cloudflare. Create each one once with `bunx wrangler queues create <name>`: for production `martebizuteria-audit-log-dlq`, `martebizuteria-newsletter` and `martebizuteria-newsletter-dlq`, and for preview, which development shares, `martebizuteria-audit-log-preview-dlq`, `martebizuteria-newsletter-preview` and `martebizuteria-newsletter-preview-dlq`. Check that `bunx wrangler queues list` shows all six beside `martebizuteria-audit-log` and `martebizuteria-audit-log-preview`. An `auditQueueFailed` alert naming `martebizuteria-audit-log-dlq` means an entry failed on its own; one that still fails after three retries there is lost, so act on it (see [Monitoring and alerts](/docs/guides/monitoring-and-alerts#e-mail-alerts-from-the-shop)).

5. **The GitHub environments hold their own values.** Under **Settings**, **Environments**, `production`, every name under `secrets.required` of the `production` environment in `wrangler.jsonc` has a value, because `prepare-deploy-secrets.ts` stops the deploy at the first blank one other than the two InPost secrets of item 11, and the browser values are set as environment variables. The Stripe keys are the live ones, which exist once Stripe has activated the account: `VITE_STRIPE_PUBLISHABLE_KEY` starting with `pk_live_` as a variable, and `STRIPE_SECRET_KEY` starting with `sk_live_`, or a restricted `rk_live_`, as a secret. Preview needs test keys, so set both on each environment rather than once for the repository; the deploy refuses keys of the wrong mode (see [Stripe](/docs/integrations/stripe#secrets)). `AUTH_SECRET` has a value of its own, not preview's. Google is the only sign-in provider, and Better Auth builds its callback from the host the customer signs in on, so the OAuth client whose id and secret are an environment's `AUTH_GOOGLE_CLIENT_ID` and `AUTH_GOOGLE_CLIENT_SECRET` lists `https://martebizuteria.pl/api/auth/callback/google` for production and `https://preview.martebizuteria.pl/api/auth/callback/google` for preview (see [Environment variables](/docs/getting-started/environment-variables#provider-callbacks-to-register)). Nothing reads `AUTH_GITHUB_CLIENT_ID`, `AUTH_GITHUB_CLIENT_SECRET` or `SENTRY_AUTH_TOKEN` any more:
   - delete the two `AUTH_GITHUB_*` secrets from the `preview` and `production` environments, and from both Workers with `wrangler secret delete` or in the dashboard if they were ever uploaded, since a deploy adds secrets but never removes them;
   - remove all three names from the local `.env.development`, `.env.preview` and `.env.production`;
   - delete any GitHub OAuth app registered for the shop at `github.com/settings/developers`.

6. **Stripe sends live events to the shop.** In the Stripe Dashboard, in live mode, a webhook endpoint for `https://martebizuteria.pl/api/webhooks/stripe` listens to the eight events in `STRIPE_WEBHOOK_EVENTS` (`src/integrations/stripe/stripe.constants.ts`):

   - `checkout.session.completed`
   - `checkout.session.async_payment_succeeded`
   - `checkout.session.async_payment_failed`
   - `checkout.session.expired`
   - `payment_intent.payment_failed`
   - `charge.refunded`
   - `charge.dispute.created`
   - `charge.dispute.closed`

   Give the endpoint the API version `2026-08-26.dahlia`, the one `STRIPE_API_VERSION` pins, so the payloads have the shape the handlers read. The endpoint's own signing secret, `whsec_…`, is the production `STRIPE_WEBHOOK_SECRET`. Preview's endpoint, on `https://preview.martebizuteria.pl/api/webhooks/stripe` or the preview `workers.dev` host, is a test-mode endpoint whose own secret is preview's `STRIPE_WEBHOOK_SECRET`. The route acknowledges an event from the other mode without acting on it, so a `[Stripe] Ignoring … event` line in a Worker's logs means its endpoint or secret belongs to the other mode; replace the secret with the one of an endpoint in the right mode. `checkout.session.expired` matters as much as the payment events, because it is how the stock an abandoned checkout held comes back. See [Stripe](/docs/integrations/stripe#webhooks).

7. **Cards, BLIK and Przelewy24 are on in live mode.** The Checkout Session names no payment methods, so Stripe offers the ones turned on in the Dashboard, and `CHECKOUT_PAYMENT_METHOD_ORDER` only orders them. In live mode, under **Settings**, **Payment methods**, cards, BLIK and Przelewy24 are on; the terms of service promise all three. Test-mode settings do not carry over to live mode.

8. **Resend sends from the shop's domain, on a plan that covers its mail.** `martebizuteria.pl` is verified in Resend, with the DKIM record (`resend._domainkey`), the SPF records on the `send` subdomain and a DMARC record (`_dmarc`, `v=DMARC1; p=none;` to start), and `RESEND_EMAIL_FROM` in the production environment is a bare address on it whose mailbox someone reads, because the shop's notices of new orders and of withdrawals sent online, and the incident alerts, among them a newsletter that stopped and an order e-mail that still failed after its retries, go to it. Development and preview send the same notices to their own `RESEND_EMAIL_FROM`, with the same subjects, so if that is the same mailbox, check in the production admin that an order is real before packing it. `bun run email:verify production` passes; every deploy runs the same check, which reads the DKIM and SPF records but not DMARC, and does not check that the sender's domain is `martebizuteria.pl`. Add a Full access key of the same Resend team as the secret `RESEND_MANAGEMENT_API_KEY` of the `preview` and `production` environments, which only this check reads, so that it reads the domain; without it, each deploy sends a test e-mail that counts against the quota (see [Resend](/docs/integrations/resend#sender-domain)). Order e-mails, the e-mails visitors can request and newsletters share the account's daily and monthly quota. `PUBLIC_EMAILS_DAILY_MAX` in `src/integrations/resend/resend.public-email-limits.server.ts` caps the e-mails visitors can request at 50 a day, half the free plan's 100, and on the free plan a newsletter to more than a few dozen subscribers would stop order e-mails until the next day. Move to a paid Resend plan before the newsletter list grows, and on a larger plan raise `PUBLIC_EMAILS_DAILY_MAX` if real sign-ups and confirmations come near 50 a day.

9. **Someone reads `kontakt@martebizuteria.pl`.** It is `BUSINESS.EMAIL`, and it receives customers' replies to every e-mail the shop sends, each of which carries it as `Reply-To`, and the withdrawals and complaints that the terms, the returns page, the forms and the order confirmation direct there. The domain's MX records point at a real mailbox, a message from an outside address arrives, and someone reads it every working day: a complaint left unanswered for 14 days counts as accepted.

10. **Turnstile has a production widget.** A new checkout, a sign-up, a password-reset request, a verification resend, a newsletter sign-up and a withdrawal by order number each need a Turnstile token, which the server checks with siteverify. In the Cloudflare dashboard, under **Turnstile**, a widget in **Managed** mode for `martebizuteria.pl` and `martebizuteria.pjborowiecki.workers.dev`, the two hosts production accepts, supplies the production values: its site key as the variable `VITE_TURNSTILE_SITE_KEY` and its secret key as the secret `TURNSTILE_SECRET_KEY` in the GitHub `production` environment, and both in `.env.production` for a deploy from a laptop. Preview keeps Cloudflare's always-passing testing keys: the variable `VITE_TURNSTILE_SITE_KEY` set to `1x00000000000000000000AA` and the secret `TURNSTILE_SECRET_KEY` set to `1x0000000000000000000000000000000AA` in the GitHub `preview` environment, and the same two lines in `.env.development` and `.env.preview`, without which a preview deploy stops and the local dev server cannot open a checkout. `scripts/verify-turnstile-keys.ts` stops a production deploy when a key is missing, when a testing key is paired with a widget's key, or when the keys are the testing ones, but it calls no Cloudflare API and cannot see whether the widget lists the shop's hosts. Check: after the deploy, open a checkout, sign up, request a password reset and join the newsletter in a normal browser on `https://martebizuteria.pl`; each form passes the widget and the checkout shows the payment form. The browser tests use a widget double, so only a real browser exercises the real widget. See [Cloudflare Turnstile](/docs/integrations/cloudflare-turnstile#keys).

11. **InPost can book shipments and print labels.** In InPost Manager (`https://manager.paczkomaty.pl`, **My account**, **API**), generate the ShipX API token and copy the organisation ID, and make sure the organisation's sender details are complete, because every shipment is booked with them. Put the two values in the GitHub `production` environment as the secrets `INPOST_API_TOKEN` and `INPOST_ORGANIZATION_ID`, and in `.env.production` for a deploy from a laptop, and set the webhook address in the same API section to `https://martebizuteria.pl/api/webhooks/inpost`. The deploy accepts the two values blank, which keeps InPost shipping off, but stops when `.env.preview` or `.env.production` has no `INPOST_API_TOKEN=` or `INPOST_ORGANIZATION_ID=` line at all. Rehearse on preview first, against InPost's sandbox at `https://sandbox-manager.paczkomaty.pl`, whose account needs its own details, a virtual top-up under **Payments**, and its own token and organisation ID in `.env.preview` and the GitHub `preview` environment, with `https://preview.martebizuteria.pl/api/webhooks/inpost` as its webhook address: book a shipment for a test order from its page in `/admin/orders`, refresh its status, download its label, cancel it in the sandbox InPost Manager and check that the order shows it as Cancelled and offers **Create shipment** again. With the values blank, create each parcel in InPost Manager and enter its tracking number when you mark the order shipped. See [InPost](/docs/integrations/inpost#shipments-through-shipx).

12. **Production runs the configuration above.** The last **Production Deployment** run on `main` succeeded after every value above was set. It starts when CI passes for a push to `main`, not on the push itself, and a run whose commit is no longer the tip of `main` ends with a warning and a skipped deploy job, which is expected. This deploy is also what turns on the alerts and Workers Issues in production. A `VITE_` value is built into the browser bundle, so changing one needs a new deploy. See [CI/CD](/docs/tooling/ci-cd#what-a-production-deploy-waits-for).

13. **The unused `inventory.version` column is dropped after that deploy.** The Drizzle schema no longer declares the column, but the preview and production databases keep it until the branch `drop-inventory-version` is merged. Its one migration, `ALTER TABLE inventory DROP COLUMN version`, may reach a database only when no Worker that still selects the column runs against it: on a Worker running older code, the product page, a new checkout and the admin product editor fail once the column is gone. Merge `drop-inventory-version` into `main` only after the deploy in item 12, which carries the commit "refactor(inventory): stop declaring the unused version column", is live on preview and production, and open its pull request only once `main` has that commit, because the pull request's preview deploy migrates the database development and preview share. The next deploys apply the migration as item 2 describes. Check: after the production deploy, `vp exec wrangler d1 execute DB --env production --remote --command "SELECT name FROM pragma_table_info('inventory')"` no longer lists `version`. See [Roll back a deploy](/docs/guides/roll-back-a-deploy#when-a-migration-has-already-been-applied).

14. **The daily clean-up runs.** In the Cloudflare dashboard both the `martebizuteria` and `martebizuteria-preview` Workers list the Cron Trigger `0 3 * * *`, and after the next run at 03:00 UTC their Workers Logs show a `[Retention] <kind>: <count> cleared` line for each kind (see [Data retention](/docs/guides/data-retention#checking-that-it-ran)). The periods it enforces are in `src/lib/retention.ts`, and the privacy policy states them; if the policy was edited at `/admin/content`, check that it still gives the same periods.

15. **Every admin signs in with a second factor.** The admin panel sends an admin without two-factor authentication to `/admin/security` and refuses them every admin action, and Google sign-in is refused for admins. After the deploy, sign in to the admin with the password, turn two-factor authentication on at `/admin/security` with an authenticator app, and keep the recovery codes somewhere safe outside the shop. An admin account created through Google has no password: set one first with **Forgot password?** on the sign-in page. See [Better Auth](/docs/integrations/better-auth#two-factor-authentication-for-admins).

16. **An uptime monitor watches `/api/health`.** A monitor requests `https://martebizuteria.pl/api/health` every one to five minutes, expects `200` and `"status":"ok"`, and alerts the owner: Cloudflare Health Checks if the zone is on Pro or higher, otherwise a hosted uptime monitor. It is what notices an outage the Worker cannot report itself. In the Cloudflare dashboard, under **Notifications**, add the Health Checks status alert if Health Checks are used, and consider a Custom Alert on `5xx` responses and a Workers Issues automation. See [Monitoring and alerts](/docs/guides/monitoring-and-alerts#pointing-an-uptime-monitor-at-it).

17. **A backup exists and has been restored once.** rclone and GnuPG are installed (`brew install rclone gnupg`), a read-only R2 API token limited to `martebizuteria` is kept in the password manager, you know the Time Travel window of the account's plan, the first encrypted export of the production database and the first copy of the image bucket are stored outside Cloudflare, and the export has been loaded into a local database once, as [Backup and restore](/docs/guides/backup-and-restore) shows.

18. **Data the shop no longer keeps is gone.** Three things written before the current code stay until they are removed by hand:
    - Users created by the anonymous sign-in the shop no longer offers. List them, and what they own, in production:

      ```sh
      vp exec wrangler d1 execute DB --env production --remote --command "SELECT id, email, name, stripe_customer_id, created_at FROM user WHERE is_anonymous = 1"
      vp exec wrangler d1 execute DB --env production --remote --command "SELECT (SELECT count(*) FROM \"order\" WHERE user_id IN (SELECT id FROM user WHERE is_anonymous = 1)) AS orders, (SELECT count(*) FROM checkout WHERE user_id IN (SELECT id FROM user WHERE is_anonymous = 1)) AS checkouts"
      ```

      If the first query returns rows, delete them with `vp exec wrangler d1 execute DB --env production --remote --command "DELETE FROM user WHERE is_anonymous = 1"`. Their sessions, sign-in accounts, addresses and wishlists go with them; their orders, checkouts and carts stay and lose the user link, like a guest's. Do the same with `--env preview`. A user with a `stripe_customer_id` also left a Stripe customer with a placeholder address, which can be deleted in the Stripe Dashboard. Once neither database holds such a user, the `is_anonymous` column can be dropped, as the [Roadmap](/docs/project/roadmap) notes.

    - Stripe customers left behind by accounts deleted earlier, when deleting an account did not yet delete its Stripe customer. In the Stripe Dashboard, delete each customer, with its saved cards, whose metadata `userId` belongs to no account any more.
    - Activity and sign-in entries of those accounts. In `/admin/audit`, delete the entries of accounts that no longer exist.

19. **The shop's own texts say how the business works.** Before the lawyer reads them, read the live pages in both languages, edit them at `/admin/content` where practice differs, and check that:
    - the privacy policy's retention periods, KSeF wording and recipients match how the business works, with any accounting office or e-mail host that handles customer data added; if Bot Fight Mode or WAF rate limiting is on for the zone, Cloudflare's own cookies, such as `__cf_bm` and `_cfuvid`, are listed;
    - the privacy policy says that deleting the account ends the newsletter subscription, and names the withdrawal by order number among the places the Turnstile check runs and its acknowledgement among the e-mails counted per address;
    - the first step of "How to withdraw" on `/exchanges-and-returns` and § 8 on `/terms-of-service` link `/withdraw-from-contract`;
    - `/exchanges-and-returns` no longer says "Okres gwarancji na biżuterię M'Arte wynosi 2 lata" or "The warranty period for M'Arte jewellery is 2 years", and no product description or other text entered in the admin says "gwarancja", "warranty" or "guarantee": the shop gives no guarantee, only the statutory liability for lack of conformity;
    - `/faq` and `/en-US/faq` describe how invoices reach the buyer and how customers hear that a collection order is ready the way the shop does it, and the care advice suits every finish and stone it sells;
    - every `delivery_method` description in D1 gives the delivery times of § 7 of the terms; the migration that rewrote them left alone a description edited since it was seeded.

    A migration that changes one of these sentences skips a language whose sentence was edited, so a sentence still missing has to be added by hand.

20. **Every product page names its manufacturer.** The catalogue has no manufacturer fields, so every product page names the seller from `BUSINESS` as the manufacturer, which holds for the pieces the shop makes. A product made by someone else needs its own manufacturer's name, postal address and e-mail address on its page before it is sold. Any warning or safety information that has to accompany a piece is in its specifications, as a product attribute in `/admin/catalog`. See [Legal pages](/docs/features/legal-pages#manufacturer-on-product-pages).

21. **A lawyer has read the shop's legal texts.** Start this early; it takes the longest. The review covers the terms of service, § 8 with the online withdrawal included, the returns page, the FAQ and the privacy policy, with its legal bases, recipients and retention periods, as published on the live site, since they are rows in the production database edited at `/admin/content`; the customer e-mails, which `bun run dev` previews at `http://localhost:3000/dev/emails` in both languages, above all the order confirmation with its withdrawal and complaint texts and the wording of the acknowledgement of a withdrawal sent online; the withdrawal function at `/withdraw-from-contract` and on the order page of an account; the two forms in `public/forms`; and the seller's details in `BUSINESS` (`src/presentation/branding/business.ts`), which the e-mails print, every product page names as the manufacturer, and the terms and forms repeat. Three questions are the lawyer's to settle: whether the order confirmation may link the terms instead of attaching them, whether both forms may be in Polish only, and whether logging the page views of signed-in customers, with the session-storage markers that go with it, needs their consent under the Electronic Communications Law. See [Legal pages](/docs/features/legal-pages) and [Transactional email](/docs/features/email).

22. **Preview has been rehearsed in a real browser.** On `https://preview.martebizuteria.pl`, after a preview deploy:
    - pay with a Stripe test card and open the parcel-locker map, and check that the browser console shows no Content-Security-Policy refusal; the browser tests block Stripe.js and the map tiles, so only a real browser exercises those hosts;
    - at `/admin/marketing`, send a test to yourself, then a newsletter to a confirmed address you own, and check that Gmail shows its **Unsubscribe** button and that both the button and the link in the letter unsubscribe.

    Then let the real Payment Element pay in CI: create a Stripe sandbox with no webhook endpoint, so its test payments never reach the preview Worker or e-mail `RESEND_EMAIL_FROM`; under **Settings**, **Secrets and variables**, **Actions**, add its keys as the repository secrets `E2E_STRIPE_SECRET_KEY` (`sk_test_`) and `E2E_STRIPE_PUBLISHABLE_KEY` (`pk_test_`); run the **E2E (full)** workflow by hand and check that its **E2E (Stripe test mode)** job passes. Without the secrets that job reports its spec skipped. See [Testing](/docs/tooling/testing#stripe-test-mode).

23. **A live test order has gone through end to end, refund included.** On `https://martebizuteria.pl`, buy a cheap product with a real card or BLIK. Then check that:

    - the payment step offered card, BLIK and Przelewy24;
    - the Stripe endpoint shows the order's events delivered with `200`;
    - the order is in `/admin/orders`, `/admin/audit` records it, and the product's stock went down;
    - the confirmation reached the buyer with `formularz_zwrotu.pdf` attached, and the new-order notice reached `RESEND_EMAIL_FROM`, neither of them in spam.

    Then refund the order from its page in `/admin/orders`, answering that the item came back, and check that Stripe shows the refund, the order reads as refunded, the stock is back and the buyer received the refund e-mail. Stripe keeps its processing fee on a refunded payment, so the test costs that fee.

## After launch

These stay with the shop for as long as it sells:

- Repeat the database export and the image copy of item 17 regularly, for example every week and before a risky migration, and keep only the last few encrypted exports, outside Cloudflare.
- Act on every alert that reaches `RESEND_EMAIL_FROM`; [Monitoring and alerts](/docs/guides/monitoring-and-alerts#e-mail-alerts-from-the-shop) says what each one means.
- Before shipping a parcel-locker order, look for the **Locker not confirmed** tag on its admin page. It means InPost could not be reached to confirm the locker when the order was placed, so check in InPost that the locker exists.
- Watch `/admin/audit` for **Account deletion failed**: each one is a customer whose account was kept because Stripe could not delete their Stripe customer. Ask them to try again, or delete the account from `/admin/customers` once Stripe answers.
- The product editor has no compare-at field yet. To put a variant on sale, lower `product_variant.price` and set `compare_at_price` in D1; the database records the change in `price_history`, and the storefront shows the reduction, with the lowest price of the 30 days before it struck through, only when the new price is below that lowest price. A variant that already had a compare-at price when the price history began shows only its price until its price is cut again. See [Product page](/docs/features/product-page#reduced-prices-and-the-lowest-price-of-the-30-days-before).
