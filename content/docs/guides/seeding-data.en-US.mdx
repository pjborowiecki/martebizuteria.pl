## Read this first

**Do not run `bun run db:seed`, `bun run db:seed:preview` or `bun run db:seed:production`.**

The seed files in `src/integrations/drizzle-orm/seeds/` were written against an earlier state of the catalog. The live preview and production databases have since been edited through the admin console. Ten of the eleven files open with a `DELETE` and then write their rows with an upsert, so running one now would remove real rows and overwrite admin edits with the fixtures checked into the repository:

- `product-categories.sql`, `product-collections.sql`, `product-attributes.sql` and `products.sql` delete every row that has one of their handles but not one of their ids, and `product-variants.sql` does the same by SKU.
- `inventory.sql`, `product-images.sql` and `attribute-on-product.sql` delete the rows of the seed variants or products that are not their own, and `category-on-product.sql` and `collection-on-product.sql` delete every category and collection link of the two seed products.
- Each of these files then writes its rows with `ON CONFLICT(id) DO UPDATE` or `INSERT OR REPLACE`, which puts a seeded row edited since — its titles, descriptions, price, status or images — back to the file's values.

Only `delivery-methods.sql` deletes and overwrites nothing; it uses `INSERT OR IGNORE`.

They stay in the repository for three good reasons: they document the reference catalog shape, they are the starting point for a brand-new database, and the local test database the E2E suite runs against is built from them (see [The local test database](#the-local-test-database)). They are not a "reset to a known state" button for an environment that has real data in it. Remember also that `development` and `preview` point at the **same** D1 database (`martebizuteria-preview`), so the only safe place to practise is the local `test` database.

A new seed file goes into all three at its place in that order.

## The conventions they follow

Read one before writing one. `delivery-methods.sql` is the simplest, and it uses `INSERT OR IGNORE`, so re-running it is harmless — and also changes nothing in a database that already has its rows:

```sql
INSERT OR IGNORE INTO courier (id, internal_code, is_active, logo, name, created_at, updated_at) VALUES
('019f4a10-0000-7000-8000-000000000001', 'inpost', 1, NULL, 'InPost', unixepoch() * 1000, unixepoch() * 1000),
('019f4a10-0000-7000-8000-000000000002', 'marte-atelier', 1, NULL, 'M''ARTE Atelier', unixepoch() * 1000, unixepoch() * 1000);
```

It seeds three delivery methods against two couriers, each with its Polish `name`, its `names` in Polish and English and its `rank` in the checkout: `inpost_courier_standard` (Kurier InPost / InPost courier, `type: "courier"`, 1999, rank 0), `inpost_locker_standard` (Paczkomat InPost / InPost parcel locker, `type: "locker"`, 1499, rank 1) and `marte_atelier_pickup` (Odbiór w atelier / Pickup at the atelier, `type: "in_store"`, 0, rank 2). Once the shop is live, the methods are changed in the admin under Settings → Delivery, not in this file (see [Shipping and delivery](/docs/features/shipping-and-delivery#managing-delivery-methods)).

The catalog files are destructive by design. `products.sql` opens with:

```sql
DELETE FROM product
WHERE handle IN ('lapis-lazuli-necklace', 'onyx-necklace')
  AND id NOT IN (
    '019e99d8-9f56-777d-8f3c-95c393be568b',
    '019e99f2-dfa2-7798-b04f-cebfdbbdb427'
  );
```

It then inserts its two products with `ON CONFLICT(id) DO UPDATE SET handle = excluded.handle, titles = excluded.titles, …`, which overwrites every column it lists on a row that already exists. The pattern is "delete any row with one of my handles that is not one of my rows, then upsert my rows" — idempotent as long as the file's own ids never change, and destructive as soon as the live catalog has other rows sharing a handle or has edited one of the seeded rows.

Other conventions worth matching:

- **Fixed ids, written out in full.** A seed row's id is part of the file's contract, because dependent files reference it, and so do the E2E fixtures in `e2e/data/catalog.ts`, which name the seeded products, SKUs, prices and delivery-method ids. Only `delivery-methods.sql` uses hand-composed ids such as `019f4a10-0001-7000-8000-000000000001`, which read as obviously synthetic; the catalog files carry generated ids, UUIDv7 and, for product images, UUIDv4.
- **Timestamps in milliseconds**, matching the `timestamp_ms` mode the schema uses: `delivery-methods.sql` writes `unixepoch() * 1000`, the catalog files fixed values such as `1780698778000`.
- **Booleans as `1` and `0`.**
- **Translated columns as `json_object`:**

```sql
json_object('pl-PL', 'Naszyjnik Lapis Lazuli', 'en-US', 'Lapis Lazuli Necklace')
```

Both locale keys are always present, with full BCP 47 tags.

- **Prices as integer minor units.** `1499` is 14,99 zł.
- **Doubled single quotes for apostrophes**, since `M'ARTE` has to be written `M''ARTE` in SQL.
- **Image URLs pointing at the production bucket's `r2.dev` address**, `https://pub-a9ce13f98e72423eb72107a4e696f2e0.r2.dev/products/<sha256>.webp` — the same content-addressed keys `uploadImageFn` produces in `src/integrations/cloudflare-r2/media.mutations.ts`. `resolveAssetURL` moves them onto each environment's `VITE_R2_URL` when they are read, so preview loads them from `martebizuteria-preview`, which needs a copy of these objects; see [Image delivery](/docs/guides/image-delivery).

## What the seed catalog contains

Enough to exercise every storefront and admin surface, not a realistic inventory: seven Polish product categories (naszyjniki, kolczyki, chokery, bransoletki, bransoletki urodzeniowe, pierścionki, biżuteria z odciskami), three collections (Nowości, Srebro 925, Złoto 585), fifteen product attributes, two products (`lapis-lazuli-necklace` and `onyx-necklace`) with one variant each (`MRT-0001`, `MRT-0002`, 379,00 zł), 99 pieces of stock per variant, five product images, and the join rows that place both products in Naszyjniki, Nowości and Srebro 925 and give them their attribute values. Three delivery methods complete it.

Both products carry full Polish and English titles and long descriptions, which is what makes them useful for checking the locale switch on the product page.

## The local test database

The `test` environment's local database is where the seed files run as a whole, and the place to try a change to them:

```sh
bun run db:reset:test   # rm -rf .wrangler/test, then db:migrate:test, then db:seed:test
```

`db:migrate:test` applies every migration to an empty local D1 database in `.wrangler/test`. `db:seed:test` runs `scripts/seed-test.ts`, which:

1. reads the eleven seed files in the table order above;
2. adds the three E2E accounts from `e2e/data/accounts.ts` — `admin` (`admin@marte.example.test`), `adminWithoutTwoFactor` (`new-admin@marte.example.test`) and `customer` (`customer@marte.example.test`) — each with a verified e-mail and a credential account whose password is `TEST_PASSWORD`, hashed with Better Auth's `hashPassword`;
3. turns on two-factor authentication for `admin`, because the `test` build requires it of admins as production does: it sets `two_factor_enabled` and writes a `two_factor` row whose secret, `ADMIN_TOTP_SECRET`, and empty backup-code list are encrypted with Better Auth's `symmetricEncrypt` under the `AUTH_SECRET` read from `.env.test`, the key the test Worker decrypts them with. The E2E setup signs in with a code computed from the same secret. `adminWithoutTwoFactor` stays without it, for the specs about an admin who still has to set it up;
4. sets the customer's saved time zone to `Europe/Warsaw`;
5. writes all of it into one temporary SQL file, executes that file with a single `bun x wrangler d1 execute DB --env test --local --persist-to .wrangler/test --file <file>`, and deletes it.

Playwright's web server runs `db:reset:test` before a local E2E run, unless a server already answers on port 3000, which it reuses. In CI, every E2E job runs `db:reset:test` as a step — the pull-request job, the browser jobs of "E2E (full)" and its Stripe test-mode job — so a seed file that no longer fits the schema fails there.

## Seeding another new database

For any other genuinely empty D1 database, such as a new environment, apply the migrations with that environment's migrate script first, then run the eleven files in the table order above with `wrangler d1 execute`. `db:seed:preview` and `db:seed:production` chain exactly that with `&&`, one `--file` per seed, so you can copy the command and change the `--env` flag, but check twice which database you are pointing at first.

## Changing a seed file

If you do change one, keep it consistent with the current schema:

- Column lists must match the current table exactly; `bun run db:reset:test` fails on one that does not. A column added after a file was written takes its default, so check whether the seeded rows need a value: `product-variants.sql`, `product-images.sql` and the three join files were last changed in June, `inventory.sql` and `delivery-methods.sql` in October, and the others at the end of September.
- Keep the ids stable, or update every file that references them, and `e2e/data/catalog.ts`.
- Keep both locale keys in every `json_object`.
- No linter reads the SQL, and the unit and integration suites load only `delivery-methods.sql`, in the delivery-method descriptions migration test. What checks the seed files is `bun run db:reset:test` and the E2E specs that rely on the seeded catalog, so run both after a change.
- A changed seed file reaches only new databases. A database that already has the rows needs a migration as well: commit b77f58dd rewrote the delivery-method descriptions in `delivery-methods.sql` and added `20261010220000_delivery_method_descriptions.sql`, with its test, to update the existing rows.

## Adding test fixtures instead

For a test you almost never want a seed file. The integration tests build their own schema in memory:

```ts
const sqlite = new DatabaseSync(":memory:")
const database = drizzle(createTestD1Database(sqlite))

beforeAll(() => {
  sqlite.exec("create table search_entry (id integer primary key, label text not null, reference integer not null)")
})
```

`createTestD1Database` in `src/platform/testing/mocks/d1.ts` adapts Node's built-in `node:sqlite` to the `D1Database` interface, including `batch()` with a real transaction. `src/modules/_core/utils/__test__/search-conditions.integration.test.ts` is the model. When a test needs the real schema, `applyMigrationHistory(sqlite)` from `src/platform/testing/mocks/migrations.ts` builds it from the migration files, and the test inserts only the rows it needs; 58 integration suites work that way. See [Writing tests](/docs/guides/writing-tests) and [Testing a data migration](/docs/guides/database-migrations#testing-a-data-migration).
